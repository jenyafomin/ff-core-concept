## 1. Четыре недостающих механизма движка — конкретно

### 1.1 Backlink-rollup (фан-ин)

**Проблема.** `@ff/core` v1 хранит рёбра ВО ФРОНТМАТТЕРЕ ИСТОЧНИКА (`links: [{to, rel}]`).
Следствие: получить «кто ссылается на узел X» (backlinks, фан-ин) требует полного скана всех файлов.
На 500 входящих рёбрах (кейс GitHub: утилита с 500 импортами, N-043) это O(N-файлов) чтение при каждом запросе.
Это не только медленно — это **блокирует паспортную операцию «сослаться»**: вопрос «какие узлы задействованы в
клапане v1 (прямые входы)?» требует быстрого обратного поиска.

**Что нужно.**
Движок обязан поддерживать **backlink-index** — обратную карту `{target_id → [source_id, rel, edge_attrs]}`.

Контракт индекса (инвариант):
- Заполняется при ingestion и обновляется в той же транзакции записи, что и прямое ребро.
- Живёт как производная (derived), НЕ как истина-файл. Истина = прямые рёбра в md+frontmatter.
- При перестройке с нуля должен сходиться за O(E) (один проход по всем рёбрам).
- Инвалидируется атомарно: записать ребро → обновить backlink-index → commit.

**Уверенность: высокая.** Это стандартное требование любого графового хранилища.
Риск: если реализовать как eventually-consistent (кэш, не транзакция), v1-клапан (ADR-0002 §3) сломается —
при проверке «прямо задействованных нод» клапан видит неактуальный срез.

### 1.2 Section-index для широких контейнеров

**Проблема.** N-043 («огромные секции»): chat-thread с миллионом сообщений, папка с 2000 файлами.
Паспорт правильно решает это через stream-class (записи голые, наследуют от потока), но поток сам по себе
не даёт способ «прочитать эту секцию не вскрывая все записи».

Конкретные запросы, которые это блокирует:
- «Сколько сообщений в треде X?» (count без перечисления)
- «Какой последний seq в потоке Y?» (tail без полного скана)
- «Какие id входят в контейнер Z?» (membership query для клапана v1)
- «Покажи 20 сообщений вокруг N-043» (window query)

**Что нужно.**
Для каждого контейнера типа stream (и для широких folder-контейнеров) движок ведёт **section-index**:

```
section-index[container_id] = {
  count: int,
  tail_seq: int,          // последний seq среди дочерних рёбер
  min_created: iso,
  max_updated: iso,
  member_ids: [id, ...]   // только для узких контейнеров (< threshold); иначе lazy/pagination
}
```

Инвариант: section-index обновляется в той же транзакции, что и добавление/удаление дочернего узла.
Для stream (миллионы записей): `member_ids` НЕ хранится целиком — только `count`/`tail_seq`/временной диапазон.
Полный перебор членов — пагинированный cursor-запрос, не разовая загрузка в память.

**Уверенность: высокая.** Это прямое следствие N-043 и stream-class (SYNTHESIS-stress §2B).
Риск единственный: граница threshold (до какого count хранить member_ids в памяти). Предложение: 300 (вслед за
STATE.md «индекс после ~300 узлов»), настраивается.

### 1.3 Abstract-by-name для потоков

**Проблема.** Агент не может работать с потоком в 1 млн сообщений как с единицей — он тонет.
Задача: получить «суть потока» БЕЗ чтения всех записей, и БЕЗ вскрытия payload у каждой (инвариант I-1 ADR-0002).

Что «суть» в разных случаях:
- Для chat-stream: последние N сообщений + count + участники (из рёбер, не из payload)
- Для commit-stream / lineage: последний seq + временной диапазон + затронутые файлы (из рёбер `touches`)
- Для metric-stream: последнее значение + диапазон времен + unit (из type@version паспорта потока)

**Что нужно.**
Движок поддерживает **abstract-by-name** — конвенция паттерна поверх section-index:

```
PATTERN abstract-stream:
  input: stream_node_id, budget: int
  output:
    passport: stream.passport         // из паспорта потока (читается без payload)
    summary:
      count: section-index[stream].count
      seq_range: [min_seq, tail_seq]
      time_range: [min_created, max_updated]
      recent_ids: last N ids (cursor)   // только id, не payload записей
    edges_by_type: group рёбер потока по rel (без вскрытия payload участников)
```

Принцип: «абстракция по имени/источнику» = паспорт потока + агрегаты из section-index + сгруппированные рёбра.
Payload записей НЕ вскрывается. Это ПАТТЕРН-узел в control-plane (контракт = `compose(поток) → абстракт`).

**Уверенность: средняя-высокая.** Конкретная форма «абстракта» зависит от типа потока (chat vs metric vs commit)
и будет раскрыта в TYPE-узлах. Но контракт ПАТТЕРНА фиксирован: принимает stream_id, возвращает агрегат без payload.

### 1.4 Инвалидация кэша производных

**Проблема.** Движок выводит производные значения:
- `stale` (устарел ли узел)
- `canonical_id` (дедуп)
- `level?` дефолт-от-типа (при ingestion)
- backlink-rollup агрегаты
- section-index агрегаты
- рёбра `derived:true` (автоматические связи, `rule_ref`)
- функции-узлы (производные проекции файлов)

Файл = истина. Производные = read-only. Но «файл изменился» может инвалидировать цепочку производных
с неочевидными зависимостями: изменение ребра → обновить backlink-index + section-index + stale у
зависимых → возможно пересчитать `level?` у узлов с дефолтом-от-типа.

**Что нужно: явная модель зависимостей кэша.**

Правило derived read-only (инвариант, уже зафиксирован SYNTHESIS-stress §2C):
> Производный узел/ребро нельзя писать напрямую. Запись идёт в файл-истину; движок пересчитывает производное.

Граф инвалидации (дизайн-контракт):

```
Изменение → Что инвалидируется
─────────────────────────────────────────────────────────────
Паспортное поле узла X       → stale у X; derived-рёбра из X; агрегаты секций X
Ребро (добавл./удал.)        → backlink-index[target]; section-index[home-container]; cascade-кэш дочерних
type@version у узла X        → level?-дефолт у X (пересчёт при инджестии); валидатор-кэш типа X
Удаление узла X              → backlink-index[X]; home-ребро у дочерних (re-home); section-index[parent X]
Изменение TYPE-узла          → cache всех узлов этого типа (ленивый пересчёт, не eager)
```

Режим инвалидации: **транзакционный** для структурных инвариантов (ровно один home, section-index count),
**lazy** для семантических производных (stale, level?-дефолт пересчитывается при следующем чтении, не при записи).

**Уверенность: средняя.** Конкретные правила для derived-рёбер (какой rule_ref инвалидируется при каком изменении)
требуют инвентаря всех rule_ref в системе — он растёт с модулями. Контракт выше задаёт структуру, конкретные
правила наполняются при реализации TYPE- и PATTERN-узлов.

## 2. Правило стоимости: что достойно узла

SYNTHESIS-stress §4 дал правило из 3 условий. Разбираю каждое с данными.

### Правило (три условия, все три обязательны)

**Вещь = узел ⟺ (a) стабильный id при правках + (b) своя принадлежность (свой home осмыслен) + (c) ценность как ЕДИНИЦА запроса.**

**Анализ по классам:**

| Класс | (a) стабильный id | (b) свой home | (c) ед. запроса | Вердикт |
|---|---|---|---|---|
| Файл | да (ULID, ≠ путь) | да (folder) | да (код/SPEC) | **УЗЕЛ** |
| Папка / контейнер | да | да (родитель) | да (scope) | **УЗЕЛ** |
| Коммит | да (SHA стабилен) | да (lineage) | да (история) | **УЗЕЛ** |
| Сообщение чата | да (ULID) | да (stream) | НЕТ как единица (1 из млн) | STREAM-ЗАПИСЬ (почти-голая) |
| Строка кода | нет (смещение меняется при редакте) | нет | нет | **НЕ УЗЕЛ** |
| Call-site | нет (меняется при рефакторинге) | нет | нет | **НЕ УЗЕЛ** |
| Транзитивная зависимость | нет (пересчитывается) | нет | нет | **НЕ УЗЕЛ** |
| Функция | нет (имя нестабильно при переим.) | нет (home = файл, но функция = projection) | да (L2 запрос) | ПРОИЗВОДНАЯ, ленивая |
| Метрика-запись | да (ULID или timestamp) | да (metric-stream) | НЕТ как единица | STREAM-ЗАПИСЬ |
| TYPE-узел | да | да (реестр) | да (контракт валидации) | **УЗЕЛ (control-plane)** |
| Ребро `depends-on` | нет (производное) | нет | нет | **РЕБРО, не узел** |
| Трейс-событие | да (ULID) | да (agent) | да (аудит клапана) | **УЗЕЛ (движок пишет)** |

**Что «не узел» делать?**
- Строки кода, call-sites, транзитивные зависимости → **не хранить**, пересчитывать при запросе.
- Функции → **производный ПАТТЕРН** (по запросу извлекается из файла, кэшируется, `derived:true`, НЕ истина-файл).
- Сообщения/метрики → stream-записи (паспорт без большинства обязательных полей наследуется от потока по home).

### Правило порогов

Дополнительная проверка для граничных случаев (когда условия (a)/(b)/(c) неочевидны):

> **«Функция потребует мигрировать все узлы при изменении — это узел; функция потребует пересчитать производную — это не узел».**

Практически: если «добавить ребро от X к Y» требует читать/писать Z — Z должен быть узлом.
Если «изменить Z» безопасно потому что Z пересчитывается — Z не должен быть узлом.

## 3. Дополнительные инварианты движка (не новые, но не зафиксированы явно)

Из SYNTHESIS-stress §2C — три инварианта записать в контракт движка:

**I-A. Клапан = движок, агент не одобряет сам себя.**
> Перед любым необратимым внешним действием движок проверяет epistemic/sensitivity/principal прямо задействованных нод.
> Агент, инициирующий действие, НИКОГДА не может быть авторизатором клапана для той же операции.
> (Иначе возвращается дыра «автор = одобряющий», закрытая в ADR-0002 §3.)
> Enforcement: `actor(initiator) ≠ actor(approver)` проверяется движком, не самим агентом.

**I-B. Производные узлы/рёбра — read-only.**
> Ребро или узел с `derived:true` (и любой агрегат section-index, backlink-index, stale, canonical_id)
> не принимает прямую запись. Запись идёт в файл-истину; движок пересчитывает производное.
> Попытка прямой записи в производный узел → ошибка валидации, не тихий успех.

**I-C. Multi-schema реестр: `schema` = единственный ключ валидатора.**
> Поле `schema` (`type@version`) в паспорте однозначно выбирает валидатор. Никакого ветвления по payload.
> Если «один тип с разными схемами» — это разные записи `type@version` в реестре TYPE-узлов, не runtime-if.
> Нарушение: `schema` указывает на TYPE-узел, который читает payload для выбора под-схемы — запрещено.

**I-D. Контейнер home ≠ категория для тех же членов.**
> Один узел не может быть одновременно `home`-родителем и узлом `facet-of`-категории для одной и той же
> дочерней ноды. Причина: при re-home (перемещение узла) home-ребро перевешивается, а facet-ребра выживают —
> если они разные узлы, нет конфликта; если один и тот же узел был home И facet — перемещение молча теряет
> ярлык (именно это обсуждается в Q3/N-086).
> Движок проверяет: записать ребро с `home:true` к узлу X нельзя, если X уже несёт `facet-of`-ребро от той же ноды.

## 4. Split maxDepth: два параметра вместо одного

Стресс-тест выявил: текущий `maxDepth` делает два несовместимых дела.

**Проблема.** `maxDepth=3` одновременно:
1. Защищает от бесконечного обхода при циклах в ссылочных рёбрах (cycle guard)
2. Ограничивает глубину легального каскада (cascade depth)

Для кода нужна cascade depth ~6-8 (folder → package → module → file → namespace → function).
Для цикл-гарда нужен «первый визит выигрывает» (revisit → стоп), не «глубина N → стоп».

**Решение: два независимых параметра.**

```
cycle_guard:    "first-visit-wins"   // при обходе: повторный визит узла = стоп (НЕ счётчик)
cascade_depth:  int (default 8)      // максимальная легальная глубина каскада home-спины
```

`cycle_guard` применяется к ССЫЛОЧНЫМ рёбрам (calls/imports/depends-on — они могут циклиться).
`cascade_depth` применяется к HOME-СПИНЕ (она ациклична по построению — один home на узел — но может быть глубокой).

Инвариант: home-спина образует лес (ADR-0002 §2а). Поэтому `cycle_guard` на home-спине избыточен;
`cascade_depth` на ссылочных рёбрах осмысленно только как «бюджет запроса», не как safety guard.

**Уверенность: высокая.** Разделение хорошо мотивировано данными.

## 5. Терминатор ПАТТЕРНА: prune | mark-cycle

Для рекурсивных паттернов (обход графа вызовов, зависимостей) ПАТТЕРН-узел несёт поле `recursion_terminator`.

Два режима:

```
prune:      при повторном визите узла — обрезать ветку (не включать в вывод, молча)
mark-cycle: при повторном визите — включить узел в вывод с меткой {cycle:true, via: [path]}
```

**Когда prune:** cascading (нужен результат без петель, точность не критична).
**Когда mark-cycle:** анализ зависимостей (нужно ПОКАЗАТЬ цикл, это и есть искомый результат).

Контракт ПАТТЕРНА (расширяет ADR-0002 §Decision 4):
```
PATTERN = {
  compose(subgraphs) → subgraph,
  recursion_terminator: "prune" | "mark-cycle",
  maxDepth: int (для cascade_depth, не cycle_guard)
}
```

**Уверенность: высокая.** Это стандартный контракт для graph traversal.

## 6. Level ≠ центральность (уточнение, не пересмотр)

Из стресс-теста §2A: ядровая утилита с 500 импортами (высокая центральность) при этом «низкого» уровня
(L2-функция, глубоко в стеке). Это НЕ противоречие — это две разные ЛИНЗЫ:

| Что считаем | Как считаем | По каким рёбрам |
|---|---|---|
| `level` (абстракция) | ярус от корня по home-спине | home-рёбра (cascade spine) |
| Центральность / фан-ин | count входящих ссылочных рёбер | calls/imports/depends-on (НЕ home) |

Движок не должен смешивать их. Линза-level использует home-спину; линза-centrality использует ссылочный граф.
Если агент запрашивает «важные узлы» без уточнения — нужно явно выбрать ЛИНЗУ, иначе ответ неопределён.

Это уточнение к ADR-0002 §1 (level = ось линзы) — не пересмотр, но важная точность.

**Уверенность: высокая.**

## 7. Что НЕ вошло в этот разбор (честно)

- Реактивность / реактор: вне рамок (ждёт D1/topic-4 + ADR-0003). Движок описывает только
  синхронные запросы и транзакции записи, не подписки/triggers.
- Полная спека ADR-0003 (ABAC, trust horizon, first-party-only gate): отдельный ADR.
- Физическая реализация индексов (B-tree? SQLite? custom?): отложено до ~300 узлов (STATE.md).
  Здесь — контракты и инварианты, не реализация.
- Stream-записи конкретный формат: часть модуля stream-class (T6), не T3.

## ВОПРОСЫ-ДЛЯ-ОБСУЖДЕНИЯ (с провенансом)

**Q1 — Граница section-index: когда хранить member_ids целиком, когда cursor?**
- Откуда: §1.2 (section-index для широких контейнеров) + STATE.md «~300 узлов» порог.
- Почему важно: разная стоимость запросов клапана v1 (нужен быстрый набор прямых входов)
  и масштабных потоков (нельзя всё в RAM). Если порог слишком высокий — кэш ест память;
  слишком низкий — деградация клапана.
- Кому: агент (архитектор/билдер), не владелец. Предложение: 300, настраивается.
- Уверенность оценки порога: низкая.

**Q2 — Lazy vs eager пересчёт `level?`-дефолта при изменении TYPE-узла.**
- Откуда: §1.4 (инвалидация кэша) + ADR-0002 §1 (дефолт выводится при инджестии).
- Почему важно: если TYPE-узел меняется (например, меняется дефолтный `level` для типа `task`),
  нужно ли немедленно обновить все существующие `task`-узлы? Eager = дорого (полный скан),
  lazy = временная несогласованность между паспортом и ожиданием TYPE-узла.
- Кому: агент-архитектор. Предложение: lazy с явной инвалидацией-меткой `level?_stale:true`
  на уровне агрегата типа, не на уровне каждого узла.
- Уверенность: средняя.

**Q3 — Терминатор ПАТТЕРНА по умолчанию: prune или mark-cycle?**
- Откуда: §5 (prune | mark-cycle).
- Почему важно: ошибка по умолчанию в разные стороны: prune прячет реальные циклы (агент
  думает, что зависимостей нет); mark-cycle раздувает ответ (агент тонет в метках).
- Кому: агент-архитектор + позже владелец (если это затрагивает UX агентов).
