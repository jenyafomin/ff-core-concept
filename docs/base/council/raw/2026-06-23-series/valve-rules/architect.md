# RULES / PERMISSIONS layer — клапан как слой политик-узлов, который енфорсит движок

- **Тема:** T1 + Q10 — клапан как слой rules/permissions (модель Claude Code: allow/deny/ask + rules) как УЗЛЫ-политики, которые ЕНФОРСИТ движок. Как автономное действие агента (Q10/N-088) разрешается/ограничивается; гранулярность per-stage/per-cell (N-071); «агент не одобряет сам себя». Глаголы `requestExternalAction`/`requestPromotion` в этой рамке.
- **Роль:** system-architect (структурное мышление: границы, контракты, потоки данных, design patterns).
- **Дата:** 2026-06-23
- **Status:** raw (design sketch + вопросы; НЕ финальная спека). Фаза = ДИЗАЙН, без кода, без «строй».
- **Grounds on:** ADR-0002 §3 (клапан = политика движка, дефолт-закрыто, автор≠авторизатор, ГРАНИЦА v1), ADR-0002 §4 (control-plane = 3 рода; ПОЛИТИКА = класс ЛИНЗЫ hard-ABAC), ADR-0002 §Risks R4 (first-party-only gate), N-071 (гранулярное одобрение в модуле агентов, per-stage/per-cell), N-088 (rules/permissions как у Claude Code; движок енфорсит; агент не одобряет сам себя), SYNTHESIS-verbs §3/§5 (реактивность, topic-4 = ворота, принципал автономного действия), SYNTHESIS-stress §2C (клапан=движок; derived read-only). Reference: модель прав Claude Code (allow/ask/deny; deny>allow; слои managed→user→project).

---

## 0. Дисциплина, которую держу (чтобы эскиз не поплыл)

Эта задача — самая опасная для тонкого паспорта, потому что «права» интуитивно тянет добавить поле в ноду (`acl`, `owner`, `editable`). Держу три инварианта ADR-0002 и один из N-088:

- **I-1 (несущесть):** право доступа НЕ становится полем паспорта сверх уже несущих `sensitivity`/`principal`/`epistemic`. Решение «можно ли действие» движок принимает из УЗЛОВ-ПОЛИТИК + несущих осей паспорта задействованных нод — не вскрывая payload. Политика — это control-plane-данные, не поле ячейки.
- **I-2 (принадлежность⟂ссылка):** политика применяется к нодам через **scope** (= ребро/контейнер/тип), а не как собственность на ноде. «Эта политика покрывает этот подграф» — это `applies-to`-ребро, не поле.
- **I-3 (схема решает из паспорта):** какую политику применять, движок выбирает из ОСЕЙ паспорта (`type`/`sensitivity`/`principal`/`epistemic`) + контекста действия (verb, stage, connector), НИКОГДА не вскрывая payload.
- **I-N088 (движок енфорсит, агент не одобряет себя):** правило = данные (узел-политика); решение allow/deny/ask = ДВИЖОК; агент-актор не может быть авторизатором собственного действия. Это не «совет» агенту — это перехват на enforce-point движка, который агент не может обойти.

Где маппинг напрягает инвариант — флагаю в §7, не гну молча.

## 1. Рефрейм: что такое «клапан» структурно (паттерн)

Клапан в ADR-0002 §3 описан как ОДНА проверка перед необратимым внешним действием. N-071 и N-088 расширяют его в **слой**: гранулярные правила (per-stage/per-cell), модель Claude Code (allow/ask/deny + rules), автономное действие разрешено-но-ограничено.

**Паттерн, который сюда ложится точно: Policy Decision Point / Policy Enforcement Point (PDP/PEP) поверх ABAC, плюс Claude-Code-овская реляция трёх вердиктов с приоритетом deny.**

- **PEP (Policy Enforcement Point)** — место в движке, где перехватывается действие. Их немного и они фиксированы (см. §3 enforce-points). Агент физически проходит через PEP — не может его обойти, потому что вызывает действие через ГЛАГОЛ движка, а не напрямую коннектор.
- **PDP (Policy Decision Point)** — чистая функция движка: `decide(action-context, задействованные-ноды, применимые-политики) → allow | ask | deny (+reason, +trace)`. Без побочных эффектов; её решение енфорсит PEP.
- **PAP (Policy Administration Point)** — это сам граф: политики = УЗЛЫ (создаются/версионируются как данные, «control-plane = узлы», Принцип 0). Редактировать политику = редактировать узел (с собственным клапаном на это редактирование — рекурсия закрывается в §6).
- **PIP (Policy Information Point)** — паспорта задействованных нод (`sensitivity`/`epistemic`/`principal`/`source`) + коннектор (`capabilities`) + контекст актора (`principal`, `skill-manifest`, `stage`). Всё уже несущее, читается без payload.

**Почему этот паттерн, а не альтернативы** (трейд-офф в §5): он отделяет ПРАВИЛО (данные, меняемо без кода — N-088 «как Claude») от ЕНФОРСМЕНТА (движок, агент не обходит — I-N088) от ТОЧЕК ПЕРЕХВАТА (фиксированный узкий набор — узкая поверхность, аудируемо). Ровно три вещи, которые owner назвал, раскладываются на три роли PDP/PEP/PAP. Уверенность: высокая (это каноничный паттерн для «autonomous-but-gated»).

## 2. Модель правила = УЗЕЛ-ПОЛИТИКА (rule node) — контракт

Правило — узел control-plane класса ЛИНЗА hard-ABAC (ADR-0002 §4: ПОЛИТИКА = класс линзы, не 4-й род). Паспорт у него обычный; «политичность» — в его типе и payload-контракте. Контракт (payload-схема `rule@1`):

```
rule (узел; type=rule; epistemic=fact; source=human|system; sensitivity:internal;
      principal=<кто владелец правила>)
{
  effect:        allow | ask | deny              # три вердикта Claude Code
  enforce_point: promotion | valve | disclosure | edit   # ГДЕ перехват (§3)
  match: {                                        # КОГДА правило применимо (предикат над осями паспорта + контекстом)
    verb?:        requestExternalAction | requestPromotion | editNode | setLifecycle | ...
    connector?:   <connector-id> | *             # для valve: какой наружу-канал
    capability?:  read | edit | send             # какое наружу-действие
    node_match?:  { type?, sensitivity?, epistemic?, level?, principal?, facet-of? }  # ОСИ ПАСПОРТА, не payload
    actor_match?: { principal?, has-skill?, actor_class? human|verifier-agent|agent|3rd-party }
    stage?:       <stage-id>                      # per-stage (N-071): на каком шаге процесса агента
  }
  priority?:     int                              # тай-брейк внутри одного effect-класса (реже нужен — см. §4)
  reason?:       string                           # для трейса/эскалации
}
applies-to → <type | scope | container | конкретная-нода>   # РЕБРО: куда распространяется (I-2, не поле)
```

**Ключевые свойства (и чем держат инварианты):**
- `match` — предикат ТОЛЬКО над несущими осями паспорта и контекстом действия (I-3). Нельзя матчить по значению внутри payload (это вернуло бы «вскрой payload, чтобы решить право»). Если кто-то хочет «правило по содержимому» — содержимое сначала поднимается в ось (тип/facet/sensitivity), потом матчится. Уверенность: высокая, это прямой I-1/I-3.
- `applies-to` — РЕБРО к scope/типу/контейнеру/ноде (I-2). Покрытие политики = подграф, достижимый по этому ребру + каскад по home-спине. Это даёт **per-cell** (applies-to конкретной ноды) И **per-container/type** (applies-to scope) одним механизмом — отвечает N-071 «per-stage/per-cell» гранулярности без нового рода.
- `enforce_point` — связывает правило с фиксированной точкой движка (§3). Правило без валидного enforce_point не регистрируется (движок отклоняет — иначе «мёртвое» правило).
- **first-party-only gate (ADR-0002 R4):** регистрация узла-`rule` с `enforce_point ∈ {promotion, valve}` — только first-party principal. Сторонний код может регистрировать только `disclosure`-правила и soft-perception-линзы, НЕ valve/promotion. Это структурный gate, проверяемый при ЗАПИСИ rule-узла (сам по себе — правило на enforce_point=edit над типом `rule`; см. рекурсию §6).

## 3. Enforce-points (PEP) — фиксированный узкий набор точек перехвата

Это границы модуля. Их мало и они стабильны (узкая поверхность = аудируемость, ADR-0002 §4 уже назвал три; добавляю `edit` явно, т.к. N-071 «документы без одобрения не редактировать»):

| enforce_point | что перехватывает | дефолт (без правил) | чем закрывает запрос owner |
|---|---|---|---|
| **valve** | необратимое ВНЕШНЕЕ действие через коннектор с `capability: send\|edit` (отправить TG, письмо, оплатить, изменить внешний файл) | **deny** (дефолт-закрыто, ADR-0002 §3) | Q10/topic-4: автономное действие во-вне РАЗРЕШЕНО только если есть allow-правило; иначе ask/deny |
| **promotion** | подъём `epistemic` (особенно `hypothesis→fact`) | по лестнице доверия ADR-0002 §3 (автор≠авторизатор) | requestPromotion; «агент не одобряет сам себя» |
| **disclosure** | что линза раскрывает наружу/другому принципалу (id\|title\|payload) | по `sensitivity` ноды (приватное не утекает) | приватность; композиты (§7 Q-D5) |
| **edit** | мутация ноды (editNode/setLifecycle) | **allow** для first-party автора своей ноды; **ask/deny** настраиваемо per-cell/per-type | N-071 «какие документы без одобрения не редактировать» (per-cell edit-policy) |

**Принципиально:** PEP — это места В ДВИЖКЕ, где проходит ЛЮБОЙ путь к соответствующему действию. Агент вызывает действие глаголом (`requestExternalAction` → проходит valve-PEP; `editNode` → edit-PEP; `requestPromotion` → promotion-PEP). Нет «прямого» пути в обход (агент не держит сокет к Telegram — он держит глагол движка). Это и есть «движок енфорсит» (I-N088). Уверенность: высокая по структуре; конкретный список коннекторов/capabilities — средняя (зависит от ADR-0003).

**Дефолты по enforce_point различны и это намеренно:** valve дефолт-deny (необратимо вовне — консервативно), edit дефолт-allow для своего автора (иначе система неюзабельна — каждая запись ждёт апрува). Это прямая калька Claude Code: read-операции преаппрувнуты, опасные (Bash/send) — ask/deny.

## 4. PDP — алгоритм решения (точная калька Claude Code: deny > allow, слои)

Движок при перехвате на PEP вызывает чистую функцию. Алгоритм (детерминированный, по образцу Claude Code «deny takes precedence»):

```
decide(action_ctx, involved_nodes, applicable_rules) -> {effect, reason, trace}:
  1. involved_nodes := ГРАНИЦА действия (ADR-0002 §3 v1: ТОЛЬКО прямо задействованные —
       явные входы глагола + явно процитированные по id; НЕ транзитивное замыкание).
  2. applicable_rules := все rule-узлы, чей applies-to покрывает action_ctx.scope/type/cell
       И чей match(action_ctx, involved_nodes) истинен.  (PIP читает оси паспорта, не payload.)
  3. Разрешение конфликта (ТОЧНО как Claude Code):
       a. если ∃ применимое правило effect=deny  → DENY        (deny побеждает всё)
       b. иначе если ∃ применимое правило effect=ask → ASK     (эскалация человеку)
       c. иначе если ∃ применимое правило effect=allow → ALLOW
       d. иначе → ДЕФОЛТ ENFORCE_POINT (valve=deny, promotion=по-лестнице, edit=allow-своему, disclosure=по-sensitivity)
  4. ДОПОЛНИТЕЛЬНЫЕ жёсткие инварианты (не переопределяемые правилами — «конституция клапана»):
       - promotion: actor ≠ author НИКОГДА (даже при allow-правиле) — разделение обязанностей сильнее правила.
       - valve: если хоть одна ПРЯМО задействованная нода epistemic≠fact → не ниже ASK (allow не может опустить).
       - disclosure: sensitivity:private наружу — не ниже ASK независимо от правил (композиты §7).
  5. trace-узел: {actor, verb, enforce_point, involved[], matched_rules[], effect, reason, ts} — наблюдаемость.
```

**Два уровня — это сердце дизайна:**
- **Слой ПРАВИЛ (шаг 3)** — настраиваемый данными, «как Claude Code»: owner пишет allow/ask/deny узлы, deny побеждает. Гибкость, меняется без кода (N-088).
- **Слой КОНСТИТУЦИИ (шаг 4)** — жёсткие инварианты, которые правило НЕ может ослабить (автор≠авторизатор; не-fact→не вовне; private→не молча наружу). Это защита от «сторонний код написал себе allow-правило» (R4) и от «агент одобрил сам себя».

**Почему конституция отдельно от правил (трейд-офф):** если ВСЁ — настраиваемые правила, то достаточно одного вредного allow-узла, чтобы открыть клапан (ровно атака R4). Поэтому несколько инвариантов вынесены ВЫШЕ слоя правил — их нельзя переопределить allow-правилом, только сменой кода движка (R4-класс изменения, требует security review). Уверенность: высокая — это прямой ответ на названную в ADR-0002 дыру R4.

**Приоритет/слои (как managed→user→project в Claude Code):** правила имеют `principal`-владельца; first-party-owner-правила сильнее, чем 3rd-party. Но порядок слоёв НЕ переопределяет конституцию (шаг 4) и НЕ переопределяет deny (deny на любом слое побеждает). `priority` — тай-брейк только ВНУТРИ одного effect-класса на одном слое (редкий случай; чаще достаточно deny>ask>allow).

## 5. Автономное действие (Q10/N-088): как разрешается/ограничивается

Owner (N-088): автономное действие РАЗРЕШЕНО, ограничено rules-слоем, движок енфорсит. Раскладка через модель:

**Реактор (утренний триггер, SYNTHESIS-verbs §3) проходит ТЕ ЖЕ PEP, но без синхронного вызывающего.** Три проблемы, которые критик назвал нерешёнными (принципал / граница / клапан-для-автономного), решаются так:

1. **Принципал автономного действия.** Реактор действует от имени **autonomous-principal** — отдельная тонкая `principal`-идентичность (не человек-owner, не обычный агент). Правила могут адресно матчить `actor_match.principal = autonomous` → owner задаёт ОТДЕЛЬНЫЕ (строже) правила для автономных действий, чем для синхронных. Это и есть «где-то реагирует сам, где-то запрашивает» (N-071) — выражено как разные allow/ask по `actor_match.actor_class` × `stage`.
2. **Граница для действия без вызывающего.** У синхронного действия `involved_nodes` = входы глагола вызывающего. У реактора вызывающего нет → `involved_nodes` = (а) ноды, на которых сработал предикат триггера (явные входы условия) + (б) ноды, переданные в шаблон действия. Та же v1-граница (прямо задействованные), просто «прямо задействованные» определяются триггером, не агентом. Транзитив — по-прежнему ADR-0003.
3. **Дефолт строже для автономного.** Конституция (шаг 4) для autonomous-principal ужесточается: дефолт valve для autonomous = **ask** даже там, где для синхронного first-party был бы allow — пока owner явно не написал allow-правило для конкретного (connector × capability × stage). Это «autonomy с предохранителем»: можно сделать самому, НО клапан по умолчанию эскалирует, и owner один раз пишет правило «по утрам слать сводку в МОЙ TG — allow», после чего тихо.

**Гранулярность per-stage/per-cell (N-071) выражена без нового механизма:**
- **per-stage** = `match.stage` (на шаге «черновик» — allow редактировать; на шаге «отправка» — ask).
- **per-cell** = `applies-to` конкретной ноды + `match.node_match` (этот документ — deny edit без апрува; этот тип — ask на send).

Уверенность: модель — высокая; пороги/дефолты autonomous — средняя (настраиваются узлами, финал в ADR-0003).

## 6. Глаголы в этой рамке + рекурсия «кто правит правила»

**`requestExternalAction(connector, capability, payload, involved[])`** — единственный путь во-вне. Всегда проходит **valve-PEP**. Имя `request*` точное: агент НЕ выполняет, он ЗАПРАШИВАЕТ у движка; движok прогоняет PDP; allow→исполнить через коннектор; ask→эскалация owner (+ опц. dry-run/симуляция, SYNTHESIS-verbs §3); deny→отказ+trace. Агент никогда не держит сокет наружу — только глагол. Это структурно делает «агент не одобряет сам себя» неизбежным: одобряет PDP движка, не агент.

**`requestPromotion(node, to_epistemic)`** — проходит **promotion-PEP**. Конституция (шаг 4): actor≠author всегда; `hypothesis→fact` только human|verifier-agent с capability. `request*` снова точно: агент просит повышения, авторизует другой субъект.

**Рекурсия (кто правит сами правила) — закрыта так:** узел-`rule` — обычная нода; её редактирование проходит **edit-PEP**. Над типом `rule` стоит мета-правило (конституция): «edit узла type=rule с enforce_point∈{valve,promotion} → first-party-only; 3rd-party → deny». Это не бесконечная регрессия: мета-правило для `rule`-узлов — часть КОНСТИТУЦИИ (код движка, шаг 4), не data-правило. Так слой правил гибок (data), но «правила-о-правилах безопасности» прибиты к движку (R4-защита). Уверенность: высокая — без этого слой rules самоподрывается.

## 7. Скептицизм — где напрягает, ПРУФЫ, и где честно НЕ решено

**ПРУФЫ (модель держит):**
- **0 новых обязательных полей паспорта.** Весь слой — узлы-`rule` (control-plane) + рёбра `applies-to` + фиксированные PEP в движке. `sensitivity`/`principal`/`epistemic` (уже несущие) = PIP. Паспорт не толстеет — сложность ушла в control-plane + движок, ровно по дисциплине задачи.
- **Калька Claude Code точна и проверена в реальном продукте:** allow/ask/deny + deny>allow + слои + дефолты-по-инструменту — это рабочая модель прав CC (подтверждено docs). owner назвал именно её (N-088) — маппинг 1:1, не изобретение.
- **«Агент не одобряет сам себя» структурно неизбежно**, а не дисциплинарно: агент проходит через PEP движка, решает PDP, конституция (шаг 4) ставит actor≠author выше любого data-правила.
- **Гранулярность per-stage/per-cell** выражена без нового рода: `match.stage` + `applies-to`-ребро. N-071 закрыт механизмом, который уже есть.

**ИЗЪЯНЫ / напряжения (честно):**
- **Конституция vs «control-plane = всё узлы».** Принцип 0 говорит «всё видно ИИ и всё — узлы». Но я вынес часть инвариантов (шаг 4) в КОД движка, не в узлы — иначе R4-атака (сторонний allow-узел открывает клапан). Это сознательное нарушение «всё — узлы» ради безопасности: «правила гибкие — данные; правила-о-безопасности-правил — код». Owner должен это принять явно (Q-T1-1).
- **Граница v1 (прямо задействованные) для реактора слабее, чем для синхронного.** У синхронного агент явно передаёт входы; у реактора «прямо задействованные» определяет предикат триггера — легче случайно зацепить лишнее/упустить нужное. Транзитивный trust-horizon отложен в ADR-0003, но для АВТОНОМНОГО действия отсутствие горизонта острее (некому переспросить в момент). Флаг в ADR-0003.
- **`priority` на правилах — риск God-реестра** (SYNTHESIS-verbs §4: когда правил 200, какое сработало — снова задача поиска). Митигация: предпочитать deny>ask>allow (не нуждается в priority) + трейс показывает `matched_rules[]` (объяснимость, почему это решение). Но при росте — нужна навигация по реестру правил (= «карта», та же проблема, что у линз).
- **Композиты (D5/Q-D5) НЕ решены этим слоем.** disclosure-PEP ловит ОДНУ ноду по sensitivity; но композит из 5 приватных входов → один «безопасный» выход проходит, а атака вывода (4 известных → 5-й) — нет. Конституция шаг 4 (private→не ниже ask) смягчает, но не решает inference-атаку. Явно отложить в ADR-0003 (бюджеты раскрытия/шум). Не подавать как решённое.
- **Stage как ось матчинга** требует, чтобы «stage» где-то жил. ADR-0002 §5 вынес `stage`→движок (производное). Если правила матчат по stage, stage должен быть НАБЛЮДАЕМ движком в момент действия — это контракт между модулем-агентов (он знает шаг процесса) и движком (он енфорсит). Граница между ними — открытый дизайн (Q-T1-3).

## ВОПРОСЫ-ДЛЯ-ОБСУЖДЕНИЯ (с провенансом)

Формат: **вопрос · откуда · почему важно · кому.**

1. **Q-T1-1 — Принять, что «конституция клапана» (autor≠авторизатор; не-fact→не вовне; private→не молча наружу; valve/promotion-rule = first-party-only) живёт в КОДЕ движка, а не как переопределяемые узлы-правила?**
   *Откуда:* §4 шаг 4 + §6 рекурсия vs Принцип 0 «control-plane = всё узлы» (ADR-0002 §4 R4).
   *Почему важно:* это сознательное исключение из «всё — узлы». Без него один вредный allow-узел открывает клапан (атака R4). С ним — часть control-plane не редактируема как данные (нужен code-change R4 + security review). Это фундаментальная граница «гибкое vs прибитое».
   *Кому:* **владельцу** (это политическое решение о границе доверия, не механика).

2. **Q-T1-2 — Дефолт valve для autonomous-principal = `ask` (а не `allow`), пока owner явно не написал allow-правило на конкретный connector×capability×stage?**
   *Откуда:* §5 (autonomy с предохранителем) ← N-088 «действовать самому, но с rules» + N-071 «где-то сам, где-то запрашивает».
   *Почему важно:* задаёт «скорость клапана» для автономных действий — это прямо тот вопрос из STATE «облегчение или тревога, когда агент сделал без тебя». Дефолт-ask = безопасно-но-надоедливо на старте; дефолт-allow = быстро-но-страшно. Один раз настроив правила, owner уходит в тишину.
   *Кому:* **владельцу** (его толерантность к необратимости — субъективна, N-071 прямо назвал это «субъективным моментом»).

3. **Q-T1-3 — Где живёт `stage` и как движок видит его в момент действия (контракт модуль-агентов → движок)?**
   *Откуда:* §3/§7 (per-stage матчинг) vs ADR-0002 §5 (`stage`→движок, производное) + N-071 (per-stage одобрение в модуле агентов).
   *Почему важно:* правила матчат по stage, значит stage обязан быть наблюдаем движком при перехвате. Но N-071 положил «одобрение» в модуль агентов. Если stage живёт в агент-модуле, а енфорс — в движке, нужен явный контракт передачи stage в action-context. Иначе per-stage гранулярность не исполнима.
   *Кому:* **агенту** (это контракт между двумя модулями; механика, не политика).

4. **Q-T1-4 — Реестр правил при росте: навигация/«карта правил» — отдельная линза, или предпочитаем deny>ask>allow без `priority` и живём на трейсе?**
   *Откуда:* §7 (риск God-реестра) ← SYNTHESIS-verbs §4 (God-реестр линз, «карта»).
   *Почему важно:* при 200 правилах «какое сработало и почему» — снова задача поиска. Если выбираем priority-механику — нужна навигация; если жёстко deny>ask>allow + трейс — проще, но возможны «непредвиденные deny». Влияет на объяснимость (N-040 «объяснимая система»).
   *Кому:* **агенту** (later round; механика реестра).

5. **Q-T1-5 — Граница клапана для АВТОНОМНОГО действия: достаточно ли v1 «прямо задействованные» (входы предиката триггера + шаблон), или автономному нужен НЕМЕДЛЕННО хотя бы 1-хоп trust-horizon (раньше, чем общий ADR-0003)?**
   *Откуда:* §5/§7 ← ADR-0002 §3 (trust horizon → ADR-0003) + SYNTHESIS-verbs §3 (клапан-для-автономного не спроектирован).
   *Почему важно:* у синхронного действия человек рядом и может переспросить; у автономного — нет. v1-граница, безопасная для синхронного, может пропустить «не-fact в одном хопе» для автономного. Возможно, автономному нужен более строгий горизонт РАНЬШЕ остального ADR-0003.
   *Кому:* **владельцу** (риск-аппетит) + **агенту** (механика горизонта в ADR-0003).

6. **Q-T1-6 — Род КОННЕКТОРА и его регистрация: подтвердить, что connector с `capability: send|edit` = first-party-only (как valve/promotion-rule), а read-коннекторы — открыты сторонним?**
   *Откуда:* §2/§3 ← SYNTHESIS-verbs §1 (коннектор = первый наружу-смотрящий, род по безопасности в ADR-0003) + ADR-0002 R4.
   *Почему важно:* коннектор, умеющий `send`, — это де-факто часть клапана (он и есть «наружу»). Если сторонний код регистрирует send-коннектор, он обходит first-party-gate с другой стороны. Симметрично R4: writing-наружу регистрируется только first-party.
   *Кому:* **владельцу** (граница маркетплейса/доверия) → формализуется в **ADR-0003**.
