# Движок / ADR-0004 (направление 3) — стоячий риск №1

> 2 агента: архитектор + критик. Фаза = DESIGN. Это слой, на котором условно держится изящество всей модели.

## Сквозной вывод (оба агента сошлись)
**Движок = CQRS над файлами-истиной + материализованный индекс.** Файлы (.md+frontmatter) = модель записи / ИСТИНА;
движок = производная, одноразовая, ПЕРЕСОБИРАЕМАЯ модель чтения. Это разрешает риск №1: истина в файлах (git/портативность),
скорость в индексе. Закон всего движка: **разделять обход ХРЕБТА (home, ацикличный, каскад) и обход ССЫЛОК (любой граф,
данные)** — слияние = баг.

**🔴 Самый важный нерешённый вопрос (выше всего остального): движок = БИБЛИОТЕКА в процессе агента или СЕРВИС?** Если
библиотека — любой агент обходит ЛЮБОЙ клапан, просто записав .md напрямую → «движок енфорсит» становится ЛОЖЬЮ. Это
upstream всех остальных решений клапана.

## Ответственности движка (9 производных видов, по `id`, пересобираемы)
V1 id→паспорт · **V2 рёбра+backlink (блокирует клапан v1)** · V3 home-хребет + каскадные rollup · V4 section-index
(ленивые огромные секции, триггер по ШИРИНЕ) · V5 **FTS/BM25 (основной поиск)** · V6 **вектор (ОПЦ./отложен)** ·
V7 heat/recency · V8 проекции типа/линзы · V9 кэш производных рёбер. Инвалидация = правка файла → content-hash diff →
mark dirty → **PULL-пересчёт** (тянем, не пушим — это НЕ реактивность). `level`(хребет) ⟂ `centrality`(fan-in) ⟂
`priority`(ручной) — не путать.

## Retrieval API (один глагол `query`, операторы)
lookup · filter · neighbors(spine|link) · backlinks · cascade · section · fts · semantic · search(RRF) · getContext.
**Закон: запросы истины НИКОГДА не идут в векторы.** `search` деградирует: V6 off → search==fts. **sensitivity-фильтр =
SQL-предикат ДО возврата** (отсутствие клапана не утечёт через поиск).

## Каскад/rollup
cycle_guard (ссылки, first-visit-wins) ⟂ cascade_depth (хребет, по умолчанию БЕЗ ограничения — старый maxDepth=3 молча
ломал глубокие каскады) ⟂ терминатор паттерна prune|mark-cycle (enforce-классы — принудительный prune). Цикл в хребте =
ОШИБКА целостности, не молчаливый prune.

## Векторы (твёрдая рекомендация)
Вторичный, одноразовый, по `id` индекс в движке. **Сначала FTS**; векторы только при доказанных >10-15% промахов
keyword (кросс-язык ru↔en — единственный реальный кейс). **Эмбеддить `title+description+summary-по-типу` — НЕ сырой
payload и НЕ голый паспорт** (закрывает развилку). Исключение по sensitivity на этапе эмбеддинга. RRF-слияние.
Инструмент: `sqlite-vec + sqlite-fts5` в одном локальном файле.

## 🔴 3 CRITICAL — это ОДНА проблема под тремя углами
Транзакционность + граница клапана при ребилде + холодный старт = движку нужны ACID-подобные гарантии для структурных
операций, а md-файлы их не дают. Re-home трогает ≥5 файлов атомарно; крах между записями 2 и 5 → молчаливо битый граф →
движок пересобирает из битого → клапан пропускает sensitivity-ребро → разрешает утечку.

### Вердикт по «файлы vs SQLite»
**Рекомендация: SQLite для СТРУКТУРЫ** (паспорт-поля, рёбра, индекс, rollup), **.md для ТЕЛА** (проза, payload).
SQLite WAL решает все 3 CRITICAL разом. WAL-поверх-файлов не исключён, но его сложность реализации = исходному риску
корректности (flock на Mac+iCloud ненадёжен). Формулировка: **«файлы = истина для СОДЕРЖИМОГО; движок = истина для
СТРУКТУРЫ»** — это уточнение принципа, НЕ его разворот. **Требует решения владельца — смена архитектурного принципа.**

### Холодный старт
До построения индекса (свежий клон/после краха): O(E) чтений (~10-30с на графе ~13k рёбер). **SAFE-DEGRADED MODE:** все
записи заблокированы, requestExternalAction/requestPromotion отклонены, чтения несут `{degraded:true, completeness}`,
bootstrap-seed политики грузятся первыми. Выход — только когда индекс полон; обход — только конфиг владельца, не запрос
агента. С SQLite этот CRITICAL сжимается до быстрой проверки консистентности.

## Кандидат-инварианты движка (писать СЕЙЧАС — текст, не код; молчание = баг)
1. **Safe-degraded mode** (см. выше).
2. **Область клапана = read-trace движка ∪ объявленное агентом** (движок добавляет все узлы, тронутые через graph-API
   за ход; прямые чтения файлов — вне границы енфорса, документировать явно). ⚠ если модель «доверять списку агента» —
   «защита от adversarial-агента» ЛОЖНА, и это надо назвать явно.
3. **`seq` назначает только движок** (caller-set seq отклоняется; lexorank; уникальность per-anchor).
4. **frozen-binding всегда разыменовывается к источнику**, применяется строжайшее из (источник-текущий, потребитель);
   `binds:frozen` запрещён для sensitivity>internal без revalidation_policy.
5. **Проверка sensitivity ДО эмбеддинга** (движок не шлёт private/sensitive в облачный эмбеддер → нужен **5-й PEP
   «embed»** в клапане).
6. **rollup-поля считает только движок** (запись их агентом/человеком отклоняется).

## 🟡 Решения к владельцу (ADR-0004)
- **OQ-1 (CRITICAL):** SQLite-для-структуры (уточняет «файлы=истина»)? Рекоменд.: да/гибрид.
- **OQ-2 (CRITICAL):** **библиотека vs сервис** — самый upstream-вопрос; если библиотека, клапан обходится прямой
  записью .md. И: клапан строит список сам (Y) или доверяет агенту (X)?
- **OQ-3 (CRITICAL):** блокировать внешние действия на холодном старте? Рекоменд.: да.
- **OQ-4:** принять ADR-0004? Рекоменд.: да, скелет готов.
- **NOD:** единица эмбеддинга (title+desc+summary) · bi-temporal инвалидация (Zep) — включить · in-process→sidecar
  поэтапно · `weight(0..1)` на ребре · `seq` — единственный честный рост (+1 опц. поле ребра).

## Дисциплина
Δ паспорта = 0, Δ обязательных рёбер = 0 по всему движку, кроме честного `seq` (+1 опц. поле ребра, уже предсказано).
Движок больше НЕ «неописанная зависимость» — это описанный контур.
