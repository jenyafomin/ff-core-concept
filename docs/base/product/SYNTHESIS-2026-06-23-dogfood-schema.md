## 0. Главный вердикт (одной картиной)

**Конкретная схема СОБРАЛАСЬ; паспорт снова не растолстел (0 новых обязательных полей на ~28 типах + реальных файлах
репо).** Архитектор предъявил рабочую схему (5 регистров, словарь рёбер, многомерность на реальном `node.ts`, готовый
путь промоушна THREAD). Критик НЕ нашёл ни одного дефекта, требующего расширения паспорта — все 4 CRITICAL и 5 CONCERN
лежат **вне ядра**: протоколы перехода, спека движка, неоднозначность принадлежности, граница между типами.

**Но есть одно структурное напряжение, которое архитектор и критик увидели НЕЗАВИСИМО и одинаково остро: ДУБЛИРОВАНИЕ
истины при промоушне (THREAD-файл ⟷ dialogue-node-ячейка).** Это #1 к закрытию ПЕРЕД любым промоушном — иначе два
источника истины об одном факте. Это не дефект модели, это дефект отсутствующего ПРОТОКОЛА миграции.

**Честный рост модели (повтор stress, не новое):** ровно 2 места — модуль версий/lineage и stream-класс. §5 ADR-0002 их
предвидел; dogfood сделал их конкретными (git-история, THREAD-сообщения).

## 1. ДОКАЗАНО / решено (пруфы, с механизмом)

1. **Многомерность реальна и даёт то, чего ФС не может** (architect §3, пруф на `packages/core/src/node.ts`). ОДИН `home`
   (folder, каскад-спина) + N `facet-of` (service × data-model × core-kernel-area) + `part-of` план + `version-of` lineage.
   `id`(ULID) отвязывает идентичность от пути → `git mv` = re-home, все facet/spec-рёбра выживают (указывают на `id`).
   **Уже материализовано** в `docs/graph-example/file-node-ts.md`. Запрос «service-ячейки про data-model в плане X» = линза
   через 3 facet-оси — нативно здесь, невозможно на ФС без параллельной БД.
2. **Принадлежность ⟂ ссылка держится и на dogfood** (architect §2b, critic «что искал и не нашёл»). Каскад-спина = home-рёбра
   (всегда лес); `calls/imports/facet-of/version-of/depends-on` могут циклиться/фан-инить 500 — каскад не возмущают. Критик
   проверял адверсариально — пруф математически верен.
3. **Паспорт type-agnostic на ~28 типах FF + 12 сущностях GitHub — 0 новых обязательных полей.** Честный результат ДВУХ
   раундов стресса (critic §283). 9 обязательных + 2 опц. (`level?`,`canonical_id?`) + `external_ref?` покрывают всё.
4. **Мост v1→dogfood однозначен** (architect §1-E). `node.ts` хардкодит 9 `NODE_KINDS` (ADR-0001-прототип) → открытый реестр
   ~28 типов SUPERSEDES их таблицей 1:1 (`note`→analysis/spec/instruction; `group`→folder/category/chat/scope; `importance`→
   priority-ребро; `parentId`→home-ребро; `tags`→facet-рёбра). Это ровно таблица Supersedes ADR-0002. v1 `kind`-дискриминатор =
   анти-паттерн, от которого I-3 защищает.
5. **Путь промоушна THREAD конкретен и безопасен на текущем масштабе** (architect §5): формат файла-ячейки (паспорт+links+
   «Поведение») перенесён 1:1 из graph-example; маппинг THREAD-нотации (refines/grounds/raises…) → рёбра прямой; 89 узлов = 89
   файлов, stream-класс ещё не нужен (порог ~300). Рекомендация: инкрементально, начиная с pinned-узлов L0/L1.
6. **Виды диалог-узла (goal/insight/decision…) = ОДИН тип `dialogue-node@1`, не 8 типов, не payload-дискриминатор** (architect
   §5c, держит I-3). Вид влияет на `epistemic`/`level`/линзу, валидатор один. Расщепляется в свой тип ТОЛЬКО если вид
   потребует своей валидации (напр. `decision` обязан нести `decides→`) — сейчас не требуется.

## 2. ЧТО ЧИНИТЬ и ГДЕ ЖИВЁТ (паспорт / ребро / control-plane / движок / модуль / инвариант)

Сводка обеих линз. **Ни одно — не в паспорте.** Группировка по месту жизни.

### ПРОТОКОЛ ПЕРЕХОДА (новый слой — отсутствует, #1 приоритет)
- **C1+C4+P1+D-CR-1 — ДУБЛИ при промоушне (THREAD-файл ⟷ ячейка; CLAUDE.md/rules ⟷ instruction-узел; graph-example ⟷
  реальный граф).** Корень: при промоушне один факт живёт в двух местах без правила, кто истина. **Где живёт: дизайн-протокол
  миграции** (не движок, не паспорт). Архитектор предложил частичный ответ (§5a): нить-исходник = human-индекс, ячейки =
  машинная истина, «истина в 1 месте, проекция в других» → нить становится производной линзы. **Не финализировано** —
  требует явного решения владельца о судьбе исходных файлов. То же для `instruction`: файл CLAUDE.md = истина, узел =
  карточка-указатель (как git-commit), НЕ дубль payload.

### ИНВАРИАНТЫ записать (0 нового; молчание = баг)
- **Контейнер `home` ≠ категория** для тех же членов (architect §4a, stress §2C). Перенесёшь файл из `auth/` → молча потеряет
  ярлык «auth», если категория = home. **Это корень спора Q3/Q-D** — см. §3.
- **`function`/derived узлы кода = read-only** (файл=истина; функция-узел = проекция; писать в файл, не в узел).
- **Multi-schema реестр:** `schema` обязан однозначно выбрать валидатор из паспорта; ветвление по payload запрещено (I-3).
- **Control-plane-узлы аннотированы РОДОМ** (CN1): обход реестра типов должен отличать `model-def/lens/pattern/connector`
  (control-plane) от бизнес-типов (`task/goal`). Иначе агент получит их вперемешку. Род = свойство, читаемое без вскрытия.
- **Клапан: агент НИКОГДА не одобряет сам себя** (stress §2C, critic P4/D-CR-7); енфорсит движок, модуль агентов несёт только
  данные-политику. Тип вывода агента не присваивается агентом-автором как `fact`.

### РЕБРО (мелкие добавки из stress, подтверждены dogfood)
- **`seq`** (порядок ≠ важность): шаг-3 не «важнее» шага-2; коммит N — после N-1, не выше. **Открыто (CN5/D-CR-5):** `seq`
  per-parent / глобальный монотонный / свободный? Что при ретро-вставке (N-045a между N-045 и N-046)? → спека движка.
- **`binds: live|frozen`** (живая привязка vs снимок общего значения). **Открыто (W4):** нет бизнес-сценария «настройка
  изменилась — что с привязанными задачами» → проверить на конкретном примере.
- **`priority` (важность, per-parent) ≠ `seq` (порядок) ≠ `sort` (вторичный ключ)** — три разных поля, самое нарушаемое место.
  **Наблюдать (W2):** `sort` объявлен в ADR-0002, но не появился в dogfood — пробел или лишнее поле.

### ДВИЖОК / ЕНДЖИН-СПЕКА (главный стоячий риск — назван, не описан)
- **Индекс / rollup / кэш производных** — на масштабе обязательны (бэклинк-rollup фан-ина, секция-индекс широких папок,
  abstract-by-name для потоков N-043). 0 полей модели, но СПЕКУ надо написать. **#1 риск всей dogfood-схемы.**
- **Staleness для `external_ref`** (CN2/D-CR-3): git-sha удалён/переименован, Telegram message_id исчез → ячейка паспортно
  валидна, функционально мертва. Нет детектора (в отличие от `stale` для temporal). Утрата connector-узла → потеря resolver.
  → движок-спека (тема engine-spec).
- **Масштаб THREAD** (C3/critic): 89 узлов за 8 дней ≈ 4000/год; в одном файле = 60-100k строк. Промоушн в ячейки + section-index
  это решает, но механизм «найти N-078 не читая N-001…N-077» не проработан конкретно → движок (section-index / abstract-by-name).
- **split `maxDepth`** на `cycle_guard` (revisit) + `cascade_depth` (легальная глубина); терминатор паттерна `prune|mark-cycle`;
  `level` ≠ центральность (две разные линзы — не сливать). (stress, подтверждено.)

### МОДУЛИ (модель честно РАСТЁТ — ровно 2; §5 ADR предвидел)
- **Версии / lineage** (architect §4b): узел-`lineage` + рёбра `version-of`+`seq` + `home` на якорь. Выражает «сосуществующая
  упорядоченная история, всё реально» (цепочка коммитов — не замена). `supersedes` СУЖАЕТСЯ до настоящей замены. «Каждый
  вариант=тип» — НЕТ (взорвёт реестр на 120k). **Открыто (Q6/Q-F):** граница «какой commit становится узлом».
- **Stream-класс** (architect §4c): узел-`stream` держит паспорт, записи почти голые (наследуют по home). Строки кода/call-sites/
  транзитивные зависимости — НЕ узлы (правило: узел ⟺ стабильный id + свой home + ценность как единица запроса). **Это вычитание
  полей, в духе «меньше».**

### НЕОДНОЗНАЧНОСТЬ ПРИНАДЛЕЖНОСТИ (структурный выбор без аргументации — критик прав)
- **C2/D-CR-2 — home у commit/PR:** lineage (вертикаль истории) vs project (горизонталь) vs spec/task (функция). ADR требует
  ровно один. Архитектор выбрал `home→lineage`, **но не обосновал**. PR хуже — пересекает файлы. → агент-раунд (архитектор+critic):
  обосновать выбор с примером каскада. (Кандидат: home→lineage держит историю, project/spec = facet/ссылки; но требует пруфа.)
- **CN3/D-CR-4 — home у instruction (CLAUDE.md/rules):** home→project (каскадит scope на всё — паразитный каскад?) vs только
  `governs→` (задачи не видят инструкцию в home-цепочке). → агент-раунд (архитектор). Связано с C4 (instruction = карточка, не дубль).

### ГРАНИЦА МЕЖДУ ТИПАМИ (требует архитектурного ответа)
- **P3/D-CR-6 — `dialogue-node` vs `message`:** Telegram-сообщение, которое ЯВЛЯЕТСЯ insight владельца — оно message (поток,
  голый паспорт) И dialogue-node (типизировано). Два типа на сущность или один + категория? → тема smart-categories.
- **P4/D-CR-7 — `agent-thought` = тип `dialogue-node` (семантика) или `trace` (провенанс)?** Кто присваивает тип? Если агент сам
  → клапан-epistemic прозрачен (security-дыра). → инвариант «агент не одобряет сам себя» + тема valve-rules.

## 4. МИНИМАЛЬНЫЕ СЛЕДУЮЩИЕ ШАГИ (дизайн, без «строй»)

Порядок выбран по принципу «сначала то, что блокирует безопасный промоушн, потом стоячий риск»:

1. **Записать ПРОТОКОЛ перехода THREAD→ячейки** (OW-1): кто истина в момент промоушна, судьба исходника, инкрементальность.
   Блокирует Q11. Дизайн-артефакт, не код. *(Ждёт OW-1 владельца.)*
2. **Записать 5 инвариантов** (§2 «Инварианты»): home≠категория · derived read-only · multi-schema · control-plane-род ·
   агент-не-одобряет-себя. 0 нового, молчание = баг.
3. **Описать движок** (engine-spec тема): индекс/rollup/кэш + staleness external_ref + section-index + split maxDepth + терминатор
   паттерна + level≠центральность. **Главный стоячий риск.**
4. **Закрыть 2 неоднозначности принадлежности** агент-раундом: commit-home (OA-1), instruction-home (OA-2).
5. **Рёбра вместе:** `seq`-семантика (OA-3) + `binds:live|frozen` пример (W4).
6. **Модули:** версии/lineage (граница commit-узла OA-5) · stream-класс (THREAD-сообщения, git-история).
7. *(Вне рамок, флаг)* реактивность — ждёт D1/topic-4 + ADR-0003.

**Дисциплина соблюдена:** тонкий паспорт НЕ потолстел (0 новых обязательных полей на ~28 типах + реальных файлах). Сложность
ушла в движок / control-plane / 2 модуля. Вынужденный рост честно отмечен ровно в 2 местах (версии, stream) — оба §5 ADR-0002
предвидел. Главный незакрытый риск — не паспорт, а **протокол промоушна** (#1) и **неописанный движок** (#2).
