## 0. Самый важный факт (system-architect)
**Бóльшая часть «хотелок» уже реализована в `@ff/core`:** единый `FFNode` (single-table) +
`kind`-дискриминатор + `meta` (JSON-карман для специфики) + `parentId` (вложенность) +
`links[]` (типизированные рёбра) + `tags[]` + `importance` + вычисляемые уровни + `trace` (логи).
→ Вопрос не «строить с нуля», а **«где текущая файловая single-table модель ЛОМАЕТСЯ под фасеты,
рост подтипов и обратный обход — и лечить это индексом/БД или сменой истины».**

## 1. Требования (атомарно, сгруппировано) — analyst
**Схема:** R1 узел = чёткая структура; R2 особые типы со своими данными/настройками/схемой;
R3 двухуровневая схема (общая база + специфика в JSON); R5 наследование подтипов («лучше для роста»);
R6 важность многоуровневая; R7 метки/пометки отдельно от категорий; R8 лог = отдельный тип-узел;
R9 лог типизированно связан с планированием.
**Категории:** R10 контролируемые (не свободные); R11 иерархия (Спорт→Баскетбол→…); R12 свой набор
фасетов на каждом уровне; R13 ОБЩИЕ фасеты переиспользуются (Планирование везде — один тип, не дубль);
R14 категории = ключи, определяющие суть; R15 проектировать и для ИИ, и для человека (одна схема).
**Связи:** R16 всё связано как граф (фундамент); R17 связи типизированы; R18 быстрее/дешевле рынка;
R19 «комбинации» (составные связи нескольких типов).
**Хранилище:** R20 ElasticSearch для ИИ-поиска; R21 Mongo (гибкость+схемы в БД); R22 Postgres
(много FK→скорость); R23 выбор открыт; R24 данные грамотно сгруппированы; R25 схемы хранятся в БД (meta-schema).
**Поиск/ИИ:** R26 «живые» данные (семантический/полнотекст); R27 ИИ ЗНАЕТ где что лежит (карта знаний);
R28 человек тоже ориентируется; R29 масштаб «огромное скопление за огромное время».
**Документы:** R30 документы остаются; R31 БД = коннекты + агрегат «что в документе»; R32 коннект
к коммиту/логу изменений; R33 единый центр (информация и всё вокруг); R34/R35 кастом, не на базе чужих.

**Тонкие детали (легко потерять):** «живые» данные ≠ только ES (динамичность); категории должны быть
машино- И человекочитаемы (ограничивает именование); «не делать структур кроме особых» = жёсткая
типизация ТОЛЬКО для выделенных типов, остальное гибко; наследование > простота (явный приоритет);
логи = первоклассные сущности, не audit-trail; общие фасеты = REUSE, не дубль; «единый центр» =
БД как точка истины (инверсия «файлы первичны»).

## 2. Пять обязательных развилок (system-architect)
1. **Источник истины:** файлы+индекс (эволюция) vs БД-истина (замена, противоречит ратифицированному
   «строим на существующем субстрате» → нужен ADR) vs разделённое владение (контент=файл, связи=БД).
2. **Рост типов:** свободный `meta` vs реестр схем по `kind`+`subtype` vs наследование схем. Нужен ли
   новый уровень `subtype`? «Наследование» — это про схему (форма растёт) или про данные (узел наследует значения)?
3. **Модель связей:** embedded `links[]` (текущее, дорогой обратный обход) vs рёбра-как-сущности
   (свойства на ребре, двунаправленный обход). Нужна ли графовая БД (скорее нет на личном масштабе,
   но обратный обход обязателен).
4. **Фасеты/таксономия:** controlled-vocabulary-как-узлы vs facet-schema-на-категорию vs
   namespaced-теги. Где живёт «общий vs специфический». Фасет «Планирование» == тип узла «Планирование»?
5. **Важность:** одна ось или ДВЕ (текущая `importance` = операционная для компакции; владелец говорит
   о пользовательском приоритете — возможно две разные важности). Уровни — поле или вычисление.

Карта зависимостей: Развилка 1 → определяет хранилище и отношение к @ff/core. Развилки 2↔4 связаны
(фасет может быть типом). Развилка 3 → блокирует связь лог↔план↔коммит. Развилка 5 относительно независима.

## 3. Противоречия и допущения (critic)
- **C1 (блок):** три хранилища (ES+PG+Mongo) без разделения ролей = тройной операционный долг для solo.
- **C2 (блок):** «документы остаются + БД хранит коннекты» = два источника истины; стратегия конфликта не задана.
- **C3 (блок):** «контролируемые категории» ⟂ «гибкость пользователя» — прямая противоположность.
- **Допущения:** «кастом лучше рынка» — вера, не факт (нужен конкретный сценарий, где готовое провалилось);
  «ИИ нужен ES» — непроверено (pgvector закрывает <10k узлов); «огромное скопление» — 100k узлов = ~50 лет
  ведения = классический over-engineering. «Mongo vs Postgres по числу FK» — неверно поставлено (FK сами по
  себе PG не замедляют; замедляет плохое индексирование).

## 4. Рынок (business-analyst, веб-проверено)
- **Graphify** = граф ЗНАНИЙ О КОДЕ через MCP (YC S26, ~63k звёзд) — НЕ личный PKM, но его архитектура
  (офлайн локальный граф + MCP) — прямой прецедент.
- Задача владельца = пересечение **PKM + Knowledge Graph + GraphRAG + Agent Memory**; ни один продукт не
  закрывает все 4 для индивидуала → это и есть окно для кастома.
- **Брать готовое:** граф-хранилище (Neo4j/Memgraph), вектор (pgvector), RAG-каркас (LlamaIndex).
- **Кастом оправдан:** типизированные контролируемые фасеты (Спорт→Баскетбол); уровни важности в
  ранжировании retrieval; логи-как-тип; единый граф для ИИ+человека (dual-access через MCP).
- **3 урока:** граф должен быть QUERYABLE (а не декоративным как Obsidian); ВРЕМЕННОЕ измерение критично
  (Zep > mem0 на 15пп — факты меняются, не перезаписывать); MCP — де-факто стандарт (выставить граф как MCP).
- Итог: владелец строит **персональный GraphRAG с типизированной онтологией и dual-access**; кастом — как
  оркестрация+онтология ПОВЕРХ готовых компонентов, не замена инфраструктуры.

## 5. Рефрейм и порядок (abstract-thinker)
**Абстракция 1 — «как узел знает свой смысл»:** из ВИДА (kind+схема), по НАСЛЕДСТВУ (позиция в иерархии
фасетов/контекст родителя), от СВЯЗЕЙ (рёбра). Сообщение — не про БД, а про то, как `FFNode` получает
идентичность. БД — следствие.
**Абстракция 2 — «документ=истина, БД=его тень»:** классический CQRS / source-of-truth + read-model.
Документ остаётся истиной; БД = производный индекс связей/агрегатов/фасетов для быстрых запросов.
Владелец интуитивно нащупал «files as truth, DB as read-model».

**Порядок причинности (что первично):** (1) контракт смысла узла [ПЕРВИЧНО, уже на 80% в коде] →
(2) фасеты-ключи (дисциплина над тегами) → (3) связи (типы рёбер) → (4) хранилище [ПОСЛЕДНИМ, обратимо] →
(5) поиск/агрегация. **Минимальное ядро = (1) + дисциплина (2).** Выбор БД нельзя принимать первым —
он производный и обратимый; преждевременный выбор = смерть в проектировании.

**Правильный незаданный вопрос:** «**Какой РЕАЛЬНЫЙ запрос файловый граф уже НЕ вытягивает — и как часто
я его делаю?**» Универсальная БД оправдана ровно одним: запросом, который по файлам слишком медленный или
невозможный. Если такого запроса ещё нет — БД сейчас не нужна. Если есть — его форма и диктует движок.

## 6. Вопросы владельцу
**Микро-вопросы (разблокируют консилиум №1):**
- **В1.** Назови ОДИН запрос, который сейчас раздражает делать по файлам/в голове (пример: «покажи все
  застрявшие задачи Разработки за неделю»). — *это и есть критерий «нужна ли БД».*
- **В2.** «Особый тип-узел со своей схемой» — это про ВАЛИДАЦИЮ (поля проверяются) или про
  ПОВЕДЕНИЕ/UI (тип выглядит/действует иначе)?
- **В3.** Фасеты Спорт→Баскетбол — для ТЕБЯ (навигация) или для АГЕНТА (фильтрация/понимание)?

**Блокирующие (из critic, для консилиумов):** единый источник истины (файлы или БД, без «оба»); сколько
хранилищ (1 / 2 / 3+ с ролями); контроль схемы vs гибкость — где линия; конкретный сценарий, где готовое
провалилось; «логи» == `trace` или другое; через сколько месяцев нужна ощутимая польза.

## 7. Предлагаемая последовательность (конечная, не бесконечная)
Жёсткое правило против бесконечности: **каждый консилиум выдаёт (а) последовательность, (б) сильные
моменты, (в) ровно ≤3 спорных пункта как вопросы. Больше 3 — запрещено.**

1. **Микро-вопросы В1–В3** (5 минут) →
2. **Консилиум №1 — «Контракт смысла узла»** (схема, особые типы, фасеты vs теги). →
   вопросы/предложения владельцу →
3. **Консилиум №2 — «Связи и тень»** (документ=истина/БД=тень? типы связей лог→план→коммит; назвать
   доминирующий запрос). → вопросы владельцу →
4. **Консилиум №3 — «Движок и первый срез индекса»** (Mongo/PG/ES — теперь как ВЫВОД из доминирующего
   запроса, или НИКАКОЙ пока; триггер «когда файлов не хватит»). →
5. **Финальный командный спор** (`/pos-debate`): команда «Сейчас» (строим индекс-тень) vs команда
   «Позже» (файлы — единственная истина до порога-триггера). Синтез = не «кто прав», а **порог-триггер**
   (число узлов / частота запроса / время ожидания), при котором тень строится. → владелец утверждает порог.

## 8.5 Ответы владельца + уточнение модели сообщения (2026-06-14, голос)
- **В1 (зачем БД):** и голова, и много файлов не масштабируются → **склоняется к БД** (оптимизировать).
  *(Контраст с рекомендацией агентов «БД последней/обратимо» — фиксируем как напряжение для Консилиумов 2–3.)*
- **В2 (валидация):** НЕ решено, явно просит обсудить → ядро Консилиума №1.
- **В3 (фасеты):** **неограниченная глубина** (Спорт→Баскетбол→Контакты→Тренировки→…→∞, «сети чего угодно»);
  общие фасеты переиспользуются (Планирование везде).
- 🆕 **Модель «сообщения» (агрегатор):** сообщение = одно связное целое (как в Telegram), содержит:
  (а) **многоуровневое ОПИСАНИЕ работы** L1 (короткий отчёт) / L2 (детальнее) / L3 (очень подробно) —
  описывает ЧТО/КАК сделано, **но НЕ сами изменения/диффы**;
  (б) **прикреплённые ссылки** на сами файлы/документы/изменения (коммиты).
  Документ-истина = файл; сообщение-узел = его многоуровневое описание + ссылки.
- ⚠️ **Нюанс уровней:** здесь L1/L2/L3 звучат как **АВТОРСКИЕ хранимые слои** (написанные отчёты разной
  детальности), а не вычисляемый zoom (как решено для заметок ранее). Возможно: у сообщения/лога —
  хранимые авторские уровни, у простой заметки — вычисляемые. Развести в Консилиуме №1.

## 8. Честные флаги (перенести в каждый консилиум)
- Главный враг — **over-engineering** (3 хранилища; онтология под 50 лет данных; БД до первой пользы).
- «Кастом лучше рынка» — пока вера; брать готовые компоненты, кастом — только онтология+оркестрация+MCP.
- Выбор БД обратим и производен → решать ПОСЛЕДНИМ.
- Многое уже есть в `@ff/core` → уточнять 2 поля, не переписывать.
