## 2. Единая ячейка данных (хочет продумать тщательно)
- **Максимально модульная:** какие-то поля появляются, каких-то нет.
- **Резервируемые поля как МОДУЛИ:** общие поля резервируются системой; другие поля — модулями,
  которые «подключаются» (plug-in). Категории тоже частично зарезервированы системой.
- **Подтипы / ветвление:** у типа ячейки могут быть подтипы; ветвление на разные ВЕТКИ — как разные
  ячейки информации об одном и том же, но «новый план / новый взгляд», и **сравнение двух веток**
  между собой = граф-представление, ссылки между ветками. Найти, что общее между ними.
- **Группа ячеек:** информация может идти ячейками; если они родитель/дети — они просто связаны
  (это разные ячейки информации). Ссылки в основном внутри документа, но группа ячеек — тоже связи.
- **Цель:** информация одновременно МАКСИМАЛЬНО ОБЩАЯ и очень КОНКРЕТНАЯ.

## 3. Ответ на вопрос Консилиума №1 про уровни (Q1)
- **Всегда есть короткое `description`** — обязательно МЕНЬШЕ, чем само тело/описание; помогает ИИ.
- Уровни гибкие: **либо один полный отчёт, либо с описаниями для мелких**. Для мелких — короткое

  для ИИ) + `body` (полный отчёт, L3). Авторское/нормализованное — гибко; короткое описание обязательно.

## 4. НОВОЕ: три параметра-дескриптора («вектор»)
Добавить к ячейке понимание как **вектор из трёх параметров: ФОКУС / ГЛУБИНА / АБСТРАКТНОСТЬ** —
примерно определяют, насколько хорошо описана информация. L1/L2/L3 частично ложится на ось
абстрактности. Полезно ИИ для ранжирования/выбора нужного уровня. *(Кандидат на «живые данные для ИИ».)*

## 5. Агенты сами логируют работу (нормализация)
- Агент выполняет код → каждый раз шлёт **лёгкий запрос**: что сделал, какой был план, что сделано —
  с connection (связями). Это нормализуется в L1/L2/L3.
- **Каждая задача в плане = отдельная ячейка данных**, связанная с другими. У планировщика может быть
  своя структура данных; желательно, чтобы структуры поддерживали гибкость в будущем.

## 6. n8n-подобный конструктор
Владелец представляет «конструктор как n8n», который полностью создаёт автоматизации. Идея: создать
**системный план**, где всё на основе ОДНОЙ единой структуры (всё хранится в одном виде, нормализуется),
и автоматизации/планы реализованы/представлены поверх неё.

## 7. ДВА главных модуля (рамка всей системы)
1. **Модуль информации** — единая ячейка/граф (разделы 2–6).
2. **Модуль управления агентами** — умные чаты, общий/управляемый контекст, наблюдаемый мульти-агент.
- С этими двумя можно создавать и управлять всем. Агенты должны **максимально управлять компьютером**.

## 9. Второе голосовое (2026-06-14) — глубже, методы, представление

### 9.1 Мета: нужны лучшие методы, не только консилиумы
Владелец: ход мыслей нравится, но не хватает **скилла(ов)** — поискать, возможно несколько; обдумать
концепт на гораздо более глубоком уровне, с реально разных векторов. Нужен **ресёрч**, разные стратегии
**помимо консилиума/дебатов** — реальные **связки агентов**, которые делают совсем другие вещи.
Система: человекочитаемая + человеком контролируемая + полностью ориентированная на ИИ (ИИ умеет делать
запросы в эту БД, знает все её тонкости). Возможно **отдельный ИИ** для БД, или просто **MCP** — доступ каждому.

### 9.2 Иерархическая важность (ответ на Q3 Консилиума №1)
Важность не одна: есть **глобальная** + **важность у каждого родителя**. При углублении в секцию видны
ДРУГИЕ приоритеты: задача может быть не помечена явно, но её **родитель попадает в важную секцию** —
и там «самое важное дно». Разные важности выставляются по уровням иерархии. → Q3 ≈ **важность контекстна
родителю** (относительная важность внутри секции), а не «одна vs две глобальные оси».

### 9.3 Представление: mind-map, а не документы
Видит как **mind map**: чёткие структуры + данные, раскиданные по моментам, глубокие связи. Представление
БД должно быть очень обильным/хорошим → агенты круто им пользуются, каждый получает выхлоп.

### 9.4 «Одна ячейка = всё» (ключевой вызов)
Ячейка может хранить: сам результат-данные / ссылку на документ / весь документ. Варианты:
- **отказаться от файлов**, хранить в одном месте; документ существует «виртуально», скачивается как MD;
- или **файл создаётся сразу + контролируемая ссылка** на него (хук/скрипт заполняет файл из ячейки);
- дублировать (MD лёгкий) если по токенам недорого. **Решить границу файл↔ячейка.**

### 9.5 Многоэтапная загрузка (inbox → routing)
Сохранение в БД в несколько этапов: по умолчанию — **инбокс** (возможно с догадками); если есть
изначальная **цель** — маршрутизируется; **статусы** по данным (когда обновлялись в разных направлениях).

### 9.6 Создание ПЛАНА как большой единицы информации
Сам план — очень большая единица; дробить по документам неудобно → **mind-map навигация** по пунктам,
авто-связи отчётов задач, связки любые. Задачи о чём угодно (видеомонтаж, делегирование агентам, надзор).
Нужно: понять, КАК создавать такой план, из чего состоит, что получаем — с максимальной креативностью
(векторов направлений много).

### 9.7 НОВЫЙ вопрос: коммуникация между сессиями
Могут ли две запущенные сессии Claude Code общаться между собой? Как запускать сессии; нужно ли держать
их постоянно активными. Эти «мелочи» определяют главный UX и наши возможности/ограничения.
**Ответ (из ранее проведённого ресёрча):** нативно сессии НЕ общаются; варианты — внешний оркестратор
брокерит между сессиями, ИЛИ Managed Agents (нативный агент↔агент), ИЛИ — для нас — через ОБЩЕЕ
СОСТОЯНИЕ: сессии читают/пишут один граф (@ff/core как MCP) = асинхронная «коммуникация» через общую
память (trace/proposal-узлы). Сессии НЕ надо держать активными: персистятся в транскрипт, resumable по
`--resume`; агент работает по вызову, не постоянно. Модель = resumable-сессии + общий граф + оркестратор.

### 11.3 Новое — что система должна вмещать
- **Техническая составляющая как ячейки:** промпты, понимание агентов в системе, понимание кода,
  **коммиты** (если что-то меняется/ломается — иметь это понимание, а не просто искать).
- **Агрегирующая инфа поверх**, но без потери скорости → возможно отдельно выделять все
  подключения/ссылки, чтобы быстро делегировать.
- **Полиморфизм:** каждая сущность может крепиться к разным; перепроверять отсутствие **циклов**
  (узел не должен повторяться на одной ветке — «не сам своё дерево»).
- **Система = ПАМЯТЬ:** твоя память + память любого агента, и **управление** этой памятью.
- **Одна единая БД на всё:** вся чат-система (команды агентов, разные модели — отдельно) тоже
  должна, возможно, жить прямо в одной БД.
- **Типы как правила/модули:** у каждой ноты есть ТИП (план/задача/заметка). Есть БАЗОВЫЕ типы
  (доступны всем) + типы, **подключаемые модулем** (со своими правилами валидации/значениями).
  Возможно отдельный «скилл», показывающий, как всё взаимодействует. Нужна **грамотная система поиска**
  по сущностям (по типам; полиморфные/объектные ссылки; «как рассылки»).

## 10. Третье сообщение (2026-06-14) — файлы, мульти-родители, фильтры, механизм графа

### 10.1 Хранение файлов (first-class)
Система должна хранить **файлы** (любые + их описания). У каждого файла своя **категория** и
**важность** + описания папок, и возможно **связи** между всем этим. Если достичь модульности, где
каждая ячейка имеет тип или просто категорию (что лучше — пока TBD), это очень полезно для управления.
Отчёт агента становится очень связанным.

### 10.2 Лимиты выборки + ИИ достаёт разные графы
Должны быть **ограничения на количество данных**, доставаемых по графу. ИИ должен доставать **разные
графы данных** — хоть всё, что есть, и видеть, как это выглядит (не всё сразу, а в виде). **Основные
направления + фильтры + углы обзора** (глубина, вектор/фокус, абстракция, разная детализация).

### 10.3 Быстрый механизм работы с графом + рынок
Нужен продуманный и **быстрый механизм** для работы с графом; что на рынке для подобного (может Mongo
идеален, или другая БД). → прямой вход в ресёрч.

### 10.4 Мульти-родители + связи отдельно
Под механизм — удобные готовые **фильтры** (могут напрямую зависеть от информации). У одной ячейки
**могут быть НЕСКОЛЬКО РОДИТЕЛЕЙ**. Связи — это ДРУГОЕ, с теми же ячейками. → граф настоящий (DAG),
не дерево; нужно развести «родительство» и «связи».

### 10.5 Виденье фильтров (абстрактно)
- **Фильтр обзора:** показывает до определённого уровня, с возможностью в интерфейсе раскрыть/дополнить.
- **Детализация:** по уровням информации в моменте.
- **Лимит итераций** + в интерфейсе каждая итерация может содержать свои фильтры и поиски.
- **Типы связей:** коммит-агент, коммит-PR, и т.д.

### 10.6 Масштаб
Представление данных — огромный, продуманный проект; возможно, в дальнейшем как **целая БД**, чтобы
всё работало как нужно. → подтверждает: механизм графа/представление = отдельная крупная тема (ресёрч + консилиум).
