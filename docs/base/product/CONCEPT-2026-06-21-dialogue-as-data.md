## Контекст и постановка

**Источник:** N-055, msg 231, 2026-06-21.

Сейчас весь дизайн-диалог ведётся в Telegram и фиксируется вручную в `docs/dialogue/THREAD-*.md`.
Владелец поставил вопрос: почему диалог не является данными в той же БЗ?

> Сам диалог должен сохраняться как данные. Ответы агента (в чате, результаты, даже «мысленное»
> обсуждение) — почему бы не сохранять. Сессии разные (по-разному записываются) + темы диалога =
> узлы в той же БД. Каждое отправленное в Telegram сообщение (и моё, и владельца) = информация,
> которой можно управлять: редактировать, использовать.

Это прямое следствие рефрейма N-016: **БЗ = рабочий субстрат агента**. «Всё, с чем работают
агенты» — значит и сообщения, и сессии, и мысли агента входят в этот список.

## 1. Ценность/боль — зачем это владельцу

### Боли (текущее состояние)

**Боль 1. Потеря контекста между сессиями.**
Каждая новая сессия Claude Code начинается почти с нуля. Диалог в Telegram — это последовательность
сообщений, которую система не видит как структурированные данные. Агент не может ответить на вопрос
«что мы решили в прошлый раз про клапан?» — он лезет в файлы вручную или теряет нить.

**Боль 2. Диалог эфемерен или требует ручной фиксации.**
Сейчас THREAD-файлы ведутся вручную: Claude пишет обмен → сам же кодирует его как узел N-0xx.
Это трудоёмко и неполно. Много «между строк» (суждения агента, отложенные вопросы, черновые
размышления) теряется или не попадает в граф вообще.

**Боль 3. Нет возможности управлять сказанным.**
Сообщение отправлено — оно «мёртвое». Нельзя отметить его как «устарело», связать с решением,
которое оно породило, переоткрыть вопрос через полгода с контекстом. Telegram message_id
существует, но не используется как ключ управляемой сущности.

**Боль 4. Агент не может «думать» в наблюдаемой форме.**
Когда агент выполняет сложный анализ, его промежуточные рассуждения (которые сейчас уходят в
`docs/council/raw/`) существуют отдельно от основного потока. Нет единой точки, где видно: вот
вопрос, вот ход рассуждения, вот вывод, вот решение. Связь между ними — ручная.

### Выгоды нового подхода

**Выгода 1. Непрерывность контекста.**
Агент, начинающий новую сессию, читает не файлы-конспекты, а реальный поток сообщений с типами,
epistemic-статусами и рёбрами. «Что мы решили» — это запрос к графу, а не поиск по файловой системе.

**Выгода 2. Управляемость диалога.**
Каждое сообщение — узел с `epistemic`, `sensitivity`, связями. Можно отметить устаревшее,
связать ответ агента с узлом-решением, прицепить кнопку-action, переспросить спустя месяц.

**Выгода 3. Первый реальный наполнитель графа.**
Система уже генерит этот контент прямо сейчас — мы не придумываем синтетические данные. Диалог
сразу проверяет модель паспорта на реальных разнообразных узлах.

**Выгода 4. Наблюдаемость агента («видно, что он делает»).**
Мысли агента (agent-thought) — тоже узлы, `epistemic: proposal`, `source: agent`. Владелец видит
не только финальный ответ, но и ход рассуждения как структуру, с которой можно взаимодействовать
(согласиться, оспорить, отметить `fact`, удалить).

## 2. Сущности — типы узлов

Ниже — предложения по типам. Замечание: это гипотезы (`epistemic: proposal`), не зафиксированные
решения. Каждый тип должен пройти валидацию на паспорте ADR-0002.

### 2.1 `session`

**Что это.** Один рабочий сеанс: запуск Claude Code → выход. Контейнер для набора сообщений и
рассуждений этого сеанса.

**Паспорт ADR-0002:**

| Поле паспорта | Значение для `session` |
|---|---|
| `type` | `session` |
| `schema` | `session@1.0` |
| `epistemic` | `fact` (сессия либо была, либо нет; но идёт → `draft`) |
| `sensitivity` | зависит от содержимого; наследуется по home-каскаду |
| `source` | `system` (создаётся движком) |
| `principal` | id владельца |
| `level?` | дефолт-от-типа → `data` |

**Ключевые поля payload (не паспорт):**

```
title:        "Сессия 2026-06-21 — паспорт + диалог-как-данные"
started_at:   iso
ended_at:     iso | null
channel:      "telegram" | "claude-code-cli" | "api"
agent_ids:    [id, ...] — агенты, действовавшие в сессии
```

**Home:** корень-проекта / системный inbox для сессий.

---

### 2.2 `dialogue-thread`

**Что это.** Тема или нить диалога — логически связанный кластер сообщений вокруг одного вопроса
(= то, что сейчас отражается как `THREAD-YYYY-MM-DD-*.md`). Может охватывать несколько сессий.

**Паспорт ADR-0002:**

| Поле паспорта | Значение |
|---|---|
| `type` | `dialogue-thread` |
| `epistemic` | `draft → fact` (тема «открыта» → «закрыта с решением») |
| `sensitivity` | `internal` (переговоры владельца с агентом) |
| `source` | `human` (инициирован владельцем) |
| `level?` | `why` или `what` (тема уровня L0-L2 = почему/что) |

**Payload:**

```
topic:        "диалог как данные"
layer:        "L1" | "L2" | ...  (воронка из CLAUDE.md)
status:       "open" | "resolved" | "parked"
resolution:   id → узел-решения | null
```

**Открытый вопрос:** `dialogue-thread` как тип — это скорее **линза** (способ смотреть на
подграф сообщений), а не отдельный узел-контейнер. Нужно проверить, не нарушает ли создание
узла-нити принцип «control-plane = линза».
*Уверенность: средняя.*

---

### 2.3 `message`

**Что это.** Одно атомарное сообщение в диалоге: входящее (от владельца) или исходящее (от агента).

**Два подтипа через `schema@version`, не через отдельный тип:**
- `message@human` — слово владельца
- `message@agent` — ответ агента (финальный, отправленный)

**Паспорт ADR-0002:**

| Поле паспорта | Значение |
|---|---|
| `type` | `message` |
| `schema` | `message@human` / `message@agent` |
| `epistemic` | человеческое → `fact` (факт, что сказано); агентское → `proposal` дефолт |
| `sensitivity` | может варьироваться (голосовые сообщения владельца — чувствительные) |
| `source` | `human` / `agent` |
| `principal` | id владельца (оба: агент действует в его пространстве) |
| `level?` | `data` (сырые данные диалога) |

**Payload:**

```
text:          строка (транскрипт или текст)
telegram_msg_id: int | null  — внешний ключ Telegram
direction:     "in" | "out"
media_type:    "text" | "voice" | "file" | null
ts:            iso
```

**Замечание по `telegram_msg_id`:**
Это внешний идентификатор. Он НЕ должен становиться `canonical_id` узла — `canonical_id` движок
выставляет для дедупликации ВНУТРИ графа. `telegram_msg_id` лучше хранить как payload-поле
(внешняя ссылка). При необходимости сослаться из Telegram на узел — href-ребро (`to: telegram://...`,
`href: true`).

---

### 2.4 `agent-thought`

**Что это.** Промежуточное рассуждение агента: черновик анализа, мнение в дебате, план до
финального ответа. Сейчас попадает в `docs/council/raw/`.

**Паспорт ADR-0002:**

| Поле паспорта | Значение |
|---|---|
| `type` | `agent-thought` |
| `epistemic` | `draft` → `proposal` (агент может повысить свой черновик до предложения) |
| `sensitivity` | `internal` (видно только first-party, не утекает вовне) |
| `source` | `agent` |
| `level?` | зависит от содержания (`why`/`what`/`how`) |

**Payload:**

```
agent_id:     id агента
thought_type: "analysis" | "critique" | "proposal" | "synthesis"
parent_msg:   id → message (к чему относится)
```

**Замечание:** `agent-thought` — это первый тип, к которому клапан ADR-0002 НЕ применяется
(нет внешнего необратимого действия; просто запись). Это и есть «безопасный» тип.

---

### 2.5 `action` (кнопка/действие)

**Что это.** Потенциальное или выполненное действие, которое можно прикрепить к сообщению через
Telegram Inline Keyboard (message_id → кнопки).

**Паспорт ADR-0002:**

| Поле паспорта | Значение |
|---|---|
| `type` | `action` |
| `epistemic` | `proposal` (предложено) → `fact` (выполнено; требует авторизации) |
| `sensitivity` | зависит от типа действия |
| `source` | `agent` или `system` |

**Payload:**

```
label:        "Ратифицировать ADR-0002"
action_type:  "approve" | "reject" | "open-thread" | "link-node"
target:       id → узел (к чему применяется)
state:        "pending" | "executed" | "cancelled"
```

**Замечание:** `action` с `epistemic: proposal` → внешнее действие → клапан ADR-0002 ДОЛЖЕН
сработать. Это хорошая первая проверка клапана на реальных данных. Но MVP без кнопок — см. §4.

## 3. Связи

### 3.1 Топология session → messages

```
session ─home→ message (все сообщения этой сессии)
session ─home→ agent-thought (мысли агентов сессии)
message ─involves→ dialogue-thread (если сообщение принадлежит теме)
```

**Вопрос:** `dialogue-thread` как каскад-родитель messages — или как линза поверх них?
Если тред = линза, то нет узла-треда, а есть предикат «все messages с rel→этой теме».
Если тред = узел, то нужен явный home-ребро от message к thread.

*Предварительный ответ:* для MVP проще начать с thread как узлом (конкретная структура понятна,
линзы ещё не реализованы). Можно переосмыслить после появления линзового движка.

### 3.2 message → узел-решение

Это самое ценное ребро. Сообщение порождает решение — `message ─grounds→ decision-node`.
Сейчас это делается вручную (N-0xx в THREAD). При автоматической записи message-узлов
это ребро может проставляться агентом вручную или автоматически (авто-ребро → `derived: true`).

### 3.3 Редактирование сообщения

Варианты:

| Вариант | Механика | Плюсы | Минусы |
|---|---|---|---|
| **supersedes-ребро** | новый message@v2 + ребро `supersedes→v1`; v1 → `archived` | audit trail; v1 не теряется | два узла, объём растёт |
| **мутация + трейс** | payload меняется; трейс-узел фиксирует (кто, когда, что) | один узел | нарушает принцип «файлы-истина» при мутации |

**Рекомендация (пропоузал):** supersedes-ребро, как это сделано для других типов в ADR-0002.
Мутация payload на `message` нарушает инвариант «manual = файл-истина», если узел хранится в
markdown. *Уверенность: средняя — нужно проверить на практике.*

### 3.4 Кнопка → action-узел

```
message ─triggers→ action (ребро от сообщения к потенциальному действию)
action ─involves→ target-node (к чему применяется)
```

`telegram_msg_id` на message → это внешняя ссылка, не canonical_id.
Добавление Inline Keyboard в Telegram = отправка `message@agent` с `action`-рёбрами к action-узлам.

## 4. Минимальный механизм (MVP)

**Что наименьшее нужно, чтобы начать:**

### MVP-0: Запись message-узла при каждом обмене

При каждом Telegram-обмене (входящее от владельца + исходящее от агента):
1. Создать `message@human` с `telegram_msg_id`, `text`, `ts`, `epistemic: fact`.
2. Создать `message@agent` с `text`, `ts`, `epistemic: proposal`.
3. Создать `session`-узел (или использовать текущий) как home для обоих.
4. Опционально: вручную добавить ребро `message ─grounds→ N-0xx` если обмен породил решение.

**Формат хранения (согласно ADR-0002: файлы-истина, markdown+frontmatter):**

```markdown
---
id: 01J5XXXX...
type: message
schema: message@human
epistemic: fact
sensitivity: private
source: human
principal: jenya.stasik@gmail.com
created: 2026-06-21T14:23:00Z
updated: 2026-06-21T14:23:00Z
telegram_msg_id: 231
---
«Сам диалог должен сохраняться как данные...»
```

### Что откладываем (не в MVP-0)

| Функция | Почему откладываем |
|---|---|
| Кнопки / action-узлы | Требует Telegram Inline API; клапан ADR-0002; до ADR-0003 рискованно |
| `agent-thought` в граф | Нужен автоматизированный hook в цикл агента; не ручной процесс |
| `dialogue-thread` как узел | Пока достаточно меток/рёбер на message; тред = линза до появления движка |
| Редактирование (supersedes) | Нужен движок; сначала накопить узлы, потом добавить versioning |
| Автоматическое ребро `grounds` | Требует контекстного понимания агентом; сначала вручную |

## 5. Почему это хороший первый наполнитель графа

**Аргумент 1. Контент уже генерится.**
Мы не придумываем синтетические тесты — мы просто начинаем сохранять то, что уже происходит.
Нет дополнительной работы по созданию данных.

**Аргумент 2. Безопасность по умолчанию.**
Запись в граф — это внутреннее действие (`sensitivity: private`, `principal` = владелец).
Клапан ADR-0002 для этого не нужен (нет внешних необратимых действий). Это первый класс узлов,
где мы точно не нарушим правило «дефолт-закрыто».

**Аргумент 3. Разнообразие паспортных значений.**
Message от человека (`source: human`, `epistemic: fact`) и от агента (`source: agent`,
`epistemic: proposal`) — уже два разных профиля паспорта. Session (`source: system`).
Это лучше синтетических 10 ячеек — реальный стресс-тест инвариантов.

**Аргумент 4. Проверяет механику home + принадлежность.**
Session → messages — первая реальная проверка инварианта «ровно один home» на потоке данных,
а не на единичном примере.

**Аргумент 5. Замыкает петлю «виден, что делает».**
N-015 (принцип): «трейсы действий ИИ — first-class и видимы». Message-узлы + agent-thought-узлы
— это и есть первый слой этой видимости. Без кода, без агентов — просто запись.

## 6. Риски и спорное

### Риск 1. Приватность и sensitivity сообщений

Голосовые сообщения владельца часто содержат личную или стратегическую информацию.
`sensitivity: private` помечает их, но:
- Кто может читать эти узлы? До ADR-0003 (ABAC) нет механизма, который это enforcement-но проверяет.
- Если в будущем появится маркетплейс или сторонние агенты — нужно, чтобы `sensitivity`
  уже была проставлена правильно с самого начала.

**Митигация:** ставить `sensitivity: private` на все message-узлы по умолчанию; явно понижать
до `internal` только для технических сообщений без личного контекста.

### Риск 2. Объём — N-043

N-043 уже поднял этот вопрос: «граф растёт; отдельные секции могут стать огромными».
Если каждое сообщение в Telegram = узел, а сессий много — граф message-узлов вырастет быстрее,
чем граф решений/идей. ADR-0002 упоминает `section-index`-конвенцию (ленивая загрузка огромных
секций). Без её реализации retrieval по потоку сообщений будет дорогим.

**Митигация:** ограничить MVP-0 сохранением только ЗНАЧИМЫХ обменов (где явно что-то решается или
поднимается вопрос), а не КАЖДОГО сообщения-уточнения. Дифференциация: «значимое сообщение» vs
«служебный ответ» — по типу диалога, а не по объёму.

### Риск 3. Дубли

Если агент фиксирует обмен как message-узел И одновременно пишет N-0xx в THREAD вручную —
у нас два представления одного события. До появления движка с `canonical_id` дедупликации не будет.

**Митигация:** в MVP-0 принять решение о единственном canonical-источнике истины:
ЛИБО THREAD-файл (ручной граф), ЛИБО автоматические message-узлы. Гибрид создаёт дубли.
Рекомендация (к обсуждению): перейти на message-узлы как primary, THREAD оставить как линзу
(производный вид над message-узлами, не отдельная запись).

### Спорное: `dialogue-thread` — узел или линза?

Это открытый вопрос дизайна. Если тред — узел, он нарушает принцип «control-plane = линзы»
(тред — это способ СМОТРЕТЬ на сообщения, а не отдельная сущность). Если тред — линза,
то нет удобного якоря для навигации «открытые темы».

*Это не блокер для MVP-0. В MVP-0 тред = опциональная метка (ребро message→category-node),
а не первоклассный тип.*

## Итог

Тема «диалог как данные» — не просто удобная фича. Это **логическое завершение рефрейма N-016**:
если БЗ = субстрат агента, и агент работает через диалог, то диалог ОБЯЗАН быть в БЗ.

Минимальный механизм (MVP-0) прост: при значимом Telegram-обмене создавать `message@human` +
`message@agent` + home-ребро к session. Это работает уже сейчас, без движка, без линз, без кода
`@ff/core`. Тестирует паспорт ADR-0002 на реальных данных.

Откладываем: кнопки, `agent-thought`-автоматизацию, `dialogue-thread` как тип, редактирование.
Закрываем первым: вопрос о canonical-источнике истины (дубли) и о фильтре значимости (объём).
