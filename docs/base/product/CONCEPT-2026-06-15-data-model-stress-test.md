# Стресс-тест модели данных → простой концепт

- **Status:** review
- **Owner:** jenya.stasik@gmail.com
- **Date:** 2026-06-15
- **Метод:** 5 агентов × ~50 примеров-ячеек (области жизни / карьера+коммуникация / технические / память+агенты / крайние случаи)
- **Related:** [data-cell-and-modules](ANALYSIS-2026-06-14-data-cell-and-modules.md), [Консилиум №1](../council/COUNCIL-2026-06-14-c1-node-meaning.md), [Консилиум №2](../council/COUNCIL-2026-06-14-c2-links-and-shadow.md)

## 1. Что модель ДЕРЖИТ хорошо
Однородный граф (узел + рёбра + теги + иерархия) отлично держит **СТРУКТУРУ и КОНТЕНТ**: группы-
направления, задачи, заметки, уроки, проекты, иерархию, каскад контекста, вычисляемые уровни.
Простые иерархические случаи (карьера→подобласти→проекты→задачи; хобби-проект с задачами) ложатся чисто.

## 2. Где ЛОМАЕТСЯ — дыры сошлись в 4 ОСИ (главный вывод)
Все 5 агентов независимо пришли к одному: модель сильна на структуре, но **четыре измерения висят на
`meta` без схемы, запросов и семантики**. Почти каждая «дыра» — это одна из них:

### Ось A — ВРЕМЯ (самая дорогая)
- Метрики/временные ряды (вес, броски, траты, оценка навыка) — нет `value/unit/occurredAt`, всё в meta, не агрегируется. *(6/10 бытовых ячеек)*
- Рекуррентность/расписание (привычки, ежемесячные траты) — `due` это ОДНА дата, нет повторов.
- **Темпоральность фактов** («вчера верно, сегодня нет») — `created/updated` = время файла, не время
  истинности. Нет `validFrom/validUntil/supersedes`. → память не отличает свежий факт от протухшего.

### Ось B — ПРИНАДЛЕЖНОСТЬ vs СВЯЗЬ (центральное противоречие)
- `parentId` один; «принадлежит и Спорту, и Карьере» — через что? parentId/tags/links перекрываются,
  нет канонического «принадлежит».
- **Каскад контекста и важности идёт ТОЛЬКО по `parentId`** → мульти-принадлежность через `links`
  контекст НЕ получает. Полиморфизм и каскад **несовместимы как сейчас закодировано**.
- Важность при мульти-родителях не определена (max/min/взвеш?); важность сейчас абсолютна, а не
  контекстна родителю (противоречит решению Консилиума №2).
- Template vs Instance: агент-роль (переиспользуемо) vs агент-в-чате (своя память) — не различены.

### Ось C — СТАТУС ЗНАНИЯ (эпистемика)
- Факт человека / гипотеза агента / предложение-на-апрув / архив — всё в одном пространстве. Нет
  `proposed/approved`. → риск: агент цитирует свои гипотезы как факты и «исполняет» неодобренное.

### Ось D — ТИПЫ: закрытый enum vs модульные типы (архитектурный разрыв)
- `kind` — закрытый enum (9 значений), заморожен в TS. Заявленные «типы, подключаемые модулем со
  своей валидацией» — рантайм-невозможны без ОТКРЫТОГО реестра типов. Блокирует промпты/коммиты/людей/
  правила-валидации. Полиморфный «узел = заметка+задача+лог сразу» тоже невозможен при одном kind.

### Сквозная инфраструктура (не модель, но обязательно)
- **Циклы:** защита есть только для `parentId`, для обхода по `links` — НЕТ; `maxDepth=3` обещан, но
  в коде ОТСУТСТВУЕТ → `getContext` зациклится.
- **Запросы:** нет фильтра по `due`/диапазону/`rel`/обратным рёбрам/полнотексту; `query()` грузит весь
  каталог. Класс запросов «все обязательства людям за неделю по направлениям» сейчас невозможен.
- **Внешние ссылки:** `Link.to` ждёт id узла, а нужны URL/git-коммит/файл — нет `href`, нет проверки
  целостности (висячие рёбра).
- **git/коммиты:** git — уже БД коммитов со своей истиной; зеркалить = две истины. Граница не проведена.
- **`description`** (короткое, всегда, для ИИ — твоё решение) — пока НЕТ в коде. Добавить.
- **Rollup:** прогресс проекта/курса/серии — в meta, не синхронизирован с детьми.

## 3. ПРОСТОЙ КОНЦЕПТ (абстракция, к которой всё сводится)
> **Узел — это типизированная, датированная, имеющая статус единица смысла. У неё ОДИН дом (где она
> живёт и откуда берёт контекст и важность) и МНОГО связей (со всем остальным). Всё — задача, заметка,
> метрика, человек, встреча, коммит, агент, сообщение — это узел с типом и несколькими типизированными
> рёбрами. Типы — это правила (базовые в ядре + добавляемые модулем). Граф — это память. Рёбра
> первоклассны и безопасны: типизированы, с обратным поиском, без циклов, с лимитом глубины.**

Форма узла (просто, 6 граней):
- **Кто я:** `id`, **`type`** (открытый, с опц. схемой), `title`, `description` (короткое, всегда), `body`.
- **Когда:** `created/updated` (файл) + **`occurredAt` / `validFrom` / `validUntil`** (событие/истинность) — НОВОЕ (ось A).
- **Статус:** `status` расширить до факт | гипотеза | предложение | open/doing/done | архив (ось C).
- **Где живу:** **`home`** = ОДИН дом (бывший `parentId`) — отсюда каскад контекста и важности (ось B).
- **С кем связан:** **`links[]{to, rel, href?}`** — N типизированных рёбер (мульти-принадлежность = связь,
  не второй дом; люди, коммиты, файлы, внешние URL).
- **Важность:** ручная 1-5 (контекстна дому) + наследование + touch-сигнал.
- **`meta`:** только специфика типа, валидируется схемой ЭТОГО типа.

**Что это даёт:** все 50 ячеек выражаются как «узел + тип + время + статус + 1 дом + N связей».
Метрика = тип со значением+временем. Человек/встреча/обязательство = типы с типизированными рёбрами
(история берётся обратным поиском). Полиморфизм = 1 дом + N связей (противоречие каскада исчезает).
Промпт/коммит/правило = типы из модуля. Память = узлы со временем истинности.

## 4. Что НЕ закрыто — решения, нужные от владельца (5)
1. **Принадлежность (ось B):** принять правило «ОДИН дом = контекст+важность; мульти-принадлежность =
   связь, НЕ второй родитель»? *(разрешает главное противоречие)*
2. **Время/метрики (ось A):** метрики и события — первоклассный тип (значение+единица+время) и
   `occurredAt` на узлах, или оставить в заметках? *(6/10 бытовых ячеек требуют)*
3. **Открытые типы (ось D):** принять «`type` — открытый реестр: базовые типы в ядре + типы от модулей
   со своей валидацией»? *(разблокирует промпты/коммиты/людей/правила)*
4. **Эпистемика (ось C):** нужен ли статус «факт / гипотеза агента / предложение-на-апрув» на узле?
   *(чтобы агент не выдавал гипотезы за факты и не исполнял неодобренное)*
5. **git/коммиты:** зеркалить коммиты как узлы (ради рёбер баг→коммит→план) ИЛИ git = внешняя истина +
   ссылка `href`? *(где проходит граница «всё узел» vs «git уже БД»)*

## 5. Вывод
Модель верна как СКЕЛЕТ (узлы+рёбра). Стресс-тест показал: чтобы она «вмещала всё», нужно добавить
**4 оси — Время, Принадлежность(1-дом-vs-связи), Статус-знания, Открытые-типы** — и починить
инфраструктуру (циклы/maxDepth/обратные рёбра/внешние ссылки/description). Это НЕ усложнение, а
**достройка скелета до простого тела из 6 граней**. Дальше — твои 5 решений, и концепт фиксируется.
