# Синтез — T1 + Q10: клапан как слой rules/permissions (узлы-политики, енфорсит движок)

- **Status:** review · **Owner:** jenya.stasik@gmail.com · **Date:** 2026-06-23
- **Сводит:** `docs/council/raw/2026-06-23-series/valve-rules/{architect.md, critic.md}` (system-architect — конструктивная
  модель PDP/PEP; critic — адверсариальный стресс, 3 CRITICAL + 4 CONCERN).
- **Grounds on:** ADR-0002 §3 (клапан=политика движка, дефолт-закрыто, автор≠авторизатор, ГРАНИЦА v1), §4 (control-plane=3
  рода; ПОЛИТИКА=класс ЛИНЗЫ hard-ABAC), Risks R4 (first-party-only gate); N-088 (rules/permissions как у Claude Code,
  движок енфорсит, агент не одобряет сам себя); N-071 (гранулярное одобрение per-stage/per-cell в модуле агентов);
  SYNTHESIS-stress §2C (клапан=движок, агент не одобряет себя); conception-mapping §1b/§2 (`trace`/`instruction`-типы, рёбра).
- **Дисциплина:** тонкий паспорт НЕ толстеет (0 новых обязательных полей). Сложность — в control-plane (узлы-`rule`),
  рёбра (`applies-to`) и движок (enforce-points + конституция). Вынужденный рост отмечен честно (он минимален: 1 тип-узел,
  1 род ребра, фиксированный набор PEP — всё control-plane/движок, не паспорт).

---

## 0. Главный вердикт (одной картиной)
Модель клапана как rules/permissions **строится чисто** на ADR-0002 без роста паспорта: паттерн **PDP/PEP/PAP/PIP поверх
ABAC** + реляция вердиктов Claude Code (`allow/ask/deny`, **deny побеждает всё**, слои principal). Правило = **узел-`rule`**
(control-plane, класс ЛИНЗА hard-ABAC); покрытие = ребро **`applies-to`** (I-2: scope, не собственность); решение = чистая
функция движка; точки перехвата = **4 фиксированных PEP** (`valve / promotion / disclosure / edit`).

**НО** критик вскрыл **конструктивную дыру, которой нет защиты СЕЙЧАС:** «агент не одобряет сам себя» защищено для подъёма
`epistemic`, но **НЕ для мутации самих узлов-политик**. Агент с write-доступом к control-plane может **отмыть** одобрение
через правило: написать allow-`rule` → тут же им воспользоваться (laundering). Это два шага вместо одного, результат тот же.
Защита (R4 first-party-only gate) **отложена в ADR-0003** — значит дыра открыта ровно в фазе, где мы разблокировали
автономность (N-088). Архитектор это частично предвидел (его «конституция» §4 шаг 4 + мета-правило §6), но не сформулировал
как немедленно-обязательный инвариант движка. **Оба сходятся на ОДНОЙ строке-инварианте**, которую надо записать сейчас, не
дожидаясь ADR-0003.

Изящество модели **условно** на двух нерешённых развилках (обе — к владельцу): (1) граница «гибкое-правило vs прибитая-в-код
конституция»; (2) кто старший при конфликте файловых rules Claude Code vs graph-политик.

## 1. ДОКАЗАНО / решено (пруфы — с механизмом, не «работает»)

1. **Паттерн ложится 1:1 на то, что назвал владелец (N-088).** Три вещи owner-а — правило-как-данные, движок-енфорсит,
   агент-не-сам-себя — это ровно **PAP (граф) / PEP+PDP (движок) / разделение актор≠авторизатор**. Не изобретение: каноничный
   ABAC-паттерн «autonomous-but-gated» + точная калька прав Claude Code. *(architect §1, §7; пруф: маппинг ролей.)*
2. **0 новых обязательных полей паспорта.** Весь слой = узлы-`rule` + рёбра `applies-to` + фиксированные PEP. PIP читает уже
   несущие оси (`sensitivity`/`epistemic`/`principal`/`source`) — **без вскрытия payload** (I-1/I-3). Право доступа НЕ стало
   полем ячейки. *(architect §0, §7 пруф 1; держит дисциплину.)*
3. **«Агент не одобряет сам себя» структурно неизбежно для ИСПОЛНЕНИЯ.** Агент вызывает действие **глаголом** движка
   (`requestExternalAction`/`requestPromotion`), не держит сокет наружу → физически проходит через PEP, решает PDP, не
   агент. Имя `request*` точное: просит, авторизует другой субъект. *(architect §3, §6; critic §5 «держится».)*
4. **Гранулярность per-stage/per-cell (N-071) выражена БЕЗ нового рода.** `per-cell` = `applies-to` конкретной ноды +
   `match.node_match`; `per-stage` = `match.stage`. Один механизм закрывает обе оси. *(architect §5.)*
5. **`allow/ask/deny` + deny>allow + слои + дефолты-по-инструменту** — рабочая, проверенная в продукте модель Claude Code;
   PDP-алгоритм (deny → ask → allow → дефолт-enforce_point) детерминирован. *(architect §4.)*
6. **Дефолты по enforce_point РАЗНЫЕ и это намеренно:** `valve`=дефолт-deny (необратимо вовне), `edit`=дефолт-allow своему
   автору (иначе каждая запись ждёт апрува — система неюзабельна). Прямая калька «read преаппрувнут, send/Bash — ask/deny».
   *(architect §3.)*
7. **Критик подтвердил здоровым** (проверил, дыр нет): автор≠авторизатор для `epistemic`; дефолт-закрыто как база; трейс
   каждого повышения; v1-граница «только прямо задействованные»; R4-флаг зафиксирован. *(critic §5.)*

### 2.1 МИНИМАЛЬНЫЙ ИНВАРИАНТ-СТРОКА (главный результат раунда — записать СЕЙЧАС)
Оба агента сходятся на этой строке. Её можно внести в ADR-0002 §3 (или список инвариантов движка SYNTHESIS-stress §2C)
**до** ADR-0003 — без неё клапан имеет конструктивную дыру:

> **Ни один агент не может создать, изменить или удалить узел `class: hard-ABAC` с `enforce_point ∈ {valve, promotion}`
> без явного действия `source: human` и записи трейс-узла. Движок отклоняет такую мутацию НЕЗАВИСИМО от capability агента.
> Единственное исключение — bootstrap-seed политики, помеченные владельцем при инициализации.**

Это закрывает C1 (laundering), C2 (default-deny на регистрацию) и P1 (рекурсия epistemic политик) одной строкой. `disclosure`-
и `soft-perception`-правила остаются открыты сторонним (read-only, не часть клапана) — R4-симметрия.

### 2.2 Структура (контракты — для справки, не «строй»)
- **PDP** (чистая функция движка): `decide(action_ctx, involved_nodes, rules) → {effect, reason, trace}`.
  Шаги: (1) граница = только прямо задействованные (ADR-0002 v1); (2) применимые правила по `applies-to`+`match`(оси
  паспорта); (3) **deny > ask > allow > дефолт-enforce_point**; (4) **конституция** (неотменяемо): автор≠авторизатор ·
  не-fact→≥ask · private→≥ask; (5) трейс-узел.
- **PEP** (4 точки): агент проходит ТОЛЬКО через глагол → перехват неизбежен.
- **PAP** = граф (политики = узлы, версионируются как данные — Принцип 0).
- **PIP** = паспорта задействованных нод (уже несущие оси).

## 3. ОТКРЫТЫЕ ВОПРОСЫ

### 3a. ВЛАДЕЛЬЦУ (политические решения о границе доверия — не механика)

- **🟡 V-1 — Принять, что «конституция клапана» живёт в КОДЕ движка, а НЕ как переопределяемые узлы-правила?**
  (автор≠авторизатор · не-fact→не вовне · private→не молча наружу · valve/promotion-rule = first-party-only.)
  *Почему важно:* сознательное исключение из Принципа 0 «control-plane = всё узлы». Без него один вредный allow-узел
  открывает клапан (атака R4/C1). С ним — часть control-plane не редактируема как данные (нужен code-change R4 +
  security review). Фундаментальная граница «гибкое vs прибитое». *(architect Q-T1-1; critic C1.)*

- **🟡 V-2 — Дефолт `valve` для autonomous-principal = `ask` (не `allow`), пока owner явно не написал allow-правило на
  конкретный connector×capability×stage?** *Почему важно:* задаёт «скорость клапана» автономного действия — прямо тот
  вопрос из STATE «облегчение или тревога, когда агент сделал без тебя». ask = безопасно-но-надоедливо на старте; allow =
  быстро-но-страшно. N-071 назвал это субъективным. *(architect Q-T1-2.)*

- **🟡 V-3 — Кто СТАРШИЙ при конфликте: файловые rules Claude Code (`settings.json`/`.claude/rules/`) vs graph-политики
  (узлы-`rule`)?** И «как в Claude Code» (N-088) = буквально использовать settings.json как primary layer, или построить
  аналогичный механизм внутри FF? *Почему важно:* без иерархии — два клапана без координации, один обнуляет другой;
  выбор «буквально CC» привязывает рантайм к Claude Code. *(critic C3/QC-V2, P3.)*

- **🟡 V-4 — Bootstrap-seed: одобрить процедуру, где ПЕРВЫЙ набор политик создаёт только человек и метит immutable?**
  Риск: на старте создать policy со сверхправами («дай всем всё — потом ограничим»), после чего ограничить трудно.
  *(critic W1/QC-V3.)*

- **🟡 V-5 — Граница клапана для АВТОНОМНОГО действия: достаточно ли v1 «прямо задействованные», или автономному нужен
  1-хоп trust-horizon РАНЬШЕ остального ADR-0003?** *Почему важно:* у синхронного действия человек рядом и переспросит; у
  автономного — нет, некому. *(architect Q-T1-5; critic W2.)*

### 3b. АГЕНТАМ / ADR-0003 (механика, не политика)

- **A-1 — Контракт `stage`: где живёт и как движок видит его в момент перехвата?** ADR-0002 §5 вынес `stage`→движок
  (производное), но per-stage матчинг требует, чтобы движок наблюдал stage при действии; N-071 положил «одобрение» в
  модуль агентов → нужен явный контракт передачи stage в action-context. *(architect Q-T1-3.)*
- **A-2 — Различение режима агента** (настройщик-политик vs исполнитель): разные principal или capability-токен? Без
  него инвариант §2.1 неверифицируем движком для multi-role агента. → ADR-0003. *(critic W4/QC-V5; F9.)*
- **A-3 — «Движок енфорсит» = библиотека или сервис?** `@ff/core` сейчас библиотека в процессе агента → агент может
  обойти PEP прямой записью файла. Архитектурный выбор для engine-spec. *(critic P2/QC-V4; F11.)*
- **A-4 — Род и регистрация КОННЕКТОРА:** connector с `capability: send|edit` = first-party-only (симметрично
  valve/promotion-rule)? read-коннекторы — открыты сторонним? *(architect Q-T1-6 → ADR-0003.)*
- **A-5 — Реестр правил при росте** (200 правил → «какое сработало»): отдельная линза-навигация, или жёстко
  deny>ask>allow + трейс `matched_rules[]` без `priority`? *(architect Q-T1-4; critic P1.)*
- **A-6 — Композиты/inference-атака (D5):** disclosure-PEP ловит ОДНУ ноду по sensitivity, но композит из N приватных
  входов → один «безопасный» выход проходит, а атака вывода — нет. Конституция (private→≥ask) смягчает, не решает.
  Явно отложить в ADR-0003 (бюджеты раскрытия/шум) — НЕ подавать как решённое. *(architect §7; critic — связано с C2.)*

## 4. МИНИМАЛЬНЫЕ СЛЕДУЮЩИЕ ШАГИ (дизайн, без «строй»)

1. **Записать инвариант §2.1** в ADR-0002 §3 / список инвариантов движка — закрывает C1+C2+P1 одной строкой,
   не требует ADR-0003. *(R0/R1 — дизайн-правка.)*
2. **Записать 3 инварианта конституции** (F4): автор≠авторизатор · не-fact→≥ask · private→≥ask — «неотменяемы data-правилом».
3. **Зафиксировать 4 PEP** (F5: `valve/promotion/disclosure/edit`) и контракт узла-`rule` (F6) как design-набросок в
   будущий ADR-0003 (или раздел engine-spec) — без кода.
4. **Решить V-1…V-5 с владельцем** (§3a) — это разблокирует ADR-0003 (модель доступа/ABAC); особенно V-1 (граница
   гибкое/прибитое) и V-3 (иерархия rules) — без них слой не сходится.
5. **A-1…A-6 → накопить как повестку ADR-0003** (механика); A-3 (библиотека vs сервис) влияет на то, реальна ли вообще
   фраза «движок енфорсит» — пометить как блокер реализации (не дизайна).
6. *(Вне рамок, флаг)* реактивность/реактор — каркас autonomous-principal (F7) готов на бумаге, но «строй» ждёт V-2 + ADR-0003.

**Статус ADR-0002:** остаётся APPROVED и здоров. Этот раунд его НЕ пересматривает — он добавляет один инвариант (§2.1) и
наполняет повестку ADR-0003. Вынужденный рост минимален и весь вне паспорта (1 тип-узел `rule`, ребро `applies-to`, 4 PEP,
конституция в коде) — дисциплина тонкого паспорта удержана.
