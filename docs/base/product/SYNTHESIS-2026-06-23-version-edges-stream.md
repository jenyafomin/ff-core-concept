## 0. Главный вердикт (одной картиной)

Архитектор и критик **сходятся на концепции** и **расходятся на enforcement-деталях**. КОНЦЕПЦИЯ здорова (критик прямо: «что искал,
но не нашёл» — принадлежность⟂ссылка для версий, сужение `supersedes`, stream-как-оптимизация = архитектурно верны). Но три темы —
**не три фичи, а одна система; дефект в одной протекает в две другие** (критик §337, архитектор §0). Открыто 3 CRITICAL, которые
надо закрыть ДО любого «строй»: **(1)** правило выбора идентичности (`canonical_id` vs `version-of` vs `supersedes`); **(2)** протокол
назначения `seq` (коллизии/вставки/удаления); **(3)** `frozen`-binding обходит клапан (security-дыра). Паспорт при этом не трогается —
все три чинятся как ИНВАРИАНТ реестра / правило ДВИЖКА / правило КЛАПАНА (ADR-0003).

## 1. Что ДОКАЗАНО / решено (пруфы) — можно фиксировать как дизайн-решения

| # | Решение | Пруф/механизм | Где живёт | Увер. |
|---|---|---|---|---|
| D1 | **`seq` ⟂ `priority` ⟂ `sort` — три разных ключа ребра** (порядок ≠ важность ≠ текст-сорт) | два разных частичных порядка над одним множеством рёбер; шаг-3 не «важнее» шага-2, коммит N — «после», не «выше» (оба согласны) | РЕБРО (опц. поле `seq`) | высокая |
| D2 | **`version-of`/`part-of-stream`/`binds` — обычные рёбра, НЕ `home`** → история и потоки любого размера НЕ трогают каскад | I-2: home-спина = лес (ацикличен). Прямое следствие несущего пруфа stress §1; критик подтвердил («дефектов не нашёл») | ИНВАРИАНТ (ядро) | высокая |
| D3 | **`version-of` НЕ несёт `home`** (история = ОСЬ, не принадлежность) | если `version-of`=home → два home, нарушение ядра; ревизия-1 не наследует контекст ревизии-5 | ИНВАРИАНТ модуля версий | высокая |
| D4 | **Сужение `supersedes` до НАСТОЯЩЕЙ замены** (не для версионной истории) | `supersedes`=«старое мертво» ≠ «сосуществующая история»; критик: «правильное, устраняет путаницу» | ИНВАРИАНТ реестра `rel` | высокая |
| D5 | **«Каждый вариант = тип» ЗАПРЕЩЁН для версий** (взорвёт реестр на 500k узлов); «один логический объект» собирает ЛИНЗА | I-3 + stress §2B; критик флагует обратное для user-типов (см. §3-O5) | ИНВАРИАНТ реестра | высокая |
| D6 | **Git = книга, узел-версия = карточка** (`external_ref{connector:git,key:sha}` + резюме; diff живёт в git, граф НЕ зеркалит) | зеркалить 120k diff = дублировать byte-truth + взрыв хранилища; `diff(A,B)` = операция КОННЕКТОРА | МОДУЛЬ версий + ДВИЖОК | высокая |
| D7 | **stream-класс = ВЫЧИТАНИЕ онтологии** (записи теряют 9 полей, наследуют от потока), а не новый род | N-040: меньше при той же выразительности; млн листьев одной спины = плоский каскад, не взрыв | ТИП `stream` + ИНВАРИАНТ наследования | высокая |
| D8 | **Строки кода · call-sites · транзитивные зависимости — НЕ узлы и НЕ записи** | правило «достоин узла» (stable id + свой home + ценность-как-единица-запроса) — каждое проваливает пункт | ИНВАРИАНТ (правило ингестии) | высокая |
| D9 | **`binds` (подписка, значение втекает) ≠ `references`/`calls` (упоминание)** — разные `rel`, движок различает по типу ребра | `binds:live` обязан инвалидировать потребителя; `references` — нет | РЕБРО (новый `rel`) | высокая |

## 2. Что ЧИНИТЬ и ГДЕ живёт (карта размещения — паспорт не трогаем)

### 2A. КРИТИЧЕСКОЕ (закрыть до «строй»)

| Дефект (источник) | Что чинить | ГДЕ живёт | Размер |
|---|---|---|---|
| **CRITICAL-1 — коллапс идентичности** (3 механизма `canonical_id`/`version-of`/`supersedes` без правила выбора → тихая потеря данных) | Зафиксировать ПРАВИЛО выбора как инвариант реестра: `canonical_id`=«я дубликат, схлопни» (ingestion-дедуп) · `version-of`=«сосуществующая упорядоченная история, всё реально» · `supersedes`=«настоящая замена, старое неактуально». Триггер каждого — однозначен | ИНВАРИАНТ реестра типов + ДВИЖОК (ingestion) | 1 правило, 0 полей |
| **CRITICAL-2 — `seq` без протокола назначения** (коллизии параллельных источников; hotfix-вставка; дыры при удалении) | Зафиксировать: (а) КТО назначает (рекоменд.: ДВИЖОК монотонно при ingestion, не автор) · (б) ТИП (рекоменд.: дробный/lexorank для дешёвых вставок, не int) · (в) уникальность — на множестве рёбер к ОДНОМУ якорю, не глобально · (г) удаление → дыра допустима (порядок относителен, «следующий» = по возрастанию, не по +1) | ДВИЖОК (протокол `seq`) + ИНВАРИАНТ | спека движка |
| **CRITICAL-3 — `frozen`-binding обходит клапан** (источник стал `archived`/скомпрометирован после заморозки → потребитель «выглядит fact» → клапан пропускает) | Решить ЯВНО (3 опции критика): (а) клапан при `frozen` доп-проверяет epistemic ИСТОЧНИКА на момент действия · (б) `frozen`-ребро несёт `epistemic`-snapshot+ts, движок сравнивает с текущим · (в) `frozen` запрещён для `sensitivity > internal` без ревалидации. **Рекоменд.: (а)+(в)** | ПРАВИЛО КЛАПАНА → **ADR-0003** | правило, 0 полей паспорта |

### 2B. CONCERNS (закрыть или принять риск явно)

| Concern (источник) | Что чинить | ГДЕ живёт |
|---|---|---|
| **CONCERN-1 — граница «что становится узлом» размыта** (advisory, не enforcing; «не-узел» сейчас → нужен узлом потом → переиндексация) | Принять явно одно из: (i) «граница размытая, переиндексируем» ИЛИ (ii) минимальный обязательный набор: **каждый commit ВСЕГДА = запись stream** (не пропускается, даже голая). Рекоменд.: (ii) для commit/message — пропуск = безвозвратная потеря | ИНВАРИАНТ ингестии (правило-минимум) |
| **CONCERN-2 / PROVOCATION-3 — stream-записи: blob vs узел-с-наследуемым-паспортом** (противоречие «9 обяз. полей» vs «почти голые»); если blob — невидимы клапану, дыра в «всё видно ИИ»/privacy | **Решить: записи = узлы с НАСЛЕДУЕМЫМ паспортом** (вариант б), НЕ blob. Зафиксировать: запись хранит только `seq`+`payload`(+редкие оверрайды); `type/schema/sensitivity/source/principal/epistemic` = `effective` one-hop resolve от stream по home. Движок отдаёт полный effective-паспорт клапану → запись ВИДНА | ИНВАРИАНТ наследования + ДВИЖКА (effective-resolve, горячий путь — кэш) |
| **CONCERN-3 / QD-5 — live-binding без семантики pull vs push** | Зафиксировать на уровне ДИЗАЙНА семантику (даже если детали отложены): `live` = подписка; pull (резолв при чтении) vs push (индекс обратных рёбер + инвалидация) = выбор движка, но граница «design vs impl» проведена | ДВИЖОК (спека) — выбор объявить |
| **CONCERN-4 / QD-6 / PROV-2 — `lineage`-anchor: новый узел vs конвенция рёбер** | Решить: anchor-УЗЕЛ (материализован, «дай всю историю» дёшево, но +1 тип) vs конвенция (v1=anchor, дешевле, но запрос дорогой). Архитектор склонен «вынуждены» (якорь ≠ объект: своя ось-идентичность). Рекоменд.: anchor-узел, но как ДАННЫЕ открытого реестра (`type:lineage`), НЕ 4-й control-plane род | ТИП `lineage` (данные) ИЛИ конвенция — выбрать |
| **CONCERN-5 — тень имён ЛИНЗЫ при мультиродителе для версий** (commit `version-of→lineage` И `touches→file` → два пути к разным дефолтным линзам; ромб-правило решает каскад ЗНАЧЕНИЙ, не выбор ЛИНЗЫ из control-plane) | Сформулировать правило выбора дефолтной ЛИНЗЫ при мультиродителе ОТДЕЛЬНО от ромб-правила каскада. Это уточнение уже-признанного CRITICAL «тень имён» (N-070) | ДВИЖОК (resolution дефолтной линзы) — общий блокер, шире этой темы |

## 3. Открытые вопросы — ВЛАДЕЛЬЦУ vs агентам

### 🟡 ВЛАДЕЛЬЦУ (принципиальные, требуют его решения)

- **O1 [CRITICAL-3 / QD-3 / архитектор S2 / D5-композиты]:** `binds:live` через границу `sensitivity` = КАНАЛ ВЫВОДА приватного значения
  (потребитель отражает чужое приватное). Та же семья, что композиты (твой D5, N-077). **Разрешать до ADR-0003 или БЛОКИРОВАТЬ?**
  *Рекоменд. обоих агентов: БЛОКИРОВАТЬ live-через-sensitivity до ADR-0003* (как и композиты). — здоровье/финансы, риск утечки высок.
- **O2 [CONCERN-2 / QD-4 / архитектор T6]:** Видит ли ИИ КАЖДУЮ stream-запись (млн сообщений) или только агрегат/проекцию? Концептуально:
  «чат = один поток с видимыми записями» vs «поток отдаёт abstract-by-name, записи лениво». *Влияет на клапан/privacy/«всё видно ИИ».*
- **O3 [CONCERN-1 / QD-6 / архитектор S1, T6.4]:** Как ты видишь «чат»: ОДИН гомогенный поток (один `record_type`) ИЛИ КОНТЕЙНЕР потоков
  (вложения/системные события/реплаи вперемешку)? Гомогенность — реальное ограничение модели; от ответа зависит число потоков и линз.
- **O4 [CRITICAL-1 / QD-1]:** На уровне смысла — «история ЖИВЁТ (всё реально)» vs «замена УБИВАЕТ старое» vs «дедуп СХЛОПЫВАЕТ дубликаты»:
  подтверждаешь, что это три РАЗНЫЕ ситуации (а не одна)? Это задаёт правило выбора `version-of`/`supersedes`/`canonical_id`.

### Агентам (механика/спека, не нужна ратификация владельца)

- **A1 [QD-2]:** Протокол `seq` (кто назначает, тип, hotfix, удаление) → engine-spec.
- **A2 [QD-5]:** live-binding pull vs push → engine-spec (объём работы движка сильно различается).
- **A3 [архитектор Q2]:** `binding` как атрибут ребра `binds` vs два `rel` (`binds-live`/`binds-frozen`) → review (обратимо R1; склонность — атрибут).
- **A4 [QD-6 / архитектор Q8]:** `lineage`-anchor — узел vs конвенция → дизайн модуля версий (склонность — узел-данные).
- **A5 [CONCERN-5]:** правило выбора дефолтной ЛИНЗЫ при мультиродителе → общий блокер «тень имён» (шире темы, к engine-spec).
- **A6 [архитектор Q7 / S5]:** записать ИНВАРИАНТ+ТЕСТ границы `binds`(консистентность) ⟂ реактивность(реакция) — чтобы реактор не протёк
  через `binds:live` чёрным ходом. Закрепить до «строй».
- **A7 [критик «отмечено»]:** cross-validation `version-of`-рёбер против git-порядка (кто проверяет согласованность карточки и книги); split
  `cascade_depth`/`cycle_guard` нужен ДО lineage-запросов (100 версий = depth 100 упрётся в старый `maxDepth`).

## 4. Минимальные следующие шаги (дизайн, без «строй»)

1. **Записать 4 инварианта** (0 новых полей): D2 (version/stream/binds = не-home) · D3 (`version-of`≠home) · D4 (`supersedes`=замена) ·
   D8 (строки/call-sites/транз.-зависимости = не узлы). + правило CRITICAL-1 (выбор идентичности) и CONCERN-2 (запись=узел-с-наследуемым-паспортом).
2. **Дополнить engine-spec** (та же #1-стоячий-риск, что в stress §0; идёт параллельной темой): протокол `seq` (A1) · `binds`-инвалидация pull/push (A2) ·
   `lineage resolve(at)` битемпорал · stream rollup + abstract-by-name + effective-resolve · split `maxDepth`→`cascade_depth`/`cycle_guard`.
3. **Передать в ADR-0003** правило клапана для `frozen`-binding (CRITICAL-3, O1) — НЕ решать в тонком паспорте; это модель доступа.
4. **Дождаться ответов владельца O1-O4**, затем — спека модуля версий/lineage и stream-класса (дизайн), с порогом «достоин узла» из §0.
5. **Не «строй».** Все три темы остаются эскизом+контрактами; ни одно решение не требует кода сейчас.

> **Честный итог о росте:** модель РАСТЁТ ровно в 2 предсказанных §5 ADR-0002 местах (версии/lineage · stream) — и это вынужденный, признанный
> рост В МОДУЛЯХ/ДВИЖКЕ, не в ядре. Паспорт цел (0 обяз. полей). Новый род узлов — только `lineage` (и то спорно: возможна конвенция, A4),
> и он остаётся ДАННЫМИ открытого реестра, НЕ четвёртым control-plane родом. Три CRITICAL — про enforcement (инвариант/движок/клапан),
> не про толщину паспорта. Это ровно та дисциплина, которую держим: сложность ушла в движок/control-plane/модули, ядро не тронуто.
