## 0. Главный результат (одной картиной)

«Умная категория» владельца (N-087) — **НЕ один род и НЕ новое поле паспорта**. Все три линзы сошлись: это **композиция
уже существующих примитивов ADR-0002**. Но под словом «категория» владелец свернул **ДВА разных феномена**, и их надо
расщепить, иначе спор «узел vs facet vs под-тип» неразрешим (архитектор), а валидация недетерминирована (критик C1/CON-1):

- **1a — Категория-КЛАССИФИКАТОР** («к чему относится»; N-042б, N-081 многомерность): узел `category` + ребро `facet-of`.
  Членов МНОГО, у ячейки таких рёбер МНОГО. **Формы НЕ диктует.** Доказана на `node.ts` (один home + N facet).
- **1b — Категория-ВАРИАНТ-ФОРМЫ** («у покупки dropdown, которого нет у продажи»; N-087 L2.2): это **ТИП** открытого
  реестра (`deal-buy`, `deal-sell`) + ребро `variant-of → deal`. **Форму диктует** (delta-схема). Дискриминатор — в
  паспорте `schema`, НЕ в payload (I-3/«вариант=тип» из стресс-теста §3). «Один логический deal» собирает ЛИНЗА.

**Паспорт остаётся тонким; control-plane остаётся 3 рода (ТИП·ЛИНЗА·ПАТТЕРН).** Рост = 0 новых обязательных полей,
0 новых родов. Единственная честная дельта — **движок-спека слияния delta-схем по `variant-of`** (та же категория
«неописанный движок», что индекс/rollup — #1 стоячий риск).

## 1. ДОКАЗАНО / решено (пруфы — где сходятся все три линзы)

| # | Что доказано | Механизм | Линзы |
|---|---|---|---|
| P1 | «Умная категория» — НЕ 4-й род control-plane | раскладывается на ТИП-контракт + facet-ребро + ЛИНЗА-предикат + (опц.) ПАТТЕРН | abstract §3, architect §5, critic «не нашёл проблем» |
| P2 | Многомерность (N-081) реализуется БЕЗ нового поля | `facet-of`-рёбра (без home, сколько угодно); доказано на `node.ts` | все три + conception-mapping §3 |
| P3 | «Свои поля/dropdown» (N-087) = вариант-ТИП, не payload-дискриминатор | `variant-of`+delta-схема; выбор валидатора из паспорта `schema` (I-3 цел) | architect §1b/§2a, abstract A1, critic (через C1) |
| P4 | Граница тип↔категория НЕ размыта по сути — двойственна в СЛОВЕ | в любой ячейке роль однозначна: `facet-of`-членство (не диктует) ЛИБО `schema` паспорта (диктует) | architect §5, abstract §«граница» (3 да/нет) |
| P5 | Умные категории НЕ блокируются Q3 (живут в зоне facet/variant, не home) | ни 1a, ни 1b не претендуют на home → I-3 не задет → можно проектировать не дожидаясь консилиума Q3 | architect §6, abstract §Tensions |

**Несущая формула границы (ратифицируема, высокая уверенность):**
> **ТИП = «что ячейка ЕСТЬ» (одно, в паспорте, базовый валидатор). КАТЕГОРИЯ-классификатор = «к чему ОТНОСИТСЯ»
> (много, на рёбрах, ось линзы, формы НЕ несёт). КАТЕГОРИЯ-вариант = ЕСТЬ тип (`variant-of`, delta-форма, дискриминатор
> в паспорте).** Тот же раскол, что `home`⟂`facet`, применённый к ВАЛИДАЦИИ.

**Ментальная модель для владельца (магазин, abstract §):** ТИП = «что за товар» (книга/молоко — один, на товаре/в
паспорте); КАТЕГОРИЯ-классификатор = «полки-ярлыки» (акция/хрупкое — много, не меняют что за товар, помогают найти);
`home` = «склад, где физически лежит» (один). Опасность, которую владелец почувствовал (Q3): нельзя путать СКЛАД и ПОЛКУ —
иначе перевёз товар на другой склад и он молча СЛЕТЕЛ с акции. «Покупка»/«продажа» = либо две полки (если формы не диктуют),
либо два под-товара `deal-buy`/`deal-sell` (если у покупки своя форма с dropdown).

## 2. Что ЧИНИТЬ и ГДЕ живёт (дисциплина размещения)

**Сквозное расхождение линз, которое синтез РЕШАЕТ:** abstract предложил «категория несёт `extra_schema`, валидация =
композиция контрактов ПО facet-рёбрам». Критик (C1/CON-1) показал: если facet-ребро инжектирует ФОРМУ, движок обязан
обойти рёбра ДО валидации → неоднозначность схемы (одна ячейка в 4 категориях = 4 валидатора) + тень имён на DAG (T4/Q4).
**Решение — позиция архитектора §3c (берём её как несущую):**

> **Форму диктует ТОЛЬКО `type`/`schema` ПАСПОРТА + линейная `variant-of`-цепочка в реестре. Классификатор (`facet-of`)
> НИКОГДА не инжектирует поля/дефолты.** Это снимает C1 и тень имён (Q4) для категорий НАЧИСТО: «какая из 4 категорий
> диктует форму» = несуществующий вопрос (ни одна). `extra_schema`-на-facet (idea abstract) **отклонена** как нарушающая
> I-1. Если владелец ХОЧЕТ, чтобы категория диктовала форму — это смена `type` ячейки (она `deal-buy`, а не `deal`+ярлык).

| Что | Где живёт | Деталь | Род роста |
|---|---|---|---|
| Классификатор 1a (членство, срез, многомерность) | **узел `category` (обычный) + ребро `facet-of`** | без home, без формы; уже в ADR-0002 Supersedes #9 | 0 нового |
| Вариант-форма 1b (свои поля/dropdown) | **ТИП-узел `model-def` + ребро `variant-of`** (control-plane) | delta-схема: `base ∪ delta` вдоль `variant-of`; дискриминатор = паспорт `schema` | 0 родов (реестр растёт горизонтально) |
| Вложенность категорий | **рёбра** `subcategory-of` (1a) / `variant-of` (1b) | классиф.-иерархия ⟂ home-спине; обычные рёбра | 0 нового |
| Наследование ФОРМЫ без вскрытия payload | **ДВИЖОК** читает `variant-of`-цепочку (control-plane-узлы), как level-из-топологии | payload ячейки НЕ вскрывается для выбора схемы | движок-спека (дельта) |
| Наследование КОНТЕКСТА (sensitivity/scope) | **home-спина** (ADR-0002 §2а) | классификатор НЕ каскадит контекст — защита I-3 | 0 нового |
| Авто-связи «только в группах» (N-087 L2.4) | **узел `pattern` + `when_scope` + рёбра `derived:true`+`rule_ref`** | scope правила = «в этой группе» → не сканирует весь граф (анти-взрыв); read-only | контракт паттерна (дельта) |
| Слияние delta-схем + применение авто-правил | **ДВИЖОК-СПЕКА** (отдельный этап) | та же категория риска, что индекс/rollup (#1 стоячий) | спека, не код |

**ИНВАРИАНТЫ записать (0 нового кода, молчание = баг):**
- **INV-SC1:** классификатор (`facet-of`) НЕ несёт payload-схему членов; форму несёт ТОЛЬКО `type`/`schema` + `variant-of`-цепочка. (Снимает C1/Q4.)
- **INV-SC2:** дискриминатор валидации варианта — в ПАСПОРТЕ (`schema`), ветвление по значению payload запрещено (I-3, повтор реестра multi-schema).
- **INV-SC3:** авто-рёбра категорий = `derived:true`+`rule_ref`, read-only; enforce-влияющие авто-рёбра (cites/promotion-влияющие) = **first-party-only** (R4 ADR-0002).
- **INV-SC4:** вложенность категорий (`subcategory-of`/`variant-of`) — НЕ home-спина → нужен cycle-guard + maxDepth движка (критик P2: вторая иерархия без защиты от циклов).

### 3c. КАНДИДАТ-МОСТ для консилиума Q3 (вход, не финал)

**Q3 (dual-role: папка = и home, и категория?) может СНЯТЬСЯ без нарушения I-3:** «папка навешивает категорию» =
**авто-связь-правило** (`pattern` с `when_scope: folder:auth`, эмитит `derived facet-of → category:auth`), а НЕ слияние
home+facet в один узел. Тогда: home остаётся чистым каскадом; ярлык — отдельный `derived`-facet; перенос файла →
правило перестаёт матчить → ярлык **детерминированно пересчитывается** (не «молча теряется»). Передаётся в консилиум Q3
как кандидат-резолюция (architect §6/Q-SC5; средняя уверенность).
