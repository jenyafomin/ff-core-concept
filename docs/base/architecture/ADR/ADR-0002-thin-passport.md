## Контекст

Проект: граф узлов («ячеек») + ИИ-агенты. Ядро ноды = **паспорт интерпретации** — узкий набор полей, по которым
ИИ/движок решает, КАК обращаться с ячейкой, **не вскрывая payload и не зная тип**. Это и есть **инвариант несущести**
(N-046, RESEARCH §0/§2): *поле несущее ⟺ по нему принимается решение об обращении без чтения содержимого и без знания
типа*. Четыре первичные операции по паспорту: **сослаться · разместить · довериться · датировать.**

Владелец (N-048) делегировал решение агентам: «пусть сами подумают и решат задачу». Запущен автономный дебат —
адвокат-поле, адвокат-линза, архитектор. Этот ADR выносит твёрдое решение по пяти вопросам и фиксирует паспорт как
ратифицируемый артефакт. Фаза проекта — **дизайн, не код**; «строй» для `@ff/core` ждёт отдельной команды владельца.

Спор не разрешён владельцем напрямую — он передан агентам. Поэтому ADR обязан **решить**, а не вернуть вопрос.

## Decision

### 0. Сводка решений (одной строкой каждое)

1. **Уровень абстракции** — НЕ обязательное поле. Опциональный тег-подсказка `level?` (дефолт-от-типа, переопределяемый)
   + уровень = первоклассная ось **ЛИНЗЫ**; при конфликте линза/топология побеждает тег.
2. Принимаются 3 подтверждения архитектора (важность-на-ребре + один home + opt-in каскады; вектор = узел-линза;
   `epistemic`-enum + `draft`) — с уточнёнными инвариантами.
3. Авторизация `epistemic→fact`: **никогда не сам автор**; человек или verifier-агент; правило = узел `promotion-policy`;
   клапан = политика движка проверяет epistemic+sensitivity+principal на всех задействованных нодах; дефолт-закрыто;
   сторонним `→fact` запрещён.
4. Control-plane = **3 рода (ТИП · ЛИНЗА · ПАТТЕРН)**; ПОЛИТИКА = класс ЛИНЗЫ (hard-ABAC), не четвёртый род.
5. `stage` → движок (не паспорт); шкала `priority` → `number` на ребре, семантику задаёт линза-сортировщик;
   `canonical_id` → движок проставляет (опц. поле в паспорте, не ось); `instance_of` → отложить в модуль.

### 1. Уровень абстракции (почему/что/как/data) — РЕШЕНО: опциональный тег + ось линзы

**Решение.** Уровень абстракции НЕ становится обязательным несущим полем паспорта. Он фиксируется двумя носителями:

- **`level?`** — опциональный тег-подсказка в паспорте (класс «тег/аннотация» по N-042(б), НЕ несущая ось).
  Enum значений: `why | what | how | data`. **Механика дефолта (однозначно, закрывает замечание ред-тима 7a):** движок
  выводит дефолт из `type@version` ПРИ ИНДЖЕСТИИ (`principle→why`, `spec→what`, `guide→how`, `log-entry/metric→data`),
  поэтому для типов С дефолтом поле **де-факто почти всегда заполнено**. Пустым `level?` остаётся ТОЛЬКО для типов,
  у которых реестр типов не задал дефолт (тогда нет основания угадывать). Автор может переопределить выведенный дефолт.
  **Важно:** «де-факто почти всегда заполнен» НЕ делает `level?` обязательной несущей осью — отличие от обязательного
  поля принципиальное: (1) для ~20% наблюдатель-относительных нод значение **слабый приор, а не контракт**, и при
  конфликте **линза/топология ПОБЕЖДАЕТ тег** (см. правило конфликта ниже); (2) для структурно-плоских классов узлов
  (см. Consequences) тег — лучший доступный носитель, но всё равно переопределяемый, не истина. То есть это
  опциональное-с-дефолтом поле, чьё значение НЕ авторитетно — а не обязательное-с-дефолтом поле, чьё значение было бы
  единственным ответом всем наблюдателям. Спор §1 был про АВТОРИТЕТНОСТЬ (контракт vs приор), не про заполненность.
- **Уровень = первоклассная ось ЛИНЗЫ.** Истина об уровне «для этого наблюдателя» живёт в проекции, которую строит
  линза из топологии подграфа (ярус относительно якоря по осям `refines`/`grounds`/`home`/каскад) + предиката запроса.
  Линза может аннотировать каждый узел вычисленным `projected_level` как эфемерную метку ответа (как движок проставляет
  `stale`/`derived`).

**Правило конфликта:** при расхождении тега `level?` и вычисленного линзой уровня — **побеждает линза/топология**. Тег —
слабый приор (полезен на холодном старте, пока рёбер мало), не контракт.

**Почему так — взвешивание по 5 критериям задачи:**

- **(а) Практическая гарантия агенту действовать без вскрытия payload.** Адвокат-линза предъявил решающий
  контрпример к главному аргументу адвоката-поля: дихотомия «либо поле, либо вскрытие payload» — ложная. Есть третий
  источник уровня — **позиция в подграфе**, которую движок читает из рёбер (они и так несущие, видны без payload).
  Это удовлетворяет ровно тому же инварианту несущести, который защищает поле. Значит «без поля ИИ вынужден вскрыть
  payload» — неверно. Гарантия обеспечивается линзой, не полем.
- **(б) ~20% нод наблюдатель-относительны.** Оба адвоката согласились: уровень ко-вариантен наблюдателю для значимой
  доли граничных артефактов (ADR, стратегические задачи, сообщения, метрики — узлы B и C адвоката-линзы скользят по
  всей оси). Обязательное поле даёт ОДИН ответ всем наблюдателям → **ложная глобальная точность**: системно неверно
  для мульти-наблюдательной системы, которой проект является по построению (N-037 перцептивные углы, N-016 много
  агентов). Это не «медленно» — это «неверно».
- **(в) N-040 «простая ячейка».** Обязательное поле, по которому НЕЛЬЗЯ однозначно обращаться с ячейкой (т.к. значение
  зависит от наблюдателя), раздувает ядро и плодит непоследовательные/мусорные значения (этот риск признал сам
  адвокат-поле в «честной цене», §4.1). Это прямой анти-N-040. Тег + линза сохраняют ядро тонким.
- **(г) Асимметрия обратимости.** Добавить/промотировать тег позже — дёшево (R0). Вынуть обязательное поле из ядра
  позже = миграция всех узлов и всех запросов. По правилу обратимости (rules/evolution) дефолт — **не класть в ядро**.
- **(д) Не расщеплять единый рычаг ЛИНЗЫ.** RESEARCH §4/§5: «вектор наблюдения / уровень абстракции / авто-связи /
  зум секций / паттерны» оказались ОДНИМ механизмом — линзой. Вытащить уровень в обязательное поле = вернуть
  фрагментацию «пять подсистем», от которой синтез ушёл.

**Кого и что отвёл (честно):**

- **Отведён главный тезис адвоката-поля** («без обязательного поля ИИ вскрывает payload ⇒ поле несущее») — опровергнут
  топологическим контрпримером: уровень-из-позиции-в-графе удовлетворяет инварианту без поля. Его 4 сценария
  (суммаризатор/планировщик/обучатель/оркестратор) **покрываются линзой** через позицию-в-подграфе + предикат, а в
  контекстных случаях линза даёт ПРАВИЛЬНЫЙ (наблюдатель-зависимый) ответ, тогда как поле дало бы один неверный для
  всех.
- **Но зерно адвоката-поля принято**: для 80% «стабильных» нод уровень действительно почти инвариантен, и на холодном
  старте (пустой граф, бедная топология) линза слаба. Именно это закрывает **`level?` как опциональный приор с
  дефолтом-от-типа** — ровно компромисс, на котором оба адвоката сошлись («`level` с дефолтом-от-типа»). Реальный спор
  был ОБЯЗАТЕЛЬНОСТЬ vs ОПЦИОНАЛЬНОСТЬ — и он решён в пользу опциональности по критериям (б)(в)(г)(д).
- **Отведена слабость адвоката-линзы** (холодный старт, стоимость движка проекций, объяснимость) как НЕ перевешивающая:
  окна слабости линзы локальны и временны (закрываются тегом+дефолтом), ложь обязательного поля — глобальна и постоянна.

**Уверенность: высокая.** Четыре из пяти критериев и оба честно признанных слабых места сходятся на «опциональный тег +
ось линзы».

### 2. Три подтверждения архитектора — ПРИНЯТЫ (с уточнёнными инвариантами)

**(а) Важность-на-ребре + один home + opt-in каскады — ПРИНЯТО.** N-041 (важность относительна к родителю) и N-020
(один привилегированный home) ортогональны и складываются.

Инварианты BELONGING (несущие, проверяет движок при записи):
- **Ровно один home.** Среди входящих рёбер принадлежности ноды ровно одно несёт `home:true`. Ноль — только для
  корня/inbox (явные системные ноды). Два+ — ошибка целостности, запись отклоняется. `home` — флаг НА РЕБРЕ
  (уточнение к ADR-0001, где `home` был полем-указателем).
- **Слияние контекста только по home-ребру.** Каскад (наследование sensitivity-дефолтов, тегов-категорий, дефолтной
  линзы) идёт по home-ребру; прочие родители каскадят только при `cascade:true` + `cascade_order:<int>`. Конфликт
  соседних рёбер → выигрывает меньший `cascade_order`; home = неявный `cascade_order:0`. Детерминированно, без max/min/avg.
- **Разрешение РОМБА (DAG, не дерево) — детерминированное правило (закрывает блокер ред-тима 2.1a).** `cascade_order`
  разрешает конфликт соседних рёбер, но НЕ конфликт двух разных ПУТЕЙ к общему предку (узел D достижим из A через
  D→B→A и D→C→A). Правило:
  1. **Спина каскада — цепочка home-рёбер.** Базовое наследование контекста идёт ТОЛЬКО по home-спине (она ациклична
     по построению — ровно одно home на ноду, поэтому home-рёбра образуют лес). Это всегда даёт ровно один путь к
     предку и потому детерминировано без оговорок.
  2. **Не-home opt-in каскады вносят вклад по `cascade_order`** поверх home-спины (меньший порядок — выше приоритет).
  3. **Значение, достижимое несколькими путями (ромб), берётся по пути с наименьшей СУММАРНОЙ `cascade_order`** вдоль
     пути (home-рёбра = 0, поэтому home-путь всегда выигрывает у любого opt-in пути той же длины). **Тай-брейк:**
     ближайший предок (меньшая глубина пути), затем — **стабильный `id`** наименьшего предка. Это полностью снимает
     недетерминизм на уровне путей: при равенстве сумм всегда есть детерминированный финальный разрешитель (id).
  4. **Обход:** home-first, затем opt-in по возрастанию `cascade_order`; **первый визит узла выигрывает, повторный
     визit игнорируется** (защищает от ромба и от opt-in циклов вместе с `maxDepth`).
  5. **Произвольный DAG.** Полное слияние произвольного DAG (не сводимого к home-спине + редким opt-in) **отложено в
     спеку движка наследования** с ЭТИМ ЖЕ правилом nearest-wins + наименьшая-сумма-`cascade_order` + тай-брейк-`id`.
     Спека лишь обобщает уже зафиксированный здесь детерминированный принцип, не вводит новый.
- **Re-home при удалении/перемещении home-родителя (закрывает правку ред-тима 2.1b — сирота-кейс).** Удаление home-ребра
  у обычной ноды мгновенно нарушило бы инвариант «ровно один home». Правило движка: при удалении home-ребра движок
  ОБЯЗАН в той же транзакции либо (а) перевесить `home:true` на другого существующего родителя по детерминированному
  правилу (наименьший `cascade_order` среди оставшихся рёбер принадлежности; тай-брейк — стабильный `id` родителя),
  либо (б) если других родителей нет — перевести ноду в inbox (системный home), либо (в) заблокировать удаление,
  если политика типа это требует. Дефолт: (а)→(б). Сироты без home (кроме корня/inbox) недопустимы ни на миг.
- **Глобальной важности нет.** Запрос «важность ноды X» без контекста-родителя невалиден (движок возвращает карту
  `{parentId→priority}`). Запрос планировщика «что делать сейчас?» требует якорь; дефолтный якорь = home-ребро.

**(б) Вектор наблюдения = узел-ЛИНЗА, не поле ноды — ПРИНЯТО (единогласно).** Вектор = отношение наблюдатель→подграф;
полем дал бы God-object. Линза = сохранённый узел control-plane (предикат + политика раскрытия + класс hard-ABAC/soft).
Паспорт даёт лишь ОСИ фильтрации (`type`, `epistemic`, `sensitivity`, время, home/принадлежность, опц. `level?`).
Уточнение: `level?` — ещё одна ось фильтрации, не «вектор». Вектор остаётся линзой при любом исходе спора §1.

**(в) `epistemic` enum + `draft` — ПРИНЯТО.** `epistemic: draft | proposal | hypothesis | fact | archived`. Это ось
**доверия к содержимому**, ортогональная `state` (рабочий процесс, типо-зависим, в модуле). Порядок зрелости
`draft → proposal → hypothesis → fact`; `archived` — терминальный вне линии. `draft` = «человек ещё пишет»;
`proposal` = «агент предложил». Флаг на будущее (не блокер): если ось начнёт нести два смысла (зрелость документа ⟂
доверие к утверждению), расщепить `epistemic ⟂ maturity`; сейчас НЕ делаем.

### 3. Авторизация `epistemic→fact` + клапан — ПРИНЯТА модель архитектора

**Принцип:** право поднимать `epistemic` и право на необратимое внешнее действие = **политики**, живущие как
**узлы-политики** в графе (control-plane = данные). Движок — исполнитель (enforcement), правило — данные.

**Лестница доверия:**

| Переход | Кто авторизован | Где правило |
|---|---|---|
| `draft → proposal` | автор-агент или человек (любой first-party) | дефолт-политика |
| `proposal → hypothesis` | агент с capability `assert:hypothesis` | узел-политика |
| `hypothesis → fact` | **НЕ сам автор.** Только: (1) человек-владелец; (2) агент с явной capability `assert:fact` для данного type/scope; (3) verifier-агент ≠ автор (разделение обязанностей) | узел `promotion-policy` |
| `* → fact` сторонним (3rd-party) агентом | **запрещено** дефолтно | узел-политика + principal |

Инварианты:
- **Самоповышение до `fact` запрещено** — закрывает дыру «клапан открыт по самооценке» (RESEARCH §4.1).
- **Каждое повышение логируется трейс-узлом** (`actor`, `from`, `to`, `policy_ref`, `ts`) — наблюдаемость.
- **first-party vs сторонний** различается по `principal` + `source` (оба типизированы, в паспорте/ребре).

**Узел-политика** `promotion-policy` (контракт):
```
{ applies_to: <type|scope|*>, transition: "hypothesis→fact",
  requires: { capability: "assert:fact", actor_class: "human|verifier-agent", not: "author" },
  principal_scope: <id> }
```

**Клапан внешних действий** (политика движка, НЕ ось ноды). Перед любым необратимым внешним действием (отправить,
оплатить, удалить вовне) движок:
1. Собирает **прямо задействованные ноды** (см. ГРАНИЦУ ниже).
2. Проверяет `epistemic` каждой. **Хоть одна не `fact` → действие закрыто** (дефолт-закрыто, требует апрува).
3. Проверяет `sensitivity` каждой против политики раскрытия адресата (не утекает ли приватное).
4. Проверяет `principal`: действует ли агент в рамках своего арендатора/scope.
5. Закрыто → эскалация владельцу ИЛИ опц. ручной `override` (логируется).

**ГРАНИЦА замыкания клапана v1 (закрывает блокер ред-тима 3.2).** «Все транзитивно задействованные ноды» без границы
непригодно: в связном графе жизни транзитивное замыкание ≈ весь граф, в нём почти всегда найдётся хоть одна не-`fact`
нода → клапан становится «всегда-закрыто», владельца спамит апрувами. Поэтому:

- **v1-клапан проверяет ТОЛЬКО ПРЯМО задействованные ноды:** (а) явные входы действия (ноды, переданные агентом как
  аргументы операции) + (б) явно процитированные ноды (на которые агент сослался по `id` в обосновании действия).
  **НЕ транзитивное замыкание** подграфа.
- **Распространение доверия по транзитиву (trust horizon) отложено в ADR-0003.** Там решается, как далеко по цепочке
  выводов проверять `epistemic` (1 хоп? home-цепочка до maxDepth? полное замыкание с порогами?) — это самостоятельная
  модель доступа, не часть тонкого паспорта.
- **Дефолт-закрыто сохраняется** на прямой границе: если хоть одна ПРЯМО задействованная нода не `fact` → закрыто.
  Сужение границы НЕ ослабляет дефолт — оно делает его исполнимым, а не гипер-консервативным до неюзабельности.

Таким образом модель клапана РЕШЕНА (дефолт-закрыто, автор ≠ авторизатор, прямая граница), а ширина транзитивного
горизонта доверия — явный открытый вопрос ADR-0003, а не молчаливо «решённое».

**Уверенность:** модель — высокая; конкретные пороги/детали политик — средняя (настраиваемо узлами-политиками).

### 4. Control-plane: 3 рода, не 4

**Решение: 3 рода — ТИП · ЛИНЗА · ПАТТЕРН.** ПОЛИТИКА (доверие/доступ/раскрытие) = **класс ЛИНЗЫ hard-ABAC**, а не
отдельный четвёртый род.

Архитектор честно вынес развилку: его блокер §2 показал, что доверие/доступ — отдельный род контракта (`promotion`/
`valve`/`disclosure` enforce-points), и предложил ПОЛИТИКУ четвёртым родом с пометкой «возможно подвид ЛИНЗЫ класса
hard-ABAC; уверенность средняя».

**Решаю в пользу 3 родов**, потому что:
- Линза УЖЕ определена как «предикат отбора + политика раскрытия (id/title/payload) + **класс: hard-ABAC vs
  soft-перцепция**» (architect §1(б), RESEARCH §3.3). Класс hard-ABAC — это и есть политика доступа/раскрытия.
  Вводить её четвёртым родом = дублировать ось, которая уже встроена в линзу.
- `promotion-policy` (кто поднимает epistemic) — это предикат над `actor`/`principal`/осями паспорта, применяемый в
  enforce-point движка. Структурно это линза-класс-hard-ABAC с enforce-point `promotion` вместо `disclosure`. Тот же
  контракт `condition(actor, principal, осиПаспорта) → allow|deny`.
- N-040: меньше родов при той же выразительности — предпочтительнее. Три рода уже покрывают «как вскрыть одну ячейку
  (ТИП) · как спроецировать подграф (ЛИНЗА, вкл. hard-ABAC) · как собрать из многих (ПАТТЕРН)».

**Честно:** ПОЛИТИКА получает собственный **enforce-point** (`promotion | valve | disclosure`) внутри класса ЛИНЗЫ —
это не «спрятать» её, а классифицировать. Если практика покажет, что hard-ABAC-линзы и soft-perception-линзы расходятся
настолько, что общий контракт мешает — расщепить ПОЛИТИКУ в 4-й род (обратимо, R1). **Уверенность: средняя-высокая.**

**Контракты родов (минимальные):**

| Род | Что делает | Контракт |
|---|---|---|
| **ТИП** | вскрыть ОДНУ ячейку | `{ name, version, payload_schema, validate(node)→ok\|errors }` |
| **ЛИНЗА** | найти/спроецировать ПОДГРАФ | `{ predicate(осиПаспорта+level?), disclosure: id\|title\|payload, class: hard-ABAC\|soft-perception, enforce_point?: promotion\|valve\|disclosure, sort? }` |
| **ПАТТЕРН** | собрать подграф из многих | `{ compose(подграфы)→подграф, recursion_terminator, maxDepth }` |

### Зафиксированный паспорт (итог)

#### ПАСПОРТ — несущие поля ноды (читаются без вскрытия payload)

| Поле | Тип | Операция | Обяз. | Примечание |
|---|---|---|---|---|
| `id` | ULID | сослаться | да | стабильный ключ связей; ≠ имя файла/title |
| `type` | string | разместить/вскрыть | да | открытый реестр; правила → узел-ТИП |
| `schema` | `type@version` | вскрыть | да | какой валидатор; миграции |
| `created` | iso | датировать | да | системное время |
| `updated` | iso | датировать | да | системное; `stale` выводит движок |
| `epistemic` | enum | довериться | да | `draft\|proposal\|hypothesis\|fact\|archived` |
| `sensitivity` | enum | довериться | да | приватность/ACL; ИИ знает без вскрытия payload |
| `source` | enum | довериться | да | `human\|agent\|system\|import` (типизирован) |
| `principal` | id (тонкий) | довериться/разместить | да | арендатор; multi-tenant/маркетплейс заблокированы без него |
| `level?` | enum | (фильтрация) | **нет** | `why\|what\|how\|data`; тег-подсказка; движок выводит дефолт-от-типа при инджестии (де-факто почти всегда заполнен); пуст только для типов без дефолта; линза побеждает при конфликте — значение приор, не контракт |
| `canonical_id?` | id | сослаться | нет | дедуп; **движок** проставляет, не грань-ось. В паспорте (не в производном-движком как `stale`), потому что это **стабильная ссылочная цель операции «сослаться»** (на него ссылаются другие ноды) — должно быть частью идентичности, а не эфемерной меткой ответа; `stale` ни на что не ссылается (замечание ред-тима 5.2 разрешено) |

#### Минимальный payload (НЕ паспорт, не несущая ось — для согласованности оформления)

`title` и `description` — agent-first резюме, которое автор пишет почти всегда, но это **payload, а НЕ несущие поля
паспорта** (по ним не принимается решение об обращении без чтения; это и есть само краткое содержимое). Держим их
явно отдельной строкой, чтобы устранить несоответствие с текстом: «9 обязательных + 2 опц.» относится к НЕСУЩИМ полям
паспорта; `title`/`description` де-факто всегда присутствуют, но считаются минимальным payload, не паспортом.

| Поле | Тип | Слой | Обяз. | Примечание |
|---|---|---|---|---|
| `title` | string | payload (не паспорт) | де-факто да | короткий ярлык; читается первым, но это содержимое, не несущая ось |
| `description` | string | payload (не паспорт) | де-факто да | 1-2 строки agent-first резюме; содержимое, не несущая ось |

**Намеренно НЕ в паспорте:** `importance`/`home`→ребро · `priority`→ребро · `occurred`/`valid_*`→модуль · `state`→модуль ·
`stage`→движок · `actor`/`trace`→движок · `supersedes`→ребро · `branches`/`reactivity`→движок/модуль · `instance_of`→модуль ·
`tags`-фасеты→**рёбра-категории** (см. ниже) · payload→тип.

**Теги-фасеты (закрывает замечание ред-тима 6.2a — молчаливая потеря).** ADR-0001 имел `tags: [..]` (сквозные
фасеты/направления, НЕ принадлежность; N-039 «теги ≈ типы», N-042б «теги двух родов»). Решение: фасеты-направления
становятся **рёбрами-категориями** (`rel: facet-of` / `tagged-as` → узел-категория), НЕ полем-массивом на ноде. Это
согласуется с «связи по id» и «control-plane = узлы»: категория — это узел, принадлежность к ней — ребро. Тег-аннотация
рода `level?` (N-042б другой род) остаётся опц. полем паспорта. Таким образом теги ADR-0001 НЕ потеряны: фасеты→рёбра,
аннотация-уровня→`level?`. (Внесено в Supersedes #9 как уточнение.)

#### РЕБРО — несущие поля связи

| Поле | Тип | Обяз. | Примечание |
|---|---|---|---|
| `to` | id \| url | да | цель; url → внешняя (`href:true`) |
| `rel` | string | да | типизированная связь (child-of/involves/supersedes/variant-of/…) |
| `home` | bool | да* | *на рёбрах принадлежности; ровно одно `true` на ноду |
| `priority` | number | нет | важность В контексте этого родителя (N-041); дефолт 0 |
| `sort` | string | нет | вторичный ключ сортировки |
| `cascade` | bool | нет | участвует ли в наследовании контекста (не-home opt-in) |
| `cascade_order` | int | нет | порядок слияния; home = неявный 0 |
| `provenance` | enum | да | `manual\|auto\|inferred`; manual=файл-истина, auto=движок |
| `derived` | bool | нет | true ⇒ ребро вывел движок (+ `rule_ref`); не истина-файл |

#### ДВИЖОК (`@ff/core`, без ИИ)

Сериализация frontmatter↔узел; реестр типов + наслоённая валидация; сбор графа из рёбер + backlinks; **цикл-гард +
`maxDepth`**; вывод производного (`stale`, `canonical_id`, авто-рёбра `derived:true`+`rule_ref`); **enforcement**
(инвариант одного home, слияние контекста, `promotion-policy`, клапан); контракт запроса с viewport (линза применяется
здесь); трейс-узлы; `section-index`-конвенция (ленивая загрузка огромных секций); вывод дефолта `level?` из типа.

#### CONTROL-PLANE — узлы графа (3 рода)

ТИП · ЛИНЗА (вкл. уровень абстракции как ось, hard-ABAC/soft-perception классы, `promotion`/`valve`/`disclosure`
enforce-points) · ПАТТЕРН. Узлы-политики (`promotion-policy`, ABAC/раскрытие) = линзы класса hard-ABAC.

## Alternatives considered

1. **Уровень абстракции = ОБЯЗАТЕЛЬНОЕ поле паспорта `level: why|how|what|data` (позиция адвоката-поля).**
   Отклонено. Сильнейшие аргументы (4 сценария вскрытия payload) опровергнуты топологическим контрпримером: уровень-
   из-позиции-в-подграфе удовлетворяет инварианту несущести без поля. Обязательность даёт ложную глобальную точность
   для ~20% наблюдатель-относительных нод (системная ложь в мульти-наблюдательной системе), нарушает N-040 (раздувает
   ядро полем, по которому нельзя однозначно действовать) и проигрывает по асимметрии обратимости. Зерно позиции
   (стабильные 80% + холодный старт) сохранено в виде опционального `level?` с дефолтом-от-типа. **Это проигравшая
   сторона спора — отведена честно, по существу, а не по умолчанию.**

2. **Уровень абстракции = чистая ось линзы, БЕЗ тега на ноде (крайняя позиция адвоката-линзы).**
   Отклонено как недостаточное. Адвокат-линза сам признал остаточный случай (автор хочет заявить намерение узла до
   вплетения в граф; холодный старт пустого графа). Опциональный `level?` закрывает это окно — поэтому берём
   тег + ось, а не только ось.

3. **Control-plane = 4 рода (+ ПОЛИТИКА).** Отклонено (с явным признанием развилки архитектора). ПОЛИТИКА сводится к
   классу ЛИНЗЫ hard-ABAC с собственным enforce-point; четвёртый род дублирует уже встроенную в линзу ось класса.
   Обратимо при необходимости.

4. **`stage` / обязательная `importance:1..5` / `home`-поле-указатель / битемпоральность в ядре (ADR-0001).**
   Отклонены/перенесены: `stage`→движок, `importance`→`priority` на ребре, `home`→флаг на ребре, `occurred`/`valid_*`→
   модуль. См. Supersedes.

5. **Самоповышение `epistemic→fact` агентом по самооценке (статус-кво до этого ADR).** Отклонено — это и есть открытый
   клапан, названный «первым к закрытию» в ADR-0001. Закрыто разделением обязанностей (автор ≠ авторизатор).

## Consequences

**Плюсы:**
- Паспорт остаётся тонким (9 обязательных + 2 опц. поля) — прямое исполнение N-040 «простая ячейка → много возможностей».
- Уровень абстракции работает контекстно (правильный ответ на наблюдателя) без раздувания ядра и без миграционного риска.
- Единый рычаг ЛИНЗЫ не расщеплён: вектор/уровень/авто-связи/зум/паттерны — один механизм, один движок проекций.
- Клапан из декларации стал механизмом: дефолт-закрыто, автор ≠ авторизатор, правило = данные (узел-политика).
- Control-plane самохостится (3 рода = узлы графа) — «всё видно ИИ» работает и для управляющего слоя.

**Минусы / принятые издержки:**
- **Холодный старт линзы** (пустой/бедный рёбрами граф) — уровень опирается только на слабый `level?`+дефолт. Принято:
  окно локально и временно, закрывается ростом графа.
- **Структурно-плоские классы узлов** (млн сообщений чата N-043, импорты, потоки метрик) — у них топология НЕ
  «дозреет» рёбрами иерархии, поэтому линза-из-топологии для них слаба не временно (холодный старт), а **структурно
  постоянно**. Для таких классов `level?`-тег (дефолт-от-типа: `message→data`, `metric→data`) — практически
  единственный носитель уровня. Принято: для плоских классов уровень и так почти инвариантен (`data`), поэтому
  дефолт-от-типа достаточен; тег остаётся приором (линза не обязана его подтверждать), и это НЕ возвращает обязательное
  поле — для плоских классов нет наблюдатель-относительности, ради которой поле было бы вредно. (Замечание ред-тима
  1.3 учтено: роль `level?` для плоских классов названа явно — основной носитель там, где топологии нет по природе.)
- **Стоимость движка проекций** до первого полезного результата выше, чем наивный `WHERE level=`. Принято: уровень-из-
  топологии всё равно нужен движку для зума/каскада/maxDepth — амортизированная стоимость, не новая.
- **Объяснимость проекции** («почему этот узел показан как why») сложнее, чем для поля. Принято: линза обязана уметь
  объяснять свою проекцию (требование N-040 «объяснимая система»).
- **3 рода control-plane** могут оказаться тесными для ПОЛИТИКИ — флаг на расщепление в 4-й род, если практика покажет.

**Риски:**
- R1: непоследовательное заполнение `level?` авторами → митигируется тем, что тег не несущий (линза побеждает) +
  движок-дефолт + валидатор-предупреждение.
- R2: недоопределённые предикаты линз → уровень «прыгает» между запросами. Митигация: линзы — версионируемые узлы
  control-plane; плохая линза правится как данные, не как код.
- R3: ошибка в `promotion-policy`/клапане → ложно-открытое внешнее действие. Митигация: дефолт-закрыто + трейс каждого
  повышения + эскалация владельцу.
- **R4 (флаг доступа при маркетплейсе — замечание ред-тима 4.2): сторонний код может зарегистрировать узел-линзу
  класса hard-ABAC с `enforce_point: promotion|valve` и ослабить клапан под видом «перцептивной линзы».** Поскольку
  ПОЛИТИКА = класс ЛИНЗЫ (3 рода, §4), граница доступа проходит ВНУТРИ рода узлов, которые пишет и сторонний субъект.
  **Митигация, фиксируется СЕЙЧАС (даже при отложенном расщеплении родов):** регистрация узлов класса `hard-ABAC` с
  `enforce_point ∈ {promotion, valve}` — **first-party-only** (только владелец/доверенный principal). Сторонний
  (3rd-party) код может регистрировать только `soft-perception`-линзы и `disclosure`-проекции, но НЕ
  promotion/valve-политики. Структурный gate на регистрацию детализируется в ADR-0003; до него действует дефолт-запрет
  на сторонние hard-ABAC/valve-узлы. Это снимает «сторонний код пишет себе политику».

## Validation plan

1. **Прогнать зафиксированный паспорт против 50 ячеек стресс-теста** (метрики, люди, память агента, трейсы, конфиги,
   сообщения чата) — подтвердить, что ни один сценарий не требует нового обязательного поля и что `level?`+линза
   покрывают 4 сценария адвоката-поля без вскрытия payload.
2. **Проверить инвариант «ровно один home»** на узлах с N родителями (мультиплановость N-036) — движок отклоняет 0/2+.
3. **Проверить слияние контекста** детерминированно по `cascade_order` (нет max/min/avg).
4. **Промоушн `epistemic`:** агент НЕ может поднять собственный вывод до `fact`; verifier-агент/человек — может;
   сторонний → запрещён. Трейс-узел создаётся на каждое повышение.
5. **Клапан:** необратимое внешнее действие при хоть одной не-`fact` ноде → закрыто/эскалация; при всех `fact` +
   sensitivity ок + principal в scope → разрешено.
6. **Walking skeleton (захват→хранение→связь→достать)** на паспорте БЕЗ обязательного `level`, с одним типом, ТИП-родом
   и минимальной ЛИНЗОЙ — подтвердить, что фундамент стоит без отложенных частей.
7. **РОМБ-наследование (закрывает 2.1a/7d):** узел, достижимый к общему предку двумя путями (home-путь + opt-in путь).
   Проверить детерминизм: значение берётся по наименьшей сумме `cascade_order`, тай-брейк nearest→`id`; повторный
   визит игнорируется. Результат стабилен между прогонами. Заодно проверить, что `refines`/`grounds`/`home`/каскад
   как класс рёбер-иерархии (носитель уровня для линзы, замечание 1.2a) присутствуют в реестре `rel` и движок умеет
   считать ярус по ним; зафиксировать, чем гарантируется их наличие (инференс движка vs обязательность для типа).
8. **СИРОТА при удалении home-родителя (закрывает 2.1b/7d):** удалить home-ребро у обычной ноды → движок в той же
   транзакции перевешивает home (наименьший `cascade_order`→`id`) ИЛИ переводит в inbox; нода никогда не остаётся без
   home (кроме корня/inbox).
9. **ГРАНИЦА клапана (закрывает 3.2/7d):** действие с прямым входом-`fact`, но с процитированной не-`fact` нодой в
   ПРЯМОЙ границе → закрыто. Действие, где не-`fact` нода лежит ТОЛЬКО в транзитивном замыкании (не прямо задействована)
   → НЕ блокируется v1-клапаном (trust horizon отложен в ADR-0003). Подтвердить, что v1 исполним, а не «всегда-закрыто».
10. **Сторонний код пишет hard-ABAC/valve-узел (закрывает 4.2/7d):** попытка регистрации 3rd-party узла-линзы класса
    `hard-ABAC` с `enforce_point ∈ {promotion, valve}` → отклонена (first-party-only); `soft-perception`/`disclosure`
    от стороннего — разрешены. Подтверждает, что граница доступа не выставляется сторонним кодом.

> MUST-FIX ревьюера (до ИСПОЛНЕНИЯ этого плана, не до подписи): список 50 ячеек (п.1) и 4 тест-кейса адвоката-поля
> (суммаризатор/планировщик/обучатель/оркестратор, для п.1) фиксируются в `docs/qa/VALIDATION-0002-50cells.md`.

#### Процессное правило статуса ADR-0001 (закрывает блокер ред-тима 6.1)

ADR-0001 находится в статусе `review` (не `approved`), с пометкой «требует ревизии v2.1 / 9 правок до кода». Нельзя
оставить два недо-approved документа об одном предмете (схема узла) — это нарушает docs-standard и source-of-truth
Rule 2 («approved beats draft»). Поэтому **при ратификации этого ADR действует следующее процессное правило**:

- **ADR-0001 переводится в статус `superseded (partial) by ADR-0002`** одним действием оркестратора в момент
  ратификации. ADR-0002 не «дописывает черновик» — он **поглощает и заменяет** ревизию v2.1 ADR-0001.
- **Сохраняемые принципы ADR-0001 считаются ПЕРЕНЕСЁННЫМИ в ADR-0002** (перечислены строкой выше: agent-first,
  файлы=истина, всё-видно-ИИ first-party, открытые типы, `epistemic ⟂ state`, связи по `id`, границы
  СКИЛ/АГЕНТ/ДВИЖОК). После ратификации **ADR-0002 самодостаточен** как источник истины по схеме узла; ADR-0001
  читается только как исторический контекст и НЕ является актуальным контрактом ни в одной части.
- Таблица Supersedes (12 строк выше) фиксирует, что именно заменено/уточнено/дополнено; всё, не перечисленное в ней
  как «Supersede/Уточнение», но названное в «сохраняет без правок» — наследуется ADR-0002 дословно.

Это снимает «два частично-живых ADR»: после ратификации жив один (ADR-0002, approved), ADR-0001 — superseded целиком.
(Сам статус ADR-0001 в его файле меняет ОРКЕСТРАТОР при ратификации — см. вердикт `docs/product/VERDICT-2026-06-21-ratify.md` §4.)

**Дальнейшее:** клапан/ABAC детализируется отдельным **ADR-0003** (модель доступа, principal-scope, disclosure-политики,
**граница транзитивного замыкания клапана / trust horizon**, **семантическая независимость verifier**,
**first-party-only gate на регистрацию hard-ABAC/valve-узлов**). `instance_of`/рекуррентность — Этап 2 (внутренняя
структура ячейки/модули).
