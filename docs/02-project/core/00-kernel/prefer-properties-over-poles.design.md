# 🎚 Prefer-Properties-over-Poles — развилку разрешаем свойством, не глобальным бинаром

> ✅ **РАТИФИЦИРОВАНО 2026-07-26** (P-1, канон метода ядра). Акт:
> `./decisions/2026-07-26-ratification-p1-block1-b2a.decision.md`.

> **Источник (владелец, голос 2026-07-26, развилка B2-a).** «Не выбирать полюс — сделать оба через
> настройку; и вообще спросить, ЗАЧЕМ выбирать. База должна быть ГИБКОЙ.» Этот файл поднимает реплику в
> метод ядра и — главное — ставит ему ГРАНИЦЫ, чтобы гибкость не превратилась в death-by-design.

---

## 1. Правило (в одну строку)

**Прежде чем разрешить любую развилку «да/нет», прогони её через тест «оба / либо / комбинация / спектр».
Если хоть один вариант законен для РАЗНЫХ единиц — не выбирай глобальный полюс, а сделай развилку
СВОЙСТВОМ (паспортное поле / policy-as-data / lens-конфиг) с разумным дефолтом.**

Полюс замораживает модель. Свойство её раскрывает — и решение перестаёт быть хардкодом.

Это НЕ новьё для проекта — это уже дважды принятый разворот:
- L0-В1: «не единый глобус агрессивности забывания, а **свойство самих данных**».
- combinator (terminology §4): «ВЫБОР = данные (R1); РЕАЛИЗАЦИЯ = движок (R3)».
Этот файл делает разворот **методом по умолчанию**, а не разовым инсайтом.

## 2. Три уровня разрешения развилки

Развилка почти никогда не «одна кнопка». У неё есть естественная ВЫСОТА — выбери минимальную, где она честно живёт:

1. **Уровень единицы (паспортное поле узла).** Свойство самой вещи. Пример: `temporal: uni | bi`
   (нужна ли узлу битемпоральность) — уже реализовано на `meta:type`. Дом — тонкий паспорт.
2. **Уровень связи (поле/тип ребра).** Развилка живёт НЕ в вещи, а в отношении. Пример: «насколько
   единица влияет на другую» = `confidence`/`priority` на insight-EDGE (В4). «Влияние на другое» —
   всегда ребро, не поле узла. Это и есть измерение «как единица влияет на другое», которое просил владелец.
3. **Уровень policy-as-data (каскад per-scope).** Одно значение не подходит всем контекстам → правило
   в данных, сворачиваемое LSR-стеком (`node > space > project > module`) через `resolve()`. Пример:
   retention `observation` — «прунить или нет» решает политика скоупа, не глобальный флаг.

Правило высоты: **бери самый нижний уровень, где развилка честно принадлежит.** Не тащи в policy то,
что есть свойство одной вещи; не хардкодь то, что расходится по скоупам.

## 3. Дефолт-с-гибкостью (а не дефолт-вместо-гибкости)

Свойство ВСЕГДА получает разумный дефолт — но дефолт **переключаем**, не зашит.

- База остаётся гибкой: значение живёт в данных (паспорт/policy), меняется без правки движка.
- Решение не «выбрано навсегда» — оно **отложено в данные** с безопасным стартовым значением.
- Дефолт выбираем по правилу §5.3 (консервативный/обратимый полюс), а не «что удобнее сейчас».

## 4. ⚠️ Границы — что НЕЛЬЗЯ property-ize (антидот death-by-design)

Метод опасен ровно тем, чем полезен. Три ловушки:

### 4a. Настоящие инварианты остаются ЖЁСТКИМИ
Некоторые «развилки» — не выбор, а ЗАЖИМ, который держит систему. Сделать их конфигом = пробить дыру,
которую нельзя закрыть снаружи. Такие НЕ property-ize:
- **append-only / иммутабельность акта** (I-3, I-4) — «забыть» настраивается ВИДИМОСТЬЮ (проекция), но
  сам журнал не стирается по флагу. Конфиг «append-only: off» = потеря истории навсегда.
- **deny / Конституция как зажим ПОСЛЕ свёртки** (I-8) — запрет не может быть «ещё одним настраиваемым
  слоем», иначе его перебьёт слой выше. Пол/потолок не конфигурируются данными.
- **единственный PEP `resolve()`** (I-7), **fail-closed** (I-9), **admission-gate на входе** — врата не
  делаются опциональными; «пускать без проверки» — не настройка, а брешь.
- **стабильность id** (I-1) — идентичность не «свойство на выбор».

### 4b. Тест-различитель «свойство-гибкости vs жёсткий-инвариант»
Прогони кандидата через ТРИ вопроса. Хоть одно «да» → это ЖЁСТКИЙ инвариант, не свойство:

| # | Вопрос | «Да» означает |
|---|--------|---------------|
| **T1 · Локальность** | Если РАЗНЫЕ единицы держат разные значения — рушится ли гарантия, на которую опираются ДРУГИЕ единицы/движок? | Гарантия ГЛОБАЛЬНА → жёсткий инвариант (напр. append-only: цепочка аудита узла B ходит через узел A). |
| **T2 · Асимметрия побега** | Есть ли значение, которое УБИРАЕТ пол/потолок/врата (позволяет обойти зажим)? | Это clamp/gate/ledger, не преференция → жёсткий. |
| **T3 · Безопасность строгого полюса** | Самое СТРОГОЕ значение — безопасно и осмысленно? Если полезность требует ПЕРМИССИВНОГО дефолта — подозрительно. | Свойство-гибкости обязано уметь дефолтиться в безопасный полюс и всё равно работать. |

Короткая формула: **свойство-гибкости — ЛОКАЛЬНО и обратимо; его строгий полюс всегда безопасен.
Жёсткий инвариант — ГЛОБАЛЕН, и у него есть полюс, снимающий защиту.**

### 4c. Комбинаторный взрыв — не каждое поле должно быть настраиваемым
Каждое переключаемое поле умножает пространство состояний и стоимость понимания. Гибкость — это ПАССИВ,
который оплачивают. Плати только когда **два реальных случая расходятся**.
- Нет двух живых единиц, которым нужны разные значения → это НЕ свойство, а фиксированный дефолт.
- Ср. L0: из 11 осей в канон вошло 6, реально новых — ОДНА (волатильность/ставки). Тонкий паспорт — цель,
  не побочка (Г1). Бюджет внимания — ИНВАРИАНТ, не рычаг (Г15).
- Правило: **свойство появляется по факту расхождения, а не «на всякий случай».** Иначе не единица — хаос.

## 5. Применение: B2-a рефлексивность памяти — ложная дилемма

Развилка (KQ-11-Q1): питает ли `observation`-акт запоминания обратно вход будущего recall —
**ДА (рефлексивно)** vs **НЕТ (инертный audit-trail)**?

### 5.1. Почему это ложный выбор — «оба» достигается СЛОЯМИ, не переключателем
- **Инертный audit-trail — это САМ субстрат, не полюс.** Акт `observation` фиксируется всегда
  (append-only, I-3). Это ФЛОР, который есть по определению — его не «выбирают».
- **Рефлексивное подкрепление recall — это ПРОЕКЦИЯ/policy СВЕРХ субстрата.** Влияние на ранжирование
  живёт в rebuildable-проекции (I-6/I-14), не в каноне.
- Значит слои независимы: инертное — снизу (всегда), рефлексивное — сверху (опционально). «Оба» = два
  разных этажа, а не одна кнопка. Дилемма растворяется.

### 5.2. Предложенное свойство: `recallFeedback` (паспорт-дефолт + policy-override)
Уровень 1 (паспорт единицы/типа) с каскадным override policy-as-data (уровень 3). Значения:

| Значение | Что делает | Пишет ли новый канон? | Обратимо? |
|----------|-----------|----------------------|-----------|
| `off` | observation фиксируется (аудит), но НИКОГДА не влияет на recall. Чистый инертный след. | нет | — |
| `passive` *(дефолт)* | observation влияет на salience/ранжирование наблюдаемой единицы, но НЕ создаёт новых адресуемых узлов. Влияние живёт в rebuildable-проекции. | нет | да (rebuild проекции) |
| `active` | recall порождает новые observation/insight-РЁБРА (память-о-запоминании), которые сами адресуемы и питают вперёд. | **да (канон)** | только эрейжем |

### 5.3. Обоснование дефолта = `passive`
- **Не `off`:** L0 прямо говорит «память замыкается на использование; без обратной петли — каталог, не
  память» (Г2 запах/резонанс, Г7 живое доверие). `off` убивает саму ценность памяти.
- **Не `active`:** `active` пишет НОВЫЙ канон, который питает сам себя → дрейф/самоусиление вбивается в
  историю и снимается только эрейжем (необратимо).
- **`passive` проходит T3:** его влияние живёт в проекции (I-6/I-14) — дрейф ОБРАТИМ через rebuild из
  канона. Ценность «память на использовании» есть; необратимого самозаписывания — нет. Это безопасный
  полюс, который всё равно работает.

### 5.4. Риск — рефлексивная петля (владельцу видеть)
`active` (и в меньшей мере `passive` при компаундинге) даёт **самоусиление**: «часто вспоминаемое
вспоминается ещё чаще» → память дрейфует к rich-get-richer, теряет калибровку доверия (Г7). Нужен
**клапан затухания** (decay/damping, ограниченный gain) — особенно для `active`, где дрейф каноничен.
Для `passive` спасает rebuild (сброс проекции). → Открытый под-вопрос: параметры затухания = отдельное
свойство метаболизма (фаза C), не решать здесь.
