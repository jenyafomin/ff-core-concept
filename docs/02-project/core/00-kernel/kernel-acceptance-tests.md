# Kernel Acceptance Tests — 7 практических проверок «ядро получилось правильным» (T-1..T-7)

> **PLACEMENT:** staged in `00-kernel/` autonomously per night handoff 2026-07-25 (тот же дом, что
> `invariants.md`/`terminology.md`/`open-questions.md`); владелец может перенести узел — **обратимо**.

Этот файл — **acceptance-контракт**, парный к [`invariants.md`](./invariants.md): там — ЧТО ядро обязано
гарантировать всегда (I-1..I-14), здесь — КАК мы это проверяем практическим прогоном, а не на словах.
`invariants.md` уже несёт теги `proven-by:` на каждый инвариант, ссылающиеся на эти семь тестов; здесь
связь становится **двусторонней** — см. §Test → invariant matrix.

## Зачем практические тесты, а не красота абстракции

GPT-review (§«Как понять, что ядро получилось правильным», `docs/_inbox/1-gpt-review/2-overview-direction.md`)
называет это прямо: «Не по количеству классов и не по красоте abstraction layer. Проверка должна быть
практической.» Причина — та же, что стоит за самими инвариантами (`invariants.md` §«Зачем этот файл»): если
критерий «ядро готово» расплывчат («выглядит стройно», «модель элегантна»), **код начинает принимать
архитектурные решения случайно** — один разработчик тихо добавит bespoke-таблицу под удобный шорткат, другой
захардкодит `if (project === 'alpha')`, и заявленная архитектура разойдётся с фактической в первый же месяц.

Семь тестов ниже — это **фальсифицируемые** проверки: у каждой есть конкретный CLI-вызов (или явно
обозначенное «команды ещё нет — контракт цели», когда механизм отложен) и PASS/FAIL критерий, который можно
исполнить на seed-корпусе, а не оценить «на глаз». Это тот же принцип, что уже применён в
`vertical-scenario.spec.md` §Acceptance criteria (a): «прогон» = конкретный CLI-вызов с ожидаемым результатом.

**Три вещи, которые в сумме доказывает весь набор T-1..T-7** (эхо GPT-review §Итог, уже сформулированное в
`vertical-scenario.spec.md` §Problem):
1. Новая модель подключается без перестройки ядра (T-1).
2. История, права и retrieval остаются согласованными при добавлении/смене модулей (T-2, T-3, T-5, T-6).
3. Каждое изменение объяснимо и восстановимо (T-4, T-7).

Честность прежде оптимизма: часть тестов в Фазе 1 **STUBBED** (механизм реален, качество — заглушка) или
**DEFERRED** (контракт описан, реализации ещё нет). Ниже это не скрыто — статус явно на каждом тесте, и
итоговая матрица показывает, какие инварианты сейчас доказаны **реально**, какие — только **на бумаге**.

## T-1 · add-type

**Goal.** Добавить новый тип данных, НЕ меняя физические таблицы ядра.

**Setup / шаги.**
1. Baseline: `ff-engine load --store store-md corpus/` — зафиксировать текущую PG-схему (`nodes(JSONB,GIN)`,
   `edges PK(source,pred,target)+btree`, `acts(seq)`) как снимок «до».
2. Завести НОВЫЙ тип как **данные**: узел реестра `meta:type:note` (schema/поля/валидация) —
   `ff-engine write --actor user:jenya --node meta-type-note.json`.
3. Записать инстанс: `ff-engine write --actor user:jenya --node note-001.json` (`type:"note"`).
4. `ff-engine validate corpus/` — должен пройти на новом типе без правок валидатора.
5. Снять PG-схему «после» и сравнить с «до» (`\d nodes`, `\d edges`, `\d acts` — байт-в-байт то же самое).

**PASS criterion (falsifiable).** Схема PG идентична до/после; `type:"note"` валидируется и читается тем же
generic view-компилятором (`ff-engine view --from type:note`), без нового кода. **FAIL**, если добавление типа
потребовало новой таблицы/колонки/DDL/кодовой ветки в `core/*`.

**Invariant(s) proven.** I-13 (старые/новые данные — данные+конфиг, не DDL ядра).

**Phase-1 status: REAL.** Реестр `meta:type` уже грузится и enforced валидатором в текущем seed (D-5, M-G3
в MVP-объёме); JSONB-хранилище узлов по конструкции не требует DDL на новый тип.

## T-2 · semantic-as-plugin

**Goal.** Добавить семантический поиск как плагин/линзу, НЕ меняя механизм записи (`engine.write()` /
акт-путь).

**Setup / шаги.**
1. Baseline: зафиксировать хэш/диф `core/envelope-validator.ts` + write-path ДО подключения семантики.
2. Подключить `similar`-предикат в стадию `filter` (аддитивно к 4-стадийному компилятору `from·traverse·
   filter·shape`, R-1) по дизайну `semantic-lens.design.md`; эмбеддер — детерминированный стаб
   (bag-of-tokens cosine, per A-2); вектор — производный pgvector-индекс.
3. `ff-engine view hybrid --viewer agent:planner --query "<текст>" --top_k 5` — возвращает `type:"decision"`
   ранжированные по порядку **rights → similarity** (order B).
4. Снова сравнить write-path/`envelope-validator.ts` — должны остаться БЕЗ изменений.

**PASS criterion.** Подключение плагина не потребовало правок write-пути/валидатора конверта; `similar` —
значение закрытого enum в `filter`, а не новая ветка кода на пути записи. **FAIL**, если включение
семантики потребовало трогать акт/write-код.

**Invariant(s) proven.** I-14 (эмбеддинги — производная проекция, RAG ≠ источник истины).

**Phase-1 status: STUBBED.** Механика rights→similarity и `SemanticIndexEntry` (projectionId/Version +
sourceId/Version) реальны; сам эмбеддер — стаб (A-2), НЕ доказывает качество поиска, только контракт.

## T-3 · rebuild-index

**Goal.** Полностью удалить семантический индекс (и/или текущее состояние-проекцию) и восстановить его из
канонических данных без потери знания.

**Setup / шаги.**
1. Journal-нога: `ff-engine rebuild --from journal` — пересобрать текущее состояние целиком из `acts[]`;
   сравнить результат с состоянием ДО пересборки — должно быть детерминировано (I-4) и побайтово совпадать.
2. Semantic-нога: снести производный индекс (`DROP` таблицу pgvector / `ff-engine rebuild --index semantic
   --drop`), затем `ff-engine rebuild --from nodes --index semantic` — переэмбеддинг из канонического текста
   (стаб-эмбеддер), с новыми `projectionId/Version` + `sourceId/Version` на каждой записи индекса.
3. `ff-engine view hybrid ...` после пересборки возвращает те же релевантные узлы, что и до удаления (с
   допуском на плавающую точку в `_score`).

**PASS criterion.** Состояние + индекс после пересборки неотличимы по СОДЕРЖАНИЮ от состояния до удаления
(та же видимость узлов/связей); ни один факт не потерян; новая проекция несёт свежие id/version. **FAIL**,
если хоть один факт существовал ТОЛЬКО в удалённом индексе.

**Invariant(s) proven.** I-3 (append-only даёт replay), I-5 (state = проекция), I-6 (проекция несёт
id+version), I-11 (истина = граф, размещение = policy), I-14 (эмбеддинги пересобираемы).

**Phase-1 status: REAL** для journal→current-state ноги (`rebuild --from journal|files` — DoD-пункт Фазы 1).
**STUBBED** для semantic-index ноги (стаб-эмбеддер, A-2) — контракт пересборки доказан, качество — нет.

## T-4 · as-of

**Goal.** Показать состояние объекта на определённый момент времени (`recordedAt ≤ T` + свёртка до точки).

**Setup / шаги (целевые, ПОКА недоступны).** Целевой вызов: `ff-engine view as-of --node <task-id> --at
2026-07-18T00:00:00Z` — реконструированное состояние на срез.

**PASS criterion (целевой).** Возвращённое состояние совпадает с ручной свёрткой актов с `recordedAt ≤ T`;
разные `T` дают разные валидные исторические состояния.

**Invariant(s) proven.** I-1 (стабильный id переживает срез), I-4 (акт неизменяем → «во что верили тогда»
восстановимо), I-5 (состояние = свёртка, а не отдельная snapshot-таблица).

**Phase-1 status: DEFERRED (per D-5).** `recordedAt` реален на актах, и полный `rebuild --from journal` до
ТЕКУЩЕГО состояния доказан (см. T-3) — но сама линза **as-of-СРЕЗА** (фильтр `recordedAt ≤ T` как
исполняемый `view`) вне MVP-объёма. **У этого теста сейчас НЕТ CLI-команды для прогона** — это целевой
контракт, не исполняемая проверка, до пересмотра D-5 (см. KQ-5/KQ-6/KQ-7 в `open-questions.md`).

## T-5 · deny-field-everywhere ★ флагман

**Goal.** Запретить агенту доступ к полю/узлу и доказать, что оно отсутствует ВЕЗДЕ: в обычном query, в
graph traversal, в vector search, в prompt, И в trace.

**Setup.** Требует именованного примера (владелец/builder ещё не назвал конкретное поле+агента — см.
KQ-12): рабочий кандидат — `task.body.private_note`, закрытое для `agent:crm` (ограниченный сторонний
агент), либо связанный узел `type:"person"`.

**Шаги (5 ног).**
1. **Query-нога:** `ff-engine view cockpit --viewer agent:crm --node <task-id>` → `private_note` отсутствует
   в выводе.
2. **Traversal-нога:** `ff-engine resolve part-of --viewer agent:crm --node <task-id>` (обход связей) →
   запрещённое поле/узел не всплывает после graph-expansion; recheck после traverse срабатывает.
3. **Vector-нога:** `ff-engine view hybrid --viewer agent:crm --query "<текст, совпадающий с private_note>"`
   → запрещённый узел никогда не входит в `top_k` / не получает `_score` (rights ПЕРЕД similarity, order B).
4. **Prompt-нога:** context-assembly для `agent:crm` строится ИЗ вывода (1)/(2)/(3); если там пусто — в
   промпте тоже пусто; нужен отдельный прогон реального prompt-builder'а агента, а не вывод по аналогии.
5. **Trace-нога:** дамп `agent_trace` сессии `agent:crm` не содержит запрещённое значение.

**PASS criterion.** Все 5 ног показывают нулевую утечку. **FAIL**, если значение всплывает ХОТЯ БЫ в одной
из пяти.

**Invariant(s) proven.** I-7 (`resolve()` — единственный PEP), I-8 (deny = зажим после свёртки), I-9
(fail-closed по поведению), I-10 (партиция — слой-данные).

**Phase-1 status: PARTIAL.**
- Query- и traversal-ноги — **REAL**, доказаны capability-killer'ом `resolve()` 15/15 NAIVE-vs-FIXED.
- Vector-нога — **STUBBED** (семантика в Фазе 1 — стаб-эмбеддер, тот же принцип rights→similarity).
- Prompt-нога — **REAL в принципе** (производна от уже gated view-вывода), но ЕЩЁ НЕ подключена к реальному
  harness'у сборки промпта агента — нужен отдельный конкретный шаг в seed.
- Trace-нога — **NOT-yet-verified, OPEN по KQ-4**: `agent_trace` — поток ЗАПИСИ (свой `ActKind`, свой
  retention), а не read-path под единым `resolve()`; собственный дамп агента может повторно эмитить
  запрещённое значение в обход PEP. Механизм закрытия не выбран (redaction-до-сериализации vs
  trace-как-проекция-на-чтении).

**Итог по T-5 как целому: НЕ PASS.** Из 5 ног верифицированы 2 (query, traversal); 1 стаб (vector); 1
не подключена (prompt); 1 открыта (trace). Это флагманский тест набора — его частичность стоит держать на
виду, а не считать «в целом ок».

## T-6 · plugin-upgrade

**Goal.** Обновить плагин, сохранив возможность читать старые записи, созданные предыдущей версией.

**Setup / шаги (целевые).** Нужна ВТОРАЯ версия типа/плагина, например `meta:type:research@v2` (новое
обязательное/опциональное поле) поверх уже существующего `meta:type:research@v1` (шаг 3 вертикального
сценария). Целевые вызовы:
1. `ff-engine load meta:type:research@v1`; записать `research`-узлы (v1).
2. `ff-engine load meta:type:research@v2` (обновлённая схема).
3. `ff-engine validate corpus/` → старые (v1) узлы по-прежнему валидны под v2-валидатором.
4. `ff-engine view --from type:research --node <old-id>` → старая запись по-прежнему читается.

**PASS criterion (целевой).** Старые записи валидируются и рендерятся под новой версией без миграции;
апгрейд фиксируется версионным реестром типов, а НЕ физическим DDL.

**Invariant(s) proven.** I-12 (снятие плагина не удаляет канонические данные), I-13 (старые данные читаемы
после апдейта типа/плагина).

**Phase-1 status: DEFERRED.** Нужна вторая версия плагина/type-def, которую однолинейный (single-lifecycle)
вертикальный сценарий не производит — это ЕДИНСТВЕННЫЙ из 7 GPT-тестов, явно НЕ покрытый
`vertical-scenario.spec.md` (см. его §Mapping to the 7 kernel tests, «честный пробел»). Плагин-реестр и
версионирование за пределами Фазы 1 (README §НЕ-цели: vendor/marketplace-загрузка модулей) — вероятно
post-MVP. Требует либо 11-й шаг сценария, либо отдельный мини-прогон (см. KQ-13).

## T-7 · explain-chain

**Goal.** Объяснить каждое изменение цепочкой `source → actor → command → policy decision → act →
resulting projection`.

**Setup / шаги.** Любая запись из шагов 1, 2, 3, 4, 10 вертикального сценария.
1. `ff-engine write --actor agent:planner --node task-003.json`.
2. `ff-engine inspect --act <act-id>` (или `explain --node <id>`) → печатает полную 6-звенную цепочку:
   source (`provenance.sourceIds`) → actor (`agent:planner`) → command (`write-knowledge`) → policy decision
   (`allow`, грант из `access-priority`) → act (append, immutable) → projection (дельта current-state).

**PASS criterion.** Для каждой из 5 целевых записей полная 6-звенная цепочка воспроизводима и совпадает с
ожидаемыми значениями; ни одно звено не пропущено и не сфабриковано постфактум. **FAIL**, если хотя бы одно
звено нельзя восстановить из журнала/провенанса.

**Invariant(s) proven.** I-1 (стабильный id), I-2 (actor+provenance), I-3 (append-only act), I-4 (act
неизменяем).

**Phase-1 status: REAL.** Это ядро DoD Фазы 1 (валидатор конверта требует actor+provenance+act-id; write-path
всегда идёт через `resolve()`); доказано на шагах 1–4 вертикального сценария. Вклад шага 10 (`sum(cost)`
fold) — **provisional**, пока не решён KQ-10 (R1-data-enum vs R3-new-fold); это НЕ блокирует T-7 в целом
(шагов 1–4 достаточно), но ослабляет именно шаг-10-ногу демонстрации.

    резервного теста — тонкое, но не нулевое покрытие.
  - **I-14** (embeddings rebuildable) — покрыт T-2 и T-3, но ОБА на стаб-эмбеддере → механизм доказан,
    качество — нет.
  - **I-1 / I-4 / I-5** имеют REAL-ногу через T-7/T-3 (базовый write/rebuild), но их «полная» темпоральная
    версия (T-4 as-of) остаётся `○` DEFERRED — базовый инвариант жив, его time-travel половина — нет.

## § CI integration note

Какие из семи тестов реалистично гонять в CI рядом с `concept-lint` / `test/invariants.test.ts` (уже
запланированный NAIVE-vs-FIXED конверт/рёбра/meta/PEP прогон, README §Карта модулей):

| Тест | CI-able в Фазе 1? | Почему |
|---|---|---|
| **T-1 add-type** | **ДА.** | Детерминировано, без LLM: фикстура `meta:type` + инстанс, ассерт `validate()` + снимок PG-схемы до/после (diff = пусто). Дёшево. |
| **T-2 semantic-as-plugin** | Технически можно (стаб-эмбеддер детерминирован), но **НЕ вписано в DoD** явно — опционально; write-path-untouched diff дёшево гонять уже сейчас. | Стаб детерминирован → не флаки, но не мандаторно per текущий DoD. |
| **T-3 rebuild-index** | **ДА** (journal-нога). | `rebuild --from journal` — детерминированный прогон, естественный сосед `test/invariants.test.ts`; semantic-нога тоже CI-able на стабе (детерминирована), но не приоритет. |
| **T-4 as-of** | **НЕТ.** | Реализации нет (DEFERRED D-5) — нечего гонять. |
| **T-5 deny-field-everywhere** | **Query/traversal-нога — ДА** (это и есть уже доказанный 15/15 NAIVE-vs-FIXED capability-killer, естественный кандидат в `test/invariants.test.ts`). Vector-нога — CI-able, как только стаб-семантика подключена к движку (не блокер). Trace-нога — **НЕТ**, пока не выбран механизм (KQ-4). | Смешанный статус — гонять то, что REAL, явно не гонять то, что OPEN, чтобы не создавать ложный green. |
| **T-6 plugin-upgrade** | **НЕТ.** | Нет второй версии плагина/type-def для прогона (DEFERRED). |
| **T-7 explain-chain** | **ДА.** | Детерминированная реконструкция цепочки на фиксированном корпусе + фиксированной последовательности write — естественный ассерт на 6 полей. |

**Итог:** сегодня в CI разумно закрепить **T-1, T-3 (journal-нога), T-5 (query/traversal-ноги), T-7** —
все четыре детерминированы, дёшевы, без LLM/сети, естественно ложатся рядом с `concept-lint` и
`test/invariants.test.ts`. **T-4 и T-6 в CI не идут** — реализации нет. **T-2 и T-5-vector-нога** технически
годны (стаб детерминирован), но не мандаторны, пока сама семантическая линза не интегрирована в движок Фазы
1/2 (см. README §📌.2). **T-5-trace-нога** намеренно НЕ в CI — включать её означало бы либо false green
(тест не проверяет то, что должен), либо блокировать CI на нерешённом KQ-4.
