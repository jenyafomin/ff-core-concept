# 💡 Захват: граф ↔ дерево ↔ git — через проекции

## 1 · Что услышал (4 под-нити)
- **(a) Параллельная документация.** Наша (платформенная) документация идёт ПАРАЛЛЕЛЬНО документации
  проекта. Сейчас — agents-manager; впредь в КАЖДОМ проекте логическая развилка: создаются определённые
  **типы по дереву**, которые потом **как-то связаны** — теоретически через **проекции**.
- **(b) Проект-как-единица + гранулярная видимость.** Не факт что нужно хранить весь проект; но
  теоретически можно сохранить проект целиком отдельно — при этом его **видимость** разбивается на
  **под-пункты** (описываем не «всё-или-ничего», а по частям).
- **(c) Объём → дом.** Спорно: первично инфа, возможно, живёт **в коде, по веткам (git)** — всё вместе
  держать сложно; часть фактов всё равно пишется по коду.
- **(d) Акты по веткам.** Как акты/инфа по разным веткам соотносятся (вместе ли) — **сам git может
  подсказывать путь/направление** (git как источник сигнала для графа).

## 2 · Как это ложится на уже ратифицированное (не переоткрываем)
- **ADR-0006** уже сказал: «одна адресуемая модель НАД многими стораджами». → **git-ветка = ещё один
  стор/проекция**, не новый движок. Концепт (c) — это выбор стора per-тип, а не новая ось.
- **Принцип «свойства вместо полюсов»** (только что принят): «граф ИЛИ дерево ИЛИ git» — ложная развилка;
  правильно — **представление = свойство/проекция** узла (где хранится, что видно) с дефолтом. Гибкая база.
- **KQ-11**: «акт по ветке» уже имеет форму — `observation`/`domain_event`-акт; git-коммит ≈ акт-событие.
- **KQ-12/policy-as-data**: «видимость по под-пунктам» = **field-level policy** (уже решённый механизм).
- **doc-tree закон #1**: git-история — это скорее **trace-вещество** (append-only след), а knowledge =
  граф-истина. Ключевой водораздел: что из git — trace, а что поднимается в knowledge-граф.

## 3 · Ядро концепта (одной фразой)
**Граф — единственная адресуемая ИСТИНА; дерево-документов и git-ветки — это ПРОЕКЦИИ/сторы над ним,
выбираемые как свойство типа (объём/доступ), а git-история дополнительно служит источником актов-сигналов.**
→ Это НЕ 3 конкурирующих дома, а один граф + N проекций (как ADR-0006, расширенный на git).

## 4 · Напряжения (честно, не замазывать)
- **T-1 Источник истины vs объём.** Если факты живут «по веткам в коде», а истина — граф, кто ведущий при
  расхождении? (doc-tree Rule 3: executable reality breaks ties — но тут граф претендует на истину).
- **T-2 git-коммит ⟂ акт.** Коммит иммутабелен (как `domain_event`), но git-историю можно переписать
  (rebase/force-push) — конфликт с append-only (I-3). Значит git = ненадёжный event-store?
- **T-3 Проект целиком vs под-пункты.** «Сохранить проект целиком» ⟂ «видимость по под-пунктам» — это
  один узел-проект с field-level видимостью или дерево узлов? (связь KQ-12).
- **T-4 Комбинаторный взрыв** (граница принципа): не каждый факт должен быть узлом графа — иначе объём.
  Нужен admission-порог «что поднимается в граф, что остаётся только в git/коде».

## 5 · 🔴 Фокус-вопросы владельцу (растим L0→L1, ответь текстом)
- **Q-0 (СТАТУС КОНЦЕПТА, развилка владельца 2026-07-26):** чем это является для базы —
  **(A) тест/полигон** (проект типа agents-manager = проверочный жилец, на котором обкатывается связка),
  **(B) доп-функционал** (опциональный модуль связи граф↔git поверх ядра),
  **(C) взаимосвязка/ядро** (фундаментально, как устроен субстрат)? Владелец: «точно не уверен».
  *Примечание: по принципу свойств — может быть НЕ или-или: стартуем как (A) тест, где валидируется (C)
  взаимосвязка, а (B) — то, как плагин её выставляет. Но нужно твоё направление.*
- **Q-1 (ЦЕЛЬ/БОЛЬ, L0):** какую конкретную боль решает связка? Догадка: «в каждом новом проекте заново
  разбираемся в структуре / хочу чтобы граф подсказывал направление из git-истории». Это оно, или другое?
  Якорь: что за эпизод в работе над agents-manager это породил?
- **Q-2 (водораздел объёма):** какие типы инфы = дом «код/git-ветки» (факты, трейс), а какие обязаны быть
  в графе (акты, связи, паспорта, политика)? Т.е. где порог «поднять в граф vs оставить в коде»?
- **Q-3 (git↔граф):** git-ветка — это ПРОЕКЦИЯ узла (вид) или отдельный scope/тип? И «акт по ветке» —
  адресуем в графе как observation, или git — только внешний сигнал, который граф ЧИТАЕТ, но не хранит?
- **Q-4 (проект-узел):** проект = один узел с гранулярной видимостью (field-level, как salary в KQ-12),
  или под-дерево узлов? «Разбить видимость на под-пункты» — это про policy на полях или про декомпозицию?
- **Q-5 (git как подсказка пути):** «git подсказывает направление» — это отдельный проектор/act-kind
  (читает историю веток → предлагает путь), Фаза-2+? Или прямо сейчас закладываем крючок?

## 6 · Что НЕ трогаем (решено — explorer)
Проекция-первой (KQ-11) · одна модель над сторами (ADR-0006) · trace⟂knowledge (doc-tree) ·
field-level policy (KQ-12) — это фундамент, на нём строим, его не переоткрываем.
