# ✅ Разрешение Q0–Q5 — граф ↔ дерево ↔ git

> **Критерий решения (якорь).** Оптимизируем **СКОРОСТЬ + УДОБСТВО агента** (цель системы агентов, папка
> `02-agents/`, НЕ проектная цель), и максимально. На каждом да/нет применён метод
> `prefer-properties-over-poles` («оба через свойство/слой, где это честно»). Жёсткие границы
> (I-3 append-only · врата/эрейж) НЕ ломаем — они остаются полюсами по конституции.
>
> **Одной фразой (ядро, из capture §3).** Граф — единственная адресуемая ИСТИНА; дерево-доков и
> git-ветки — ПРОЕКЦИИ/сторы над ним (свойство типа: объём/доступ), а git-история дополнительно служит
> **читаемым сигналом** актов. Это НЕ 3 конкурирующих дома, а один граф + N проекций (ADR-0006,
> расширенный на git).

---

## Q0 — Статус концепта

**Ответ (оба через слои, вход = A→C).** Это ВСЕ ТРИ, разложенные по слоям, но **заходим через A**:
- **A (тест/полигон)** — операционный вход: один реальный killer-кейс на настоящем поддереве.
- **C (взаимосвязка/ядро)** — то, что A валидирует: «граф=истина, дерево/git=проекции» есть закон субстрата.
- **B (доп-функционал)** — поздняя упаковка: как плагин выставляет связь наружу (маркетплейс-горизонт).

**С чего заходим.** Стартуем killer-тестом tree↔graph на реальном поддереве (кандидат — `docs/` FF; см.
развилку владельцу ниже) — это ТОТ ЖЕ тест, что P-2 полигона `folder-tree-as-graph`, не второй. git-ось
подключаем ДЕШЁВЫМ read-only слоем (см. Q5), не строим git-синхронизацию в итерации-0.

**Почему в пользу скорость+удобство.** Ядро строить «строго и надолго» — медленно и рискованно, пока
модель = гипотеза. Тест даёт агенту РЕАЛЬНЫЙ ответ на РЕАЛЬНЫХ папках за один проход → быстрая обратная
связь, минимум спекуляции. Но тест не одноразовый: он валидирует именно C, поэтому усилие не выбрасывается.

**Затронутая граница.** Нет жёстких. Метод свойств прямо разрешает не выбирать полюс A/B/C.

## Q1 — Корневая боль (L0)

**Ответ.** Корневая боль = **структура (и дерева доков, и git-истории) невидима агенту КАК ДАННЫЕ.**
Агент «видит файлы», но не видит типы/дома/статусы/связи/направление как запрашиваемый граф. Следствия
(они же три симптома, все — одна боль):
1. В каждой сессии/новом проекте агент **заново разбирает структуру из файлов** — медленно, повторно.
2. **Карты гниют, файлы сыплются в кучу** — дисциплина живёт в тексте-правилах, а не как проверяемый
   граф (линт = запрос, а не скрипт мимо модели). Это дословно `folder-tree-as-graph` §2.
3. **git-история нечитаема как направление** — агент не может спросить «куда двигалась работа по ветке X»,
   хотя сигнал физически есть.

**Почему в пользу скорость+удобство.** Это и есть боль АГЕНТА: невидимая структура = агент слепнет и
тратит проход на реконструкцию вместо работы. Убрать её = прямой прирост скорости+удобства.

**«Оба».** Не нужно; боль одна. Это **консолидация-вглубь (KQ-14)**: та же боль, что в
`folder-tree-as-graph` §2, расширенная git-осью. Не заводим второй корень.

**Затронутая граница.** Опора на рефрейм msg 141 (база = субстрат для агентов) — устройство самой базы
обязано лежать в базе как узлы.

## Q2 — Водораздел объёма (что в код/git ⟂ что в граф)

**Ответ (правило-порог admission).** Поднимаем узел в граф **⇔ агент должен его АДРЕСОВАТЬ**: связать,
отфильтровать, применить политику или принять над ним решение — через сессии/скоупы. Оставляем в git/коде
как сырьё **⇔ это байты-контент или реконструируемый trace**, который агент читает по указателю on-demand.

Тест одной строкой: **«Агент когда-нибудь линкует на это, фильтрует по этому или применяет policy?»**
Да → узел графа. Только открывает контент, когда надо → сырьё git (указатель `path@rev`, не дубль-узел).

| Дом | Что кладём | Почему |
|-----|------------|--------|
| **Граф (knowledge, адресуемые узлы)** | паспорта (`id·type·state`), рёбра/связи, акты (решения/`observation`, меняющие канон), policy (`homeRule`, visibility), `view`-узлы | это СТРУКТУРА и РЕШЕНИЯ — по ним агент навигирует/запрашивает/решает |
| **git / код (сырьё-стор, по указателю)** | тела файлов (байты), диффы коммитов, полный исходник, построчная история, trace | контент/след — читается on-demand, не участвует в обходах графа |

**Почему в пользу скорость+удобство.** Агент держит в «рабочей памяти» только адресуемый скелет (быстрые
обходы/запросы), а тяжёлый контент подтягивает лениво. Это прямо гасит **T-4 (комбинаторный взрыв)**: не
каждый факт — узел, иначе граф раздувается и запросы тормозят.

**«Оба/свойство».** Порог сам есть свойство типа: `placement: graph-node | git-raw | both(pointer)` на
`meta:type`. Дефолт по таблице выше, но переключаем per-тип (ADR-0006 (a), I-11).

**Затронутая граница.** **I-11** (истина=граф, размещение=политика-на-тип) — прямое применение.
**doc-tree закон №1** (trace ⟂ knowledge): git-байты/история = ближе к trace-веществу.

## Q3 — git ↔ граф

**Ответ (свойство, два слоя).**
- **git-ветка = ПРОЕКЦИЯ/стор, НЕ отдельный тип узла.** Per ADR-0006 git — «ещё один стор», а не новая
  ось/движок. Ветка — это значение lens/scope (место хранения), не сущность первого класса. НО если ветка
  несёт смысл, который агент должен адресовать (напр. «поток работы feature-X»), этот смысл = отдельный
  узел-`stream/work`, на который git-ветка ПРОЕЦИРУЕТСЯ. Ветка — стор; поток — узел.
- **Коммит = внешний СИГНАЛ, который граф ЧИТАЕТ; канонический акт граф хранит У СЕБЯ.** Граф НЕ делает
  git-SHA своим авторитетным иммутабельным актом. Коммит может быть **ингестирован как `observation`-акт**
  (засвидетельствованное внешнее событие) в собственный append-only журнал графа — но граф копирует
  значимый факт к себе, а не зависит от неизменности git.

**Почему в пользу скорость+удобство.** Агент получает удобный запрос «что произошло по ветке X» из графа
(быстро, единый ID-простор), НЕ дёргая git на каждый обход. При этом граф не платит за ненадёжность git.

**Затронутая граница — это разрешение T-2.** git переписывается rebase/force-push → git = **ненадёжный
event-store**, конфликтует с **I-3 (изменения только через append-only Acts)** и **I-4 (акт иммутабелен)**.
Вывод жёсткий: **канонический acts[]-журнал — собственный у графа (I-3), git НИКОГДА не источник истины
актов.** git = read-only сигнал; ingest коммита = `observation` в журнал графа. Так I-3/I-4 не ломаются.

## Q4 — Проект-узел

**Ответ (оба, через слои).** Проект = **`folder-node` (F1) — корень ПОД-ГРАФА — c field/node-level
policy видимости.** Не или-или:
- **«Сохранить проект целиком»** = проект есть один адресуемый узел (корень под-графа), который можно
  подключить/перенести/сослаться как единицу (plug-in модульность).
- **«Видимость по под-пунктам»** = field-level + node-level policy ВНУТРИ этого под-графа (механизм
  KQ-12, как `salary` у `person`) — на полях и на под-узлах.

Так **T-3 снимается**: «целиком vs под-пункты» — это не выбор, а два слоя одной вещи (корень-скоуп +
каскад policy). Проект уже есть слой LSR-стека (`node > space > project > module`).

**Почему в пользу скорость+удобство.** Агент подключает/отключает целый проект как под-граф одним
действием (удобство), и показывает/скрывает части политикой БЕЗ дробления узла (безопасно и быстро — один
`resolve()` вместо ручной сборки видимых кусков).

**Затронутая граница.** **KQ-12 / policy-as-data** (field-level policy) · **I-7** (`resolve()` —
единственный PEP видимости) · **I-10** (партиция-проект = слой-данные, не `if(project===X)`).

## Q5 — git как подсказка направления

**Ответ (свойство: дешёвый крючок СЕЙЧАС, проектор ПОЗЖЕ).**
- **Сейчас (near-zero cost):** закладываем крючок = коммит ингестируется как `observation`-акт (из Q3) с
  указателем `branch`/`path@rev` в поле узла. Это всё. Модель уже это позволяет — новых сущностей не
  вводим.
- **Фаза-2+:** отдельный **read-only проектор/`view`** «читает историю актов по веткам → предлагает
  направление». Это лишь запрос над уже накопленными `observation`-актами.

**Почему в пользу скорость+удобство.** Крючок стоит ~0 (одно поле-указатель + переиспользование
`observation`), а строить проектор-подсказку сейчас = трата без валидированной боли. Закладываем дёшево,
чтобы потом встроить БЕЗ миграции.

**«Оба».** Именно оба-через-время: крючок-сейчас + проектор-позже — не конкурирующие, а фазы.

**Затронутая граница.** **I-13** (старые данные читаемы после обновления типа): заложить поле-указатель
сейчас = нулевая миграция позже. Никаких жёстких границ не трогает (проектор read-only, ничего не пишет
в канон помимо `observation`).

## Соотношение двух домов + merge-направление

**Кто есть кто (KQ-14, консолидация-вглубь).**
- **`00-kernel/concepts/graph-tree-git-projection/` = ДОМ-ИСТИНА ПРИНЦИПА.** Здесь живёт закон субстрата
  (граф=истина; дерево/git=проекции; порог admission; git-как-сигнал) и эти решения Q0–Q5. Место — `00-kernel`,
  дом законов субстрата.
- **`02-agents/examples/02-folder-tree-as-graph/` = ПОЛИГОН/ИСПОЛНЕНИЕ.** Killer-жилец: «наша
  инфраструктура папок как данные», реальные конверты, реальный `view`. Место — `02-agents/examples`, дом
  прогонов.

Они **сильно пересекаются на оси tree↔graph** — это ожидаемо: полигон ИНСТАНЦИИРУЕТ принцип. Новый
инкремент концепта поверх полигона = **git-ось** (Q3/Q5), которой в полигоне ещё нет.

**Merge-направление (НЕ выполнять git mv — предложение):**
> **Kernel-концепт держит ПРИНЦИП+решения (этот файл); `folder-tree-as-graph` держит ИСПОЛНЕНИЕ; они
> связаны как закон↔его killer-кейс, а не дублируются. Конкретно: killer-поддерево концепта (Q0) = P-2
> полигона — это ОДИН тест. git-ось входит в полигон новой под-папкой `03-git-signal/`. НЕ переписывать
> «дерево-как-узлы» в kernel — ЦИТИРОВАТЬ полигон.**

Что гасим (дубль-риск): не re-derive «tree as nodes» в kernel — ссылка на `folder-tree-as-graph` §5-6.
Что добавляем в полигон: `03-git-signal/` как следующий инкремент (Q3 ingest `observation` + Q5 крючок).
