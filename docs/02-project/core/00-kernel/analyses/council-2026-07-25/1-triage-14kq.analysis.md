## 🟢 A — РАТИФИЦИРОВАТЬ (ответ крепкий, нужен «да» владельца)

- **KQ-3 · Само-референс политики.** Политика управляется через гейт `core:manage-*` + genesis-нота
  (первичная политика вводится актом генезиса, дальше — только через это право). → ратифицировать.
- **KQ-5/6/7 · Время.** v1 = только `recordedAt`; битемпоральность — **опт-ин по типу**; valid-time
  моделируется как интервал `[validFrom, validTo)`. → ратифицировать (as-of отложен, D-5).
- **KQ-12 · Скрытое поле.** Конкретный пример: поле `salary` на `person` — deny для `planning-agent`
  (field-level, не node-level). → ратифицировать как канонический пример.
- **KQ-13 · Апгрейд плагина.** Добавить **step-11 «plugin-upgrade»** в vertical-сценарий. → ратифицировать.

## 🟡 B — СИЛЬНАЯ РЕКОМЕНДАЦИЯ (ответ есть, но с законом/следствием)

- **KQ-2 · Отношение.** Логически — first-class и **policy-bearing**; физически живёт в конверте
  источника; `resolve()` перепроверяет политику НА ОБОИХ концах. (не отдельная таблица — свойство ребра).
- **KQ-9 · Persistence-as-policy.** Ратифицировать **ADR-0006**. File-first типы = `doc · note ·
  prompt · config(non-secret) · spec`. **ЗАКОН:** file-first ⇒ **НЕ access-bearing**; access / registry /
  policy = **DB-first ONLY**.
- **KQ-10 · Агрегаторы.** `sum/avg/count/min/max` = **closed enum**, поставляемый движком → *выбор*
  агрегатора = R1, *добавление нового* = R3. Рекомендация: **ship их в Phase-1**, чтобы step-10
  vertical-сценария был доказуем.
- **KQ-14 · Вширь vs вглубь.** **Консолидация-ВГЛУБЬ**, не идти вширь. Доказательство: 3 красных
  блокера + частичное покрытие инвариантов (I-12 без теста; I-7/8/9/10 частичны). См. `2-consolidation-plan`.
