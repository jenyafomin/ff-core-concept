# Sealing-план: durable-store / survive-turn (S7, GAP 1)

> **Фаза = дизайн на бумаге.** Ниже — ПЛАН (что запечатать и каким тестом), не код. `packages/`, git,
> шлюз не тронуты. Контракт (C1–C5, инвариант survive-turn) уже зафиксирован в
> [`durable-storeport.design.md`](../../durable-storeport.design.md) — здесь он не повторяется, только
> используется. Этот файл отвечает на вопрос «как довести GAP 1 (W2: durable-store физически
> ОТСУТСТВУЕТ) до красного→зелёного теста», а не переопределяет контракт.

## 1. Что значит «запечатано» — точное определение

**Формулировка (кровля контракта, дословно из `durable-storeport.design.md` §2):**
> Акт, записанный в ход N, читаем в ходе N+1 после того, как процесс завершился и поднялся заново.

**Разбор до тестируемого условия — 4 обязательных компонента, ВСЕ одновременно:**

1. **Реальная граница ОС-процесса.** Не «новый объект `Engine` в том же `node`-процессе», не
   «`dropProjection()` + `rebuild()` в том же тесте» — это класс ложной зелени, который уже поймал M2
   (SYNTHESIS 2026-07-30) и который W2 явно называет: «44/44 зелёные, но в ОДНОМ процессе». Нужен
   `spawn`/`fork` нового процесса P2 ПОСЛЕ `exit` процесса P1.
2. **Тот же store-dir, ничего не передано через память.** P2 не получает состояние P1 через
   переменные/closures/shared-объект — только путь на диске. Иначе тест проверяет IPC, а не durability.
3. **Акт виден именно через порт чтения движка**, а не прямым чтением файла с диска мимо `StorePort`
   (`readNode`/`acts`/`load` — те же методы, которыми пользуется прикладной код). Тест обязан идти через
   `Engine`, не в обход него — иначе зелёный тест докажет «файл на диске есть», а не «движок его видит».
4. **До первого чтения в P2 не было явного «догрузи вручную» шага со стороны теста** — только штатный
   boot P2 (конструктор `Engine` + `rebuild-from-journal`, C2). Если тест сам вручную читает файл и
   инжектит в `MemoryStore` — это обходит контракт, а не проверяет его.

**Testable condition (одна строка):**
> `exists(P1 writes act A) ∧ exit(P1) ∧ spawn(P2, same store-dir) ∧ boot(P2) ⇒ P2.engine.readNode(A.subject) reflects A`
> — без ЛЮБОГО из компонентов 1–4 выше тест НЕ закрывает survive-turn, даже если он зелёный.

**Что НЕ входит в «запечатано» (важно не спутать, см. `durable-storeport.design.md` §5):**
живой фоновый агент, переживающий рестарт ШЛЮЗА между ходами — это отдельный трек (`agents-manager`,
баг `gateway-agents-die-on-restart`), НЕ scope S7. S7 = «перечитайся с диска на старте», не «не умри».

## 2. RED→GREEN test plan (спека, без кода)

### Почему тест КРАСНЫЙ сегодня (факт-проверка кода, не прогноз)

Цепочка доказательства (ground truth, `packages/engine/src/`):
- `engine.ts:70` `Engine.write()` вызывает ровно один `store.writeAct(finalized)` — на конкретный
  инжектированный `StorePort`.
- `store-memory.ts:41-45` — единственный сегодня подключаемый в `Engine` адаптер, `MemoryStore`. Его
  `journal: Act[] = []` — **приватное поле в памяти процесса**. `writeAct` делает `this.journal.push(act)`
  и ничего не пишет на диск.
- `store-md.ts:1-16` (комментарий автора, дословно): «the SYNC StorePort contract at M0 is served by
  MemoryStore; this adapter is the async @ff/core bridge that **hydrates a MemoryStore from disk**» —
  т.е. `MdEnvelopeStore` умеет ЧИТАТЬ с диска при бутстрапе, но `Engine.write()` НИКОГДА не вызывает
  его `writeAct` — он не реализует интерфейс `StorePort` (async-сигнатура ≠ sync-контракт
  `store-port.ts:16-27`), поэтому физически не может быть подставлен в `Engine`.
- Вывод: между «акт записан» и «диск» сегодня НЕТ пути в коде. Любой запуск P2 после `exit` P1 увидит
  ПУСТОЙ journal — акт испарился вместе с процессом. Это не гипотеза, это следствие прочитанного кода.

### Тест 1 — `survive-turn.spec.ts` (★ несущий, = AC-2 контракта)

- **Name:** `durable StorePort survives an OS-process boundary` (реализует AC-2 из
  `durable-storeport.design.md` §4 / AC-S7 из ADR-DRAFT §Validation plan).
- **Arrange:**
  - Создать чистый temp store-dir (уникальный на прогон, напр. `os.tmpdir()/ff-survive-turn-<uuid>`).
  - Процесс P1: отдельный дочерний скрипт (`node <harness>.mjs --store-dir <dir> --write`), который
    конструирует `Engine` с (пока не существующим) durable-`StorePort`, зарегистрированным на этот
    store-dir, и вызывает `engine.write(actA)` с известным `actA` (фиксированный `id`/`subject`).
  - P1 завершается штатно (`process.exit(0)`) СРАЗУ после того, как `write()` вернул `ok:true` — тест
    НЕ ждёт никакого фонового флаша (это и проверяет C1: акт на диске уже к моменту возврата из `write`).
- **Act:**
  - Тестовый раннер дожидается реального завершения процесса P1 (exit-код) — не просто резолва промиса.
  - Спавнит НОВЫЙ процесс P2 (`node <harness>.mjs --store-dir <dir> --read <actA.subject>`) на ТОМ ЖЕ
    store-dir. P2 конструирует свежий `Engine` (боевой путь конструктора → C2 rebuild-from-journal на
    boot) и вызывает `engine.readNode(actA.subject)` (или эквивалент через `view`/`resolve`).
  - P2 печатает результат в stdout как JSON и завершается.
- **Assert:**
  - P1 завершился с exit-код 0 (запись прошла, `ok:true`).
  - P2 завершился с exit-код 0 и его stdout содержит узел, спроецированный из `actA` (тот же
    `subject`/поле, которое было записано).
  - (Негативный контроль в том же тесте) — если store-dir НЕ передавать P2 (пустой temp-dir),
    `readNode` возвращает `null` — доказывает, что зелень не от переиспользования состояния раннера.
- **Почему RED сегодня:** нет реализации durable-`StorePort`, подставляемой в конструктор `Engine`; тест
  либо не компилируется (нет такого адаптера), либо явно падает на assert (P2 видит пустой граф),
  потому что `MemoryStore` не переживает `exit`, а `MdEnvelopeStore` не реализует `StorePort`.

### Тест 2 — `idempotent-reboot-reingest.spec.ts` (= AC-3 / C4)

- **Name:** `re-ingest after reboot does not duplicate or clobber observations`.
- **Arrange:** P1 пишет `domain_event` с `source_ref=R, snapshotHash=H` → exit → P2 бутится с диска.
- **Act:** P2 повторно вызывает `engine.write()` с БАЙТ-ИДЕНТИЧНЫМ `domain_event` (тот же `R`/`H`), а
  также отдельно пишет `observation`-акт без `source_ref`.
- **Assert:** журнал P2 после обоих write НЕ содержит дубль `domain_event` (dedup сработал ПОСЛЕ
  рестарта, не только внутри одного процесса, как сегодня проверяет `invariants.test.ts`); `observation`
  остаётся нетронутым.
- **Почему RED сегодня:** дедуп-ключ (`T1`, engine.ts:81-88) сверяется с `this.store.acts()` — а после
  рестарта `store.acts()` на `MemoryStore` пуст (журнал не пережил `exit`), значит дедуп физически не
  может сработать «через границу процесса», даже если сам алгоритм дедупа корректен внутри процесса.

### Тест 3 — `forward-monotone-rebuild-after-reboot.spec.ts` (= AC-4 / C3)

- **Name:** `rebuild-from-journal on P2 reproduces P1's projection bit-for-bit`.
- **Arrange/Act:** P1 пишет N актов в разном порядке, включая один late-arriving акт, что меняет
  проекцию узла → exit → P2 boot → P2 вызывает `rebuild('journal')`.
- **Assert:** проекция P2 после `rebuild` идентична (deep-equal) финальной проекции P1 ДО exit
  (сравнение через сериализованный snapshot, записанный P1 перед выходом в отдельный контрольный файл —
  не через shared-память).
- **Почему RED сегодня:** зависит от теста 1 (нет диска-источника, нечего ребилдить); дополнительно
  проверяет, что `rebuild('journal')` на реальном диске = не no-op (сегодня `from==='files'` — M0-заглушка
  по коду `store-memory.ts:60`, `'journal'` работает, но только над in-memory journal, который пуст на P2).

### Тест 4 — `single-writer-lock.spec.ts` (= AC-5 / C5, младший приоритет — можно отложить до появления второго писателя, OQ-4)

- **Name:** `two concurrent writers on the same store-dir do not corrupt the journal`.
- **Arrange:** два процесса P1a/P1b стартуют одновременно на один store-dir, оба пишут разные акты.
- **Assert:** журнал после обоих содержит ровно оба акта БЕЗ повреждения (не interleaved-обрезанные
  строки); либо один из писателей явно fail-closed с понятной ошибкой lock — оба исхода приёмлемы,
  «тихая порча» — нет.
- **Статус:** формализуется, когда появится реальный второй параллельный писатель (design-документ,
  §OQ-4) — держим спекой здесь для полноты RED→GREEN матрицы, не блокирует GAP 1 sealing.

## 3. Rebuild-on-boot — план на уровне дока (C1–C5)

Не переопределяю контракт (см. `durable-storeport.design.md` §2) — здесь фиксирую ПОСЛЕДОВАТЕЛЬНОСТЬ
шагов sealing-хода, чтобы 4 обязательных свойства не остались прозой.

1. **C1 durable append-on-write.** Новый адаптер (рабочее имя `store-durable-fs`, НЕ пишется в код без
   «строй») реализует ТОТ ЖЕ sync-интерфейс `StorePort` (`store-port.ts:16-27`), что и `MemoryStore`
   сегодня — нулевая правка сигнатуры при выборе (A) из §3 design-дока. `writeAct` делает: (а) append
   строки в journal-файл через синхронный fs-вызов (кандидат: `appendFileSync` + explicit fsync, чтобы
   не остаться в OS page cache при внезапном kill — деталь ниже, п.5), (б) `foldInto` той же projection,
   что и `MemoryStore` (переиспользуем `core/projection.js`, не форкаем логику фолда).
2. **C2 rebuild-from-journal on boot.** Конструктор `Engine` УЖЕ вызывает `store.load()` при старте
   (engine.ts:41). Durable-адаптер при СВОЁМ конструировании (до того, как попадёт в `Engine`) читает
   journal-файл целиком и сворачивает через `project()` (`core/projection.js`) — механизм ребилда уже
   доказан (ADR-0008 §2, `store-memory.ts` `rebuild('journal')`), новизна только в ИСТОЧНИКЕ данных
   (диск вместо in-memory `journal[]`).
3. **C3 append-only-forward.** Journal-файл — только `append`, НИКОГДА не переписывается построчно.
   Формат на диске должен быть построчно-парсибельным (JSONL-кандидат: один акт = одна строка) именно
   потому, что append к такому формату тривиально безопасен при обрыве записи (частичная последняя
   строка отбрасывается при парсинге, не портит предыдущие). Это отдельное решение от «поздняя запись не
   переигрывает projection» (AC-debt-3 из ADR-DRAFT §3.3) — то про порядок FOLD, это про порядок ЗАПИСИ;
   оба должны держаться одновременно.
4. **C4 идемпотентность переживает boot.** Дедуп-ключ (`source_ref+snapshotHash`, T1) сегодня сверяется
   с `this.store.acts()` в памяти (engine.ts:81-88) — после смены адаптера тот же код автоматически
   начинает сверяться с ПОЛНЫМ диск-журналом (т.к. `acts()` durable-адаптера возвращает то, что реально
   лежит на диске после ребилда) — ключевое свойство: **эта проверка НЕ требует правки engine.ts**, она
   наследуется бесплатно, если durable-адаптер честно реализует `acts()` поверх ребилженного journal.
5. **C5 single-writer.** Advisory file-lock на store-dir (кандидат: lock-файл рядом с journal,
   `proper-lockfile`-класс библиотек или ручной `O_EXCL`-флаг создания) — формализуется при появлении
   второго параллельного писателя (OQ-4); для sealing GAP 1 достаточно НАЗВАТЬ контракт (сделано выше в
   тесте 4), не обязательно реализовывать раньше срока.

**Что переиспользуется без изменений (важно для оценки объёма работы):** `core/projection.js`
(`foldInto`/`project`), интерфейс `StorePort`, конструктор `Engine`, dedup-логика в `write()`. **Что
новое:** ровно один адаптер (диск вместо RAM) + формат journal-файла на диске + boot-time чтение файла
вместо пустого массива.

## 4. Values lens — какие из 7 ценностей запечатывает GAP 1

| Ценность | Как именно GAP 1 её запечатывает |
|---|---|
| **Ц-4 Витальность** (durability) | Прямое попадание — Витальность буквально означает «переживает». Сегодня Витальность акта = 0 после `exit` процесса; sealing делает акт живым ЧЕРЕЗ границу процесса, а не только внутри хода. Без этого GAP-а Витальность не измерима, а декларативна. |
| **Ц-2 Тождество** | Тождество узла держится идентичностью акт-лога, из которого узел ФОЛДИТСЯ (ADR-0008: граф — производная от журнала). Если журнал испаряется, «тот же узел» после рестарта — это заново собранный (и потенциально другой) узел, а не тот же самый. Durable-journal — необходимое условие, чтобы Тождество было проверяемым фактом, а не совпадением. |
| **Ц-3 Доверие** | Доверие требует, чтобы система не ЗАЯВЛЯЛА свойство, которое не доказано (см. W2-коррекцию ADR-DRAFT: «Петля ложная — недоказано, а не факт»). Тест из §2 — это именно механизм, переводящий заявление «памяти можно доверять между ходами» из прозы в проверяемый факт; до него доверие держится на честности комментария в коде, не на тесте. |

(Читаемость, Суверенность, Реляционность, Согласие — не затронуты напрямую этим GAP-ом; не включаю их
в таблицу, чтобы не растягивать значимость произвольно.)

## 5. Owner P0 — StorePort sync vs async (OQ-1) — НЕ решаю, план держится под ОБЕ ветки

`durable-storeport.design.md` §3 и ADR-DRAFT §4 называют эту развилку **one-way door**, решает
ТОЛЬКО владелец. План в §§2–3 выше написан так, чтобы не зависеть от исхода — но не все шаги
одинаковы под (A) и (B):

| Шаг плана | Ветка (A) sync + durable-fs (★ рекомендация ADR-DRAFT §4) | Ветка (B) async порт |
|---|---|---|
| Гармонезы теста 1 (arrange/act/assert) | Без изменений — тест спавнит процессы и сверяет stdout, сигнатура `write`/`readNode` внутри P1/P2-harness не видна раннеру | Без изменений (harness сам await'ит внутри своего процесса) |
| §3 п.1 (новый адаптер) | `writeAct` остаётся `(act: Act) => Act`, диск-запись — `appendFileSync` (блокирующий вызов, укладывается в существующую sync-сигнатуру без правки `store-port.ts`) | `writeAct` меняет сигнатуру на `Promise<Act>` → **это меняет `store-port.ts` для ВСЕХ адаптеров разом** (в т.ч. `MemoryStore`), а не только новый durable-адаптер |
| §3 п.4 (dedup наследуется бесплатно) | Держится как описано — `engine.ts` не трогаем | `engine.write()` тоже становится `Promise<Ack>` → каждый вызывающий код (`ingest-rentacar`, `rental-balance`, CLI) требует `await` — заявленный владельцем «нулевая правка вызывающих» (ADR-DRAFT §4 табл.) перестаёт быть верным для ЭТОГО GAP-а тоже |
| Объём работы GAP 1 сам по себе | Наименьший: 1 новый адаптер, 0 правок сигнатур | Больше: 1 новый адаптер + правка `store-port.ts` + все вызывающие места `Engine.write` |

**Флаг, а не решение:** если владелец выбирает (B), тесты 1–3 из §2 остаются валидными КАК СПЕКА
(arrange/act/assert через границу процесса не меняются), но harness внутри процессов P1/P2 обязан
`await` write/read, и сам GAP 1 расширяется на правку `store-port.ts` + вызывающих модулей — то есть
объём GAP 1 перестаёт быть «только новый адаптер» и захватывает часть того, что ADR-DRAFT §4 называет
«one-way door». Рекомендую владельцу закрыть OQ-1 ДО начала реализации GAP 1 (не после) — иначе есть
риск построить durable-адаптер под (A), а потом переписывать его сигнатуру под (B).

## ✅ Реализация — 2026-08-03 (Test 1 GREEN, ветка `refactor-tree`, не закоммичено)

Выбор OQ-1 = **(A) sync** (владелец, принятый пакет). Построено ровно то, что план назвал «новое»:
- **`packages/engine/src/adapters/store-durable-fs.ts`** — `DurableFsStore implements StorePort`
  (тот же sync-контракт, **0 правок** `store-port.ts`/`engine.ts`/вызывающих). JSONL-журнал на диске,
  `appendFileSync`+`fsyncSync` на запись (C1), rebuild-from-journal через `project()` на boot (C2),
  torn-last-line drop (C3), `acts()` поверх диск-журнала → дедуп переживает рестарт (C4),
  advisory PID-lock с реклеймом мёртвого владельца (C5 — закрывает V3-риск дублей).
- **`packages/engine/src/index.ts`** — экспорт адаптера.

## Резюме для владельца (1 абзац)

«Запечатано» = один конкретный тест (§2, тест 1), гоняемый через реальный `spawn`+`exit` границы
процесса, а не переиспользование состояния в раннере — сегодня он RED, потому что в коде физически нет
пути «акт → диск» (`MemoryStore` — RAM, `MdEnvelopeStore` — async и не подставляется в `Engine`).
Rebuild-on-boot почти целиком переиспользует уже существующий код (`core/projection.js`, конструктор
`Engine`, dedup-логику) — новое ровно одно: durable-адаптер + формат journal-файла. Единственная развилка,
меняющая ОБЪЁМ этого GAP-а — OQ-1 (sync/async), и она уже названа owner-gated в обоих читанных доках;
здесь она не решается, только показано, какие строки плана переключаются при каждом исходе.
