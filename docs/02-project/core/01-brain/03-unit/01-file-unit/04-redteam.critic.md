# Red-team — файл↔единица

> DESIGN-фаза, READ-ONLY адверсариал. Не выбирает модель — ищет, где каждая ломается, и что от владельца
> скрывает язык, которым модели описаны.

## Критика

### Critical (must address)

- **M-a («файл IS единица») уже противоречит РАТИФИЦИРОВАННОМУ ADR-0006.** ADR-0006 §(b) прямо перечисляет
  DB-first-ТОЛЬКО типы БЕЗ файла вообще («клиенты, снапшоты, память агента, трейсы, телеметрия, сообщения,
  метрики, канонический журнал `acts`») и §(c) прямым текстом отменяет закон «1 файл = 1 узел» («Файл = БАНДЛ
  узлов… НЕ закон»). Но `01-reality-map.analysis.md:38-44` показывает, что именно так живёт код СЕГОДНЯ
  (`@ff/core` `FileNodeStore`, `store.ts:21` — «the files ARE the graph», буквально 1 файл = 1 `.md` на `id`).
  Это не гипотетический breaking case — это **текущий код, нарушающий уже approved ADR**. Ломающийся пример:
  агент-память/метрика/человек-referent (DB-first по §(b)) физически не может получить файл в модели `@ff/core`
  — модель либо соврёт («у всего есть файл»), либо потребует второй, несовместимый способ хранения для
  DB-first-типов, которого сегодня в `@ff/core` просто нет.
  — Lens: assumption audit + contradiction detection.

- **M-c («грань = свойство взгляда/файл — линза») ложна ИМЕННО для file-first-типов, а это ядро её claim.**
  ADR-0006 §(f) прямо говорит: для file-first (`doc/config/prompt/agent/adr/spec/lens`) **`md+journal` =
  write-model (истина)**, движок — «первый ЧИТАТЕЛЬ, не первый писатель». Если файл — источник, из которого
  диффом ВЫВОДИТСЯ акт, то файл не проекция чего-то более фундаментального — он и есть точка входа. «Грань как
  линза, файл — просто один из её материализаций» работает для DB-first (там ADR-0006 §(d) явно называет
  файл экспортом-по-требованию, вниз по течению от лога), но для file-first течение ОБРАТНОЕ. M-c, заявленная
  как единая абстракция, на деле верна только для половины типов и ложна для другой половины — не общий закон,
  а частный случай, замаскированный под общий.
  — Lens: contradiction detection + assumption audit.

### Concerns (should address or accept)

- **Ни один документ не специфицирует, КАК один file-first-акт (диф файла) расщепляется на N единиц.**
  ADR-0006 §(c) уже разрешил «1 файл = много узлов» (бандл); UNIT-SPEC §5 требует, чтобы каждая грань, которой
  нужны свои грани, «повышалась до единицы + ребро». Комбинация: длинный `.md`, который правит владелец
  (file-first, §(g) `doc`), содержит 5 независимых фактов/задач → одна правка файла = один git-diff-акт по
  ADR-0006 §(f). Кто решает, что это 5 разных `canonical_id`, а не 1? Ни UNIT-SPEC, ни ADR-0006/0007 не называют
  это решение (splitting/admission policy) — реальность-карта (`01-reality-map.analysis.md:73-84`) уже фиксирует
  это как незакрытое (`OQ-6`/`TODO(M3)`), но не как отдельный риск ГРАНУЛЯРНОСТИ diff→unit, который шире, чем
  просто «reconcile две модели узла».
  — Lens: missing perspective + scalability (что произойдёт при 10⁴-строчном `.md`, а не игрушечном примере).

- **M-b («файл — payload-грань единицы») не покрывает N:M между файлом и гранями, а ADR-0006 §(c) требует
  именно N:M.** Payload-by-ref модель UNIT-SPEC §4/§6 подразумевает: один `payloadRef` → один payload-blob.
  Но бандл-файл (§(c)) содержит payload для НЕСКОЛЬКИХ единиц одновременно — тогда либо (i) один физический
  файл даёт несколько `payloadRef` (адресация внутри файла — байтовые диапазоны? YAML-ключи? не специфицировано
  нигде), либо (ii) грани разных единиц делят один `payloadRef`, что ломает стираемость per-грань (§4, «стираемость
  = атрибут ТИПА грани») — стереть payload одной единицы стирает payload соседней. Конкретный ломающийся кейс:
  спека, разбитая на несколько файлов (сама UNIT-SPEC-v1 + ADR-0006..0009 функционально ОДНО «решение о единице»,
  физически 5 файлов) — М-b не говорит, входят ли 5 файлов в одну грань с 5 `payloadRef`, или это 5 разных
  единиц, связанных рёбрами (тогда что стягивает их в «одно решение» для агента, читающего одну грань?).
  — Lens: failure mode analysis (payload-стирание не гранулярно) + contradiction (§(c) vs payload-модель §4).

### Provocations (consider)

- **«Грань = свойство взгляда» (M-c) — профинд как АНТИ-ФРАКТАЛЬНАЯ дисциплина (UNIT-SPEC §5: грань не
  цепляется за грань, повышается до единицы), но КОП-АУТ как операционализация.** Как принцип против
  разрастания она хороша — режет N-003/N-011. Но как ОТВЕТ на «файл↔единица» она ничего не решает: если
  зерно — свойство взгляда, то СТАБИЛЬНАЯ вещь, на которую агент пишет РЕБРО, — это `canonical_id` единицы
  (UNIT-SPEC §3). А кто МИНТИТ `canonical_id` из сырого материала (файла/диффа/текста) — это ИМЕННО тот вопрос,
  который «взгляд решает зерно» откладывает, а не закрывает. Сегодня `@ff/core` минтит `id` = 1 на файл
  (детерминированно, но неверно по ADR-0006 §(c)); UNIT-SPEC вообще не говорит, откуда берётся `canonical_id`
  для НЕ-файловых DB-first-единиц. Два минт-механизма существуют параллельно и не сведены — «зерно=взгляд»
  красиво объясняет ЧТЕНИЕ, но не отвечает на ЗАПИСЬ (кто решает, что вот ЭТО — новая единица).
  — Lens: abstraction stress-test. Verdict: **профинд-как-принцип, коп-аут-как-текущая операционализация** —
  не отвечает на вопрос идентичности/минтинга, только переименовывает его в «взгляд решит».

- **Соблазн, который прячется под M-c, а не под M-a.** M-a очевидно re-центрирует файл (это прямо запрещено
  msg-141: «файл — один тип узла, не центр»), и её легко поймать за руку — код сам себя цитирует «the files
  ARE the graph». Более коварный соблазн — в M-c: язык «файл — просто линза/проекция, не привилегированная
  сущность» ЗВУЧИТ максимально agent-first, но при трассировке ADR-0006 §(f) (file-first = md первично) и
  `store-md.ts` (`packages/engine/src/adapters/store-md.ts:8-9,31` — весь `EnvelopeNode` кладётся JSON-блобом
  ВНУТРЬ тела ОДНОГО `FFNode`-carrier'а, помечено «честно провизорно») видно, что для целого класса типов
  НЕТ независимого субстрата, из которого файл мог бы быть «просто одной из проекций» — файл единственный
  extant поток. Называть это «линзой» — риторически agent-first, структурно file-centric. Это опаснее M-a,
  потому что не палится на слово.
  — Lens: missing perspective (whose voice: чтение vs запись) + contradiction.

### Noted (watch)

- ADR-0006 §(c) и UNIT-SPEC §5 сами по себе НЕ противоречат друг другу (бандл-файл + грань-повышается-до-
  единицы — совместимы), но их СТЫК (сколько единиц в одном бандле, кто решает) не написан нигде явно.
  Наблюдение уже частично отражено в `01-reality-map.analysis.md` как `OQ-6`/`TODO(M3)` — не новая находка,
  но недооценённая по масштабу (см. Concern выше). Revisit при следующей волне M3.

### Файл↔единица переоткрывает шов erasure/act-log — да, и не только уже известным OQ-7

- **Известная часть (не новое, но подтверждается атакой):** ADR-0007 §b/B3-d уже маркирует CRITICAL/OPEN
  (`OQ-7`): `shred` доказуемо работает только для DB-first-payload; для file-first-типов (`doc/prompt/agent/
  adr/spec`) payload физически живёт в git-истории, `shred` там НЕ гарантирован, честный максимум — `hide`.
  Если владелец склоняется к M-a/M-b (файл несёт единицу/её payload) для «человеческих» типов — это ПРЯМО те
  же типы, что уже отмечены как erasure-дыра. Файл↔единица не открывает новый вопрос здесь — она РЕЗОНИРУЕТ
  с уже известным зазором, делая его выбор архитектурно более весомым (если файл = единица/payload-носитель
  по умолчанию для человеческих типов, дыра `shred` перестаёт быть краевым случаем и становится default path).
- **Новая часть (не зафиксирована ни в одном ADR/OQ явно):** ADR-0006 §(c) бандл (1 файл = много узлов) +
  ADR-0007 §OQ-1 (collateral-erasure по гранулярности КЛЮЧА) вместе рождают **третий вектор collateral-erasure,
  никогда не перечисленный** — collateral-erasure через СОВМЕСТНОЕ РАЗМЕЩЕНИЕ В ОДНОМ ФАЙЛЕ. Если единица A
  (referent X просит erasure) и единица B (другой referent/тип) физически лежат в ОДНОМ git-tracked бандл-файле
  (легально по §(c)), то любой механизм, целящийся в «erasure единицы A» через файл-уровень (delete файла,
  git-history-purge — единственный реальный путь для file-first по OQ-7), физически задевает B. `OQ-1`
  (`ADR-0007`) формулирует гранулярность коллатерали ТОЛЬКО через ключ crypto-shred (per-node/per-referent/
  per-field), не через физическое совместное размещение в файле — это отдельная, необсуждённая ось. Файл↔
  единица не закрывает существующий шов — она добавляет к нему НОВУЮ, ещё не поименованную грань риска.
  — Lens: security/adversarial + failure mode analysis (blast radius: erasure одного человека может
  технически требовать переписывания истории файла, где лежит и чужой payload).
- **Формально лог/акт (ADR-0008 CQRS: лог=SoR, граф=проекция) не ломается** ни одной из трёх моделей — акт
  всё ещё пишет координаты+`payloadRef`, а file↔unit-развилка живёт целиком на уровне «что стоит за
  `payloadRef`/что материализуется из акта», не трогая инвариант «лог append-only, граф пересобираем». Шов,
  который реально трещит, — не лог⟂граф, а **erasure-периметр (ADR-0007)**, и именно там file↔unit решение
  имеет реальные, ещё не оценённые последствия.

## Что я искал, но не нашёл проблем

- **Тождество лога (ADR-0008 SoR/проекция) под всеми тремя моделями держится** — ни M-a, ни M-b, ни M-c не
  предлагают писать акт мимо `resolve()`/PEP; развилка файл↔единица не про ПУТЬ ЗАПИСИ (тот уже закрыт I-7 +
  ADR-0006 §(e)/(f)), а исключительно про то, что физически СТОИТ за грань материализуемого содержимого.
