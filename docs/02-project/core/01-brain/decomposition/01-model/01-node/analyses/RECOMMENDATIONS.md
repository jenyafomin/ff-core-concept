# 📋 РЕКОМЕНДАЦИИ ПО КОНВЕНЦИЯМ — на подпись (5 разборов, 2026-07-17)

> По каждой: правило (рек.) + 1 главный риск. Скажешь «да/поправка» → свежая сессия вносит дифы.

## R1 · Нумерация
**Правило:** именованная папка-узел всегда получает порядковый префикс (`01-`, `02-`) по очереди
обсуждения; при пересборке — перенумеровка. Плюральные контейнеры (`analyses/ questions/ ideas/
plans/ states/`) — без номера, но файлы внутри нумеруются.
**Неизвестная папка** → «доска» внутри обязательного `INDEX.md` (3 строки: Концепт · Ожидаемый тип ·
Проверка зрелости), НЕ отдельная `rules/` (коллизия с `.claude/rules`). concept-first сигналит момент,
doc-discipline делает механику.
**Риск:** гонка номеров при параллельных агентах (нет единого счётчика).

## R2 · Состояния (states)
**Правило:** `docs/00-states/` на корне дерева (не внутри тем); плоско `NN-<slug>/`, тема = поле.
Внутри: `state.md` (id·theme·status·opened/updated·agents[]·plans[]) + append-only `log.md`; связи —
ссылками. **Многопоточность:** новая параллельная работа → новый state сразу. Агент входит по `state_id`
на ход (привязка временная, вход/выход с таймстампом → фильтруемый срез «кто/что/когда»). Не удалять →
архив статусом + git.
**Риск:** рост без компрессии при «никогда не удалять» → нужна архивация статусом.

## R3 · Логи
**Правило:** `logs/` (весь в `.gitignore`) → `conversations/NN/` (NN = `/new`) → внутри `analyses/
questions/ ideas/` + `concept.json`; разрастётся → `speeches/NN/`. `concept.json`: id·started·topic·
status·summary·`canon_links[]`·`speeches[]`. Сырой промпт владельца не хранить даже локально — только
summary/canon_links. **Это ЗАМЕНА схемы `session-logging`** (единица: сессия-дата → разговор-`/new`);
`STATE.md` в docs остаётся единственным committed-указателем, синк вручную.
**Риск:** `logs/` вне git → `canon_links` тихо расходятся с `docs/` (orphan-указатели) без сверки со STATE.

## R4 · План / Задача
**Правило:** `plan` = упорядоченный обновляемый список задач, ведущий текущий `state` → целевой.
`task` = атом: по умолчанию строка в плане, либо промотированный узел `tasks/<id>/` (когда нужен подграф,
с обязательным `parent_plan`). Контейнер `plans/` (`PLAN-<id>-<slug>.md`). Поля: `node_type·status
(draft/active/blocked/done/archived)·topic·target_state·parent_plan·owner·date`. Ребро `plan --targets-->
state`; один state держит несколько планов (большой луп).
**Риск:** раздвоение статуса (чекбокс в плане vs статус узла) → строка-в-плане становится read-only ссылкой.

## R5 · Реестр + навигация (несущая идея)
**Правило:** реестр типов — **с сидом** (10 базовых: theme-card·analysis·synthesis·decision·plan·state·
registry·open-question·concept·INDEX; 9 уже в use). Глобальный (out-of-box) + проектный (надстройка),
конфликт решает явный `scope: global|project`. Тип = мини-шаблон папки (завёл `plan` → ждёт рядом
`state`+`decisions`). **4 системных типа навигации:** `link` (типизированное ребро) · `projection`
(тема=проекция, не копия) · `index/registry-of` · `concept` (`*.concept.json` — единственный слой,
знающий ЛОГИЧЕСКОЕ расположение; отвечает на «найди active plans по теме Y → state↔plan↔analysis» через
ссылки, не путь). Тип входит в реестр только при ≥1 реальном узле.
**Риск:** соблазн засеять мёртвые спекулятивные типы → правило «≥1 узел, иначе open-question».

## 🔗 Сквозное схождение (важно)
Во всех 5 разборах всплыл ОДИН элемент — **`concept.json` как слой перелинковки**: доска в INDEX, логи,
навигация, реестр. Это подтверждает твою несущую идею: **дерево доков навигируется как БД через типы +
`concept.json`-ссылки, а не пути.** Один механизм — сначала на файлах, потом в базе.
