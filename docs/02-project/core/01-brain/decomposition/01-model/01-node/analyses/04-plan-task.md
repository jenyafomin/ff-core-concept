# 🔬 АНАЛИЗ — модель `plan` vs `task`

## 1. Определения (одна строка каждая)
- **`plan`** — упорядоченный, обновляемый список шагов/задач, нацеленный на переход текущего `state` → целевой `state` (или удержание лупа).
- **`task`** — атомарная единица работы с собственным жизненным циклом; существует либо как **строка внутри плана**, либо как **промотированный узел** со своим деревом (когда обрастает подартефактами).

## 2. Где лежат
- Контейнер планов: **`plans/`** (мн.ч., без номера) — каждый план = файл `PLAN-<id>-<slug>.md` со списком задач-строк (id, статус, ссылка на state).
- Задача по умолчанию — **строка в плане** (не отдельный файл). Промотируется в **`tasks/<task-id>/`** (папка-юнит, своё дерево) только когда ей нужны собственные под-доки/решения — критерий промоции: «нужен подграф» (>1 артефакта), не «стало сложно».
- Промотированный task обязан хранить `parent_plan` — иначе теряется, откуда он взялся (см. риск).

## 3. Обязательные поля-статусы (для будущего типизированного поиска «активные планы в статусе X по теме Y»)
- `node_type`: `plan` | `task`
- `status`: единый словарь для обоих — `draft | active | blocked | done | archived`
- `topic` / `theme` — ссылка на тематический узел (ось поиска «по теме Y»)
- `target_state` — id state, к которому план ведёт (только у `plan`)
- `parent_plan` — id родителя (только у промотированного `task`)
- `owner`, `date` — стандартные

## 4. Привязка плана к state
Ребро `plan --targets--> state` (не state хранит список планов, а план ссылается на целевой state — planning is directional). Один state может иметь **несколько параллельных планов** (большой луп = несколько state-переходов сразу); план закрывается/обновляется по факту достижения state, а не по календарю.

## 5. Риск (1 шт.)
**Раздвоение источника истины.** Пока задача — строка в плане, статус живёт в одном месте; после промоции в `task`-узел появляются ДВА статуса (чекбокс в плане + `status` узла), которые могут разойтись. Нужно явное правило: после промоции строка в плане либо удаляется, либо становится read-only ссылкой (`→ tasks/<id>`), никогда не редактируется вручную параллельно с узлом.
