# ✅ РАТИФИКАЦИЯ + новые концепты (2026-07-17)

## Решение владельца
- **R1–R5 приняты** («везде смело вносить»).
- **R1 нумерация · R2 states · R3 логи · R4 план/задача → применять сейчас** (agent-builder).
- **R5 реестр/навигация → НЕ применять «в лоб», а поднять в отдельный концепт** (владелец добавил
  крупный нюанс — см. Концепт-1). Пока — только минимальный сид, полный дизайн отдельной волной.

## Нюансы к R4 (план/задача) — заложить
- Планы и задачи желательно **в JSON** (машиночитаемо), либо доки с внутренней перелинковкой через
  `concept.json`. Чёткий план/задача = **явный статус + момент времени + `id`**. Маленькая система
  помогает системно.
- **Гибкие/самовоссоздающиеся планы** = loop-engineering → в это НЕ нырять, держать высоту; помнить
  глубинные цели. План может быть **глобальным**, на который ссылается конкретное **состояние запуска**.
- **Глобальный контекст под человека** (кто управляет всей жизнью) — нравится, база под это и точится.
- JSON-схема самовоссоздаётся, если её можно прочитать; системные модули (помощники, переходы,
  **миграции**) дописываются позже — помогают быстро переносить с назначением.

## 🔷 Концепт-1 (поднять) — Реестр + навигация как МЕХАНИЗМ
> Владелец: сделать простую вариацию, но **вынести задачу и спланировать**, как должно выглядеть — в т.ч.
> в будущей модели данных как механизм для планов/задач.
- **Реестр = слойные папки.** Глобальный: папка (напр. `ideas/`) с `rules` (skill.md) — описывает
  нумерацию, советует теоретические папки, **возможно с версиями** (каждая папка теоретически версионна;
  версии пока можно упустить, но заложить).
- **Проектная специфика:** в `project` указываем, что в `domains` есть N конкретных групп/баз, у них —
  подразделы; на базовом уровне `project > domains` всем разрешены папки определённого рода, ИЛИ весь
  список заведён в реестр с **глубиной** → по списку видно грани узла → быстро понять / **чисто
  склонировать** уже заведённую структуру. Правила — в коротких индексах.
- **Формат JSON** (читаемо): сначала инфо для агента; позже agent-manager строит механизм чтения/показа
  как **инструмент**; добавить инструмент в **шлюз** → дешевле находить связи, правила вшиты, «дай контекст».
- ⭐ **`concept.json` = «зрение», расширяется как дерево, но на деле ГРАФ** — теоретически должен уметь
  **зацикливаться**; текущая реализация не совсем это разрешает (ограничения UX и логики). Это несущее.
→ Отдельная волна concept-first.

## 🔶 Концепт-2 (поднять ЯВНО) — GitHub-модель / хранение истины / акты = коммиты
> Владелец: «выделить эту идею явно, обсудить, поднять в контексте», потом concept-first с вектором;
> посмотреть на GitHub — что взять, альтернативы, древовидный поиск. **Это и была основная задумка.**
- То, как мы **трекаем акты**, сильно напоминает **GitHub** — и это ядро идеи: трекаем все изменения
  данных + **утилизация** (erase = удаляем; ограничение — не всё храним).
- **Истина — в файлах.** Текст весит мало (можно держать весь проект); **фото — возможно не храним**; код
  — истина в файлах, файл теоретически в нескольких местах.
- **Проекция всего, что происходило** (само-улучшение, полная картина, развитие плана отдельно) — сильно
  помогла бы. Вопрос «что считать истиной: файл или папку» (папки в git-репо = отдельный слой владения).
→ Отдельная волна concept-first + разбор GitHub-параллелей/альтернатив.

**⭐ Уточнение владельца (2026-07-17): GitHub-модель = часть policy-as-data.**
- Версионирование/история «как git» — **не отдельная система, а флаг policy на данных**: какие-то данные
  ведутся такой аналитикой (полная история актов), какие-то — нет. **По умолчанию** настраивается policy.
- Сюда же **erase-по-времени / TTL** — по умолчанию хранится, но настраивается; **контроль ОБЪЁМА**
  изменений и хранимых данных. Бесконечно хранить нельзя — **за это надо платить** (cost-tradeoff).
- Красиво садится на уже принятое: `policy = правило-ссылка`, а «сколько истории/сколько хранить» = поле
  политики (retention/TTL/history-mode) с дефолтом. Связь с ценностями Витальность (метаболизм/забывание)
  и Суверенность. Закрывает и слепую зону масштаба (cost/ROI, D8-Q5).

## 🟩 Концепт-3 (поднять) — Полнота примитивов (вещь · связь · акт · линза)
> «4 главных» из L0 (вещь/связь/акт/линза). Рассмотреть **5-ю/6-ю грань** и **как они миксуются между
> собой** — отдельной папкой. Возможно свои концепты, связывающие факты → выводы (несколько пунктов,
> связи между ними, возможно дерево). Как это правильно строить — решает **doc-discipline**.
→ Отдельная волна (высокий приоритет, до стройки).

## 🧭 Мета-правило процесса (владелец)
Крупные запросы нельзя исполнить разом — **декомпозировать, чтобы не забивать контекст**. Модель делает
первичную приёмку, прикидывает раскладку; где чувствует путаницу — **запускает доп. агентов**, чтобы явно
фиксировать и улучшать. Всё крутится вокруг того, как мы строим БД + агентную систему — **тщательно
обдумывать, не упускать детали**.
