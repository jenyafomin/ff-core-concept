# 🎯 Резолвер контекста — концепт-схема (B3)

> Вход: **«агент + его состояние + запрос»**. Выход: **правильный срез ОДНОГО графа-субстрата** — не копия,
> не силос. Резолвер — read-time сборка трёх уже существующих опор поверх рёбер. Форма — концепт + границы
> модуля + развилки. Кода нет (фаза = дизайн).

## 0. Формула в одну фразу

**Контекст агента = Reachable ∩ Relevant ∩ Permitted**, вычисляемое над единым графом от узла-якоря агента.

- **Reachable** — что достижимо обходом рёбер по `id` от якоря (Session/Task/Slot).
- **Relevant** — что линза (`view-def`) коллапсирует в нужную грань под состояние агента.
- **Permitted** — что PEP пропускает по паспорту (owner/scope/policy/consent) и в каком виде.

Это НЕ конвейер с фиксированным порядком, а **пересечение трёх множеств-предикатов** над одним субстратом.
Порядок исполнения (см. §7, развилка A) — оптимизация, а не семантика.

## 1. Три слоя резолва и как они складываются в один

### Слой 1 — ССЫЛКИ (обход рёбер по id)
Состояние агента — это **узел** в подграфе оркестрации (Personality→AgentSlot→Session, см. M-G2), а его
«текущая задача/тема» — узлы Task/Concept, связанные рёбрами. Резолв стартует от **узла-якоря** и идёт
обходом `thin-ref` рёбер по `canonicalId`.
- Даёт **множество-кандидат Reachable** — «всё, на что показывает состояние агента».
- Обход **ограничен** (глубина · фильтр типов рёбер · направление) — иначе «весь граф».
- Ничего не вскрывает из payload: ходит по тонким паспортам + `fetchInstruction`.
- «Правильными ссылками агент дотягивает информацию» (формулировка владельца) = **этот слой**.

### Слой 2 — ЛИНЗА (`view-def`, коллапс в грань)
Над Reachable накладывается **линза** — декларативный `view-def` (узел реестра, примитив №3), который
**коллапсирует волну в релевантный срез**: фильтрует по `node_type`/`edge-type`/`salience`/`temperature`,
выбирает нужные поля паспорта и нужный **вариант** контента, задаёт форму вывода.
- Линза **вычислима read-time, НЕ материализуется** (инвариант: производное = read-time проекция).
- **Какую линзу взять** — решает состояние агента: Personality/Slot несёт дефолтную линзу, Task её
  **override**-ит (каскад, как effective-binding у M-G2: чат→топик→слот).
- Линза «паритетна»: обязана дать **fallback-рендер без агента** (опора #6, Ц-1) → срез читаем человеком.

### Слой 3 — ПАСПОРТ + ПОРОГ ДОСТУПА (PEP)
Каждый кандидат-узел/ребро несёт **тонкий паспорт** (owner/scope/storageLevel + policy-блок). **PEP
(опора #5)** — ОДНА точка принуждения на все каналы извлечения — оценивает каждого кандидата против
**идентичности и capability агента**: виден ли; в каком виде (read · use≠read · redacted · reference-only);
не нарушен ли consent (Ц-7) и потолок Конституции (#16).
- **Референтная видимость на ребре** = AND видимостей его концов (опора #5).
- Линза **консультирует PEP** на read-plane (опора #6) — то есть слой 2 и слой 3 сцеплены: линза не может
  показать то, что PEP запретил.

### Сборка в один резолв
```
resolve(anchor, query, agentIdentity) :=
    Permitted( Relevant( Reachable(anchor) , lens ) , PEP@passport )
где Permitted — не финальный фильтр, а ПРЕДИКАТ, вдавленный (pushdown) в обход:
    запрещённые capability-подграфы не обходятся вовсе (safety + скорость).
```
Один вызов, три декларативных входа (ребро-якорь · view-def · policy на паспорте), один исполнитель-движок.

## 2. Разные состояния агентов = разные подграфы над общим субстратом (без силосов)

**Изоляция логическая, не физическая.** «Контекст агента» = срез, заякоренный на его Session-узел, а НЕ
скопированная память. Два агента различаются тремя параметрами резолва — **якорь · линза · capability** —
и получают разные срезы из ОДНОГО графа.

- **Деление без копий:** два среза пересекаются там, где пересекаются их Reachable∩Permitted — это **те же
  узлы по `canonicalId`**, не дубликаты. Расходятся там, где разные якоря/права. Нет дрейфа копий.
- **«Память НЕ одна на проект» + «подфильтры»** выражается тремя механизмами, ноль новых колонок:
  - **scope-диапазон** — `scope` это ось-иерархия/диапазон, не одно значение; проект = **полоса scope**,
    а не стена. Подфильтр = вложенный диапазон внутри полосы.
  - **owner / tenant** — ось `owner` (до person-узла) даёт мульти-владельца и tenant-изоляцию (PEP).
  - **категория-view** — ребро членства + `view-def`: произвольный подфильтр внутри проекта как линза.
- Реляционность (Ц-6) — **сильнейший выигрыш**: агенты живут в общем графе, контекст = пройденные связи,
  а не изолированный ящик.

## 3. Варианты и проекции: выбор под состояние + видимость конфликта

- **`variant-of`** = альтернативное **содержание** одного референта (иная формулировка/сводка/уровень).
  **`view-def`** = вычисляемая **проекция** (линза), не хранимый альт-контент. Оси не путать (B4).
- **Кто выбирает вариант:** линза несёт **selector** (аудитория · гранулярность · confidence · locale).
  Резолвер ранжирует `VariantGroup` по selector-у под состояние агента и берёт лучший — **детерминированно
  и только когда selector однозначен**.
- **Конфликт вариантов виден арбитру:** если варианты расходятся (спор), резолвер **НЕ выбирает молча** —
  отдаёт `VariantGroup` целиком с **провенансом (опора #4)** и confidence. Арбитр/человек видит развилку
  (кокпит-линза рендерит конфликт). Это держит Доверие (Ц-3) и Читаемость (Ц-1): расхождение показано,
  не спрятано.

## 4. Где живёт: ГИБРИД (рецепт=данные · исполнение+принуждение=движок)

Ответ отображается на канонический раскол **control-plane над data-plane**.

| Часть резолвера | Где живёт | Почему |
|-----------------|-----------|--------|
| **ЧТО** резолвить (рецепт) | **ДАННЫЕ** | Якорь = ребро; линза = `view-def`-узел; порог = policy-блок паспорта; выбор варианта = selector-policy. Всё декларативно, self-describing (JSON-LD @context). Даёт «резолвер живёт в самих данных» (владелец) и рост=INSERT: новая линза/фильтр/право = новая строка, не миграция. |
| **КАК** исполнить + **ПРИНУДИТЬ** | **ДВИЖОК (система)** | Обход/коллапс/фильтр + PEP исполняет обобщённый evaluator. Не может быть чистыми данными: принуждение обязано быть **необходимо-непроходимым** (опора #16 integrity-as-engine-duty). |

**Резолвер = новая опора или сборка?** → **Не новая опора — именованный ШОВ (resolve-contract), собирающий
опоры #5 (PEP) + #6 (Линза) + #7 (Паспорт) поверх рёбер.** Он не вводит ни нового примитива, ни нового
физического хранилища; вся его машинерия уже есть. НО его надо **явно назвать и дать владельца** — иначе
это ровно скрытый шов **D-7** / слепая зона **D8-Q2** (никто не владеет порядком composition и семантикой
пересечения). Аналог — `effective-binding` у M-G2: не отдельный движок, а именованная каскадная проекция.

## 5. Как тот же механизм помогает человеку

**Человек — просто ещё одна идентичность/аудитория.** Кокпит (M-P4) = резолв, где:
- **якорь** = узел фокуса человека (текущий проект/тема),
- **линза** = кокпит-`view-def`,
- **PEP** = capability владельца (суверен: видит всё; эпистемический статус = **метка, не стена**; «клапан»
  только на внешние необратимые действия).

Один движок обслуживает и агентов, и человека — различаются лишь идентичность + линза. «Правильный
срез/кокпит» = `resolve(human-anchor, cockpit-lens, ownerIdentity)`. Сильная унификация: Читаемость (Ц-1,
паритетный fallback-рендер) + Суверенность (Ц-5).

## 6. Enforcement (ответ на D8-Q2)

**Кто физически проверяет доступ/согласие в рантайме → ДВИЖОК, в точке PEP, непроходимо.**

- Данные **декларируют** policy; движок её **принуждает** (опора #16). Кооперативных «данных, которые сами
  себя охраняют», недостаточно.
- **Единый порог (#5):** каждый путь чтения — агент, человек, кокпит, telegram, петли — проходит через
  ОДНУ точку PEP. Нет обхода мимо.
- **БД-уровень (RLS) = defense-in-depth, вторичный** страховочный гейт, НЕ первичный: policy графо-формна
  (зависит от обхода, consent-taint, референтная видимость на ребре) и богаче строковых предикатов RLS.
- Итог формулой: **PEP-в-движке = единственное седло принуждения; БД RLS = бэкстоп; резолвер = сборка,
  которая обязана пропускать всё чтение через это седло.**

## 7. Развилки (+ отклонённое, с пометкой «почему»)

### Развилка A — семантика и порядок composition
- **A1 — чистый конвейер** (обойти → линза → PEP последним). **Отклонено:** обходит запрещённые узлы до
  фильтра → риск утечки в трейсах + расход. «почему»: PEP как финальный фильтр не защищает сам обход.
- **A2 — пересечение с capability-pushdown** (PEP как предикат, вдавленный в обход; линза консультирует
  PEP). **✅ Выбор.** Безопаснее (в запретный подграф не заходим) и быстрее. Держит Согласие/Доверие.

### Развилка B — где живёт резолвер
- **B1 — чистые данные** (декларативный рецепт, привилегированного движка нет). **Отклонено:** принуждение
  обходимо → рушит integrity-as-duty (#16), Согласие (Ц-7).
- **B2 — чистая система** (резолвер захардкожен). **Отклонено:** каждая новая линза/фильтр = код → рушит
  рост=INSERT (Витальность Ц-4) и policy-as-data.
- **B3 — гибрид** (рецепт=данные, исполнение+PEP=движок). **✅ Выбор** (см. §4).

### Развилка C — изоляция памяти между агентами
- **C1 — физические per-agent хранилища (силосы).** **Отклонено:** владелец прямо против; дубли, дрейф,
  рушит Реляционность (Ц-6) и single-source.
- **C2 — логический срез (якорь + линза + capability над одним графом).** **✅ Выбор** (см. §2).

### Развилка D — конфликт вариантов
- **D1 — резолвер авто-выбирает победителя всегда.** **Отклонено при споре:** прячет расхождение → рушит
  Доверие (Ц-3), Читаемость (Ц-1, провенанс).
- **D2 — детерминированный выбор при однозначном selector-е, иначе отдать `VariantGroup` арбитру с
  провенансом.** **✅ Выбор** (см. §3).

### Прочее отклонённое
- **Материализация per-agent context-снапшота как источника истины** — **отклонено:** рушит read-time
  проекцию, устаревает. Допустимо ТОЛЬКО как `derived=true` кэш с гарантией rebuild.

## 8. Границы модуля (интерфейсный контракт)

| Модуль | Ответственность | Вход → выход | Зависит от |
|--------|------------------|--------------|-----------|
| **Reference-walk** (в M-G1) | ограниченный обход рёбер от якоря | (anchorId, edge-filter, depth) → Reachable-set | canonicalId, edge-registry |
| **Lens** (#6, M-P5) | коллапс Reachable в грань + выбор варианта | (Reachable, view-defId, selector) → срез-кандидат | view-def реестр, VariantGroup, консультирует PEP |
| **PEP** (#5) | единый порог: видимость/форма/consent | (кандидат, agentIdentity, capability) → Permitted-view | паспорт #7, policy-as-data, Конституция #16 |
| **Resolve-contract** (ШОВ, этот док) | порядок + семантика пересечения (§0/§7-A) | (anchor, query, identity) → контекст-срез | собирает 3 выше; владелец шва = открыт |

**Поток данных:** `agent-state(node) → [Reference-walk] → Reachable → [Lens⇄PEP] → Permitted-срез → агент/человек`.

## 9. Проверка оценочной функцией (7 ценностей)

| Ценность | Держит? | Чем |
|----------|:------:|-----|
| Читаемость | ✓ | рецепт (линза/policy) — данные; паритетный fallback-рендер; провенанс на конфликтах |
| Тождество | ✓ | всё по `canonicalId`; срезы = виды, идентичность узла стабильна |
| Доверие | ✓ | PEP + провенанс + confidence; конфликт показан, не спрятан |
| Витальность | ✓ | рост=INSERT: новая линза/scope/право = строка, без миграции |
| Суверенность | ✓ | owner-ось; человек = full-capability; статус = метка не стена; consent-клапан на PEP |
| Реляционность | ✓ | без силосов; агенты делят ОДИН граф, пересечение по id |
| Согласие | ✓ | consent-taint принуждается в движке per-read, непроходимо; забвение (tombstone) уважается в обходе |

## 10. Открытые вопросы (в наследство)
- **Владелец шва:** завести `resolve-contract` отдельным узлом-владельцем (консолидируется с D-7)?
- **D8-Q1 мульти-владелец:** при конфликте policy двух owner одного узла — кто побеждает в PEP? (сейчас R5 = один владелец, держим как ось).
- **Кэш срезов:** когда `derived=true` материализация линзы оправдана (read-scale #12) и как гарантируется rebuild/инвалидция?
- **Стоимость обхода** на большом графе (recursive-обход) — порог глубины/индексация как policy.
