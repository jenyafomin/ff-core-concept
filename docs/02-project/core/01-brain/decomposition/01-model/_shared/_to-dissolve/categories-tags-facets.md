# 🏷️ Категории / теги / грани  ← P10

## Что это / что хранит
Механизм наслоения значений на узел поверх его типа. По единой модели (DL-09/10/11): **категория** =
контейнер + ребро членства (акт); **тег** = слабая категория; **грань** = aspect-узел + `facet-of`;
**проекция** = view. Владелец: это **один из главных инструментов** агента/системы, чтобы анализировать
данные и полноценно с ними работать.

## Ключевое требование владельца
Они должны быть **«умными и продолжительными»** — вычисляемыми/само-поддерживающимися, чтобы БД **всегда
знала, как узел делится и как эволюционирует**. Описание этой «умности» — через **policy-as-data**, и они
связаны между собой.

## Уровни детализации (новое)
Есть **разные уровни детализации** того, что мы представляем. Продумать: сколько уровней; какой **тип
информации** на каждом (просто текст? JSON-структура, читаемая на каком-то уровне?). Возможно описывается
в policy-as-data. (Владелец: придумано на ходу — под сомнение.)

## Напряжение (для критика)
«Умные/само-поддерживающиеся» ↔ инвариант **«проекция-первой»** (R4: материализация только с rebuild-
гарантией + `derived=true`). Как «умность» не превращается во второй источник истины?

## Где ляжет в канон
`domains/03-category-taxonomy` (грань домена 01) + policy-as-data; DL-09/10/11 уточняются.

## Готово к потоку
abstract-thinker (рефрейм «умной категории») + critic (сломать против проекция-первой) + analyst (уровни детализации).
