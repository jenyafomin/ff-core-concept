# Линза B — ГРАФ и РАСШИРЯЕМОСТЬ

## Механики
- **B1 · Реестр типов рёбер как ДАННЫЕ (`edge-type` = узел).** Тип ребра = узел с узким паспортом (направленность, DAG-флаг, propagation-policy, consent-taint, слот триггера). Таблица рёбер одна; `type` → canonicalId типа. Новая механика = INSERT узла-типа, не миграция. Главная точка-плагин.
- **B2 · VariantGroup = узел-контейнер + рёбра `variant-of` + `mode: xor|or|and`.** Оба варианта — живые узлы, ни один не удаляется. Выбор = assertion-edge `chosen-in` (адресуемо). Разрешение = read-time вид `effective`. «Оба варианта» первоклассны буквально.
- **B3 · Assertion-edge как универсальный носитель поведения.** Каскад/вес/триггер/taint = декларативные слоты на ребре. caused/derived-from/computed-from/contradicts — одна таблица, разное поведение через тип+policy. Интерпретаторы регистрируются НА ТИП РЕБРА — второй plugin-порт.
- **B4 · Паспорт узла: тонкое ядро + policy-payload.** Ядро = canonicalId, type, scope, bitemporal-метки. Всё прочее — payload, валидируемый схемой-узлом `node-type`. Personality/Slot/Session/Concept/Task/память/файл/трейс = строки реестра node-type, НЕ таблицы. Взрыва сущностей нет по построению.
- **B5 · Виды как данные (`view-def`/`flow-def` = узел).** pending/effective/diff/поток = декларации параметризованного обхода (R-B). Плагин привозит свой вид — третий plugin-порт, без схемных изменений.

## Стыки
- **→ A:** реестры (edge-type, node-type, view-def) — сами узлы → реплицируются как данные; «схема» раздаётся через материализацию; `scope` в ядре = ось локальности.
- **→ C:** Personality→Slot→Session = seed node-types + edge-types в том же реестре; арендность = scope/tenant + `member-of`; слияние БД = слияние реестров (canonicalId един).
