# Р-4 · Память-diff — в объём? Папка-оркестрация — что это? — ✅ НЕТ · УЗЕЛ

## §3.4 Память-diff/снапшоты — в объёме этой сессии?

**Вердикт: НЕТ.** Bitemporal (В2) уже даёт diff «что менялось за промежуток» запросом — хранить нечего,
проектировать нечего. Фиксируем одну строку-инвариант (она и есть весь NOW-вклад):

> **Diff/снапшот = проекция над bitemporal, НИКОГДА не хранимая сущность.**

Совместимо с F6/ChangeTrace стороны агентов (там diff — тоже слой процесса, не таблица-истина).
Завести FQ «память-как-инструмент» (аналитика изменений · сферы вне охвата памяти) — в триаж, не в сессию.

## §3.3 Папка-оркестрация — узел / слой scope / отдельная сущность? (выбрать ОДНО)

**Вердикт: УЗЕЛ особого типа (`container`).**

**Обоснование через гибкость:** узел получает всё бесплатно — `canonicalId` (на него можно ссылаться
ребром → «рёбра-над-папками» работают без спец-кейса), паспорт (policy-as-data → «оркеструющее»
поведение декларируется данными на этом же узле), участие в scope, bitemporal-историю. Два отвергнутых:
- *Слой scope* — смешение осей: scope отвечает «ГДЕ живёт», оркестрация — «ЧТО делает». Склеить —
  потерять возможность оркестратора внутри одного scope и поверх нескольких.
- *Отдельная инфра-сущность* — третий примитив: каждый механизм (адресация, согласие, забвение,
  репликация) пришлось бы дублировать для него. Максимальная цена, нулевой выигрыш в гибкости.

«Оркестрация» как поведение = паспорт container-узла + интерпретатор (движок). Данные не знают слова
«оркестратор» — это роль, а не тип хранения.
