# ⚖️ FABLE — вердикт готовности к первой строке кода (2026-07-12)

## 1. Общий вердикт

**НЕ готов к первой строке кода — но отделяет вас от неё ОДНА ратификационная сессия владельца, а не новая волна ресёрча.** Концептуальная работа сделана: несущая модель сошлась независимо у 3× Fable и 8 агентов, инварианты «заложить сейчас» перечислены дословно. Всё, что осталось, — акты ПРИНЯТИЯ уже готовых рекомендаций (D1–D4 разобраны, у каждого есть рекомендация), а не исследование. Писать код ДО этих актов нельзя: три открытых пункта (канон-имена типов, D1, D2) сидят прямо в схеме первых двух таблиц — ретрофит будет стоить миграции, которой архитектура поклялась не иметь.

Отдельный резкий сигнал: **дизайн-фаза достигла точки убывающей отдачи.** Следующие настоящие ответы (контракт ребра, payload-форма, границы модулей на практике) добываются только кодом walking skeleton, не девятой волной агентов.

## 3. Минимальные блокеры ДО кода (безопасно начать без ретрофита)

Все шесть — ратификационные акты одной сессии владельца, не ресёрч:

1. **5 канон-имён типов (D3)** — `profile`/`profile-ref`, `journal-entry(kind)`, `supervised-by`≠`reports-to`, `verified-by`-канон, сироты в реестр. Без этого type-gate мёртв с первой строки — свалка синонимов гарантирована.
2. **D1: M-G1↔M-G3** — принять рекомендацию «гибрид» (два понятийных модуля, одна пара запуска). Три модуля уже строят на этом молча.
3. **D2: Session ↔ домен 01** — принять гипотезу thin-ref (2 агента сошлись: Session = координата исполнения, не хранилище).
4. **D4: владелец rebuild/reconcile** — принять рекомендацию (rebuild = долг M-G1, reconcile = policy, человек = эскалация). Rebuild-from-scratch — операция ПЕРВОГО дня, у неё должен быть хозяин.
5. **Пакет механики одним махом:** 10 полей паспорта · `scope=private` дефолт · расщепление `member-of`/`categorized-as` · поправка «проекция-первой» (уже пережила адверсариальную проверку).
6. **Hard-erase: минимальная спека-обязательство** (1 страница): в скелете нет эмбеддингов/реплик → tombstone достаточен; но путь `создание→hard-erase` объявляется долгом движка ДО того, как в БД попадут первые реальные личные данные.

НЕ блокеры (не поддаваться соблазну «доразобрать»): M-P1 Планы, M-P5-view, integrity-подшов D5, полный контракт ребра, спека Concept (Н-2).

## 4. Первый срез сборки — walking skeleton

**ОДИН модуль первым: M-G1 с самозахостенным M-G3** (реестр типов = строки в тех же таблицах — это и есть проверка гибрида D1 делом).

- **2 таблицы (SQLite, с миграциями с первого коммита, не `synchronize`):** `nodes` и `edges`.
- **Паспорт-колонки (минимум, остальные пустые с дефолтами — по завету консилиума):** `canonicalId(UUID) · node_type · scope(default private) · storageLevel · ownerId · committed · status · derived · provenance · validFrom/validUntil · created/updated` + `payload(JSON)`.
- **node-type (5):** `cell · container · journal-entry(kind) · node-type-registry-row · view-def` (registry-row = self-hosting M-G3).
- **edge-type (4):** `member-of` (thin-ref) · `derived-from` + `provenance` (assertion) · `same-as` (слияние).
- **Проверяемые инварианты дня-1 (это и есть смысл скелета):**
  1. слияние двух БД по `canonicalId` идемпотентно (`same-as`, не мутация);
  2. rebuild-from-journal с нуля даёт тот же граф;
  3. проекция-первой: членство/`effective` считаются read-time через `view-def`, ничего не материализовано;
  4. type-gate: INSERT узла с типом вне реестра — отбивается.

Скелет прошёл 4 теста → ADR утверждается из draft, модули наращиваются INSERT'ами.
