# ADR-DRAFT — Оркестрация STATE·PLAN·TASK·LOOP над 4 примитивами

> ⚠️ **proposed, НЕ approved.** Ответы на 5 развилок выведены из ТИПОВ (4 примитива, DL-01…29) и
> из 7 ЦЕННОСТЕЙ, а не из «что быстрее». Ждёт ратификации владельцем + стресс-критика
> (read-time-cost ~100k). Источник: DESIGN оркестрации (2026-07-19) + голосовая директива владельца.

## Контекст

Четырём сущностям — **STATE / PLAN / TASK / LOOP** — нужно место в модели памяти. Соблазн: сделать
каждую спец-таблицей или хранимым полем-истиной. Это ломает несущее решение субстрата (DL-01): рост
через **INSERT `node_type`/`act_type`/`edge_type` + view-def, никогда не миграция**; истина = журнал
Актов (event store), статус = **линза** (CQRS read-model), восстановимость среза «кто-что-делал».

**Принцип решения (директива владельца, 2026-07-19):** выбираем **из ценности**. Если ценность
искренне обслуживается **обоими** вариантами — «оба» и есть ответ, но как **две разные грани** (у
каждой — свой единственный дом), а НЕ как компромисс, чтобы не выбирать. Если ценность за один —
ответ приходит из ограничения (тип-система, read-cost), а не из удобства.

> ⚠️ **Записанная неточность владельца (для честности):** в голосовом «возможно где-то нужно оба, но
> это не факт» звучало так, будто «оба» — всегда доступный выход. Уточнение, вшитое в этот ADR:
> «оба» законно **только когда две ГРАНИ различимы** (напр. тождество ≠ статус). «Оба» как способ
> отложить выбор — запрещено. Ниже у каждой развилки явно помечено: `ОБА-грани` или `ОДИН`.

7 ценностей (якорь рассуждений): Читаемость · Тождество · Доверие · Витальность · Суверенность ·
Реляционность · Согласие.

## Решение (ядро)

Ни STATE, ни PLAN, ни TASK, ни LOOP — **не новый примитив и не спец-таблица.** Каждый собирается из
четырёх примитивов:
**узел-якорь (identity + паспорт) · акты (журнал = истина) · линза (статус = проекция) · policy-as-data (переходы).**

## Развилка 1 — STATE: линза или узел? → **ОБА-грани (node + lens)** ✅

**Ответ:** и то, и другое — потому что это **две разные вещи**, а не два мнения об одной.
- **Узел-якорь `state`** несёт *тождество*: стабильный `id`, паспорт, `theme`, `opened_at`. Нужен,
  чтобы `session` жёстко привязывалась (`state_id` на отрезок) и было к чему адресовать акты.
- **Линза `state.current`** несёт *статус*: `active|paused|done` вычисляется из журнала актов
  (`state.open/transition/pause/close`). Читается **ПЕРВОЙ** — дешёвая проекция «на чём работаем».

**Почему не иначе:**
- *Тождество* (ценность) требует узла — линза не имеет собственного id, к линзе нельзя привязать сессию.
- *Восстановимость / Доверие* запрещают хранить статус полем-истиной: он должен вычисляться из журнала,
  иначе теряется срез во времени и откат (DEC-10: без обязательного закрытия сессии).
- Здесь «оба» = чистые грани: **узел = тождество, линза = статус**, у каждой ровно один дом
  (закон «один дом» из doc-discipline). Это не компромисс.

**Контракт:** узел `state` хранит ТОЛЬКО неизменное тождество + паспорт; **никакого `status`-поля
в узле как истины**. Для человекочитаемости файла разрешено поле `status_cache` с `derived=true`
(исключение DL-04), пересобираемое политикой reconcile DL-05 — файл читаем, но истина остаётся в линзе.

> 🔴 **Блокер согласованности (нашёл критик):** источники РАСХОДЯТСЯ. `01-node/analyses/02-states.md`
> (§2, до-CQRS, ратифицирован раньше DL-20) описывает `state.md` с **хранимым полем `status`, которое
> пишет агент напрямую** — это модель «файл-истина», не сверенная с event-sourcing. Таблица в самом
> DESIGN тоже перечисляет `status{…}` как поле паспорта, а проза говорит «статус = линза». **До
> approved: пометить `02-states.md` superseded/поправить** и явно закрепить: узел несёт `status_cache`
> (derived), истина — журнал+линза. Иначе подписывать разв.1 нельзя — доки противоречат друг другу.

## Развилка 2 — Единый словарь статусов? → **Хребет + локальные листья** ✅

**Ответ:** общий **хребет** `draft|active|blocked|done|archived` для plan/task/loop; типам разрешены
**локальные листья**, где жизненный цикл искренне другой.
- **state** — свой лист: `active|paused|done` (`paused` ≠ `blocked`: пауза добровольна, блок — по зависимости).
- **loop** — маппинг на хребет: `halt`→`done|archived`, guard-wait→`blocked`, виток идёт→`active`.

**Почему так (не «всё одинаково», не «всё раздельно»):**
- *Читаемость* хочет ОДНУ линзу `board` (по `theme/status`) через plan/task/loop → нужен общий хребет.
- Но насильно втянуть `state` в хребет = соврать про его цикл (`paused`≠`blocked`). Ограничение
  приходит из домена, не из удобства → state держит лист.
- Форма «жёсткий хребет + органичные листья» — прямой перенос правила `value-decomposition`.

**Это НЕ «оба» в смысле развилки 1.** Здесь один словарь-хребет; листья — расширение, а не второй
параллельный словарь. Инвариант: **новый статус добавляется как лист только если существующий хребет
искажает смысл** (линт doc-discipline это проверяет).

> ⚠️ **Правка после критика — не «схлопывать», а ПРОЕЦИРОВАТЬ.** Маппинг `halt→done` терял бы смысл
> (остановленный луп можно возобновить; `done` терминален → `board` дал бы ложные «завершено»).
> Поэтому: `board` показывает **значение хребта только для фильтра**, а **исходный тип-специфичный
> статус узла НИКОГДА не перезаписывается** и остаётся запрашиваемым. Таблица маппинга «лист↔хребет»
> живёт как **policy-as-data**, а НЕ логикой внутри view-def (иначе `board` превращается в
> спец-кейсовый монолит — анти-паттерн DL-02, но уже для линз).

## Развилка 3 — LOOP: подтип plan или свой node_type? → **свой `node_type`, КОМПОЗИЦИЯ plan (has-a), не наследование (is-a)** ✅

**Ответ:** `node_type: loop` — отдельный первоклассный тип, который **оркестрирует** план/группу через
витки, а не «является планом».

**Почему не подтип:**
- *Семантика цикла:* `plan` имеет семантику **конечного завершения** (`done`); `loop` по природе
  **цикличен/непрерывен** (виток за витком, DEC-7 рекурсия). is-a-наследование натягивает finite-lifecycle
  на non-terminating → скрытое напряжение, всплывёт в линзах прогресса.
- *Ценность Витальность:* «петли живут во времени, цикл — это фича» (вердикт реактивности 2026-07-07).
  Первоклассность = петля видна и подключаема, а не сноска-подтип плана.
- *Модульность (plug-in):* луп должен подключаться независимо → отдельный тип-гражданин субстрата.

**Почему это дёшево (нет дублирования):** в едином субстрате `node_type` — это метка-паспорт, не
жёсткий класс. `loop` **переиспользует РЁБРА плана** (`has-subplan`/`has-task`) и несёт план в теле
(`carries`/`orchestrates` → plan|группа). Значит tooling плана работает и над лупом **без наследования**.
Свои у лупа: `act_type` (`loop.spawn/iterate/guard-check/halt`) и линза `loop.ledger` — они и так
отдельные при любом ответе, что дополнительно оправдывает отдельный тип.

**Здесь `ОДИН` ответ:** и семантика, и Витальность, и Модульность толкают в одну сторону — «оба» тут
было бы дырой (луп-как-подтип-плана тащит завершение-семантику). Отвергнуто.

> 🔒 **Обязательное правило (нашёл критик):** субстрат = 2-табличный граф **без валидации концов
> рёбер** (DL-01/DL-25). Раз `loop` переиспользует `has-subplan`/`has-task`, то запрос, идущий по
> `has-task`, начнёт **молча цеплять и рёбра лупа**. Значит: **каждая линза, обходящая
> `has-subplan`/`has-task`, ОБЯЗАНА фильтровать по `node_type` источника** — субстрат за тебя это не
> сделает. Это правило идёт вместе с ADR (не блокер, но без него — тихая путаница типов на чтении).

## Развилка 4 — TASK после промоции: строка-плана = read-only ссылка? → **ДА, read-only проекция** ✅

**Ответ:** да. Больше того — строка-в-плане **ВСЕГДА** проекция (линза `plan.progress` над актами
`task.*`), а не хранимая копия. Промоция (`>1 артефакта`) лишь даёт задаче **свой узел-якорь**; после
неё строка = read-only указатель (ребро `has-task`/`attached-to`) на узел-истину.

**Почему:**
- *Тождество* запрещает раздваивать истину: одна задача — один дом (узел после промоции), не «строка И
  узел с разными статусами». Каскад `canonicalId`-слияния (DL) — тот же закон.
- До промоции задача дёшева (строка = проекция акта). Это не «два представления одной истины», а
  **одна истина (акты) + её проекции**. Ничего не дублируется по определению.

**Контракт (уточнён критиком — «проекция» переобещает живость):** развести два носителя, чтобы не
плодить неоднозначность реализации:
- **Файл `plan.md`** хранит ТОЛЬКО статический указатель: `- [ ] → tasks/<id>` — **без дублирования
  статуса даже приблизительно.** Файл не «живой», зато однозначен и читаем без движка.
- **Линза `plan.progress`** — единственное место, где агрегатный статус задач **вычисляется** из актов.

  То есть слово «проекция» относится к **линзе**, а не к строке файла; строка = мёртвый указатель на
  дом-узел. Так снимается расхождение источников (`04-plan-task.md` §5 «статическая ссылка» vs
  «live-проекция»): оба верны, но про разные носители.

## Развилка 5 — Дом типов? → **НЕ семантическая развилка ADR; это исполнение DL-29 через doc-discipline** ✅

> ⚠️ **Пере-рамка (критик прав):** «где живут типы» — это размещение в дереве, уже управляемое
> ратифицированным DL-29 («1 unit = 1 home»), а НЕ архитектурная развилка. Держать её как «развилку 5»
> рядом с 4 семантическими вопросами — категориальная ошибка (docs-standard: ADR — про
> архитектуру/хранение/интеграции, не про имена папок). Поэтому: ответ ниже — **исполнительная
> заметка для `doc-discipline`**, а не пункт на архитектурную ратификацию. ADR по существу = разв. 1–4 (+6).

**Ответ (исполнение DL-29, не ратификация):**
- **Определения типов (def)** — знание → живут в `_shared/mechanisms/orchestration/` (эта папка). Сюда
  свести разрозненные def’ы `01-model/state/` + `plan/`.
- **Рантайм-экземпляры** — данные → `00-states/NN-slug/`, `plans/…` (инстансы состояний/планов).

**Разрешение дубля O-1b (два `state/`) — по правилу def-vs-runtime + «одно имя ≠ одна вещь»:**
| Папка | Что это на самом деле | Куда |
|-------|----------------------|------|
| `…/decomposition/01-model/state/` | **трейс-указатель** «где мы в ДИЗАЙНЕ модели» (дублирует `NAV.concept.json → current_direct_tasks`) | растворить в NAV/трейс; это не def механизма |
| `…/01-brain/state/` | **концепт МЕХАНИЗМА `state`** (state = первоклассный узел в БД) | это def → перенести в `orchestration/` как дом механизма state |

Т.е. «один дом» не нарушается двумя разными вещами с одинаковым именем — их надо **переименовать/развести**,
а не слить контент. Def механизма state → `orchestration/`; дизайн-трейс → трейс.

**Миграция — обратимая (правило evolution): план отката ДО переноса.**
1. `mkdir orchestration/state/` (дом def механизма state) — DEF.
2. Перенести содержимое-def `01-brain/state/README.md` → `orchestration/state/` (редирект-заглушка на старом месте).
3. `01-model/state/README.md` → пометить `trace`, слить указатели в `NAV.concept.json`, оставить заглушку.
4. Рантайм-инстансы (когда появятся) → `00-states/`. Пусто сейчас — лес не плодим (правило хребта).
5. Бэкап перед движением (как `/tmp/ff-mig-backup` в прошлой консолидации).

**Механизм отката (явно):** каждый перенос оставляет редирект-заглушку на старом пути + бэкап-копию →
откат = вернуть содержимое из бэкапа и снять заглушку; git-коммит перед миграцией = точка возврата.

## Развилка 6 (НОВАЯ — критик нашёл пропуск) — Политика материализации линз 🔴 РЕАЛЬНЫЙ БЛОКЕР

Пять развилок молчат о главном операционном вопросе: **для каждой из 4 линз** — `state.current`,
`board`, `plan.progress`, `loop.ledger` — она **live-считается** (дефолт DL-04) или
**материализована с обязанностью пересборки** (исключение DL-04 + reconcile DL-05)?

Это **предратификационный блокер**, который сам DESIGN назвал («read-time-cost ~100k»), но не закрыл.
Особенно горячо для `state.current`: её читают **ПЕРВОЙ на каждом открытии сессии** — самый частый
путь чтения в системе; ошибка стоимости/корректности здесь = не край, а горячая тропа.

**Рекомендация к решению (владельцу — по каждой линзе):**
| Линза | Частота чтения | Реком. | Обоснование |
|-------|----------------|--------|-------------|
| `state.current` | очень высокая (каждый session-open) | **материализована** (`status_cache` derived, reconcile DL-05) | горячая тропа, N мал |
| `board` | средняя | live | обзорный, редкий, широкий UNION по типам |
| `plan.progress` | средняя, N мал на план | live | дёшево |
| `loop.ledger` | по витку | live (или кэш при частых guard-check) | зависит от частоты витков |

→ После ответа на разв.6 форки 1 и 2 становятся исполнимыми; без неё — нет.

## Открытый риск (критик, вторично) — гонки записи в одно `state`
`state.md` несёт `agents: [...]` (мн.ч.) → два агента могут одновременно писать акты в журнал одного
`state` → `state.current` рискует увидеть рваный срез в середине перехода. **DL-26 (Temporal-lite
движок)** зовётся для оркестрации в других местах, но НЕ подключён к этой гонке. → занести в
дизайн-очередь как отдельный вопрос порядка/разрешения записи (не блокирует ратификацию 1–4/6, но
блокирует build state-механизма).

## Альтернативы (отвергнуты)
- **Спец-таблицы** для state/plan/task/loop — ломают DL-01 (рост = миграция), теряют event-sourcing.
- **STATE как хранимое поле-истина** — теряет восстановимость среза во времени (DEC-10).
- **LOOP как подтип plan** — натягивает finite-completion на цикличность; напряжение в линзах.
- **task = строка И узел (две истины)** — раздваивает тождество.
- **Плоский единый словарь на все 4** — искажает цикл state (`paused`≠`blocked`).

## Последствия
- ✅ Рост без миграций сохранён; статусы восстановимы; один `board` через plan/task/loop.
- ✅ Дубль O-1b получает правило разрешения (def-vs-runtime), а не разовый хак.
- ⚠️ Больше линз-вычислений на чтение → **риск read-time-cost** (см. валидацию). Смягчение:
  денормализованный `derived`-кэш линзы `state.current`.
- ⚠️ `loop` как отдельный тип = дисциплина tooling: не забыть, что он переиспользует рёбра плана.
