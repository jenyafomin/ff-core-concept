# Плагины и системные типы — разрез архитектора

## Главная мысль
Видение владельца не противоречит канону — оно **возвращает ADR-0006 (a)**: «ОДНА адресуемая модель над
МНОГИМИ хранилищами, размещение = политика на тип». «Одна память» = один реестр типов, один `id`-простор,
одни рёбра, одни виды. НЕ один файл-журнал. Миллионы записей кухни на JSONL-в-RAM (запись O(N), ADR-0016
«терпимо до ~50k») невозможны — значит у системного пака своя **полоса хранения** (Postgres), но тот же реестр.

## A. Слои типов
| Слой | Namespace | Кто определяет | Кто пишет записи | Эволюция |
|---|---|---|---|---|
| **kernel** | `core:` (scope, actor, task, event, document, decision, type-def, pred-def) | genesis в коде (ADR-0016 D3) | движок/владелец | только аддитивно |
| **system pack** | `sys:gateway/…` | пак, поставляемый с системой | только принципал пака (`sys:gateway`) | аддитивно; breaking = новый major |
| **plugin pack** | `pack:<id>/…` | манифест плагина | принципал плагина + агенты по policy | semver пака |
| **user** | `u:` | владелец/агент (`candidate`, D11) | все по policy | свободно |

**«Запечатан, но расширяем» конкретно:**
1. `type-def` `sys:message@1` неизменяем; в пределах major — только новые **необязательные** поля (`type_v` 1.1).
   Breaking → `@2` + upcaster-вид (чтение старых записей как новых), журнал не переписывается.
2. Расширение — **не правкой базы**, а (а) `extends: sys:message@1` (подтип, D5), или (б) **фасетом-ребром**:
   своя запись `pack:x/annotation` → ребро → базовая запись. База остаётся предсказуемой.
3. Право записи — **capability на тип**, а не на хранилище (ADR-0010: авторитет≠атрибуция). Ссылаться
   рёбрами на системные записи может любой; менять их — только владелец пака.
4. У типа новое обязательное поле `persistence_class`: `event` (append-only: messages, decision_journal),
   `state` (CAS-ячейка: jobs, sessions, lease — история по политике, не акт на каждый heartbeat),
   `config` (версионируемый документ: PROMPT.md, bindings), `ephemeral` (dedup, lease — TTL, НЕ память).
   Без этого «акт на каждое изменение» раздует журнал и убьёт V4 Витальность.

## B. Плагин = манифест
```
pack: { id, version, requires: {kernel: ">=1", packs: [...]},
  types: [...], predicates: [{name, from: <interface>, to: <interface>}],
  implements: { "pack:bt/issue": ["core:task"] },      ← анти-силос
  policies: [placement, retention/cold, visibility default],
  consent_purposes: [...], views: [...], capabilities_requested: [...] }
```
**Анти-силос = интерфейсные kernel-типы.** Пак объявляет «мой `issue` реализует `core:task`» → все виды/агенты,
понимающие задачи, видят issue без знания о плагине; предикаты пака типизируются по интерфейсам, поэтому
ребро `pack:bt/issue —blocks→ u:idea` легально. Без интерфейсов маркетплейс = N островов.
**V5:** запись несёт `type@v` + ссылку на манифест; экспорт уносит манифест-цепочку. Удаление плагина →
типы `cold`, данные и рёбра живут. **V7:** установка = грант владельца по `consent_purposes`; `use_consent`
на цель, не на пак целиком. **Изоляция:** софт плагина ходит через сервисный API с токеном, ограниченным
своими типами + чтением интерфейсов (ISO-2/3, ADR-0011).

## C. Кухня шлюза как первый системный пак — это ЛЕСТНИЦА, не шаг
| Ступень | Что | Истина | Гейт выхода |
|---|---|---|---|
| **L0 бумага** | 15 TypeORM-сущностей → манифест `sys:gateway` с `persistence_class` | SQLite | все выразимы, движок не ветвится по имени типа |
| **L1 зеркало** | read-only tail SQLite → проекция в мозг (`derived_from`/`source`, D7) | SQLite | связь задача↔сообщение работает; владелец смотрит через мозг; лаг ≤ N с |
| **L2 полоса PG** | PG-адаптер для `sys:`-полосы, асинхронный горячий API (не MCP) | SQLite | бенч 1M: point-read p95 ≤5 мс, write p95 ≤10 мс, старт не O(N) |
| **L3 dual-write + shadow-read** | шлюз пишет в оба, сравнивает чтения | SQLite | 0 расхождений 7 дней; мозг упал → шлюз жив |
| **L4 cut-over по типу** | холодное→горячее: decision_journal → messages → sessions/topics/bindings/PROMPT → jobs | мозг (по типу) | откат на тип; SLO мозга ≥ SLO шлюза |

**Честная точка трения.** Fail-open возможен только пока мозг НЕ истина. После cut-over тип становится
**fail-closed** зависимостью — доступность мозга = доступность Telegram. Поэтому `seen_updates`/`process_lease`
(класс `ephemeral`) я предлагаю **не переносить никогда**: это механизм процесса, не знание; в мозг уходит их
*след* (event), не сам замок. Если владелец настаивает — мозг должен стать встраиваемой библиотекой в
процесс шлюза над общим PG, а не внешним сервисом. PROMPT.md: файл = истина (D7), мозг индексирует как
`config`; шлюз читает через мозг только с локальным кэшем.

## D. Влияние на ADR-0016
ADR-0016 отверг «мозг в `unit_event`» и **мост** = две истины одновременно. Лестница держит одну истину
**на тип в каждый момент** (L1–L3 мозг = производный вид, L4 = переключение) → дух не нарушен. Но меняются
двери: D1 «один писатель + JSONL» → «один реестр, полосы хранения по типу»; D3 genesis → kernel-пакет.
**Нужен новый ADR-0017 «Слои типов и паки»** (односторонние двери: namespace, запечатанный kernel,
интерфейсные типы, `persistence_class`, capability-на-тип) — до L0-манифеста в коде. Кухня (L2+) —
отдельный ADR-0018 позже + аддендум к ADR-0005 agents-manager. v0.5 не блокируется.

## E. Самый дешёвый решающий тест
**L0 на бумаге + один бенч:** (1) выразить все 15 сущностей шлюза манифестом `sys:gateway` и один чужой пак
(багтрекер: issue/comment/label) через `implements core:task` — 2–3 часа; провал = модель слоёв неверна.
(2) Синтетически масштабировать messages до 1M в PG-полосе, замерить p95 и кросс-пак `find`
(«задачи + их сообщения»). Реальные сообщения — только с согласия владельца (V7, PII третьих лиц).
