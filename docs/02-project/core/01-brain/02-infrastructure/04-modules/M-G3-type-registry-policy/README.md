# M-G3 — Реестр типов + policy-as-data (глобальный)

## Назначение
Слой, где **поведение системы живёт как ДАННЫЕ**. `node-type`, `edge-type`, `view-def` — строки реестра, не
код и не таблицы (I-2). M-G3 держит **3 plugin-порта** (три класса типа-строки) и **гейт добавления типа** —
чтобы открытый реестр не выродился в «свалку синонимов» (риск B консилиума): добавить тип = мини-решение с
объявленной policy, а не тихий INSERT. Рост системы = INSERT типа/вида, не миграция.

## node-type / edge-type (что вводит модуль)
Мета-типы (сам реестр — узлы того же субстрата, self-hosting):
- **node-type `type-def`** — описатель типа. Подвиды по порту: `node-type-def`, `edge-type-def`, `view-def`.
  Payload: seed-схема паспорта/payload, класс связи (thin-ref/assertion) для edge-типов, mode для видов.
- **node-type `policy`** — одна политика = один узел (см. развилку ниже). Payload: предмет, правило,
  ценность-источник, уровень каскада, mode при вариантах.
- **node-type `constitution`** — корневые инварианты (вершина каскада, немигрируемое ядро).
- **edge-type `governed-by`** — `type-def` / любой узел → `policy` (что чем управляется).
- **edge-type `refines`** — `policy` → `policy`/`constitution` (звенья каскада; DAG-инвариант).
- **edge-type `applies-to`** — `policy` → scope/домен/проект (где действует).
- **edge-type `supersedes`** — версия политики → предыдущую (append-only, не удаляем).

## policy-as-data
**Структура policy-узла:** `subject` (на что), `rule` (декларация: constraint / default / valve),
`valueRef` (какая из 7 ценностей питает), `cascadeLevel` (constitution|policy|integrity), `scope`+`applies-to`,
опц. `variant-of` (когда правил несколько — живут оба, выбор — ребром).
**Каскад/композиция:** три уровня, разрешаемые сверху вниз через `refines`:
`Конституция (инвариант, немигрируем) > policy (предметная, переопределяема проектом) > integrity (долг движка на write/read)`.
Композиция = обход рёбер `refines`+`applies-to`, не наследование в коде. Проектная политика **переопределяет**
глобальную для своего scope, не переписывая её (I-1: у каждой свой canonicalId, свой провенанс).
**7 ценностей → policy:** каждая ценность = источник группы политик, а не один узел:
Читаемость→policy рендера/эпист-метки; Тождество→canonicalId/дедуп-инвариант (Конституция); Доверие→provenance/valve
на внешние действия; Витальность→forgetting/метаболизм; Суверенность→DataResidency/localOnly; Реляционность→класс
связи+cascade-taint; Согласие→consent-gate на assertion-рёбрах. Ценность — не узел, а **тег-источник** на policy.

## Поведение-в-БД
- **Гейт типов:** новый `type-def` проходит правило — обязан сослаться `governed-by` на policy «когда вводить
  тип» (тест дубликата/синонима, объявленный класс связи, seed-паспорт). Нет policy → тип не активируется.
- **Валидация:** движок читает `type-def` при записи узла/ребра (паспорт-форма, класс связи, DAG на derived).
- **Разрешение каскада (read-time):** вид `effective-policy` обходит `refines`+`applies-to`+VariantGroup и
  отдаёт действующую политику для (subject, scope). Ничего не «зашивается» — только проекция.

## Развилка «один policy-узел vs много» — ВЕРДИКТ
**МНОГО policy-узлов + один каскад.** Один гигант нарушает I-1/I-2: на его пункт нельзя сослаться, оспорить,
версионировать, дать/отозвать согласие, приписать провенанс; при слиянии БД он — конфликт-магнит и **второй
источник истины** (главный риск консилиума). Много узлов = адресуемость каждой политики, per-value провенанс,
проектный override без переписывания, VariantGroup для «двух правил», журнал изменений по звену. Каскад
`Конституция>policy>integrity` — это рёбра `refines`, разрешаемые read-time. Кандидат-ответ владельца **подтверждён**.

## Память
Реестры-узлы (self-hosted) + append-only журнал: `supersedes`/Observation фиксируют эволюцию политик и типов.

## Global / project
**Глобальный.** Конституция и базовые policy — global; проектные политики = узлы `policy` со `scope=project` и
`applies-to`→проект, переопределяющие глобальные для своего scope через тот же каскад.

## Кросс-связи
M-G1 (движок читает `type-def`/`effective-policy` при каждой записи) · M-G5 (каскад политик самости) ·
M-G4 (DataResidency-policy) · M-P3 (verifier-гейт петель как policy) · все модули регистрируют свои типы здесь.
