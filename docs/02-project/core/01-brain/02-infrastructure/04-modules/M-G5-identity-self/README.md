# M-G5 — Идентичность / самость (глобальный)

## Назначение
Слой, который отвечает на два вопроса: **«кто это?»** (стабильный адрес каждой сущности) и **«чей это граф?»**
(граница брейна + от кого каскадится политика). Держит **`canonicalId`** (I-1) как ключ федерации и
**бесколлизионного слияния БД**, **узел-профиль** (FQ22) как носитель политики ячейки и **корневой профиль
«Самости»** (FQ18) как вершину каскада и границу «чей я». Питает ценности **Ц-2 Тождество** и **Ц-5 Суверенность**.

## node-type / edge-type
- **node-type `profile`** — обычная ячейка (0 новых родов, FQ22): `profile-ref` + inline-`override`, каскад
  `override > profile > конституция`, глубина = 1. Переиспользуем, адресуем.
- **node-type `root-self`** — **корневой экземпляр `profile`** (FQ18 вариант C, НЕ новый род). «Профиль профилей»:
  вершина каскада + граница брейна. Поля: `ownerId`, `stewardId`, `successorId` (единичные root-поля, ретрофит дёшев).
- **edge-type `profile-ref`** — ячейка → `profile` (**thin-ref**: навигация, судьба = судьба узла, не оспаривается).
- **edge-type `same-as`** — canonicalId ↔ canonicalId (**assertion-edge**: адресуемо, оспоримо, свой провенанс) —
  «эти два адреса — одна реальная сущность». Резолюция идентичности при федерации, НЕ мутация ID.
- **edge-type `owned-by` / `steward-of` / `successor-of`** — `root-self` → узел-персона (governance-данные).

## policy-as-data (identity-политики + каскад)
- **`canonicalId`-инвариант = уровень Конституции** (немигрируем): всё адресуемое имеет глобально-уникальный
  стабильный UUID; ссылки — по ID, **никогда по path** (path умирает при реорганизации).
- **Каскад от корневого профиля:** для любой ячейки эффективная политика = `override(ячейки) > profile > root-self`.
  `root-self` сидит на границе конституции — источник дефолтов и «чей я». Глубина = 1 (профиль не несёт своего
  `profile-ref` — конституц. лимит FQ22). Разрешение — обход рёбер, не наследование в коде.
- **merge-policy** — как резолвится `same-as`: чей провенанс/committed выигрывает при конфликте (read-time).
- Политики регистрируются в **M-G3** (`governed-by` → `policy`, `valueRef` → Ц-2/Ц-5).

## Поведение-в-БД (слияние + разрешение идентичности)
- **Слияние двух БД = идемпотентный union** таблиц узлов/рёбер: одинаковый `canonicalId` = буквально одна
  сущность (без перенумерации, без переписывания путей). Разные ID, оказавшиеся одной сущностью → связываются
  `same-as`, а НЕ сливаются мутацией ID.
- **Разрешение идентичности (read-time):** вид `effective-identity` обходит `same-as` (mode `xor` — какой
  canonicalId — канонический представитель кластера). Проекция, ничего не зашивается.
- **Граница «чей я»:** паспорт-колонки `ownerId/tenantId` привязаны к `root-self`; открытие сессии к графу
  сверяется с `root-self` (см. открытый вопрос — возможно уровень движка/деплоя, а не только данных).

## Память
`root-self` + `profile`-узлы (self-hosted) + append-only журнал: `supersedes`/Observation фиксируют смену
owner/steward/successor и эволюцию профилей; `same-as`-ассерции несут провенанс.

## Global / project
**Глобальный.** `root-self` = один на граф (граница брейна, «чей я»); `profile` могут быть `scope=project`.
Федерация/слияние — глобальный механизм. **Bus factor** (FQ18 п.4) = вероятно НЕ узел, а внешний runbook.

## Кросс-связи
M-G3 (profile/policy = узлы реестра; identity-политики `governed-by`; каскад через `refines`) ·
M-G1 (движок применяет `canonicalId`-инвариант на КАЖДОЙ записи, читает `effective-identity`) ·
M-G4 (DataResidency: `ownerId/tenantId` = граница суверенности Ц-5) · M-P2 (`conversationRef` резолвится к идентичности).

## 🔴 Сейчас (ретрофит невозможен)
`canonicalId`-UUID везде · endpoint = ID, никогда path · `profile` = обычная ячейка + `profile-ref` (thin-ref) ·
`root-self` = корневой экземпляр `profile` с owner/steward/successor как ПОЛЯ · глубина каскада = 1 ·
`same-as` = assertion-класс (резолюция, не мутация ID) · паспорт `ownerId/tenantId`.

## 🟢 Позже (дёшево, т.к. заложен I-1)
Реальное слияние двух БД · multi-tenant/shared граф · версионирование `profile-ref` (пин vs latest, blast-radius) ·
цепочка профиль→профиль (только при 2-м живом кейсе) · steward-runbook / мониторинг bus factor · ABAC поверх `ownerId`.

## Открытые вопросы Fable
1. **FQ18 развилка A/B/C:** подтвердить вариант **C** (Самость = корневой `profile`, без нового рода)? Рекомендую C.
2. **Bus factor (FQ18 п.4):** узел в графе ИЛИ внешний runbook (как ADR/Charter, вне метаболизма)? Рекомендую runbook.
3. **«Чей я»** — уровень ДАННЫХ (узел/паспорт) или уровень ДВИЖКА/деплоя (кто вообще может открыть сессию)?
4. `same-as` (cross-DB резолюция) — assertion-edge достаточно, или нужен отдельный merge-policy-узел с tie-break?
5. **NB (FQ21):** узел Самости **≠** 8-я ценность «Идентичность личности» — узел = СХЕМА, ценность = GOVERNING LENS.
   Ц-2 `canonicalId` про ЯЧЕЙКУ, не про ЛИЧНОСТЬ; не закрывать FQ21 ссылкой на M-G5.
