# Сценарии — МАСШТАБ / СТОИМОСТЬ / ПРОИЗВОДИТЕЛЬНОСТЬ (цикл 3)

- **Status:** draft — цикл 3 · **Owner:** JenyaFomin · **Date:** 2026-07-09
- **Related:** `../INDEX.md` (костяк 16 модулей), `../ideas/candidates.md` (полный пул),
  `../open-questions.md`, `../../values/V1-chitaemost/` · `../../../01-overview/01-values/06-relyacionnost/`

> Класс задачи: 10^6–10^7 ячеек. Насыщение индекса, горячие пути чтения, взрыв стоимости токенов,
> массовые миграции/пересчёты, деградация графа-ткани, поиск задыхается раньше данных, батч vs
> суверенный путь на масштабе. Перебираю сценарии, которых ещё нет среди 16 модулей, и вывожу, какая
> инфраструктура из них напрашивается.

## Метод

Взял каждую заявленную опасность класса («поиск задыхается раньше данных», «взрыв токенов», «массовые
миграции», «деградация ткани») и спросил: у какого из 16 модулей это уже ЕСТЬ владелец, а у какого —
только смежное поле без явного механизма. Где владельца нет — новый модуль-кандидат.

## S1 — Дедуп перестаёт быть точным матчем при 10^6–10^7

Ingress Adapter (#13) описан как guard на входе (entity-resolution + идемпотентность), но точный
матч (по canonical_id/алиасам) на 10^7 записей — это либо полный скан, либо индекс, который сам
насыщается. На масштабе дедуп обязан стать **вероятностным** (LSH/MinHash/embedding-blocking с
порогом), а не точным — иначе сам guard становится узким местом раньше данных.

## S2 — Rollup fan-in storm (шторм пересчёта предков)

Read-scale Index (#12) даёт incremental rollup summary-tree, но не решает: что если у узла-предка
(сводки уровня «неделя»/«проект») **много детей меняются одновременно** — каждый чейндж триггерит
пересчёт одного и того же предка. Без коалессинга/дебаунса пересчётов — предок пересчитывается N раз
вместо одного батча. Это отдельный failure mode, не покрытый описанием #12.

## S3 — Дрейф эмбеддингов при смене модели (владелец просил копать явно)

Когда модель эмбеддингов меняется (апгрейд), 10^6–10^7 векторов в старом пространстве **несравнимы**
с новыми. Полный ре-эмбеддинг разом — дорогая batch-операция; частичный — создаёт **split-brain
поиск**: часть корпуса ищется в старом пространстве, часть в новом, near-neighbor результаты
несопоставимы, а пользователь не видит этой границы. Нужен явный протокол: versioned embedding
namespace + shadow-index (параллельно строится новый) + cutover-точка + маркер «в каком пространстве
жила эта грань на момент индексации».

## S4 — Read-triggered confidence write = hot-cell write contention

Confidence (#8) описан как «доверие как живая величина, Байес по использованию». Если апдейт доверия
пишется СИНХРОННО на каждое чтение — то популярная ячейка (referent, который читают 100 агентов/час)
превращается в hot write key: чтение больше не read-only, оно конкурирует за запись с другими
читателями того же узла. На масштабе это классический thundering herd на горячей ячейке. Нужна
развязка: асинхронная/батчевая запись-назад (write-back queue), а не read=write в одной транзакции.

## S5 — Hot/cold граница сама должна масштабироваться

Fast-lane/slow-lane (#12) предполагает классификатор «что горячее». На 10^6–10^7 ячеек периодическая
batch-пересортировка (ночной джоб) даёт **лаг классификации**: ячейка стала горячей в 9 утра, но
переедет в fast-lane только следующей ночью. Нужен streaming top-K (потоковая реклассификация), не
батч-сортировка раз в сутки — иначе «горячий путь чтения» половину времени читает из холодного яруса.

## S6 — Массовая миграция/пересчёт по 10^7 существующих ячеек без владельца

Ни один из 16 модулей не владеет операцией «применить f(cell) → cell' ко ВСЕМ существующим
ячейкам, без даунтайма, резюмируемо после сбоя, с версионированным выходом (старое и новое
сосуществуют на время отката)». Bitemporal (#2) хранит версии, но не оркестрирует массовую
перезапись. Gardener (#14) — про метаболизм по одной ячейке с подтверждением человека, не про
детерминированный батч-джоб по всему корпусу. Схема-миграция (добавить обязательное поле паспорта),
смена ключевой схемы canonical_id, ре-эмбеддинг (S3), рекалибровка confidence (S4/S12) — всё это
частные случаи ОДНОЙ отсутствующей операции.

## S7 — Fan-out explosion на супер-узлах (хабах)

Edge Engine (#11) даёт индекс «все рёбра X», но не бюджет на трассировку. Сущности-хабы («я»,
«работа», «деньги») на масштабе накапливают 10^4–10^5 рёбер. Рендер линзы (#6) или обход графа (Ц6
Реляционность) на таком узле либо взрывается по стоимости, либо теряет навигируемость (граф-ткань
деградирует локально вокруг хабов раньше, чем в среднем по графу). Нужен fan-out budget на
трассировку + механизм разуплотнения хаба (edge-bundling/промежуточные сводные узлы), не только
contagion-circuit-breaker (который про confidence, не про сырой объём рёбер).

## S8 — Нет планировщика бюджета чтения между агентом и Read-scale Index

Явно названная владельцем боль «взрыв стоимости токенов» — структурная, а не случайная. #12 даёт
СТРУКТУРУ данных (summary-tree + эмбеддинги + hot/cold), но никто не решает ВО ВРЕМЯ запроса: на
сколько уровней вниз спускаться по дереву при ДАННОМ бюджете токенов/времени. Без этого слоя
progressive disclosure (Ц1) — просто фиксированная глубина, не адаптивная. Нужен рантайм-планировщик
между агентом и индексом, аналог query optimizer в БД: не «есть ли индекс», а «сколько стоит ЭТОТ
конкретный запрос и как ужать до бюджета».

## S9 — Ремедиация неверного merge canonical_id на масштабе

canonical_id/union-find (#1) описан статично: id + алиасы + классы эквивалентности. На малом масштабе
неверный merge — мелкая неприятность. На 10^7 ячеек, когда на неверно слитый id уже навешаны тысячи
версий/рёбер/провенанс-цепочек, **разлить обратно (re-split)** — комбинаторно дорогая операция:
blast radius растёт со временем жизни ошибки. Нужен явный протокол ремедиации идентичности с
ограничением радиуса поражения — сейчас у #1 нет истории обратимости merge, только forward union-find.

## S10 — Неограниченный рост провенанс-графа (diamond explosion)

Провенанс/Lineage (#4) фиксирует `wasDerivedFrom` как явное ребро. На масштабе ячейка, выведенная из
50 источников, каждый из которых сам выведен из других, порождает граф происхождения, где полный
обход («покажи всё происхождение») — O(корпуса) в худшем случае (классический diamond-dependency
взрыв, как в build-системах). #4 не описывает компакцию — нужна суммаризация/«сквош» линии
происхождения на масштабе (аналог git squash), иначе стоимость трассировки провенанса растёт быстрее
самого графа.

## S11 — Лаг свежести ANN-индекса (поиск задыхается раньше данных, буквально)

«Поиск задыхается раньше данных» — конкретно: ANN-индексы (HNSW и аналоги) на 10^7 векторов обычно
строятся/перестраиваются офлайн-батчем; свежезаписанные ячейки НЕ ищутся, пока не пройдёт следующий
цикл пересборки. Это отдельный лаг от rollup-лага (#12 hot/cold), специфичный именно для векторного
поиска. Нужен двухъярусный индекс: быстрый инкрементальный (малый, неточный, для последних N часов) +
периодический полный ребилд, с явным SLA свежести — иначе «недавно записанное не находится».

## S12 — Батч-пересчёт vs суверенный путь: кто платит consent-tax на 10^7 ячеек

Прямое противоречие класса «батч vs суверенный путь». Если появляется Migration/Recompute Engine
(S6), встаёт вопрос: массовый системный пересчёт (ре-эмбеддинг, рекалибровка confidence) — это
«чтение», которое обязано пройти Единый PEP (#5) + consent-taint (#10) ПО КАЖДОЙ ячейке (10^7
проверок consent на один батч-джоб), или это системная операция с конституционным исключением
(Конституция #16: «движок сам исполняет»)? Без решения — либо consent превращается в узкое горлышко
батча, либо появляется дыра в суверенности (система массово трогает ячейки в обход согласия под
видом «внутренней операции»). **Это развилка уровня конституции, не деталь реализации.**

## S13 — Протокол «пробуждения» spящей ячейки на масштабе

Forgetting Engine (#9) даёт `sleep` (обратимый) как примитив. Но НИКТО не описывает многошаговый флоу
пробуждения на масштабе: спящая ячейка была заэмбежена моделью версии N, сейчас живёт версия N+2
(S3) → при пробуждении её нужно (а) вытащить из холодного яруса, (б) ре-эмбednуть в текущее
пространство, (в) заново прикрепить к дереву сводок (её родительские rollup-узлы могли уже
«забыть» её вклад). Это не одна операция, а составной флоу без владельца — естественно исполняется
через Migration Engine (S6), но должен быть явно описан как binding #9+#12(+S6).

## S14 — Полный обход графа на консистентность становится невозможен

Gardener (#14) — фоновый мотор метаболизма, но текущее описание не разделяет «предложить
переосмысление одной ячейки» и «проверить целостность графа целиком» (висячие рёбра, orphan-узлы
после hard-erase каскада). На 10^6–10^7 полный обход-проверка (mark-and-sweep) — это job, который не
влезает в разумное окно. Нужен явно **инкрементальный/потоковый** consistency-checker (проверяет
дельту с последнего прохода, не весь граф), иначе GC-проверка сама станет узким местом раньше, чем
накопится мусор.

## Самый сильный вывод

Два по-настоящему новых модуля повторяются как субстрат под ПОЛОВИНОЙ сценариев (S3, S6, S9, S10,
S12, S13 — все требуют «безопасно применить операцию ко множеству существующих ячеек»; S8 — отдельная
ось, «сколько стоит ЭТОТ запрос»). Это не совпадение — оба напрямую отвечают на явно названные в
задаче боли («массовые миграции/пересчёты» → #17; «взрыв стоимости токенов» → #18), и ни один из
существующих 16 модулей их не покрывает (Gardener — proposal-based по одной ячейке; Read-scale Index —
структура данных, не планировщик бюджета; Bitemporal — хранит версии, не оркестрирует переход).
