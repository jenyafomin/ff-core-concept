# FQ7 · Обзор вариантов

- **A — заложить `referent` + `hard-erase` сейчас** (рекомендуется).
  Грань резервируется в паспорте, операция hard-erase — в контракте движка с итерации 1.
  Плюс: право на забвение и согласие референта реализуемы. Минус: небольшой аванс сложности сразу.
- **B — добавить позже.**
  Минус: **ретрофит невозможен** — нельзя восстановить, какие старые записи про третьих лиц.
  Класс death-by-design, поэтому вариант отвергается.

## Узел напряжения: append-only (FQ13) ↔ hard-erase
hard-erase — это операция; по FQ13 операции иммутабельны и ложатся в неизменяемый журнал. Прямое
прочтение даёт противоречие: «как удалить то, что обязано остаться в логе навсегда?».

**Разрешение (со-проектируемый инвариант FQ7↔FQ13):**
- журнал хранит только **МЕТАДАННЫЕ** операции стирания (кто/когда/тип/target-id) — они вечны;
- **payload** (содержимое стёртого факта) заменяется **tombstone-маркером** («содержимое удалено по
  согласию референта, T»); сама замена — тоже append-only запись;
- движок ГАРАНТИРУЕТ, что лог не копирует стираемый payload внутрь себя.

Без этого разделения FQ13 построит журнал, физически несовместимый с забвением, и ретрофит будет
невозможен — та же death-by-design категория, что и сам FQ7. Плюс: производные/эмерджентные узлы
(FQ5) должны наследовать стирание источника.
