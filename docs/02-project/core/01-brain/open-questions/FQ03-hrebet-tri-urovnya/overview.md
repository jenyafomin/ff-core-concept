# FQ3 · Обзор вариантов

## 1. Трёхуровневый хребет (рекомендуемый Opus)
Конституция > policy-as-data > integrity/propagation-as-engine-duty.
- **+** Чистое разделение «что нельзя нарушить» / «что ячейка выбирает сама» / «что гарантирует
  коллектив»; закрывает оба найденных провала (конфликт политик, лживая ячейка).
- **+** Прямая опора под маркетплейс/plug-in-видение (Ц-5) без риска, что чужая ячейка обойдёт
  этику через свою же политику.
- **+** Фрактальное совпадение с уже принятой структурой POS (hard constraints > approved docs >
  codebase reality) — переиспользуемый шаблон, не изобретение с нуля.
- **−** Требует сформулировать конституционные инварианты УЖЕ СЕЙЧАС, хотя маркетплейса ещё нет.
- **−** Три локуса вместо одного — выше нагрузка на документацию/governance без дисциплины FQ14.
- **−** (найдено recheck) Механизм различия уровней 1 и 3 нигде не специфицирован — риск, что
  «Конституция» окажется просто ярлыком поверх тех же 2 реальных слоёв.

## 2. Плоская модель (только policy-as-data + движок) — исходная формулировка Opus
- **+** Проще и быстрее для старта, один уровень политики.
- **−** Нет ответа, кто арбитр при конфликте политик двух ячеек и что мешает ячейке солгать о себе.
- **−** Ретрофит уровня конституции позже означает переаудит политики каждой уже написанной
  ячейки — дорого, возможно невозможно для больших объёмов старых записей (аналогия с FQ7 про
  `referent`, но слабее: здесь конфлируется «слой»-концепция с «гранью»-полем данных, см. ниже).

## 3. Движок-командир (всё поведение в движке, ячейка — голые данные)
Классическая централизованная альтернатива, уже отвергнутая ревизией Fable.
- **+** Просто, одно место правды о поведении, легко отлаживать в изоляции.
- **−** Убивает plug-in-видение целиком: чужая ячейка в другом движке теряет поведение, потому что
  поведение жило не в ней. Отвергнута не по вкусу, а по несовместимости с модульностью с 1-й
  итерации (CLAUDE.md проекта, Ц-5).

## Неразведённая граница Конституция / integrity (главный открытый пункт)

Recheck ([checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md), раздел B) показал: обе
гарантии («Конституция» и integrity-as-engine-duty) в тексте описаны как то, что обеспечивает ОДИН
И ТОТ ЖЕ движок. Пример нестыковки внутри исходного документа — «единый порог доступа для всех
каналов» отнесён к Конституции, хотя по формулировке integrity-уровня («категории/связи/дедуп/
конфликты/циклы гарантирует только база») это тот же тип кросс-ячейкового инварианта.

Два прочтения, между которыми пока не сделан выбор:
- **(a) 3 реальных рантайм-слоя** — Конституция имеет собственный механизм исполнения (например,
  отдельный валидатор/линтер политик, вызываемый ДО integrity-проверок).
- **(b) 2 архитектурных слоя** (policy-as-data + движок), где «Конституция» — governance-маркировка
  (ADR-утверждаемое, неизменяемое подмножество правил) внутри того же integrity-as-engine-duty;
  различие уровней — не рантайм, а процедура изменения (ADR vs свободная эволюция).

Ответ нужен до передачи system-architect на engine-spec — иначе границу между уровнями 1 и 3
нечем будет проверить в коде. Также «ретрофит невозможен» (аргумент, calqued с FQ7) справедлив
только для (a): концепция уровня не занимает байт в записи, физически невосстановимо именно
зарезервированное ПОЛЕ (как `referent` в FQ7), а не ярлык уровня — если выбор (b), death-by-design
довод для FQ3 ослабевает.
