# Переверификация FQ14 — Протокол «конституционного чека» фичи

## Вердикт
**УТОЧНИТЬ** — направление («да, нужен дешёвый чек фичи на инварианты») скорее верно, но текущая
формулировка/триаж/статус ✅ маскируют реальную незакрытую поверхность вопроса. Уверенность: средне-высокая (~70%).

## A. Формулировка
Неоднозначно, что такое «фича»: продуктовая фича приложения или грань/операция единицы памяти?
Принятое допущение — любая dev-фича, трогающая брейн/движок. Отдельная проблема: FQ14 стоит в
таблице «Гр.2 — Хребет и движок (**архитектура**)» рядом с FQ3/FQ11/FQ23, но по содержанию это
**процесс/governance**, а не архитектура памяти — категориальное смешение осей в карте вопросов.

## B. Опровержение (стилман)
- Чек не может иметь содержание, пока не ратифицирован сам объект проверки: FQ3 (Конституция) до
  сих пор «ждёт владельца». Протокол «проверь фичу на непротиворечие инвариантам» невозможно
  наполнить, если список инвариантов ещё пуст — это чек-лист для закона, которого ещё нет.
- Проект сейчас явно в фазе DESIGN, не BUILD (`CLAUDE.md` проекта: «НЕ строим — разбираемся, КАК
  построить»). Процесс проверки фич по определению относится к фазе имплементации — вводить его
  «сейчас» как решённый ✅-факт может быть преждевременным governance, а не design-решением.
  Риск governance-fatigue (см. `~/.claude/rules/on-demand/evolution.md`: «автономия/процесс до
  оценки» — анти-паттерн).
- Скрытое допущение: что дешёвый чек-лист = реально предотвращает нарушения. Но ни механизм
  (кто проверяет — человек/reviewer-агент/CI-gate), ни строгость (блокирующий гейт vs
  рекомендация) нигде не описаны — заявлена только метка «✅ дёшево».
- Существенно: этот класс проблемы уже решён на уровне POS глобально — `evolution.md` даёт
  R0-R4 классы риска изменений + права по слоям, `docs-standard.md` — ADR-дисциплину с обязательными
  полями. FQ14 рискует изобретать бесплатно уже существующий механизм вместо того, чтобы сослаться
  на него (как это сделала сама FQ3, переиспользовав `source-of-truth.md` как шаблон для «Конституции
  памяти»).

## C. Триаж — «сейчас» или «потом»?
FQ7 — образец «сейчас» (death-by-design, ретрофит физически невозможен для данных). FQ14 — не
такой: это процессный шаг, который можно ввести в любой момент без retrofit-издержки (это не грань
паспорта ячейки, а шаг ревью). Значит FQ14 логически должен разделиться на:
(a) **решение-обязательство** — да, чек будет существовать (можно принять сейчас, дёшево);
(b) **содержание чека** — невозможно определить до ратификации FQ3 (инварианты ещё не существуют).
Текущий статус «✅ очевидно-да — вводим обязательный чек-лист» сливает (a) и (b) в одну метку,
создавая ложное впечатление, что вопрос полностью закрыт, тогда как содержательная часть ждёт FQ3.

## D. Анатомия vs FQ7 (эталон)
FQ7 имеет `zachem.md` (объясняет неретрофитируемость) + `overview.md` (варианты с trade-offs) —
несмотря на статус 🔴✅, у него полный разбор. FQ14 имеет только `INDEX.md` из двух однострочных
пунктов «Рекомендация/Статус», без `zachem.md`/`overview.md`, хотя реально нерешённые вопросы
(кто проверяет, блокирует ли фичу, как соотносится с FQ3/FQ11/FQ23) не меньше, чем у FQ6/FQ17
(оба помечены ⚠️ «спорно»). По правилу роста из корневого `INDEX.md` («простой ✅ → хватает
INDEX.md; спорный ⚠️ → добавляются zachem/overview») FQ14 сейчас недооформлен относительно
реального объёма неопределённости — по существу ближе к ⚠️, чем к чистому ✅.

## E. Связи (FQ3/FQ23/FQ11) — главная находка
Сама **FQ3/INDEX.md** уже явно называет нерешённый вопрос о границе с FQ14 в разделе «Новые
вопросы»: *«FQ3 (архитектура уровня) и FQ14 (процесс конституционного чека) — один документ или
два разных артефакта (данные/инварианты vs процесс/чеклист)? Разграничить явно при ратификации.»*
Это прямая, уже сформулированная связь — и она **полностью отсутствует** в `FQ14/INDEX.md`: нет
раздела «Контекст», нет ссылки на FQ3, FQ11, FQ23. Дополнительно:
- **FQ23** (стоп-правило слоёв: новый слой только при другом темпе И другом авторе) — сама по себе
  первый кандидат в конституционный инвариант, который чек FQ14 обязан проверять. Не увязано.
- **FQ11** (закон композиции политик, 2-й столп движка) — тоже кандидат-инвариант для проверки
  фич движка. Не увязано.
Отсутствие раздела «Контекст» в FQ14 нарушает же принятую в этой же папке конвенцию (FQ3 имеет
раздел «Контекст» с явными ссылками на FQ7/FQ11/раунд-3).

## Правки (1-5)
1. Добавить в `FQ14/INDEX.md` раздел «Контекст» со ссылками на FQ3 (зависимость по содержанию),
   FQ23 (кандидат-инвариант для проверки), FQ11 (кандидат-инвариант, 2-й столп движка) — воспроизвести
   уже написанную в FQ3 связь, а не оставлять её односторонней.
2. Разделить решение на две части в самом INDEX.md: (a) обязательство «чек будет существовать» —
   можно закрывать ✅ сейчас; (b) «содержание/механизм чека» — статус должен явно висеть на FQ3
   (например «⏳ ждёт ратификации FQ3»), а не быть слитым в общий ✅.
3. Явно сослаться на существующий POS-механизм `~/.claude/rules/on-demand/evolution.md` (R0-R4
   классы риска изменений) и `docs-standard.md` (ADR-дисциплина) как переиспользуемый шаблон для
   самого протокола чека — не изобретать отдельный механизм с нуля.
4. Пересмотреть категоризацию строки FQ14 в таблице «Гр.2 — Хребет и движок (архитектура)» верхнего
   `INDEX.md` — либо пометить как «процесс/governance поверх архитектуры», либо вынести в отдельную
   группу с FQ23 (оба — governance-правила, не архитектура единицы памяти).
5. Добавить короткий `overview.md` (или расширить INDEX.md), фиксирующий минимум: кто исполняет чек
   (владелец / system-architect / reviewer-агент), блокирующий гейт или рекомендация, что происходит
   при провале — иначе статус ✅ не подкреплён содержанием, сравнимо с FQ6/FQ17 (⚠️).

## Под-вопрос для дальнейшей проработки
Сливать ли FQ14 в единый документ с FQ3 («Конституция памяти»: архитектура инвариантов + процесс их
соблюдения в одном артефакте), как сама FQ3 предлагает решить «явно при ратификации» — или держать
двумя раздельными папками с явной перекрёстной ссылкой? И: кто физически исполняет чек — человек
по чек-листу, reviewer-агент (PASS/FAIL gate), или встроенная CI/build-проверка движка?
