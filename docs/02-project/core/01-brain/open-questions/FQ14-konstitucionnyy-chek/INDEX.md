# FQ14 — Протокол конституционного чека фичи

> Родитель: [../INDEX.md](../INDEX.md) · Слой: Гр.2 — Хребет и движок (в карте; по содержанию —
> процесс/governance, не архитектура памяти, см. «Возражения») · ✅ уточняется

## 1. Вопрос
Нужен ли протокол «конституционного чека» каждой новой фичи на непротиворечие инвариантам?
(Допущение: «фича» = любая dev-фича, трогающая брейн/движок, не продуктовая фича приложения —
формулировка неоднозначна, см. «Возражения».)

## 2. Рекомендация
Направление («да, нужен дешёвый чек») скорее верно, но статус ✅ сливает два разных вопроса:
**(a)** обязательство, что чек будет существовать, и **(b)** содержание/механизм чека. (a) можно
закрыть сейчас дёшево. (b) закрыть нельзя, пока нет ратифицированного списка инвариантов —
чек-лист для закона, которого ещё нет (FQ3 всё ещё «ждёт владельца»). Зачем вопрос вообще возник:
дожим Fable, даёт предсказуемость (Г45), дёшево во внедрении.

## 3. Выбор / что делаем
_план, НЕ решение владельца — владелец решает после того, как пункты ниже закрыты._

1. Разделить статус на две части вместо одного слитого ✅:
   - (a) **обязательство «чек будет существовать»** — можно принять сейчас, дёшево.
   - (b) **содержание/механизм чека** (кто исполняет — владелец / reviewer-агент / CI-gate;
     блокирующий гейт или рекомендация; что происходит при провале) — статус висит на
     ратификации FQ3, помечается «⏳ ждёт FQ3», не «✅».
2. Зафиксировать как открытую развилку (не решать здесь): **FQ3 vs FQ14 — один документ или два
   разных артефакта** (данные/инварианты vs процесс/чеклист)? FQ3/INDEX.md уже называет этот вопрос
   в своих «Критериях готовности» — здесь он воспроизведён как та же развилка, не закрыт.
3. При наполнении механизма (после FQ3) не изобретать чек с нуля — переиспользовать уже
   существующие POS-механизмы: `evolution.md` (классы риска изменений R0-R4 + права по слоям) и
   `docs-standard.md` (ADR-дисциплина, обязательные поля) как шаблон.
4. Кандидаты в первые пункты содержания чека (когда оно будет готово): инвариант FQ23
   (стоп-правило слоёв) и инвариант FQ11 (закон композиции политик, 2-й столп движка).

## Возражения
Стилман (полный разбор → [checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md)): чек не
может иметь содержание, пока не ратифицирован сам объект проверки (FQ3). Проект сейчас в фазе
DESIGN, не BUILD — процесс проверки фич по определению относится к фазе имплементации; вводить его
как решённый ✅-факт сейчас рискует быть преждевременным governance (анти-паттерн «автономия до
оценки», `evolution.md`). Скрытое допущение «дешёвый чек-лист = реально предотвращает нарушения» не
подкреплено: ни механизм исполнения, ни строгость (блокирующий гейт vs рекомендация) нигде не
описаны. Также: формулировка «фича» неоднозначна (dev-фича движка vs продуктовая), и позиция FQ14 в
таблице «Гр.2 — архитектура» верхнего `INDEX.md` категориально смешивает процесс/governance с
архитектурой памяти — это отмечается здесь как наблюдение; сама таблица и родительский `INDEX.md` не
трогаются в рамках этой правки.
