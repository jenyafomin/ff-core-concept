# 🔮 FABLE-ANSWER — тип · категория · тег · проекция: одна модель, ноль новых примитивов

> Резюме одной строкой: **тип = паспорт-поле, категория = узел, тег = дешёвая категория,
> проекция = view-def, роль = ребро.** Новых примитивов НЕ нужно — нужна дисциплина «что чем является».

## 0. Единая модель (несущая)

Четыре слова владельца — это ЧЕТЫРЕ разных вопроса к одной ячейке, и каждый ложится на УЖЕ имеющийся примитив:

| Вопрос к ячейке | Слово | Примитив | Кардинальность | Кто меняет |
|---|---|---|---|---|
| «Что это ПО ФОРМЕ?» (какой паспорт/payload, как движок обрабатывает) | **тип** | паспорт-поле `node_type`, значение = строка реестра M-G3 | ровно 1, задаётся при рождении | движок/гейт типов |
| «К чему это ОТНОСИТСЯ в чьей-то логике?» | **категория** | узел `container` + ребро членства | 0..N | пользователь/агент |
| «Какой ЯРЛЫК на это налеплен?» | **тег** | тот же `container` с ослабленной policy | 0..N | кто угодно (по policy) |
| «Каким это ВИДИТСЯ отсюда?» | **проекция** | `view-def` (read-time), ничего не хранит | ∞ | автор вида |
| «Какую РОЛЬ это играет?» (и роль несёт своё состояние) | **грань/аспект** | aspect-узел + ребро `facet-of` | 0..малое N | тот, кто открыл роль |

**Правило различения (одно, механическое):**
- Может ли ответ измениться без изменения самой вещи? Нет → тип. Да → дальше.
- Является ли принадлежность чьим-то АКТОМ (мнением), который нельзя пересчитать из данных? Да → ребро к контейнеру. Нет → view-def.
- Несёт ли грань СВОЁ состояние/жизненный цикл? Да → aspect-узел + `facet-of`. Нет → это просто категория.

Это не «одно и то же на разных уровнях». Это **один субстрат (узел/ребро/поле/вид) и четыре разных
контракта поверх него**. Унифицировать контракты — значит потерять различие «форма vs мнение vs правило»,
и это ровно та ошибка, которая дорого стоит.

## 1. Тип vs категория vs тег

**ВЕРДИКТ:** разные примитивы, НЕ уровни одного. Тип — системное singleton-поле паспорта (реестр M-G3).
Категория — адресуемый узел `container` + ребро членства. Тег — та же категория с другой policy
(без иерархии, без гейта создания, `containerKind: tag`), НЕ третий механизм.

**Обоснование:** у типа и категории противоположные жизненные циклы: тип меняется через гейт-решение
и определяет поведение движка; категория — свободный акт пользователя, движку безразличный. У категории
есть всё, что есть у вещи (canonicalId, provenance, её можно оспорить, переименовать, слить через
`same-as`) — значит, она узел по определению В4.

**Риск наоборот:** (а) слить тип и категорию → пользовательская правка категорий начнёт мутировать
поведение движка, либо гейт типов задушит свободную категоризацию; (б) завести отдельное поле
`tags: []` в паспорте → второй механизм группировки, второй источник истины, теги невидимы для
policy/consent/forgetting.

**Вы не заметили:** тег как отдельный примитив соблазнителен именно потому, что дёшев. Дешевизна —
свойство POLICY контейнера, а не механизма. Один механизм, две policy — и «тег дорастает до категории»
становится сменой policy, а не миграцией данных.

## 2. Одна ячейка — много граней

**ВЕРДИКТ:** один узел = РОВНО ОДИН `node_type`, всегда. «Встреча + идея + задача» — это не три типа,
а один тип формы + роли. Механика двухступенчатая:
- роль БЕЗ собственного состояния («это ещё и идея») → ребро членства в контейнер «идеи»;
- роль СО своим состоянием (задача имеет status/due/done, живущие отдельно от записи) →
  **aspect-узел** (`node_type: cell` или свой тип, паспорт роли) + ребро `facet-of` → базовая запись.

**Лимит / анти-паттерн (когда грани становятся свалкой):** каждый aspect-узел обязан иметь
(а) ≥1 собственное паспортное поле, которого нет у базы, И (б) ≥1 view/policy, который его читает.
Aspect без собственного состояния = должен был быть `member-of`. Это не числовой лимит, а тест;
числовой сигнал тревоги — >5–7 граней у одной ячейки почти всегда значит, что базовый узел на самом
деле контейнер и его надо расщепить.

**Риск наоборот:** мульти-`node_type` (массив типов) ломает всё разом — валидацию паспорта (какая
схема?), policy-разрешение (какая политика?), гейт типов (что гейтить?), слияние БД (какой тип
канонический?). Это самая дорогая из доступных ошибок в этой развилке.

**Вы не заметили:** `facet-of` уже лежит в реестре как thin-ref — но у aspect-узла СВОЙ жизненный цикл
(задачу закрыли, запись живёт). Судьба aspect'а ≠ судьба базы, но и оспаривать «фасетность» некому →
thin-ref корректен, направление стрелки: aspect → база (aspect умирает со своей ролью, база не тронута).

## 3. Группировка: таксономия vs теги vs вычисляемая группа

**ВЕРДИКТ:** грань проходит по признаку «акт vs правило».
- Членство = чей-то АКТ (владелец положил, агент предложил) → ребро к контейнеру. Храним, потому что
  мнение невозможно пересчитать.
- Членство ВЫЧИСЛИМО из данных («все события июля», «salience > x») → `view-def`, НИКОГДА не
  материализованный контейнер (правило «проекция-первой» V1 уже это ратифицировало — примените его сюда).
- Таксономия = контейнеры, вложенные друг в друга рёбрами членства, + policy DAG-инварианта на цикл.

**Риск наоборот:** материализованная «умная папка» = второй источник истины (главный риск консилиума,
он же БОЛЬШОЙ форк синтеза) — она разъедется с данными и никто не заметит.

**Вы не заметили:** гибрид «правило + ручные исключения» (умная папка, откуда владелец руками выкинул
узел) — это view-def + ребро-исключение `excluded-from` (assertion: это акт!). Не решайте это
материализацией — паттерн уже покрывается имеющимися примитивами.

## 4. Где живут схемы и списки категорий

**ВЕРДИКТ:** РАЗНЫЕ места, не смешивать.
- **Схемы** (что такое тип, форма паспорта, класс связи) = M-G3, узлы `type-def`. Вход через гейт.
- **Списки категорий** = обычные `container`-узлы домена 01. Это ДАННЫЕ, не реестр. Создаются свободно.
- **Ограничение «какие категории допустимы для типа X»** = policy-узел M-G3
  (`applies-to` → type-def, правило «member-of только в containerKind ∈ {...}»). Изменение списка =
  правка policy-узла, ноль миграций.

**Обоснование:** реестр отвечает «какие ФОРМЫ существуют», категории — «какие ГРУППИРОВКИ навёл
пользователь». Первое — редкое и гейтованное, второе — ежедневное и свободное.

**Риск наоборот:** затащить категории в M-G3 → каждая новая папка пользователя проходит гейт типов,
система мертвеет; либо гейт ослабляют — и реестр типов превращается в ту самую свалку синонимов.

**Вы не заметили:** синтез уже назвал риск «обход type-gate через `container`» (пробел M-P5). Ответ —
не гейт на контейнеры, а **policy на `containerKind`**: закрытый маленький enum видов контейнера
(folder/category/tag/pool) гейтуется как тип, а ЭКЗЕМПЛЯРЫ свободны. Гейт на класс, свобода на экземпляр.

## 5. Кто навешивает + согласие/провенанс

**ВЕРДИКТ:** три автора — три механики.
- **Движок** навешивает только тип (при рождении) и derived-маркеры. Никогда — категории.
- **Владелец** навешивает членство напрямую: ребро с provenance=owner, вступает в силу сразу.
- **Агент/импорт** навешивает членство как ПРЕДЛОЖЕНИЕ: используйте уже существующий паттерн FQ19
  `origin → confirms → effective` — агентская категоризация есть origin, действующей становится через
  `confirms` (владельцем или policy-автоконфирмом для доверенных агентов).

**Риск наоборот:** агентское членство, неотличимое от владельческого, — прямая дырка в Ц-7 (Согласие)
и Ц-3 (Доверие): нельзя ни оспорить, ни отозвать, ни спросить «кто это сюда положил».

**Вы не заметили (ОСТРОЕ):** `member-of` лежит в реестре как **thin-ref** — но thin-ref по определению
В4 «никто не оспаривает, без паспорта». Как только категории навешивают агенты, членство обретает
автора и оспоримость → это assertion. Не превращайте member-of целиком в assertion (владельческая
навигация должна остаться дешёвой). Расщепите: **`member-of` = thin-ref, только акт владельца**;
**`categorized-as` = assertion** для агентов/импорта/вычислений, с provenance и confirms-петлёй.
Это то же расщепление, что канон уже сделал для `reports-to`/`supervised-by` — примените его симметрично.

## 6. Must-have поля-настройки (короткий список)

**ВЕРДИКТ по узлу** — общий паспорт хорош, но в нём ТРИ дыры. Полный must-have (5 групп, 12 полей):
- **Идентичность:** `canonicalId`, `node_type` — есть.
- **Владение:** `ownerId/tenantId`, `scope`, `storageLevel`, `localOnly` — есть.
- **Жизненный цикл:** `created/updated`, `committed` — есть; **`status`
  (draft|active|archived|tombstone) — ДЫРА №1**: tombstone упомянут только у journal-entry, общего
  lifecycle-поля нет, а forgetting/метаболизм (Ц-4) без него не на чем стоять.
- **Эпистемика:** `provenance` — есть; **`epistemic` (fact|hypothesis|imported|confirmed) — ДЫРА №2**:
  канон msg 141 требует «эпистемический статус = метка, не стена», а колонки нет;
  **`derived` + `derivationRef` — ДЫРА №3**: поправка V1 ратифицировала маркер производности, в паспорт
  не внесён.
- **Витальность:** `salience` — есть.

**ВЕРДИКТ по assertion-ребру** (8 полей, не больше): `canonicalId`, `edge_type`, `from/to`
(только canonicalId), `actor` (кто утверждает), `provenance`, `consent` (taint Ц-7),
`validFrom/validUntil` (**ДЫРА №4**: bitemporal В2 заявлен, но на рёбрах времени валидности нет —
`contradicted-by` без него не работает), `derived`-маркер. Слот реактивного триггера уже зарезервирован — ок.

**Thin-ref:** РОВНО `edge_type` + `target`. Любое добавленное поле — сигнал, что это assertion.
Держите этот тест жёстко.

**Риск наоборот:** «настраиваемость разными векторами» через раздувание паспорта — ловушка. Паспорт —
для того, что читает ДВИЖОК на каждом узле. Всё предметное — в payload по seed-схеме type-def. Каждое
новое паспорт-поле — налог на все узлы навсегда.

## 7. Ограничения модели и вектор расширения

**Ограничения (честно):**
1. Один `node_type` жёсток: смена типа = операция миграции с журналом. Это НАМЕРЕННО дорого — тип есть
   форма, форма не «перетегивается».
2. Read-time проекции на больших графах упрутся в перф → легитимная материализация строго по
   V1-поправке (derivation-rule + rebuild + derived=true).
3. Aspect-узлы умножают количество узлов — плата за адресуемость ролей. Тест из п.2 держит это в узде.

**Вектор расширения (всё = INSERT, ноль миграций):**
- новый тип → type-def через гейт M-G3;
- новая категория/тег → container-узел, свободно;
- новая роль → aspect-узел + facet-of;
- новый взгляд → view-def;
- **плагин = подграф**: пакет из type-def'ов + policy-узлов + view-def'ов, регистрируемый через порты
  M-G3 разом и удаляемый разом (`member-of` → plugin-container). Manifest плагина — это container-узел.
  Маркетплейс из VISION ложится на это без единого нового примитива.

## Три форка

### F1 — D5 `integrity`: пол движка или policy-узлы?
**ВЕРДИКТ: долг движка. Integrity-правила НЕ интерпретируются из узлов на hot-path.** Иначе
bootstrap-цикл: движок читает узлы, чтобы узнать, как валидировать чтение узлов. НО уровень
`integrity` в каскаде ОСТАВИТЬ — как хранимую ДЕКЛАРАЦИЮ контракта движка (адресуемая, аудируемая,
на неё ссылаются policy), а расхождение «декларация vs реальное поведение» ловится conformance-тестом
при rebuild-from-scratch (операция первого дня — она у вас уже есть, повесьте на неё вторую работу).
**Риск наоборот:** integrity как исполняемые узлы = движок без гарантий до чтения БД + произвольная
пользовательская правка инвариантов. **Не заметили:** декларация-без-исполнения — это управляемый
второй источник истины; он легитимен ровно потому, что есть механический тест схождения.

### F2 — Домен 03: отдельный домен или грань домена 01?
**ВЕРДИКТ: НЕ отдельный домен. Грань домена 01** (container + member-of/categorized-as) + одна
policy-группа «taxonomy» в M-G3 (гейт containerKind, DAG-инвариант иерархии, правила допустимости).
Домен = зона смысла с СОБСТВЕННЫМ читателем (у 01 — память, у 02 — оркестрация); у категорий
собственного читателя нет — их читают все. Домен без читателя — это папка с амбициями.
**Риск наоборот:** отдельный домен породит собственные node-types категорий → параллельная система
группировки → та самая свалка. **Не заметили:** M-P5 (модуль «Категории») при этом может жить — как
UX/view-слой над гранью домена 01, но он модуль, а не домен.

### F3 — Мульти-категорийность: VariantGroup(`and`) или N рёбер?
**ВЕРДИКТ: N независимых рёбер.** VariantGroup держит ВАРИАНТЫ одного смысла (конкурирующие
альтернативы с выбором `chosen-in`); членства в N категориях — не альтернативы, а N независимых
актов с разными авторами, временем, провенансом. **Риск наоборот:** слить членства в VariantGroup =
потерять адресуемость каждого акта — нельзя отозвать согласие/забыть/оспорить ОДНО членство, не
тронув остальные. Это тот же грех, что «один гигант policy-узел», который вы уже отвергли — примените
собственный вердикт. **Не заметили:** VariantGroup(`and`) вообще подозрителен как режим: `and` значит
«все варианты истинны одновременно» — но тогда это не варианты, а просто N рёбер. Проверьте, нужен ли
режим `and` хоть где-то; кандидат на удаление из R-A.

## Что вы упустили (сводно, по остроте)

1. **`member-of` thin-ref ломается об агентскую категоризацию** → расщепить на `member-of` (thin-ref,
   владелец) и `categorized-as` (assertion + confirms-петля FQ19). Дырка в Ц-7, чинится имеющимся паттерном.
2. **Четыре дыры паспорта:** `status` (lifecycle), `epistemic`, `derived+derivationRef` на узле,
   `validFrom/validUntil` на assertion-ребре. Все четыре — следствия УЖЕ принятых решений (Ц-4, msg 141,
   V1, В2), просто не донесены до колонок.
3. **Тип ≠ роль** нигде не проговорено — соблазн мульти-`node_type` вернётся при первом же «это и
   встреча, и задача». Зафиксируйте правило п.2 в ADR явно.
4. **Гейт на класс, свобода на экземпляр** (`containerKind` — закрытый enum через гейт, контейнеры —
   свободно) — закрывает названный, но не решённый риск «обход type-gate через container».
5. **Переименование/слияние категорий бесплатно** уже сейчас: категория-узел с canonicalId + `same-as`
   / `supersedes` — назовите это в доке домена 01, чтобы никто не изобрёл отдельную механику.

## Вектор расширения — одной строкой
Система расширяется **четырьмя независимыми векторами** (тип через гейт · контейнер свободно ·
aspect-узел по тесту состояния · view-def без ограничений), и плагин = регистрируемый подграф из этих
же четырёх — новых примитивов не понадобится до тех пор, пока держится правило различения из п.0.
