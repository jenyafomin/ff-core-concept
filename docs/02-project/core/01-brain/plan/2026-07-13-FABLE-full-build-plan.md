# 🗺️ FABLE — полный roadmap сборки (M0 → M8)

> Несущий артефакт. По нему строим. Контракт: 16 решений DECISIONS-LOG (DL-01…DL-16) — не переспариваются.
> Жёсткие входные: **PostgreSQL + миграции с первого дня · новый репо в `TOOLS/` · `agents-manager`
> переиспользуем для оркестрации/агентов/telegram · модель переносима FF↔agents-manager**.

## Логика порядка (почему именно так)

Физическая цепочка зависимостей, не вкусовщина:

1. **Субстрат → реестр → движок (M0)** — всё остальное = узлы НА субстрате. Пока type-gate и журнал не живут, любой модуль, построенный раньше, придётся ретрофитить — а архитектура поклялась расти INSERT'ом, не миграцией (DL-01).
2. **Паспорт добить ДО потребителей (M1)** — 10 полей DL-12 сидят в схеме `nodes`. Добавить колонку после того, как M-G2/M-P2 начали писать узлы, — дёшево физически (Postgres), но дорого семантически: старые узлы без `consent`/`retention` = юридически «серая масса», которую потом не расчистить. Дефолты закладываются, пока БД пуста.
3. **Оркестрация M-G2 раньше Telegram** — Telegram-адаптер БЕЗ Slot/Session некуда доставлять сообщения; Session-узлы — первый настоящий потребитель субстрата и проверка DL-07 (thin-ref) делом.
4. **Telegram M-P2 раньше петель** — петли без живого входа гоняют синтетику; реальный поток сообщений = реальные паттерны.
5. **Петли M-P3 раньше кокпита** — кокпит читает журнал, который петли наполняют; кокпит по пустому журналу — витрина без товара.
6. **Категории/policy (M6) после петель** — `categorized-as` требует confirms-петлю (DL-11 + FQ19), т.е. механику M-P3. Ставить категоризацию раньше петель = assertion без механизма оспаривания = дыра в Ц-7.
7. **Hard-erase (M7) после категорий** — стирание должно каскадировать по ВСЕМ классам рёбер, включая categorized-as; спека забвения пишется по полному, а не растущему реестру типов. НО: обязательство-tombstone живёт с M1 (см. риск R1 — главный риск порядка).
8. **Календарь/отношения (M8) последними** — DL-14 прямо: «INSERT'ом типа, не в первый релиз». Это чистая проверка вектора расширения: если M8 требует миграцию — модель провалена.

## M0 — Walking Skeleton *(принят как есть из `2026-07-12-BUILD-milestone-0.md`)*

- **id:** M0
- **Цель:** доказать 4 несущих инварианта кодом на минимальном субстрате.
- **Scope:** таблицы `nodes`/`edges` (PostgreSQL, миграции, новый репо в `TOOLS/`); node-type seed: `cell · container · journal-entry(kind) · registry-row · view-def`; edge-type seed: `member-of · derived-from · provenance · same-as`; минимальный паспорт (`canonicalId · node_type · scope=private · status · validFrom/validUntil · provenance · derived` + payload JSONB); M-G3 self-host (типы = `registry-row`-узлы, type-gate); M-G1 запись + append-only журнал + read-path через `view-def`. Батчи B0–B5 по milestone-0-доку.
  **Кларификация `view-def`:** это app-level композиция запроса (проекция строится в движке), а **НЕ** динамический `CREATE VIEW`/DDL. Схема БД мутирует только через `migrations/`; view-def не имеет права трогать схему.
- **Критерии приёмки (4 теста-инварианта, в CI навсегда):**
  - T1 `canonicalId-merge` (исполнимо, не лозунг): сид ДВУХ фикстур-датасетов A/B (часть UUID пересекается, часть — разные) → CLI-merge → прогнать ДВАЖДЫ → проверить (а) идемпотентность повторного прогона, (б) разные ID стали `same-as`-ребром, а НЕ мутацией/перенумерацией.
  - T2 `rebuild-from-journal`: снести проекции → пересобрать из журнала → граф идентичен.
  - T3 `projection-first` (статический schema-introspection, НЕ рантайм на пустой БД): в схеме физически нет авторитетной колонки под производное (`effective`/агрегаты); всякий кэш помечен `derived=true`.
  - T3a `dag-guard` (перенесён из M1): цикл в `derived-from` отклоняется на записи — ребро вводится уже в M0-seed.
  - T4 `type-gate`: узел/ребро неизвестного типа отклоняется.
  - T4a `append-only-enforcement`: UPDATE/DELETE на `journal_entry` физически запрещены (триггер/GRANT), не только соглашением в коде.
- **Зависит от:** решение B0 — язык/раннер + инструмент миграций (рекомендация: TypeScript/Node, чтобы модель и типы были переносимы в `agents-manager` без FFI; миграции — node-pg-migrate или Drizzle; финал — за владельцем, это единственный открытый вход M0).
- **Осознанно откладываем:** всё из «🟢 позже» вердикта: агенты, каналы, петли, ACL-механика, эмбеддинги, per-project БД, материализация видов.

## M1 — Паспорт-полнота + реестр закрыт («контракт шва»)

- **id:** M1
- **Цель:** субстрат доведён до полного контракта DL-12, чтобы НИ ОДИН последующий модуль не трогал схему.
- **Scope:**
  - Паспорт +10 полей (DL-12): `status · epistemic · derived · validFrom/validUntil · confidence · language/locale · timezone · retention/TTL · consent-на-узле · acl-to-agents` — все с дефолтами, enforcement позже.
  - Реестр рёбер добит: сироты `supersedes / governed-by / applies-to / refines` → строки M-G3 (коллизия №5 SYNTHESIS-matrix); канон-имена DL-08 зафиксированы в реестре.
  - Расщепление членства (DL-11): `member-of` (thin-ref) vs `categorized-as` (assertion; сам тип заводим сейчас, confirms-петля — M6).
  - Класс ребра (`thin-ref | assertion`) — атрибут строки реестра edge-type. (DAG-проверка `derived-from` уже введена в M0 как T3a — здесь только регресс.)
  - `rebuild`/`reconcile` как CLI-операции движка (DL-05): rebuild = долг M-G1, расписание reconcile = policy-узел (пока один, каркасный).
  - Node-type `profile` (M-G5): корневой профиль владельца = обычный узел; **tombstone-механика — новый `journal-entry` + read-time вычисление видимости, а НЕ UPDATE поля `status`** (сохраняет append-only DL-01); мягкое сокрытие из всех view — предвестник M7.
  - **VariantGroup:** завести явный scope + тест на `mode`/`variant-of` (какие варианты видны в какой view, как выбирается активный) — если не всплыл раньше, фиксируется здесь.
- **Критерии приёмки:**
  - T5 `insert-not-migrate`: новый node-type + edge-type + view-def добавляются транзакцией INSERT'ов; `ls migrations/` не изменился.
  - T6 `scope-private-default`: узел без явного scope невидим ни в одной view кроме owner-view.
  - T7 `bitemporal-smoke` (перенесён раньше M8): лёгкий поведенческий тест — узел с `validFrom` в будущем невидим в «сейчас»-view, виден в «как-будет»-view; проверка колонок `validFrom/validUntil` из M1, а не полный bitemporal-сьют (тот — M8).
  - T8 `tombstone`: tombstone = новый `journal-entry` (НЕ UPDATE `status`); tombstoned-узел исчезает из всех view; T2-rebuild его не воскрешает в проекции; append-only DL-01 не нарушён.
  - T1–T4 (+ T3a `dag-guard`, T4a `append-only`) зелёные на полном паспорте (регресс).
- **Зависит от:** M0.
- **Осознанно откладываем:** enforcement `acl-to-agents`/consent (поля пишутся, движок не проверяет — единственный пользователь пока владелец); `DataResidency` сверх пустых колонок; VariantGroup сверх `mode`+`variant-of` колонок.

## M2 — Оркестрация M-G2 (агенты живут на субстрате)

- **id:** M2
- **Цель:** Personality→Slot→Session как подграф на том же субстрате; `agents-manager` переиспользован как раннер, пишущий через движок.
- **Scope:**
  - Node-types (INSERT): `personality · slot · session`; edge-types: `supervised-by` (иерархия слотов, thin-ref) / `reports-to` (журнал→Slot, assertion) — строго по DL-08; `executed-by`.
  - Session = координата исполнения: thin-ref на узлы домена 01 + короткий буфер-черновик в payload; консолидация — отдельный шаг (DL-07).
  - Журнал-шина: каждая механика пишет `journal-entry(kind=worklog)`; диспетчер читает журнал, не приватные таблицы.
  - «≤1 Active» на слот — partial-index: **легитимная материализация** класса uniqueness по DL-04 → обязана иметь derivation-rule + синхронную инвалидацию.
  - Интеграция `agents-manager`: раннер вызывает **только API движка M-G1** (см. риск R6) — ни одного прямого SQL из шлюза.
- **Критерии приёмки:**
  - T9 `session-thin-ref`: в payload Session нет копий контента домена 01 — только id-ссылки + буфер ≤ лимита.
  - T10 `one-active`: конкурентные INSERT'ы второй Active-сессии на слот — ровно один побеждает (тест гонки, не unit).
  - T11 `journal-spine`: spawn/finish сессии восстановимы из одного журнала (кокпит-предикат заранее).
  - T12 `hierarchy-view`: дерево слотов = read-time view по `supervised-by`, не хранимое поле.
- **Зависит от:** M1 (полный паспорт: session-узлам нужны retention/consent-дефолты); открытый D5 (integrity) НЕ блокирует, но решить до M6.
- **Осознанно откладываем:** реплики/флот слотов, per-project БД (M-G4 физраскол), circuit breaker (M4), кросс-тенант.

## M3 — Telegram M-P2 (первый живой вход) 🎯 ← первая реальная ценность

- **id:** M3
- **Цель:** сообщения владельца из Telegram становятся узлами графа с provenance; агент отвечает с опорой на память, переживающую сессии.
- **Scope:**
  - Node-type `channel-binding`; channel-нейтральный `conversationRef` (🔴-список консилиума); проекция `Topic.threadId` = view, не поле.
  - Входящее сообщение → узел (`cell`/`journal-entry(kind=observation)`) + `provenance`-ребро + consent/retention-дефолты из M1.
  - Гейтвей `agents-manager` (готовый Telegram-транспорт) подключён к M2-сессиям; ответ агента тоже пишется в граф.
  - **Гейт входа реальных данных:** hard-erase SPEC-обязательство (вердикт §3.6) подписано; tombstone (T8) работает — иначе M3 не открывается.
- **Критерии приёмки:**
  - T13 `ingest-provenance`: у каждого узла из TG — provenance до сообщения-источника; `scope=private`.
  - T14 `memory-survives`: факт, сказанный в сессии №1, доступен агенту в сессии №2 через read-path (не через контекст-окно).
  - T15 `unbind-no-orphans`: удаление binding не рвёт граф (узлы остаются, канал отвязан).
  - T8 повторно на реальном узле из TG (tombstone скрывает из ответов агента).
- **Зависит от:** M2; tombstone из M1.
- **Осознанно откладываем:** другие каналы, медиа-пайплайн сверх текста/голоса, эмбеддинги/семантический поиск (read-path пока структурный: типы/рёбра/view).

## M4 — Петли M-P3 (работа становится проверяемой)

- **id:** M4
- **Цель:** Pattern/Task-циклы с verifier-гейтом — агент не «сделал и забыл», а прошёл ворота.
- **Scope:**
  - Node-types: `pattern · task`; канон verified-by по DL-08/коллизии №4: `task → journal-entry(kind=verdict)` (assertion) + `executed-by` на verifier-слот.
  - Гейт читает ТОЛЬКО журнал; `gateState` = read-time проекция, не поле.
  - Circuit breaker: счётчики отказов — второй легитимный класс материализации (hot-path инвариант, DL-04) с синхронной инвалидацией.
  - `derived-from`-DAG между task-артефактами.
- **Критерии приёмки:**
  - T16 `verdict-gate`: task без verdict-узла не переходит в done ни при каком пути записи.
  - T17 `breaker`: N подряд отказов → слот стопится; счётчик помечен `derived=true`, rebuild из журнала даёт то же число.
  - T18 `gate-projection`: снос всех вычисленных gateState + rebuild → идентичные решения гейтов (T2-семейство).
- **Зависит от:** M2 (слоты/сессии), M3 желателен (живой поток), не обязателен.
- **Осознанно откладываем:** worktree-изоляция, авто-эскалации человеку сверх простого стопа.

## M5 — Кокпит M-P4 (доверие через наблюдаемость)

- **id:** M5
- **Цель:** «кто-где-сколько» + cost + Fable self-report — исключительно view-def'ами над журналом.
- **Scope:** пакет view-def'ов (кто работает, где, сколько токенов/денег, что сделано); Fable self-report токенов/контекста как `journal-entry`; ноль новых авторитетных полей — это витринная проверка «проекция-первой» на масштабе продукта.
- **Критерии приёмки:**
  - T19 `cockpit-rebuild`: все цифры кокпита восстановимы из журнала с нуля (расширение T2).
  - T20 `no-new-truth`: статический тест — в схеме/паспорте не появилось ни одного нового хранимого производного без `derived=true`.
- **Зависит от:** M2+M4 (журнал наполнен).
- **Осознанно откладываем:** UI сверх табличных view (рендер в Telegram/файл достаточен); алёрты.

## M6 — Категории + policy-каскад (M-P5 + M-G3 policy)

- **id:** M6
- **Цель:** 7 ценностей = 7 policy-узлов с работающим каскадом; категоризация — оспоримый акт с согласием.
- **Scope:**
  - **Пре-гейт: ратифицировать D5** (integrity = уровень каскада ИЛИ долг движка) — DECISIONS-LOG прямо требует решить ДО обрастания M-G3 policy.
  - 7 policy-узлов (DL-02) + каскад Конституция > policy > integrity; расписание reconcile = policy-узел (DL-05) обретает содержание.
  - `categorized-as` (заведён в M1) получает confirms-петлю на механике M4; taxonomy = policy-группа в M-G3 (DL-10); тег = категория со слабой policy (DL-09); домен 03 = view, не домен.
  - Первый enforcement: consent/acl-to-agents начинают ПРОВЕРЯТЬСЯ движком (поля живут с M1).
- **Критерии приёмки:**
  - T21 `cascade-deterministic`: конфликт policy-узлов разрешается каскадом одинаково при любом порядке вставки.
  - T22 `contest-categorization`: agent-категоризация без confirms не попадает в owner-view как факт; оспаривание меняет статус append'ом, не мутацией.
  - T23 `acl-enforced`: узел с `acl-to-agents` невидим не-перечисленному агенту через ЛЮБОЙ read-path.
- **Зависит от:** M4 (confirms-петля), решение D5.
- **Осознанно откладываем:** per-tenant overrides, богатый UI таксономии.

## M7 — Забвение hard-erase

- **id:** M7
- **Цель:** путь узла «создание → … → hard-erase» реализован как долг движка (DL-13); стирание безусловно и не воскресает.
- **Scope:**
  - SPEC-DRAFT → инженерная спека → реализация. **Пре-гейт: решение владельца FQ7** (каскадирует ли стирание на потомков-агрегаты — определяет цену забвения).
  - Разрешение несущего конфликта **append-only журнал vs стирание**: erase-механика для журнала (crypto-shredding payload'ов или журнальная редакция с erase-маркером) — выбор в спеке.
  - Каскад по всем классам рёбер (включая `categorized-as` из M6) + инвалидация derived-кэшей (breaker, partial-index).
- **Критерии приёмки:**
  - T24 `erase-total`: hard-erase → узла нет в nodes/edges/view/derived-кэшах И `rebuild-from-journal` его НЕ воскрешает. **Обязан адресовать Postgres WAL / бэкапы / реплики:** либо crypto-shredding payload'ов (стёртый ключ → мёртвый payload и в WAL, и в бэкапе), либо ЯВНОЕ письменное признание владельцу, что бэкапы/WAL вне scope стирания (осознанный остаточный риск, не молчание).
  - **T2 ПЕРЕПИСЫВАЕТСЯ:** «rebuild даёт идентичный граф» → «rebuild даёт идентичный граф МИНУС стёртое». Полный прогон T1–T23 после правки — обязателен (см. R2).
  - T25 `erase-cascade`: поведение потомков-агрегатов соответствует решению FQ7 (тест пишется ПО решению).
- **Зависит от:** M6 (полный реестр рёбер), решение FQ7.
- **Осознанно откладываем:** стирание в эмбеддингах/репликах (их ещё нет — потому erase и идёт ДО них; это осознанный порядок, не дыра).

## M8 — Календарь + отношения людей (агрегатор жизни)

- **id:** M8
- **Цель:** первые «грани жизни» чистым INSERT'ом — доказательство вектора расширения (COMPLETENESS §7).
- **Scope:** node-types `event` (`validFrom` в будущем — механика уже в паспорте с M0) и `person` + edge-types отношений (семья/друг/коллега — assertion с consent); view «сегодня/неделя/этот человек»; вход через Telegram («напомни…», «встреча в пятницу»).
- **Критерии приёмки:**
  - T26 `insert-only-extension`: весь M8 — ноль миграций (жёсткая версия T5; если провален — модель неверна, стоп и разбор).
  - T27 `today-view`: bitemporal-запрос «что сегодня» корректен на границах timezone (поле из M1).
  - T28: person-узел + отношения проходят T22/T23 (категоризация людей = самые чувствительные assertion'ы).
- **Зависит от:** M3 (вход), M6 (consent-enforcement — отношения людей без него не заводить), M7 желателен (право стереть человека).
- **Осознанно откладываем:** внешние календари (Google Calendar sync), полный CRM.

## ⚠️ Риски порядка и где перепроверять тестами

| # | Риск | Где стреляет | Митигция |
|---|---|---|---|
| **R1 🔴 главный** | **Реальные личные данные входят в M3, а hard-erase готов только в M7** — четыре майлстоуна БД копит то, что не умеет стирать | M3–M7 | Усиленная митигация: **сырой личный payload (Telegram, M3) пишется в граф ТОЛЬКО когда есть путь tombstone (T8) + hard-erase — иначе это осознанно принятый владельцем риск с письменной пометкой** (не по умолчанию). Плюс: hard-erase SPEC подписан; `retention/TTL` пишется с M1; в M3–M6 не заводить чужие персональные данные (person-типы только в M8, ПОСЛЕ M7) |
| R2 | **T2 (rebuild-from-journal) семантически конфликтует с забвением** — инвариант дня-1 придётся править | M7 | Правка T2 = отдельное ревью + полный прогон T1–T23; это единственная легальная правка инварианта за весь roadmap |
| R3 | **D5 (integrity) не решён**, а M2 уже пишет на шов M-G1↔M-G3 | M2→M6 | Дедлайн решения = конец M2; до него integrity-проверки не хардкодить в движок |
| R4 | **Легитимные материализации** (≤1 Active в M2, breaker в M4) — первые исключения из «проекция-первой»; каждое следующее захочет стать «тоже исключением» | M2, M4 | Каждая — derivation-rule + `derived=true` + тест синхронной инвалидации (T10, T17) + T20 статически ловит безбилетников |
| R5 | **Policy-enforcement только в M6** — до него consent/acl лежат мёртвыми полями | M1–M5 | Приемлемо при одном пользователе-владельце; жёсткое правило: ни одного второго человека/арендатора до M6 |
| R6 | **`agents-manager` пишет мимо движка** (прямой SQL из шлюза) → второй источник истины — главный риск консилиума | M2–M3 | Контракт: раннер видит только API M-G1; T11/T13 проверяют, что всё пришло через журнал; ревью интеграции отдельным гейтом |
| R7 | Язык/раннер (B0) выбран несовместимо с переносимостью FF↔agents-manager | M0 | Решить в B0 с явной проверкой: типы модели импортируемы в agents-manager без дублирования |

**Точки обязательной перепроверки всего сьюта:** конец M1 (полный паспорт), конец M2 (первая гонка/конкуренция), M6 (первый enforcement меняет видимость) и M7 (правка T2). T1–T4 — в CI на каждый коммит навсегда.

## 🎯 Что делает продукт полезным впервые

**M3.** До него — фундамент; после M3 владелец получает то, чего нет ни у одного чата: **память, переживающую сессии** — сказанное в Telegram становится узлами графа с provenance, и агент в новой сессии отвечает с опорой на неё (T14 — это и есть тест ценности). M4–M5 превращают полезное в **доверенное** (гейты + видно кто-где-сколько), M8 — в **агрегатор жизни** (календарь/люди). Если после M3 ценность не ощущается владельцем в ежедневном использовании — стоп и разбор ДО M4: дальше строить дороже.

## 🔍 Перепроверка критика (v2) — поправки к тестам

Порядок майлстоунов НЕ менялся. Все правки — уточнение/усиление тестов и снятие двусмысленности:

1. **M0·T1 `canonicalId-merge`** переписан из лозунга в исполнимый: две фикстуры A/B (частично пересекающиеся UUID) → CLI-merge → прогон ДВАЖДЫ → идемпотентность + разные ID стали `same-as`, не мутацией.
2. **M0·T3 `projection-first`** = статический schema-introspection (в схеме нет авторитетной колонки под производное), а не рантайм на пустой БД.
3. **M0·T4a `append-only-enforcement`** (новый): UPDATE/DELETE на `journal_entry` физически запрещены триггером/GRANT.
4. **DAG-guard → M0** (T3a): ребро `derived-from` вводится в M0-seed, там же и тест; в M1 остаётся регресс.
5. **`view-def` = app-level композиция запроса, НЕ динамический CREATE VIEW/DDL** — впрямую в M0-scope и в модель (схема мутирует только через `migrations/`).
6. **tombstone (M1) = новый `journal-entry` + read-time видимость, НЕ UPDATE `status`** — сохраняет append-only DL-01 (уточнено в scope и T8).
7. **Bitemporal smoke (T7, M1)** — лёгкий поведенческий тест `validFrom`-в-будущем раньше, полный сьют остаётся в M8.
8. **VariantGroup** — явный scope + тест (`mode`/`variant-of`) добавлен пунктом в M1.
9. **M7·T24 `erase-total`** — обязан адресовать Postgres WAL/бэкапы/реплики: crypto-shredding payload'ов ЛИБО явное признание владельцу, что бэкапы вне scope.
10. **R1** усилен: сырой личный payload (M3) пишется только при готовом пути tombstone+erase, иначе — осознанно принятый владельцем риск с письменной пометкой.
