## 2. Лучшая позиция из двух сильнейших (B6 + B1)

B6 и B1 вместе дают тезис, который по отдельности не виден: **корм уже есть, он лежит не в мозге, а в шлюзе.** Привычка «вести дела через агента» у владельца де-факто существует: 2605 его собственных сообщений за 99 дней. Нет не привычки, а читателя. Тогда:

- **память = читатель по адресу над логом шлюза**, а не писатель; в мозг попадает только отобранное (решение/дело/вопрос) с адресом источника `gw:topic56/m8404` (T0 по B6, код `validateSource` это уже допускает);
- B1 «корм» превращается из «владелец, диктуй» в «владелец, подтверди список» (да/нет вместо диктовки: дешевле по вниманию);
- «первое чтение» B2 перестаёт быть `total:0`: оно читает то, что существует.

**Шаг «сейчас» в этой позиции:** ноль новых записей и ноль рук владельца на RUNBOOK. Один запрос только на чтение: `messages where direction='in'` за последние 14 дней (≈234 сообщения), выжимка «что у владельца открыто: обязательства, вопросы, ожидания», выдача в чат. Дешевле контура B1→B3→B2 (не нужен pm2-запуск мозга), даёт полезное чтение сегодня, ничего не персистит, значит вопрос стирания (B5) не возникает.

**Что в позиции слабо (честно):**
1. Фильтр по фразам бесполезен: «надо/нужно/не забыть/напомни» совпали в 1452 из 2605 входящих (56%). Нужна LLM-выжимка, а это токены и приватность содержимого (третьи лица).
2. Это тестирует читателя, а **не рост памяти**. Корень ствола про «в память стало выгодно писать»; читатель над чужим логом может показать, что память = индекс над логом, и тогда мозг остаётся без жизни (его 463 теста не оживают). Это прямая развилка для владельца, не для W5.
3. Не проверено: нет ли у шлюза уже поиска/`/context`, делающего то же. Читал только схему.

## 3. ③ При каком мире оба правы

Сердцебиение и сильнейший «против» совместимы, если **писать в мозг только то, что отобрал читатель и подтвердил владелец**:

1. Читатель (ленивый, над БД шлюза) выдаёт 10 кандидатов с адресами.
2. Владелец одним проходом отмечает да/нет (минимальная привычка, не диктовка).
3. Принятые 5–10 записываются как `backlog-seed` (B1 сам просил этот узел) + семя-вопрос «как растёт память?» (B3) с `source` = адрес сообщения.
4. Утреннее чтение (B2) уже не пустое.

Порядок осей: B6-читатель идёт ПЕРЕД B1, а не вместо. Спор «хук пишет» против «читатель резолвит» исчезает: пишущий хук замораживается (B6b), читатель идёт вперёд (B6a).

**Третий ход:** вопрос B6 («какой запрос не выполнить поиском по БД») становится критерием, а не возражением. Мозг оправдан только тем, что отвечает на запросы, которые SQL по шлюзу не может: «почему принято решение» (`derived_from`), «что заменило» (`supersedes`), прогноз с датой проверки. Это ровно B3, и оно остаётся.

## 4. Вердикт

**Кандидат «сердцебиение» ДОПОЛНЯЕТСЯ, порядок меняется, ядро держится.**

- Добавить шагом 0: читатель над БД шлюза, только чтение, 14 дней, показать владельцу (≈0 новых записей).
- `backlog-seed` берётся из ответа владельца на этот список, а не из памяти лида/диктовки.
- B3 (семя-вопрос + решение с прогнозом) и B2 (одно чтение «открытые вопросы») остаются как есть.
- Карта: B6 делится на B6a (читатель, вперёд) и B6b (хук-писатель, заморожен до запроса, не выполнимого SQL). B5 сжимается до чек-листа трёх дверей перед первой записью. B4 — три ребра, B7/B8 — только слияние с B2 и словарь имён.
- **Проверка (дёшево, до 2026-10-18):** выжимка за 14 дней; если ≥5 из 10 пунктов владелец признаёт реально открытыми, «против» B6/B1 правы и читатель — основной путь корма; если <3, шлюзовой текст слишком шумный и возвращается диктовка B1.
- Развилка владельцу (не решать за него): «память = индекс над логом» или «память = отдельное хранилище отобранного».

Итог: решение — дополнить кандидата шагом 0 «читатель над шлюзом, read-only» и разделить B6 на читателя и хук; проверка до 2026-10-18.
Вопрос-цель: ответил — если «против» правы, карта сжимается (B6b/B7/B8 заморожены, B5 = чек-лист), а «сейчас» получает дешёвый шаг 0 без рук владельца; оговорка: рамка «рост памяти» против «индекс над логом» остаётся неразрешённой и требует владельца.
