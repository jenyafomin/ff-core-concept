Источник п.2, 5, 6, 19. Жизнь = 0: мозг не запущен, поэтому «сейчас» значит «можно спроектировать и разрешить», а не «уже пишет».

## 3. Находки, меняющие картину
1. **Сырой адрес шлюза не пройдёт валидацию.** `validateSource` отвергает `ref` с цепочкой ≥9 цифр (`pii-scope.ts:62-72`, `contract.ts:153`), а chat id = `-1004351636302`. Нужен алиас чата вне мозга + тема + message_id (`gw:topic56/m8404`); новый `kind` не нужен, `url` разрешает `: / #`.
2. **Идемпотентность по message_id уже есть на двух уровнях:** шлюз (`orchestrator.ts:79-88`, ключ `channel:conv:msg`) и brain idem v1 (`ordinal.ts:26-38`, `idem.ts`, заморожен ADR-0017 D4). Ретрай хода дубля не даст. Не покрыто: одинаковый контент с разными message_id и голосовой дубль до влива P-2. Дедуп шлюза держит 2000 ключей и пишет fire-and-forget (`dedup-store.ts:41-56`).
3. **Лог п.5 фактически уже ведётся шлюзом** (`unit_event`), но это решения о доступе к инструментам, а не результаты дел. Годится как хронология действий. Поле `reason` не проверено на PII.
4. **Транскрипты скоропортящиеся:** старейший файл ровно ~30 дней, `cleanupPeriodDays` в `~/.claude/settings.json` не задан. Адрес в БД шлюза долговечнее.
5. **V5 напрягается:** адрес в чужую БД привязывает единицу к конкретному шлюзу. Смягчение: соленый хеш + алиас, висячий адрес допустим (семантика dangling есть).
6. **Хук:** в шлюзе уже есть программная точка (`sdk-query.adapter.ts:49-53`, только PreToolUse). Глобальные хуки пользователя — `echo`/`osascript`. Подхватывает ли SDK-раннер хуки из settings, неизвестно.

## 4. Против
Шлюз уже хранит всё нужное и с ключами. Хук-писатель строит второй индекс для мозга без записей и без читателя (B2 тоже жизнь = 0): объём без запроса бьёт по V4/V1. Возможно, рамка неверна: не «хук пишет акт», а «читатель резолвит адрес по запросу» (ноль записей в мозг), а в мозг идёт только отобранное, то есть B1+B3. Вопрос, вскрывающий рамку: какой запрос B2 в первые 7 дней нельзя выполнить прямым поиском по БД шлюза?

## 5. Ответ на вопрос-цель
- **Безопасно адресом сразу (T0):** алиас чата, тема, message_id, соленый хеш, время; машинные поля хода (тулы, пути проекта, счётчики — T1 после проверки на имена). Стирание источника даёт висячий адрес, а не утечку. Ограничить белым списком чатов (в `.gateway/conversations` ≥8 чатов; брать топик 56/личный).
- **Ждёт `hard_erase` в brain (T2):** всё, выведенное из содержимого: темы и заголовки («важные переписки» п.2 требуют оценки по тексту), выжимки, люди, транскрипты голосовых, retention-классы (п.9). В engine акт `erased` есть (`types.ts:256`), в brain нет.
- **Ждёт отдельно:** голосовые до влива P-2.

## 6. Связи наружу
Нужны: **B5** (`erase-gate`, жёстко), **B1** (`source-pointers` — тот же узел, владеть должен B6), **B2** (читатель адреса). Открывает: **B2** (богатство), **B3** (derived_from из хода), **B7** (лента по времени), **B4-люди** (после B5).

## 7. Оценка «куда сейчас»
0.3 = unlocks 2 (B1, B2) × код 0.3 (формы есть, писателя нет, валидатор режет адрес) × чтение 0.5. Срез T0 (`msg-address`+`tool-journal`) после алиаса ≈ 0.6, но ниже контура B1→B3→B2 (B1 даёт 2). Вывод: B6 не на первом сердцебиении; делать узко после живого B1, T2 заморожен.

## Не знаем
Работают ли settings-хуки под SDK-раннером; хранятся ли транскрипты дольше 30 дней; чистый ли `unit_event.reason`; нужен ли владельцу автозахват именно «важного» (оценка по содержимому = T2).

Итог: решение — захват адресом (T0/T1) разрешён после алиаса чата и белого списка; T2 и голосовые отложены до `hard_erase` в brain и влива P-2; сам B6 отложен до живого B1.
Вопрос-цель: ответил — T0/T1 безопасны, T2 ждёт стирания; вопрос частично неверен: сначала надо спросить, какой запрос B2 требует записи, а не чтения шлюза.
