## Вопрос владельца
«Если бы инструмент аренды строили на памяти — занимались бы наполнением; типы, правила, рекурсия; гибко; разные анализы. Сколько стоит и как реализовать в этом ключе?»

## Свод (2 линзы сходятся)
- **Вектор верен как ГИБРИД, неверен как замена.** Память = общий слой процессов, знаний, жизненных циклов, связей и анализа (+ единый контекст для агентов). Деньги/двойная запись, синхронизация Sheets, ПДн, интерактивный UI — специализированные ядра в коде.
- Аналогия: 1С/Salesforce/Odoo/Airtable — выигрывают на справочниках, циклах, задачах, анализе; проигрывают на деньгах, скорости отчётов, сложном UI, и рискуют стать «вторым языком программирования». Удачные дают НЕСКОЛЬКО типизированных примитивов (как «регистр» в 1С), а не один общий узел.
- **Стены памяти сейчас:** нет транзакций/constraints, конкурентной записи, индексов агрегаций (→ после Postgres); ПДн нельзя до стирания/согласия (V7).
- **«Наполнение без мысли» — полуправда:** проектирование переезжает в схему типов; ошибка типа в append-only дороже.
- **Цена:** один бизнес «на памяти с нуля» — дорого (движок + продукт); гибрид — мало/средне; движок окупается на 2–3 бизнесах только с общими примитивами. Честная цифра — после живого прогона.
- **Переписывать rentacar — нет.** Живой продукт, Phase 5.

## Тест вектора (1 сессия, без ПДн и денег)
Взять 1 жизненный цикл rentacar (напр. перегон/претензия/задача) ИЛИ слой знаний (BP/BR/GAP/ADR), объявить типы ДАННЫМИ, наполнить обезличенными событиями/адресами, ответить общим видом на 3 реальных вопроса владельца. **Провал:** хоть один ответ потребовал правки кода памяти. (Вариант critic с деньгами — баланс инвестора через готовую вертикаль `ingest-rentacar → engine → rental-balance` — сверять суммы с SQL rentacar; только на обезличенном срезе.)

## Вопросы, вскрывающие рамку (владельцу)
1. Что в rentacar было ДОРОГО менять за 3 месяца: модель и процесс — или деньги, синхронизация, интерфейс? (первое → вектор памяти бьёт в цель; второе → память не поможет)
2. Чего хочется на деле: гибкости процесса, анализа или единого контекста для агентов? (все три достижимы без переписывания)
