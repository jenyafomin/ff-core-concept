Потребитель: владелец (развилки) + следующая сессия трека «мозг». Поглощает: ответы analyst + critic этой волны (сырьё в контекстах агентов).

## Вопрос-цель
Как динамически давать топикам доступ к памяти и как совместить «FF — общая» с изолированными проектами (rentacar)?

## Факты (analyst, file:line по коду)
- Под шлюзом доступ = `readers.json → chats["chat"|"chat:thread"]` (`packages/brain/src/read/access.ts:60-90`). `cli` (по папке) топикам не помогает — поэтому сейчас из Telegram пусто/SCOPE_DENIED.
- Слияние chat→thread поверхностное: scopes топика ЗАМЕНЯЮТ scopes чата (`access.ts:73`).
- Файл перечитывается без рестарта (`service/readers.ts:19-21`); API для правки нет — только файл.
- Команды шлюза доходят только от владельца (`telegram-channel.ts:489,728`); образец — `/bind` + `patchLevelConfig` (`command-handler.ts:1370,1423`). Новая команда ≈40 строк. Имя `/memory` занято → `/access` или `/brain`.
- Видимость идёт от записи ВВЕРХ к родителям: родитель видит всё под собой (`access.ts:207,235`). Запись может лежать в нескольких областях (до 10).
- `write` — на читателе целиком, не на области (`access.ts:82`).
- Родителя к существующей области не повесить без кода (`domain/schemas.ts:73-74`).
- Хранилище: один append-only журнал, одна очередь записи, проекция в RAM, find = подстрока без индекса. Postgres меняет носитель (надёжность, бэкап вне Mac, сеть), модель доступа не решает.

## Критика (critic) и как снята
- «Команда = самоэскалация агента» → **снято фактом**: команды парсит код шлюза из сообщений владельца; агент их вызвать не может. Остаётся: команда — только владелец, только кодом, не LLM.
- «rentacar под ff → ПДн видны всем» → **принято**: ff НЕ делать родителем. Модель = мульти-области: топик rentacar получает `[rentacar, ff]`, топик FF — `[ff]`.
- «Топик-настройщик = суперпользователь, правила в памяти = вечная инъекция» → **принято частично**: правила ДОСТУПА живут вне памяти (readers.json, правит шлюз по команде владельца); правила ЗАПОЛНЕНИЯ (как писать, типы) — в памяти; CLAUDE.md проекта — только указатель, не копия.
- «Postgres — не главное узкое место» → **принято**: узкие места = модель доступа (профили), обзор, типы.
- Рефрейм: не «тумблер на топике», а **профиль проекта** (области + запись + типы), который топик получает при `/bind`.

## Открытые развилки владельцу
1. Команда `/access` в шлюзе (профиль на топик) — да/нет.
2. Нужна ли «запись только в свою область» (read ff, write только rentacar) — это правка кода.
3. Топик-настройщик: только правила заполнения/типы, без прав на доступ — ок?

Итог: задача в плане (второй волны трека «мозг»), ждёт «да» владельца по развилкам 1–3.

## Волна 2 (2026-10-23): ответы владельца + 3 линзы (analyst · abstract-thinker · critic)
Владелец: `/access` = да, инлайн-список с эмодзи + «Сохранить»; запись пока всем полная; центральная точка входа — да, глобальная + на проект.

### /access — дизайн (analyst, по коду шлюза)
- Есть всё нужное: callback_query с проверкой нажавшего (`telegram-channel.ts:466,726`), паттерн меню-кнопок с префиксами (`parse-control.util.ts:65`), состояние в первой строке сообщения (`file-browser-handler.ts:30`), `GATEWAY_BRAIN_HOME` (`brain-client.ts:29`). Нет: префикса `ac:`, команды, списка областей от сервиса.
- Эмодзи: ✅ сохранена · ➕ добавить · ➖ убрать · ⬜ нет. Тап: ⬜↔➕, ✅↔➖. Кнопки «💾 Сохранить (+N −M)» / «✖ Отмена».
- Черновик — в самом сообщении (переживает рестарт). Перед записью перечитать файл, сверить версию; запись tmp→fsync→rename + .bak (НЕ как `patchLevelConfig`, тот пишет голым writeFile).
- Список областей — лучше вызовом сервиса, не чтением service.json.
- Место под права записи: вторая кнопка в строке 👁/✍️, поле `write_scopes[]` (обратно совместимо).

### Критичное (critic, подтверждено analyst)
1. **Показывать ЭФФЕКТИВНЫЙ доступ и откуда он** (топик/чат): scopes топика заменяют чат → можно молча отрезать `ff`. При первом сохранении в топик копировать унаследованный набор.
2. **«Запись всем полная» — ок ТОЛЬКО до rentacar.** ПДн, записанные в `ff`, станут видны всем, а стирание (V7 hard_erase) не подключено. Ограничение «писать только в свою область» = предусловие подключения rentacar, не «потом».
3. Дефолт нового топика — решить явно (рекомендация: минимум).
4. Новые области в списке появляются только после заведения в сервисе + рестарта — подсказать в карточке.

### Центральная точка (abstract-thinker + critic, сходятся)
- «Обзор» = два слоя: **карта** (генерируется кодом: области×типы×статусы, счётчики, свежесть — не протухает) + **устав** (5–15 строк рукой: что писать, как называть; = готовый `sys:prompt-layer applies-to: scope`, нового механизма не нужно).
- Уровни: глобальная (~1.5k симв.) → проектная (~2.5k + 3–5 готовых find) → обычный find.
- Устав пишет/утверждает владелец (агент предлагает) — V3. Дата рядом; расхождение карта↔устав = видимый сигнал дрейфа (V4).
- CLAUDE.md проекта: одна строка «первым ходом — обзор памяти». Правила ЗАПОЛНЕНИЯ памяти — в уставе; правила работы проекта — в CLAUDE.md. Не копировать.
- Вскрывающий вопрос: слепота наблюдалась или ожидается? Может, корень — бедные типы (task/decision/note) и слабый find. Дешёвая проверка: холодный агент + 2–3 реальных вопроса.

### Порядок (свод)
0. Временно: скрипт `chats`-доступа для нужных топиков (владелец запускает) — чтобы память заработала из Telegram уже сейчас.
1. Пресет `overview` (только карта, генерируемая) — малый код.
2. `/access` с кнопками (+ эффективный доступ и источник).
3. Устав ff как слой; строка-указатель в CLAUDE.md.
4. До rentacar: запись только в свою область + дефолт нового топика.

Итог: задачи в плане второй волны; к коду — по «строй» владельца.
