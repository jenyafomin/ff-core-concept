## Проблема
Топики шлюза не видят памяти: доступ в `readers.json → chats` правится только руками владельца. Право записи — на весь топик, не на область (риск ПДн при rentacar). Обзора «что где лежит» нет.

## Контракт данных (общий для обеих частей) — `readers.json`
`ChatBinding` и `CliBinding` получают необязательное поле `write_scopes?: string[]` (слаги/ids областей, как в `scopes`).
- Если `write_scopes` ЗАДАНО: запись разрешена ТОЛЬКО в эти области; каждая из них должна быть и в `scopes` (запись ⇒ чтение; лишнее в `write_scopes` вне `scopes` игнорируется, warn). `write` считается `write_scopes.length > 0`.
- Если НЕ задано: прежнее поведение (`write: true` = во все `scopes`). Полная обратная совместимость.
- `default_scope`, если не в `write_scopes`, для записи не используется — берётся первая из `write_scopes`.
- Слияние chat→thread остаётся поверхностным; `write_scopes` следует тем же правилам (топик заменяет чат).

## Часть A — ff-brain (`packages/brain`, при необходимости `packages/brain-mcp`)
A1. Резолвер читателя несёт `write_scopes` в `Reader`.
A2. Проверка записи (record, link, любые записывающие пути): каждая область записи ⊆ `write_scopes` (если задано); иначе отказ `SCOPE_DENIED` с понятным `hint` («запись в область X закрыта для этого чата, есть только чтение»).
A3. Пресет `find preset:"overview"`: БЕЗ тел. По каждой видимой читателю области: имя/слаг, режим (👁/✍️), счётчики по типам × статусам, число cold, дата последней записи. Плюс итог. Бюджет ответа ≤ ~1500 символов (обрезка с пометкой). Описание MCP-инструмента обновить («overview — карта памяти, первый вызов»).
A4. Тесты: запись в область только-чтение → отказ; legacy `write:true` без `write_scopes` → как раньше; overview на фикстуре с 2 областями — счётчики верны, чужая область не видна, тел нет.

## Часть B — шлюз agents-manager: команда `/access`
B1. `/access` в топике → карточка для ключа топика (`chat:thread`, тот же формат, что шлюз кладёт в `FF_BRAIN_CONVERSATION_ID`); `/access group` → уровень всей группы (`chat`). Только владелец (существующая авторизация канала + проверка нажавшего на callback).
B2. Список областей — из `service.json` (`GATEWAY_BRAIN_HOME`, по умолчанию `~/.ff-brain`) `scopes[]`. Область в binding, но не в service.json → строка «⚠️ неизвестна», не стирается.
B3. Главный экран: строка на область: `<режим> <имя>` где режим ⬜ нет · 👁 чтение · ✍️ чтение+запись; если в черновике изменено — пометка `→ <новый режим>`. Над списком: «Действует: свой набор топика / унаследован от группы». Снизу: `💾 Сохранить (N изм.)` · `✖ Отмена`. Подсказка: «новые проекты появляются после заведения в памяти и рестарта ff-brain».
B4. Тап по области → экран области: кнопки `⬜ Нет` · `👁 Чтение` · `✍️ Чтение + запись` (текущий/черновой отмечен) · `⬅ Назад`. Выбор пишется в черновик, возврат на главный.
B5. Черновик хранится в самом сообщении (первая строка/скрытое состояние, как файловый браузер), не в памяти процесса; callback_data ≤ 64 байт (индексы).
B6. Сохранить: перечитать `readers.json`, сверить версию (mtime+size или hash, снятые при открытии карточки) → если изменился, «файл изменён, открой /access заново». При первом сохранении в топик без своей записи — взять унаследованный набор группы за основу. Записать `scopes`, `write_scopes`, `write` (= write_scopes непуст), сохранить остальные поля binding и файла. Атомарно: `.bak-<ts>` → tmp в той же папке → fsync → rename, права 0600. Сервис мозга подхватит сам.
B7. Итог-сообщение: что изменилось (+/−/режимы).
B8. Тесты: парсинг команды; рендер карточки (эффективный набор + источник); переключение режима в черновике; save — слияние, атомарность (tmp+rename), сохранение чужих полей, отказ при смене версии; чужое нажатие отклонено.
