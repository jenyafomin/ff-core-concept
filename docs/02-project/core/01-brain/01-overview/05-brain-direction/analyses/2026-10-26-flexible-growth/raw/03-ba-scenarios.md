## 2. Тип · вид · правило

**S1 Туду.** Тип: `task` {глагол+предмет, область, due?, why, статус open/doing/done/dropped, источник=голос}. Виды: А — «что открыто/просрочено в моей области»; В — канбан по статусу + «сегодня»; П — календарь по due, напоминание. Правило: без due → «входящие»; due наступил → событие; done только по слову владельца.

**S2 Ритм фокуса.** Тип: `commitment` {период, направление, результат «человек X может сделать Y», адресат, доля}. Вид: В — неделя + итог пятницы; А — «что обещано кому»; П — календарь/цикл. Правило: пятница → вопрос «показано ли адресату»; повтор раз в неделю.

**S3 Rentacar.** Тип: поток `event` (платёж, выдача, бронь) + `state` (клиент/авто); баланс — производное, не запись. Вид: П — наблюдатель/отчёт; В — свод; А — только агрегаты. Правило: событие → пересчёт; срок брони → календарь. ПДн: тело вне памяти, в памяти адрес+агрегат.

**S4 Решения.** Тип: `decision` {выбрано X, rationale, автор «со слов»/«вывод агента», proposed→approved→superseded}. Вид: А — «что решено про…»; В — лента по области; П — граф supersedes. Правило: новое решение закрывает старое, не дубль.

**S5 Вопросы.** Тип: `question` {формулировка, статус open/answered/changed/reframed/dropped, ссылка на ответ}. Вид: А — «поднять открытые на старте»; В — 3–7 на старт/конец; П — счётчик. Правило: старт/конец сессии — событие; reframed сохраняет старую формулировку.

**S6 Итог сессии.** Тип: `note` {1–2 строки + source.ref+hash}. Вид: А — «где остановились»; В — по датам; П — сверка хеша. Правило: ≤1 на сессию; хеш не совпал → stale.

**S7 Промпты шлюза.** Тип: `layer` {область чата/топика, адрес текста, версия}. Вид: П — шлюз читает каскад на каждый ход; А — «в каком я слое»; В — правка. Правило: правка действует со следующего хода; откат по версии.

**S8 Зёрна.** Тип: `seed` {type из 5, seed, spark, link, seed→candidate→direction}. Вид: А — «похожие зёрна до новой идеи»; В — периодический синтез; П — счёт зрелости. Правило: закрытие темы → консолидация; давно не касались → cold.

**S9 Люди.** Тип: `party` {роль, область}; имени нет. Вид: А — только роль («бухгалтер», «PM»); В — полное. Правило: имена третьих лиц не пишем (устав п.9).

**S10 Cardex deal-flow.** Тип: task+decision+question по ролям заказчика {источник ТЗ, версия}. Вид: В — «чего ждём от кого». Правило: ожидание ответа → срок → напоминание.

## 3. Повторы — кандидаты в общие примитивы

1. **Статусный жизненный цикл** — S1, S4, S5, S8, S10. Механизм: тип объявляет свои статусы и допустимые переходы.
2. **Время/календарь** — S1, S2, S3 (бронь), S5 (старт/конец), S10. Общее: поле `when` + событие «наступило» + повтор.
3. **Группировка по области** — все. Уже есть.
4. **Новое закрывает старое** (proposed→approved, supersedes) — S4, S7, S8, S6 (stale по хешу).
5. **Адрес вместо тела** (source.ref+hash) — S3, S4, S6, S7.
6. **Автор/уверенность** («со слов»/«вывод») — S4, S6, S8.
7. **Связь** (решает/отвечает/заменяет) — S4, S5, S8, S10.
8. **Затухание (cold)** — S1 (брошенное), S5, S8.
9. **Роль без лица** — S3, S9, S10.

Вывод: типов много, примитивов около пяти — статус-цикл, время, адрес+хеш, связь, область. task/decision/note — частные случаи; question, seed, commitment, layer — те же примитивы с другими статусами. Это гипотеза [Г]: по 10 сценариям, не по измеренному использованию.

## 4. Что ломает простую модель

- **S3 Rentacar** — поток событий, не карточки: баланс производный, объём, ПДн. Главный стресс «все как узлы».
- **S9 Люди** — V7: запись о третьем лице запрещена, а польза (кто это) требует хранить. Выход — роль/адрес; но «контакты» как сервис без согласия не получатся.
- **S7 Промпты** — читает программа на каждый ход (горячий путь, версия, откат), не агент по запросу.
- **S2 Ритм** — повторяющиеся обязательства; одного `due` мало.
- **S1 Туду** — «done по слову владельца» при записи агентом: право смены статуса зависит от потребителя.
- **S8 Зёрна** — объект меняет тип (seed→direction): тождество должно пережить смену типа (V2).
- **S6 stale** — правило зависит от внешнего файла (git), не от памяти.

## 5. Два первых сценария как живая проверка

1. **Личный: S1 Туду-пул** (область personal). Уже заявлен первым в RUNBOOK. Проверяет статус-цикл, due/календарь, три вида (канбан для В, «что открыто» для А, напоминание для П), право «done по слову». Критерий гибкости [Г]: добавить статус или поле без миграции кода.
2. **Проектный: S4+S5(+S10) Решения и вопросы Cardex deal-flow**, не rentacar. Причина: rentacar несёт ПДн, потоковость и согласие (enforcement V7 в движке пока не подключён — только форма), слишком много неизвестного. Cardex: роли без лиц, статус-цикл + связь + «жду ответа от роли» + срок. Проверяет supersedes, link, календарь ожиданий и второй тип поверх тех же примитивов. Rentacar (S3) — вторым этапом как стресс-тест потока событий после решения по ПДн.
