# Critic: ловушка "максимальной гибкости" памяти ff-brain

- Status: draft (raw, линза critic)
- Owner: jenya.stasik@gmail.com
- Date: 2026-10-26
- Потребитель: лид волны 2026-10-26-flexible-growth (свод). Поглощает: ничего.
- Вопрос-цель: где гибкость превратится в ловушку и как совместить её с пользой на этой неделе.
- Допущения (не проверял по коду, взято из постановки лида): в памяти 3 записи; видов зашито 5-7; docs:code ~14:1.

## Critical

1. Три примитива выводятся из 0 живых случаев. Lens: assumption audit.
   Тип/вид/правило спроектированы по воображаемым потребителям. Память пуста, "правильная форма типа" неизвестна. Это ровно та же болезнь, что признана 08-16: шлифуем замок на пустом хранилище. Тройка-как-данные - это "уровень N+1" (compound-engineering п.5) до живого прогона уровня N. Worst case: ещё 2-3 месяца дизайна платформы, 3 записи в базе.

2. ПРАВИЛО (событие -> условие -> действие) как данные, которые пишет агент, а владелец "утверждает" = постоянная инъекция. Lens: security / V3. Агент пишет автозаписи (proposed) из недоверенного контента (письма, чужие сообщения). Правило-как-данные - исполняемый артефакт, и утверждение владельцем одним тапом по непонятному DSL это rubber-stamp. Правило срабатывает позже и без владельца: ревью происходит не в момент действия. Любая запись, влияющая на поведение (правило, вид с форматом, тип с lifecycle), должна быть за отдельным, более жёстким шлюзом, чем обычная запись. Сейчас таких нет. V7 enforcement тоже "только форма" - правило, читающее данные третьих лиц, обходит согласие.

## Concerns

3. Inner-platform effect реален для ПРАВИЛА и ВИДА-с-языком. Lens: failure mode. Выборка+группировка+формат = маленький язык запросов; событие-условие-действие = язык правил. Цена данных вместо кода: нет типов и компилятора, отладка "почему правило не сработало" без стектрейса, тесты нужны на каждый экземпляр данных, миграции схемы правил, версии. Гибкость данных дешевле кода только когда правит НЕ программист и часто. Здесь правит лид/агент раз в неделю - код (TS-модуль + тест + PR) дешевле и безопаснее.
4. ТИП: открытые поля уже дают 80% гибкости. Формализованный lifecycle-как-данные - преждевременно. Lens: scalability. Каждый новый тип с жизненным циклом требует решения про supersession/cold (V3/V4), а оно не построено (merge/cold = test.todo).
5. Измеримость: "гибкость" без метрики это вкусовщина. Без критерия проект вернётся к анализу как избеганию коммита.

## Provocations

6. Видов зашито 5-7: сработал ли "3-й раз = обобщи"? Частично. Это повод вынести ОДИН generic-вид (фильтр по type/scope/tag + выбор полей + один рендер), потому что дубли реально есть в коде. Это оправдано. Но ВИД как хранимая сущность, которую агент предлагает, нет: достаточно параметров generic-вида в запросе (/view?type=..&group=..), без хранения.
7. Из тройки оправдан только ВИД (и то в минимальной форме). ТИП - пока соглашения; ПРАВИЛО - преждевременно, не трогать, пока нет 2-3 повторяющихся ручных действий, которые владелец реально делает руками 3-й раз.
8. Контрверс-вопрос: "владелец хочет гибкий инструмент" - или он боится зашить неверное решение (страх односторонних дверей)? Гибкость данных лечит страх переписывания, но переносит риск с кода на данные, где его хуже видно. Лучшее лекарство от страха - обратимость (миграции, версии, открытые поля), не язык.

## Переформулировка вопроса

Было: "как сделать память максимально гибкой". Лучше: "какие 2-3 повторяющихся действия владельца/агентов уже сегодня стоят ручного труда, и какое самое дешёвое, ОБРАТИМОЕ изменение сделает их автоматическими - без закрытия дверей для остальных?" Гибкость - свойство, которое проявляется на 3-м случае, не проектируется на 0-м. Вопрос-близнец: "что мы потеряем, если через месяц потребуется иной тип, а у нас только открытые поля?" Если ответ "ничего не потеряем, мигрируем скриптом" - гибкость уже есть.

## Минимальный шаг без платформы

- Открытые поля + соглашения: `attrs` (произвольный json) + теги + единый префикс типов; документ-соглашение на 1 страницу, не схема.
- Один generic-вид: параметры в запросе, рендер общий для MCP/Telegram/HTTP; старые 5-7 видов становятся пресетами-параметрами (код), без хранения.
- Живой прогон: владелец и агенты пишут реальные записи неделю (цель >=20), лид фиксирует "трения" (что хотелось, но пришлось костылить) в одном файле.
- Правила: НЕ строить. Только записывать повторения как зёрна.

Измеримый критерий "гибкость работает" (на конец недели):
(a) >=2 новых вида данных заведены БЕЗ изменения кода сервиса (только attrs+теги+параметры вида);
(b) 0 записей, где пришлось "ломать" соглашение;
(c) >=20 живых записей и список трений (>=3), из которого видно, какой примитив реально нужен;
(d) ни одно действие агента не исполняется из данных (инъекция невозможна по построению).
Если (a) не выполнен - только тогда обсуждаем ТИП как данные. Если (c) показывает повтор 3 раза - тогда правило, и с отдельным гейтом.

## Noted

- Фаза DESIGN: любая стройка по-прежнему требует "строй" владельца. Минимальный шаг выше - предложение, не разрешение.
- Не проверял реальный код видов и состав 3 записей (взято из постановки); пересчитать при свод-проходе.

## Что не нашёл проблем

- Идея "агент предлагает -> владелец утверждает" как статус proposed для ЗАПИСЕЙ-фактов: нормально, пока запись не исполняема.
- Привязка к ценностям как линзе: уместно, но V7 пока не enforce - не опираться.

Итог: ответил, с оговоркой: тройка преждевременна кроме generic-вида; правило-как-данные - отложено.
