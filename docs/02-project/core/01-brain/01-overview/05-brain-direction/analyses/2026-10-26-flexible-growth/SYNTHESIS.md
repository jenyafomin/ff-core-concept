## Вопрос владельца (2026-10-26)
«Решения хорошие, но могут быть зашиты под конкретное. Нужен максимально гибкий инструмент, готовый к повторяющимся шаблонам; полезный агентам, мне и программе. Идти от ценностей.»

## Факты (analyst)
- ТИП: форма уже данными (`definitions.ts planDefinition`), но входа нет — нет маршрута «определить тип»; 13 типов, все из кода. Статусы — enum в данных, переходы/категории — код; пресеты видят только `open/doing/blocked/done` → **новый тип с другими статусами невидим** для morning/open (скрытая связка).
- ВИД: 7 экземпляров (5 пресетов, /state, prompt-compose), данными — 1 (prompt-compose). Пресеты — закрытый union + switch.
- ПРАВИЛО: 0 экземпляров.
- «Агент предлагает → владелец утверждает» есть только для записей (`proposed`). Неизвестный тип → `raw` + friction `UNKNOWN_TYPE` = сигнал спроса, который сейчас никто не видит.

## Расхождение линз и как снято
abstract-thinker: «линза как данные — первой, случаев хватает». critic: «только один generic-вид с параметрами, в памяти не хранить; правила/типы с lifecycle — преждевременны, правило-как-данные = вечная инъекция». Проверка «при каком мире оба правы» → **третий ход**:
- Исполнитель вида — ОДИН и в КОДЕ (выборка → группировка → поля → сортировка → лимит; только чтение, тот же гейт видимости). Это требование critic.
- «Именованный вид» = сохранённые ПАРАМЕТРЫ к этому исполнителю, а не язык. Параметры — данные (сначала в коде как пресеты, потом записями). Это требование abstract-thinker. Инъекции нет: вид только читает и не шире читателя.
- Формат отделён: вид отдаёт структуру; MCP / Telegram / HTTP — адаптеры. /state становится Telegram-адаптером любого вида, а не зашитым экраном.

## Принцип (ответ на «гибко vs системно»)
**Гибкость — в данных. Безопасность — в коде. Обобщение — только из ≥2 живых случаев.**
| Слой | Что | Где |
|---|---|---|
| Пол (никогда не данные) | тождество, видимость, согласие, стирание, право утверждать, список действий, часы | код |
| Примитивы | один исполнитель вида; категории статусов (open/active/done/cold); открытые поля; адрес `source.ref`; рёбра | код, общие |
| Настройки | именованные виды (параметры), объявления типов (поля + статусы → категория), устав | данные, автор + кто утвердил (V3) |
| Адаптеры | MCP (агент), Telegram /state (владелец), HTTP (программы) | код, тонкие, один на канал |

Повторяющиеся шаблоны (BA, 10 сценариев) ложатся в примитивы: жизненный цикл статусов, время/срок, адрес вместо тела, «новое закрывает старое», связь+область. task/decision/note/question/idea = одни примитивы с разными статусами.

## Ценности
V1 — вид отдаёт нужную грань по цене (параметры полей/лимита). V2 — тип меняется, id живёт (объявление типа не трогает тождество). V3 — у каждой настройки автор и утвердивший; выход вида подписан видом+версией. V4 — категория `cold` общая для всех типов. V5 — параметры вида и объявление типа переносимы (контракт исполнителя версионирован). V6 — тип связи = тот же механизм типа. V7 — пол в коде, вид не шире читателя.

## Шаги (порядок, каждый — живая проверка, не платформа)
1. **Общий исполнитель вида**: `find` получает `group_by` (область/тип/статус/поле), `fields`, фильтры по открытым полям, сортировку. Пресеты переписываются как параметры к нему (поведение не меняется — тесты). /state рендерит любой вид.
2. **Категории статусов**: тип объявляет свои статусы → категория. Пресеты «открытое/утро» работают для ЛЮБОГО типа.
3. **Путь «агент предлагает тип → владелец утверждает»**: friction `UNKNOWN_TYPE` видна владельцу (в /state и в карте); маршрут объявления типа, статус `candidate` → `active` только владельцем. Первая проверка гибкости: типы `question` и `idea` заводятся ДАННЫМИ, без правки кода сервиса.
4. **Живая неделя на 2 сценариях**: личный туду (personal, по слову владельца) + вопросы/решения проекта (ff или Cardex). rentacar — позже (ПДн, V7 не форсится).
**Не делаем сейчас:** правила-как-данные (0 случаев; риск инъекции), язык запросов/DSL, фронтенд, хранение видов в памяти до 2-го пользовательского вида.

## Критерий «гибкость работает» (конец недели, от critic)
≥2 новых вида данных заведены без правки кода сервиса · ≥20 живых записей · ≥3 зафиксированных трения · ни одно действие агента не исполняется из данных.

## Вопросы, вскрывающие рамку
- Мы обобщаем память или ДОСТАВКУ («кому, что, когда, где»)? Если второе — следующий примитив = адаптер/канал, а не тип.
- Какой один вопрос владельца на завтра нынешние виды НЕ покрывают? (ответ = первый живой тест шага 1)

Итог: развилка владельцу — шаги 1–3 «строй» + выбор 2 сценариев живой недели.

## Поправки после повторной проверки critic (вердикт PATCH, 2026-10-26) — ПЕРЕКРЫВАЮТ шаги выше
- **Параметры вида — только плоские:** `group_by`, `fields`, фильтры по полям (равенство/наличие), `sort`, `limit`. Запрет: вложенность, выражения, композиция, действия. Иначе — платформа.
- **Шаги 1+2 сливаются** (≈3 дня): `group_by`+`fields`+`sort` + категории статусов. Переписывание всех пресетов и «/state как адаптер любого вида» — после того, как появится 2-й пользовательский вид. Регрессия — golden-снимки вывода пресетов ДО/ПОСЛЕ. Ответ исполнителя несёт версию контракта (`view_v`) — V5.
- **Шаг 3 (≈1–2 дня) — сначала закрыть дыру V3:** `u:`-объявление типа может только УЖЕСТОЧАТЬ `approval`/`write` (никогда не ослаблять до агентской записи `active`); активирует объявление только владелец. Сейчас `hasAuthorFlags` проверяет лишь флаги полей (`validate-act.ts:313,612`, `registry.ts:336`). Friction `UNKNOWN_TYPE` хранить с ИМЕНЕМ типа (сейчас sha256, `validate-act.ts:438`), счётчик трений — в карте/`/state`.
- **Критерий недели (исправлен):** ≥2 новых типа заведены ДАННЫМИ без правки кода сервиса · ≥10 записей, которые владелец открыл в /state или агент использовал в ответе (не просто записал) · счётчик трений виден и ≥3 трения разобраны · ни одно действие не исполняется из данных.
- **Условие входа в шаг 1:** назвать один реальный вопрос владельца, который нынешние виды не покрывают.
