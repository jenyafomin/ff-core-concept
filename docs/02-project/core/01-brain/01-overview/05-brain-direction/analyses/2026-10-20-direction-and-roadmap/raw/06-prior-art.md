## 1. Документация/знания поверх git для нескольких репозиториев

**Что делают другие**
- **Backstage TechDocs** — docs-like-code: markdown живёт РЯДОМ с кодом в каждом репо, CI собирает MkDocs-сайт, Backstage рендерит всё централизованно; связь «док ↔ компонент» через каталог (`catalog-info.yaml`). Для монорепо — `mkdocs-monorepo-plugin` (один сайт из многих папок); у плагина ограничения (конфликт с поиском, нельзя ссылаться на корень). [backstage.io/blog/2020/09/08/announcing-tech-docs](https://backstage.io/blog/2020/09/08/announcing-tech-docs) · [roadie.io monorepo guide](https://roadie.io/md/blog/backstage-monorepo-guide/)
- **git submodules / subtree** — известная боль для «равноправных» репо: рассинхрон коммитов родитель↔подмодуль; альтернативы — манифест (`repo` у Android), subtree, менеджеры пакетов. [codingkilledthecat: why not submodules](https://codingkilledthecat.wordpress.com/2012/04/28/why-your-company-shouldnt-use-git-submodules/) · [openembedded MultipleRepositoryMethods](https://www.openembedded.org/wiki/MultipleRepositoryMethods)
- **Logseq** — ушёл от «markdown-файлы = истина» к «БД (Datascript поверх SQLite) = истина» ради надёжного sync/коллаборации; двусторонний sync с md отложен, остался импорт/экспорт «в той мере, в какой форматы совместимы»; граф выбирает режим при создании, переключать нельзя. Пользователи жалуются: потеря доступности для внешних инструментов/LLM, риск порчи одного файла БД. [discuss.logseq.com: bi-directional?](https://discuss.logseq.com/t/is-there-still-a-bi-directional-approach-of-db-markdown-or-only-export-to-markdown-remains/26051) · [Why the database version](https://discuss.logseq.com/t/why-the-database-version-and-how-its-going/26744)
- **Dendron** (local-first md, иерархии, схемы, VS Code) — разработка остановлена, режим поддержки. [wiki.dendron.so](https://wiki.dendron.so/notes/egxM8X43CqrQLuhYQ6Wu8) · Причины публично не нашёл; **[из знаний, гипотеза]**: монетизация командной версии не сложилась, а строгая схема-иерархия требовала дисциплины, которую мало кто держал.
- **Obsidian + git** — **[из знаний]**: плагин obsidian-git автокоммитит по таймеру; конфликты всплывают при правке с двух устройств, `.obsidian/` (настройки) — частый источник конфликтов; файлы остаются истиной, индекс — внутренний кэш приложения.
- **Notion↔git sync** — **[из знаний]**: сторонние односторонние экспортёры (Notion→md в репо) живут; двусторонние ломаются на потере форматирования/ID блоков при обратном пути.

**Уроки для нас**
1. **Доки остаются у себя дома (в репо проекта), центр — каталог + индекс, а не копия.** TechDocs не тащит доки в один репо — он знает, ГДЕ они, и собирает вид. Для мозга: узел «документ проекта X» = адрес (repo+path+commit) + производные (summary, рёбра), а не тело-копия. Совпадает с нашим «адрес-не-копия» (INTAKE 10-11). Submodules/monorepo для объединения доков — не брать.
2. **Logseq — прямое предупреждение по развилке «файлы vs база = истина».** Они выбрали базу ради sync/коллаборации и потеряли открытость; двусторонний sync так и не сделали. Для нас: у документации истина — файлы в git (их правят люди, IDE, другие агенты); у мозга истина — журнал актов о них. Две разные истины для разных веществ, не одна общая.
3. **Строгая схема без немедленной пользы умирает (Dendron, гипотеза).** Первый сценарий должен давать ценность при нуле ручной разметки: индекс по существующим `docs/` проектов автоматически, типизация — потом.

## 2. Память агентов на Postgres / графовые слои

**Что делают другие**
- **Zep / Graphiti** — три подграфа: **эпизоды** (сырой вход, без потерь, якорь провенанса) → **семантические сущности/рёбра** (выведены из эпизодов) → **сообщества** (сводки кластеров). **Би-темпоральность**: время события (T) и время узнавания (T'); противоречие **инвалидирует** старое ребро (valid_to), не перезаписывает → запрос «что граф думал на дату». Цена: LLM-извлечение на каждую запись (заметные токены на разговор); чтение быстрое (гибрид BM25+вектор+обход, без LLM на чтении, p95 ~300 мс). [arXiv 2501.13956 Zep](https://arxiv.org/pdf/2501.13956.pdf) · [Thoughtworks Radar: Graphiti](https://www.thoughtworks.com/es-es/radar/platforms/graphiti) · [Graphiti agent memory review](https://codex.danielvaughan.com/2026/03/30/graphiti-agent-memory-store/)
- **mem0** — извлекает «значимые факты» из диалогов и делает ADD/UPDATE/DELETE/NOOP; три стора (вектор: pgvector/Qdrant; граф: Neo4j; KV); скоупы user/session/agent. Выигрыш в латентности/токенах против полного контекста. **[из знаний]** слабое место — UPDATE/DELETE по решению LLM = потеря истории и тихие перезаписи. [mem0 graph memory docs](https://docs.mem0.ai/platform/features/graph-memory) · [mem0 architecture overview](https://agentmarketcap.ai/blog/2026/04/14/mem0-agent-memory-architecture-production-latency-token-savings-2026)
- **Letta (MemGPT)** — ядро-блоки в контексте (label + description + value с лимитом символов) + архивная память (поиск по эмбеддингам) за инструментами; хранение в Postgres. **Agent File (.af)** — открытый формат сериализации агента целиком (блоки, промпты, тулы, история) для переноса между серверами. [docs.letta.com memory](https://docs.letta.com/guides/agents/memory) · [letta.com/blog/agent-file](https://letta.com/blog/agent-file)
- **Cognee** — пайплайн Extract→Cognify→Load, онтология, API из 4 глаголов (remember/recall/forget/improve); недавно — «всё в одном Postgres»: граф + pgvector + сессии + метаданные без Neo4j. [cognee.ai/blog/deep-dives/just-postgres](https://www.cognee.ai/blog/deep-dives/just-postgres)
- **Basic Memory (MCP)** — markdown-файлы = истина, SQLite-индекс (сущности/наблюдения/связи) — производный, пересобирается командой `sync`; агент пишет через MCP → сервис создаёт файл. Три идентификатора: внутренний int, внешний UUID, permalink — чтобы пересборка индекса не ломала ссылки. Postgres — опция для облака. [Basic Memory: how it works](https://mintlify.wiki/basicmachines-co/basic-memory/concepts/how-it-works) · [docs.basicmemory.com](https://docs.basicmemory.com/technical/technical-information)
- **Event sourcing на PG (общий опыт)** — ловушки: эволюция схемы событий (нужны upcaster'ы и версии проекций), ручные SQL-правки проекций ломают детерминизм пересборки, полная пересборка может душить БД часами, гонки inline-проекций под нагрузкой; лечится: проекции проектировать под пересборку с нуля, causation/idempotency-ключи. [event-driven.io: rebuilding read models](https://event-driven.io/en/rebuilding_read_models_skipping_events/) · [kurrent: consistency counterexamples](https://next.kurrent.io/blog/counterexamples-regarding-consistency-in-event-sourced-solutions-part-2/) · [Event Sourcing Fails: 5 lessons](https://kitemetric.com/blogs/event-sourcing-fails-5-real-world-lessons)

**Уроки для нас**
1. **Наш выбор «журнал актов = истина» совпадает с самым сильным образцом (Graphiti: эпизоды без потерь + инвалидация, не перезапись).** mem0-стиль UPDATE/DELETE — антиобразец для V2/V3. Стоит взять у Graphiti явно **би-темпоральность** (когда было верно vs когда узнали) — проверить, есть ли оба времени в нашем акте (гипотеза: есть `ts` записи, но нет `valid_from/valid_to` факта — проверить в `packages/brain/src/domain`).
2. **«Всё в одном Postgres» (Cognee: граф + pgvector + метаданные) — признанный путь, и он поддерживает наше «PG = носитель журнала + проекции».** Отдельная графовая БД (Neo4j) не нужна на нашем масштабе. Но pgvector/эмбеддинги — отдельная, НЕ срочная дверь: первый сценарий (доки) хорошо обслуживается полнотекстом + рёбрами.
3. **Три ID у Basic Memory = наш V2 (тождество) в готовом виде:** `canonical_id` (стабильный) ≠ путь файла ≠ внутренний ключ носителя. И урок по проекциям: никаких ручных правок проекции — только через акт, иначе пересборка соврёт. **Letta .af** — образец для V5: портируемость = «весь агент/память в одном открытом файле экспорта» — это и есть наш гейт «экспорт→импорт побайтно».
4. **Цена LLM-извлечения на запись — главный счёт у графовых памятей.** Для доков: извлекать рёбра/резюме лениво (по чтению/по изменению файла), не на каждую мелочь.

## 3. Синхронизация файлы↔база агентами

**Что делают другие**
- Общий опыт интеграций: «два односторонних синка ≠ двусторонний» — нет единого арбитра, петли обновлений, конфликты при одновременной правке, ошибки множатся; двусторонний файловый sync — «огромная банка червей» с худшим исходом — потерей данных. [stacksync: two one-way syncs](https://stacksync.com/blog/why-two-one-way-syncs-arent-true-bi-directional-synchronization-the-hidden-integration-challenge)
- **Logseq**: сознательно отказался (пока) от двустороннего DB↔md — только импорт/экспорт (см. §1).
- **Basic Memory**: «двусторонний», но с жёстким арбитром: **файл всегда побеждает**, БД — пересобираемый индекс; изменения ловятся по SHA-256 + mtime + size; запись агента = запись файла.
- **CRDT** (Kleppmann, Automerge): решают параллельную правку без арбитра, но «CRDT легко реализовать плохо», есть аномалии; уместны для совместного редактирования текста в реальном времени, а не для «агент синкает папки». [CRDTs: the hard parts](https://martin.kleppmann.com/2020/07/06/crdt-hard-parts-hydra.html)
- **[из знаний]** last-writer-wins по времени ломается на рассинхроне часов и тихо теряет правку проигравшего.

**Уроки для нас**
1. **Не строить симметричный двусторонний sync.** Строить «одну истину на вещество + однонаправленные производные»: файл дока → (watcher/хук по коммиту) → акты в журнал мозга → проекции. Обратное направление (мозг → файл) — только как **предложение** (PR/патч/черновик), которое применяет человек/агент через git, а не тихая запись. Это совпадает с наказом владельца «мозг ДОПОЛНЯЕТ git».
2. **Арбитр и обнаружение изменений — как у Basic Memory:** хэш содержимого + путь + коммит; акт «документ X изменился (hash a→b)» ссылается на коммит → провенанс V3 бесплатно из git.
3. **CRDT и LWW — не нужны на первой итерации** (один писатель на файл — git; один писатель в журнал — сервис). Возвращаться, только если появится живое одновременное редактирование одной единицы.

## 4. NestJS для такого сервиса

**Что говорят другие:** NestJS — тяжёлый, опинионированный (DI, модули), окупается при 3+ разработчиках, 20+ эндпоинтах, 50+ файлах; «время до первого эндпоинта» — в пользу Fastify/Hono, «время до 20 единообразных эндпоинтов» — в пользу Nest. Для маленьких сервисов — Fastify/Hono. [encore.dev: NestJS vs Fastify vs Hono](https://encore.dev/articles/nestjs-vs-fastify-vs-hono) · [pkgpulse 2026](https://www.pkgpulse.com/guides/nestjs-vs-fastify-2026)

**Уроки для нас**
1. **Наш профиль (1 разработчик + агенты, транспорт = MCP/stdio, небольшое API) — не зона NestJS.** Подтверждает свод 10-14: Nest по триггеру (второй транспорт HTTP с десятками эндпоинтов / второй разработчик). Basic Memory, Graphiti-MCP, Letta обходятся без тяжёлого фреймворка на уровне ядра.
2. **Ядро памяти фреймворк-независимо, хост — тонкий адаптер.** Если Nest когда-нибудь — только как хост вокруг `@ff/brain`, без «пакет = Nest-модуль» (риск V5/plug-in, см. свод 10-14 §2). Если нужен HTTP раньше — Fastify/Hono как минимальный хост.

## Сводная карта: что берём / что отвергаем
| Берём (образец) | Откуда | Ценность |
|---|---|---|
| Эпизоды без потерь + инвалидация вместо перезаписи, би-темпоральность | Graphiti | V2, V3, V4 |
| Файл = истина документа, индекс пересобираем; хэш-детект; 3 ID | Basic Memory | V2, V5 |
| Один открытый файл экспорта всей памяти | Letta .af | V5 |
| «Всё в одном Postgres» (журнал + проекции + позже pgvector) | Cognee | V5 (один носитель) |
| Доки у себя в репо, центр = каталог + вид | Backstage TechDocs | V1, V6 |
| Проекции — только из актов, проектировать под пересборку | ES-практика | V3 |

| Отвергаем | Почему |
|---|---|
| Симметричный двусторонний sync файлы↔база | петли, конфликты, потеря данных (stacksync, Logseq отказался) |
| UPDATE/DELETE памяти по решению LLM (mem0-стиль) | тихая потеря истории, против V2/V3 |
| submodules/monorepo для сведения доков | рассинхрон, не для «равноправных» репо |
| Отдельная графовая БД (Neo4j) | не наш масштаб; PG закрывает |
| NestJS сейчас | профиль 1 dev + MCP |

## Вопросы, которые внешний опыт вскрывает (на вход синтезу)
- Есть ли в нашем акте второе время — «когда факт верен» (valid_from/to) отдельно от «когда записан»? (Graphiti) — проверить код.
- Для сценария «документация» что считаем эпизодом: коммит, файл-версию (hash) или правку агента? От этого зависит провенанс и объём журнала.
- Мозг → файл: только предложение (PR/черновик) или право писать? Внешний опыт однозначно за «только предложение».

Ответил (частично, внешней линзой): внешний опыт подтверждает направление свода 10-14 (журнал = истина, PG = носитель/проекция, Nest по триггеру) и даёт конкретную форму первому сценарию — «доки остаются в git, мозг = каталог+журнал актов о них, sync однонаправленный, обратное — предложением»; порядок roadmap и рефакторинг не решает — это задача других линз.
