## 0. Главная находка (до модели)
**Каскад «как CLAUDE.md» в мозге уже построен — под другим именем.** `sys:prompt-layer` + `sys:target` +
`sys:applies-to` + линза-данные `lens:prompt-compose@1` (`packages/brain/src/domain/sys-types.ts:52-118`,
интерпретатор `packages/brain/src/read/lens.ts:96-194`, SPEC `docs/spec/SPEC-brain-r1-prompt-layers.md`). Это
ровно «слои текста, применимые к контексту, собранные по порядку с манифестом и хэшем». Сейчас он настроен на
Telegram-контекст (`order: bot, project, agent, chat, topic, user`) и открыт только мандату шлюза
(`service/runtime.ts:259-267`).
Значит, вопрос не «как построить систему правил», а **«как обобщить уже существующий каскад промптов до
каскада правил по организациям/проектам, не плодя второй механизм»**.

Вторая находка (ловушка): **наследование видимости в мозге идёт ВВЕРХ, а наследование правил должно идти
ВНИЗ.** Шлюз чтения: запись видна, если `замыкание member-of её областей` пересекает области читателя
(`read/access.ts:235`, `domain/validate-act.ts:142-160`, ≤2 хопа). Компания видит записи своих проектов; проект
НЕ видит записи компании. Если повесить правила на области и дать проекту родительскую область — он увидит
**всё** соседей (утечка, V7). Правила нельзя возить на оси видимости.

## 1. Простая модель (один экран)

**Четыре понятия, все — данные в одном журнале:**

| Понятие | Что это | Аналог в Claude Code сегодня | Есть в коде? |
|---|---|---|---|
| **Область (scope)** | «где»: личное / организация / проект; дерево `member-of` | папка проекта, `~/.claude` vs `./.claude` | да (`genesis.ts:83-91,174-178`) |
| **Слой (layer)** | «какое вещество»: семейство типов с одним поведением хранения | `rules/` vs `docs/` vs `_log/` vs задачи | частично (типы есть, «семейства» — нет) |
| **Правило (rule-layer)** | текст-политика, применимый к контексту; запись с целями `applies-to` и порядком | один файл `rules/*.md` с шапкой Scope/Status/Owner | да как `sys:prompt-layer` |
| **Линза (lens)** | правило ЧТЕНИЯ как данные: что собрать, в каком порядке, с каким бюджетом | механизм загрузки CLAUDE.md харнессом | да, одна форма `compose` |

**Корень = не новая сущность, а одна линза с бюджетом** (`lens:root@1`), которую агент вызывает первой.
Она возвращает ≤1 экран:
1. **Кто ты** — твой принципал и области (из мандата, не из заявлений).
2. **Действующие правила** — каскад `универсальное → организация → проект → (агент/тема)` для твоего контекста,
   собранный `compose` с манифестом `[id, rev, source_hash]` (видно, ОТКУДА каждая строка).
3. **Карта слоёв** — сколько и чего есть в твоих областях по семействам (правила · решения · задачи · документы-
   адреса · трейсы), со ссылками-фильтрами.
4. **Доступные линзы** — список (`morning`, `open`, «почему это решение», «лента темы»…) — дальше агент тянет их сам.

**Проход агента:** `root` (одно чтение, ≤4000 симв.) → выбирает слой/линзу из карты → `find` с фильтром
(область × семейство × статус) → `read` конкретной записи → для документа — открывает файл по `source.ref`.
Это тот же V1 «нужная грань по нужной цене»: корень дёшев, тела грузятся только по требованию.

**Правило как данные — разделить два вещества, которые в `~/.claude/rules/` слиты:**
- **Текст-совет** (что агенту знать/делать) → слой в памяти, собирается линзой в контекст. Совещательный.
- **Принуждение** (что запрещено независимо от агента) → «пол» в коде/хуках/`policy:constitution`
  (`domain/constitution.ts`, `no_read_ids`). В память как текст НЕ переезжает — переезжает только описание со
  ссылкой на исполнителя. Иначе «правило в памяти» станет обещанием без зубов (V3).

**Наследование — ось ЛИНЗЫ, не ось видимости.** Слой правила цепляется `applies-to` к цели вида `scope`
(новый вид цели — данные, без кода: `sys:target.kind` открытый словарь, `sys-types.ts:68-70`). Линза при сборке
берёт область контекста и идёт по `member-of` **вверх**, собирая слои предков; порядок = глубина (предок раньше,
ребёнок позже, `merge: replace` у ребёнка перекрывает). Записи правил живут в отдельной области «свод правил»,
читаемой всеми (правила не секрет, `pii: none`) — видимость данных проектов не трогается.

**Кастомная карта** = линза-данные с другой `spec` (другой порядок, другой фильтр, другой бюджет). Организация с
«другими правилами» = её слои + при желании своя версия линзы `root@N`. Новая карта — новый узел, не код.

## 2. Как ложится на существующий код

| Нужно | Есть | Нет / путь |
|---|---|---|
| Области + иерархия | `scope` (kind `personal|company|project`), `member-of` M:N, замыкание ≤2 (`genesis.ts:174-178,214`; `validate-act.ts:139-160`) | вида `org`/`domain` нет — `company` ≈ организация; «домен» (класс продуктов) — либо новый kind (аддитивно, enum), либо просто область-родитель. 3 уровня (универсал→организация→проект) = ровно 2 хопа — впритык |
| Каскад текстов | `sys:prompt-layer` (body verbatim ≤32 КБ, priority, merge), `sys:target`, `sys:applies-to`, `lens:prompt-compose@1` (`sys-types.ts:52-118`, `lens.ts`) | цели вида `scope` и обход `member-of` в `compose` нет; `order` фиксирован в spec@1 (новый порядок = `prompt-compose@2` / `rules-compose@1` — данные, `lens.ts:150-162` уже грузит по `<id>@<v>`) |
| Доступ к линзе | `/v1/lens` (`http.ts:141`) | только `sys:gateway` (`runtime.ts:263`); в MCP 4 инструмента `record/find/read/link` (`brain-mcp/src/server.ts:96-131`) — **инструмента `lens`/`root` нет** |
| Дайджесты-«линзы» | presets `morning|evening|open|scope` (`read/presets.ts:120-187`) | они в КОДЕ, не данные; preset `root/orient` нет. Это вторая, кодовая форма линзы — расхождение с «линза = данные» |
| Фильтры find | `scope, type, status, text, due_before, edge` (`contract.ts:285-298`) | фильтра по семейству/слою нет (только точный `type`) |
| Слои типов (семейства) | ядро `task/decision/note/person/day/friction/scope/raw` (`genesis.ts:148-203`); резерв `persistence_class: event|state|config|ephemeral` и `placement` (ADR-0017 D2) | поле не реализовано (сознательно — нет потребителя); типа `rule`, `doc`(конверт), `trace` нет; `sys:prompt-layer` — это и есть «rule», но имя/поле `slot primary|extra` заточены под промпт шлюза |
| Принуждение | `policy:constitution` (`constitution.ts`), PII-шлюз, `approval: owner` у слоя (агент только предлагает, R-04) | — (это хорошо: пол уже отделён от текста) |

**Слои типов — ответ на «какая ветка какой памяти».** Не вводить сущность «слой». Слой = **пара фасетов на
type-def**, оба уже названы в доках:
- **хозяин тела** (из `00-SYNTHESIS` §3): `file-mastered` · `brain-mastered` · `derived`;
- **класс хранения** (ADR-0017 D2): `event` · `state` · `config` · `ephemeral`.

| Ветка владельца | Тип | Хозяин тела | Класс | Комментарий |
|---|---|---|---|---|
| Правила | `sys:prompt-layer` → обобщить | file-mastered сейчас | `config` | версии = ревизии записи |
| Решения | `decision` (ядро) | brain (из чата) или file (ADR) | `state` | ADR = конверт + `supersedes` |
| Логи/трейсы `docs/_log` | новый `trace`/`session` | **brain-mastered** (владелец п.2: «могут переехать сразу») | `event` (append-only) | крупное сырьё агентов — АДРЕСОМ, не телом (идея-конструктор, «защита от раздувания») |
| Задачи | `task` (ядро) | brain | `state` | presets уже работают |
| Документы-адреса | конверт (`note` с `source{ref,hash}` в Э1; `doc` — ADR-0019) | file | `config` | тело не пишется |

Акты наслаиваются поверх единообразно (журнал один, id-простор один — ADR-0017 D2 «едины всегда»). Фасеты
становятся полями type-def **в момент первого потребителя** — им и станет линза `root` (ей нужно группировать по
семействам). До этого семейство = таблица соответствия тип→ветка в самой линзе (данные).

## 3. Правила в памяти vs `~/.claude/rules` — варианты

Факт: Claude Code грузит `CLAUDE.md` и `.claude/rules/*.md` **файлами, харнессом, до первого хода**. Никакой
MCP этого не заменит: агент без памяти (мозг лёг, другой компьютер, новая сессия) должен оставаться безопасным.

| Вариант | Суть | Цена | Вес | Риск |
|---|---|---|---|---|
| **A. Замена** — правила живут только в мозге, агент тянет через MCP | файлы удаляются | средне | мало сейчас | **ломает работающее**: мозг лёг → агент без правил безопасности; харнесс не грузит MCP до хода. Нет |
| **B. Генерация** — мозг хозяин, `CLAUDE.md`/rules рождаются экспортом | `derived`-файлы | средне | средне | обратный хозяин тела — противоречит §3 (rule = file-mastered); ручная правка файла затирается; двойная правда до shadow-доказательства |
| **C. Индекс** — файл истина, мозг держит конверт: `applies-to` область, статус, рёбра, `source_hash`; агенты вне харнесса читают каскад через линзу | файл → мозг синком (как R1-импортёр с round-trip) | мало | много: кросс-проект, «откуда это правило», stale-детектор, одна точка для шлюза | тело для `compose` нужно — копия с `source_hash` (как R1) или чтение по ref |
| **D. Путь R1 целиком** — C сейчас → shadow N дней «0 diff» → потом для части правил хозяином становится мозг (R1.1-паттерн LKG: файл побеждает, если хэш разошёлся) | лестница | мало→средне | много | — это и есть C с честным выходом в B |

**Рекомендация: C сейчас, D как лестница; A — никогда для «пола».** Конкретно:
- Харнесс продолжает читать файлы (ничего не ломается).
- В `CLAUDE.md` одна строка-указатель: «карта памяти: вызови `root`» (как `docs/STATE.md` сегодня).
- Мозг — **единственное место, где правила видны КАК СИСТЕМА**: какие действуют на проект X, откуда унаследованы,
  какие устарели (hash), какие противоречат (`supersedes`/`tension-with`). Этого файлы не умеют — это и есть ценность.
- Агенты шлюза/SDK (не Claude Code) получают каскад из мозга — там мозг становится хозяином раньше, по R1.1.
- **Флаг (владелец п.3):** правила, которые называют шлюз «Движ», — первые кандидаты на stale-проверку; синк
  индексом их найдёт (это бесплатный первый полезный вывод «системы правил»).

**Напряжение (не разрешаю, передаю своду):** §3 свода говорит «file-mastered → тело в мозге НЕ пишется», а R1
пишет тело слоя дословно (`body verbatim`). Для правил нужен `compose` текста → либо копия тела с `source_hash`
(R1; stale ловится хэшем), либо `body_ref` (R1.x, ещё нет). Это одна развилка для ADR-0019, не две.

## 4. Минимальный первый срез (не платформа)

**Этап 1 (до 10-27) — 0 кода** (заморожено §4: тип `doc`, рефакторинг и т. д.). Только данные:
- В `stage1-scopes.sh` дописать третью область `universal` (kind `company`, временно) и сделать `ff`,
  `agents-manager` её детьми (`member-of`). Это проверяет дерево областей на живых данных до первой записи
  правил. ⚠️ Читателям `universal` НЕ давать (утечка вверх, §0).
- Записать карту слоёв **файлом** (таблица §2 «ветка → тип → хозяин → класс») в дом-тему — бумажный корень,
  чтобы свежий агент на Э2 проверил: понятна ли карта без мозга.

**Этап 2 (до 11-03) — один вертикальный срез «правило читается из другого проекта»:**
1. **Второй документ Э2 уже правило** — блок «шлюз» (`~/.claude/rules/gateway-telegram-egress.md` + FF
   `CLAUDE.md`). Записать его конвертом с `applies-to → scope:universal` (не `in-scope` проекта).
2. **Один код-шов:** инструмент MCP `lens` (read-only) для cli-читателей, или preset `root` — выбрать один.
   Рекомендую **preset `root`** (дешевле: паттерн `presets.ts`, без новой поверхности мандата), содержимое: кто
   ты · области · правила с `applies-to` на твою цепочку областей · счётчики по типам. Обобщение до
   `lens:root@1`-как-данные — когда появится вторая карта (компаунд-триггер 4: ≥2 реальных случая).
3. **Тест (критерий надёжности, п.5):** агент в `agents-manager` первым ходом вызывает `root` и называет
   действующее на него правило + его источник (путь) + «оно устарело?» по hash. Да → система правил живая.

**НЕ делать на Э1–Э2:** тип `rule`, фасеты в type-def, обход `member-of` в `compose`, организации с ролями,
кастомные карты, генерацию `CLAUDE.md`, перенос `docs/_log` (п.2 владельца — «сразу», но это Э2+ после
первой живой записи; кандидат — один хендофф как `trace`-запись, чтобы проверить класс `event`).

## 5. Вопрос, вскрывающий неверную рамку

> **«Правило в памяти» — это ТЕКСТ, который агент читает, или ПОВЕДЕНИЕ, которое кто-то проверяет?**

Если текст — то «центральная точка как CLAUDE.md» это просто лучший CLAUDE.md (каскад + источник + stale), и
он почти построен (R1). Если поведение (владелец п.5: «агент ведёт себя правильно, владелец получает фидбэк») —
то настоящая система правил это **петля: правило → наблюдаемое действие агента в журнале → сверка → `friction`
→ правка правила**, а корень/каскад — лишь её вход. Тогда первым срезом должен быть не `root`, а
**одно правило + одна проверка его соблюдения по журналу** (например, «агент не пишет в ref Telegram-id» уже
проверяется `pii-scope.ts:42` — это правило-с-зубами, у которого нет текстового двойника в памяти).
Ставлю на второе: владелец просит «система развивается сама через правила», а текст сам не развивается —
развивается только то, что измеряет своё нарушение.

Подвопрос для свода: **а нужна ли «организация» сейчас, если реальный второй организации нет?** Наследование
`универсал → проект` (1 хоп) покрывает 100% сегодняшних правил владельца; «домен/организация» — уровень N+1
(гардрейл конструктора: только после живого N).

---

**Ответил на вопрос-цель:** да — (а) корень = линза/preset с бюджетом, (б) правила = существующий каскад
`prompt-layer`, обобщённый целями `scope` и обходом по линзе (не по видимости), (в) слой = два фасета type-def
(хозяин тела × класс хранения), включаются первым потребителем. Рамка частично неверна: «система правил» без
петли проверки соблюдения — это документация, не контроль.

Итог: задача в плане — Э1: область `universal` данными + бумажная карта слоёв; Э2: правило-шлюз конвертом
`applies-to universal` + preset `root` + тест «агент AM называет своё правило и его источник»; развилка
«правило = текст или поведение» и напряжение «тело file-mastered в мозге» — владельцу/ADR-0019.
