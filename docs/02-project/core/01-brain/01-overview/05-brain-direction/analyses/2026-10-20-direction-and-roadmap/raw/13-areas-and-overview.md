## 1. Как подключить проект (шаги)

**Что есть:** область = узел типа `scope` (kind `personal|company|project`, `domain/genesis.ts:87,173-178`). Читатель по cwd — запись в `readers.json` `cli[<абс. путь>]` (`read/access.ts:91-108`, сравнение по realpath `:128-135`). Без записи — `DEFAULT_DENY` (`:93`).

| # | Шаг | Кто | Навсегда? |
|---|---|---|---|
| 1 | Выбрать **слаг** (kebab-case, без `:`, `to-act.ts:257`) = ключ реестра: `cardex`, `crm-server`, `forms-sidebar`, `profit-swimming`, `music-video`, `claude-setup` | владелец | **Слаг и kind навсегда** (скрипт останавливается при расхождении kind, `stage1-scopes.sh` строка ~69) |
| 2 | Добавить сид в `service.json.scopes`: `{slug,name,kind:'project',pii:'none'}` | владелец (скрипт-образец `launch-kit/stage1-scopes.sh`, расширить `WANT`) | да (области не удаляются) |
| 3 | Рестарт `ff-brain` — области сидятся только при старте (`service/runtime.ts:141`, `domain/schemas.ts:71`) | владелец (pm2) | нет |
| 4 | `readers.json` → `cli[<путь проекта>]`: `{principal:"cli:<путь>", scopes:[слаг], default_scope:слаг, write:true|false, personal:false}`. Перечитывается без рестарта (`stage1-scopes.sh` шапка) | владелец | нет, правится |
| 5 | В проекте нужен MCP `ff-brain` (4 инструмента `record/find/read/link`, `brain-mcp/src/server.ts:96-131`) и 3 строки в его `CLAUDE.md`: «перед ответом `find`; пиши с `scopes`» | владелец/агент проекта | нет |
| 6 | Проверка: `find` из папки проекта возвращает пусто без ошибки; чужой слаг → `SCOPE_DENIED` | агент | — |

Для шлюза (топики) вместо `cli[...]` — `chats["chat:thread"]`, та же форма (`access.ts:60-90`).

**Агент сам области НЕ заводит:** `record` с типом `scope` превращается в `raw` (`domain/validate-act.ts:415-417`), а `scopes` в записи обязаны ⊆ области читателя (`:536-538`). Новая область = только владелец.

### Ловушка 1 (проверено чтением, не запуском): родителя существующей области задним числом не повесить
`writeGenesis` пропускает сид, если узел уже есть (`domain/schemas.ts:73-74`: `if (store.readNode(ref)) continue`). Значит `member_of` в `service.json` для **уже созданных** `ff` и `agents-manager` будет молча проигнорирован. Инструмент `link` не поможет: `member-of` берётся с узла-области, а `link` проверяет `from.scopes ∩ reader` (`validate-act.ts:696-700`) — у узла-области своих `in-scope` нет → ожидаемо `SCOPE_DENIED` (требует теста). **Следствие для плана `10-root-rules-layers.md` §4 («сделать ff, agents-manager детьми universal»):** этот шаг не выполним без кода (новый ход «member-of для существующей области» — маленький, но это код + тест). Дешёвая альтернатива — см. §2.3.

**Решить ДО подключения новых проектов:** нужна ли им родительская область (компания/домен). Если да — выставить `member_of` сразу в первом сиде нового слага (для новых слагов работает: `to-act.ts:264-270`).

## 2. Пересечение областей

### 2.1 Как работает сейчас
- Запись имеет **множество** областей (ребро `in-scope`, M:N, ≤10 — `LIMITS.recordScopesMax`, `validate-act.ts:533`).
- Читает запись тот, у кого **замыкание областей записи** (сами + родители `member-of`, ≤2 хопа: `validate-act.ts:140,143-158`, `access.ts:207-223`) пересекается со своими областями — `access.ts:235`. Плюс PEP по `readable_by`/`personal` (`:234`).
- Пишет только в области, которые **все** есть у читателя (`validate-act.ts:536-538`). Нет `scopes` → `default_scope` (`:528-531`).
- Одна запись в двух проектах = один `id`, видна из обоих и из их общего родителя (ADR-0016 D4, строка 46; AC-08).
- `find scope=X` берёт и детей X: фильтр идёт по замыканию записи (`read/find.ts:107`); родитель-фильтр разрешён, если родитель выше области читателя (`:93-100`) — но результат всё равно режется по записям.

### 2.2 Ловушка видимости ВВЕРХ (`access.ts:235`)
Замыкание идёт от записи к **родителям**. Поэтому:
- Читатель с областью-родителем (`universal`/компания) видит записи **всех** детей. Дать проекту родителя «чтобы видеть общее» = дать ему всех соседей (утечка, V7).
- Запись, помеченная ТОЛЬКО родителем, ребёнок НЕ видит (его замыкание — он сам + его родители, не наоборот).
- То есть «общая запись для детей» через родителя не работает: она видна только держателям родителя.

### 2.3 Рекомендация: запись в нескольких областях, а не родитель-область
| Потребность | Решение | Почему |
|---|---|---|
| Запись нужна проектам A и B | `scopes:[A,B]` при записи (писатель должен держать оба слага) | работает уже сегодня, без кода; `id` один; видимость явная и читается из самой записи (V1, V6) |
| Владелец хочет единый обзор всего | читатель-«агрегатор» (cwd `FF`, personal) держит **все** слаги | не нужен родитель; сам агрегатор и есть «верх» |
| Правила/общее знание для всех проектов | отдельная область-«свод» (`universal` как **обычная** область), проекты получают её в `scopes` **читателя** (read-only, `write:false` нельзя на уровне области — см. риск) | без `member-of`; видимость данных проектов друг другу не меняется |
| Иерархия «компания → проекты» нужна только как рубрика | `member-of` при заводе НОВОГО слага | видеть вверх = для владельца/агрегатора, не для проектных читателей |

**Родитель-область (`member-of`) оставить для ситуации, где родителя держит только владелец/агрегатор**: тогда «вверх» = его честный обзор. Проектным читателям родителя не давать.

**Риск (M):** `write` — флаг на читателе целиком (`access.ts:82,102`), не на область. Проект, которому дали `universal` читать, получит и право писать в неё, если `write:true`. Для read-only общего свода нужен либо отдельный читатель с `write:false`, либо код (per-scope права) — отложено, нет потребителя.

### 2.4 Поправка к `10-root-rules-layers.md` §4
Там: «сделать `ff`, `agents-manager` детьми `universal`; читателям `universal` не давать». Две проблемы: (а) не выполнимо без кода (Ловушка 1, §1); (б) и не нужно — ради правил достаточно §2.3 строки 3 (область-свод в `scopes` читателей), родитель не требуется.

## 3. Виды записей проектов → типы и статусы мозга

### 3.1 Что есть (ядро, `domain/genesis.ts:148-196`)
| Тип | Статусы (поле `status`) | Заметка |
|---|---|---|
| `task` | `open · doing · blocked · done · dropped` (+ `due`, `priority p0-p3`, `assignee`, `why`) | единственный, с которым работают presets |
| `decision` | `proposed · accepted · superseded` | ADR-подобное |
| `note` | нет (`text`) | универсальная заметка |
| `person`, `day`, `friction` | — / — / `code,count,status:text` | `person` owner-only (PII) |
| `raw` | — (`declared_type`) | приёмник «неизвестного типа» |

Системный статус записи отдельно: `active · proposed · retracted · superseded` (`contract.ts:213`); ретрагированные всегда скрыты (`access.ts:268`). Холодные (`temperature: cold`) скрыты из presets, но `find` их находит (`presets.ts:6,126`).

### 3.2 Чего нет (желаемые виды владельца)
| Вид | Что случится при `record type:"question"` | Эффект |
|---|---|---|
| **вопрос, идея, направление, цель, описание проекта** | типа нет → сохраняется как **`raw`** + `declared_type:"question"`, предупреждение `UNKNOWN_TYPE_AS_RAW`, фрикция (`validate-act.ts:420-430`) | **не теряется, но «схлопывается»**: `stats.by_type` покажет `raw` (`service/stats.ts:25`, берёт `rec.type`); `find type:"question"` **ничего не вернёт** (сравнивает с `rec.type='raw'`, `find.ts:105,108`) |
| «открыт/закрыт» не у `task` | у `decision` нет `open`; у `raw`/`note` нет поля `status` | presets `open/morning/evening` считают открытым только `fields.status ∈ {open,doing,blocked}` (`presets.ts:12,33`) — запись с таким полем в любом типе подхватится (по значению поля, не по имени типа — AC-14), но без схемы поле не проверяется |

Временная обходная тропа (0 кода): писать `raw` с `declared_type` и искать `find text:"question"` (`textMatches` смотрит строковые поля, `find.ts:46-53`) — шумно, не рекомендую как норму.

### 3.3 Как добавить вид правильно
Новый тип = type-def. Агент через `record` его создать **не может** (`type-def` → `raw`, `validate-act.ts:415-417`); определения принимаются только от допустимого писателя, иначе `DEF_REJECTED` при реплее (`runtime.ts:183-185`, ADR-0017 D1). Путь:
1. **Тропа** (ADR-0016 D11 / ADR-0017 D1): тип `u:<name>` со `status: candidate` — повышение в пакет потом, `id` записей не меняются.
2. Единая «семья проектных видов» — **один** набор для ВСЕХ проектов, не свой набор на проект (иначе обзор не сводится): `question` (статусы `open · answered · reframed · dropped` — как в `altitude-question-loop`), `idea` (`seed · candidate · direction · rejected`), `direction`, `goal`. `task`/`decision` — как есть.
3. Чек-лист предложения типа — скилл `ff-brain-build`; код — builder по SPEC. ⚠ Статус-значения `open` у `question` автоматически попадут в presets `open/morning` (по значению поля) — это плюс (общий список открытого), но надо решить сознательно, чтобы «открытый вопрос» не забил «открытые задачи» (AC-14 даёт фильтр `type`).

Рекомендация: **1 новый узкий тип `question` первым** (наша петля вопросов уже живёт на этих статусах; ≥2 реальных случая — компаунд-триггер 4 выполнен), `idea/direction` — после первого живого прогона.

## 4. Чтение «через линзы»: что есть и чего не хватает

### 4.1 Presets (в КОДЕ, `read/presets.ts:125-137`, `contract.ts:221-222`)
| Preset | Что отдаёт | Потолок |
|---|---|---|
| `morning` | ≤2 «несущих» открытых (pin → p0 → due) + число просроченных (`presets.ts:140-150`) | ≤12 строк, ≤4000 симв. (`contract.ts:137-138`, `capDigest :94`) |
| `evening` | закрыто сегодня · изменено сегодня · открыто без движения >7 дн (`:153-169`) | то же |
| `open` | все открытые по порядку (`:171-178`) | то же + «ещё N» |
| `scope` | все записи области, свежие первыми (`:180-187`) | то же |

Все — списки **записей**, не сводки. Ни один не отвечает «сколько чего где».

### 4.2 Линзы-данные
`lens:prompt-compose@1` (`read/lens.ts`) — только сборка промпта, `/v1/lens` открыт ТОЛЬКО мандату шлюза (`service/runtime.ts:262-266`), в MCP инструмента `lens` нет (`brain-mcp/src/server.ts:96-131`). Для проектных агентов линз-данных как инструмента не существует.

### 4.3 «Обзор на абстрактном уровне» — частично есть, агенту недоступно
- `GET /v1/stats` → `{total, by_scope{слаг:N}, by_type{тип:N}}`, с тем же гейтом, что `find` (`service/stats.ts:20-32`, `runtime.ts:270-275`, `contract.ts:424-428`; маршрут `brain-mcp/src/contract.ts:188`). Но:
  - **нет в MCP** (агент его не вызовет);
  - **нет `by_status`**;
  - `by_scope` считает **прямые** области записи: запись в двух проектах учтена в каждом — сумма `by_scope` > `total` (`stats.ts:26-29`; это нормально, но объяснить);
  - `by_type` схлопывает неизвестные виды в `raw` (§3.2).
- **Бесплатный обзор уже сейчас, 0 кода:** `find` возвращает `total` при любом фильтре (`find.ts:144`). `find{scope,type,status,limit:1}` → одно число ценой ≤1 строки. Матрица «проект × тип × статус» = N таких вызовов. Работает, но дорого по числу вызовов и раздувает ход агента.

### 4.4 Чего не хватает: preset `overview` (он же «root» из `10-root-rules-layers.md`)
**Минимальный срез (≤12 строк / ≤4000 симв., в том же `capDigest`):**
```
Обзор · записей 142 · областей 3 · холодных 4
ff: task 31 (open 12, blocked 2) · decision 9 · question 6 (open 4) · note 20 · raw 3
agents-manager: task 8 (open 3) · decision 4 · note 5
(общее): …
Просрочено 2 · без движения >7 дн 5
Дальше: find{scope:ff,type:task,status:open} · preset open · read #<id>
```
Состав: (1) итог и число областей, доступных ЭТОМУ читателю; (2) по каждой области — тип × счётчик, у типов со `status` — разбивка открыт/закрыт; (3) просрочено и «застряло» (уже считаются в `morning`/`evening`, переиспользовать `isOverdue`, `presets.ts:72`); (4) строка-подсказка «что звать дальше» — это и есть заготовка «каскада»: обзор дёшев, тела только по запросу (V1).

**Где менять (небольшой код, не платформа):** добавить `'overview'` в `FindPreset`/`FIND_PRESETS` в **обоих** контрактах (`brain/src/contract.ts:221-222` и байт-копия `brain-mcp/src/contract.ts:221-222`; тест `brain-mcp/test/contract-sync.test.ts` их сверяет), в zod-enum MCP (`brain-mcp/src/server.ts:28`), и ветку в `runPreset` (`presets.ts:127-136`). Считает по уже отфильтрованному гейтом `pool` → **утечки нет**: читатель видит счётчики только по тому, что видит сам (тот же `visibleRecords`, `access.ts:262-273`). Никаких новых прав и поверхностей MCP.
**Чего overview НЕ делает (сознательно):** правила/каскад и «кто ты» — это `lens:root` из `10-root-rules-layers.md`, отдельный шаг; не мешать с первым срезом.

**Побочная находка для overview:** без типа `question` (§3.2) обзор покажет вопросы как `raw` — поэтому порядок такой: сначала `question` как тип, потом `overview` (или overview группирует `raw` по `declared_type`, `fields.declared_type` — доступно в `rec.fields`, дёшево).
