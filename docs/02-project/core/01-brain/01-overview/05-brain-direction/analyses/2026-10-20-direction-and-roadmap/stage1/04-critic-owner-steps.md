## Вердикт: SHIP-AFTER-PATCH (P0 применены в документе)

## P0 (применены)
1. **Баннер pm2 «do: pm2 update».** При запуске `launch-brain.sh` pm2 в памяти (5.4.2) старее локального (7.0.3) и сам советует `pm2 update`. Это перезапустит живого агента шлюза и оборвёт ходы. В шаге A добавлено «не делать `pm2 update`/`pm2 kill`».
2. **Блок «NEXT» в конце `launch-brain.sh`** велит делать `prompt:import`, править `.env` шлюза и `pm2 restart agent`. Это противоречит «шлюз не затрагивается». В шаге A добавлено «этот блок в Этапе 1 пропустить».

## P1 (применены, мелкие и очевидные)
3. `~/.config/ff-brain/mcp.json` нужен в E и F, но ни один шаг его не создаёт. Сейчас файл есть и содержимое верное. Добавлена проверка и команда копирования шаблона.
4. Шаг F: добавлено, что Claude Code в agents-manager спросит разрешение на `find`/`read`.
5. Шаг G: временная копия личных данных оставалась в `/tmp`. Теперь команда с `--cleanup`.
6. Шаг H: коммит только ADR-0016, `git status --porcelain` отдельным шагом (в дереве лежит чужой untracked `docs/03-projects/00-portfolio-focus/`).
7. Строка «acts N → N» в таблице: скрипт после рестарта может опросить ещё старый сокет. Раньше инструкция была сразу откатывать. Теперь сначала подождать и проверить `stats`.

## P1 (не применены, решение лида или владельца)
- **Доступ папки FF шире минимума.** `stage1-scopes.sh` оставляет у FF `personal:true` и добавляет `write:true`. Любая сессия Claude Code в папке FF с `--mcp-config` читает и пишет личное. Для первой записи в `ff` хватило бы `personal:false`. Решение владельца. Привязка идёт по cwd, а не по человеку.
- **Квитанция с пустой областью** (`runtime.ts:221`, `recordReceipt` получает `reader.scopes`): после починки другим агентом убрать ⚠️ из шага E.5.
- **Хеш ADR-0016 устаревает сразу после шага H** (id известен только после записи). Это порочный круг. Принято как «находка» в roadmap. Лучше решить: хешировать тело без frontmatter.
- Абсолютный путь `node v22.23.2` зашит в 4 местах (скрипты, mcp.json, ecosystem). Смена версии nvm сломает всё разом.
- Если папок `backups/journal-*.jsonl` ещё нет, команда шага B даст непонятный вывод (`.sha256`). Лучше сказать «подожди минуту после старта».

## Проверка по пунктам задания
1. **Команды.** Пути, кавычки и cwd корректны. Каждая отдельной строкой, с ожидаемым выводом. Деструктива нет. Скрипт D делает бэкап `.bak-<ts>` перед записью, пишет атомарно (tmp, затем mv), безопасно повторяется. Диагностика (dry-run) отделена от `--apply`. Откат есть у A, D, G. У E (запись) отката нет, об этом честно сказано («навсегда»).
2. **Порядок верный.** A, затем B, C, D (нужны service.json и readers.json из A), затем E (нужны области из D), F (нужна запись из E), G, H. Зависимостей вперёд нет. C можно делать после D, но не вредно.
3. **Риски.** Поправлены pm2 и «NEXT». Хеш после `brain_id` описан. Доступ FF: см. выше. Квитанция: косметика, запись верна.
4. **Язык.** Понятен, но местами жаргон («genesis», «cli[…]», «области», «квитанция»). Для владельца, который в курсе, достаточно.
5. **Время.** Около 17 команд и 3 диалога с агентом, 45–60 минут чистого времени, 1–1,5 часа с чтением. Оценка документа верна. Один рестарт `ff-brain`, плюс один необязательный в G.

Итог: решение — SHIP-AFTER-PATCH, P0/P1 применены; открыто: доступ FF (`personal`/`write`) и хеш ADR после `brain_id` — решения владельца.
