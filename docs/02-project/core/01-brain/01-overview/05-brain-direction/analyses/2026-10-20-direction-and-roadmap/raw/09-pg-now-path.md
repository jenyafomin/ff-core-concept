## 0. Рефрейм (главное, до шагов)

Владелец в п.4 называет одной фразой три **разные** вещи. Их надо развести, иначе «PG сейчас» превращается в платформу:

| Что хочет владелец | Чем это на самом деле решается | Зависит от PG? |
|---|---|---|
| «Память, которая везде есть» (другие машины, телефон) | **где работает сервис** + **сетевой транспорт MCP** + авторизация | **нет**. Сервис на файле-журнале на сервере так же «везде» |
| «Сервер + MCP, к которому подключаются агенты любых проектов» | транспорт и онбординг проекта (`readers.json`, `--mcp-config`) | **нет**. Локально это уже работает (см. §2) |
| «Надёжно, качественно, не потерять» | один носитель истины с транзакциями, бэкап вне Mac, **проверенное** восстановление | **да**, здесь PG реально добавляет вес |

Отсюда: **PG сейчас = смена носителя журнала на транзакционный, с бэкапом вне машины.** Это качество. «Везде» и «много агентов» — отдельные шаги со своей ценой, их нельзя смешивать с PG.

Важно: `pm2 list` показывает процесс `pg` в состоянии `stopped` после 278 рестартов (`raw/01` §1.1, §5.8г). В этой среде Postgres уже падал под pm2. PG ставим через `brew services`, а не через pm2. Чей был тот `pg`, выяснить до установки.

## 1. Путь «PG сейчас» шагами

### 1.1 Какой паттерн и почему (сверено с ADR-0017 D3)

ADR-0017 D3 разбирает четыре варианта: A (всё async), B (sync-порт + RAM + write-through в PG), C (async `JournalPort`/`ProjectionPort` в оболочке), C-bis (файл = истина, PG = проекция). F2 рекомендует C-bis. Но C-bis **не даёт того, чего хочет владелец**: истина остаётся файлом на Mac, PG там только индекс. Решение «PG сейчас» значит, что истиной становится PG.

**Выбор: «журнал в PG как истина + проекция в RAM как кеш + fail-stop». Это C-минимум.** Async-порт `JournalPort` живёт в оболочке brain, ядро не трогаем.

- `Engine.write(act): Ack` синхронный и заморожен ADR-0010 (`engine/src/engine.ts:73`). Его **не трогаем**. Вариант A отвергнут ADR-0017 как перепись.
- `StorePort` остаётся синхронным для Engine, но его реализация теперь `CachedStore`: проекция и `acts()` в памяти, как у `MemoryStore`. Engine продолжает читать из RAM, и 50 вызовов `store.*(` в 22 файлах (grep) **не меняются**.
- Новый **async `JournalPort`** в оболочке brain. Через него проходят только долговечность и эксплуатация:
  ```
  JournalPort {
    open(): AsyncIterable<{seq, line}>      // загрузка на старте, порядок = seq
    append(seq, line): Promise<void>         // ok только после COMMIT / fsync
    lock(): Promise<Release>                 // file: PID-lock; pg: pg_try_advisory_lock
    health(): Promise<{lagSeq, badLines}>    // заменяет readFileSync в runtime.ts
    backup(): Promise<BackupReceipt>         // file: копия + sha256; pg: pg_dump (снаружи процесса)
  }
  ```
  Адаптеры: `FileJournal` (текущий JSONL, логика `journal.ts`/`backup.ts` переезжает сюда) и `PgJournal`.
- **Граница async = `WriteQueue`** (`brain/src/service/queue.ts`). Порядок внутри очереди: idem-проверка → `Engine.write` (sync, кладёт акт в RAM и в pending) → `await journal.append` → индекс idem → `ok:true`. Свойство «ok:true только после долговечности» (ADR-0016 D10, атомарность в очереди) сохраняется.
- **Fail-stop.** Если `append` отклонён, сервис переходит в read-only и выходит, pm2 его перезапускает, проекция заново собирается из PG как из истины. RAM никогда не переживает истину. Остаточное окно: `find`, пришедший во время `await`, может увидеть ещё не закоммиченный акт (миллисекунды). Принимаем и документируем. Если у Engine есть чистый `admit`/prepare, лучше коммитить **до** применения в RAM, и тогда окна нет. Это проверит builder на `engine.ts:73-160`.
- **Предел масштаба:** всё в RAM. При ~50k актов или записи дольше 200 мс включается полный C (проекция в PG, tsvector/pg_trgm). Это **аддитивно**: тот же `JournalPort`, к нему добавляется `ProjectionPort`. Порог взят из ADR-0017 F2.

| # | Шаг | Что меняется (file:line) | Выход / проверка | Дни агента |
|---|---|---|---|---|

**Итого честно:** ~6.5–8 дней агента, ~1.5–2 недели календаря с приёмкой и критиком. Прежняя оценка «3–5 дней» (`raw/01` §4) считала только ядро, без P0/P6. Руки владельца: ~1.5–2 ч (установка PG, бэкап-цель, репетиция восстановления, переключение).

### 1.3 Что ломается

- `launch-kit` и RUNBOOK шаги 1/1б (пути и бэкап привязаны к файлу) → переписать под `JOURNAL=pg|file`.
- Подсказка «удали stale lock руками» (`journal.ts:preflightLock`) в PG не нужна: advisory lock снимается вместе со смертью сессии. Это плюс.
- Запуск теперь зависит от PG: если PG не поднят, сервис не стартует. MCP-клиент уже паркует записи в outbox (`brain-mcp/src/client.ts:162,168-181`), поэтому для агентов это выглядит как сегодняшний SERVICE_DOWN. Новых режимов отказа у агента нет.
- Бэкап «каждые 50 актов» (`backup.ts`, `LIMITS.backupEveryActs`) в PG теряет смысл, его заменяют WAL + ночной `pg_dump`. Если нужен PITR, это WAL-архивирование, отдельный шаг (мало-средне).
- Файловый адаптер **не удаляем**: он остаётся для тестов, экспорта в JSONL (переносимость, V5) и как цель аварийного replay pg→file.

### 1.4 Где живёт PG

| Вариант | Цена | Вес | Вердикт |
|---|---|---|---|
| **Локально, brew, рядом с сервисом на Mac** | мало | много: транзакции, pg_dump, копия вне Mac, 0 сетевых задержек | **сейчас** |
| Docker на Mac | средне (ещё один демон и ресурсы Docker Desktop) | то же, что brew | не нужен |
| PG на сервере, сервис на Mac | средне | **отрицательный**: каждая запись идёт по сети, Mac офлайн = записи в outbox | нет |
| Сервис **и** PG вместе на сервере (VPS / домашний сервер) | средне-много: новая граница доверия (сеть вместо unix-сокета 0600), TLS, токен на каждого клиента, обновления ОС | много, **когда** появится вторая машина или реальная потребность писать без Mac | отдельный ADR по триггеру |
| Управляемый облачный PG (Neon/Supabase и т.п.) | мало по деньгам | **минус по V5/V7**: личная память у третьей стороны, бэкапы вне нашего контроля, erase через чужие бэкапы | не для личной памяти |

Переезд «Mac → сервер» потом = `pg_dump/restore` или replay. Это **не дверь**, если схема из §4 верна. Телефон у владельца **уже есть**: Telegram → шлюз agents-manager на Mac → мозг. «Телефон без Mac» = вариант «сервис+PG на сервере».

### 1.5 Порядок относительно «первой живой записи»

См. §3: **сначала первая запись на файле (Э1, до 10-27), PG-трек параллельно в worktree, переключение через replay**, цель ~2026-11-07. P0 уже стоит в своде как «параллельно Э1». P1–P5 идут в ветке и **не трогают живой сервис** до переключения.

## 2. Доступ агентов: «сервер + MCP для агентов любых проектов»

### 2.1 Как сейчас (факты)

```
[агент Claude Code / ход шлюза]  ×N
   └─ spawn → brain-mcp (stdio, свой процесс на каждую сессию)   brain-mcp/src/index.ts:8,20
         └─ HTTP/JSON по unix-сокету 0600 + Bearer-токен           client.ts:218-248, http.ts:1,211-233
               └─ ОДИН сервис ff-brain (pm2) — единственный писатель, WriteQueue
```

- Идентичность берётся только из env → заголовков (`client.ts:57-74`, `http.ts:46-62`). В теле запроса её нет.
- Доступ определяется по `readers.json`: чаты/топики шлюза плюс записи `cli` с ключом = абсолютный cwd (`readers.ts:28`). Файл перечитывается на лету, при ошибке fail-closed.
- Токен один (`main`) плюс мандат шлюза (`gateway`) (`http.ts:166-171`).

**Вывод: «много агентов разных проектов одновременно» на одной машине уже работает.** N stdio-процессов ходят в один сервис, очередь сериализует записи. Не хватает только онбординга: проекту нужен `--mcp-config` / `.mcp.json` и строка `cli` в `readers.json`. Это ~5 минут на проект, и его можно свести к одному скрипту `ff-brain onboard <ключ реестра>`. PG здесь ни при чём.

### 2.2 Что нужно для удалённых агентов (другая машина, облачные сессии)

1. **Транспорт:** MCP **Streamable HTTP**. SSE в TS SDK помечен deprecated (Context7, `modelcontextprotocol/typescript-sdk`: `SSEClientTransport @deprecated`). Удалённый режим = отдельный вход `brain-mcp --http`: тонкий адаптер, который принимает MCP по HTTP и проксирует в тот же сервис. Контракт `record·find·read·link` не меняется.
2. **Авторизация:** сегодняшний «cwd как ключ» — это **заявление**. На одной машине под одним пользователем ОС (ISO-2) это допустимо, по сети нет. Нужен **токен на клиента → запись читателя** (токен = принципал, области из `readers.json`), отзыв токена, хранение только хеша. Это та же форма, что `gateway`-мандат в `http.ts:169`, только обобщённая на N клиентов.
3. **Сеть:** без публичного порта. Сначала Tailscale/WireGuard (приватная сеть, TLS даёт она). Публичный HTTPS + OAuth нужен только для custom connector в claude.ai/мобильном приложении. Цена честно: 2–4 дня + security-review. Без отдельного решения владельца не делать.
4. **Readers.json → в мозг?** Владелец хочет «систему правил внутри памяти». Правила доступа как данные (`policy`) — это направление ADR-0006, но ключ доступа к самому мозгу нельзя хранить только в мозге (курица и яйцо: кто читает правило до авторизации). Файл `readers.json` остаётся корнем доверия, а правила уровня «организация/линза» могут жить в мозге.

### 2.3 Нужен ли NestJS

**Нет.** Сервис уже тонкий HTTP-слой: `http.ts` 248 строк, маршрутизация 8 глаголов, лимиты тела, коды ошибок. Удалённый MCP — это ещё ~150–300 строк адаптера (Streamable HTTP из SDK + проверка токена). Nest добавит DI/декораторы, ESM↔CJS трение (ADR-0016 D1 уже чинил ESM-импорты) и привязку плагинов к фреймворку (риск V5). Второго HTTP-потребителя, которому нужны модули Nest, нет. Цена Nest: 1–2 дня + постоянные «проценты», вес мало. Триггер пересмотра прежний (§5 свода): третий входной адаптер или второй транспорт с общей бизнес-логикой. И даже тогда Nest допустим только как хост.

**«Центральная точка как CLAUDE.md»** (п.4) — это вопрос контракта, а не транспорта. Её можно отдать как MCP-ресурс/промпт `brain://start` или как пресет `find` поверх `sys:prompt-layer`/`sys:lens`, которые уже есть (`domain/sys-types.ts`). Дизайн — отдельный разбор волны 4, к PG не привязан.

## 3. Развилка: (А) первая запись на файле → replay в PG, или (Б) сначала PG

| | (А) файл → replay | (Б) PG → первая запись |
|---|---|---|
| Когда первая запись | Э1, до 10-27 | после P0–P6, ~11-07+ |
| Через какой путь идут первые реальные данные | через проверенный путь: fsync, 214 тестов, гейт ADR-0016 AC-19…23 | через адаптер, написанный неделю назад |
| Проверка «журнал переносим» | **реальным** replay ~10–30 реальных актов. Это лучший contract-тест, какой может быть | только синтетикой |
| Цена ошибки replay | дёшево: 10–30 актов, источник не меняется и архивируется (`store-port.ts` R-4.4) | — |
| Риск | двойная эксплуатация 1–2 недели (файл живёт, PG в ветке) | повтор «готовим фундамент, 0 данных» (`raw/04`, `raw/07`): 0 реальных данных за 4 месяца |
| Путь replay всё равно нужен? | да: восстановление, переезд на сервер, экспорт | да, те же причины, но проверяется позже |

**Рекомендация: (А).** Надёжнее, потому что (1) первые данные идут по проверенному пути, (2) переносимость журнала доказывается на настоящих данных, а не обещается, (3) replay нужен в любом случае, так что (А) просто проверяет его раньше. «PG сейчас» владельца выполняется: **работа начинается сейчас и параллельно**, переключение получает **дату** (~11-07), а не триггер. Условие: до переключения записи в Э1 держатся в белом списке (§6 свода: без третьих лиц и id), чтобы replay не перенёс в PG и его бэкапы то, что потом придётся стирать.

## 4. Односторонние двери PG (решить до первого `CREATE TABLE`)

| # | Дверь | Решение по умолчанию | Почему необратимо |
|---|---|---|---|
| PG-1 | **Что считается истиной в строке** | истина = **строка журнала побайтно** из `journal-codec.encodeLine` (`text`, v0/v1 как есть). `jsonb` — только **производная** колонка для запросов, допускает NULL | `jsonb` переупорядочивает ключи, схлопывает дубли ключей и **отвергает `\u0000` и одиночные суррогаты**. Хранить только jsonb = потерять «verbatim» (ADR-0017 D3, `store-port.ts` R-4.5) и побайтную эквивалентность replay |
| PG-2 | **Порядок (`seq`)** | `seq bigint` явный: писатель выдаёт max+1 под advisory lock, `UNIQUE(seq)`. **Не `bigserial`** | sequence в PG не транзакционна, оставляет дыры, а при гонке порядок nextval ≠ порядок commit. Порядок журнала несёт смысл (`rev`, «последний побеждает») |
| PG-3 | **Время** | `recordedAt` берём только из строки акта (его ставит Engine), производная колонка `recorded_at timestamptz` для индексов. Отдельно `committed_at timestamptz default clock_timestamp()` — аудит, не данные. Никаких `default now()` на данных | если PG «штампует» время, replay меняет смысл (тот же запрет, что для `Engine.write`, `engine.ts:74`) |
| PG-4 | **Id** | `text`, непрозрачный, чеканит только мозг (`u_…`, ADR-0017 D4). Не `uuid`-тип, никаких id от PG. `UNIQUE(act_id)` | смена типа колонки и формата = миграция всех ссылок, рёбер (`edgeIdOf`) и frontmatter (`brain_id`, дверь D-1) |
| PG-5 | **Append-only** | роль приложения без UPDATE/DELETE + триггер, запрещающий их. Будущий `hard_erase` идёт **отдельной привилегированной процедурой** | без этого «журнал не переписывается» (ADR-0017 §0) держится только на честности кода |
| PG-6 | **Стирание и бэкапы (V7)** | хранить **meta и `erasable` раздельно** (`acts` + `act_erasable(seq, body, erased_at)`). Codec уже делит акт (`splitAct`, `journal-codec.ts:18-19`). Contract-тест: склеенная строка == строке файла побайтно. Тела и PII третьих лиц в PG **не пишем до Э4** | всё, что попало в PG, попадает в WAL, `pg_dump` и **копию вне Mac**. Стереть из всех бэкапов почти невозможно. Раздельное хранение (на будущее crypto-shred по ключу referent) дёшево сейчас и дорого потом. Если отложить, ровно эту развилку отдать в ADR |
| PG-7 | **Кодировка и пути** | БД `ENCODING 'UTF8'`. Для ключевых колонок `COLLATE "C"`: побайтный порядок, не зависит от ICU/glibc. **Нормализация путей `source.ref` в NFC на границе контракта**, до хеша и валидации. До этого правило Э1: только ASCII | macOS отдаёт кириллицу в NFD. «й» в NFD ≠ «й» в NFC → один документ получит два адреса и два тождества (V2). Смена collation после индексов = переиндексация и тихие расхождения сортировки |
| PG-8 | **Топология БД** | одна БД `ff_brain`, схема `brain`. Области (`ff`, `agents-manager`, `personal`) — **данные**, а не БД или схемы на проект | «БД на проект» ломает M:N (одна запись в ≤10 областях, `LIMITS.recordScopesMax`) и рёбра между проектами |
| PG-9 | **Версия схемы** | `schema_migrations` + только аддитивные миграции. Версия строки — `_v` codec'а и `provenance.schema_v`, а не колонки | переписывать строки журнала запрещено (ADR-0017 §0), поэтому эволюция схемы может быть только аддитивной |

Обратимо (не двери): место PG (Mac → сервер), версия PG, способ бэкапа, транспорт MCP, Nest.

## 5. Что предлагаю зафиксировать

- **ADR-0020 «Носитель журнала = Postgres (C-минимум)»**: supersedes F2 в ADR-0017 по пункту «C-bis сейчас» (C-bis остаётся как будущая проекция). Содержание: §1.1 + двери §4 + fail-stop + контракт `JournalPort`. Перед `approved` — critic.
- Удалённый доступ (§2.2) — **отдельный** ADR по триггеру «вторая машина / облачные сессии». Это граница доверия ISO-2 → сеть (ADR-0011).
- Патч свода: §2 (вариант «PG сейчас» = (А) + дата), §4 Э1 «Заморожено: PG» → «PG в worktree, не в живом сервисе», §5 строка «PG как носитель журнала» → дата вместо триггера.

## Итог

Ответил на вопрос-цель. Чтобы PG был качеством, а не платформой, нужно три вещи. Первая: PG меняет только **носитель истины**, через async `JournalPort` в оболочке; ядро, Engine и 50 sync-вызовов не меняются. Вторая: «везде» и «много агентов» не смешиваются с PG; много агентов локально уже работает, удалённый доступ идёт отдельным ADR. Третья: первая запись идёт на файле, переключение через replay с датой ~11-07. Рамка владельца была частично неверна: «PG = память везде» — неправда, «везде» даёт расположение сервиса и транспорт.

Итог: решение (А) + ADR-0020 на critic; задача в плане: P0–P6 в worktree параллельно Э1.
