## 0. Главная находка: решение о модели истины УЖЕ принято, а не построен только мост

Рамка «файлы против мозга» снова встаёт как новая, но она закрыта ратифицированными ADR:
- **ADR-0006 §(b),(g)** (approved 2026-07-26): размещение задаётся **на тип**. `doc`, `adr/spec`, `prompt`, `config`, `agent`-проза, `lens` — **file-first** («файл = истина»). Всё машинное (задачи, память, трейсы) — DB-first.
- **ADR-0006 §(f):** для file-first типов движок — **«первый читатель, не первый писатель»**: правка ФС → акт в журнале строится диффом (git-hook / fs-watcher).
- **ADR-0006 §(d):** DB→file = **экспорт по требованию**. Постоянная двусторонняя синхронизация **отклонена**.
- **ADR-0016 D7:** поля `layer · derived_from · source{kind,ref,hash}` уже есть по форме (`packages/brain/src/domain/validate-act.ts:77,336,629`; `SOURCE_KINDS = file|act|url` — `packages/brain/src/contract.ts:219`). Правило «файл = истина, правки тела документа в мозге не принимаются» отложено до «ингеста документов».

**Значит, по существу это вариант (C), и владелец его уже утвердил.** Не хватает трёх вещей: (1) контракта синхронизации (кто, куда, когда), (2) модели адресации «один дом → много проектов», (3) закрытых дверей данных для типа `doc`. Ниже я разбираю A/B/C заново: семя владельца п.4 («писать в мозг эффективнее») давит в сторону B, и это надо проверить, а не проглотить.

**Рефрейм боли (гипотеза, проверить вопросом владельцу):** боль из п.4 — это **дубли**, то есть проблема **адресации**, а не носителя. Дубли убирает правило «один дом + ссылки», а не перенос тел в базу. Перенос тел в базу дублей сам по себе не убирает (дубль можно завести и в базе), зато ломает git-инструменты.

## 1. Три модели истины

### (A) Файлы/git = истина, мозг = индекс + граф + адресация (для ВСЕХ типов)
- **Синхронизация:** в одну сторону, файл → мозг. Пишет человек или агент в файл, а синк-агент поднимает акт. Конфликтов нет: писатель один.
- **История/откат:** git (diff, blame, revert, PR). В журнале мозга только конверты с `hash` версии.
- **V5 портируемость:** максимальная, файлы и есть экспорт. Но задачам, людям, дням, трейсам и мелким заметкам из Telegram пришлось бы стать файлами. Это **уже отвергнуто владельцем** («память в файлах проекта», ADR-0016 «Альтернативы»).
- **V2 тождество:** держится только при `id` во frontmatter. Путь тождеством быть не может: дерево постоянно переезжает по законам `doc-tree`.
- **V6 рёбра:** рёбра, выведенные из ссылок, легко посчитать. Рёбрам, которые утверждает человек, жить негде, кроме как в frontmatter, а frontmatter распухает.
- **V7 согласие:** тела лежат в git и навсегда остаются в истории коммитов. `hard_erase` = переписывание истории git.
- **Цена:** мало сейчас, много потом (машинные типы в файлах). **Вес:** средне (V5 высокий, V6/V4 низкие). **Вердикт:** годится для документов, для мозга в целом нет.

### (B) Мозг = истина, файлы = генерируемые виды/экспорт
- **Синхронизация:** в одну сторону, мозг → файл (материализация). Ручная правка файла = конфликт: её либо теряем, либо нужен обратный парсер, а это и есть двусторонняя синхронизация, отклонённая ADR-0006 §(d).
- **История/откат:** только журнал актов (supersedes). Нет diff/blame/PR, Claude Code и ревью не видят истории. Инструменты пришлось бы строить заново.
- **V5:** держится, если экспорт полный (журнал + схемы). Но человек и агенты в других проектах **читают через сервис**: мозг лежит, значит документации нет.
- **V2:** сильное (id чеканит мозг).
- **V6:** сильное (рёбра = записи).
- **V7: опасно.** Тело документа ложится в append-only журнал, а `hard_erase` не построен нигде (свод 10-14 §2), и `payload` от конверта не отделён. Первый документ с чужими данными (CRM, клиенты Cardex) становится неудаляемым.
- **Цена:** много (редактор, история, diff, ревью, доступность). **Вес:** много для V2/V6, против V7/V5-доступности и против наказа «мозг ДОПОЛНЯЕТ git» (семя п.5). **Вердикт:** сейчас отклонить. Переход к B для отдельного типа оставить возможным через смену размещения (см. дверь D-3).

### (C) Гибрид по типу единицы — рекомендую (это и есть ADR-0006, доведённый до контракта)
| Вещество | Хозяин тела | Мозг хранит | Примеры |
|---|---|---|---|
| **file-mastered** | файл в git (один дом) | конверт: `id`, `source{kind:file, ref, hash}`, label/summary (V1), рёбра, области, статус | `doc`, `adr`, `spec`, `prompt`, `config`, `rule`, `skill` |
| **brain-mastered** | журнал мозга | всё | `task`, `decision` (захваченное в чате), `note`, `person`, `day`, `friction` |
| **derived** (`layer ≥ 1`) | никто, пересобирается | `derived_from: [id@rev]` + `stale` | сводки, индексы, `_generated/` виды, общий указатель в проекте |

- **Синхронизация:** у каждой единицы **ровно один хозяин тела**, поэтому направление всегда одно, и это свойство типа (single-master per unit). Конфликт тела невозможен по построению. Метаданные делятся **по полям**: поле во frontmatter → хозяин файл; поля, которые есть только в мозге (рёбра от агентов, `confidence`, счётчики чтений), в файл не пишутся никогда.
- **История/откат:** тело → git. Мозговая сторона (рёбра, статусы) → журнал. Мост между ними: `rev` = хеш содержимого, плюс необязательный `git_commit` в provenance.
- **V5:** тела портируемы как файлы, конверт и рёбра экспортируются из журнала. Перенос в другой движок = журнал плюс репозитории.
- **V2:** `id` во frontmatter переживает переезд файла. Без него V2 ломается при первом `git mv`.
- **V6:** рёбра двух родов (см. дверь D-6): выведенные из ссылок (`author=sys:docsync`, `derived_from=doc@rev`, пересобираемые) и утверждённые человеком или агентом (журнал, полноправная память).
- **V7:** тела не попадают в неизменный журнал. Стереть = удалить файл (плюс история git, когда это реально нужно) + tombstone-акт. Пока нет `hard_erase`, это **единственная** честная форма для документов с чужими данными.
- **Цена:** средне (синк-агент + 6 дверей данных, ≈1–2 дня по «строй»). **Вес:** много (V1, V2, V5, V6, V7 и наказ «дополняет git»).

### Синхронизация в (C): кто и как пишет
1. **Файл → мозг (детерминированный синк, это КОД, не LLM).** `ff-brain sync <repo>`: по git-hook post-commit или вручную. На каждый `*.md` по белому списку путей: (а) нет `id` во frontmatter → чеканит мозг, синк вписывает его в файл. Это **единственная запись мозга в файл**, она идёт отдельным коммитом и только с согласия владельца (правило проекта «не коммитить без просьбы»). (б) Считает `hash`, ставит `record`/`update` идемпотентно по `(id, hash)`. (в) Ссылки и `Related:` превращаются в выведенные рёбра. (г) Переезд файла: тот же `id`, новый `ref` → `update`. Файл исчез → `status: cold` + `source-missing`, удаления нет (V4).
2. **Мозг → файл, только два легальных пути.** (а) **Виды** (`_generated/`) с баннером «не править, источник id@rev». Пересобираются, ручная правка затирается по контракту. (б) **Повышение (promotion):** brain-mastered заметка вырастает в документ. Агент пишет черновик файла, владелец коммитит, затем акт `placement: file` (supersedes) передаёт хозяйство файлу. Это **разовая передача хозяйства**, а не синхронизация.
3. **LLM-агенты «помечают» (семя п.5), а не синхронизируют.** Их работа смысловая: кандидат-ребро `duplicate-of`/`supersedes` между документами, предложение «у темы два дома», сводки. Всё пишется со `status: proposed` (ADR-0016 D8), тела файлов агенты не трогают. Детерминированный синк и смысловая разметка — **два разных модуля**. Слить их = получить молчаливые правки истины.

## 2. «Одна документация на много проектов»: хранение или адресация

**Это адресация.** Хранение остаётся по закону «один дом» (`doc-tree` закон 2). У документа один физический дом, а много проектов видят его через **области** (ADR-0016 D4): единица несёт `in-scope` M:N → `project:cardex`, `project:crm-server` или `company:…`. Проект, который `member-of` компании, видит её документы. Модель уже построена ради этого, новой сущности не нужно.

**Где дом общего документа:** в репозитории, который **по смыслу им владеет** (модель Client→Deal живёт в `crm-server`, хотя её читает и `forms-sidebar`, см. `~/.claude/registry/projects.json`). У документа без естественного владельца (общие конвенции, правила работы владельца) дом = один общий репозиторий-«commons». Кандидат: `WORKFLOW/Claude_setup` или FF `docs/01-organization/`. Это развилка для владельца, не моя. Отдельное хранилище внутри мозга не нужно.

**Как проект «видит» общий документ:**
| Механизм | Как | Цена | Вес | Вердикт |
|---|---|---|---|---|
| **MCP мозга** (`find` по области → `read` id) | агент в проекте X спрашивает мозг; сервис отдаёт конверт + тело, прочитанное из файла по `ref` (проверка `hash` → `stale`) | мало (глаголы есть; нужен `read` тела по `source`) | много: одна точка, области/доступ держит сервис | **основной** |
| **Сгенерированный указатель** `docs/_generated/shared-docs.md` в проекте-потребителе | синк пишет список «id · заголовок · summary · абсолютный путь дома» | мало | средне: работает без MCP и без запущенного мозга; деградирует правильно | **страховка** |
| **`@`-импорт в CLAUDE.md** на абсолютный путь дома (гипотеза: Claude Code поддерживает `@path`-импорты, проверить по документации) | 1–3 несущих документа «всегда в контексте» | мало | средне, но съедает контекст | точечно, для правил |
| Симлинк | ссылка ФС в чужой репо | мало | отрицательный: git хранит путь, на другой машине ломается, `grep` видит дубль, правка через симлинк молча уходит коммитом в чужой репо | **отклонить** |
| Копия/транслюзия при сборке | генерировать копию тела в проект | средне | отрицательный: это и есть нынешний дубль | **отклонить** (кроме `_generated` с баннером) |

**Скрытое условие доступа (факт):** Claude Code вне шлюза ходит в мозг **только по allowlist `cwd`** в `readers.json` (ADR-0016 D8). Каждому проекту-читателю нужна строка в allowlist, иначе он ничего не увидит. Это не дефект, но шаг онбординга проекта, и его надо внести в roadmap.

## 3. Место Postgres и NestJS

**Postgres.** Роль одна, с двумя полосами (ADR-0017 D3 C-bis, свод 10-14 §2):
1. **Проекция (read-model) через хук `JournalSink`.** Таблицы `units`, `edges`, `docs` (колонки-индексы + `jsonb` акта целиком). Главный выигрыш для документов: **полнотекстовый поиск по ТЕЛАМ** (`tsvector` с `russian` + `pg_trgm`), а позже `pgvector` для поиска дублей. Поиск дублей и есть суть сценария владельца.
   **Важное свойство:** тело документа в проекции — **производная копия**, её можно стереть и пересобрать. Тело получает полный поиск и при этом не попадает в неизменный журнал. Так V7 и «качество поиска» не спорят.
2. **Журнал в PG — позже**, одной replay-миграцией ниже Engine (ADR-0017 D3), по триггеру >~50k актов, второму писателю или записи >200 мс.
- **НЕ CRUD-истина** (свод 10-14: ломает V2/V5/V6).
- **Когда:** PG-проекцию ставить **при живом запуске сценария «документы»**, если выполнены оба условия: (а) проиндексировано ≥2 репозиториев, (б) поиск in-memory проваливает реальные запросы владельца (каждый провал = `friction`). Два-три таких провала за неделю = триггер. Объём сам по себе не триггер: ~2100 md только в FF (`find docs -name '*.md'`) — по оценке, это ещё по силам RAM. Но поиск по телам in-memory не построен вообще, поэтому триггер, скорее всего, сработает в первую же неделю (гипотеза). Это совпадает с позицией Fable 10-14: «страдает читатель». Обязательное предусловие: 3 файловые привязки сняты, контракт-тест порта зелёный.

**NestJS.**
- **Что есть:** `@ff/brain` уже **сервисный слой** (`packages/brain/src/service/{http,server,queue,auth,readers,health,…}.ts`): единственный писатель, очередь, сокет + токен, MCP-клиент. Nest не добавляет ни одной **ценности данных** (V1–V7). Он добавляет **гигиену хоста**: DI, guards, interceptors, OpenAPI, тестовый каркас.
- **Риски:** ESM↔CJS трение (свод 10-14); риск V5, если «пакет = Nest-модуль» привяжет плагины к фреймворку. Закон: пакеты остаются манифестами-данными (ADR-0017 D5), Nest только хостит.
- **Паттерн:** гексагональный. `@ff/brain/domain` + `read` без фреймворка; хост = адаптер. Замена хоста проверяется **контракт-тестом API сервиса** (тот же набор на «голый» хост и на Nest). Его стоит иметь независимо от решения про Nest.
- **Триггер:** **третий входной адаптер** или **второй транспорт**. Сейчас входы такие: MCP; HTTP по сокету; появятся git-hook синка и `gw-reader`. Синк документов приближает к триггеру, но сам его не взводит. Взводит его web-UI, удалённый доступ с другой машины или второй разработчик.
- **Цена** сейчас: средне (1–2 дня + трение ESM). **Вес** сейчас: мало. Позже, по триггеру: средне/средне.
- **Ответ на «если правильнее»:** «качественно» здесь = **швы и контракт-тесты** (порт хранилища, API сервиса), на которых PG и Nest встают добавлением. Сразу вставлять фреймворк не нужно. Это не осторожность, а порядок: Nest без контракт-теста = перепись без проверки равенства.

## 4. Односторонние двери — закрыть ДО первой записи `doc`

Уже закрыты (не трогать): `id` без проекта/типа (ADR-0016 D2) · append-only + `schema_v/type_v` (D3) · области-узлы (D4) · канон имён/принципалов (ADR-0017 D1) · idem v1 (D4).

Новые двери типа `doc` (каждую записанную ячейку потом пришлось бы мигрировать):

| # | Дверь | Почему необратима | Рекомендация | Цена / вес |
|---|---|---|---|---|
| **D-1** | **Тождество документа = `id` во frontmatter**, а не путь и не хеш | на `id` ссылаются чужие проекты и рёбра; путь меняется при каждом переезде `doc-tree` | мозг чеканит `u_…`, синк вписывает в frontmatter (поле, например `brain_id`). Файл без `id` = ещё не единица | мало / много (V2) |
| **D-2** | **Формат `source.ref`** = логическое имя репо + относительный путь (`repo:ff/docs/…`), не абсолютный путь | ref пишется в журнал навсегда; абсолютный путь привязан к машине (против V5) | репо = единица-узел (`scope`/`repo` с `path` локально), имя из `projects.json`. **Факт-риск:** regex `^[A-Za-z0-9._/:#-]+$`, ≤200 (`contract.ts:140,152`) отбрасывает кириллицу/пробелы: 13 md-путей в FF+Forms-Sidebar уже не пройдут, 72 пути FF длиннее 140 символов. Нужен формат ref для документов: percent-encoding или ref=`id` репо + путь в теле конверта | мало / много (V5) |
| **D-3** | **Хозяин тела (`placement`) — поле типа/единицы, передача хозяйства = акт** | если первые документы запишутся без явного хозяина, потом не отличить «копию» от «истины» | для `doc` ставим `placement: file`. Тело документа в журнал **не пишется** (только `hash` + summary). Смена хозяина = акт `supersedes`. Это открывает путь к (B) для отдельного типа без переписи. Совпадает с резервом `placement` (ADR-0017 D2): вводить с первым потребителем, и этот потребитель — `doc` | мало / много (V3, V7) |
| **D-4** | **Ключ ревизии `rev`** = хеш нормализованного содержимого (sha256), `git_commit` — необязательная подсказка | `derived_from: id@rev` других единиц хранит rev навсегда; git-sha меняется при rebase/squash | хеш содержимого; формат `derived_from` (`^[ua]_[a-z0-9]+@\d+$`, ADR-0016 D9) **сейчас не допускает хеш**. Надо решить: rev = порядковый номер в мозге (маппинг rev→hash в акте) или расширить формат. Решить до первого производного слоя | мало / средне (V3 stale) |
| **D-5** | **Гранулярность: единица = файл**, якорь раздела `id#anchor` зарезервирован | если начать с разделов, файлы-бандлы (ADR-0006 §(c)) и `id` во frontmatter не сойдутся | файл = единица; раздел — адрес (аддитивно, позже) | мало / средне (V1) |
