# Analyst: реальность хранилища мозга (файл-журнал → свой Postgres + NestJS?)

- **Status:** draft · **Owner:** jenya.stasik@gmail.com · **Date:** 2026-10-14
- **Потребитель:** лид / архитектор (волна `2026-10-14-settings-and-storage`) · **Поглощает:** ничего (приложение к своду)
- **Вопрос-цель:** что реально стоит за переводом мозга на свой Postgres (+ NestJS): где шов хранилища, сколько мест завязано на файл-журнал, что уже есть в экосистеме владельца?
- **Related:** `ideas/2026-10-14-owner-seed-settings-and-pg.idea.md` · ADR-0016 · ADR-0017 D3 · `docs/_log/2026-10-05-personal-memory-launch/g1/analyst-storage-files-vs-postgres.md` (прежний разбор, сверен)

## 1. Шов хранилища (готовность ≈ 0.6)
- **Порт есть:** `packages/engine/src/ports/store-port.ts` — `load · readNode · writeAct · acts · rebuild`. Контракт: акт хранится дословно, порядок и `recordedAt` не меняются (ADR-0017 D3). Миграция между адаптерами — ниже Engine (`adapters/replay.ts`).
- **Реализации:** `store-memory.ts` (71 стр.), `store-md.ts` (241), `store-durable-fs.ts` (312). PG-адаптера, схемы и драйвера `pg` нет нигде.
- **Порт СИНХРОННЫЙ** (`writeAct(): Act`, `acts(): readonly Act[]`). Драйвер PG асинхронный, поэтому «просто адаптер» верно только с кэшем в RAM + write-through. Это главная ловушка (ADR-0017 D3 вариант B/C-bis).
- **Три привязки к файлу мимо порта (ADR-0017 их перечисляет, не снято):**
  1. `packages/brain/src/domain/schemas.ts:48,84,99,123` — тип `DurableFsStore`, а не `StorePort`;
  2. `domain/registry.ts` `scanJournalRegistry(journalPath)` читает файл напрямую (pass 1 реестра, `schemas.ts:115`);
  3. `service/backup.ts` (`readFileSync`, `copyFileSync`, sha256-сайдкар, зеркало `backup_mirror`), `service/journal.ts` (`preflightLock`, `repairTornTail`: усечение хвоста, fsync файла и каталога), `service/runtime.ts:153` (чтение сырых байт для хэша битых строк), `contract.ts:202` (путь `store/journal.jsonl`).
- Итого **~5 файлов с прямой файловой логикой** (schemas, registry, backup, journal, runtime) + сам `store-durable-fs.ts`. Потребителей через `Pick<StorePort,…>` ещё ~6 (access, idem, receipt, friction, to-act) — они порт уже используют и не меняются.
- **Что предполагает файл:** единственный писатель (PID-lock `.lock`, `store-durable-fs.ts:99-128`); атомарность = O_APPEND + `fsync` до `ok:true`; рваный хвост чинится бэкапом-копией; бэкап = копия файла + sha256 + зеркало (10-10 п.10); сокет не зависит от хранилища (HTTP по unix-сокету 0600, `service/http.ts:1`, токен). В PG: lock → advisory lock, torn tail исчезает (транзакция), бэкап → `pg_dump`/WAL, зеркало → другой механизм. Часть кода (journal.ts, torn-tail, bad lines) становится не нужна, а не переписывается.

## 2. Event-sourcing и масштаб
- Да: журнал `acts` = система записи, граф = проекция (ADR-0008). `DurableFsStore.hydrateFromDisk` при старте читает ВЕСЬ файл целиком и фолдит в Map (`store-durable-fs.ts:~170`), параллельно `IdemIndex.fromJournal` (`runtime.ts:~158`).
- **Узкие места на запись, не только на старт:** `Engine.write` делает `store.acts().filter(...)` по всему журналу (`engine.ts:145`) и после каждой записи `load(this.store.load())` — пересборку всего графа (`engine.ts:153`). Это O(N) на запись. ADR-0017 держит триггер «>~50k актов или запись >200 мс»; бенч AC-47 (`test/bench.test.ts`, 10k записей: старт ≤2 с, find p95 ≤100 мс) опциональный, результатов на живых данных нет. Мой вывод: комфортно до ~10–20k актов, дальше деградация линейная (оценка по коду, не замер).

## 3. NestJS
- **Шлюз НЕ на NestJS:** `agents-manager/package.json` — plain Node + TypeORM + better-sqlite3 + grammY, ручная сборка `src/app/build-app.js`, слои `core/ server/` (ports, repositories). Зависимости `@nestjs/*` нет. Хранилище шлюза — SQLite через TypeORM (миграции есть: `src/server/persistence`, `migration:run`).
- **Nest-код у владельца есть, но в других мирах:** `PROJETS/whalelounch/tglead-api-gateway` (Nest 10 + `@nestjs/typeorm` + `pg` + typeorm 0.3.20, миграции) — единственный найденный паттерн Nest+PG+TypeORM; `TOOLS/telegram/telegram-nestjs`; Cardex `scaner` (Nest + Prisma) и `crm-nest-telegram` (Nest, но в compose Mongo/Redis/RabbitMQ, не PG). Реестр: `cardex`, `crm-server` — Nest.
- **Мозг сейчас:** plain Node, ESM, vitest, зависимость только `@ff/core`; DI нет, сервис собран руками (`BrainService`, `runtime.ts` 488 стр.). Обёртка в Nest-модуль: провайдер `BrainService` + контроллеры вместо `http.ts` (248 стр.) — оценка 1–2 дня механики, но: (а) тянет ESM/CJS-несовпадение (Nest 10 — CJS-центричен, репо — ESM), (б) утраивает зависимости у «единственного писателя», (в) выигрыша для brain нет, пока нет второго потребителя/нужды в DI/guards. Это инфраструктурный вкус, не требование хранилища.

## 4. Варианты Postgres
| Вариант | Цена | Что сохраняет / ломает |
|---|---|---|
| (а) журнал-файл = истина + PG-индекс (ADR-0017 C-bis: хук `JournalSink.append` после fsync, ~20 строк) | мало, 0 правок Engine | V5 цела (файл самодостаточен), бэкап = cp, hash/idem/erase не тронуты; лаг проекции; PG только для find/JOIN/pgvector |
| (б) PG append-only таблица `acts(seq, body jsonb, recorded_at)` = журнал, проекции там же/в RAM | средне: `store-pg.ts` ~250–350 стр., кэш в RAM (sync-порт), 1–2 дня; 3–5 дней при async-порте | транзакции и конкуренция; V5 слабее (нужен экспорт); бэкап `pg_dump`; порядок `seq` и дословность `jsonb` сохраняются; тесты durability параметризуются фабрикой стора |
| (в) PG CRUD-модель | много, ломает event-sourcing | теряется replay, `rev`, «последний побеждает», аудит. Не рекомендую (против ADR-0008/0010) |

- **hash-chain:** его в мозге НЕТ — в `packages/*/src` нет `prevHash`/цепочки. Есть `idempotencyHash` (содержимое акта, `engine.ts:144`), idem-ключ `sha256(conv+message_id+verb+ordinal)` (`idem.ts`, `IDEM_V1`, живёт в индексе над журналом — не зависит от хранилища) и sha256-сайдкары бэкапов. Терять нечего; в PG цепочку можно добавить позже.
- **hard_erase при append-only:** inline-стирание в `store-durable-fs.ts:254-297` ПЕРЕПИСЫВАЕТ файл (помечено DEPRECATED/DEV-ONLY). Целевой путь — разнесённая форма: `splitAct` (неизменяемая мета ⟂ стираемая `erasable`-зона, `core/erasure.ts`) + `PayloadStore.shred(ref)` + терминальный акт `erased`. В PG стираемая зона живёт отдельной колонкой/таблицей и обнуляется UPDATE'ом (append-only тут допускает исключение для одной колонки) — проще, чем перепись файла. Но это один из пунктов «отложено» в ADR-0016: `hard_erase` каскадом и enforcement согласия НЕ построены ни для файла, ни для PG.
- **Локально:** `postgresql@14` стоит через brew, не запущен (`pg_isready`: нет ответа). Docker работает; контейнер `pg` (postgres:15) уже запущен у владельца (чей — не проверял, отдельная БД под мозг предпочтительна). Свой PG-демон добавляет pm2-процесс и заботу о бэкапе — против V5 «портируемость одним файлом».

## 5. Нулевые данные: цена СЕЙЧАС vs ПОЗЖЕ
- Живых записей 0 (мозг не запущен; подтверждено прежним разбором и зерном). Миграция данных = 0, replay-скрипт не нужен. Дешёвое окно именно для (1) снятия трёх файловых привязок (типизация на `StorePort`, registry-scan за порт, backup за порт) и (2) решения «sync-порт + кэш» vs «async-порт»: потом это правка ядра под данные.
- Позже цена растёт не от PG, а от **объёма и от файловых бэкапов/зеркал в обращении**: replay придётся делать ниже Engine с сохранением `seq`/`recordedAt` (механизм `replay.ts` уже есть, ADR-0017). То есть миграция и позже остаётся обратимой (журнал → архив, не удаление). Срочности нет; снятие привязок можно сделать сейчас дёшево и без PG.
- Рекомендация аналитика: сейчас — снять 3 привязки (0.5–1 день, данных не касается); PG — по варианту (а) как проекция по триггеру (боль в `find`, >20k актов, запись >200 мс) или когда понадобится pgvector/JOIN. Вариант (б) осмыслен, если владелец хочет конкурентных писателей/транзакции — сейчас единственный писатель этого не требует. Nest — отдельное решение, к хранилищу ортогонально.

## Неизвестные
- Реальный объём/профиль запросов (появится после запуска; замерять `/health`, AC-47 на живом журнале).
- Чей контейнер `pg` и можно ли держать в нём отдельную БД.
- Готов ли владелец к CJS/ESM-расходу ради Nest.

**Итог:** решение — шов есть (порт `StorePort`, ~0.6), но синхронный и с тремя файловыми обходами; PG сейчас — не нужен, задача в плане: снять привязки, PG как проекция по триггеру; Nest ортогонален и не оправдан хранилищем.
