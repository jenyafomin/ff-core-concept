# Двери Д2/Д3 как настройки: что переключаемо, а что нет (линза архитектора)

**Вопрос-цель:** можно ли сделать ОБЕ стороны Д2 и Д3 настройками и не потерять V2/V3/V5/V6?

**Короткий ответ:** да, но только если настройкой будет **ВИД (как читаем)**, а не **ПОВЕДЕНИЕ ЯДРА (как пишем)**. Различие пишется в данные один раз и с самой мелкой точностью. Дальше линза показывает его либо «как одно», либо «как два». Переключение туда-обратно ничего не стирает: в журнале меняется только версия линзы.

## 1. Ключевой приём: «двойное представление + проекция»

Правило простое: **данные пишем с максимальной точностью, а склеиваем при чтении.** Склеить мелкое в крупное можно всегда. Разделить крупное на мелкое задним числом нельзя.

Что есть в коде (проверено):
- Предикаты — это данные. Определение проходит одним путём `planDefinition` (`packages/brain/src/domain/definitions.ts:30`). Слои: ядро — только genesis; `pack:<id>/<n>` — только сам пакет; `u:<n>` — пользователь или агент (`domain/names.ts:70-84`). То есть пакет и пользователь **уже могут** добавить свой предикат.
- `part-of` — ядерный, `many` (`domain/genesis.ts:218`). Переопределить его не из genesis нельзя (правило «в» в ADR-0017 D1). Значит, Д1 для самого `part-of` уже закрыта.
- Переклассификация = ребро `instance-of`, **id записи не меняется** (`validate-act.ts:395`, `:570`). Это основа для Д3.
- Политика как данные на type-def уже работает: `approval: owner`, `write: owner` (`genesis.ts:50-58`). Версионируемые системные узлы `lens:<id>@<v>` append-only (`genesis.ts:59-66`).

Чего НЕТ:
- **Иерархии предикатов нет.** В `PredicateDef` нет поля «родитель» (`genesis.ts:72-81`). У `TypeDef.extends` есть только форма, оно не разрешается.
- Поиск по ребру сравнивает только написания одного предиката (`read/find.ts:116`, `samePredicate`). Потомков он не видит.
- **Дыра Д1 для не-ядерных предикатов.** В fold реестра (`registry.ts:226-262`) я не нашёл запрета на то, чтобы v2 определения `u:x`/`pack:…` сузил `many→one`. Защищены только `LOCKED_PREDICATES` (`engine/src/core/predicates.ts:56`). Это надо подтвердить тестом.

**Минимум, который нужен:**
1. Необязательное поле `refines: "<предикат>"` в predicate-def. Это аддитивно, 0 миграций.
2. При чтении «запрос по `part-of` ловит и потомков»: одна функция вместо `samePredicate` в `find`.
3. Инвариант в fold: потомок не меняет смысл родителя. Кардинальность любого предиката можно только расширить (`one→many`), сузить нельзя. Это и есть Д1 как закон для всех слоёв, а не только для ядра.

## 2. Каждая дверь: настройка или односторонняя

Тест для каждой: «переключили туда-обратно — целы ли данные, тождество и история?»

| Дверь | Что пишем в данные (один раз, неизменно) | Что становится настройкой (вид) | Тест туда-обратно | Что остаётся односторонним |
|---|---|---|---|---|
| **Д2** смысл `part-of` | Три уровня: `part-of` («не уточнено»), `pack:groups/groups` и `part-of-whole`, оба `refines: part-of` | Линза «один смысл» склеивает потомков в `part-of`. Линза «два смысла» показывает их раздельно | ✅ Рёбра и их id не трогаются, меняется только версия линзы | Точность записи. Если агенты пишут голый `part-of`, вид «два» покажет «не уточнено». Это не потеря, а отсутствие знания: ребро можно уточнить позже (retract + новое ребро, `supersedes`) |
| **Д3** группа: тип или роль | Роль считается всегда: «на ячейку указывают рёбра `groups`». Тип `pack:groups/group` — по желанию, через `instance-of` | (а) Вид: показывать группы по роли или по типу. (б) Правило записи: агент создаёт группу как `note`+роль или сразу как тип | ✅ Повысить и понизить = два ребра `instance-of`, id тот же, история в журнале | **Нужна проверка:** что происходит с полями типа `group` после понижения до `note`. Если `validate-act` их отрезает или прячет — это потеря. Правило: поля типа живут в теле записи, вид их скрывает, но не удаляет |
| **Д1** many→one | Ничего не сужаем. «Одна родительская папка» = отдельный предикат `u:filed-in` (`one`, `refines: part-of`) или «главная группа» как свойство вида | Какое ребро рисовать деревом — настройка вида | ✅ для вида | ❌ **Сужение кардинальности — не настройка.** Fold молча схлопнет M:N в один → правда поменяется. Это закон ядра |
| **Д4** БД = индекс | Журнал — истина | Какой индекс у журнала (файл/Postgres) — настройка инфраструктуры | ✅ Индекс перестраивается из журнала (replay) | ❌ «БД = истина» — односторонне: история перестаёт быть бесплатной |

Вывод: Д2 и Д3 переводятся в настройки **целиком**. Д1 и Д4 — это **законы, на которых держатся** эти настройки: без них переключение перестанет быть обратимым.

## 3. Где живут настройки и кто их меняет

- **Настройки вида (Д2, вид Д3)** — это и есть **линза**: узел `lens:<id>@<v>`. Механизм уже есть: append-only версии, тип `write: owner`. Новой сущности не нужно. Сменить настройку = записать `@v+1`. История — сама цепочка версий плюс `supersedes`.
- **Настройки записи (правило Д3: как агент создаёт группу)** — это policy-as-data на type-def (как `approval`) или узел `sys:setting`, тоже versioned и `write: owner`. Для второго варианта нужно добавить префикс в `VERSIONED_NODE_PREFIXES` (`genesis.ts:66`).
- **Область действия:** ребро `in-scope` к области, пакету или пользователю. Каскад: ядро-дефолт → пакет → область → пользователь, побеждает самый узкий. Важно: каскад есть **только у настроек**, у данных его нет.
- **Кто меняет:** только с авторитетом владельца (F2 «власть разная»). Код это уже даёт: `write: owner` и `approval: owner` (`validate-act.ts:440-445`). Агент может только **предложить** версию со статусом `proposed`. Активирует владелец.
- **Видимость истории:** «какая настройка действовала в момент T» — запрос по версиям линзы. Каждый ответ агента может нести `lens@v` в провенансе. Тогда видно, через какой вид он смотрел (V3).

## 4. Общий механизм гибкой доработки

Это паттерн конструктора (п.17): **принцип → паттерн → пакет.**
- **Принцип:** «развилка смысла решается в ВИДЕ, а не в ДАННЫХ».
- **Паттерн «двойное представление + проекция»** из четырёх шагов:
  1. Найти самую мелкую точность различия и писать её. Плюс уровень «не уточнено».
  2. Различие выразить данными: предикат-потомок, тип-повышение через `instance-of`, поле.
  3. Склейку и разделение сделать линзой с версиями.
  4. Проверить закон обратимости: тест «туда-обратно».
- **Фильтр «можно ли сделать настройкой»:** нельзя, если переключение требует **переписать, сузить или удалить** записанное: кардинальность, id, удаление, источник истины. Такие развилки остаются дверями, их решает владелец, ответ записывается в ADR.
- **Цена.** Каждая ручка — это ось сложности. N ручек дают 2^N миров, которые надо тестировать, и агент перестаёт понимать, «что значит ребро». Ограничители:
  - (а) ручка появляется только при ≥2 реальных случаях (компаунд, триггер 4);
  - (б) у каждой ручки есть дефолт, и он работает без настройки;
  - (в) ручки только для вида, не для поведения ядра;
  - (г) реестр ручек — один вид («какие линзы активны»).
  
  Настройка ради настройки = смысл размыт. Пример: Д2 «один смысл» по умолчанию, а «два» включается, когда появилась первая настоящая задача из частей.

## 5. Ценности V1–V7

- **V1 Читаемость** — 🟢 Линза отдаёт нужную грань дёшево: «группы» без «состава» и наоборот.
- **V2 Тождество** — 🟢 Id записи не меняется ни при повышении, ни при понижении (`instance-of`). 🟡 Id ребра меняется, когда `part-of` уточняют до потомка. Это новое ребро, старое → `supersedes`. Уточнять лучше при создании.
- **V3 Доверие** — 🟢 Провенанс несёт `lens@v`. Настройки меняет только владелец. 🟡 Без закона «не сужать» любой `u:`-предикат можно тихо переопределить. Закрыть до данных.
- **V4 Витальность** — 🟢 Ненужная линза уходит в `cold`, данные не трогаются.
- **V5 Суверенность** — 🟢 Различие лежит в данных (`refines` в predicate-def едет с пакетом). Линза — тоже данные. В другом движке без линз читается «как два», то есть самым точным способом. 🟡 Склейка зависит от того, умеет ли движок `refines`: это часть манифеста пакета (ADR-0017 D5).
- **V6 Реляционность** — 🟢 Ребро остаётся полноправным: потомок со своим паспортом, родитель целый, сирот нет.
- **V7 Согласие** — ⚪ Не затронуто. Настройка вида не должна открывать то, что закрыто `visibility`: видимость проверяется до линзы.
