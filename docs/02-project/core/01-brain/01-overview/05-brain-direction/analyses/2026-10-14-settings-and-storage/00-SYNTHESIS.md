## 1. Д2/Д3 «обе — настройками»: ДА, при одном законе
**Закон (сходятся architect + critic; но critic в итоге против переключателей до живого прогона, и Д2 с потомками он считает «двумя типами, а не настройкой» — настройкой остаётся только склейка-вид):** настройка меняет только **ЧТЕНИЕ** (вид/линзу), никогда — **ЗАПИСЬ**. Пишем различие один раз, с максимальной точностью; линза показывает его «как одно» или «как два». Переключили туда-обратно — в журнале не изменился ни байт → V2/V3/V5 целы.
- **Д2:** `part-of` остаётся общим родителем («не уточнено»), добавляются два уточняющих предиката-потомка — «состоит в группе» и «часть целого». Настройка-вид: «склеить в одно» / «показывать два». Нужно в ядре: поле `refines` у предиката + `find`, понимающий потомков + закон «кардинальность только расширяется» для всех слоёв (сейчас для пакетов не найден — дыра, проверить тестом).
- **Д3:** «оба» уже даром: группа = **роль** любой ячейки всегда; «тип группы» — по желанию, повышением через `instance-of` (id ячейки не меняется — `definitions/genesis`). Отдельный переключатель не нужен. Не проверено: что с полями типа при возврате группы в обычную заметку.
- **НЕ настройки (законы ядра):** Д1 «не сужать many→one», и форма истины (журнал актов). На них держится обратимость всего остального.
- **Где живут настройки:** как данные в памяти (линзы с версиями, `write: owner`), каскад ядро → пакет → область → пользователь; агент только предлагает; история смены видна по версиям.
- **Общий механизм «гибкой доработки» (паттерн конструктора):** «двойное представление + проекция» — любую будущую дверь записываем точно, а развилку переносим в вид. Оговорки architect: уточнять `part-of` лучше при создании (голый `part-of` = «не уточнено»; уточнение позже = новое ребро + supersedes, id ребра меняется); цепочку `refines` ограничить 1 уровнем. Предохранитель от взрыва ручек: ручка появляется только при ≥2 реальных случаях, у каждой — дефолт.

## 2. Хранилище: Postgres — ДА как носитель, НЕТ как CRUD; NestJS — отдельная дверь
- **Сходятся все 3 (analyst, Fable, critic):** истина = **журнал неизменных актов** (event-sourcing). Файл и PG-таблица событий — одна форма в двух носителях. **PG как обычная CRUD-модель отвергнута** — ломает V2 (история), V5 (переносимость), V6 (рёбра-память).
- **Факты кода (01):** порт хранилища есть (`packages/engine/src/ports/store-port.ts`), готовность к замене ~0.6. Мешают: синхронный порт vs асинхронный `pg` (нужен кэш + запись через него); 3 прямые привязки к файлу (`schemas.ts:48,84,99,123` тип вместо порта; `registry.ts` читает журнал мимо порта; бэкап копирует файл). Каждая запись пересобирает граф целиком (`engine.ts:145,153`) — по оценке, комфортно до 10–20 тыс. записей. hash-chain нет; `hard_erase` не построен нигде. Локально: postgresql@14 установлен, не запущен.
- **🟡 Расхождение (вектор-гард):** Fable — «PG-проекция для ЧТЕНИЯ с первого дня живого использования (страдает читатель, а не писатель); триггер Д4 "несколько писателей" неверен». analyst + critic — «PG по триггеру: >20 тыс. записей / медленный find / второй писатель». **Третий ход («при каком мире оба правы»):** оба правы, если PG-проекция — **переключаемый адаптер чтения** поверх журнала: сделать его можно в момент живого запуска, а журнал перенести в PG позже одной replay-миграцией. Это компромисс лида, не сходимость линз: analyst/critic держат PG до триггера, Fable — с первого живого дня; хук-проекция стоит ~20 строк и 0 правок Engine (analyst) — потому дёшево уступить владельцу. Условие: PG-проекция ставится после §4-теста и ответа на В1, а не автоматически. Риски PG от critic/analyst: поверхность секретов/бэкапов, чужой контейнер `pg` (postgres:15, чей — не проверено), свой PG-демон против V5 «одним файлом».
- **СЕЙЧАС (0 записей = самый дешёвый момент), без PG:** (1) снять 3 привязки к файлу; (2) contract-тест порта хранилища (один набор тестов на любой носитель); (3) **payload отдельно от конверта акта** — дверь для `hard_erase` при append-only (Fable: закрыть сейчас); (4) гейт «экспорт журнала → импорт побайтно» (V5). Оценка 0.5–1 день, эксперимент с потолком.
- **NestJS:** шлюз НЕ на NestJS (чистый Node + TypeORM + SQLite); Nest+PG есть только в `PROJETS/whalelounch/tglead-api-gateway`. Обернуть мозг в Nest-модуль ~1–2 дня, но репо на ESM, Nest CJS-ориентирован. Риск V5: «пакет = Nest-модуль» привяжет plug-in'ы к фреймворку. Мнение лида (владелец просил): PG — да, как носитель/проекция журнала, это совпадает с «полноценной основой»; NestJS — да возможен, но ради хоста, не хранилища. Вердикт: независимая, двусторонняя, **несрочная** дверь; триггер — второй транспорт или второй разработчик.

## 3. Вопросы владельцу (уровень концепта, ≤3)
- **В1:** Чего тебе не хватает СЕГОДНЯ — **читать** (быстро искать, фильтровать, группы) или **писать** (надёжно, много, несколько агентов)? → решает, ставим ли PG-проекцию при запуске.
- **В2:** Что ты хочешь сделать с мозгом через месяц, чего нельзя на файле? (один реальный эпизод)
- **В3:** Если через год уносить мозг в другой движок — уезжает файл, дамп или контейнер?
- Дефолты, если «ок»: §1 как есть (Д2 — потомки + вид; Д3 — роль+тип даром); §2 «СЕЙЧАС» 4 шага; PG-проекция — при живом запуске; NestJS — позже.

## 4. Опровергающий тест до любой стройки (critic)
5 реальных записей, из них 2 группы (`part-of`), и 3 чтения, одно — по входящим рёбрам. Если всё проходит без переключателя Д2/Д3 и без БД → стройка PG/Nest не нужна сейчас. Требует запуска мозга (рука владельца).
