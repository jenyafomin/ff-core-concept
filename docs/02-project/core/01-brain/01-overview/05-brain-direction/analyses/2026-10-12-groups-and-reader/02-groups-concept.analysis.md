**Вопрос-цель:** «Как сделать группы/объединения/перелинковку такими, чтобы ячейку можно было быстро перевести на другую абстракцию, не теряя её тождество и историю, — на существующих примитивах мозга?»

## 1. Модель: группа = ячейка, членство = ребро

Одна мысль: **группа — обычная запись мозга, а «быть в группе» — ребро `part-of` с паспортом.** Перелинковать = погасить старое ребро и поставить новое. Ячейку никто не копирует и не переносит — меняются только связи. «Уйти на другую абстракцию» = группа сама становится членом другой группы (группа групп).

Что уже есть в коде (проверено):

| Нужно | Есть? | Где |
|---|---|---|
| Быть в нескольких группах | Да: `part-of` = `many` | `packages/brain/src/domain/genesis.ts:218` |
| Погасить ребро (не удалить) | Да: `link {status:'retracted'}`; паспорт (author/created_at/confidence) сохраняется | `packages/brain/src/domain/validate-act.ts:691`, `:699-713` |

Вывод: **модель владельца ложится на примитивы без нового ядра.** Не хватает двух вещей: пакетного акта «перевесить N рёбер разом» и входящего обхода для вида «группа и всё вокруг».

## 2. Сценарий владельца по шагам

«Задача → много тем → объединил в группу X → вокруг X появились другие»:

1. `record task T` («Запустить бизнес Y»).
2. `record note A,B,C,D` с `edges:[part-of → T]` — четыре темы висят на одной точке (п.2 зерна).
3. Владелец: «объедини A,B,C в группу "Маркетинг"» →
   - `record note X` «Маркетинг» (+ `part-of → T`) — новая ячейка-группа, своё имя (п.4);
   - для A,B,C: `link part-of → T status:retracted` + `link part-of → X`.
   Итого 1 + 6 актов. Тождество A,B,C не тронуто (id те же); старые рёбра живы как `retracted` с автором и датой.
4. Рядом с X появляются Y «Продажи», Z «Финансы» — тоже `part-of → T`. Теперь у T два слоя: группы и под ними темы (п.5 — «ячейка ушла на абстракцию»).
5. Позже «Маркетинг» становится частью большей группы «Рост»: `link X part-of → R`. Сам X не меняется — он просто получил родителя. Это и есть группа групп.
6. Тема в двух группах сразу: `link B part-of → Y` — `many` позволяет.

**Что видно в истории («git для смысла», п.21):** журнал хранит каждый акт: кто, когда, какое ребро погасил, какое поставил. Можно ответить «где была тема B в сентябре» — свёрткой журнала до даты. Сейчас такого запроса в чтении нет (это будущий вид, данные уже есть).

## 3. Три вида группы

| Вид | Суть | Механизм | Когда |
|---|---|---|---|
| **Тег/категория** | много групп на ячейку | `part-of` (`many`) или `about` | **СЕЙЧАС** — работает |
| **Папка** (одна родительская) | дерево | отдельный предикат с `one`, напр. `u:filed-in` | **СЕЙЧАС как соглашение, не как ядро** — см. дверь Д1 |
| **Умная группа** (правило, сохранённый запрос) | членство вычисляется, не хранится | запись-линза с `spec` = запрос `find` | **N+1** — `lens.ts` знает только `compose`; нужна вторая форма `query` |

Рекомендация: начать с одного вида — **ручная группа через `part-of`**. Папку как отдельный вид не вводить: «главная группа» — это свойство вида (какое ребро рисуем деревом), а не данных. Умная группа — после живого прогона ручной (правило гардрейла «N+1 только после живого N»).

## 4. Хранение и «интерпретация в файлы»

Сейчас мозг = **один файл-журнал** (append-only) + свёртка в памяти + блокировка одного писателя. Это уже то, что просит п.9: «один файл, легко развивается» — история бесплатна, схема растёт данными (type-def / predicate-def).

| Вариант | Плюс | Минус |
|---|---|---|
| Журнал-файл (сейчас) | история = истина, портируемо (V5), ноль инфраструктуры | запросы по истории и большие объёмы — свёрткой в памяти |
| SQLite как **индекс** поверх журнала | быстрые входящие/исторические запросы, всё ещё один файл | второй источник — только как пересобираемая проекция |
| Postgres | много писателей, сеть | сервер, миграции; сейчас один писатель — не нужно |

**Рекомендация (не ADR):** журнал остаётся истиной; любая БД — только пересобираемый индекс за портом `store-port.ts`. Postgres — когда появятся параллельные писатели, не раньше.

**Вид для владельца (п.8):** генерируемые md, как `render.mjs` ночи (`questions/2026-10-11-how-memory-grows/maps/render.mjs`): по каждой группе — файл `groups/<label>.md` со списком членов, родителей и последних перевесок. Вид = чтение, файлы не правятся руками, пересобираются командой.

## 5. Ценности и односторонние двери

- **V2 Тождество** — укрепляет: перегруппировка не трогает id ячейки.
- **V6 Реляционность** — укрепляет: членство = полноправное ребро с паспортом. Риск: гасить N рёбер поштучно → полуперевешенное состояние при сбое (нет атомарности).
- **V4 Витальность** — пустая группа должна остывать (`cold`), а не висеть вечно.
- **V1 Читаемость** — группа даёт дешёвую грань («Маркетинг, 12 тем»), не вскрывая всех.
- **V3 Доверие** — перевеска агентом = предложение (`proposed`), не факт.
- **V5 Суверенность** — журнал + md-вид портируемы.
- **V7 Согласие** — группа не должна смешивать области (`in-scope`) разных людей; enforcement пока не подключён.

**Односторонние двери (что потом не поменять):**
- **Д1. Кардинальность предиката членства.** Ядро запрещает `many→one`. Если введём «папку» как `part-of` с `one` — не вернуть. Поэтому: `part-of` оставить `many`, «одного родителя» делать отдельным предикатом или видом.
- **Д2. Что значит `part-of`.** Сейчас «часть целого» общее. Если группировка, состав задачи и иерархия проектов сольются в один смысл — потом не развести по старым рёбрам. Решить до первых реальных данных: группировка = `part-of` или свой предикат (`u:grouped-in`).
- **Д3. Группа — тип или роль?** Отдельный тип `group` — запись навсегда; «группа = любая ячейка, на которую указывают» — гибче. Рекомендую роль (без нового типа): метаморфоза «тема → группа» без смены типа.
- **Д4. Журнал как истина.** Переход на БД-как-истину ломает историю-бесплатно; держать БД только индексом.

## 6. Минимальный срез для живого показа

1. Читатель в шлюзе предлагает кандидатов: `find` по теме → список ячеек.
2. Владелец одной командой: «объедини 3,5,7 в "Маркетинг"» → агент делает 1 `record` + 2N `link` (пока без пакетного акта — честно, N малое).
3. Скрипт-вид пересобирает `groups/Маркетинг.md` (члены, откуда пришли, кто/когда перевесил).
4. Владелец открывает md и видит: группа, её члены, старая привязка погашена, но видна в истории.

Нового кода ядра не нужно; нужен скрипт-вид и протокол команды агенту. Пакетный акт и умная группа — следующий шаг.

Итог: решение-рекомендация — группы на `part-of` (many) + retract, группа = роль ячейки; до первых данных владельцу закрыть Д2 (смысл предиката) и Д3 (тип или роль); пакетная перевеска и умная группа — задачи N+1 в плане.
