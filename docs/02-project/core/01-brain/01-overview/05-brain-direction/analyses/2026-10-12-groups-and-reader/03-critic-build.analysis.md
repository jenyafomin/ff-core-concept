# Критик стройки: читатель над логом в живом шлюзе

- **Status:** draft · **Owner:** jenya.stasik@gmail.com · **Date:** 2026-10-12
- **Потребитель:** builder / лид · **Поглощает:** ничего
- **Вопрос-цель:** что сломается при встраивании читателя в живой шлюз + рестарте, и какой минимальный безопасный срез с критериями приёмки?
- **Опора:** w5-links/02-fable-adversarial-now (A1, A3, A4), 03-step0-probe-metrics, w6-gate/01-final-critic; правила git-working-tree-safety, security.

## 1. Топ-5 рисков
1. **Рестарт обрывает ход и живой бот.** Этот разговор идёт под шлюзом; рестарт убивает ход и фоновое. Главный чекаут шлюза грязный (docs/00-states/state-08-*), значит `git checkout/merge` в него запрещён. Landing только через ветку и отдельный worktree; переключение pm2 и рестарт делает владелец.
2. **Секреты в контекст модели (A1).** Фильтр «после» бесполезен: пароли уже были в модели и в trace. Нужен регэксп по строкам БД ДО выдачи, плюс deny-by-default для строк с URI-кредами и словами пароль/password/token/ключ.
3. **Пересланное третьих лиц (V7).** В пробе отсеивалось суждением модели. Метаданных forward в схеме пробы нет. Без поля-признака фильтровать нечем: сначала проверить схему, при отсутствии признака исключать эвристикой и фиксировать как известный пробел.
4. **Читатель пишет/мутирует БД шлюза.** Живая WAL-БД: писатель-читатель на одном файле, блокировки, случайный DDL. Только `mode=ro` (лучше копия/снимок), без миграций.
5. **Scope-creep: группы + Postgres сразу.** Рестарт один; три новых слоя в одном срезе = откат нечего локализовать. Плюс адрес `gw:topic<N>/m<id>` не резолвится без chat id (A3), а метка открыто/закрыто неизвестна (A4).

## 2. Срез v0
**Входит:** одна функция-читатель (отдельный пакет/скрипт, не правка ядра шлюза): БД ro → окно 14 дней, direction=in → фильтр секретов и forward → кандидаты с адресом (чат+топик+message id, резолвимым) → вывод карточки без копий текста сверх короткого заголовка; три метки владельца (открыто · закрыто · не напоминать); вызов командой владельца, не автозапуском.
**Не входит:** группы/перелинковка (после: нужен живой прогон читателя и ответы по меткам); Postgres/граф-БД и автогенерация файлов (после: решение хранилища = ADR); авто-запись в мозг; фоновый цикл; правки core шлюза.
**Сегодня:** читатель + тесты + ветка. **После:** группы, затем хранилище.

## 3. Критерии приёмки
1. Тест: открытие БД с `mode=ro`; INSERT/UPDATE/DDL падает.
2. Тест: строки с `amqp://user:pass@`, `пароль: …`, `token=` не попадают в выход и в логи.
3. Тест: пересланные исключены; без признака forward строка исключается (fail-closed).
4. Адрес резолвится обратно в ровно одно сообщение; тест на два чата с одним топиком.
5. Трассировка и выход не содержат тела сообщений сверх лимита N символов.
6. `git status --porcelain` главного чекаута шлюза до и после идентичен; работа в worktree.
7. Читатель не стартует сам; нет изменений в обработке `out`/сессий (тест регрессии шлюза зелёный).
8. Рестарт: последним шагом, действие владельца, с планом отката (прежний cwd pm2 + прежний коммит), вне активного хода.

## 4. ADR
Нужен лёгкий ADR (интеграция шлюз↔память: граница, ro-доступ, формат адреса, fail-closed секреты) — это «key integration» по docs-standard. Хранилище (PG/файл) вынести в отдельный ADR позже; для v0 хватит ADR + критериев выше.

Итог: решение — v0 только читатель ro с фильтрами и адресом; группы и PG после; ADR интеграции до кода.
