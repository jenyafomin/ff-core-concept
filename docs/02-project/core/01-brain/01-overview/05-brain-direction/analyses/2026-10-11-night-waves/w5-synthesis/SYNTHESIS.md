## 3. Архитектурные решения — РЕКОМЕНДАЦИЯ владельцу (не ратифицировано; источник `../w2-direction/architect-doors.analysis.md`)
1. **Области.** Общий корень над `personal` не нужен: читатель в `readers.json` держит список областей, видимость поднимается ≤2 уровня (`validate-act.ts:140-158`). Поставить корень над существующей областью сегодня нельзя (нет пути записи ребра на ребёнке, `schemas.ts:71-75`). До первой записи фиксируем только: slug `personal`, `kind: personal`, без родителя. **Проектные области без родителя не заводить**; компании потом — новыми областями, проекты сидятся сразу с `member_of`. Настоящие двери: slug, kind, pii-флаг. Опция на будущее: owner-only операция «прикрепить область» с предпросмотром «эти N записей станут видны X» (триггер — первая реальная просьба).
2. **Два дома задачи → вариант A (CQRS).** Смысл задачи — `task` в мозге; БД шлюза держит только исполнение (конверт, парковка, попытки) с **ключом = id мозга**; итог хода лупа — акт с ребром к задаче. Единственная дверь: ключ = id мозга, закрыть до первого прогона лупа. Не противоречит ADR-0016 D1 после F6 («правда в памяти, горячая копия локально»).
3. **Выученные числа лупа → гибрид C.** Текущее значение — состояние в БД (пересобираемо); каждое изменение правила/коридора и значимый сдвиг — акт `decision` в мозге (ровно резерв `persistence_class` ADR-0017). Сейчас решать нечего; триггер — первое выученное число.
4. **Рамка направления — 6 слов** (+связь V6, +сигнал; согласие — внутри «читателя»: кто + какие области + для какой цели).
