## 1. CRITICAL — противоречия внутри набора

**K1. C x B: все предложения агента навсегда остаются `proposed` -> S1 = 0.**
C п.6: после «да» писать `record{id, fields:{status:"open"}}` — «станет open». Но `validate-act.ts:577-579`: `initiative:"agent"` -> `proposed`; при апдейте `status = existing.status`; активация только при `req.initiative==='owner'` (`:578`), а `:356-358` отдаёт `WRITE_DENIED` читателю с agent-authority (чат-путь всегда agent, B §3 со ссылкой на `access.ts`). Статус записи НЕ меняется; меняется лишь `fields.status`. Следствия: (а) B jq (`status=="active"`) не считает ни одного захваченного через C дела -> S1 = 0 при реально работающем захвате -> ложный «провал» либо слепой гейт; (б) C §5 «считаем только после да» невыполнимо кодом. Ответ на вопрос задания: `find(status:"open")` ПОКАЗЫВАЕТ proposed (`read/find.ts:109` сравнивает `fields.status`; `visibleRecords` режет только `retracted`, `access.ts:268`) — гипотеза C «не видна» ложна, в обратную сторону: список дня 0 смешает подтверждённое и непринятое, различить по ответу `find` нельзя (`toFindItem`, `find.ts:39`, показывает `fields.status`, а не статус записи).

**K2. C: `src:"offer"` — не существует как верхнеуровневый ключ.** `validate-act.ts:315` + `RECORD_KEYS:75-78` -> `BAD_REQUEST unknown key 'src'`. Работает только как `fields.src` (неизвестные поля сохраняются, `:216`). Сам C пишет «src:"owner"» «обычным путём» — агент, следуя тексту, получит отказ на КАЖДОЙ записи. Есть реальный ключ `source` (provenance, формат валидируется `:336`) — путаница с `src`. Это ломает смоук шага 6.

**K3. A: команда просмотра export не работает.** A §4: `ff-brain export personal > /tmp/brain-export.json; grep ... /tmp/brain-export.json`. CLI печатает `{ok,path,count}` (`stats.ts:56`, B §1), данные в отдельном файле 0600. Все grep дадут 0 попаданий = ложное «чисто» именно на стоп-кране приватности. Бонус: перенаправление/копия в `/tmp` плодит нешифрованную копию личной памяти. Должно быть: `p=$(... export personal | jq -r .path)`, grep по `$p` (как в B §2).

**K4. B x C: две противоположные развилки дня 3.** B: S1<3 -> ветка A «push НЕ включаем». C §5: S1<3 и ответ «забываю» -> «включить M-19 (push)». GATE уже содержит третье правило (:28). Плюс C п.14 включает pull-список в начале КАЖДОЙ сессии с дня 0: это раздувает R-agent (B: ветка push требует R-agent непустых <=1 -> недостижимо), и загрязняет S3 («вспомнил благодаря памяти» принесён агентом, не запрошен). Нужно ОДНО правило дня 3, зафиксированное до старта.

## 2. CONCERNS

- **C1. A x C: цитата в `why`.** C: «в `why` цитата слов владельца <=10 слов» — владелец диктует «позвонить Андрею…»; цитата протащит имя/секрет в необратимый журнал (стирания нет). Прямо ломает правило A (имена=0). Цитата допустима только после обезличивания, либо отказаться от неё (прибор src и так в `fields.src`).
- **C2. Длина протокола.** Сейчас 13 пунктов/52 строки. A (+4 строки+3 класса), C (п.2 перепис. 6 буллетов, п.3, п.6, новый п.14), F (+2 правила, дублируют существующие п.7/8/11 «dedup/queued/не говори записал») -> ~80 строк, 16+ пунктов, из них 4 условных механизма («предлагай», «2 отказа подряд», «<=3 пункта», «один раз за сессию»). Агент в рабочем топике 56 (проектная работа, 18 сообщений/нед) будет предлагать «Записать как дела?» после каждого хода — шум; кап «2 отказа» это лечит лишь постфактум. Слияние обязательно.
- **C3. Дубли пунктов.** F 0.2(а) повторяет п.7/8/11; F 0.2(б) «ключи/пароли» = A «секреты». Один пункт на смысл.
- **C4. «Всегда» x C.** C п.6 делает «да» в чате единственным тормозом после «Всегда»; F 6.2a подталкивает нажать «Всегда» на record+link сразу в смоуке. Правило пишется в `FF/.claude/settings.local.json` (gitignored глобально, ok), но оно общее для ВСЕХ топиков и обычных сессий Claude Code в этой папке (F row 2) — в том числе этой. Развилка D4 владельца не решена; не решать за него в смоуке.
- **C5. Запуск делается хрупче.** Шаги в день X: шаги 1-7 + F шаг 0 + 1б (репетиция восстановления с `ff-brain-serve` в чужом home — гипотеза F «не проверено», возможны конфликты сокета/pm2) + 6.2a + 6.6 + 6.7 (`pm2 stop ff-brain` на живом боте). Лишнее в первый день: 1б-репетиция и 6.7. Остановка мозга в смоуке = риск забыть `pm2 start`.
- **C6. B: имя тула и R-agent — гипотезы** (`mcp__ff-brain__find` в транскриптах «проверить день 0»); часовой пояс владельца не выбран (по умолчанию UTC -> «день» сдвинут, S1_days искажается для Москвы/другого пояса ночью).
- **C7. A x B: export-проверки A (день 1,3) увеличивают счётчик файлов export, который B берёт как R-owner.** B вычитает «свои гейт-прогоны», A не оговорён. Пометить.
- **C8. F row 1:** 0.1 «фикс дедупа НЕ летит» — корректно (факт из git), но «записи защищены idem» верно только если у голосового есть `messageId` (F сам помечает гипотезой). Для голосового (основной ввод владельца!) это главный сценарий — вынести в смоук явно (6.6 уже есть; сделать обязательным, не «по желанию»).
