## 3. Черновик дерева областей — 3 варианта (OPTION SET, не решение)

Контекст-ограничения [факт: BRIEF]: область = узел + рёбра; стартуем с одной областью `personal`; родителя у существующей области позже НЕ добавить; имя и kind зафиксированы.

### Вариант A. Плоско: `personal` и всё внутри как теги/рёбра
```
personal
  (проекты = узлы типа project внутри personal, связь рёбрами)
```
- Плюс: ничего не фиксируем лишнего; соответствует «одна память для всего». Дёшево.
- Минус: потом права/согласие (V7: `visibility`, `readers`) по компаниям придётся делать политикой, а не границей области; «чужая» компания (дубайская команда) живёт в личной области. Если позже компания должна стать родителем — **нельзя** (родитель не добавляется). Вынос = миграция.
- Подходит, если компании — просто контекст, а не отдельные юр./доступные границы.

### Вариант B. Две ветки: `personal` + `work` (+ проекты внутри)
```
root?                          (нужен ли общий корень — Q2)
  personal   (music-video, ff, agents-manager, claude-setup)
  work       (cardex, ga-rentacar, profit-swimming)
```
- Плюс: делит личное и рабочее — главная граница согласия. Дёшево раздвинуть читателей.
- Минус: `work` — это не компания, а категория; компании внутри (Cardex vs ga-rentacar — разные бизнесы/люди) смешаны. Если нужен корень сверху `root`, его надо завести сейчас, иначе `personal` уже не получит родителя.

### Вариант C. Компании как родители: `personal` + по области на компанию
```
personal            (music-video, ff, agents-manager, ...)
company:cardex      (deal-flow, work-org, forms-sidebar)
company:ga-rentacar (rental-balance, ingest, fleet, customers)
company:<profit-swimming?> / <partner>
```
- Плюс: граница = реальные люди и данные; для ga-rentacar PII изолируется на уровне области; соответствует вашей формулировке «companies → projects».
- Минус: самый «дорогой» односторонний вариант — нужно знать точный состав компаний и имена **сейчас**; ошибка = переименование невозможно. Cardex и ga-rentacar могут быть одной компанией (или нет) — я не знаю.
- Нужен общий `root`, иначе `personal` и компании — несвязанные деревья (Q2).

**Мой наклон [гипотеза, не решение]:** стартовать A или B (минимум фиксаций) и держать проекты узлами с ребром `part_of`, чтобы вариант C достраивался СВЕРХУ новым `root`, а не требовал родителя для `personal`. Это нужно проверить на ADR-0017: допускает ли модель «новый корень над существующими областями» — иначе A/B ведут в ловушку. Это вопрос к analyst/архитектору, не ко мне.
