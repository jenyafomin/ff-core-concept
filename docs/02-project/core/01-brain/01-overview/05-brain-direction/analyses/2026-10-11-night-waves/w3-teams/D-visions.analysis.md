## 0. Главный вывод (одной мыслью)
Все видения используют ОДНУ рамку из 6 слов (**источник → запись → связь → читатель → действие → сигнал**) и один субстрат (журнал ADR-0016). Они спорят не о том, «что строить», а о том, **какое слово сейчас узкое место** — т.е. какой шов рвётся первым:

| Видение | Узкое слово | Какой шов рвётся (altitude §1: «разрыв непрерывности») |
|---|---|---|
| A. Петля | связь + сигнал | ход↔ход, агент↔агент: работа не компаундит |
| B. Протез внимания | действие (момент) | память↔владелец: записано, но не вернулось вовремя |
| C. Кухня в память | запись (надёжность) | шлюз↔сам себя: дубли, обрывы, две правды |
| D. Секретарь итогов (своё) | источник | разговор↔журнал: захвата нет (0 сообщений в «МОИ ЗАДАЧИ», `launch/GATE-7days.md:10-12`) |
| Ø. Нулевое (честный контроль) | — | шов не в памяти, а в шлюзе |

Аналогия: **одна бухгалтерская книга, четыре аудитора**, и каждый уверен, что дыра в своём месте — один в проводках (секретарь), другой в отчётах руководству (протез), третий в сверке отделов (петля), четвёртый в самой кассе (кухня). Неделя данных = ревизия, которая покажет, где дыра на самом деле. Поэтому видения не надо выбирать сейчас — надо **мерить так, чтобы каждое могло проиграть**.

## 1. Видения

### A. «Петля» — память = субстрат петель (агенты и лупы читают то, что писали прошлые ходы)
- **Тезис:** ценность памяти — в замкнутых петлях: запись, которую прочёл НЕ автор, и от этого изменилось действие. Направление = петля, иначе склад (altitude §3).
- **Оптимизирует:** компаунд — каждый ход дешевле прошлого; агент не переспрашивает.
- **Петля (6 слов):** итог хода агента → `decision`/`task` с label → `in-scope` проект + `derived_from` сообщение → агент следующего хода/другого топика (читатель вправе по `readers.json`) → не переспрашивает, продолжает → счётчик «агент нашёл и использовал» (агент-читатель).
  Вторая: тик лупа (S1, `../w1-scout/loops-x-memory.analysis.md` §3) → акт итога → `in-scope` проект → следующий тик/ретро → следующий шаг без `loop_run` → `find` по проекту восстанавливает ход.
- **Куда ложится:** память (ядро), шлюз (протокол агента, G-05), лупы agents-manager (`loop_runs=0`, G-29), cardex work-org.
- **Ценности:** укрепляет V3 (провенанс итогов), V6 (рёбра несут ценность), V1 (label = дешёвая грань). Напрягает V4 (раздувание записями агентов, S6), V7 (агент пишет о коллегах — M-02), V3 (агент пишет `active` от имени владельца — M-05).
- **Односторонние двери:** записи агента в неудаляемый журнал до `hard_erase` (M-01); ключ задачи в БД шлюза = id мозга (architect Q2-A) — до первого прогона лупа.
- **7 дней подтвердят:** ≥1 петля замкнута ≥3 раза (запись прочитана не-автором → действие изменилось) и её можно назвать 6 словами. **Опровергнут:** S1 выполнен, замкнутых чтений 0 (склад).
- **Первый дешёвый шаг:** вопрос дня 7 «что изменилось от этой записи?» + счётчик агент-читателя (цена ≈ 0, данные уже копятся).

### B. «Протез внимания» — память сама приносит то, что владелец забывает
- **Тезис:** хранение вторично; узкое место — момент возврата. Владелец не будет звать `find` (привычки нет), значит pull-тест даст ложный провал (altitude R3; `GATE-7days.md:35`).
- **Оптимизирует:** внимание владельца — минимум «я забыл», минимум усилия на вспоминание.
- **Петля:** слова владельца / итог хода → `task` с `due`/`why`/salience → `in-scope personal` или проект → push при входе в топик / утром (читатель = владелец; видимость: личное не в групповой топик) → дело сделано/закрыто/отложено → доля push-пунктов, по которым было действие; S3 «вспомнил благодаря памяти».
- **Куда ложится:** шлюз (push-линза «контекст хода» G-09/M-19, live egress G-26, пульт G-27), память (вторая линза после `lens:prompt-compose` — lens-as-data M-26), music-video («где остановились»), personal.
- **Ценности:** укрепляет V1 (нужная грань в нужный момент), V4 (salience/остывание становятся ОБЯЗАТЕЛЬНЫМИ — без них push = шум). Напрягает V3 (push устаревшей записи действует на ложной ячейке), V7 (личное всплывает в групповом топике), V1-масштаб (линза перебирает все акты, M-32).
- **Двери:** почти нет — push обратим. Полудверь: семантика salience (если будет полем в паспорте — пол `_CARDS-2026-07-08.md`).
- **7 дней подтвердят:** владелец сам почти не зовёт `find` (CL-025), но на принесённое реагирует ≥3 раза (сделал/закрыл). **Опровергнут:** принесённое игнорируется/раздражает ИЛИ владелец сам активно спрашивает (тогда узкое место не момент).
- **Первый дешёвый шаг:** без кода — строка протокола «при первом сообщении дня в топике дел — покажи 1–2 несущих дела» (утренний список уже в PLAN-v2 §3). Порог дня 3 (DIRECTION-v2 патч 4): S1 провален → включаем этот шаг.

### C. «Кухня в память» — память доказывает себя на собственной инфраструктуре шлюза (F6, R1–R6)
- **Тезис:** ближайший реальный пользователь памяти — сам шлюз (промпт-слои, привязки, джобы, дедуп). Он пишет каждый ход, не зависит от привычки владельца, и его боли (G-20/G-21) — самые регулярные. Личная память — второй жилец того же дома.
- **Оптимизирует:** одна правда о системе, устойчивость к рестартам/дублям, заменяемость шлюза.
- **Петля:** `/prompt` владельца → `sys:prompt-layer` → `applies_to` топик → `lens:prompt-compose` каждого хода (читатель = шлюз) → промпт собран из памяти → shadow `equal:true` 7 дней. Будущая (R4): ход → `sys:job` → `in-scope` топик → шлюз после рестарта → ход продолжен → 0 потерянных ходов.
- **Куда ложится:** шлюз (главное), ядро памяти, лупы (луп-как-данные ADR-0018).
- **Ценности:** укрепляет V2 (один id у слоя/джоба), V5 (шлюз заменяем, правда переносима), V3 (кто и когда менял промпт). Напрягает V4 (операционные события раздувают журнал — architect Q3 «гибрид»), V1 (бюджет 150 мс, M-32), надёжность («мёртвый мозг при флаге ON», M-41).
- **Двери:** R5/R6 требуют CAS/fencing (M-33); второй писатель до `i2:`-идем (M-36, **1-WAY, если опоздать**).
- **7 дней подтвердят:** shadow без расхождений, 0 случаев «мозг упал — бот замолчал». **Опровергнут:** diff>0 или падения мозга бьют по живому боту → лестница R1.1+ стоп.
- **Первый дешёвый шаг:** уже идёт — держать shadow и считать diff (G-01). Ничего не добавлять.
- **Честное напряжение:** M-45 — «за 2 дня выросли ADR, двери, R1, F6, а ценности для человека 0». Видение C говорит «это И есть ценность»; критик — «это бегство от проверки пользы». Разводится только раздельным мерилом (§3).

### D. «Секретарь итогов» (своё, сильнее туду) — агент сам записывает итог содержательного разговора
- **Тезис:** туду, диктуемый владельцем, — новая привычка (0 сообщений за 7 дней). А существующая привычка есть: проектные разговоры в топиках (18 сообщений в 56 — все проектные, altitude R4). Значит источник — не владелец, а разговор; память ловит решения/договорённости, а не задачи. Это ответ на боль cardex «договорённости теряются между чатами» (`../w1-scout/projects-x-memory.analysis.md` 1.2).
- **Оптимизирует:** стоимость захвата → ~0 для владельца.
- **Петля:** содержательный ход в топике проекта → `decision` (`initiative: agent`, статус `proposed`) одной строкой → `in-scope` проект + `derived_from` id сообщения → владелец при возврате в проект / агент другого топика → не пересказывает контекст заново → счётчик «возврат без пересказа» + доля принятых владельцем `proposed`.
- **Куда ложится:** cardex work-org (лучший), agents-manager (итоги инцидентов), FF (решения сессий — уже делается вручную хендоффами!), ga-rentacar (решения S1–S9, без PII клиентов).
- **Ценности:** укрепляет V6 (итог связан с проектом и источником), V1, V3-провенанс (`derived_from` на сообщение). **Сильно напрягает** V3 (агент пишет от имени владельца — M-05, отравление пересказом S4) и V7 (имена коллег в итогах — M-02, скан имён не ловит).
- **Двери:** записи агента о третьих лицах в неудаляемый журнал (M-01 не построен) — **самая опасная дверь из всех видений.** Поэтому `proposed` по умолчанию — не опция, а условие.
- **7 дней подтвердят:** `decision`-записей больше, чем `task`, и их читают из ДРУГОГО топика/дня. **Опровергнут:** владелец отклоняет >50% предложенных итогов или они не читаются (S6-сигнал).
- **Первый дешёвый шаг:** строка протокола «в конце содержательного хода предложи 1 строку итога как `proposed`» (это и есть дефолт Q6 altitude) + в RUNBOOK — только в топике проекта без чужих имён.

### Ø. Нулевое видение (контроль, не цель)
Память пока не нужна; настоящая боль — надёжность шлюза (дубли/обрывы/«фикс ждёт деплоя», три поколения записей, `../w1-scout/gateway-backlog.analysis.md` «Топ-3»). Подтверждается, если за неделю S1–S3 провалены, а жалобы владельца — про бота. Шаг: `pm2 stop ff-brain` (данные остаются, `GATE-7days.md:35`). Держим как фальсификатор, чтобы провал не прочитали как «надо ещё инфраструктуры».

## 2. Сквозное, не луп (V4–V7 + доверие): когда строить — по триггеру, не по календарю
Эти вещи не имеют своей петли; они — свойства любой записи. Строить, когда сработал триггер; до этого — только форма (она уже есть).

| Сквозное | Ценность | Что уже есть | Триггер «строить сейчас» | Какое видение дёрнет первым |
|---|---|---|---|---|
| Стирание `hard_erase` | V7 | шов в движке, мозг не выставляет (M-01) | ПЕРВОЕ из: запись о третьем лице · вторая область кроме `personal` · ga-rentacar · конец недели 1 (решение владельца п.7) | D (итоги с именами) |
| Согласие enforcement (`use≠read`, referent) | V7 | форма, `test.fails` (M-04) | второй ЧЕЛОВЕК-читатель в `readers.json` ИЛИ первый внешний ингест (F-D, M-47) | D, затем проекты |
| Затухание / `cold` / salience | V4 | статусы, `test.todo` (M-14) | выбран push (B) ИЛИ >50% `proposed` не прочитаны (S6) ИЛИ дайджест >N пунктов | B |
| Портируемость (`i2:`, манифест) | V5 | форма, `manifest_v:0` (M-36/38) | второй писатель/пакет (`pack:bt`) — **до** него, иначе 1-WAY | C |
| Доверие как policy-data | V3/V7 | «Всегда» в `localSettings` (G-08, M-25) | второй контекст с ДРУГИМ уровнем доверия (2+ топика пишут) ИЛИ первый случай записи из пересланного/веба | A, D |
| Наследование недоверия `derived_from` | V3 | форма D7 (S4) | агент пишет итог из пересланного/веб-текста | D |
| Слияние тождества merge/split | V2 | Reserved (M-11) | первый РЕАЛЬНЫЙ дубль (кандидат №1 — дубль голосового G-20) | все |
| Ребро first-class, сироты | V6 | хранится, не отбивается (M-12) | первая межпроектная связь | A |

Правило: если триггер сработал, а сквозное не построено — **стоп-кран для того видения, которое его дёрнуло**, не для всей памяти.

## 3. Где видения сходятся → делать при любом выборе
1. **Дубль голосового закрыть ДО флагов** (G-20 + M-17 фолбэк `replyToMessageId`). Дубли пишут двойные записи в неудаляемый журнал → ломают сигнал КАЖДОГО видения. Проверить, жива ли ветка `fix/p2-voice-dedup-ingress` (`/tmp`!).
2. **Два счётчика читателя + вопрос дня 7 «что изменилось от этой записи?»** (владелец / агент / шлюз-shadow отдельно). Это единственный способ, чтобы провал одного видения не засчитался как провал всех (M-45, altitude R1).
3. **Агент пишет как `initiative: agent`, по умолчанию `proposed` для `decision/person/note`** (M-05). Нужно A и D, защищает B и C.
4. **Старт только `personal`, проекты без родителя не заводить** (architect Q1) — совместимо со всеми.
5. **Протокол: `find` со `scope`, идемпотентная вставка** (M-18); **секрет-сканер проверить** (S8) — сквозная гигиена.
6. **Shadow R1 держать** — бесплатный сбор доказательств для C, не мешает остальным.
7. **Restore из бэкапа проверить** (M-39) — неудаляемый журнал без проверенного отката опасен в любом видении.

## 5. Зёрна идей

### От проблем шлюза
- **G-20 дубль → первый реальный эпизод тождества (V2).** Не только чинить: каждый пойманный дубль — живой случай для merge-правила M-11 и для переписи загорания (M-46). Счётчик «idem отбил дубль» = доказательство двери данных №3 на реальности.
- **G-20/G-23/G-24 «фикс ждёт деплоя» → первые данные бумажного баг-трекера `pack:bt` (F5).** Вместо выдуманного сценария — реальные висящие фиксы шлюза как `task` (`implements task@1`) со статусом «в коде / ждёт land / развёрнут». Одна петля кормит и C (кухня), и F5, и ритуал «окно рестарта» (кандидат в скилл, правило «3-й раз вручную»).
- **G-07 кнопка → кнопка = акт согласия.** Каждое нажатие «разрешить запись» — это решение доверия; если их считать (сколько, по какому топику, какой инструмент), trust-as-policy-data (M-25) вырастет из истории, а не из головы («автономия зарабатывается историей», L-M8). Цена: счётчик в логе, без кода мозга — гипотеза, проверить, что шлюз уже логирует решения апрува.
- **G-21 фон гибнет → «итог волны в память».** Правило `orchestration-sync-under-gateway.md` п.3 велит спасать результаты из `journal.jsonl`; если агент пишет итог волны актом, восстановление = `find`, а не археология. Это видение D, применённое к самим оркестрациям (FF уже делает это вручную хендоффами).
- **G-17 тупик стоп-листа → эскалация как `proposed`-акт.** Запрос к владельцу «разреши X» — запись с ожиданием (контракт «ожидание-парковка» лупа); сходится с G-07 в один шов «просьба → решение владельца → правило».

### От концептов
- **Push = вторая линза.** `lens:prompt-compose` уже живая линза-данные; «контекст хода» — та же форма. Если B победит, lens-as-data (M-26) получает второй экземпляр → обобщение законно (правило ≥2 случаев).
- **Один протокол «предложение → проба → тап»** для правил лупа, типов садовника и слоёв промпта (S3) — три клиента одного механизма.
- **Перепись загорания как станция лупа** (S7): метрики недели записать актами — тогда сама проверка видений становится данными памяти.
- **«Два продукта» лупа** (исполнитель vs секретарь-подготовщик, loops §1 п.8) зеркалит A vs D: возможно, это одна развилка на двух уровнях.

## Что эта модель НЕ покрывает
- Цену привычки владельца (видение может быть верным, но неделя — слишком короткой для новой привычки).
- Качество выдачи `find` (петля замкнута, но шумит).
- Возможность, что победят два видения на разных читателях — модель это допускает, но визард должен не заставлять выбирать одно.
