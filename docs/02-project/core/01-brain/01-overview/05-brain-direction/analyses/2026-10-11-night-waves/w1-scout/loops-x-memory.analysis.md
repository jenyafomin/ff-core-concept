## 1. Модели лупа и открытые решения

Три слоя истории, каждый частично заменяет прошлый:

| Дата | Модель | Суть | Статус |
|---|---|---|---|
| 2026-07-31/08-01 | **Граф-луп, durable tick** | Следующий шаг = строка `loop_run` в SQLite (`nextStep`), внешний тикер, CAS-чекпоинт; швы `ILoopStep / ILoopFinalizer / ILoopBudgetGuard`; «луп-как-файл» (Definition vs Instance). `handoff.md` §1–2, §7 | Stage 1 живой; под тиком **плейсхолдер** `ChecklistLoopStep`; «continuation-Job — метафора, луп изолирован от очереди IJob» |
| 2026-09-25 | **Общество персистентных ролей** (ADR-0014) | Роль ≠ Луп; «персистентность = идентичность + память, а не живой процесс»; топик = витрина, event-журнал = шина; 7 слов словаря (Триггер, Роль, Команда, Тема, Ход, Память-роли, Пульт) | active; ROADMAP: гейт-0 первым |
| 2026-10-04…09 | **Луп = процесс из фаз, заданный данными** | Один диспетчер-КОД + плоские плейбуки; 7 контрактов (задача с досье, карточка фазы, конверт, ожидание-парковка, политика, метка доверия, диспетчер); 3 слоя A конституция(код) / B конфиг(YAML в git) / C выученное(числа в БД в коридорах); граф из 9 станций (разведка → пул → приоритеты → разбор → план → исполнение⟲тесты → проверка → слияние → обучение) | review; кода нет, `loop_runs = 0` |

**Открытые решения (из `handoff.concept.json` и сводов):**
1. Шаг 0: ключи (файлы настроек уже на GitHub в `dev` и `feat/phase-0-unblock`) — **сменить** ключи; решение за владельцем (`07-step0-keys/Response.md`).
2. A: свод 5→1 = черновик **ADR-0018 «луп = данные»** (+ пустые колонки `projectKey, parentLoopId, rootLoopId, budgetCap*, waitingOn, originKind`).
3. B: канал «ответ владельца → луп» + проверка «точно от владельца».
4. C: первый живой прогон ($1, таймер, стоп) + ретро. D: загрузчик — только после C.
5. Правка правил: «лид готовит с пробой, владелец тапает»; авто для «строже» — позже и конфликтует с ADR-0014 §4 (нужен новый ADR).
6. Молчание владельца: «ждём, необратимого не делаем» (реком.) vs «по сроку действие по умолчанию».
7. «Дёргать меньше» vs «делать больше»; доделывать ли проекты без тестов; первый проект для бумажного прогона (реком. crm-server).
8. Развилка критика: возможно, это два продукта — «исполнитель с проверкой» и «секретарь-подготовщик».
9. Исследовательский/идейный луп не имеет настоящей проверки → «принято владельцем» (прямо касается памяти — см. §3).

**Метазакон (компаунд, `~/.claude/rules/compound-engineering.md`):** о теме написано ~30 файлов, 0 живых запусков; «не создавать новых ресерчей до `loop_runs ≥ 1`». Баланс хендоффа: открыто +4 / закрыто 2. Это прямо ограничивает и наши ночные волны — каждая идея ниже обязана нести «первый дешёвый тест», а не новый разбор.

## 2. Где лупу НУЖНА память / где памяти НУЖЕН луп

### 2.1 Лупу нужна память (потребности, найденные в доках)
| # | Потребность | Где сейчас | Дыра |
|---|---|---|---|
| L-M1 | **Состояние между ходами** (под шлюзом каждый ход = свежий `claude -p --resume`; непрерывность несут ДАННЫЕ) | SQLite `loop_run` + континуация (`handoff 07-31 §1`); «Память-роли поверх многих тем» (ADR-0014, wave1) | Память роли описана, хранилища нет; `loop_run` — изолированный мир, не общий граф |
| L-M2 | **Самопродолжение** (следующий шаг = строка) | `nextStep` в БД; Reflexion-память `reflections[]` (feedback→вход следующего тика) | `reflections[]` — маленькая локальная память без тождества, провенанса, затухания |
| L-M3 | **Досье задачи = единица контекста** («хранить анализ или держать контекст», 02-conceptual-tests п.11) | Описано как примитив | Физического дома у досье нет; оно ≈ узел с рёбрами + `source/confidence` |
| L-M4 | **Самоэволюционирующий конфиг** — слой C «выученное» (оценки цены/времени/успеха, веса) + версии правил + «было/станет/проба/откат» | `05-self-evolving-config`: числа в БД, снимок в git | Это по форме «акты с провенансом и откатом», т.е. то, что мозг уже умеет (append-only, `retracted`) |
| L-M5 | **Ключи/step0** | Уроки: секреты ушли в git | Для памяти: **секрет не должен попасть в запись** (PII-гейт D9 сканирует телефоны/email, не токены — гипотеза: проверить паттерны ключей) |
| L-M6 | **Трассы верификации** («готово» подтверждает другой источник, критерий заморожен ДО работы, журнал намерений «собираюсь → сделал») | Контракт 1 и принцип 8 | Журнал намерений = append-only акты; трасса «проверил кто/чем» = провенанс. Нет единого места |
| L-M7 | **Метка доверия на тексте, не смывается пересказом** (контракт 6, «2 из 3»: личные данные + чужой текст + канал наружу) | Только в проекте шлюза | В мозге `author/owner/referent/source` есть, но «недоверенное-после-пересказа» (транзитивность) — нет (`derived_from` лишь форма, D7) |
| L-M8 | **Автономия зарабатывается историей** (контракт 5) | История исходов задач | Нужна память об исходах по ролям/проектам — естественный клиент мозга |
| L-M9 | **Ретро/обучение** (станция 9 графа) и **пул задач** с факторами | Пул — «правда в БД, файлы генерируемые» | Пул задач ↔ `task` в genesis-типах мозга: риск ДВУХ домов |

### 2.2 Памяти нужен луп
| # | Функция памяти | Какой луп-механизм подходит | Статус в ADR |
|---|---|---|---|
| M-L1 | **Садовник типов** (v1: candidate → active, слияние/расщепление) | Диспетчер-код + карточка фазы + проба на прошлых актах + тап владельца (ровно протокол правки правил) | ADR-0016 D5/D11: только ФОРМА, поведение в 1c |
| M-L2 | **Консолидация / LOSE-NOTHING** | Периодический плейбук «разведка → пул → разбор → проверка» над журналом | не построено |
| M-L3 | **Затухание → cold** (V4) | Тикер по расписанию, коридор в слое B, откат | не построено (`test.todo`) |
| M-L4 | **Перепись загорания (census)** — прибор ≥4/7 ценностей на реальных эпизодах | Станция «обучение/ретро» графа | трек открыт, не заменён синтетикой |
| M-L5 | **Счёт гейта 7 дней** (`GATE-7days`) | Счётчик в слое C + порог «≥N» как условие | вручную |
| M-L6 | **Очередь записи/outbox/бэкап/дедуп-friction** (D10, D12) | Это уже малый луп внутри сервиса; нужен «признак жив» и «почему не запущено» из контракта 7 | в ADR есть вручную |
| M-L7 | **Ингест документов, `stale`-пересчёт производных слоёв** | Ожидание с парковкой + диспетчер перечитывает состояние | отложено |

## 3. Зёрна идей (seed · spark · ценность · цена · первый дешёвый тест)

Цена по правилу компаунда: мало/средне/много.

**S1. Луп-сброс «тик пишет в мозг»**
- Seed: итог каждого хода лупа (что сделал, что проверил, чем) пишется АКТОМ `task`/`decision` + рёбра `derived_from`/`in-scope`, а не только строкой `loop_run`.
- Spark: `loop_runs = 0` и память `n=0` — оба «замка без данных»; первый живой луп даёт ПЕРВЫЕ реальные эпизоды для переписи (закрывает общий разрыв «0 реальных данных»).
- Ценности: V3 Доверие (provenance), V1, V6. Цена: средне. Вес: много (одним прогоном закрываем два пустых трека).
- Тест: первый «$1-прогон» (C шагов шлюза) → после него `find` по `in-scope: project` возвращает ≥3 акта, и по ним можно восстановить, что было сделано, без `loop_run`.

**S2. Мозг как «Память-роли» ADR-0014**
- Seed: «память роли» = `scope` вида `personal`/`project` + узел `role` с рёбрами `in-scope`; роль читает только свои + общие области.
- Spark: «100 агентов = 100 строк памяти, а не 100 процессов» — ровно D4 (области = узлы M:N).
- V2, V5, V7. Цена: мало (тип `role` — `u:` или `core`?). Вес: много.
- Тест: на бумаге — взять 2 существующих топика шлюза (скажем 56 «brain» и 65 «агенты») как две роли; проверить, что их память разделима без поля `tenant`.

**S3. Правка правил как акты (протокол «проба + тап» = протокол садовника)**
- Seed: один и тот же шаблон «предложение → проба на прошлых актах → карточка ≤5 строк → тап → версия → авто-откат» обслуживает и правила лупа, и `type-def candidate → active`.
- Spark: логика из `05-self-evolving-config` уже совпадает с 1c-плана; зачем два механизма.
- V4, V3, V7. Цена: мало (переиспользовать), вес: много (избегаем второго пути активации).
- Тест: проигрыш на бумаге 1 реального candidate-типа (напр. из первой недели запуска) через этот шаблон; если не ложится — нашли расхождение.

**S4. Метка недоверия, не смываемая пересказом → `derived_from` с наследованием**
- Seed: `derived_from[…]` в D7 получает правило: производная запись наследует «недоверенность» источника; видимой остаётся до явного подтверждения владельцем.
- Spark: контракт 6 лупа («trifecta») и D7 мозга описывают одно и то же с разных сторон.
- V3, V7. Цена: средне (поведение отложено в 1c). Вес: много (защита от отравления через память).
- Тест: синтетический день «шумный»: запись с `source.kind=web` → пересказ агента → `find` должен отдать метку недоверия; сегодня — fail (`test.fails`).

**S5. Журнал намерений = первый-класс акт `intent` (двухфазная запись)**
- Seed: «собираюсь → сделал» для необратимых действий хранится как два акта, второй `retracts`/`fulfills` первый; мозг даёт идемпотентность D10 лупу бесплатно.
- Spark: гейт-дубль шлюза (`gateway-dup-message-bug`) — тот же класс, что «не сделать дважды после падения».
- V3, V2. Цена: мало. Вес: средне.
- Тест: имитация дубля сообщения: два вызова `record` с одним `(conversationId, message_id)` дают 1 акт (D10) — уже должно работать; расширить тестом на пару intent/done.

**S6. Бюджет внимания / WIP-лимит для самой памяти (anti-bloat)**
- Seed: «производить не быстрее, чем потребляется» применить к записи: лимит proposed-актов агента на ход/день; непринятые `proposed` остывают в `cold` автоматически.
- Spark: два корня prior-art ↔ V4 (не раздувать базу) + гейт-7-дней.
- V4, V7. Цена: мало (счётчик + порог в слое B). Вес: средне.
- Тест: в первую неделю запуска посчитать долю `proposed`, не прочитанных ни разу; если >50% — лимит нужен.

**S7. Перепись как станция «обучение» графа**
- Seed: `census` — это не отдельный проект, а станция 9 графа-лупа памяти: еженедельный плейбук читает журнал и считает загорание V1–V7.
- Spark: «прибор против плоскости» ↔ «ретро» с неудаляемыми метриками.
- V1–V7. Цена: средне. Вес: много.
- Тест: ручной прогон на 3–5 реальных эпизодах первой недели; метрики записать АКТОМ (не файлом) — тогда сама перепись становится данными.

**S8. Секретный сканер в PII-гейте (урок step0)**
- Seed: расширить D9: паттерны ключей/токенов (длинные base64/hex, `sk-…`, `ghp_…`, `-----BEGIN`), а также запрет записывать значения из env.
- Spark: ключи уже ушли в git (07-step0-keys); память — второй канал утечки, причём «лог — истина», удалить нельзя (нужен `hard_erase`, V7).
- V7, V5, V3. Цена: мало. Вес: много.
- Тест: unit `record` с телом `{"note":"ghp_…16 символов"}` → отказ с читаемым кодом (гипотеза: сейчас пройдёт — проверить `admission.ts:47,56`).

**S9. Кросс-проектная очередь через мозг, не через общий БД-список лупа**
- Seed: «общий список задач» портфеля — это проекция графа `task`+`in-scope`; БД шлюза хранит ТОЛЬКО исполнение (конверт, ожидание), а смысл задачи — в мозге.
- Spark: два дома для `task` (пул лупа и тип `task` мозга) — прямое нарушение doc-tree закона 2 (один дом).
- V2, V6. Цена: средне. Вес: много, но нужна развилка владельца.
- Тест: сопоставить схему `task` genesis с полями «досье» (замысел, критерий готово, источник готово) — сколько полей не хватает.

**S10. Диспетчер-код мозга: «признак жив» и «почему не запущено»**
- Seed: у сервиса мозга есть то же, что требует контракт 7: heartbeat, лимит перезапусков, объяснение отказа записи.
- Spark: D12 уже имеет `SERVICE_DOWN` и outbox; это половина контракта.
- V4, V3. Цена: мало. Вес: средне.
- Тест: из RUNBOOK прогнать kill -9 сервиса и проверить, что outbox дозаписывает после рестарта и `/health` объясняет, что было.

## 4. Конфликты и напряжения с ADR-0016/0017

| # | Напряжение | Обе стороны | Что решать |
|---|---|---|---|
| T1 | **Два «дома» для задач/досье.** Лупу нужны пул/досье/ожидания (`loop_run`, БД шлюза), мозгу — `task`/`decision` (D4/D5). | ADR-0016 D1: «`unit_event` шлюза — журнал решений шлюза, мозг не он; моста не строим». Луп-доки: «правда в БД, файл генерируемый». | Развилка владельцу (см. S9): смысл задачи — в мозге; исполнение — в БД шлюза с ссылкой по `id`. Иначе «моста не строим» бьёт по лупу. |
| T2 | **Эволюция правил vs «агент не активирует типы».** Луп-доки: сам улучшатель предлагает и применяет «строже» авто позже. ADR-0016 D11: агент заводит `candidate`, но не активирует/сужает/сливает. | `05-self-evolving` п.5 «авто-применение узкого класса “строже”»; ADR-0016 D11 + UNIT-SPEC §9. | Согласованный протокол S3; явное «строже» ≠ расширение типа. Нужна формулировка, что авто-«строже» к типам не применимо. |
| T3 | **Слой C выученных чисел в БД vs «лог — истина».** Слой C: числа в SQLite + снимок в git. ADR-0016 D3: всё — акты журнала. | Дубль механизмов хранения. | Либо числа слоя C — акты `observation`, либо граница: «мозг не хранит операционные оценки лупа». Требует решения (гипотеза: второе проще). |
| T4 | **Конституция A = код, вне зоны записи лупа** vs **реестр типов в журнале актами** (D3). | Тип/предикат пишется агентом через мозг; правила лупа — нет. | Хорошая асимметрия: genesis/конституция в коде, `type-def` — актами. Но явно записать, что `type-def` ≠ конфиг лупа (разные границы доверия). |
| T5 | **Эволюция формата/версий:** лупы-как-файлы с `defRef`, версии карточек (YAML в git) vs `name@major` + upcaster (ADR-0017 D1) и «journal не переписывается». | Две схемы версионирования. | Свести: карточка фазы — это `u:`/`pack:` тип со своим `@major`? Или оставить YAML вне мозга. |
| T6 | **Доверие/владелец.** Луп требует «команда точно от владельца» (иначе оркестратор = инъекция). ADR-0016 D8: читатель выводится сервисом из env, самозаявление не принимается. | Совпадает по духу; но шлюз обязан выставлять env и для лупа, и для мозга одним механизмом. | Один «шов принципала» (ADR-0010/0011); следить, чтобы второй не вырос. |
| T7 | **Порядок / компаунд.** Луп-доки сами остановили новые разборы до `loop_runs ≥ 1`. Мы (память) тоже не имеем реальных данных. Ночная оркестрация добавляет документы, а не прогоны. | compound-engineering п.5: «уровень N+1 — после одного живого прогона N». | Каждая зерно-идея ночных волн должна идти с «первым дешёвым тестом»; свод — один, заменяет, не добавляется. |
| T8 | **Реальные эпизоды vs синтетика.** У лупа и памяти одна болезнь — 0 прогонов. | Раньше выбрано: «перепись на реальных». | S1: один прогон лупа может быть источником реальных эпизодов (но согласие V7 не форсится движком; PII не ингестить автономно). |
| T9 | **Фоновое vs синхронное.** Луп живёт на внешнем тикере; под шлюзом фон гибнет.
