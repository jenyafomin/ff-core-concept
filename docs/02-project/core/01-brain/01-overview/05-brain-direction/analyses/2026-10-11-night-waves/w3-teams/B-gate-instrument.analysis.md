## 1. Что реально отдают stats и export
- `ff-brain stats` → `GET /v1/stats` (`bin/ff-brain.ts:48`) → `{ok,total,by_scope,by_type}` (`contract.ts:424-429`). Считает `visibleRecords` (`service/stats.ts:23-25`), а тот выкидывает ТОЛЬКО `retracted` (`read/access.ts:268`). **`proposed` и `superseded` входят в `by_type.task`.** Значит `by_type.task` из GATE:18 завышает S1. Дней и статусов в stats нет. Вывод: stats для гейта не годится, только как sanity-проверка «мозг жив».
- `ff-brain export personal` → файл `brain-export-<ts>.json` (0600) с `{exported_at, reader, records[NodeView], lenses}` (`stats.ts:35-56`); CLI печатает `{ok,path,count}` (`ff-brain.ts:65`). NodeView (`contract.ts:343-359`): `type`, `status` (запись: active/proposed/superseded; retracted не бывает), `fields.status` (задача: open/doing/blocked/done/dropped, `genesis.ts:150`), `fields.done_at`, `meta.author`, `meta.created_at`, `meta.updated_at`, `initiative?`.
- Побочный эффект: каждый export пишет новый файл в папку export. Читает только то, что видит CLI-читатель по `readers.json cli` (`readers.ts:28`); если cli-привязка без scope `personal` — получим тихие нули при `ok:true`. Сверка: число `record ok:true` в транскриптах (уже в GATE:18).
- **Истории нет:** export — срез. «Когда стало done» не восстановить, если не задан `fields.done_at` (свободное поле `date()`, `genesis.ts:155`, необязательное). Правило: время закрытия = `done_at`, иначе `meta.updated_at` (гипотеза: правка после done сдвинет его вперёд).

## 2. Точный счёт (проверен сухим прогоном на фиктивном export из 7 записей, `/tmp/gt/ex.json`; stats-стиль дал 6, точный 4)
Окно `[A,B)` = день 0 … день 7, границы в локальном поясе владельца (в export время UTC; пояс — вопрос владельцу, по умолчанию UTC).
```
jq --arg a "$A" --arg b "$B" '
 [.records[]|select(.type=="task" and .status=="active" and .meta.created_at>=$a and .meta.created_at<$b)] as $t
 | {S1_tasks:($t|length),
    S1_days:([$t[]|.meta.created_at[0:10]]|unique|length),
    S1_burst:([$t[]|.meta.created_at[0:16]]|group_by(.)|map(length)|max),
    S2_done:([$t[]|select(.fields.status=="done" and (.fields.done_at//.meta.updated_at)>=$a and (.fields.done_at//.meta.updated_at)<$b)]|length),
    proposed_not_counted:([.records[]|select(.type=="task" and .status=="proposed")]|length)}' "$FILE"
```
Файл: `p=$(node packages/brain/dist/bin/ff-brain.js export personal | jq -r .path)` (путь берётся из ответа, литерал в команде не пишем). Retracted уже скрыты сервисом; `proposed`/`superseded` отсекает `status=="active"`. `dropped` не `done`.
- **S1** = число + `S1_days ≥ 4`. **Накрутка:** `S1_burst > 3` (больше 3 задач в одну минуту) → владелец глазами подтверждает «это реальные дела», иначе лишние не считаются. **S2** = задача из S1-набора со статусом done; done в ту же минуту, что создана, помечается флагом.
- **S3 не считается кодом:** export не знает, что было в выдаче `find` (чтения не логируются, см. §3). Пока: владелец называет label, лид сверяет по транскрипту, что запись была в ответе `find` ДО действия, и что автор записи != инициатор ответа «вспомнил» (вопрос: «что изменилось от этой записи?»). Критерий «изменила действие» — слово владельца, не метрика.

## 3. Два счётчика читателя
В коде у чтения нет трассы: `readPath` (`service/runtime.ts:~370`) пишет только отказы (friction). Читатель в `Reader.authority` (`contract.ts:561`), но чат-путь всегда `agent` (`access.ts:57,85,104`).
| Счётчик | Что это | Как считаем сейчас (без кода) |
|---|---|---|
| **R-agent** | агент сам делает `find`/`read` в рабочем топике | число tool-вызовов `find`/`read` brain-MCP в транскриптах топика за окно (grep по tool_use; точное имя тула — гипотеза `mcp__ff-brain__find`, проверить на день 0) + из них с непустым результатом |
| **R-owner** | владелец сам смотрит память | число файлов `brain-export-*.json` в папке export (ls, не открывая путь литералом: `dirname "$p"`) минус свои гейт-прогоны + его ответ на день 3/7 «заглядывал сам?» |
Смысл: R-owner высок, R-agent ≈ 0 → память как склад (владелец ходит сам); R-agent высок, S3 = 0 → агент ищет, но владельцу не помогает.
**Наименьший будущий прибор (НЕ строим до гейта, GATE:34):** на успешном `find`/`read` в `readPath` одна запись-счётчик по ключу (UTC-день, verb, reader.authority/kind) по образцу friction mode `count` (`friction.ts` шапка, `LIMITS.frictionPerDay=50`, `contract.ts:141`) + поле в stats. ~30 строк, аддитивно, без тел запросов (V7). Включать только если транскрипт-прокси даст спор на день 3.

## 4. Порог ветвления дня 3 (идём ли в push-контекст)
Логика: push помогает, только если есть что приносить. Если не пишет — причина во входе, а не в извлечении.
- **Ветка A (вход):** S1 < 3 задач ИЛИ задачи в 1 день → как в GATE:28: вопрос «почему не пользовался?», правка сценария. Push НЕ включаем.
- **Ветка B (push):** S1 ≥ 4 задач на ≥ 2 днях (захват идёт, темп ≈ 10/7) И R-agent с непустым результатом ≤ 1 И S3-кандидатов 0 → с дня 4 включаем push-контекст (агент в начале хода сам приносит открытые задачи). Режим фиксируем в счёте: S3 считается раздельно «по запросу» / «принесено».
- **Ветка C:** остальное → ждём день 7 без изменений.
Пороги — предложение; владелец утверждает до старта (Q8).
