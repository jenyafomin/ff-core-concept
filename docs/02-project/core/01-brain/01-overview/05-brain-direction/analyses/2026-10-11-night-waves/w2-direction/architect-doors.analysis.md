## Q1. Дерево областей: можно ли позже поставить корень НАД существующими?

### Как устроено в коде (факты)
1. Область создаётся **только** сидом genesis при старте: `writeGenesis` пишет `buildScopeAct`, а если узел уже есть — **молча пропускает** (`packages/brain/src/domain/schemas.ts:71-75`). Т.е. добавить `member_of` в сид для уже существующей области = тихий no-op.
2. Через `record` область не правится: `scope` — не-запись (`validate-act.ts:116`, комментарий `:461`).
3. Через `link` тоже нет: у узла-области нет рёбер `in-scope` → `from.scopes` пуст → `SCOPE_DENIED` (`validate-act.ts:697-699`; узел не legacy, т.к. несёт meta — `to-act.ts:329`).
4. Ребро `member-of` хранится **на ребёнке** (`to-act.ts:264-270`), видимость идёт **вверх** от областей записи, не дальше 2 шагов (`validate-act.ts:140-158`, `MEMBER_OF_HOPS = 2`).

**Вывод:** «новый корень над `personal`» сегодня **невозможен** — для этого нужно ребро на уже существующем ребёнке, а пути записи нет. Новый корень сам по себе — сирота, он ничего не видит.

### Но: что на самом деле необратимо
| Что | Почему | Насколько страшно |
|---|---|---|
| **slug** (`scope:<slug>` = id, `to-act.ts:260`) | на него ссылаются рёбра `in-scope` всех записей (V2) | **ДА**, настоящая дверь |
| **kind** (`personal/company/project`) | `personal` включает гейт и «впекается» в `readable_by` каждой записи при записи (`validate-act.ts:99-105, 593-595`; `pii-scope.ts:114-116`) | **ДА**: смена потом не исправит старые записи |
| **pii-флаг** | то же самое | ДА |
| **member_of существующей области** | нет пути записи (п.1-3) | ДА сегодня, но это **отсутствие API**, а не физика журнала: append-only движок примет акт-ребро от будущей owner-only операции [гипотеза: чтение кода, не тест] |
| **name** (подпись) | пути правки тоже нет | мелочь: в квитанциях показывается slug (`validate-act.ts:195-199`) |
| **область отдельной записи** | `record` с тем же id и новыми `scopes` переносит её; рёбра retract/add (`validate-act.ts:557-567`) | **обратимо** |

**Главная скрытая опасность «родителя потом» — не техника, а V7.** Добавить родителя = **задним числом расширить видимость**: все, у кого есть родитель, сразу видят старые записи ребёнка. Записи в `personal` защищены вдвойне — у них `readable_by` = только владелец, впечено при записи. Для `company`/`project` защиты нет.

### Нужен ли вообще общий корень? Нет.
Читатель в `readers.json` держит **список** областей (`ADR-0016:58`). «Видеть всё» = перечислить все области в биндинге. Корень — удобство, не необходимость. Плюс лимит 2 шага: `project → company → work → root` = 3 шага, такой корень проекты уже **не увидит**. Глубокие деревья противопоказаны в принципе.

### Безопасен ли старт только с `personal` для A/B/C?
- **A (плоско):** да.
- **B (`personal` + `work`):** да — `work` заводится потом как новая область без родителя; корень не нужен (см. выше).
- **C (компании-родители):** да — компании заводятся потом новыми областями; проекты сидятся **в момент заведения** с `member_of: [company]`. Условие одно: **НЕ заводить сейчас области-проекты (`ff`, `cardex`…) без родителя** (совпадает с M-08 в `../w1-scout/memory-backlog.analysis.md:37`).
- Рабочие записи, по ошибке попавшие в `personal` в 1-ю неделю, переносятся `record`-ом (видимость пересчитается, `validate-act.ts:593-595`). Старые версии остаются в журнале (append-only) — это V7-шрам, а не блок.

### Что владелец решает ДО первой записи (минимум)
1. **Слаг первой области = `personal`** (написание окончательное), `kind: personal`, **без родителя**.
2. **Обещание:** в первую неделю не сидим никаких проектов/компаний (ждут диктовки компаний).
Всё. Остальное ждёт: A/B/C, имена компаний, нужен ли `work`, корень (не нужен), `personal:true` в биндингах (`readers.json` — правится, не дверь).

### Опция на будущее (не для запуска)
Если родитель над существующей областью всё-таки понадобится — не «запрет навсегда», а owner-only `sys:`-операция «прикрепить область» с **предпросмотром видимости** («эти N записей станут видны читателям X»). Превращает одностороннюю дверь в обратимую с ценой «внимание владельца». Триггер: первая реальная просьба.

## Q2. Два дома задачи: пул лупа (БД шлюза) vs тип `task` мозга

Контекст: `task@1` в ядре (`genesis.ts:149-156`: status/due/priority/assignee/why/done_at). ADR-0016 D1 «`unit_event` ≠ мозг, моста не строим» (`ADR-0016:32`) — но позже принятый F6 сказал «**правда в памяти, горячая копия — локально в шлюзе**» (`ADR-0017:208`, `SYNTHESIS-f6.md:7`). Лупов пока 0 прогонов (`loops-x-memory.analysis.md:18`) → мигрировать нечего.

### Вариант A. Смысл — в мозге, исполнение — в шлюзе (CQRS: мозг = запись-истина, шлюз = горячая проекция + своё рабочее состояние)
Задача (замысел, критерий «готово», связи) = `task` в мозге. БД шлюза хранит **только исполнение**: конверт, парковка-ожидание, попытки, аренда — с ключом = id задачи из мозга. Итог хода лупа = акт (`decision`/исход) с ребром к задаче, не каждый шаг.
- V2 🟢 один id, одна задача. V3 🟢 провенанс и retract у смысла; 🟡 исполнение без провенанса мозга (норм, оно операционное). V5 🟢 задача переносима, шлюз заменяем. V6 🟢 рёбра (`in-scope`, `derived_from`, блокирует) живут в мозге.
- Цена: средне. Шлюз зависит от мозга → по F6 fail-open: локальный кэш + флаг `local|shadow|brain`.

### Вариант B. Всё в мозге: `task` + `sys:loop-step` (исполнение тоже актами, связь ребром)
- V2/V6 🟢 всё в одном графе. **V4 🔴** каждый шаг/перезапуск — акт в append-only журнале: раздувание. Надёжность 🔴: горячий путь лупа ждёт fsync мозга; нужен CAS (R4) раньше времени. `persistence_class: state/ephemeral` зарезервирован, не реализован (`ADR-0017:72-79`).
- Цена: много.

### Вариант C. Два дома с мостом по требованию (как сейчас в доках лупа)
- V2 🔴 дубли и расхождения; V3 🔴 какая версия правда?; V6 🔴 связи рвутся на границе. Нарушает doc-tree закон 2 и F6. Цена: мало сейчас, много потом.

**Рекомендация: A.** Единственная дверь, которую надо закрыть ДО первого прогона лупа: **ключ задачи в БД шлюза = id из мозга** (V2). Поля «досье» (критерий готово, источник готово) — либо необязательные minor-поля `task@1` (разрешено в пределах major, `ADR-0017:53-57`), либо `sys:loop-task` с `implements: ["task@1"]`; выбрать после сверки досье с `task@1` (тест S9 из `loops-x-memory.analysis.md:119`). B — не раньше реализации `persistence_class`.

## Q3. Выученные числа (слой C лупа) в БД vs «всё актами» (ADR-0016 D3)

| Вариант | Суть | Плюс | Минус |
|---|---|---|---|
| **A. Всё актами** (`sys:estimate`) | каждое обновление числа = акт | провенанс, откат бесплатно | V4 🔴 шум и раздувание; агент читает поток мелких изменений |
| **B. Только БД шлюза + снимок в git** | граница «мозг не хранит операционные оценки» | дёшево, быстро | V3 🔴 откат и «кто поменял» — вне мозга; второй механизм версий |
| **C. Гибрид (event sourcing решений, state-кэш значений)** | текущее значение — в БД (состояние, пересобираемо); **каждое изменение правила/коридора и значимый сдвиг** («было/станет/проба/откат») — акт `decision` в мозге | V3 🟢 там, где важно; V4 🟢; ровно повторяет резерв `persistence_class: state` vs `event` (`ADR-0017:75-77`) и протокол садовника (S3) | нужно правило «что считается значимым» |

D3 говорит про журнал **мозга** (`ADR-0016:39`), а не «каждый байт любой системы — акт»; прецедент — D1 (`unit_event` шлюза не мозг). Значит C не нарушает ADR.
**Рекомендация: C.** Сейчас решать нечего, кроме принципа: в слое C лупа пока нет ни одного числа. Триггер: первое выученное число.

## Q4. Рамка «направление = луп: источник → тип записи → читатель → какое действие меняется»

**Годится** — это замкнутый контур управления (pipeline к ценности): заставляет каждое направление назвать потребителя и эффект (компаунд-тест). Но в 4 словах три дыры:
1. **Связи (V6) и область.** Запись ценна не сама, а тем, к чему прикреплена: область, человек, проект. Находится она через рёбра. Без этого слова «тип записи» тянет в «склад заметок».
2. **Право/согласие (V7, policy).** «Читатель» без «вправе ли» = утечка. Лучше не отдельное слово, а уточнение: читатель = кто + какие области + для какой цели.
3. **Замыкание.** Нет слова «как узнаем, что действие изменилось» → луп разомкнут, гейт (S1–S3) висит отдельно.

**Предложение (6 слов):** **источник → запись (тип) → связь (область + рёбра) → читатель (кто вправе) → действие → сигнал (как меряем)**.
«Сигнал» — то, что потом считает прибор гейта; «связь» — где живут V6 и одна из дверей Q1. Затухание (V4) — свойство «записи», отдельного слова не нужно.

---

Итог: решение — Q1: корень над существующей областью сегодня невозможен (нет пути записи, ребро на ребёнке), но и не нужен (читатель держит список областей); старт только с `personal` безопасен для A/B/C при условии «не сидить проекты без родителя»; до первой записи владелец фиксирует только slug/kind `personal`. Q2: вариант A (смысл в мозге, исполнение в шлюзе; дверь — id задачи из мозга). Q3: гибрид C (значения — состояние в БД, изменения правил — акты). Q4: рамку расширить до 6 слов (+связь, +сигнал; согласие — внутри «читателя»).
