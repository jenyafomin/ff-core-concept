## Наказ (голос 2026-11-01)
Гибкий инструмент просмотра памяти с разных позиций: линзы-инструменты показа для ИИ и те же — для человека; интерфейс подстраивается под данные (карты, графы, процессы, типы).

## Свод (4 линзы сходятся, расхождение только в порядке)
1. **Цепочка:** вопрос → вид (структура) → форма (таблица/доска/таймлайн/граф/текст) → адаптер (MCP / Telegram / web).
   Данные: параметры вида + поле `layout`. Код: один исполнитель вида (с гейтом видимости), 4–5 готовых отрисовщиков, тонкие адаптеры.
2. **Линза одна на агента и человека.** Одна структура, разные адаптеры: агенту плотно и дёшево (V1), человеку обзор и переходы. «Раскрыть» у человека = `read` у агента. Человек видит ровно то, что агент (V3).
3. **«UI под данные» = данные сами объявляют форму**, а не ИИ пишет интерфейс. Тип объявляет: какое поле время, статус, связь → форма выводится (связи→граф, статусы→доска, даты→таймлайн, иначе таблица). ИИ только подбирает параметры. Главная работа — описание типов (шаг 2 гибкого роста), не вёрстка. Генерация кода UI = второй язык → не делаем.
4. **Индустрия делает так же:** Obsidian Bases, Notion, Airtable, NocoDB — «вид = параметры + layout». Брать готовым отрисовку (Cytoscape.js+ELK — граф, JSON Forms — правка, JSON Canvas — выгрузка). Платформы-хранилища (Notion/Airtable/Tana) — нет: ломают V2/V5.
5. **Мост «один ответ — два адаптера» есть стандартом:** MCP Apps (стабилен с 2026-01): инструмент отдаёт агенту данные, хост рисует человеку виджет `ui://`. Но Claude Code и наш Telegram-шлюз его не рисуют → это поздний адаптер, не первый. (Лицензии/зрелость из 01-research — не перепроверены.)
6. **Склад, а не витрина:** в памяти 3 записи. Реальные данные сегодня — дерево docs FF: ~1540 md вне `_log`, ~665 со `status`, ~150 с `type`, 45 concept.json; rentacar docs ~795 md (только структура). Без ПДн → первый тест на docs FF.

## Расхождение и как снято
research/abstract — «сразу общий виджет по `layout`, граф готовым»; critic — «сначала таблица/текст, окно только если не хватило». Мир, где оба правы = порядок: **A (таблица/текст двум адаптерам) → B (одно готовое окно)**.

## Шаги (потолок 3 рабочих дня, концепт → тест, не платформа)
- **A0 (владелец):** назвать 1–3 реальных вопроса, на которые сейчас не ответить за минуту, и что сделаешь с ответом. Без этого не стартуем (условие входа гибкого роста).
- **A1:** исполнитель вида: `group_by`/`fields`/`sort`/плоские фильтры + категории статусов (`proposed` = открытое) + `view_v` в ответе. Источники: память + дерево docs (frontmatter) как второй источник.
- **A2:** ответ на вопросы A0 — агенту (MCP `find`) и владельцу (/state) из ОДНОЙ структуры.
- **B:** только если таблицы мало — одно окно (Cytoscape граф или доска) локальной web-страницей.
- **Провал:** владелец за 3 дня не открыл вид сам; или форму приходится раскладывать руками (→ строить описания типов, не UI).

## Риски (analyst)
`group_by` строго после гейта видимости (иначе счётчики утекут) · вид над docs идёт мимо гейта памяти — для агентов других проектов ограничить областью · копия контракта в шлюзе (`topic-brain-reader.ts:59`) без теста на совпадение · HTTP для людей нет (только unix-сокет) · Telegram не вмещает граф.

## V1–V7 кратко
V1 ✔ плотность по адаптеру · V2 ✔ вид не трогает id · V3 ✔ одно и то же видят оба, вид подписан `view_v` · V4 ✔ `cold` — общая категория · V5 ✔ вид = переносимые параметры, не чужое хранилище · V6 🟡 граф рёбер — когда рёбер будет больше 0 · V7 🟡 вид не шире читателя; docs-источник — следить за областью.

## Волна 2 (тот же день) — ПЕРЕКРЫВАЕТ шаги выше
Наказ владельца (голос): заносим в память анализы проекта и систему аренды (документы уже на компьютере) → граф, смотреть, анализировать. Цель — **рабочая память для агентов и системы: предсказуемая, контролируемая, читаемая**. GraphQL — предложение. UI — **полностью генеративный** (как в агентных системах, AG-UI), не «выбор окна».

### Свод 4 линз (genui-research · architect · builder dry-run · critic)
1. **Генеративный UI — да, и это совместимо с контролем.** Во всех зрелых системах (A2UI Google, json-render, Adaptive Cards) ИИ свободно СОБИРАЕТ экран как декларативное дерево из закрытого каталога компонентов; код не генерирует никто. AG-UI (CopilotKit) = транспорт событий, не формат экрана; формат — A2UI. Граница: дерево ссылается на вид, данные приходят только через исполнитель вида с гейтом, без выражений/кода. → Наказ не сужаем: **окна закрыты, компоновка свободная**. Первым брать A2UI (сверить версию/Markdown-рендер на a2ui.org), json-render — запасной.
2. **GraphQL — не сейчас.** Обход графа уже есть (`read`: глубина ≤2, ≤50 узлов, фильтр рёбер, гейт на входе). GraphQL требует гейт на каждом резолвере (риск утечки V7), второй контракт (V5), свободный язык агенту (V1). Контроль даёт allow-list запросов = наш «именованный вид». Триггер: ≥50 рёбер + ≥2 программы-клиента с вопросом, не выразимым плоским видом; узко: только чтение, глубина ≤2, persisted queries, без интроспекции. ADR — тогда.
3. **Данные есть (dry-run, ничего не записано):** FF ≈1350 адресов, 2651 ссылок-рёбер; rentacar ≈780 (69% планы, frontmatter у 55). Типа «документ-адрес» нет → `u:doc@1` + ребро `u:refs`. Тело не заносим (устав: адрес+hash). Блокеры: лимит ≤3 записи/ход (нужен служебный путь `ingest-docs`), 472 битых ссылки FF, 697 длинных заголовков, 26 путей не проходят формат адреса. ПДн-сигналы в 40 файлах rentacar → rentacar только после вычитки и слова владельца.
4. **Обратимость (стирания нет):** песочница-область `import-ff`, ключ путь+hash (повтор = 0 дублей, новый hash = правка той же записи), метка партии, бэкап до заноса, пилот ~50 доков `05-brain-direction/`.

### Порядок (ПЕРЕКРЫВАЕТ A0–B)
1. **Импорт docs FF как адресов** (≈1,5 дня): SPEC → тип `u:doc` + `u:refs` → `ingest-docs` → пилот 50 → партия ≤150 → весь FF.
2. **Исполнитель вида** (≈2 дня): `group_by/fields/sort`/плоские фильтры + категории статусов + `view_v`.
3. **Спайк генеративного UI** (≈1 день): каталог 3 компонентов, ИИ собирает A2UI-дерево по вопросу; одно дерево → Markdown (Telegram) и React (web).
Позже: rentacar, GraphQL, MCP Apps.

### Критерий «память работает» (неделя)
