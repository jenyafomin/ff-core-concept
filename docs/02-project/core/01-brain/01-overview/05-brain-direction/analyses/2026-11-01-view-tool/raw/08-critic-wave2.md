Потребитель: лид волны + владелец (развилки). Поглощает: ничего (приложение к своду).

Рамка: наказ владельца не отвергаю, он сознательно расширяет. Ищу, КАК сделать безопасно. Факты ниже по трём прочитанным сводам; содержимое rentacar docs на ПДн я НЕ сканировал (не проверено).

## (1) Массовый импорт
- **CRITICAL.** Устав п.11: «стирания нет — записанное навсегда». ~800 rentacar md в docs, ПДн вероятны (клиенты, номера, договоры). Одна ошибка сканера = необратимая утечка в навсегда-хранилище. Это ровно то, что V7 «не форсится» (память: enforcement согласия не подключён).
- **CRITICAL.** Устав п.5/6: «пересказ файлов не идёт, только адрес+hash». «Занести полностью» совместимо ТОЛЬКО как адрес+hash+минимум метаданных (label, type, status из frontmatter), НЕ как тело. Если владелец понимает «полностью» как тело/выжимки, это прямое противоречие уставу; надо спросить одним вопросом.
- **CONCERN.** Массовая запись противоречит «≤3 record за ход» и «перед record — find». Нужен отдельный путь импортёра (не агент-в-ходе), иначе либо обход устава, либо 1500 ходов.
- Как безопасно: (а) отдельная область-песочница `import-ff` (слаг навсегда, но легко игнорируется читателями по умолчанию); (б) идемпотентность: ключ = путь+hash, повтор ничего не плодит, изменение файла = тот же id + новый hash (п.10); (в) dry-run со списком «что запишется» до записи; (г) rentacar: только пути-позитивный список (allowlist папок) + сканер ПДн, блок при любом срабатывании; первый прогон только docs FF; (д) пометка `import_batch` в записи, чтобы батч можно было скрыть из видов целиком (стирания нет, но видимость обратима).
- Остаточный риск: «скрыть» ≠ «стереть». Ограничить потолком первой партии (≤150 записей, только с `status` во frontmatter).

## (2) GraphQL сейчас
- **CONCERN.** Рёбер в памяти ≈0, записей 3. GraphQL выигрывает на обходе графа и произвольной вложенности; свод гибкого роста прямо запрещает вложенность/выражения в параметрах вида («иначе платформа»). GraphQL = эта платформа по определению. Плюс новая поверхность: интроспекция, глубина/стоимость запросов, обход гейта видимости на резолверах (классическая дыра: каждое поле проверяется отдельно).
- Провокация: боль «не могу найти/посмотреть» лечится исполнителем вида с плоскими параметрами + MCP. GraphQL ничего не покрывает, чего не покроет `find` с `group_by`, пока рёбер нет.
- Как безопасно (если владелец настаивает): схема-как-проекция исполнителя вида (резолвер = один исполнитель, гейт один, на уровне выборки, не поля), persisted queries, лимит глубины 2, только чтение. Триггер включения: ≥50 рёбер И вопрос, не выразимый плоским видом.

## (3) Генеративный UI и «второй язык»
- Граница, при которой это контролируемо: **ИИ отдаёт декларативное дерево, не код.** (а) закрытый каталог компонентов (table, board, timeline, graph, text, form), версия каталога `ui_v`; (б) дерево валидируется схемой, неизвестный узел = отказ; (в) узлы несут не данные, а ссылку на вид (`view_id`+параметры); данные тянет ТОЛЬКО исполнитель вида с гейтом, ИИ-вывод данных не содержит (иначе обход V7 и подмена фактов, V3); (г) действия: только навигация/раскрыть(read); записи через форму идут обычным record с утверждением владельцем; (д) никакого HTML/JS/выражений в дереве.
- Это не сужение до «готовых окон»: набор окон закрыт, компоновка свободна и порождается ИИ. Это честный компромисс: владелец получает генеративность, система сохраняет контроль. AG-UI/A2UI-подобный протокол как формат дерева, но без выполнения чужого кода.
- **CONCERN.** Генерация без живого вопроса = витрина над 3 записями. Рендерер в Claude Code/Telegram нет; web-страница локально = первый реальный адаптер, и до импорта показывать на нём нечего.
- Провокация: «полностью генеративный» тестируется дёшево: дерево от ИИ + 3 компонента, 1 день, без изменения хранилища.

## (4) «Память работает» измеримо (неделя)
1. **Использование:** ≥10 записей/адресов, которые агент использовал в ответе или владелец открыл (не записал), и ≥3 реальных вопроса владельца (A0) отвечены из памяти быстрее минуты.
2. **Прогнозируемость:** повторный импорт той же партии = 0 новых записей и 0 дублей; один и тот же вопрос двум агентам даёт один состав ответа (golden-снимок вида).
3. **Безопасность/читаемость:** 0 ПДн-срабатываний сканера в записанном; каждый ответ вида несёт `view_v` и виден человеку и агенту идентично.
Провал: владелец за 3 дня не открыл вид сам; или импорт дал >30% записей без пользы (шум в find).

## (5) Порядок и потолки
1. **A0 + песочница-импорт docs FF (≈1,5 дня, ≤150 записей):** владелец называет 1–3 вопроса; импортёр адрес+hash, dry-run, идемпотентность, область `import-ff`. rentacar НЕ трогаем. Стоп: хоть одно срабатывание ПДн-сканера или find замусорен.
2. **Исполнитель вида A1 с плоскими параметрами + ответ на вопросы A0 (≈2 дня):** по нему же MCP. Стоп: вопросы A0 не отвечены → чинить описания типов, не UI.
3. **Спайк декларативного UI (≈1 день, experimental):** 3 компонента, закрытый каталог, дерево ссылается на вид. GraphQL — отложен до триггера (≥50 рёбер). rentacar — после отдельного ПДн-решения (owner-gate) и, желательно, после enforcement согласия.

Что держится: «A → B» порядок свода, гейт видимости до group_by, плоские параметры.
