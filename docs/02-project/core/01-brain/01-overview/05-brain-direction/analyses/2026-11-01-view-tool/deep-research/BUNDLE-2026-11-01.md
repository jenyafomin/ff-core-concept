Вопрос-цель: какие решения интерфейса реально толкнут FF вперёд (человек и ИИ) и в каком порядке строить. Метод свода: сверка находок между собой; первоисточники я не открывал (см. §8).

## 1. Где линзы сходятся
Сила: ●●● три и больше независимых линз · ●● две · ● одна.
1. **Вид = запись памяти (ephemeral → pinned, версия, hash)** ●●●: R1 (1, 2, 5), R3 (ход 2), R4 (ход 1), R8 (ход 1). Хранится спека, намерение, запрос, а не пиксели; рендерер сменный. Оговорка: цельного примера «вид-запись в графе памяти» нет, R1 и R4 прямо пишут «это мой синтез».
2. **Каркас кодом, содержимое в слотах** ●●: R8 (граница), R1 (Jelly 5, слои 6), R2 (каналы фиксированы, правило данными), R3 (не генерировать на каждый вопрос). Числового порога «сколько менять» нет нигде (R8).
3. **Граф как надзор, не шар** ●●●: R4 (1, 3, ход 2), R5 (ход Б), R2 (без hairball). Окрестность ≤2 или срез с одним вопросом.
4. **Утренний дифф памяти / входящие одобрений** ●●●: R5 (А, Б, 1, 2, 4), R4 (ход 2), R3 (6: живёт регулярный отчёт).
5. **Бюджет внимания вместо «показать всё»** ●●: R2 (DOI, 4) и R7 (PPR, бюджет токенов, ход B) — одна идея для человека и агента. Миссии её не связали, это находка свода.
6. **Сводка кластера как грань** ●●: R7 (ход A, 3) и R2 (3, уровень Cluster). Для агента опора только GraphRAG, со слов.
7. **Лестница деградации Telegram** ●: только R6 (R3 косвенно: Atlas, Poke). Не сходимость.
8. **Грамматика состояния (stale→туман, confidence→насыщенность)** ●: R2. Остальные только косвенно (R4-3, R8-метки). Не сходимость.

## 2. Расхождения и детектор (е)
- **D1, сработал 3/3.** Изолят R5-А (авто-приём записей) против «агент пишет только proposed, человек подтверждает» (R8-5, R1-2, R4-1, устав, V7). Уверенность R5 высокая, развилка несущая (кто решает, что память истинна). Хитрая проверка: ② авто-принять всё = слепое «да», от которого R5 и лечит; ③ мир, где оба правы: авто-приём только класса «заметка сессии без пересечений», decision всегда человеку; ④ валюта: дешевле опровергнуть неделей «тени» (система только пишет, что приняла бы; владелец сверяет выборку). Вывод: в карту идёт только тень.
- **D2, конфликт с уставом.** R3 ход 1 пишет каждый эфемерный вид в память. Устав: ≤3 record за ход, не писать мусор, стирания нет (V4). Решение: эфемерные виды и счётчик возвращений живут в кэше исполнителя, в память только при «закрепить».
- **D3.** Закреплять по умолчанию (R8, R1) против «вид = намерение, перегенерировать» (R3-2). Оба правы: хранится спека с hash, перегенерация по явному «пересобрать». Вопрос 3.
- **D4.** «Полностью генеративно» (наказ) против R8 (каркас не генерировать, NN/g) и R1 (без следа нельзя). Оба правы: композиция свободна, каркас и каталог закрыты. Это уже линия волны 2.
- **D5.** R6 ход 2 оценён «мало», но Mini App требует публичного хостинга, а у шлюза HTTP для людей нет (только unix-сокет). Цена = много.
- **Дыры, не споры:** тождество вида при смене спеки (R1) · позицию записи на карте хранить или считать (R2).

## 3. ТОП-7 ходов
1. **Вид-запись: спека + hash, «закрепить»/«предложить».** Хороший вид закрепляется как закладка и не меняется, пока не нажмёшь «пересобрать». Опоры: R1-1,2,5; R3-2; R4-1; R8-1. Владелец узнаёт вид; агент стартует с ближайшего закреплённого. Цена: **средне**. Зависит: исполнитель вида, решение о тождестве.
2. **Каркас в коде, содержимое и правило стиля данными (A2UI, закрытый каталог, метка провенанса в рамке).** ИИ собирает экран свободно, рамка, доверие и действия наши. Опоры: R8; R1-5,6; R2 (ход 1). Цена: **средне**. Зависит: спайк, 7 контролей. Грамматику состояния откладываем.
3. **Утренний дифф + очередь «на твой взгляд».** Один экран «что изменилось с вчера»; причина отказа возвращается агенту (R5-2). Опоры: R5, R4-ход 2, R3-6. Цена: **средне**. Зависит: полнота журнала (не проверено), карточка Telegram.
4. **Аудит дефектов графа:** сироты, битые ссылки, без hash, открытые proposed. Опоры: R4-3, ход 2. Уже есть данные (472 битые ссылки, волна 2). Цена: **мало**. Зависит: импорт docs.
5. **Формат вида для агента:** incident-блоки, `detail=ids|labels|summary`, бюджет токенов, потом PPR. Опоры: R7-1,2,8,9, ход B; R2-4. Агенту дешевле и точнее. Цена: **мало** (эксперимент 1 день), потом средне. Зависит: 1350 адресов после импорта.
6. **Сводка кластера (digest) как запись.** Агент отвечает на «что у нас по X» без чтения 1350 узлов. Опоры: R7-A, R2-3. Цена: **средне**. Зависит: рёбра (в памяти сейчас 0) или scope-группы; доля глобальных вопросов.
7. **Лестница Telegram:** Rich Message → PNG → кнопка Mini App по полю `needs`. Опоры: R6 (1, 2, ход 1). Цена: **мало** для карточки, **много** для Mini App. Зависит: проверка лимитов Rich Messages.

## 4. Порядок поверх волны 2
Волна 2 (импорт 1,5д → исполнитель 2д → спайк 1д) остаётся. Меняется:
- **Вход:** A0 владельца (вопрос 1). Без него шаги 4–5 вслепую.
- **Эксперимент R7 (1д)** после импорта, параллельно исполнителю: 10 вопросов с золотыми ответами, 5 форматов. Результат определяет вывод исполнителя и `detail`.
- **Спайк 1д → 1,5д:** + каркас/слоты, метка провенанса, 7 контролей как приёмка.
- **Шаг 4 (1д):** тип вида-записи. Только после живого спайка (N+1 после N).
- **Шаг 5 (1,5д):** аудит дефектов + утренний дифф, Markdown-карточка. Авто-приём только тень.
- **Параллельно (0,2д):** один вызов Rich Messages, закрыть 4 неизвестных R6.
- **Позже, по триггеру:** digest (порог по логам вопросов агентов), грамматика+DOI (рёбер ≥50), Mini App (владелец хочет менять, не читать), линзы Cambria (первая реальная смена спеки).
- **Потолок:** волна 2 ≈4,5д + новое ≈4д = ≤9 рабочих дней. Стоп: владелец за неделю не открыл вид сам; форматы R7 не различаются.

**Новые требования SPEC:** R9 `u:view@1` (спека, `schema_version`, hash, `pinned`/`proposed`, эфемерное вне памяти) · R10 `detail` + бюджет токенов в `read`/`find` · R11 каркас/слоты/метка провенанса · R12 вид-аудит дефектов · R13 вид-дифф из журнала · R14 тень авто-приёма · R15 проба Rich Messages. Приёмка: AC7 три автопроверки (схема, канарейка, инъекция) · AC8 повторное открытие закреплённого = тот же hash · AC9 аудит показывает 472 битые ссылки.

## 5. Обязательные контроли в коде (R8)
1. Каталог = allowlist типов и пропсов, схема-валидация до рендера, неизвестное = отказ.
2. Фильтр видимости до генерации (генератор видит label/summary/адрес, не тела); исполнитель режет по читателю повторно.
3. Нет внешних URL в данных вида, текст как текст (без markdown-картинок).
4. Разрыв «текст записи → решения генератора»: выбор компонентов из доверенного намерения, тексты как помеченные данные.
5. Действия только из закрытого списка; запись из вида только `proposed`, подтверждает человек.
6. Лимиты: узлы, глубина, запросы, размер вывода.
7. Метка «собрано ИИ, hash, источники» рисует каркас.

В SPEC сегодня есть только п.2 (R7) и частично п.1 (R8). П.3–7 отсутствуют. Заголовки 1350 доков — недоверенный текст, п.4 нужен уже на спайке.

## 7. Вопросы владельцу (≤5)
1. Назови 1–2 вида, которые откроешь каждый день/неделю. Что первым в утренней карточке: ждёт ОК, протухло/осиротело или окрестность проекта? Достаточно читать или нужно менять (R3, R4, R6)?
2. Какие записи агентов ты готов не видеть вовсе: только заметки сессий или и decision (R5)? Согласен на неделю «тени» вместо авто-приёма?
3. Знакомый вид важнее свежести: закреплённый по умолчанию, «пересобрать» по кнопке? Принимаешь «полностью генеративно = свободная композиция внутри закрытой рамки»? (R8, D3, D4)
4. Нужна ли «пространственная память» (карта помнит, где что лежало), то есть хранить позицию? (R2)
5. «Строй» на эксперимент форматов R7 (1 день) и пробу Rich Messages (0,2 дня)?

## 8. Не проверено и дрейф (г)
**Не проверено по первоисточникам:**
- Я сверял находки между собой; веб не открывал. Большинство опор [С]/[Ч] (сниппеты, чужие слова).
- R2: шапка признаёт «страницы целиком не открывал», но пункты помечены [П]. Метки ненадёжны.
- Цифры без первичной проверки: удержание Lovable/v0/Bolt, закрытие Atlas, покупка Poke (R3); 93–97% одобрений и 13,6% против 89% (R5, источники расходятся); GraphRAG 2–3%, Zep +18,5%, Mem0 +2–2,6 (R7, со слов).
- R6: Bot API 10.1–10.3 и Rich Messages взяты из пересказа WebFetch. Лимиты, топики, клавиатура, drafts неизвестны.
- R8: EvoGenUI-Bench не читался.
- Данных удержания именно генеративного UI нет ни у кого (R3, R4, R6). «Нет продукта с дифом графа памяти» (R5) — слабое отрицание.
- В коде не проверил: что журнал ff-brain полон (R1, R5 это предполагают), рёбер 0, записей 3 (беру из волны 2).

**Дрейф:**
- Ход «вид = запись» предложен четырьмя линзами под разными именами (спека, намерение, запрос, hash). Свёл в один; не плодить четыре типа.
- Слово «линза» в R1 (миграции Cambria) сталкивается с «lens-as-data» проекта (candidate/gated, D9 не минтили). Брать reuse, отдельно не заводить.
- `view-style` (R2) = часть описания типов (шаг 2 гибкого роста), а не новый тип.
- Метки «Толкает: много» не откалиброваны; цена в §3 — мои.
- Критерий волны 2 («≥3 вопроса отвечены <1 мин») ресёрчем не оспорен. Риск: UI-инновации опередят, что владелец реально откроет. Страж: A0.
- Кода нет, «строй» не нарушен.

Итог: решение — строить по порядку волна 2 → эксперимент R7 → закреп вида → аудит и утренний дифф; автоприём только в тени, Mini App и грамматику состояния откладываем по триггерам; ждём A0 и 5 ответов владельца.

## Поправки critic (SHIP-AFTER-PATCH, 2026-11-01) — ПЕРЕКРЫВАЮТ разделы выше (см. CRITIC.md)
1. **D1 переформулирован:** устав уже разрешает агенту писать в проектные области сам (решение владельца 10-26). Вопрос владельцу: нужна ли очередь подтверждения для обычных записей — или только для decision? «Тень» авто-приёма — только при ≥20 записях агентов за неделю, иначе отменяется.
2. **D2 + AC8:** закреплённый вид несёт метку ДАТЫ ДАННЫХ (не только hash спеки), иначе устаревший вид выглядит доверенным (V3); потолок числа pinned (V4).
3. **Порядок стройки ≠ ТОП.** Первым — **аудит дефектов графа** (данные уже есть: 2651 ссылок, 472 битых) Markdown-карточкой в Telegram, за часы, без исполнителя и UI. Вторым — эксперимент R7 (формат вида для агента, 5 форматов × 10 вопросов) — единственный, кто измеряет пользу агенту. Затем импорт → исполнитель вида → спайк UI → вид-запись → утренний дифф (при 3 записях он пуст).
4. **Потолок реалистично 12–14 рабочих дней**, не ≤9: импорт 3–4 дня (ПДн-скан, бэкап/откат, служебный принципал, битые ссылки/длинные заголовки), контроли R8 п.3–7 в SPEC.
5. **Наказ «полностью генеративно» не растворять:** в спайке UI — один свободный эксперимент, где ИИ сам предлагает композицию из каталога без закрепа; смотрим, что он соберёт.

## Вердикт: SHIP-AFTER-PATCH
Порядок строить можно, но свод частично описывает несуществующий конфликт с уставом, занижает потолок и ставит «вау» не туда.

## Критично
- **D1 опирается на неверное прочтение устава.** Свод пишет «устав: агент пишет только proposed». Устав п.0 и «Решено 2026-10-26» говорят обратное: в проектных областях агент пишет САМ, владелец смотрит `/state`. Авто-приём уже решение владельца, а не изолят R5. Реальный вопрос другой: нужна ли вообще очередь proposed для обычных записей. Proposed есть только у видов (R9). Свод должен это исправить, иначе владельцу задают вопрос 2 не про то.
- **Тень D1 неизмерима.** Запись идёт 3 штуки на всю память. Неделя «тени» не наберёт выборку, сверять нечего. Стоп-критерий отсутствует.

## Концерны
- **D2 верен по уставу (V4, «не мусор», стирания нет), но дыра в тождестве.** AC8 «тот же hash при повторном открытии» гарантирует неизменность спеки, а не содержимого: данные под закреплённым видом живые. Рамка «собрано ИИ, hash» создаёт ложное чувство замороженности (V3: протухший вид выглядит доверенным). Нужен второй hash, hash результата, или явная метка «данные на <дата>».
- **Кэш эфемерных видов вне памяти** теряет их при рестарте pm2; инцидентный разбор «что видел владелец» невозможен. Приемлемо, но принять явно и писать короткий лог, не записи.
- **Закреплённый вид = вечная запись** без стирания. Нужен потолок числа pinned на область и `retract` как штатный путь, иначе V4 вернётся через закладки.
- **Потолок ≤9 дней занижен.** Не вошли: контроли R8 п.3–7 (в SPEC нет, ~1–1,5д), ПДн-скан, бэкап/репетиция отката, 472 битые ссылки, 697 длинных заголовков, 26 непроходящих путей, служебный принципал `ingest-docs`, тесты golden. A2UI не сверен по версии. Импорт 1,5д оптимистичен: реалистично 3–4. Честный потолок 12–14 дней или вырезать каркас/слоты из первого прохода.
- **Утренний дифф (ход 3) стоит на непроверенной полноте журнала** и при 3 записях пуст. Вау = ноль до импорта и накопления.

Потребитель: свод deep-research (лид + критик). Поглощает: ничего. Миссия R1 из `../missions/A1-frontier.md` (M1) и `A3-gaps.md` (M4).
Пометки: [П] = страница открыта и прочитана; [С] = только сниппеты поиска / чужие слова.

## Находки

1. **Ink & Switch, «Malleable software» (июнь 2025)** [П] — https://www.inkandswitch.com/essay/malleable-software/
   Идея: изменяемость = общие данные + «пологий склон» правок; инструмент не приложение. ИИ полезен только внутри «кухни» (общие данные, правка существующих инструментов), а не как генератор изолированных приложений.
   FF: это прямое обоснование «вид = запись над общей памятью». Толкает: **средне** (рамка и язык, не механизм).

2. **Patchwork: инструменты — тоже документы** [П] — https://buttondown.com/geoffreylitt/archive/towards-universal-version-control-with-patchwork ; эссе (п.1)
   Идея: и данные, и код инструмента — документы Automerge; ветки, диффы, «группы правок» работают на любом типе. Инструмент делится ссылкой.
   FF: вид-запись получает ветки и ревью теми же примитивами, что и остальная память. Толкает: **много** (ответ «версионируем виды без своего git»).

3. **Cambria: двунаправленные линзы схем** [П] — https://www.inkandswitch.com/cambria/
   Идея: миграции между версиями схемы = граф линз (узел — схема, ребро — линза); линзы можно хранить прямо в документе, старый клиент подтягивает новые.
   FF: вид, переживающий смену рендерера, = вид + линзы к версиям спеки. Ребро-линза — уже родной ход для графа с паспортом ребра. Толкает: **много**. Примечание: [С] про жизнеспособность проекта сегодня — не проверял, Cambria давно исследовательский.

4. **Potluck: обогащение как оверлей** [П] — https://www.inkandswitch.com/potluck/
   Идея: исходный текст не меняется; поверх лежат слои «поиск → вычисленная аннотация». Структура добавляется по мере нужды.
   FF: вид не переписывает запись-адрес, а лежит слоем над ней; тот же принцип «адрес, не копия». Толкает: **средне**.

5. **Jelly (CHI 2025): UI генерируется из data model, а не из кода** [П] — https://arxiv.org/html/2503.04084v1 (Cao, Jiang, Xia)
   Идея: LLM порождает схему задачи + граф зависимостей + данные; UI выводится по правилам паттернов; пользователь правит схему напрямую; история промптов прослеживается. Правки схемы преобладали в задачах обучения (92%).
   FF: подтверждает, что стабильный артефакт — схема/спека, а не код рендерера; человек правит тем же слоем, что агент. Толкает: **много**.

6. **Gradual generation (UCSD, янв. 2026)** [П] — https://arxiv.org/html/2601.17975v1
   Идея: UI генерируется слоями (категории → раскладка → содержимое → стиль); у каждого слоя своя спека (JSON-схема, CSS-переменные, текст); пользователь «перематывает» к слою; личные слои из следов правок.
   FF: вид как стек слоёв-записей (что показывать / как расположить / стиль), правится на любой глубине; личный слой владельца. Толкает: **средне**.

7. **Webstrates / Codestrates** [С] — https://hal.archives-ouvertes.fr/hal-01242672
   Идея: сам DOM документа персистентен и синхронизируется; граница «использовать/разрабатывать» стёрта.
   FF: как историческое подтверждение; брать механизм не нужно. Толкает: **мало**.

8. **Свежие работы по генеративным виртуальным виджетам (TaskArtisan, arXiv 2607.17394; UIST 2026 «Conversational customization»)** [С, только сниппеты]. Сигнал: направление живо, но детали не проверены; не опираться без чтения.

## Два инновационных хода для FF

**Ход 1. Тип `view` как запись памяти: спека + линзы + снимок.**
Построить: запись `type: view` с телом = узкая декларативная спека (источник запроса find, поля label/summary/body, группировка, правило статуса → стиль), `schema_version`, `renderer_hint` (необязательный) и ссылки-рёбра `lens` на запись-миграцию к следующей версии. Правят человек и агент одним `record` (поправка = новая версия, `supersedes`, провенанс «владелец/агент»). Рендерер читает спеку; смена рендерера = новый читатель той же спеки. Вопрос-цель закрывается: вид переживает рендерер, пока спека версионируема и линзы лежат в памяти (Cambria + Jelly). Стоимость: мало кода (тип + валидатор спеки), нового языка нет.

**Ход 2. Закрепление и ветки видов через «ветку записи».**
Построить: «закрепить» = рёбро `pinned` на конкретную версию вида (hash), а не на «последнюю»; черновик агента живёт как предложение (`proposed`) и принимается владельцем одним действием — аналог ветки и группы правок из Patchwork, на примитивах памяти (supersedes + статус). Удачный сгенерированный вид превращается в запись с провенансом; следующая генерация начинается с ближайшего закреплённого вида (компаунд).

## Что не брать
- Automerge/CRDT как хранилище видов: у FF уже есть журнал, версии и supersedes; второй движок синхронизации = второй источник правды (V5). Брать идеи, не стек.
- Webstrates-подход «персистентный DOM»: вид привязан к рендереру, ломает переносимость.
- Код-как-вид (инструменты-документы с JS из Patchwork): это «второй язык программирования»; брать только декларативную спеку.
- Свободная генерация UI «на лету» без записи следа: нет стабильности и провенанса.

## Вопрос, который вскрыла миссия
Что считается тождеством вида при смене спеки: тот же `canonical_id` с линзой или новая запись? От этого зависит, переживает ли закрепление миграцию (V2).

Вопрос-цель: ответил — да, вид может быть записью (спека + версия + линза + `pinned`/`proposed`), но на уровне источников подтверждено лишь для изолированных частей (Cambria, Patchwork, Jelly); цельный пример «вид-запись в графе памяти» не найден, это синтез мой, а не чужая находка.

## Находки

1. **Semantic zoom = уровень детализации, а не масштаб (Pad++).** Объект рисуется по-разному в зависимости от размера: при отдалении упрощённая форма, при приближении детали. [П] [Bederson, Pad++](https://static.usenix.org/publications/library/proceedings/tcl95/full_papers/bederson.txt). Идея: зум переключает грань. FF: label→summary→тело уже есть как поля, нужен только порог «размер на экране → грань». Толкает: много.

2. **Heptabase: при зуме <30% остаются только заголовки, секции видны всегда.** [П] [wiki.heptabase.com/section](https://wiki.heptabase.com/section). Идея: пороговая лестница + «якорные» контейнеры. FF: scope/область = секция, label = заголовок. Толкает: средне.

3. **LLM-канвасы с семантическим зумом: Sensecape (UIST'23), CanvasConvo (4 уровня: Cluster/Minimal/Compact/Full), MindTrellis, ScholarMate, VisCanvas.** [П] [Sensecape](https://arxiv.org/pdf/2305.11483); остальные только по сниппету [Сл], [поиск](https://arxiv.org/pdf/2605.15848). Идея: 4 дискретных уровня + переключатель «холст/иерархия». FF: четыре уровня = кластер → label → summary → тело; иерархия = дерево scope. Толкает: средне.

4. **Degree-of-Interest (Furnas 1986, Card&Nation 2002): показывать то, у чего интерес выше порога, остальное сжимать.** [П] [сниппет](https://homes.cs.washington.edu/~jheer/files/2003-InterestEstimation-CHI.pdf). Идея: видимость = функция (близость к фокусу + априорная важность). FF: априорная важность = status/confidence/stale; фокус = текущий запрос агента или человека. Решает «1350 узлов не влезают». Толкает: много.

5. **Value-Suppressing Uncertainty Palettes (CHI'18): при высокой неопределённости цвету отдаётся меньше диапазона (блёкнет), при низкой — больше.** [П] [Tableau Research](https://www.tableau.com/research/publications/value-suppressing-uncertainty-palettes). Идея: confidence управляет насыщенностью/бюджетом канала, не отдельным значком. FF: confidence/stale → насыщенность и резкость. Толкает: много.

6. **Stale data в картах-рабочих пространствах: визуально выдавать устаревшее и срок годности.** [П, оборонные работы; сниппет](https://www.dst.defence.gov.au/publication/visualising-uncertainty-decision-support). Аналогия fog of war: неизвестное/старое затуманено, а не скрыто. FF: `cold`/`stale` = туман, запись остаётся на карте. Толкает: средне.

7. **Sparklines Тафти: «слово-размерная» графика, без осей и легенд, вставляется в текст/таблицу.** [П] [edwardtufte.com](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/). FF: микро-график «жизни» записи (правки/обращения за время) в строке label. Нужны данные истории; сколько их у ff-brain — не проверено. Толкает: средне.

8. **Grafana Node Graph: у узла кольцо-дуга из секторов (доли суммируются в 1), цвет и граница настраиваются полями.** [П] [docs](https://grafana.com/docs/grafana/latest/panels-visualizations/visualizations/node-graph/). Идея: узел = диаграмма-«циферблат» по полям. FF: кольцо = доли рёбер (подтверждающие/противоречащие/устаревшие). Толкает: средне.

Не проверял: Factorio/Civ tech tree, Kinopio/Muse, Dynamicland, GDC — остаются за пределами этой миссии [Сл].

## Два ИННОВАЦИОННЫХ хода для FF

**Ход 1. «Грамматика состояния как данные».** Одна таблица-правило (запись типа `view-style`, хранится в памяти): поле → визуальный канал. `status` → форма/заполнение (open пусто, active полно, done галочка-тень, cold ледяной контур); `stale` → туман (размытие); `confidence` → насыщенность по VSUP; противоречие → разрыв/красная дуга на ребре; свежесть → пульс-ореол. Рендерер читает правило и применяет, не зная смысла полей. Меняют правило человек или агент (гибкость в данных), а набор каналов фиксирован в коде и проверен на читаемость (безопасность в коде). За 5 секунд: пятно ярких узлов = живое, блёклое = остыло, красные дуги = конфликт.

**Ход 2. «Зум по интересу, а не по масштабу».** Объединить 1 и 4: грань записи определяется не размером на экране, а DOI = близость к фокусу × важность (status/confidence/свежесть). Рядом с фокусом (запросом агента, текущей задачей) раскрыто тело, у периферии summary, у далёких label, у остывших — только туман-точка. Одна и та же карта для человека и ИИ: агент задаёт фокус через MCP, и ответ — тот же вид, что видит владелец. Правило порогов тоже запись.

## Что не брать
- Силовые «hairball»-раскладки на все 2650 рёбер сразу. Гравитационная раскладка без DOI превращает карту в клубок [Сл].
- Баллы/бейджи/уровни (геймификация). Берём только визуальную грамматику.
- Свободный холст в стиле Muse/Heptabase как первичный вид: ручная расстановка не масштабируется до ~1350 адресов и расходится с генерацией [Сл].
- Шкалы ценности «хорошо/плохо» по цвету: цвет несёт статус, не оценку.

Где живёт «координата» записи на карте: раскладка вычисляется из рёбер каждый раз (дёшево, но нестабильно — владелец теряет «где что лежало») или запись хранит свою позицию (стабильно, но это новое поле и потенциальная «ручная» часть)? Вопрос-цель: ответил частично (дан набор приёмов и грамматика; не проверено на реальной выборке ff-brain и не проверено, достаточно ли 5 секунд на 1350 узлов).

## Главное
Прямых данных «генеративный UI удерживает людей 3+ мес» **не нашёл ни по одному продукту** — это пробел рынка, не моего поиска. Есть косвенные: что умирает и что остаётся.

## Находки
1. **Google Generative UI (dynamic view / visual layout).** [П] research.google/blog/generative-ui-… Gemini 3 Pro пишет HTML/CSS/JS на каждый промпт; люди сильно предпочитают его тексту, но эксперт-дизайн всё же выше; генерация «минуту и более», бывают неточности; про сохранение/повторное использование UI в статье ничего. Идея: эфемерный UI = ответ, не артефакт. FF: подтверждает, что без слоя «сохранить» он одноразовый. Толкает: средне.
2. **Vibe-coding платформы теряют трафик после пика.** [Сл, agnost.ai] Lovable −40% от пика, v0 −64%, Bolt −27%; главный предиктор удержания — «вернулся ли за вторым проектом». Тот же источник: AI-приложения держат 21% годовых подписчиков против 30,7% (не проверял первоисточник). Идея: удерживает не генерация, а доведённый до конца и снова нужный результат. Толкает: средне.
3. **Lovable растёт по выручке** (500 млн ARR, 1 млн проектов в неделю, TechCrunch 2026-06) [Сл]. Проекты ≠ повторное использование. Показатель «создано» вводит в заблуждение. Толкает: мало.
4. **ChatGPT Atlas закрыт 9 августа 2026**, функции ушли в десктоп-приложение; Comet жив (~10 млн MAU) [Сл, tech-insider и др.; towardsai дал 403]. Идея: «свой интерфейс-поверхность ради агента» проигрывает тому, где человек уже сидит. Толкает: средне (для FF = Telegram остаётся основным).
5. **Poke (в iMessage/Telegram/WhatsApp), куплен Cognition в июле 2026** [Сл]. Ставка: нет отдельной иконки, нет цены удержания. Метрик удержания не нашёл [П: runtimewire данных не даёт]. Толкает: средне (канал владельца уже чат).
6. **Notion Custom Agents: 1 млн+ создано за ~3 мес** [Сл]. Реальный аудит владельца: из 3 агентов оставлен 1 (ежедневный отчёт, ~$15/мес); убиты почасовой разбор почты и недельный клиентский статус; 40% «агентов» оказались разовыми вопросами [П: pravinkumar.co, один автор, n=3]. Идея: живёт **регулярное, повторяющееся, безопасно ошибающееся**; одноразовое не заслуживает сохранения. Толкает: много.
7. **ChatGPT Apps (интерактивные виджеты в чате).** [П: HN-ветка] Большинство приложений остались на v1.0.0, метрик реального использования нет. Толкает: мало, сигнал «каталог без привычки».
8. **«Disposable software» (a16z, Lütke и др.).** [П: lobstercap] Самое чистое утверждение «построил, использовал, забыл» — без единой цифры. Идея принимать как гипотезу: большинство видов не должно сохраняться. Толкает: средне.
Также [Сл]: Claude Artifacts сохраняются в библиотеку и ремиксуются; 500+ млн артефактов создано, но данных, сколько открыто повторно, нет. NN/g «intent-based outcome specification» — рамка, не данные.

## Что реально живёт (вывод агента, не факт)
Повторяемое (расписание/триггер) + результат, который владелец иначе делал бы сам + безопасная ошибка + живёт там, где человек и так находится. Эфемерное «по вопросу» хорошо как ответ, плохо как привычка.

## Два инновационных хода для FF
1. **Вид-кандидат с «счётчиком возвращений».** Каждый сгенерированный вид пишется в ff-brain как `view` (status: ephemeral) со ссылкой на запрос-намерение. Повторное открытие/повторный похожий запрос (≥3 раз за 30 дней) = автопредложение «закрепить». Закрепление — решение владельца. Сохраняет не удачное, а **востребованное**; вес: много, цена: средняя (счётчик + одно поле).
2. **Вид = намерение, а не пикселы.** Хранить в `view` текст намерения + запрос к графу + JSON-описание, а HTML каждый раз перегенерировать/кэшировать. Тогда смена рендерера (A2UI/json-render/Telegram-карточка) не ломает сохранённое, а повторная генерация не стоит «минуты». Вес: много, цена: малая (один тип, без второго языка).

## Что не брать
- Отдельную «поверхность-приложение» ради агента (урок Atlas).
- Метрику «создано видов» как успех.
- Генерацию кода на каждый вопрос как основной путь (латентность ≥1 мин, неточности у Google).
- Каталог видов без расписания/триггера (урок ChatGPT Apps).

## Вопрос владельцу
Какие 1–2 вида ты бы открывал **каждую неделю по расписанию**, даже если бы не задавал вопроса? Именно они — кандидаты на первое закрепление.

Вопрос-цель: ответил частично — паттерн, переживающий демо, = регулярный + доведённый до конца + в привычном канале; прямых данных удержания именно генеративного UI рынок не публикует.

# R4 — Интерфейс над графом: что прижилось

Потребитель: свод deep-research по инструменту видов. Поглощает: ничего.
Пометки: [В] — открыл страницу и прочитал; [С] — по сниппету поиска/с чужих слов.
Слабое место ресёрча: прямых данных ретеншна («смотрят каждый день») нет ни у кого — только отзывы и docs.

## Находки

1. **Глобальный граф-шар — диагностика, а не навигация.** Ежедневно им почти не пользуются [С: сводка поиска по Obsidian]. Автор подборки по локальным графам [В: pjordan.substack.com/p/a-pkm-revelation-obsidian-local-graphs]: с ростом заметок global graph стал трудно использовать, local graph («вокруг одного узла») — «почти магия». Идея: граф работает на масштабе одного узла и его соседей. FF: вид «окрестность записи» (1–2 шага) вместо всех ~1350 документов. Толкает: **много**.

2. **Запрос к графу = рабочий стол (Tana, Anytype).** Tana: supertag + live query (search node) + представления список/таблица/карточки/вкладки/календарь; power-юзеры держат 15–20 сохранённых запросов по контекстам [С: tana.inc/search-nodes, dev.to/pickuma Tana review]. Anytype: Set = живой запрос по типу/связи, Collection = ручная подборка [С: doc.anytype.io]. Идея: вид = сохранённый запрос + выбор представления, а не нарисованная картинка. FF: type/status/scope у записей уже есть — «вид» = {фильтр, группировка, представление}. Толкает: **много**.

3. **Граф нужен, чтобы курировать, а не читать.** Автор Graph Explorer для Obsidian Bases [В: dsebastien.net/i-built-a-graph-explorer-...]: при 50+ связанных статей, сгенерированных LLM, теряешь общую картину; граф показывает кластеры, сирот, хабы, «frontier» (ссылка есть — записи нет), статус и уверенность узлов. «Курация требует осознанности, осознанность — возможности увидеть». FF: прямо наш случай (агент пишет в память, владелец проверяет). Виды: сироты, proposed-записи, слабые доверие/источник, протухшие. Толкает: **много**.

4. **Пространственная ручная раскладка (Heptabase) — для мышления, не для хранилища.** Карточки на whiteboard, понимание рождается из раскладки; «на 2–3 сессии раскладка начинает работать» [С: tana.inc/blog/best-heptabase-alternatives-2026, capacities.io/compare/heptabase]. В обсуждении запроса графа у Tana [В: ideas.tana.inc, пост 114]: хотят не смотреть граф, а «создавать информацию, манипулируя графом»; существующие графы — «gimmick» без запросов, фильтров, side-by-side. FF: холст-вид с закреплёнными позициями как проекция, а истина остаётся в графе. Толкает: **средне** (после находок 2–3).

5. **Онтология как основа UI (Palantir).** Workshop — no-code приложения прямо на Ontology: объекты, связи и действия (Actions) как строительные блоки; Object View — «хаб» вокруг объекта; не пассивные дашборды, а «user-driven workflows» [С: palantir.com/docs/foundry/ontology/applications, app-building/overview]. Идея: UI не рисует данные, а выводится из типов + связей + разрешённых действий. FF: type-реестр ff-brain + действия (record/link/supersede) = готовый «онтологический» слой; вид типа генерируется по описанию типа. Толкает: **много**.

6. **Neo4j Bloom/NeoDash: перспективы и почти-естественный поиск.** Bloom: поиск шаблонами без Cypher, сохраняемые «перспективы» под бизнес-цель; NeoDash связывается с ними по deep link [С: neo4j.com/docs/bloom-user-guide, neodash bloom-integration]. Идея: перспектива = стиль и фильтр «под роль», дашборд (сводка) + граф (раскопка) вместе. FF: перспективы = наши scope-виды (ff, аренда авто). Толкает: **средне**.

7. **Граф-память агентов: визуализатор вторичен.** У Zep есть дашборд с графом и логами отладки; Graphiti — open-source движок, «свои dev-инструменты строй сам»; для Microsoft GraphRAG есть лишь сторонние визуализаторы (graphrag-visualizer, graphrag-workbench с цветными сообществами и чатом) [С: dev.to/noworneverev, sourcepulse]. Идея: рынок мемори-слоёв отдал UI на откуп — свободная ниша, но и сигнал, что платят за поиск, а не за картинку. FF: не конкурируем по картинке; показываем «что агент записал и почему». Толкает: **средне**.

8. **Kumu: граф-карта живёт, когда у неё один вопрос.** Стейкхолдер-карты из таблиц, виды разрезаются по команде/сайту, чтобы не перегружать [С: fitgap-гайды]. Идея: у каждого вида один вопрос и один срез. Толкает: **мало** (подтверждает находку 1).

## Ответ на вопрос-цель
Граф смотрят, когда он (а) ограничен окрестностью или срезом, (б) отвечает на рабочий вопрос — что осиротело, что не проверено, что недавно изменилось, (в) позволяет действовать на месте. Шар «всё и сразу» не прижился. Чат отвечает на вопрос; вид нужен там, где вопрос не сформулирован — обзор, пробелы, надзор.

## 2 инновационных хода

**Ход 1. «Вид = запись в самой памяти».** Сохранённый запрос ({фильтр по type/status/scope, представление, окрестность}) хранится как обычный узел ff-brain с паспортом (автор, статус proposed/approved, supersedes). Агент предлагает вид, владелец принимает одним касанием; вид версионируется и стареет как любое знание. Рабочий стол = набор принятых видов-узлов. Чего нет у Tana/Anytype: агент сам растит рабочий стол, а владелец одобряет. (Рекомбинация находок 2+5; аналога в изученных продуктах не нашёл — гипотеза, не факт.)

**Ход 2. «Вид надзора по дефектам графа».** Генерируемый из самого графа аудит-вид: сироты, frontier (ссылка без записи), записи без source.ref/hash, открытые proposed, конфликтующие рёбра. В Telegram — карточка с числами и deep link на вид-окрестность проблемного узла. Граф как инструмент контроля агента, а не картинка. (Находка 3 + Telegram-канал; для ~2650 рёбер импорта сразу полезен.)

## Что не брать
- Глобальный force-directed шар как главный экран (находка 1).
- 3D-графы и «красоту» GraphRAG-визуализаторов — без сценария.
- Полную копию Palantir Workshop (редактор приложений) — берём только принцип «UI из онтологии».
- Ручную whiteboard-раскладку как первую фазу — дорого, ценность проявляется со 2–3 сессии.

## Один вопрос владельцу
Что ты хочешь увидеть первым в утренней карточке: «что агент записал и ждёт твоего ОК», «что осиротело/протухло» или «окрестность проекта, над которым работаешь»?

Вопрос-цель: ответил (частично — по отзывам и докам, без числовых данных ретеншна).

# R5 — Контроль агентов

- Потребитель: итоговый свод deep-research (вид «владелец + агенты»). Поглощает: ничего.
- Related: ../missions/A2-market.md (M3).
- Метки: [П] = страница открыта в поиске, содержание из выдачи (полный текст не открывал); [Ч] = с чужих слов (агрегаторы, блоги). Все цифры без первичной проверки.

## Находки

1. **LangChain Agent Inbox** [П]. Отдельный UI над LangGraph `interrupt()`: агент встаёт на паузу, задача падает во «входящие», человек принимает / правит / отклоняет / отвечает. https://github.com/langchain-ai/agent-inbox · https://blog.langchain.com/introducing-ambient-agents
   Идея: одобрение = письмо во входящих, а не модалка в чате. FF: proposed-записи ≤3/ход это те же «письма». Толкает: **много**.

2. **HumanLayer** [П]. `require_approval` блокирует вызов, запрос уходит в Slack/email/SMS/Discord, ответ с комментарием возвращается агенту; есть `human_as_tool` (агент сам просит ввод). https://humanlayer.dev
   Идея: одобрение живёт в канале владельца, с комментарием «почему нет», который агент читает. FF: Telegram-шлюз уже такой канал, не хватает комментария-причины как возврата в агента. Толкает: **много**.

3. **Letta ADE** [П]. Панель Core Memory: блоки памяти агента видны человеку, правятся руками, можно смотреть, как агент правит их вживую. https://docs.letta.com/guides/ade/core-memory
   Идея: память показана как редактируемый текст, а не как граф. Дифа и очереди нет (в выдаче не нашёл). FF: показ записи = карточка с полями + правка. Толкает: **средне**.

4. **Mem0 history** [Ч]. Неизменяемый журнал событий ADD/UPDATE/DELETE: old_memory, new_memory, actor_id, время; дашборд показывает историю изменений каждой записи. https://deepwiki.com/mem0ai/mem0/5.4-history-and-audit-trails
   Идея: лента = журнал событий с old/new и автором-агентом. FF: ложится прямо на supersedes/retract и статус proposed. Толкает: **много**.

5. **Cursor / Copilot / Devin: ревью результата, а не процесса** [Ч/П]. Агент работает в фоне, человек получает diff/PR; у Copilot каждый коммит агента ссылается на лог сессии для аудита, вкладка Agents = центр всех задач. https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/coding-agent/agent-management · Cursor: https://www.datacamp.com/blog/cursor-3 [Ч]
   Идея: «итог + дифф сверху, лог процесса по ссылке». FF: у записи `source.ref` на сессию агента = та же схема. Толкает: **средне**.

6. **Усталость от одобрений** [Ч]. Anthropic (март 2026): пользователи одобряют ~93–97% запросов, люди ловили 13,6% опасных команд против 89% у классификатора; Auto mode стал дефолтом с 14 августа [Ч, цифры расходятся между источниками]. https://tessl.io/blog/claude-code-gets-auto-mode-to-cut-approval-fatigue/ · https://hyrax.dev/blog/claude-code-auto-mode-default-august-14
   Идея: очередь, где всё надо одобрять, превращается в «да, да, да». FF: проект-области с низким риском должны авто-приниматься, человеку показывать только отклонения. Толкает: **много**.

7. **Annotation queues Langfuse/LangSmith** [П]. Очередь на проверку: фильтр отбирает трейсы, ревьюер ставит оценку + комментарий. У LangSmith есть маршрутизация и приоритет риска, у Langfuse нет. https://langfuse.com/docs/evaluation/evaluation-methods/annotation-queues
   Идея: очередь не FIFO, а по риску. Это про разработчиков (анти-цель миссии), берём только приоритет. Толкает: **мало**.

## Две инновационных хода

**А. «Одобрение по исключению с ленивой выборкой».** Очередь не показывает все proposed. Система сама авто-принимает записи, которые не конфликтуют ни с чем (нет пересечения с существующими, низкий риск, область ff/agents-manager), а владельцу утром приходит ОДИН дайджест: «принято сама N (свернуто), на твой взгляд M: конфликт/спорное/впервые». Плюс случайная выборка 1–2 авто-принятых «на проверку честности» (против слепого «да»). Это ответ на 93–97% одобрений.

**Б. «Дифф памяти за день как один сгенерированный вид».** Не поток карточек, а один экран: «что изменилось в моей голове с вчера»: новые узлы/рёбра, замены (было → стало), и кто из агентов написал. Генерируется из журнала событий (как Mem0 history, но по графу, с рёбрами как первоклассными), чтобы владелец за 30 секунд видел картину. В Telegram идёт сжатой карточкой + ссылка на веб-вид. Не нашёл готового продукта, который показывает дифф графа памяти человеку [нет данных, не утверждаю, что нет].

## Что не брать

- Полный LLM-трейсинг (Langfuse/Phoenix-стиль, спаны и токены): для разработчика, не для владельца.
- Модалку «одобрить каждый вызов»: усталость, 97% «да».
- Лог процесса как главный вид: показывать только по ссылке из записи.
- Правку памяти руками как основной путь (Letta): у FF владелец утверждает, а не пишет.

## Вопрос владельцу

Какие записи агентов ты готов НЕ видеть вообще, если будешь получать утренний дайджест и выборочную проверку: только проектные «заметки сессии» или также решения (decision)?

Вопрос-цель: ответил частично (что смотреть ежедневно: итоговый дифф и очередь по исключению; не проверил первичные источники и не нашёл продукт с дифом графа памяти).

# R6 — Telegram как канал вида

Потребитель: синтез deep-research. Поглощает: ничего.
Метки: [П] проверено по core.telegram.org (через пересказ WebFetch, не руками); [С] со слов вторичных источников.

## Находки
1. **[П] Bot API дошёл до 10.3 (24.08.2026).** Ключевое для нас: 10.1 (11.06) принёс **Rich Messages** (`sendRichMessage`): структурированный текст с блоками — заголовки, списки, таблицы, коллажи/слайдшоу, фото/видео/документы, раскрывающиеся блоки (details), карты, цитаты; 10.3 добавил блоки-кнопки, expandable quote, document-блоки. Правится через `editMessageText` с `rich_message`.
2. **[П] Стриминг:** `sendMessageDraft` (9.3 — топики в личке, 9.5 — всем ботам) и `sendRichMessageDraft` — прогрессивная сборка карточки.
3. **[П] Не выяснено:** числовые лимиты Rich Messages, поддержка `message_thread_id` в форум-топиках, совместимость с inline-клавиатурой, ограничение drafts приватными чатами. Пересказ докой не дал. Это первый тест до любых решений (дешёвая проверка: один вызов).
4. **[П] Mini App (Web App):** 8.0 — fullscreen, ярлык на домашний экран, геолокация, скачивание файлов; хранилища: CloudStorage 1024 ключа, DeviceStorage 5 МБ, SecureStorage 10 элементов (9.0). Ссылка-на-вид: `t.me/bot/app?startapp=<param>`, параметр приходит как `tgWebAppStartParam` (лимит в доках не указан).
5. **[П] Авторизация:** initData подписан HMAC-SHA256 от токена бота; есть Ed25519-`signature` для проверки третьей стороной без токена. Поля: `user.id`, `chat_instance`, `chat_type`, `start_param`, `query_id`, `auth_date`; свежесть по `auth_date` проверяет сам сервер (срок не задан). Итого Mini App даёт **криптографически подтверждённую личность Telegram-пользователя без логина**.
6. **[С] Poke** живёт в iMessage/SMS/Telegram без своего приложения; в Apple Messages (одобрен 04.06.2026) показывает структурные карточки и пикеры, в остальных каналах — текст и ссылки, деградирует «вниз». Это тот же принцип «один вид → разные рендереры по возможностям канала».
7. **[С] A2UI называют «Telegram Mini App для ИИ»** (LogRocket); json-render (Vercel) — каталог компонентов на Zod. Публичных примеров «Mini App рендерит A2UI/json-render-дерево» я не нашёл — значит, это не готовый паттерн, а наш шов (поиск на 1 запрос, не исчерпывающий).
8. **[С/слабо]** Данных о ретеншне утилитарных Mini App vs inline-кнопок нет; найденные цифры (15–20% завершения inline-флоу) — маркетинговые, не брать.

## Где мессенджер ломается
- Нет интерактивной сортировки/фильтра/графа внутри сообщения; карточка — снимок (устаревает, нужен edit).
- Лимит ~3500 знаков карточки (наш практический, не API); Rich Messages, возможно, смягчают — см. п.3.
- Mini App: холодный старт, отдельный веб-хостинг, хранение сессии; в форум-группе контекст топика приходит только через `chat_instance`/`start_param`.
- Картинка графика: статична, не копируется как данные, но читается мгновенно на телефоне.

## Два инновационных хода
1. **Лестница деградации одного дерева вида (без новых слоёв).** Один декларативный узел вида имеет 4 рендера по цене: (a) Rich Message-блоки/Markdown-карточка → (b) PNG с сервера (для графиков/таблиц) → (c) кнопка «Открыть вид» = Mini App `startapp=<view_id>` → (d) React web. Рендерер выбирается по полю `needs: [interactive|graph|edit]` в самом дереве: нет needs — остаёмся в чате, есть — карточка кончается кнопкой «развернуть». Чат — по умолчанию, Mini App — эскалация, не замена.
2. **initData как готовый гейт видимости.** Mini App = тонкий React-рендерер, открывающий `view_id` из `start_param`; сервер проверяет initData (HMAC/Ed25519) → получает `user.id` → прогоняет через тот же гейт `reader/visibility`, что и /access. Короткоживущий view-токен не нужен: ссылка в чате безопасна, потому что ссылка — только `view_id`, а право даёт личность. Бонус: ссылку нельзя переслать в чужой чат с утечкой (чужой initData → отказ). Минус: привязка к Telegram-личности; веб-вариант вне Telegram потребует другого входа.

## Что не брать
- Крипто/игровые Mini App-паттерны, платёжные флоу, монетизацию.
- Mini App как основной вид «вместо» чата: цена хостинга/холодного старта выше пользы, пока нет сценария интерактива.
- Любую опору на лимиты Rich Messages и топики до проверки п.3.
- Цифры ретеншна из маркетинговых блогов.

## Вопрос владельцу
Какой ежедневный вид владелец реально хочет «раскрыть» из чата — только прочитать (карточка/картинка достаточно) или менять (тогда Mini App оправдан)? Назови один конкретный вид из последней недели.

Источники: core.telegram.org/bots/webapps, /bots/api, /bots/api-changelog; blog.logrocket.com/is-a2ui-the-telegram-mini-app-of-ai; infoq.com/news/2026/03/vercel-json-render; letsdatascience.com (Poke в Messages).

Вопрос-цель: ответил частично — минимальный ежедневный вид = карточка (Rich Message/Markdown) + эскалация кнопкой в Mini App; ломается на интерактиве и актуальности; не проверены лимиты Rich Messages и поведение в топиках.

## R7-graph-for-llm

status: draft
owner: jenya.stasik@gmail.com
date: 2026-11-01

Потребитель: синтез deep-research view-tool. Поглощает: часть M3 из A3-gaps.md.
Пометки: [проверено] = открыл источник/абстракт сам; [с чужих слов] = только пересказ в выдаче поиска, статьи целиком не читал.

## Находки

1. **Talk like a Graph (Google, ICLR 2024)** — [arXiv 2310.04560](https://arxiv.org/pdf/2310.04560) [проверено, блог Google]. Способ текстового кодирования графа меняет точность до ~60%; «incident»-кодирование (узел: список соседей) лучшее в целом; топология и размер модели тоже влияют. Для FF: вид узла = «узел + его соседи с типом ребра», а не плоский список троек. Толкает: средне.
2. **Прогрессивное раскрытие на LLM-вики** — [arXiv 2607.04576](https://arxiv.org/pdf/2607.04576) [проверено, абстракт]. 709 страниц markdown, 4 версии доступа к тем же страницам: качество в рамках допуска, стоимость упала во всех условиях. Но сильный агент вообще не грузил большой индекс; качество при принудительной загрузке каталога не доказано; согласие человека и LLM-судьи слабое. Для FF: не заставлять агента читать overview целиком, дать дешёвый find. Толкает: много.
3. **GraphRAG, сводки сообществ** — [Microsoft Research](https://microsoft.com/en-us/research/blog/graphrag-new-tool-for-complex-data-discovery-now-on-github) [с чужих слов]. Иерархические сообщества, у каждого сводка; на верхних уровнях ~2–3% токенов против суммаризации исходников, на средних 20–70%. Подходит для вопросов «про всё». Для FF: сводка области/кластера как грань между label и summary. Толкает: много.
4. **LightRAG** — [с чужих слов] двухуровневый поиск (сущность + тема) без предвычисленных сводок сообществ, индексация дешевле на порядки. Для FF: дешёвая альтернатива п.3, если сводки кластеров устаревают. Толкает: средне.
5. **Zep/Graphiti** — [arXiv 2501.13956](https://arxiv.org/html/2501.13956) [с чужих слов]. Три яруса: эпизоды, сущности, сообщества; рёбра с периодом валидности; LongMemEval +до 18.5% при −90% задержки. Для FF: наш паспорт ребра (status/supersedes) это то же самое, нужно отдавать «актуально на дату» прямо в виде. Толкает: средне.
6. **HippoRAG 2** — [arXiv 2502.14802](https://arxiv.org/pdf/2502.14802) [с чужих слов]. Personalized PageRank от найденных узлов; +7% на ассоциативных вопросах. Для FF: ранжировать обход ≤2 по PPR, а не обрезать по ≤50 слепо. Толкает: средне.
7. **Mem0 graph** — [arXiv 2504.19413](https://huggingface.co/papers/2504.19413) [с чужих слов]. Граф даёт лишь +2–2.6 п. на multi-hop/temporal, цена ~2× токенов (~14K против ~7K). Для FF: граф окупается только на связных вопросах, не по умолчанию. Толкает: мало.
8. **TOON и компактные форматы** — [arXiv 2605.29676](https://arxiv.org/abs/2605.29676) [проверено, абстракт]: TOON −18% токенов, но −9 п. точности и каскадные сбои в агентских мульти-ходах (TRON −27%, до −14 п.). Бенчмарки авторов TOON (~−40% токенов, +1–4 п.) [с чужих слов] относятся к однородным таблицам. Выигрыш реален только для табличных данных; [arXiv 2603.03306](https://arxiv.org/abs/2603.03306) [проверено]: для генерации plain JSON точнее. Для FF: таблица «id | type | label | status» в TOON/CSV для чтения, JSON для записи. Толкает: средне.
9. **Anthropic: инструменты и контекст** — response_format concise/detailed (≈⅓ токенов в примере статьи), лёгкие идентификаторы + догрузка по требованию [с чужих слов, пересказы]. Для FF: параметр `detail` в find/read. Толкает: средне.

## Два инновационных хода

**Ход A. Сводка кластера как узел графа (label → cluster-digest → summary → body).** Раз в N записей считаем сообщества (Leiden по рёбрам, либо готовые scope/type) и записываем digest ~150 токенов как запись type=digest с рёбрами `summarizes` и паспортом (hash состава, stale при изменении >X% членов). Агент сначала видит 15–30 digest (~3K токенов), потом спускается. Закрывает «глобальные» вопросы без чтения 1350 узлов; хранится в самой памяти, переносимо.

**Ход B. Вид «стабильный каркас + incident-блоки + ранжирование PPR».** Ответ read: заголовок узла, затем сгруппированные по типу ребра соседи в табличной строке, обход ограничен бюджетом токенов, а не числом узлов (ранжирование по PPR от стартового узла). Параметр `detail=ids|labels|summary`.

**Мини-эксперимент (локально, 1 день).** Выбрать 10 вопросов по реальным данным: 3 точечных (какой статус у X), 3 двухшаговых (какие решения связаны с задачей X и устарели ли), 2 агрегатных (чем занимается область Y), 2 временных (что заменило решение Z). Золотые ответы разметить заранее руками. Форматы кормить одной моделью и одним промптом: (1) список троек, (2) JSON-adjacency, (3) markdown-outline с incident-блоками, (4) TOON/CSV-таблица узлов + ребра отдельной таблицей, (5) вариант 3 плюс digest кластеров (ход A). Мерить: точность (судья LLM + ручная проверка 20%, помня о слабом согласии из п.2), токены на вход, число вызовов инструментов. Масштаб: всё 1350 узлов, label+summary.

## Что не брать
- Полный GraphRAG-индекс (дорого, вердикт сообществ по сырому тексту нам не нужен: тела в git).
- TOON как формат записи/ответа агента (сбои мульти-хода, п.8).
- Векторную БД ради вида: для адресов с label хватает find + граф.
- Мнение «граф всегда лучше»: п.7.

## Вопрос
Какая доля реальных вопросов агента к памяти глобальные («что у нас по X вообще») против точечных? От этого зависит, нужен ли ход A сразу.

Вопрос-цель: ответил частично — направление (incident + digest + detail-параметр) названо, но точность форматов на ~1350 узлах не измерена, нужен мини-эксперимент.

## R8-failures-and-security
> Источник: `deep-research/findings/R8-failures-and-security.md`

---
title: R8 — Провалы генеративного UI и безопасность UI-канала
status: draft
owner: jenya.stasik@gmail.com
date: 2026-11-01
---

Потребитель: синтез deep-research view-tool. Поглощает: A3-gaps M1, M2.
Пометки: [В] = открыл страницу/сниппет поиска сам; [СЧ] = со слов вторичных источников, не проверено по первоисточнику.

## Находки

1. **NN/g: меняющийся UI ломает обучаемость.** «Constantly changing UIs will cause usability problems»; чем чаще пользуешься, тем эффективнее, а genUI может показывать другой UI каждый раз; дизайнер должен балансировать выигрыш кастомизации и потерю консистентности. Что именно держать стабильным, NN/g не говорит. [В, nngroup.com/articles/generative-ui/]
2. **Gajos и др., CHI'08: точность важнее предсказуемости, но оба поднимают удовлетворённость.** Предсказуемая модель = та, которую пользователь может смоделировать в голове. Точность сильнее влияет на скорость и использование адаптивной зоны. Количественного порога «сколько можно менять» нет. [В, сниппет поиска, harvard.edu/~kgajos]
3. **Провал №1 по бенчмаркам: поддержка между ходами.** EvoGenUI-Bench (150 пятишаговых задач): узкое место не однократное качество, а сохранение вида между ходами. Design Theater вводит индекс гомогенности. arXiv-id из выдачи поиска; PDF не читался. [СЧ]
4. **Eval ещё не зрелый.** Один LLM-судья даёт один неявный взгляд (UIPersonaBench, панель персон). Для замкнутого каталога eval проще: схема-валидность + снимки вывода, а не «красота». [СЧ]
5. **«Смертельная тройка» (Willison, июнь 2025):** приватные данные + недоверенный контент + канал наружу. EchoLeak (CVE-2025-32711, M365 Copilot) эксфильтрирует через markdown-картинку, которая грузится при рендере. [В, сниппеты; по EchoLeak со слов]
6. **MCP tool poisoning / rug pull (Invariant Labs).** Инструкции в описаниях и схемах, которые читает модель, а человек нет; сервер мутирует после одобрения. Средний успех атак ~36.5% [СЧ]. Для FF аналог: текст документа/записи в графе, попавший в промпт генератора вида.
7. **CaMeL (DeepMind, arXiv 2503.18813):** план выполняется из доверенного запроса, недоверенные данные не влияют на control flow; 77% задач AgentDojo с доказуемой безопасностью против 84% без защиты. Но требует ограниченного интерпретатора Python. [В]
8. **A2UI / MCP Apps / json-render:** граница безопасности = клиентский каталог (компонент вне каталога не рендерится); MCP Apps: iframe на отдельном origin, CSP-allowlist, действия только через хост (openLink, callServerTool). Худший выход json-render = ошибка валидации. Но аудит Thesys-пайплайна всё же отметил риск инъекции. Каталог защищает от кода, но не от вредного ТЕКСТА внутри разрешённых компонентов. [В, сниппеты]

## Обязательные контроли в коде (≤7)

1. **Каталог = allowlist типов и пропсов**, валидация схемой ДО рендера; неизвестное = отказ, а не «лучшее усилие».
2. **Фильтр видимости до генерации:** генератор видит только поля, доступные читателю (label/summary/адрес), а не тела. Исполнитель вида повторно режет по читателю при выдаче.
3. **Нет внешних URL в данных вида:** картинки и ссылки только на внутренние id/адреса; без автозагрузки внешних ресурсов (закрывает markdown-эксфильтрацию). Текст рендерится как текст, не как markdown с картинками.
4. **Разрыв «текст записи → решения генератора»:** содержимое записей передаётся как помеченные данные; выбор компонентов и запросов делается из доверенного намерения владельца (идея CaMeL без интерпретатора: спека фиксируется до чтения недоверенных тел).
5. **Действия из вида только из закрытого списка** (open address, link, record-proposed), с подтверждением человеком для записи; писать «proposed», не «active».
6. **Лимиты:** число узлов, глубина, число запросов исполнителя, размер вывода.
7. **Провенанс-метка в хроме, не в генерируемом:** «вид собран ИИ, хеш спеки, источники» рисует каркас, модель не может подделать.

## Граница: стабильный каркас / генерируемое

- **Каркас (неизменно, рисует код):** навигация, место и вид действий, метки доверия и провенанса, индикаторы согласия/видимости, предупреждения, структура «где что». Это то, что нужно для мышечной памяти (вывод из п.1–2, не измерено).
- **Генерируемое:** выбор и порядок блоков из каталога внутри слотов, группировка, плотность, заголовки. Для повторного открытия того же вида: спека закреплена хешем и воспроизводима; меняется только по явному действию «пересобрать».
- Порог в числах литература не даёт; нужен собственный тест (вопрос ниже).

## Инновационные ходы

1. **Вид как закреплённая запись с хешем:** генерация один раз, дальше открытие идёт из зафиксированной спеки; «пересобрать» даёт diff от прошлой версии. Убирает главный провал (нестабильность между показами) и даёт регресс-тест.
2. **Eval без глаз человека на замкнутом каталоге:** три автопроверки: валидность схемы, «утечка» (канарейка-поле, невидимое читателю, не должно появиться в выводе), «инъекция» (запись с вредным текстом не меняет набор компонентов/действий). Прогон на каждом изменении каталога.

## Что не брать

- Интерпретатор кода/выражения во виде (CaMeL целиком): второй язык, против принципа.
- Произвольный HTML/iframe с кодом (MCP Apps целиком): песочница нужна, только если есть код; у нас кода нет.
- Полную «пер-сессионную» генерацию каркаса (genUI по NN/g): ломает обучаемость.
- LLM-судью красоты как единственный eval.
