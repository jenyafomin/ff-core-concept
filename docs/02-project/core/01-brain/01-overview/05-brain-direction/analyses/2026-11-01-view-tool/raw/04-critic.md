## (1) Как провалится
1. **Фронтенд над пустотой.** Граф из 3 узлов не отличим от красивой картинки. Любой выбор React Flow/Cytoscape/tldraw делается без данных, значит вслепую; через неделю выяснится, что нужна не карта, а список.
2. **Генеративный UI = второй язык.** «UI подстраивается под данные» = схема → интерфейс = DSL, прямо запрещённый сводом («не делаем: DSL, фронтенд»). Плюс LLM-генерация окон даёт недетерминизм: тот же вид завтра выглядит иначе, golden-снимки невозможны, V1/V3 не проверить.
3. **Разрыв «агент видит одно, человек другое».** Два адаптера (MCP и окно) к одному исполнителю разъедутся по полям, лимитам, гейту видимости. Человек доверяет картинке, агент решает по тексту; расхождение найдут в проде. V3/V7 нарушаются тихо.
4. **Граф-красота без вопроса.** Условие входа гибкого роста («один реальный вопрос владельца, не покрытый видами») не выполнено: QUESTIONS.md Q1 открыт. Без вопроса критерий успеха = «нравится», это не критерий.
5. **Витрина вместо наполнения.** Рентакар-слой знаний ПДн-чувствителен (V7 не форсится), «новая гибкая память» не наполнится сама. Строим вид — наполнять нечем, и вектор снова уезжает в анализ (docs:code ≈14:1).
6. **Подмена задачи ресёрчем.** Тема сессии = «обсуждать концепт, не строить», но план первого хода — обзор 15 инструментов. Это самый дешёвый способ ничего не решить и назвать это прогрессом.

## (2) Противоречит ли наказ своду
Не противоречит по сути, противоречит по порядку. Свод: исполнитель вида в коде, плоские параметры, «окна = адаптеры», шаги 1–3 ждут «строй». Наказ владельца (линзы для ИИ и человека, UI под данные) ложится как **шаг 1b: ещё один адаптер** к тому же исполнителю, но только если соблюдены: (а) один реальный вопрос; (б) плоские параметры; (в) «UI под данные» понимается как выбор из 3–4 готовых окон (список/таблица/канбан/граф) по форме результата `group_by/fields`, а не генерация. Фраза «UI, который генерируется» — прямой конфликт с «не DSL»; её надо явно сузить или явно отменить запрет (решение владельца, не молча).

Скрытый конфликт: свод написан про память (3 записи), а реальные данные — docs-дерево. Либо вид работает над docs (тогда это не «вид памяти», а индекс git-файлов, другой исполнитель), либо ждёт наполнения памяти. Выбор не сделан.

## (4) Верная постановка
Не «инструмент визуализации», а **«один вопрос → вид → смотрю → следующий вопрос»**. Вид рождается из вопроса (Q7), а не из схемы.
- Шаг A (1 день): взять 3 реальных вопроса владельца к docs/rentacar. Ответить на них текстовым/таблишным видом (скрипт по frontmatter → md/таблица в Telegram). Агент и человек читают ОДИН и тот же вывод (снимок = золотой файл).
- Шаг B (≤2 дня, только если A вскрыл, что таблицы мало): одно готовое окно (граф или канбан) на готовой библиотеке, плоские параметры, без генерации.
- Шаг C: вид возвращается в память как параметры только при втором пользовательском виде (по своду).
- **Критерий провала:** за 3 дня владелец не открыл ни один вид по собственному желанию, либо вопросов не набралось 3; либо агент и человек получили разные числа на одном виде. Тогда стоп, возврат к наполнению памяти.
- **Потолок:** 3 рабочих дня на A+B, 0 строк генеративного UI, 0 новых зависимостей фронтенда до шага B, ресёрч инструментов ≤0.5 дня и только под вопрос, на который таблица не ответила.
