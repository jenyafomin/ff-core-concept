## 1. Цепочка из четырёх звеньев: где гибкость, где пол

| Звено | Что это | Где живёт |
|---|---|---|
| **Вопрос** | «что открыто по мозгу?», «кто с кем связан?» | у человека или агента |
| **Вид** (структура) | плоские параметры: выборка, `group_by`, `fields`, `sort`, `limit` → дерево узлов и рёбер + `view_v` | параметры — **данные**, исполнитель — **код** (один, только чтение, гейт читателя) |
| **Форма** | граф · таблица · канбан · таймлайн · текст | конечный набор рендереров — **код**; выбор формы — **данные** (подсказка) |
| **Адаптер** | MCP · Telegram · web | **код**, тонкий, по одному на канал |

**Кто выбирает форму.** По слоям, сверху вниз:
1. **По умолчанию — по форме данных (shape→form).** Это детерминированно. Есть рёбра → граф. Есть категория статуса → канбан. Есть дата → таймлайн. Одни плоские поля → таблица. Один узел → текст.
2. **Вопрос может переопределить.** Это параметр `form` у вида.
3. **ИИ выбирает только ПАРАМЕТРЫ, но не пишет интерфейс.** Аналогия — грамматика графики (Vega-Lite): описываешь данные и кодировку, ничего не рисуешь руками.

«Генеративный UI» здесь = ИИ заполняет параметры внутри конечной грамматики. Так нет инъекции, есть кэш, а результат воспроизводим.

**Главная развилка оказалась не в интерфейсе.** Чтобы shape→form работал, ТИП должен объявить свою форму: какое поле — время, какое — статус, какое — связь. Это уже лежит в шаге 2 «гибкого роста» (категории статусов). Интерфейс «подстраивается под данные» ровно настолько, насколько данные себя описали.

## 2. Линза — один примитив для агента и человека

**Одинаково:** вид, гейт видимости (не шире читателя), `view_v`, провенанс в выходе. **«Раскрыть» = новый вызов вида с более узким фильтром.** Клик человека и `read` агента — одна и та же операция. Значит, интерфейс человека — это навигация по видам, а не отдельное приложение.

**Различно только в адаптере:**
- **Агенту** нужна плотность. Label и summary вместо тела, бюджет в токенах, усечение с пометкой «ещё N» (V1).
- **Человеку** нужен обзор. Пространственная раскладка, свернуть/развернуть, переход по ребру, светофор.

Одна структура, два «объектива» (ответ на Q2).

## 3. Рефреймы типа Q7

- **R1. Не «инструмент просмотра», а «сохранённый вопрос».** Вид = вопрос, у которого есть имя. Владелец не листает, а спрашивает. Удачный вопрос сохраняется и становится видом.
- **R2. Инверсия: не «UI подстраивается под данные», а «данные объявляют свою форму».** Вся работа уходит в объявления типов. Рендереры — конечный и скучный код, их можно взять готовыми (Cytoscape или Mermaid для графа, любой канбан). Ответ на Q3 и Q4: собираем из готовых окон, а выбор окна генерирует форма данных.
- **R3. «Покажи, что видит агент».** Самый ценный вид для человека — это контекст, который линза собрала агенту под задачу. Тогда визуализация = аудит доверия (V3), а не витрина.

**Вопрос, который вскрывает неверную рамку:** «Если завтра появится идеальный граф памяти — какое решение ты примешь иначе, чем сегодня?» Если ответа нет, боль не в «увидеть», а в «решить или найти». Тогда нужен вопрос-инструмент (R1), а не карта.

## 4. Самый дешёвый тест на реальных данных

**Дерево `docs/` FF уже имеет форму:**
- папки = иерархия;
- frontmatter `status` и `date` = статус и время;
- `related` = рёбра;
- суффикс `.{type}.md` = тип.

Это сотни узлов, без ПДн (rentacar отпадает по V7).

**Тест (≈1 день, без фронтенда и без правки мозга):**
1. Скрипт-исполнитель читает `docs/` → узлы и рёбра.
2. На тех же данных применить shape→form. Должны получиться 4 формы: дерево или граф `related`, канбан по `status`, таймлайн по `date`, таблица по типу. Вывод — Mermaid или markdown в Telegram.
3. Ответить на реальный вопрос владельца (Q1), например: «что в треке мозга draft и не трогалось больше 2 недель». Ответ дать в двух адаптерах: человеку — форма, агенту — плотный текст.

**Критерий:**
- форма выбрана автоматически верно в ≥3 из 4 случаев;
- новое поле во frontmatter даёт новую группировку без правки кода;
- владелец получил ответ, которого сейчас не видит.

**Провал:** если формы приходится раскладывать руками — значит, тип не описал себя, и строить надо объявления, а не UI.

Этот тест проверяет концепт вида, а не сам ff-brain. Но docs и так попадут в память через `source.ref`, так что тест переносится.

## 5. V1–V7 коротко
- **V1** — укрепляет: label/summary, бюджет агента, «раскрыть» по цене. Риск — граф, который грузит всё тело.
- **V2** — узел формы держит `id`. Форма — проекция, она не создаёт копий.
- **V3** — выход подписан видом и `view_v`. R3 превращает вид в аудит. Напряжение: параметры, придуманные ИИ, нужно показывать как «вывод агента».
- **V4** — остывшее (`cold`) по умолчанию свёрнуто, но не исчезает.
- **V5** — параметры вида и объявление формы переносимы. Рендереры заменяемы, данные к ним не привязаны.
- **V6** — граф показывает рёбра как полноправные элементы со своим паспортом. Висящее ребро видно как сироту.
- **V7** — вид не шире читателя, и человек видит не больше агента с теми же правами. Честно: согласие пока только в форме, поэтому тест идёт на docs, а не на данных о людях.

Итог: задача в плане — тест §4 как условие входа в шаг 1 гибкого роста; фронтенд отложен до прохождения теста.

Вопрос-цель: ответил. Вид-контракт становится интерфейсом без ручной вёрстки через цепочку «тип объявляет форму → shape→form → конечный набор рендереров → адаптер». Агент и человек делят одну линзу, разница только в адаптере. Рамку вскрывает вопрос: «какое решение ты примешь иначе, увидев идеальный граф?»
