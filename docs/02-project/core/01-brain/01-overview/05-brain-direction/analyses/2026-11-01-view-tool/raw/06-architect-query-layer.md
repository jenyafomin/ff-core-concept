Потребитель: свод волны 11-01 + владелец (развилка «GraphQL?»). Поглощает: ничего.

## Реальность (на что опираюсь)
- Микро-запрос по графу у нас УЖЕ есть: `read` = обход рёбер с ограничениями: глубина ≤2, узлов ≤50, фильтр по типу связи `preds` (`brain/src/contract.ts` LIMITS `readDepthMax:2`, `readMaxNodesMax:50`; `read/traverse.ts`). По сути это и есть «GraphQL с глубиной ≤2», только формой зашитый в код.
- Гейт видимости стоит ОДИН раз, на весь набор записей: `visibleRecords(gate)` до любых фильтров (`read/find.ts`). Каждая запись проверяется до того, как дальше идёт выборка. Это «один вход — один гейт», а не проверка в каждом резолвере.
- Транспорт: HTTP/JSON по unix-сокету, Bearer, личность только из заголовков, `CONTRACT_VERSION=1`, копия контракта в brain-mcp сверяется тестом (`service/http.ts`). Хранилище — журнал в памяти процесса, полный проход (scan) на каждый find.
- Объём: 3 записи, рёбер почти нет.

## (1) Сравнение
| | GraphQL | Расширенный find (плоские параметры) | Вид = именованный набор параметров |
|---|---|---|---|
| Гибкость | максимальная: любая форма ответа | средняя: `group_by/fields/sort/фильтры` | как у find + повторное использование |
| Предсказуемость (стоимость, глубина, N+1) | нужны свои ограничители (глубина, сложность, лимиты на списки); N+1 по рёбрам лечится DataLoader-ом | стоимость = один проход + сортировка, верхняя граница известна | то же + заранее известный набор |
| Безопасность (V7) | гейт обязан стоять у каждого резолвера рёбер/полей; одна забытая связь = утечка; интроспекция показывает форму типов | один гейт на входе, как сейчас | то же; вид не шире читателя |
| Версия контракта (V5) | эволюция без версий: поля помечаются устаревшими (`@deprecated`), но схема — второй контракт рядом с `CONTRACT_VERSION` | один контракт, `view_v` | параметры вида = переносимые данные |
| Агенту через MCP (V1) | агент пишет текст запроса → дорого по токенам и легко ошибиться; инструмент «выполни GraphQL» = свободный язык в руках LLM | плоский JSON, схема инструмента самоописывается | `view: "<имя>"`, дешевле всего |

Вывод: у GraphQL выигрыш по гибкости, а за предсказуемость и безопасность он требует строить заново то, что у нас уже есть бесплатно (один гейт, жёсткие потолки). Кроме того, он прямо нарушает запрет 10-26 «без DSL/вложенности». Граф-форму лучше дать двумя плоскими шагами (`find` → `read depth≤2`), а не вложенным запросом.

## (2) Схема из данных-типов
Технически реально: типы уже лежат данными (`definitions.ts`), а схему можно собирать при старте. Чем грозит:
- Схема меняется под клиентами. Владелец утвердил новый тип или поле, и у клиентов сломались закешированные запросы и сгенерированные типы. Сломается и тест на совпадение копии контракта.
- Открытые поля `fields` в схеме станут либо `JSON` (тогда GraphQL ничего не даёт), либо жёсткими полями, и тогда тип, объявленный данными, начнёт ломать контракт.
- Если интроспекция отдаёт один набор типов всем, она раскрывает чужие типы и области (V7). Значит, схема должна быть своей у каждого читателя, а это ещё сложнее.
Если всё же делать: генерировать только добавлением, удалённое поле = `@deprecated` минимум одну версию, интроспекция выключена, схема снимается слепком и версионируется.

## (3) Persisted queries / allow-list
Это действительно путь «гибко, но под контролем»: клиент шлёт хэш или имя, сервер выполняет только заранее одобренный запрос. Но если вдуматься, persisted query и есть наш «вид = именованный набор параметров», просто записанный на языке GraphQL. Контроль даёт allow-list, а не GraphQL. Его можно получить и без второго языка: именованный вид (параметры + автор + кто утвердил, V3) — это ровно allow-list.

## (4) Postgres
- Расширенный find плоско ложится на SQL: `WHERE` по полям (jsonb `fields`), `GROUP BY`, `ORDER BY`, `LIMIT`; гейт = row-level security или предикат по областям. Обход `read depth≤2` = рекурсивный CTE с лимитом.
- GraphQL поверх PG (PostGraphile / Hasura) — соблазн «схема из таблиц», но тогда контракт будет выведен из устройства хранилища и привяжет данные к движку (V5 нарушен). Гейт придётся переносить в RLS, и он разъедется с кодовым гейтом.
- Правильный шов: порт хранилища под исполнителем вида. Запрос (как ни выглядит снаружи) → один исполнитель → порт (журнал сегодня, PG завтра).

## (5) Рекомендация
**Сейчас (ничего нового сверх 10-26):** расширенный find с плоскими параметрами, именованные виды как allow-list, `view_v` в ответе. Граф-запрос = `read` (уже есть). Добавить в `read` один фильтр «тип узла на выходе», если попросит живой случай.
**Потом (после PG):** порт хранилища, исполнитель транслирует параметры в SQL/CTE.
**GraphQL — только по триггеру, в узкой форме.** Триггер: ≥2 реальных клиента-программы (не агенты) с ≥3 разными формами вложенного ответа, которые не собираются из `find`+`read` за ≤2 вызова. Или owner-UI с графом, которому нужен N-уровневый fetch за один заход. Форма: только чтение, без мутаций · глубина ≤2 (как `readDepthMax`) · лимиты на списки ≤50 · только persisted queries, интроспекция выключена · каждый резолвер вызывает тот же исполнитель/гейт (GraphQL — адаптер, а не новое ядро) · схема снимается слепком и версионируется, не генерируется на лету. Агентам GraphQL не даём: MCP остаётся на плоских параметрах.

## Тезисы ADR (если сработает триггер; сейчас ADR НЕ нужен — новых решений сверх 10-26 нет)
1. Контекст: запросы клиентов-программ, которые не покрывает find+read; есть Postgres.
2. Решение: GraphQL = адаптер чтения над единым исполнителем вида. Ядро, гейт и потолки остаются в коде.
3. Инварианты: без мутаций; глубина ≤2; только persisted; интроспекции нет; гейт в исполнителе, а не в резолверах; схема — версионированный слепок, меняется только добавлением.
4. Отвергнуто: «схема из таблиц PG» (V5), «GraphQL как MCP-инструмент» (V1, свободный язык у LLM), «схема на лету из типов» (ломает клиентов).
5. Проверка: golden-тест «GraphQL-ответ = find/read-ответ» на одних и тех же видах; тест утечки (запрос по чужому ребру → пусто); тест глубины/стоимости (3-й уровень → отказ).

Вопросы, вскрывающие рамку: что владелец не может получить сегодня за два вызова `find`→`read`? Нужна ли гибкость самим запросам, или нужна она описаниям ТИПОВ, из которых виды выводятся?

Итог: решение — GraphQL сейчас не делаем. Расширенный find + именованные виды = allow-list; GraphQL отложен до триггера (≥2 клиента-программы с вложенными формами или граф-UI после PG), в узкой форме адаптера.

Вопрос-цель: ответил. Нет: тот же контроль дешевле даёт вид-как-именованный-запрос поверх одного исполнителя; GraphQL — поздний узкий адаптер, а не слой ядра.
