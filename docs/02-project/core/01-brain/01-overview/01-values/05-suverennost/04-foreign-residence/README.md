## Суть

Объект суверенности здесь — **МЕСТО ЖИТЕЛЬСТВА payload**. Суверенность включает право ячейки жить **НЕ
в родном движке**: быть **прокси** на внешнюю БД (foreign-data-wrapper) — паспорт локально, payload по
API+кэш; конфигурироваться из общего конфига через адаптер (Г22/Г30, напр. Telegram); материализоваться
на выбор: **live / кэш / замороженная копия** (Г34). Модуль с большими данными выносится в свою личную
БД, сам управляет, отдаёт через API с чёткой инструкцией (Г27).

## Границы

- **Входит:** прокси-ячейка (FDW): payload = рецепт получения, не данные; хранимая **инструкция КАК себя
  достать** (Г33); материализация live/cached/frozen как статусное поле (Г34); кэш с политикой удаления;
  адаптер/общий конфиг источников (Г22/Г30); внешняя БД модуля за API (Г27/Г29); what-if песочница
  copy-on-write (данные, не трогая оригинал).
- **НЕ входит:** самоописание формы → `01`; правила доступа/забывания → `02`; версия контракта с движком
  → `03`; ключ доступа к внешней БД → `05 ownership-keys`.
- **Тонкая граница с 05:** здесь — «ГДЕ лежат данные и как их достать»; в 05 — «каким КЛЮЧОМ и по чьей
  власти». Прокси без ключа (05) — пустая оболочка; но это разные объекты защиты.

## Развилки (веер «как», не режем)

1. **Что внутри прокси-ячейки.** Только рецепт+`source_id` [+ лёгкая / − ничего не видно без вызова API]
   vs рецепт + кэшированный корешок-паспорт для дешёвой оценки (Ц-1 «оценить не вскрывая») [+ Г1 работает
   локально / − кэш протухает] vs рецепт + last-known snapshot payload.
2. **Материализация (Г34).** Всегда live (каждый доступ → внешний вызов) [+ свежесть / − latency, зависимость]
   vs кэш с TTL/политикой удаления [+ быстро / − устаревание] vs замороженная копия (снапшот) [+ автономна,
   аудит / − расходится с источником] — **одна ячейка может быть в разных материализациях у разных владельцев**.
3. **Кто держит рецепт доступа.** Внутри ячейки (Г33, самодостаточна) [+ едет с ней / − секрет доступа
   рядом с данными → шов с 05] vs в общем конфиг-адаптере (Г22/Г30), ячейка ссылается [+ дедуп, ротация
   в одном месте / − при переносе нужен конфиг].
4. **Модель федерации.** Read-through прокси (движок сам ходит в API) [+ прозрачно / − движок знает про
   внешнее] vs sidecar-адаптер на источник (Г27, модуль сам отдаёт) [+ инкапсуляция / − доп. сервис] vs
   импорт-и-забыть (разовая миграция в родной движок) [+ автономно / − теряем «живость» источника].
5. **Инвалидация кэша.** Хард-удаление по TTL (Г27) [+ просто / − можем потерять нужное] vs
   инвалидация по сигналу источника (webhook/versioning) [+ точно / − нужна связь] vs
   волатильность-политика из `02` управляет кэшем [+ единый метаболизм / − связывает 04↔02].
6. **What-if песочница.** Copy-on-write форк payload для «а что если» [+ безопасно эксперименты / − форк
   расходится → тождество Ц-2] vs materialized view только для чтения [+ дёшево / − нельзя менять].
