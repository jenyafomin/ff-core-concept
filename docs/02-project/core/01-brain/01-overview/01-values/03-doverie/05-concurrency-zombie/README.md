## Суть

Доверие рушится не только внутри одной записи — оно тихо деградирует, когда несколько агентов пишут
confidence ОДНОВРЕМЕННО без протокола, когда порог видимости расходится между каналами извлечения
(«зомби-память»: где-то запись уже забыта, но всплывает в другом канале), и когда деградирует не сама
запись, а СВЯЗЬ между двумя записями об одном факте (Sonnet #7, из исходной ценности). Объект защиты —
**множественность писателей/каналов**, а не отдельная запись сама по себе.

## Границы

- **Входит:** разрешение конфликта параллельной записи confidence (DB-control «последний победил» vs
  явный merge-протокол); единый порог видимости/доступа на ВСЕ каналы извлечения (устраняет зомби-
  память по конструкции, а не по дисциплине); явное заявление конфликта между двумя записями об одном
  факте, видимое ТРЕТЬЕЙ стороне (Г17), вместо тихого затирания одной версии другой.
- **НЕ входит:** механизм самоаннулирования ОДНОЙ уже-опровергнутой записи (→ 04 supersession-audit);
  кто ВПРАВЕ разрешить обнаруженный конфликт (→ 03 poisoning-defense, авторизация); содержательная
  причина расхождения фактов — это может быть вопрос Тождества («та же ли это память») или Реляционности
  (механика самого ребра-конфликта в графе); здесь — только доверительный аспект: какой confidence
  присвоить каждой стороне, пока конфликт не разрешён.
- **Тонкая граница с Ц-6 Реляционность:** там — как ребро-конфликт ПРЕДСТАВЛЕНО в графе (тип ребра,
  куда оно ведёт); здесь — как ТРАКТОВАТЬ confidence двух конфликтующих записей, пока конфликт открыт
  (понижать обе? оставить как есть? кто-то один «замораживается»?).

## Развилки

1. **Разрешение конкурентной записи confidence.** Last-write-wins / DB-control (последний пишущий
   побеждает) [+ просто, без блокировок, дёшево / − теряется сигнал более раннего агента, результат
   недетерминирован в зависимости от того, кто «успел последним», прямое нарушение цели предсказуемости]
   vs явный merge-протокол (агрегация нескольких сигналов использования по формуле) [+ честнее отражает
   реальный консенсус нескольких агентов / − сложнее реализовать, требует времени на согласование или
   очередь] vs версионирование обоих (bitemporal, обе версии видны, конфликт явный, никто не побеждает
   автоматически) [+ ничего не теряется, честно перед аудитом / − кто-то ДОЛЖЕН разрешить это потом,
   иначе висит неопределённость].
2. **Единый порог доступа vs порог per-канал.** *(сквозной спин, см. `../README.md`)* Один порог
   видимости на ВСЕ каналы извлечения — API, поиск, резонанс-push одинаково уважают «забыто» [+ по
   конструкции не бывает зомби-памяти / − требует единой точки правды на все интеграции, дороже
   архитектурно, каждый новый канал обязан подключиться к ней] vs разные пороги на разных каналах (по
   историческим причинам — интеграции писались в разное время) [+ дешевле встроить новый канал / −
   прямой путь к «зомби»-памяти: забытое в одном канале продолжает всплывать в другом, единый порог
   доступа — открытый вопрос TQ3 из исходной ценности: инженерное требование или конституционный
   инвариант].
3. **Заявление конфликта — явное ребро vs тихая перезапись.** Явное отдельное ребро `conflicts-with`,
   видимое третьей стороне при чтении любой из двух записей (Г17) [+ прозрачно, конфликт можно разрешить
   осознанно, а не притвориться, что его нет / − новый тип ребра, кто-то должен его создавать и следить,
   что оно не висит вечно] vs тихая перезапись более новой версией без следа [+ просто, ничего
   дополнительного строить не нужно / − деградация доверия ко ВСЕМУ графу происходит незаметно —
   именно сценарий Sonnet #7 из исходной ценности].
4. **Кто замечает конфликт первым.** Движок при записи — сравнение с существующими фактами на лету
   [+ ловит конфликт сразу, не даёт ему распространиться / − дорого при каждой записи, нужна семантика
   сравнения «это об одном и том же»] vs фоновый процесс-«садовник», периодически сверяющий граф
   [+ дешевле в среднем случае / − окно, в котором конфликт уже разошёлся по производным/агрегированным
   узлам (пересечение с 03, contagion threshold)].
