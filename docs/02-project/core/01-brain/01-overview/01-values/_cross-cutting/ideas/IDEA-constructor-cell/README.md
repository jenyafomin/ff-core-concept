# IDEA · Конструктор-ячейка (один узел → что угодно)

> Статус: draft · Дата: 2026-07-08 · Родитель: [../../README.md](../../README.md)

## Суть

Единица памяти — не набор разных типов файлов/сущностей (задача, человек, сообщение, файл,
метрика — как отдельные схемы), а **один универсальный "конструктор"-узел**, который
СТАНОВИТСЯ чем угодно через внутреннюю типизацию/индексацию. Снаружи — единый интерфейс узла
(id, связи, метаданные, политика); внутри — слот, который наполняется под конкретную роль
(пользователь / система / сообщение / задача / …), и эта роль сама несёт свою структуру
(policy-as-data — ячейка знает "что я есть").

Отличие от классической полиморфной схемы БД: типизация не фиксируется на уровне таблицы/схемы
раз и навсегда, а является ЖИВЫМ атрибутом ячейки, который может уточняться, расширяться,
переопределяться — потому что сама природа памяти agent-first подразумевает, что новые роли
узлов появятся уже после того, как система запущена (новый plug-in подключил пользователь →
новый тип узла не должен требовать миграции схемы).

## Какие ценности задевает

- **Ц5 Суверенность** — прямое попадание: "единица носит СВОЮ политику и рецепт доступа →
  живёт в любом движке" — конструктор-ячейка это буквальная реализация этой идеи.
- **Ц2 Тождество** — типизация ячейки это часть того, "что это" — конструктор должен уметь
  сохранять тождество при смене/уточнении типа (не терять id и историю при "превращении").
- **Ц1 Читаемость** — риск: универсальный конструктор может стать нечитаемым "блобом" без
  явной типизации на поверхности; нужен баланс — гибкость внутри, ясность снаружи.
- **Инвариант движка (К-2, масштаб)** — универсальный узел без индекса по типу может стать
  узким местом на больших объёмах (полный скан вместо типизированного индекса); конструктор
  обязан сохранять индексируемость каждой роли, иначе конфликт с масштабом.

## Открытые вопросы

- Где граница "один узел = всё" против "слишком абстрактно, чтобы быть полезным"? Нужен
  конкретный контракт минимального набора полей, общих для ЛЮБОЙ роли (id, author — см. К-1,
  referent, source, timestamps bitemporal), и опциональных полей "под роль".
- Кто решает, когда конструктор "стал" новым типом (авто-типизация агентом vs явная разметка
  пользователем)? Пересекается с идеей auto-index-wave.
- Совместимо ли это с engine-contract-version (уже упомянуто в Ц5) — версионирование самой
  формы конструктора при эволюции схемы.
