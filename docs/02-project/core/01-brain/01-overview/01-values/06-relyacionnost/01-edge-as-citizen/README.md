## Суть

Ребро — не пара указателей `from_id/to_id` внутри узла, а самостоятельная мини-ячейка: у него есть
`id`, паспорт (кто/когда/зачем/каким актом заявил связь), опциональные `salience`/`confidence`, и —
для узкого класса рёбер-утверждений — собственный жизненный цикл. Объект защиты — **факт
существования связи как утверждения**, которое можно найти, атрибутировать и не спутать с
утверждением о самих узлах.

## Границы

- **Входит:** хранение ребра как отдельной адресуемой сущности (property-graph/RDF-star-стиль);
  авторство ребра отдельно от авторства узлов (кто именно заявил связь — человек, агент, движок);
  узкий паспорт для рёбер-утверждений (В4); опциональный lifecycle `nascent → confirmed → stale`.
- **НЕ входит:** что ИМЕННО означает тип связи и как он ведёт себя при удалении стороны (→ 02);
  пересчёт `confidence`/устаревания как процесс во времени (→ 04, здесь — только факт, что поле
  есть); конфликт, когда два владельца узлов спорят за одно ребро (→ 06, мультиарендность).
- **Тонкая граница с 02:** здесь решается «ЕСТЬ ли у ребра паспорт и кто автор», там — «что тип
  ребра ОБЯЗЫВАЕТ движок делать физически».

## Развилки

1. **Хранение ребра.** Отдельная сущность с `id` (property-graph/RDF-star) [+ полноценный паспорт
   и версия ребра / − вдвое больше сущностей, тяжелее движок] vs атрибут узла (список ссылок в
   JSON-поле) [+ просто, дёшево / − провенанс и версия ребра теряются, RQ1]. В4 уже сузило спор:
   паспорт нужен не всем рёбрам, только рёбрам-утверждениям.
2. **Кто автор связи.** Явная роль «заявитель» отдельно от авторов узлов (тема A прежнего цикла)
   [+ точная атрибуция агентского инсайта / − новое обязательное поле на каждое ребро] vs
   наследование авторства от узла-источника [+ ничего нового не считать / − теряется «чьё именно
   это утверждение», критично для инсайтов агента между чужими узлами].
3. **Lifecycle ребра.** Свой `nascent → confirmed → stale`, синхронный с Согласием (Ц-7: агентский
   инсайт ждёт подтверждения референта) [+ единое правило с узлом, агент не может тихо «утвердить»
   связь / − второй lifecycle-движок, сложнее] vs ребро сразу «живое» без стадии ожидания [+ проще
   реализовать / − связь между чужими узлами может появиться без спроса].
4. **Гранулярность паспорта.** Полный паспорт узла на каждом ребре [+ единообразно, один code
   path / − тяжело для 95% структурных рёбер (`home`, `facet-of`), которым это не нужно] vs узкое
   подмножество только для рёбер-утверждений (В4-решение) [+ дёшево для структурных рёбер / − две
   ветки схемы, сложнее API и запросы].
