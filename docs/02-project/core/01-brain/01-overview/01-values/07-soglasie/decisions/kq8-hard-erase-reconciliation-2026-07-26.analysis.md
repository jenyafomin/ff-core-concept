## 0 · TL;DR
- **Совет и SPEC-DRAFT НЕ противоречат — они на разных высотах.** SPEC-DRAFT = инженерный механизм
  (R1-R6/A1-A5/T1-T5). Совет = семантический разбор («удаление» = 3 несвязанных обязательства) + сдвиг
  фокуса на **admission-gate** (решение дня-1, а не времени удаления).
- **Единственное настоящее концептуальное ДОБАВЛЕНИЕ совета к канону:** (1) явный **split иммутабельных
  `acts` ⟂ стираемого `payload`** через ref+hash как предусловие настоящего consent-эрейжа; (2) перенос веса
  с «стереть потом» на «не впускать в канон сейчас» (admission-gate); (3) требование оформить это как
  **I-15 + ADR-0007** (чего в SPEC-DRAFT нет).
- **Дом остаётся один:** `./SPEC-DRAFT-forgetting-hard-erase.md` (инженерный механизм) + этот файл (свод и
  дельта) + ADR-0007 (архитектурное решение). Совет-синтез (`kq8-deletion--council-...`) остаётся как ВИД
  дня совета, но перестаёт быть параллельным «вторым каноном» — он теперь читается ЧЕРЕЗ эту карту.

## 2 · Несущая конструкция реконсиляции: split `acts` ⟂ `payload`

Ось, вокруг которой всё сходится (объединяет SPEC R4 tombstone + совет-split + MERGE-NOTES «erasable payload
separation»):

```
АКТ (иммутабелен, I-4/I-3, append-only)                     PAYLOAD (стираем)
┌───────────────────────────────────────┐                  ┌────────────────────────────┐
│ id · actor · provenance · recordedAt   │  ── ref+hash ──▶ │ содержимое (текст/PII/blob) │
│ act-kind · edges (рёбра целы, I-1)     │   (указатель +   │ живёт в отдельном payload-  │
│ tombstone-факт «здесь было / стёрто»   │    контент-хеш)  │ store / key-store           │
└───────────────────────────────────────┘                  └────────────────────────────┘
     остаётся ВСЕГДА (replay детерминирован                       можно физически purge
     ДО границы: «был акт с таким hash»)                          или crypto-shred по согласию
```

- **Replay остаётся детерминированным-ДО-границы:** журнал воспроизводит «был акт X с payload-hash H, затем
  payload стёрт актом erase» — а не воскрешает контент. Это и есть **carve-out к I-4**: неизменяемость акта
  сохраняется, но «неизменяемость» распространяется на *координаты и факт*, НЕ на *содержимое payload*, которое
  по дизайну отделяемо и стираемо. Граница эрейжа детерминирована.
- **Три режима — это три политики над этой одной осью:**
  - **(A) tombstone + hide** — payload помечен hidden (soft-sleep, salience→0) ИЛИ tombstoned, но НЕ стёрт.
    Дёшево, обратимо (для soft-sleep), детерминированно. **НЕ erasure.**
  - **(B) crypto-shred** — payload зашифрован ключом из отдельного key-store; эрейж = уничтожение ключа →
    контент математически невосстановим. **Единственный настоящий consent-эрейж.** Сам эрейж пишется КАК акт.
  - **(C) plugin-removal** — снят плагин-владелец типа; payload выживает (I-12), рендерится fallback-ом
    «unknown-type». **Вообще не про забвение** — про эволюцию модели.

## 3 · Admission-gate — настоящее решение дня-1 (перенос веса)

Ключевой сдвиг совета: **самый сильный контроль над «правом быть забытым» — не удалять хорошо, а не впускать
сверх-чувствительное в неизменяемый канон вообще.**

- Данные, которые слишком чувствительны, чтобы стать иммутабельным актом, должны **с момента записи** жить в
  **эфемерной / неканонической полосе** (TTL, вне append-only журнала, вне replay).
- Это решение **схемы дня-1** (свойство типа/потока), а не решение времени удаления.
- Связка с ADR-0006: это новый вид размещения-политики-на-тип (I-11) — «canonical | ephemeral». Не физический
  дом, а **эпистемический статус потока**: canonical (append-only, переживает) vs ephemeral (истекает, не в логе).
- Связка с ADR-0007 §crypto-shred: admission-gate + crypto-shred — **комплементарны**. Admission решает «а надо
  ли вообще это в канон»; crypto-shred решает «то, что в каноне, но с PII — как стереть по согласию».

## 4 · Нерешённые трещины (НЕ замазывать — выносим как открытые)

Совет и MERGE-NOTES честно оставили эти швы открытыми. Реконсиляция их НЕ закрывает — фиксирует как явные
открытые вопросы для ADR-0007 §Открытые и/или owner-развилки:

1. **Гранулярность ключа vs collateral-erasure.** Если crypto-ключ покрывает целый сегмент, уничтожение ключа
   стирает и **co-referents** (соседние данные под тем же ключом). Гранулярность ключа (per-node? per-referent?
   per-field?) не решена → риск сопутствующего стирания. **OPEN.**
2. **Taint-closure уже эмитированных производных (C-offgraph / «SLOMAN»).** Сводки/копии, ушедшие ВНЕ графа
   (Telegram-сообщение, экспорт, кэш получателя), механизмом hard-erase НЕ покрываются. В прошлой архивной
   критике оценено как **«SLOMAN»** (не решено). MERGE-NOTES §C-offgraph — та же дыра в A1-A5. **OPEN, вероятно
   принципиально неполно-решаемо** (внешние копии вне нашего контроля). ADR-0007 должен ЧЕСТНО заявить границу
   scope: эрейж гарантирован ВНУТРИ субстрата, не в утёкших внешних копиях.
3. **Metadata-residue.** Сам факт существования (tombstone, «здесь что-то было и стёрто по требованию») —
   неустраним в append-only. Для части legal-эрейж-режимов даже метаданные факта — утечка. **OPEN, признаётся
   неустранимым** в append-only; admission-gate (§3) — единственный обход (не впускать вовсе).
4. **R-ERASE / примат референта** (из MERGE-NOTES) — приоритет ролей при конфликте прав на забвение. Совет не
   адресовал. **OPEN.**
5. **Каскад по потомкам (consent-taint, SPEC R5 / FQ7)** — эрейж узла vs эрейж его lineage-производных; параметр
   каскада. **OPEN** (SPEC уже держал открытым).
6. **🔧 `shred` против file-first-payload (CRITICAL, риск #1 критика; добавлено B3-d 2026-07-27).** Crypto-shred
   недоказуем против payload file-first-типов, физически лежащего в **git-истории** (ADR-0006 §g): обычная
   правка файла не стирает историю (нужен деструктивный history-rewrite, избегаемый git-правилами). Значит
   режим удаления `shred` гарантирован **ТОЛЬКО для DB-first-payload**; для file-first честный максимум —
   `hide` (tombstone). **OPEN — уходит в отдельный совет «эрейж ⟂ file-first/git» (Блок 4), смыкается с Г20**
   (память о третьем лице). Задокументировано в `ADR-0007 §b + Consequences + OQ-7`. Здесь фиксируем только
   границу — сам механизм НЕ решаем.
