# Q-ERA-07 — Тайминг key-store Стадии-2

> Узел-вопрос с потенциалом роста. Обсуждение — ВНУТРИ. Может дорасти до раздела ADR-0008.

## Суть
Крипто-shred (стирание по ссылке через уничтожение ключа) требует **key-store**. Заложить его шов
**СЕЙЧАС** (M1) как ретрофит-невозможный (как был заложен рано раскол payload/act) — или **ждать**,
пока реально появится бэкап/реплика, где он понадобится?

## Природа: чистый размен во времени, НЕ условие данных
Это не «оба-под-условием» — нет природного предиката на данных. Это **бет во времени**:
- **Заложить сейчас** [+ ретрофит потом невозможен, шов не пропустим / − цена и сложность до нужды].
- **Ждать** [+ не строим лишнего рано (over-proof — риск переписи) / − если понадобится, ретрофит
  через append-only лог может быть невозможен].

## Что бы это решило
Явный тайминг-вердикт владельца/архитектуры. Зависит от того, насколько реально/скоро появятся
вторые хранилища (бэкапы, реплики, плагинные сторы).

## Зацепки
- **Q-ERA-01r вариант (b)** (keyed-shred свидетеля) — если его выбирают, key-store нужен сразу → этот
  вопрос перестаёт быть отдельным.
- **ADR-0007 OQ-1** (гранулярность ключа vs коллатеральное стирание) — та же территория, дом в ADR-0007.

## Вердикт Fable (2026-08-06) — РЕШЕНО (T3), ждёт ратификации
**Ждать МАШИНЕРИЮ key-store; заложить МИНИМАЛЬНЫЙ шов сейчас** — зарезервировать поле `hashScheme`
(+ опц. `keyId`) в формате акта-свидетеля + одно правило-гейт: «никакой второй копии (бэкап/реплика/
экспорт) до Стадии-2 ключей ИЛИ явной метки-честностного-понижения». Разлом рамки: предикат ЕСТЬ —
**топология: одна копия vs много**. Первый бэкап с plaintext-payload = горизонт событий, которого
крипто-shred уже не достанет → «ждать, пока появится бэкап» = слишком поздно; честный триггер — ДО него.
Формат акта пишет замороженные байты с 1-го дня (ретрофит невозможен), а key-store — сервис, не
поверхность данных (лишь дорого потом, не невозможно).
**Сцепка с Q-ERA-01r:** если принят ход (d) 01r (соль-в-blob), key-store-машинерия **не нужна вовсе** —
этот вопрос почти растворяется; поле `hashScheme` всё равно резервируем.
→ `fable-keystore-timing.advisory.md`.

**Наименьшее первое решение:** зарезервировать `hashScheme` в свидетеле (R0/R1, только спека).

## Статус
**РЕШЕНО Fable (T3) → ждёт ратификации; зависит от 01r.**
