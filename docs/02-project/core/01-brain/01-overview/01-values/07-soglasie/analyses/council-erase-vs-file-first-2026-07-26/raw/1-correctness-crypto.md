# Линза 1 · Корректность / крипто

Позиция: «а математически/механически эрейж вообще доказуем на этом субстрате?»

## 1. Что crypto-shred на самом деле гарантирует (и чего НЕ требует)
- Crypto-shred = payload зашифрован at-rest ключом из отдельного стора; эрейж = **уничтожение ключа** →
  ciphertext становится вычислительно бесполезен.
- **Ключевое следствие:** shred **НЕ требует догонять все копии ciphertext.** Можно оставить шифротекст
  где угодно (бэкапы, реплики, даже git) — убил ключ → контент невосстановим. Это и есть сила метода:
  он решает то, что физический purge не решает (недосягаемые копии).

## 2. Но: crypto-shred и plaintext-file-first взаимоисключающи ДЛЯ ОДНОГО payload
- Чтобы file-first-контент был shreddable, его надо хранить **зашифрованным at-rest**.
- Зашифрованный = НЕ human-readable, НЕ hand-editable, НЕ git-diffable, НЕ портативный глазами.
- Это убивает ВСЮ ценность file-first (ADR-0006(g): «человеческий контент, что владелец правит руками»).
- **Вывод: нельзя иметь один и тот же payload одновременно plaintext-в-git И crypto-shreddable.**
  Развилка не property-изируется на уровне механизма — она решается на уровне **класса payload**
  (что вообще пускать в git), не на уровне «как стирать».

## 3. Новая находка — `payloadHash` в иммутабельном акте = остаточный канал для low-entropy PII
- ADR-0007(a)/I-15: акт хранит `payloadHash` навсегда (иммутабелен, carve-out его НЕ трогает).
- Если это хеш **plaintext** низкоэнтропийного PII (телефон, имя, номер документа, email) — после shred
  **сам хеш в неудаляемом акте подтверждает значение**: атакующий с хешем брутфорсит/сверяет по словарю.
- Значит эрейж НЕПОЛОН: контент «стёрт», но иммутабельный акт продолжает выдавать его хешем.
- **Требование корректности (не просто open):** для erasure-eligible PII-payload в акте хранить
  **keyed/salted-хеш (HMAC с ключом, который сам shredded)** ИЛИ хеш ciphertext — не голый content-hash.
  Это расширяет OQ-3 (metadata-residue) из «tombstone-факт» в «хеш-канал».

## 4. Content-addressable store × дедуп × shred (питает OQ-1)
- CAS адресует по хешу контента → идентичный контент двух референтов = один блоб = один адрес.
- Shred по одному референту убивает блоб → **collateral-erasure второго** (или наоборот, дедуп мешает
  стереть). Дедуп и erasability конфликтуют.
- **Жёсткое ограничение к OQ-1:** гранулярность ключа/блоба для erasure-eligible payload **≥ per-referent**;
  дедуп НЕ пересекает границу референта. Иначе shred либо неполон, либо сопутствующе стирает соседей.

## 5. Каскад (питает OQ-5)
- Shred узла без каскада на lineage-производные (эмбеддинги, сводки, insight-рёбра, кэши) = неполон:
  контент восстановим из производной. Для in-substrate — обязателен обход по DataResidency (SPEC R3).
- Для off-graph производных (ушедших наружу) — недосягаемо (см. линза 2/3, OQ-2). Граница.

## Вердикт линзы
Crypto-shred **корректен и доказуем** — но ТОЛЬКО когда: (1) payload off-git и зашифрован/удаляем;
(2) хеш в акте не реверсится для low-entropy PII (keyed); (3) ключ ≥ per-referent (нет collateral);
(4) каскад по in-substrate производным. Plaintext-в-git НЕ shreddable в принципе — для него честен
только tombstone/hide. Развилка решается классом payload, НЕ механизмом стирания.
