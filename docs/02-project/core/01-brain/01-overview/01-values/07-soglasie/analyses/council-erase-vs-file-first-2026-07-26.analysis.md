# 🔴 Совет «истинный эрейж ⟂ file-first/git» — синтез-вердикт

> Фаза = DESIGN. Совет адверсариальный, 4 линзы (корректность/крипто · юр/GDPR · архитектура хранения ·
> доверие/этика-Г20). Ничего не пишу в канон/ADR/invariants (ждёт «строй»). Это output совета B4-a.
> Сырьё линз — `./council-erase-vs-file-first-2026-07-26/raw/1..4`.

---

## 0 · Несущий вопрос и ответ (одна строка)
**Approve ли ADR-0007 «истинный эрейж» при ADR-0006 (payload file-first в git)?**
→ **APPROVE-WITH-SUBSTRATE-CHANGE.** Механизм эрейжа (split акт⟂payload, crypto-shred, admission) —
здоровый; но заявку «право-быть-забытым исполнимо» **нельзя подписывать**, пока file-first (git) —
неохраняемый вход для не-стираемого PII/referent-payload. Минимальный фикс — на ДОПУСКЕ, не на механизме.

---

## 1 · Где линзы сошлись (конвергенция — это и есть решение)
Все 4 линзы сошлись в одном: **важен КЛАСС payload, а не механизм стирания.** Фикс живёт на admission
(что впускать в git), а не на erase (как шредить).
- Crypto-shred сам по себе **корректен и не требует догонять копии** (убил ключ → ciphertext бесполезен) —
  но **несовместим с plaintext-file-first для ОДНОГО payload** (шифрование убивает human-readable git).
- Юридически crypto-shred **защитим**; plaintext-PII в git-истории — **неизлечимая постфактум**
  ответственность (history-rewrite не достаёт клонов/бэкапов; проектные git-правила его избегают).
- Архитектурно **не надо вырывать весь payload из git** — надо admission-правило, **симметричное уже
  ратифицированному** DB-first-ONLY списку ADR-0006(g): «erasure-eligible / PII / referent≠owner =
  не file-first-eligible». Тогда эрейж доказуем **по построению** (всё стираемое off-git).
- Этически: заявить «истинный эрейж» там, где субстрат не даёт, = **обещание-дыра**, бьющее по референту
  (Г20). Честный fail для git-контента: «скрыто, не стёрто».

## 2 · Где линзы спорят (и как разрешено)
- **Корректность vs ценность file-first:** сделать git-контент shreddable = зашифровать = убить file-first.
  → Разрешение (архитектура): не пытаться; **запретить** erasure-eligible контент в file-first.
- **Этика/референт vs суверенность владельца:** «безусловный» эрейж референта (И2) vs plaintext-дневник
  владельца. → Юр+этика: для household-режима мягко, для маркетплейса household-исключение ломается.
  Разрешение: **эрейж-гарантия ограничена «в пределах субстрата + до внешней эмиссии»**, а данные
  референта admission-запрещены в git. Тогда «безусловность» исполнима В ГРАНИЦАХ.

## 3 · Почему это НЕ property-ize (граница метода — §4 prefer-properties)
Прогон через тест-различитель T1/T2/T3 (`prefer-properties-over-poles.design.md §4b`):
- **T2 (асимметрия побега):** «positing PII в git можно/нельзя» — значение «можно» **снимает врата**
  эрейжа (payload становится нестираемым). Это clamp/gate, не преференция → **жёсткий инвариант**.
- **T1 (локальность):** гарантия эрейжа **глобальна** (референт X опирается на неё через чужой узел) →
  жёсткий, не локальное свойство.
- **T3:** строгий полюс («не пускать PII/referent в git») **безопасен и осмысленен** как дефолт.
→ Значит это **admission-gate + жёсткий инвариант размещения**, а НЕ настраиваемое свойство. Совпадает
с §4a («admission-gate на входе — врата, не делаются опциональными»).

## 4 · Граница гарантии эрейжа при file-first (что достижимо, что нет)

| Режим payload | Что честно достижимо | Доказуемый эрейж? |
|---|---|---|
| **DB-first payload-store (G3, approved)** | tombstone + физ. delete строки/blob | ✅ **да, сегодня (M1)** |
| **DB-first + crypto-shred (key-store, proposed)** | убить ключ → устойчив к бэкапам/репликам без догона копий | ✅ да (нужен key-store; ключ ≥ per-referent) |
| **file-first payload В GIT** | только режим (A) tombstone/hide, честная метка «скрыто» | ❌ **нет** (git-история + клоны; history-rewrite не достаёт) |
| **off-graph эмитированное** (Telegram-сводка, экспорт) | ничего не достаёт | ❌ **нет** — объявляемая граница (OQ-2) |

**Резюме границы:** эрейж доказуем ТОЛЬКО для payload, который (a) off-git — в удаляемом/шифрованном сторе
под движком; (b) с не-реверсируемым хешем в акте для low-entropy PII (keyed/salted, сам shreddable);
(c) ещё не эмитирован наружу. Всё в git-истории / клонах / бэкапах вне движка / уже ушедшее наружу —
эрейж НЕ доказуем, честен только hide/tombstone.

## 5 · Что вообще НЕЛЬЗЯ класть в git (жёсткий admission-инвариант)
Симметрично DB-first-ONLY списку ADR-0006(g) добавить класс:
- любой **PII** (имя, телефон, email, номер документа, адрес) любого лица;
- любой payload, где **референт ≠ владелец** (третье лицо, Г20) — класс с безусловным правом эрейжа,
  которое владелец не может отменить;
- всё **erasure-eligible / consent-revocable**.
→ Эти классы **DB-first-ONLY (или off-git shreddable)**, не eligible для file-first. И нужен
**write-time-гейт на file-first** (тот же fast-follow долг ADR-0006(g)) — иначе admission структурно
пост-фактум, PII уже в git к моменту, когда движок «заметил» файл диффом.

## 6 · Развилки для владельца (крисп, с рекомендациями)

**Развилка 1 — статус ADR-0007.**
- 1a ⭐(рек.): **approve-with-substrate-change.** Секция G3 (approved) остаётся; §Consequences и заявку
  «право-быть-забытым исполнимо» AMEND: добавить границу «эрейж доказуем ТОЛЬКО off-git; file-first
  git-payload = tombstone/hide, честная метка». Не подписывать заявку эрейжа без этой строки.
- 1b: approve как есть. ❌ Отклонить — подпись под недоказуемым обещанием (риск №1 критика).

**Развилка 2 — где живёт erasure-eligible payload.**
- 2a ⭐(рек., минимум, ничего нового сверх approved): DB-first payload-store + G3 tombstone+delete на
  день-1; **добавить** (i) admission-правило «PII/referent не file-first», (ii) file-first write-time-гейт.
- 2b: сразу off-git зашифрованный CAS + shred-by-key. Мощнее (устойчив к бэкапам), но больше поверхности;
  → **fast-follow**, когда бэкапы/маркетплейс реальны.

**Развилка 3 — третье лицо (Г20).**
- 3a ⭐(рек.): заложить грань `referent` + флаг `erasure-eligible`/класс-согласия в паспорт **сейчас**
  (ретрофит невозможен), referent≠owner payload = DB-first-only + гейт перед маркетплейс-шерингом.
- 3b: отложить до маркетплейса. ❌ Отклонить — ретрофит невозможен, грань нужна до первого шаренного узла.

**Развилка 4 — хеш-канал (новая находка, расширяет OQ-3).**
- 4a ⭐(рек.): для erasure-eligible PII акт хранит **keyed/salted-хеш** (HMAC ключом, который сам
  shredded), не голый content-hash — иначе `payloadHash` в иммутабельном акте подтверждает low-entropy
  PII (телефон/имя) после shred. Для не-PII контента голый хеш ок (целостность).
- 4b: принять голый хеш как residue. ❌ Для PII отклонить (сводит эрейж на нет).

## 7 · MUST-TRACK — как закрыт каждый (не потеряно)

- **OQ-1 (гранулярность ключа vs collateral):** переведён из «open» в **design-требование с жёстким
  ограничением** — ключ/блоб для erasure-eligible ≥ **per-referent**; дедуп/CAS НЕ пересекает границу
  референта (иначе shred неполон ИЛИ collateral-стирание соседей). Точный уровень (referent/field) —
  остаётся open-параметром, но нижняя граница зафиксирована. → Развилка 2b.
- **OQ-2 (taint-closure off-graph «SLOMAN»):** **CLOSED как честная граница** — гарантия явно исключает
  эмитированные наружу копии; ADR-0007 §Consequences это уже заявляет; усилить **перекрёстной ссылкой на
  Г20** (критик просил скрестить). В-субстрате непокрываемо — объявленный предел, не дыра.
- **OQ-4 (R-ERASE / примат референта, Г20):** конституционная «безусловность» референта (И2)
  **переформулируется честно** → «безусловно в пределах shreddable-субстрата и до внешней эмиссии» +
  admission-запрет данных референта в git (делает обещание исполнимым в границах). Механика приоритета
  ролей при конфликте — остаётся open, но **граница субстрата теперь определена**. → Развилка 3.
- **OQ-5 (каскад по потомкам):** in-substrate каскад shred по lineage-производным (эмбеддинги/сводки/
  insight-рёбра) = **корректностное требование** (SPEC R3 / DataResidency), иначе shred неполон;
  off-graph производные падают под границу OQ-2. Параметр «как далеко каскад» — остаётся open. → линза 1/4.
- **OQ-3 (metadata-residue) — судьба:** **принят как честный предел И расширен.** В ADR-0007 §Consequences
  задокументировать: (i) tombstone не идентифицирует референта; (ii) `payloadHash` low-entropy PII = keyed
  (Развилка 4). Из «tombstone-факт неустраним» → «tombstone + хеш-канал», оба ограничены дизайном.

## 8 · Рекомендация совета (для «строй» владельца)
1. ADR-0007 → **approve-with-substrate-change** (Развилка 1a): подписать G3 + границу эрейжа; заявку
   «исполнимо» — с оговоркой off-git.
2. В ADR-0006 добавить admission-класс «PII/referent/erasure-eligible = не file-first» (симметрично D4) +
   зафиксировать file-first write-time-гейт как предусловие (Развилка 2a).
3. Паспорт: грань `referent` + класс-согласия — заложить сейчас (Развилка 3a).
4. ADR-0007 §Consequences/§Открытые: OQ-3 расширить хеш-каналом (Развилка 4a), OQ-2 скрестить с Г20.
Всё выше — **предложение**; применение на диск (правка ADR-0006/0007, invariants, паспорт) ждёт «строй».
