# Линза 2 · Юридический / GDPR (право быть забытым)

Позиция: «что регулятор считает исполненным эрейжем, и где субстрат создаёт необратимую ответственность.»

## 1. Crypto-shred юридически защитим
- Регуляторы/DPA всё чаще признают **crypto-shredding** валидным средством стирания: сделать данные
  недоступными (уничтожить ключ) ≈ стереть, ЕСЛИ управление ключом надёжно и остаточный ciphertext
  реально невосстановим. → Режим (B) ADR-0007 — юридически «правильная» ось.

## 2. Plaintext-PII в git-истории = неизлечимая ответственность
- Обычный commit НЕ удаляет контент из истории. Право-на-стирание требовало бы history-rewrite
  (`filter-repo`/BFG) — деструктивно, **и всё равно не достаёт клонов/форков/бэкапов/чужих чекаутов**.
- Проектные git-правила (`git-working-tree-safety.md`, `security.md`) history-rewrite явно избегают.
- Юридически: PII в git-истории — **удерживаемые персональные данные, которые нельзя честно стереть
  постфактум.** «Вылечить» после записи нельзя → единственная защита превентивна (не впускать).

## 3. Metadata-residue как персональные данные
- Tombstone «здесь была запись о лице X, стёрта по требованию» — если идентифицирует X или сам факт
  отношения, это САМО может быть персональными данными.
- **Ограничение дизайна:** tombstone не должен нести идентифицирующего о референте (только координаты
  акта + факт эрейжа). Иначе OQ-3 из «остаточный факт» превращается в «остаточная утечка PII».

## 4. Третьи лица + маркетплейс = слом household-исключения (прямо про Г20)
- GDPR Art.2(2)(c) household-exemption покрывает чисто личное/бытовое использование (дневник о людях —
  ок). **Момент plug-in/маркетплейса исключение ЛОМАЕТ:** при шеринге/монетизации владелец становится
  контроллером с полным набором обязанностей по данным референтов, не дававших согласия.
- Это ровно «взрывоопасно в момент маркетплейса» из Г20. Ретрофит невозможен (README 07-soglasie):
  грань `referent` + класс согласия надо заложить ДО первого шаренного узла.

## 5. Безусловность референта (И2) vs реальность
- Конституция ценности (07.C): «hard-erase референта исполняется **безусловно**».
- «Безусловно» **неисполнимо**, если данные референта в git-истории владельца и клонах.
- Либо переформулировать честно: «безусловно **в пределах shreddable-субстрата и до внешней эмиссии**»,
  либо запретить данные референта в не-shreddable сторах. Второе — честнее.

## Вердикт линзы
Юридически единственный масштабируемый эрейж — **crypto-shred-by-key** (нельзя догонять каждую копию).
Plaintext-в-git для чего-либо, что может быть PII/о третьем лице, = ответственность, неизлечимая
постфактум. Следствие: **PII / referent≠owner payload НЕ должен попадать в git**; admission обязан это
запрещать ДО записи. Границу «эрейж не достаёт внешних эмитированных копий» (OQ-2) заявить явно.
