# Видение владельца (сырой ввод, 2026-09-06) — «память-первична как слой знаний»

> Вербатим-фиксация голосового ввода владельца. Раскладка на развилки — в `what-memory-is.concept.json`.
> Дом-развилок каждого пункта (fan-out в существующие узлы ценностей/модулей) — там же. НЕ терять мелочи.

## 8 пунктов (как сказал владелец)

1. **Знание копится по проектам** (проект B, C…), внутри чат-групп / чатов / **топиков**. Где-то знание
   копится прямо в топике, где-то — в целом чате, где-то на уровне проекта, где-то просто «в памяти»,
   крепится к состояниям/темам.

2. **То, что мы делаем в ПАПКАХ, должно жить в памяти** — в более глубоком, СВЯЗАННОМ виде. Память
   первостепенна; **файлы лишь ПОКАЗЫВАЮТ**. Файлы ≈ «грязный» слой синхронизации. Есть **ОТДЕЛЬНЫЙ слой
   СВЯЗЕЙ** между элементами, который подсказывает, какие куски информации актуальны и где они.

3. **Память, возможно, должна хранить ВЕТКИ** (разные ветки / разная информация) → явная **привязка к
   GitHub**. Может, даже ДУБЛИРОВАТЬ информацию git (чтобы явно понимать, где что лежит) — но **НЕ делать
   работу git** до коммитов; мы понимаем файлы.

4. **Нужен механизм КАК git-сравнение веток.** Сценарий: в одном чате работали над новым проектом, при
   этом создался другой чат/топик (возможно, целый чат под него). **Они САМИ определяют, кому доступна**
   создаваемая ими информация. Чат = **условность / оболочка / зона / папка** (видимая), может идти по теме.

5. **Информация может захотеть жить в чуть другом виде** → **версионирование** определённых данных в
   определённых местах (явное чёткое версионирование тех или иных данных).

6. **НО есть тип данных, которому этот сценарий НЕ подходит.** Пример: **список клиентов** — всегда ОДНА
   версия; не может быть нескольких версий одного клиента (клиент привязан, например, к менеджеру по дате).
   ⇒ **разные ПАТТЕРНЫ данных** (версионируемое/ветвимое знание vs одно-версионные канонические записи).
   База должна поддерживать разные паттерны — это один из них.

7. **Хочется КОНТРОЛИРУЕМАЯ ОБОЛОЧКА** — в идеале **ИНСТРУМЕНТ сравнения + слияния веток**, и он должен
   быть **ГЛУБЖЕ, чем это делает git**.

8. **Мета-цель.** Пересмотреть этот вопрос, ДОПОЛНИТЬ, разобрать ПУТАНИЦУ разными вариантами «жизни
   данных». Как понимать разные **СЛОИ информации**: кто что залил в код; кто работает локально; чья-то
   приватная память / личные настройки; персистентные долгие личные мысли по теме; vs всё сразу в общий
   доступ. Разный доступ по информации / пользователям / чатам. Это гибкость «по разуму» — но **ДАННЫЕ
   сами должны уметь это строить и определять**, и вокруг этого появляются механизмы.

## Связь с уже открытой дверью
Пункты 1-2-8 = детализация стороны **B** двери «память-первична vs новый верхний слой» (Q-obs-vector).
Пункты 3-7 = downstream-дизайн, предполагающий выбранное B (ветвление/версии/доступ/паттерны). Их нельзя
молча вшивать в инфраструктуру до решения владельца по A/B (иначе тащим одностороннюю дверь). Поэтому здесь —

## Уточнение владельца 2026-09-07 (п.9 — ОБЪЕДИНИТЬ A и B, не выбирать)
9. Не выбирать A vs B — **объединить**. Память = УНИВЕРСАЛЬНЫЙ субстрат; идея «GitHub» применима к нам **по
   ДАННЫМ, не по файлам** (версии/ветки/коммиты ЕДИНИЦ), как замена. Свой хаб может идти **параллельно
   реальному git** (коммитим свои данные + храним указатель на файлы, что положили в GitHub/GitLab, несколько
   remote); «5 веток = ОДНА память», не разные проекты — просто знаем, где что лежит/используется. Анти-сложность
   = **жить КАК ЕДИНИЦА**; память поддерживает разные ПАТТЕРНЫ (паттерн сам = данные, единица задаёт свои
   ограничения); единицы = блоки постройки, полезны агентам+системе+пользователям. Не буквальный GitHub —
   **«конструктор памяти»**: система понимает данные как полноценная БД (схемы по типу), под тип свой МОДУЛЬ —
   универсальный от движка ИЛИ кастомный плагин, который пользователи переиспользуют; для агентов must-have,
   человек может смотреть.

> **Разбор этого п.9 (3 линзы + помощник) → `ab-unification-2026-09-07.analysis.md`.** Кратко: объединение =

> policy-as-data на ТИПЕ; приручается только малым закрытым словарём паттернов + не строить merge-инструмент
> сейчас; минимальный срез = `plan-week`(branchable) + `client`(single-version) через ОДИН путь движка.
