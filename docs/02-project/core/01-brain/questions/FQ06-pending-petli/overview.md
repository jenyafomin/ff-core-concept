# FQ6 · Обзор вариантов

- **A — спец-поле/статус `pending` в паспорте ячейки.**
  Плюс: состояние «петля открыта» явно лежит на узле, читается напрямую без вычислений.
  Минус: нарушает ратифицированный инвариант «0 новых обязательных полей паспорта»
  (L0/ADR-0002); дублирует план Намерение (FQ16), который уже даёт намерениям дом;
  не death-by-design — заложить сейчас ничем не обосновано, кроме удобства.

- **C — производный вид над планом Намерение + salience** (рекомендуется агентом).
  Механизм: «петля открыта» = существует узел-намерение (план Намерение, FQ16), на который
  НЕ указывает ребро `answers/closes`. Вычисляется по запросу (вид/access plane), не хранится.
  Всплытие каких петель показывать первыми — решает **salience** (FQ17), иначе все петли
  «кричат» одинаково громко.
  Плюс: 0 новых полей, тонкий паспорт цел; ретрофит возможен в любой момент (не
  death-by-design); переиспользует уже принятую структуру (FQ16 ✅).
  Минус: требует, чтобы план Намерение и механизм salience были на месте до того, как вид
  станет полезным пользователю (небольшая зависимость по срокам, не по архитектуре).

**Скрытое допущение обоих вариантов**, отмеченное recheck: петля не бинарна open/closed —
реально бывает брошено/отложено/заблокировано/частично. Какой бы вариант ни выбрали, эта
градация должна быть выражена через существующие грани плана Намерение (статус намерения),
а не через новый бинарный флаг `pending`.

**Открытый под-вопрос** (нужен для полного разрешения развилки): где кончается ПАМЯТЬ и
начинается runtime-состояние сессии агента — компакт-тревога это грань паспорта памяти или
состояние рантайма конкретного агента? От ответа зависит, принадлежит ли `pending` брейну
вообще (в любом варианте A/C).
