# FQ11 · Обзор кандидатов на закон композиции

Контекст: когда две ячейки несут разную политику об одном и том же факте (не intra-cell каскад
FQ22, а конфликт МЕЖДУ ячейками), чем разрешается спор. Ни один кандидат ниже не выбран — выбор за
owner/system-architect на этапе engine-spec. Единственный подтверждённый частный факт (см. FQ7):
согласие референта побеждает политику владельца — это ограничение, которому должен подчиняться
любой из кандидатов.

## Кандидат A — фиксированный приоритетный список (по типу правила)
Один статический порядок применяется всегда, независимо от оси политики:
`Конституция > согласие референта (FQ7) > самая строгая политика из двух > tie-break по времени
(последняя запись побеждает)`.

- Плюс: просто реализовать, предсказуемо, один код-путь в движке.
- Минус: «самая строгая политика побеждает» — произвольный выбор, не обоснован ни для одной оси
  кроме retention/видимости (для «право на изменение» неочевидно, что значит «строже»).
- Минус: один список на все оси политики может быть категориальной ошибкой (см. Кандидат B).

## Кандидат B — таблица правил по осям политики (нет единого закона, есть per-axis правила)
Отдельное правило разрешения для каждой оси: retention → строже побеждает; видимость/access →
самый ограничительный побеждает; право на изменение → референт/оригинальный автор побеждает;
приоритет по времени — только как fallback, если ось не даёт ответа.

- Плюс: не притворяется, что все конфликты одной природы — соответствует возражению из
  [checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md) §B («скрытое допущение»).
- Плюс: расширяемо — новая ось политики добавляет строку в таблицу, не ломает существующие.
- Минус: больше поверхности для проектирования до engine-spec — нужно перечислить все оси заранее
  (см. чек-лист в [INDEX.md](INDEX.md) «Критерии готовности»), иначе новая ось = снова ad hoc.

## Кандидат C — делегировать каскаду FQ22 (переиспользовать CSS-механизм)
Рассматривать конфликт между ячейками как частный случай того же каскада, что FQ22 использует
intra-cell (profile-ref → parent): расширить цепочку override, чтобы она могла пересекать границу
ячейки, специфичность/порядок решают победителя так же, как в CSS.

- Плюс: один механизм на оба масштаба (intra-cell и inter-cell) — меньше кода, единая ментальная
  модель для разработчика.
- Минус: FQ22 явно спроектирован для ДРУГОГО масштаба (одна цепочка override внутри одной ячейки);
  расширение на межъячейковый случай — непроверенное допущение, требует отдельной валидации перед
  выбором (иначе рискуем повторить ошибку «одно решение на разные по природе проблемы», см.
  Кандидат A минус).

## Открытый вопрос, не закрытый ни одним кандидатом
Все три кандидата используют инвариант FQ7 (референт побеждает владельца) только как один из
входов. Ни один явно не решает случай **owner-A vs owner-B без референта** для оси «право на
изменение» — это должно быть проверено на конкретном примере до выбора кандидата.
