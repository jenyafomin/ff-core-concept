# FQ15 — обзор чужих проектов как постоянный вход?

> Родитель: [../INDEX.md](../INDEX.md) · Слой L0 · ⚠️ уточняется формулировка

## 1. Вопрос
Исходная формулировка («обзор чужих проектов — это ПОСТОЯННЫЙ вход в брейн, а не разовый импорт?»)
двусмысленна и смешивает два разных класса вопросов (см.
[checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md), раздел A):
1. **PROCESS** — эвристика проектирования: перед КАЖДЫМ новым примитивом спрашивать «а нет ли уже
   такого в CRM-Rent/InstaApp?» (собственные прошлые проекты владельца), обобщать боевые паттерны,
   не изобретать заново.
2. **DATA** — гипотетический буквальный импорт операционных данных этих проектов (тенанты, клиенты)
   как постоянного источника узлов брейна.

Слово «чужих» в первоисточнике = «другие (не этот проект)», НЕ «принадлежащие посторонним людям» —
CRM-Rent/InstaApp это проекты самого владельца. Текущий INDEX не различал эти два смысла.

## 2. Рекомендация
**Да по PROCESS, нейтрально/не решается здесь по DATA.** Дом дееспособен — 8 из ~15 несущих граней
единицы памяти уже прошли продакшн в CRM-Rent/InstaApp (снапшот-в-момент, append-only лог операций,
status-lifecycle, soft-delete ⟂ hard-erase, RLS/tenants, planned/actual, полиморфное ребро,
embeddings-матч — источник:
[`synthesis/2026-07-05-fable-nonlinear-dig.md:102`](../../analyses/2026-07-05-fable-brain-dig/2026-07-05-fable-nonlinear-dig.md)).
Дешевле подтвердить паттерн боем, чем изобретать с нуля — поэтому «смотреть на дом перед новым
примитивом» становится постоянной практикой проектирования Fable/Opus. Это НЕ канал операционных
данных в работающую память: ничего из CRM-Rent/InstaApp не льётся в брейн как узлы этим решением.

## 3. Guard-rail (если DATA когда-либо потребуется)
Если владелец в будущем решит буквально ПОДКЛЮЧИТЬ операционные данные CRM-Rent/InstaApp (не только
паттерны) как постоянный источник узлов брейна — это **не** покрывается текущим ✅ и требует заранее:
- **FQ19 (import ≠ human)** — такие узлы обязаны нести `source=import` (презумпция недоверия), не
  наравне с human-authored записями.
- **FQ7 (referent-разметка)** — тенанты/клиенты CRM-Rent — третьи лица; перенос их данных в личный
  брейн владельца без грани `referent` и без их согласия строже исходного кейса FQ7 (согласие
  референта здесь отсутствует полностью, а не просто не формализовано).

Без этих двух пунктов, зашитых ДО итерации импорта, ретрофит невозможен (death-by-design, как в FQ7).

## Связи
- **FQ19 (import ≠ human)** — активируется только в сценарии DATA (буквальный импорт); не относится
  к PROCESS-эвристике.
- **FQ7 (referent + hard-erase)** — активируется в том же гипотетическом сценарии; тенанты CRM-Rent —
  третьи лица без согласия, риск строже базового FQ7-кейса.
- **Ц-5 Суверенность** ([V5-suverennost.md](../../01-overview/01-values/V5-suverennost.md)) — если паттерны/данные из
  CRM-Rent когда-либо материализуются как узлы, им нужен собственный «рецепт доступа»
  (policy-as-data, foreign-data-wrapper), т.к. они относятся к другому контексту доступа.
- **Гр.5 «Значимость и внешний вход»** (родительский INDEX) — FQ15 соседствует с FQ8 (сигнал
  значимости на ребре); важно не читать FQ15 как DATA-вопрос по аналогии с FQ8 — это PROCESS-вопрос.

## Возражения (стилман, из recheck раздел B)
- **Стилман «обзор чужих проектов = внешний источник, не относится к единице памяти» —
  ПОДТВЕРЖДАЕТСЯ** для исходного намерения: это практика проектирования («обобщать работающее»), не
  грань схемы узла. Реального риска приватности/referent в этом смысле почти нет — обобщаются
  архитектурные паттерны, а не персональные записи о людях.
- **Скрытое допущение «раз это очевидно-да (✅), можно закрыть без под-грани» — неверно.** CRM-Rent —
  это CRM для АРЕНДЫ, там неизбежно есть тенанты/клиенты (третьи лица). Если решение когда-либо
  расширится на буквальный импорт операционных данных — это мгновенно попадает под FQ19+FQ7, а
  прежний INDEX не фиксировал эту развилку. Отведено разделом 3 (guard-rail) этой правки.
