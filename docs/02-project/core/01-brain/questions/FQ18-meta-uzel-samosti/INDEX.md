# FQ18 — мета-узел «Самости»

> Родитель: [../INDEX.md](../INDEX.md) · ⚠️ уточняется — под одним ярлыком склеены 4 разных вопроса

## 1. Вопрос

Нужен ли мета-узел «Самости» (границы брейна, «чей я», successor/наследование)?

Формулировка вводит в заблуждение: под словом «Самость» на деле склеены **4 разных вопроса**,
разного типа и разной срочности:

1. **Граница брейна** — «чей я» (single-owner scope графа vs потенциальный multi-tenant/shared)
   — архитектурная граница схемы.
2. **Steward** — кто оперирует системой, если владелец недоступен — governance/policy-данные.
3. **Successor** — кому передаётся граф при передаче/наследовании — governance/юридический вопрос.
4. **Bus factor** — риск-метрика («что ломается, если владелец пропал») — риск-анализ/runbook,
   вероятно вообще НЕ узел, а документ (как ADR/Charter), не подчиняющийся метаболизму наравне
   с обычными ячейками.

Ответ «нужен узел» может отличаться по каждому пункту — карточка отвечала на все четыре сразу.

## 2. Рекомендация

Тема важна («да, нужно где-то держать owner/steward/successor»), но **не «да, это один узел, как
описано»**. Признать, что (1)-(3) — вероятно данные, а (4) — вероятно нет. Не 🔴/death-by-design
в строгом смысле FQ7: owner/steward/successor — единичные root-поля, ретрофит дёшев (в отличие
от referent'а на миллионах записей). Zachem с механизмом необратимости не написан — статус
«очевидно-да» из старой карточки не был обоснован.

## 3. Выбор / что делаем

**⚠️ ждёт владельца — развилка не решена.** Три варианта реализации для (1)-(3):

- **Вариант A — отдельный мета-узел Самости (sui generis).** Новый РОД узла специально под
  owner/steward/successor. Плюс: явный, легко находимый. Минус: дублирует форму FQ22 — если
  профиль-узел уже даёт каскад override, зачем ещё один род.
- **Вариант B — распределить по конституции без спец-узла.** Плюс: не плодит сущности. Минус:
  не даёт стабильного адреса (id), на который можно сослаться из движка/runbook.
- **Вариант C (новый, из перепроверки) — Самость = КОРНЕВОЙ экземпляр FQ22 (узел-профиль).**
  owner_id/steward_id/successor_id — те же поля каскадной политики FQ22, только на верхнем
  уровне графа («профиль профилей»). Снимает необходимость нового РОДА узла — остаются только
  новые ПОЛЯ на существующем роде. Не был рассмотрен в исходной карточке (только A/B).

**Явно зафиксировать (не зависит от выбора A/B/C):** наличие узла Самости **не эквивалентно**
решению об 8-й ценности в FQ21. Узел — вопрос СХЕМЫ (что хранится), 8-я ценность — вопрос
GOVERNING LENS (что управляет поведением по всему графу, уровня Ц1-Ц7). Можно иметь узел
Самости и не иметь 8-ю ценность (узел — просто данные), или иметь ценность без отдельного узла
(принцип без хранилища). FQ21's option C («покрыть мета-узлом Самости, без новой ценности»)
некорректна как ЗАКРЫВАЮЩАЯ альтернатива для FQ21 — годится только как ЧАСТИЧНОЕ решение.

_Пока ответ не получен — не проектировать мета-узел как отдельный род; не закрывать FQ21 ссылкой
на этот FQ без разбора уровня абстракции._

## Под-вопрос

Является ли «Самость» вопросом МОДЕЛИ ДАННЫХ (узел в графе, пункты 1-3) или вопросом ГРАНИЦЫ
ДВИЖКА/ДЕПЛОЯ (кто может открыть сессию к графу вообще, вне схемы узлов, пункт 4/bus factor) —
и если второе, должен ли граф хранить steward/successor как узел, или это исключительно внешний
runbook (как ADR/Charter), не подчиняющийся метаболизму/policy-as-data наравне с обычными
ячейками?

## Возражения / что может сломать

- **Категориальный разрыв внутри самого FQ18.** Граница-брейна/steward/successor (данные) и
  bus factor (риск-метрика) — не одна сущность; триаж «очевидно-да» применённый ко всей связке
  скрывает, что bus factor может вообще не требовать узла.
- **Скрытое допущение уровня.** «Чей я» может быть вопросом уровня ДВИЖКА (auth/deployment
  boundary — кто может открыть сессию), а не уровня ДАННЫХ (узел в графе). Если так, граф не
  обязан хранить это как узел вообще.
- **Риск подмены в FQ21.** Если FQ18 реализуют и не зафиксируют явно «узел ≠ ценность», FQ21
  рискует «закрыться» решением FQ18, хотя вопрос об 8-й ценности останется открытым.

## Критерии готовности

- Выбран один из вариантов A/B/C для (1)-(3) — явно, с обоснованием, почему не выбраны
  остальные два (в частности, почему НЕ вариант C, если выбор не C).
- Для bus factor (4) отдельно зафиксировано: узел в графе ИЛИ внешний runbook — не по умолчанию.
- В FQ21 (при следующей правке FQ21) учтено, что «наличие узла Самости не эквивалентно решению
  об 8-й ценности» — иначе FQ21 нельзя закрывать ссылкой на исход FQ18.
- Написан `zachem.md` с механизмом необратимости (что именно нельзя реализовать позже и почему),
  если выбор всё же в пользу срочного ретрофита.
