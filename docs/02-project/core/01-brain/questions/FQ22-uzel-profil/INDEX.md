# FQ22 — узел-профиль вместо «этажа ниже»

> Родитель: [../INDEX.md](../INDEX.md) · Слой: Гр.2 — Хребет и движок (архитектура) · ⚠️ уточняется

## 1. Вопрос
Политику ячейки — в отдельный узел-ПРОФИЛЬ (`profile-ref` + inline-override, каскад в 2-3
ступени как CSS: override > profile > конституция) вместо буквального «этажа ниже» (рекурсивных
«настроек настроек», отвергнутых стоп-правилом FQ23)?

## 2. Рекомендация
**Направление верное** — profile-ref + override адресуемо и переиспользуемо, профиль = обычная
ячейка (0 новых родов), FQ4 (линза) закрывается как частный случай. Но recheck
(см. [checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md)) нашёл, что решение потеряло по
дороге границу глубины: ничто в тексте не запрещает профилю нести собственный `profile-ref`, а это
и есть источник CSS-специфичности как реальной боли (не сам каскад, который прост при глубине 1).
Плюс: FQ22 (внутриячейковый каскад) и FQ11 (межячейковый закон композиции политик) — разные оси,
их порядок применения нигде не выписан.

## 3. Выбор / что делаем
_план, НЕ решение владельца — владелец решает после того, как пункты ниже закрыты._

1. **Рекомендация-инвариант (на ратификацию владельцем):** зафиксировать конституционный лимит —
   глубина каскада профилей = 1 (профиль не может нести собственный `profile-ref`; максимум
   `override → profile → конституция`) до предъявления второго живого кейса, требующего цепочки
   профиль→профиль. Основание — стоп-правило FQ23: «профиль профиля» имеет тот же темп изменения
   и того же автора, что профиль первого уровня → по FQ23 не новый слой, различающей силы нет.
2. Развести порядок применения в engine-spec: сначала FQ22 даёт **эффективную политику ячейки**
   (разрешение override/profile/конституция внутри одной ячейки), затем FQ11 разрешает **конфликт
   между двумя такими эффективными политиками** двух разных ячеек. Один раздел engine-spec, не
   два разрозненных — иначе легко забыть про второй при имплементации (тот же риск, что FQ3 уже
   называет для FQ11 vs propagation).
3. Явно зафиксировать открытым вопросом (не решать сейчас): профиль-ссылка пинуется на конкретную
   ВЕРСИЮ профиля или всегда читает последнюю? Не решено → изменение разделяемого профиля молча
   меняет эффективную политику всех ссылающихся ячеек задним числом (blast-radius) — риск нигде не
   разобран (ни в FQ22, ни в FQ11, ни в FQ3).
4. Пометить FQ4 как **зависящий от финальной механики FQ22** (глубина каскада, версионирование,
   blast-radius) — FQ4 явно строится как частный случай FQ22, поэтому пересмотр механики FQ22
   автоматически требует пересмотра FQ4. Ратифицировать в одном раунде/ADR либо явной парной
   ссылкой, не порознь.

## Возражения
Стилман «каскад как CSS = источник непредсказуемости» (полный текст →
[checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md), раздел B). Возражение верное лишь
частично: источник использует CSS-аналогию для ОДНОГО уровня приоритета (простой, детерминированный
2-3-ступенчатый порядок), не для полной модели CSS-специфичности (селекторы, `!important`, cascade
layers) — той, что действительно известна багами. Боль CSS-специфичности материализуется НЕ от
текущего описания, а от потенциального расширения: если профиль сможет ссылаться на профиль,
глубина каскада станет переменной, и тогда порядок разрешения конфликтов реально станет проблемой
в духе CSS. Документ сейчас этого явно не запрещает (говорит только «иерархию профилей строить не
надо» — мягкий YAGNI, не конституционное ограничение) — отсюда п.1 плана: превратить молчаливый
YAGNI-комментарий в письменное правило.
