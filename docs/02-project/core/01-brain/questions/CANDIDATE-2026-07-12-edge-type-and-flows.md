# CANDIDATE-FQ — Тип связи как первоклассная переменная → «потоки» (flows)

> ⚑ Сырьё владельца (голос, 2026-07-12), НЕ триажировано в FQ-номер. Зафиксировано, чтобы не потерять.
> Кандидат на объединение с FQ8 / edge-typing (стр.141) — решает владелец при триаже.

## Идея (как сказал владелец)
Помимо самих узлов (единиц памяти) у **связи (ребра) должен быть ТИП** — отдельная переменная. С ней
модель становится намного гибче:
- можно строить **потоки** (streams/flows) — направленные цепочки узлов по типу связи;
- у узла может появиться поведение, завязанное на поток — например, узел **закрывается (auto-close)
  только через поток**, а не произвольно;
- владелец сам сомневается: «всё ограничивать — глуповато», но для сущностей, которые **могут ошибаться**
  (агенты, импорт), ограничение через поток может быть оправдано.

## Почему это НЕ новое, а усиление уже принятого (связи)
- **FQ8** — «значимость-для-человека живёт на РЕБРЕ человек→единица, а не как ось узла». Уже про то,
  что ребро несёт семантику.
- **Строка 141 open-questions/INDEX.md** (заложить сейчас): **«типизация рёбер — проводит ли ребро поток
  доверия/согласия»** (структурные = нет, деривационные = да) + второй столп движка
  **`propagation-as-engine-duty`** (распространение по рёбрам — обязанность движка). Идея владельца =
  расширение этого: тип ребра управляет не только распространением доверия, но и **жизненным циклом узла**.
- **В4 (закрыто)** — ребро может нести узкий паспорт (для рёбер-инсайтов). Тип связи — ещё одно поле
  этого паспорта.
- **OQ-8** — провенанс/consent-taint/forgetting ходят по одному графу lineage; «поток» — обобщение этого
  обхода на произвольный тип ребра.

## Что здесь на самом деле спрашивается (для триажа)
1. **Тип ребра = обязательное поле** каждого ребра (enum/расширяемый реестр типов), или опциональная грань?
2. **«Поток»** — это производный ВИД (проекция обхода по рёбрам одного типа), или хранимая сущность?
   (Ср. FQ6: pending — вид, не поле.)
3. **Flow-gated lifecycle** (узел закрывается только через поток) — это policy-as-data на узле, или
   обязанность движка? Не переоборачивает ли это FQ23 (стоп-правило против оверинжиниринга)?
4. Для кого ограничение включено по умолчанию — только для error-prone источников (агент/импорт), или для всех?

## Рекомендация (предварительно, до совета)
Скорее **да на типизацию ребра** (дёшево, ретрофит труден — попадает в «заложить сейчас» по стр.141),
но **flow-gated auto-close — отложить** как policy-грань: заложить поле типа сейчас, механику потоков —
позже, когда есть БД и обход графа. Не строить «поток» как отдельную сущность раньше времени.

## Добавление 2026-07-12 (раунд 2, голос владельца)

Владелец углубил идею — три новых грани связи, которые дают системе «очень сильную гибкость»:

1. **Реактивное ребро (edge реагирует на изменение).** Связь не только «проводит поток», но и
   **срабатывает на определённое изменение**: что-то поменялось у A → по ребру идёт реакция к B
   (триггер/подписка на графе). Это семантика поведения, а не только маршрут.
2. **Ребро несёт то, что нода одна определить НЕ может.** Часть смысла живёт «за рамками самой ноты» —
   в отношении между узлами. Нода не может знать всё абсолютно; связи между другими узлами достраивают
   то, что ей недоступно. → ребро как носитель кросс-узловой семантики (усиление FQ8 и Ц-6 Реляционности).
3. **Рёбра поверх ПАПОК, не только узлов; «папка-оркестрация».** Связь может связывать не только ноды,
   но и **папки** (грани/разделы). Отдельно встаёт вопрос: **какая папка «оркеструет» всё это** — есть
   грань между «ровно/узлом» и «папкой-оркестратором». Как связи и папки соотносятся — открытый вопрос.

### Что это добавляет к триажу (сверх пунктов 1–4 выше)
5. **Реактивность на ребре** — это policy-as-data (ребро описывает свой триггер) или обязанность движка
   (`propagation-as-engine-duty` расширяется до event-driven)? Не пересекается ли с FQ23 (оверинжиниринг)?
6. **Уровень адресуемости ребра:** ребро только узел↔узел, или узел↔папка / папка↔папка тоже?
   (Связано с адресной схемой: path / node-ID / ref — синтез `../analyses/2026-07-12-fable-series/2026-07-12-brain-scopes-and-identity.md`.)
7. **«Папка-оркестрация»** — это узел особого типа, слой scope, или отдельная инфраструктурная сущность?
