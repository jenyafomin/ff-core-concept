# FQ13 — операция как append-only

## 1. Вопрос
Операция как append-only запись (иммутабельна; сами факты — нет)?

## Зачем / откуда
Из activity_logs; укрепляет аудит и Тождество.

## Варианты ответа
- A — операции append-only (журнал)
- B — перезапись операций

## 2. Рекомендация
**Да — но с оговоркой.** Буквально «журнал иммутабелен» противоречит FQ7 (hard-erase): hard-erase
сам — операция, значит по FQ13 обязан попасть в append-only журнал; если журнал хранит payload,
«неизменен навсегда» = референт-данные остаются в логе несмотря на hard-erase. Понижено с
«✅ очевидно-да» до «да-с-оговоркой», пока это не зафиксировано в контракте движка СОВМЕСТНО с FQ7
(разбор → [checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md)).

## 3. Выбор / что делаем (план)
Зафиксировать в контракте движка разделение журнала:
1. **Метаданные операции** (кто/когда/тип/target-id) — иммутабельны, добавляются вечно.
2. **Payload** операции, затрагивающей referent-грань, при `hard-erase` заменяется
   tombstone-маркером («операция X: содержимое удалено по референт-согласию, T»); сама эта замена —
   тоже append-only запись (не переписывание истории, а новая запись поверх).

Не решать/строить схему `activity_logs` до совместного решения с FQ7 (риск ретрофита той же
категории — см. ниже).

## B. Возражения (стилман → опровержение)
Стилман защиты старой формулировки: «конфликта нет — hard-erase (FQ7) удаляет ФАКТЫ, append-only
(FQ13) — только ЖУРНАЛ ОПЕРАЦИЙ, разные слои».
Опровержение: пересечение неизбежно — hard-erase сам является операцией и обязан попасть в журнал.
Два непроверенных допущения ломают стилман: (1) что в логе нет payload; (2) что запись о самом
hard-erase не содержит стёртых данных (before/after снапшот). Если оба ложны — «право на забвение»
выполняется формально, но данные остаются в логе навсегда. Подробности →
[checks/2026-07-07-recheck.md](checks/2026-07-07-recheck.md).

## Критерии готовности
- Контракт движка явно описывает две части журнала (метаданные / payload) и правило tombstone.
- FQ7 закрыт (владелец дал финальное «да») — FQ13 не финализируется раньше него.
- Явно решено, распространяется ли tombstone-механизм на FQ20 (биография).

## Связи
- **FQ7** — tension-with / co-design (**КРИТИЧНО**): append-only буквально конфликтует с hard-erase,
  примирение — только через разделение метаданные/payload+tombstone; решать одной спецификацией.
- **FQ20** (биография, append-only род узлов) — тот же риск tombstone, если содержит referent-контент.
- **FQ12** (снапшот-в-момент) — снижает объём payload, застрявшего в логе, не отменяет проблему.
- **Ц-2 Тождество** — где Тождество (владельца, аудит) сталкивается с правом референта на забвение,
  референт имеет приоритет (см. FQ7 zachem.md → FQ3).
