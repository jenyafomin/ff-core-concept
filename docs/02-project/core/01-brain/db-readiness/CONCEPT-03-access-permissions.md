# 🔐 CONCEPT-03 — Доступ, права, области и клапан самоулучшения

> Разрез архитектора: **границы модулей → контракты → потоки данных**. Одна несущая мысль:
> **доступ пользователя и «акт агента» — ОДНА таблица прав, а не две системы.** Всё остальное —
> проекции этой таблицы. Ниже — как это ложится на субстрат (DL-01…DL-19) без нового примитива.

---

## 0. Несущий тезис (чтобы не расползлось)

Слой агентов уже дал формулу (VISION-agents §0): **каждый ход — это АКТ = (принципал × класс-действия × scope)**,
а «слой управления = ОДНА таблица грантов + классификатор (AI Guard)». Этот концепт делает один шаг,
который замыкает витск 1:

> **Пользователь — тоже принципал. Его «прочитать/записать/удалить» — тоже АКТ.**
> Значит доступ человека к данным и авторизация акта агента — **не два механизма, а один**:
> одна грант-таблица над `(принципал × класс-действия × scope)`, один каскад проверки, один аудит.
> Разница только в ТОЧКЕ ВХОДА классификации: акт пользователя обычно приходит через UI (класс
> известен статически — «кнопка Удалить» = класс `erase`), акт агента иногда требует Guard.

Это прямой ответ на задачу №4 (изоморфизм) и он же диктует всё остальное: **мы не проектируем
«права доступа» — мы ПЕРЕИСПОЛЬЗУЕМ уже спроектированную грант-таблицу, добавив в неё принципалов-людей.**

Паттерн: **Policy-as-Data + Ports & Adapters** (движок = единственный порт проверки прав) +
**Defense in Depth** (грубая стена в БД, тонкая логика в движке). Обоснование выбора — по ходу.

## 1. Модель прав как данные

### 1.1 Грант — это узел, не строка кода

Единица прав = **grant-node** (строка реестра M-G3, не отдельная таблица — DL-01). Схема конверта
(наследуется из VISION §3.2, расширяется принципалом-человеком):

| Поле гранта | Смысл | Тип-значение |
|---|---|---|
| `principal` | КТО действует | thin-ref на узел: `person:*` / `agent:*` / `plugin:*` / `role:*` |
| `action_class` | ЧТО делает | ссылка в реестр классов: `read · write · exec · erase · promote-policy · speak · grant` |
| `scope` | НАД ЧЕМ | **предикат-селектор** над паспортами (см. §3) — область, node_type, подграф |
| `mode` | как | `allow · deny · gated · auto` |
| `ttl` | до когда | null=постоянный · timestamp=истекающий (окно автопилота) |
| `evidence_ref` | на основании чего | thin-ref на вердикты/прогоны (лестница доверия C6) |
| `issued_by` | кем выдан | thin-ref на принципала-издателя (аудит) |

Всё это — **паспорт + payload одного узла типа `grant`**. Выдача/отзыв/истечение = события журнала
(append-only, DL-01/DL-17): отзыв = tombstone-событие, **не UPDATE** статуса.

### 1.2 Каскад проверки = каскад policy (DL-02), не новый механизм

Проверка «можно ли принципалу P сделать акт класса C над scope S» идёт по тому же каскаду
`Конституция > policy-as-data > integrity-as-engine-duty` (DL-02), что и вся policy:

```
акт(P, C, S)
   │
   ├─ [Конституция]  class ∈ RED (внешне-необратимое, само-изменение прав) → deny всегда, не грантуется
   │
   ├─ [policy-as-data] ищем матчащие grant-узлы (P, C, S); deny > allow; самый узкий scope выигрывает
   │        ├─ есть allow/auto + не истёк TTL → пропуск
   │        ├─ gated → человек (или Guard, если окно активно и класс YELLOW)
   │        └─ нет матча → default-deny (fail-closed)
   │
   └─ [engine-duty] движок РЕШАЕТ (integrity), агент/пользователь не решает сам за себя
```

**Секреты сюда не пишем** (задача №1): grant над интеграцией хранит `handle`-ссылку
(`secret-ref: vault://…`), а не значение. Это уже канон витка 1 («секрет = ссылка, не значение» —
README чек-лист). Grant даёт право *использовать* хэндл, движок разворачивает его в момент вызова.

### 1.3 Границы модуля

| Модуль | Ответственность | Интерфейс (что отдаёт) | Зависимости |
|---|---|---|---|
| **M-G3 реестр** | хранит grant-узлы, классы действий, area-узлы как ДАННЫЕ | `resolveGrants(P, C, S) → verdict` | nodes/edges |
| **M-G1 движок** | ЕДИНСТВЕННЫЙ порт проверки; каскад; разворот secret-ref | `authorize(act) → allow/gate/deny` | M-G3, журнал |
| **AI Guard** (домен 02) | классифицирует акт, когда класс не статичен | `classify(act) → {class, confidence}` | — (ноль инструментов) |
| **Пульт (M-P4 кокпит)** | UI выдачи/отзыва грантов из Telegram | пишет grant-события в журнал | write-pipeline |

**Ключевая инвариант-граница:** проверка прав живёт ТОЛЬКО в движке (M-G1). Ни агент, ни UI, ни SQL
не проверяют права «сами» — иначе получаем две правды и дыру (VISION ловушка №1). Это Ports & Adapters:
один порт `authorize`, много вызывающих.

## 2. Области: локальное / проектное / глобальное

### 2.1 Область — это узел, принадлежность — это ребро (DL-11)

Область (`area` / `space`) = узел-контейнер. Три канонических уровня (растяжимо INSERT'ом, DL-01):

- `area:local:<person>` — **моё-личное** (дефолт `scope=private`, DL-12);
- `area:project:<id>` — **проектное** (общее внутри проекта);
- `area:global` — **общее/каноничное** (реестры типов, policy, публичные узлы маркетплейса).

**Принадлежность = `member-of`** (thin-ref, акт владельца — DL-11): узел `member-of` area:project-FF.
Это структурный акт хозяина: «эта нода живёт здесь». **У узла РОВНО ОДНА область-резиденция** (home).
Резиденция отвечает на вопрос «чьё это / где физически» — она же управляет `storageLevel` /
DataResidency (M-G4): local-узел лежит в личной БД, project-узел — в проектной, global — в control-plane.

### 2.2 «Та же нода видна/невидна в разных областях» — это ГРАНТ, не копия

Различение, которое всё упрощает (изоморфно паре member-of ↔ categorized-as, DL-11):

| Механизм | Что делает | Класс связи |
|---|---|---|
| **Резиденция** (`member-of` area) | ОДИН дом узла; кто владелец; где лежит payload | thin-ref, акт владельца |
| **Видимость через границу** (grant `read` на scope, включающий узел) | узел ПОКАЗЫВАЕТСЯ в другой области; копии нет | grant-узел (policy-as-data) |
| **Заимствование-ассерция** (`categorized-as` в чужую категорию) | кто-то *утверждает* принадлежность → нужно согласие (Ц-7) | assertion + consent |

Поток: узел N живёт в `area:local`. По умолчанию **через границу области — default-deny**: в проекте
его не видно. Владелец выдаёт grant `(agent:planner, read, scope: node ∈ area:local ∧ node_type=task)` —
и планировщик видит личные задачи, не видя личных заметок. **Одна нода — одна резиденция — много
грантов видимости.** Никакой синхронизации копий (это и есть DL-01: один узел, не дубли).

Это решает задачу №2 целиком: локальное/проектное/глобальное = area-узлы; принадлежность = member-of;
кросс-областная видимость = грант; согласие на заимствование = categorized-as. Всё — данные, ноль схемы.

### 2.3 Поток данных (резиденция → видимость)

```
[owner акт]──member-of──►[area:local]      (резиденция, один дом)
      │
      └─[owner выдаёт grant read scope⊇N]──►[grant-node]
                                                │
[agent:planner чтение]──authorize(read,N)──►[M-G1 каскад]──► allow (грант матчит) ──► N видна в проекте
[agent:coder   чтение]──authorize(read,N)──►[M-G1 каскад]──► deny (нет гранта)    ──► N невидна
```

## 3. Гранулярность read/write внутри проекта

### 3.1 «Этот агент код НЕ трогает» = grant-данные, не хардкод

Задача №3. Гранулярность достигается тем, что **`scope` гранта — это предикат-селектор
(view-def, DL-18/примитив №3)**, а не константа. Селектор — предикат над полями паспорта:

```
scope := предикат( area? node_type? tag? subgraph(member-of X)? epistemic? )
```

Примеры-строки (данные, живут в реестре):

| principal | action_class | scope-предикат | mode |
|---|---|---|---|
| `agent:coder` | `write` | `node_type ∈ {code-file, config}` | `allow` |
| `agent:coder` | `write` | `node_type ∈ {journal, task, note}` | `deny` |
| `agent:writer` | `write` | `node_type ∈ {code-file, config}` | `deny` |
| `agent:writer` | `read` | `area:project:FF` (весь проект) | `allow` |
| `agent:planner` | `write` | `node_type=task ∧ member-of area:project:FF/plans` | `gated` |

«Агент код не трогает» = одна строка `deny write on node_type∈{code-file}`. Хочешь поменять — правишь
данные, не код (DL-01: рост = INSERT/tombstone). **read vs write vs exec** — разные `action_class`,
поэтому «читает проект целиком, но пишет только в свой подграф» = два гранта с разными классами и scope.

### 3.2 Почему предикат-scope — это переиспользование примитива №3, а не новая машина

`view-def` уже определён как «app-level композиция запроса, НЕ CREATE VIEW» (DL-18). Селектор гранта =
ровно такой же предикат. Движок, разрешая чтение, **композирует запрос = базовый view ∧ grant-предикаты**
(та же операция, что проекция производного состояния DL-04/18). Никакого нового механизма фильтрации:
**ACL = это ещё одна проекция на чтении.** Это главный аргумент, что модель держится без пятого примитива.

## 4. Изоморфизм с агентной грант-таблицей

Задача №4 — прямой ответ: **это ОДНА таблица, не две.** Доказательство через сведение колонок:

| VISION-agents (акт агента) | CONCEPT-03 (доступ пользователя) | Общее |
|---|---|---|
| принципал = агент/плагин | принципал = человек/роль | `principal` — thin-ref на узел |
| класс акта GREEN/YELLOW/RED | read/write/erase/grant… | **один реестр классов действий** |
| scope = `chat:thread` | scope = area/подграф/node_type | **один селектор-предикат** |
| режим+TTL (окно автопилота) | mode+TTL (временный доступ) | **одна колонка mode+ttl** |
| evidence-ref (лестница C6) | evidence-ref (повышение доступа) | **один механизм повышения** |
| AI Guard классифицирует | UI даёт класс статически | **одна точка: `classify` (иногда тривиальна)** |

Хребет `Конституция > policy-as-data > integrity-as-engine-duty` держит обе стороны (VISION §0, таблица
изоморфизма). **Вывод: доступ пользователя — это ПРОЕКЦИЯ агентной грант-таблицы на принципалов-людей.**
Мы не плодим вторую систему прав (явное требование задачи). Практический след: `03-contract/` (пустой
узел из аудита A2) наполняется ОДИН раз — и обслуживает и агентов, и людей, и маркетплейс.

**Что важно НЕ перепутать (граница):** «всё видно ИИ» (инвариант brain) — про **чтение внутри одного
владельца/тенанта**, это не отменяется. Грант-видимость (§2.2) и тенант-стена (§6) — про **границы
между областями и между владельцами**. Внутри моего мира ИИ не ограничен; на границе области/тенанта —
ограничен грантом. Это два разных радиуса, не противоречие.

## 5. Клапан самоулучшения (F-3)

Задача №5. Владелец: «клапан само-улучшения должен определяться механизмом доступа/подтверждений,
может быть и так и так». Архитектурный ответ — **клапан НЕ отдельная сущность, это грант над двумя
разными классами действий**:

### 5.1 Правило: синтез рождает ПРЕДЛОЖЕНИЕ; сила даётся ПРОДВИЖЕНИЕМ

Когда конструктор-луп (CONCEPT-02, движок) синтезирует правило/план — это два разделённых акта:

| Акт | Класс | Что порождает | Дефолт-режим |
|---|---|---|---|
| **Синтез** | `write` (draft) | proposal-узел: `status=proposed, epistemic=hypothesis`, в буфер сессии (DL-07) | **auto** — писать черновики свободно |
| **Продвижение** | `promote-policy` | тот же узел → `status=active`, входит в каскад DL-02 и НАЧИНАЕТ управлять поведением | **по гранту** — «и так и так» |

Клапан = **грант на класс `promote-policy` для этого принципала и scope**. Отсюда «может быть и так
и так» получает точное значение:

- `grant(constructor-loop, promote-policy, scope: узкая само-настройка) = auto` → правило активируется само;
- `grant(constructor-loop, promote-policy, scope: что угодно шире) = gated` → правило ждёт тапа владельца;
- `promote-policy` над **самой грант-таблицей / Конституцией** = **RED, не грантуется никогда**
  (само-изменение прав — конституционный запрет, VISION ловушка 5c: «Guard не ревьюит свой промпт»).

### 5.2 Почему это тот же механизм, а не новый

Продвижение по evidence = лестница доверия C6: proposal копит `evidence_ref` (N прогонов без REJECT),
и только тогда grant позволяет auto-promote в данном scope. Кнопка «активировать навсегда» без истории —
максимум «на день» (VISION §2, V-6). **Клапан самоулучшения = grant `promote-policy` + лестница C6.**
Ни новой таблицы, ни нового примитива — F-3 закрывается той же грант-машиной, что и всё остальное.

### 5.3 Поток

```
[constructor-loop] ──synthesize──► [proposal-node status=proposed]   (auto, дешёвый класс)
        │                                   │
        │                          accrue evidence_ref (N прогонов)
        ▼                                   ▼
   authorize(promote-policy, scope) ──► [M-G1 каскад]
        ├─ scope узкий + evidence достаточно + grant=auto → status=active (само-улучшение сработало)
        ├─ grant=gated → человек (тап в Telegram)
        └─ scope = права/Конституция → RED, deny всегда
```

## 6. Мульти-юзер / маркетплейс / БД

Задача №6 — вердикт по стеку. Мульти-юзер вводит **тенантность** (много владельцев × много областей).
Разбор по слоям — и это **усиливает** выбор Postgres, а не переоткрывает его.

### 6.1 Два слоя изоляции (Defense in Depth) — и где НЕ надо использовать RLS

| Слой | Что изолирует | Механизм | Растёт ли схема? |
|---|---|---|---|
| **Тенант-стена (БД)** | владелец A ↔ владелец B (маркетплейс) | **ОДНА статичная RLS-policy**: `tenant_id = current_setting('app.tenant')` на `nodes`/`edges` | **НЕТ** — одна policy на всё |
| **Тонкий доступ (движок)** | области, read/write по node_type, гранты агентам | grant-резолюция в M-G1 (§1–3), композиция предиката | **НЕТ** — рост = INSERT грантов |

**Критический архитектурный запрет:** НЕ выражать области/гранты через per-область `CREATE POLICY` в
Postgres. RLS-policy — это DDL; если каждая новая область/грант = новая policy, то **схема мутирует =
миграция = нарушение DL-01/DL-18**. Поэтому RLS используется РОВНО для одного: **грубая стена между
тенантами** (одна параметризованная policy по `tenant_id`, добавляется один раз). Всё, что тоньше тенанта,
— грант-данные в движке. Это чистый Defense in Depth: БД ловит катастрофу (кросс-тенант утечку) даже
при баге в движке; движок делает тонкую логику, которую БД делать не должна.

### 6.2 Вердикт по стеку

- **Postgres УСИЛИВАЕТСЯ.** RLS + колоночная тенантность + зрелый MVCC/конкурентность — ровно то, что
  нужно мульти-тенанту. Графовая БД (склон DL-15) такой зрелой построчной тенант-изоляции из коробки
  НЕ даёт. **Мульти-юзер — это аргумент ЗА Postgres против графовой БД, а не против.** Рекомендация:
  зафиксировать DL-15 в сторону Postgres именно на основании тенантности (см. открытые вопросы).
- **TS/Node держится** для v1 и далеко в мульти-юзер. Грант-резолюция на TS — это предикат-композиция,
  не bottleneck при разумной конкурентности.

### 6.3 Когда всплывёт Rust (конкретный триггер, не «на всякий случай»)

Не wholesale-переписывание. Rust всплывает как **точечная замена ОДНОГО горячего пути** при измеренном
нарушении latency-SLA под мульти-тенантной нагрузкой:

- **Горячий путь = grant-резолюция на каждом чтении** (каждый read фильтруется через grant-предикаты).
  Это единственное место, где доступ-как-данные стоит денег на p99.
- **Триггер:** p99 `authorize+read` под N параллельных тенантов пробивает SLA (напр. >X мс) — и профиль
  показывает, что горит именно резолюция/композиция предиката, а не БД.
- **Сначала — не Rust, а кэш:** **effective-permissions как производное состояние (DL-04)** —
  материализованная проекция «принципал → его эффективные гранты» с rebuild-гарантией и синхронной
  инвалидацией при изменении гранта (ровно условие DL-04). Кэш снимает 90% горячего пути на TS.
- **Rust — только если и с кэшем SLA не держится:** переписать модуль grant-evaluation (и, возможно,
  Guard-throughput) как изолированный сервис. Субстрат (2 таблицы) и остальной движок остаются на TS.

**Итог задачи №6:** Postgres — да, крепче прежнего; RLS — да, но одна статичная тенант-policy, не per-грант;
Rust — не сейчас, триггер = измеренный SLA-провал grant-резолюции после того, как кэш-проекция (DL-04)
исчерпан. Стек v1 не переоткрывается.

## 7. UX и агенты

Задача №7. Как владелец выдаёт/ограничивает права из Telegram и как агенты узнают границы.

### 7.1 Пульт = UI над грант-таблицей (не новая подсистема)

Выдать грант = записать grant-событие в журнал (write-pipeline). Из Telegram:

- **Команда/натуральный язык** → парсер (`parse-control.util.ts`, VISION §4) → grant-узел.
  Пример: «планировщик пусть читает мои задачи, но не заметки» → две строки (allow read task,
  deny read note) с `scope: area:local`.
- **Отзыв** = tombstone-событие (DL-17), не удаление.
- **Окно автопилота** = grant с TTL (VISION §2): «на 2 часа разреши writer писать в проект» →
  `mode=auto, ttl=+2h`.
- **Полный аудит** прав — из журнала (кто выдал, когда, на основании чего) — бесплатно из append-only.

### 7.2 Агент ЗНАЕТ свои границы (инъекция) И ограничен движком (принуждение)

Двухслойно (Defense in Depth и здесь):

1. **Знание (кооперация):** на старте сессии движок резолвит эффективные гранты принципала и
   **инжектит их в системный промпт** агента: «ты можешь читать X; писать Y; код НЕ трогаешь; внешне-
   необратимое — через владельца». Агент не гадает границы — **их вычисляет тот же `resolveGrants`**,
   что и enforcement (одна правда).
2. **Принуждение (движок):** даже если агент проигнорит промпт, `authorize()` в M-G1 отклонит акт вне
   гранта (fail-closed). Промпт = вежливость и экономия ходов; движок = стена.

### 7.3 Что упущено / что подготовить (прекурсоры, без которых доступ не строится)

- **Реестр классов действий** (`03-contract/`, пустой узел из аудита A2) — GREEN/YELLOW/RED + read/write/
  erase/promote-policy/grant. **Без него не над чем выдавать гранты.** Первый артефакт.
- **Area-модель** — три area-узла + `member-of` + правило дефолт-резиденции (`scope=private`, DL-12).
- **effective-permissions проекция** (DL-04) — и для инъекции в промпт, и как будущий кэш горячего пути.
- **Схема грант-узла** — канонический конверт §1.1, объявлен на бумаге СЕЙЧАС (VISION §3: два дома данных
  стыкуются контрактом, не блокируя друг друга).
- **Пороговое поле `tenant_id`** на nodes/edges — заложить с первого дня (ретрофит тенантности = боль,
  как provenance-метка). Даже при одном владельце сегодня — колонка есть, RLS-policy одна, дешевле сейчас.

## 8. Открытые вопросы

- **OQ-1 (для DL-15):** ратифицировать Postgres на основании тенантности §6.2? Владелец склонялся к
  графовой БД (DL-15) — этот концепт даёт сильный контраргумент. **Решение владельца.**
- **OQ-2:** резиденция узла — строго ОДНА область (§2.1), или бывают «бездомные»/мульти-резидентные узлы
  (напр. глобальный тип, живущий и в global, и локально)? Дефолт концепта: одна резиденция + гранты
  видимости; подтвердить.
- **OQ-3:** класс `promote-policy` над узкой само-настройкой — какой конкретно scope считается «узким»
  (auto-безопасным)? Нужен критерий границы auto/gated для F-3 (§5.1) — иначе клапан размыт.
- **OQ-4:** `tenant_id` vs `area:local:<person>` — тенант и личная область это одна ось или две?
  (Тенант = биллинг/изоляция маркетплейса; область = логическая группировка внутри тенанта.) Похоже две,
  но подтвердить, чтобы не слить их ошибочно.
- **OQ-5:** секрет-хэндлы (`secret-ref`) — где физически живёт vault и кто разворачивает (движок под
  каким принципалом)? Смежно с M-G4 DataResidency; вынести в отдельную мини-спеку.
- **OQ-6:** нужен ли **ADR** на единую грант-модель? Это auth/storage-решение (по docs-standard — да).
  Рекомендация: завести `ADR-000N-unified-access-grants` после ратификации OQ-1/OQ-4, ссылаясь на
  VISION-agents и этот концепт.

### Резюме для синтеза
Доступ пользователя и акт агента — **одна грант-таблица** над `(принципал × класс × scope)`, каскад DL-02,
всё данные (DL-01). Области = area-узлы + `member-of` (резиденция) + гранты (видимость). Гранулярность =
scope-предикат (view-def, DL-18) — «код не трогает» = одна строка `deny`. Клапан F-3 = грант
`promote-policy` (синтез auto → продвижение по гранту/evidence; над правами — RED). Мульти-юзер **усиливает
Postgres** (RLS = одна тенант-стена, не per-грант); Rust — только точечно на grant-резолюции после
исчерпания кэш-проекции DL-04. UX = пульт над грант-таблицей из Telegram; агент знает границы через
инъекцию `resolveGrants` и ограничен тем же движком. **Пятый примитив и вторая система прав НЕ нужны.**
