## Суть

Объект суверенности здесь — **КОНТРАКТ между ячейкой и движком-хостом**. Ячейка декларирует минимальный
набор примитивов, которые ей нужны от среды (хранить, считать salience, применять линзу, разрешать id).
При переносе в другой движок несовместимость **обнаруживается явно** (рукопожатие версий), а не ломается
молча. Сюда же — **версия схемы при откате движка** (DB-control): движок откатили — старая ячейка не
должна получить неверную трактовку. Это грань «на каких примитивах ячейка вообще может жить».

## Границы

- **Входит:** поле `engine-contract-version` (DATA, заложить сейчас); список требуемых примитивов;
  протокол рукопожатия при импорте; поведение при несовместимости (жёсткий отказ vs деградация до
  частичной функциональности); версия схемы при откате/апгрейде движка (DB-control); кто арбитр
  совместимости (движок / владелец / посредник-агент — Q-S2).
- **НЕ входит:** ЧТО ячейка описывает про свою форму → `01 self-describing`; правила поведения →
  `02 policy-as-data`; где физически payload → `04 foreign-residence`.
- **Тонкая граница с 01:** 01 = «ячейка описывает себя» (форма данных); 03 = «ячейка требует от среды»
  (контракт услуг). При переносе оба проверяются, но это две независимые проверки.

## Развилки (веер «как», не режем)

1. **Модель версии контракта.** Semver примитивов (`engine-contract >= 2.1`) [+ понятно, привычно /
   − надо вести реестр примитивов] vs capability-набор (список требуемых примитивов, а не число)
   [+ точная совместимость / − многословно] vs гибрид: версия + опциональные capability-флаги.
2. **Кто проверяет совместимость (Q-S2).** Сам движок при импорте [+ автоматически / − каждый движок
   реализует] vs посредник-агент/валидатор-сервис [+ единая точка / − доп. компонент] vs владелец
   вручную по отчёту [+ контроль / − ручной труд, блокер].
3. **Поведение при несовпадении.** Жёсткий отказ импорта [+ безопасно, нет тихой поломки / − блокирует]
   vs **деградация**: ячейка живёт частично, недоступные примитивы отключены с пометкой [+ работает
   хоть как-то / − риск скрытой потери поведения] vs read-only-режим для несовместимых.
4. **Заложить сейчас: где хранится версия.** В паспорте каждой ячейки [+ автономно, едет с ней /
   − вес, дубль] vs на уровне типа/шаблона (Г26/Г32) [+ дедуп / − ячейка без типа теряет] vs оба:
   дефолт от типа, override в ячейке.
5. **Откат движка / версия схемы (DB-control).** Транзакционное время на схеме (bitemporal, В2) —
   читать «as-of версия движка T» [+ аудит, чистый откат / − сложность] vs миграции только вперёд +
   запрет отката [+ просто / − теряем откат] vs снапшот схемы в ячейке при записи [+ самодостаточно / − вес].
6. **Что считается «примитивом среды».** Узкий набор (store/read/id-resolve) [+ легко реализуемый на
   любом движке = широкая портируемость / − мало услуг] vs широкий (salience/линза/материализация тоже)
   [+ богато / − мало движков потянут = уже портируемость] — прямая развилка «портируемость vs мощь».
