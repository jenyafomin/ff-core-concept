## Суть

Объект суверенности здесь — **КЛЮЧ и ВЛАСТЬ**: чем открывается доступ и **чья воля** исполняется движком.
Суверенность выражается через то, ЧТО можно делать (capability-токены: «разрешение, а не проверка
личности»), а не только КТО ты. И через **метку источника политики** — `system-default` / `user-defined` /
`agent-proposed+user-approved`: без неё непонятно, чья на самом деле воля исполняется. Центральная
развилка **заложить сейчас**: ключ шифрования **путешествует с ячейкой** (самодостаточна) **vs остаётся
дома** (при переносе — пустая оболочка).

## Границы

- **Входит:** развилка «ключ дома vs с ячейкой» (Q-S1, заложить сейчас); поле `key_ref` внутри/снаружи;
  capability-токены (что можно, а не кто); метка источника политики (делегированная vs первичная
  суверенность, Q-S4, тема A); акт «владелец утвердил политику» (делегированная → подтверждённая); ключ
  доступа к внешней БД прокси (шов с 04).
- **НЕ входит:** ЧТО именно политика разрешает (правила) → `02 policy-as-data`; ГДЕ payload → `04`;
  конституционный потолок над волей (согласие референта) → `06`; проверка личности/роли в UI — это
  Согласие/управляемость, не тут.
- **Тонкая граница с 06:** здесь — «чья власть и ключ у ячейки»; в 06 — «какую власть ячейка/владелец
  НЕ вправе иметь» (референт > владелец). 05 = свобода носителя ключа; 06 = её предел.

## Развилки (веер «как», не режем)

1. **Ключ: дома vs с ячейкой (Q-S1, заложить сейчас).** Ключ едет с ячейкой [+ полностью автономна,
   истинно суверенна / − украл ячейку = украл доступ, риск] vs ключ остаётся в исходном движке [+ перенос
   ≠ утечка данных / − ячейка при переносе пустая оболочка] vs **split**: зашифрованный payload едет,
   ключ по капабилити-токену отдельно [+ баланс / − сложнее, нужен обмен токеном].
2. **Доступ: identity vs capability.** ACL/роли в движке (кто ты) [+ привычно / − не едет с ячейкой,
   зависит от движка] vs **capability-токены** (предъявитель токена может X) [+ переносимо, суверенно /
   − отзыв/ротация сложнее] vs гибрид: capability для переноса, роли внутри дома.
3. **Метка источника политики (тема A).** Обязательное поле `policy_source` в каждой ячейке [+ всегда
   ясно чья воля / − вес] vs выводить из провенанса паспорта [+ дедуп / − неявно] vs только для
   ячеек с override, дефолт = system.
4. **Делегированная → подтверждённая (Q-S4).** Нужен явный акт «владелец принял политику» (статус
   `awaiting-sovereignty` → `confirmed`) [+ честно, чья воля / − трение UX] vs молчаливое принятие по
   умолчанию [+ гладко / − «суверенность» ячейки на деле системная, скрыто].
5. **Право override системного дефолта.** Владелец всегда может переопределить шаблонную политику
   [+ автономия / − ломает гарантии системы?] vs override в рамках, заданных потолком (06) [+ безопасно /
   − связывает 05↔06] vs override с аудит-записью «кто и когда сменил».
6. **Отзыв/ротация капабилити.** Токены с TTL [+ авто-протухание / − надо обновлять] vs отзыв-лист
   (revocation) [+ мгновенно / − нужен онлайн-движок = бьёт по автономии переноса] vs короткоживущие
   + refresh у владельца.
