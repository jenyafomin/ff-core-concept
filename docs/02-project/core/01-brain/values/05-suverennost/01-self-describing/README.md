## Суть

Объект суверенности здесь — **ФОРМА**. Ячейка сама заявляет свою схему/структуру, так что любой движок
прочитает её, **не имея заранее знания о типе**. Перенёс ячейку в чужой продукт — он понимает, что это,
из самой ячейки (self-describing payload: Avro/JSON-LD-подобно), а не из внешнего справочника типов,
которого в чужом движке нет. Сюда же — Г26: разные типы несут свои своеобразные структуры, и эта
структура едет вместе с ячейкой.

## Границы

- **Входит:** декларация схемы внутри ячейки; типы со своей структурой (Г26); версия/эволюция формата
  формы; уровень «жёсткости» схемы (строгая vs schema-less); отделяемость паспорта от payload как
  форма-контракт (паспорт читается по общему правилу на любом зуме — Г6/Ц-1).
- **НЕ входит:** ПРАВИЛА обращения (доступ/забывание) — это форма несёт, но смысл в `→ 02 policy-as-data`;
  минимум примитивов ДВИЖКА, нужных ячейке → `03 engine-contract`; где физически лежит payload
  → `04 foreign-residence`.
- **Тонкая граница с 03:** здесь — «как ячейка описывает СЕБЯ» (её схема); в 03 — «что ячейка требует от
  СРЕДЫ» (примитивы движка). Одна декларация, две стороны: форма данных vs контракт услуг.

## Развилки (веер «как», не режем)

1. **Носитель схемы.** Встроенная inline-схема в каждой ячейке [+ полностью автономна / − вес пассажира,
   бьёт по Ц-1] vs ссылка на схему по `schema_id` + реестр схем, едущий рядом [+ дёшево, дедуп / − нужен
   реестр при переносе] vs гибрид: ходовые типы по `schema_id`, экзотика — inline.
2. **Язык самоописания.** JSON-LD/RDF (граф, связи-как-данные, prior art W3C) [+ стандарт, интероп /
   − многословно] vs Avro/Protobuf-стиль (компактно, эволюция схемы) [+ быстро, версионируемо / − меньше
   семантики] vs свой минимальный `md+frontmatter`-контракт (файлы-истина проекта) [+ читается человеком
   Г4 / − не стандарт].
3. **Строгость.** Строгая схема (валидация на входе) [+ гарантия формы / − жёстко, ломает гибкость Г23]
   vs schema-on-read (форма described, но не enforced) [+ гибко / − мусор проникает] vs дуальность:
   паспорт строгий, payload свободный.
4. **Эволюция формы.** Версия формата в ячейке + правила миграции внутри [+ переживает апгрейд / − вес]
   vs bitemporal-версия схемы (as-of T, как В2 в L0) [+ аудит старой формы / − сложность] vs «форма
   только вперёд-совместима» соглашением.
5. **Кто описывает нестандартный тип.** Автор типа (шаблон) один раз [+ дедуп / − нужен шаблон-механизм,
   смыкается с Г32 наследование] vs каждая ячейка сама [+ автономно / − дубль] vs ИИ выводит схему из
   payload и предлагает на утверждение [+ ленивая типизация / − риск ошибки].
