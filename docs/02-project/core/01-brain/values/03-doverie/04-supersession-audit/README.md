# Направление 04 — Самоаннулирование и аудит (bitemporal-доверие)

## Суть

Устаревшая или опровергнутая запись обязана САМА понизить себя ПРИ ЧТЕНИИ — не молчать с застывшим
высоким confidence (Opus-сценарий «агент на устаревшей ячейке → катастрофа»). Система при этом обязана
уметь ответить «во что я верил(а) в момент X» (аудит назад, Г9) и показать ПОЧЕМУ confidence упал —
иначе доверие превращается в чёрный ящик, которому либо слепо верят, либо слепо не верят. Объект
защиты — **обязанность записи реагировать на своё опровержение** и **честность истории** этой реакции.

## Границы

- **Входит:** `contradicted-by` → самоаннулирование при чтении (policy-as-data, активная обязанность
  записи, не пассивное поле); bitemporal-версионирование confidence (valid-time читается «as-of T»,
  Г9 — это решение В2 из L0 уже принято на уровне узла в целом, здесь — применение конкретно к оси
  доверия); лог/объяснение «что именно упало и почему» при падении confidence (Д8).
- **НЕ входит:** кто вправе выставить `contradicted-by` изначально (→ 03 poisoning-defense —
  авторизация); что происходит, когда ДВЕ записи конкурентно пишутся ОДНОВРЕМЕННО без явного
  противоречия одной из них (→ 05 concurrency-zombie); сама формула обновления confidence при обычном
  использовании (→ 02 calibration).
- **Тонкая граница с 05 (concurrency-zombie):** здесь — реакция ОДНОЙ записи на то, что её явно
  опровергли (`contradicted-by` уже проставлен); там — что делать, когда конфликт ещё НЕ формализован,
  потому что два агента пишут одновременно и ни один не знает про другого. Граница тонкая: неразрешённый
  конкурентный конфликт из 05 со временем должен либо превратиться в явный `contradicted-by` (перейти
  сюда), либо в `conflicts-with` без победителя (остаться в 05).

## Развилки

1. **Где живёт обязанность самоаннулирования.** *(сквозной спин, см. `../README.md`)* Policy-as-data на
   самой записи — каждая запись несёт логику проверки `contradicted-by` [+ суверенно, соответствует духу
   проекта (Ц-5) / − дорого: каждая запись фактически несёт код] vs единый примитив движка, проверяющий
   ВСЕ записи одинаковым протоколом [+ дёшево, гарантированно единообразно / − меньше автономии записи,
   прямое трение с Суверенностью — «своя политика жизни», Г14].
2. **Глубина bitemporal-аудита.** Полная история версий confidence навсегда (Г9, «снапшот назад» без
   ограничений) [+ полный аудит, можно восстановить решение агента в любой момент прошлого / − объём
   данных растёт бесконечно, конфликт с классами памяти по «температуре» (Г13)] vs скользящее окно
   (N версий или M дней, дальше — агрегированная сводка) [+ ограниченный, предсказуемый объём / −
   теряется древняя история, которая может понадобиться юридически или для финансового аудита (Г10)].
3. **Формат прозрачности деградации.** Человекочитаемое объяснение «почему упало» текстом [+ сразу
   понятно человеку без посредника (Г4) / − требует генерации объяснения, рискует быть неточным или
   упрощённым] vs структурный лог событий (что / когда / кто / дельта, машиночитаемо) [+ точно, годится
   для программной проверки и для будущей генерации любого текста поверх / − сам по себе не Ц-1-дёшев,
   требует отдельного просмотра].
4. **Обязательность самопроверки при каждом чтении.** Всегда синхронно проверять `contradicted-by` при
   чтении (гарантия свежести, соответствует Г7 буквально) [+ никогда не отдаст устаревший высокий
   confidence / − цена проверки на КАЖДОЕ чтение] vs проверка лениво / по TTL (кэшируется на период)
   [+ дешевле в среднем / − окно, в котором агент видит устаревший высокий confidence — прямое
   противоречие цели «актуальная истинность», именно тот сценарий, который направление призвано снять].
