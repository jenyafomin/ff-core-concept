# Направление 03 — Защита от отравления (кто вправе писать доверие)

## Суть

Не любой актор может двигать confidence чужой записи — иначе отравление тривиально: массовое
«фейковое использование» поднимет доверие к любой лжи. Нужен явный барьер между «кто-то использовал
запись» (сигнал) и «кто-то подтвердил её» (авторизованное действие), плюс порог, который останавливает
заражение производных/автособираемых индексов раньше, чем оно материализуется в инсайт. Объект защиты —
**сама операция записи доверия**, не факт и не срок его годности.

## Границы

- **Входит:** роль «верификатор», отдельная от автор/владелец/референт; разделение «сигнал использования»
  (пассивно, агрегируется) от «явное подтверждение» (активно, авторизованно меняет confidence); порог
  заражения (contagion threshold) для авто-агрегируемых индексов/линз; распознавание аномальных
  паттернов массового фейкового использования.
- **НЕ входит:** сама формула байесовского обновления после того, как сигнал авторизован (→
  02 calibration); откуда взялась запись изначально (→ 01 provenance); что делает запись, когда её
  явно опровергли (`contradicted-by`, → 04 supersession-audit); что происходит, когда ДВЕ записи
  конкурентно пишутся ОДНОВРЕМЕННО без злого умысла (→ 05 concurrency-zombie — там про недетерминизм,
  здесь — про намеренную/массовую подделку).
- **Тонкая граница с Ц-7 Согласие:** там — «кому видно эту запись вообще» (авторизация ЧТЕНИЯ); здесь —
  «кто вправе МЕНЯТЬ метрику confidence» (авторизация ЗАПИСИ доверия). Легко перепутать: актор может
  иметь право видеть запись, но не иметь права её подтверждать/опровергать.

## Развилки

1. **Кто вправе поднять/опустить confidence (TQ1).** Любой читатель — одним фактом использования
   [+ живо, дёшево, не требует инфраструктуры ролей / − тривиально отравляется массовым фейк-
   использованием] vs отдельная явная роль «верификатор» [+ защищено от отравления / − бюрократия,
   замедляет живую калибровку, может не масштабироваться] vs owner/референт самой записи (Fable §4)
   [+ совпадает с уже существующей моделью прав, не плодит новую роль / − не масштабируется на общие/
   разделяемые записи, где владелец один, а пользователей много].
2. **Сигнал vs подтверждение — одно действие или два шага.** Использование = прямое изменение confidence
   [+ просто, один шаг / − легко засорить одним скриптом] vs использование = сигнал, который лишь
   агрегируется по формуле в отдельном авторизуемом шаге [+ нельзя тривиально отравить одним действием
   / − нужен отдельный агрегирующий примитив и понятная семантика «сигнала»].
3. **Contagion threshold для авто-индексов (TQ6).** Фиксированный порог confidence, ниже которого запись
   не участвует в авто-агрегации [+ просто внедрить и объяснить / − негибко, разные домены требуют
   разной строгости] vs настраиваемый per-домен порог [+ точнее отражает ставки конкретного домена / −
   больше конфигурации, кто её задаёт и пересматривает] vs без порога вовсе, агрегат пересчитывается на
   лету с учётом confidence каждого компонента [+ честно отражает реальный состав, ничего явно не
   исключается / − дорого, недетерминировано при параллельных изменениях компонентов].
4. **Прозрачность решения об исключении.** Исключение записи из волны — видимое, объяснимое решение
   (лог «почему не участвует», смыкается с Д8/04) [+ соответствует цели прозрачности деградации / −
   лишняя телеметрия на каждое авто-исключение] vs тихое исключение движком без следа [+ дёшево / −
   непрозрачно, конфликт с Читаемостью и общей целью Г7 «доверие не должно быть чёрным ящиком»].
