# Направление 06 — Честность данных (единицы/локаль/валюта не врут молча)

- **Status:** draft — дивергенция · **Owner:** JenyaFomin · **Date:** 2026-07-09
- **Related:** `../README.md`, `../../V3-doverie.md` («тихая ложь» единиц/локали/валюты, DATA-side,
  заложить сейчас), `../01-provenance/README.md` (кто ввёл число — там; что число ЗНАЧИТ — здесь),
  `../../V1-chitaemost.md` (тонкая граница: дёшево ли прочитать vs не обманешься ли, прочитав)

## Суть

Доверие рушится незаметнее всего, когда данные технически «верны», но интерпретированы неверно: число
без явной единицы измерения, локали или валюты. «100» — рублей или долларов? «5» — дней или часов?
Это DATA-side проблема, а не процессная: если единица не была записана В МОМЕНТ создания, восстановить
её позже часто НЕВОЗМОЖНО (ретрофит не работает — источник истины утерян навсегда). Объект защиты —
**однозначность интерпретации числового значения**, не его точность и не его происхождение.

## Границы

- **Входит:** явное поле unit/locale/currency на записи там, где применимо (число с «физическим
  смыслом»); проверка на границе записи (Гуард/схема), что число с физическим смыслом не проходит без
  единицы; перечень типов данных, где это критично (деньги, даты, физические величины, проценты,
  временные интервалы).
- **НЕ входит:** сама калибровка confidence (→ 02 calibration); кто ввёл число и на каком основании
  (→ 01 provenance) — это направление НЕ про то, кто соврал, а про то, что даже честное число может
  быть понято неверно из-за скрытого контекста; содержательная проверка правильности значения (не наша
  зона — мы гарантируем, что значение ОДНОЗНАЧНО читается, а не что оно верно).
- **Тонкая граница с Ц-1 Читаемость:** там — можно ли прочитать запись ДЁШЕВО (один взгляд, без
  вскрытия payload); здесь — если прочитал, не обманешься ли из-за скрытого контекста. Дешёвое чтение
  неоднозначного числа — это ХУЖЕ, чем дорогое чтение однозначного: скорость молчаливой лжи опаснее
  медленной честности.

## Развилки

1. **Обязательность поля.** Обязательное поле unit/locale для распознанных типов (Гуард отклоняет
   запись без него) [+ невозможно тихо соврать по конструкции / − нужна надёжная типизация «где
   применимо», лишний барьер для простых записей без числового физического смысла] vs опциональное поле,
   конвенция «указывай, если важно» [+ не тормозит запись простых данных / − возвращает ровно тот риск
   тихой лжи через забывчивость, который направление призвано устранить].
2. **Уровень внедрения.** Часть тонкого паспорта — обязательное поле для ВСЕХ записей с числовым
   значением (системная гарантия, единая для графа) [+ гарантия распространяется автоматически / −
   раздувает тонкий паспорт, от раздувания которого проект сознательно уходил (L0: «0 новых
   обязательных полей»)] vs часть схемы конкретного ТИПА записи (только там, где критично: деньги,
   физвеличины, а не любое число) [+ не раздувает общий паспорт / − нужна поддерживаемая таблица типов
   и её эволюция, риск, что новый тип забудут добавить].
3. **Момент проверки.** На входе — Гуард блокирует запись без явной единицы для распознанных типов
   [+ грязь физически не может попасть внутрь / − требует надёжного распознавания типа «на лету» в
   момент записи, ложные срабатывания тормозят легитимную запись] vs на выходе при чтении — движок
   предупреждает, если единица не задана, но не блокирует запись [+ не тормозит запись / − грязь уже
   внутри графа, видна только постфактум, риск, что предупреждение проигнорируют].
4. **Locale как часть данных vs часть контекста читателя.** Locale хранится вместе с записью
   (абсолютное значение + контекст создания, портируемо между системами — Г19) [+ самодостаточно,
   переживает смену хоста/агента / − увеличивает размер записи] vs locale не хранится, конвертация
   происходит по умолчанию на чтении в locale текущего читателя [+ компактнее / − именно так рождается
   тихая ложь, если конвертация неявная и читатель не заметил, что значение было пересчитано].
