# Ц-1 · Читаемость (Legibility) — углублённая декомпозиция

> Родитель: [../../INDEX.md](../../INDEX.md) · базовый файл: [../V1-chitaemost.md](../V1-chitaemost.md) · L1→L2 · draft

## Определение

Единица отдаёт нужную грань нужному читателю по нужной цене, не вскрываясь целиком.
Поглощает **Прозрачность** (частный случай: грань = «стоит ли брать») и **Полисемию**
(общий случай: граней много) — это две стороны одного разрыва: запись одномерна, чтений
много. Плюс **температуру** (Г13: cold = «читается только по запросу, не всплывает») —
режим существования единицы без изменения её сути.

Читаемость — это не «у единицы есть summary». Это способность единицы **отвечать на вопрос
дешевле, чем стоит вскрыть весь payload**, причём разным вопрошающим — разными гранями.

## Декомпозиция (под-грани)

Одна ценность разложена на 7 атомарных под-граней. Каждая — отдельно тестируема («что
теряется, если убрать именно эту грань»):

1. **П1 — Дешёвый паспорт.** У ячейки есть лёгкая метка (id, тип, salience, one-liner),
   которую можно прочитать не трогая payload. Без неё: любой обзор графа стоит как полное
   чтение — сводки невозможны.
2. **П2 — Полисемия / много граней.** Одна и та же единица имеет несколько валидных
   «ответов» в зависимости от того, КТО спрашивает и ЗАЧЕМ (человеку — одно, агенту-таск-раннеру
   — другое, агенту-архивариусу — третье). Без неё: одна проекция навязывается всем читателям,
   теряется контекст-специфичность.
3. **П3 — Прогрессивное раскрытие (progressive disclosure).** Грани упорядочены по цене:
   label → one-liner → summary → payload → трейс. Читатель платит ровно за глубину, которая
   ему нужна, не за всё дерево целиком. Без неё: «дёшево» и «дорого» не имеют промежуточных
   ступеней — либо всё, либо ничего.
4. **П4 — Линза / точка зрения.** Читаемость не абсолютна — она относительна СПОСОБА
   смотреть. Линза коллапсирует «волну» (потенциальные грани) в конкретную грань. Без неё:
   непонятно, откуда берётся конкретная проекция — граней «много», но нет механизма выбора.
5. **П5 — Температура / видимость без вскрытия.** Cold-единица не всплывает сама, но
   остаётся читаемой по прямому запросу; hot-единица читается по умолчанию. Это ось «когда
   грань доступна», отдельная от «какая грань доступна». Без неё: либо всё в поле зрения
   всегда (шум), либо забытое реально теряется (не читаемость, а эрозия).
6. **П6 — Самоописание цены (self-pricing).** Единица знает и объявляет, СКОЛЬКО стоит её
   прочитать на каждом уровне (токены/время/риск). Без неё: читатель (агент) не может
   бюджетировать чтение заранее — сводка «под бюджет» (Г3) невозможна как гарантия, только
   как угадывание.
7. **П7 — Читаемость для агента ≠ читаемость для человека.** Формат паспорта должен быть
   одновременно машинно-парсируемым (структурные поля) и человеко-читаемым (естественный
   язык) — не два разных объекта, один. Без неё: либо агент не может дёшево матчить (нет
   структуры), либо человек не может понять без агента-переводчика (Г4 нарушен).
8. **П8 — Устойчивость грани к смене типа.** Когда ячейка меняет тип/роль (упомянуто в
   canon-брифе: «конструктор-узел становится чем угодно»), старые грани не должны стать
   нечитаемыми мусором — либо мигрируют, либо явно помечаются устаревшими. Без неё:
   читаемость деградирует при каждой смене типа, копится молчаливый долг.

## Как проявляется

### (i) В механике самой ячейки

- **Поля:** `label` (человеческий заголовок), `summary` (1 строка), `passport` (структурный
  срез: id, type, salience, status, temperature), `payload` (полное тело), `price_hint`
  (оценка стоимости чтения каждого уровня — П6).
- **Рёбра:** ребро само может нести мини-паспорт («о чём эта связь»), чтобы граф был
  читаем без захода в оба узла — читаемость не только у узлов, но и у топологии.
- **Поведение:** ячейка реагирует на «уровень запроса» (label-only / summary / full) как
  на параметр чтения, а не отдаёт всегда всё. Это и есть policy-as-data применительно к
  Читаемости: политика раскрытия — часть данных ячейки, не внешнего движка.
- **Статус `nascent`/`cold`/`hot`:** температура (П5) — явное поле, не побочный эффект
  давности последнего обращения; движок обязан её уважать при построении сводок.

### (ii) В триаде ИИ ↔ человек ↔ система

- **Кто видит:** линза (П4) определяет, какая проекция открывается конкретному читателю —
  агенту с задачей X видна одна грань, владельцу в UI — другая, ИИ-архивариусу при
  консолидации — третья. Видимость грани ≠ видимость факта существования (последнее —
  зона Согласия Ц7, не Читаемости).
- **Кто пишет:** паспорт/summary может писать как человек (вручную), так и агент
  (автогенерация one-liner при создании узла) — но per canon-бриф "владелец ИИ не
  ограничен" (см. корень): агент имеет доступ ко всей полноте, ограничение читаемости
  касается ЧТО ПОКАЗЫВАТЬ ПО УМОЛЧАНИЮ, а не что технически доступно.
- **Кто владеет ценой:** self-pricing (П6) — обязанность самой ячейки, а не внешнего
  калькулятора; это и есть перенос принципа "policy-as-data" на измерение стоимости чтения.

## Новые темы

- **(A) Авторство/владение → П7 (агент/человек-читаемость) и П3 (progressive disclosure).**
  Если узел создан СИСТЕМОЙ (например, автоагрегированный из лога), его паспорт должен явно
  нести признак происхождения, иначе читатель не может калибровать доверие к one-liner'у —
  системный auto-summary и человеческий summary читаются по-разному ("это машина написала"
  vs "это я написал"). Читаемость требует, чтобы authorship был частью самого паспорта
  (лёгкое поле), не глубоко в payload.
- **(B) Авто-индекс/домен-как-волна → прямое попадание в П4 (линза).**
  Если домены/индексы "собираются автоматически как волна по дереву", то линза — это и есть
  тот механизм, который коллапсирует волну в конкретный домен-срез. Читаемость домена
  («к какому направлению жизни это относится?») — не статичное поле, а результат применения
  линзы поверх дерева в момент запроса. Это значит: паспорт не может жёстко зашивать
  "домен = здоровье", только держать сырые сигналы, из которых линза выводит домен на лету.
- **(C) Масштаб/скорость/big-data → П1, П3, П6 напрямую.**
  Читаемость — единственная ценность, которая физически несёт нагрузку масштаба: если
  паспорт не дёшев (П1), если нет промежуточных ступеней (П3), если цена не известна заранее
  (П6) — при росте графа до тысяч/миллионов узлов Читаемость первой ломается и тянет за
  собой продукт (owner: "если хоть одна грань слабая — продукт недееспособен"). Читаемость —
  грань, которая ломается ПЕРВОЙ при масштабе, значит именно её надо стресс-тестировать на
  big-data сценарий раньше остальных.

## Напряжения

- **Читаемость ⟂ Согласие (Ц7).** Дешёвый паспорт хочет быть максимально информативным
  (П1/П6), но pasport сам может утечь чувствительное («о ком», «что скрыто») — cheap-read
  не должен обходить consent-фильтр. Требуется: паспорт фильтруется линзой ДО того, как
  считается «дешёвым», не после.
- **Читаемость ⟂ Суверенность (Ц5).** Self-describing (паспорт несёт свою политику) —
  общая точка, но если каждая ячейка сама решает, что «дёшево» показать, единого контракта
  чтения по графу может не быть (разные ячейки — разные форматы паспорта). Нужен минимальный
  общий шейп паспорта поверх суверенной политики.
- **Читаемость ⟂ Тождество (Ц2).** Полисемия (П2) допускает много граней одной единицы, но
  если грани расходятся слишком сильно, читатель может не узнать, что это ОДНА память —
  граница «разные грани одной вещи» vs «две разные вещи» размыта.
- **Читаемость ⟂ Витальность (Ц4).** Температура (П5) была перенесена из Витальности в
  Читаемость (см. ревизия Fable) — но сам механизм остывания/разогрева (metabolism) остаётся
  в Ц4; граница ответственности («кто решает температуру» vs «как температура влияет на
  видимость») требует явной фиксации, иначе дублирование логики.
