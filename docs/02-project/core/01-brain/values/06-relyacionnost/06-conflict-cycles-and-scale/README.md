# Направление 06 — Конфликт, цикл и масштаб (conflict-cycles-and-scale)

- **Status:** draft — дивергенция · **Owner:** JenyaFomin · **Date:** 2026-07-09
- **Related:** `../README.md`, `../../V6-relyacionnost/ideas/IDEA-conflict-visible-third/README.md`
  (портировано), `../../V6-relyacionnost/questions.md` RQ5/RQ6/RQ7/RQ8, `../../L0-memory-unit.md`
  (Г16 мультиарендность, Г17 конфликт видим третьему)

## Суть

Два ребра могут утверждать несовместимое, граф может зациклиться, два владельца могут спорить за
одно ребро между их узлами — задача реляционности не запрещать это, а сделать ВИДИМЫМ третьей
стороне, вместо тихой поломки или тихого молчания. Отдельно — масштаб: граф с миллионами рёбер
должен обслуживать целостность (осиротение, циклы, каскады) без полного обхода на каждую операцию,
иначе «ткань, не мешок» дискредитируется на практике. Объект защиты — **видимость противоречия +
производительность на масштабе**, обе — потому что незамеченный конфликт и нечитаемо-медленный
граф одинаково убивают доверие ко всему слою.

## Границы

- **Входит:** конфликт двух рёбер = видимый артефакт (не молчаливая перезапись, не блокировка
  записи); намеренные vs случайные циклы в графе; чьё ребро, когда узлы принадлежат разным
  владельцам (мультиарендность, Г16); обратный индекс («кто ссылается на меня») без дублирования
  данных; референсный запрос для нагрузочного теста реляционного слоя.
- **НЕ входит:** сама типизация/каскад ребра (→ 02); протухание одного конкретного ребра во времени
  (→ 04, здесь — противоречие МЕЖДУ рёбрами, а не возраст одного); авторство отдельного ребра
  (→ 01, здесь — спор о владении между СТОРОНАМИ, когда обе претендуют).
- **Тонкая граница с 04:** там — «одно ребро стало неверным со временем»; здесь — «два ребра прямо
  сейчас противоречат друг другу, и кто-то должен это заметить».

## Развилки

1. **Как проявляется конфликт.** Отдельный узел-инцидент, ссылающийся на оба конфликтующих ребра,
   ждущий разрешения [+ конфликт — часть графа, не лог в стороне, виден при обходе / − плодит
   инцидент-узлы, если конфликтов много] vs событие/уведомление во внешнем логе наблюдаемости, не в
   самом графе [+ не засоряет граф служебными узлами / − конфликт не виден при обычном обходе,
   RQ5].
2. **Кто «третий» по умолчанию.** Владелец затронутых узлов (человек решает) [+ финальное слово у
   владельца, соответствует источнику истины / − блокер, если владелец недоступен] vs дежурный
   агент-арбитр с правом временного решения + эскалация человеку при высокой цене ошибки
   [+ не блокирует, автономно разруливает мелкое / − риск, что агент «решит» то, что должен был
   решить человек].
3. **Намеренный цикл vs баг.** Явный маркер `intentional-cycle: true` на ребре, замыкающем цикл
   (например, взаимная causal-связь двух привычек) [+ движок и человек сразу видят «так и
   задумано» / − ещё одно поле, которое легко забыть проставить] vs эвристика (движок сам решает,
   устойчивый ли это паттерн или ошибка ввода) [+ ничего не требует от автора / − ложные
   срабатывания, RQ6].
4. **Чьё ребро при разных владельцах.** Ребро принадлежит создателю (кто заявил связь — тот и
   владелец, независимо от того, что затрагивает чужой узел) [+ просто, соответствует «авторство»
   из 01 / − второй владелец не может отредактировать/оспорить без прав на объект, которым не
   владеет] vs совладение (оба референта — совладельцы ребра, любой может оспорить/пометить `stale`
   со своей стороны) [+ честно отражает, что связь касается обоих / − сложнее модель прав,
   пересекается с Согласием Ц-7].
5. **Видимость ребра отдельно от узлов.** Собственное поле `visibility` на ребре, комбинируется с
   видимостью узлов через AND (строже побеждает) [+ покрывает случай «связь чувствительнее, чем оба
   узла по отдельности» (пример: «A и B встречаются», оба узла публичны) / − ещё одно измерение
   доступа для проверки на каждый запрос, RQ7] vs видимость ребра всегда наследуется от узлов, без
   своего поля [+ проще модель доступа / − не может защитить именно ФАКТ связи, если оба узла
   открыты].
6. **Референсный запрос для масштаба.** «Дай все рёбра узла X» (локальная навигация, наиболее
   частый запрос агента) [+ оптимизируется индексом по узлу, дёшево / − не покрывает многошаговые
   связи] vs «кратчайший путь A→B» (многошаговая навигация, нужна для причинных цепочек) [+ отвечает
   на «как связано» глубже / − дорогой обход без готового индекса путей, RQ8]. Выбор референсного
   запроса определяет, какой индекс строить в первую очередь.
