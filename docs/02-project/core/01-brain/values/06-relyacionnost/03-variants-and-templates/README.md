## Суть

«Другой вариант той же мысли» — это ветвление (git-branch-подобная модель: `variant-of` + указатель
на активную ветку), а не перезапись единицы на месте и не полный форк с потерей связи с оригиналом.
Отдельно — «шаблон → экземпляр»: наследование/переиспользование структуры без того, чтобы экземпляр
тянул за собой судьбу шаблона. Объект защиты — **возможность держать несколько версий мысли
одновременно, зная, какая активна, не путая вариант с мутацией и с полным клоном**.

## Границы

- **Входит:** поле `variant-of` + указатель «активная ветка» как обязательная часть модели вариантов
  (не отдельный хак поверх); разграничение вариант (веер альтернатив от общего якоря) vs форк (новый
  `id`, самостоятельная судьба) vs просто новая temporal-версия той же ячейки (В2); шаблон→экземпляр
  как отдельный род связи (наследование структуры, Г32).
- **НЕ входит:** каскад удаления для типа `variant-of`/`template-of` как таковой (→ 02, здесь —
  модель ветвления, не поведение при разрыве); собственно bitemporal-версионирование одной ячейки
  без вариантов — это Тождество (В2 уже решено на уровне L0, здесь используется как данность).
- **Тонкая граница с 02:** там — «что произойдёт с `variant-of`-ребром, если оригинал удалят»; здесь
  — «как пользователь/агент переключается между вариантами и что значит "активный"».

## Развилки

1. **Модель ветвления.** Git-branch-подобная (несколько параллельных веток от общего якоря +
   указатель активной) [+ явное сравнение вариантов, история сохранена / − нужен UI/API
   «переключить ветку», непривычная модель для не-технического владельца] vs плоский список
   альтернатив без иерархии («вариант 1», «вариант 2» как равноправные независимые узлы) [+ проще
   реализовать / − теряется общий якорь, сложно понять, что это варианты ОДНОГО].
2. **Форк vs вариант vs версия.** Три разных механизма с разным намерением: вариант (`variant-of`,
   веер, может остаться не связанным с другими вариантами) vs форк (новый `id`, самостоятельная
   судьба, историческая ветка разошлась совсем) vs temporal-версия (та же ячейка, В2, для эволюции,
   не альтернатив) [+ точная семантика под три разных сценария / − три похожих механизма, риск
   путаницы «каким пользоваться»] vs один универсальный механизм версии+ветки [+ проще ментальная
   модель / − теряет нюанс «это правда другой вариант, а не следующий шаг эволюции»].
3. **Шаблон→экземпляр: что наследуется.** Экземпляр копирует структуру шаблона при создании
   (snapshot, дальше независим) [+ просто, экземпляр не ломается при правке шаблона / − изменения
   шаблона не долетают до старых экземпляров, дрейф] vs экземпляр держит живую ссылку на шаблон
   (`template-of`, структура резолвится на лету) [+ правка шаблона обновляет всех сразу / − риск
   сломать все экземпляры одной правкой шаблона, обратный каскад].
4. **Кто переключает активную ветку.** Явное действие пользователя/агента («сделай вариант Б
   активным») [+ осознанный контроль / − лишний шаг в интерфейсе, трение при частом планировании
   (сценарий «разные планы недели»)] vs движок сам предполагает активную ветку по последнему
   обращению [+ ничего не спрашивает / − неявное решение, легко потерять, какой вариант «на самом
   деле» текущий].
5. **Схлопывание вариантов.** Варианты можно смёрджить обратно в один (веер закрылся, выбор
   сделан, остальные архивируются, не удаляются) [+ обратимо, история выбора видна / − нужен явный
   merge-протокол, кто решает конфликт полей] vs варианты живут вечно параллельно, ничего не
   схлопывается [+ просто / − граф копит бесконечно альтернативных веток, которые никто не
   закрывает].
