# 🔶 Fable-ответ #1 — hard-erase

## 1. ПРАВИЛО приоритета ролей (owner / referent / author)

Вы спорите «кто главнее» — это ложная постановка. Роли не конкурируют за один объект:
их претензии направлены на РАЗНЫЕ части ячейки. Конфликт решается **расщеплением узла**,
а не выбором победителя.

> **ПРАВИЛО R-ERASE (три строки):**
> 1. `referent` абсолютен над **содержанием-о-себе** (PII-payload, assertion «о нём»). Owner не имеет вето.
> 2. `owner` абсолютен над **существованием и структурой записи** (оболочка узла, свои аннотации,
>    факт «запись была»). Referent не может требовать удаления чужой записи целиком.
> 3. `author` = **ноль erase-прав.** Авторство — провенанс (факт), не собственность. Претензии автора
>    редуцируются либо к owner-праву (если он owner), либо к referent-праву (если контент — о нём).

Исполнение: erase-запрос референта = **редакция** (purge payload-about-referent + терминальное
событие), запись owner'а живёт дальше как «узел с вырезанным сегментом». Это ровно GDPR-логика:
право на забвение бьёт по персональным данным, а не по чужому архиву. Следствие для модели: узел,
смешивающий «о ком» и «чьё» в одном payload, — анти-паттерн; assertion-рёбра (DEC-8) уже дают
нужную гранулярность — erase режет по рёбрам-об-референте.

**Опекун согласия (consent guardian) — нужен, но не как человек-роль.** Активируется ровно в одном
случае: **референт не является действующим субъектом системы** (третье лицо, упомянутое в записи;
умерший; недееспособный). Тогда его согласие держит **конституционный слой** (policy-as-data,
верх оси авторитета): default-deny на выдачу PII не-субъектов наружу, erase-по-запросу через
owner-канал. Не заводите guardian'а как четвёртую роль ячейки — это дежурное поведение Конституции,
иначе плодите роли.

## 2. Тип × слой: вердикт + физическое исполнение

**Да, слой бьёт тип — но по причине, которую надо зафиксировать точно.** Не «слой главнее», а:
запрет журнала лежит на оси **авторитета** (конституционный `no-mutate` append-only структуры),
а `erase=true` — на оси **охвата** (тип). Авторитет > охват — это уже ваше принятое правило
двух осей; C-1 закрывается им без новых сущностей. DEC-2 не «сломан», он **неполон**: erase-capability
типа = *необходимое* условие, конституция слоя = *ограничение способа исполнения*.

Ключевой сдвиг: запрет журнала — про **целостность цепочки**, а не про payload. Значит правило:

> **Журнал никогда не хранит единственную копию стираемого контента.**
> journal-entry = `ref + hash`, payload живёт в payload-store. Erase = purge в payload-store +
> терминальное событие в журнал. Hash остаётся — цепочка цела, PII невосстановима
> (hash обязательно СОЛЁНЫЙ per-record, иначе низкоэнтропийные PII — телефон, имя — добираются перебором).

Для копий, которые нельзя purge'ить (WAL, бэкапы, реплики — ваш блокер R1 и D-3a):
**crypto-shredding с гранулярностью ключа = гранулярность erase-права**, т.е. ключ
per-(referent × record-сегмент), не per-база. Erase = уничтожение ключа; WAL/бэкапы мгновенно
превращаются в шум без перезаписи.

**ADR — да, один, и шире, чем спрошено:** не «журнал без инлайн-payload», а
**«Разделение стираемого payload» (erasable payload separation)**: (1) журнал ref+salted-hash;
(2) payload-store purge-able; (3) crypto-shredding для WAL/бэкапов/реплик; (4) терминальное событие
как единственный след. Узкий ADR только про журнал оставит R1 открытым — сырой payload
в WAL переживёт любое ваше правило.

## 3. Слепая зона (невидимая линзам analyst/critic)

Все четыре спора (a-d) молча предполагают, что стираемый факт живёт в **одном узле**. Но ваш же
рефрейм (msg 141): граф — субстрат, агенты **читают и пишут обратно**. Стёртый факт к моменту
erase уже **метастазировал в производные**: summary-узлы, память агентов, эмбеддинги/индексы,
трейсы, отправленные наружу сообщения. Вы закрыли (c) каскадом на VariantGroup — но variant-of
это один тип ребра; деривация идёт по **всем** типам (summarize, infer, quote). «Consent re-check
at emit» ловит будущие выдачи — никто не спросил: **что делать с уже-выведенным?** Erase без
taint-замыкания по деривациям — театр: агент «помнит» стёртое и переизлучит его своими словами.
Это FQ7 (каскад на агрегаты), но радикальнее: каскад не по иерархии, а по ВСЕМУ графу происхождения,
включая вне-графовые артефакты (индексы, кэши).

Вторая, мелкая и острая: **терминальное событие само — PII.** «Референт X потребовал стереть» —
утечка того, что X существовал и что о нём была запись. Терминальное событие обязано быть
анонимизированным по тому же ref+hash-правилу.

## 4. Один инвариант-на-сейчас (ретрофит невозможен)

> **INV-LINEAGE: «erase-охват вычислим с рождения записи».**
> Движок отклоняет любую запись (узел/ребро), не несущую в момент создания:
> (1) `about`-ссылки — о каких референтах, и (2) `derived_from`-ссылки — из чего выведено.
> Без исключений, включая записи самих агентов.

Почему именно это: провенанс **невозможно восстановить задним числом** — через полгода никто не
скажет, из каких источников агент собрал summary, и erase станет неразрешимой задачей навсегда.
Все четыре спора брифа + слепая зона п.3 упираются в один вопрос «ЧТО входит в охват erase(x)?» —
INV-LINEAGE делает ответ вычислимым (taint-замыкание по `derived_from` ∩ `about`). ref+hash-журнал
тоже нетретрофитен, но он уже пойман DEC-6; lineage не поймано никем — и оно дешёвое сейчас
(два обязательных поля паспорта) и бесконечно дорогое потом.

## Следующий шаг
Ратифицировать: R-ERASE (расщепление, не победитель) + «авторитет>охват» как закрытие C-1 +
ADR «erasable payload separation» (расширенный DEC-6) + INV-LINEAGE в Конституцию. Затем
system-architect: спека taint-замыкания erase по `derived_from` (включая индексы/кэши агентов).
