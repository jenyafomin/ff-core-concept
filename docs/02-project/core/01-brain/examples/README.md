# Examples — как мы проектируем brain через примеры

> **Зачем эта папка.** Мы проектируем субстрат памяти не кабинетным спором, а **на реальных данных**.
> Пример — это узлы/рёбра/акты в **чистом JSON** + разбор того, как субстрат должен их принять,
> сохранить, показать. JSON здесь — **главный показатель**: насколько модель вообще способна честно
> отобразить живой факт. Этот файл = ВИД контейнера + **правило**, которому следует каждый пример.

## Два вида примеров (различаются намерением)

| Вид | Зачем | Обязателен | Привязка |
|-----|-------|-----------|----------|
| **killer** (фальсификатор) | **РЕШИТЬ** спорное | имеет **критерий провала** — прогон может упасть и сломать ратифицированное (DL) | `targets: [FQ25, FQ7, DL-27…]` |
| **exemplar** (иллюстратор) | **ПОНЯТЬ** возможность/форму | падать не обязан; должен быть честным | `targets: [способность/сценарий]` |

Правило killer'а (по Fable): пример закрывает вопрос, только если у него **заранее объявлен исход,
который опровергает конкретный DL**. Нет падающего критерия → это иллюстрация, не решение.

## Три режима работы над примером

1. 🔍 **Разобраться** — агент читает пример + доки-модель → «понял бы? где неоднозначно?». Распутать путаницу.
2. 💥 **Прогнать** — скрипт/агент вытягивает данные по правилам модели → сверка с ожиданием → падает/нет.
3. 🎨 **Творческий** — берём идею ОДНОГО примера и несколькими итерациями **абстрактно углубляем,
   расширяем, усложняем** его: даём максимально гибкую, объёмную форму и всё, что ему понадобится.
   Цель — вырастить богатое, интересное взаимодействие со всей моделью на одном живом кейсе.

## Структура (каждый пример = своя папка)

```
examples/                         ← контейнер (плюрал, БЕЗ номера) — этот README = ВИД + правило
  NN-<slug>/                      ← ОДИН пример = одна папка (узел, R1: 01- 02- …)
    INDEX.md                      ← ВИД примера: frontmatter (kind, targets, mode, status) + разбор/вердикт
    data/                         ← ЧИСТЫЙ JSON: узлы/рёбра/акты. Главный фокус — показатель отображаемости
    01-<stage>/ 02-<stage>/ …     ← ЭТАПЫ примера, СВОЯ нумерация на каждый пример; наборы разные:
                                     напр. 01-analysis → 02-db-concept → 03-build → …
    analysis/  ideas/             ← общие плюрал-контейнеры (по потребности; дети нумеруются)
    probe/                        ← (только killer) гипотеза-фальсификации + падающий скрипт
```

**Закон:** папка примера подчиняется тому же дерево-канону (`.claude/rules/doc-tree.md`) —
три архетипа: `NN-` узел (этапы) · `plural/` контейнер (`analysis/ ideas/`) · `_` служебка.
Этапы у каждого примера **свои и в своей последовательности** — не все примеры одинаковы:
иногда нужна лишь аналитика; иногда — аналитика → концепт-схема БД → сборка.

## Дисциплина

- **Фокус на данные:** сначала честный JSON в `data/`, потом разбор. JSON — индикатор качества модели.
- **Итеративно и по-отдельности:** новый приход → новая нумерованная папка-пример, приходы не смешиваем.
- **Истина в домах:** решения/инварианты, рождённые примером, поднимаются в `../decisions.INDEX.md`
  и соответствующий `../questions/FQ*/`; сам пример остаётся кейсом-свидетельством.
- **Строй-гейт:** на диск — только по явному «строй» владельца; иначе описываем.
- **Trace хода** пишется в `docs/_log/<дата-тема>/` (gitignored), истина сюда не дублируется.

## Реестр типов

Тип файла `example` пока описан локально этим README. Внесение `example` в канон
`docs/.doc-types.json` (homeRule → `01-brain/examples/NN-<slug>/`) — правка канона (R1),
делается через `agent-builder` + одобрение владельца. До тех пор правило живёт здесь.
