# Killer-кейс: модель, доказанная НА ДАННЫХ

> До этого файла модель существовала как **проза** (13 единиц, схема, граф-вид, 9 процессов, сквозная
> картина). Верификация (VERIFICATION.md) вынесла вердикт **УСЛОВНО-НЕТ**: «модель правильно описывает
> себя как ИДЕЮ, но ни разу не показывает себя как ДАННЫЕ». Здесь мы это чиним: берём **один реальный
> прогон graph-loop**, заворачиваем его в **65 узлов одного конверта** и **реально исполняем** линзу
> расходов скриптом. Пока `view:cost-tree` не вернул реальную сумму токенов — модель была гипотезой.
> **Он вернул. Гипотеза стала данными.**

## Что за прогон моделируем

Реальная сессия-обзор (2026-07-24): владелец голосом попросил «объясни, что такое 13 видов». Главный
агент `agent:ff-personal` прочитал контекст, **делегировал ТРЁМ под-агентам-разведчикам** чтение единиц
(1–4 / 5–8 / 9–13), затем синтезировал ответ. Это настоящий graph-loop с делегированием и настоящими
замерами токенов у детей.

## Как воспроизвести

```bash
cd docs/02-project/core/02-agents/examples/01-agent-manager/_generated-examples
node run-view.mjs
```

Скрипт: (1) строит **инверсный индекс рёбер** (DEC-12 — храним одну сторону, обратную вычисляем);
(2) **валидирует** весь корпус (конверт · рёбра-пары · meta-типы с example); (3) **исполняет три линзы**.
Ничего не пишет на диск. `exit 0` = валидация прошла и линза вернула сумму.

## Что это ДОКАЗЫВАЕТ (на данных, не на слове)

- **Дерево расходов — настоящее.** `view:cost-tree` обошёл рёбра `delegates-to`, для каждого агента
  вычислил стоимость через **инверсию** `measures` (snapshot → agent), свернул по поддереву и вернул
  **181 946 токенов** — реальная сумма реального прогона, а не иллюстрация. Дети (`measured`) дают
  124 546; self главного — `57 400` и честно помечен **RECONSTRUCTED** прямо в выводе.
- **Права видимости = ТОТ ЖЕ запрос.** `view:visible-to` — тот же движок, только `filter` читает поле
  **конверта** `visibility.readable_by`, а не body. Гостю видно 2 узла из 65 — новый вопрос про доступ
  решён линзой, не новой схемой (DEC-11).
- **Инверсия вычисляется, не хранится.** В данных лежит только одна сторона каждого ребра (54 ребра);
  обратный обход (25 целей) построен скриптом — ровно закон doc-tree №1 «файлы=истина, индекс=generated»
  и DEC-12.
- **Meta-слой замкнут.** 13 доменных типов + `view`/`policy` объявлены узлами `meta:type/*`, у каждого —
  ребро `example` на живой узел; 18 предикатов — узлы `meta:pred/*` с инверсией и `canonical_direction`.
  Валидатор падает (`exit 1`), если хоть один тип без примера или предикат без пары — «тип без данных»
  структурно запрещён (DEC-13).

## Развилки, зафиксированные ПО ФАКТУ ДАННЫХ

- **Q-10 (учёт затрат) — РЕШЕНО как `subtree`.** `policy:snapshot-adaptive.body.aggregate = "subtree"`:
  родитель показывает `self + все потомки`. Скрипт реализует именно рекурсивный rollup по всему
  поддереву делегирования. Здесь глубина = 1 (main → A/B/C), но `costTree()` рекурсивен — на внуках
  свернёт так же. Это **осознанный выбор для проверки**; альтернатива (только прямые дети) дала бы то же
  число на этом прогоне, но разошлась бы на 2+ уровнях делегирования.
- **Q-9 (стопкран лупа) — предохранитель заведён.** `policy:loop-guard.body.max_iterations = 5`,
  `on_exceed = "halt+flag"`; `graph-loop:agent-map` и `loop-run` ссылаются на него через `policy_ref`.
  В этом прогоне `loop_backs = 0` — предохранитель не сработал, но в модели теперь ЕСТЬ (раньше `loop-back`
  мог крутиться бесконечно).

## Что осталось ЧЕСТНО недоказанным

- **Масштаб (Q-7).** 65 узлов — не нагрузка. «Не станет ли одна база тормозом» этот корпус НЕ проверяет;
  нужен корпус на 10³–10⁴ узлов, чтобы увидеть предел единой БД.
- **self реконструирован, не измерен.** 57 400 токенов главного агента — разумная оценка (чтение 5 файлов
  + оркестрация 3 делегирований + синтез), помеченная `reconstructed` и в данных, и в выводе. Итоговое
  число поддерева ЧАСТИЧНО reconstructed — честнее было бы взять реальный замер self в следующем прогоне.
- **Глубина делегирования = 1.** Разница `subtree` vs `direct-children` (Q-10) на этих данных НЕ видна
  (совпадает). Нужен прогон с под-под-агентами (внуки), чтобы число реально разошлось и выбор subtree
  стал доказанным, а не просто заявленным.
- **loop-back не исполнен.** `policy:loop-guard` заведён, но `loop_backs = 0` — предохранитель ни разу не
  сработал. Проверка «стоп при превышении max_iterations» требует прогона с реальным циклом.
- **B2/B4 вне этого дома.** Консолидация `task` и propagate переименований в `05-processes/` — отдельный
  проход, не входит в killer-кейс.
- **view-над-view и материализация запрещены в v1** (DEC-11) — здесь не проверялись, потому что не
  использовались; ограничение принято на веру.
