# Процесс: knowledge-resolve

## Суть
Единица (агент/задача/…) достаёт знание одним из двух режимов — **`embed`** (данные лежат прямо в узле)
или **`ref`** (ссылка на партицию единой базы знаний), плюс **линза** — фильтр вида без копирования
данных.

## Вход
- `policy:knowledge-ref` — `{target: knowledge, mode: embed|ref, fallback}`.
- `knowledge-base(U7)` — `partitions[]` (`user-knowledge`, `project-knowledge`, `agent-memory`),
  `operations[]`, `lenses[]`.
- Запрашивающая единица (агент/task/…) и её `policy_ref`.

## Шаги
1. Единице нужно знание → читает свой `policy_ref` на предмет `knowledge.mode`.
2. **`mode = ref`**: единица хранит/читает указатель на партицию базы (`kb:*#partition`) — данные не
   копируются.
3. **`mode = embed`**: знание лежит инлайн в `body` самой единицы — самодостаточно, без зависимости от
   графа.
4. Если запрошен `ref`, а партиция/линза недоступна — включается `policy.fallback` (обычно `embed`).
5. Чтение через линзу: `agent --views-via--> lens`; `lens.filter` применяется к целевой партиции(ям),
   возвращая отфильтрованный вид — БЕЗ создания копии.
6. Запись: выполняется `capability` (`op:write`, scope `own-partition`) или `op:link` (межпартиционная
   связь), с проверкой `requires_valve`.

## Выход
- Знание доступно единице (через ссылку или встроенное).
- Линза-вид вычислен на лету (не хранится как отдельный узел-истина).
- `knowledge-base.acts[]` пополняется при записи (`{at, op, node_id, by}`).

## Ограничения
- **Embed рискует дублированием.** Если тот же факт уже существует как партиция базы, embed создаёт
  второй, несинхронизируемый экземпляр — правила дедупликации между embed-копией и партицией не описаны.
- **Ref зависит от доступности базы.** Если партиция/линза недоступна, единица деградирует до fallback —
  без явного правила, восстанавливается ли позже связь с базой (промоция embed→ref) или это разрыв
  навсегда.
- **Граница партиций размыта.** Неясно, где заканчивается `project-knowledge` и начинается
  `agent-memory` (напр. «агент запомнил, что в этом проекте лучше не спешить» — факт о проекте или
  память агента?) — влияет на то, В КАКУЮ партицию резолвится ref.

## Открытые вопросы
- Q-1: физически — один граф с тегами-партициями, или отдельные графы/индексы per partition? Влияет на
  стоимость линзы «сквозь» несколько партиций сразу.
- Q-2: fallback `ref → embed` при недоступности — временный (реконсилируется потом) или постоянный?
- Q-3: кто утверждает новую линзу — агент автономно, или нужно явное одобрение владельца (по аналогии с
  R1/promotion из `~/.claude/rules/on-demand/evolution.md`)?

## Мини-пример
```json
// до: agent-memory ещё не связана с базой (недоступна партиция)
{ "policy_ref": ["policy:knowledge-ref"], "knowledge": null }

// после: fallback на embed сработал
{
  "policy_ref": ["policy:knowledge-ref"],
  "knowledge": { "mode": "embed", "fact": "владелец не спешит в код без явного «строй»" }
}
```
