# Схема агентской системы — одна база, простой скелет, гибкая надстройка

> Цель этого файла: показать **из чего всё состоит** и **как взаимодействует** — максимально просто,
> но детально. Это не 12 разных структур, а **одна модель**: всё — узлы одной базы. Читается сверху вниз
> «от простого к сложному»: сперва один общий скелет, потом типы, потом движение, потом настройка.

---

## Уровень 0 — одна идея

**Всё — узел одной базы. Узел = системный конверт + обычные поля + рёбра.**

```
node = { <системные поля>  +  <обычные поля>  }  --рёбра--> другие node
```

- **Системные поля** — общие для ЛЮБОГО узла, ими владеет движок (framework-owned). Их не сочиняют под
  каждый тип — они всегда одни и те же (id, тип, состояние, видимость, акты…). Полный список → `_system/envelope.md`.
- **Обычные поля** — доменные, свои у каждого типа (у `task` — срок, у `snapshot` — метрики). Их мы придумываем.
- **Рёбра** — связи между узлами, полиморфные (см. Уровень 2).

Почему так: лечит «подключается, но невидимо». Скилл, MCP, правило, затрата — **не скрытая обвязка, а узлы**
с одинаковым конвертом. Всё видно ИИ единообразно.

---

## Уровень 1 — системный конверт (скелет любого узла)

Минимальный общий набор (детали и примеры — в общем `../../_schema/envelope.md`, он один на все примеры):

| Системное поле | Что | Зачем |
|----------------|-----|-------|
| `id` | адрес узла | тождество, ссылки |
| `type` | тип узла | решает обычные поля и дом |
| `state` | живое состояние | статус/фаза сейчас |
| `edges` | рёбра к другим | связность графа |
| `view` (lens) | сохранённая проекция/фильтр | СМОТРЕТЬ данные разными видами, **без копии** |
| `visibility` | кто/что видит узел | эпистемический клапан (метка, не стена) |
| `access` | что узел вправе трогать | права (это НЕ `view` и НЕ `visibility`) |
| `acts` | append-only история | что менялось, кем, когда → связь с затратами |
| `policy_ref` | ссылки на политики | настраиваемое поведение (Уровень 4) |

> **Развод перегруженных слов** (по критику): `scope` больше не одно поле — распадается на
> `visibility` (кого видно), `access` (что можно), `binding.target` (к чему привязан). `lens`↔`view` —
> одно: сохранённый вид/фильтр. `rule` (утверждение-норма) и `policy` (настройка поведения движка) — РАЗНЫЕ узлы.

## Уровень 2 — рёбра (полиморфные связи + словарь)

Ребро = `{ predicate, target, ...мета }`. Один узел может крепиться к разным вещам разными предикатами —
**связи непредсказуемы** (ответ владельца по playlist). Поэтому предикат — данные, а не хардкод.

**Словарь канонических пар (инверсии)** — чтобы граф читался с обеих сторон:

| Прямой | Обратный |
|--------|----------|
| `runs-in` | `hosts` |
| `composed-of` | `part-of` |
| `delegates-to` | `delegated-by` |
| `drives` (loop) | `driven-by` |
| `emits` (output) | `emitted-by` |
| `scopes` (space→x) | `scoped-by` |
| `measures` (snapshot→x) | `measured-by` |
| `triggers` (event→x) | `triggered-by` |
| `bound-to` (skill→phase) | `binds` |

Правило: **новое ребро объявляется парой** и поднимается в `01-overview`. Иначе граф «лжёт».

## Уровень 3 — типы узлов (это просто `type` + обычные поля)

12 единиц из дефектовки — это НЕ 12 структур, а один конверт с разным `type` и своими обычными полями:

`agent · user · project · space · role · telegram-module · planning-module · knowledge-base ·
skill · playlist · loop(graph-loop) · phase · action* · event · snapshot · output · rule · policy · view`

\* `action` — **добавлен** (был дырой): центральный узел `loop --sequences--> action --emits--> output`,
`snapshot --measures--> action`. Каждый тип детально расписан в `../02-defectovka/<единица>/`.

## Уровень 4 — движение и настройка (где живут «по-разному»)

Данные не лежат мёртво — ими двигают **механики**, а КАК именно — задаёт **политика-узел** (настройка = данные).
Здесь приземляются 4 ответа владельца:

| Механика | Статическая связь | Настройка (policy-узел) — «по-разному» |
|----------|-------------------|----------------------------------------|
| **Знание** | `x --stores/reads--> knowledge-base` | `knowledge.mode = embed \| ref` — знание внутри единицы ИЛИ ссылкой на партицию единой БД (оба режима, выбор = данные) |
| **Пространство** | `space --scopes--> {user,agent,rule}` | `space.parent` → **вложенные** space; per-user `policy_overrides` |
| **Скиллы/луп** | `phase --binds--> playlist --bundles--> skill` | привязка **полиморфна**: playlist крепится к phase (дефолт для поиска), к loop, к типу задачи — к чему угодно |
| **Затраты** | `snapshot --measures--> action` | `snapshot.policy`: адаптивная частота (гуще при росте контекста), хранение **деревом**, агрегат по дочерним агентам |

**Ключевой принцип (DEC-6):** гибкость — не «решим потом», а **first-class**: режим поведения — это узел
`policy`, который движок читает. Одна и та же схема работает по-разному в разных местах/времени.

## Уровень 5 — «всё в одной БД»: сила и предел (открытый вопрос Q-7)

Плюс единой базы: один конверт, один язык рёбер, один способ смотреть (view) — ИИ видит всё однородно.
**Предел, который проверяем на killer-примере:** не станет ли «всё в одной БД» тормозом (масштаб, изоляция
доменов, права)? Ответ ищем данными, не спором — это цель фазы 2.

## Что системное, а что обычное — и куда класть

- **Системное** (конверт, словарь предикатов, политики-движка) → ОБЩИЙ `../../_schema/` (одно на все примеры).
- **Обычное** (доменные поля типа) → в дефектовке своего типа `../02-defectovka/<тип>/`.
