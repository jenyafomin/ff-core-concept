# U4 · space / team / role — эталон дефектовки

## 1. Суть
Пространство взаимодействия — TG-группа/топик (или другая площадка в будущем) как **область
настройки**. Не «чат, куда пишут», а узел с собственными участниками, собственными правилами и
собственным «можно/нельзя» для КАЖДОГО участника отдельно. Один и тот же агент в разных пространствах
может вести себя по-разному — это не хардкод в коде агента, а данные пространства.

## 2. Переменные (поля)

| Поле | Тип | Зачем | Пример |
|------|-----|-------|--------|
| `id` | node-id | тождество пространства | `space:tg-ff-personal:topic-56` |
| `surface` | конструктор | где физически живёт | `{channel, chat_id, thread_id}` |
| `members` | member[] (конструктор) | кто в пространстве и с каким статусом | `[{user, status, joined_at}]` |
| `policy_default` | конструктор | правило «по умолчанию» для пространства | `{can_read, can_write, can_trigger_agent}` |
| `policy_overrides` | override[] (конструктор) | **per-user** отклонения от default (не строка!) | `[{user, allow[], deny[], note}]` |
| `roles` | role[] (конструктор) | именованные роли, на которые ссылаются overrides | `[{role_id, allow[], deny[]}]` |
| `binding` | конструктор | к какому проекту/агенту привязано пространство | `{project, agent}` |
| `state` | конструктор | текущий живой статус | `{active, last_activity_at}` |
| `acts` | акт[] | история изменений правил/участников (append-only) | `[{at, kind, by, target}]` |

## 3. Под-сущности (сами становятся узлами)
- `member` — участник пространства: ссылка на `user(U2)` + статус в ЭТОМ пространстве (не глобальный
  статус пользователя).
- `policy-override` — точечное правило «для этого юзера в этом пространстве» — расширяет или сужает
  `policy_default`; хранится отдельной записью, не мержится молча.
- `role` — переиспользуемый набор allow/deny, на который может ссылаться несколько `member` (чтобы не
  дублировать один и тот же набор прав в каждом override).

## 4. Связи (рёбра)
```
space(U4) --scopes--> {user(U2), agent(U1), rule}     (кто/что можно в этом чате)
space(U4) --binds-to--> project(U3)
space(U4) --hosts--> agent(U1)                          (какой агент отвечает в этом пространстве)
telegram-module(U5) --surfaces--> space(U4)              (пространство = слепок реального чата/топика)
user(U2) --member-of--> space(U4)
```

## 5. Форма данных (конструктор)

**Быстрый пример:**
```json
{
  "id": "space:tg-ff-personal:topic-56",
  "type": "space",
  "surface": { "channel": "telegram", "chat_id": "1112667160", "thread_id": "56" },
  "binding": { "project": "project:ff-personal", "agent": "agent:ff-personal" },
  "members": [
    { "user": "user:owner", "status": "owner", "joined_at": "2026-06-01" },
    { "user": "user:guest-1", "status": "member", "joined_at": "2026-07-10" }
  ],
  "roles": [
    { "role_id": "role:read-only", "allow": ["read"], "deny": ["trigger_agent", "write"] }
  ],
  "policy_default": { "can_read": true, "can_write": false, "can_trigger_agent": false },
  "policy_overrides": [
    { "user": "user:owner", "allow": ["*"], "deny": [], "note": "полный доступ" },
    { "user": "user:guest-1", "role": "role:read-only", "note": "смотрит, не пишет" }
  ],
  "state": { "active": true, "last_activity_at": "2026-07-23T10:00:00Z" },
  "acts": [ { "at": "2026-07-10", "kind": "member.added", "by": "user:owner", "target": "user:guest-1" } ]
}
```

**Вариант A (личный чат, без team):** `members` — один элемент (owner), `policy_overrides` пустой,
`policy_default` = «всё можно» — пространство вырождается в приватный канал одного агента и владельца.
**Вариант B (пространство без топика, весь чат):** `surface.thread_id` отсутствует — правила
пространства действуют на уровне всей группы, а под-пространства (топики) наследуют и переопределяют.

## 6. Дизайн-паттерн / метод
- **Policy-as-overrides, не policy-as-string.** `policy_default` + список точечных `policy_overrides`
  вместо одной строки прав на пространство — позволяет настроить «можно/нельзя» под каждого без
  переписывания всего правила.
- **Role — переиспользуемый узел, не копипаста прав.** Несколько `member` ссылаются на один `role`,
  вместо того чтобы каждый override нёс свой полный набор allow/deny.
- **Member ≠ user.** Статус участника — свойство ПРОСТРАНСТВА (кто он ЗДЕСЬ), а не глобальное свойство
  пользователя — тот же человек может быть owner в одном топике и guest в другом.

## 7. Открытые вопросы
- Q-1 (владелец, открыт явно): **space/team/role — одна единица с гранями (surface+members+policy) или
  три разные единицы**, где `team` = снятый с конкретного чата список участников (переиспользуемый между
  пространствами), а `role` = вообще отдельный самостоятельный справочник прав? Текущий черновик
  склеивает их в одну единицу с под-сущностями — нужно решение, стоит ли разрывать.
- Q-2: если пространств много и в них один и тот же `role:read-only` — где физический дом ролей: внутри
  каждого `space` или в общем справочнике `roles/` (плюрал-контейнер), на который пространства ссылаются?
- Q-3: `policy_overrides` наследуются ли от группы к топику (см. Вариант B), и как разрешается конфликт
  «default группы» vs «override топика»?
