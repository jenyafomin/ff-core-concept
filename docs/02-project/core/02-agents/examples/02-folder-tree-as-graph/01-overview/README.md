# Folder-tree-as-graph — как наша инфраструктура папок ложится в базу

> **Одной фразой.** Берём наш второй пример (после `01-agent-manager`) и кладём как **данные (граф)**
> не «мир вокруг агента», а **саму нашу инфраструктуру папок/доков** — чтобы увидеть: дерево доков
> УЖЕ является прото-графом, и его можно поселить в тот же субстрат, что и всё остальное.
> Это конкретное воплощение направления **D-META** из `01-agent-manager` («система, описывающая сама себя»).

## 1. Что делаем

Показываем, что каждый элемент нашего дерева доков — это **узел в базе** с тем же системным конвертом
(`id · type · state · edges · view · visibility · access · acts · policy_ref · body`), а не «файл на диске».
Папка-узел, файл-лист, контейнер-сборщик, служебная `_`-папка, реестр типов, INDEX/concept.json —
всё это типы узлов и рёбра между ними.

## 2. Зачем (боль)

- Дерево доков и база знаний живут как **две разные вселенные**: одна — файлы на диске, другая — граф
  для агента. Агент «видит файлы», но не видит **структуру как данные** (типы, дома, статусы, связи).
- Карты гниют, файлы сыплются в кучу — потому что дисциплина живёт в правилах-тексте, а не как
  **проверяемый граф** (лінт = запрос, а не отдельный скрипт мимо модели).
- Концепция plug-in (модульность) требует, чтобы структура была **данными**, которые можно подключать/
  переносить/描ать, а не жёстко зашитой иерархией папок.
- Прямая связь с рефреймом msg 141: «база = субстрат для агентов». Тогда и **устройство самой базы**
  (её папки/типы/дома) обязано лежать в базе как узлы — иначе часть мира невидима ИИ.

## 3. Возможности — что это разблокирует (черновой веер, растёт в дефектовке)

- **Дерево как данные.** Агент читает не «файлы», а типизированные узлы: `folder-node`, `file-node`,
  `container`, `service`, `type`, `view`, `status`, `edge`.
- **Авто-виды вместо рукописных карт.** INDEX/NAVIGATION/карты веток = `view`-узлы (сохранённые запросы
  над графом), а не второй дом истины. Прямо закон doc-tree №8 («предпочитай генерируемые авто-виды»).
- **Дисциплина = запросы.** «Суффикс не на своём месте», «loose-файлы», «needs-home», «дубль карты» —
  это `view`/`filter` над графом, а не отдельный линт мимо модели.
- **Размещение как политика-данные.** `homeRule` из `.doc-types.json` → `policy`-узел; агент спрашивает
  граф «где дом для узла типа X», а не угадывает (реестр project-registry — тот же приём для проектов).
- **Переезды без потерь.** Реорг/слияние дублей = переписывание рёбер (`superseded`, `redirect`),
  LOSE-NOTHING (закон №10) становится операцией над графом, а не `git mv`.
- **Plug-in / модульность.** Поддерево (`docs/`, репозиторий agents-manager, проект) = под-граф, который
  подключается/переносится целиком.

## 4. Требования (инварианты — нельзя нарушать)

1. **Переиспользуем общий конверт** из `examples/_schema/` — не изобретаем новый (закон _schema).
2. **Конструктор, не массив.** Папка ≠ строка-путь. Узел несёт `id · type · state · edges · view · acts`.
3. **Один дом на узел.** Ровно один постоянный дом; связи — рёбрами, объявлены **парами** (прямой/обратный).
4. **Два навигатора.** `INDEX.md` (человек) + `concept.json` (машина) — как в `01-agent-manager`.
5. **Не мешать два вещества** (закон №1): *trace* (`_log/`, след) и *knowledge* (дерево) — разные узлы,
   trace только ссылается.
6. **Урок из `01-agent-manager` (не наступить):** НЕ расти вширь до одного честного killer-кейса.
   Там модель «разошлась сама с собой» (B1: 13 JSON так и не завёрнуты в конверт; B3: `view` в 6 формах),
   потому что накидали много единиц, но ни одну не прогнали на реальных данных. Здесь — сначала ОДНО
   реальное поддерево в конвертах + реальный `view`, потом ширина.

## 5. Первый набросок единиц (node_type) — растёт в `../02-defectovka/`

> Каждая — **конструктор**. Ниже одна фраза; переменные/форма — позже, по подпапке на тип.

| # | Единица (node_type) | Что это, коротко | Прообраз в doc-tree |
|---|---------------------|------------------|---------------------|
| F1 | **folder-node** | Нумерованный узел-ствол (`NN-`/дата). Потенциал роста, может делиться. | архетип 1 |
| F2 | **container** | Плюрал-сборщик однотипного (`ideas/ questions/ decisions/`). БЕЗ номера. | архетип 2 |
| F3 | **service** | Служебная `_`-папка (виды, сквозное, черновое, `_archived/`). | архетип 3 |
| F4 | **file-node** | Финальный неделимый лист с суффиксом `.{type}.md` (`body`). | файл-стандарт |
| F5 | **type** | Запись реестра `.doc-types.json`: тип → дом (`homeRule`). Сам — meta:-узел. | реестр типов |
| F6 | **view** | Навигатор/карта/INDEX как сохранённый запрос-проекция, не копия данных. | закон №8 |
| F7 | **status** | Жизненный статус во frontmatter (`draft…archived…superseded`) = `state`. | закон №9 |
| F8 | **edge/link** | Связь по `id`/`related` (`refines · answers · supersedes · redirect`). | связи-по-id |
| F9 | **trace** | След в `_log/` (append-only, только указатели) — отдельное вещество. | закон №1 |

## 6. Связи (первый черновик рёбер — сводится в дефектовке)

```
folder-node(F1) ──contains──> {folder-node(F1), container(F2), service(F3), file-node(F4)}
container(F2)   ──collects──> file-node(F4)               (однотипные дети)
file-node(F4)   ──typed-as──> type(F5) ──home-ruled-by──> policy(homeRule)
file-node(F4)   ──has-state──> status(F7)                 (frontmatter → state)
file-node(F4)   ──links-to──> file-node(F4)               (edge F8: refines/answers/supersedes)
view(F6)        ──projects──> {folder-node, file-node}    (INDEX/карта = запрос, не дом истины)
service(F3)     ──hosts──> view(F6)                        (_generated/, навигаторы)
trace(F9)       ──points-to──> {file-node, folder-node}   (след ССЫЛАЕТСЯ, не хранит)
type(F5)        ──describes──> type(F5)                    (meta: самоописание — D-META fixpoint)
```

> Каждое ребро при заведении объявляется **парой** (прямой/обратный) и поднимается сюда — иначе карта «лжёт»
> (урок реконсиляции из `01-agent-manager` §4). Словарь предикатов — общий, из `../../_schema/`.
