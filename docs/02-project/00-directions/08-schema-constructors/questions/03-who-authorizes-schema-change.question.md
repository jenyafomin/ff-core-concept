# Вопрос в · Кто авторизует изменение схемы

> ⚗️ Открытый вопрос концепт-эксплорации. Честно: enforcement согласия в движке пока НЕ подключён (только форма).

## Формулировка
Loop-агент, меняющий схему сам, — это **власть над фундаментом**. Кто/что даёт ему право? Изменение схемы
может затронуть данные под чужим согласием (Ц7) и опереться на непроверенную «ячейку-правило» (Ц3). Нужен
явный **шов авторизации**: кто подписывает изменение, на каком доверии, с чьего согласия.

## Почему это несущий вопрос
Без шва авторизации «постоянно улучшающий» агент = агент с бесконтрольной властью над правдой пользователя.
Это стык двух ценностей: **Ц3 Доверие** (провенанс и калибруемое доверие предложения) и **Ц7 Согласие**
(данные под одним согласием не утекают в другое использование при перекройке схемы).

## Грани для разбора
- **Уровни авторизации по обратимости:** обратимое обогащение → низкое трение (критик + автозапись версии);
  необратимое/затрагивающее согласие → явное «да» владельца (человек-в-контуре, «клапан доверия»).
- **Провенанс предложения (Ц3):** кто предложил (какой агент/модель), на каком основании, с какой уверенностью;
  защита от отравления схемы через подсунутое правило.
- **Consent-шов (Ц7):** если изменение схемы меняет use/read согласие данных — оно проходит consent-проверку.
  ⚠️ Честно: в движке это сейчас ФОРМА, не enforcement — разрыв надо назвать, не спрятать.
- **Разделение властей:** loop-агент ПРЕДЛАГАЕТ, критик ОСПАРИВАЕТ, движок ОХРАНЯЕТ инвариант, владелец
  ПОДПИСЫВАЕТ необратимое. Ни одна роль не совмещает предложение и подпись.

## Гипотеза для оспаривания (не ответ)
Loop-агент не имеет права финальной записи в схему НИКОГДА: он открывает «pull-request», критик визирует
обратимое, владелец подписывает необратимое и затрагивающее согласие. Авторитет ≠ атрибуция (ср. ADR-0010):
кто предложил — не тот, кто разрешил.
