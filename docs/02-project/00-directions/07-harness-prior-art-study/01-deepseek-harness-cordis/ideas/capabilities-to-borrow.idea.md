# Идеи: что заимствовать из DeepSeek Harness (Движ / FF-память)

Контекст: FF = память-субстрат + plug-in архитектура (D1/D2), 7 ценностей —
`docs/02-project/core/01-brain/01-overview/01-values/_CARDS-2026-07-08.md`. Ниже — что из
возможностей/кастомизации DeepSeek Harness закрывает наши текущие висяки, и что у нас концептуально
сильнее (не заимствовать, беречь как отличие). Источник фактов — `facts/capabilities-facts.md`.

## Идея 1 — Auto-capture прогонов как «capability seam», не отдельная фича

**Наш висяк:** run-logger/авто-захват прогонов агентов (упоминается в MEMORY как регулярно нужное, но не
формализованное).

**Что взять:** `session-telemetry` (`packages/session/session-telemetry/README.md`) — Service Definition,
которая отделяет ТРИ независимые вещи: (а) точки захвата (`session/created`, `session/event`,
`session/flush`, `session/disposed`, `agent/error` — фиксированный, документированный набор триггеров),
(б) redact-waterfall (`sessionTelemetry/record`) — расширяемая цепочка очистки данных ПЕРЕД экспортом,
канонический лог никогда не переписывается, и (в) сам backend (реализует `emit()`/`flush()`/`shutdown()`,
неблокирующий). Ключевое дизайн-решение: пакет «stops after it calls `emit()`» — батчинг/ретраи/queue не
его забота, это ответственность backend SDK.

**Почему подходит нам:** у нас уже есть различение `trace` (append-only, `docs/_log/`) vs `knowledge`
(дерево) — `.claude/rules/doc-tree.md` закон 1. Их «canonical session log никогда не переписывается,
экспортируемая копия — только через redact-waterfall» — это ТОЧНО наш же принцип «trace ссылается, не
хранит», применённый к телеметрии агент-прогонов. Можно взять форму: (1) фиксированный список точек
захвата на нашем событийном слое (day-mirror/domain_event — `6c33395`), (2) отдельный redact-шов между
захватом и любым внешним использованием (для V7 Согласие — критично, у нас согласие ЕЩЁ не enforced в
движке, по MEMORY «isolation-model-and-seam-freeze»), (3) backend как plug-in — сначала можно вообще без
backend (события просто накапливаются), потом подключить любой.

**Агент для реализации:** `system-architect` (спроектировать capture-точки на нашем графе) →
`builder` (реализация).

## Идея 2 — Approval-queue как переиспользуемый seam с ПРЕСЕТАМИ, а не самописный флаг

**Наш висяк:** approval-queue (человек одобряет действия агента) — по CLAUDE.md/rules у нас пока «клапан
только на внешние необратимые действия», формализованного механизма нет.

**Что взять:** `dsh-permission-presets` (`packages/interaction/permission-presets/README.md`) — паттерн:
approval — не булев тумблер, а ИМЕНОВАННЫЙ ПРЕСЕТ, который бандлит несколько «knobs» разом (у них:
`sandbox/mode` + `approval/policy`; у нас могло бы быть: `read_consent`/`use_consent`/`hard_erase`-
доступность + уровень автономии агента). Их дефолты: `workspace-write` (спрашивать) и
`danger-full-access` (никогда не спрашивать) — т.е. ДВА именованных полюса, а не градиент настроек.
Второй паттерн: выбор пресета фиксируется В МОМЕНТ СОЗДАНИЯ сессии («creation pins... into that session,
so later changes never alter an existing session») — смена дефолта не задним числом не трогает уже
идущие процессы. Это прямая защита от «правила поменялись под ногами у уже одобренного прогона».

**Почему подходит нам:** approval у нас должен быть завязан на V7 Согласие (`use_consent`≠`read_consent`)
и V3 Доверие (какому агенту доверяем что без вопроса). Их принцип «выбор фиксируется на старте эпизода
работы, не глобально и не задним числом» — хорошая защита будущего approval-queue от типичной дыры
«владелец расслабил правило, а старый прогон по инерции унаследовал новое разрешение».

**Ограничение, которое стоит знать заранее** (их «Known Limitations»): «preset table is process-level —
changing available presets requires reloading the plugin» — у них это статично на процесс. Для нас (где
дом = граф, не процесс) стоит сразу спроектировать пресеты как ДАННЫЕ в графе (не в коде), чтобы не
унаследовать это ограничение.

**Агент для реализации:** `analyst` (декомпозировать, какие «knobs» реально нужны approval-пресету у
нас, по V7/V3) → `system-architect`.

## Идея 3 — Topic-awareness лишь ЧАСТИЧНО закрывается их «agent-presets»; routing остаётся нашей задачей

**Наш висяк:** topic-awareness (шлюз знает, в какой теме/каком топике идёт разговор, разная композиция
на разный контекст) — уже частично решено у нас (`.gateway/conversations/<chatId>/<threadId>/PROMPT.md`
+ `config.json` с `cwd`).

**Что НЕ стоит заимствовать буквально:** их `agent-presets` решает СМЕЖНУЮ, но другую задачу — какая
композиция ИНСТРУМЕНТОВ/ПРОМПТА у ОДНОЙ сессии (Standard/Code/Minimal/Creator), а не роутинг «какой топик
Telegram → какой проект». У них нет аналога нашего per-topic `cwd`-биндинга.

**Что взять частично:** сам механизм — «сессия присоединяется к стоящей композиции через scope-цепочку,
переключение возможно только пока сессия ничего не произвела» (`recompose()`, blank-only lock,
`packages/preset/agent-presets/README.md`) — это применимо к НАШЕЙ проблеме «владелец меняет `/bind` или
`/prompt` посреди уже идущего разговора»: сейчас непонятно, к какому моменту привязывается смена. Их
инвариант («смена состава — только у сессии без истории вызовов») можно позаимствовать КАК ПРАВИЛО для
`/bind`/`/prompt`: смена вступает в силу со следующего НОВОГО хода шлюза (что у нас уже отчасти так — «правка
применяется со следующего сообщения» в CLAUDE.md), но явно зафиксировать это как инвариант, а не побочный
эффект реализации.

**Агент для реализации:** не приоритет отдельной сессии — фиксировать как уточнение существующего
поведения `.gateway/` при следующей ревизии шлюза.

## Что у нас концептуально СИЛЬНЕЕ (не заимствовать — беречь как отличие)

1. **V3 Доверие / V7 Согласие — заложены как ценности данных, у DeepSeek Harness — их аналога нет.** Их
   `sandbox` — про файловые эффекты ВЫПОЛНЕНИЯ КОДА (`read-only`/`workspace-write`/`danger-full-access`),
   не про provenance/confidence данных о людях, и НЕ про право на забвение (`hard_erase`). Их
   `session-telemetry` redact-waterfall — ближе всего, но это защита ЭКСПОРТА, не встроенная модель
   consent на уровне единицы памяти. У нас V3/V7 — часть модели данных с 1-й итерации (пусть даже
   enforcement пока не подключён — честно зафиксировано в MEMORY: «isolation-model-and-seam-freeze»).

2. **V4 Витальность (остывание памяти) — у них нет аналога.** Их `session` — append-only лог без
   концепции «остывания», консолидации, `cold`-статуса. У нас это заложенная ценность (в разработке).

3. **V5 Суверенность у нас — про переносимость ДАННЫХ между движками, у них — про переносимость
   ПЛАГИНА/КОДА между процессами.** Их `bundle` — self-contained патчируемая единица КОМПОЗИЦИИ
   («whatever it inserts stays patchable by the layers above it»), не единица ПАМЯТИ со своей policy.
   Похожая ФОРМА (самодостаточная переносимая единица), но другой ПРЕДМЕТ переноса — этот разрез стоит
   держать явным при разговоре про D2 (plug-in), чтобы не спутать «плагин Движа» с «единицей памяти FF».

## Вопрос владельцу (не решать здесь, только зафиксировать развилку)

Стоит ли для будущего approval-queue Движа взять их «фиксация выбора на старте эпизода, не задним числом»
как жёсткий инвариант, или у нас достаточно softer-версии (владелец меняет право прямо сейчас, старый
прогон предупреждается постфактум)? Разница цены: их вариант надёжнее, но требует поля «под каким
approval-контекстом стартовал этот прогон» в каждой единице — доп. поле в модели данных.
