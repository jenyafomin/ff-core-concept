# Анализ: возможности, кастомизация и переиспользование DeepSeek Harness

Линза A2 (скаут-волна изучения prior art). Разбор строго по фактам из `facts/capabilities-facts.md`
(со ссылками на repo file:line/README-якоря). Не код, только чтение клона
`git clone --depth 1 https://github.com/deepseek-ai/deepseek-harness`.

## 0. Стадийная рамка

DeepSeek Harness — **developer preview**, версия `0.1.1-rc.2`, с прямым заявлением «THERE WILL BE
COMPATIBILITY-BREAKING CHANGES» (README.md) и явно нестабильным форматом хранения
(`SESSION_FORMAT_VERSION = 0`, `AGENTS.md`). Это значит: всё нижеописанное — это **дизайн-паттерны для
заимствования идей**, НЕ готовая интеграционная поверхность (API/схемы могут смениться завтра). Читать как
«как решить задачу X», а не «на что опереться версией».

## 1. Четыре режима = не хардкод, а ОДИН универсальный механизм композиции

Ключевая находка: «Standard/Code/Minimal/Creator» — это не четыре разных кодовых пути, а **четыре
экземпляра одного и того же механизма** — `AgentPresets` (`packages/preset/agent-presets/`). Пресет = папка
с одним `agent.cordis.yml` (список плагин-строк) + опциональный `preset.yml` (display-метаданные). Все
четыре монтируются идентичным путём:

- `standard` (order 1) — полный набор: fs, shell, web, skills, plan, goals, subagents, workflow.
- `code` (order 2, «PTC 模式») = `standard` + ОДНА добавленная строка `tool-presentation`, которая меняет
  ПРЕДСТАВЛЕНИЕ существующего реестра инструментов моделью (пошаговые вызовы → один TypeScript-скрипт
  через `run_code`). Реестр инструментов не дублируется — это слой презентации поверх него.
- `minimal` (order 3) — обратный полюс: персона = ПОЛНЫЙ системный промпт (`complete: true`, `persona`
  config), убраны все секции промпта кроме двух инструментов (persistent bash + str_replace_editor),
  компакция контекста выключена. Это специально узкий, дешёвый по токенам режим.
- `cordis` (order 4, «创造模式»/Creator) = `standard` + тулсет `dsh-tool-cordis` (`cordis_mount` и др.),
  который даёт агенту читать/писать СВОЮ ЖЕ композицию плагинов (self-modification). Персона прямо
  инструктирует агента о двух планах (host vs preset) и запрещает трогать `standard`, только копировать.

**Важное признанное ограничение** (не спрятано, названо в «Known Limitations»): `cordis` и `code` —
ПОЛНЫЕ копии `standard`, не наследование/дельта. Причина: на уровне preset нет патч-семантики «standard
плюс одно изменение» — та существует только уровнем выше, на bundle-патчах (`cordis.patch.yml`).
Т.е. кастомизация внутри пресетов = полное дублирование композиции, а не diff. Для 4 пресетов это терпимо
(«assembly stays readable in one file»), но не масштабируется на N пресетов без дублирования обслуживания.

**Механизм переиспользования тот же самый, что даёт владельцу возможность создавать СВОИ режимы**:
`copy()` — единственный способ авторства, копирует всю директорию пресета в
`$DSH_HOME/.agent-presets/<id>/`, дальше редактируется как обычный YAML-файл. `remove()` защищает
поставляемые пресеты. Переключение пресета внутри УЖЕ идущей сессии заблокировано, если сессия что-то уже
произвела («produced-nothing» lock) — предотвращает «осиротевшие» вызовы инструментов, для которых новая
композиция не поддерживает схему. Это ХОРОШО спроектированный инвариант: переключение состава возможностей
= смена контракта модели, и harness относится к этому как к необратимому после первого шага решению.

## 2. Провайдеры моделей — не «поддержка 6 вендоров», а универсальный шов + каталог одного SDK

Разбор снимает путаницу из брифа («провайдеры DeepSeek/Anthropic/OpenAI/Bedrock/Vertex/Azure/OpenAI-
compatible») — это НЕ шесть встроенных адаптеров харнесса. Фактическая структура двухслойная:

1. **Шов `ctx.llm`** — Service Definition, харнесс-agnostic к вендору (`packages/llm/README.md`).
2. **Два ПРОДУКТОВЫХ адаптера-Provider'а на этот шов**: `llm-deepseek` (прямой DeepSeek) и `llm-pi-ai`
   (обёртка вокруг СТОРОННЕЙ библиотеки `@earendil-works/pi-ai`, которая и несёт мультипровайдерный
   каталог).

Внутри `llm-pi-ai` провайдеры делятся на два класса по механизму подключения:
- **Каталожные** (то, что уже знает `pi-ai`: openai, anthropic, deepseek, а также Bedrock/Vertex/Azure/
  Codex) — работают «из коробки» через нативную аутентификацию каждого (SigV4, ADC, api-version,
  OAuth), но explicit override (смена `baseURL`/`api`) для Bedrock/Vertex/Azure/Codex ОТКАЗАН намеренно
  («offering those would hand back a route that cannot authenticate»).
- **Hand-declared** (произвольные OpenAI-совместимые шлюзы/self-hosted сервера) — полностью описываются
  вручную (`api`, `baseURL`, `models[]`, `compat`), это и есть путь для «любого OpenAI-compatible».

Значит связка «6 провайдеров» правдива ТОЛЬКО в смысле «pi-ai это умеет», и харнесс это ПРОЗРАЧНО
прокидывает как конфигурацию, а не пишет 6 адаптеров сам. Дизайн-урок для нас: не переизобретать
мультипровайдерный слой — взять готовую библиотеку и написать ОДИН тонкий адаптер сверху, который
экспонирует её каталог + позволяет «hand-declared» escape hatch. Кастомизация без рестарта (thunk
«once per operation», не freeze при construction) — тоже важный паттерн: смена ключа/route/proxy
подхватывается со следующего запроса, без даунтайма процесса.

## 3. Инструменты — генерируемый (не ручной) каталог, схема = функция рантайма

`docs/tool-catalog.md` — не написанный руками маркдаун, а **артефакт**, который бутстрапит каждый
tool-плагин на реальном контексте и читает `ctx.tools.schemas()`, потому что схема не статична
(runtime-spread enums, config-driven имена, сырой JSON-Schema из MCP). Это устраняет класс багов «доки
разошлись с кодом» механически (CI гейт `verify-tool-catalog`). Для нашего FF (где `doc-tree.md` уже
требует «навигатор=вид, не второй дом истины») это прямое структурное решение той же проблемы: делать
каталог ГЕНЕРИРУЕМЫМ, а не поддерживаемым руками, там где источник истины — код/конфиг.

~30 инструментных пакетов сгруппированы по capability seam (shell/fs/web/lsp/skill/subagent/workflow/
session-query/goal/schedule/jobs...), каждый — Service Definition + Provider + Consumer. Заметный паттерн:
**имя модель-видимого инструмента — конфигурируемо на загрузке** (`toolName` config), т.е. один и тот же
пакет может быть смонтирован дважды под разными именами для разных бэкендов (пример: `subagent` vs
`subagent_fork` — тот же пакет, разный backend/toolName).

**Опциональность как первоклассный дизайн, не заплатка**: `dsh-tool-cordis` (self-modification) и
`dsh-experimental-tool-agent-team` (командная работа, 10 инструментов) прямо помечены «not in any shipped
tree» / «kept disabled» — мощные, но опасные/незрелые возможности не удалены и не спрятаны в коде, а
просто НЕ включены в стандартную композицию. Это ровно паттерн, который нам нужен для `dsh-tool-cordis`-
аналога в Движ (если когда-то дадим агенту право чинить свою же оркестрацию) — включаемость через
композицию, а не через отдельную ветку кода.

## 4. MCP-клиент = осознанный тонкий мост, не встроенная экосистема

`packages/mcp/mcp-client/` явно ограничивает свою ответственность (`examples/mcp-memory/README.md`):
парсит overlay, поднимает stdio/HTTP, дискаверит тулы, экспонирует как `mcp__<server>__<tool>` — и НЕ
устанавливает сервер, не создаёт облачный аккаунт, не мигрирует данные вендора. Примеры интеграции
(Memorix/MCP Reference Memory/Engram) поставляются как default-off overlay-патчи, каждый со своим
«tested pin» (закреплённая версия), а НЕ как автоматическая загрузка «последней версии чего попало» — это
явная защита от supply-chain дрейфа. Также stdio-бридж ЯВНО стрипает переменные окружения, похожие на
секреты, и все `DSH_*` перед запуском дочернего процесса — осознанная граница доверия к третьей стороне.

## 5. Песочницы — файловая только, платформо-специфичная, честно названные пределы

`ctx.sandbox` — контракт `confine(argv, policy)`, вокабуляр (`read-only`/`workspace-write`/
`danger-full-access`) — **исключительно файловые эффекты**. Явно документировано отсутствие сетевой/
процессной/syscall-политики как «Known Limitations», не как скрытый дефект. Backends: `bwrap`/Landlock на
Linux, `sandbox-exec`/Seatbelt на macOS, ACL-runner на Windows — «same-world confinement», т.е. общий
kernel/файловая система с хостом (в отличие от контейнеров/microVM, которые тут — замена ЦЕЛЫХ capability
seams, не провайдер этого шва). Fail-closed по умолчанию — если backend недоступен, харнесс ОТКАЗЫВАЕТ
запуск (не деградирует молча в unconfined). E2B (remote/cloud sandbox) прямо маркирован POC: «not a
whole-harness runtime», эфемерное состояние, «No deployment platform is configured».

Landlock-launcher — отдельный, крошечный (~300 строк C11, статик-линк musl), издаваемый как npm
native-addon с platform-специфичными пакетами (`os`/`cpu` поля npm сами фильтруют установку) — хороший
образец «маленький острый инструмент, публикуемый отдельно от монолита».

## 6. UI как плагин — типобезопасная слот-система, а не «просто React app»

`packages/client/` — 45 пакетов. `ui-slots` — ЧИСТОЕ ядро (React-free, cordis-free) слот-реестра:
регистрация компонента ОДНОВРЕМЕННО декларирует дочерние слоты, store-seat и «business face» — три
источника типов пересекаются в один `ComposedProps`, проверяемый статически TypeScript'ом на месте
регистрации. Это НЕ рантайм-plugin-система с произвольным рендером (как большинство «drop a widget here»
UI-плагинных систем) — расширяемость типобезопасна на этапе компиляции.

`ui-settings-plugin-inventory` даёт вкладку «инвентарь Host Loader» (что реально смонтировано) — но это
ЧТЕНИЕ, не установка. `ui-settings-plugins` конфигурирует УЖЕ смонтированные host-plane плагины из UI.
Установка НОВОГО плагина/бандла остаётся CLI-операцией (`dsh plugin --profile <name> add <package>`) —
т.е. «UI как плагин» верно для КОМПОЗИЦИИ интерфейса, но НЕ распространяется на «установи новый плагин
через UI-клик» (в отличие от классического app-маркетплейса).

## 7. Реестр/маркетплейс плагинов — НЕ существует как отдельная сущность харнесса

Прямая проверка (grep по docs/README на `marketplace`/`plugin registry`/`plugin store`) — ноль совпадений
кроме UI-инвентаря (п.6). Официальный механизм обнаружения — децентрализованный: GitHub-топик
`dsh-plugin` + Discord-комьюнити (`README.md`). Технически бандл = обычный npm-пакет с полем `dsh.bundle`
в `package.json` — значит вся инфраструктура распространения = npm registry, харнесс не строит свой.
Это принципиальная развилка дизайна: «маркетплейс» = метаданные (топик на GitHub) + существующая npm-
инфраструктура, а не отдельный продукт внутри харнесса. Дешевле в разработке, но требует, чтобы
пользователь САМ искал/оценивал качество — нет курируемого/проверенного канала.

## 8. Что именно переиспользуемо — сводный ответ

Единица переиспользования на каждом уровне:
- **Плагин** (Cordis Service) — атом; contribution через `ctx.effect()`/`ctx.on()`, реверсируемый.
- **Capability seam** (Definition+Provider+Consumer) — переиспользуемый КОНТРАКТ (например `ctx.llm`,
  `ctx.sandbox`, `ctx.skills`) — новый провайдер подключается без изменения консьюмеров.
- **Bundle** (npm-пакет + `cordis.patch.yml`) — переиспользуемая ЕДИНИЦА ДИСТРИБУЦИИ, патчибельна дальше
  вышестоящими слоями («whatever it inserts stays patchable by the layers above it»).
- **Preset** (директория с `agent.cordis.yml`) — переиспользуемая ЕДИНИЦА РЕЖИМА АГЕНТА, копируемая
  (не наследуемая) владельцем.
- **Profile** (`$DSH_HOME/profiles/<name>`) — переиспользуемая ЕДИНИЦА РАЗВЁРТЫВАНИЯ (композиция
  bundles + личные патчи владельца).

Все пять — вариации ОДНОГО механизма (Cordis-композиция + YAML-патчи), не пять разных подсистем. Это,
пожалуй, главный структурный вывод для нас: единый примитив композиции, применённый рекурсивно на разных
масштабах (инструмент → режим агента → развёртывание), вместо отдельного механизма кастомизации на
каждом уровне.

## 9. Границы и риски (для трезвой оценки заимствований)

- Developer preview, breaking changes заявлены прямо — НЕ копировать API 1:1, только паттерны.
- Формат сессий (`SESSION_FORMAT_VERSION=0`) без гарантий совместимости — если бы мы когда-то
  интегрировались напрямую с их session log, это ломкая опора.
- Sandbox-шов не покрывает сеть/процессы/syscalls — при заимствовании идеи «policy rides the call, not
  the provider» помнить, что периметр защиты уже сейчас признанно неполный у самого DeepSeek.
- E2B — POC без persistence/templates/сети — не готовая интеграция для «облачная песочница».
- Presets без наследования (только полное копирование) — если взять идею «режимов» к нам, стоит сразу
  спроектировать ДЕЛЬТА-семантику (patch поверх базового режима), а не повторять их «полная копия»
  ограничение, которое они сами назвали известным долгом.
- MCP-клиент — тонкий мост с осознанными несделанными вещами (нет установки сервера/аккаунта) — если
  берём MCP к себе, взять тот же принцип "мост, не платформа".

## Связки с FF (по брифу)

FF = память-субстрат + plug-in архитектура (D1/D2, `docs/product/VISION.md`); 7 ценностей действуют как
линза. Ниже — прямое сопоставление (детали заимствований → `ideas/capabilities-to-borrow.idea.md`):

- **Наши текущие висяки** (run-logger/авто-захват прогонов, approval-queue, topic-awareness) частично
  закрываются готовыми capability seams харнесса: `ctx.sessions`+`ctx.sessionQuery`+`session-telemetry`
  (append-only session log с read-моделью поверх — прямой аналог «авто-захвата прогонов»);
  `ctx.interaction`/`permission-presets` (approval-queue как первоклассный шов, не отдельная фича);
  `agent-presets` косвенно решает часть topic-awareness (разная композиция на разный контекст), но НЕ per-
  topic routing самого шлюза — это остаётся нашей задачей.
- **Что у нас концептуально сильнее** (по прочитанному): у DeepSeek Harness НЕТ явного слоя «доверие/
  provenance к данным» (V3) и НЕТ согласия/consent-шва (V7) — их sandbox — про файловые эффекты
  выполнения кода, не про данные о людях; у нас V3/V7 — заложенные с нуля ценности графа. У них также нет
  явной модели «остывания»/vitality (V4) для данных (сессии — append-only лог, а не память с затуханием).
  Их сила — V1 Читаемость на уровне ИНСТРУМЕНТОВ/композиции (генерируемые каталоги, типобезопасные слоты)
  и V5 Суверенность на уровне ПЛАГИНА (bundle как self-contained патчируемая единица) — это ближе всего к
  нашему D2 (plug-in), но заточено на код/композицию рантайма, не на переносимость ДАННЫХ между движками
  (наша V5 — про портируемость ЕДИНИЦЫ памяти со своей policy, не про портируемость плагина).
