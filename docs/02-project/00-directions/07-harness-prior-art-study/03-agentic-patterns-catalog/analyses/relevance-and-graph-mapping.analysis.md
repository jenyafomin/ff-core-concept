# Отбор релевантных паттернов + маппинг «паттерн → узел графа»

> Advisory. Внешний каталог не ратифицирован. Это ЧЕРНОВОЙ разбор скаута C для синтеза лида (co-orchestrator
> приёмка). Задача: (1) отобрать паттерны, которые РЕАЛЬНО ложатся на нашу память-субстрат (D1: «память
> помнит себя», agent-run как граф agent/task/finding/verdict; дневник узлов diagram — goal · principle ·
> open-question · answer · insight · problem · decision); (2) для каждого показать форму узла;
> (3) отдельно — с чем мы УЖЕ пересекаемся (не открытие, а подтверждение метода).

## Как читать таблицу узла

Для каждого паттерна: **id-паттерн** (как он бы вошёл в наш граф, если решим завести типизацию
`pattern`) · **какой НАШ тип узла/сущности он лучше всего населяет** (dialogue-graph тип ИЛИ agent-run тип
ИЛИ новый предлагаемый тип) · **связи** (какие рёбра он тянет: `refines/grounds/tension-with/…`) · **когда
применять** (триггер в нашей практике). Источник — `agentpatternscatalog/patterns` (URL в файле каждого
паттерна, см. `catalog/patterns-catalog.md`).

## Блок 1 — Memory (прямое попадание в D1 «память помнит себя»)

### 1. Episodic Memory / Semantic Memory / Procedural Memory (three-way split)
- **Узел:** три РАЗНЫХ типа памяти — у нас пока ОДИН недифференцированный узел «сессия/находка». Паттерн
  предлагает различать: episodic (что произошло, привязано к времени) vs semantic (что мы теперь считаем
  истиной) vs procedural (как делать — наши скиллы/agents/rules УЖЕ это, неявно).
- **Связи:** episodic `grounds` semantic (эпизод порождает вывод-факт); semantic `supersedes` semantic
  (новый факт заменяет старый — у нас это `status: superseded`).
- **Когда применять:** прямо сейчас в agent-run→память (упомянуто в MEMORY.md «розжиг графа дня-1» F3) —
  РЕШИТЬ явно, эпизод (agent-run trace) и факт-вывод (insight/decision) это ДВА разных узла, не один.
  Наш `docs/_log/` (trace) уже играет роль episodic по факту, но НЕ типизирован как таковой.

### 2. Adaptive Memory Decay / Hippocampal Rehearsal
- **Узел:** свойство существующего узла (`retention_score`, decay function) + операция «rehearsal»
  (поднять archived-узел обратно в активный слой при повторном обращении).
- **Связи:** узел `refines` сам себя во времени (decay), rehearsal создаёт ребро `reactivated-by`.
- **Когда применять:** это ПРЯМОЕ попадание в нашу Ц4 Витальность («может затухать→cold, переосмысляться»,
  см. `.claude/rules/recursive-orchestration-method.md` банк вопросов). Паттерн даёт конкретный МЕХАНИЗМ
  (weighted retention score modulated by relevance/access-frequency/recency), а не только принцип. Наш
  канон уже НАЗВАЛ ценность, паттерн даёт КАК её посчитать.

### 3. Salience Attention Mechanism
- **Узел:** скоринговая функция над узлами памяти — не новый тип узла, а АЛГОРИТМ выбора top-k при чтении.
- **Связи:** нет новых рёбер, но меняет, КАКИЕ рёбра/узлы агент реально прочитает за один проход.
- **Когда применять:** прямое попадание в Ц1 Читаемость («нужную грань по нужной цене, не вскрываясь
  целиком») — салиенс-скоринг это конкретный механизм цены-грани, которого у нас пока нет (мы полагаемся
  на ручной выбор файлов/агента-скаута).

### 4. Knowledge Graph Memory / World-Model Graph Memory
- **Узел:** это, по сути, ОПИСАНИЕ нашей архитектуры (граф узлов = субстрат). Разница: паттерн различает
  «memory as retrieval index» (Knowledge Graph Memory) от «memory as authoritative planning substrate»
  (World-Model Graph Memory) — у нас это НЕ разделено явно, граф служит обеим ролям молча.
- **Связи:** нет новых, но подсвечивает, что наш граф носит ДВЕ роли одновременно (RAG-индекс + мир для
  планирования) — стоит спросить, не конфликтуют ли они (напр. эпизодический шум мешает planning-срезу).
- **Когда применять:** вопрос для F-D / архитектурного форка, не срочно.

### 5. Memory-Type Storage Specialization
- **Узел:** инфраструктурный, не граф-узел — «разные типы памяти хотят разное хранилище» (Redis для
  episodic, vector DB для semantic, реляционка для procedural). У нас единый md+frontmatter субстрат —
  это НАРОЧИТОЕ отличие (Ц5 Суверенность: портируемость важнее производительности специализации), не гэп.
- **Когда применять:** не применять сейчас — записать как СОЗНАТЕЛЬНОЕ расхождение с индустрией (наш выбор
  «один субстрат» ради переносимости, паттерн там, где производительность важнее).

## Блок 2 — Verification & Reflection (пересекается с законом 5 «адверсариал до готово»)

### 6. Blind Grader with Isolated Context
- **Узел:** `verdict`-узел, порождённый агентом БЕЗ доступа к reasoning-трейсу производителя — только
  артефакт + рубрика.
- **Связи:** `verdict` → `grades` → artifact-узел; explicit НЕ связан с producer's-task узлом (изоляция —
  это и есть суть).
- **Когда применять:** это ТОЧНОЕ описание того, что уже делает `co-orchestrator` (приёмка читает сырьё
  ВМЕСТО лида, не видя намерений исполнителя, кроме заявленной цели задачи) — **подтверждение, не гэп**.
  Стоит явно зафиксировать в контракте co-orchestrator: «не читай reasoning исполнителя, только
  вход/выход/рубрику» — сейчас это неявно.

### 7. Generator-Critic Separation
- **Узел:** роль-типизация двух агентов; критик НИКОГДА не генерирует.
- **Связи:** `critique` edge критика → артефакт, без обратного `generates`.
- **Когда применять:** совпадает с законом 5 нашего метода (критик = ДРУГОЙ агент). Наш `critic` агент уже
  разделён от builder/analyst по контракту — **подтверждение**.

### 8. Cross-Reflection
- **Узел:** явно требует, чтобы критик был на ДРУГОЙ модели/агенте, чем генератор («decorrelated error»).
- **Когда применять:** у нас `critic`-агент = sonnet, генераторы разные (analyst/builder/opus) — частично
  выполнено, но стоит спросить: разводим ли мы модель КРИТИКА от модели ИСПОЛНИТЕЛЯ систематически, или
  иногда критик = тот же класс модели (систематическая correlated-error слепая зона)?

### 9. Commitment Tracking
- **Узел НОВЫЙ, которого у нас НЕТ:** типизированный ledger «заявленное намерение» со статусом
  `open / followed-through / expired`, извлечённый из КАЖДОГО хода агента.
- **Связи:** `commitment` узел `raised-in` agent-run, `resolved-by` следующий agent-run или `expired`.
- **Когда применять:** ПРЯМОЙ ГЭП. У нас в хендоффах постоянно фигурируют «owner-pending» пункты (видно в
  MEMORY.md — I-4, R3/R4/R5, F-D, ратификация proposed-текстов) но они живут ТЕКСТОМ в хендоффе, не как
  структурированный ledger-узел с статусом. Commitment Tracking формализовал бы именно этот повторяющийся
  паттерн «висяков» — кандидат в `analyses/patterns-open-questions.md` §Гэпы.

### 10. Frozen Rubric Reflection
- **Узел:** критик ограничен ФИКСИРОВАННОЙ рубрикой (не изобретает критерии на лету).
- **Когда применять:** банк вопросов по 7 ценностям (`.claude/rules/recursive-orchestration-method.md`) —
  это УЖЕ frozen rubric для помощника (обязанность д). Явное совпадение — подтверждение, что метод уже
  инстанцирует этот паттерн для одной из ролей.

## Блок 3 — Multi-Agent (пересекается с законами 2-4 метода)

### 11. Orchestrator-Workers
- **Узел:** оркестратор ДИНАМИЧЕСКИ решает subtasks в рантайме (не заранее прошитый план).
- **Когда применять:** это наш ЛИД + команды. Совпадение почти буквальное — **подтверждение**.

### 12. Lead Researcher
- **Узел:** лид пишет research-план и рассылает ПАРАЛЛЕЛЬНЫХ саб-агентов на breadth-first сбор, потом
  сливает.
- **Когда применять:** это ТЕКУЩИЙ прогон (я — скаут C в волне из нескольких скаутов). Совпадение —
  подтверждение существующей практики (синхронные волны 3-6 агентов, закон 4).

### 13. Blackboard / Stigmergic Coordination
- **Узел:** агенты координируются ЧЕРЕЗ общее пространство (файлы), не прямыми сообщениями — след одного
  стимулирует следующего.
- **Связи:** это буквально описание doc-tree как координационного слоя между волнами агентов.
- **Когда применять:** УЖЕ практика (сессии пишут в файлы, следующая сессия/агент читает) — но паттерн
  предупреждает о риске «Hidden State Coupling» (антипаттерн, см. Блок 5) — если файл читается неявно, не
  через явную задачу-карту, это дрейф.

### 14. Board-Mediated Async Inter-Agent Coordination (nibzard)
- **Узел:** формализация Blackboard с явной доской-состоянием (не просто файлы, а СТРУКТУРИРОВАННАЯ доска
  со статусами задач).
- **Когда применять:** релевантно для будущего TaskCreate/TaskList слоя (если решим сильнее формализовать
  волны за пределы текущего ad-hoc «Agent() в одном сообщении»).

## Блок 4 — Cognition & Introspection (СИЛЬНОЕ пересечение с «узел = типизированный ledger»)

Эта категория (agentpatternscatalog, 24 паттерна) — самая близкая по ДУХУ к нашей модели узла. Многие
паттерны здесь буквально описывают «типизированный ledger с id/status/confidence», что и есть наш узел
диалога (`open-question · answer · insight · problem · decision`), но с деталями, которых у нас нет.

### 15. Hypothesis Tracking
- **Узел:** типизированный ledger «summary · confidence · status · next-test» — почти 1:1 наш `insight`
  узел, НО с явным полем `next-test` (что проверить, чтобы подтвердить/опровергнуть), которого у нас нет.
- **Когда применять:** гэп-кандидат — наши `insight`-узлы редко несут явный «как проверить» указатель.

### 16. Open-Question Tension Store
- **Узел:** практически буквально наш `open-question` тип, включая идею, что «неразрешённые вопросы
  ДВИГАЮТ следующий inquiry» — у нас это спонсирует протокол диалога-проектирования (L0-L5 воронка), но
  не формализовано как отдельный persistent ledger с полем «pull/tension score».
- **Когда применять:** подтверждение направления + идея добавить приоритетность (tension score) вместо
  плоского списка открытых вопросов.

### 17. World-Model Separation
- **Узел:** явно РАЗДЕЛЯТЬ файл «модель мира» (репо, люди, сервисы) от файла «модель себя» (agent
  self-model), чтобы рефлексия не путала два и не co-mutated их случайно.
- **Когда применять:** релевантно для будущего self-memory слоя (упомянут в MEMORY.md «agent-run→память»)
  — если агент начнёт писать заметки О СЕБЕ (self-identity accumulation, см. ниже), стоит держать это
  строго отдельно от узлов «о продукте/мире».

### 18. Self-Identity Accumulation (nibzard)
- **Узел:** агент накапливает устойчивую идентичность через сессии (не путать с V2 Тождество единицы
  данных — это про идентичность САМОГО агента/помощника).
- **Когда применять:** пограничный гэп — у нас `co-orchestrator` как роль без персистентной идентичности
  между сессиями (каждый спавн заново). Не факт, что нужно — флаг, не рекомендация.

### 19. Preoccupation Tracking
- **Узел:** «средне-срочные, affect-tagged заботы», которые переживают дни и всплывают в каждом промпте —
  отличается от single-item working focus и от long-term insight.
- **Когда применять:** близко к тому, что MEMORY.md уже делает вручную («⭐⭐⭐ START HERE» записи, PARKED
  пункты) — паттерн предлагает формализовать это как ТИП узла со своим decay/surfacing правилом, а не
  плоский markdown-список, который владелец каждый раз читает целиком.

## Блок 5 — Anti-Patterns как КРАСНЫЕ ФЛАГИ (использовать для критик-чек-листа)

Эти — не узлы, а ПРОВЕРКИ, которые должен прогонять критик/co-orchestrator ДО «готово» (закон 5).

- **Same-Model Self-Critique** — если критик = тот же класс модели, что генератор, ожидание независимости
  ложно. Прямая проверка для нашей волны агентов.
- **Perma-Beta / Eval Vacuum** — «фаза DESIGN» длится 2 месяца без реальных данных (см. MEMORY.md
  2026-08-16 «шлифуем замок на пустом хранилище») — это ИМЕННО симптом этого антипаттерна, названный
  паттерн-каталогом независимо. Совпадение подтверждает, что владельческий вердикт «анализ стал избеганием
  коммита» — это распознанный класс failure, не разовая проблема.
- **Prompt Bloat / Guardrail Erosion Through Compaction** — риск для растущего CLAUDE.md/rules (у нас уже
  10+ global rules + project rules + method-правило) — стоит периодически проверять, не деградирует ли
  сила инструкции через накопление.
- **Re-Proposing Rejected Decisions** — стейтлесс-агент видит код, но не историю решений, предлагает уже
  отклонённое заново. Прямая причина, зачем нужен `docs/` slim canon (не только `_log/`) — иначе каждый
  новый агент/скаут рискует переизобретать закрытые развилки.
- **Ghost Delegation** — делегированная подзадача молча теряется (родитель закрывается, саб-таск
  осиротевает). Релевантно для наших синхронных волн — закон 4 (`run_in_background:false`) СНИМАЕТ этот
  риск структурно (волна не завершается, пока все агенты не вернули результат), но стоит явно записать
  ПОЧЕМУ синхронность — не только экономика (gateway), но и анти-Ghost-Delegation.
- **Memo-As-Source Confusion** — агент цитирует СВОЙ прошлый memo/хендофф как истину вместо перепроверки
  артефакта. Прямая опасность для MEMORY.md-driven старта сессий (единственная защита — явно помечать
  хендофф как УКАЗАТЕЛЬ, не источник, что закон 6 уже требует: «хендофф-указатель, не дубль контента»).
- **Context Anxiety** — модель урезает работу, ошибочно считая, что кончается бюджет, хотя места много.
  Релевантно для лимитов-слов в задачах помощника («лимит слов · как проверю» в шаблоне мандата).
