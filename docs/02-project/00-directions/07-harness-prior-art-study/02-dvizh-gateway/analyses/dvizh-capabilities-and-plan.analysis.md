# Анализ — возможности Движа сейчас + план, по осям сравнения с DeepSeek Harness

Источник фактов: `../facts/dvizh-facts.md` (все утверждения ниже опираются на конкретные ADR/README/файлы
локального репо `agents-manager`). Этот документ — СИНТЕЗ по осям, не дублирует факты дословно.

## Как читать статус

- **есть/approved** — реализовано и подтверждено ADR/README/тестами.
- **draft/proposed** — спроектировано, код может частично существовать, но не ратифицировано владельцем.
- **DEFERRED/roadmap** — явно отложено (не путать с «забыто» — решение принято сознательно, зафиксировано).
- **нет** — не найдено ни в коде, ни в доках.

## Ось 1 — Расширяемость / плагин-архитектура

| Что | Движ | Статус |
|---|---|---|
| Структурная расширяемость (гексагональная архитектура, порты/адаптеры) | Да: `core/ports/` — 15 интерфейсов (`IChannel`, `IAgentRunner` через `ports`, `IApprovalGate`, `IPermissionPolicy`, `ISummarizer`, …); жёсткое правило зависимостей `channel → core ← server` | **есть** |
| Множественные реализации портов сегодня | Нет: 1 канал (`TelegramChannel`), 1 боевой раннер (`SdkRunner`, + fallback `PrintRunner`) | **нет** (архитектурно готово, фактически моно) |
| Пользовательская плагин-система (устанавливаемые сторонние модули, реестр, marketplace) | Явно НЕ строится: критик называет риск «plugin hell» без реестра типов, архитектор относит «plugin-реестр паттернов» к отложенным пунктам roadmap | **DEFERRED** (осознанно, «правило двух»: не строить generic-конструктор по одному прецеденту) |
| Динамические «паттерны как данные» (ADR-0009) | Задел на будущую расширяемость через данные (TypeUnit `system:pattern@1`), но БЕЗ generic-исполнителя — паттерн хэндоффа исполняет частный код, не движок | **draft**, слайс-1 = только доки, БД не тронута |

**Вывод оси 1:** Движ выбрал ту же общую стратегию, что архитектурно правильна для расширяемости
(hexagonal/ports), но **сознательно НЕ строит** plugin-marketplace слой — есть явный протокол «сначала
2 прецедента одного механизма, потом обобщение» (ADR-0009 «правило двух»). Если Harness (A) уже имеет
рабочую модель «всё — плагин» с установкой третьей стороной, это прямая ось ПОЗАДИ для Движа — но с
осознанной причиной (анти-plugin-hell), а не как упущение.

## Ось 2 — Раннер (SDK)

| Что | Движ | Статус |
|---|---|---|
| In-process SDK-раннер поверх `@anthropic-ai/claude-agent-sdk` | `SdkRunner implements IAgentRunner`, `query()` с типизированными событиями | **approved**, реализовано (ADR-0001) |
| Approval мид-ран (per-tool) | `canUseTool` → `SdkToolGate` → `ToolApprovalGate`: 3 кнопки в Telegram (Раз/Всегда/Отклонить) на КАЖДЫЙ мутирующий тул-колл | **approved**, реализовано |
| Постоянные разрешения («Всегда») без своего хранилища | SDK-нативный `updatedPermissions` → `localSettings` | **approved** |
| Реальный токен-стрим в чат (не финал одним чанком) | `stream()` сейчас = финал одним чанком (MVP-упрощение) | **нет** — открытый пункт ADR-0001 |
| e2e-валидация из живого Telegram (не тестов) | Помечена pending на дату ADR (approved-статус ADR не значит e2e подтверждена) | **не верифицировано** в этом разведпроходе |
| Fallback раннер (без SDK) | `PrintRunner` (CLI one-shot `claude -p --resume`) остаётся за флагом `GATEWAY_RUNNER_MODE=print` | **есть**, как страховка |

**Вывод оси 2:** Раннер — самая зрелая и лучше всего документированная часть системы: явная эволюция
(CLI one-shot → in-process SDK) с зафиксированными причинами (one-shot-смерть, approval мид-ран, фейковый
стрим) и планом валидации. Это прямая точка сравнения с Harness — если Harness тоже строит поверх SDK/API
с approval-петлёй, здесь сопоставимо; отсутствие реального токен-стрима — конкретный минус, если у Harness
он есть.

## Ось 3 — Топики / сессии (scope=topic)

| Что | Движ | Статус |
|---|---|---|
| Сессия = единица на топик Telegram-форума | `conversationId = chat:thread`, сквозной от ingress до egress; `GATEWAY_BOT_SCOPE=topic` (дефолт) или `user` | **approved**, реализовано и проверено на живых логах |
| Reply-awareness (агент видит цитату) | `replyToText`/`inReplyToText`, фолбэк на сниппет, если сообщение не в истории сессии | **approved** (ADR-0002-топики) |
| Топик знает о своём названии/регистрации | `ITopic`/`ITopicRepo.findByThreadId`, без молчаливой авто-регистрации (осознанное решение D2) | **approved** |
| Кросс-топиковый обзор для агента-координатора (Layer-2 awareness: топик↔state↔handoff-лог) | `ITopicAwarenessRef` спроектирован (JSON-колонка, без миграций на новое измерение), но порт `IAwarenessProjector.forBot` — **DEFERRED** | **proposed**, не реализовано |
| Устойчивость topic-контекста к рестарту посреди хода | `originThreadRef` в `job-row` — companion-фикс, тоже **DEFERRED** | **не реализовано** |
| Команды управления сессией | `/new /resume /compact /context /fork` | **есть** |

**Вывод оси 3:** Scope=topic — одна из самых сильных и завершённых возможностей Движа: конкретная,
проверенная на практике модель адресации (не абстрактная концепция). Layer-2 (кросс-топиковая осознанность
для координатора) — спроектирована, но явно отложена; это конкретный gap, если у Harness координатор уже
видит несколько сессий разом.

## Ось 4 — Egress / доставка в Telegram

| Что | Движ | Статус |
|---|---|---|
| Ответ уходит в тот же топик, откуда пришло сообщение | Подтверждено на живых логах + отдельным ГЛОБАЛЬНЫМ правилом FF (`gateway-telegram-egress.md`) — двойное подтверждение | **approved** |
| Живой прогресс (эдит одного сообщения) | `IMessageHandle` (egress) | **есть** |
| Мультисообщения за ход (live-egress) | Реализовано технически, но выключено по умолчанию (`GATEWAY_LIVE_EGRESS`), с гардами ≤2/ход ≤500 симв. | **есть, но off-by-default** |
| Governance-контроли инлайн (`/approve`, `/reject`, inline-кнопки) | Есть текстовые команды; inline-кнопки для approval заявлены под M5 | **частично** |
| Хедер с ценой хода/сессии | `GATEWAY_REPLY_HEADER` (вкл по умолчанию): роль/модель/💰 | **есть** |
| Голосовые сообщения → whisper → обычный ingress | `message:voice` → скачивание → whisper → префикс `[voice]` | **есть** |

**Вывод оси 4:** Egress — зрелая, продакшн-обкатанная часть (в отличие от памяти/паттернов, это не
draft-ADR, а работающий код с живыми логами). Хорошая точка «мы впереди», если у Harness egress абстрактнее
и не привязан к конкретному мессенджеру так плотно.

## Ось 5 — Awareness (reply/topic контекст в промпте агента)

Уже покрыто в осях 3-4 частично; отдельно стоит подчеркнуть: awareness в Движе строится **послойно и
явно версионируется ADR-ами** (ADR-0002-топики → ADR-0004-topic-awareness-model), а не одним махом — это
паттерн инкрементального проектирования, отличимый от «сразу полная модель». Полезно для сравнения
методологии, не только фич.

## Ось 6 — Связь с памятью

| Что | Движ | Статус |
|---|---|---|
| Единая модель памяти (Unit/Event/Ref) | Спроектирована (ADR-0005), append-only Events, «fold = текущая форма» | **draft** |
| Путь внедрения без риска для живого канала | Strangler-миграция, флаг `GATEWAY_UNIT_STORE` default OFF, откат = флаг off / drop tables, стадии S0-S7 фиксированы | **draft**, но с ОЧЕНЬ конкретным operability-инвариантом |
| Реконсиляция существующих 9-10 операционных репо (не greenfield) | Явный вердикт-таблица Coexist/Absorb/Wrap/Reconcile на каждый существующий кусок | **draft**, задокументировано детально |
| Паттерн-как-данные (для будущего auto-handoff и т.п.) | ADR-0009: минимальная форма, БЕЗ generic-движка (правило двух) | **draft**, слайс-1 = только доки |
| Фактическая реализация Unit-стора на диске | Не верифицировано в этом разведпроходе (не читал `src/server/persistence/entities` на предмет `unit`/`unit_type`/`unit_event`) | **неизвестно** — открытый вопрос |

**Вывод оси 6:** Это ось, где FF (память-субстрат, D1) имеет наибольшее концептуальное пересечение с
Движом — оба движутся к «единому стору типизированных версионируемых единиц с append-only историей».
Разница: у Движа это в первую очередь **инструмент для агента, работающего под шлюзом** (runtime substrate
для одного оператора-владельца), у FF — заявлено как «рабочий субстрат для ИИ-агентов» шире. Возможен прямой
reuse паттерна ADR-0005 (Unit/Event/Ref) как референса для FF-модели узла, а не только сравнение с Harness.

## Ось 7 — Изоляция

Фактов о явной модели изоляции процессов/данных за пределами topic/user scope и permission-policy
(GREEN/YELLOW/RED классификация действий) в этом разведпроходе не собрано отдельно — она частично покрыта
осью governance (ADR-0002-роли, draft). Отдельный вопрос — см. `../questions/`.

## Сводная таблица «где Движ ВПЕРЕДИ / где ПОЗАДИ Harness» (предварительно, без чтения самого Harness-разбора A)

**Вероятно ВПЕРЕДИ** (конкретные, продакшн-проверенные механики, которых типовой генерик-harness обычно
не имеет из коробки, т.к. они привязаны к конкретному мессенджеру/владельцу):
1. **Topic-scoped сессии с проверенной на живых логах адресацией** (ось 3) — конкретная, не абстрактная модель.
2. **Per-tool approval-мост в реальном мессенджере** (3 кнопки, «Всегда» без своего хранилища) — ось 2.
3. **Reply-awareness** (агент видит, на какое сообщение отвечает владелец) — ось 3/5.
4. **Явный operability-инвариант для эволюции хранилища** (strangler + флаг off + фиксированные стадии) — ось 6, методология внедрения, не только фича.

**Вероятно ПОЗАДИ** (то, что у типового harness часто есть «из коробки», а у Движа — намеренно отложено
или не начато):
1. **Плагин/marketplace-архитектура** (ось 1) — осознанно отложена («правило двух», риск plugin hell).
2. **Мультиканальность** (ось 1) — архитектурно готово (порт `IChannel`), фактически 1 канал (Telegram).
3. **Роли/permission-policy сверх одного владельца** (governance, ADR-0002-роли) — всё ещё draft, код не начат на дату последнего чтения ADR.
4. **Реальный токен-стрим в чат** (ось 2) — MVP-заглушка (финал одним чанком).
5. **Кросс-топиковая осознанность координатора** (`forBot`, ось 3) — спроектирована, не реализована.

## Главный вывод для сравнения с A

Движ — это НЕ generic-harness: это **специализированный, глубоко продакшн-обкатанный Telegram-шлюз с
одним владельцем**, где сильные стороны сконцентрированы в том, что уникально ценно ИМЕННО для этого
сценария (topic-адресация, per-tool approval в реальном мессенджере, reply-awareness), а слабые стороны —
именно то, что становится нужным при переходе к МНОЖЕСТВЕННОСТИ (много каналов, много ролей, много
паттернов-плагинов) — и это множественное сознательно отложено, а не забыто. Сравнение с Harness будет
честным только если Harness оценивается по той же оси «специализация vs генерик»: Движ выигрывает там, где
конкретика важнее общности; проигрывает там, где общность (плагины, мультиканальность, роли) — это и есть
предложение ценности Harness.
