# Синтез Wave 1-2 — что нашли, что заимствуем, где НЕ строить

> Основано на 4 скаутах (A1/A2/B/C) + приёмка помощника + критик. Внешний контент = advisory
> (`security.md`), в истину не ратифицирован. Это ВИД, дом-истина — в папках A/B/C.

## 1. Трёхстороннее сравнение (карта, НЕ вердикт)
- **DeepSeek Harness / Cordis (A):** один примитив «плагин = `{inject?, apply(ctx)}` / Service»; реактивный DI (Fiber/epoch); mount/unmount = чистая FSM с LIFO-teardown; `ctx.isolate()` = мульти-tenancy без синглтонов; LLM-агенту дан тот же примитив как tool-surface (`cordis_define/run`), версии immutable/append-only, approval = состояние машины. Границы: dev-preview (breaking changes, `SESSION_FORMAT_VERSION=0`), «sandbox — защита от ошибок, НЕ граница безопасности», presets = полное копирование (не наследование), маркетплейса нет (только CLI + GitHub-топик).
- **Движ / agents-manager (B):** гексагон (15 портов), но фактически 1 канал (Telegram) + 1 раннер (SDK, ADR-0001); topic-scoped сессии + reply-awareness (ADR-0002, проверено на живых логах); per-tool approval прямо в мессенджере; модель памяти Unit/Event/Ref (ADR-0005, близко к D1) под strangler-миграцией; «паттерн-как-данные» с «правилом двух» (ADR-0009) — generic-движка плагинов НЕТ осознанно.
- **Паттерн-каталог (C):** 531 паттерн / 14 категорий (agentpatternscatalog) + 194 (nibzard, вторично). Наш уже-работающий метод ПОДТВЕРЖДЁН каталогом: Blind Grader (=co-orchestrator), Generator-Critic Separation (=critic), Orchestrator-Workers (=лид+волны), Blackboard (=doc-tree как слой координации), Frozen Rubric (=банк 7 ценностей).

## 2. ⛔ Три предохранителя (критик+помощник сошлись — НЕ строить на этом)
1. **Cordis ≠ наша V5 Суверенность.** Их «всё-плагин» = ВНУТРИрантаймовая композиция (`inject`/`provide` в одном Context); наша V5 = единица несёт policy+схему как ДАННЫЕ и переживает перенос в ДРУГОЙ движок. Прецедент, не решение. Не цитировать «strongest signal» (`architecture-…analysis.md:84`) без коррекции Q1 (`architecture-open-questions.md:21-30`).
2. **Таблица «Движ впереди/позади Harness» — НЕ вердикт.** Построена против стереотипа «типового harness» без сверки с уже собранными фактами A (`dvizh-…analysis.md:113`). Разные классы систем (специализированный single-owner шлюз vs generic harness). Требует кросс-чека до входа в финальный синтез.
3. **НЕ начинать Commitment/Salience/Preoccupation Tracking как следующий шаг.** Это ещё один слой типизированных ledger-надстроек поверх субстрата с **0 реальных данных** — прямое повторение антипаттерна **Perma-Beta / Eval Vacuum**, который сам каталог называет (`relevance-…analysis.md:187-190`) и который владелец уже диагностировал (MEMORY.md 2026-08-16: «анализ стал избеганием коммита»). Committed next-move владельца — перепись загорания на 3-5 РЕАЛЬНЫХ эпизодах, не ещё раунд харвестинга паттернов.
4. **approval-borrow → это для ДВИЖА, не для FF-графа.** Реальный approval-механизм живёт в agents-manager (другой репозиторий). Не приписывать задачу FF-памяти — иначе builder уйдёт не в тот проект.

## 3. ✅ Что реально ценно (конвергенции, которых скауты по отдельности не видели)
- **Кандидат-инвариант FF:** три независимых источника сходятся на «policy/approval фиксируется на СТАРТЕ эпизода, неизменно в полёте» — Cordis (preset-locked, recompose только у пустой сессии), Движ (`route.approverId` пинится при создании сессии), каталог (Frozen Rubric). Кросс-валидировано → кандидат в явный инвариант (не 3 отдельных borrow).
- **Reuse-чек до стройки:** у Движа уже есть репо `decision-journal` + ADR-0009 «паттерн-как-данные». Прежде чем проектировать любой commitment-ledger/capture-seam — проверить, что там уже есть.
- **A's open Q3 закрывается ссылкой на B:** «давать ли агент-записям рантайм-вес (как `cordis_define`)?» — у Движа ADR-0009 «правило двух» уже отвечает (нет generic-исполнителя до 2-го прецедента; критик там же назвал риск «plugin hell»).

## 4. 🔴 Реальный нерешённый пробел (в синтез, не проглотить)
**V3 Доверие + V7 Согласие:** работающий approval-гейт Движа действует на ВЫЗОВЫ ИНСТРУМЕНТОВ (Write/Edit/Bash), и у него НЕТ точки крепления к consent-семантике ДАННЫХ (`use_consent`/`read_consent`/`hard_erase`). Даже когда V7-модель FF появится на бумаге — в единственном реально работающем approval-механизме её нечем enforce-ить. Названный gap, не «решено by design».

## 5. Честная стратегическая рамка (для владельца)
Карта нарисована и полезна. НО сам этот этюд рискует стать ещё одним витком «шлифуем замок на пустом хранилище»: мы обогатили DESIGN-слой, данных не прибавилось. Вывод исследования согласуется с committed-ходом, а не спорит с ним: **паттерны/прецеденты — это словарь и предохранители для будущей стройки; спусковой крючок остаётся — реальные данные (перепись загорания / реальные дни / rentacar-Postgres).** Решение о следующем шаге — за владельцем (см.
