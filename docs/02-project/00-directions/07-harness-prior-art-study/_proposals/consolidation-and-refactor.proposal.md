## 1. Оценка размещения — где этюд сидит и где должна осесть его ИСТИНА

**Вердикт: узел `07-harness-prior-art-study/` сидит ПРАВИЛЬНО как дом для САМОГО ИССЛЕДОВАНИЯ** (факты,
разборы, сравнение — это реальный, не-производный контент). Структура A/B/C (`01-deepseek-harness-cordis/`,
`02-dvizh-gateway/`, `03-agentic-patterns-catalog/`) образцово следует трём архетипам: узел-папка + плюрал-
контейнеры `facts/ analyses/ questions/ ideas/`, README = ВИД. Это ЛУЧШЕ структурировано, чем некоторые
соседние направления (01/02 уже используют тот же паттерн — 07 ему соответствует).

Но у этюда 07 есть отличие от D1-D6: он НЕ ценность-направление сам по себе (в отличие от D3/D4/D5, у
которых уже есть канонический дом в дереве ценностей и 00-directions хранит только указатель ➡️). 07 — это
**исследование-катализатор**: его находки должны РАЗОЙТИСЬ по нескольким существующим канонам (V5
`policy-as-data`, kernel-инварианты, V2/V6 разделы), а не осесть в одном месте. Дом-СТУДИЯ (07 целиком) —
верный; но её выводы сейчас **никуда не посажены** — только описаны внутри самого этюда. Это и есть разрыв
между «правильно разложено» и «наполняет систему» (задача §3 ниже закрывает разрыв конкретными адресами).

**Конкретный дефект навигатора (закон 8 — навигатор обязан быть правдивым):** `00-directions/INDEX.md`
(портфель, таблица «6 направлений» D1-D6) **не содержит строку для D7**. Карта устарела в момент, когда 07
завёлся — ровно тот запах, от которого закон 8 предостерегает («карты гниют»). Два варианта чинки (владелец
выбирает при «строй»):
- (a) добавить строку `07 🟢 harness-prior-art-study | investigation (не value-direction) | project | — |
  ./07-harness-prior-art-study/` — трактовать как полноправный member портфеля;
- (b) добавить сноску под таблицей: «07 — исследование-катализатор, не value-direction; см. §3 этого файла
  за адресами, куда УЖЕ разошлись его находки» — если владелец хочет держать таблицу строго «7 ценностных
  векторов» и не путать классы.

Рекомендация наблюдателя: (a) — дешевле, не плодит второй класс сущностей в портфеле, а зависимость D7→D1/D2
уже показана в самом README этюда.

## 2. Консолидация/дедуп — конкретный план переездов (обратимо, `git mv` с историей по «строй»)

### 2.1 Главный переезд — `04-integration-strategy/` использует НЕ-канонические контейнеры

**Находка:** `01-`/`02-`/`03-` (сиблинги того же этюда) корректно кладут все `.analysis.md` в `analyses/`.
`04-integration-strategy/` вместо этого завела **шесть ОДНОФАЙЛОВЫХ singular-папок**: `frame/` (1 файл),
`rubric/` (1), `critique/` (1), `stage2-gamma/` (1), `stage2-delta/` (1), `aggregator-readiness/` (1). Ни
одно из этих имён не зарегистрировано как folder-type в `.doc-types.json` (там `analyses/questions/decisions/
plans/ideas` — плюрал-контейнеры). Это прямое нарушение закона 4 «нет loose-файлов / много папок-одиночек =
запах» и закона 5 «тип решает дом» (суффикс `.analysis.md` уже говорит «дом = `analyses/`», но файл лежит не
там). Разнобой ломает читаемость: сравнить 04 с 01/02/03 нельзя одним взглядом на дерево.

**План (LOSE-NOTHING, `git mv`, ничего не удаляется):**

### 2.2 Второстепенное наблюдение — `03-agentic-patterns-catalog/catalog/`

`catalog/` — тоже non-canonical singular-имя (1 файл: `patterns-catalog.md`), но это **сырьё-реестр**
(advisory, внешний контент), концептуально не «разбор» (`.analysis.md`) — переименование в `analyses/`
исказило бы тип. Низкий приоритет: либо (а) оставить как есть и явно зарегистрировать `catalog` как folder-
type в `.doc-types.json` (если паттерн повторится ещё раз где-то в дереве — тогда стоит), либо (б) просто
переименовать файл в `01-patterns-catalog.reference.md` внутри существующей `analyses/`-соседки как
suffix-тип `reference` (если такой тип заведём). НЕ включаю в срочный план — одноразовое явление, не мешает
чтению так же сильно, как 2.1 (там ШЕСТЬ папок ломают обзор одного этапа, здесь одна и по смыслу иная).

## 3. Как выводы этюда НАПОЛНЯЮТ систему (не складируются) — конкретные адреса

Задача не «переместить этюд», а **посадить его находки** в уже существующие канонические дома, где их
УЖЕ ждут открытые развилки/инварианты. Три конкретных адреса:

### 3.1 → `docs/02-project/core/01-brain/01-overview/01-values/05-suverennost/02-policy-as-data/README.md`
Этот дом УЖЕ существует (draft, открытые «Развилки», в частности развилка #2 «Кто исполняет политику» —
движок-параметры vs ячейка-запрос-примитив vs гибрид). Находка этюда `aggregator-readiness/…analysis.md`
(P1-P8, вердикт: state/topology/decl — да как данные; live-propagation/render-engine — нет, это ВСЕГДА
обязанность движка) — это ПРЯМАЯ evidence-цитата на развилку #2, причём внешняя и независимая (Cordis
пришёл к тому же расколу для СВОЕГО домена). Рекомендация: НЕ создавать новый файл здесь (закон 2 «один
дом») — добавить абзац-цитату к развилке #2 с ссылкой `→ 07-harness-prior-art-study/04-integration-
strategy/analyses/06-aggregator-readiness-representability.analysis.md` (после переезда §2.1).

### 3.2 → `docs/02-project/core/00-kernel/invariants.md` (кандидат-инвариант, НЕ ратификация)
`_synthesis/2026-08-23-comparison-and-guardrails.analysis.md §3` уже назвал кросс-валидированный
кандидат-инвариант: «policy/approval фиксируется на СТАРТЕ эпизода, неизменно в полёте» — 3 независимых
источника (Cordis preset-locked, Движ `route.approverId`, каталог Frozen Rubric). Файл `invariants.md`
— единственный канонический дом для этого класса утверждений (структура I-1, I-2… с полями Statement/why/
enforced-at/violated-when/proven-by). Рекомендация: дописать `I-N · Episode-scoped policy lock` со статусом
**proposed** (не ratified — по конституции требует явного владельческого решения), `proven-by:` ссылкой на
синтез. Это единственная находка этюда, которая реально претендует на статус ПРАВИЛА системы, а не просто
заметки — стоит явно вынести на «строй» отдельным пунктом, не хоронить в § синтеза.

### 3.3 → `docs/02-project/core/01-brain/01-overview/01-values/02-tozhdestvo/06-dvizhkovyy-dolg/` (нужна проверка перед слиянием)

## 4. Процесс

**(а) Что сделало волны точными.** Скауты этюда 07 систематически цитировали `file:line` на ВНЕШНИЙ код
(Cordis) и на СВОИ предыдущие волны (`architecture-facts.md #N`) — это резко подняло проверяемость
(`aggregator-readiness` analysis особенно дисциплинирован: каждый паттерн → цитата → representability-
вердикт по фиксированной трёхзначной шкале). Критик Этапа 1 (`premise-critique.analysis.md`) поймал РЕАЛЬНУЮ
скрытую ложную дихотомию (Мишень 4 — «какой рантайм» не входил в согласованное owner-меню 2026-08-22) —
это именно то, для чего нужен критик ДО «готово» (закон 5 метода). Что размылось: у САМОГО этюда (README)
нет явного поля «куда садятся выводы после ратификации» — отсюда и разрыв §1/§3 этого предложения; будущим
этюдам стоит завести секцию «Landing map» в README ещё на старте (не постфактум).

**(б) Нужен ли стоячий наблюдатель структуры — ДА, но лёгкий, не полная роль.** Обоснование: находка §2.1
(шесть однофайловых папок вместо `analyses/`) НЕ была поймана ни одним из скаутов/критика/помощника —
все они смотрели на КОНТЕНТ, не на форму дерева; это ровно слепое пятно, которое существующие роли метода
(лид/помощник/критик, `.claude/rules/recursive-orchestration-method.md`) не закрывают ни одной из своих
5 обязанностей. НО не нужен новый агент — хватит ОДНОГО дешёвого чек-пункта помощника (обязанность «г»
наблюдение-за-дрейфом уже мандатирована; расширить её конкретным вопросом «новая папка = плюрал-контейнер
из `.doc-types.json` ИЛИ имеет причину не быть им?») перед закрытием КАЖДОЙ волны, что создаёт НОВУЮ папку —
дешевле отдельной роли, закрывает именно этот класс дрейфа.
