# D1 · Субстрат + policy-as-data — что это НА САМОМ ДЕЛЕ

## 1. Суть (подъём до паттерна)

D1 — это НЕ «фича памяти». Это выбор архитектурного **разреза**: одна память как
**СУБСТРАТ** (общий граф-узлы + append-only лог), над которым сидят разные
**потребители**, а правила «кто что может» лежат **внутри самого субстрата как
данные**, а не в коде приложений.

**Ментальная модель — «ОС для жизни».** Субстрат = ядро+ФС; приложения = процессы,
которые пишут/читают файлы; полис = биты доступа + reference-monitor, но САМ хранимый
как файл в той же ФС (self-hosting, `policy:constitution` — узел графа, engine.ts:21).
Аналог из БД: это **Row-Level-Security-as-data** плюс триггеры/материализованные виды
(«система сама действует»).

Три вещи, которые надо развести, иначе спор идёт на разных этажах:
- **substrate vs application** — приложение НЕ владеет данными, оно их «сдаёт на
  хранение» в субстрат (владелец N-011). Граница «хранит ↔ понимает/действует» = не
  граница модулей, а граница ЧТЕНИЯ: любой, кто читает через линзу (view-compiler) и
  реагирует, уже «действует».
- **два потребителя одной памяти** — (1) агенты ЗАПОЛНЯЮТ (write-plane), (2) система
  САМА читает и показывает/действует (read-plane; `day-mirror.ts` — первый живой
  read-grain: лог → линза → зеркало). Это ОДНА память, два конца, а не две базы.
- **policy-as-data vs policy-as-code** — ключевой рефрейм. Часть УЖЕ данные (гранты-узлы,
  `policy:constitution.body.protected_namespaces/no_read_ids`, `space.policy_overrides`
  в resolve.ts:187-193). Но **логика разрешения — ещё код** (комбинатор, имена мета-капов
  `core:manage-core`, каскад) в resolve.ts. Вижн M-G3 (полис-узлы + рёбра `refines`,
  разрешаемые read-time) — НЕ построен. Вот истинная дельта D1.

## 2. Векторы устройства policy-as-data

- **A. Полис на ТИПЕ** (`type-def → governed-by → policy`, M-G3). За: рост = INSERT
  типа, естественно для «направлений» владельца (приложения/бухгалтерия). Против:
  тип-центризм слаб там, где правило зависит от контента ячейки, не её типа.
- **B. Полис на ДАННЫХ/паттерне** (полис матчит по предикату/scope/значению, как
  `no_read_ids` точечно, resolve.ts:251). За: точность, приватность-как-исключение.
  Против: дорого читать (обход при каждом resolve), риск «свалки» частных правил.
- **C. Универсальный + каскад-override** (Конституция > policy > integrity, разрешение
  сверху вниз по `refines`). За: один потолок, проект переопределяет для своего scope не
  переписывая (M-G3 вердикт «много узлов + один каскад»). Против: каскад read-time = ещё
  нет в движке; сегодня потолок ЗАШИТ в resolve.ts, не в рёбрах.
- **D. «Личный модуль» агента = его capability-набор** (гранты + `core:*`). За: «что
  агент делает/не делает» уже выражается грантами (holdsCapability, resolve.ts:151); не
  нужна новая сущность. Против: сейчас `actor` самозадекларирован (engine.ts:96-98,
  T-actor-delegation) — «личный модуль» без аутентифицированного принципала спуфится.

**Рекомендация-направление:** C как скелет (каскад-потолок), A как основной способ
навешивания, B как исключение. Но сперва закрыть разрыв «логика в коде → логика в
рёбрах», иначе policy-as-data — наполовину лозунг.

- Полис-как-данные: `policy:constitution` узел + fail-stop если его нет (engine.ts:58-62);
  гранты-узлы + мета-капы (resolve.ts:75-101, 151-176); space overrides (resolve.ts:187).
- Write-PEP / force-bind авторитета: engine.ts:99-125 (D4-смежное).
- One-home registry (policy-as-data, инжектируется): admission.ts:129-162.
- Система-как-читатель: day-mirror.ts (read-lens), surface-port.ts (paper-freeze M5).
- Вижн, ещё НЕ в коде: M-G3 README — полис-узлы, `refines`-каскад, `effective-policy` view.

**Другие направления:** D2 (микросистемы = «направления» = разные scope полисов,

## 4. Развилки для владельца (односторонние двери)

1. **Скоуп по умолчанию** (Q-D1-1): default-DENY (сейчас floor в FIXED, resolve.ts:170)
   ИЛИ default-по-типу? Ретрофит дорогой — потолок закладывается один раз.
2. **Где живёт ЛОГИКА разрешения** — в коде движка (как сейчас) или в рёбрах-данных
   (M-G3)? Это выбор «движок = интерпретатор полисов». Обратный ход = переписать ядро.
3. **«Система сама действует»** (Q-D1-2) — читатель-и-показывает (безопасно) vs
   читатель-и-совершает-внешние-действия (нужен consent-клапан, сейчас valveGate
   resolve.ts:273 существует, но enforcement согласия НЕ подключён — types.ts:73-82).
4. **Личность агента** — привязать «личный модуль» к аутентифицированному принципалу
   (D4) ДО того, как агенты начнут писать реальные данные.

## 5. Напряжения по 7 ценностям

- **Ц3 Доверие** («правда, калибруется, несёт провенанс, защита от отравления»): полис
  общий на много потребителей = один отравленный полис-узел заражает всех. Провенанс
  полиса (`minted_by`, grantValid resolve.ts:136-148) есть для грантов, НО для
  будущих полис-узлов supersession/порог заражения — только вижн. Риск: система «сама
  действует» на устаревшей ячейке (сценарий Opus #6).
- **Ц5 Суверенность** («ячейка носит СВОЮ политику → живёт в любом движке»): прямое
  напряжение с «логика в коде». Если разрешение зашито в resolve.ts, ячейка НЕ переносима
  — полис не путешествует с ней. Настоящий policy-as-data (полис едет с ячейкой) — условие
  plug-in/маркетплейса, ещё не выполнено.
- **Ц7 Согласие** («знает кому показать и ЧЬЯ она»; референт-третье-лицо неотменяем
  политикой ячейки): форма есть (`referent` в day-mirror, ConsentAssurance), но
  **enforcement НЕ подключён** (types.ts:73-82; ребро `{status:'revoked'}` не блокирует
  ничего). «Система сама действует/показывает» БЕЗ consent-enforcement = утечка «данные
  под одним согласием в другое использование» (Opus #4). Ц7 ограничивает Ц5 (референт над
  владельцем) — при переносе ячейки согласие референта должно ехать с ней, иначе теряется.

Второстепенно: **Ц1** — полис-узлы должны отдавать «действующее правило» дёшево (view
`effective-policy`), не вскрывая весь каскад; **Ц2/Ц6** — у полиса свой `canonical_id` и
рёбра `refines`/`supersedes` как полноправная память (M-G3), не служебные нити.
