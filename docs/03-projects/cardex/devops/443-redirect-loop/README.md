## Что это (в одной мысли)
Приложение на сервере уходит в **бесконечную петлю редиректа** http→https, из-за чего льются гигабайты трафика на порт 443. Локально это НЕ повторяется — значит баг проявляется только на сервере (за TLS-прокси).

## Где болит
🔴 **На сервере** — гигабайты трафика на :443.
🟢 **Локально в docker** — crm back-end и tg-bot здоровы, трафик копеечный. Гигабайтов нет.

## Главная причина (гипотеза №1, с якорем)
`services/back-end/src/main.ts:63-70` — мидлварь безусловно редиректит http→`https://host`, а `trust proxy` нигде не выставлен. За TLS-терминирующим прокси (nginx/traefik на сервере) каждый запрос зацикливается. Локально прокси нет → петли нет → это объясняет «на сервере льётся, локально тихо».

## Побочная находка
🔴 Отдельный контейнер `bot` (image `yashabot_bot`, python/aiogram, restart:always) — крэш-луп 151 рестарт (`ModuleNotFoundError: No module named 'aiogram.fsm'`, aiogram v2 vs v3). Сеть 0 → НЕ источник гигабайт, но сломан. Фикс: aiogram≥3 + rebuild, либо стоп если лишний.

## 🛰️ Апдейт 2026-09-24 — серверные улики подтвердили причину
Скрины сетевого монитора сервера (в `assets/2026-09-24-*`): домен **`pr-888.duckdns.org` (77.42.89.53)**
резолвится **каждую минуту** и составляет **31% всего DNS-трафика**; внутренний `192.168.52.2` непрерывно
шлёт TCP на этот хост. Это **публичное имя самого сервера** (DuckDNS) — в репо его нет. Мидлварь редиректит
на `https://${req.headers.host}` = на это же имя → за TLS-прокси петля бьёт в собственный хост. **Гипотеза
№1 подтверждена живыми данными.** Разбор → `443-redirect-loop.analysis.md` (раздел «Серверные улики»).

## Статус развилок
- 🟡 **Фикс 443:** выставить `trust proxy` + убрать безусловный http→https редирект (TLS терминирует прокси) → подготовить в ветке. Ждёт «строй».
- 🟡 **Подтверждение на сервере:** снять `docker stats` / `tcpdump port 443` в момент пика.
- 🟡 **`bot`(yashabot):** чинить или стоп — ждёт решения владельца (из этой задачи или другой проект?).
