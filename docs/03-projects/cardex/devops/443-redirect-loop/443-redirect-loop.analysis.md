## Гипотезы (ранжировано, с якорями)
1. **🎯 HTTPS-редирект без `trust proxy` → петля через 443.** `services/back-end/src/main.ts:63-70`: мидлварь шлёт 3xx на `https://${host}` при `req.protocol==='http'`, регистрируется ПОСЛЕ `app.listen`, `trust proxy` нигде не задан (в attachments-store — задан, `.../main.ts:33`). За TLS-прокси = бесконечный цикл = гигабайты. **Лучшее совпадение.**
2. **Crash-loop grammY бьёт api.telegram.org.** `@grammy-nestjs/services/listeners-explorer.service.ts:59-63`: `bot.start().catch()` при любой ошибке шлёт себе SIGTERM → рестарт → снова getMe()/polling на 443.
3. **Обязательные root-`.env`** (`MONGO_USER/PASS`, `REDIS_PASS`, `${VAR:?}`) `docker-compose.apps.yml:14-18` — если нет в корневом .env, back-end не создаётся.
4. **Healthcheck врёт:** TCP-only на 3001 → back-end «healthy», но функционально мёртв; `depends_on: service_started` (не healthy) для инфры `docker-compose.apps.yml:22-27`.

  гигабайты на :443. Ровно то, что не воспроизводится локально (прокси нет → нет петли).

**Вывод:** гипотеза №1 подтверждена живыми серверными данными. Цель петли = собственный хост
`pr-888.duckdns.org`. `192.168.52.2` — внутренний источник шторма (контейнер/хост за прокси).

## 🔧 Фикс собран (2026-09-24, ветка `fix/back-end-https-redirect-loop-trust-proxy`)
`services/back-end/src/main.ts` — 24 стр. +/8 −, typecheck чистый (`tsconfig.typecheck.json`). Что сделано:
1. `app.getHttpAdapter().getInstance().set('trust proxy', 1)` — приложение доверяет одному краевому
   TLS-прокси, `req.secure`/`req.protocol` теперь отражают `X-Forwarded-Proto`, а не хоп прокси→апп.
2. Редирект переписан loop-safe и перенесён ДО `app.listen`: 3xx на https шлём **только** когда исходная
   схема клиента положительно `http` (`X-Forwarded-Proto: http`). Если https уже терминирован или заголовка
   нет → `next()`, петли нет ни при каком раскладе.

**Безопасность НЕ потеряна (наоборот):**
- Принуждение http→https сохранено (когда клиент реально пришёл по http).
- `trust proxy:1` безопасен: API опубликован только на `127.0.0.1:3001` (`docker-compose.apps.yml:29`) —
  снаружи напрямую не достучаться, подделать `X-Forwarded-*` в обход прокси нельзя.
- Убран open-loop 3xx на собственный хост (был вектор self-DoS/трафик-шторма).

**⚠️ Зависит от края (проверить на сервере — там живёт настоящая гарантия https):**
- Прокси ДОЛЖЕН прокидывать `X-Forwarded-Proto`. Если не прокидывает — редирект приложения просто не
  сработает (петли всё равно не будет), а принуждение https должен обеспечивать сам прокси (:80→:443 / HSTS).
- Публичное http→https для юзеров — ответственность **краевого прокси**, не приложения (приложение публичное
  соединение вообще не видит). Подтвердить конфиг прокси.

**Пред-существующий gap (НЕ трогал, минимальные правки):** Helmet и CORS в `main.ts:45-53` закомментированы →
