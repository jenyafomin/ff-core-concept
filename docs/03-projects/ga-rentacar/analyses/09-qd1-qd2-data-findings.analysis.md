## Q-D1 — какой лист транзакций КАНОН: `transactions` (клиентские) vs `exp-transactions` (операционные)?

### Ответ (сжато)
Это **не одна роль с двумя кандидатами**, а **две разные роли**. Спор «кто канон» поставлен неверно:
- **`transactions` (8739, таблица `1aZ6…`) = клиентские ПЛАТЕЖИ по заказу** → канон для **баланса/долга клиента**
  (линза M2/M3, пакет `rental-balance`).
- **`exp-transactions` (5934) / `exp-transactions-old` (9005), таблица `1nx9…` = операционные РАСХОДЫ**
  (CAR WASH / PETROL / PARKING по машине+инвестору) → это **другой домен** (cost/investor-учёт), НЕ реестр
  клиентских платежей.

Для вопроса, как он задан («какой лист транзакций-клиента канон»), эмпирический ответ: **`transactions`**.
`exp-transactions` вообще не про клиента — он про операционные расходы на машину. Реальный риск, который
зафиксировали analysis-04 §5.3 и spec-04 §6, — не «мы не знаем, какой канон», а **«линза случайно СМЕШАЕТ
клиентские платежи с операционными расходами»**, если их не развести явно.

### Доказательства

**1. Код уже коммитится на `Transactions` (клиентский лист), `exp-transactions` в коде НЕТ вообще.**
[ДОКАЗАНО]
- `packages/rental-balance/src/ingest.ts` L24: порядок листов = `Orders` → `Transactions`. Комментарий
  L2–4: «drive a RowSource (Orders then Transactions)… Orders ingested BEFORE Transactions so the order/car
  nodes exist before the payments that point at them».
- `packages/rental-balance/src/core/reduce.ts` L112 `reducePaymentRow`: строка Transactions → акт `payment`
  с ребром `paid-against` → заказ. То есть семантика ровно клиентская: **платёж гасит заказ**.
- `packages/rental-balance/src/balance.ts` L3: «remaining = order.total − Σ(payments paid-against …)».
  Это баланс КЛИЕНТА по заказу, а не расход на машину.
- `grep -rniE "exp-transaction|exp_transaction|expTransaction"` по `packages/**` = **0 совпадений**.
  Операционного листа код не читает ни в одном адаптере/редьюсере.

**2. Фикстура `rental-balance/test/fixtures/transactions.json` — это клиентские платежи, не расходы.**
[ДОКАЗАНО]
- Колонки: `Txn / Order Ref / Amount / Date`. Каждая строка ссылается на заказ (`ORD-9001`), сумма гасит
  тотал заказа (1000+800 из 3000 ⇒ remaining 1200). Ни `car`, ни `investor`, ни `category` (CAR WASH/PETROL),
  ни `currency/rate` — т.е. это форма клиентского платежа, а не операционного расхода.
- Сам `_note` фикстуры трактует строки как платежи, гасящие заказ, + orphan-платёж по несуществующему
  заказу (TXN-1003→ORD-9999) → «есть транзакции», расхождение поднимает агент.

**3. Peek реального экспорта разводит две таблицы по СЕМАНТИКЕ и ПО ФИЗИЧЕСКОЙ ТАБЛИЦЕ.** [ДОКАЗАНО из
analysis-04, цитирующего peek; сами peek-файлы вне этого репо]
- analysis-04 §0: `transactions` = 8739 строк, таблица `1aZ6…`, «клиентские, join по Order Id».
- analysis-04 §0 + §5.3: `exp-transactions` 5934 / `exp-transactions-old` 9005 — **другая таблица `1nx9…`**,
  «расходы (CAR WASH/PETROL/PARKING по машине+инвестору, RU-даты `пн, 17 февраля 25`, десятичная запятая
  `20,0`, колонка `rate 3,67`)».
- Разные ключи джойна (Order Id vs машина+инвестор), разные даты (EN vs RU), разная валютная механика
  (`rate`/`currency` колонки только у exp) — это два разных объекта учёта, а не две копии одного.

### Что это значит для дизайна (adversarial)
- Постановка «какой из двух канон» **скрывает настоящую ошибку**: если кто-то возьмёт `exp-transactions`
  как «транзакции клиента», линза покажет расходы прокатчика как долг/платёж клиента — грубо неверно.
  Канон для клиентского баланса — `transactions`, и это уже зашито в коде. Развилки «выбрать лист» по сути
  нет; есть **обязанность НЕ смешать**.
- По трём осям для решения «привязать линзу к `transactions` как канону клиентских платежей»:
  - **ВЫГОДА:** высокая — совпадает с уже написанным кодом (`rental-balance`), с семантикой `paid-against`,
    с join-по-Order-Id из peek. Ноль переделки.
  - **СОХРАНЁННАЯ ГИБКОСТЬ:** высокая — `exp-transactions` остаётся отдельным будущим доменом (расходы/
    инвестор), его можно подключить как ОТДЕЛЬНЫЙ лист/линзу, не трогая клиентскую. Разведение = больше
    гибкости, чем слияние.
  - **ОБРАТИМОСТЬ:** высокая — это выбор источника на входе ingest, не структура ядра; сменить/добавить
    лист = поправить список `SHEETS` в `ingest.ts` + редьюсер, лог перестраивается (`rebuild-from-journal`).

### Границы доказательства (честно)
- **[ДОКАЗАНО по репо]:** код и фикстуры канонизируют `transactions` (клиентские платежи); `exp-transactions`
  не читается кодом; по peek две таблицы физически и семантически различны.
- **[ЗА ВЛАДЕЛЬЦЕМ / живой Sheets]:** полнота и авторитетность `transactions` (8739) для ВСЕХ клиентских
  платежей; не «утекают» ли отдельные клиентские платежи в exp-таблицы; нет ли пересечения/двойного счёта
  одного денежного события в обеих таблицах; актуальна ли `exp-transactions` vs `exp-transactions-old` (какая
  из двух живая). Peek — только верх листа, это не подтвердить по репо.

## Q-D2 — есть ли ПАСПОРТ / EMIRATES ID в выгрузке?

### Ответ (сжато)
**Нет — ни в фикстурах, ни в схеме, ни в peek реального экспорта документа личности (паспорт / Emirates ID)
не видно.** Идентичность клиента держится на СЛАБЫХ сигналах: `Name` + `Mobile` + `Nationality`. Это прямо
подтверждает, почему дедуп M2 запрещает автослияние и опирается на телефон+имя, а не на юридический id.

⚠ **Важно не спутать:** слово «passport» в коде движка — это НЕ документ личности, а метафора «edge-passport /
провенанс». Оно не является доказательством, что паспортные данные есть в данных проката.

### Доказательства

**1. Ни одна фикстура не содержит колонки паспорта/Emirates ID.** [ДОКАЗАНО]
- `ingest-rentacar/test/fixtures/orders.json`: PII-колонки = `Customer`, `Mobile`, `Recent Note` (в реале ещё
  `Nationality`). Поля документа личности нет. `_note` перечисляет «PII columns (Customer/Mobile/Recent Note)» —
  паспорт/Emirates ID не упомянут.
- `ingest-rentacar/test/fixtures/cars.json`: только `Plate Number/Status/NODE ID/Model/Make` — про машину, не про человека.
- `rental-balance/test/fixtures/orders.json`: `Order/Plate/Customer Code/Total/Status` — `Customer Code`
  (непрозрачный код), НЕ документ.

**2. Схема порта не требует и не запрещает — она нетипизирована.** [ДОКАЗАНО]
- `ingest-rentacar/src/ports/row-source.ts` L13–14: `Row = Record<string, unknown>` — колонки не
  перечислены by design («upstream columns are dirty and drift»). Значит порт САМ по себе паспорт не
  доказывает и не опровергает; решает то, какие колонки ЧИТАЕТ редьюсер.
- Редьюсеры читают конкретные колонки и НИ ОДИН не читает паспорт/Emirates ID:
  - `ingest-rentacar/src/core/reduce.ts` L76–77: читает `Mobile/Phone/Customer Phone`, `Recent Note/Note`. Плюс имя. Всё.
  - `rental-balance/src/core/reduce.ts` L61: `Customer Code/Customer Ref/Customer`. Документа нет.
- `keys.ts`: ключи строятся из `#` (numCore заказа) и `Plate No` — документа личности среди ключей нет
  (customerSourceRef = per-order `…:customer`, без юридического id).

**3. Peek реального экспорта: документа личности нет ни в одном листе.** [ДОКАЗАНО из analysis-04, цитирующего peek]
- analysis-04 §4 (L132–133): «**Нет документа личности** — в Orders только Name+Mobile+Nationality;
  **паспорта/Emirates ID нет ни в одном листе peek** → юридическая идентичность отсутствует, дедуп опирается
  на слабые сигналы». То же зафиксировано в spec-04 §3 (L182–184) как «линза честно НЕ отвечает».

**4. Слово «passport» в коде — ложный след, разоблачаю явно.** [ДОКАЗАНО]
- `engine/src/core/types.ts` L26 «D3 (edge-passport…)» и `engine/src/core/admission.ts` L36–37
  (`'passport','passportnumber'`) — это **словарь PII-скана/провенанса движка** (что НЕЛЬЗЯ пускать инлайн),
  а не колонка данных проката.
- `ingest-rentacar/src/core/reduce.ts` L12/L97/L153 «strictly non-PII passport fields» — здесь «passport» =
  «паспорт узла» (набор безопасных полей-тела узла), метафора, НЕ Emirates ID. Наличие этих строк в коде
  НИКАК не свидетельствует, что паспортные данные присутствуют в выгрузке.

### Что это значит для дизайна (adversarial)
- Отсутствие юридического id — **не мелочь, а фундамент M2**: `same-as` строится на телефон+имя (оба
  гнилые — analysis-04 §2: пустой Mobile, мультиформат, транслит Mohammed). Никакого «сверить по Emirates ID»
  запасного якоря НЕТ. Дизайн дедупа обязан жить с этим (high = телефон+имя, автослияния нет) — что spec-04 и делает.
- **Противоречие, которое обязан снять владелец:** `decisions/03-vertical-and-signoffs.decision.md` (EQ-3,
  L71) утверждает, что реальный Dubai-экспорт «**правдоподобно несёт PII (имена/телефоны/Emirates ID)**» и
  потому нужен PII-гейт. Но analysis-04 на peek Emirates ID НЕ нашёл. Либо (а) Emirates ID в peek не попал
  (правее/ниже/в отдельной KYC-вкладке, которой нет в наборе peek), либо (б) аналитический экспорт его вообще
  не содержит (KYC живёт в другой системе — для проката в Дубае это юридически обязательный документ, так что
  его отсутствие именно в АНАЛИТИЧЕСКОМ экспорте правдоподобно). Это не разрешить по репо.

### Границы доказательства (честно)
- **[ДОКАЗАНО по репо]:** в фикстурах, в читаемых редьюсером колонках и в peek-верхушке всех листов
  документа личности нет; «passport» в коде — про движок/провенанс, не про данные.
- **[ЗА ВЛАДЕЛЬЦЕМ / живой Sheets]:** нет ли Emirates ID/паспорта в редко-заполненной колонке ПРАВЕЕ/НИЖЕ
  видимого peek-окна; нет ли отдельной KYC/contracts-вкладки вне набора из 8 peek-листов; снять противоречие
  EQ-3 (decision-03) ↔ analysis-04. Всё это — только на полном живом экспорте (гейт F-D/Q4).
