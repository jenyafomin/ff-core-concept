# Модули ga-rentacar — как данные ложатся в мозг, и «проект из проектов»

> **Фаза = дизайн на бумаге.** Этот файл ничего не решает заново — он раскладывает уже написанные
> spec'и/decision'ы (`specs/02-07`, `decisions/05-06`) под конкретный вопрос владельца: **какие модули
> есть, как их данные ложатся в мозг (акты/узлы/рёбра, один дом на факт), можно ли увидеть ga-rentacar
> как «проект из нескольких проектов» на одном мозге, и где проходит граница корень↔жилец (G1)**. Ссылки
> ниже — не дубли контента, а маршрут к дому истины (doc-tree закон 2).

## 2. Данные → мозг: как каждый модуль пишет (один дом на факт)

Не повторяю полные контракты (они в spec'ах) — только «где дом» и «что доказывает один-дом».

- **M1 (ingest).** Дом факта = `domain_event`-акт с `provenance.source_ref` (`sheets:Orders#<numCore>`,
  `sheets:Cars#<Plate No>`); проекция строит `order`/`car`/`customer`-узлы редьюсером
  (`specs/02` §2-3, §6). Идемпотентность — по `source_ref+snapshotHash` (движок дедупит на этом ключе,
  `specs/02` §4). Единственный писатель этих трёх типов узлов — реализация M1, ничего другого их не
  трогает (D2, `decisions/01`).
- **M2 (same-as).** Дом факта = ребро `same-as` на узле-клиенте. Обратимость держится НЕ на новом
  предикате ядра, а на существующем поведении `foldEdges` ветки `many` (`same-as` не зарегистрирован →
  дефолт `many` → replace-in-place по `(predicate,target)`, `specs/06` §0). merge/un-merge/re-merge — три
  акта с РАЗНЫМ `snapshotHash` (иначе идемпотентность съест toggle, R-LIGHT-1). Один писатель ребра
  `same-as` = write-helper M2 (`specs/04` R2 + `specs/06` S3/S4). Кандидаты (R1) — **не пишутся в
  канонический граф вовсе**: они non-projectable вывод, не проходят `foldInto` (`specs/06` §0
  "Кандидаты НЕ пишутся"). Это делает автослияние структурно невозможным, а не отфильтрованным.
- **M3 (observation).** Дом факта = `observation`-акт с `payload:{type,subject,ref}` (ключ обязателен,
  `specs/03` §4 — provenance-only ключ доказанно неверен, сольёт разные субъекты). Non-projectable →
  ре-синк Sheets domain-состояния его не трогает (замок анти-коррозии, `specs/05` §5). Один писатель на
  ключ, коррекция = новый акт с бОльшей позицией в журнале, latest-wins в read-path (EQ-1) отдаёт
  текущее. Идемпотентность записи имеет известную дыру на возврате-к-прежнему-значению (`specs/03` §3
  ⚠ дедуп наблюдателя) — write-side провизо помечено M3-deferred, не read-path багом.
- **rental-balance / Payment.** Дом факта = `Payment`-акт под `rentacar.onecar:Payment#`. **Это точка
  реального конфликта одного-дома сегодня**: критика B-1 (`decisions/06` вступление) нашла, что
  `decisions/03`/старый раунд цитировал несуществующий namespace `sheets:Transactions#…` для клиентского
  платежа, а реальный код пишет платёж только в `rental-balance`. Два пакета формально претендуют на
  «клиентский платёж» → owner-гейт: подтвердить `rental-balance` единственным писателем (`decisions/06`
  §6 п.2). До подтверждения `sheets:Transactions#…` — «ошибочный ориентир прошлого раунда, не действующий
  контракт» (дословно из decision).
- **exp-transactions.** Ещё не построен; контракт на будущее — отдельный namespace
  (`sheets:ExpTransactions#`), ДРУГОЙ предикат ребра (не `paid-against`), явный `domain`-тег в payload как
  третья линия защиты (`decisions/06` §1, три уровня развода). Структурный барьер (namespace+предикат)
  — жёсткий (линза физически не может обойти); domain-тег — вторая линия, не первая.
- **A4 (durable StorePort).** Не владеет доменным фактом — это уровень «доходит ли акт до диска вообще».
  Контракт: `Engine.write() → store.writeAct(act)` синхронно на диск + rebuild-from-journal on boot + re-
  ingest не трогает `observation` (`specs/07` §2). Это ROOT-инфраструктура (см. §5), не tenant-модуль —
  но её отсутствие сегодня физически блокирует M3 (акт испаряется в конце хода, `specs/05` §4).

**Сквозной инвариант, которого держатся все модули:** граф = проекция append-only лога (ADR-0008);
ничего не мутируется, откат = обратный акт, `rebuild-from-journal` восстанавливает то же состояние
(LOSE-NOTHING). Разные модули различаются только **какой namespace/предикат/act-kind** они используют —
не механикой записи.

## 3. «Проект из проектов» — модель на одном мозге

Данные показывают, что ga-rentacar уже сегодня — не один монолитный модуль, а **несколько
поддоменов-подпроектов**, которые владелец интуитивно назвал «проект из проектов»:

1. **Core rental ops** (M1→M2→M3: заказы/машины/клиенты/дедуп/живая линза) — основной вертикальный срез,
   первая ценность.
2. **Client payments / balance** (`rental-balance`, `Payment`-акты, `balance-observer`) — исторически
   отдельный пакет, парковался decision-03 (деньги грязные), сейчас частичный кандидат на «дом» платежа
   (owner-гейт §6 п.2 выше).
3. **Operational expenses / investor accounting** (`exp-transactions`) — распознан как отдельный домен по
   данным (другая Google-таблица, другой предикат), но модуля физически нет — только правило развода на
   будущее.
4. **Fines/maintenance** (упомянуты в источниках данных, `INDEX.md` "Источники данных": FINES,
   Maintenance, Unpaid Fines) — сегодня используются ТОЛЬКО как кросс-листовое обогащение линзы клиента
   (`specs/04` R3, best-effort join по plate/имя+телефон), не отдельный модуль-писатель.

**Что делает их «проектами», а не просто таблицами:** у каждого — потенциально свой namespace
(`sheets:Orders#`, `rentacar.onecar:Payment#`, будущий `sheets:ExpTransactions#`), свой предикат
(`rented`/`for-customer` vs `paid-against` vs будущий), свой reducer-пакет (`ingest-rentacar` vs
`rental-balance` vs будущий expense-пакет). Это ровно форма #3 инварианта read/write-плоскостей (родитель
`decisions/05`/`06`): **write = один дом на домен** — не «один дом на весь ga-rentacar», а один дом НА
КАЖДЫЙ поддомен.

**Что их держит ОДНИМ тенантом, а не отдельными системами:**
- Один граф/один журнал/один engine-инстанс — акты всех поддоменов идут в тот же append-only лог, ту же
  admission, ту же constitution-ceiling (S1-S6 в kernel-ADR).
- Один грубый scope-тег `project: ga-rentacar` / `node.body.tenant` на паспорте узла (D4, `decisions/01`;
  tenant-изоляция read идёт через `node.body.tenant`, не через форму id — `decisions/05` со ссылкой на
  `resolve.ts`).
- Одна линза-компилятор (`from · traverse · filter · shape`) — разные поддомены получают разные
  view-контракты (`customer-lens` для M2/M3, будущий `payment-lens`, будущий `expense-lens`), но
  механизм обхода/фильтра/шейпа — общий движковый, не переизобретается на поддомен.
- Структурный барьер между поддоменами (namespace+предикат) — это то, что не даёт линзе одного поддомена
  случайно утечь в другой (три уровня развода `decisions/06` §1: физическая таблица · namespace+предикат
  · domain-тег payload; жёсткость дают уровни 1-2, domain-тег — вторая линия).

**Пользовательский скоуп (не переопределяю здесь).** Как именно агент/пользователь видит срез графа —
уже описано: топик = scope, роль = authority, линза компилится под (viewer×scope)
(`analyses/02-lenses-and-access-mapping` §2, В-4). Свежее развитие (2026-08-03, тот же день) —
`analyses/11-lens-as-flexible-access` раскладывает линзу на три слоя (видимость/формулы/адаптеры) и
явно называет открытый вопрос: **enforcement обхода PII через PayloadStore не подтверждён как проходящий
через тот же `resolveRead`** (`analyses/11` §5 п.1) — это прямое пересечение с «проектом из проектов»,
потому что platform-PEP обязан быть ЕДИНЫМ для всех поддоменов (иначе каждый поддомен изобретает свой
гейт).

## 4. Описание модуля и миграция данных

**Как модуль ДЕКЛАРАТИВНО описан в системе сегодня (по факту кода, не по желаемому):**
- **Predicate + cardinality** — `PredicateRegistry` (`packages/engine/src/core/types.ts`,
  `Record<string, Cardinality>`) — уже DATA-форма (growth = INSERT), но сегодня дефолтный набор
  `DEFAULT_PREDICATES` физически лежит в кернел-пакете, а не в tenant-пакете (см. §5, GAP-2). Правильная
  форма (не построена, но спроектирована в GAP-2 §2): каждый tenant-пакет (`ingest-rentacar`,
  `rental-balance`) экспортирует СВОЙ `PredicateRegistry` и передаёт его явно в `foldInto`/`project`/
  конструктор `MemoryStore` — регистрация нового предиката = INSERT в tenant-пакете, не правка ядра.
- **RowSource port** — `readRows(sheet): Row[]` (`specs/02` §8). Сегодня единственная реализация —
  fixture-адаптер (сэмпл `*.peek.json` + синтетика); реальный Sheets/PG-адаптер подключается ЗА ТЕМ ЖЕ
  портом после F-D (доступ к данным/секретам решает владелец). Это конкретный, уже построенный на
  бумаге пример «модуль как порт + registry-данные», не гипотеза.
- **view-def / lens contract** — сегодня НЕ формализован как registry-запись (`analyses/11` §5 п.3:
  «нужен ли формальный контракт lens-adapter в ядре» — открытый вопрос, не решён). Линза клиента
  (`customer-lens`) сегодня — код в app-слое, не декларация. Это разрыв между «предикат как data» (есть)
  и «view как data» (нет) — стоит явно назвать, а не смешивать со зрелым куском.
- **admission domain-tag** — payload-поле `domain: 'customer_payment' | 'operational_expense'`
  (`decisions/06` §1 п.3) — дешёвая, аддитивная декларация принадлежности акта поддомену; не механизм
  доступа (уровень 3, вторая линия), но полезна для человека/агента, читающего акт напрямую.

**Итог по «декларативному добавлению нового модуля» (сегодняшнее состояние, не идеал):** новый поддомен
(например exp-transactions) сегодня потребовал бы (а) новый namespace-префикс `source_ref`, (б) новый
предикат в `DEFAULT_PREDICATES` — **сейчас это правка файла в `packages/engine/src/core/`, то есть
правка движка**, прямое нарушение G2 (второй-жилец-ноль-правок-движка) — это тот самый разрыв, который
GAP-2 называет живым, а не теоретическим (§5). Только ПОСЛЕ извлечения predicate-registry из ядра в
tenant-пакет добавление поддомена станет чистой data-вставкой.

**Миграция существующих Sheets/CRM данных:**
- **Источник истины остаётся Sheets, не CRM** (D2/D3, `decisions/01`). CRM-Rent (`PROJETS/CRM-Rent`) явно
  НЕ поднимается — берутся только словарь модели и идеи ABAC (роли SUPER_ADMIN/ADMIN/MANAGER/
  ACCOUNTANT/DRIVER/INVESTOR) на будущее (`INDEX.md` "Источники данных").
- **Механика миграции = идемпотентный ре-инжест через RowSource**, не разовый импорт: тот же
  `source_ref+snapshotHash`-дедуп, что и обычный синк (`specs/02` §4). Изменённая строка → новый
  `domain_event` (версия = проекция числа актов, не мутируемое поле); исчезнувшая строка → `archived`-акт
  → узел `tombstone=archived`, не удаляется.
- **Ре-инжест не имеет права стирать `observation`-акты** (C-S7.3 в kernel-ADR, R-LIGHT/M3 замок
  анти-коррозии `specs/05` §5) — это то же правило, применённое и к M1-ре-синку, и к будущему
  CRM/PG-адаптеру за тем же портом.
- **Полнота данных — открытый F-D гейт** (не-секретный экспорт Orders 4102 строк или санкция на
  безопасный путь к БД, `specs/02` §10) — миграция «в полном объёме» физически заблокирована этим, а не
  архитектурой.

## 5. Root/tenant линия (gate G1)

Эта разметка **уже сделана и ратифицирована на бумаге** в kernel-слое (`ADR-DRAFT-root-seal-durable-
store.md` §6, discriminator + таблица форков ga-rentacar) — здесь не переизобретаю, а привожу маппинг
на модули §1, плюс один живой пример нарушения (GAP-2), который тот же документ и W2-верификация уже
зафиксировали.

**Дискриминатор (дословно из kernel-ADR §6):** *«Требование ROOT ⟺ оно верно и для 2-го/3-го/N-го
жильца (инвариантно к смене домена). Требование TENANT ⟺ выражено как ТИП/ПРЕДИКАТ/ПОЛИТИКА (registry-
данные) и умирает при замене "прокат авто" на "здоровье"/"календарь"».*

### Кандидаты UP в kernel (root)

| Что | Почему root | Модуль-источник |
|---|---|---|
| Механизм «один дом на факт» (admission one-home barrier, S5) | Нужен любому жильцу с фактами/деньгами, не только прокату | Пересекает M1/M2/rental-balance |
| `same-as cardinality='many'` + запрет retroactive-переписывания истории (append-only-forward, S8) | Идентити-резолюция универсальна; иначе 1-й жилец ретроактивно портит истину при регистрации нового правила | M2 |
| Полнота линзы (traverse доходит до конца, без произвольного обрыва) | Любому жильцу нужна линза, которая реально дотягивается до данных | M2/M3 (`analyses/02` §3 — вскрытая дыра: bound глубины+cycle-guard) |
| Durable StorePort / cross-turn persistence (S7) | Долговечность истины универсальна — разрыв, который ПЕРВЫЙ жилец форсирует, не специфика проката | A4 |
| Level-as-reading + rollup-контракт (S8, не построено) | Иначе каждый жилец переизобретает merge/промоушен заново | Пока не задействован модулями §1 напрямую |
| Само устройство predicate-registry (`Record<string,Cardinality>` как SHAPE, injection-параметр на `foldInto`) | Форма кардинальности-как-данных — root; содержимое — нет (GAP-2 §2) | Все модули |
| Единый PEP чтения (`resolve()`/`resolveRead` как единственный путь видимости) | Без единого гейта каждый tenant-модуль изобретает свой контроль доступа | Пересекает M2/M3 (открытый вопрос в `analyses/11` §5 п.1 — PayloadStore обязан идти через тот же PEP) |

### Живое нарушение G1 сегодня (не гипотеза)

**GAP-2** (`kernel/analyses/predicates-as-data/01-extract-predicates.analysis.md`) фиксирует, что
`DEFAULT_PREDICATES` (пять ga-rentacar-предикатов из таблицы выше) сегодня физически лежит в
`packages/engine/src/core/predicates.ts` — то есть в кернел-пакете, не в `ingest-rentacar`/
`rental-balance`. По собственному дискриминатору kernel-ADR это TENANT-словарь внутри ROOT-пакета —
прямое нарушение G2 («второй жилец = ноль правок движка»): второй, непохожий жилец (календарь/здоровье)
сегодня НЕ может зарегистрировать свой `one`-кардинальный предикат без правки `predicates.ts` ИЛИ без
молчаливого падения в `many`-дефолт (оба пути ломают гейт). GAP-2 уже предлагает Path A (извлечь сейчас)
vs Path B (записать как долг) и **не выбирает** — это открытый owner-гейт, не решаю его повторно здесь
(см. §6).

## 6. Открытые вопросы владельцу (не решаю)

1. **`rented` vs `for-customer` — одно отношение или два факта?** Прямое противоречие между тем, что
   эмитит M1 (`rented`), и тем, что обходит линза M2/M3 (`for-customer`) — разные предикаты и keyspace,
   линза вернёт 0 заказов, если не унифицировать (P0, общий гейт `decisions/05` §6 п.1 и `decisions/06`
   §6 п.1). Развилка: унифицировать предикат (write-один-дом) ИЛИ признать два факта и обходить оба
   (read-и-так-и-так). Влияет на границу модулей M1↔M2 из §1-2.
2. **Кто единственный писатель клиентского платежа?** `rental-balance`/`Payment#` — фактический кандидат
   по коду, но не канонизирован владельцем; старый ориентир `sheets:Transactions#…` признан ошибочным
   прошлым раундом (`decisions/06` §6 п.2). Это прямо определяет, сколько «проектов внутри проекта»
   реально формализуются в §3 п.2.
3. **GAP-2 Path A (извлечь predicate-registry из ядра сейчас) vs Path B (записать как долг)?**
   (`kernel/analyses/predicates-as-data` §5) — определяет, декларативно ли описание модуля УЖЕ сегодня
   или ещё «правка движка» до этого решения. Не выбираю за владельца.
4. **A4/StorePort sync vs async (one-way door)** (`ADR-DRAFT-root-seal-durable-store.md` §4) — влияет на
   то, как модули §1 персистируют акты; отдельный owner-гейт с пометкой «дверь в одну сторону», не
   переоткрываю.
5. **canonicalId (ADR-04) — переклассификация в PREREQ M4 подтверждена владельцем?** `decisions/05`
   рекомендует отложить (light read-path M2 идёт на `source_ref`), но financial recorded as "что осталось
   владельцу" в самом decision-файле — не факт ратификации.
6. **Формальный lens-контракт в kernel (view-def как registry-данные)?** Сегодня разрыв: predicate — уже
   data, view — ещё код (`analyses/11` §5 п.3). Если владелец хочет «модуль полностью декларативен» (§4),
   это следующий кусок, который нужно поднять в root, не решённый ни здесь, ни в `analyses/11`.
7. **Становится ли `exp-transactions` реальным модулем сейчас или остаётся бессрочно «правилом на
   будущее»?** Ни в одном прочитанном доке нет решения строить его в обозримых вехах (`plans/01` не
   упоминает его среди M0-M6) — стоит явно спросить, входит ли он в горизонт «проекта из проектов» или
   это гипотетический слот.
