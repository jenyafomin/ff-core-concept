# Grounding реальных данных: на цифрах

> Задача (A1): проверить дизайн M2 (дедуп `same-as` + клиентская линза) → M3 против **реальных**
> экспортов, а не предположений. Всё ниже — из peek-файлов
> `PROJETS/RENTACAR_EXCEL_ANALYTICS/data/raw/*.peek.json` (заголовки + sample-строки). Каждый факт —
> с указателем на файл · строку · поле. Peek = верх листа, поэтому оценки распространения помечены как оценки.
> Вывод-хедлайн: анализ-01 подтверждается на живых данных — **дедуп людей и грязь строк реальны и
> измеримы**; вдобавок вскрылись факты, которых в анализе-01 не было (см. §5 «Новое»).

## 1. Дублирование клиента — реально, и телефон+имя вместе его берут (грунт под confidence M2)
Внутри крошечного окна из 19 order-строк (`orders.peek.json`) уже видны повторные клиенты:
- **Kriukovskyi Oleksii**, Mobile `380674842880`, Ukraine — **3 заказа**: `45638-2856` (row 18),
  `45618-2854` (row 19), `45570-2852Collection` (row 21). Имя+телефон совпадают точно → **сильный `same-as`**.
- **Kushnerev Vladislav**, Mobile `79263869765`, Russia — **2 заказа**: `45731-2861` (row 13),
  `45456-2849` (row 23). Снова точное совпадение имя+телефон.

Вывод для M2: **высокая уверенность `same-as` = совпадение И телефона, И нормализованного имени** (а не
одного телефона — см. §2). На order-уровне такой кандидат реально существует и его видно без эвристик.

**Кросс-листовая идентичность тоже есть** (та же личность в разных листах, склеенная по телефону):
- **NAGAEV TALGAT** — Orders `45832-2865` (row 9, Mobile `971501534168`) ↔ FINES row 8, поле Customer =
  `"NAGAEV TALGAT  971501534168"` (имя+телефон в одной ячейке). Телефон совпал → линза может подтянуть штраф.
- **FILKEVYCH YANINA** — FINES row 13 (`"FILKEVYCH YANINA  35799118301"`) ↔ UNPAID row 35 (Name
  `FILKEVYCH YANINA`, Mobile `35799118301`). Телефон `+357` (Кипр) совпал через два листа.

## 2. Почему только-телефон и только-имя ломаются (гнилые опоры — подтверждено данными)
**Телефон:**
- **Отсутствует** — Orders row 7 `45854-2867` (Armen Llchlyan): поле Mobile пустое → дедуп по телефону
  невозможен в принципе для части заказов.
- **Разноформатный, без нормализации** — в одном окне: `393664327852` (Италия, без +), `33689748926`
  (Франция), `971585833657` (ОАЭ), `79263869765` (РФ), `380674842880` (Украина), `35799118301` (Кипр),
  `6287729691630` (Индонезия, fines row 11). Один человек-турист легко имеет ОАЭ-SIM на одном заказе и
  домашний номер на другом → тот же человек ≠ тот же телефон (подтверждает анализ-01 «SIM ≠ человек»).

**Имя:**
- **Хаос регистра/порядка** — `Andrea Guerrini` (Title) vs `BRANCO JORDAN` / `OLEG MALKIN` (CAPS);
  `Kushnerev Vladislav` (фамилия-первой) vs `Thomas Luke James` (имя-первым) — всё `orders.peek.json` sample.
- **Многотокенные имена** — `Andre Hernung Kemer E Silva` (row 6), `SAEED YAQOOB BEHROOZ SAQER ALBALOOSHI`
  (fines row 15) → парсинг «имя/фамилия» ненадёжен.
- **Нестабильный транслит Mohammed** — `MOHAMMAD IBRAHIM KHAN SHARIF KHAN` (transactions row 12) vs
  `Mohamed Aziz Rebai` (unpaid row 34): разные люди, но ровно та вариативность написания, из-за которой
  анализ-01 запретил автослияние по имени. **Вывод: нормализация имени (upper+trim+сорт токенов) — только
  для confidence-скоринга, не для ключа; автослияния нет.**

## 3. Грязь полей, угрожающая дедупу/линзе (реальные примеры)
**Orders (`orders.peek.json`):**
- **Приклеенные хвосты к номеру заказа** `#`: `45875-2870 [AL]` (row 4), `45832-2865Long term` (row 9),
  `45821-2864Short term` (row 10), `45570-2852Collection` (row 21). Подтверждает правило `numCore`
  из спека §3 (отрезать `[AL]`/`Long term`/`Short term`/`Collection`). numCore = `NNNNN-NNNN`.
- **Order Type = тип+ставка склеены** в одной ячейке: `Daily400.00`, `Monthly5500.00` (rows 4, 10).
- **Деньги грязные/плейсхолдерные**: Remaining отрицательный (`-5316.67` row 10, `-1666.67` row 15) =
  переплата/кредит; row 8 `45835-2866` Daily Rate `1` / Invoice `2` = явно тест-заказ. → подтверждает
  вырез «денег из MVP» (анализ-01, decision-03).
- **Формат времени плавает**: `2026-02-22 17:05` vs `2026-02-19 18:36:32` (с секундами) vs `2026-02-16 9:02`
  (без ведущего нуля).
- **Recent Note = свалка НЛ** с приклеенным автором+таймстампом (`…Abhijit2026-02-27 10:31`), эмодзи
  (✅ ⛽️), чеклистами доставки и лог-записями изменений полей (`Update Followup Date from "-" to …`).
  Заносить сырьём (анализ-01), извлечение отдельно.

**Cars (`exp-cars.peek.json`):**
- **SOLD-плейсхолдер**: row 10 — Plate `SOLD-123`, VIN `SOLD123`, Mark `FORSELL`, Status `-`,
  NODE ID `-`. Это не машина → фильтровать до создания car-узла.
- **Мусорный VIN**: row 12 VIN `BGHL4475686897DGCJHVBKJ` (23 симв., не валидный 17-символьный VIN).
- Дублирующиеся filler-колонки заголовков (`-`, `-`, `col_22`) → разреженный лист.

**Форматы номера машины НЕ совпадают между листами** (угроза join машина↔штраф↔транзакция):
- Cars/Orders: `FF-71397`, `DD-59346` (буквы-дефис-цифры).
- FINES `Vehicle`: `Y-62392#25`, `K-20640#5415` (плита + приклеенный суффикс, `fines.peek.json` rows 14,17).
- Transactions: номер спрятан в Description как `(CC) 78750`, `(Y) 32642`, `(X) 16483`
  (`transactions.peek.json`) — буква-в-скобках + число, формат вообще другой. **Джойн по плите нетривиален,
  требует нормализатора плиты.**

**UNPAID — самый опасный лист (взрыв заметки в строки):**
- Rows 8–33 (`unpaid-fines.peek.json`) — это **ОДНА заметка о доставке, разлитая на ~26 строк**: колонка
  `#` несёт `Car.   : - Hyundai Elantra gray`, `No plate :- F 98950`, `Check Levels:`, `Oil :✅`,
  `Fuel⛽️%    :-50%`, `Money.    :- 2000 AED`, `Comments:-…Abhijit…`. Наивный инжест сделает **26 мусорных
  узлов**. Плюс перекос колонок: row 33 Name = `F-98950` (это плита!), Mobile = `Olga` (это человек!).
  **Гейт для M1/M2: строка-кандидат клиента валидна только если есть numCore-`#` И (Name ИЛИ Mobile);**
  иначе — не узел.

**Transactions — перепутаны колонки:**
- Заголовок `Customer` на деле содержит **модель машины** (`Infiniti QX80 2021`), а `Customer Phone`
  содержит **имя клиента** (`MAHMUDOV TAHIR`) — `transactions.peek.json` rows 4–5. Реальное имя клиента —
  в `Customer Phone` и внутри `Description`. Нельзя доверять именам колонок; маппинг — по содержимому.
- Мультивалюта в свободном тексте: `CASh USD 2000= AED 7315 after exchange currency` (row 5).
- Перевод денег между людьми: `transferred from MOHAMMAD IBRAHIM…` / `transferred to OLEKSANDR DEHTIAROV`
  (rows 11–13) → деньги и идентичность переплетены (ещё довод не считать деньги на MVP).
- Колонка-заголовок `#ERROR!` (битая формула, коды `CB+`/`BA+`).

## 4. Клиентская линза: что реально ответит СЕГОДНЯ vs чего нет
После дедупа (M2) собрав кластер `same-as`, линза **«что знаем о клиенте X»** может отдать из имеющихся полей:
- **Аренды**: какие машины (Plate No + Make Model), когда (Order Open Time / Expected Return Date), статус
  (`Active`/`Completed`), ставка/инвойс, число дней, продавец/автор — всё из Orders.
- **Национальность и контакт(ы)**: Nationality + один/несколько телефонов из его заказов.
- **Штрафы**: через плиту машины ИЛИ имя+телефон в FINES/UNPAID → сумма, причина, чёрные точки
  (`Black Points`), неоплаченный остаток. (Пример: NAGAEV TALGAT §1.)
- **Заметки о клиенте/доставке**: сырой текст Recent Note (без извлечения).
- **Платежи по заказу**: через Order Id → Transactions (но суммы грязные — только как «есть транзакции», не баланс).

**Чего в данных НЕТ / линза честно не ответит:**
- **Нет стабильного id клиента** — «все заказы клиента X» невозможны без дедупа (это и есть смысл M2).
- **Нет документа личности** — в Orders только Name+Mobile+Nationality; **паспорта/Emirates ID нет ни в
  одном листе peek** → юридическая идентичность отсутствует, дедуп опирается на слабые сигналы.
- **Нет надёжного баланса/долга** — мультивалюта, переводы между людьми, отрицательные остатки.
- **Renter vs driver** — телефон = SIM, заметка иногда называет другого водителя; связь «кто вёл» не структурна.
- **Структурные факты из Recent Note** (уровень топлива, км, локация выдачи) — заперты в тексте, извлечение отложено.
- **Контакт может отсутствовать** — заказы с пустым Mobile (Orders row 7).

## 5. Новое, чего не было в анализе-01 (усилить дизайн)
1. **Header-offset пер-лист** (заголовки на строках 2–7; в Maintance строка-заголовок сама лежит данными,
   rows 2–3 — мусор `| Green Age Rent a Car |`). Адаптер обязан знать offset — иначе мусорные узлы.
2. **Спилл заметки в строки (UNPAID rows 8–33)** — не «грязная ячейка», а **фантомные строки-узлы**. Нужен
   явный валидатор строки-кандидата (§3).
3. **Три экспорта транзакций, две таблицы, разная семантика** — `transactions` (8739, клиентские,
   таблица `1aZ6…`) vs `exp-transactions`(5934)/`exp-transactions-old`(9005) — **другая таблица `1nx9…`,
   расходы** (CAR WASH/PETROL/PARKING по машине+инвестору, RU-даты `пн, 17 февраля 25`, десятичная запятая
   `20,0`, колонка `rate 3,67`). → **неоднозначность источника истины**: какой транзакционный лист канон?
   Решить до M3, иначе линза смешает клиентские платежи с операционными расходами.
4. **Мультивалюта не только в заметках** — в exp-таблице отдельные колонки `currency`/`rate` → если деньги
   когда-нибудь войдут (условие честности decision-03), конвертация обязательна на входе.
5. **Джойн по плите требует нормализатора** (три формата плиты, §3) — заложить в M2 как отдельный шаг.

## 6. Числа под M2 (оценки с методом, не ложная точность)
- **Orders: 4102 строки** (`orders.peek.json`). Гейт спека T2 (уникальность numCore по 4102) остаётся обязательным.
- **Повторные клиенты — не редкость, а норма**: в окне 19 order-строк **≥4 строки (~21%)** принадлежат
  повторному клиенту (Kriukovskyi ×3, Kushnerev ×2). Бизнес — long-term/повторный (много `Monthly`,
  один клиент циклит машины), поэтому доля повторов правдоподобно **высокая**.
- **Оценка distinct-клиентов**: при среднем ~1.5–2 заказа на клиента → грубо **~2000–2700 уникальных
  клиентов** на 4102 заказа. Это оценка окна, не подсчёт (peek = верх листа); точное число — задача первого
  реального прогона дедупа M2.
- **Оценка доли дубль-кандидатов**: если ~21% из окна — повторные вхождения, то на полном листе
  **порядка 15–25% order-строк** склеятся в кластеры `same-as` >1 узла. → дедуп в критическом пути, как и
  говорил анализ-01; на нём и стоит/падает клиентская линза.

## Итог для M2/M3 (что фундамент требует заложить)
1. **Confidence `same-as`**: high = телефон-норм И имя-норм; medium = один сигнал; **никогда автослияние**.
2. **Валидатор строки-кандидата клиента** (numCore + Name|Mobile) — до создания узла (защита от спилл-строк UNPAID).
3. **Нормализаторы**: телефон (E.164 по стране), имя (upper+trim+сорт токенов, только для скоринга), плита (три формата → один).
4. **Header-offset пер-лист** и **фильтр плейсхолдеров** (SOLD-*, тест-заказы rate=1).
5. **Разрешить неоднозначность источника транзакций** (какой лист канон) до того, как линза заговорит о деньгах.
6. **Линза отдаёт только доказуемое** (аренды/штрафы/заметки-сырьё), деньги — как «есть транзакции», не баланс.
