# M3 — контракт живого топик-агента (клиентская линза)

> **Что это.** Дизайн одного хода живого Telegram-топик-агента: он **читает клиентскую линзу графа →
> отвечает владельцу/оператору → дописывает факт `observed` обратно в граф**, переиспользуя доказанный
> паттерн `balance-observer.ts` (read→compute→write-back), заменив «посчитать баланс» на «ответить из
> клиентской линзы» (решение Q1=B, `decisions/03`). **Только бумага. Не авторизует стройку** — фиксирует,
> что стройка должна удовлетворить и что сегодня заблокировано.

> предусловий B0..B11) жила в gitignored `_log/…/M3-LAUNCH-SPEC.draft.md` и терялась. Теперь она
> **кристаллизована в этом коммитимом спеке**: контракт хода — §1, модель персистентности и требования к
> `StorePort` — §4, полный список предусловий — §6. Черновик в `_log/` остаётся **только историческим следом
> (trace)**, не домом истины. Зависимость персистентности вынесена в отдельный спек **A4 =

> инлайн, чтобы M3 читался без A4.

## 1. Контракт одного хода

Один ход = один свежий процесс шлюза (`claude -p --resume`). Ничто в RAM не переживает ход → граф живёт
на диске, каждый ход коротко-синхронный: **boot ← диск → work → persist → диск → exit** (§3).

| # | Шаг | Кто | Построено? |
|---|-----|-----|-----------|
| T-1 | NL-вопрос приходит; шлюз доставляет топик-агенту с awareness темы/reply (ADR-0002). Агент **не** пересчитывает id тем. | шлюз | BUILT (шлюз) |
| T-2 | Агент **распознаёт интент**: субъект (клиент — имя/телефон/`source_ref`), линза (`customer-summary` «что знаем о клиенте X»), и утверждает ли сообщение **новый факт** для записи. | топик-агент (промпт) | UNBUILT (маппинг NL→args не написан) |
| T-3 | Агент **вызывает runner** (§3) подпроцессом над **персистентным диск-стором**, передавая субъект. | агент → runner | UNBUILT (нет verb `ask`/`record` + `--store`) |
| T-4 | Runner **поднимает движок с диска** (rehydrate журнала → rebuild проекции), **идемпотентно ре-инжестит текущий Sheets-источник** (dedup по `source_ref`+`snapshotHash`), **компилит клиентскую линзу ЧЕРЕЗ `resolve()`** (единый PEP, I-7). | runner / `@ff/engine` | PARTIAL (rebuild+resolve BUILT; boot-с-диска UNBUILT — A4) |
| T-5 | Runner отдаёт линзу клиента (сам клиент + его заказы + рёбра `same-as` из M2 + прежние наблюдения) структурой на stdout. | runner / линза | UNBUILT (M2-линза не построена — `specs/04`) |
| T-6 | Агент читает stdout, **переформулирует в NL**, честно метя эпистемику (`observed` ≠ истина-Sheets; устаревшее/конфликтующее — назвать прямо), возвращает; шлюз доставляет. | топик-агент | UNBUILT (промпт-уровень) |
| T-7 | Если T-2 нашёл **новый факт из диалога** — агент пишет его `observed`-актом в диск-журнал (свободная внутренняя запись, §5) и **докладывает полный node-key/путь** записанного. | агент → runner (`record`) | UNBUILT (нет verb `record`; провенанс факта-из-чата = DQ5) |

**Гарантия чтения (BUILT):** каждый узел проходит `engine.resolve('read', viewer, node)`
(`balance-observer.ts:readGraph`). Живой цикл использует `resolve()` (только политика), **не** `view()`
(политика + структурный `assertValid`) — намеренно, чтобы граф не отказал на интенциональном orphan-ребре.
Следствие: следующий Observer наследует **негейченную структурную целостность** (kb red-team §d) — это
документируем явно, чтобы не превратилось в молчаливый прецедент.

**Гарантия записи (BUILT, RAM-scope):** `Engine.write()` fail-closed — admission (отказ на inline-PII)
до журнала; `recordedAt` назначает движок; идемпотентность гасит байт-идентичный акт. UNBUILT — что запись
доходит до **диска** (см. §4): сегодня `Engine.write()` зовёт `store.writeAct()` на **RAM-`MemoryStore`**,
персистентный `writeAct` в `Engine.write()` не подключён.

## 2. Как ложится паттерн `balance-observer` (что переносится, что заменяется)

`balance-observer.ts` — доказанный **первый честный агент-цикл**: читает проекцию через PEP, вычисляет
реальное, пишет знание обратно `observation`-актом, который переживает сессию (едет по append-only журналу,
non-projectable). M3 берёт **форму цикла целиком**, меняет только «вещество» вычисления.

**ПЕРЕНОСИТСЯ без изменений (машинерия — vertical-agnostic):**
- Чтение через единый PEP: `store.load().filter(n => engine.resolve('read', viewer, n) === 'allow')`.
- Запись через `engine.write(act)` актом `actKind:'observation'` — **non-projectable side-journal**
  (не сворачивается в каноническое состояние → §5 анти-коррозия).
- **Идемпотентность записи** `writeOnce`: детерминированный `id`, ключённый на hash payload; байт-идентичное
  наблюдение не дописывается повторно.
- **Read-back переживших наблюдений** (`readObservations`) как контекст следующего хода.
- `viewer = OBSERVER_ACTOR`; зависимость от `StorePort` (конструктор), а не от конкретного хранилища.

**ЗАМЕНЯЕТСЯ (плагин — money-specific → customer-specific):**
| Слой balance-observer | Заменяется на (M3 клиентская линза) |
|---|---|
| `computeOrderBalance` / `orphanPayments` (арифметика) | линза `customer-summary`: клиент X + его заказы + рёбра `same-as` (M2, `specs/04`) |
| payload `BalanceObservation` (`subject:'order'\|'orphan-payment'`) | payload факта клиента (`subject:'customer'\|'customer-fact'`, `ref = source_ref` клиента) |
| `OBS_KIND = 'balance-observation'` | напр. `'customer-fact'` (провенанс метит источник: диалог ≠ Sheets — DQ5) |
| verb `balance` (read-only-shaped) | verbы `ask` (линза) + `record` (факт-из-чата) с `--store` |

**Ключевое различие «вещества» (важно — не спрятать):** у `balance-observer` факт **вычислен из графа**
(оракул = арифметика). У M3 факт-из-диалога **приходит из чата, а не из графа** (T-7, T4-критерий). Форма
записи та же (append `observed`-акт, идемпотентно, non-projectable), но **источник знания — внешнее
утверждение владельца**, поэтому его провенанс/эпистемическая метка обязаны честно отличать чат-факт от
Sheets-факта (DQ5). Линза-ответ (T-5/T-6) — прямой аналог balance-observer; факт-из-чата (T-7) — новый
ingress-путь поверх той же машинерии записи.

## 3. Форма интеграции (как шлюз запускает ход)

Шлюз на каждый ход поднимает `claude -p --resume`. Внутри агент (Claude) вызывает **runner** инструментом
Bash, парсит stdout, переформулирует. Три кандидата (DQ3):

- **(a)** `node dist/.../cli.js` — **сломан сегодня** (`ERR_MODULE_NOT_FOUND` на `@ff/core/dist/index.js`,
  extensionless ESM-emit).
- **(b)** `tsx src/.../cli.ts` — **работает.** ← **выбор для первого supervised-запуска.**
- **(c)** MCP-сервер, биндящий `EngineClient` напрямую — тяжелее; позднее упрочнение.

**Решение: (b) `tsx` как контракт M3 — ЯВНО ВРЕМЕННЫЙ, supervised-only.** Обоснование выбора: это самая
тонкая реальная форма, не требующая чинить ESM-сборку перед первой ценностью; переиспользует seam
`EngineClient`, который движок уже объявил «крос-модульным на M3»; полностью совместима с коротко-синхронной
моделью хода.

> **⚠ tsx — не финальная форма (обязательный follow-up, не блокер первого хода).** `tsx`-per-turn допустим
> **только под supervised-запуском** (владелец рядом). Он гоняет TS из исходников на каждый ход (медленнее,
> тянет dev-тулчейн в рантайм, не проверяет реальный prod-путь сборки). До любого **не-supervised** режима
> ТРЕБУЕТСЯ снять одно из:
> - **(a) фикс ESM-emit** `@ff/core` (extensionless → расширения в import-путях) → рабочий `node dist/cli.js`; **ИЛИ**
> - **(c) MCP-hardening** — сервер, биндящий `EngineClient`, как долгоживущий упрочнённый вход.
>
> Оба трекаются как **P10 (§6)** — «упрочнение раннера». `tsx` закрывает первую ценность, но не снимает P10.

**Импортировать пакет или звать shell?** — звать **shell-подпроцесс** (Bash → `tsx cli.ts`), НЕ импортировать
`@ff/engine` внутрь агентского процесса. Причина: агентский процесс эфемерен и перезапускается шлюзом; вся
несущая state-логика (boot-с-диска, ре-инжест, запись) должна жить в **одном детерминированном runner-входе**,
тестируемом свежим OS-процессом отдельно от vitest (vitest резолвит ESM мягко и **не** доказывает, что вход
реально запускается). Runner = единственный владелец `StorePort`; агент — только NL-обёртка вокруг него.

**Коротко-синхронный ход (принцип анти-хрупкости):** boot → rehydrate-с-диска → work → persist-на-диск → exit.
Никакой state в фоновом процессе → баги шлюза `background-agents-die-on-restart` и `dup-kill` **иррелевантны
корректности** (в RAM между ходами нет несущего). Это ответ дизайна на баги шлюза, а не зависимость от их фикса.

## 4. Зависимость персистентности — `StorePort` (PREREQ, спек A4 = `specs/07-durable-storeport.spec.md`)

**Жёсткий предикат M3:** живой ход невозможен без **персистентного диск-`StorePort` с реальным WRITE-путём.**
Требования к порту заданы ЗДЕСЬ (инлайн, чтобы M3 читался автономно); **реализовать** их должен отдельный
спек **A4 = `specs/07-durable-storeport.spec.md`** (сегодня — **Status:draft СТАБ**: дом + требования
зафиксированы, реализация раскрывается на P2). M3 **потребляет** порт через конструктор
`Observer(engine, store, viewer)`.

**Требования M3 к диск-`StorePort` (контракт стыка M3↔A4):**
1. **Durable append-on-write.** `Engine.write()` → `store.writeAct(act)` **дописывает акт на диск** синхронно
   в момент записи (а не только в RAM). Rehydrate следующего хода видит этот акт.
2. **Rebuild-from-journal on boot.** На старте процесса: прочитать диск-журнал → свернуть проекцию (уже
   доказано, ADR-0008 §2).
3. **Идемпотентный re-ingest не затирает наблюдения.** Ре-синк Sheets (`domain_event`) не трогает
   non-projectable `observation`-акты (§5).
4. **Модель персистентного узла зафиксирована ADR.** EnvelopeNode↔FFNode; сегодня `store-md` несёт конверт
   **непрозрачным JSON-блобом** в `@ff/core`-note (rental-данные не обходятся через `links/tags/parentId`).
   Реконсиляция и её цена — в `analyses/07-canonicalid-cost.analysis.md`; **«ADR-0012» из D6 не существует** →
   нужен настоящий ADR (см. P2, §6).

**Честный статус store-md сегодня (правка REVISE — не переоценивать «ноль тестов»):**
- `store-md` (`MdEnvelopeStore`) — **load-only мост**: гидрирует sync-`MemoryStore` с диска
  (`loadEnvelopeNodes → toMemoryStore`). Его `writeAct`/`writeNode` **не подключены к `Engine.write()`**
  (движок пишет в инъектированный sync-`StorePort`, т.е. в RAM-`MemoryStore`).
- **У store-md ЕСТЬ тест — но узкий.** `test/invariants.test.ts:275` round-trip'ит **только `writeNode`**
  (`writeNode → toMemoryStore → readNode`). **Точное упущение:** `writeAct` **не имеет round-trip покрытия**,
  и **durable append-on-write путь до `Engine.write()` не протестирован** (нет теста «write → рестарт
  процесса → re-read акта с диска»). Это, а не «ноль тестов», — реальная дыра, которую закрывает A4 (§7 AC-2).
- `balance-observer` green **только над RAM-only `MemoryStore`** — ровно тот путь, на котором живой запуск
  работать НЕ может (наблюдение исчезает в момент конца хода).

- **Стык M3↔A4:** M3 задаёт требования (выше 1–4); A4 их реализует + пишет недостающий тест. **Без A4 — M3
  не сдвигается** (T4 недостижим по построению).
- **Дом журнала:** непубличный per-topic store-dir под FF-репо; точное место — doc-discipline решение A4,
  но должно быть зафиксировано ДО wiring, чтобы агент не выдумывал путь. Согласованность записи (single-writer/
  file-lock при перекрытии ходов) — тоже A4; при коротко-синхронном ходе + supervised-соло контеншн низкий.

## 5. Замок анти-коррозии (T4 — факт переживает синк)

D2 (`decisions/01`): **синк владеет своими полями; граф/агенты/чаты — своими; друг к другу не пишут.** M3
реализует это на уровне записи. Из трёх вариантов персистентности (рассмотрены в A4) выбран **B — durable
append-only журнал на диске (CQRS-native)**: acts-log = system-of-record (ADR-0008); граф —
детерминированная перестраиваемая проекция. (A — stateless re-ingest каждый ход — **отвергнут: T4 падает по
построению**, наблюдение эфемерно; C — `store-pg`/ADR-0006 — правильный end-state, но это M4.) Механика замка:

- Агент пишет **исключительно свои** акты: `actKind:'observation'` (линза-ответ) и `observed`-факт-из-чата
  (T-7). Он **никогда** не пишет `domain_event` и **не мутирует** канонические узлы клиента/заказа.
- Наблюдения — **non-projectable side-journal**: не сворачиваются в каноническое состояние (`projection.ts` §3;
  комментарий `balance-observer`). Поэтому **ре-синк Sheets перезаписывает domain-состояние, но наблюдения
  остаются нетронутыми → T4 держится.**
- **Идемпотентность в обе стороны:** ре-инжест dedup по `source_ref`+`snapshotHash` (синк не плодит дублей);
  запись наблюдения dedup по детерминированному act-id (агент не плодит дублей).
- **Коррекция факта = EQ-1 latest-wins** (`spec/03`): ошибочное `observed` отзывается свёрткой «последнее на
  `(subject,ref)`» в **read-path**. Первичный ключ упорядочивания — **порядок в append-only журнале**, а не
  wall-clock `recordedAt` (иначе сдвиг часов даст проигрыш поправки старому факту — см. `analyses/06`). Без
  этого поправка неотличима от устаревшего факта — ровно риск Q1 «грязные поля → агент соврёт». **EQ-1 —
  предусловие любого живого хода на изменяемых данных.**

**DoD анти-коррозии (T4, ручная проверка):** записать `observed`-факт из чата → ре-инжест/ре-синк источника →
факт по-прежнему на диск-журнале и всплывает на следующем чтении (domain-ре-синк его не стёр).

## 7. Acceptance (ручно-проверяемо, при снятых P*)

1. **Свежий процесс.** Реальный OS-процесс (не vitest) запускает `ask` над диск-стором и печатает корректную
   линзу клиента (клиент + заказы + `same-as`), с честными эпистемическими метками.
2. **Переживание рестарта (закрывает дыру store-md).** Ход-1 пишет наблюдение через `Engine.write()` →
   процесс exit → ход-2 (новый процесс) поднимается с диска и читает наблюдение хода-1. (Это и есть
   отсутствующий сегодня тест durable-`writeAct` — см. §4.)
3. **T4 анти-коррозия.** `record` факта-из-чата → ре-синк источника → факт остался и всплыл (§5 DoD).
4. **Чтение под PEP.** Узел, недоступный viewer (`readable_by`, default-deny), отсутствует в линзе агента.
5. **Идемпотентность.** Идентичный ход дважды не плодит ни domain-, ни observation-дублей.
6. **Клапан.** Ни один external-write инструмент недостижим из топика; каждая внутренняя запись доложена полным
   node-key; гипотетическое внешнее действие спрашивает владельца **простым текстом** (не `AskUserQuestion`).
7. **Wiring.** Первый wake резолвит `cwd = FF-root` (не fallback Cardex); топик-`PROMPT.md` загружен.
8. **Коррекция (EQ-1).** Исправленное наблюдение по тому же `(subject,ref)` отличимо и вытесняет прежнее
   (primary-ключ = порядок журнала); read-path отдаёт только текущее.
