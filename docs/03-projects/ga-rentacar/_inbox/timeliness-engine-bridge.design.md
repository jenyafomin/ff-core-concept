# Своевременность / Оперправда — инженерный мост

> **Ценность говорит ЧТО** (компания выходит первой, до дедлайна; факт не протухает) →
> **движок делает КАК** (этот док). Закрывает РАЗРЫВ из хендофа: ни один форк не покрывал
> «Своевременность/Оперправда» операционно (алерты/сроки).

## 1. Что это операционно (две ценности, один субстрат = время)

- **#3 Своевременность** — СРОКИ: ТО, страховка/лицензия авто, ожидаемый возврат авто, просрочка
  оплаты/депозита. Операционно: **алерт ДО даты** (порог lead-time) и подсчёт **дней просрочки** после.
- **#5 Оперправда / anti-corrosion** — СВЕЖЕСТЬ ПРАВДЫ: факт «протух» (наблюдён давно, горизонт вышел)
  или **противоречив** (синк перезаписал более свежий факт из чата; два источника расходятся).

Обе — про одно измерение, которого в движке СЕГОДНЯ НЕТ: **время `now`**. Ключевая находка ревью:
движок event-sourced — `граф = чистая проекция журнала` (`store-durable-fs.ts` C2). Время `now` —
**недетерминированный вход**. Если пустить его в редьюсер, проекция перестанет быть воспроизводимой
(реплей журнала через год даст другой граф). Поэтому **время входит ТОЛЬКО на границе оценки, через
порт-часы, и НИКОГДА внутрь проекции** (I-T1). Это несущая ось всего моста.

## 2. Где живут дедлайны и метки времени

Не новый «тип узла-таймер». Дедлайн — это **нормализованное ЧТЕНИЕ существующих полей** доменного узла:

| Дедлайн | Источник (поле body доменного узла) | Ценность |
|---|---|---|
| Страховка/лицензия истекает | `car.insurance_expiry`, `car.license_expiry` | #2, #3, #6 |
| ТО | `car.maintenance_due` / edge `maintenance` | #2, #3 |
| Ожидаемый возврат | `order.expected_return` | #3 |
| Просрочка оплаты/депозита | `order.payment_due` / payment-vertical | #1, #3 |
| Свежесть факта | `<любой факт>.observed_at` / `asserted_at` (провенанс) | #5 |

**Инвариант провенанса (I-T7):** каждый факт несёт `observed_at`. Факт без него — не «свежий по
умолчанию», а **«свежесть неизвестна»** → отдельный флаг, не тихое доверие (мираж «свежо» — это и есть
корозия). Схема «поле → дедлайн» — **доменное ЗНАНИЕ rentacar, НЕ ядро** (I-T6): ядро остаётся
time-agnostic; rentacar поставляет маппинг. Это соблюдает G1/G2 (линзы не правят `engine`/`core`).

## 3. Границы модуля

| Модуль | Ответственность | Интерфейс (порт) | Зависимости |
|---|---|---|---|
| **kernel `engine`** | только объявить `ClockPort` (крошечный, kernel-neutral). Остальное — НЕ трогать. | `ClockPort.now(): Instant` | — |
| **`packages/timeliness`** (новый, engine-adjacent, доменно-нейтральный) | чистый вычислитель + материализатор + линза алертов | `TimelinessEvaluator`, `AlertMaterializer`, `AlertLens` | `engine` (read-примитивы `Graph`/`buildIndex`, write-план `StorePort`, `resolve()`), `ClockPort` |
| **`ingest-rentacar`** (доменный) | схема «поле→дедлайн», горизонты свежести rentacar | `DeadlineSchema` (адаптер) | `timeliness` порты |
| **алерт как узел** | `type: 'alert'`, живёт в графе как любой узел | проходит `resolve()` PEP, durable в журнале | write-план (§2 store) |

**Правило-нейтральность:** `timeliness` НЕ знает про rentacar; rentacar даёт ему дескрипторы через
`DeadlineSchema`. Это plug-in дисциплина (модульность — цель проекта).

## 4. Порты / контракты (интерфейсы, НЕ реализация)

```
// Ядро: единственный источник «сейчас». Инъекция — чистота проекции сохранена.
port ClockPort { now(): Instant }

// Доменный адаптер (rentacar): нормализует body-поля узла в дескрипторы дедлайнов.
port DeadlineSchema {
  deadlinesOf(node): Deadline[]   // {kind, subjectRef, dueAt, sourceFactId} | []
  freshnessOf(node): Freshness[]  // {subjectRef, observedAt, horizon} | []
}

// Чистый вычислитель: НЕ пишет, НЕ падает, тотален (I-T5).
port TimelinessEvaluator {
  evaluate(graph, now, horizons): Finding[]
  // Finding = {rule:'deadline'|'corrosion', subjectRef, key, severity,
  //            leadTime?, overdueDays?, staleBy?, derivedFrom}
}

// Материализатор: Finding -> alert-акт, ИДЕМПОТЕНТНО (дедуп по key).
port AlertMaterializer {
  materialize(findings, store, clock): AlertAct[]  // 0 новых при повторном свипе в том же окне
}

// Read-план: как customer-lens — чистое чтение, «открытые алерты для X / для компании».
port AlertLens {
  openAlerts(subjectRef?, graph, now): Alert[]     // материализованные + живые derived-findings
}
```

## 5. Поток данных

```
ingest-rentacar → acts → DurableFsStore.journal (C1 fsync) → project() → граф
        │
   [триггер свипа: on-ingest | внешний cron | lazy-on-read]  ← развилка D2
        ▼
DeadlineSchema.deadlinesOf/freshnessOf(узлы)  →  Deadline[]/Freshness[]
        ▼
TimelinessEvaluator.evaluate(граф, ClockPort.now, горизонты)  →  Finding[]
        ▼
AlertMaterializer.materialize (дедуп по key)  →  alert-акты
        ▼
ТОТ ЖЕ write-план: writeAct → журнал (durable, single-writer lock) → проекция;
alert-узел подчиняется resolve() PEP как любой узел (I-T4)
        ▼
AlertLens.openAlerts → пульт компании   +   MetricsReducer → метрики ценности (§7)
```

**Жизненный цикл алерта:** `open → acknowledged → resolved/expired`. Переходы — акты (latest-wins
редьюсер M2 уже есть). **Авто-резолв:** когда дедлайн удовлетворён (авто вернули, страховку продлили)
или finding перестал срабатывать — вычислитель эмитит resolve-акт; дедуп не даёт переоткрыть.

## 6. Инварианты

- **I-T1 Время инъектируется, не хранится в редьюсере.** `project(log)` остаётся чистой и
  воспроизводимой; `ClockPort.now` — только на границе оценки. Реплей журнала не меняет историю.
- **I-T2 Алерт — ПРОИЗВОДНОЕ, не истина о мире.** Истина = дедлайн-факт (`insurance_expiry`); алерт =
  проекция `(факт, now, правило)`. Расходятся → **факт побеждает**.
- **I-T3 Материализация идемпотентна.** `key = {rule, subjectRef, dueAt|state.version}`. Повторный свип
  в том же окне = 0 новых акт. **Переиспользует R5 idempotency-хэш и C4 dedup — не новый механизм.**
- **I-T4 Алерты идут тем же write-планом** (durable-журнал, PEP, single-writer). Никаких сайд-каналов.
- **I-T5 Оценка чистая и тотальна.** Нет записей, нет падений; нет due-date → нет finding (не ложный
  алерт) — зеркалит линзу «пустой список, не ложь».
- **I-T6 Схема дедлайнов — доменные ДАННЫЕ, не ядро.** Ядро остаётся time-agnostic.
- **I-T7 Корозия требует провенанс-времени.** Факт без `observed_at` = «свежесть неизвестна», флаг, а
  не тихое доверие.

## 7. Мост к метрикам ценности (ЧТО → КАК)

| Ценность (VALUES v2) говорит ЧТО | Движок меряет КАК (эмитит вычислитель) |
|---|---|
| #3 «алерт ДО даты» | `leadTime = dueAt − firstAlertAt ≥ horizon[kind]` на каждый дедлайн-kind |
| #3 «дни просрочки» | `overdueDays = now − dueAt` по overdue-findings |
| #3 «риск помечен до сделки» | AlertLens.openAlerts(subject) непусто ДО риск-гейта коммитмента |
| #5 «доля протухших фактов» | `staleFindings / фактыСГоризонтом` (MetricsReducer над findings) |
| #5 «факт из чата переживает синк» | корозия ловит регресс `observed_at` (синк перезаписал свежее) |
| #5 «0 дублей» | уже покрыто M2 dedup + I-T3 |

Так каждая метрика — **прямой выход вычислителя**, а не пост-фактум замер: ценность стала измеримой
операцией движка.

## 8. Развилки / риски владельцу

- **D1 Материализовать vs только-derive.** Алерты ПЕРСИСТ как акты (инбокс, ack, нотификация, история)
  или эфемерные derived-виды, пересчёт на каждый read? **Реком: гибрид** — derive всегда (дёшево,
  всегда актуально); материализовать ТОЛЬКО когда нужен жизненный цикл/уведомление. Владелец: хотим
  персистентный «инбокс алертов компании»?
- **D2 Кто «тикает» свип.** Правило `orchestration-sync-under-gateway.md`: **фон под шлюзом умирает**.
  Значит НЕ фоновый таймер. Опции: (a) lazy — оценка на каждый релевантный read; (b) on-ingest —
  свип после каждого приёма; (c) внешний cron дёргает sweep-capability. **Реком: (a)+(b) сейчас**,
  внешний cron — позже. Владелец: есть ли хост, способный тикать (cron), или строго pull-only?
- **D3 Горизонты свежести.** Пороги «протухания» на тип факта (страховка = жёсткая дата; телефон
  клиента = мягкие 90д?). Кто автор — узел `policy:freshness-horizons` (policy-as-data)? Владелец:
  дать горизонты или принять дефолты?
- **D4 fail-open vs fail-closed на ОТСУТСТВИИ due-date** (СЦЕПЛЕНО с F-3). Нет `insurance_expiry` —
  считать авто «неизвестно = блок обещания» (fail-closed, риск-аверсно) или «нет finding» (fail-open)?
  Ценности #2/#3/#6 тянут к fail-closed для юр-дедлайнов актива. Решать ЕДИНО с F-3.
- **D5 Область anti-corrosion.** v1 — только по возрасту (age-based staleness). Кросс-источник-
  противоречие (sheets: возвращён; чат: нет) — **v2**, требует same-as-кластеров из F-4. **Реком:
  v1 age-based, v2 contradiction после F-4.**
- **Риски:** даты в sheets — строки (парсинг/таймзоны Dubai); clock skew; «шум алертов» без ack/snooze
  (⇒ D1 материализация нужна для заглушения); зависимость от НЕпостроенного spine P1-P6 (dedup/durable).

## 9. Статус ADR

**Кандидат в ADR-0005 «Temporal / Timeliness plane».** Значимо архитектурно: новый порт (`ClockPort`),
новый тип узла (`alert`), новая семантика границы write-плана (материализация findings). Сам ADR
**НЕ финализирую** — ждёт ответов D1-D4 и ратификации ценностей #3/#5 (развилка «раствор vs отдельная»
из VALUES v2 ещё открыта: если #3 растворяют в #1+#2, мост остаётся, но теряет отдельное имя ценности).
