# Решение: процесс — это конфиг, не ядро

## Зафиксировано (владелец, 2026-07-25)
- **D7. Бизнес-процесс НЕ проектируем в ядре.** Его строит команда позже, как **под-пункт настройки чата**.
  Правила поведения в чате = зашитый промпт/набор правил на топик; агент реагирует на распознанное бизнес-событие.
- **D8. Топик = «умный конструктор».** Знает: где лежат какие данные · через какого пользователя (роль) идёт взаимодействие ·
  что ему разрешено (линза + capability). Настройку топика позже может делать сам агент по инструкции (сделать + перепроверить).
- **D9. Пользователи заводятся явно, с ролями** (переиспользуем набор CRM: SUPER_ADMIN/ADMIN/MANAGER/ACCOUNTANT/DRIVER/INVESTOR).
  Роль → ось `authority` (ADR-0004); топик → `scope`. Линза компилится под (роль × топик) — см. В-4.
- **D10. Модель сессий — конфигурируемая, но решается ПОЗЖЕ.** Варианты: одна сессия на всех · сессия на юзера · на топик.
  Вопрос очистки контекста — **следующий этап**, не сейчас (отложено).

## Что это значит для нас сейчас
- Мы НЕ описываем процесс проката. Мы обеспечиваем **субстрат + линзы + доступ**, на которых процесс потом настраивается конфигом.
- Наш вклад на S3: показать **потенциал по данным** (что вообще можно) и заложить базовые механизмы (см. analyses/03).
