# ADR-draft: идентичность узла — аддитивный `canonicalId` (Q2)

> **Статус решения.** Направление принято владельцем-делегированием (Q2 = **A**, см.
> `03-vertical-and-signoffs.decision.md`, Группа 1). Этот файл переводит направление в форму ADR, чтобы
> его можно было **ратифицировать до того, как M2 начнёт писать рёбра `same-as`**. Это `adr-draft`
> проектного уровня; присвоение номера ядрового ADR (напр. `ADR-0006`) — только по явному «строй»
> владельца (см. §6).

> **⚠ Ревизия 2026-07-30 (regrounded on real code).** Прежняя редакция опиралась на неверное прочтение
> движка: будто гейт `resolve()` определяет пространство узла по ns-префиксу id, и будто M1 уже чеканит
> стабильный id отдельно от `source_ref`. **Обе посылки ложны** (см. §1.3 и §2, evidence по файлам).
> Направление A СОХРАНЕНО, но обоснование честное: `canonicalId`, отвязанный от `source_ref`, — это
> **изменение ядра (re-key CQRS-редьюсера + персистентный индекс `source_ref → canonicalId`)**, а НЕ
> «+1 поле, гейт не трогаем». Тесты §5 переклассифицированы как **машинерия-к-постройке**: на сегодняшнем
> движке они КРАСНЫЕ — и это и есть доказательство, что идентичности-как-контракта ещё нет.

---

## 1. Контекст — почему сейчас

Три силы сходятся ровно в точке «как узел называется», и все три упираются в один нерешённый вопрос
Q2:

1. **M2 вот-вот запишет рёбра `same-as`.** Одобренный роудмап ведёт следующую сборку в M2 = дедуп
   клиентов (`same-as`-кандидаты с уверенностью) + линза «что знаем о клиенте X». Ребро `same-as`
   **связывает две идентичности узлов**. Сегодня идентичность узла = `source_ref` (см. §1.3, evidence):
   ребро привяжется к нему по умолчанию. А `source_ref` строится **из содержимого строки Sheets**
   (order number / составной ключ — см. analysis), у него нет стабильного row-id, и он **дрейфует при
   правке данных**. Ребро дедупа на дрейфующем ключе = дедуп, который сам себя ломает при следующем
   синке. D5 требует **обратимого** слияния — это невозможно гарантировать, пока идентичность не
   отвязана от изменчивого содержимого.

2. **Денежная вертикаль возвращается в очередь (не похоронена).** `03-vertical...decision` явно держит
   `rental-balance` как кандидата назад «через дверь». Денежный слой добавляет **версии + tombstone**
   (analysis §«изменение/удаление строк»): та же строка меняется (остаток 5000→0), исчезает, приходит
   снова. Всё это = разные состояния **одной идентичности во времени**. Без устойчивого имени узла
   версионность плодит дубли вместо истории. Значит идентичность надо решить **до**, а не во время
   разморозки денег.

3. **Напряжение с инвариантом ядра I-1 «Stable ID» — и оно СЕГОДНЯ нарушено для узлов проката.** Ядро
   требует: у каждого канонического узла — **стабильный, глобально адресуемый ID, не меняющийся при
   правках содержимого** (I-1). **Но фактический движок этого не даёт.** Редьюсер проекции (CQRS)
   ключует read-model прямо по `source_ref` и кладёт его же в `id`:

   > `packages/engine/src/core/projection.ts` (~L110):
   > `const ref = sourceRefOf(act); … proj.set(ref, { id: ref, … })`

   То есть **`node.id === source_ref` — отдельного стабильного `canonicalId` не чеканится вовсе.** А
   `source_ref` дрейфует с содержимым строки. Значит на сегодняшнем движке узел проката **уже
   нарушает I-1**: правка order number в Sheets → новый `source_ref` → новый ключ проекции → **новый
   узел** (см. §5, тест 4 — он на этом и падает). Это не «риск в будущем», это дефект-в-фундаменте,
   который Q2 обязан закрыть до того, как поверх него легли рёбра и версии.

   **Уточнение про гейт (исправление прежней ошибки).** Ранее ADR утверждал, что гейт `resolve()` (I-7)
   читает принадлежность узла к пространству по префиксу id (`node.id.startsWith(ns)`), и что «scope
   закодирован В id». **По коду это неверно.** В `resolve.ts`:
   - **Изоляция по пространству/арендатору идёт через `node.body.tenant`**, а не через id:
     `resolveRead` (L236–237): `const tenant = node.body?.tenant; if (tenant && !holdsCapability(viewer,'core:read',tenant,graph)) return DENY;`
     плюс capability-гранты и space-оверрайды (`node.body.space` / ребро `occurs-in`).
   - **Ceiling-зажимы защиты policy-узлов ключуются по `node.id`, но РАЗНЫМИ матчерами** (две
     отдельные проверки, прежняя редакция их слила — ошибка):
     - `protected_namespaces` на **write** — **префиксный** матч: `node.id.startsWith(ns)` (L223–225).
     - `no_read` на **read** — **точный** матч членства: `(…no_read…).includes(node.id)` (L235), а НЕ
       `startsWith`.
     Обе проверки ключуются на `node.id` (не на `body`), поэтому после re-key обе начинают ключеваться
     по `canonicalId` — субстантивное следствие ниже держится. Это Конституция-ceiling (I-8), а не
     общий механизм scope.

   Правильная формулировка напряжения: id несёт (а) идентичность и (б) через ceiling — защиту
   protected-пространств; **scope живёт отдельно, в `node.body.tenant`.** Осмысленный, но изменчивый
   `source_ref` в роли id ломает именно (а) — стабильность идентичности (I-1) — и заодно делает
   ceiling-ключ дрейфующим. Отсюда Q2.

**Вопрос Q2, дословно:** делаем ли мы идентичность узла как *(A)* аддитивный `canonicalId` рядом с
натуральным `source_ref`, — или *(B)* непрозрачный UUID-везде как единственный ключ, с алиас-слоем
натуральных ключей поверх? Владелец делегировал **A**; ниже — обоснование в форме, годной к ратификации.

## 2. Решение — аддитивный `canonicalId` рядом с `source_ref`

Узел несёт **два поля идентичности с разными ролями**, которые не конкурируют, а дополняют друг друга:

| Поле | Роль | Свойства | Кто владеет |
|------|------|----------|-------------|
| **`source_ref`** | *натуральный ключ происхождения / дедупа* | из содержимого строки Sheets (order number / составной); **человекочитаемый, может дрейфовать**; НЕ ns-префиксован | синк (анти-коррозия D2: синк владеет своим полем) |
| **`canonicalId`** | *идентичность узла в графе* | **стабильный, ns-префиксован (см. constraint MINT-1 ниже), не меняется при правках содержимого** (удовлетворяет I-1); чеканится один раз при первом создании | **инжест/write-граница** (чеканит + ведёт реестр `source_ref → canonicalId`); редьюсер только ЧИТАЕТ его из акта |

**Как они сосуществуют (жизненный цикл) — ГДЕ чеканится id (несущая точка детерминизма):**

Чеканка `canonicalId` и реестр `source_ref → canonicalId` живут на **инжест/write-границе** (адаптер-синк
+ store-порт), **НЕ в редьюсере**. Редьюсер остаётся чистым и читает `canonicalId` **уже из провенанса
акта** — он никогда не консультируется с реестром. Это разделение — не деталь, а условие
rebuild-детерминизма (см. §2b, §4a).

1. **Первый инжест строки.** Синк вычисляет `source_ref` из содержимого → инжест-граница ищет его в
   реестре; не нашла → **чеканит новый `canonicalId`** (ns-префиксованный стабильный id, constraint
   MINT-1) и заносит пару в реестр → **штампует `canonicalId` в провенанс акта** (I-2) и аппендит акт.
   Редьюсер сворачивает акт, ключуя узел по `canonicalId`, **прочитанному из акта**.
2. **Идемпотентный upsert (повторный синк).** Тот же `source_ref` → инжест-граница находит в реестре
   **тот же `canonicalId`** (id не перечеканивается, I-1) → штампует его в акт → редьюсер апдейтит узел
   в месте. Новый `source_ref` → новая чеканка на границе → новый `canonicalId` → новый узел.
   → **двойной прогон = 0 дублей.**
3. **`same-as` (дедуп людей).** Ребро связывает **два `canonicalId`**, а НЕ два `source_ref`. Несёт
   паспорт ребра (уверенность · происхождение · время — D6). Слияние ручное, обратимое (D5): снятие
   ребра возвращает исходное состояние, оба `canonicalId` уцелевают раздельно.
4. **Изменение/tombstone/версия** = новые состояния **того же `canonicalId`** (append-акт), а не новый
   узел. `source_ref` может дрейфовать — идентичность держит `canonicalId`.

**Constraint MINT-1 (жёсткое требование к чеканке — НЕ допущение).** `canonicalId` становится `node.id`,
а Конституция-ceiling делает по `node.id` **префиксный** матч на write:
`protected_namespaces.some(ns => node.id.startsWith(ns))` (`resolve.ts` L223–225; тот же префикс-матч в
`canWriteNamespace` L89–91). Если минтящийся namespace-префикс `canonicalId` **попадёт под любой префикс
из `protected_namespaces`**, то `constDeny === true` и **КАЖДАЯ запись узла проката** требует
`core:manage-core` → иначе **DENY** (L93). Поэтому это фиксируется как инвариант чеканки, а не как «узлы
проката, предположим, не защищены»:

> **MINT-1.** Минтящийся namespace-префикс `canonicalId` для узлов проката ОБЯЗАН быть выбран так, чтобы
> **не совпадать и не начинаться** ни с одним префиксом из `policy:constitution.body.protected_namespaces`
> (и id не входить в `no_read`). Нарушение → каждый rental-write клампится в DENY. Проверяется тестом §5.3.

*Открытый вопрос владельцу:* финальный namespace-префикс проката (кандидат — доменный `rental:`) должен
быть подтверждён как лежащий ВНЕ `protected_namespaces` действующей Конституции. Это решение владельца, не
догадка агента.

**На что ключуется гейт доступа (по коду, не по памяти).** Изоляция scope в `resolve()` идёт через
`node.body.tenant` + capability-гранты + space-оверрайды — **не через форму id**. Поэтому введение
`canonicalId` в роли `node.id` **не переписывает scope-логику гейта**. Единственное, что меняется:
ceiling-зажимы (`protected_namespaces` на write, `no_read` на read) начинают ключеваться по
`canonicalId` вместо `source_ref`. Для узлов проката (при соблюдении MINT-1 они вне protected-префиксов и
вне `no_read`) это **поведенчески нейтрально** — и, более того, ПОЛЕЗНО: ceiling-ключ перестаёт дрейфовать
вместе с содержимым. `source_ref` **никогда не участвует в решении доступа** (он не ns-префиксован и изменчив).
Это ключевая граница: `source_ref` — для дедупа/происхождения, `canonicalId` — для идентичности (и как
ceiling-ключ). Разведение ролей и есть суть варианта A.

**Честная цена: это изменение ЯДРА, а не «+1 поле».** Прежняя редакция утверждала, что «движок уже
выдаёт стабильный id, canonicalId — лишь явное имя уже существующей роли». **По коду это ложь.**
Сегодня `node.id === source_ref` (`projection.ts` ~L110), отдельного стабильного id НЕТ, редьюсер
**ключует всю проекцию по `source_ref`**. Ввести `canonicalId`, отвязанный от `source_ref`, значит:

- **(a) Re-key CQRS-редьюсера.** `foldInto`/`project` (`projection.ts`) сейчас делают `proj.set(ref, …)`
  и `id: ref` (`ref = sourceRefOf(act)`, L82/L110). Их надо переключить: ключ проекции и `node.id` — это
  `canonicalId`, **прочитанный из провенанса акта**, а НЕ разрешённый редьюсером по `source_ref` через
  живой индекс; `source_ref` уезжает в `body` вторым полем. Редьюсер остаётся чистым: он не консультируется
  с реестром (иначе `rebuild --from journal` со стартово-пустым реестром дал бы другие id и убил бы
  детерминизм — ровно то, ради чего re-key и делается). Это правка **ядрового редьюсера**, а не адаптера-синка.
- **(b) Реестр `source_ref → canonicalId` — на инжест-границе, НЕ в редьюсере.** Редьюсер обязан быть
  детерминирован: «свёртка всего журнала == свёртка по одному, бит-в-бит» (docstring `projection.ts`
  L11–15; I-4/I-5). Отсюда жёсткое разделение: **реестр и mint живут на инжест/write-границе**, а
  `canonicalId` **уже вшит в провенанс каждого акта** (Act/Provenance аддитивно расширяемы — `types.ts`).
  Редьюсер только **читает** `canonicalId` из акта. Поэтому `rebuild --from journal` детерминирован даже
  при **стартово-пустом реестре**: id берутся из журнала, не пересчитываются на лету. Будь mint случайным
  UUID «в редьюсере», ребилд выдал бы **другие** id → сломались бы и детерминизм, и I-1 (id сменился на
  ребилде). Сам реестр — производная проекция инжест-стороны (пересобирается из журнала свёрткой того же
  `provenance.canonicalId`), не второй источник истины (I-5). Это и есть машинерия, которую §5 проверяет.

Иначе говоря: A не «дешевле B на одно поле». A **дешевле B по другой оси** (см. §3) — но сам по себе A
всё равно **инженерная работа в ядре**. Прежний тезис «A ничего не вводит» снят как неверный.

## 3. Рассмотренные альтернативы

### B — непрозрачный UUID-везде как единственный ключ (+ алиас-слой)

Единственный ключ узла — непрозрачный UUID; `source_ref` не первоклассен, а живёт в отдельном
**алиас-слое** (натуральный ключ → UUID), через который проходит любой дедуп/lookup.

**Что B НЕ стоит (исправление прежней ошибки).** Ранее B отклоняли по аргументу «UUID без ns-префикса
сломает гейт, `resolve()` не сможет определить пространство через `startsWith(ns)`». **По коду это
неверно:** гейт определяет scope по `node.body.tenant`, а не по префиксу id (§1.3). Непрозрачный UUID
**не ломает scope-резолюцию** — tenant остаётся в `body` при любой форме id. Значит этот довод против B
снят.

**Что B действительно стоит — и почему всё равно отклонён:**

1. **Общая с A машинерия — не экономия.** И A, и B требуют одинакового: чеканку стабильного id +
   персистентный/воспроизводимый индекс `натуральный_ключ → id` + re-key редьюсера (§2). По этой оси
   B и A равны; «дешевизны» у B тут нет.
2. **B прячет натуральный ключ без выгоды на MVP.** Разница A↔B: под A узел НЕСЁТ `source_ref` видимым
   полем `body` (человекочитаемо, удобно для дедупа/разбора/explain-chain); под B `source_ref` живёт
   только в алиас-слое, и каждый дедуп/lookup обязан пройти **обязательную индирекцию** перед доступом
   к нему. На текущей фазе (один жилец, один проект) сокрытие натурального ключа **ценности не даёт**, а
   постоянный налог на lookup — даёт.
3. **Алиас-слой над append-only логом (I-4).** Журнал `acts[]` immutable — под B алиас натуральных
   ключей всё равно приходится держать как проекцию-индирекцию перед каждым чтением. То же, что индекс
   в A, но обязательное на пути ВСЕХ чтений, а не только идемпотентного upsert.

**Вывод:** B ≈ A по стоимости базовой машинерии, но добавляет обязательную индирекцию и прячет
человекочитаемый ключ ради нулевой выгоды на текущей фазе. Отсюда выбор A.

### C — «просто `source_ref` как id» (без `canonicalId`)

Отклонено: нарушает I-1 (id дрейфует с содержимым) и ломает `same-as`/версионность (ребро и история
виснут на изменчивом ключе). **Важно:** это НЕ гипотетика — **это ровно то, что движок делает
СЕГОДНЯ** (`node.id = source_ref`, `projection.ts` ~L110). То есть текущее состояние M1 = вариант C.
Поэтому «переиспользовать id из M1 как canonicalId» — это НЕ бесплатная миграция, а **сохранение
варианта C**, который мы и отвергаем (см. §4, разрешение самопротиворечия).

## 4. Последствия

**Честный, посчитанный налог (изменение ядра, не «+1 поле»):**
- **+1 поле на конверте** (`source_ref` в `body` рядом с `canonicalId`-как-id) — аддитивно по форме, в
  духе additive-only дисциплины конверта (`axes-and-time.design.md §3.3`: отсутствие поля = дефолт, без
  миграции формы). Но само по себе это поле **не решает задачу** без пунктов ниже.
- **Re-key CQRS-редьюсера** (`projection.ts`: `foldInto`/`project`) — ключ проекции и `node.id`
  становятся `canonicalId`, **прочитанным из провенанса акта**, а НЕ разрешённым редьюсером по `source_ref`
  через живой индекс. Mint и реестр `source_ref → canonicalId` остаются на **инжест-границе** (§2b) —
  границу нельзя размывать: если редьюсер начнёт сам резолвить id, он перестанет быть чистым и `rebuild`
  (стартово-пустой реестр) выдаст другие id. Это **правка ядрового редьюсера** (риск-класс — изменение
  движка, требует зелёных §5 + возможно ADR-0006). Прежний тезис «гейт/движок не трогаем» — неверен:
  гейт-scope действительно не трогаем, но **редьюсер трогаем обязательно**. Re-key затрагивает не только
  `node.id`, но и **цели рёбер** (`edge.target` сворачивается из `act.edges`, L110–115) и body-ссылки
  (`body.space`, `occurs-in`) — их инжест-граница/миграция переводит через тот же реестр перед аппендом
  (см. миграцию ниже).
- **+1 реестр (инжест-сторона)** `source_ref → canonicalId` — производная проекция под I-6
  (`projectionId/Version`), пересобираемая из канона (не второй источник истины, I-5); `canonicalId`
  воспроизводимо восстанавливается из журнала (mint штампуется в провенанс акта, §2b), поэтому редьюсер
  его лишь читает, а `rebuild --from journal` детерминирован (I-4).
- **Гейт-scope I-7 НЕ трогаем** — scope живёт в `node.body.tenant`, форма id на него не влияет. Это
  реальная (и единственная честная) экономия A против гипотезы «переписать PEP».

**История миграции / алиасинга (разрешение самопротиворечия).**
Прежняя редакция утверждала «M1-узлы уже имеют стабильный id → он становится `canonicalId` без
перечеканки, миграция не требуется». **Это ложно и внутренне противоречиво:** M1-id **есть**
`source_ref` (§3-C), значит «переиспользовать M1-id» = «оставить `source_ref` в роли id» = **вариант C**,
который §3 отвергает. Честная миграция:
- **M1-узлы НЕ имеют отдельного `canonicalId`.** Миграция обязана **отчеканить `canonicalId` каждому
  существующему узлу** и построить индекс `source_ref → canonicalId`. Это реальный шаг данных, а не
  «отсутствие поля = дефолт». (Аддитивно читается только `source_ref` как новое поле; сам id-контракт
  меняется.)
- **Re-point рёбер и body-ссылок (критично — иначе рёбра повиснут).** Рёбра сегодня адресуют цель по
  `source_ref`-id: `foldEdges` сворачивает `edges` прямо из `act.edges` (`projection.ts` L110–115), где
  `edge.target` — это тот же `source_ref`-ключ, что и `node.id`. Если перечеканить только `node.id` →
  `canonicalId`, а `edge.target` оставить как есть, то **каждое существующее доменное ребро укажет на
  старый `source_ref`, которого больше нет ключом** → повиснет (dangling). То же с телом: `spaceOf`
  читает `node.body.space` / цель ребра `occurs-in` (`resolve.ts` L53–58) — эти ссылки тоже
  `source_ref`-адресны. Поэтому миграция обязана **третьим шагом прогнать каждый `edge.target` и каждую
  body-ссылку (`body.space` и т.п.) через индекс `source_ref → canonicalId`** и переписать на
  `canonicalId`. Это не отдельная опция, а часть того же re-key: пропустив его, мы разорвём граф ровно
  в тот момент, когда M2 начнёт вешать `same-as`.
- **`source_ref` изменился у той же сущности** (Sheets переписали order number): под целевой моделью это
  **не новый узел** — индекс обновляет запись `source_ref → тот же canonicalId`; при неоднозначности —
  кандидат в ручной review (та же дисциплина, что дедуп людей), не автослияние (D5). *(На сегодняшнем
  движке это, наоборот, ПЛОДИТ узел — см. §5 тест 4. В этом и разница «до/после».)*
- **Обратимость.** До фактической записи M2 решение обратимо (снятие поля/статус). После — индекс
  производный (откат = пересборка), но отчеканенные `canonicalId` в журнале уже канон (I-4): их откат =
  компенсирующий акт, не стирание.

**Что ломается, если отложить (не ратифицировать до M2):**
- Идентичность останется = `source_ref` (вариант C, текущее состояние). M2 привяжет `same-as` к
  дрейфующему ключу → при следующем синке рёбра дедупа указывают «в никуда» → **слияние
  необратимо/некорректно** (нарушение D5). Это ровно «главный риск дедупа» из analysis §🔴-1, внесённый
  в фундамент.
- Разморозка денег упрётся в отсутствие устойчивой идентичности для версий/tombstone → дубли истории.
  Дешевле отчеканить `canonicalId` **сейчас**, пока рёбер и версий ещё нет и re-key редьюсера дешёв.

## 5. План валидации — машинерия-к-постройке (ратификационные тесты)

> **Читать как спецификацию работы, а не как «уже зелено».** На **сегодняшнем** движке
> (`node.id = source_ref`, реестра/mint нет) тесты 1, 3, 4 **КРАСНЫЕ** — и это и есть доказательство
> §2/§3-C: отдельной идентичности-контракта ещё не существует. Тесты **5 (supersede по `snapshotHash`)** и
> **6 (рёбра)** сегодня резолвятся тривиально (`node.id = source_ref`), но существуют как **регресс-стражи**:
> ловят неполный/сломанный re-key — перечеканку `node.id` без сохранения supersede/no-op-дискриминанта
> (тест 5) и без перевода `edge.target`/body-ссылок (тест 6). Каждый тест = приёмочный критерий для правки
> редьюсера. Ратифицируем A, когда на фикстуре проката держатся **все** утверждения.

1. **Идемпотентность → 0 дублей.** Прогнать инжест дважды на фикстуре. **Assert:** число узлов
   стабильно; каждый узел ключуется своим `canonicalId`; индекс `source_ref → canonicalId` не содержит
   дублей записей; ни один `canonicalId` не перечеканен между прогонами (I-1).
   *Сегодня:* индекса/`canonicalId` нет → assert недостижим. **Красный → зелёный после re-key.**
2. **Обратимое слияние `same-as`.** Взять двух кандидатов-клиентов (разные `canonicalId`) → создать
   `same-as` с паспортом (уверенность/происхождение/время, D6) → затем снять. **Assert:** граф вернулся
   в исходное состояние; оба `canonicalId` существуют раздельно; факты каждого уцелели; ребро несло
   паспорт (не голая связь). Ни при слиянии, ни при раз-слиянии `canonicalId` не менялись.
   *Сегодня:* нет `canonicalId` для привязки ребра — тест невозможно даже поставить корректно.
3. **Гейт-scope ключуется на `body.tenant`, `source_ref` не участвует в доступе.** `resolve(key,
   viewer, node)` даёт тот же вердикт scope-доступа (он и так идёт через `node.body.tenant`); **assert**,
   что ни `source_ref`, ни форма id не участвуют в scope-решении. Отдельно зафиксировать: ceiling-зажимы
   (`protected_namespaces`/`no_read`) ключуются по `node.id` — после re-key это `canonicalId`, а не
   `source_ref`. **Плюс проверка MINT-1:** взять реально отчеканенный rental-`canonicalId` и заассертить,
   что он **не** `startsWith` ни один префикс из `policy:constitution.body.protected_namespaces` (и не в
   `no_read`) → `resolveWrite` для rental-узла НЕ клампится в DENY по `constDeny` (`resolve.ts` L223–226),
   т.е. запись проката не требует `core:manage-core`. Гарантирует, что перенос id не открыл обход PEP, не
   оставил дрейфующий ceiling-ключ и не загнал каждый rental-write под защищённый префикс.
   *Сегодня:* `node.id = source_ref`, поэтому ceiling дрейфует вместе с содержимым — это и чиним.
4. **Дрейф `source_ref` не плодит узел.** Изменить `source_ref` строки между прогонами → **assert:**
   тот же `canonicalId`, апдейт в месте, 0 новых узлов (идентичность отвязана от содержимого — I-1).
   *Сегодня:* редьюсер `proj.set(source_ref, …)` при новом `source_ref` создаёт **новый узел** →
   **тест КРАСНЫЙ**. Это прямое доказательство, что I-1 сейчас нарушен и canonicalId нужен.

5. **Supersede/no-op по `snapshotHash` (тот же `source_ref`, изменился хэш) — ОТЛИЧНО от теста 4.** В
   тесте 4 меняется `source_ref`; здесь `source_ref` **тот же**, меняется только `snapshotHash` акта
   (`snapshotHashOf`, `projection.ts` L33–36). Дискриминант «freshest-wins против дедуп-no-op» сегодня —
   пара `source_ref`+`snapshotHash` (docstring L14–15); после re-key узел ключуется `canonicalId`, и эта
   семантика ОБЯЗАНА сохраниться. **Assert (supersede):** тот же `source_ref` с **новым** `snapshotHash` →
   **тот же `canonicalId`**, тело узла обновлено (freshest wins), `state.version` увеличен (++), **0 новых
   узлов**. **Assert (no-op):** тот же `source_ref` с **тем же** `snapshotHash` → дедуп-no-op на
   инжест-границе (акт не аппендится) → узел и `canonicalId` не меняются, 0 новых узлов. Ловит регрессию,
   где re-key на `canonicalId` разорвал бы связку supersede/no-op с `source_ref`.
   *Сегодня:* дискриминант ключуется по `source_ref` (L82) — тест требует, чтобы после re-key он ключевался
   по `canonicalId`, разрешённому из того же `source_ref`. Regress-страж: держит supersede/no-op сквозь re-key.
6. **Рёбра переуказаны на `canonicalId` (нет висячих целей).** Взять фикстуру M1, где узел A ссылается
   ребром на узел B (сегодня оба адресуются по `source_ref`). Прогнать миграцию/re-key. **Assert:** после
   re-key `edge.target` ребра A→B равен `canonicalId` узла B (а не старому `source_ref`), и цель
   **резолвится** (`graph.byId.get(edge.target)` возвращает B, не `undefined`); аналогично `body.space` /
   цель `occurs-in`, если присутствуют, указывают на существующий `canonicalId`. Иными словами: 0 висячих
   рёбер после перечеканки id.
   *Сегодня:* `node.id = edge.target = source_ref`, рёбра резолвятся тривиально; но наивный re-key только
   `node.id` **оставил бы `edge.target` на старом ключе → висячее ребро**. Тест ловит именно этот пропуск.

Все шесть зелены → A ратифицируем как контракт идентичности для M2.

  «CQRS/projection») — **отдельный акт, только по явному «строй» владельца.**
