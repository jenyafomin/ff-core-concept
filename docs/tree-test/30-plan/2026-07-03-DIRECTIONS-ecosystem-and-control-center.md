# НАПРАВЛЕНИЯ — экосистема проектов и центр управления (2026-07-03)

> Владелец в этой сессии НЕ ставил задачу строить или анализировать — только ОСОЗНАТЬ и ЗАФИКСИРОВАТЬ
> цель и направления всего проекта. Дальнейшая работа: **каждое направление = отдельная сессия** со своей
> структурой общения группы агентов (sub-agents + другие виды коммуникации между ними).

## 0. Суть (одним абзацем)

FF Personal Management = **центр управления самим собой**: личный граф знаний, работающий в ДВЕ стороны —
для человека и для ИИ (совпадает с рефреймом msg 141: субстрат для агентов, не хранилище заметок).
Поверх графа — **явное управление агентами через удобный интерфейс** (сид: dwizh gateway / Telegram).
Всё строится **модульно**: каждый модуль в будущем может быть взят другим человеком, улучшен, форкнут
или гибридизирован в новую версию (механизм версий/гибридов — сам по себе ценная фича, если получится).
К концепту относиться **критично** — не влюбляться в свою идею, сверять с конкурентами.

### D-B. Модуль управления агентами (сид: dwizh gateway)
- Существующее решение: `/Users/mac16/Documents/IT/Apps/PROJETS/dwizh/dwizh-monorepo`, модуль **gateway**
  (управление через Telegram). К нему отнестись **критично**: тщательный анализ → пересмотр архитектуры.
- Возможности, которые владелец хочет:
  - контроль терминала из интерфейса: видеть, к какому проекту запущен агент;
  - **навигация коммуникации между агентами** — владелец называет это самой слабой частью текущей реализации;
  - **агенты знают друг о друге**: кто над чем работает, лёгкая синхронизация («кто-то сделал больше/меньше»).
    Решается ИНФОРМАЦИЕЙ: логи разговора, тема, текущая работа… Ключевой открытый вопрос: **КАК агент
    выбирает, что смотреть** — информация должна уже существовать и читаться с минимальными затратами
    токенов, в идеале автоматически;
  - **ввод в терминал через Telegram** с безопасностью: кнопки для явного выбора + опросники через
    conversation (интересные решения есть в Cardex `crm-nestjs` — посмотреть);
  - вообще понять, **что это приложение из себя представляет** (overview, capabilities) и значительно улучшить.
- Связь с ядром FF: это «Модуль 2» из рамки STATE.md; клапан/ABAC (ADR-0003) и principal — прямые зависимости.

### D-C. Документация → дерево → в граф (БД)
- В dwizh есть древовидная система хранения документации (сейчас хаос, но структура ценная).
- Главная идея: перенести её **в первую очередь в БД** — в ту самую ячейку/ноду, которую мы проектируем.
- Полностью переделать текущую документацию на древовидную систему: **не удалять, плавно
  перенести/переписать** (совпадает с конвенцией `DOC-CONVENTION.md`: never delete → 90-historical).
- Ключевое преимущество БД над ФС: **файл в папке живёт в одном месте, узел в БД — в нескольких**
  (это уже валидировано: мультипринадлежность, Q3 = дом+категория = 2 ребра; сид Stage 1: «папки=группы,
  но ФС фиксирует»). Документация — естественный dogfood-наполнитель графа.

### D-D. Сложные структуры данных: планы / привычки / прогрессии
- Как система создаёт ячейки под более сложные структуры? Пример-полигон — **планирование**:
  - разные **варианты** одного плана (тренировочная программа для разных уровней сложности);
  - план **статичный vs цикличный/автоматичный**: цикличный трекает, что пользователь делает,
    и понемногу увеличивает нагрузку (**прогрессия**, настроенная для плана);
  - **задача vs привычка** — привычка повторяется очень разными способами;
  - **ветки** активности: пользователь композитно подключает себе готовые программы.
- Давняя идея владельца; обдумать именно на этом примере. Ограничения на старте допустимы —
  система и так должна уметь «Оооочень много».
- Ложится на уже спроектированное: control-plane (тип·линза·паттерн), умные категории,
  вариант=тип+линза, реактивность (класс №1 отсутствующий — «каждое утро…»), version/lineage-модуль.
  Это направление — их **стресс-тест реальным доменом**.

### D-G. Регламент делегирования и управления контекстом (мета-направление)
- Владелец требует: **Claude (Fable 5) сам много не анализирует** — запускает sonnet для анализа,
  opus при необходимости; пусть агенты сами продумывают организацию между собой по промпту.
- Роль сильной модели: **сложные/креативные/важные задачи (чётко в цель)** + управление процессом
  на максимально абстрактном уровне: не «глупый переключатель», а **держит глубокую мысль**, смотрит
  под разными углами, доводит продукт до идеала, **ищет подозрения и улучшения** — при этом сам
  потребляет минимум контекста (экономно, но креативно).
- Контекст не перегружать между агентами; самопроверка агентов — собой или через других
  (иногда дешевле чужим агентом, чтобы не забивать контекст исполнителя, у которого ещё есть задачи).
- **Это отдельная задача:** обдумать, явно структурировать и ЗАДОКУМЕНТИРОВАТЬ, чтобы отныне и система,
  и владелец понимали, как лучше делегировать. «Эта простая задача явно улучшила бы всю коммуникацию
  проекта и все дальнейшие взаимодействия».
- Формат работы: **сессия = одно направление** с заранее определённой структурой общения группы агентов.
