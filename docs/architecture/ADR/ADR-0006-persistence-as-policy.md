## Контекст

Фаза 1 (тонкий движок) упёрлась в развилку, которую все формулировали как **«файл ПРОТИВ базы»**: держать
истину в `md+frontmatter` (как сегодня) или в PostgreSQL? Развилка оказалась **ложной** — она смешивала два
разных уровня и заставляла выбирать глобально то, что глобально не выбирается:

- **Истина ЛОГИЧЕСКАЯ = сам граф** (узлы+рёбра, модель адресации `thing × actor × scope × lens × time`). Она
  **одна, всегда**. Это то, что переживает любую перекладку байтов.
- **Где узел лежит ФИЗИЧЕСКИ** (файл на диске / строка в PG / чанк в векторном индексе) — это **размещение**,
  свойство ТИПА узла, выражаемое ДАННЫМИ (`policy`-узел), а не хардкод и не глобальный закон.

Пока эти уровни слипались, спор «файл или база» был неразрешим: у file-first-истины (git, ручная правка,
портативность) и у DB-first-истины (запросы, масштаб, транзакции, множество производных индексов) РАЗНЫЕ
правы — потому что они отвечают на разные вопросы про РАЗНЫЕ типы узлов. Документ, который владелец правит
руками, и трейс агента на 10⁴ строк не могут иметь один физический дом по одному закону.

**Коррекция GPT-review (file 1 §1): «одна база» = ЛОГИЧЕСКАЯ, не физическая.** Не надо класть всё в одну
физическую таблицу или один движок. Скорее всего понадобятся несколько стораджей (event store · проекции
текущего состояния · graph index · vector index · blob · telemetry). Преимущество субстрата — **не `one
database engine`, а `one addressable model`**: единый ID-простор, единый envelope, провенанс, политики,
система типов, журнал операций — ПОВЕРХ возможно многих физических хранилищ.

**Рамка D-1 ратифицирована владельцем (2026-07-25).** Этот ADR **формализует** уже принятую рамку в
ратифицируемый storage-контракт: снимает ложную развилку, фиксирует «размещение = политика на тип»,
привязывает всё к одному инварианту-замку (в PG пишет только движок, риск R-2) и — по рекомендации
`axes-and-time §4.3` — **складывает сюда же битемпоральные поля конверта** (это их storage-ADR). Фаза
проекта — **дизайн**; сам код Фазы 1 не стартует, пока этот ADR не `approved` (см. Validation).

Опорой служит порядок арбитража из ADR-0005 — **Конституция > policy-as-data > integrity-as-engine-duty**:
размещение-на-тип есть прямое следствие средней опоры (правила живут ДАННЫМИ), а замок «пишет только движок» —
нижней (целостность — обязанность движка).

## Decision

**Persistence = policy-per-type.** Ниже — семь несущих правил (a–g) плюс складка битемпорального конверта (h).

### (a) Одна адресуемая модель над МНОГИМИ стораджами

Субстрат — **`one addressable model`**, а не `one database engine`. Единая логическая модель (граф) может
проецироваться на несколько физических хранилищ:

```
Единый логический knowledge plane (одна адресуемая модель)
├── event store            (канонический журнал acts[] — write-model истины)
├── current-state proj.    (свёртка acts → текущее состояние; сносимо и пересобираемо)
├── graph index            (инверсный индекс рёбер, обходы)
├── vector index           (pgvector — производная семантическая проекция)
├── blob / file storage    (крупный контент, вложения)
└── telemetry / cost       (замеры, трейсы, стоимость)
```

Их связывает в ОДНУ модель: **общие ID · единый envelope (10 полей ADR-0005) · провенанс · политики ·
система типов (`meta:type`) · журнал операций (`acts`)**. «Одна база» = это связывание, а НЕ один физический
движок. **PostgreSQL — главная по умолчанию**, но не самоцель: «одна физическая БД» как цель прямо отклонена
(см. Alternatives 2). В MVP Фазы 1 физически развёрнуто ДВА стораджа (`md+journal` + PG); остальные — по
факту боли, каждый за `StorePort` (Hexagonal, phase-1 §🧭), ядро о них не знает.

### (b) PostgreSQL = default (DB-first) · file-first = опт-ин на «человеческие» типы

Размещение — **настройка на тип** (`policy`-узел, ровно как существующий `knowledge.mode = embed|ref`):

- **DB-first (по умолчанию, в файлы НЕ сохраняем):** клиенты, клиенты клиентов, снапшоты, память агента,
  трейсы, телеметрия, сообщения, метрики, канонический журнал `acts`. Всё, что машинно-порождаемо, объёмно,
  запрашиваемо или чувствительно к масштабу.
- **file-first (опт-ин, «файл = истина»):** только «человеческие» типы — то, что владелец правит РУКАМИ и
  версионирует в git. Список — см. (g).

Размещение хардкодить в ядре запрещено (I-11 `violated when`): тип несёт policy-размещения как данные.

### (c) Файл = БАНДЛ узлов (не «1 файл = 1 узел»)

Файл — это **контейнер многих единиц**, ровно как сегодняшний `nodes.json` = 65 узлов в одном файле. «1
файл = 1 узел» **НЕ закон.** file-first-тип раскладывается по файлам-бандлам по смыслу (дом дока/модуля), а
адресность держится по `id`, а не по пути файла (I-1). Это разводит две дисциплины: **`doc-tree` закон №1
«файлы = истина» относится к ДЕРЕВУ ДОКУМЕНТОВ проекта** (где живут доки-артефакты, как этот ADR), **а не к
рабочим данным движка** (клиенты/трейсы/снапшоты). Конфликта между `doc-tree` и persistence-as-policy нет —
это два разных вещества (trace vs knowledge vs engine-data), и мы это фиксируем явно.

### (d) DB→file = ЭКСПОРТ по требованию (не двусторонняя синхронизация)

Портативность обеспечивается **экспортом среза графа в файл по требованию** (снять slice для git / переноса /
бэкапа), а НЕ постоянной двусторонней синхронизацией `file↔DB`. `ff-engine export <slice>` = материализация
проекции в файл; это одноразовая операция чтения, не живой мост. Обратная сторона (`import`) для DB-first
типов — тоже разовая (`load`), не непрерывный watcher. (Двусторонний sync отклонён — Alternatives 3.)

### (e) Правило-замок: в PG (канон) пишет ТОЛЬКО движок

**Единственный путь записи в PG/канон — через `resolve()`/`engine.write()`** (I-5, I-7; риск R-2). Прямой
SQL/debug-скрипт в обход `resolve()` минует ВЕСЬ capability-слой (D4 ADR-0004: мета-гейты `core:manage-*`),
доказанный killer-прогоном только на in-memory. Поэтому:

- сырой write в PG запрещён политикой и (позже) правами БД-роли движка;
- на производной read-model висит **staleness-маркер** (проекция может отставать от журнала → помечается,
  а не выдаётся как «свежая истина»); эффект eventual-consistency признаётся, не прячется;
- `rebuild --from journal` восстанавливает current-state с нуля (проекция сносима — I-5).

### (f) Write-path per stream (D-2) — следствие (b), не отдельная развилка

Кто пишет журнал ПЕРВЫМ — решается **per-поток политикой размещения**, а не глобально:

| Поток | Тип | Путь записи | Роль движка |
|-------|-----|-------------|-------------|
| **DB-first** (по умолчанию) | клиенты, снапшоты, память, трейсы… | `engine.write()` → `journal (acts)` → PG-проекция | **первый писатель** (API-first) |
| **file-first** (опт-ин) | доки, конфиги, промпты… | правка ФС → `journal` строится диффом (git-hook / fs-watcher) | **первый читатель**, не первый писатель |

Оба потока сходятся в **CQRS-lite**: канонический `acts`-журнал = **write-model истины** (append-only, I-3);
current-state = **read-model** (проекция, сносимо). Для file-first движок наблюдает ФС и поднимает акт; для
DB-first движок сам эмитит акт. Развилка «кто первый» перестаёт быть глобальной — её закрывает та же
политика-на-тип.

**Где физически живёт write-model — зависит от размещения-типа (разрешение I-5).** `invariants.md` I-5 был
намеренно смягчён: пункт «PG = read-model всегда» помечен PROVISIONAL до ЭТОГО ADR. Разрешаем явно:

- **file-first-типы:** `md+journal` = **write-model (истина)**; PG = производный **read-model**
  (пересобираемый, со staleness-маркером). Здесь верно CQRS-lite «md=write / PG=read».
- **DB-first-типы (по умолчанию):** **PG — физический дом ОБОИХ**: и append-only-журнала `acts` (write-model /
  истина), и проекции текущего состояния (read-model). Файлы — только export-on-demand (d). Здесь PG держит и
  ИСТИНУ тоже, а не только read-model.

Поэтому blanket-формулировка phase-1 README «md=write-model / PG=read-model» (CQRS-lite) **верна ТОЛЬКО для
file-first-типов**; для DB-first-типов PG держит и write-model. **Этот ADR разрешает provisional-клаузу
`invariants.md` I-5** (её хедж снимается). Универсальная часть I-5 — «текущее состояние есть ПРОЕКЦИЯ, не
второй источник истины» — держится для ОБОИХ путей: в обоих случаях current-state сносим и пересобираем из
журнала (см. (e), проверка 4).

### (g) Список file-first типов — СЕМЯ к ратификации (KQ-9)

> **MVP-правило разделения (несущее).** Типы, несущие **доступ / авторизацию / реестр / политику**, —
> **DB-first ТОЛЬКО, НЕ eligible для file-first.** Причина: file-first-путь строит журнал ДИФФОМ ФС (см.
> (f)) — на нём **нет `resolve()`/capability-проверки в момент записи**. Пустить такие типы через file-first =
> позволить редактору файлов молча переписать данные контроля доступа В ОБХОД capability-гейта. Это прямо
> нарушает **ADR-0004 D4** (мета-гейты `core:manage-access` / `core:manage-grants` / `core:manage-core` на
> плоскости управления). Поэтому такие типы ходят ТОЛЬКО через `engine.write()`→`resolve()`.

**DB-first ТОЛЬКО (никогда не file-first) — плоскость управления (ADR-0004 D4):**

| Тип (thing) / поле | Почему DB-first-ТОЛЬКО | Гейт ADR-0004 D4 |
|--------------------|------------------------|-------------------|
| **`meta:type` / `meta:pred`** — определения типов/предикатов | защищённый ядро-неймспейс реестра; растёт и плагинами/движком | `core:manage-core` |
| **`meta:cap`** — определения возможностей | минт возможности = плоскость управления | `core:manage-core` / `core:manage-grants` |
| **`policy`-узлы** — политики доступа/размещения | enforcement ниже линз, риск self-ref (KQ-3); правка мимо `resolve()` = privilege-escalation | `core:manage-core` |
| **любое поле `access` / `visibility`** на ЛЮБОМ узле | решает авторизацию само по себе | `core:manage-access` |
| **`grant`-узлы / capability-гранты** | выписывание прав | `core:manage-grants` |

Эти типы/поля **исключены из file-first при любом sign-off** — они не предмет KQ-9-торга, а следствие
ADR-0004 D4. Раньше (черновик) `meta:type/pred` (строка 7) и `policy` (строка 8) стояли в white-list
file-first с пометкой «напряжение / под вопросом»; ревью показало, что это не «низкая уверенность», а
**прямое противоречие** замку доступа — поэтому они перенесены СЮДА, а не оставлены обсуждаемыми.

**file-first (опт-ин) — только НЕ-access-bearing «человеческий» КОНТЕНТ.** Стартовый белый список — **seed,
ратифицируемый владельцем** (KQ-9), не финал. Важно: file-first покрывает **контент-тело** этих типов, но
**НЕ их capability/access-поля** — те всегда DB-first по правилу выше (напр. проза `agent`-манифеста —
file-first; поля `access`/грантов того же агента — DB-first):

| # | Тип (thing) | Почему file-first | Уверенность |
|---|-------------|-------------------|-------------|
| 1 | **`doc`** — документ/контент, что владелец правит руками | git-версионирование, ручная правка, портативность | высокая |
| 2 | **`config`** — конфиг модуля/топика (`config.json`, gateway) | правится руками, живёт рядом с кодом/деревом | высокая |
| 3 | **`prompt`** — промпт / каскад `PROMPT.md` | владелец редактирует голосом/текстом каждый ход | высокая |
| 4 | **`agent`-определение / паспорт** (проза манифеста, НЕ access-поля) | owner-authored манифест, ревьюится в git | высокая |
| 5 | **`adr` / `spec`** — сами доки-решения (как этот файл) | это артефакты дерева документов (doc-tree), не рабочие данные | высокая |
| 6 | **`lens` / `view-def`** (декларация, НЕ enforcement) — определение линзы/представления | owner-authored, декларативно, редко и вручную | средняя |

Всё, чего нет в этом белом списке, — **DB-first**. Финал контент-списка — за владельцем при sign-off (KQ-9);
DB-first-ТОЛЬКО-список — НЕ на торг (ADR-0004 D4).

**Fast-follow-условие (гейт перед включением file-first рядом с доступом).** Прежде чем file-first включён
для ЧЕГО-ЛИБО, что соседствует с access-плоскостью, должен существовать **гейт ВРЕМЕНИ ЗАПИСИ** (pre-commit /
CI-hook, проверяющий `core:manage-*` на защищённых полях ДО принятия правки). Пост-фактум-дифф журнала
**НЕДОСТАТОЧЕН** — он ловит нарушение уже ПОСЛЕ записи, когда контроль доступа уже переписан. До появления
этого write-time-гейта file-first ограничен строго типами 1–6 без каких-либо access/capability-полей.

### (h) Битемпоральный конверт — складываем СЮДА (storage-схема)

По рекомендации `axes-and-time §4.3` битемпоральные поля — это **storage/schema-решение конверта**, и их дом
= этот ADR.

> **Граница (h): что КОММИТИМ vs что ОТКЛАДЫВАЕМ.** Чтобы (h) не выглядел ответом на ещё открытые KQ-5/6/7,
> проводим черту явно:
>
> **(h) КОММИТИТ ровно два решения:**
> 1. **Аддитивность.** Любые temporal-поля вводятся как **аддитивные** (узел без них читается по дефолту, без
>    миграции данных) — та же additive-only-дисциплина, что в ADR-0004 D1.
> 2. **Опт-ин-по-типу.** Наличие valid-time объявляется **на типе** через `meta:type temporal: uni | bi`
>    (согласуется с (b) «политика на тип»); `recordedAt` (system-time) — **обязателен всегда**.
>
> **(h) ОТКЛАДЫВАЕТ форму (не пред-решает её):**
> - **нужна ли valid-time в v1 вообще** (только `recordedAt` vs реально включаем `bi`) — **KQ-5**;
> - **`recordedAt` только на акте** (а не на entity-конверте) — **KQ-6** (склонность — да, но подтверждается там);
> - **valid-time как интервал `[from,to)` vs точка+close-event** — **KQ-7**.
>
> jsonc ниже — **иллюстрация формы-кандидата под коммит №1–2**, а НЕ ратифицированная схема valid-time.

Склонность (leaning, не коммит): крепить temporal к **АКТУ**, а не к entity-конверту — акт неизменяем (I-4) и
append-only (I-3), поэтому битемпоральность «выпадает из лога даром», и не появляется второй источник времени;
финальное подтверждение — за KQ-6.

```jsonc
// элемент acts[] — существующие поля + аддитивный temporal-блок (форма-кандидат, KQ-7):
{
  "recordedAt": "2026-07-03T12:00:00Z", // system-time — REQUIRED, назначает движок, immutable
  "validFrom":  "2026-07-01",            // valid-time начало — OPTIONAL (умолчание = recordedAt)
  "validTo":    "2026-07-10"             // valid-time конец  — OPTIONAL (умолчание = ∞)
}
```

- **`recordedAt`** (system-time) — обязателен всем, пишет движок в момент append, не редактируется.
- **`validFrom` / `validTo`** (valid-time) — опт-ин **по типу**: `meta:type` объявляет `temporal: uni | bi`
  (согласуется с (b) «политика на тип»). `uni` = только system-time; `bi` = обе оси.
- **Аддитивность (без миграции данных):** узел без `validFrom/validTo` читается как `valid = [recordedAt, ∞)`.
  Отсутствие поля = дефолт — та же additive-only дисциплина, что в ADR-0004 D1.
- **Коррекция valid-time = НОВЫЙ акт (supersede), не мутация** (I-4): «на самом деле факт действовал 1–5, а
  не 1–10» → добавляем акт с `validTo:07-05` и большим `recordedAt`; старый акт остаётся как «во что верили».
- **ЗАКЛАДЫВАЕМ поля, НЕ движок запросов.** `as-of` / time-travel / компакция-snapshot — **отложены (D-5)**.
  Это forward-compat: координаты кладём, чтобы позже включить time-travel аддитивно (новая линза над теми же
  `acts[]`), а не переписывая конверт. Форма valid-time (интервал vs точка+close-event) — открыта, KQ-5/6/7.

## Alternatives considered

1. **Всё в файлах (md-first истина для всех типов).** Отклонено для DB-first типов: клиенты, снапшоты,
   трейсы, память агента, метрики не переживают ручной файловой раскладки — это машинные, объёмные,
   запрашиваемые данные; git-дерево из 10⁴ трейс-файлов = бардак и провал Q-7-масштаба. file-first оставлен
   как ОПТ-ИН на «человеческие» типы, не как глобальный закон.
2. **Всё в одной физической БД (один движок/одна таблица — самоцель).** Отклонено (GPT §1: логическое ≠
   физическое). Разным нагрузкам нужны разные стораджи (event store · graph · vector · blob · telemetry);
   насильно в один движок = либо неоптимально, либо невозможно (вектор/blob). Преимущество — `one addressable
   model`, а не `one engine`. PG остаётся ГЛАВНЫМ по умолчанию, но не единственным и не «целью».
3. **Постоянная двусторонняя синхронизация `file ↔ DB`.** Отклонено: два живых писателя = конфликты,
   гонки, «кто победил» и второй источник истины (нарушение I-5). Вместо этого — **экспорт по требованию**
   (d): один write-model (журнал), проекции сносимы, файл — разовый снимок среза, не живой мост.
4. **Битемпоральные поля на entity-конверте, а не на акте.** Отклонено: конверт-состояние — это проекция
   свёртки; авторитетное время на нём = второй источник истины о времени (риск рассинхрона, KQ-6). Поля
   крепятся к неизменяемому акту; конверт-`temporal` допустим лишь как денормализованная производная сводка.

## Consequences

**Что разблокируется (+):**
- **Ложная развилка «файл vs БД» снята.** Фаза 1 может стартовать: размещение — data-настройка на тип, а не
  архитектурный тупик. Store-адаптеры (`store-md` / `store-pg`) реализуемы параллельно за `StorePort`.
- **Одна адресуемая модель.** Общие ID/envelope/провенанс/политики/типы/журнал держат целостность ПОВЕРХ
  разных стораджей — рост числа индексов не плодит источников истины.
- **Портативность без связанности.** Экспорт среза в файл (git/перенос) — по требованию, не ценой живого sync.
- **Capability-safe (с оговоркой пути).** Замок «пишет только движок» сохраняет доказанный LSR/PEP-слой
  (ADR-0004) при переходе in-memory → PG; сырой SQL не обнуляет права. **Область действия:** это верно
  безусловно для **DB-first-пути** (всё через `resolve()`). **file-first-путь** capability-safe ТОЛЬКО при
  ограничении (g): (1) никаких access/registry/policy-типов на file-first (они DB-first-ТОЛЬКО, ADR-0004 D4)
  И (2) наличие fast-follow write-time-гейта на защищённых полях. Без этих двух условий FS-дифф-путь
  capability-safe НЕ является (у него нет `resolve()` в момент записи) — не заявляем обратного.
- **Битемпоральность заложена даром.** Immutable-лог (I-4) делает историю «во что верили / что было правдой»
  восстановимой без мутаций; поля готовы, движок включается позже аддитивно.

**Издержки / принятые минусы (−) — называем честно:**
- **Снапшоты и откаты НЕ бесплатны (GPT §4).** Быстрый доступ к прошлому состоянию потребует materialized
  views · snapshots · versioned reducers · replay-инфраструктуры · контроля совместимости событий. Replay
  длинных потоков дорожает → периодические snapshots (производная оптимизация поверх лога, не замена ему).
  Точнее: **историческая реконструкция заложена в фундамент; быстрые снимки — производная оптимизация.**
- **«Никаких миграций» — переоценка, смягчаем (GPT §3).** Мы убираем БОЛЬШУЮ ЧАСТЬ **физических миграций
  storage-schema** (новый тип/модуль = данные+конфиг, не DDL ядра — I-13). Но модель ВСЁ РАВНО эволюционирует:
  определения типов · правила валидации · индексы · projection templates · event schemas · контракты плагинов ·
  UI-представления · значения старых объектов · embedding-модели. Event-sourcing отдельно требует стратегии
  schema-evolution + backward-compat + тестирования проекций. Честная формулировка: **«эволюционирует модель,
  а не фундамент базы»** (не «миграций нет вообще»).
- **Два write-path (DB-first API · file-first FS-diff) = два механизма приёма.** file-first-журнал через
  git-hook/fs-watcher — живая деталь, её надо держать консистентной; движок как «первый читатель» ФС слабее
  гарантий, чем API-first (правка мимо watcher-а = пропущенный акт). Принято, ограничено опт-ин-типами.
- **Staleness-окно на read-model** (eventual consistency) — проекция может отставать; помечается маркером,
  но потребитель обязан это учитывать.
- **Операционная поверхность мульти-стораджа** (несколько хранилищ мониторить/бэкапить) — реальна, но
  отложена: MVP = только `md+journal` + PG; остальные стораджи — по факту боли, не заранее (анти-ossification).

## Validation plan

Как доказываем контракт (в духе walking-skeleton — на прогоне, не на слове):

1. **Вертикальный сценарий без per-step таблиц** (`vertical-scenario.spec.md`). 10-шаговый жизненный цикл
   одной вещи проходит через один envelope + один журнал + policy-размещение — БЕЗ заведения отдельной
   физической таблицы под каждый шаг. Если шаг требует новой таблицы ядра — persistence-as-policy провалена.
2. **Q-7 killer-прогон** (phase-1 DoD). 10³–10⁴ адверсариальных узлов на PG (после индексов + кеша грантов):
   `cost-tree` P95 ≤ 200 мс PASS / > 1000 мс FAIL. Доказывает, что DB-first-размещение несёт масштаб, а
   read-model-проекция не ломает права (resolve() внутри линз с capability-гейтом).
3. **Kernel-тест 1 `add-type`** (GPT). Добавить новый тип узла как ДАННЫЕ (`meta:type`+конфиг) — **без правки
   физических таблиц ядра** и без DDL. Старые узлы остаются читаемы (I-13). Провал = размещение зашито в код,
   не в policy.
4. **Kernel-тест 3 `rebuild-index`** (GPT). Снести current-state / graph-index / vector-index целиком и
   пересобрать из канонического журнала `acts[]` без потери знания (I-5, I-6, I-14). Доказывает: истина =
   граф/журнал, проекции — производные и сносимые.
5. **Замок R-2 — исполняемый тест** (`test/persistence-lock.test.ts`, в духе `run-capability.mjs` ADR-0004:
   один прогон, `exit 0` при корректном отказе). Тест ПЫТАЕТСЯ записать защищённое поле D4 двумя путями и
   утверждает, что ОБА отбиты/зафлагованы:
   - **(a) сырой SQL в обход `resolve()`** — прямой write в PG-канон по роли-движка → должен быть **REFUSED**
     политикой/ролью БД (не молча применён);
   - **(b) FS-правка DB-first/защищённого типа** — Edit по `md` файлу типа из «DB-first-ТОЛЬКО» списка (g)
     (напр. `policy`-узел или поле `access`) → FS-дифф-путь должен **отказать/зафлагать** (write-time-гейт),
     а не поднять акт молча.
   Ассерт: обе попытки refused/flagged → `exit 0`; любая прошедшая молча → FAIL. Дополнительно: на read-model
   присутствует staleness-маркер; `rebuild --from journal` восстанавливает проекцию с нуля. *(NB: пункт (b)
   требует наличия fast-follow write-time-гейта из (g) — до него подпроверка (b) стоит как запланированный
   DoD-гейт, а не «зелёная сегодня».)*
6. **Битемпоральная аддитивность.** Узел без `validFrom/validTo` читается как `[recordedAt, ∞)`; коррекция
   valid-time = новый superseding-акт, старый не стёрт (I-4); reducer берёт по valid-интервалу акт с
   максимальным `recordedAt`. (Проверяется на форме, не на as-of-движке — он отложен D-5.)

**Критерий выхода `proposed` → `approved`:**
1. **Ратификация владельцем** текста этого ADR (рамка D-1 уже принята 2026-07-25; здесь — контракт целиком).
2. **Финализация списка file-first типов** (g) владельцем — закрывает KQ-9.
3. **Проверки 1–6 зелёные** на реальном прогоне Фазы 1 (или явно запланированы как DoD-гейт кода). В частности
   — не только 1–4: **проверка 5 (замок-write-lock)** — центральное утверждение безопасности этого ADR, её
   пропуск = гейт не пройден; **проверка 6 (битемпоральная аддитивность)** подтверждает форму под коммит (h).

> Пороги/строки правятся как ДАННЫЕ (policy-узлы/линты), не как код (опора #2 ADR-0005). Проверки 3/4 —
> кандидаты в постоянный CI-прогон рядом с `concept-lint` (опора #3).

## Открытые вопросы

Не закрываются этим ADR — маршрутизированы в реестр ядра:

- **KQ-9 · file-first type list** — стартовый список (g) = seed; финал за владельцем при sign-off. 🔴 гейтит
  всю тему хранения и опт-ин типов.
- **KQ-5 · bitemporal в v1?** — `recordedAt`-only vs per-type `temporal: uni|bi`; склонность к опт-ин по типу.
- **KQ-6 · `recordedAt` только на акте?** — подтвердить, что entity-конверт НЕ несёт собственного
  авторитетного времени (иначе второй источник истины о времени).
- **KQ-7 · valid-time: интервал `[from,to)` vs точка + close-event** — форма хранения; влияет на reducer и
  будущий as-of-движок; кандидат в под-запись этого ADR.
- **KQ-8 · что считается deletion** (tombstone-act / projection-hide / physical erase) — пересекается с
  persistence + consent-erasure (ADR-0005 F6); держим связанным.
- **KQ-3 · policy self-reference** — можно ли править policy тем же `resolve()`, которым она управляет; именно
  этот риск и есть причина, по которой (g) относит `policy`-узлы к **DB-first-ТОЛЬКО** (бывшая строка 8
  file-first перенесена), а не оставляет их редактируемыми файлом.
