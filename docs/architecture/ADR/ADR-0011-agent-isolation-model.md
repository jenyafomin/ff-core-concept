## Контекст

**Почему изоляция несущая (а не деталь развёртывания).** Три независимых артефакта design-wave сошлись
(`02:57-78`, `03` F1 CRITICAL, `04 §2`): модель изоляции — это gating variable, от которой зависит ВСЁ
остальное в модели доверия принципала:

1. **Она решает, станут ли варианты A/C источника принципала (ADR-0010 ③) когда-либо РЕАЛЬНОЙ границей.**
   In-process границы НЕТ: плагин, загруженный через `require()`, неотличим от first-party-кода; ocap-handle
   подделываем через общий object graph (`03:67-80`). A/C становятся барьерами только там, где есть
   process/realm-барьер. Без него A/C — ярлыки-конвенции, «theatre», что уже отвергнуто (`ADR-0010:113-114`,
   `02:82-112`).
2. **Она решает, ОБЯЗАТЕЛЕН ли вариант B (крипто-аттестация).** Недоверенный транспорт ⇒ достаточен только
   самоверифицируемый маркер. Локальная process-граница ⇒ channel-trust (A) честен и дёшев.
3. **Она — скрытая посылка северной звезды.** VISION — hub с подключаемыми подсистемами/плагинами; ADR-0010
   называет северной звездой «плагинные/потенциально враждебные агенты по недоверенному транспорту»
   (`ADR-0010:49-50`). Это УЖЕ неявный выбор изоляционной модели. Marketplace-vision и trust-модель нельзя
   развести — этот ADR делает выбор явным.

**Ground truth сегодня (analyst, `02`).** 100% вызывающих `engine.write()` — **in-process**: `ingest-rentacar`,
`rental-balance` ingest, `BalanceObserver`, `DurableRunner` — все конструируют/получают тот же экземпляр
`Engine` и зовут `.write()` обычным вызовом метода в одном адресном пространстве. Ни HTTP, ни IPC, ни очереди,
ни RPC-границы в коде НЕТ. **Аутентифицированного источника личности не существует нигде** — каждый
`actor`/`viewer` это либо compile-time-литерал, либо неваидированная строка из CLI-флага/фикстуры
(`02:34-39`). `ViewerResolver` (read) и seam M5 (write) — 100% не построены. CLI `write` — мёртвый stub.

**Что уже зафиксировано и НЕ переоткрывается здесь (ADR-0010).** Инвариант ① (авторитет никогда из тела) —
approved. Форма ② (`Act.principal?: PrincipalAssurance`, пер-осевое доверие + issuer + слот делегации) —
approved/зарезервировано-в-коде, аддитивно, `write(act): Ack` заморожен. Поведение ③ (выбор источника A/B/C +
enforcement) — open, отложено. Этот ADR отвечает на вопрос, который ③ держал открытым как prerequisite: **где
сидит граница доверия** — потому что от этого зависит, что вообще значит «аутентифицированный принципал».

**Первый реальный инстанс ISO-2 уже запланирован.** Шлюз `agents-manager` УЖЕ работает по модели «каждый ход =
свежий `claude -p --resume`» (project `CLAUDE.md`; `durable-runner.ts:4-15`). На M3 он станет первым вызывающим
`engine.write()` через границу процесса (`engine-client.ts:2` «agents-manager at M3»). ISO-2 — не гипотеза,
это ближайшая реальность кодовой базы.

Опора — порядок арбитража ADR-0006: **Конституция > policy-as-data > integrity-as-engine-duty**. «Где проходит
граница доверия принципала» — долг движка/хоста (integrity-as-engine-duty), не политика-на-тип.

## Decision

### Ветки (design-ready, из `04-SYNTHESIS §2`)

| | **ISO-1 — in-process навсегда** | **ISO-2 — out-of-process, та же машина** | **ISO-3 — недоверенный транспорт** |
|---|---|---|---|
| Что это | плагин = импортируемый npm-модуль, общий V8-heap | плагин/агент = отдельный процесс/воркер, IPC-граница | удалённые плагины, marketplace по сети |
| Trust-модель | runtime-границы НЕТ; безопасность = vetting/supply-chain; A/C = ярлыки | **A реален**: хост-процесс = владелец шва, штампует принципала по IPC (аналогия `thread_id`/`uid`); C = handle-через-IPC = настоящий ocap | **B обязателен** (маркер валиден вне зависимости от пути вызова); + делегация; + ключевая инфра |
| Decision ③ при ветке | «enforce нечего — честно не притворяться» | A≡C у IPC-границы; B — позже как порог для привилегированных namespace | B минимум для cross-host; A/C недостаточны |
| Цена | 0 сейчас, весь риск в supply-chain | процессная модель + IPC-протокол; первый инстанс = шлюз M3 | ключи/ротация/issuer-инфра |

### РЕШЕНИЕ — траектория **ISO-2 → ISO-3** (ISO-1 отклонён)

**ISO-2 (сейчас — целевая граница).** Единица кода-агента/плагина исполняется в ОТДЕЛЬНОМ процессе/воркере;
взаимодействие с движком идёт через **IPC-границу**, не через общий heap. **Хост-процесс = ВЛАДЕЛЕЦ ШВА:** он
аутентифицирует сессию/канал и ШТАМПУЕТ принципала на пересечении IPC (drop-and-re-stamp тела акта, `01`
Resolver+Stamper), ровно как шлюз ставит `thread_id`, а ядро ОС — `uid` (`ADR-0010:45-46`). Заявленный `Act.actor`
из-за границы = **атрибуция-данные**, никогда не основание авторитета (инвариант ① ADR-0010).

**Первый конкретный инстанс: шлюз `agents-manager` на M3.** Каждый Telegram-ход = отдельный OS-процесс
(`claude -p --resume`), вызывающий `engine.write()` через границу. В этот момент A (доверенный канал) перестаёт
быть theatre естественно: появляется реальная граница, за которой сидит вызывающий, чью личность хост
проставляет, а не принимает на веру из тела.

**ISO-3 (позже — ПРЕДВАРИТЕЛЬНЫЙ эндстейт, пересматривается).** Когда плагины приходят по НЕдоверенному
транспорту (сеть, marketplace), channel-trust недостаточен: нужен самоверифицируемый маркер, валидный
независимо от пути вызова ⇒ **B (крипто-аттестация) становится обязательным** + делегационная цепочка +
ключевая инфра. Форма под B уже зарезервирована (② ADR-0010, `PrincipalAssurance.issuer` + слот делегации,
`types.ts`) — ISO-3 не требует смены конверта, только реализации. **Оговорка (провокация 4a):** «ISO-2 сейчас»
твёрдо; ISO-3 — предварительный эндстейт, **пересматриваемый, если сроки/форма marketplace изменятся**. Charter
или Spec под marketplace ещё НЕ существует (только VISION-намерение) — потому будущая сессия НЕ должна трактовать
ISO-3 как предрешённую реализацию. Зарезервировано направление и форма, не обязательство построить ISO-3 к дате.

**ISO-1 отклонён** (не «отложен») как несовместимый с северной звездой: враждебный плагин в общем heap не
сдерживается ничем, A/C сводятся к ярлыкам. Детали — §Альтернативы.

### Что ISO-2 разблокирует для Decision ③ (ADR-0010)

- **У IPC-границы A≡C становится РЕАЛЬНОЙ границей, а не theatre.** Растворение под-развилки из design-wave
  (`ADR-0010 §③-bis`): `submit(id, act) ≡ makeEngineClient(resolve(id)).write(act)` — один механизм
  (Resolver → Stamper → frozen `write()`) на двух временах жизни принципала (per-write vs per-session). Настоящая
  ось — время жизни, не «A против C». ISO-2 даёт место, ГДЕ этот механизм имеет силу.
- **B остаётся отложенным как ПОРОГ.** B нужен не для локальной IPC-границы, а как порог для привилегированных
  namespace / cross-host (ISO-3). До этого порога — A/C у границы.
- **Секвенс (G2 ADR-0010):** **ADR-0011 → M5 (surface-identity resolution, форма которого зависит от того, ГДЕ
  граница) → enforcement-флип Decision ③.** Выбор A/B/C не производится до ратификации этой модели изоляции.

**Форма M5 зависит от выбора границы.** «Surface identity» — это ЧТО именно: Telegram-uid через шлюзовой IPC?
OS-идентичность процесса? Ответ определяется тем, ГДЕ проходит граница ISO-2 — потому этот ADR обязан
предшествовать M5, а не наоборот.

### Guardrail G4 (CRITICAL) — легитимность владельца шва сама есть зарезервированная форма, не допущение

Продолжает G-серию ADR-0010 (`ADR-0010 §③-bis`, G1/G2/G3). ADR резервирует форму ВЕЗДЕ, кроме СОБСТВЕННОГО
авторитета хост-штампующего. Названы 3 прогнозных хоста (шлюз M3 / будущий HTTP / будущий CLI) — каждый
односторонне стал бы владельцем шва без кросс-хостовой согласованности и без аудит-следа самогО акта штампа.
Это ровно та ретрофит-невозможность, ради предотвращения которой существует ADR-0010, на уровень выше:
append-only журнал + `principal.issuer:"agents-manager"` при trust>unverified = навсегда.

> **G4 — легитимность владельца шва сама есть зарезервированная форма, не допущение.** Форма Resolver/Stamper
> на M5 ОБЯЗАНА зарезервировать поле-аналог `seamAuthority` / `policy_source` (issuer-of-the-issuer: кто
> авторизовал ИМЕННО ЭТОТ хост штамповать) ДО того, как приземлится любой код. Enforcement НИКОГДА не вправе
> считать «хост вызвал stamp()» достаточной авторизацией. Ноль поведения сейчас; резерв поля ретрофит-дёшев,
> добавить его ПОСЛЕ того, как акты зажурналированы, — невозможно.

**Категорийная страховка (провокация 4b):** `principal.issuer` (② ADR-0010) — это КТО ПРОСТАВИЛ штамп
(атрибуция шва), его НЕЛЬЗЯ читать как АВТОРИТЕТ-хоста-штамповать. Это тот же разрез актор≠принципал /
атрибуция≠авторитет, что ADR-0010 закрыл на уровне акта, здесь повторённый на уровне ШВА: «кто штампанул» ≠
«кто дал право штамповать». Первое — `issuer` (есть). Второе — `seamAuthority` (G4, резервируется). Смешать их
= рецидив класса дыры ADR-0010 одним уровнем выше.

**OQ-1 (governance владельца шва) ПОВЫШЕН из parked-prose в guardrail G4.** Ниже в §Открытые вопросы он
оставлен как повестка проектирования, но его retrofit-невозможная ЧАСТЬ (резерв поля) теперь — обязательство
G4, не «на будущее».

## Альтернативы (рассмотрены)

- **ISO-1 — in-process навсегда.** **Отклонено.** Враждебный/сторонний плагин в общем V8-heap неконтейнируем:
  `require()`-загруженный модуль неотличим от first-party-кода; любой ocap-handle подделываем через общий object
  graph (`03:67-80`); A/C = метки-конвенции, не барьеры. Северная звезда (подключаемые/потенциально враждебные
  агенты, VISION + `ADR-0010:49-50`) при ISO-1 недостижима в принципе — безопасность свелась бы к supply-chain-
  vetting, что не масштабируется на marketplace третьих сторон. Отклонён как направление, не отложен.
- **ISO-1.5 — capability-based in-process изоляция (middle path).** **Рассмотрено, не выбрано как эталон;
  конкретный транспорт отложен до M5.** Между ISO-1 (голый общий heap) и ISO-2 (отдельный OS-процесс + IPC) лежит
  промежуточный класс: изоляция ВНУТРИ процесса capability-средствами — `worker_threads` со structured-clone
  границей сообщений, SES-закалённые realms (заморозка intrinsics, endowment-only), или `vm.Context`. Она дешевле
  (нет процессного оверхеда, IPC-сериализации, lifecycle воркеров) и уже даёт часть барьера: worker не делит
  object graph напрямую (structured-clone рвёт живые ссылки), SES отнимает ambient authority. **Почему НЕ эталон:**
  против враждебного плагина гарантии слабее — `worker_threads` делит память через `SharedArrayBuffer` и уязвим к
  side-channel/ресурс-exhaustion в общем runtime; SES/`vm` исторически обходятся (realm-escape, prototype-
  pollution через утёкшие intrinsics). Жёсткая process/OS-граница даёт containment на уровне ядра (отдельное
  адресное пространство, killable, cgroup-лимитируема) — сильнейшее сдерживание против hostile-plugin-угрозы
  северной звезды, и потому она — ЭТАЛОННАЯ модель ISO-2. **Конкретный выбор транспорта (worker vs
  child_process/OS-process vs SES-realm) отложен до M5** и может варьироваться по классу плагина (доверенный
  first-party агент → worker достаточно; сторонний плагин → hard process). ISO-1.5 — допустимая ОПТИМИЗАЦИЯ под
  доверенные единицы, не замена эталонной границы для недоверенных.
- **ISO-3-first (сразу крипто/сеть, минуя ISO-2).** **Отклонено как преждевременное.** Строить ключевую
  инфру/issuer/ротацию (B) ДО того, как существует хотя бы одна работающая граница процесса и штампующий её
  хост — значит возводить дорогую крипто-надстройку над несуществующим швом. Ground truth (`02`): нет ни
  границы, ни источника личности. B без ISO-2 негде проверять и незачем — как строить турникет до того, как
  построена стена. ISO-2 — обязательная ступень, на которой B обретает смысл.
- **Оставить как «Открытый хвост» ADR-0010 (не решать).** **Отклонено.** Design-wave (`03` F1 CRITICAL) показал:
  это не заметка, а gating variable — форма M5 и осмысленность Decision ③ висят на ней. Оставить нерешённой =
  строить M5/③ на нефиксированной посылке (риск G2).

## Последствия

- **(+)** A/C становятся РЕАЛЬНОЙ границей у IPC-шва (не theatre) → write-плоскость сможет перестать быть
  authority-blind в момент, когда появляется настоящий вызывающий (шлюз M3), а не искусственно.
- **(+)** Открывается путь к marketplace/plug-in северной звезды: ISO-2 — обязательная ступень, ISO-3 достраивает
  её реализацией B поверх уже зарезервированной формы ② (0 миграций конверта).
- **(+)** Секвенс проясняется: ADR-0011 → M5 → ③; выбор A/B/C привязан к месту границы, не угадывается заранее.
- **(−)** Процессная модель + IPC-протокол — реальная инженерная работа (сериализация актов, backpressure,
  lifecycle воркеров), которой сегодня нет.
- **(−) Шлюзовая IPC-граница обязана быть надёжно закалена — это ЖЁСТКОЕ ТРЕБОВАНИЕ, не сноска.** Баги
  dup/restart (`gateway-dup/INDEX.md`, память `gateway-dup-kill-bug`) сегодня: дубль голосового убивает фоновых
  агентов и приходит без ответа. Если хост-процесс = владелец шва, штампующий принципала, то дубль/рестарт =
  двойной/потерянный штамп принципала на append-only акты → отравление журнала. Надёжность границы (ровно-один-
  раз доставка хода, идемпотентность рестарта) — предусловие ISO-2, не отдельная забота эксплуатации.
- **(−) Governance владельца шва + портируемость trust-истории между хостами — ОТКРЫТЫЕ вопросы, паркуются
  ЗДЕСЬ** (остаток V5 Суверенность из design-wave, `04 §4`, `03` F4). См. §Открытые вопросы.
- **Координация:** ISO-2 меняет то, КАК вызывающие (agents-manager M3, будущий HTTP, CLI) достигают движка —
  через IPC + хост-штамп, а не прямой вызов метода. Планируется через аддитивную форму ② (без смены сигнатуры
  `write()`), но требует нового транспортного слоя вокруг `EngineClient`.

## Открытые вопросы (паркуются в этом ADR — остаток V5 Суверенность)

Перенесены сюда из design-wave осознанно (`04 §4`: «не решается там — вход изоляционного ADR»):

- **OQ-1 — Governance владельца шва (retrofit-невозможная часть ПОВЫШЕНА в G4).** Кто вправе БЫТЬ
  хост-процессом, штампующим принципала? По какому авторитету (аналог `policy_source`/`seamAuthority`)?
  Централизация этого авторитета преждевременно нарушила бы V5 Суверенность — потому СЕМАНТИКА остаётся открытой
  повесткой M5. Но retrofit-невозможная часть — РЕЗЕРВ поля `seamAuthority` до кода — теперь обязательство
  guardrail G4 (см. Decision), не «на будущее».
- **OQ-2 — Портируемость trust-истории между хостами** (`03` F4). Если единица переезжает между хостами
  (устройствами/развёртываниями), как переносится её накопленная trust-история, не теряя и не подделывая
  атрибуцию? Особенно остро на переходе ISO-2 → ISO-3.
- **OQ-3 — Гранулярность границы.** Один процесс на плагин? На агента? На ход (текущая шлюзовая модель)? На
  сессию? Влияет на время жизни принципала (per-write vs per-session, `01` A≡C) и на цену IPC.
- **OQ-4 — Надёжность как контракт границы.** Формализовать требование ровно-один-раз/идемпотентного штампа
  (следствие dup/restart-багов) как явный контракт IPC-шва до постройки ISO-2.

Эти вопросы НЕ блокируют ратификацию направления ISO-2→ISO-3; они — повестка M5-сессии и проектирования
IPC-шва.

## План валидации (что доказывает, что граница РЕАЛЬНА)

Привязан к адверсариал-гейту ADR-0010 (`ADR-0010:175-187`) — тесты-ЦЕЛИ, красные до enforcement по построению:

1. **Cross-IPC forge-actor.** Вызывающий из-за IPC-границы (напр. воркер плагина/шлюзовой ход) НЕ может подделать
   ЧУЖОГО принципала: что видит PEP — это принципал, проштампованный ХОСТОМ, а не поле `actor` из тела акта.
   Прямое расширение `forge-actor`-гейта ADR-0010 на out-of-process-путь: `mallory` в отдельном процессе ставит
   `actor:'user:admin'` → хост-штамп перебивает → PEP гейтит по штампу → **REFUSED** (сегодня: эскалирует — тест
   обязан быть КРАСНЫМ до M5/enforcement, это открытая цель, не регрессия).
2. **Штамп хоста — единственный источник для PEP.** Ни один путь (включая IPC) не даёт PEP консультировать сырой
   `actor` из тела; только производную `authority` из проштампованного `principal.*` (guardrail G1 ADR-0010,
   REFUSE-не-rewrite).
3. **Граница отличима от in-process.** До-ISO-2 in-process-акты читаются как `unverified`; акты через
   штампующую IPC-границу несут ось-доверие + issuer (проверяемо через аудит-читаемость, `ADR-0010:184`).
4. **Идемпотентность рестарта (следствие OQ-4).** Дубль/рестарт хода не порождает двойной противоречивый штамп
   принципала на один логический акт (защищает append-only журнал от dup/restart-отравления).

Пункты 1–3 наследуют от гейта ADR-0010; пункт 4 — специфичен для ISO-2 и связан с надёжностью границы.

**Предусловия enforcement-флипа (нумерованные гейты, не проза):**
- **P-1.** Ратифицирован ADR-0011 (эта запись) → построен M5 (surface-identity под ISO-2-границу).
- **P-2 (из OQ-4, F-A).** Enforcement-флип ТРЕБУЕТ связанной, ВЕРИФИЦИРОВАННОЙ починки бага dup/restart шлюза
  (`docs/01-organization/process/bugs/gateway-dup/INDEX.md`, кросс-репо `agents-manager`) — простого признания
  этого ADR НЕДОСТАТОЧНО. Двойной/потерянный штамп на append-only журнал = ровно то перманентное отравление, о
  котором предупреждает ADR; сегодня ничто структурно не мешает флипнуть enforcement при живой багованной
  границе. Флип заблокирован до линка на верифицированный fix.
- **P-3.** Зарезервировано поле `seamAuthority` (G4) — enforcement не вправе стартовать без него.
- **P-4.** Явный кивок владельца (как в ADR-0010).

Включение enforcement — отдельный кивок владельца (после ADR-0011 → M5), как и в ADR-0010; все P-1…P-4 должны
быть зелёными.

## Самокритика (adversarial, до ратификации формы)

- **«ISO-2 решает границу до того, как есть код границы — не преждевременно ли, как ISO-3-first, который сам же
  отвергает?»** Разница: ISO-3-first требует строить дорогую крипто-ИНФРУ до шва. ISO-2-как-РЕШЕНИЕ ничего не
  строит — это ADR-текст, выбор направления, ноль кода (как D2 в `04 §5`). Он лишь фиксирует ГДЕ будет граница,
  чтобы M5 не спроектировали под неверную посылку. Стройка ISO-2 наступает не раньше M3-интеграции шлюза,
  которая и так запланирована. Риск преждевременности снят тем, что решается направление, а не реализация.
- **«Шлюз M3 назван первым инстансом, но analyst показал: сегодня шлюз НЕ вызывает `engine.write()` вообще
  (`02:32`, только forward-looking-комментарии).»** Верно и учтено: M3 — БУДУЩЕЕ, ADR фиксирует траекторию, а не
  наличный код. Именно поэтому Status = proposed и Validation-тесты помечены как красные-по-построению. ADR
  описывает, куда идём; отсутствие кода сегодня — не контраргумент к выбору направления, а причина решать его
  ДО стройки.
- **«Надёжность шлюза (dup/restart) — не делает ли она ISO-2 нежизнеспособным?»** Нет — и это осознанный разрез
  (`04 §2`, оговорка Fable): баги надёжности — ВХОД в ADR (требование OQ-4 к границе), не причина выбрать ISO-1.
  ISO-1 не имеет этих багов лишь потому, что не имеет границы вовсе — но и не даёт trust-модели. Правильный ответ
  — закалить границу, а не отказаться от неё.
- **«ISO-2 vs ISO-3 — это точно две ступени, а не ложная дихотомия?»** Возможный контр-сценарий: часть плагинов
  сразу удалённые (ISO-3), минуя локальный ISO-2. Ответ: траектория — про ПОРЯДОК ПОСТРОЙКИ инфры, не про запрет
  сосуществования. Первая реальная граница (шлюз, локальная) — ISO-2; B-инфра достраивается, когда появляется
  недоверенный транспорт. Форма ② A/B-нейтральна, так что ранний удалённый плагин не ломает конверт — только
  требует B раньше. Это ускорение по той же траектории, не другая ветка.
- **«Не переоткрывает ли этот ADR инвариант/форму ADR-0010?»** Нет: инвариант ① и форма ② не трогаются. ADR-0011
  отвечает строго на prerequisite-вопрос Decision ③ (G2) — ГДЕ граница — и явно оставляет enforcement отложенным.
- **Остаточная слабость (честно):** governance владельца шва (OQ-1) и портируемость trust-истории (OQ-2) не
  решены — только локализованы. Если marketplace-давление придёт раньше M5, эти открытые вопросы станут
  критическим путём быстрее, чем этот ADR предполагает. Приняты как осознанный остаток V5, не как решённое.

## P-5 (added 2026-08-12)

**Аддитивная регистрация пятого предусловия enforcement-флипа.** Раздел «Предусловия enforcement-флипа»
выше (P-1…P-4) расширяется P-5 — без удаления/переписывания P-1…P-4. Введён Fable-форком decision-4

`docs/00-states/05-assemble-and-direct/_shared/topics/03-actor-model/m5-surface-identity/design/06-enforcement-precondition-map.design.md`.

- **P-5 — вне-полосный КОРЕНЬ ДОВЕРИЯ `seamAuthority` назван + заполнен.** Enforcement-флип ③ ТРЕБУЕТ,
  чтобы вне-полосный якорь, удостоверяющий право хоста штамповать (issuer-of-the-issuer, G4), был:
  (1) **назван** как механизм — Constitution-class защищённый узел `policy:seam-authority`
  (`protected_namespaces`, `can_write: []`), читаемый движком как *клэмп* оси доверия (переиспользование
  ADR-0004 D3 + арбитраж ADR-0006), физический дом = `$FF_ENGINE_HOME/trust/`, engine-principal-owned;
  (2) **заполнен** владельцем ВРУЧНУЮ (TOFU отклонён — самоудостоверение = запрещённый паттерн); и
  (3) **write-канал верифицированно НЕпересекается** ни с одним путём, куда может писать разрешаемый
  агент-юнит (T-seed), + решён scope реестра project-vs-platform (T-scope) — обе части через критик-пасс.
  **Флип ③ не вправе зеленеть, пока P-5 красный.** Это превращает «defer корня» из умолчания в ГЕЙТ:
  пока корень не заполнен, каждый штамп честно несёт `unverified` («seam authority not vouched»).

**Секвенс P-5 (Fable §2, не переоткрывает P-1…P-4):** decision-4=C **назвать** корень (бумага, сейчас) →
P-2-фикс параллельно → **isolation uid-split** (даёт «агент не может писать корень» ЗУБЫ вместо конвенции) →
**заполнить** корень (P-5→green) ТОЛЬКО после P-2 ∧ uid-split → флип ③ (P-1…P-5 + кивок владельца P-4).
Ничто не зависит от B (ISO-3-крипта).

**Честный предел P-5 (owner-facing):** под сегодняшней same-uid ISO-2-реальностью (движок и `claude -p`-child
= один OS-uid, in-process) файловая граница = конвенция, не enforcement — потому часть «write-канал disjoint»
**НЕтестируема до isolation uid-split**. Заполнять корень (green) до uid-split = удостоверять хост, который
двойно штампует за несуществующей границей. P-5 сцеплен с P-3 (`seamAuthority`-резерв, spec 05): P-3 резервирует
ФОРМУ поля, P-5 наполняет её ДОВЕРИЕМ — разные предусловия, не путать.
