# ADR-0015 — Edge identity (тождество ребра, форк D4)

## Статус
**proposed** — ждёт ратификации владельца. Лёг на диск как решение-запись (чтобы не потеряться), enforcement/стройка — по «строй».
Явно: **этот ADR СТОИТ на ADR-0014, который сам `proposed` (НЕ ратифицирован).** Если ADR-0014 будет отклонён/переписан, пересмотреть §Decision здесь. Форма (поля на `Edge`) от ADR-0014 не зависит и безопасна при любом его исходе; зависит только рамка «рёбра-как-данные-того-же-ранга».

## Контекст

### Почему СЕЙЧАС (retrofit-impossible, единственное «невозможно потом» этой ночи)
Журнал актов (`Act.edges`) — **append-only, источник истины** (ADR-0008). Граф (`EnvelopeNode.edges`) — **перестраиваемый read-model** (`project()` = свёртка журнала). Проверено на боевых данных:
- `packages/engine/.data/day-graph/journal.jsonl` — 30 актов, ~11 несут рёбра; `packages/engine/.data/day-mirror/journal.jsonl` — 9 актов.
- Форма журналированного ребра сегодня: `{"predicate":"involves","target":"person:Женя","provenance":"day-graph:2026-08-21"}` — **у ребра НЕТ поля `id`. Ни одного.**

Интерфейс `Edge` (types.ts:32-51) не имеет поля тождества вообще. Ребро сегодня идентифицируется **позиционно**: тройкой `(владеющий-узел = source_ref акта, predicate, target)`. `foldEdges` (predicates.ts) дедупит по `(predicate, target)` для `many` и по `(predicate)` для `one`. То есть у ребра НЕТ паспорта — оно служебная нить, а не память своего ранга.

### Ценностный драйвер
- **Ц6 Реляционность** (канон `_CARDS-2026-07-08.md`): ребро — память ТОГО ЖЕ РАНГА, что и узел: свой `id`/паспорт/`confidence`/`stale`, ссылочная целостность (не плодить сироты-рёбра). Сегодня ребро низведено до служебной нити — прямое нарушение Ц6.
- **Ц2 Тождество**: «меняем не теряя себя» — тождество переживает смену/вариант/слияние. Для ребра это значит: у ребра должна быть идентичность, переживающая ретаргет/merge/split.

### Что именно retrofit-impossible (честно, без переоценки)
Разложим на два вещества (это ядро решения):

1. **Производный АДРЕСНЫЙ ключ ребра (`id`)** — детерминированная функция от текущего содержания ребра. **НЕ retrofit-impossible**: вычислим по журналированному содержанию в любой момент, на каждом историческом ребре, с НУЛЁМ миграции. Это «дешёвое сейчас».

2. **Стабильная идентичность, переживающая изменение (`canonical_id`)** — способность сказать «ребро E1 (…→A) и E2 (…→B после ретаргета) — ОДНО ребро, которое переехало». Это **retrofit-impossible в строгом смысле**: связка «одно ребро сквозь изменение» в журнале никогда не записывалась → её нельзя восстановить постфактум. Чтобы будущие рёбра МОГЛИ нести такую идентичность, СЛОТ должен существовать на момент записи. Исторические рёбра его не имели — и это честный факт, а не баг.

Это ровно тот же класс, что уже решён в проекте Reserved-Form-ом: `Act.principal` (ADR-0010 §② — пре-шовный акт не отличить от пост-шовного без слота) и `HashScheme` (ADR-0007 — версия схемы заложена ДО первой боевой PII). **Единственная односторонняя дверь этой ночи — заложить СЛОТ тождества ребра в форму до того, как журнал накопит историю.**

## Решение

Применяем **принцип Reserved-Form (ADR-0010 §②, Закон ①): резервируем ФОРМУ тождества сейчас, откладываем ПОВЕДЕНИЕ (merge/split/каскад/enforcement).** Форма — два поля на `Edge`, аддитивно-опциональных (0 миграций), плюс одна чистая функция вывода id. Ноль поведения, тривайр-тест фиксирует «не enforced» в коде.

### D1 — Два поля тождества на `Edge` (аддитивно, опционально)

```
interface Edge {
  predicate: string;
  target: string;
  // ... существующие: meta?, provenance?, validFrom?, validTo?, subjectRole? ...
  id?: string;            // RESERVED-FORM: производный content-addressed ОТПЕЧАТОК (адресный ключ)
  canonical_id?: string;  // RESERVED-FORM: стабильная идентичность (Ц2), переживает ретаргет/merge/split
}
```

- **`id` = АДРЕСНЫЙ КЛЮЧ (форма-отпечаток).** Content-addressed: `edge:sha256:v1:<hex>` — sha256 по каноническому JSON тройки-тождества **`{ source, predicate, target }`**. Схема самоописательна в префиксе (прецедент `sha256:`/`djb2:` в idempotency/snapshotHash), поэтому ОТДЕЛЬНОГО поля `idScheme` НЕ вводим — как только префикс `edge:sha256:v1:` заморожен, смена схемы = новый префикс, старые id читаются по своему.
  - **⚠️ ПАТЧ КРИТИКА (2026-09-15): `validFrom` ИСКЛЮЧЁН из ключа `id`.** Ключ `id` ОБЯЗАН совпадать с ключом дедупа `foldEdges` = `{ source, predicate, target }`. `foldEdges` (predicates.ts:110-131) для `many` матчит слот по `(predicate, target)` — `validFrom` в матче НЕ участвует. Если включить `validFrom` в `id`, два ребра одного `(predicate, target)` в разное время получат разные `id`, но `foldEdges` заменит одно другим in-place (refresh) → ребро с «валидным» id исчезнет из read-model (потеря ребра). Подтверждено `packages/engine/test/second-form-spine.test.ts:54-56` (A1 и A3 = одна `(drives, car:X)`, `validFrom` намеренно держат ТЕМ ЖЕ, меняется только `validTo` → refresh-in-place). Поэтому `id` берётся ТОЛЬКО от идентичность-несущей тройки `{ source, predicate, target }`.
  - **Намеренно ИСКЛЮЧЕНЫ из отпечатка:** `meta`, `provenance`, `subjectRole`, `validFrom`, `validTo`. Причина — стабильность через refresh: `foldEdges` для `many` «обновляет meta/provenance на месте» (predicates.ts:125-127) и матчит по `(predicate, target)` без времени. Если бы отпечаток зависел от `meta`/`validFrom`, обновление меняло бы `id` → ребро теряло бы адрес при живом refresh. Отпечаток берётся ТОЛЬКО от идентичность-несущей тройки.
  - **Будущие `stale` / `confidence` на ребре — ВНЕ хеша `id`** (как `meta`/`provenance`/`subjectRole`): их изменение при рефреше не должно двигать `id`, иначе ключ нестабилен. Резервируются как provenance/аннотации, а не как часть тождества.
  - **`source` в отпечатке** = id владеющего узла (`source_ref` акта, в который ребро сворачивается; в графе — `node.id`). Ребро не инлайнит source (он подразумевается узлом-владельцем) → функция вывода принимает `sourceNodeId` явным аргументом.
  - Свойство: ретаргет `one`-ребра (predicate: `owner` A→B) даёт ДРУГОЙ `id` — и это КОРРЕКТНО: по кардинальности это REPLACE (старое ребро выброшено, новое добавлено), семантически новое ребро. `id` — ключ версии-ребра, не сквозная идентичность.

- **`canonical_id` = СКВОЗНАЯ ИДЕНТИЧНОСТЬ (Ц2).** Стабильна ЧЕРЕЗ изменение содержания. **Конвенция при отсутствии: `canonical_id ?? id`** — если явно не назначен, каноническая идентичность = производный отпечаток. Исторические рёбра (все 39 актов) → `canonical_id` отсутствует → канон = их отпечаток. Это ЧЕСТНО: их переезды сквозь изменение мы никогда не отслеживали, и притворяться иначе нельзя. С этого момента будущая запись/агент МОЖЕТ проставить стабильный `canonical_id`, переживающий ретаргет/merge/split.

### D2 — Обратная совместимость (0 миграций боевого журнала)

- **Оба поля опциональны** → существующий `Edge` без `id`/`canonical_id` типизируется без изменений (тот же приём, что `principal?`, `subjectRole?`). Журнал НЕ переписывается (append-only, `git-working-tree-safety`).
- **`id` производный** → для любого исторического ребра вычисляется чистой функцией `edgeIdOf(sourceNodeId, edge)` в момент чтения/rebuild. Миграция журнала НЕ требуется вообще.
- **Going-forward:** поле остаётся опциональным на уровне ТИПА (иначе сломались бы 155+ тестов и сам append-only). «Обязательность» — это ПОВЕДЕНИЕ (стемпинг на записи + отказ при отсутствии), а поведение отложено (§Reserved-Form). Инвариант «каждое ребро адресуемо» держится за счёт того, что `id` ВСЕГДА ВЫВОДИМ, даже когда не материализован.

### D3 — Что материализуем СЕЙЧАС vs откладываем
**Сейчас (форма):** поля на типе + чистая функция вывода `edgeIdOf`/`edgeCanonicalIdOf` + тривайр-тест. Read-model НЕ переписываем, стемпинг в проекцию НЕ включаем — это уже поведение (см. ниже), и оно рябит по рендер/snapshot-тестам без нужды для сохранения односторонней двери.

## Reserved-Form — что ОТЛОЖЕНО (форму НЕ строим, только резервируем в этом ADR)

Явно за швом (НЕ в этой поставке, требуют отдельного «строй» + ADR/спека):

1. **Стемпинг `id` на записи и/или в read-model.** Сегодня `id` только выводим чистой функцией; никто его не проставляет в журнал или в проекцию. Материализация — поведение.
2. **Назначение `canonical_id` и перенос идентичности сквозь ретаргет** (Ц2 «меняем не теряя себя» в действии).
3. **merge/split ребра** — слияние двух рёбер-кандидатов в одну идентичность и обратное разделение (аналог `same-as` для узлов, но на рёбрах). Только зарезервировано.
4. **Каскад удаления по ребру** — ссылочная целостность (сирота-ребро при удалении узла-конца; каскад по типу ребра). Ц6 «не плодить сироты» — форма-цель, enforcement отложен.
5. **`stale` / `confidence` на ребре** (Ц6 «свой confidence/stale») — **НЕ добавляем поля сейчас.** Честно: это НЕ retrofit-impossible (опциональное поле-аннотация добавляется позже аддитивно, отсутствие = «неизвестно», 0 миграций — как `principal` добавился аддитивно). Поэтому вне scope этой односторонней двери; резервируем как namesake будущего слота, но форму не занимаем, чтобы не раздувать.
6. **Enforcement уникальности/referential-integrity по `id`** — `edge-index`/`foldEdges` сегодня дедупят позиционно (predicate/target), НЕ по `id`. Переключение на id-based identity — поведение.

## Рассмотренные альтернативы

- **A. Ничего не делать (оставить рёбра позиционными).** Отклонено: журнал append-only копит рёбра без слота сквозной идентичности → `canonical_id` становится невосстановимым. Это единственная дверь, которая закрывается со временем.
- **B. Явный ULID/случайный `id`, проставляемый на записи (как `Act.id`).** Отклонено как ФОРМА тождества, хотя годится как будущий `canonical_id`. Минусы для СЕЙЧАС: (1) требует стемпинга на записи → не вычислим на исторических рёбрах → migration или вечная дыра «до-ULID рёбра без id»; (2) не даёт дедуп/идемпотентность по содержанию. Content-addressed отпечаток даёт и адрес, и «одинаковое ребро → одинаковый ключ» бесплатно на всей истории. B живёт как ОТЛОЖЕННЫЙ механизм назначения `canonical_id`.
- **C. Одно поле `id` (без `canonical_id`).** Отклонено: схлопывает две ОРТОГОНАЛЬНЫЕ оси — адрес-версии (меняется с содержанием) и сквозную идентичность (переживает изменение). Ровно ту же ошибку критик ловил в ADR-0010 (edit #2: «плоский enum схлопывает две оси»). Ц2 требует идентичность, переживающую смену → нужен второй, стабильный слот. Пара `id`+`canonical_id` зеркалит узловой канон (node.id / canonical_id).
- **D. Content-addressed по ПОЛНОМУ ребру (включая meta/provenance/validFrom).** Отклонено: `foldEdges` рефрешит meta на месте и матчит по `(predicate, target)` без `validFrom` (predicates.ts:125) → id прыгал бы при живом обновлении/коррекции интервала, ребро теряло бы адрес и/или исчезало бы из read-model при refresh-in-place. Отпечаток ТОЛЬКО от тройки-тождества `{ source, predicate, target }` (см. патч критика в §D1).

## Последствия / план валидации

**Позитивные:**
- Ц6: у ребра появляется паспорт-адрес → память своего ранга (форма). Ссылочная целостность/каскад теперь ИМЕЮТ якорь (`id`) для будущего enforcement.
- Ц2: слот `canonical_id` заложен → сквозная идентичность ребра станет возможной без миграции журнала.
- 0 миграций: производный `id` вычислим на всей истории; оба поля опциональны.
- Согласованность с домом: то же вещество, что `idempotencyHash` (content-addressed sha256), тот же Reserved-Form, что `principal`/`subjectRole`.

**Негативные (приняты осознанно):**
- **Сквозная идентичность исторических рёбер невосстановима** (canonical_id = отпечаток) — принято: это и есть суть retrofit-impossible; честно зафиксировано, не заметено. Ретаргеты, случившиеся ДО этого ADR, навсегда выглядят как два разных ребра.
- **`id` пока не материализован** (только выводим) → потребитель, желающий адрес, зовёт `edgeIdOf`. Принято: материализация — поведение, откладываем, чтобы не рябить по 155+ тестам и не занимать read-model раньше нужды.
- **Поле опционально going-forward** (не обязательное на уровне типа) → инвариант «каждое ребро имеет id» держится выводимостью, а не типом. Принято: обязательность = поведение (стемпинг+отказ), отложено.

**План валидации (аддитивно, НЕ ломая существующие 155+ тестов):**
1. `edge-identity.test.ts` (новый): детерминизм `edgeIdOf`; стабильность при рефреше `meta`/`provenance`/`validFrom` (id НЕ меняется — патч критика); ретаргет target → id меняется; разный `source` → id меняется; исторические рёбра из боевого журнала получают id без миграции; `canonical_id ?? id` конвенция.
2. `edge-identity-not-enforced.test.ts` (новый, ТРИВАЙР по образцу `consent-not-enforced.test.ts`): утверждает, что СЕГОДНЯ (а) проекция не проставляет `id` на рёбра read-model, (б) `foldEdges`/`edge-index` дедупят позиционно, НЕ по `id`. Написан так, чтобы УПАСТЬ, когда enforcement/материализация приземлится — сигнал обновить doc-comment и этот ADR.
3. Регресс: `npm test` в `packages/engine` — все существующие тесты зелёные (форма аддитивна, поведение не тронуто).
4. Ратификация: владелец переводит proposed → approved (или возвращает с правками). Стройка формы — по явному «строй».

## Честное ограничение (provisional)
- Этот ADR фиксирует ФОРМУ и НАПРАВЛЕНИЕ, а не старт стройки. Commit-триггер проекта (реальные данные / явное «строй») не вытесняется.
- Стоит на нератифицированном ADR-0014 — при его пересмотре перечитать §Decision.
- **Reconsider-by:** при ратификации/отклонении ADR-0014, ИЛИ когда появится первый реальный процесс, требующий merge/split/каскад ребра (тогда поведение выходит из Reserved-Form по отдельному ADR).
- **Reconsider-by (наследование `canonical_id` при ретаргете):** перенос сквозной идентичности через ретаргет `one`-ребра — это REPLACE-splice в `foldEdges` (predicates.ts:117-122): старое ребро выбрасывается, новое добавляется. Наследовать `canonical_id` со старого ребра на новое = ЛЕЗТЬ в `foldEdges` (поведение read-model). ОТЛОЖЕНО как явный триггер: первый реальный процесс, требующий «ретаргет НЕ теряет сквозную идентичность» (Ц2 в действии), выводит это из Reserved-Form отдельным ADR, затрагивающим `foldEdges`.
