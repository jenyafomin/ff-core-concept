# ADR-0016 — Мозг между проектами

## Статус
**proposed, ревизия 2.** «Строй» владельца на Этап 0 (PLAN-v2 §8) дан. Ревизия 2 закрывает 3 BLOCKER критика и противоречия ADR↔SPEC из reviewer-gate. Ратификация — владельцем. Код не тронут.

## Контекст
Владелец отверг «память в файлах проекта»: память должна жить **между** проектами (компания → проекты, общие задачи, пересчёт). Обе существующие схемы привязывают память к месту: движок — `body.tenant` одной строкой с дефолтом `'project:ff'` (`resolve.ts:61`, клэмп S8 `:253`); шлюз — проект в id (`unit.id = 'ns:slug'`, agents-manager ADR-0005:96). Типы и предикаты сегодня — seed/инъекция в коде (`predicates.ts:33`), глобальный валидатор (`envelope-validator.ts`) роняет весь граф на одной битой записи. PII-гейт режет по имени ключа, время с пробелом и длинные номера (`admission.ts:47,56`). Шлюз дублирует сообщения. Журнал при чтении обрывается на первой битой строке (`store-durable-fs.ts:184` `break`) — последующие записи молча теряются после рестарта (проверено критиком). `@ff/engine` не импортируется под обычным `node` (`packages/core/src/index.ts`: импорты без `.js`). Все разговоры владельца в Telegram — форум-топики супергруппы `-1004351636302` (conversationId = `chat:thread`, `normalize-inbound.util.ts:41`): правило «группа = отказ» сделало бы мозг мёртвым.

## Решение

**D1 Один мозг.** Один долгоживущий сервис `@ff/brain` (pm2) вне всех проектов — **единственный писатель** (очередь записи; PID-lock `store-durable-fs.ts:99`) поверх журнала `@ff/engine`. Агенты шлюза и Claude Code ходят через тонкий MCP-клиент `@ff/brain-mcp` (`record · find · read · link`). Сервис — отдельный процесс за IPC-границей (ISO-2, ADR-0011), unix-сокет 0600 + токен. `unit_event` шлюза = журнал решений шлюза (транспорт/апрув), не мозг; моста не строим. Хранилище — за портом: JSONL сейчас, Postgres позже.
- **Мозг не вызывает `engine.view()`**; глобальный `envelope-validator` не в его пути. Проверка акта — поактовая, в `@ff/brain/domain`. Переписывание глобального валидатора в v0.5 НЕ делается.
- **Запуск под node:** сервис стартует из собранного `dist` обычным `node` (pm2). Для этого чинятся ESM-импорты `@ff/core` (расширения `.js`). Fallback — запуск через `tsx` (записанное отклонение, не норма).
- Выгрузка/статистика/бэкап — только через сервис (HTTP по сокету): второй процесс не может открыть журнал под тем же локом.

**D2 Тождество.** `id` неизменен навсегда и **не содержит проекта или типа**. Область и тип — рёбрами/полями, не в id.

**D3 Журнал и реестр.** Append-only (I-3/I-4). Каждый акт несёт `schema_v` и `type_v` (в `provenance`).
- **Реестр типов и предикатов живёт АКТАМИ в журнале** (`type-def` / `pred-def`). Код держит только **genesis-пакет** — его сервис идемпотентно пишет в журнал при первом старте (повторный старт = 0 новых актов). Дальше реестр читается **только из журнала**.
- **Двухпроходный старт:** (1) сканировать журнал на `pred-def` → вычислить кардинальности; (2) открыть `DurableFsStore` с этим реестром. Следствие: новый `pred-def`, записанный на ходу, вступает в силу после рестарта (в v0.5 предикаты пишет только genesis — см. D6).
- **Replay никогда не отказывает и ничего не теряет молча.** Правка движка: `hydrateFromDisk` пропускает битую строку (`continue` вместо `break`) и сообщает о ней колбэком/счётчиком. Сервис: битая строка → счётчик в `/health` + один `friction` (код причины + хэш, **без тела**, V7; дедуп по `hash(act_id|line_hash, reason)`). **Оборванный хвост** (нет финального `\n`) сервис усекает до последнего `\n` **после** бэкап-копии журнала.
- **Подтверждение записи только после fsync.** Факт по коду: `writeAct` уже делает `fsyncSync` до возврата (`store-durable-fs.ts:199-206`). Сервис отдаёт `ok:true` только после возврата `writeAct`.
- Бэкап делается задачей **внутри очереди записи** (копия + `.sha256`), чтобы не ловить недописанную строку.

**D4 Области = узлы.** Тип `scope` с видами `personal | company | project` (других видов в v0.5 нет). Принадлежность записи — ребро `in-scope` (M:N), проект → компания — `member-of` (M:N). Заменяет одиночный `tenant`; ключ `tenant` в теле новых записей зарезервирован и отклоняется. **Совместимость:** при проекции старый акт с `body.tenant=X` (или без него → `project:ff`) читается как неявное ребро `in-scope → X`; журнал не переписывается. Это задача с тестом в v0.5. Клэмп S8 вычисляется по множеству областей.

**D5 Типы.** Запись несёт **объявленный тип + `type_v`**; переклассификация — ребром `instance-of` (действующий тип = последнее **не-отозванное** ребро, иначе объявленный); `id` не меняется (V2). `type-def` = единица (автор, история, `confidence`, `status active|candidate|cold`). Наследование — **одним источником: поле `extends: "name@v"` в `type-def`** (закреплённая версия, одиночное, глубина ≤2); отдельного предиката `extends` нет. Тип при экспорте уносит цепочку предков (V5). Поправка к M-G3: `variant-of` остаётся (резерв), `extends@v` добавляется в узкой форме.
- **Неизвестный тип в v0.5** → запись принимается как `raw` (объявленный тип сохраняется в поле `declared_type`) + warning + `friction`. Не отказ.
- **v0.5 = только ФОРМА:** поля `status: candidate`, `extends`, `confidence` у `type-def` принимаются и возвращаются. **Поведение отложено в 1c:** видимость `candidate` в `find`, активация («да» владельца или ≥N чтений не-автором), запрет агенту сужать/сливать/расщеплять, разрешение полей по `extends`. MCP v0.5 не даёт агенту глагола создания `type-def`.

**D6 Рёбра = записи.** Ребро несёт `id`, `author`, `confidence`, `status`; `id` = `edgeIdOf(source, predicate, target)` (ADR-0015). Предикат — запись реестра с подсказкой `from/to` и строкой смысла. **Неизвестный предикат в v0.5 → отказ `UNKNOWN_PREDICATE` с подсказкой** (список известных); `candidate`-предикаты — Этап 1c. Цель отсутствует → ребро `dangling`, не отказ. Отзыв ребра = `meta.status=retracted`, сервис **сливает** meta (не теряет author/confidence/created_at). Обход — `depth` по умолчанию **1**, максимум **2**, `max_nodes` и visited-set.

**D7 Слои и документы (только форма).** Опциональные поля акта: `layer` (0 = факт), `derived_from: [id@rev]`, `source: {kind, ref, hash}`. В v0.5 поля принимаются, валидируются по формату и возвращаются. **Поведение `stale`** (производный слой с изменившимся источником не отдаётся как свежий) и правило «файл = истина, правки тела документа в мозге не принимаются» — отложены (1c / ингест документов).

**D8 Доверие, согласие, читатель.** На единицах `author / owner / referent` — атрибуция-данные, не основание прав (ADR-0010). `referent ≠ owner` → жёстко `visibility = owner`. Агент пишет всегда (запись внутрь обратима): по прямой просьбе — `active`, по своей инициативе — `proposed` (метка, не стена; агент передаёт `initiative`). Наружу (людям) факты из мозга — только с подтверждения владельца.
- **Читатель выводится сервисом, самозаявление не принимается.** Шлюз выставляет env (`FF_BRAIN_CONVERSATION_ID`, `FF_BRAIN_MESSAGE_ID`, `FF_BRAIN_SENDER_ID`, …); в JSON-схемах tools полей личности нет, лишние поля = 400.
- **Allowlist `readers.json`** по ключу `chatId` или `chatId:thread` (более узкий ключ главнее). Группа владельца `-1004351636302` и её топики разрешены. Запись читателя несёт `principal`, `scopes`, `default_scope` (биндинг топика), `write`, `personal`.
- **Проверка отправителя обязательна:** `FF_BRAIN_SENDER_ID` (id автора входящего сообщения от шлюза) должен совпасть с `owner_id` в `readers.json`. Чужой или отсутствующий отправитель в разрешённой группе → **отказ `SENDER_DENIED`** (и чтение, и запись; строгий вариант).
- Неизвестный чат/топик → `DEFAULT_DENY`. Область записи по умолчанию — `default_scope` биндинга топика.
- **CLI (Claude Code вне шлюза)** — только по явному allowlist `cwd` в `readers.json` (правит владелец), по умолчанию запрет. Это **осознанное исключение** из «нет conversationId → запрет»: идентичность CLI = `cli:<cwd>`, без `message_id` (без идемпотентности).
- Ходы шлюза без контекста отправителя (loop-тики, print-режим) — MCP мозга не подключается.

**D9 PII-гейт для области `personal`.** Время («14:30»), даты, номера заказов, `person{name}` проходят; телефоны и email — нет (скан **значений**). Отказ — читаемая ошибка с кодом.
- **v0.5 честно: политика = код** (опции схемы `allowKeys` / `opaqueValueKeys` в `admission.ts` + `pii-scope.ts` мозга), не данные. Перенос в данные — 1c.
- Даты-время с пробелом (`YYYY-MM-DD HH:MM`) нормализуются в `T` **во всех текстовых полях** до скана.
- `opaqueValueKeys` действует только для значений формата `^[A-Z0-9-]{1,20}$`; иное сканируется полностью.
- `provenance` скан не покрывает → сервис валидирует формат: `source.ref` — путь/url/`act:` (`^[A-Za-z0-9._/:#-]+$`, ≤200, без `@`, без цифровых серий ≥9), `source.kind` — enum, `derived_from` — `^[ua]_[a-z0-9]+@\d+$`.
- Зарезервированные ключи тела (`tenant`, `space`, `capability`) отклоняются (движок читает их как политику).

**D10 Идемпотентность.** Ключ = `sha256(conversationId + message_id + verb + ordinal-вызова-в-ходе)` — **без args** (дубль шлюза при перегенерации даёт иные args). Проверка ключа, слияние тела, `Engine.write`, обновление индекса и триггер бэкапа выполняются **атомарно внутри очереди записи**. Нет `message_id` (CLI) → без idem. Открыто: в G1 подтвердить, что шлюз отдаёт id **входящего** сообщения (а не `replyToMessageId`), иначе дубль с новым message_id не схлопнется.

**D11 Поправка UNIT-SPEC §9.** Агент МОЖЕТ заводить `candidate`-типы; активировать, сужать, сливать, расщеплять — не может. **В v0.5 — только форма** (D5); исполнение — 1c. Остальной CANNOT-list §9 не меняется.

**D12 Недоступность и квитанции.** Агент никогда не говорит «записал» без `ok:true`. Квитанцию (`receipt`) строит сервер, агент передаёт дословно. Сервис недоступен: `find/read` → `SERVICE_DOWN`; `record` → `brain-mcp` кладёт вызов в outbox `~/.ff-brain/outbox/` (0600) с уже вычисленным idem и env-личностью и отвечает `queued:true`; первый успешный вызов досылает outbox с тем же idem, сервис заново проверяет личность по `readers.json`.

## Что ОТЛОЖЕНО (форма есть, поведения нет)
Садовник типов: видимость/активация `candidate`, бюджет кандидатов, остывание (1c); запрет агенту сужать/сливать типы (1c); `candidate`-предикаты (1c); разрешение полей по `extends`, апгрейд базы; `stale`-проекция слоёв и их генерация (1c); ингест документов и правило «правки тела документа не принимаются»; PII-политика как данные (1c); переписывание глобального `envelope-validator`; монотонность `assertForwardMonotone`; `hard_erase` каскадом; consent enforcement; «чей id выживает при слиянии»; линзы-как-данные; Postgres-адаптер; семантический индекс; токен на ход от шлюза (v1).

## Рассмотренные альтернативы
- **Память в файлах проекта / per-project store** — отклонено владельцем.
- **Мозг в `unit_event` шлюза** — отклонено: проект зашит в id, нет рёбер-как-памяти, второй движок.
- **Мост движок↔шлюз** — отклонено: два источника истины.
- **Тип только ребром / только полем** — сведены в «оба» (D5).
- **Форк типа с `derived-from` вместо `extends`** — принят как более слабая форма; `extends@pinned` в поле type-def.
- **«Групповой чат = отказ»** (рев. 1) — отклонено: все разговоры владельца в супергруппе; заменено allowlist + проверкой отправителя.
- **Реестр seed-константами в коде** (рев. 1 SPEC) — отклонено: противоречит D3; оставлен только genesis-пакет, который пишется актами.
- **Pre-scan журнала сервисом без правки движка** — отклонено: движок всё равно делал бы `break`; правка `continue`+колбэк проще и тестируется в движке.
- **Бандлер (esbuild) для сервиса** — отклонено как основной путь: чинить импорты `@ff/core` дешевле и полезно всем пакетам; `tsx` — fallback.
- **Postgres сразу** — отложено.

## Последствия
- (+) Одна задача — один `id`, видна из обоих проектов и из компании; схема растёт без кода; сбой одной записи не роняет мозг и не теряет следующие.
- (+) Приватность держит сервис (allowlist + проверка отправителя), а не добросовестность агента.
- (−) Три точечные правки вне нового пакета: `admission.ts` (опции схемы), `hydrateFromDisk` (`continue`+колбэк), ESM-импорты `@ff/core`. Глобальный валидатор не переписывается (заменяет оценку рев. 1 «M→L»). Принято.
- (−) Временное отклонение от PG-default ADR-0006. Принято: адаптер за портом.
- (−) Пишем о людях до consent enforcement. Компенсация: `visibility=owner` жёстко, контакты режутся, чужой отправитель — отказ.
- (−) Новые предикаты вступают в силу после рестарта; запись O(N) по журналу (`Engine.write`) — терпимо до ~50k, время записи в `/health`.
- (−) Риск v0.5: агент с Bash может прочитать токен (тот же пользователь ОС) — принят по прецеденту ADR-0013 + стоп-лист; v1 — токен на ход. **Подтверждено живым прогоном критика 2026-10-09 (build/critic-live-run.md F-1): с токеном и подменёнными заголовками читаются все области** — до G1 (стоп-лист `~/.ff-brain/**` для агентов шлюза) мозг не подключать к агентам с Bash без этого запрета.
- (−) Межрепо: agents-manager должен пробросить env мозга (G1) и получить аддендум к своему ADR-0005 — в этом ADR не правится.

## План валидации (гейт до первой реальной записи; AC — в SPEC-brain-v0.6)
1. **G1 изоляция:** чат/топик не из allowlist → `DEFAULT_DENY`; топик группы владельца из allowlist + отправитель = владелец → данные; разрешённая группа + чужой/пустой отправитель → `SENDER_DENIED`; CLI без allowlist cwd → запрет, с ним → доступ; поля личности в теле → 400. → **AC-01…AC-07**
2. **Тождество/области:** общая задача с двумя `in-scope` находится из обоих проектов и из компании — `id` один; legacy-акт с `tenant` читается как `in-scope`; область записи ⊆ области читателя. → **AC-08…AC-10**
