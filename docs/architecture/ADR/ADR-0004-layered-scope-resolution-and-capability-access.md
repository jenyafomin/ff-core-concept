# ADR-0004 — Layered Scope Resolution (LSR) + доступ по возможностям

> **Нумерация.** ADR-0004 ранее был зарезервирован под тему «Движок / Engine» (см. примечание в ADR-0005).
> LSR — это и есть **несущий контракт разрешения, который исполняет движок**: одна операция «свернуть
> упорядоченный стек в эффективное значение», применяемая к доступу, промптам, политикам. Поэтому тема
> не подменяется, а конкретизируется. ADR-0005 (структура субстрата) стоит рядом: там — ГДЕ живут узлы,
> здесь — КАК движок разрешает конфликтующие вклады слоёв.
>
> **Гранулярность.** Пока это ОДИН файл. Если capability-набор или combinator-таксономия разрастутся,
> выделять под-записи `ADR-0006…` с обратной ссылкой сюда.

---

## Контекст

Северная звезда проекта — **модульность/plug-in**: чужие модули подключаются как ДАННЫЕ, движок остаётся
фиксированным (`boundary-and-prototype.design.md` §0-1). Из этого следует, что и **доступ («что можно /
что нельзя») должен быть данными, а не ветками в коде**. Черновик границы (§2) развёл три понятия —
`visibility` (кто видит), `access` (что узел вправе трогать), `capability`-грант (что субъект может в
рамке) — и предложил один порядок приоритета для разрешения их конфликтов (§2.4, вопрос Q-14/Q-12).

Три независимых наблюдения сошлись в один вывод и заставили переписать черновик, а не просто ратифицировать:

1. **Слоистость — не про доступ.** Abstract-thinker (`abstract-layered-resolution-primitive.md`) показал:
   ТОТ ЖЕ «упорядоченный стек → эффективное значение» повторяется в доступе (OVERRIDE), каскаде промптов
   (ACCUMULATE), конфигах (MERGE) и арбитраже политик (VETO/CLAMP). Проектная путаница «каскад
   перезаписывает или накапливает?» существует лишь потому, что **никто не назвал свёртку (fold) отдельным
   параметром**. Назвать её — растворить противоречие.
2. **Capability-слой никогда не был доказан.** Критик (`critic-boundary-ADR-0004.md`) установил: killer-прогон,
   на который все ссылались как на «доказано делом», проверял конверт/инверсию/мета-слой/view — но НЕ
   доступ (ноль grant-узлов, ноль `meta:cap/*`, ноль разрешения каскада, ноль клапана). Он же нашёл дыры
   привилегий: (а) node-level `access` на ВЕРХУ каскада + не защищено, кто пишет эти поля → любой writer
   штампует пермиссивный `access` и перебивает space-level deny админа; (б) минт `grant`-узла сам не
   capability-gated → writer выдаёт себе `core:*`; (в) `default:deny` ставит сам модуль → «нижний
   предохранитель» = opt-out тем, кого он ограничивает. Корень всех трёх — **`deny` смоделирован как нижний
   СЛОЙ стека, а должен быть ЗАЖИМОМ (clamp) после свёртки** (независимо выведено LSR-агентом).
3. **Q-14 ратифицирован владельцем (2026-07-24)** — порядок приоритета доступа утверждён как решение. Но по
   принципу-зеркалу (И-2: «тип без живого примера запрещён») правило-в-прозе = недоказанный конструкт, пока
   не записано ПРОВЕРЯЕМЫМ узлом-данными.

Фаза проекта — **дизайн**. По стратегической развилке (`SYNTHESIS` §Развилка) выбран **путь A: доказать
capability сейчас** маленьким killer-прогоном ДО ратификации ADR — в духе walking-skeleton. Прогон исполнен
и независимо проверен (см. Validation plan). Поэтому ADR пишется `proposed` **на твёрдом, а не на гипотезе**.

## Decision

### D0. Один примитив — Layered Scope Resolution (LSR); доступ = инстанс №1

Ратифицируется **LSR как системный примитив разрешения**, а не access-only правило. Движок читает один
контракт; доступ — лишь ПЕРВЫЙ прожжённый инстанс, не единственный.

```
resolve(key, viewer, node) = clamp( fold( combinator, orderedStack, safeDefault ) )
                               │       │        │            │             │
                             ЗАЖИМ   СВЁРТКА  комбинатор  упорядоченный  безопасный
                          (пол+потолок) (fold)  из enum      стек слоёв     низ
                          после свёртки          (ДАННЫЕ)   (ранг=приоритет) (пол при молчании)
```

- **Access** = `clamp_authority( OVERRIDE_reach( stack ), floor=deny, ceiling=Конституция )`.
- **Каскад промптов** = `ACCUMULATE`, одна ось, без veto.
- **Конфиги** = `MERGE`, одна ось.

И-5 черновика («политики разрешаются по ОДНОМУ явному приоритету; дефолт deny») **заменяется на INV-LSR**:
> *Движок владеет РАЗРЕШЕНИЕМ; слои владеют ДАННЫМИ. Каждый ключ разрешается ровно одним комбинатором из
> фиксированного набора; пол/потолок зажимаются движком и не выразимы данными. Ничто, выразимое данными,
> не может убрать пол.* И-5 была слишком узкой — хардкодила один fold (OVERRIDE) и не видела, что промпты
> ACCUMULATE. INV-LSR обобщает корректно.

### D1. Упорядоченный стек и ranking contract

Стек доступа (от узкого к широкому; ранг = приоритет):

```
node  >  space.override  >  space.default  >  project  >  module
```

- Порядок ЯКОРЕЙ фиксирован движком. Модуль/capability может **ВСТАВИТЬ новый слой**, но обязан объявить
  свой ранг относительно якорей («более специфичен, чем project; менее, чем node») — это **ranking contract**,
  а не замороженный список. Membership слоёв — данные (расширяемо); ordering якорей — движок (неизменно).
- Это разрешает противоречие черновика §1.2 («модуль просит своё место») ⟂ §1.1/§2.4 («порядок —
  фиксированный ядро-инвариант»): якоря фиксированы, вставка в рамках контракта разрешена, переупорядочить
  якоря или перепрыгнуть потолок — нельзя.

**Ranking contract — формально:**
- **Engine-fixed:** ЯКОРЯ (верх = `node`; нижний зажим = `deny`/потолок) + закрытый combinator-enum (D2).
- **Data-declared:** MEMBERSHIP слоёв и РАНГ каждого слоя между якорями.
- **Additive-only rule:** новый слой вставляется на объявленный ранг и может только СУЖАТЬ (никогда не
  расширять) то, что более общий слой уже запретил — это гарантирует **отсутствие молчаливой регрессии** на
  уже существующих разрешениях. Изменение якоря или enum = **supersede (новый ADR)**, не молчаливый патч.

### D1a. Две оси (reach + authority)

Резолвер доступа — **НЕ единая свёртка**, а конвейер по двум независимым осям:

```
effective(access) = CLAMP_authority( OVERRIDE_reach( orderedStack ) )
```

Это уже доказано, а не предположено: admin-clamp прогнан в killer-прогоне в ОБЕ стороны (deny-dir: admin-deny
бьёт node-allow; allow-dir: admin-allow чтится, хотя узел ничего не даёт), а M-G3 моделирует authority × reach
как две оси.

- **Ось reach** = containment-стек `node > space.override > space.default > project > module`, свёрнутый
  комбинатором **OVERRIDE** (самый специфичный вклад побеждает). «Насколько узко адресован вклад».
- **Ось authority** = **CLAMP, применяемый ПОСЛЕ reach-свёртки** (сегодня — бинарный admin; здесь же живут
  `deny`-пол и Конституция-потолок из D3). «Кто вправе перекрыть результат reach».

**Q-11 mapping (делает «provisional» конкретным):**
- `team` = операция на оси reach. **Проверено growth killer-прогоном (2026-07-24):** *подстановка*
  контейнера (`space`→`team`, тот же ранг) — **data-only, движок 0 правок** ✅. НО *вложенная вставка*
  нового ранга (`node > team > space` одновременно) сегодня **НЕ выразима данными**: `writeStack` берёт
  узел + РОВНО ОДИН контейнер, а не итерирует объявленную цепочку scope. Полная N-уровневая reach-вставка
  требует **аддитивной правки движка** (writeStack проходит цепочку рангов) — additive, но это ИЗМЕНЕНИЕ
  КОДА (см. Consequences #3, F2). ranking contract (D1) сегодня доказан для authority-оси и reach-подстановки.
- `role` = **градация на оси authority** — слотится на существующий clamp, НЕ в reach-стек. Обобщить
  сегодняшний бинарный admin-clamp до градуированного `owner > member > guest` — **позднее ADDITIVE
  изменение, а не блокер Фазы 1**.

Так Q-11 (space → team/role) получает формальный дом: reach-подстановка + authority-градация доказаны
аддитивными; N-уровневая reach-ВСТАВКА — известная аддитивная правка движка, гейтится вместе с Q-11.

### D2. Комбинатор — из ЗАКРЫТОГО enum, как ДАННЫЕ

Комбинатор выбирается из закрытого набора и хранится как данные (тег на ключе/типе):

| Комбинатор | Правило свёртки | Держит | Инстанс проекта |
|-----------|-----------------|--------|-----------------|
| **`override`** | самый специфичный не-∅ вклад побеждает | ОДИН | access §2.4 |
| **`accumulate`** | конкатенация всех вкладов по порядку | ВСЕ | каскад промптов |
| **`merge`** | объединение под-ключей; override по каждому листу-полю | ВСЕ ключи, ОДНО знач/ключ | config / policy_overrides |
| **`veto` / `clamp`** | монотонный пол+потолок; после установки границы её не пересечь | границу | `deny`-пол, Конституция-потолок |

**Несущий шов controlled-vs-flexible:** **выбор комбинатора = данные (R1); реализация комбинатора =
движок (R3).** Автор ПИКАЕТ fold из набора — автор не ПИШЕТ новый fold. Новый fold = код + ADR. Это и есть
линия «жёсткое/гибкое», и она проходит СКВОЗЬ разрешение, а не вокруг него.

### D3. deny / Конституция — ЗАЖИМЫ после свёртки (единственный несущий инвариант безопасности)

**`deny`-пол и Конституция-потолок — НЕ позиции в стеке.** Это порядко-НЕзависимые зажимы (lattice
meet/join), применяемые ПОСЛЕ всех data-driven свёрток:

```
effective = clamp( fold(stack) , floor=deny , ceiling=Конституция )
```

- `deny` — низ, поглощающий всё под собой; Конституция — верх, над которым ничто не поднимается.
- Моделировать `deny` как «последний OVERRIDE-слой» — та самая тонкая ошибка, которая позволила бы модулю
  со временем перебить пол (killer-прогон S1: NAIVE так и делает — node-allow перебивает admin-deny).
- Это **единственное место, где инвариант абсолютен.** Мэппится на И-3 (нет записи в `policy/core:*`) и
  И-6 (клапан согласия). Конституция сама `access.can_write: []` — не переписываема данными.

### D4. Мета-capability гейт на плоскости управления

Поля и узлы, которые решают АВТОРИЗАЦИЮ саму по себе, — не рядовые данные. Их запись гейтится отдельными
`core:manage-*`, НЕ рядовым `core:write-knowledge`:

| Действие плоскости управления | Требуемая возможность |
|-------------------------------|-----------------------|
| писать поля `access` / `visibility` на узле | `core:manage-access` |
| минтить `grant`-узел | `core:manage-grants` |
| писать в защищённый ядро-неймспейс (`meta:type/`, `meta:envelope`, `policy/core:*`, `meta:cap/core:`) | `core:manage-core` |
| минтить новый `meta:cap/*` (даже vendor-cap требует review-авторитета) | `core:manage-core` / `core:manage-grants` |

Это закрывает privilege-escalation корня (критик CRITICAL #1/#2/#3): нельзя самому выписать себе права
дешёвым `write-knowledge`. Проверено S4/S5/S10/S11 killer-прогона.

### D5. Клапан согласия сверяет флаг возможности, а не самодекларированную метку

`consent-valve` гейтит необратимое внешнее действие. FIXED-движок сверяет `irreversible: true` на самой
`meta:cap/*`-возможности, которую действие называет, — а НЕ доверяет самодекларированной строке
`visibility.valve` на узле (её пишет автор → спуфится). Проверено S6. Двойной замок: возможность
`external-irreversible` надо (1) явно выдать грантом И (2) явно подтвердить событием на исполнении.

### D6. Принцип-зеркало — каскад живёт как узел-данные

Каскад существует не прозой, а **живым узлом `policy:access-priority`** в реальном 10-полном конверте
(Appendix A). FIXED-движок ЧИТАЕТ его; `deny`/потолок применяет зажимом после свёртки. Это закрывает
mirror-principle gap #1 (правило-в-прозе = недоказанный конструкт по И-2). Узел уже в тестовом корпусе
(`nodes-cap.json`); в целевой корпус добавляется отдельным «строй».

## Alternatives considered

1. **Access-only приоритет (исходный §2.4 черновика), без обобщения.** Отклонено: хардкодит один fold
   (OVERRIDE), не видит, что промпты ACCUMULATE, а конфиги MERGE; тот же примитив пришлось бы пере-выводить
   на каждой фиче. Обобщение почти бесплатно и убирает латентное противоречие «override vs accumulate».
2. **`deny` как нижний СЛОЙ стека.** Отклонено — это несущая ошибка безопасности: слой можно перебить более
   специфичным слоем, зажим — нельзя. Killer-прогон S1: под NAIVE (deny=слой) node-allow перебивает
   admin-deny (breach); под FIXED (deny=зажим) — блокируется.
3. **Author-definable комбинаторы (открытый набор folds).** Отклонено: новый fold = код = R3-изменение;
   открытый набор = неограниченная поверхность движка, несовместимая с «движок фиксирован». Пикать из enum —
   можно (R1); писать fold — нельзя.
4. **Поля `access`/`visibility` и `grant` пишутся рядовым `write-knowledge`.** Отклонено: прямой путь
   самоэскалации (S4/S11 под NAIVE — breach). Плоскость управления обязана быть отдельно гейтнута.
5. **Модуль договаривается о «своём месте» в приоритете.** Отклонено: ломает фиксированность якорей.
   Разрешено через ranking contract (D1) — вставка в рамках якорей, без переупорядочивания.
6. **Замороженный 5-уровневый список навсегда.** Отклонено в пользу ranking contract; но сам список
   заморожен СЕГОДНЯ (см. Consequences #3, provisional pending Q-11).
7. **Клапан доверяет `visibility.valve`-строке.** Отклонено: строка спуфится автором (S6 под NAIVE — breach).
   Сверять с `irreversible`-флагом возможности.

## Consequences

**Что разблокируется (+):**
- **Доступ, промпты, политики — один читатель.** Рост = INSERT слоя в стек (как `grAdd` в M-G3), не код.
  «Добавить уровень доступа» перестаёт быть правкой движка.
- **Capability-слой прожжён на данных, не гипотеза.** Три несущих хода подтверждены killer-прогоном:
  зажим-после-свёртки, мета-гейт плоскости управления, стоимость+доступ через один `resolve()`.
- **Линия жёсткое/гибкое названа точно** (выбор=данные, реализация=движок) — маркетплейс модулей может
  вносить слои и возможности, не трогая резолвер.

**Издержки / принятые открытые пункты (−) — 5 честных OPEN, не закапываем:**

1. **Ничья при равном ранге** (M-G3 D8-Q1: две политики равного authority И равной reach, multi-owner) —
   набор комбинаторов НЕ имеет ответа на истинной ничье; нужен **5-й тай-брейкер** (deny-wins? newest? явный
   флаг?). INV-LSR не решает — изолирует. **Не блокирует сегодня** (single-owner проект); держать открытой осью.
2. **Комбинатор данными лишь наполовину:** SELECTION = данные, IMPLEMENTATION = движок. **Новый fold — это
   изменение движка (R3), не данные.** Этот шов заявлен явно: гибкость внутри enum, не за его пределами.
3. **5-уровневый стек заморожен сегодня → каскад PROVISIONAL pending Q-11** (split space/team/role). Путь
   роста ФОРМАЛЕН (D1a) и **проверен growth killer-прогоном (F2):** `role` (authority-градация) и `team` как
   *reach-ПОДСТАНОВКА* — аддитивны и data-only, движок 0 правок ✅. НО `team` как *reach-ВСТАВКА* нового ранга
   (node > team > space вложенно) сегодня **НЕ выразима данными**: `writeStack` берёт узел + один контейнер,
   не итерирует цепочку. Полная N-уровневая reach-вставка = **аддитивная, но реальная правка движка**
   (writeStack проходит объявленную цепочку рангов), гейтится вместе с Q-11. ranking contract доказан для
   authority-оси и reach-подстановки, НЕ ещё для reach-вставки. Изменение якоря/enum — **supersede, не
   молчаливый патч.** Ратифицировать каскад как final при открытом Q-11 небезопасно.
   *(F1, минор: движок `run-capability.mjs` не импортируем — нет export + top-level exit; дешёвый R1-рефактор
   без изменения логики, чтобы будущие прогоны переиспользовали резолвер, а не пере-выводили его.)*
4. **Автоматическое сужение делегирования** (`sub-grant = parent ∩ context`) — НЕ смоделировано, это работа
   движка. S9 доказывает лишь корректность резолвера при УЖЕ-суженном sub-grant; если узкий грант просто не
   написан автором — защита не срабатывает. Named residual gap.
5. **Целостность клапана согласия зависит от того, что действие ЧЕСТНО называет свою возможность** — не
   может быть полностью закрыта на уровне данных. Действие, ошибочно/злонамеренно не назвавшее
   `irreversible`-возможность, проходит клапан. Компенсируется мета-гейтом на запись `access` + review минта
   возможностей, но остаточный риск на уровне данных остаётся.

## Validation plan

**Исполненное доказательство (путь A).** `_generated-examples/run-capability.mjs` + `nodes-cap.json`:
реальный корпус (`nodes.json`) + синтетический capability-overlay = единый 10-полный конверт. Каждый

- **Результат: NAIVE 3/15 · FIXED 15/15 · exit 0.** 12 атак (S1–S12) пробивают NAIVE, блокируются FIXED;
  3 легитимных (L1–L3) проходят в обоих — фикс не переблокировал рабочий доступ.
- **Полный цикл доверия:** враждебная сборка (builder) → независимая проверка (critic,

- **Комбинаторное покрытие (порог SYNTHESIS «≥2 комбинатора»):** прогон демонстрирует **OVERRIDE**
  (write-stack fold) и **VETO/CLAMP** (deny-пол + Конституция-потолок в обоих `resolveWrite`/`holdsCapability`)
  — два из четырёх. ACCUMULATE/MERGE (промпты/конфиги) вне области access-теста; порог выполнен.

## Appendix A — узел `policy:access-priority` (реальный 10-полный конверт)

Каскад как ДАННЫЕ (не проза). Добавляется в целевой корпус отдельным «строй». SELECTION комбинатора —
данные (`combinator`, `within_grant_combinator` из закрытого enum); IMPLEMENTATION — движок. `floor`/`ceiling`
— зажимы ПОСЛЕ свёртки, НЕ слои стека.

```json
{
  "id": "policy:access-priority",
  "type": "policy",
  "state": { "status": "active" },
  "edges": [],
  "view": [],
  "visibility": { "level": "visible-to-ai", "valve": "none", "readable_by": ["agent:*", "user:jenya"] },
  "access": { "can_read": ["agent:*"], "can_write": ["agent:ff-personal"] },
  "acts": [],
  "policy_ref": [],
  "body": {
    "target": "access",
    "stack": ["node", "space.override", "space.default", "project", "module"],
    "combinator": "override",
    "within_grant_combinator": "veto",
    "floor": "deny",
    "ceiling": "policy:constitution",
    "note": "Q-14 каскад записан КАК ДАННЫЕ (закрывает mirror-principle gap #1). SELECTION комбинатора = данные (enum override|accumulate|merge|veto); IMPLEMENTATION = движок. FIXED читает это; deny/ceiling — зажимы ПОСЛЕ свёртки, НЕ слои стека."
  }
}
```

> Спутник — `policy:constitution` (потолок): `access.can_write: []` (сама не переписываема данными),
> `protected_namespaces` (`meta:type/`, `meta:envelope`, `policy:constitution`, `policy:access-priority`,
> `meta:cap/core:`), `no_read` — применяются зажимом после свёртки, независимо от грантов/`readable_by`.
