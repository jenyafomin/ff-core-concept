## КОНСЕНСУС

1. **Одна таблица `nodes`, одна БД.** Схема несёт всё; глубину режем из UI, не из БД.
   Минимальный примитив: `nodes(id, parent_id, type, title, body, tags[], status, due, created)`
   + пустая `links` с дня 1.

2. **Две ОРТОГОНАЛЬНЫЕ оси (ключевое различение Reframer).**
   - **Ось вложенности** = `parent_id` (папки, «где живёт узел»; подзадача расширяет родителя).
   - **Ось детализации** = уровни L1/L2/L3 (насколько детально смотрю на ОДИН узел).
   Их нельзя путать: уровни — это НЕ дети в дереве. Иначе дерево засорится и навигация сломается.

3. **Захват = ноль трения.** L1 одной строкой + Enter (Cmd+K → ввёл → исчезло). Никаких папок/
   категорий при вводе. Заметка падает в **инбокс-полку, а не очередь**: без бейджа «непрочитано»,
   без обязанности разбирать. Это гасит «тревогу классификации» (Скептик), которая убивает привычку.

4. **База знаний скрыта первые 2 недели, разблокируется на 14-й день** (явным UI-событием).
   Скептик принял это как «активную детоксикацию от онтологии», а не отложенную ловушку.
   Первые 2 недели мозг привыкает к ОДНОМУ паттерну — задачам.

5. **Ритуал = утренний список задач. Триггер удержания — АДАПТИВНЫЙ** (не фикс 07:25):
   «первое открытие за день» + выбор времени на онбординге; для ночного графика (23:00) —
   уведомление в 22:45. Десктоп Notification API, без сервера, без Telegram.

6. **Две метрики-гейта (Definition of Done среза за 21 день):**
   - **Удержание:** ≥10 внесений задач к дню 21 без напоминаний подряд.
   - **Экономия времени (новая, Скептик):** медианное время захвата мысли ≤15 сек без подсказок.
     Растёт → система создаёт работу, а не экономит.

7. **Отложено, но не закрыто миграцией:** глубокий UI L2/L3, `node_versions` (авторские слои),
   граф/`links` (пустая), продвинутая навигация по иерархии.

### Реалистичный план 3 недель (Pragmatist)
- **Неделя 1:** бэкенд (CRUD `nodes`, фильтр due+status), миграции БД, десктоп-уведомление
  (нативное macOS), минимальный React — список задач работает.
- **Неделя 2:** ритуал-UI (сегодня / просрочено / инбокс), захват L1, дерево папок (parent_id).
- **Неделя 3:** поиск (title+tags), полировка (пустые состояния, ошибки), буфер на баги,
  разблокировка Knowledge-UI на 14-й день. **ЗАПУСК — владелец реально пользуется.**

## НЕРАЗРЕШЁННЫЕ РАЗВИЛКИ

### Развилка X — «task = note»: один тип или два? (минорная, есть компромисс)
- Reframer/User-Advocate/Pragmatist: один тип, `type` = фильтр-проекция → проще ментальная модель.
- **Скептик (бомба):** если задача и заметка — одно, что значит «выполнить» заметку? Checkbox на
  произвольной мысли ломает модель → пользователь начнёт городить папки-костыли «делаю» vs «помню».
- **Компромисс (сходится):** одна таблица `nodes` + `type` (task|note); `status/due` ТОЛЬКО у задач;
  заметка не «выполняется», пока её не повысили до задачи. Структурно один узел — семантически два лица.

### Развилка Y — что значит «×10 уровней / многоуровневый контекст»? (ТРЕБУЕТ ОТВЕТА ВЛАДЕЛЬЦА)
Reframer вскрыл: **«уровень» — омоним, три разные вещи:**
- **(а) Zoom/линза** — прогрессивное раскрытие ОДНОГО текста: L1=title → L2=сниппет/первые N слов →
  L3=полный body. Вычисляемое, без отдельного хранения. Дёшево.
- **(б) Версии/авторские слои** — отдельно ХРАНИМЫЕ редакции одного узла (черновик → конспект → эссе).
  Это `node_versions`. Намёк «×10 объёма с каждым уровнем» похож именно на это.
- **(в) Вложенные узлы** — иерархия через `parent_id` (узел → под-узлы, каждый со своим контекстом).
- Эти три НЕ конкурируют — ортогональны. Но что из них (или комбинацию) имел в виду владелец —
  определяет схему. **Это вопрос к владельцу, не выбор архитектора.**

Минимальный примитив, не закрывающий ни одну дверь (Reframer):
`nodes(id, parent_id, type, title, body, tags[], status, due)` — линзы вычисляются из body,
версии добавляются позже как `node_versions` без переписи схемы, parent_id даёт вложенность.

## Несокращаемые риски
- **Онтология-ловушка** (severity critical): строить иерархию заметок до наличия контента →
  проектирование вместо использования. Гасится: скрыть базу знаний 2 недели + инбокс-без-разбора.
- **Scope-creep «добавлю L2/L3 на неделе 2»** (high/high): держать гейт «резать из UI».
- **Семантический распад task=note** (Скептик): решается `type` + status только у задач.
- **Уведомление игнорируется после 3 дней** (high): адаптивный триггер + конкретика в тексте.

## Минорные dissent (сохранены)
- Скептик: предпочёл бы вырезать заметки полностью; принял скрытие на 2 недели как компромисс.
- Reframer (conf 0.66): без дизамбигуации «×10» модель уровней неустойчива — это gate, не выбор.
- Architect снял своё jsonb `context_levels` в пользу вычисляемых линз + отдельных версий позже.

## РЕШЕНИЯ ВЛАДЕЛЬЦА (2026-06-13, после совета #2)
- **Развилка Y («×10 уровней») → Zoom одного текста + Вложенные узлы.** НЕ хранимые версии.
  Значит схема `nodes(parent_id, title, body)` покрывает обе оси: линзы вычисляются из `title`/`body`,
  вложенность через `parent_id`. `node_versions` НЕ нужен на старте.
- **Приложение → Electron** (десктоп-обёртка; даёт нативные уведомления и единый локальный UX).
- **К Spec пока РАНО.** Владелец хочет сначала посмотреть на концепт под другим углом, найти косяки
  и до-продумать на абстрактном уровне (1-3 вопроса). Альтернатива на столе: построить базовое ядро
  (`nodes`), а детали каждого направления доделать позже, когда станет ясно, из чего они состоят.

## Открытые косяки концепт-уровня (выявлено Председателем, для обсуждения)
1. **AI-gap.** Главный мотив владельца не забросить — «ИИ реально делает работу за меня». Но всё,
   что спроектировали советы, — это место, куда ВЛАДЕЛЕЦ вносит данные (CRUD + уведомление).
   Где ИИ делает работу САМ — не определено. Это риск: построим todo-приложение, а душа проекта (агенты) — нет.
2. **Shape-неизвестность.** Не решено: 11 направлений — это одна форма (узлы+задачи+заметки+метрика)
   или разные машины (Финансы=реестр, Духовное=дневник состояний, Разработка=проекты/код)? Ответ
   определяет, работает ли стратегия «одна база → растим направления» или направлениям правда нужны
   отдельные ядра. Это прямой ключ к «построить базу, потом доделать».
3. **Capture-источник.** Система живёт захватом, данные разбросаны. Главный вход не определён:
   голос (Whisper уже стоит), пересланные сообщения, ручной ввод, или ИИ сам тянет из других инструментов.
