- **Status:** review

- **Date:** 2026-06-13
- **Метод:** ask-council, 7 ролей, 2 раунда (независимый анализ → перекрёстный разбор)
- **Related:** [VISION.md](../product/VISION.md), [ANALYSIS-2026-06-12-multi-lens.md](../product/ANALYSIS-2026-06-12-multi-lens.md)

## Вопрос
Какова связующая архитектура и первый срез (~3 недели до пользы) для системы, которую
владелец хочет строить как глубокие отдельные приложения-направления, которые при этом
должны плотно связываться? Разрешить T1 (Hub нечего обозревать), T2 (отдельные БД vs
связность), T3 (фронтенд для N модулей vs быстрая польза).

---

## КОНСЕНСУС (совпала и позиция, и аргументация)

1. **Единое хранилище, НЕ N баз данных.** Единогласное вето на «БД на модуль».
   Монорепо + одна Postgres (или SQLite) со схемами/неймспейсами per-domain.
   «Отдельность» = границы в КОДЕ + представления/фильтры в UI, не инфраструктура.
   → **T2 разрешено.** Связать N отдельных БД по живому графу = распределённые транзакции
   (саги/2PC) без команды → гарантированный заброс. Внутри одного стора связь = JOIN.

2. **Hub — это проекция (read-model), а не первый модуль.** Пустой Hub демотивирует
   («витрина пустого магазина»). → **T1 разрешено:** Hub не строится отдельно первым,
   он рождается как фильтр над данными, как только данные появятся.

3. **Не строить 11 модулей и не стартовать их параллельно.** Главный враг — смерть
   в проектировании. Больше модулей разом → НИЖЕ итоговая связность (долг внимания).

4. **Стартовая модель данных = одна таблица tasks/nodes** с `parent_id` (иерархия,
   «подзадача расширяет контекст родителя») + теги-направления. Эта таблица ОДНОВРЕМЕННО
   есть Hub, Финансы, Планирование — через фильтры. К этому независимо пришли 5 ролей.

5. **`tags[]`, а не `ENUM module`.** ENUM хардкодит 11 направлений в схему (12-е =
   миграция) и запирает в дерево; реальная жизнь многосвязна (задача может быть и в
   Финансах, и в Здоровье). Теги-массив стоит столько же, но не запирает.

6. **Дешёвая таблица `links(from, to, type)` с дня 1** (1 строка DDL, пустая до ~месяца 4)
   как страховка от полного графа. Полноценную графовую БД и event bus — отложить.

7. **Event bus выброшен** — даже его автор (Reality-Analyst) согласился: для соло это
   неотлаживаемый оверхед. Модули читают чужие данные только через сервис-функции/вью
   (дисциплина в коде), не через шину.

8. **Нужна фальсифицируемая метрика удержания с дня 1 + внешний триггер** (уведомление/
   дайджест), который тянет назад. Без триггера retention → 0.

## НЕРАЗРЕШЁННЫЕ РАЗВИЛКИ (выбор за владельцем — зависят от твоего реального поведения)

### Развилка A — Первый интерфейс: Telegram-захват vs локальный фронтенд
- **Если веришь, что привычка решает всё** (Адвокат пользователя, conf 0.72; Future-Self):
  привычка формируется в первые 7 дней или никогда. Telegram-ввод = петля онбординга,
  должен быть с дня 1, но ТОЛЬКО ввод (`/add`, `/list`, без callback-логики) →
  **сначала Telegram-захват, фронтенд на неделе 2.**
- **Если веришь, что нужен реальный экран** (Прагматик 0.74, Reality-Analyst 0.82,
  Архитектор 0.78): ты сам хотел фронтенд; бот = 6-10ч холодного старта и риск стать
  отдельным проектом; Telegram = продюсер событий, не центр →
  **сначала локальный фронтенд (React+Vite+Postgres), Telegram как ambient-capture на неделе 4.**

### Развилка B — Первый контент/ритуал: Финансы (транзакции) vs Задачи (с датами)
- **Если нужен объективный сигнал** (Reality-Analyst 0.82): Финансы — единственное
  направление с ежедневно ВЕРИФИЦИРУЕМЫМ сигналом (транзакция объективна; «закрытая
  задача» субъективна, её можно отметить формально). Gate: 5 ручных транзакций/нед × 3 нед.
- **Если нужен минимум поверхности** (Скептик 0.71, dissent): совет сошёлся на
  «Финансы+Hub» слишком легко — это комфортный средний вариант. Настоящий минимум:
  ТОЛЬКО задачи с датой + одно уведомление в день; Финансы — неделя 3.
- **Непроверенное допущение, которое назвал Скептик:** будет ли владелец вообще вводить
  данные ЕЖЕДНЕВНО? Это поведенческая бомба, не архитектурная. Habit = триггер+рутина+награда.

### Развилка C — почти закрыта
Форма иерархии/связей: `parent_id` + `ltree`/closure-table (Архитектор) против
`links`-таблицы (Future-Self). Сводится к: tasks/nodes + `tags[]` + `links` с дня 1,
графовую БД отложить. Остаточное расхождение минорное (ltree vs links для пути).

## ВЗВЕШЕННАЯ РЕКОМЕНДАЦИЯ (там, где есть консенсус)

**Связующая архитектура (высокая уверенность, ~0.8):**
- Монорепо, одна БД (Postgres). Никаких БД-на-модуль.
- Таблица `nodes` (или `tasks`): `id, type, parent_id, tags[] (направления), title,
  context, status, due, created`.
- Таблица `links(from_id, to_id, rel_type)` — пустая, но с дня 1.
- «Направление» = сохранённый фильтр (`tags @> '{finance}'`), не отдельное приложение.
- Hub = вью «всё» над `nodes`. Модули = вью с фильтром. Глубина (многоуровневые задачи) =
  `parent_id`-рекурсия. Кросс-связи = `links`.
- Без event bus, без графовой БД, без микросервисов на старте.
- «Глубокие отдельные приложения» сохраняются как UX-эмоция (отдельные «двери»-вью),
  но за ними одна комната (один стор). Отпочковать реальный отдельный модуль — позже,
  от зрелой схемы, если правда понадобится.

**Первый срез (~3 недели):** одна таблица + один тонкий интерфейс (развилка A) +
наполнение одним типом контента (развилка B) + ежедневный триггер + метрика удержания.

**Развилки A и B — отдать владельцу:** они зависят от того, будешь ли ты реально открывать
экран каждый день или тебе нужен ноль трения через Telegram; и даёт ли тебе финансовый
ритуал больше, чем задачи. Это знаешь только ты.

## Несокращаемые риски (severity H, названы любой ролью)
- **Поведенческая бомба:** проект мёртв, если владелец не вводит данные ежедневно —
  архитектура вторична. Нужен внешний триггер с дня 1 (Скептик, Future-Self).
- **Scope-creep до 11 направлений** убивает фокус (very high likelihood — Скептик, Прагматик).
- **Telegram-бот разрастается в отдельный проект**, если дать ему callback-логику (Прагматик).
- **Hub без данных демотивирует** на неделе 1-2 (несколько ролей).

## Минорный dissent, сохранён
- Reframer изолирует несогласие против ENUM как фундамента (разрешено через `tags[]`).
- Адвокат пользователя держит dissent: «откладывать Telegram = строить продукт без точки входа».

## РЕШЕНИЯ ВЛАДЕЛЬЦА по развилкам (2026-06-13)
- **Развилка A → Локальный фронтенд первым** (React+Vite+Postgres). Telegram — ambient-захват позже.
- **Развилка B → Задачи с датами** как ежедневный ритуал. ВАЖНОЕ ДОПОЛНЕНИЕ: заметки/мысли
  строятся как **база знаний** с многоуровневыми папками и разным уровнем контекста
  (смыкается со Smart-сообщениями L1/L2/L3 из VISION §3.3 и с `parent_id`, расширяющим контекст).
