# Карта агентного слоя (S-C) + как 3 trust-бага его гейтят + секвенсинг

> Линза = архитектор (границы/контракты/точки доверия). НЕ стройка, НЕ код. Свод из существующих карт +
> прямого чтения движка. Тезис проверяется параллельно — здесь честная структурная проверка, не подыгрыш.

---

## 1. ЧТО ТАКОЕ АГЕНТНЫЙ СЛОЙ (S-C) в нашем дизайне

**Ценность одной фразой (census 03):** слой, который ЧИТАЕТ граф, ДЕЛАЕТ работу, ПИШЕТ результат обратно
(write-back), живёт как модульный плагин поверх субстрата. Северная звезда проекта: *доверяемая композиция* —
агент растит единицу, но не ломает **тождество / правду / согласие**.

**Минимальная единица работы S-C = один write-back-цикл:**
`agent → view()/resolve() (читает разрешённую грань) → делает работу → write(act) (append акт обратно)`.
Единственный кросс-модульный шов, к которому привязан любой потребитель — порт **`EngineClient`**
(`ports/engine-client.ts`, ЗАМОРОЖЕН: 4 метода `view · resolve · write · rebuild`). Агент — это новый
ВЫЗЫВАЮЩИЙ через этот шов, не новый примитив.

**Что уже есть в коде:** РОВНО ОДИН реальный агент — `packages/rental-balance/src/agent/balance-observer.ts`
(читает граф, считает остаток, пишет `observation` обратно; первый write-back-цикл). До него — 0 агентов.

**Что пусто:** контракт `brain↔agents` (`core/03-contract/INDEX.md`) = только РАМКА («клапан на необратимое»),
НИ ОДНОГО конкретного правила записи агента. Дизайн `01-orchestration/` (STATE·PLAN·TASK·LOOP) — proposed,
НЕ ратифицирован. То есть S-C сегодня = один захардкоженный доверенный агент + пустой контракт.

**Точки доверия (где живёт «не сломать»):**
- **READ-гейт:** каждое чтение агента идёт через `resolve()` PEP (в `view-compiler`). Сегодня read гейтится.
- **WRITE-гейт:** каждая запись идёт через `Engine.write()` → `admit()` (нет inline-PII) + `admitHome()`
  (один-дом) + идемпотентность. **Но НЕ через `resolveWrite` — авторитет писателя НЕ проверяется.**
- **Клапан (valve):** на необратимые внешние действия (концепт, не в коде записи-в-граф).

**Ключевой структурный вывод:** «агентный слой» как ЕДИНИЦА уже существует (balance-observer). Чего нет —
это **доверяемый** агентный слой для >1 / плагинных / потенциально враждебных агентов. Ровно это и есть
северная звезда. Именно её гейтят 3 бага — не «существование слоя», а его **доверяемость**.

## 2. КАК 3 TRUST-БАГА ГЕЙТЯТ S-C (по одному, честно)

Общий принцип: пока агент = один доверенный захардкоженный `balance-observer`, ни один баг не «жмёт»
(он не враждебен). Баги гейтят ГЕНЕРАЛИЗАЦИЮ до многих/плагинных агентов — то есть *доверяемую композицию*.

### Баг-1 · `T-write-pep-unwired` (`engine.ts:73-108`) — write-половина PEP не подключена
- **Факт:** `resolveWrite` (`resolve.ts:191-231`) построен и подключён в generic `resolve()` (`:120`), но
  `Engine.write()` его НЕ ЗОВЁТ — 0 продакшн-вызовов. Write-путь гейтит только PII/один-дом/дедуп, НЕ
  авторитет. Прямое нарушение I-7 (resolve() = единственный PEP, ни один путь не обходит).
- **Какую способность S-C блокирует:** безопасный **write-back для НЕдоверенного агента**. Сейчас агент
  может записать ЛЮБОЙ акт на ЛЮБОЙ узел как ЛЮБОЙ `actor`. «Агент не ломает тождество/правду» — ложь в
  тот момент, когда агент не balance-observer. **НА КРИТИЧЕСКОМ ПУТИ — это и ЕСТЬ write-гейт слоя.**

### Баг-2 · `T-grant-forgery` (`resolve.ts:136-141`) — capability форжится на READ-пути
- **Факт:** `grantValid()` доверяет самозаявленному `body.minted_by` БЕЗ проверки; `canMintGrant`/
  `canMintCapability` имеют 0 call-sites → агент минтит себе грант и проходит `holdsCapability` на
  read-пути (`:247`). Эксплуатируемо СЕГОДНЯ, независимо от бага-1 (read vs write путь).
- **Какую способность S-C блокирует:** **доверяемое ЧТЕНИЕ** агента по согласию/видимости (Ц-7 Согласие).
  Агент, форжащий грант, читает любую PII мимо consent-scope. «Не ломает согласие на чтении» — ложь.
  **НА КРИТИЧЕСКОМ ПУТИ к read-стороне S-C.** Независим от бага-1 → параллелится.

### Баг-3 · `T-policy-node-provenance` (`loader.ts:8-11` + `store-durable-fs.ts:191-192`) — перезапись policy-узла
- **Факт:** акт с `source_ref='policy:constitution'` перезаписывает реальный узел через last-write-wins;
  admission/projection не проверяют namespace/source_ref. Форж самой Конституции. Эксплуатируемо СЕГОДНЯ.
- **Какую способность S-C блокирует:** **целостность правил, на которые опираются фиксы бага-1 и бага-2.**
  Конституция — потолок, к которому клампится каждый resolve() (движок даже отказывается стартовать без неё,
  `engine.ts:CONSTITUTION_ID`, но НЕ защищает от перезаписи). Почини write-PEP и гранты — атакующий просто
  перепишет policy-узел и выдаст себе всё. **НА КРИТИЧЕСКОМ ПУТИ — это ПОЛ (floor) под остальными двумя.**
  - Нюанс: у бага-3 ДВА слоя. (a) `canWriteNamespace` УЖЕ существует в `DEFAULT_META_GATES` (проверяет
    `protected_namespaces` + `core:manage-core`) — но НЕ зовётся, потому что write-PEP не подключён (= баг-1).
    (b) даже с подключённым PEP, projection/loader last-write-wins по `source_ref` (`store-durable-fs.ts:191-192`)
    — ОТДЕЛЬНЫЙ deref, которому нужен свой guard. То есть баг-3 частично = симптом бага-1 + отдельная дыра проекции.

**Вердикт честности:** все 3 НА критическом пути к *доверяемому* S-C. Ни один не «подыгрыш» — каждый
привязан к конкретной способности (write-авторитет / read-согласие / целостность правил). НО: к УЗКОЙ цели
«просто сделать второго агента-демо» — не гейтят (демо-агент доверенный). Это фейн-развилка (см. §5).

## 3. СЕКВЕНСИНГ

```
[OWNER-GATE-0: premise-check timebox 10 мин] — баги реальны (verified 0 call-sites), фикс дёшев?
        │  (уже ~сделан на бумаге threat-model; остаётся «дёшев и не ре-открывает S3-формы»)
        ▼
[OWNER-GATE-1: FORK-U3 — write-principal model: force-bind vs attest]  ◄── НЕСУЩИЙ, см. §4
        │  малое решение владельца; ЯКОРЬ для КОРРЕКТНОГО фикса бага-1
        ▼
┌─ PARALLEL (разные файлы, разные builders) ─────────────────────────┐
│  Баг-3 (namespace/policy integrity)  ← ПОЛ, желательно первым       │  разные пути:
│  Баг-1 (wire resolveWrite в write)   ← зависит от GATE-1 (actor)    │  engine.ts / resolve.ts /
│  Баг-2 (grant-forgery, mint-authority) ← read-путь, независим       │  loader.ts+store
└────────────────────────────────────────────────────────────────────┘
        ▼
[SERIAL: ОДИН объединённый адверсариал-гейт] — forge-actor · forge-grant · forge-policy → ВСЕ падают
        ▼
[Контракт brain↔agents — скелет] (design; можно СТАРТОВАТЬ параллельно фиксам, ЛАНДИТ после)
        ▼
[S-C: 2-й реальный агент / >1 write-back над доверяемым гейтом]  ← собственно способность слоя
        ▼
[OWNER-GATE-2: F-D санкция] → реальные данные (R4 PII-барьер, отдельный гейт)
```

- **Строго serial:** GATE-1 → фиксы (актор-модель якорит корректность бага-1); фиксы → объединённая
  адверсариал-верификация (три форжа должны падать ВМЕСТЕ, не по-одному); гейт → S-C-слой → реальные данные.
- **Параллелится:** сами 3 фикса (разные файлы) РАЗНЫМИ builder-агентами; скелет контракта как design.
  ⚠️ но общий концептуальный якорь = GATE-1, и верификация — общая. Волнами 3-6 агентов (правило sync-под-шлюзом).
- **Owner-гейты:** (0) premise-check; (1) **FORK-U3 — обязателен до корректного фикса бага-1**; (2) F-D данные.

## 4. ЧТО МЫ УПУСКАЕМ (несущий пропущенный вопрос между «баги» и «слой»)

**Пропущенный несущий вопрос = МОДЕЛЬ ИДЕНТИЧНОСТИ АГЕНТА КАК WRITE-PRINCIPAL (FORK-U3).**
Из actor-model §3/§5: write-principal-seam НЕ построен — `Engine.write()` берёт `act.actor` ВЕРБАТИМ; нет
write-choke-point, резолвящего surface-identity → principal. FORK-U3: **force-bind** (движок ставит actor =
резолвнутый principal) vs **attestation-stamp** (клиент заявляет, движок штампует «заявлено, не доказано»).

**Почему это делает фикс багов ПРЕЖДЕВРЕМЕННЫМ, если не ответить:** нельзя КОРРЕКТНО подключить write-PEP
(баг-1), не ответив «против КАКОГО актора гейтит `resolveWrite` и как этот актор аутентичен». Если подключить
`resolveWrite` гейтя на `act.actor`, пока actor — самозаявленный (нет principal-seam), ты построишь гейт,
проверяющий самозаявленную личность — **ТОТ ЖЕ класс дыры, что grant-forgery** (самозаявленный `minted_by`).
Ты «починишь» баг-1, переместив форж с гранта на актора. → FORK-U3 — не downstream-мелочь, а ПРЕРЕКВИЗИТ
корректного фикса бага-1.

**Вторичное (не немедленный гейт):** F2 data-subject/consent-binding (цель стирания = opaque `source_ref`,
не личность; `erasure.ts` без consent-поля) — несущее для Ц-7/стирания, но не для авторизации read/write S-C.
Отметить, не блокировать этим первый шаг.

**Также:** контракт `brain↔agents` пуст. Мы хардним гейт (`resolveWrite`) без спеки, ЧТО он должен пускать.
Движковую capability-модель можно строить независимо, но скелет write-контракта = реальный design-артефакт
S-C, ради которого баги — пререквизит-инфраструктура. Не потерять.

## 5. САМОКРИТИКА (где карта может быть неверной)

1. **Я читаю synthesis-черновики, не пере-трассировал весь код сам.** «0 call-sites» у `canMintGrant`/
   `resolveWrite` — из threat-model критика (верю, но не пере-грепал каждую строку). Если где-то есть
   подключение, которое я не нашёл — гейтящая сила бага слабеет. *(Дёшево проверяемо грепом перед фиксом.)*
2. **Фрейм «все 3 на критпути к S-C» верен только для ДОВЕРЯЕМОГО-МУЛЬТИ/плагинного слоя.** Узкое чтение
   «сделать balance-observer #2» их не требует. Если следующий шаг владельца — демо, а не генерализация
   доверия, секвенсинг меняется. Это фейн-развилка — вынести владельцу, не предрешать.
3. **FORK-U3 как «пререквизит корректного бага-1» — моё арх-утверждение.** Контр-взгляд: можно подключить
   `resolveWrite` гейтя на capability-актора СЕЙЧАС, а аутентичность-актора трактовать как ОТДЕЛЬНЫЙ поздний
   слой (attest-default) — это строго лучше «нет гейта». Тогда FORK-U3 = should-decide, не hard-block.
   Я склоняюсь к «несущий», но помечаю мягкое чтение.
4. **Баг-3 — один баг или два?** Я вывел два слоя (write-PEP-namespace vs projection-path-namespace) из двух
   файловых ссылок; может оказаться одним фиксом. Влияет на параллелизм.
5. **Порядок «пол первым» (баг-3) vs «параллельно»** — я поставил параллельно с общей верификацией; если
   фиксы 1/2 читают правила из policy-узлов во время своих тестов, баг-3 может понадобиться СТРОГО первым.
