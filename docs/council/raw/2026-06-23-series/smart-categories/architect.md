# Тема №2 — Умные категории (гибкие типы, N-087): архитектурный разбор

- **Тема:** Умные категории — где живут (control-plane-узел vs facet-тег vs под-тип), как несут поля/валидацию/уровни, как НАСЛЕДУЮТСЯ во вложенности БЕЗ вскрытия payload, авто-связи «только в группах», пересечение с открытым реестром типов и с Q3.
- **Роль:** system-architect (структурное мышление — границы, контракты, потоки данных).
- **Дата:** 2026-06-23
- **Статус:** raw (глубокий разбор; не финальная схема). Фаза = ДИЗАЙН, без кода, без «строй».
- **Опирается на:** ADR-0002 (паспорт, ровно один home, инвариант несущести, control-plane=3 рода, теги-фасеты=рёбра-категории), `SYNTHESIS-2026-06-23-stress-test.md` (вариант=тип+линза; home≠категория; multi-schema реестр), `conception-mapping.md` (category как узел-цель facet-of; ~28 типов), `STRATEGY-2026-06-23-smart-categories.md` (L1-L3 вектор владельца), THREAD N-042/N-074/N-075/N-081/N-086/N-087.

## 0. Дисциплина, которую держу (чтобы не растолстел паспорт)

Три инварианта из зафиксированной модели гейтят каждый выбор ниже. Выписываю явно, потому что концепт «умные категории» соблазняет нарушить ровно их:

- **I-1 Несущесть (ADR-0002 §Контекст).** Поле несущее ⟺ движок/агент решает, КАК обращаться с ячейкой, **не вскрывая payload и не зная тип**. Всё прочее — payload, ребро или control-plane. Дискриминатор валидации берётся из паспорта (`schema`), не из значения payload.
- **I-2 Принадлежность ⟂ ссылка (стресс §1).** Ровно один `home`-ребро = каскад-спина (лес, ацикличен). Любая иная связь (`facet-of`, `kind-of`, `calls`, `version-of`) — обычные рёбра, могут циклиться/фан-инить свободно. Это позволяет держать многомерность без взрыва каскада.
- **I-3 home ≠ категория для одних членов (стресс §2C).** Один узел не может быть и `home`-контейнером, и `facet`-категорией для ОДНИХ И ТЕХ ЖЕ членов — иначе перенос члена из home молча снимает ярлык. (Это и есть открытый спор Q3.)

Где маппинг ниже напрягает инвариант — флагую в §7, а не гну модель молча.

## 1. Главный вопрос: категория = узел control-plane vs facet-тег vs под-тип? — РЕШЕНИЕ

**Категория — это НЕ один род, а ДВА разных феномена, которые владелец (N-087) свернул в одно слово. Их надо расщепить, иначе спор неразрешим.** Уверенность: высокая.

Феномен раскрывается уже в N-042 («теги двух родов»): (а) тег-ТИП «что это»; (б) тег-категория «к чему относится». Умная категория владельца (N-087) несёт ОБА смысла сразу — отсюда путаница «может совпадать с типами» (L2 §5). Расщепляю на две оси, которые в модели живут по-разному:

### 1a. Категория-как-классификатор (членство = `facet-of`-ребро; цель = узел)

Это «к чему относится» (N-042б). Чистая многомерность N-081: файл — `service` × `data-model` × `core-kernel-area` одновременно.

- **Где живёт:** целевой узел типа `category` (НЕ control-plane-род; обычный узел-цель) + членство = ребро `facet-of` (без `home`, может быть сколько угодно).
- **Что НЕ несёт:** валидацию/обязательные поля членов. Классификатор не диктует форму. Это ровно то, что ADR-0002 уже зафиксировал в Supersedes #9 («теги-фасеты → рёбра-категории»).
- **Почему не под-тип:** под-тип менял бы `schema` в паспорте → менял бы валидатор → но один файл в 4 категориях не может иметь 4 валидатора. Многомерность и единственность валидатора несовместимы. Значит классификатор обязан быть РЕБРОМ, а не частью `type`/`schema`.

### 1b. Категория-как-уточнённая-форма (= ТИП открытого реестра; «вариант=тип» из стресса)

Это случай N-087, который владелец имеет в виду под «свои уровни определения / dropdown у покупки, которого нет у продажи». Здесь категория НЕСЁТ поля/валидацию. Это уже не классификатор — это **уточнение схемы**.

- **Где живёт:** отдельный `model-def` (ТИП-узел) в открытом реестре: `deal-buy`, `deal-sell` — оба `variant-of → deal` (control-plane-ребро). `deal-buy` несёт доп. поля/dropdown, которых нет у `deal-sell`.
- **Дискриминатор:** в паспорте (`schema: deal-buy@1`), НЕ в payload. Движок выбирает валидатор по паспорту → I-1 цел. Это ровно «вариант=тип» из стресс-синтеза §3 и I-3-инварианта реестра.
- **«Один логический deal» собирается ЛИНЗОЙ** (`kind-of: deal` через `variant-of`-рёбра). Владельцу видно «сделки» как один срез; движку — безопасные разные типы.

### 1c. Вердикт по «vs»

| Что владелец называет «категория» | Реальный род в модели | Несёт форму/валидацию? | Дискриминатор |
|---|---|---|---|
| «к чему относится», срез, перелинковка (N-042б, N-081) | **узел `category` + ребро `facet-of`** | НЕТ | — (членство = факт ребра) |
| «свои уровни определения / dropdown покупки» (N-087 L2.2) | **ТИП-узел `model-def`, `variant-of → базовый тип`** | ДА (это его суть) | паспорт `schema`, не payload |

**Под-тип как ОТДЕЛЬНЫЙ механизм — отклонён.** Он либо сводится к 1b (вариант=тип с `variant-of`-ребром), либо нарушает I-1 (если «под-тип внутри одного `type` по значению payload»). Третьего непротиворечивого варианта нет. Уверенность: высокая — это прямое следствие I-1+I-3, уже подтверждённых двумя стресс-тестами.

**Что это даёт владельцу честно:** его интуиция «категории и типы должны играться/быть связаны» (N-081) — ПРАВА, но связь идёт через `variant-of`-ребро в control-plane, а не через слияние категории и типа в один род. «Может совпадать с типами» (L2.5) реализуется тем, что 1b-категория ПРОСТО ЕСТЬ тип. Граница «тип↔категория» не размыта — она ПРОХОДИТ ровно по линии «несёт форму (тип) vs только классифицирует (facet)».

## 2. Как категория несёт свои поля/валидацию/уровни

Разделение §1 диктует разные носители для разных «несёт»:

### 2a. Поля и валидация (только 1b — категория-как-тип)

Несёт **`model-def`** (ТИП-узел), контракт из ADR-0002 §4: `{ name, version, payload_schema, validate(node)→ok|errors }`. Вариант-тип наследует базовую схему + добавляет свои поля:

```
model-def: deal           payload_schema: { amount, counterparty, date }
model-def: deal-buy        variant-of → deal
                           payload_schema_delta: { + seller_rating: dropdown[A..D], + warranty_months }
model-def: deal-sell       variant-of → deal
                           payload_schema_delta: { + delivery_terms: enum, + invoice_ref }
```

- **Слияние схем = функция ДВИЖКА над `variant-of`-цепочкой** (а не payload). Движок собирает эффективную схему = base ∪ delta вдоль `variant-of`-рёбер ДО валидации, читая только паспорта+control-plane-узлы. payload не вскрывается для ВЫБОРА валидатора (выбор — по `schema` в паспорте); вскрывается только для самой проверки уже выбранной схемой — это легально (валидатор по определению читает payload своей же ячейки).
- **«не всё всем; свои ограничения, заложенные механиками» (N-081)** = delta-схема варианта + (опц.) предикаты-узлы (лестница constraints из канваса universal-node: декл.→условн.→предикаты-узлы). Уверенность: высокая на декларативной части, средняя на предикатах (это E2/движок).

### 2b. «Уровни определения» — ОСТОРОЖНО: омоним, расщепить (важно)

Владелец «уровни определения» (N-087) ≠ ось `level?` (why/what/how/data) из ADR-0002. Это РАЗНЫЕ вещи, их легко спутать:

| «уровень» владельца | что это на самом деле | носитель |
|---|---|---|
| «у покупки Категория2 содержит dropdown, которых нет у продажи» (N-087 L2.2) | **доп. поля/ограничения варианта** | delta-схема `model-def` (§2a) |
| «категории вложенные, категория в категории» (L2.3) | **иерархия классификации** | `subcategory-of`-рёбра (см. §3) |
| ось абстракции why/what/how/data (ADR-0002 §1) | **проекция линзы** | `level?` тег + ось линзы |

Если не расщепить — `level?` начнёт нести два смысла (как ADR-0002 §2(в) уже флагует риск двойного смысла). **Рекомендация: «уровни определения категории» НЕ переиспользуют поле `level?`; это delta-схема (2a) + глубина классификации (3).** Уверенность: высокая (прямой анти-паттерн смешения осей).

### 2c. «Уровни» как уточнение валидации по глубине вложенности

Если владелец имеет в виду «чем глубже категория, тем строже/специфичнее форма» (покупка → покупка-авто → покупка-авто-б/у, каждый уровень добавляет поля) — это §3 (наследование delta вдоль цепочки), а НЕ новое поле паспорта. Покрывается тем же `variant-of`/`subcategory-of` + слиянием delta. Ничего нового в ядре.

## 3. Как поля/валидация/уровни НАСЛЕДУЮТСЯ во вложенности — БЕЗ вскрытия payload (инвариант I-1)

Это сердцевина вопроса. Ключ: **наследование идёт по РЁБРАМ control-plane, которые движок читает без вскрытия payload — ровно как level-из-топологии в ADR-0002 §1.** Два разных наследования, не путать:

### 3a. Наследование ФОРМЫ (схемы) — по `variant-of` / `subcategory-of` (НЕ по home)

- Цепочка `deal-buy --variant-of--> deal` — это control-plane-рёбра между ТИП/категория-узлами, а НЕ принадлежность ячеек.
- Эффективная схema ячейки = слияние delta вдоль этой цепочки. Движок проходит цепочку, читая control-plane-узлы (их payload — это и есть схема, читать его движку легально: он и есть носитель контракта). **payload САМОЙ ЯЧЕЙКИ не вскрывается для выбора/сборки схемы** — выбор стартует от паспортного `schema`. I-1 цел.
- **Вложенные категории (L2.3)** = `subcategory-of`-рёбра между category-узлами. Если 1a-категория (классификатор) — наследование НЕ формы, а только «членство в под-категории ⇒ членство в родительской» (транзитивность facet для линзы-запроса). Если 1b-категория (тип-вариант) — наследование delta-схемы (3a).

### 3b. Наследование КОНТЕКСТА (sensitivity/scope/дефолт-линза) — по home-спине (ADR-0002 §2а)

Это уже зафиксировано в ADR-0002: каскад только по home-ребру + opt-in `cascade:true`. Категория-классификатор (1a) **НЕ каскадит контекст** — она не home. Это и есть защита I-3.

### 3c. Критический риск: тень имён полей при мультиродителе (тот самый баг N-070/Q4)

Файл faceted в две 1b-категории, каждая объявляет поле `budget` по-разному — чья схема? **На DAG `nearest-first` не разрешает однозначно.** Это уже пойман как CRITICAL (стресс §6). Архитектурное решение:

- **Форму инжектирует ТОЛЬКО `home`-спина + `variant-of`-цепочка от паспортного `type`.** Категории-классификаторы (`facet-of`) **НИКОГДА не инжектируют поля/дефолты схемы.** Это превращает «какая из 4 категорий диктует форму» в несуществующий вопрос: ни одна. Форму диктует ровно один `type@version` (паспорт) + его `variant-of`-предки (линейная цепочка в реестре, не DAG ячеек).
- **Правило-инвариант (записать):** *классификатор (`facet-of`) не несёт payload-схему членов; форму несёт только `type`/`schema` ячейки и его `variant-of`-цепочка.* Это снимает Q4 для случая категорий начисто. Уверенность: высокая.
- Если владелец ХОЧЕТ, чтобы категория диктовала форму (1b) — тогда это не `facet-of`, а смена `type` ячейки (она становится `deal-buy`, а не «`deal` с ярлыком buy»). Дискриминатор переезжает в паспорт. Это цена непротиворечивости, которую надо назвать владельцу.

## 4. Авто-связи «только в группах» = правило какого узла

Владелец: «часть связей авто (только в определённых группах), часть явно» (N-087 L2.4, корнями в N-042 «связи образуются автоматически»). Архитектурно это **правило-узел**, не свойство ячейки.

- **Где живёт:** узел рода **ПАТТЕРН** (control-plane, ADR-0002 §4: `{ compose(подграфы)→подграф, recursion_terminator, maxDepth }`), расширенный полем-условием `scope` = «в какой группе/категории это правило активно».
- **Контракт авто-связи-правила (предварительно):**
  ```
  pattern: auto-link-rule
    when_scope: <category|container id>      # «только в этой группе» — где правило живёт
    match: <предикат над паспортами кандидатов: type/level/facet/время>
    emit_edge: { rel: <напр. relates-to>, derived: true, rule_ref: <self id> }
  ```
- **Инвариант (из ADR-0002 §Движок + стресс §2A):** авто-созданные рёбра = `derived:true` + `rule_ref`, **read-only, не файл-истина** (движок вывел, не человек). Ручная связь = файл; авто = производное движка. Это уже зафиксированный инвариант — авто-связи просто его частный случай.
- **«Только в группах»** = область действия правила ограничена `when_scope`: движок применяет правило, обходя членов группы (по `facet-of`/home), а не весь граф. Это и защищает от взрыва (правило не сканирует миллион узлов — только scope).
- Уверенность: средняя-высокая. Род (ПАТТЕРН) ясен; точная форма предиката и движок применения — E2/движок-спека.

**Тонкость безопасности:** авто-связь, которая порождает ребро, влияющее на КЛАПАН или promotion (напр. авто-`cites`), — это first-party-only (R4 ADR-0002). Сторонний код может авто-создавать только нейтральные рёбра (классификация/relates), не enforce-влияющие. Флаг в §7.

## 5. Пересечение с открытым реестром типов

Умные категории НЕ вводят новый род в control-plane. Они раскладываются на УЖЕ существующие 3 рода (ADR-0002 §4) + узел-цель:

| Аспект умной категории | Где в реестре | Новый род? |
|---|---|---|
| Категория-классификатор (1a) | обычный узел `category` (цель `facet-of`) | НЕТ — это узел-цель, не control-plane-род |
| Категория-как-вариант-формы (1b) | `model-def` (ТИП) + `variant-of`-ребро | НЕТ — открытый реестр типов уже есть |
| «Свои уровни/dropdown» | delta-схема в `model-def` | НЕТ |
| Вложенность категорий | `subcategory-of` (1a) / `variant-of` (1b)-рёбра | НЕТ |
| Авто-связи в группах | `pattern`-узел + `derived`-рёбра | НЕТ |
| Срез/поиск по пересечению осей | `lens` (пересекает facet-оси + type) | НЕТ |

**Вывод: умные категории — это КОМПОЗИЦИЯ имеющихся примитивов, а не новый род.** Это ровно дисциплина «новый род только если вынуждены». Мы НЕ вынуждены. Открытый реестр типов растёт горизонтально (добавить вариант = добавить `model-def`-узел), не вертикально (не трогаем ядро/паспорт). 0 новых обязательных полей паспорта. Уверенность: высокая.

**Честная оговорка о «совпадает с типами» (L2.5):** граница тип↔категория не размыта, а ДВОЙСТВЕННА по смыслу слова «категория»: 1a-категория ≠ тип (классификатор), 1b-категория = тип (вариант). Владелец прав, что «играются между собой» — через `variant-of`. Но в любой конкретной ячейке роль однозначна: либо `facet-of`-членство (не диктует форму), либо `schema` в паспорте (диктует). Двойственность — на уровне СЛОВА, не на уровне механики. Это и снимает «размытость».

## 6. Пересечение с Q3 (группа = и папка, и категория?)

Q3 (N-086, отложен в консилиум) и умные категории — ДВА РАЗНЫХ вопроса, которые легко слить:

- **Q3 спрашивает:** может ли ОДИН узел быть и `home`-контейнером (папкой), и `facet`-категорией для ОДНИХ И ТЕХ ЖЕ членов (нарушение I-3).
- **Умные категории НЕ требуют этого.** 1a-категория — отдельный узел-цель, НЕ папка. 1b-вариант — тип, тоже не папка. **Умные категории живут целиком на стороне `facet-of`/`variant-of`, ни разу не претендуя на home.** Поэтому умные категории МОЖНО проектировать НЕ дожидаясь Q3 — они в безопасной зоне I-3.

- **Где они СОПРИКАСАЮТСЯ:** если владелец захочет, чтобы папка-контейнер (home) ОДНОВРЕМЕННО навешивала ярлык-категорию на содержимое автоматически («положил файл в `auth/` ⇒ он автоматически в категории auth») — это И ЕСТЬ Q3, и это нарушает I-3 (перенёс из `auth/` → потерял ярлык). Развязка через умные категории: **авто-связь-правило (§4) с `when_scope: folder:auth` может ЭМИТИТЬ `facet-of → category:auth` как `derived`-ребро.** Тогда:
  - home-папка остаётся чистым home (каскад контекста);
  - ярлык-категория — отдельный `derived`-facet, навешенный правилом;
  - перенос файла → правило перестаёт матчить (файл вышел из scope) → `derived`-facet снимается движком автоматически и предсказуемо (не «молча теряется» — а детерминированно пересчитывается).
  - **Это потенциальный МОСТ для Q3:** dual-role не нужен, если «папка-навешивает-категорию» = авто-связь-правило, а не слияние home+facet в один узел. Уверенность: средняя — это кандидат-резолюция для консилиума Q3, не финал. Передаю в консилиум Q3 как вход.

## 7. Где маппинг НАПРЯГАЕТ — и ВОПРОСЫ-ДЛЯ-ОБСУЖДЕНИЯ (с провенансом)

Скептицизм: и изъяны, и пруфы.

**Пруфы (где модель держит умные категории по-настоящему):**
1. Многомерность (N-081) реализуется 1a-категориями БЕЗ нового поля — `facet-of`-рёбра, доказано на `node.ts` (conception-mapping §3).
2. «Свои поля/валидация» (N-087) реализуется 1b-вариантами через `variant-of`+delta-схему — это уже принятый «вариант=тип» (стресс §3), не новый механизм.
3. Наследование формы БЕЗ вскрытия payload работает, потому что идёт по control-plane-рёбрам (как level-из-топологии) — I-1 цел.
4. Авто-связи укладываются в существующий `derived`+`rule_ref`-инвариант — 0 нового рода.
5. Q3 НЕ блокирует умные категории (они в зоне facet, не home).

**Изъяны/напряжения (честно):**
1. «Уровни определения» владельца — омоним оси `level?`; без расщепления (§2b) рискуем перегрузить ось.
2. «Категория диктует форму» (1b) требует, чтобы дискриминатор был в ПАСПОРТЕ (смена `type`), а не ярлыком — это против интуиции владельца «один тип сделка, варианты внутри». Цена непротиворечивости.
3. Слияние delta-схем по `variant-of` — это НЕОПИСАННЫЙ движок (как и индекс/rollup — #1 стоячий риск). Род ясен, спека нет.

### ВОПРОСЫ-ДЛЯ-ОБСУЖДЕНИЯ

1. **Q-SC1 — Принять расщепление «категория = ДВА рода» (1a классификатор-facet vs 1b вариант-тип)?**
   - *Откуда:* N-087 (умные категории) + N-042 («теги двух родов») vs I-1/I-3.
   - *Почему важно:* это ядро всего разбора. Без расщепления спор «узел vs facet vs под-тип» неразрешим, а с ним — растворяется (оба ответа верны для разных феноменов). Определяет, как владелец будет МЫСЛИТЬ категории.
   - *Кому:* **ВЛАДЕЛЬЦУ** (концептуальный выбор, как он хочет видеть категории).

2. **Q-SC2 — Принять, что форму диктует ТОЛЬКО `type`/`schema`+`variant-of`-цепочка, а классификатор (`facet-of`) НИКОГДА не инжектирует поля?**
   - *Откуда:* §3c, баг тени имён N-070/Q4 (CRITICAL).
   - *Почему важно:* снимает недетерминизм тени имён для категорий начисто; но означает, что «категория с dropdown» = смена типа ячейки (`deal-buy`), а не ярлык на `deal`. Прямо противоречит интуиции «один тип, варианты-ярлыки».
   - *Кому:* **ВЛАДЕЛЬЦУ** (подтвердить цену) + агенту (механика слияния).

3. **Q-SC3 — «Уровни определения категории» (N-087) — это delta-схема варианта + глубина классификации, а НЕ ось `level?` (why/what/how/data)?**
   - *Откуда:* §2b, омоним «уровень»; ADR-0002 §2(в) флаг двойного смысла оси.
   - *Почему важно:* смешение перегрузит ось абстракции и вернёт фрагментацию, от которой ADR ушёл.
   - *Кому:* **ВЛАДЕЛЬЦУ** (сверка понимания — что он называет «уровнем»).

4. **Q-SC4 — Авто-связи = `pattern`-узел с `when_scope` + `derived`-рёбра; «только в группах» = scope правила?**
   - *Откуда:* N-087 L2.4, N-042 (авто-связи), ADR-0002 §4 (ПАТТЕРН) + инвариант `derived`+`rule_ref`.
   - *Почему важно:* определяет, где живёт «реактивная классификация» и как она не взрывается на масштабе (scope, не весь граф). Безопасность: enforce-влияющие авто-рёбра = first-party-only (R4).
   - *Кому:* агенту (точная форма предиката + движок) + **флаг ВЛАДЕЛЬЦУ** на безопасность.

5. **Q-SC5 — Кандидат-МОСТ для Q3: «папка навешивает категорию» = авто-связь-правило (`when_scope:folder`, emit `derived facet-of`), а НЕ dual-role home+facet?**
   - *Откуда:* §6, Q3 (N-086, отложен в консилиум), I-3.
   - *Почему важно:* может СНЯТЬ Q3 без нарушения I-3 — перенос файла детерминированно пересчитывает ярлык, не теряет молча. Это прямой вход в отложенный консилиум Q3.
   - *Кому:* **консилиум Q3** (как кандидат-резолюция) + **ВЛАДЕЛЬЦУ** (приемлемо ли «ярлык авто-снимается при переносе»).

6. **Q-SC6 — Слияние delta-схем по `variant-of` + применение авто-связь-правил — описать в движок-спеке (как индекс/rollup)?**
   - *Откуда:* §2a/§4, стресс §2A («#1 риск — неописанный движок»).
   - *Почему важно:* род и контракты ясны, но без спеки движка «изящество условно». Это та же категория риска, что индекс/rollup.
   - *Кому:* агенту (движок-спека, отдельный этап).

## Резюме (для родителя)

- **Главное решение:** «умная категория» — НЕ один род, а ДВА свёрнутых: **(1a) классификатор** = узел `category` + ребро `facet-of` (не несёт форму, даёт многомерность/срез) и **(1b) вариант-формы** = ТИП-узел `model-def` + `variant-of`-ребро (несёт delta-поля/валидацию). Расщепление растворяет спор «узел vs facet vs под-тип»: оба верны для разных феноменов. Под-тип как отдельный механизм — отклонён (сводится к 1b или ломает I-1).
- **Поля/валидация:** несёт только 1b (delta-схема в `model-def`); дискриминатор — в паспорте `schema`, не в payload (I-1 цел).
- **Наследование БЕЗ вскрытия payload:** идёт по control-plane-рёбрам (`variant-of`/`subcategory-of`) — движок читает их, как level-из-топологии; payload ячейки не вскрывается. Классификатор (`facet-of`) НИКОГДА не инжектирует форму → снимает баг тени имён (Q4) для категорий начисто.
- **«Уровни определения» владельца ≠ ось `level?`** — омоним; это delta-схема + глубина классификации. Расщепить, иначе перегруз оси.
- **Авто-связи «только в группах»** = `pattern`-узел с `when_scope` + `derived`-рёбра (read-only, `rule_ref`); scope защищает от взрыва; enforce-влияющие = first-party-only.
- **Реестр:** 0 новых родов, 0 новых обязательных полей паспорта — чистая КОМПОЗИЦИЯ примитивов ADR-0002. «Новый род не вынужден».
- **Q3:** умные категории НЕ блокируются Q3 (живут в зоне facet, не home). Бонус: предложен МОСТ — «папка навешивает категорию» = авто-связь-правило, а не dual-role → кандидат-резолюция для консилиума Q3.
- **6 вопросов-для-обсуждения** в §7: Q-SC1/SC2/SC3/SC5 — владельцу (концепт+цена); Q-SC4/SC6 — агенту (движок-спека). #1 риск — неописанный движок слияния схем (та же категория, что индекс/rollup).
