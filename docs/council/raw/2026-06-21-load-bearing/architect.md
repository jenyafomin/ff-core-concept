# Линза АРХИТЕКТУРЫ — что НЕСУЩЕЕ в универсальной ячейке (где живут данные, где границы)

- **Status:** draft
- **Owner:** architect-lens
- **Date:** 2026-06-21
- **Вектор:** при огромном растущем мульти-родительском графе (важность-на-ребре, авто-связи, секции на млн
  узлов, векторы-как-фильтры, паттерны/рекурсия) — какие поля ячейки НЕСУЩИЕ, а что живёт в движке/модуле?
  Где данные должны ЖИТЬ?
- **Метод линзы:** движение ПОПЕРЁК — границы, размещение, контракты. Не «что важно» (это аналитик), а «ГДЕ
  это лежит и кто за это отвечает». Тон: сомнение, не утверждение.
- **Заземление на код (explorer):** сегодня importance — поле НА УЗЛЕ; обход вверх по одному `parentId`
  (`ancestors()`), циклы защищены, `maxDepth` НЕТ; порядка детей НЕТ; мультиродитель НЕ поддержан. Т.е.
  реальность кода — ровно то «дерево с глобальной важностью», от которого владелец уходит (msg 211).

## 0. Рамка размещения: пять «мест», где может жить аспект

Прежде чем резать — назову пять мест и контракт каждого. Это сама ось моего вклада.

| Место | Что это | Кто читает | Стоимость присутствия |
|-------|---------|-----------|----------------------|
| **[ПАСПОРТ]** | поля во frontmatter узла; читаются БЕЗ вскрытия payload и БЕЗ знания типа | ИИ, движок, человек | каждое поле = вечный налог на ВСЕ узлы графа + миграции |
| **[РЕБРО]** | поля на типизированной связи (per-pair), `links[]` | движок при обходе | дёшево добавлять, но обход дороже |
| **[ДВИЖОК/ИНДЕКС]** | производное, вычисляется/материализуется из истины; эфемерно | движок | можно перестроить из нуля → не несущее |
| **[МОДУЛЬ/ТИП]** | живёт в payload, валидируется `type@version` | только код, знающий тип | не видно ИИ без вскрытия → не для навигации |
| **[CONTROL-PLANE-УЗЕЛ]** | сам узел графа (`model-def`, `predicate`, `plugin-manifest`, `policy`) | как данные | максимальная гибкость, самохостинг |

**Главный принцип резки (мой критерий несущести):**
> Поле НЕСУЩЕЕ (→ паспорт) тогда и только тогда, когда движок обязан принять по нему решение об обращении с
> узлом, **не открывая payload и не зная тип**. Всё остальное — производное (индекс), типо-зависимое (модуль),
> реляционное (ребро) или управляющее (control-plane-узел).

Из этого критерия два следствия, которые проходят красной нитью:
1. **«ИИ должен это видеть» ≠ «это в паспорте».** ИИ видит ВСЁ (Принцип 3 владельца). Видимость даёт индекс и
   обход рёбер. Паспорт — только то, что движок читает на КАЖДОМ узле в ГОРЯЧЕМ пути обработки.
2. **«Это per-pair» → ребро, не паспорт.** Если значение зависит от того, ОТКУДА смотришь на узел (важность,
   роль в связи, порядок) — оно физически не может жить на узле без неоднозначности.

## 1. ГЛАВНАЯ ТАБЛИЦА: аспект → где живёт → почему

## 2. Важность-на-ребре + мультиродитель: как уживается с обходом, кэшем, детерминизмом

### Что меняется структурно
Сегодня (код): `importance` на узле, `ancestors()` идёт по ОДНОМУ `parentId`. Модель N-041 ломает оба
допущения: (1) у узла N родителей; (2) приоритет живёт на ребре `child→parent`.

### Контракт ребра принадлежности (предложение)
```
edge (child → parent):
  rel: home | child-of        # home = привилегированное (≤1 на узел) для дефолтного контекста
  priority: <number>          # относительный, в пределах ОДНОГО родителя
  sort: <ключ>                # детерминизм при равном priority
```

### Где это РАБОТАЕТ
- **Мультиродитель безопасен** именно потому, что важность ушла на ребро: нет глобального max/min/avg →
  нет неоднозначности (это и есть аргумент N-041, и он архитектурно корректен).
- **Сортировка детей внутри родителя** детерминирована: `ORDER BY priority DESC, sort, id`. `id` как
  финальный тай-брейк убирает зависимость от `readdir` (сегодня порядок недетерминирован — баг).

### Где это ЛОМАЕТСЯ (честно, сомнение)
1. **Обход вверх перестаёт быть линейным.** `ancestors()` по одному `parentId` — это путь. По N родителям —
   это DAG → обход даёт МНОЖЕСТВО предков, возможно с разным контекстом. Вопрос: при сборке контекст-конверта
   по какому родителю каскадить? → нужен **привилегированный `home` (≤1)** для дефолта; остальные
   родители — opt-in каскад. Иначе «контекст узла» становится недетерминированным.
2. **Каскад контекста при мультиродителе = слияние.** Если узел в 3 родителях, и каждый даёт `context` —
   движок должен СЛИВАТЬ детерминированно (порядок по priority родителя? по home-флагу?). Это решаемо, но
   правило слияния — несущее решение, его нельзя упустить (это корень провала кластера 4 в прошлом стресс-тесте).
3. **Кэш инвалидация дорожает.** При важности-на-узле смена важности = 1 запись. При важности-на-ребре +
   мультиродитель: смена priority инвалидирует кэш сортировки ОДНОГО родителя (хорошо, локально). НО смена
   `context` родителя инвалидирует кэш конверта ВСЕХ потомков по ВСЕМ путям (дороже). → нужен **dirty-флаг по
   поддереву**, не глобальный пересчёт.
4. **Циклы в DAG.** Сегодня цикл-гард есть для одного `parentId`. Для N родителей цикл-детект = полноценный
   DFS с тремя цветами. `maxDepth` (которого нет в коде) становится ОБЯЗАТЕЛЬНЫМ как страховка.

### Детерминизм сортировки — несущее правило
> При равном `priority` сортировка ВСЕГДА доопределена стабильным ключом (`sort`, затем `id`). Без этого
> «миллион сообщений» отрисуется в случайном порядке. Это закон движка, но требует, чтобы у ребра БЫЛО поле
> для тай-брейка. → значит на ребре несущее: `priority` + `sort`-ключ.

## 3. Огромные секции (чат = млн сообщений как узлы): паспорт / движок / тип?

### Размещение по слоям
- **[ПАСПОРТ] узла-СЕКЦИИ** (не каждого сообщения!): `id`, `type` (`chat`/`section`), `source`,
  `name`/`title`, `created/updated`, `child_count` (денормализованный счётчик), `summary_ref` (указатель на
  узел-абстракцию). Это «абстракция по имени/источнику» из N-043 — минимум в ячейке.
- **[ДВИЖОК]**: ленивая загрузка детей (пагинация/курсор), материализованный `child_count`, чанкинг по
  диапазонам (`messages 1-1000`), индекс по времени/автору для retrieval.
- **[МОДУЛЬ/ТИП]**: что значит «сообщение», как рендерится, семантика треда (`inReplyTo`) — типо-зависимо.

### Ключевое архитектурное решение: секция — это УЗЕЛ-ГРАНИЦА
Миллион сообщений НЕ должны быть миллионом равноправных детей в горячем обходе. Предложение:
> **Узел-секция = граница ленивости.** Обход по умолчанию НЕ спускается внутрь секции — он видит `child_count`
> + `summary_ref` (абстракция по имени) и останавливается. Вскрытие («покажи сообщения») = явный запрос с
> курсором. Это реализует требование владельца «минимум в ячейке, ИИ сам настраивает вектор».

### Контракт запросов к секции (предложение, не код)
- `getContext(node, budget)` — НЕ материализует секцию целиком; для узла-секции возвращает абстракцию
  (`name`+`summary_ref`+`child_count`), пока бюджет не велит углубиться.
- `expand(section, cursor, limit)` — постраничный спуск внутрь (ленивая загрузка).
- `summarize(section)` — движок/агент строит `summary`-узел; секция держит указатель.

### Что НЕСУЩЕЕ здесь
- `child_count` (денорм-счётчик) — иначе «насколько большая секция» требует обхода. Но это **производное**
  (движок поддерживает), значит — индекс, не истина. Несущим в паспорте остаётся `summary_ref` + `source`.
- **Граница ленивости** — это не поле, это РЕШЕНИЕ движка по `type`. Значит тип секции (`type@version`)
  должен сигналить движку «я — контейнер с ленивым телом». → флаг на уровне `model-def`: `lazy_children: true`.

## 4. Авто-связи и «вектор-как-фильтр»: рёбра, матвью или запрос на лету?

### Три варианта и их последствия на масштабе
| Реализация | Стоимость записи | Стоимость чтения | Свежесть | Риск на млн узлов |
|------------|------------------|------------------|----------|-------------------|
| **запрос на лету** | 0 | высокая (скан/вектор-поиск каждый раз) | всегда свежо | чтение деградирует линейно |
| **материализованное ребро** | при изменении | O(1) обход | устаревает | дрейф: ребро есть, релевантность ушла |
| **матвью (кэш-индекс)** | фоновое обновление | низкая | лаг обновления | сложность инвалидации |

### Моё предложение (срединное)
- **Авто-связи = материализованные рёбра, помеченные `provenance:auto` + `rule_ref`** (указатель на
  правило-узел, которое их породило). Почему ребро, а не запрос на лету: владелец описал «проект, который
  смотрит всё по планированию, сам подтягивает» (N-042) — это устойчивая подписка, а на млн узлов запрос на
  лету при каждом обращении недопустим. Материализация + фоновое обновление.
- **Критично — отличать `auto` от ручного.** Иначе пользователь не сможет доверять графу («это я связал или
  ИИ?»). → `provenance` на ребре несущее: `manual | auto | inferred`. Авто-ребро движок может пересчитать и
  снести; ручное — никогда без спроса. Это граница обратимости.
- **Вектор-наблюдения = НЕ ребро.** Это сохранённый ФИЛЬТР (запрос) + опц. матвью для дорогих. «Угол агента,
  за который не выходит» = узел-вектор + политика. Применяется на чтении, не материализуется в граф (иначе
  смешаем «что есть» с «как смотрю»).

### Архитектурное последствие, которое нельзя упустить
> Авто-связи и вектор-фильтры создают **производный слой поверх истины**. Если его не отделить меткой
> (`provenance:auto`, `rule_ref`), через год невозможно будет отличить факты графа от догадок движка. Это
> прямой риск для «всё видно ИИ» — ИИ будет видеть свои же галлюцинации как факты. → метка происхождения
> ребра = несущее.

## 6. Ответ на 3 напоминания владельца (msg 213)

1. **Уровень абстракции (почему/что/как/data) как измерение.** Архитектурно — это НЕ ещё одна грань паспорта.
   Это либо (а) ИЗМЕРЕНИЕ ВЕКТОРА (фильтр: «покажи только уровень „почему“») → живёт в запросе/движке; либо
   (б) СВЯЗЬ между узлами разного уровня (`why`→`how`→`what`→`data` как rel) → живёт на рёбрах. Скорее
   комбинация: опциональный фасет-тег `abstraction:why|how|what|data` (производный индекс для фильтра) + рёбра
   `realizes`/`grounds` между уровнями. В паспорт как обязательное поле — НЕТ (не каждый узел имеет уровень
   абстракции; налог на все узлы неоправдан).
2. **Статус «черновик/набросок» = контролируемый эпистемический статус.** Это УЖЕ есть — ось `epistemic` в
   паспорте (`proposal|draft|fact|hypothesis|archived`). Несущее, в паспорте, ✅. «Возможно нужны другие
   подобные» — да, но как ЗНАЧЕНИЯ той же оси epistemic (открытый словарь статусов доверия), не новые поля.
   Граница: epistemic = доверие (факт/черновик); `state` = процесс (open/doing) — НЕ путать (это корень
   старого бардака со `status`).
3. **Вектор наблюдения — отдельно (не растворять в importance).** Согласен архитектурно и подчёркиваю:
   importance живёт на РЕБРЕ (сортировка детей), вектор наблюдения — это ФИЛЬТР/запрос (как смотрю на граф).
   Это РАЗНЫЕ места: importance = свойство связи, вектор = свойство наблюдателя. Их нельзя смешивать —
   importance меняет ПОРЯДОК внутри родителя, вектор меняет ВИДИМОЕ ПОДМНОЖЕСТВО графа. Отдельные механизмы,
   отдельные места.

## 7. Несущее vs производное — финальный реестр

**НЕСУЩЕЕ (нельзя восстановить из ничего; теряем — теряем смысл):**
- В ПАСПОРТЕ: `id`, `type@version`, `created`, `updated`, `epistemic`, `sensitivity`, `source`, `home`-указатель,
  тонкий `principal`, `canonical_id` (поле).
- На РЕБРЕ: само ребро (`to`,`rel`), `priority`+`sort` (важность), `provenance` ребра (manual/auto/inferred).
- В CONTROL-PLANE: `model-def` (тип+валидация+`lazy_children`), `predicate`, `plugin-manifest`, политики ABAC.

**ПРОИЗВОДНОЕ (движок перестроит из истины; не несущее):**
- backlinks, adjacency/граф целиком, `child_count`, индексы по времени/автору/тегу, строковые теги-категории,
  матвью авто-связей, вычисленные levels (zoom), вектор-фильтры, dedup-кластеры.

**ТИПО-ЗАВИСИМОЕ (в payload, не видно без вскрытия; не для навигации):**
- `occurred`/`valid_from/until`, `state`/workflow, payload-поля, семантика веток/мёржа, reactivity.

## 8. Главный архитектурный риск на масштабе

> **Мультиродитель вернул проблему №4 (детерминированное слияние каскадов), которая раньше валила модель.**
> N-041 элегантно снял неоднозначность ВАЖНОСТИ (на ребро) — но НЕ снял неоднозначность КОНТЕКСТА/КАСКАДА.
> Если узел в N родителях, и каждый даёт контекст-конверт — без правила «привилегированный `home` (≤1) =
> дефолтный каскад, остальные = opt-in с явным порядком» сборка `getContext()` становится недетерминированной
> на масштабе. Это не ловится тестом на 50 узлах — только на росте. **Это надо решить ДО кода**, иначе
> «предсказуемая, контролируемая система» (требование владельца N-040) разваливается именно там, где граф
> большой.

Вторичный риск: **производный слой (авто-связи, вектор-фильтры) без метки происхождения сольётся с истиной** →
ИИ будет видеть свои догадки как факты. Метка `provenance` на ребре — дешёвая страховка, но несущая.
