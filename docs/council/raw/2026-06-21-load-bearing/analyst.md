# Анализ: что НЕСУЩЕЕ в универсальной ячейке информации

- **Status:** draft
- **Owner:** analyst-lens
- **Date:** 2026-06-21
- **Контекст:** Ресёрч по N-044/N-045. Вектор: при огромном растущем мульти-родительском графе (важность-на-ребре,
  авто-связи, секции на млн узлов, векторы-как-фильтры) — что в паспорте НЕСУЩЕЕ, что живёт в движке/модуле?

## Часть 1: 12 конкретных сложных сценариев

### С-01 — Чат на 1.2 млн сообщений, на который ссылается задача

**Описание:** Telegram-история с ботом за 3 года. 1 200 000 узлов типа `message`. Задача `task/2024-11-05-build-auth`
ссылается на «обсуждение архитектуры в декабре 2022». Агент должен найти релевантный кластер, не читая всё.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `id` | ✅ | Каждое сообщение уникально, ссылка по id работает |
| `type` | ✅ | `message` → агент знает, что не вскрывать payload при навигации |
| `home` (мульти) | ⚠️ | Какой из 1.2M узлов — «точка входа» для агента? Нет поля абстракции/summary |
| `importance` на ребре | ⚠️ | Родитель-чат ставит importance всем детям одинаково — нет сигнала «это важное сообщение» |
| `created` | ✅ | Временной диапазон «декабрь 2022» фильтрует |
| `epistemic` | ✅ | Все — `fact` (реальные сообщения) |
| `source` | ✅ | `telegram:chat/123456` — дедуп при re-import |
| вектор наблюдения | ❌ | Нет поля «уровень абстракции». Агент не знает: это сырые данные или summary? |
| абстракция секции | ❌ | Нет поля `abstract_of` / `section_summary`. Нет «главы 1-2-3» как навигационного якоря |

**Где ломается:** агент вынужден либо читать всё (OOM/cost explosion), либо угадывать ключевые слова. Нет механизма «входа в секцию по имени/источнику» (N-043 это назвал, но поля нет).

**Чего не хватает:** поле `abstract_for: [id...]` или ссылочный узел-оглавление типа `section-index`; поле уровня абстракции как часть паспорта.

### С-02 — Узел задачи в 5 родителях с конфликтующей важностью

**Описание:** Задача `task/redesign-api` принадлежит: проекту `project/backend` (важность 5), плану квартала
`plan/Q3` (важность 2), плану спринта `plan/sprint-12` (важность 4), личной очереди `queue/today` (важность 1),
и ещё прикреплена к митингу `event/2026-06-20` (важность 3). Агент составляет «что делать сегодня?».

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `id` | ✅ | Один id, 5 рёбер принадлежности с разными importance |
| мульти-`home` + importance на ребре | ✅ | N-041 решил: каждый родитель ставит свой приоритет |
| `type` | ✅ | `task` → агент знает что делать |
| `state` | ✅ | `open/doing/blocked` — читается без payload |
| `epistemic` | ✅ | `fact` |
| вектор наблюдения | ⚠️ | Агент-«планировщик дня» смотрит только через ребро `queue/today`. Но нет поля, говорящего «для этого вектора наблюдения relevance = 1». Агент должен ЗНАТЬ, какой родитель — его точка зрения |
| `due` / дедлайн | ❌ | Нет в паспорте. Агент не знает, горит ли задача без открытия payload |
| приоритет-агрегация | ⚠️ | Если агент получает узел без контекста «через какого родителя» — important на каком из 5 рёбер брать? |

**Где ломается:** агент получает узел «flat» (без контекста родителя) и не знает, какую importance читать. Нужен либо «активный вектор наблюдения» в запросе, либо поле в паспорте.

**Чего не хватает:** `due` в паспорте (или хотя бы флаг «есть временной инвариант»); контракт запроса «всегда передавать viewport/parent-context».

### С-03 — Авто-связь породила «шторм» из 12 000 рёбер

**Описание:** Включена авто-связь: «проект X смотрит всё по тегу `#planning`». В графе 12 000 узлов с тегом `#planning` накопились за 2 года. Теперь при `getContext(project/X, budget=20)` движок пытается обойти все 12k рёбер.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `id` | ✅ | — |
| `type` | ✅ | — |
| `tags` | ✅ | Тег `#planning` присутствует — авто-связь корректна по намерению |
| `created`/`updated` | ⚠️ | Можно фильтровать по дате, но нет флага «этот индекс устарел» |
| `stale` | ⚠️ | Если бы было поле `stale: true` на авто-индексе — движок мог бы сигнализировать |
| `importance` на ребре | ❌ | Авто-связи не несут importance (кто её ставит? движок? по какому правилу?). 12k рёбер без ранжирования — нет сигнала «топ-20» |
| вектор наблюдения | ❌ | Нет поля «max-fan-out» или «decay-rule» на авто-ребре |
| budget/truncation | ❌ | Нет в паспорте. Контракт запроса `getContext(budget)` не определён |

**Где ломается:** без importance на авто-рёбрах и без decay/fan-out политики движок либо рекурсирует в timeout, либо возвращает случайные 20 из 12k. Нет сигнала «контекст усечён».

**Чего не хватает:** importance на авто-рёбрах (кто ставит — движок по эвристике; по дате? по epistemic?); `truncated: true` сигнал в ответе запроса; max-fan-out политика на уровне авто-связи.

### С-04 — Черновик-набросок, принятый агентом за факт

**Описание:** Агент-планировщик создал набросок задачи `task/migrate-db` с `epistemic: proposal`. Через неделю второй агент-исполнитель читает граф и начинает выполнять задачу (пишет миграцию), не проверив epistemic.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `epistemic` | ✅ | `proposal` присутствует как поле — если агент ЧИТАЕТ его |
| `sensitivity` | ✅ | Не касается |
| `valve` (клапан) | ⚠️ | Клапан определён для ВНЕШНИХ необратимых действий. Написать миграцию внутри системы — внутреннее действие. Клапан не срабатывает |
| `state` | ⚠️ | Задача `state: open` — ничего не говорит о том, что она черновик |
| `actor` | ✅ | `agent:planner` — видно, кто создал |
| enforcement | ❌ | Нет механизма «агент-исполнитель ДОЛЖЕН проверить epistemic до action». Это политика, не поле |

**Где ломается:** паспорт содержит epistemic, но нет enforcement: ни один механизм не мешает агенту проигнорировать это поле. «Клапан» применяется к внешним действиям (отправить письмо, потратить деньги), но не к внутренним действиям внутри системы.

**Чего не хватает:** явное правило «action на узлах с epistemic != fact → требует аргументации» как часть контракта агента (не паспорта). В паспорте достаточно, но нужен enforcement-слой движка. Это именно то, что стресс-тест ADR-0001 назвал «клапан decision не реализован».

### С-05 — Плагин с 20 типами переопределяет `type` конфликтующе

**Описание:** Плагин `crm-plugin` определяет тип `contact` в неймспейсе `crm/contact`. Ядро уже имеет базовый тип `contact` (без неймспейса). Плагин устанавливается; теперь в графе есть узлы `type: contact` и `type: crm/contact`. Агент ищет все контакты.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `type@version` | ⚠️ | `contact` vs `crm/contact` — разные строки. Агент должен знать, что они «родственны» |
| namespace | ⚠️ | Канвас описывает `namespace: crm` внутри type-определения, но в паспорте узла данных нет явного поля namespace отдельно от type |
| `epistemic` | ✅ | Оба типа данных могут быть fact |
| `home` | ✅ | Принадлежность не нарушена |
| type-hierarchy | ❌ | Нет поля «этот тип расширяет базовый тип X». Агент не знает об отношении `crm/contact` → `contact` |
| dedup/canonical | ❌ | Без `canonical_id` невозможно понять: это тот же контакт или другой? |

**Где ломается:** при запросе «все контакты» агент получает два непересекающихся множества, если не знает иерархии типов. Нет поля type-supertype в паспорте.

**Чего не хватает:** либо `supertype: contact` в type-definition-узле (тогда движок раскрывает иерархию), либо алиас в реестре типов. `canonical_id` нужен в паспорте (спор B из вердикта).

### С-06 — Рекуррентная задача с 500 экземплярами

**Описание:** Задача «Еженедельный отчёт» рекуррентная. За год создано 52 экземпляра. К 2026-06-21 их 500. Агент должен: (а) найти «этот вариант на текущей неделе»; (б) показать историю выполнения; (в) изменить шаблон для будущих.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `id` | ✅ | Каждый экземпляр уникален |
| `type` | ✅ | `task` |
| `created` | ✅ | Фильтр по дате недели |
| `instance-of` | ❌ | Нет в паспорте. Нет способа найти «шаблон» без вскрытия payload |
| `state` | ✅ | `done`/`open` — история видна |
| шаблон vs экземпляр | ❌ | Нет поля в паспорте, различающего шаблон-узел и экземпляр-узел |
| recurrence-rule | ❌ | Где хранится «каждый понедельник»? В payload модуля. Агент не видит без вскрытия |

**Где ломается:** без `instance_of` агент не может: (а) найти шаблон; (б) понять, это «регулярный» или «разовый» узел; (в) изменить только будущее. Изменение шаблона без `instance_of` применится к одному экземпляру или сломает историю.

**Чего не хватает:** `instance_of: <id>` в паспорте (это упоминалось в стресс-тесте ADR-0001 как обязательная правка). Это несущее поле для рекурсии/паттерна «шаблон→экземпляр».

### С-07 — Составная метрика, зависящая от 15 узлов

**Описание:** Метрика `metric/monthly-revenue` = сумма 15 дочерних `metric/daily-revenue-*`. Один из дочерних узлов обновился (новое значение). Агент должен: (а) перевычислить `monthly-revenue`; (б) уведомить, если изменение > 10%.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `type` | ✅ | `metric` → агент знает |
| `links` к дочерним | ✅ | Рёбра `aggregates` присутствуют |
| `created`/`updated` | ✅ | Видно, что дочерний изменился |
| `stale` | ⚠️ | `stale: true` можно поставить на `monthly-revenue`, но кто ставит — не определено |
| reactivity/trigger | ❌ | Нет в паспорте. «Перевычислить при изменении дочернего» — это реактивность (вынесена в движок) |
| rollup-функция | ❌ | Нет в паспорте. `sum`/`avg`/`max` — в payload модуля |
| threshold-alert | ❌ | Нет в паспорте. «Уведомить если >10%» — логика модуля |

**Где ломается:** `stale: true` можно поставить вручную или через движок при обновлении дочернего — это работает. Но «кто триггерит перевычисление» не решено в паспорте. Движок должен знать ребро `aggregates` и реагировать на `updated` дочернего — это вне паспорта, но требует контракта с движком.

**Чего не хватает:** `stale` — несущее поле (правильно в Temporal). Но нужен контракт «движок ставит `stale: true` на агрегаты при изменении зависимостей» — это политика движка, не поле паспорта.

### С-08 — Узел одновременно данные и фильтр-наблюдения

**Описание:** Узел `view/planning-board` сам является «векторным фильтром»: «показать всё с тегом `#planning` и `state: open`, уровень абстракции = `how`». Этот узел-фильтр тоже живёт в графе. Агент должен понять: это данные или инструкция?

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `type` | ✅ | `view` — тип говорит агенту «это фильтр, не данные» |
| `epistemic` | ⚠️ | `fact` — фильтр «истинен». Но агент должен применить его как инструкцию, а не читать как данные |
| payload (фильтр-параметры) | ❌ | Фильтр-выражение внутри payload. Агент вынужден вскрыть payload чтобы применить |
| уровень абстракции | ❌ | `how` — нет поля в паспорте. Агент не может фильтровать граф по «уровню абстракции» без вскрытия |
| «применить как вектор» | ❌ | Нет семантики в паспорте «этот узел = применяемый фильтр». Только тип `view` — договорённость |

**Где ломается:** чтобы «применить» view-узел как вектор наблюдения, агент ОБЯЗАН открыть payload — разрушает принцип паспорта. Либо нужна стандартизированная «mini-query» как часть паспорта (не payload), либо узел типа `view` имеет специальный slot в паспорте.

**Чего не хватает:** либо стандартный слот `filter_expr` в паспорте для узлов-фильтров (нарушает тонкость ядра), либо соглашение «тип `view` → движок вызывает `applyAsFilter(payload)` без вскрытия ИИ». Уровень абстракции как поле паспорта здесь критичен.

### С-09 — Нода с epistemic:proposal, которую агент использует как fact для внешнего действия

**Описание (острее С-04):** Узел `decision/send-newsletter` имеет `epistemic: proposal`, `sensitivity: public`. Агент-рассылки читает `sensitivity: public` и начинает отправку. Он НЕ проверяет epistemic, потому что «sensitivity=public = можно делиться».

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `epistemic` | ✅ | `proposal` присутствует |
| `sensitivity` | ✅ | `public` присутствует |
| ортогональность | ❌ | `sensitivity` и `epistemic` ортогональны по дизайну — но агент читает sensitivity без epistemic. «Черновик с sensitivity=public» — логически допустимо, но опасно |
| клапан | ⚠️ | Клапан должен блокировать внешнее действие при epistemic != fact. Но в паспорте клапан — «политика движка», не поле. Если движок не применяет клапан — ничто не блокирует |
| `decision` ось | ❌ | Нет в паспорте. Узел-решение не отличим от узла-данных без открытия payload |

**Где ломается:** паспорт корректен по дизайну, но enforcement клапана не реализован. Это тот самый «клапан decision не реализован» из ADR-0001 стресс-теста — он назван первым к закрытию. Оба поля (`epistemic`, `sensitivity`) правильно в паспорте, но без enforcement — мёртвые метки.

**Чего не хватает:** enforcement-правило в движке: «внешнее действие на узле с epistemic != fact → заблокировать + логировать». Это не поле паспорта — это контракт движка.

### С-10 — Граф с циклом через 7 рёбер

**Описание:** Узел A → B → C → D → E → F → G → A (цикл через 7 узлов). `getContext(A, budget=50, maxDepth=3)` не достигает цикла. Но запрос `getContext(A, budget=200, maxDepth=10)` зависает.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `id` | ✅ | Посещённые id отслеживаются движком |
| `links` | ✅ | Рёбра присутствуют |
| цикл-гард | ❌ | В паспорте нет. Это инфра движка — «visited set». Упоминалось в 8 обязательных правках ADR-0001 |
| `maxDepth` в коде | ❌ | В tests/schema задан, но в коде не реализован (STATE.md: «maxDepth не в коде») |
| `truncated` сигнал | ❌ | Нет в паспорте и нет в контракте ответа |

**Где ломается:** цикл-гард и maxDepth — инфраструктура движка, не поля паспорта. Паспорт здесь правильно ничего не содержит. Но контракт запроса `getContext()` ДОЛЖЕН гарантировать: (а) visited-set; (б) сигнал усечения.

**Чего не хватает:** не в паспорте — в движке: visited-set + depth counter + `truncated: true` в ответе. Это известная «долговая инфра».

### С-11 — principal/арендатор: два пользователя в одном графе

**Описание:** Пользователь-1 (Женя) и пользователь-2 (партнёр) используют систему. У пользователя-2 свои задачи с `sensitivity: private`. Агент-1 (принадлежащий Жене) делает `getContext(project/shared)` — должен ли он видеть приватные узлы партнёра?

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `sensitivity` | ✅ | `private` присутствует |
| `principal` | ⚠️ | Спор C (вердикт): нет в паспорте или тонкий слот в Belonging. Без него движок не знает, «чьи» эти данные |
| `epistemic` | ✅ | Не касается |
| ABAC | ❌ | Нет в паспорте. Без `principal` на узле — нет основания для ABAC-фильтра |
| first-party / сторонние | ⚠️ | Принцип 3 (переопределить «всё видно ИИ» = первосторонний агент) — не закрыт |

**Где ломается:** движок не может применить ABAC без `principal` на узле. `sensitivity: private` говорит «приватно», но не говорит «для кого». Без `principal` любой агент либо видит всё, либо ничего — нет гранулярности.

**Чего не хватает:** `principal` в паспорте (тонкий слот — спор C, 1 критик из 4 настаивал). Это несущее поле для multi-tenant и маркетплейса. Без него `sensitivity` — неполная метка.

### С-12 — Узел «уровень абстракции»: почему/как/что — агент работает не на той абстракции

**Описание:** В графе есть три узла об одной теме «аутентификация»:
- `why/auth-decision` (почему выбрали JWT — стратегический) `level: why`
- `how/auth-implementation` (как реализовать — тактический) `level: how`
- `what/auth-config` (конфигурация — операционная) `level: what`

Агент-стратег спрашивает «что нужно про auth?». Без фильтра по уровню абстракции он получает все три — и перегружается деталями.

**Разбор по паспорту:**

| Поле | Статус | Комментарий |
|------|--------|-------------|
| `type` | ✅ | Разные типы (`decision`, `spec`, `config`) — частичный сигнал |
| `tags` | ⚠️ | Тег `#auth` присутствует на всех. Тег уровня? Можно добавить `#why`/`#how`/`#what` как категорию |
| уровень абстракции | ❌ | Нет поля в паспорте. Владелец (N-037, N-045) явно называет это «измерением, которого не увидели» |
| вектор наблюдения | ❌ | Агент-стратег не может объявить «я работаю на уровне why». Нет слота |
| фильтр по уровню | ❌ | Движок не может фильтровать по уровню абстракции без поля |

**Где ломается:** ИИ получает разнородную «кашу» разных уровней и должен сам разобраться. Принцип паспорта нарушен: агент вынужден вскрывать payload чтобы понять «это стратегия или конфиг?».

**Чего не хватает:** поле `abstraction_level: why | how | what | data` в паспорте. Владелец (N-037) назвал это «измерением вектора наблюдения» — возможно это не отдельное поле, а часть тегов или механики вектора. Но в паспорте должен быть слот.

## Часть 5: Где данные должны ЖИТЬ (спорные поля)

### `importance` → на ребре принадлежности (N-041 — решено)
Живёт в метаданных ребра `home`→дочерний: `{priority: 3, sort_key: "auto"}`. Движок агрегирует по родителю.
Нет в паспорте ноды — правильно.

### `abstraction_level` → в паспорте ноды (предложение)
Поле на ноде, НЕ на ребре. Аргумент: уровень абстракции — свойство самого контента, а не отношения к родителю.
`why`-узел остаётся `why`-узлом независимо от родителя. Альтернатива: системный тег `#level:why` — дешевле,
но менее явно. Риск: если в тегах — смешается с другими тегами, движок не отличит.
**Вывод: отдельное поле `level: why|how|what|data` в паспорте.**

### вектор наблюдения → в контракте запроса, не в паспорте (предложение)
Вектор — это параметр запроса `getContext(node, budget, viewport={level: how, parent: plan/Q3})`, не поле ноды.
Нода не знает, «кто на неё смотрит». Правильная архитектура: запрос несёт viewport, движок фильтрует по `level`
и `home`-пути через viewport-родителя.
**Вывод: вектор = параметр запроса; `level` на ноде = инструмент вектора.**

### `principal` → тонкий слот в Belonging (предложение)
Аргумент за паспорт: движок не может применить ABAC без `principal` на узле — должен знать «чьи данные» без
вскрытия payload. Аргумент против: principal — это ABAC, не интерпретация. Срединное: тонкий слот
`owner_principal: <id>` в Belonging, как `home` — один указатель. Движок использует для фильтрации.
**Вывод: тонкий слот в паспорте.**

### `instance_of` → в паспорте ноды
Аргумент: шаблон/экземпляр — отношение, которое агент должен знать без вскрытия payload.
«Этот узел — экземпляр шаблона X» — навигационный сигнал, а не типовые данные.
Альтернатива: ребро типа `instance-of` в `links`. Риск: ребро не отличается от обычной связи без соглашения;
движок не знает «это особое ребро». Специальное поле явнее.
**Вывод: поле `instance_of: <id?>` в паспорте.**

### `dedup/canonical_id` → поле движка при ingestion, не ось паспорта
Движок при вставке ищет дубли по `source`+`type`+хешу ключевых полей. Если найден — ставит `canonical_id`
на новый узел и помечает его `archived`. ИИ видит поле пассивно, не интерпретирует активно.
**Вывод: поле движка, но хранится на ноде; не «грань» паспорта.**

## Часть 6: Сценарии с ❌ — что нельзя упустить до кода

### ❌ Сценарий С-08 (узел-фильтр) — уровень абстракции
**Провал:** агент не может работать «на правильной абстракции» без поля в паспорте.
**Что нельзя упустить:** добавить `abstraction_level` в паспорт ДО кода. Иначе любой retrieval «смешивает уровни»
и агент перегружается или теряет стратегический контекст.

### ❌ Сценарий С-09 (клапан не реализован) — enforcement
**Провал:** `epistemic=proposal` + `sensitivity=public` → агент совершает внешнее действие. Клапан мёртв.
**Что нельзя упустить:** enforcement клапана — первым к реализации (ADR-0001 стресс-тест это уже сказал).
Контракт движка: «внешнее действие → проверить epistemic на всех задействованных узлах».

### ❌ Сценарий С-01 (чат на 1.2M) — абстракция секции
**Провал:** нет механизма навигации в огромную секцию без чтения всего.
**Что нельзя упустить:** соглашение о «section-index» узлах (N-043) до работы с большими источниками.
Иначе добавление Telegram-истории в граф = неуправляемый рост без точек входа.

### ❌ Сценарий С-06 (рекуррентность) — `instance_of`
**Провал:** нет способа найти шаблон без вскрытия payload.
**Что нельзя упустить:** `instance_of` в паспорте. Без него изменение шаблона и история выполнения = ручная работа.

### ❌ Сценарий С-03 (авто-связи, 12k рёбер) — importance на авто-рёбрах + truncation
**Провал:** авто-связи без ранжирования = information overload при getContext.
**Что нельзя упустить:** политика importance на авто-рёбрах (эвристика движка: по дате? по epistemic? по explicit weight?) + сигнал `truncated: true` в ответе контракта запроса.

## Часть 7: Ответы по 3 напоминаниям владельца (N-045)

### Напоминание 1: уровень абстракции (почему/что/как/data)
**Состояние:** отсутствует в текущем паспорте. В вердикте-2026-06-19 не упоминается. В N-037 и N-045 явно названо «измерением, которого не увидели».
**Вывод анализа:** это несущее поле. Без него retrieval смешивает уровни, агент-стратег тонет в операционных деталях.
**Рекомендация:** добавить `level: why | how | what | data` в Identity (или отдельной группой) до финализации паспорта.
**Уверенность:** высокая (3 сценария ломаются без этого поля; явная просьба владельца).

### Напоминание 2: статус «набросок/черновик» (контролируемый эпистемический статус)
**Состояние:** `epistemic: proposal` в паспорте — есть. `epistemic: draft` — нет явного значения.
**Вопрос:** `proposal` и `draft`/`sketch` — одно и то же? Или нужно расширить enum?
**Текущий enum:** `proposal | fact | hypothesis | archived`.
`draft`/`набросок` — это то, что человек создаёт как незаконченное (неполное, не для агента). `proposal` — это то, что агент предложил для ревью. Разница СЕМАНТИЧЕСКАЯ: черновик человека vs предложение агента.
**Риск слияния:** агент читает `proposal` и думает «это мне на ревью», хотя это просто незаконченная заметка.
**Рекомендация:** расширить `epistemic`: `draft | proposal | hypothesis | fact | archived`. `draft` = человек не закончил; `proposal` = агент предлагает.
**Уверенность:** средняя (логически обоснованно, но нет сломанного сценария в 12 — добавить как С-04а).

### Напоминание 3: вектор наблюдения — отдельно
**Состояние:** в паспорте отсутствует. N-042 определил вектор как «задачу для фильтра»; поля ноды = инструменты вектора.
**Вывод анализа:** вектор = параметр запроса (контракт `getContext`), а не поле ноды. Но поля ноды ДОЛЖНЫ поддерживать фильтрацию по вектору.
**Что нужно в паспорте для поддержки вектора:**
  - `level` (уровень абстракции) — фильтр по «why/how/what»
  - `type` — уже есть
  - `tags` (тип-тег vs категория-тег) — различие важно для авто-связей
  - `home` (через какого родителя наблюдаем) — уже есть
**Что НЕ нужно в паспорте:** сам вектор (это runtime-параметр запроса).
**Рекомендация:** зафиксировать «контракт вектора наблюдения» как часть контракта запроса (`getContext`), отдельно от паспорта. Паспорт предоставляет поля-инструменты; контракт запроса определяет, как они комбинируются в вектор.

## Итог: что нельзя упустить до кода

1. **`abstraction_level` в паспорте.** 3 ломающих сценария. Явная просьба владельца.
2. **enforcement клапана `epistemic`.** 2 ломающих сценария. Назван в ADR-0001 «первым к закрытию», но не реализован.
3. **`instance_of` в паспорте.** Рекуррентность и шаблоны без него = ручная работа.
4. **importance на авто-рёбрах + truncation-сигнал.** Авто-связи без ранжирования = timeout при getContext.
5. **Расширение `epistemic` enum: добавить `draft`.** Семантическое различие черновик-человека vs предложение-агента.
6. **Контракт `getContext` с viewport-параметром.** Вектор наблюдения = параметр запроса, не поле ноды — зафиксировать явно.
7. **`principal` тонкий слот.** Multi-tenant невозможен без него; маркетплейс требует.
8. **Соглашение о section-index узлах.** Огромные секции (N-043) без точек входа = неуправляемый граф.

## Неопределённости (что ещё не знаем)

- Как движок ставит importance на авто-рёбра? По какой эвристике? — не определено.
- Как цикл-гард взаимодействует с мульти-родительством? Мульти-родитель усиливает риск длинных циклов.
- Как `abstraction_level` соотносится с тегами? Дублирование? — требует дебата.
- Что такое «вектор наблюдения с явным пропуском» (N-037)? — пропуск = агент объявляет «я НЕ вижу уровень X»? Нужно уточнение.
- Поддерживает ли `mode: controlled|flexible|hybrid` (из канваса) ещё не разобранные сценарии гибкого payload? — не тестировалось.
