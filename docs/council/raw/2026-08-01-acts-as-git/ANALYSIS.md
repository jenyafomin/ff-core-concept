# T-ACTS-AS-GIT — акты как git

> **Линза:** abstract-thinker — иду ВВЕРХ. Цель файла: дать ментальную модель «акт ↔ git-примитив»,
> развести развилку copy-vs-link для «одной истины в разных ветках/источниках», связать с уже
> ратифицированным (ADR-0008), и показать, КАК это реально помогает строить концепты. Фаза = дизайн,
> не код. Ничего не строим — растим правильную модель.

## 0. Разведение двух «git» (снятие путаницы ПЕРВЫМ ходом)

В проекте теперь ДВА разных разговора про git. Их легко слить — и тогда мы переоткроем решённое или
запутаем новое. Держим их ортогональными:

| | **Концепт-A (уже решён 07-26)** `graph-tree-git-projection` | **Концепт-B (эта тема, T-ACTS-AS-GIT)** |
|---|---|---|
| Про что | ВНЕШНИЙ git-репозиторий (реальные `.git`) и как граф к нему относится | НАШ СОБСТВЕННЫЙ лог актов КАК git (git как алгебра над своей историей) |
| git здесь | **read-only СИГНАЛ**, ingest коммита → `observation`-акт | **МЕТАФОРА/операции** над одним логом `acts[]` |
| Ключевой вывод | git НИКОГДА не источник истины актов (T-2) | git-примитивы = операции ПРОЕКЦИИ над логом, тоже не новые источники истины |

**Одной фразой:** Концепт-A сказал «внешний git мы только читаем». Концепт-B спрашивает «а не устроить ли
НАШ лог так, чтобы им можно было пользоваться КАК git — ветки-гипотезы, checkout момента, merge, версии».
Это не дубль, а следующий слой: **A — про импорт; B — про внутреннюю алгебру.**

## 1. Модель акт ↔ git-примитив

### Ядро (ре-фрейм)
**Git — это не хранилище файлов, это АЛГЕБРА над append-only историей.** Коммиты неизменяемы; ветка — это
указатель на историю; состояние рабочей копии — свёртка истории; merge/diff — операции над историей. У нас
эта история УЖЕ ЕСТЬ и уже ратифицирована как истина субстрата: `acts[]` (ADR-0008, лог = система-записи;
граф = `fold(acts)`). Значит **git-примитивы ложатся на нас не как новая машина, а как ИМЕНА операций над
тем логом, что уже есть.** Ничего в фундаменте не меняется — мы получаем богатый словарь бесплатно.

### Таблица соответствий
| git-примитив | Наш эквивалент | Опора / статус |
|---|---|---|
| commit (immutable, есть parent, sha) | **акт** (`id·actor·provenance·recordedAt·edges`) | I-3/I-4, ADR-0008 write-model |
| история / commit-DAG | **журнал `acts[]`** (append-only) | I-3 |
| working copy / HEAD-состояние | **current-state = `fold(acts)`** (read-model) | I-5, ADR-0008 |
| checkout момента («стартовать с определённого момента») | **as-of replay**: `fold(acts where recordedAt ≤ T)` | битемпоральные ПОЛЯ есть (axes-and-time §3); движок **отложен D-5** ⚠️ |
| branch (линия работы) | **не новый лог**, а **метка-линия** над одним логом: `fold(acts в предках линии L)` | см. §4 развилка представления |
| tag / release | **версия проекции** (`projectionId/version`) или именованный снапшот свёртки | I-6 |
| diff | проекция разницы двух свёрток (две линии / два момента) | read-only view |
| merge | **новые merge-акты**, сводящие две линии в одну свёртку | I-3 (merge = append, не мутация) |
| conflict | два акта утверждают несовместимое про один `node/field/valid-interval`, reducer не может выбрать детерминированно | см. §5 |
| rebase / force-push | **запрещено** — это переписывание истории, ломает I-3/I-4 | граница (то же, что T-2 в Концепте-A) |

### Два несущих следствия
1. **Ветка — НЕ второй лог и НЕ новый примитив.** Это ось проекции: разметка/линия над единым `acts[]`.
   Так «ветвление» не воюет с ADR-0008 (один журнал-истина) и с I-3 (один append-only поток). Это прямое
   применение `prefer-properties-over-poles`: «ветка» — свойство (линия) свёртки, а не отдельный полюс-стор.
2. **checkout-момента = as-of, и он ОТЛОЖЕН (D-5).** Поля `recordedAt/validFrom/validTo` заложены сейчас
   (axes-and-time §3.3), но движок time-travel — post-MVP. Значит «стартовать с момента» доступно как
   forward-compat, не как фича v1. Ветку-как-метку можно проектировать раньше, чем полный as-of.

## 2. Развилка copy-vs-link + ограничения

**Зерно владельца:** «меняем ветку, а ветка — одна истина в ДРУГОМ источнике → либо КОПИЯ, либо явно
СВЯЗЫВАЕМ, и понимаем ограничения.»

### Ре-фрейм: это вопрос ИДЕНТИЧНОСТИ, не хранения
Развилка copy-vs-link — это на самом деле один вопрос: **«это ТА ЖЕ вещь, которая эволюционирует, или
НОВАЯ вещь, рождённая от неё?»** (I-1 stable id — единица тождества).

- **LINK (по умолчанию) = тот же `id`, ветка = набор актов над ОБЩЕЙ идентичностью.**
  Ветка-гипотеза добавляет акты, помеченные линией L, к тем же узлам. Проекция линии L = свёртка её
  предков-актов. Мейнлайн и ветка — ОДНА вещь под разными свёртками.
  - *плюсы:* ноль дублирования; ветка автоматически «следует» за источником (общие узлы); merge дешёв.
  - *ограничения:* идентичности сцеплены — нельзя структурно разойтись; «принять ветку» = реконсиляция
    утверждений на общих `id`; две противоречивые «текущие» истины на один `id` живут только через метку-линию.

- **COPY (opt-in) = ФОРК идентичности: новые `id` через fork-акт, записывающий origin `id` + точку форка.**
  Ветка получает собственные узлы; дальше эволюционирует независимо.
  - *плюсы:* полная независимость; можно радикально разойтись; источник не «дёргает» копию.
  - *ограничения:* **дрейф/устаревание** — копия НЕ обновляется автоматически при смене источника; ты
    владеешь реконсиляцией расхождения; провенанс форка обязателен (I-2).

### Вердикт (правило)
**LINK по умолчанию; COPY — только когда ветка ДОЛЖНА эволюционировать независимо от источника и
расхождение — цель, а не побочный эффект.** Формула-триггер: *«эти двое должны остаться ОДНИМ и тем же
(следовать источнику) → LINK; должны стать РАЗНЫМИ вещами (разойтись) → COPY».* Это снова свойство
(fork-identity? да/нет), а не жёсткий полюс.

### Ограничения, которые копия/связь НЕ имеют права нарушить
1. **append-only (I-3):** ни copy, ни link не мутируют — оба суть НОВЫЕ акты (fork-акт / branch-акты).
2. **Единый источник истины (ADR-0008) — ключевой разбор страха владельца:**
   **COPY ≠ второй источник истины.** Копия вводит вторую ИДЕНТИЧНОСТЬ, но её истина всё равно живёт в
   ОДНОМ логе `acts[]`. Внутри субстрата второго лога-истины не появляется. → «одна истина в другом
   источнике» распадается на два случая:
   - *источник = внутри субстрата* (другая ветка/линия) → LINK честен: один лог, одна истина, метка-линия.
   - *источник = ВНЕ субстрата* (внешняя система) → это уже адаптер (§3): тогда COPY несёт **staleness-маркер**
     (ADR-0006 eventual-consistency) + провенанс-ссылку на внешний origin. Честная копия с признанным
     отставанием, а не молчаливый второй авторитет.
3. **Детерминизм replay (I-5):** LINK = чистая проекция (детерминирована по определению). COPY = записанный
   fork-акт (детерминированно воспроизводится при rebuild). Оба переживают `rebuild --from journal`.
4. **Провенанс форка (I-2):** copy обязана записать `origin-id @ точка-форка` — иначе теряется «откуда
   это» и merge/сравнение невозможны.

## 3. Адаптеры / версии

**Зерно владельца:** «адаптер может быть к чему угодно — даже к самому себе / к другой версии; разные
связи/переходы между версиями.»

**Ре-фрейм:** *адаптер = отображение (reducer) между представлениями.* Тогда copy-vs-link — это два ВИДА
адаптера, а версия-к-версии — тоже адаптер:

- **link-адаптер** = ЖИВАЯ проекция над общим логом (следует источнику, детерминирован).
- **copy-адаптер** = СНАПШОТ + провенанс origin (замороженный срез, несёт staleness если origin внешний).
- **адаптер к самому себе** = тождественная ре-проекция (re-index / re-fold без смены смысла).
- **адаптер к другой версии** = migration-reducer между `projectionId/version` (I-6): «эволюционирует
  ПРОЕКЦИЯ, не лог» (ADR-0008 §Consequences). Смена reducer = новая версия read-model, пересобранная из
  неизменного лога.
- **merge** = адаптер, сводящий ДВЕ линии актов в одну свёртку.

Вывод: «git как адаптеры между версиями» — не отдельная машина, а **семейство reducer-ов над одним логом**.
Это ровно ADR-0008 + I-6, только названное словарём git. Версии, ветки, копии, merge — все выражаются как
адаптеры-проекции; фундамент (лог) неизменен.

## 4. Как это РЕАЛЬНО строит концепты (цель владельца #4)

Здесь тема окупается — иначе «акты как git» остаётся красивой метафорой без ценности.

**Killer-паттерн: КОНЦЕПТ РАЗВИВАЕТСЯ КАК ВЕТКА-ГИПОТЕЗА над логом.**

1. **Branch** — заводим линию-гипотезу концепта (по умолчанию LINK: новые акты, помеченные линией
   `hypothesis:X`, над общими узлами). Граф проецирует «как выглядел бы концепт, если принять гипотезу».
2. **Develop** — агент/владелец добавляют акты в линию; current-state гипотезы = свёртка её актов. Мейнлайн
   («во что верим сейчас») не тронут.
3. **Accept → Merge** — принятие концепта = merge-акты, сводящие линию в мейнлайн. Проекция мейнлайна
   теперь включает концепт.
4. **Reject → LOSE-NOTHING** — отклонённая ветка ОСТАЁТСЯ в логе (как заброшенная git-ветка в истории),
   просто не сворачивается в принятую проекцию. Ничего не стёрто (doc-tree закон №10, I-4). Позже к ней
   можно вернуться — история гипотез сохранена.

**Прямая связка с протоколом диалога-проектирования проекта** (CLAUDE.md, `docs/dialogue/`):
- **conflict ↔ ребро `tension-with`.** Git-конфликт = «два акта несовместимо утверждают об одном узле».
  Это буквально узел-`problem` / ребро `tension-with` из графа диалога. Merge не обязан авто-выбирать.
- **merge-resolution ↔ узел `decision`.** Разрешение конфликта = `decision`-акт (человек/агент выбирает).
  Так «слияние» концептов = ровно те решения, что проект и так фиксирует узлами.
- **as-of ↔ «во что мы верили тогда».** Когда включится time-travel (D-5), «checkout момента» даст
  «покажи концепт, каким мы его считали 3 дня назад» — прямая ценность для дизайн-диалога.

**Почему это апгрейд ADR-0008:** ADR-0008 сделал лог ИСТИНОЙ, но описал его как летопись («что произошло»).
Эта тема превращает лог в **верстак параллельных гипотез**: граф = «принятый мейнлайн», ветки = «черновики
концептов в работе», merge = «принятие», reject = «сохранённый тупик». Лог перестаёт быть пассивным
журналом и становится активным инструментом конструирования — это и есть цель #4.

## 5. Что УЖЕ решено (НЕ дублируем)

- **ADR-0008 (approved):** лог = система-записи; граф = детерминированная проекция `fold(acts)`; ни одно не
  заменяет другое; проекции версионируются, лог неизменен. → фундамент этой темы; НЕ переоткрывать.
- **I-3/I-4 (жёсткие):** append-only, акт иммутабелен; коррекция = supersede-акт, не мутация. → отсюда
  запрет rebase/force-push над логом; merge = append новых актов.
- **I-5/I-6:** состояние = сносимая проекция; проекция несёт id+version. → версии/адаптеры = reducer-ы, не
  новый лог.
- **axes-and-time.design.md §3:** битемпоральные ПОЛЯ на акте заложены; as-of/time-travel ОТЛОЖЕН (D-5);
  коррекция valid-time = новый superseding-акт. → «checkout момента» = as-of = post-MVP, не изобретаем заново.
- **Концепт-A `graph-tree-git-projection` (Q0–Q5, 07-26):** ВНЕШНИЙ git = read-only сигнал; коммит →
  `observation` (с фильтром Q5-fix); git-ветка = стор/проекция, а не тип узла; но ветка, несущая
  адресуемый смысл → узел-`stream/work`. → эта тема НЕ противоречит: мы говорим про ВНУТРЕННИЙ лог, а не
  внешний git. Паттерн «смысл, который агент адресует → узел» переиспользуем для ветки-гипотезы концепта.

## 6. Открытые развилки (владельцу / в совет)

1. **Представление ветки: метка-линия над одним логом vs узел-`hypothesis`/`stream`.**
   Рекомендация (по паттерну Q3): линия = ось проекции; НО концепт-гипотеза, которую владелец/агент
   адресуют, обсуждают и мержат — вероятно, тянет на первоклассный узел (как `stream/work` в Концепте-A).
   Развилка: ветка = только метка свёртки, или адресуемый узел-гипотеза с провенансом форка? (влияет на
   §2 и §4).

2. **Copy-vs-link: где дефолт и что ПРИНУДИТЕЛЬНО требует copy.**
   Модель говорит «LINK по умолчанию, COPY при намеренном расхождении». Нужны РЕАЛЬНЫЕ кейсы владельца:
   когда концепт/узел ОБЯЗАН форкнуться в новую идентичность (напр. «шаблон → экземпляр», «проект-A
   клонирован в проект-B»)? Без живых кейсов правило остаётся абстрактным.

3. **Разрешение конфликта: авто-reducer vs decision-акт.**
   Для данных возможен last-writer-wins по `recordedAt` (axes-and-time §3.4). Для КОНЦЕПТОВ конфликт
   семантический → должен требовать `decision`-акт (человек/агент), а не молча авто-мержить. Развилка:
   какие конфликты авто-разрешимы, какие обязаны всплыть как `problem`/`tension-with` и ждать решения?

4. **(timing) Нужен ли as-of для концепт-веток в v1, или хватает метки-линии без time-travel?**
   «Checkout момента» = as-of = отложен D-5. Ветвление-как-метка может работать раньше. Развилка: MVP
   концепт-веток без time-travel (сравниваем текущие свёртки линий), а «как было на дату T» — post-MVP?
