# Архитектор — фиксация тонкого паспорта (подтверждения + каркас)

- **Status:** draft
- **Owner:** architect
- **Date:** 2026-06-21
- **Роль в дебате:** закрываю ВСЁ, кроме спора «уровень абстракции = поле или линза» (его ведут два адвоката).
  Готовлю каркас зафиксированного паспорта со слотом-заглушкой под их решение.
- **Вход:** ADR-0001 (N-020: один home + opt-in каскады), VERDICT-2026-06-19 (тонкий паспорт ~5 граней),
  RESEARCH-2026-06-21 (инвариант несущести, 3 рода control-plane), THREAD N-036/N-041/N-046.
- **Инвариант несущести (стоп-правило раздувания):** *поле несущее ⟺ по нему ИИ/движок решает, как обращаться
  с ячейкой, НЕ вскрывая payload и НЕ зная тип.* 4 первичные операции по паспорту: **сослаться · разместить ·
  довериться · датировать.** Всё, что не одна из них, — НЕ паспорт.

## 1. Три подтверждения

### (а) Важность-на-ребре + один home + opt-in родители — ПРИНЯТО (уверенность высокая)

**Вердикт: складываются.** N-041 (важность относительна к родителю) и N-020 (один привилегированный home)
решают РАЗНЫЕ проблемы и не пересекаются:
- N-041 убирает неоднозначность **важности** (нет глобального скаляра → нет спора max/min/avg).
- Один home убирает неоднозначность **контекста/каскада** (какой родитель задаёт дефолтный контекст и наследование).

Это две ортогональные оси одной грани Belonging, а не конкуренты. Граф (N-036) разрешён: нода имеет N родителей-рёбер;
ровно одно из них помечено `home:true`.

**Инвариант BELONGING (несущий, проверяемый движком при записи):**

1. **Ровно один home.** Для любой ноды среди её входящих рёбер `rel:child-of` (или эквивалент принадлежности)
   **ровно одно** несёт `home:true`. Ноль — только для корня/inbox (явные системные ноды). Два и более — ошибка
   целостности, движок отклоняет запись. `home` — это флаг НА РЕБРЕ, не отдельное поле ноды (уточнение к ADR-0001,
   где `home` был полем-указателем — см. §6, правка к ADR).
2. **Правило слияния контекста.** Каскад контекста (наследование sensitivity-дефолтов, тегов-категорий, дефолтной
   линзы) идёт ТОЛЬКО по home-ребру. Остальные родители — opt-in: каскадят, лишь если их ребро помечено
   `cascade:true` + `cascade_order:<int>`. При конфликте наследуемых значений выигрывает меньший `cascade_order`;
   home-ребро = неявный `cascade_order: 0` (всегда первый). Детерминированно, без max/min/avg.
3. **Правило глобального запроса важности.** Глобальной важности НЕ существует (следствие N-041). Поэтому:
   - запрос «важность ноды X» **без контекста-родителя — невалиден** (движок возвращает не скаляр, а карту
     `{parentId → priority}`);
   - запрос планировщика «что делать сейчас?» обязан указать **контекст-якорь** (родитель/линзу). Дефолтный якорь,
     если агент не указал, — **home-ребро** (это и есть смысл привилегии home: дефолтная точка отсчёта для
     глобально звучащих запросов). Так «глобальный запрос» сводится к «запросу в контексте home».

**Поля ребра принадлежности (несущие):** `to` · `rel` · `home:bool` · `priority:number` · `sort:string?` ·
`cascade:bool?` · `cascade_order:int?` · `provenance: manual|auto|inferred`.

Замечание (уверенность средняя): шкалу `priority` НЕ фиксирую (N-036: «не 1-5, условно до бесконечности»). Архитектурно
`priority` — это `number` (произвольный, дефолт 0), а семантику «вверх/вниз/границы» задаёт **линза-сортировщик**
(control-plane), не паспорт. Это снимает спор о шкале с уровня ядра.

### (б) Вектор наблюдения = узел-ЛИНЗА, не поле ноды — ПРИНЯТО (уверенность высокая, единогласно по 4 линзам)

**Вердикт: подтверждаю без правок.** Вектор наблюдения / угол обзора — это **отношение наблюдатель→подграф**, а не
свойство ноды. Если положить его полем — получаем God-object (одно поле «угол» не может одновременно служить CEO и
разработчику). Линза = сохранённый узел control-plane: предикат отбора + политика раскрытия (id/заголовок/payload) +
класс (hard-ABAC право vs soft-перцепция).

**Что даёт ПАСПОРТ (и только это):** *оси фильтрации*, по которым линза строит проекцию, не вскрывая payload:
`type` · `epistemic` · `sensitivity` · время (`created`/`updated`) · home/принадлежность. Линза ВЫБИРАЕТ проекцию;
важность СОРТИРУЕТ внутри неё. Разные слои — не смешивать.

Уточнение (моё, уверенность средняя): даже опциональный тег-подсказка уровня абстракции (если спор решат в пользу
«тега») — это всё равно лишь ещё одна **ось фильтрации**, а не «вектор». Вектор остаётся линзой в любом исходе спора.
Это держит слот-заглушку §6 совместимой с обеими ветками.

### (в) `epistemic` enum + значение `draft` — ПРИНЯТО с уточнением (уверенность высокая)

**Вердикт: принимаю enum `draft | proposal | hypothesis | fact | archived`; НЕ путать с `state`.**

- `epistemic` — ось **доверия к содержимому** (насколько можно опираться). Универсальна, обязательна, в паспорте.
- `state` — ось **рабочего процесса** (task: open/doing/done). Типо-зависима → НЕ в ядре, живёт в модуле/типе.
- Это две ортогональные оси (Принцип 4 ADR-0001) — подтверждаю разделение.

`draft` обоснован (аналитик): человеческий черновик ≠ предложение агента. `draft` = «человек ещё пишет, не готово»;
`proposal` = «агент предложил, ждёт повышения». Семантический порядок зрелости: `draft → proposal → hypothesis → fact`,
`archived` — терминальный вне линии.

Помечаю кандидата на будущее расщепление (уверенность ниже, абстракт): если `epistemic` начнёт нести два смысла
(зрелость документа ⟂ доверие к утверждению), расщепить на `epistemic` ⟂ `maturity`. **Сейчас не делаем** —
одна ось + значение draft. Флаг на будущее, не блокер.

## 2. Блокер «кто авторизует epistemic→fact» + клапан внешних действий (модель)

Это «первый к закрытию» из ADR-0001 и острейший блокер из RESEARCH §4. Даю конкретную модель.
Уверенность: модель — высокая; пороги/детали политики — средняя (настраиваемо).

### 2.1. Принцип
Право поднимать `epistemic` и право совершать необратимое внешнее действие — это **политики**, а они (Принцип 0:
control-plane = узлы) живут как **узлы-политики** в графе, а не зашиты в код. Движок — лишь исполнитель (enforcement),
правило — данные.

### 2.2. Кто может поднимать epistemic (лестница доверия)

| Переход | Кто авторизован | Где правило |
|---------|-----------------|-------------|
| `draft → proposal` | автор-агент или человек (любой first-party источник) | дефолт-политика |
| `proposal → hypothesis` | агент с capability `assert:hypothesis` | узел-политика |
| `hypothesis → fact` | **НЕ сам автор-агент по самооценке.** Только: (1) человек-владелец, ИЛИ (2) агент с явной capability `assert:fact`, выданной владельцем для данного `type`/scope, ИЛИ (3) проверочный агент ≠ автор (разделение обязанностей) | узел-политика `promotion-policy` |
| `* → fact` сторонним (3rd-party) агентом | **запрещено** дефолтно (N-023: «всё видно» = first-party; сторонний — за пропуском) | узел-политика + principal |

Ключевые инварианты:
- **Самоповышение до fact запрещено.** Агент не может поднять собственный вывод до `fact` без внешнего
  авторизатора (человек или отдельный агент). Это закрывает дыру «клапан открыт по самооценке» (RESEARCH §4.1).
- **Каждое повышение логируется трейс-узлом** (`actor`, `from`, `to`, `policy_ref`, `ts`) — наблюдаемость
  «видно, что делает ИИ». Трейс — узел движка, не паспорт.
- **first-party vs сторонний различается по `principal` + `source`** (оба типизированы, в паспорте/ребре).

### 2.3. Где живёт правило: узел-политика (control-plane)
`promotion-policy` — узел control-plane, контракт:
```
{ applies_to: <type|scope|*>, transition: "hypothesis→fact",
  requires: { capability: "assert:fact", actor_class: "human|verifier-agent",
              not: "author" }, principal_scope: <id> }
```
Движок при попытке смены `epistemic` ищет применимую политику, проверяет actor против `requires`, иначе отклоняет.

### 2.4. Клапан внешних действий
Клапан — **НЕ ось ноды** (демонтирован в VERDICT §8), а **политика enforcement в движке**, читающая паспорт.
Контракт клапана перед любым необратимым внешним действием (отправить письмо, оплатить, удалить вовне):

1. Движок собирает **все ноды, задействованные** в действии (вход + транзитивно прочитанные по линзе).
2. Для каждой проверяет `epistemic`. **Если хоть одна не `fact`** → действие по умолчанию **закрыто**
   (`epistemic≠fact ⇒ внешнее действие требует апрува`).
3. Проверяет `sensitivity` каждой задействованной ноды против политики раскрытия адресата (не утекает ли приватное).
4. Проверяет `principal`: действует ли агент в рамках своего арендатора/scope.
5. Если закрыто → эскалация владельцу (апрув) ИЛИ опциональный ручной `override` на действии (логируется).

Итог блокера: **авторизатор fact = человек или отдельный verifier-агент (никогда не сам автор); правило = узел
`promotion-policy`; клапан = движок проверяет epistemic+sensitivity+principal на ВСЕХ задействованных нодах перед
необратимым действием, дефолт — закрыто.** Это разблокирует «контролируемую систему» из декларации в механизм.

## 3. Каркас зафиксированного паспорта

### 3.1. ПАСПОРТ — несущие поля ноды (узкий слой, читается без вскрытия payload)

| Поле | Тип | Операция | Обяз. | Примечание |
|------|-----|----------|-------|-----------|
| `id` | ULID | сослаться | да | стабильный ключ связей, ≠ имя файла/title |
| `type` | string | разместить/вскрыть | да | открытый реестр; правила → узел-ТИП |
| `schema` | `type@version` | вскрыть | да | какой валидатор; миграции |
| `created` | iso | датировать | да | системное время |
| `updated` | iso | датировать | да | системное; `stale` — движок выводит |
| `epistemic` | enum | довериться | да | `draft\|proposal\|hypothesis\|fact\|archived` |
| `sensitivity` | enum | довериться | да | приватность/ACL; ИИ знает, не вскрывая payload |
| `source` | enum(типизир.) | довериться | да | `human\|agent\|system\|import` (сигнал доверия) |
| `principal` | id (тонкий) | довериться/разместить | да | арендатор; multi-tenant/маркетплейс заблокированы без него |
| `canonical_id` | id? | сослаться | нет | дедуп; **движок проставляет**, не грань-ось |
| `«уровень абстракции»` | — | — | — | **СЛОТ-ЗАГЛУШКА**, см. §3.4 |

Намеренно НЕ в паспорте (вынесено): `importance`/`home` (→ребро), `occurred`/`valid_*` (→модуль), `state` (→модуль),
`actor`/`trace` (→движок), `supersedes` (→ребро), `branches`/`reactivity` (→движок/модуль), payload (→тип).
`title`/`description` — минимальный payload (agent-first резюме), не несущая ось; держим, но как «мин. payload», не грань.

### 3.2. РЕБРО — несущие поля связи

| Поле | Тип | Обяз. | Примечание |
|------|-----|-------|-----------|
| `to` | id \| url | да | цель; url → внешняя (`href:true`) |
| `rel` | string | да | типизированная связь (child-of/involves/supersedes/variant-of/…) |
| `home` | bool | да* | *на рёбрах принадлежности; ровно одно `true` на ноду |
| `priority` | number | нет | важность В контексте этого родителя (N-041); дефолт 0 |
| `sort` | string | нет | вторичный ключ сортировки |
| `cascade` | bool | нет | участвует ли в наследовании контекста (не-home opt-in) |
| `cascade_order` | int | нет | порядок слияния; home = неявный 0 |
| `provenance` | enum | да | `manual\|auto\|inferred`; manual=файл-истина, auto=движок |
| `derived` | bool | нет | true ⇒ ребро вывел движок (не истина-файл); + `rule_ref` |

### 3.3. ДВИЖОК (`@ff/core`, без ИИ) — механика, не данные

- Сериализация frontmatter↔узел; реестр типов + наслоённая валидация.
- Сбор графа из рёбер; backlinks; **цикл-гард + `maxDepth`** (обязателен до кода — RESEARCH §4.4).
- Вывод производного: `stale` (из `updated`+тип), `canonical_id` (дедуп при ingestion), авто-рёбра
  (`provenance:auto`, `derived:true`, `rule_ref`) — кэш движка, НЕ истина-файл.
- **Enforcement:** инвариант одного home; правило слияния контекста; промоушн-политики epistemic; **клапан** (§2.4).
- Контракт запроса с **viewport** (линза применяется здесь): фильтр по осям паспорта → проекция.
- Трейс-узлы (actor/ts/policy_ref) для наблюдаемости.
- `section-index`-конвенция: точки входа в огромные секции (чат=млн) по имени/источнику (ленивая загрузка).

### 3.4. МОДУЛЬ / CONTROL-PLANE — узлы графа (Принцип 0)

- **Узлы-ТИП** — схема payload + валидация конкретного типа.
- **Узлы-ЛИНЗА** — сохранённые проекции (вектор наблюдения, авто-связи, зум секций, сортировщик важности).
- **Узлы-ПАТТЕРН** — сборка подграфа из многих + терминатор рекурсии.
- **Узлы-ПОЛИТИКА** — `promotion-policy` (кто поднимает epistemic), ABAC/раскрытие (клапан), principal-scope.
- **Типо-зависимое** в payload/модуле: `state` (workflow), `occurred`/`valid_from`/`valid_until`, reactivity.

### 3.4-bis. СЛОТ-ЗАГЛУШКА: «уровень абстракции» (почему/что/как/data) — для синтеза

Спор ведут адвокаты. Каркас готов к обеим веткам, синтез подставляет ОДНУ:

- **Ветка «ЛИНЗА» (рекоменд. 3 линзами):** уровень абстракции = **измерение линзы** (control-plane, §3.4), второе
  семейство зума рядом с уровнями в `levels.ts`. В паспорте — НИЧЕГО (или опц. тег-подсказка `level?` как ещё одна
  ось фильтрации, не несущая). Истина = в проекции, которую строит агент. → правок паспорта НЕТ.
- **Ветка «ПОЛЕ» (аналитик):** добавить в §3.1 несущее поле `level: why|how|what|data` (обяз. или опц.). Тогда оно
  становится 6-й осью фильтрации, доступной линзам напрямую. → одна строка в таблицу паспорта.

Оба исхода СОВМЕСТИМЫ с остальным каркасом: линза в любом случае фильтрует по осям; разница лишь в том, лежит ось
в паспорте или вычисляется проекцией. Синтезу достаточно подставить нужную ветку — переписывать каркас не нужно.

## 4. Типология control-plane (формализация, минимальный контракт)

| Род узла | Что делает | Минимальный контракт |
|----------|-----------|----------------------|
| **ТИП** | как вскрыть ОДНУ ячейку | `{ name, version, payload_schema, validate(node)→ok\|errors }` |
| **ЛИНЗА** | как найти/спроецировать ПОДГРАФ | `{ predicate(осиПаспорта), disclosure: id\|title\|payload, class: hard-ABAC\|soft-perception, sort? }` |
| **ПАТТЕРН** | как СОБРАТЬ подграф из многих | `{ compose(подграфы)→подграф, recursion_terminator, maxDepth }` |
| **ПОЛИТИКА** | кто что может (доверие/доступ) | `{ applies_to, condition(actor,principal,осиПаспорта)→allow\|deny, enforce_point: promotion\|valve\|disclosure }` |

Все четыре = узлы графа → граф самохостится, «всё видно ИИ» работает и для control-plane. Один движок проекций
вместо пяти подсистем. (ПОЛИТИКА не была в исходной тройке тип/линза/паттерн — добавляю четвёртым родом, т.к.
блокер §2 показал: доверие/доступ — отдельный род контракта, не сводится к линзе. Уверенность средняя: возможно
ПОЛИТИКА — подвид ЛИНЗЫ класса hard-ABAC; на синтез выношу как открытую развилку «3 рода или 4».)

## 5. Что разблокирует «walking skeleton» (захват→хранение→связь→достать), что отложить

**Нужно ДЛЯ скелета (минимум):**
- Паспорт §3.1 БЕЗ `level` (берём ветку без поля — скелет нейтрален к спору): `id`, `type`, `schema`,
  `created`, `updated`, `epistemic`, `sensitivity`, `source`, `principal`.
- Ребро §3.2: `to`, `rel`, `home`, `priority`, `provenance`. (cascade-поля можно дефолтить.)
- Движок §3.3: сериализация, реестр+валидация одного-двух типов, инвариант одного home, цикл/maxDepth-гард,
  простой запрос «достать по фильтру осей».
- Один род control-plane активно: **ТИП** (чтобы вскрыть ячейку). ЛИНЗА — минимальная (фильтр по осям).

**Можно ОТЛОЖИТЬ (не блокирует первый проход захват→достать):**
- Полная модель ПОЛИТИКА/промоушн epistemic→fact (скелет создаёт ноды как `draft`/`proposal`, до fact не доходит).
- Клапан внешних действий §2.4 (скелет ничего необратимого вовне не делает — только internal CRUD графа).
- ПАТТЕРН-узлы и рекурсия-композиция.
- Авто-рёбра/`derived`, `canonical_id`/дедуп, `section-index` для огромных секций.
- Спор «уровень абстракции» — скелет к нему нейтрален; решаем параллельно, подставляем позже.

**Критично НЕ откладывать даже в скелете** (иначе переделка фундамента): инвариант **одного home**, **типизация
`source`**, **тонкий `principal`** (иначе multi-tenant ломается ретроактивно), **цикл/maxDepth-гард**. Эти четыре —
дёшевы сейчас, дороги потом.

## 6. Правки к ADR-0001 (новый паспорт его уточняет/частично supersedes)

Новый зафиксированный паспорт должен оформиться как **ADR-0002**, помечающий ADR-0001 частично superseded:

1. **`home`: поле-указатель → флаг на ребре** (`home:true`, ровно один). ADR-0001 имел `home: <node-id>` полем ноды;
   ревизия (VERDICT/RESEARCH) переносит на ребро. *Supersedes* эту часть схемы.
2. **`importance: 1..5` поле ноды → `priority:number` на ребре** (N-041). *Supersedes.*
3. **`occurred`/`valid_from`/`valid_until` из ядра → модуль** (типо-зависимо). *Supersedes.*
4. **`state` уже был отдельной осью — подтверждается;** уходит из ядра в модуль (типо-зависим). Уточнение.
5. **`epistemic`: добавить `draft`** → `draft|proposal|hypothesis|fact|archived`. Уточнение enum.
6. **`source`: типизировать** `human|agent|system|import` (был свободной строкой). Уточнение.
7. **`sensitivity`: добавить как обязательную ось доверия** (не было в ADR-0001). Дополнение.
8. **`principal`: добавить тонкий слот.** Дополнение.
9. **`stage: inbox|routed|enriched`** — пересмотреть: это, похоже, частный workflow → кандидат в модуль/движок,
   не несущая ось паспорта (на подтверждение синтезу). Уточнение/возможный supersede.
10. **Клапан/промоушн:** ADR-0001 называл клапан «первым к закрытию», но не определил кто авторизует fact.
    §2 закрывает это узлом `promotion-policy` + enforcement-клапаном движка. Дополнение (ADR-0003 ABAC/доверие).

Что ADR-0001 сохраняет без правок: принципы agent-first, файлы=истина, всё-видно-ИИ, открытые типы, две оси
статуса, связи по id; границы СКИЛ/АГЕНТ/ДВИЖОК.
