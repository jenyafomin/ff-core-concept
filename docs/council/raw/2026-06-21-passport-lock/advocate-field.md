# Адвокат позиции А: уровень абстракции — ОБЯЗАТЕЛЬНОЕ ПОЛЕ паспорта

- **Status:** draft
- **Owner:** advocate-field
- **Date:** 2026-06-21
- **Контекст:** автономный дебат-консилиум (N-048). Цель — сильнейшая защита позиции «уровень абстракции
  (`level: why|how|what|data`) должен быть обязательным полем паспорта интерпретации». Синтез — отдельно.

---

## Тезис

Уровень абстракции (`why | how | what | data`) — это ВНУТРЕННЯЯ характеристика ноды, стабильная для
подавляющего большинства типов, и ИИ вынужден знать её ДО вскрытия payload. Без этого поля паспорт нарушает
свой главный инвариант: «агент принимает решение о том, как обращаться с ячейкой, не зная типа и не вскрывая
содержимое» (N-046, формулировка резюме). Линза/тег не спасают — они работают ПОСЛЕ, паспорт работает ДО.

---

## Часть 1. Четыре сценария, где без поля ИИ вынужден вскрыть payload или знать тип

### Сценарий 1. Агент-суммаризатор: «дай мне картину проекта»

Агент получает подграф из 200 нод: задачи, принципы, логи вызовов, сырые данные метрик, решения. Его инструкция:
«сформируй краткое резюме проекта для CEO». Ожидание: принципы и решения (why/what) — в резюме;
технические детали имплементации (how) — сжать или опустить; сырые числа (data) — не включать.

БЕЗ поля `level`:
- Агент не знает, является ли нода «Принцип: архитектурная независимость» узлом-`why` или это развёрнутая
  техническая нота типа `note`. Единственный способ узнать — прочитать payload.
- Агент не знает, является ли нода «Метрика latency p99: 240ms» сырым data-логом или что-то-важным. Тип не
  помогает: обе могут быть `note` или `metric`.
- Агент вынужден вскрыть payload у ВСЕХ 200 нод — только чтобы решить, какие из них включить в резюме.

**Почему линза/тег не спасает.** Линза строится агентом в момент запроса — она задаёт проекцию подграфа
«какие ноды взять». Но вопрос ДРУГОЙ: взяв ноду, агент должен знать, что с ней делать. Линза отвечает на
«что взять из графа», `level` — на «как обращаться с тем, что взял». Это два разных слоя. Тег (`level?`)
опционален → агент не может на него положиться: в половине нод его нет, и агент возвращается к вскрытию payload.

### Сценарий 2. Агент-планировщик: «что делать сегодня?»

Агент строит дейли-план. Среди нод — стратегическая цель («удвоить выручку», уровень why),
тактический шаг («написать API-эндпоинт для экспорта», уровень how), сырой лог вчерашней активности (data).

БЕЗ поля `level`:
- Агент не знает, что стратегическую цель нужно лишь учитывать как контекст, а не ставить в to-do.
- Агент не знает, что сырой лог — не задача, а прошлое. Если оба лежат в одном родительском узле проекта,
  различить их без payload невозможно.
- Добавление в план «удвоить выручку» как задачи на сегодня — классический провал при потере уровня.

**Почему линза не спасает.** Линза «дейли-планировщик» может отфильтровать по типу `task`, но задачи бывают
стратегическими (why-level) и тактическими (how-level). Тип `task` не различает. `level` различает без payload.

### Сценарий 3. Агент-обучатель: строит обучающий маршрут

Агент формирует путь для нового сотрудника: «начни с принципов (why), потом поймёшь архитектуру (what),
потом читай имплементационные гайды (how), логи смотри только если нужна отладка (data)».

В графе — 500 нод по проекту: принципы команды, ADR, спеки, сырые баги, конфиги, митинг-ноты.

БЕЗ поля `level`:
- Агент должен классифицировать каждую ноду по уровню, чтобы выстроить маршрут. Без `level` — только через
  чтение payload + эвристики по типу. Типы (`principle`, `adr`, `spec`, `meeting-note`, `config`) частично
  коррелируют, но не покрывают: ADR может быть `why` («мы выбрали граф вместо реляционной» — ответ на вопрос
  зачем) и `what` («контракт хранения узлов» — описание решения), и `how` (детали реализации миграции).
- Чтобы правильно вставить ADR в маршрут, агент обязан прочитать его. Умноженное на 500 нод — это не маршрут,
  это полный обход с прочтением.

**Почему тег не спасает.** Автор мог не поставить тег. Или поставил неверно. Обязательное поле — с
определёнными значениями — это не «подсказка», это контракт. Тег — подсказка без гарантий.

### Сценарий 4. Мульти-агентный граф: агент делегирует другому агенту

Агент-оркестратор решает, кому передать ноду для обработки. У него два специализированных субагента:
- `why-agent`: синтезирует принципы, строит обоснования, задаёт направление;
- `data-agent`: парсит метрики, агрегирует логи, строит числовые отчёты.

БЕЗ поля `level` в паспорте оркестратор не может маршрутизировать ноду без прочтения. Но читать payload —
это нарушение принципа «паспорт говорит за ноду». Альтернатива: оркестратор читает тип. Но как показано в
сценарии 3 — тип не однозначно определяет уровень.

Критически: в многоагентной системе оркестратор маршрутизирует сотни нод в секунду. Чтение payload для каждой
— это не архитектурная проблема, это масштабирующийся сбой. `level` в паспорте — это O(1) маршрутизация
против O(N×payload_size).

## Часть 2. Опровержение аргумента «наблюдатель-относительно»

### Аргумент оппонента

«Один узел — "почему" для CEO, "как" для разработчика. Уровень абстракции — это отношение наблюдатель→нода,
а не свойство ноды.»

### Опровержение

**Аргумент верен для меньшинства случаев — но из него делается универсальный вывод.**

Рассмотрим реальный состав информационного графа (типичный «паспорт» жизни-платформы):

| Нода | Уровень для любого наблюдателя | Относительный? |
|------|-------------------------------|----------------|
| «Мы строим платформу для агентов, потому что хотим жить без ручных операций» | **why** всегда | Нет |
| Сырой лог Telegram за 2026-06-20, 14:32–14:38 | **data** всегда | Нет |
| Конфиг environment-переменных сервера | **how** (детали реализации) | Почти нет |
| Спецификация API: «ноды возвращают id, type, level» | **what** (контракт) | Почти нет |
| ADR-0001: «мы выбрали граф вместо реляционной БД» | why/what — спорно | ДА, случай относительности |

Относительные случаи — это в первую очередь «граничные артефакты»: ADR, стратегические спеки, высокоуровневые
задачи. Их в информационном графе 10–20% по объёму. Остальные 80–90% — принципы, логи, конфиги, сырые данные,
тактические задачи — имеют уровень, не зависящий от того, кто смотрит.

**Решение для 80%:** явное поле, заполняется при создании ноды (или выводится движком из типа как дефолт).

**Решение для 20% «относительных»:** дефолт от типа + override при необходимости. ADR по умолчанию `what`
(описывает решение), но конкретный ADR-0001 может быть помечен `why`, если автор хочет сигнализировать:
«это про принцип, не про детали». Линза наблюдателя при этом остаётся — но она работает ПОВЕРХ поля, не ВМЕСТО.

**Ключевое различие:** «уровень абстракции» и «угол зрения наблюдателя» — два разных слоя:
- `level` в паспорте = «что нода знает о себе» (онтологический уровень создания информации);
- линза наблюдателя = «через какой фильтр смотрит агент в данный момент».

Они не противоречат — они дополняют. Нода `why` через линзу «дайли-агент» будет обработана как «стратегический
контекст», через линзу «CEO-дайджест» — как «ключевой тезис». В обоих случаях агент знает, что это `why`,
и не читает payload для классификации.

Аналогия из реального мира: контейнер на корабле маркирован «хрупкое, не переворачивать» — это свойство
содержимого, не оценка наблюдателя. Таможенник смотрит на ярлык иначе, чем грузчик, — но ярлык один, и он
несёт неизменную функцию. Убрать ярлык, потому что «разные наблюдатели видят по-разному», — значит переложить
классификацию на каждого обработчика.

## Часть 3. Конкретная форма поля

### Enum

```
level: "why" | "how" | "what" | "data"
```

Семантика:
- `why` — принцип, цель, обоснование, мотивация («зачем»);
- `what` — контракт, спека, описание решения, требование («что»);
- `how` — имплементация, инструкция, детали реализации («как именно»);
- `data` — сырые факты, логи, метрики, записи событий (не интерпретация, а материал).

### Обязательное или с дефолтом?

Предложение: **обязательное с дефолтом от типа, выводимым движком.**

То есть:
- При создании ноды движок выставляет `level` по умолчанию исходя из `type@version` (если тип=`principle` → `why`,
  тип=`log-entry` → `data`, тип=`spec` → `what`, тип=`guide` → `how`).
- Автор может переопределить (`level: why` для ADR, если хочет сигнализировать принципиальность).
- В паспорте поле ВСЕГДА присутствует (движок гарантирует) — агент может на него положиться без проверки
  «а вдруг тега нет».

Это устраняет главное слабое место опционального тега: «половина нод без тега → агент возвращается к payload».

### Соотношение с осью линзы

Линза (сохранённый запрос агента, узел control-plane) использует `level` как **один из предикатов фильтрации**:
- `lens: { level: ["why", "what"], epistemic: ["fact"], sensitivity: ["public"] }` — конкретный пример запроса
  CEO-дайджеста.

Таким образом:
- `level` в паспорте = **ось данных** (что нода объявляет о себе);
- линза = **запрос к осям** (что агент хочет увидеть).

Поле не заменяет линзу. Линза не заменяет поле. Это два независимых, дополняющих слоя.

## Часть 4. Честная цена позиции

### Где позиция слаба

**1. Риск непоследовательного заполнения.** Если 80% нод имеют очевидный уровень, а 20% — спорный, авторы будут
заполнять 20% произвольно или забывать. Система получит «замусоренное» поле, которому агент будет доверять больше,
чем стоит.

Ответ: дефолт от типа + движок-валидатор (если `type=principle` и `level=data` — предупреждение) снижает риск.
Это не устраняет проблему полностью, но делает её управляемой.

**2. «Одна нода — несколько уровней» (реальный пример: митинг-нота с принципом внутри).** Встречаются ноды,
которые содержат и принцип, и конкретные шаги. Одного `level` мало.

Ответ: это сигнал, что нода требует «дефектовки» (N-038) — разбить на компоненты. Паспорт не обязан
поддерживать плохо структурированные ноды — он обязан честно классифицировать хорошо структурированные.
Если нода содержит несколько уровней, правильное действие — декомпозиция, а не добавление «multi-level»-флага.

**3. Четыре значения — не всегда достаточно.** Между `why` и `what` есть «vision» (более высокий уровень зачем).
Между `what` и `how` — «design» (архитектурные решения без деталей реализации).

Ответ: четыре значения — намеренно грубая сетка. Это сила, а не слабость: агент принимает решение быстро, без
тонкой классификации. Расширение до 6-8 значений — возможное будущее, если появится конкретная потребность.

### Почему выгода перевешивает

- Три из четырёх сценариев выше показывают вскрытие payload при отсутствии поля. Это не гипотетические риски —
  это следствие инварианта «паспорт говорит за ноду», который сам проект определил несущим.
- Дефолт от типа снижает бремя заполнения до нуля для 80% нод и до «опционального override» для 20%.
- Поле не раздувает паспорт — это одна строчка в frontmatter. Тогда как отсутствие поля раздувает ЛОГИКУ
  агентов (каждый вынужден самостоятельно решать проблему классификации, каждый по-своему).
- «Линза как замена» требует, чтобы каждый агент знал, какие типы соответствуют каким уровням — то есть
  встраивает знание схемы данных в агентскую логику. Это то самое «знает тип», от чего паспорт должен
  освобождать агентов.

## Итоговая рекомендация позиции А

Включить `level: "why" | "how" | "what" | "data"` в паспорт как **обязательное поле с дефолтом от типа**.

Роль: ось данных паспорта (что нода объявляет о себе) — не заменяет линзу наблюдателя, но является одним из
предикатов, по которым линза фильтрует. Агент маршрутизирует, суммаризирует и делегирует без вскрытия payload.
Движок выставляет дефолт при инджестии. Автор может переопределить.

Это не раздувание паспорта — это закрытие дыры в инварианте.
