## КОНСЕНСУС
1. **Файлы = ИСТИНА. Индекс/тень = ЭФЕМЕРНОЕ ВЫЧИСЛЕНИЕ**, не вторая истина; пересобираем из нуля
   (full-rebuild по умолчанию, пока быстрый). Это снимает риск рассинхрона архитектурно, а не дисциплиной.
2. **Не строить полный индекс сейчас. Отложить до ПОРОГА.** Триггер = **300 живых узлов**
   (`store.list().length`) **+ usage-gate** (Skeptic): ≥1 ребро/день 7 дней подряд — иначе вся тень
   решает несуществующую проблему. До порога — **обход в памяти** (один проход по загруженным узлам).
3. **Схему `@ff/core` СЕЙЧАС не менять.** `parentId` остаётся, `links[]{to,rel}` уже есть и достаточно
   для v1. Мульти-родители — отложить (позже в edge-таблице тени, НЕ в frontmatter `parents[]`).
4. **Первый реальный шаг (Pragmatist):** утилиты обхода в памяти в `@ff/core` — `getChildren(id, nodes)`
   + `getLinkedTo(id, nodes)` (обратный обход). Без БД, без нового пакета. Watcher (chokidar) — отдельный
   минимальный пакет позже; для рёбер он не нужен, пока граф влезает в `Map<id,node>`.
5. **Движок (когда понадобится): SQLite + better-sqlite3, НЕ DuckPGQ** (нестабильные биндинги,
   преждевременно; DuckPGQ — только >5000 узлов или PGQ-запрос, невыразимый через JOIN). Строить как
   **inverted edge-list + кэш важности**, а НЕ граф-БД (обходы редки, ранжирование часто).
6. **Важность — РАЗРЕШЕНО:** **ручной слайдер 1-5 при создании + наследование от родителя** = база
   (ноль трения). **touch-счётчик** (как часто открываю) = доп. сигнал в UI, НЕ замена («Цель жизни» =
   важность 5, но открывается редко → чистый decay превращает «важное» в «популярное»). **Центральность
   — отвергнута как сигнал ранжирования** на разреженном личном графе (мусор); только диагностика
   (хабы/сироты), валидна если граф >200 узлов. Формула на будущее: `importance = w1·manual(наслед) +
   w2·touch + w3·localDegree`; **стартуем с w1 only**.
7. **Канонический запрос (Reframer):** `getContext(nodeId, budget)` — «контекст-конверт узла X: предки
   (каскад) + N важнейших соседей на глубину D, ранжир важность×близость, в токен-бюджет K». Это
   eventual core-API; до порога считается обходом в памяти.
8. **maxDepth=3** — дефолт (иначе агент вернёт 200 узлов), но **мягкий/переопределяемый** (чтобы не
   предать «богатые углы обзора»). Фильтры сейчас = **глубина + фокус-по-тегу**; абстракция/детализация — позже.

## Дыра каскада (из №1) — решена
Каскад направления/фасета НЕ материализовать в файлах (тухнет). Считать обходом по рёбрам
(`links.rel='tag'`/'in-direction' к group-узлу). До индекса — в памяти; «tags=рёбра к group» закрывает
дыру без спец-механизма (Reframer; выразимо через существующее `links`).

## НЕРАЗРЕШЁННЫЕ РАЗВИЛКИ → ≤3 ВОПРОСА ВЛАДЕЛЬЦУ
1. **Что строить ПЕРВЫМ (реальный спор):** твой ежедневный запрос «что застряло / что важно в
   направлении X» (User-Advocate: вызывается каждое утро) ИЛИ «контекст-конверт» агента
   (Reframer: горячий путь — агент читает контекст перед каждым ходом)? *(Оба дёшевы в памяти <300
   узлов; вопрос — какой UX первым.)*
2. **Важность:** ок ли модель «ручной слайдер 1-5 при создании + наследуется от родителя +
   авто-сигнал "открыто N раз" (показывается, но сам не меняет важность)»? Центральность/авто-decay
   совет отверг для разреженного графа. *(Совет рекомендует.)*
3. **Usage-gate (честная проверка, Skeptic):** ты реально будешь СВЯЗЫВАТЬ ячейки между собой
   регулярно, а не только сваливать заметки? Вся ценность графа держится на этом — если связей мало,
   делаем проще.

## Сильные/важные моменты
- Менять код почти не нужно: `parentId`+`links` уже несут v1. Первый шаг — две in-memory утилиты обхода.
- Индекс/SQLite — отложен за порог (300 узлов + usage-gate), обратимо.
- Важность: ручная база + touch-сигнал; центральность отвергнута (мусор на малом графе).
