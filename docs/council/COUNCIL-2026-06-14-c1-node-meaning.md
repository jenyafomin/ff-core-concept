## КОНСЕНСУС
1. **НОЛЬ новых kind. `kind` остаётся тонким фильтром.** «Сообщение-агрегатор» = `kind='message'`
   (уже есть) + `body` (отчёт) + `links{rel:'attaches'/'documents'}` на файлы/коммиты. Работает
   сегодня, ~нулевое изменение схемы. Gate: >5 новых kind за 3 мес = тревога.
2. **Уровни = вычисляемый zoom по умолчанию; авторские — редкий опциональный КЭШ, не обязаловка.**
   L1=title (обязателен), L2/L3 вычисляет `renderLevel` из body (уже в коде), ИИ может сгенерить
   подробнее по запросу. Авторские слои хранятся ТОЛЬКО если их реально написали — как pull-кэш
   (`meta.summaries`) с детекцией устаревания (provenance/`rel='derived-from'`), НЕ фиксированные
   слоты l1/l2/l3. Так покрыты оба случая (вычисляемый дефолт + авторское исключение, устаревание видно).
3. **Фасеты СТАРТУЮТ как namespaced-теги/значения-рёбер (дёшево, обратимо) с порогом промоушена в
   узлы-категории.** Три модели фасета сведены в ОДНУ ось зрелости (Reframer, принято Architect):
   `rel='facet'` — всегда РЕБРО; цель ребра — строка (тег, стадия-0) ИЛИ узел (материализован, когда
   у фасета появилось ≥1 своё свойство/ребёнок/нужен запрос). Промоушен тег→узел без потери истории,
   по явному порогу (~≥50 узлов с одним facet-префиксом ИЛИ запрос «дай все узлы под фасетом X»).
   «Дёшево сейчас + ∞-глубина потом» = ОДИН путь, не выбор.
4. **Валидация: мягкая схема + жёсткие инварианты только (id+kind+title). НЕ Zod-реестр-по-kind сейчас**
   (преждевременная governance/онтология; отложить до ≥2 kind с уникальными обязательными полями).
   `meta` — escape-hatch, но нужна заметка-конвенция по kind, чтобы не стал помойкой.
5. **Навигация принадлежит АГЕНТУ, не ручному обходу дерева.** ∞-глубина и «сети чего угодно»
   даёт агент, обходя граф и показывая «срез» (умный домашний экран: pinned+recent+suggested),
   прогрессивное раскрытие через диалог. Человек НЕ поддерживает глубокое дерево руками. Так
   снимается конфликт «∞ глубина vs человек теряется» — меняется субъект навигации.

## НЕРАЗРЕШЁННЫЕ РАЗВИЛКИ / находки
- **A. Дыра каскада тегов (Skeptic, код):** теги НЕ каскадируют по `parentId`; `context.ts`
  каскадирует `context`, но НЕ `tags`. → «все узлы сети Финансы» по 3+ уровням на плоских тегах
  НЕ работает без каскада тегов. Либо добавить каскад тегов по parentId, либо фасеты — это рёбра/узлы
  (обход графа), а не плоские теги. **Это реальный механизм «сетей чего угодно».**
- **B. Поиск должен выйти ВМЕСТЕ с захватом (User-Advocate, диссент):** «сообщение+body+links
  достаточно как MVP» — неверно; retrieval-UX обязан выйти одновременно с capture, иначе продукт
  учит «сбросил и забыл» = тот самый failure mode. Первый срез = схема + путь поиска (агентский).
- **C. Открытая дыра:** механизм КОРРЕКЦИИ — когда структура агента неверна и человек правит, кто
  владеет сигналом коррекции и как он обновляет модель без нового ритуала обслуживания. → отдельно.
- **Важность:** Architect хотел 2 оси (операционная + приоритет), User-Advocate жёстко против (две
  калибровки = тихий заброс). **Лин: ОДНА ось сейчас**, pinned-якорь = единственный обязательный жест.

## Сильные/важные моменты (зафиксировать)
- Многое уже в коде: `message` kind, вычисляемые уровни, `links{rel}`, `importance`, `meta`. Менять
  МИНИМАЛЬНО, не переписывать.
- Минимальный дифф (Pragmatist), если что-то добавлять: в `schema.ts` — `meta.facets: string[]?`
  (namespaced) + `meta.summaries: record?` (авторские уровни-если-есть). Ноль новых kind, ноль group-узлов.
- Фасет = ребро (инвариант); цель = строка→узел по порогу (обратимо).

   умолчанию + авторское как редкое исключение.)*

   *(Это определяет: каскад тегов vs фасеты-как-рёбра-на-узлы — реальный механизм «сетей».)*
3. **Важность:** одна ось (что закреплено/важно — pinned) или две (операционная + твой приоритет)?
   *(Совет: одна сейчас.)*
