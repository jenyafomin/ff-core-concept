# docs/00-states — состояния (R2, ратифицировано 2026-07-17)

> Это каркас. На момент создания (2026-07-17) внутри нет ни одного реального `state` — папка заведена
> как ДОМ для конвенции R2, чтобы новые состояния сразу знали, куда ложиться. Полное правило — в патче
> `docs/01-organization/doc-discipline/PATCH-2026-07-17-conventions.md` (раздел R2), который ещё не внесён
> в сам скилл `doc-discipline` (заблокировано разрешениями сессии — см. флаг в патче).

## Правило (R2)

- **Единственный дом состояний** — эта папка, на КОРНЕ дерева документации. Состояния НЕ заводятся внутри
  тем/веток проекта (`02-project/...`) — только здесь.
- **Плоская схема:** `00-states/NN-<slug>/` (порядковый номер + короткое имя). Без вложенности по темам.
- **Тема — это ПОЛЕ, не папка.** Состояние, относящееся к теме X, не кладётся в подпапку темы X — тема
  указывается полем `theme:` внутри `state.md`.
- **Внутри каждого `NN-<slug>/`:**
  - `state.md` — фронтматтер `id · theme · status · opened/updated · agents[] · plans[]` + тело (что это
    за состояние, кто/что в нём).
  - `log.md` — append-only журнал: вход/выход агента с таймстампом (фильтруемый срез «кто/что/когда»).
- **Многопоточность:** новая параллельная работа → заводи НОВЫЙ `state` сразу, не переиспользуй старый.
- **Никогда не удалять.** Закрытое состояние архивируется СТАТУСОМ (`status: archived` в `state.md`), файл
  и папка остаются на месте. Рост дерева со временем компенсируется дисциплиной архивации/сжатия, а не
  удалением.
- **Связь с планами:** ребро `plan --targets--> state` — план целится в конкретное состояние; один `state`
  может держать несколько планов одновременно (см. `registry.seed.json`, тип `plan`/`state`).

## Что здесь пока НЕТ

- Ни одного реального `NN-<slug>/` — заводится по факту первой параллельной ветки работы, требующей
  собственного состояния.
- Механизма компрессии/архивации (риск роста без сжатия отмечен в RECOMMENDATIONS.md, R2) — решается
  отдельно, когда накопится достаточно состояний, чтобы увидеть паттерн.
