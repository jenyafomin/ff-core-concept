# Фаза 3 — Развёртывание на проект/группу

> Применяем на реальном проекте портфеля. «Развернуть» = навести движок на партицию проекта; agent-manager
> сам заводит нужные типы/связи; доступ — по capability.

## 🎯 Цель
Один из 5 проектов работает на движке: разные люди, разные доступы, аналитика — вживую.

## 📋 Что происходит
1. **Партиция на проект** — узлы проекта как отдельный корпус в общей базе.
2. **Capability-гранты** — субъект × проект/space × роль (один человек = разные доступы в разных проектах, один id).
3. **agent-manager создаёт узлы/рёбра** проекта сам (типы, связи, нужные для этого проекта).
4. **Фронт** — резерв/заглушка: отдельный, НЕ связан с памятью (память работает и без него); подключаем позже.

## 🚪 Вход
Фаза 2: память как корпус на движке.

## ✅ Готовность (DoD)
- [ ] Один из 5 проектов портфеля работает на движке.
- [ ] Разные люди — разные доступы, видно ЯВНО (принцип-зеркало соблюдён).
- [ ] «Всё взаимодействие через агента» выполняется; лимиты/возможности агента видны как данные в самой системе.
- [ ] Из бэкенда реально вытягиваем информацию (аналитику) по проекту.

## 🔑 Ключевые решения к доработке
- Выбор **пилотного проекта** из портфеля (7days · cardex · dwizh · ga-rentacar · video-social-music).
- Реализация **принципа-зеркала**: какие доп. узлы/линзы «система о себе» нужны, чтобы лимиты были видны.
- Стратегия фронта (когда и какой).

## 🧪 Как проверяем
Пилот вживую + проверка «зеркала»: всё, что агент может/не может, выражено узлами (`view:system-map` показывает).

## ⚠️ Гейт/риск
Принцип-зеркало может потребовать достроить «дополнительные вещи» (узлы/линзы самоописания) — заложено, не сюрприз.
