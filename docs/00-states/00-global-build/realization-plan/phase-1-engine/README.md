# Фаза 1 — Тонкий движок

> Первый **рабочий бэкенд**, из которого уже вытягиваем информацию линзами. Дорастить доказанный seed
> `run-view.mjs` до сервиса. **Один движок на все модули** (память + agent-manager) — им он видит два
> разных корпуса узлов, а не два движка.
>
> **Доработано 2026-07-25** советом из 3 линз (system-architect · analyst · critic). Разбор:
> `docs/_log/2026-07-25-phase-1-design/SYNTHESIS-phase-1-engine.md`.

## 🎯 Цель
Движок, который держит граф (узлы+рёбра), исполняет `view`-запросы и отдаёт результат/аналитику —
и делает это через **один PEP разрешения** (`resolve()` по LSR), так что права видимости = тот же запрос.

## 🧭 Несущий паттерн — Hexagonal (Ports & Adapters) + CQRS-lite
Прямая проекция северной звезды «движок ФИКСИРОВАН, модули = ДАННЫЕ» в структуру кода:

- **Ядро-домен (фиксированный движок)** = чистые функции над `Node[]`: `validate · index · compile · resolve`.
  Детерминированы, без I/O, не знают ни про диск, ни про PG, ни про сеть.
- **Порты** = `StorePort` (корпус) · `SurfacePort` (CLI/HTTP).
- **Адаптеры** = `store-md` + `store-pg` (хранилище) · `cli` + `http` (интерфейс).
- **CQRS-lite** отвечает на развилку хранилища: **md+journal = write-model (истина), PostgreSQL =
  read-model (производная проекция, одноразово rebuildable).**

Смысл: brain и agent-manager для ядра — **два корпуса на одном порту**, а не два движка. Смена стораджа
(in-memory → PG) для Q-7-прогона НЕ трогает ядро — в этом весь выигрыш.

## 🧱 Карта модулей (репо `TOOLS/ff-engine`)
```
ff-engine/
├─ src/
│  ├─ core/                    ← ФИКСИРОВАННЫЙ движок (чистый, импортируемый, без I/O)
│  │  ├─ loader.ts             from StorePort → {nodes, byId}
│  │  ├─ envelope-validator.ts конверт + рёбра-пары + meta/example (R-3) → Problem[]
│  │  ├─ edge-index.ts         инверсный индекс (R-2) → inverseSources()
│  │  ├─ view-compiler.ts      ОДИН generic 4 стадии: from·traverse·filter·shape (R-1)
│  │  ├─ resolve.ts            ★ PEP по LSR: clamp(fold(combinator,stack)) (ADR-0004)
│  │  └─ types.ts              Node, Edge, Decision, SubjectRef, GraphContext
│  ├─ ports/       store.port.ts · surface.port.ts
│  ├─ adapters/    store-md.ts (истина+journal WAL) · store-pg.ts (read-model) · store-memory.ts (seed/тесты)
│  ├─ surface/     cli.ts ★Фаза 1 (exit-code ТОЛЬКО здесь) · http.ts (Фаза 1.5, гейт auth)
│  └─ policy/      access-priority.ts (узел policy:access-priority) · manage-gate.ts (D4 core:manage-*)
├─ bench/q7-scale.ts           ★ killer-прогон 10³–10⁴ (DoD-гейт)
├─ test/invariants.test.ts     конверт/рёбра/meta/PEP (NAIVE-vs-FIXED) — В CI
└─ corpus/                     md+frontmatter (истина) + _generated/ (gitignored индекс)
```
> **F1-фикс = каркас-условие** (ADR-0004 Consequences #3): каждый `core/*` — `export`, НИКАКОГО top-level
> `process.exit` (exit живёт только в `surface/cli`). Без этого движок не переиспользуем и Q-7-bench не
> сможет звать резолвер, а пере-выведет его заново.

## 📋 Что происходит
1. **Репо** `TOOLS/ff-engine` (общий brain+agents; НЕ отдельный «brain-engine»).
2. **F1-рефактор seed → импортируемое ядро** (порезать монолит `run-view.mjs` по стадиям; портировать
   ТАКЖЕ `run-view-depth2.mjs` — там доказанные loop-guard и subtree-delta, их нельзя потерять).
3. **Единый `resolve()` PEP** (см. §🔑 D-4) — зовут оба пути: view-filter (видимость) и write-path (запись).
4. **Компилятор `view-def`** — 4 стадии `from·traverse·filter·shape` (R-1), три доказанные линзы = три вызова.
5. **Хранилище** md+journal=истина + PostgreSQL=read-model (см. §🔑 D-1).
6. **Инварианты** — валидатор конверта/рёбер-пар/meta-example, **fail-closed по ПОВЕДЕНИЮ**, не только по
   exit-коду (см. риск R-5); comb-coverage + мета-гейт — **в CI**.
7. **M-G1 Temporal-lite** (journal `acts` append-only + rebuild-from-journal) + **M-G3** (реестр типов,
   view-компилятор) — в урезанном MVP-объёме (см. §🔑 D-5).

## 🔑 Развилки — РЕШЕНО / К РАТИФИКАЦИИ
> Три из этих решений — **storage/архитектура**, по конституции требуют **ADR до кода**, а не фиксации
> «по факту». Помечены 🏛️ ADR-кандидат.

- **D-1 · Истина = граф; хранение = политика на тип 🏛️ ADR-кандидат — РАМКА РАТИФИЦИРОВАНА владельцем
  (2026-07-25).** Развилка «файл ПРОТИВ базы» была ложной — смешивала два уровня:
  - **Истина ЛОГИЧЕСКАЯ = сам граф** (узлы+рёбра, модель). Она одна, всегда.
  - **Где узел ФИЗИЧЕСКИ лежит = НАСТРОЙКА на тип** (`policy`-узел, данные — ровно как существующий
    `knowledge.mode = embed|ref`), а не глобальный закон.
  Следствия: **PostgreSQL — главная по умолчанию** (клиенты, клиенты клиентов, снапшоты, память агента,
  трейсы — их в файлы не сохраняем); **file-first — опт-ин на «человеческие» типы** (доки, конфиги, промпты —
  то, что владелец правит руками), не везде. **Файл = бандл узлов** (много единиц в одном файле — как
  сегодняшний `nodes.json` = 1 файл на 65 узлов; «1 файл = 1 узел» НЕ закон). **DB→file = экспорт по
  требованию** (снять срез графа в файл для git/портативности), а не постоянная двусторонняя синхронизация.
  `doc-tree` закон №1 «файлы=истина» относится к ДЕРЕВУ ДОКУМЕНТОВ проекта, не к рабочим данным движка —
  конфликта нет. **Правило-замок:** в PG пишет ТОЛЬКО движок (прямой SQL в обход `resolve()` минует
  capability-слой, риск R-2). Формализовать отдельным **ADR** (persistence-as-policy, storage-решение).
- **D-2 · Кто пишет журнал первым — РЕШАЕТСЯ per-поток (следствие D-1):** для **DB-first типов** (по
  умолчанию) поток — `engine.write()` → journal → PG (API-first). Для **file-first типов** (опт-ин) журнал
  строится диффом ФС (git-hook/fs-watcher) — движок «первый читатель», не первый писатель. Развилка больше
  не глобальная; закрывается той же политикой-на-тип. Детали потоков — в ADR из D-1.
- **D-3 · Интерфейс — РЕШЕНО: CLI первым, HTTP отложен за гейт.** Тончайшая поверхность над ядром, seed уже
  CLI, Q-7-bench — скрипт. **HTTP НЕ открывать, пока нет модели аутентификации viewer** — иначе дыра
  S1-класса (риск R-1). Команды: `validate · view · resolve · load · rebuild[--from journal|files] · write ·
  bench`. Команда `ff-engine resolve <key> --viewer <s> --node <id>` = прямое исполнение принципа-зеркала
  (возможности видны как данные, по запросу).
- **D-4 · Единый `resolve()` PEP — РЕШЕНО.** Одна функция-choke-point на ОБА пути (видимость + запись):
  `resolve(key,viewer,node) = CLAMP_authority( OVERRIDE_reach( orderedStack ) )`. `combinator` берётся из
  ДАННЫХ (узел `policy:access-priority`, Appendix A ADR-0004); реализация fold = Strategy (движок, R3).
  `deny`-пол / Конституция-потолок = зажимы ПОСЛЕ свёртки (D3 ADR-0004), НЕ слои. Мета-cap-гейт (D4:
  `core:manage-*`) — ПЕРЕД resolve на write-path. **Кеш грантов по viewer обязателен** (риск R-3).
- **D-5 · Границы M-G1/M-G3 — РЕШЕНО (урезано):**
  - *M-G1 в MVP:* журнал `acts` append-only + `rebuild --from journal|files`. **Откладываем:**
    битемпоральность, as-of/time-travel, компакция/snapshot журнала, retention.
  - *M-G3 в MVP:* реестр `meta:type`/`meta:pred` грузится и enforced валидатором (уже в seed); view-компилятор
    исполняет 4 стадии для доказанных линз. **Откладываем:** динамическую регистрацию новых folds (код+ADR),
    vendor-бандлы/маркетплейс, authority-градацию, N-уровневую reach-вставку.

## ✅ Готовность (DoD)
- [ ] Движок грузит корпус узлов, исполняет линзы, отдаёт результат по **CLI** (HTTP — за гейтом D-3).
- [ ] **Прогон масштаба Q-7** (10³–10⁴ узлов) на **намеренно адверсариальном** корпусе (hub-узлы, глубокие
      цепочки, near-cycles — не «просто побольше») вернул реальные числа. **Числовой порог:** PASS ≤ **200 мс**
      P95 / FAIL > **1000 мс** P95 (`cost-tree` на типичное поддерево + `visible-to` с capability-гейтом при
      N=10⁴, ПОСЛЕ PG-индексов и кеша грантов). Между — устранять конкретное узкое место, партиция последней.
- [ ] Инварианты enforced **fail-closed по поведению** (refuse-before-compute), не только exit-код; comb-coverage
      + мета-гейт — **в CI** рядом с `concept-lint`.
- [ ] Те же линзы (`cost-tree`/`visible-to`/`actions-by-agent`) работают на большом реальном корпусе.
- [ ] `resolve()`/LSR **кеширует гранты по viewer** (иначе O(N·G) даст ложный вердикт Q-7).
- [ ] `cost-tree` защищён от бесконечности: **cycle-guard (visited-set) + `policy.max_delegation_depth`**,
      итеративный обход вместо рекурсии (loop-guard лупа НЕ защищает статический обход дерева).
- [ ] **Измеренный self** — движок сам пишет `snapshot --measures--> self` из живого замера (не reconstructed).
- [ ] seed перерос в сервис: портированы **оба** seed (`run-view` + `run-view-depth2`), не игрушка.

## 🧪 Как проверяем (метод Q-7)
1. **Генератор корпуса** сам проходит `validate()`; топология по реальным пропорциям seed (agent≈11%,
   branching 2–3, 1 snapshot/agent, ~5–8 action/agent, meta-слой КОНСТАНТЕН — не растёт с N); лес независимых
   `loop-run`, ПЛЮС отдельный патологический сценарий (линейная цепочка delegates-to глубиной >10⁴).
2. **Мерим:** время `validate()` (O(N+E)), построение индекса (O(E)), `cost-tree` (O поддерева),
   `visible-to` (O(N)), **`resolve()` внутри линз (O(N·G) — реальный кандидат в «тормоз»)**. PG-схема:
   `nodes(JSONB body, GIN)`, `edges PK(source,pred,target)+btree(target,pred)`, `acts(seq)`.
3. **Порог/гейт:** см. DoD. Если FAIL после индексов+кеша → партиции по проекту (Фаза 3), но **партиция =
   ещё один слой-данные в LSR-стеке, НЕ код-ветка** `if(project===X)` (иначе второй «deny-как-слой»).

## 🚫 НЕ-цели Фазы 1 (scope-guard — «тонкий» значит тонкий)
HTTP до модели auth · vendor/маркетплейс-загрузка модулей · authority-градация (`owner>member>guest`) ·
N-уровневая reach-вставка (F2, гейт Q-11) · авто-сужение делегирования (sub-grant) · тай-брейкер ничьей
равного ранга (корпус держим single-owner) · новые комбинаторы/folds (код+ADR) · as-of/temporal-запросы ·
view-над-view и материализация (DEC-11 — проследить, чтобы Q-7 не протащил PG materialized views в обход) ·
auth/мульти-аренда/партиции (Фаза 3, только по факту боли Q-7).

## ⚠️ «Не наступить» — топ-5 рисков (от критика, ранжировано)
1. **R-1 · HTTP без аутентификации viewer = дыра S1 на сети.** `resolve(key,viewer,node)` берёт viewer
   параметром; над HTTP клиент назовётся `user:jenya` → обнуляет доказанный 15/15 capability-слой. →
   строго CLI (доверенный оператор), HTTP — за отдельным гейтом auth-модели.
2. **R-2 · PG «производный» без запрета прямой записи.** Сырой SQL/debug в обход `resolve()` минует все
   capability-гейты (D4), проверенные только на in-memory. → замок «в PG пишет только движок» + staleness-маркер.
3. **R-3 · Ложный вердикт Q-7 из-за неоптимизированных грантов.** Без кеша грантов бенч покажет «БД тормозит»,
   хотя тормозит O(N·G) capability-гейт, а не объём. → индексировать гранты по viewer ДО прогона.
4. **R-4 · Q-7 на неврждебном синтетик-корпусе = ложная уверенность.** → адверсариальная топология, как
   capability killer был NAIVE-vs-FIXED, а не «побольше узлов».
5. **R-5 · Валидатор fail-closed только по exit-коду.** Seed вычисляет/печатает линзы над невалидными данными;
   в HTTP нет exit-кода. → явный refuse-before-compute (503/отказ) ДО вычисления линзы.

## 🔓 Заповеди расширяемости (чтобы «дополнялось», а не ломалось)
- **view-def нужен свой ranking contract** (аналог D1 для access): объявить, что в грамматике `from·traverse·
  filter·shape` — ЯКОРЬ (движок-фиксировано), а что — расширяемый enum. Иначе заморозка 4-стадийной формы как
  wire-контракта сделает будущее расширение breaking, а не аддитивным.
- **R1/R3-граница для view-исполнителя** (аналог D2): новая агрегация (`avg`/`count`/новый traverse) — это
  значение enum (данные, R1) или правка движка (R3)? Продекларировать ДО M-G3, иначе билдер тихо хардкодит.
- **Партиция — слой-данные, не код-ветка** (см. §🧪.3).
- **Additive-only защищает контракт резолвера, но не код клиентов:** view/кэш-ключи не должны неявно
  закладывать «между project и space никогда ничего не вставят» (стек PROVISIONAL pending Q-11).
