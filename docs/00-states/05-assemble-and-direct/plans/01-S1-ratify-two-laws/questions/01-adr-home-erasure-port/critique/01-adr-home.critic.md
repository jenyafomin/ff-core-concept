  файлов — это ДРАФТЫ в `docs/_log/2026-08-07-whole-picture-and-cycle/ratification/ADR-0010-*.draft.md` и

- `register:37` (`00-open-questions-register.open-question.md:37`) дословно форсирует «ADR-0008 thin

  `ADR-0008-log-and-graph-cqrs.md`), коллизия с Q-ERA-04 реальна.
- ADR-0009 сам себя объявляет `Extends: ADR-0007`, ссылается на ADR-0008 как на СОСЕДНЮЮ тему (не порт) —
  подтверждает разбор автора. **Пункт 1: подтверждаю.**

## (2) Скрытый owner-форк — НЕ подтверждён, но с оговоркой
- `shred = «unrecoverable», не «файл удалён»` — НЕ изобретение этой ноды. Дословно уже стоит в approved-статусном
  ADR-0009 (`ADR-0009:240-241`, секция «Known code follow-ups»), написанном/ратифицированном раньше (голос
  «строй» 2026-08-07, Decisions ①②③ approved). Нода лишь ЦИТИРУЕТ, не решает заново. Ценностный выбор
  («стирание = необратимо, не мягкое скрытие») — это уже сделанный владельцем выбор внутри ADR-0007/0009
  (Ц-7 vs Ц-3 расщепление), не новый форк здесь. **Пункт 2: подтверждаю — owner-форк не протащен.**
- Оговорка (NOTED, не блокер): статус-шапка ADR-0009 явно маркирует approved только Decisions ①②③ и явно
  открытым — секцию Pending owner (R3/R4/R5, carve-out I-4). Секция «Known code follow-ups» (где живёт
  «unrecoverable») НЕ упомянута в статус-шапке вообще — её ратификационный статус формально не проговорён.
  Это дыра в самом ADR-0009, не в Q-OQ-D — но Q-OQ-D наследует эту дыру молча, а не флагует.

## КРИТИЧЕСКАЯ находка (не входила в 3 пункта задания, но убивает «уверенность: высокая»)

**Критерий 5 разбора («честный номер — сердце переигровки») сам сделан НЕЧЕСТНО в том же классе ошибки, что
критикует Q-ERA-04.** Автор сверился только с `docs/architecture/ADR/` (0004–0009) и с
`_log/2026-08-07-.../ratification/` (0010, 0011 drafts) — но НЕ сверился с `docs/00-states/STATE.md` (канонический
живой указатель, "единственная точка входа при старте новой сессии", status: active, дата 2026-08-05):

- `STATE.md:169` — «**T1 · единица памяти** ... → будущий **ADR-0012**» (канонизация EnvelopeNode/FFNode,
  названо «Корневая развилка / блокер низового»).
- `STATE.md:173` — есть ИСТОРИЯ именно такой коллизии: «Коллизия ADR-номеров исправлена (память=**0012**, не 0009)»
  — номер 0012 уже был предметом спора и сознательно закреплён за темой памяти-узла.
- Независимо подтверждено в живом (draft, 2026-07-30) спеке ga-rentacar:
  `docs/03-projects/ga-rentacar/specs/05-m3-topic-agent-contract.spec.md:205` — «P3 · node-model ADR ...
  («ADR-0012» не существует)» — то есть тема ждёт номера 0012, ещё не оформлена файлом, но зарезервирована.
- `T1-memory-unit.ADR-draft.md` (`_log/2026-07-26-.../post-M0-directions/`) всё ещё `Status: draft` — резервация
  НЕ снята, не superseded, не отозвана нигде найденной.

Т.е. **0012 УЖЕ негласно зарезервирован под другую, более фундаментальную тему** (канонический node-model ADR,
явно названную «корневой развилкой»/блокером). Рекомендация Q-OQ-D присвоить 0012 порту payload-стирания —
это ВТОРАЯ коллизия по имени номера, того же типа, что исходная ошибка Q-ERA-04→0008, просто на другом
уровне реестра (STATE.md не входит в перечень источников `sources:` ноды — вот почему пропущено).

Это НЕ owner-форк (не ценностный выбор), это **фактическая проверка не выполнена полностью** — прямое
нарушение собственного task-спека п.2 («честно назначить номер по реестру занятых+зарезервированных»).
Нода уже страхуется фразой «подтвердить при кристаллизации», так что риск невысок (обратимо, ADR ещё не
написан) — но заявленная «уверенность: высокая» в синтезе неточна применительно к номеру: по факту
номер скорее **0013**, либо нужен явный шаг «сверить со STATE.md/T1 прежде чем фиксировать 0012».
