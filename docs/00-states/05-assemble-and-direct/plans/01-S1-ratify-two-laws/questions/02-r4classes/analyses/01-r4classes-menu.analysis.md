# R4 referent-class menu (business-analyst lens)

> Format per `D4-decision-lens-briefs.analysis.md`: frame + trade-offs, no "should." Options A/B/C are the
> ones already named in the R4 brief (`D4-decision-lens-briefs.analysis.md:99-109`): **A** = no regime-B
> classes, ship as-is/fail-open · **B** = name classes now, admission excludes them · **C** = fail-closed
> default (unclassified referents blocked until explicitly cleared).

## 1. Несовершеннолетние (Minors)

- **Определение:** референт, чей возраст ниже юридического порога дееспособности юрисдикции (в контексте
  Dubai-рынка — местные пороги на аренду/договор варьируются; порог здесь НЕ юридически валидирован, это
  флаг классификации, не окончательное правовое определение).
- **Ценностный резон:** Ц-7 Согласие (`V7-soglasie.md:5` — «единица знает, ЧЬЯ она»/кому показать)
  ПРЕДПОЛАГАЕТ дееспособность давать согласие; несовершеннолетний структурно не может дать то согласие,
  на котором admission-gate уже стоит (`05-revocation-erasure/README.md:27-34`, FQ7 — право референта).
  Вторично — Ц-5 Суверенность (риск экспозиции асимметричен: данные ребёнка требуют опекунского контура,
  которого в системе сейчас нет).
- **Реальный пример / заземление:** `packages/ingest-rentacar/src/core/reduce.ts:77-95` — реальный reducer
  берёт `name`/`phone`/`Recent Note` в PayloadStore, но **НЕ несёт поля возраста/даты рождения вообще**.
  Значит система СЕГОДНЯ структурно не может отличить несовершеннолетнего от взрослого при admission —
  это не оценочный риск, а факт отсутствия сигнала в текущей форме данных.
- **A/B/C-проекция:**
  - **A** — минор не отличается от прочих; PII идёт в payload-store как обычно (сегодняшнее поведение,
    т.к. сигнала нет всё равно).
  - **B** — admission исключает записи, классифицированные как «минор» (но классификатору СЕЙЧАС нечем
    сработать — потребует либо нового поля в reducer, либо явного «unknown → regime-B» для всех,
    т.к. возраст не наблюдаем сегодня — см. §5 паттерн).
  - **C** — fail-closed по умолчанию означало бы: КАЖДАЯ запись без явного «подтверждён совершеннолетний»
    флага блокируется — при отсутствии поля возраста это практически ВСЕ записи ga-rentacar сегодня.
  - **Цена A (симметрично к цене B/C выше):** если запись реального несовершеннолетнего пройдёт admission
    как обычная (сегодняшнее де-факто поведение), append-only ФАКТ её существования зафиксирован навсегда —
    ретрофит постфактум невозможен (`two-laws.invariant-candidate.md:77-86`). A не «безопасный по
    умолчанию» вариант просто потому, что он ничего не блокирует — его цена переносится на будущее вскрытие
    ошибки, а не устраняется.
- **Обратимость/риск:** ФАКТ admission (что заказ существовал) необратим постфактум (append-only). Но
  СОДЕРЖИМОЕ (name/phone в payload-store) технически стираемо через существующий hard-erase примитив
  (`05-revocation-erasure/README.md:29-33`) — то есть риск здесь двухслойный: неустранимый факт-риск против
  устранимый контент-риск. Это разводит «retrofit-невозможно» по слоям, не по классу целиком — стоит
  явно назвать владельцу, т.к. брифы формулируют риск как единый блок (см. `question.md` §«Что не хватает» п.1).

## 2. Данные здоровья (Health data)

- **Определение:** любое поле/заметка, раскрывающее медицинское состояние, инвалидность, медицинский повод
  для льготы/исключения по договору.
- **Ценностный резон:** особая категория данных в большинстве privacy-режимов (повышенный порог согласия);
  Ц-7 Согласие + Ц-5 Суверенность (раскрытие здоровья — асимметрично высокий персональный риск относительно
  обычной аренды авто).
- **Реальный пример / заземление:** `Recent Note` — свободнотекстовое поле (`reduce.ts:77`,
  `02-ingest-acts.spec.md:29`), правдоподобный носитель фраз вроде «клиенту нужна машина с ручным
  управлением»/«мед.освобождение от депозита». **Ни разу не подтверждено на живых данных в этом
  разборе** (peek на полный экспорт не делался в рамках этой задачи) — пример правдоподобен по форме поля,
  не по наблюдению.
- **A/B/C-проекция:**
  - **A** — заметки идут как есть, недифференцированно (сегодняшнее поведение).
  - **B** — классифицировать «health-bearing note» отдельно, требовать особого режима/отказа при admission.
    **Инженерная оговорка:** свободный текст — классификатор на входе НЕ надёжен (ключевые слова легко
    пропустить/ложно сработать) — это НЕ вопрос ценности, а вопрос осуществимости самого B-варианта для
    этого конкретного класса.
  - **C** — fail-closed по умолчанию для любой заметки, не прошедшей проверку «не health» — вероятно
    блокирует почти ВСЕ заметки (over-block), т.к. классификатор ненадёжен в обе стороны.
  - **Цена A:** health-заметка, пропущенная в канон как обычная, — необратимый факт обработки специальной
    категории данных без повышенного согласия; обнаружится (жалоба/аудит) — контент стираем, факт-обработки
    уже свершился и зафиксирован append-only.
- **Обратимость/риск:** тот же двухслойный разрез, что у minors (факт vs контент). Дополнительно: если
  классификатор пропустит health-упоминание (false negative неизбежен на свободном тексте), risk остаётся
  даже при выбранном B/C — это НЕ решается выбором default, только полнотой классификатора.

## 3. Судебные постановления (Court orders / legal holds)

- **Определение:** запись, ссылающаяся на юридическое разбирательство, привязанное к референту (арест
  имущества по решению суда, спор об опеке, охранный ордер).
- **Ценностный резон:** Ц-3 Доверие (провенанс записи становится юридически значим — запись может подлежать
  раскрытию по запросу суда ИЛИ, наоборот, быть под печатью) + внешнее правовое обязательство вне контроля
  движка.
- **Реальный пример / заземление:** **0 наблюдаемых случаев** в текущих ga-rentacar фикстурах/спеках —
  ни одно поле reducer'а (`reduce.ts`) не несёт судебный контекст. Класс назван в брифах
  (`D4-decision-lens-briefs.analysis.md:86`) как типовой пример практики, не как найденный в данных.
  Релевантность для платформы шире одного ga-rentacar-ingest: FF агрегирует «всю жизнь человека»
  (проектный CLAUDE.md, «Что это»), и юридические кейсы (опека, ограничения) — правдоподобный будущий узел
  вне текущего домена.
- **A/B/C-проекция:** аналогично прочим (A=нет различия · B=явный provenance-тег до admission ·
  C=fail-closed на ключевые слова legal/court). Наименее срочный из пяти классов для ЭТОГО ingest (0
  вхождений сейчас), но название в меню — задел на будущие модули платформы, не для текущего M1.
  **Цена A:** если такая запись всё же появится (не наблюдалась, но не исключена) и пройдёт как обычная,
  факт её обработки/хранения зафиксирован необратимо ДО того, как выяснится, что запись подлежала печати/
  особому режиму раскрытия — низкая срочность СЕГОДНЯ не означает нулевую цену при первом реальном случае.
- **Обратимость/риск:** тот же двухслойный разрез. Ниже срочность на практике (не тикает для ga-rentacar
  M1), но включён по полноте меню (класс явно назван в брифах/OWNER-QUEUE).

## 4. No-trace юрисдикции / защита местоположения (No-trace referents)

- **Определение:** референт, для которого даже ТОПОЛОГИЧЕСКИЙ факт существования связи (не только
  содержимое) не должен быть допустим или должен допускаться только с обфускацией рёбер (напр. лицо под
  защитой, переживший насилие в семье, чьё местоположение/связи нельзя восстановить по графу).
- **Ценностный резон:** Ц-5 Суверенность + Ц-6 Реляционность в прямом напряжении — рёбра «резать нельзя»
  по дизайну ADR-0009, но именно этот класс просит ровно такого разреза.
- **Реальный пример / заземление:** **0 наблюдаемых случаев** в ga-rentacar (розничные клиенты
  автопроката) — класс релевантен по конструкции платформы (FF — агрегатор жизни, не только rentacar),
  не по наблюдению в текущем домене.
- **⚠️ Прямая связь с R3 (отдельный owner-fork, ЕЩЁ не решён).** Этот класс — конкретная реализация
  вопроса R3 («считают ли юрисдикции топологический остаток identifying» —
  `D4-decision-lens-briefs.analysis.md:56-82`, `ADR-0007:343`). Если владелец включает этот класс в R4-меню
  (B), он фактически подтягивает R3 вперёд — R3's вариант A («топология identifying, требует
  edge-обфускации») сам помечен как «reopens a genuinely unsolved design problem» (`D4-briefs:67`, рёбра
  резать нельзя по Ц-6). **Это НЕ решается здесь** — только называется зависимость, чтобы владелец видел
  цену включения этого конкретного класса выше, чем у остальных четырёх.
- **A/B/C-проекция:** A/C проецируются как у прочих классов; **B для ЭТОГО класса требует механизма
  (edge-обфускация), которого сегодня НЕТ в дизайне** — включение класса без R3-ответа даёт «названо, но
  не исполнимо» состояние.
  **Цена A — максимальная из всей менюшки:** для no-trace referents САМ факт связи (не только контент)
  и есть риск; A допускает эту связь в append-only граф без ограничений, и, в отличие от прочих классов,
  здесь «стереть контент позже» НЕ снимает риск (топология уже видна, ADR-0009 рёбра резать не позволяет).
- **Обратимость/риск:** самый высокий из пяти — для этого класса «факт vs контент» разрез НЕ спасает
  (сам факт связи — это и есть риск, не только содержимое).

## 5. VIP / защищённые лица (Protected/high-profile persons)

- **Определение:** референт, чья САМА принадлежность к канону чувствительна (публичная фигура, руководитель
  компании) — риск не в содержимом записи, а в факте её существования/доступности.
- **Ценностный резон:** Ц-5 Суверенность (асимметричный риск экспозиции — публичная фигура несёт
  непропорциональный ущерб от утечки обычной транзакции, которая для рядового клиента нейтральна).
- **Реальный пример / заземление:** упомянут только в `OWNER-QUEUE.md:54-58` и
  `QUEUE-questions.plan.md:99` (не в исходном D4-brief `:86` тексте) — то есть класс добавлен ПОЗЖЕ
  первичного R4-брифа, при компрессии в owner-очередь. Правдоподобен для Dubai luxury rental домена
  (реальный экспорт one-car), **не подтверждён на живых данных** в рамках этого разбора.
- **⚠️ Находка: VIP качественно отличается от классов 1-4.** Minors/health/court-orders/no-trace естественно
  проецируются на «admission-refuse» (не пускать факт в канон). VIP, по структуре риска, скорее просит
  **access-restriction ПОСЛЕ admission** (запись существует, но читается через более узкий PEP/PDP-контур),
  а не отказ на входе — блокировать рутинную транзакцию VIP-клиента при обычном ingest избыточно и
  операционно разрушительно (компания не может отказаться обслуживать клиента из-за его статуса).
- **A/B/C-проекция:** A/C формально применимы, но C (fail-closed) для этого класса плохо стыкуется с самим
  смыслом класса — блокировка VIP-транзакции создаёт ЕЁ СОБСТВЕННЫЙ операционный риск, отдельный от риска
  экспозиции. B здесь, вероятно, означает НЕ «отказ», а «маршрутизация на другой политики доступа» — другой
  тип действия admission-точки, не входящий в исходную A/B/C-рамку R4 буквально.
  **Цена A:** факт «этот VIP транзакцию совершил» зафиксирован необратимо в момент admission; последующее
  ограничение ДОСТУПА (B-переформулировка) не отменяет уже свершившийся факт-существования записи — цена A
  здесь репутационная/безопасностная, не только «содержимое утекло».
- **Обратимость/риск:** средний — контент стираем, факт неустраним, но операционная цена ошибочного
  fail-closed здесь выше, чем у остальных четырёх классов (реальный бизнес-конфликт, не только риск).

## 6. Биометрия (Biometric / KYC-scan data)

- **Определение:** биометрический идентификатор, используемый для верификации личности — скан/фото
  удостоверяющего документа, лицевой шаблон, отпечаток; отличается от текстового PII тем, что не подлежит
  «смене» при компрометации (нельзя выпустить новое лицо, как новый номер телефона).
- **Ценностный резон:** Ц-7 Согласие (биометрия — самая «телесная» форма согласия, в большинстве
  privacy-режимов требует ОТДЕЛЬНОГО явного согласия, не покрывается общим согласием на обработку) +
  Ц-3 Доверие (провенанс скана как юридического доказательства идентичности) + необратимость компрометации
  структурно выше, чем у имени/телефона.
- **Реальный пример / заземление:** KYC явно назван ЮРИДИЧЕСКИ ОБЯЗАТЕЛЬНЫМ для проката в Дубае
  (`analyses/09-qd1-qd2-data-findings.analysis.md:149` — «для проката в Дубае это юридически обязательный
  документ»), но живёт в ОТДЕЛЬНОЙ KYC/contracts-вкладке, которой НЕТ в текущем peek-наборе/фикстурах
  (`09-qd1-qd2-data-findings.analysis.md:148,156` — «нет ли отдельной KYC-вкладки вне набора из 8
  peek-листов» остаётся открытым). Также названо как метрика-цель, ещё не реализованная: «доля KYC до
  сделки» (`_inbox/HANDOFF-2026-08-04-wave-synthesis.md:25`). Итог: как и minors, класс сегодня структурно
  НЕ наблюдаем в ingest-коде (`reduce.ts` не несёт скан/фото-поле вообще) — но, в отличие от minors,
  бизнес-необходимость (юридическое требование KYC) уже названа, только не подключена.
- **A/B/C-проекция:** A — KYC-данные, когда подключатся, идут как обычный PII (payload-store,
  недифференцированно от name/phone); B — биометрия классифицируется отдельно, требует отдельного
  admission-режима (напр. отдельного согласия/consent-флага до записи); C — fail-closed для любого
  скан/фото-поля до явного KYC-протокола.
  **Цена A:** биометрия, admitted как обычный PII, необратимо фиксирует факт хранения данных, которые
  большинство режимов требуют защищать строже прочего PII — компрометация НЕ обратима заменой (в отличие
  от телефона/email), так что цена ошибки в сторону A здесь качественно выше, чем у текстового PII.
- **Обратимость/риск:** двухслойный разрез (факт/контент) применим, но КОМПРОМЕТАЦИЯ контента для
  биометрии ближе к необратимой даже НА СЛОЕ КОНТЕНТА (в отличие от смены телефона, лицо/отпечаток нельзя
  «перевыпустить») — единственный класс в этом меню, где стирание payload не полностью снимает риск
  прошлой экспозиции, если скан уже был скопирован/использован до стирания.

## 7. Умершие референты (Deceased referents)

- **Определение:** референт, факт смерти которого известен/зарегистрирован — вопрос, КТО обладает правом
  давать/отзывать согласие ЗА него после смерти (наследники? никто? право заморожено?).
- **Ценностный резон:** прямо бьёт в самоописание платформы FF — «агрегатор всей жизни человека»
  (проектный `CLAUDE.md`, «Что это») включает и конец жизни, не только активную фазу. Ц-7 Согласие
  предполагает живого субъекта, СПОСОБНОГО дать/отозвать согласие; смерть создаёт разрыв дееспособности —
  структурно СИММЕТРИЧНЫЙ minors (оба класса — «дееспособность отсутствует»), но с противоположной
  траекторией («уже не» vs «ещё не», и обратного пути для дееспособности не существует). Также касается
  Ц-4 Витальность (bitemporal «забыть≠удалить», `05-revocation-erasure/README.md:41-43`) — вопрос, кто
  ИСПОЛНЯЕТ право на забвение, когда сам референт уже не может его заявить.
- **Реальный пример / заземление:** **0 упоминаний где-либо в проекте** (проверено grep по «умерш/deceased/
  смерт» по всему `docs/` — ни одного вхождения в brain-ценностях, ADR, ga-rentacar). Это НЕ довод, что
  класс неважен — это находка: жизненный-цикл-до-конца-жизни тема платформой пока НЕ тронута нигде, при
  том что самоописание («вся жизнь человека») логически её включает. Для ga-rentacar (короткосрочная
  аренда) класс маловероятен как практический case; для brain/FF-ядра — открытый структурный пробел.
- **A/B/C-проекция:** A — нет отдельной обработки, референт продолжает существовать в каноне как обычно
  (текущее де-факто состояние — вопрос вообще не встаёт нигде в коде); B — admission/движок распознаёт
  «референт зарегистрирован умершим» как отдельный режим (кто теперь держит право согласия — наследник/
  никто/заморожено — САМ вопрос НЕ решается здесь, это отдельная ценностная развилка внутри B); C —
  fail-closed не имеет очевидного смысла для этого класса (референт уже существовал ДО смерти — блокировать
  нечего, вопрос не о допуске новой записи, а о судьбе существующей) — **этот класс, в отличие от
  остальных шести, слабо ложится на admission-time A/B/C рамку вообще**, т.к. смерть обычно наступает
  ПОСЛЕ, не ДО первой записи — второе структурное расхождение с рамкой R4 (первое — VIP, пункт 5).
  **Цена A:** без явного режима право согласия «умершего» референта остаётся неопределённым НАВСЕГДА
  (никто структурно не уполномочен ни продолжать, ни прекращать обработку) — это не риск экспозиции разово,
  а перманентный пробел управления согласием, копящийся с каждым новым умершим референтом.
- **Обратимость/риск:** отличается от прочих классов — риск не в МОМЕНТЕ admission (класс обычно
  постфактум состояния, не входного факта), а в ОТСУТСТВИИ механизма на будущее. Наименее «тикающий» из
  семи для ga-rentacar конкретно, но структурно первый класс в этом меню, где сама рамка R4 (admission-gate)
  может быть неверным местом решения — стоит явно передать эту оговорку владельцу, не решать здесь.

## §5. Названный (не рекомендованный) инженерный паттерн: fail-closed-до-классификации

ADR-0009 уже использует паттерн «unknown → консервативный default» для ДРУГОЙ оси (entropy-class witness
construction): «Unknown → трактуется как low-entropy (солёный, fail-safe)»
(`ADR-0009-erasure-witness-and-recursive-seam.md:220-222`). Это НАЗВАНО здесь как СИМВОЛИЧЕСКАЯ аналогия —
структурно похожий выбор («не знаешь класс → веди себя консервативно») уже принят проектом для другой
оси классификации. **Это НЕ довод в пользу выбора C (fail-closed) для R4** — паттерн лишь показывает, что
проект уже умеет жить с «unknown → conservative» без паралича (entropy-class использует его продуктивно).
Симметрия ограничена: entropy-class default НЕ блокирует ingest (соль — дешёвая операция), тогда как R4's
fail-closed БЛОКИРУЕТ ingest целиком до классификации — цена аналогичного паттерна здесь на порядок выше
(см. §1-2 — для minors/health классификатор сегодня либо отсутствует, либо ненадёжен, так что fail-closed
здесь может означать «блокировать почти весь текущий ingest», не частный случай).

## §6. Нейтральная сводка — если владелец выбирает B (стартовый набор)

| Класс | За включение | Против включения (цена) |
|---|---|---|
| Minors | Ц-7 требует дееспособности; отсутствие поля возраста — известный слепой пробел | Классификатор сегодня НЕ существует (нет поля) — включение без нового поля в reducer бессмысленно |
| Health | Особая категория данных, асимметричный риск | Свободный текст ненадёжно классифицируется; риск over/under-block одновременно |
| Court orders | Внешнее юридическое обязательство | 0 наблюдаемых случаев в ga-rentacar сейчас — не тикает для M1, задел на будущее |
| No-trace | Прямая защита самых уязвимых референтов | Требует edge-обфускации, которой нет — тянет за собой нерешённый R3 |
| VIP | Асимметричный репутационный/безопасностный риск | Структурно просит access-restriction, не admission-refuse — не ложится на A/B/C буквально |
| Биометрия/KYC | Юридически обязательна для Дубая; необратима при компрометации иначе, чем текстовый PII | Поле сегодня не подключено вообще (нет скан/фото-канала в ingest) — включение пока не на чем сработать |
| Умершие референты | Бьёт в самоописание «вся жизнь человека»; 0 механизма сегодня | Смерть обычно наступает ПОСЛЕ первой записи — слабо ложится на admission-time рамку вообще |

**Симметрично — цена варианта A (fail-open/ship-as-is) для каждого класса** (см. полный разбор в
соответствующем §1-7 выше, «Цена A»): необратимый append-only факт admission фиксируется НАВСЕГДА для
любого класса, даже если весь класс не назван; разница между классами — не «есть ли цена у A», а
НАСКОЛЬКО она серьёзна и на каком слое (факт vs контент vs, для no-trace, сам факт связи).

Это МЕНЮ, не решение. Владелец может: (а) отметить нужные классы как есть, (б) вычеркнуть/переформулировать
любой, (в) добавить класс, которого здесь нет, (г) явно отложить R4 целиком (S1 это допускает —
`OWNER-QUEUE.md:59`). Ни один пункт этой таблицы не выбран «за» владельца.
