# Карта целей и подход к БД v1 (BRAIN)

> Собрано оркестратором из плана (§1a,§3d–§3j, «Открытые вопросы») + HANDOFF.
> Цель документа: синхронизировать ЦЕЛИ с владельцем, ПОТОМ строить.

## Что уже готово / решено (опоры)
- **V3**: единая БД = один логический граф + рантаймы модулей + коннекторы.
- **ADR-0002 thin passport**: тонкий паспорт узла; дом + facet-рёбра (мультиродитель).
- **Движок = сервис** (один writer), **SQLite + транзакции** для структуры (де-факто подтверждено V3).
- **Аудит @ff/core**: ~15% переиспользуемо, skeleton ≈14–22 builder-дня, риск низкий.
- **Имя единицы = BRAIN** (решено владельцем).

## Дерево целей (~месяц)
**Ц-0 (верхняя):** запустить самонаполняемую единую БД (BRAIN) для документации и планирования ВСЕХ проектов, управляемую агентами.

- **A. Ядро БД v1 (walking skeleton)** ← фокус сейчас
  - тонкий паспорт · типы-как-узлы (адрес по ID) · категории-как-индекс
  - блочное хранение файлов · уровни описаний L1/L2/L3
  - инвариант «любой цикл имеет терминатор» · один writer/движок-сервис
  - корпус v1: какие docs инжестить (⚠️ уточнить — блокер)
- **B. Кросс-проектная синхронизация задач** ← ключевой вопрос владельца
  - один логический граф vs рантаймы per-project
  - централизованный движок-сервис, проекты подключаются (§1a, не копии)
  - стык с gateway-entities (agents/agent_bindings/topics — уже мультипроектные)
- **C. Планирование и задачи**
  - задачи · планы · инструкции/лупы (exit-условия) = типы узлов
  - глобальный план ⟂ проектные · наблюдаемость сессий/агентов (кто где, под каким контекстом)
- **D. Доступ и управление** — RBAC+ABAC+ReBAC (взять пакет CRM-Rent); клапан/default-deny модулей; права кнопками через TG; показ через линзу/фокус.
- **E. Расширяемость/плагины** — модульность = marketplace; плагин = система агентов в песочнице; версии/варианты.
- **F. Просмотр** — визуализация/агрегация графа (LIST+FOCUS, линзы, грани/многомерность).
- **G. Самоулучшение (петля P3)** — ИИ смотрит → улучшает → пишет → ставит задачи агентам.

**Для v1 минимум = A + минимальный C + модель B (решить на бумаге).** D/E/F/G — позже.

## Подход к v1 (планирование-first, расширяемость)
- Начинаем с ПЛАНИРОВАНИЯ структуры, не с массового инжеста.
- Ядро минимальное, но открытое: новые типы/контексты/связи добавляются по ходу (интуитивно),
  не ломая существующее — за счёт «тип = узел, адрес по ID» + facet-рёбер (ADR-0002).
- Наполняем на реальном корпусе (docs/) и правим модель на ходу.

## Кросс-проектная синхронизация — варианты (к решению)
1. **Один центральный движок-сервис (рекоменд.)** — БД живёт в BRAIN; проекты = рабочие директории, подключаются; синхронность автоматическая (источник один). Совпадает с §1a и с gateway (entities уже мультипроектные). Минус: BRAIN — единая точка.
2. Граф-per-project + агрегатор — независимость, но синхронизация дорогая, дубли, конфликты.
3. Гибрид — ядро глобально, «горячее» проектное локально с репликацией. Сложность выше, для v1 избыточно.

## Вопросы владельцу (синхронизация целей)
1. **Корпус v1:** что инжестим первым — только FF `docs/` или + dwizh/CRM? (блокер)
2. **Где живёт БД:** внутри `FF-Personal-Managment` или отдельная папка `BRAIN/`, к которой подключаются проекты?
3. **Порядок:** строим ядро A сразу на реальных данных — или сначала ратифицируем на бумаге (движок=сервис · stream-класс · pack-формат)?
4. **Кросс-проект:** согласен на вариант 1 (один центральный движок, проекты подключаются)?
5. **«Интуитивно»:** агенты могут заводить НОВЫЕ типы на лету — или тип создаёт только владелец/оркестратор?
6. **Критерий «v1 готова»:** назови 1 сценарий, который должен заработать (напр. «спросил у графа все задачи проекта X»).
7. **Где думаем:** строим в этой теме под оркестратором — или ты откроешь отдельную project-rooted сессию для архитектора (из-за падений в шлюзе)?
