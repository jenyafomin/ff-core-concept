# Память системы — формулировка (seed)

> Философия владельца: взять МИНИМУМ, расти по чуть-чуть; каждой новой сессии давать контекст;
> архитектор задаёт «правильные глаза» (как правильно фиксировать), чтобы память копилась структурно.

## Зачем (боль)
Каждый ход шлюза = свежий процесс: Fable/агент заново собирает контекст, знание не копится, решения
теряются в чате. Нужна память как СУБСТРАТ (не заметки): дешёвый контекст на входе + запись результатов обратно.

## Принцип (ложится на уже решённое)
- **Память = узлы в BRAIN**, не отдельное хранилище. Типы: `fact · decision · preference · status · session-log`.
- **Scope = principal × project × agent-role** (кто · где · какая роль). Основано на §3c (principal×project) и
  SYNTHESIS-2026-06-24 (user⟂agent): память пользователя ≠ память агента.
- **Чтение = линза/`getContext(узел, бюджет)`**: на старте сессии — компактная выжимка (не весь граф).
- **Запись = сессии пишут результаты узлами** (петля P3 — самонаполнение).

## Три слоя памяти (минимум сейчас, консолидация позже)
1. **Core (всегда):** канон/инварианты/предпочтения — маленький, инжектится всегда (аналог MEMORY.md).
2. **Recall (по запросу):** извлекается по релевантности к задаче (аналог on-demand rules).
3. **Episodic (логи/трейсы):** копится; консолидация («sleeptime») — отдельно, позже (ресёрч конкурентов 24.06).

## Минимальное ядро v1 (что делаем первым)
Узел памяти = тонкий паспорт (ADR-0002) + поля: `type · principal · project · scope · content · links · created`.
- `created` — не поле-«место», а линза-сортировка (§1a).
- Достаточно, чтобы: (а) на старте отдать сессии Core+релевантный Recall, (б) записать итог сессии узлом.

## Вопросы на синхронизацию (перед работой)
1. **Scope v1:** хватит principal×project — или сразу и per-agent-role?
2. **Поля узла памяти:** ок предложенные (`type·principal·project·scope·content·links·created`)?
3. **Бюджет инжекта:** сколько памяти грузить на старте (только Core, или Core+Recall)?
4. **Кто пишет память:** любой агент — или только через оркестратор/клапан?
5. **Консолидация:** пока вручную — или сразу закладываем «sleeptime»-сжатие?

## Стык
Это фундамент цели C (наблюдаемость) и лог/статус-группы: статусы сессий = `status`/`session-log` узлы.
Память и walking skeleton v1 — одно и то же ядро (узлы+типы+линзы), поэтому память = хороший ПЕРВЫЙ корпус.

## Решения раунда 2 (владелец, 04.07)
- **Scope = principal × project × ROLE** (роль ДОБАВЛЕНА). Роль — проекция памяти и для агентов, и для людей;
  одновременно роль = **проекция линзы** (смотреть/искать «глазами роли»). Работает в двух местах: scope хранения + пресет линзы.
- **Запись памяти — ГИБКО, не один клапан.** Механизм добавления/проверки памяти — **подключаемый (pluggable)**:
  конкретный процесс выбирает способ валидации (через доп. агентов и/или систему) как своё ПРЕДПОЧТЕНИЕ, не константа.
  Система понимает РАЗНЫЕ механизмы проверки и подключает нужный. (sonnet-валидатор схемы — один из механизмов, не единственный.)
  → в MVP: интерфейс «стратегия записи/валидации» + минимум одна реализация (schema-check); остальные подключаемы позже.
