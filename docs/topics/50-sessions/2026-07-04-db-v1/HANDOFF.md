## ⚑ КЛЮЧЕВОЙ ВОПРОС К ПРОРАБОТКЕ (владелец, приоритет темы)
**Мы будем создавать задачи для агентов в РАЗНЫХ проектах — как они синхронизируются в единой БД?**
Разобрать при запуске: один логический граф vs рантаймы per-project (V3, §1a плана); задача из проекта X
видна в глобальном плане; стык с gateway-entities (agents/agent_bindings/topics уже мультипроектные);
один writer/движок-сервис; где физически живёт БД, если проекты = отдельные git-репо (централизованный
сервис, проекты подключаются). → это первый дизайн-раунд под руководством оркестратора.

## Новые ветки (голос 04.07, владелец сформулирует для Fable)
1. **MCP-расширение агентов:** агент подключает MCP-серверы → новые инструменты (Gmail/Calendar/Notion/
   Drive/БД/кастом). Per-topic/per-project scope; гейт правами (canUseTool) + правило «MCP-выход непроверен
   до ратификации». claude.ai-коннекторы требуют OAuth (недоступны из шлюза — авторизовать на claude.ai).
2. **Лог/статус-группа:** отдельный топик/группа, куда оркестратор пишет статусы; логи = УЗЛЫ в BRAIN
   (session/agent/status = типы), «обновить статус» = запрос к графу. = цель C (наблюдаемость).
3. **Система памяти:** per-principal×project; фундамент — те же узлы логов/статусов + линзы.

## Технический факт (для планирования шлюза)
- Права нельзя расширять из шлюза (правка .claude/settings — под явным одобрением, by design). L1-allowlist
  вставляет владелец. L3 (кнопки прав в TG) = перевод runner на Claude Agent SDK (`canUseTool`).
- Охват оркестратора: глубоко только ЭТОТ проект; о других — лишь по докам FF (нет прямого доступа к репам).

## Раунд 2 — ответы владельца + новые ветки (голос 04.07)
**Ответы на развилки MVP:**
- **Q2 «кто пишет память» → НАПРАВЛЕНИЕ ЗАДАНО:** писать может любой агент, но ЧЕРЕЗ клапан-валидацию —
  быстрый sonnet-агент проверяет соответствие СХЕМЕ (отклонять несуществующие поля, поднимать ошибку,
  слегка чинить/улучшать). Вокруг БД — механизмы САМОУЛУЧШЕНИЯ. Память растёт с каждой сессией/агентом;
  при записи можно запускать задачи на перепроверку/переосмысление/валидацию.
- **Q1 «scope памяти» → РЕШЕНО:** scope = **principal × project × ROLE** (роль добавлена). Роль = проекция
  памяти (агенты + люди) И проекция линзы (смотреть/искать «глазами роли»). Работает в двух местах.
- **Q2 «кто пишет память» → УТОЧНЕНО (не жёстко):** механизм записи/проверки — **pluggable-стратегия**;
  процесс выбирает способ валидации (доп. агенты и/или система) как предпочтение, не константа. schema-check =
  один из механизмов. MVP: интерфейс «стратегия валидации» + одна реализация, остальные подключаемы позже.
- **Q3 «пресеты линзы»** — просит детальный разбор «как оно есть».
- **Q4 «ратифицировать SQLite/сервис» → ПЕРЕОТКРЫТО:** сомнение, подходит ли SQLite вообще; рассмотреть
  Mongo/Postgres/Redis; GraphQL vs обычные запросы (GraphQL — кандидат №1). Нужен дизайн-раунд по технологии БД.

**Новые ветки (фиксировать, работать в разных местах):**
1. **МОНОРЕПО:** переделать архитектуру проекта в monorepo — пакеты: `types` · `backend` · `telegram/gateway` · доп. аспекты. Большое структурное решение.
2. **ТЕХНОЛОГИЯ БД + API:** SQLite vs Mongo/Postgres/Redis; GraphQL. Держать инвариант «md-файлы = истина, БД = индекс/запрос» (ADR-0002/V3) — БД-движки взаимозаменяемы на слое индекса; GraphQL = форма API, ортогонально хранению.
3. **КОНТРОЛЬ/УПРАВЛЕНИЕ агентами:** видеть какие агенты есть, останавливать; отдельная сфера (= наблюдаемость, цель C / D-B).
4. **САМОУЛУЧШЕНИЕ встроить гибко в агентов** (не только вокруг БД); возможно два модуля — различны, но хорошо дружат.
5. **Формат шапки ответа** обновлён (папка · модель · ctx) → закреплён в conversation PROMPT.md.
6. Подтверждено: топик = папка `FF-Personal-Managment` (не music-video); владелец писал по адресу.

## Раунд 3 — КРУПНЫЙ РАЗВОРОТ + новый чат (голос 04.07)
