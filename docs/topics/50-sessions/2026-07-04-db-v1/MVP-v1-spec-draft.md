# MVP v1 — спецификация (черновик)

## 1. Что строим (одним абзацем)
Минимальное ЯДРО единого графа BRAIN: узлы с тонким паспортом, типы-как-узлы (адрес по ID),
категории-как-индекс, рёбра home+facet — плюс **память как первый корпус** и **линза getContext**
для чтения под бюджет. Цель — замкнуть круг: инжест `docs/` → узлы/типы/рёбра → чтение линзой →
запись результатов сессий обратно. Строим на реальных данных, модель правим на ходу.

## 2. Ядро (из аудита @ff/core: ~15% готово, ≈14–22 дня)
- **Узел = паспорт** (9 обяз. + 2 опц.): `id`(ULID) · `type`(открытый реестр) · `schema`(type@ver) ·
  `created`/`updated` · `epistemic`(draft|proposal|hypothesis|fact|archived) · `sensitivity` ·
  `source`(human|agent|system|import) · `principal`; опц. `level?`(why|what|how|data) · `canonical_id?`.
  Payload отдельно: `title` + `description`.
- **Типы-как-узлы:** `type` — открытый реестр, каждый тип = control-plane узел `{name, version, payload_schema, validate()}`, адрес по `id`, НЕ закрытый enum.
- **Категории-как-индекс:** рёбра `facet-of`/`tagged-as` к узлу-категории (не поле-массив).
- **Рёбра:** `to · rel · home:bool` (ровно один true) · `priority` · `cascade` · `cascade_order` · `provenance`(manual|auto|inferred) · `derived`.
- **Инвариант «цикл имеет терминатор»:** cascade-обход по DAG (первый визит выигрывает + `maxDepth`); ПАТТЕРН обязан нести `recursion_terminator`+`maxDepth`; движок = цикл-гард. Луп без выхода → отклоняется валидатором типа.
- ✅ Переиспользуемо: сериализация md+frontmatter, генерация id, trace, каскад контекста. ❌ Выбросить: закрытый `NODE_KINDS`(9), `importance`-на-ноде, `parentId`-как-единственная-связь.

## 3. Память — центр (как растёт и строится)
- **Память = обычные узлы графа**, 0 новых обязательных полей паспорта (усиливает существующую схему).
  Узел памяти = паспорт + `content · links`; scope через `principal`(owner|agent:N|shared) × project.
- **3 слоя:** Core (всегда инжектится) → Recall (по релевантности) → Episodic (логи/трейсы, консолидация позже).
- **Рост:** сессия пишет итог узлом → консолидация `trace[] → reflection → memory-fact(hypothesis)` →
  повышение `hypothesis→fact` делает ДРУГОЙ актор (владелец/verifier), не автор. Забывание без удаления
  (bi-temporal рёбра valid/known, `contradicts/supersedes`, `epistemic:archived`).
- **В MVP:** узлы памяти + запись сессией + Core-инжект. **Позже:** sleeptime-консолидация, heat, эмбеддинги.

## 4. Линза / фокус / уровни (проработано заранее — ответ на запрос владельца)
Что уже есть: вьюер **LIST+FOCUS**; **LENS = 4 регулятора** (видимые рёбра · глубина · поля карточки ·
`projected_level`); `getContext(узел, бюджет)` — упомянут, но **контракт НЕ специфицирован**.

**Синтез-ответ на «линза как дерево + виды»:**
- **Направление** «дерево само подсказывает» = **home-хребет** (обязательный, ацикличный) по умолчанию;
  линза сужает видимые рёбра по типу/приоритету → естественный путь; facet-рёбра = альтернативные оси.
- **Глубина** = **бюджет** `getContext(узел, бюджет)` (программный аналог ручного +/-).
- **«Виды» (полный / аналитика / дайджест)** — их как отдельного механизма НЕТ; предлагаю НЕ плодить новый,
  а сделать **пресеты линзы** (именованный узел-линза) = комбинация трёх ручек:
  - `дайджест` = `level∈{why,what}` · малый бюджет · карточка L1 (title+description)
  - `аналитика` = `level∈{what,how}` · средний бюджет · + backlinks/rollup
  - `полный` = все уровни · payload по Enter
  → ложится на существующее (LENS + `level?`), без нового механизма. **Рекомендация: так.**

⚠️ **Блокер линзы:** без контракта `getContext(бюджет)` MVP-линза не собирается — это надо специфицировать ПЕРВЫМ пунктом дизайна линзы.

## 5. Шаги стройки MVP (порядок + параллель)
1. Паспорт v2 (`schema.ts`+`node.ts`, 2–3 дн)
2. md-сериализатор authored/stream (1–2 дн) ‖ edge-модель `store.ts` (3–4 дн) — независимы после п.1
3. SQLite-индексатор M1 read-only (3–5 дн)
4. query + `getContext`/мин.линза (3–5 дн) — сначала контракт бюджета
5. Инжест корпуса `docs/` (2–3 дн) — маппинг id/type можно готовить параллельно с п.3
- Через gateway параллелятся: сериализатор ‖ edge-модель; подготовка инжеста ‖ индексатор.

## 6. Развилки к владельцу (решить ДО/в начале стройки) + риски
**Память:** (1) scope v1 — principal×project или сразу +agent-role? (2) поля узла ок? (3) бюджет инжекта — Core или Core+Recall? (4) кто пишет память — любой агент или через оркестратор/клапан? (5) консолидация — вручную или сразу sleeptime?
**Ядро:** (6) SQLite-для-структуры и «библиотека vs сервис» (OQ-1/OQ-2) — ратифицировать (блокер M2). (7) Корпус v1 — какие docs инжестим первыми?
**Линза:** (8) принять «виды = пресеты линзы»? (9) специфицировать контракт `getContext(бюджет)`.

**Top-3 риска:**
- **R1 (H):** контракт `getContext(бюджет)` не специфицирован → линза не собирается.
- **R2 (M):** «единая БД» без единого writer'а до M2 = просто общая папка (ложное доверие к централизации).
- **R3 (M):** память опирается на ещё не принятый ADR-0004 (bi-temporal/heat) + не решено «кто пишет память» (ждёт ADR-0003/клапан) → риск неконтролируемой записи.
