## 1. Целевая организация пространства на компьютере (P0)

Принцип: **три слоя, не смешивать** — совпадает с POS-scope (universal/domain/project):
```
~/Documents/IT/Apps/
├── FF-Personal-Managment/      ← ЦЕНТР УПРАВЛЕНИЯ: граф знаний, канон, управляющие сессии (эта)
├── CORE/                       ← УНИВЕРСАЛЬНЫЕ переиспользуемые модули (живут отдельными git-репо)
│   ├── agent-gateway/          ← вынесенный gateway (шаг P1)
│   └── doc-system/             ← конвенция документации как отделяемый СКИЛ (шаг P2c, позже)
└── PROJETS/                    ← прикладные проекты: dwizh · CRM-Rent · jenek · Cardex · music-video
```
- Имя `CORE/` — предложение; владелец может выбрать другое (упоминался «7days» — уточнить, что это).
- **Как работает доступ Claude:** волшебной «общей папки» нет. Каждая сессия Claude укоренена в папке запуска
  (её CLAUDE.md подхватывается автоматически); чужие пути читаются с permission-prompt; `claude --add-dir <path>`
  добавляет вторую рабочую директорию в сессию. Практика: **1 чат = 1 корень проекта**; кросс-проектное знание —
  в графе FF; управляющая сессия (эта) раздаёт задачи.
- Управление на компьютере = слой оперирования: разные чаты под разные направления, контроль команд/вводов —
  позже через сам gateway (это его прямое назначение).

## 1a. Модель распространения по проектам (ответ на вопрос владельца, голос 03.07 ночь)

Вопрос: запускать в каждой папке / «устанавливать» / копировать как пакеты? Копии ломают синхронность.
**Ответ: НЕ копировать. Один источник, три механизма по типу вещи:**
1. **Система агентов (gateway) = ОДИН центральный сервис** в `CORE/agent-gateway`, работает на весь компьютер;
   проекты не получают копий — они **подключаются** (в БД gateway уже есть entities `bots/agents/agent_bindings/
   topics` — он спроектирован под несколько проектов/ботов). Папка проекта = рабочая директория, которую
   gateway передаёт сессии Claude. Синхронность автоматическая: источник один.
2. **Знания/правила/скиллы = глобальные скиллы** `~/.claude/skills/` — один файл виден из всех проектов сразу
   (живой пример: fable-orchestrator уже так работает). Проектное остаётся в `<проект>/.claude/` и docs/.
3. **Код-библиотеки = пакет** — только когда появляется 2+ кодовых потребителя (правило dwizh); не сейчас.

Мысль владельца «файл живёт 3-4 раза: аналитика в папке проекта + та же единица в глобальном плане…» —
это ровно мультиродитель/фасеты из ADR-0002 (дом+категории = разные рёбра): подтверждение модели реальной
потребностью. Продолжение (2-й голос): файл живёт сразу в {аналитика проекта · глобальная аналитика · лог
по дате · обсуждение топика}; плюс места «без жёсткой привязки» (доменный анализ, сохранённый как глобальный,
но принадлежащий домену). Раскладка на модель: один `home` + N facet-рёбер; «лог по дате» = вообще НЕ место,
а ЛИНЗА (сортировка по created — выводится, не хранится); «глобальный анализ, принадлежащий домену» =
home=глобальная аналитика + facet-ребро к домену. Всё уже покрыто ADR-0002, новых механизмов не требуется.

## 3b. Новые концепты из голоса 04.07 (сиды, к проработке)

- **Инструкции сессий / loop prompting:** у системы, помимо задач и планов, обязательный третий род —
  ИНСТРУКЦИИ для сессий, подключаемые в нужный момент. Луп = чёткая последовательность итераций +
  обязательные ВЫХОДЫ (exit-условия/ограничения). Агенту не обязательно знать промпты всех этапов:
  видит свой текущий этап детально, может переключиться на весь контекст. «Мы — их память, направление
  и видение»: агент выполняет шикарно, если чётко сказано КАК. Задача может нести внутри промпт сессии.
  → это узлы графа (инструкция/луп/этап = типы), детальная проработка — тема отдельной сессии.
  Развёрнуто: `docs/tree-test/70-ideas/IDEA-loop-instructions.md`.
- **Одна БД для (почти) всех проектов:** базовые вещи для всех + может вырасти до целого проекта внутри;
  самоулучшаемая — ИИ имеет доступ, смотрит, улучшает, записывает, ставит задачи агентам. Структура папок
  отражает это: `PROJETS/` = проекты, а «ОРГАНИЗАЦИЯ» = организация деятельности (дерево знаний, агенты,
  планирование) — кандидат-имя для CORE/ или отдельный уровень.
- **Автономный подъём сессий:** «ты мог бы сам создать агента в папке, он бы поднялся и всё сделал —
  сейчас для этого нужен я». Ровно назначение gateway (P1); учесть в спеке доработок как требование:
  оркестратор может программно поднимать сессию в любой папке проекта.
- **Telegram-взаимодействие:** подозрение на падение больших сообщений (лимит Telegram 4096 симв. —

## 3d. Модульность = плагины (голос 04.07 00:33, «продолжение следует»)

- Модульность строится как **marketplace-механика**: скачивание → установка → подключение → расширение.
- Плагин может быть **целой системой агентов** со своей памятью и ресурсами, подключаемой к

- Пример владельца: базовый плагин «спорт» → люди накидывают свои вариации, расширяют/улучшают →

- Фундамент: единая БД позволяет **создавать гибкие структуры данных на лету, контролируемо**

  не стена» (ADR-0002) для внутренних групп; жёсткий default-deny — только для сторонних модулей.

## 3j. Голос 04.07 06:49 — механика gateway: корень, выдача прав, спавн и наблюдаемость (в спеку Этапа 3)

- **Корень агента:** у каждого агента в gateway — СВОЙ корневой каталог (cwd спавна `claude -p`), корень
  всегда ровно один; задаётся в agent_bindings (бот/топик → агент → корень). Точную текущую механику cwd
  проверит сессия выноса; требование зафиксировано.
- **Выдача прав через Telegram:** права выдаёт ТОЛЬКО владелец. Механика: агент упёрся в отсутствие
  права → gateway шлёт владельцу карточку с кнопками [разово | на сессию | навсегда | отказ] → выбор
  записывается узлом-грантом в Brain → енфорсит gateway/движок, НЕ агент. До реализации клапана права
  выдаются вручную (permission prompts в терминале).
- **Спавн агентов — два уровня:** (а) суб-агенты ВНУТРИ сессии — наследуют корень и права родителя;
  (б) НОВАЯ сессия в другом проекте/контексте (читает свой CLAUDE.md) — только ЧЕРЕЗ gateway, который
  регистрирует: кто создал · корень · контекст · зачем. Прямой неучтённый спавн чужих корней — запрещён.
- **Наблюдаемость:** каждая сессия/агент = узел в Brain (`session`/`agent` + рёбра `created-by`,
  `works-in`, привязка к топику TG). «Кто где создан, под каким контекстом» = обычный запрос по графу +
  отражение в интерфейсе Telegram (топик/статус). Хранить в памяти Brain — да (это stream/authored узлы).
- **TG-развилки:** владелец сказал «всё понятно» — рекомендации (форум-топики · HTML · порог ~7000)
  считаем принятыми, если не возразит.

## 3g. Голос 04.07 02:55 — готовность движка, категории-индекс, рекурсия, грани

- **«Насколько движок/брейн готов, можем ли стартовать наполнение БД?»** → запущен sonnet-аудит
  `@ff/core` против ADR-0002 + концепта V3 (что есть · дельта · % переиспользуемого · объём walking
  skeleton · план наполнения). Известно заранее: ядро v1 писалось под ADR-0001 (9 kinds), на ADR-0002
  НЕ переписано — готовность точно частичная.
- **Категории = индекс системы:** категория цепляется к файлу «как внутренность папок» (папка controller →
  файлы user, …). Линия умных категорий (N-087: классификатор⟂вариант-формы) + индексы движка;
  требование: механизм категорий должен работать как ИНДЕКС (быстрый доступ), не только как метка.
- **Рекурсия в паттернах:** паттерны могут быть рекурсивными; возможно особые поля; **у рекурсии
  обязательно должен быть выход** — рекурсия без выхода не допускается. Совпадает с уже решённым
  (maxDepth split, терминатор prune|mark-cycle из стресс-теста N-078) + exit-условия лупов
  (IDEA-loop-instructions) — свести в один инвариант «любой цикл имеет терминатор».
- **Грани/многомерность («5d/7d пространство»):** ключевые механики владельца апгрейдить и «сделать
  конфетку» — механизм быстрых выжимок/концептов для ИИ и пользователя. База: линзы + getContext(узел,
  бюджет) + вьюер LIST+FOCUS; требует отдельного дизайн-раунда (тема вьюера/линз, D-A).
