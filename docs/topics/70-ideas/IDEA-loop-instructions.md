# IDEA — Инструкции сессий и loop prompting

## Суть
Помимо ЗАДАЧ (что сделать) и ПЛАНОВ (в каком порядке) системе нужен третий род управляющих данных —
**ИНСТРУКЦИИ**: как именно сессия/агент должны работать, подключаемые в нужный момент времени.

## Ключевые свойства (из голоса владельца)
1. **Луп = последовательность итераций с обязательными выходами.** Каждый цикл имеет exit-условия
   и ограничения (по числу итераций, качеству, бюджету). Луп без выхода — запрещён.
2. **Ступенчатая видимость контекста.** Исполнителю не обязательно знать промпты всех этапов:
   - режим «текущий этап детально» (по умолчанию);
   - режим «весь контекст всех этапов + маркер своего текущего» (по переключению).
   Агент всегда чётко знает, на какой итерации находится и как реагировать.
3. **«Мы — их память, направление и видение».** Агент выполняет работу шикарно, если чётко сказано КАК;
   инструкция и есть носитель этого КАК. Отсюда требования: механизмы проверки (гейты между итерациями),
   максимальная гибкость композиции.
4. **Задача может нести инструкцию внутри** — промпт сессии или конкретное описание прямо в задаче;
   полный объём станет ясен в момент реализации.

## Раскладка на нашу модель (первый набросок)
- Инструкция / луп / этап = **типы узлов** control-plane (рядом с ТИП·ЛИНЗА·ПАТТЕРН; вероятно,
  инструкция — подвид ПАТТЕРНА: PATTERN-узел уже используется для протокола сессии в теме памяти).
- Этапы = дочерние узлы лупа с `seq`; exit-условия = поля/узлы-предикаты; текущая итерация = состояние
  сессии (узел session ссылается на активный этап).
- Ступенчатая видимость = ЛИНЗА над лупом (текущий этап vs весь луп) — механизм уже есть.
- Связь с gateway: команды /new /resume /compact /fork — точки, где инструкция подключается к сессии.

## Следующий шаг

(например: цикл ревью кода; цикл тренировочной прогрессии из D-D; цикл ресёрча конкурентов).
