# Инфраструктура интерфейса агент↔субстрат — разбор (analyst)

Угол: НЕ повтор 16 модулей из `infrastructure/` (те — сведение по ценностям, общесубстратные). Здесь —
узко угол **контракта 03-contract**: что происходит в момент, когда агент касается графа (читает пишет
себя-как-память трейсит). Часть уже покрыта существующими 16 модулями как носителями (см. пересечения
ниже) — не дублирую, а достраиваю то, чего там нет.

трейс как узел или как строка-лог, как рвётся круг «агент читает свою же гипотезу как факт».

## A) Инфра-модули (интерфейс, 4 шт)

### М-А. Agent Write Gateway (единая точка входа записи агента)
Каждая запись агента — не прямой upsert в граф, а: draft-узел (status=nascent, паспорт #7) +
provenance-ребро `wasDerivedFrom → run-node` (#4) + optimistic-concurrency (agent обязан указать
`based_on_version`/`as-of T`, bitemporal #2). Конфликт версии → НЕ silent overwrite, а explicit
`conflicts-with`-узел через Event/Referent Anchor (#3). Смыкается с Ingress Adapter/Дедуп (#13,
уже 🟢-приоритет из-за реального бага дублей шлюза, см. `dwizh-gateway-extraction` память) —
идемпотентность здесь = частный случай optimistic-concurrency guard.

### М-Б. Run/Trace Ledger — трейс КАК УЗЕЛ, не только строка
Текущее решение в `02-agents/runs/INDEX.md`: «только ссылки, не тела» — это **сознательно упрощённый
журнал**, и тут развилка: если трейс НЕ узел графа (а просто строка markdown), то провенанс-ребро
`wasDerivedFrom → run` (модуль М-А выше, и #4 в 16-модульном списке) не на что вешать программно —
только на текстовую ссылку, не queryable. Предлагаю: `run`-узел лёгкий (agent-id, model, prompt-ref,
input-node-ids, output-node-ids, timestamp, context-budget), «реестр» = лента ЭТИХ узлов, а не отдельная
сущность-лог. Тело работы по-прежнему в целевом документе — узел не дублирует контент, только метаданные
прогона. **Промпт тоже узел** (версионируемый, с id) — обеспечивает «каким промптом порождена эта запись»
и «что сломает откат промпта» (impact-анализ на graph, не на глазок).

### М-В. Write Authorization / Trust Tiers (запись — не то же, что чтение)
Единый PEP (#5, 16-модульный список) решает ПОРОГ ЧТЕНИЯ (anti-zombie). Симметричного «единого порога
ЗАПИСИ» в списке нет отдельным пунктом — есть только складка «trust-write роль верификатор» (упомянута
внутри #5, не раскрыта). Предлагаю поднять в модуль: уровни агент-роли (read-only / draft-write /
verified-write / steward), двухфазная запись (agent ВСЕГДА пишет nascent/draft; переход в
verified/committed — отдельное действие с ДРУГИМ актором, не автора). Это обобщение паттерна Gardener
(#14, «proposal-not-autoapply») на ВСЕХ агентов-писателей, не только садовника.

### М-Г. Agent Memory as Nodes (память агента — часть графа или нет?)
Открытый архитектурный вопрос, которого нет в 16-модульном списке явно: рабочая/эпизодическая память
агента (черновики, «заметки себе», промежуточные гипотезы между шагами) — это узлы графа с
`owner=agent-id` и ephemeral-классом (складка Ц4+Ц7 в списке, привязана к Gardener/PEP, но НЕ к вопросу
«это вообще узлы или внешнее хранилище раннера SDK?»). Если это узлы — нужен собственный PEP-scope
видимости (кто читает scratch другого агента: только сам агент? owner? другие агенты в том же run?).
Если НЕ узлы — тогда provenance-цепочка (#4) обрывается на границе агента, и «откуда взялась эта запись»
не восстановить дальше последнего committed-узла. Рекомендую: узлы, но отдельный namespace/тип
(`agent-scratch`), с более коротким TTL по умолчанию (метаболизм #9/#14) и БЕЗ провенанс-обязательства
наружу (внутри одного run можно ссылаться свободно).

## B) Упущенные сценарии

1. **Конкурентная запись** — покрыто М-А (optimistic concurrency + explicit conflict-node), НЕ
   silent-last-write-wins. Уже частично поднято как OQ-9 в `infrastructure/open-questions.md`
   (CRDT-merge vs явный конфликт) — но там про поле `confidence`, здесь про ЛЮБУЮ запись в узел.
2. **Агент пишет мусор** — нужен validation-gate НА ВХОДЕ (паспорт #7 схема + Ingress Adapter #13)
   ДО commit, независимо от trust-tier (М-В) — нельзя, чтобы «доверенный» агент обходил schema-check.
   Уже частично покрыто идеей #13, но explicit gate на garbage не выделен отдельно.
3. **Циклическая запись, буквальная** — cycle-detection на provenance-графе (М-А, `wasDerivedFrom`
   не должен образовывать цикл; если образует — hard-reject, не soft-warning).
4. **Циклическая запись, СКРЫТАЯ (эпистемический отмыв / confidence-laundering)** — САМЫЙ важный
   пропуск, не буквальный граф-цикл: агент А пишет гипотезу H (confidence=0.3, nascent). Агент Б читает
   H, не замечает низкий confidence (или замечает, но округляет вверх), деривирует H2 и коммитит с
   confidence=0.7 «потому что H уже была в графе, значит подтверждена». Агент В читает H2 — она выглядит
   committed/свежей, не видно, что корень — непроверенная догадка А. Confidence РАСТЁТ вверх по цепочке
   деривации без реальной проверки, чисто от факта «уже кто-то записал». Это НЕ отловится cycle-detection
   (граф ацикличен), и НЕ отловится существующим Confidence-модулем (#8) как он описан (там про
   CRDT-merge параллельных, не про инфляцию по цепочке). Нужен инвариант: `confidence(derived) ≤
   f(confidence(sources))`, принудительно на движке (integrity-as-engine-duty, #16), а не по доброй воле
   пишущего агента.
5. **Агент читает устаревший срез** — long-running агент строит контекст на as-of T0, граф мутирует
   до T1, агент пишет как будто T0 всё ещё верно. Bitemporal (#2) даёт МЕХАНИЗМ (as-of read), но нет
   правила «запись обязана нести `based_on_snapshot=T0`» для последующего сравнения при conflict-check
   (М-А). Без этого поля conflict-detection не может отличить «осознанное обновление» от «слепое
   перезаписывание поверх более свежих данных, которых агент не видел».
6. **Факт vs гипотеза агента** — паспорт (#7) даёт ПОЛЕ (badge author, confidence), но нет
   КОНСТИТУЦИОННОГО запрета: агент технически МОЖЕТ проставить себе confidence=1.0/status=fact
   напрямую. Нужно правило движка (#16): агент не имеет права писать status=verified/fact — только
   nascent/hypothesis; переход выше требует другого актора (человек или отдельная verifier-роль, М-В).

## C) Главный риск слоя

**Эпистемический отмыв через цепочку деривации (сценарий 4)** — единственный найденный риск БЕЗ
владельца среди уже сведённых 16 модулей. Вся архитектура построена вокруг «агенты читают граф → 
действуют → пишут обратно» как основной цикл (это буквально способ существования системы, не edge-case).
Если confidence/эпистемический статус не гарантированно НЕ РАСТЁТ при передаче по цепочке агент→агент
(а сейчас это не гарантировано нигде — ни в #7 паспорте, ни в #8 confidence, ни в #16 конституции), то
через N итераций обычной работы граф заполнится утверждениями, которые ВЫГЛЯДЯТ проверенными фактами,
а корень — одна непроверенная догадка. Это подрывает Ц-3 Доверие и Ц-1 Читаемость молча (без сбоя,
без ошибки — просто дрейф), обнаруживается поздно, откатить дорого (нужен provenance-обход всей цепочки).
Severity: H. Требует: инвариант монотонного НЕ-роста confidence по `wasDerivedFrom`, принудительный
движком (#16), а не конвенцией паспорта (#7) — иначе одна невнимательная запись ломает инвариант молча.

## Обнаруженное противоречие (флагую владельцу/оркестратору)

`02-agents/runs/INDEX.md` явно фиксирует: «реестр — ТОЛЬКО ссылки, не тела; никакого сырья и полотен».
Модуль М-Б (Run/Trace Ledger) предлагает трейс-метаданные КАК УЗЛЫ графа (не тела, но структурные
записи с id, на которые вешаются provenance-рёбра). Это не то же самое, что «сырьё в реестре» — но
формально расширяет решённый вопрос. Нужно явное решение: остаётся ли `runs/` файловым логом-указателем
(тогда provenance к прогону — текстовая ссылка, не программный граф-обход), или прогон становится
первоклассным узлом (тогда `runs/INDEX.md` описание нужно уточнить/заменить).
