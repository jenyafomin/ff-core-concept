# Инфраструктура связей и витальности графа — разбор

## Контекст / что уже решено (не переоткрываю)
- В4 ратифицирован: ребро-паспорт только у **рёбер-утверждений** (инсайты); структурные рёбра
  (`home`, `facet-of`) паспорта НЕ несут (L0-memory-unit.md:144).
- home + category = ДВА раздельных ребра (дано в задаче).
- Уже в пуле инфры: Edge Engine #11, Forgetting Engine #9, Gardener #14, Read-scale Index #12,
  Провенанс #4. Я не дублирую эти модули — углубляю их МЕХАНИКУ под своим углом и добавляю то,
  чего в свод-таблице `candidates.md` нет явно.

## A) Инфра-модули (4)

### A1. Typed Edge Contract — реестр типов рёбер как контракт, а не список имён
`candidates.md #11` говорит «typed-edges = контракт каскада», но не специфицирует ПОЛЯ контракта.
Предлагаю обязательные атрибуты на каждый ТИП ребра (не на экземпляр):
- `structural | semantic` (уже есть неявно через В4 — сделать явным полем типа)
- `on_source_delete` / `on_target_delete`: `cascade-delete | orphan-tombstone | block | reparent`
- `cardinality`: `1 (replace)` vs `N (additive)` — **это прямо решает конфликт home vs category**:
  `home` = cardinality 1 (новая запись ЗАМЕЩАЕТ старую, не копится), `category` = cardinality N.
  Без явного поля это станет invisible-баг: два конкурирующих `home`-ребра на одном узле, потому что
  ничто в схеме не запрещает вставить второе.
- `cycle_allowed`: bool — структурные рёбра (home, facet-of, template-of) обязаны быть DAG
  (cycle_allowed=false, проверка при записи); инсайт-рёбра (`derived-from`, `caused`) могут
  порождать циклы (1.10 в forgotten-check) — тогда cycle_allowed=true, но обходчик обязан иметь
  visited-set/bounded depth.
- `directionality` + нужен ли обратный индекс (см. A2).

### A2. Единый Traversal Primitive (закрывает OQ-8)
`open-questions.md` OQ-8 уже поймал риск: провенанс (#4), consent-taint (#10) и forgetting-cascade
(#9) все обходят ОДИН граф lineage — если это три независимые реализации обхода, на масштабе они
триплицируют стоимость и рискуют разойтись в поведении (один обход учёл tombstone, другой — нет).
Рекомендация: ОДИН generic traversal-сервис с примитивами:
1. `fan-out(node_id, edge_types?)` — все рёбра узла, через adjacency-индекс (не скан всего графа).
2. `reverse(node_id)` — кто ссылается НА узел (обязателен для orphan-detection при удалении).
3. `as-of(T)` — фильтр по valid-time РЕБРА (ребро само bitemporal per В2), не только узла.
4. `walk(policy)` — параметризуемый обход, где provenance/consent-taint/forgetting — это ТРИ ПОЛИТИКИ
   поверх одного `walk`, а не три написанных с нуля обхода.
Без этого примитива каждый новый каскад (а их уже минимум 3) — это новый риск рассинхрона.

### A3. Vitality-на-ребре (не только на узле)
V6 сам это отметил («деградации связей, не данных — ребру нужен свой stale», Sonnet #7), но в
`candidates.md` это осталось складкой на #8 Confidence, не отдельной механикой. Уточняю модель:
`edge.vitality = f(node_A.salience, node_B.salience, edge.confidence, edge.use_freq)`.
Ключевое архитектурное решение, которого пока нет: **производная или независимая величина?**
- Если производная — засыпание/hard-erase узла ДОЛЖНО синхронно (в той же транзакции) уценить/
  тронуть vitality всех инцидентных рёбер, иначе ребро «живо» по своим метрикам, хотя один конец мёртв.
- Если независимая — нужен отдельный gardener-проход именно по рёбрам (Gardener #14 сейчас
  сформулирован как проход по узлам/facet'ам).
Рекомендация: производная + синхронный триггер на edge-vitality при любой мутации salience узла —
дешевле, чем догонять асинхронным свипом (см. риск ниже).

### A4. Архивация без потери связей — «tombstone видим, delete нет»
Разграничить два разных результата на РЕБРЕ (не только на узле, где sleep/hard-erase уже решены #9):
- узел заснул (sleep, обратимо) → инцидентные рёбра НЕ удаляются и НЕ прячутся молча — помечаются
  `target-dormant`, видимы при обходе как «связь есть, но ведёт к спящему» (иначе тихая потеря факта
  связи = нарушение Доверия/Читаемости, тот же класс бага, что «тихая порча» в 1.4 forgotten-check).
- узел hard-erased (необратимо) → инцидентные рёбра переходят в tombstone (видимый маркер «было
  ребро на referent X, стёрто»), НЕ true-delete, кроме случаев когда referent сам требует полного
  исчезновения (конституционный потолок #16 может это форсировать).
Инвариант для DB-control (integrity-as-engine-duty, #16): ни одно ребро не может ссылаться на
`canonical_id`, который не резолвится ни в живой, ни в tombstoned узел — проверка НА ЗАПИСИ (как FK),
не только при чтении постфактум.

## B) Упущенные сценарии (5)

1. **Гонка при hard-erase (новое, не было в 1.11).** 1.11 forgotten-check уже поймал «осиротевшие
   рёбра при удалении узла», но не поймал ВРЕМЕННОЕ ОКНО: если очистка инцидентных рёбер — асинхронная
   задача Gardener (а не часть одной транзакции с hard-erase), то между «узел стёрт» и «рёбра
   подчищены» есть окно, где агент может прочитать dangling-ребро и через него косвенно восстановить
   след referent'а — при том, что конституция (#16, И2) требует hard-erase БЕЗУСЛОВНЫМ. Если PEP (#5)
   не знает про это окно, гарантия «безусловно» на практике не безусловна. Это стык Edge Engine +
   Forgetting Engine + PEP, которого нет ни в одном из трёх модулей по отдельности.

2. **Забыли узел (sleep), а на него ссылаются — тихая деградация читаемости.** Не рассмотрено: должен
   ли обход по умолчанию ФИЛЬТРОВАТЬ спящие узлы из `fan-out`/`reverse`? Если да — агент видит меньше
   связей, чем есть, и решит, что два понятия больше не связаны (ложный вывод). Если нет — читатель
   должен уметь отрендерить «тусклую» связь (Читаемость). Дефолт не зафиксирован нигде.

3. **Конфликт home vs category — конкретный failure mode.** Без cardinality-поля (A1) две системы
   импорта (Telegram-бот + web-форма), обе создающие `home`-ребро независимо, дадут узлу ДВА `home`.
   Ничто в текущей схеме это не запрещает и не обнаруживает — тот же класс проблемы, что дедуп узлов
   (1.5 forgotten-check), только на рёбрах, и пока нигде не проговорено.

4. **Циклы в графе — не только инсайт-рёбра.** 1.10 forgotten-check поймал циклы для рёбер-инсайтов.
   Но Г35 (фрактальная композиция, «единица из единиц») подразумевает composition-рёбра, которые тоже
   МОГУТ образовать цикл (A содержит B, B ссылается на A как на пример). Cycle_allowed (A1) должен
   покрывать этот тип тоже, иначе рекурсивный обходчик Gardener падает в бесконечность на композитах,
   не только на инсайтах.

5. **Масштаб — 10⁴-10⁵ узлов.** Наивные реализации `fan-out`/`walk` без индекса — O(E) на каждый
   вызов. При salience-пересчёте (Read-scale Index #12) и любом каскаде (provenance/consent/forgetting,
   OQ-8) это умножается на количество каскадов. Промисс Читаемости «дёшево прочитать грань» ломается
   первым именно на графовых операциях, не на самих узлах — потому что узел читается по id (O(1)), а
   ребро требует обхода соседей (O(degree) минимум, O(E) без индекса).

## C) Главный риск слоя

**Рёбра спроектированы как second-class relative к узлам.** Паспорт, bitemporal, salience,
forgetting — всё это ПЕРВЫМ ДЕЛОМ специфицировано для узла; ребро получило урезанный паспорт только
для узкого подмножества (инсайты, В4), а структурные рёбра (`home`, `category`, `facet-of`) — вообще
без состояния. Но целостность, витальность и читаемость ГРАФА как целого зависят именно от
состояния рёбер (cardinality, cascade-контракт, vitality, tombstone-видимость) — не только узлов.
На малом масштабе (десятки-сотни узлов, ручное тестирование) это не проявится: человек визуально
заметит два `home`-ребра или мёртвую ссылку. На целевом масштабе (агрегатор ВСЕЙ жизни, 10⁴+ узлов)
это станет статистически неизбежным и недиагностируемым постфактум — а по правилу «заложить сейчас»
(ретрофит невозможен) отсутствие сегодня полей cardinality/cascade-contract/edge-vitality означает,
что каждое существующее ребро потом придётся реконсилировать вручную. Severity: H.
