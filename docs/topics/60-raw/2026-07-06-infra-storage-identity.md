# Раскопка: инфраструктура ХРАНЕНИЯ и ТОЖДЕСТВА (сырьё)

## Контекст прочитанного

Прочитаны: `01-brain/INDEX.md`, `infrastructure/INDEX.md` (5 опор), `infrastructure/ideas/candidates.md`
(16 модулей от 7 агентов дивергенции ценностей), `infrastructure/open-questions.md` (OQ1-13),
`values/V2-tozhdestvo.md`, `values/02-tozhdestvo/` (6 направлений цикла 2), `decisions/DECISIONS-LOG.md`,
`MIGRATION-BLUEPRINT.md`, `scenarios/INDEX.md`, `docs/01-organization/data-canon/INDEX.md` (пусто —
площадка под ADR, ничего не заложено).

**Ключевое наблюдение до анализа:** существующий пул из 16 модулей (canonical_id, Bitemporal, Event
Anchor, Провенанс, PEP, Линза, Паспорт, Confidence, Forgetting, Consent-taint, Edge Engine, Read-scale
Index, Ingress Adapter, Gardener, Engine Contract, Конституция) — весь на уровне **онтологии/семантики
памяти** (что значит «та же самая ячейка», как течёт согласие, как гаснет доверие). Ни один модуль не
специфицирует **физический write-path**: как реально происходит запись .md+frontmatter на диск, кто
пишет, что происходит при одновременной записи, как индекс/поиск синхронизируется с файлами, что
происходит при переименовании файла, как мигрирует САМА схема frontmatter. `data-canon/INDEX.md` —
буквально пустая папка под будущие ADR. Это дыра ПОД всем хребтом, а не рядом с ним.

Это и есть мой угол: не переизобретать 16 модулей, а вскрыть **слой ниже** — механику, на которой
canonical_id/Bitemporal/Edge Engine вообще способны исполняться.

## A) Предложенные инфра-модули (детально)

### М1 — File-Truth ↔ Index Sync Engine (файлы=истина, индекс=производная)
Проект декларирует «файлы = истина» (CLAUDE.md, data-canon/INDEX.md), но нигде не специфицирован
механизм: индекс/граф-БД для быстрого поиска — это ПРОЕКЦИЯ файлов, не альтернативный источник.
Модуль = (а) детектор дрейфа: контрольная сумма/mtime файла vs то, что знает индекс; (б) правило
однонаправленности — индекс всегда можно пересобрать ИЗ файлов «с нуля», обратного пути нет;
(в) явный маркер «файл отредактирован мимо движка» (ручная правка человеком в редакторе, не через
агента) — такой файл должен быть переиндексирован при следующем чтении, а не тихо считаться устаревшим
индексом за истину.

### М2 — canonical_id Minting & Collision Registry
Модуль #1 в существующем каталоге называет «ULID/контент-адрес», но НЕ специфицирует: кто минтит id
(центральный сервис vs каждый агент локально/офлайн), что происходит при коллизии (два агента в разных
ветках/сессиях сгенерировали id для «одной и той же» сущности независимо — реальный кейс при
многосессийной работе через gateway, см. `dwizh gateway` память), и как id переживает `git merge`.
Нужен: алгоритм минтинга с гарантией офлайн-уникальности (ULID/UUID7 + namespace агента), явный
Collision Registry (лог случаев «два id оказались одним референтом» → сведение в alias, не в новую
сущность), и связь с М1 (кто вправе присвоить id — движок при индексации, не сам файл).

### М3 — Git-native Concurrency & Structural Merge Adapter
Хранилище — git-репозиторий md-файлов (подтверждено git status проекта). Ни один из 16 модулей не
называет git явно как субстрат конкурентной записи. Проблема: `git merge` на YAML frontmatter — это
**текстовый** merge, а не **структурный** (два агента добавили разные поля в один YAML-блок →
line-based diff может дать синтаксически битый YAML или тихо взять «одну сторону» без предупреждения).
Модуль = YAML-aware 3-way merge (сравнение по ключам, не по строкам) + политика «один писатель на файл
за раз» ИЛИ «оптимистическая запись + структурный merge при столкновении» — явно выбрать одно, сейчас
не выбрано ни то, ни другое. Также: атомарность записи (write-tmp+rename, не truncate-in-place) — без
неё краш агента в момент записи = битый .md с оборванным frontmatter, тихо ломающий весь граф на этом
узле.

### М4 — Frontmatter Schema Migration Runner
`MIGRATION-BLUEPRINT.md` существует, но это **единоразовый план переноса документации** (topics→brain),
не общий механизм эволюции схемы данных. Когда Паспорт (#7, «заложить сейчас») меняет минимальный шейп
(добавляется обязательное поле, переименовывается existing поле) — как мигрируют уже написанные файлы?
Нужен: поле `schema_version` в самом frontmatter каждого узла + реестр migration-скриптов
(v1→v2, v2→v3), применяемых либо batch (пройтись по всем файлам), либо lazily-on-read (мигрировать при
следующем чтении узла, оставить остальные до востребования) — явно решить какой режим дефолт, потому
что смешанная схема (часть файлов v1, часть v2) должна быть READABLE движком без падения, а не
блокировать граф.

## B) Упущенные сценарии (не покрыты нигде в 01-brain/)

1. **Конкурентная запись ДВУХ агентских сессий в один .md-файл** — не «конфликт двух фактов»
   (это уже покрыто `conflicts-with`/Event Anchor #3), а буквальная гонка на уровне ОС/git при
   одновременном сохранении одного файла двумя процессами (два топика gateway работают над одним узлом
   параллельно). Ничего в каталоге не адресует этот случай — весь conflict-протокол семантический,
   не файловый.
2. **Молчаливое расхождение индекса и файла** — пользователь (или другой инструмент) правит .md
   напрямую в редакторе мимо движка; индекс/поиск продолжает отдавать старую версию, ничего не
   сигнализирует о staleness. `Read-scale Index` (#12) говорит про инвалидацию «при изменении
   структуры», но не про источник изменения ВНЕ движка.
3. **Коллизия canonical_id при офлайн/многосессийной генерации** — два агента (разные топики gateway,
   разные claude-сессии) независимо создают узел про «один и тот же» реальный референт и оба минтят
   новый id до того, как второй увидел первый. `union-find слияния классов эквивалентности` упомянут
   как идея (candidates.md #1), но НЕ формализован как процесс — кто и когда его запускает.
4. **Переименование/перемещение файла на диске** — id живёт в frontmatter (хорошо), но если что-то
   резолвит узлы по ПУТИ (не по id) — например скрипт индексации, забывший, что путь не canonical —
   переезд файла рвёт эту связь молча. Не проверено нигде, что весь код резолвит СТРОГО по id.
5. **Оборванная запись при краше** — атомарность записи .md не упомянута нигде; при отсутствии
   write-tmp+rename партиальная запись = битый YAML frontmatter, узел выпадает из графа без
   диагностируемой ошибки (парсер просто падает или молча пропускает узел).
6. **Незавершённая миграция схемы** — если Паспорт (#7) меняется, а миграция накатывается по частям
   (batch прервался), движок должен уметь читать v1 И v2 одновременно; нигде не описан fallback-парсинг
   смешанных версий.
7. **Осиротевшие рёбра при удалении узла ВНЕ движка** (`rm file.md` руками, не через Forgetting
   Engine #9) — tombstone/anti-resurrection специфицирован только для управляемого hard-erase; прямое
   файловое удаление обходит весь протокол, оставляя dangling-ссылки в рёбрах других узлов.
8. **Известный баг-прецедент, подтверждающий риск класса.** Память проекта уже фиксирует «Gateway
   dup-kill bug» — шлюз дублирует голосовое сообщение → дубль убивает фоновых агентов/приходит без
   ответа. Это ЖИВОЙ пример отсутствия идемпотентности/конкурентного контроля на входе (OQ-11 уже
   привязывает это к Ingress Adapter #13), что прямо подтверждает: конкурентность — не гипотетический,
   а уже проявившийся класс проблем в этом проекте.

## C) Главный риск слоя

**Весь 16-модульный хребет (canonical_id, Bitemporal, Edge Engine, Конституция и т.д.) спроектирован на
онтологическом уровне без единого решённого вопроса о физическом write-path.** `data-canon/INDEX.md` —
пустая площадка. Ни один документ не говорит: кто в конечном счёте пишет байты на диск, что случается
при одновременной записи, атомарна ли запись, как индекс держится в синхроне с файлами-истиной, как
эволюционирует сама схема frontmatter. Это не абстрактный риск «на будущее» — проект УЖЕ работает в
режиме многосессийного параллелизма (каждый топик gateway = своя claude-сессия, несколько тем 01-brain
разрабатывались параллельно 7 агентами в один день 2026-07-09) и уже поймал live-баг именно в этом
классе (dup-message). **Ретрофит здесь буквально невозможен в том же смысле, что и canonical_id/Bitemporal
— если формат записи не атомарен и не разрешает конкуренцию с первого файла, тихая порча графа
начинается до того, как кто-то это заметит**, и её нельзя починить ретроактивно без ревизии истории
git и восстановления утраченных рёбер вручную.
