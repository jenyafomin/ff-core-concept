# REPORT — Классы данных по «температуре»: живое vs холодное (prior art)

> Дата: 2026-07-05 · Статус: draft · Автор: Opus (inline, по знаниям) · Шов Р-2
> Питает цели: Г13 (масштаб по температуре), Г7/Г14, У-1 (спектр-температура)

## 1. Storage tiering — отрасль давно делит данные по «жару»

- **Hot / Warm / Cold / Frozen(archive)** — стандарт (AWS S3 storage classes, Elastic ILM, Snowflake). Критерий перехода — НЕ тип данных, а **паттерн доступа**: частота чтения, возраст, recency последнего доступа. Горячее — дорогое хранилище/быстрый доступ; холодное — дёшево/медленно.
- **Data Lifecycle Management (ILM/DLM)** — политики «через N дней без доступа → понизить tier; через M → архив». Точный аналог **фаз фокуса** владельца: не бинарно, а лесенка, управляемая политикой.
- Ключ: **один логический объект — разные физические режимы.** Пользователь не меняет форму данных, меняется только политика хранения/доступа. Это ровно «один контракт, разные режимы».

## 2. CQRS — одна сущность, два представления

- **Command Query Responsibility Segregation:** пишущая модель (нормализованная, транзакционная) ≠ читающая модель (денормализованная, оптимизированная под запрос). Одна сущность материализуется в оба.
- Перенос: **живое** = write-side (часто меняется, дорого пересматривается); **холодное/аналитика** = read-side (проекции, индексы, сводки). Наша «волна/частица» = тот же принцип: частица (write, истина) ↔ проекции (read, дёшево).
- Важно: CQRS оправдан ТОЛЬКО при явной асимметрии нагрузки чтение≫запись. Не вводить его повсеместно — только для холодных корпусов (20 тыс. юзеров).

## 3. Lambda / Kappa — поток vs батч

- **Lambda:** быстрый живой слой (свежее, приблизительное) + батч-слой (полное, точное, пересчитывается). **Kappa:** всё как поток, батч — частный случай.
- Перенос: **живое** = streaming-слой (Episodic/trace, приходит потоком из адаптеров — связь с Г22); **холодное** = батч-консолидированные проекции. Материализованные представления (continuous aggregation) = наши предвычисленные саммари-узлы (Г3 rollup).

## 4. Где граница «живое / холодное» и по каким метрикам

Граница — НЕ по содержимому, а по **профилю жизни**. Метрики «температуры» ячейки:

| Метрика | Живое | Холодное |
|---|---|---|
| **Частота ПЕРЕоценки** (как часто пересматривается истинность) | высокая | ~0 |
| **Волатильность** (скорость протухания) | высокая | низкая/нет |
| **Объём класса** | мал | велик (тысячи+) |
| **Способ доступа** | по salience/резонансу (push) | по фильтру/поиску (pull, query) |
| **Нужен ли метаболизм** (фаза C) | да | нет (только lifecycle-архивация) |

## 5. Рекомендация

- **`temperature` — не поле-тип, а РЕЖИМ, вычисляемый из профиля доступа** (или назначаемый политикой типа). Один паспорт, разные значения λ (спад) и флага «участвует ли в salience-метаболизме».
- **Два режима как минимум, но континуум:**
  - **LIVE** — участвует в salience/забывании/консолидации (Р-1). Память агента, решения, статусы.
  - **COLD/REFERENCE** — НЕ забывается по salience; доступ только через запрос/индекс/фильтр; lifecycle-архивация по возрасту. 20 тыс. пользователей, аналитика, справочники. ⚠️ это мостик к Р-4 (федерация: холодные корпуса ⇒ кандидаты на вынос во внешнюю БД за API).
- **Назначение режима:** дефолт по типу-узлу (control-plane тип несёт политику), переопределяется по фактическому профилю доступа (auto-tiering).
- **Не плодить форматы:** и LIVE, и COLD — тот же тонкий паспорт; отличаются ТОЛЬКО политикой (веса salience, TTL, участие в фазе C). Это защищает Г13 «один контракт на разнородность».

**Риск:** авто-tiering по доступу может «заморозить» редкое-но-критичное (как LFU) — нужна защита importance-флагом (никогда не остывать), перекликается с Г11/В1 «что не забывать никогда».
