# REPORT — Проявление в пространстве: варианты/ветки · федерация через API · scope-приватность (prior art)

> Дата: 2026-07-05 · Статус: draft · Автор: Opus (inline, по знаниям) · Шов Р-4 (новые грани владельца)
> Питает цели Г21-Г27 + открывает кандидаты Г28+

## Шов 1 — Варианты / версии / ветки данных

Сценарий владельца: «разные варианты плана недели; при планировании переключаю ВЕТКУ; каждый вариант = независимая ячейка, возможно не связанная с другими».

- **Git-модель (ветки + commits + HEAD).** Вариант = ветка; «текущий план» = HEAD-указатель; переключение = смена активной ветки. Ключ: варианты НЕ обязаны знать друг о друге, но общий предок виден. **Datomic / Dolt** — реальные БД с git-подобным ветвлением данных.
- **Event sourcing** — состояние = свёртка событий; можно отмотать/переиграть. Даёт «как было в момент X» (Г9 аудит).
- **Bitemporal** (из Р-3) — варианты во valid-time.
- **Рекомендуемый паттерн:** **вариант = самостоятельная ячейка (own id), сгруппированная ребром `variant-of` к «якорю выбора»; активность = отдельное ребро `active`/HEAD на якоре.** Варианты между собой НЕ связаны (как хотел владелец) — связь только через якорь. Отображение связанности = веер от якоря.

## Шов 2 — Федерация внешних данных через API

Сценарий: модуль с огромными данными выносится в свою БД, сам управляет; достаётся через API; кэш с жёстким удалением.

- **Data Federation / Virtualization** (Trino/Presto, GraphQL federation) — единый запрос к данным, физически лежащим в разных источниках; они НЕ копируются внутрь.
- **Foreign Data Wrapper** (Postgres FDW) — внешняя таблица выглядит локальной, читается по требованию.
- **CDC (Change Data Capture)** — если нужна синхронизация, а не live-fetch.
- **Materialization vs live-fetch + cache-invalidation** — классический trade-off: держать копию (быстро, риск устаревания) vs тянуть вживую (свежо, дорого); кэш с TTL/жёстким сбросом посередине.
- **Рекомендуемый паттерн:** **ячейка-ПРОКСИ** (по мотивам FDW + nanopublication-обёртки): в графе лежит лёгкая ячейка = {паспорт + `source-ref`(коннектор+инструкция достать) + опц. кэш + политика инвалидации}. Payload материализуется по запросу. Так «20 тыс. пользователей» живут во внешней БД, а в графе — одна прокси-ячейка-указатель. **Коннектор/адаптер конфигурируется из общего конфига** (Г22) → тип-узел «connector» в control-plane.

## Шов 3 — Scope-приватность и роли («свой мир»)

Сценарий: к проекту подключают кого-то, кто видит НЕ всё; у проекта «свой мир»; роли/задачи; наследование и переиспользование.

- **RBAC** (роль→права) vs **ABAC** (атрибуты субъекта×ресурса×контекста → решение). ABAC гибче для «видит не всё».
- **Row/Field-level security** (Postgres RLS) — фильтр видимости на уровне СТРОКИ/ПОЛЯ, не таблицы. Прямой аналог: разные роли видят разные ЯЧЕЙКИ/грани одной ячейки.
- **Capability-based** — доступ = обладание «ключом-возможностью», а не проверка списка. Хорошо для plug-in/маркетплейса (Г19): плагину выдаётся capability на узкий срез.
- **Multi-tenant изоляция** — «свой мир» проекта = tenant; данные одного не текут в другой без явного шеринга.
- **Рекомендуемый паттерн:** **sensitivity + scope на паспорте → ABAC-линза (уже класс линзы в каноне) решает видимость per-роль; проект = tenant-граница; шеринг = явное capability-ребро.** Наследование/переиспользование = ребро `derives-from`/`instance-of` к шаблону-типу.

## Новые грани ценности (кандидаты-цели Г28+)

- **Г28. Быть вариантом без обязательной связи с другими вариантами** — «веер от якоря», переключаемая активная ветка.
- **Г29. Быть указателем на внешний источник** — прокси-ячейка: паспорт локально, payload по API + кэш + инвалидация (не тащить большие корпуса в граф).
- **Г30. Конфигурироваться из общего конфига через адаптер** — единый источник настроек коннекторов; данные из разных источников пересекаются по общим id (Г22).
- **Г31. Показывать себя по-разному разным ролям** — field/row-level видимость; «свой мир» проекта; capability-шеринг (расширяет Г18/Г24).
- **Г32. Наследовать/переиспользоваться** — ячейка-шаблон → экземпляры; тип со своей структурой (Г26); DRY на уровне знания.
- **Г33. Хранить инструкцию, КАК себя достать** — не только данные, но и «рецепт доступа» (для внешних/дорогих) — самодостаточность прокси.
- **Г34. Быть материализуемой на выбор** — жить как live-fetch, как кэш или как полная копия — по политике, прозрачно для читателя.

## Замечание (мостики)
- Холодные корпуса (Р-2, COLD-режим) — естественные кандидаты на прокси-ячейки (Шов 2): не забываем, не тащим внутрь, держим за API.
- Варианты (Шов 1) + bitemporal (Р-3) + salience (Р-1) сходятся: «забытый вариант» = ветка с низким salience, не удалённая.
- Приватность (Шов 3) опирается на уже существующий в каноне класс линзы-политики (ABAC) — новых механизмов почти не надо, надо сделать sensitivity/scope несущими.
