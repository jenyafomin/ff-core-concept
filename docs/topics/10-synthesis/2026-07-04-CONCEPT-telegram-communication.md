# КОНЦЕПТ — Telegram-коммуникация системы агентов

## 1. Суть

Telegram — не «чатик», а **канал-проекция графа**: каждое сообщение в обе стороны — узел графа со связями;
Telegram показывает срез, истина живёт в БД. Из этого следуют три правила:

1. **Ничего не теряется**: Bot API не даёт боту ни истории, ни поиска — значит своя БД является
   ЕДИНСТВЕННОЙ историей. Каждое сообщение (вход и выход) пишется как узел с `message_id`.
2. **Каждое сообщение самоопознаваемо**: хедер говорит, кто/откуда/о чём; reply на него однозначно
   маршрутизируется, потому что `message_id` ищется в графе.
3. **Не изобретать**: gateway уже имеет ingress `chat:thread → conversationId → sessionKey`, хедеры,
   reply-параметры исходящих, callback-парсер `gw:approve:<jobId>`. Концепт достраивает недостающее
   (нарезка, кнопки-клавиатуры, сохранение `message_id`, reply-ingress), не заменяя работающее.

Паттерн целиком: **Anti-Corruption Layer** на границе Telegram (нормализация ↔ проекция) + **Outbox**
(узел сообщения в БД — истина, отправка в Telegram — доставка проекции).

## 2. Большие сообщения и группировка

### 2.1 Egress-политика (нарезка/вложения) — сейчас в gateway нарезки НЕТ, >4096 падает

Ступенчатая политика в egress-слое (`TelegramChannel.send` оборачивается в `EgressComposer`):

| Объём ответа | Форма доставки |
|---|---|
| ≤ ~3500 симв. | одно текстовое сообщение |
| ≤ ~7000 симв. | 2–3 текстовых куска с маркером `(i/N)`, резка по границам абзацев/код-блоков (не посреди fence) |
| больше, или несколько файлов | **резюме-сообщение** (≤ ~1000 симв.: вердикт, 3–5 пунктов, что решить) + **.md-вложение** целиком (`sendDocument`, caption ≤ 1024) — ровно конвенция `bundle-md.mjs` «группируй в один файл» |

### 2.2 «Древовидная структура, разные фильтры, разные виды»

Telegram не рендерит деревья — дерево эмулируется тремя видами одного содержимого:

- **Вид «резюме»** — текст в чате (всегда).
- **Вид «раздел»** — inline-кнопки под резюме («📂 Детали», «📊 Данные», «⚠ Риски»); нажатие →
  callback → бот присылает раздел отдельным сообщением (или редактирует резюме). Это drill-down:
  владелец сам выбирает глубину.
- **Вид «полный»** — .md-вложение (открывается любым редактором, остаётся в чате как файл).

Фильтры = какие кнопки-разделы генерируются; определяется типом ответа (анализ/план/вердикт).

### 2.3 Группировка потоков: сравнение (⚑ развилка 1)

| Механизм | Плюсы | Минусы |
|---|---|---|
| **Форум-топики** (одна супергруппа с топиками) | ingress уже готов (`chat:thread`); нативная навигация в UI; pinned-README на топик; entity `topics` в БД уже есть | нужна супергруппа + право бота `can_manage_topics`; всё в одном чате |
| Reply-нити в одном чате | ноль настройки | Telegram не группирует reply визуально; навигации нет; захлебнётся на 3+ параллельных потоках |
| Отдельные боты на проект | жёсткая изоляция; gateway мультибот-ready (`bots/agents/agent_bindings`) | N токенов и чатов; кросс-проектный вид теряется; тяжелее в операциях |

**Рекомендация архитектора:** форум-топики как основной механизм (топик = проект/направление,
`chat:thread` уже маппится в сессию); отдельные боты — резерв на этап внешних пользователей
(multi-tenant), не для владельца.

## 3. README-статус и хедеры

### 3.1 README-статус топика

**Закреплённое (pinned) сообщение в каждом топике, редактируемое на месте** (`editMessageText` +
`pinChatMessage`): где мы находимся (фаза/этап лупа), какие сессии живы и их статус, что важно сейчас,
как отвечать (мини-инструкция по reply). Правки pinned-сообщения не шлют уведомлений — это фича:
живой дашборд без спама. Канон статуса — узел в графе; pinned-сообщение — его проекция (перерисовка
по событиям: старт/финиш job, развилка, approve).

### 3.2 Хедеры (развитие существующего)

Сейчас: `🤖 <agent> · <model> · 💰 $X (Σ $Y)` (`reply-header.util.ts`, env `GATEWAY_REPLY_HEADER`),
в БД хранится сырой текст без хедера — это правильно, сохранить. Развитие — вторая строка контекста:

```
🤖 researcher · sonnet · 💰 $0.42 (Σ $3.10)
📍 FF/tree-test · sess a1b2 · ↩︎ ответ | ❓ вопрос | 🔐 апрув · #m-7f3k
```

- тип сообщения (ответ сессии / вопрос владельцу / запрос апрува / развилка ⚑) — задаёт ожидание,
  что делать с сообщением;
- `#m-7f3k` — короткий id узла сообщения: любое сообщение адресуемо текстом («по m-7f3k — согласен»),
  даже без reply. Хедер — проекция, собирается из узла при отправке; «обыгрывание по-своему» = шаблон
  хедера зависит от типа узла.

## 4. Reply-маршрутизация

**Предусловие (главный пробел кода):** gateway НЕ сохраняет telegram `message_id`
(`IMessageRow` его не имеет) и НЕ читает входящий `reply_to_message`. Без соответствия
`(chat_id, message_id) → узел` никакая reply-семантика невозможна. Первый шаг любой реализации —
писать `message_id` для обоих направлений.

Алгоритм ingress при reply (детерминированный, по типу узла-цели):

```
reply_to.message_id → lookup узла в БД
├─ узел = вывод сессии S        → продолжение сессии S (route в её sessionKey)
├─ узел = вопрос/развилка ⚑     → это ОТВЕТ на вопрос: привязать edge answers→, доставить job'у-автору
├─ узел = запрос апрува         → трактовать как решение (текст/кнопка), передать в ApprovalGate
├─ узел = ретрансляция от человека P → маршрут человеку P (relay)
└─ узел не найден (до начала записи / чужое) → fallback: кнопки «в сессию X / новый вопрос / игнор»
```

Без reply — как сейчас: активная сессия топика (`conversationId`). Неоднозначность (reply на старое
сообщение закрытой сессии) — переспрос кнопками, не угадывание (⚑ развилка 4: порог эвристики).
Оговорка Bot API: reply на сообщения САМОГО бота доставляются боту всегда; reply на сообщения третьих
лиц в группе при включённом privacy mode бот может не увидеть.

## 5. Модель сообщения-узла (стык с единой БД)

Telegram-сообщение = **один тип узла графа** (agent-first, msg 141), не спецхранилище.
Паспорт — тонкий по ADR-0002, **0 новых несущих полей**: вся telegram-специфика (`channel`,
`direction`, `tg.*`) — в **payload** типа `message`, не в паспорте. Автор — НЕ `principal`
(в ADR-0002 principal = арендатор/scope, другая ось): автора выражает ребро `actor`,
происхождение — типизированное поле `source`.

```yaml
node:
  id: m-<ulid>              # короткая форма — в хедер (#m-7f3k)
  type: message             # паспорт: только стандартные поля ADR-0002
  payload:                  # типо-специфика, НЕ паспорт
    channel: telegram
    tg: { chat_id, message_id, thread_id? }  # canonical_id = (channel, chat_id, message_id) — ключ reply-lookup и дедупа
    direction: in | out
    source: human | agent | system
    ts: <iso>
    text: <сырой текст, БЕЗ хедера>          # хедер — проекция, не данные
    attachments: [<id файловых узлов>]
edges:
  actor        → person|agent  # автор входящего / отправитель исходящего
  addressed_to → person        # адресат исходящего (когда есть)
  in_reply_to  → message       # из reply_to_message
  in_session   → session       # текущий sessionKey
  in_topic     → topic         # entity topics уже есть в gateway
  answers      → question|fork
  about        → task|job
```

**Контракт стыка** (для концепта «единая БД»; механика = Outbox):
1. **Gateway пишет только к себе**: таблица `messages` в `gateway.db` — **TRANSITIONAL
   outbox-журнал** (переходный буфер, НЕ долгосрочная истина; её судьба — развилка E концепта БД).
   Движок графа **забирает записи асинхронно с ack**; до подтверждения запись живёт в outbox.
   Так доступность бота не зависит от движка («упал движок — рантайм жив»).
2. **Идемпотентность по `canonical_id (channel, chat_id, message_id)`**: повторный ingest не
   создаёт дубля; обязательный индекс `canonical_id → node.id` — он же ключ reply-lookup (§4).
3. Существующая схема (`id, sessionKey, botId, direction, userId, username, text, ts, refs,
   costUsd`) — почти готовая outbox-запись: добавить `tg.*` (message_id!) и признак ack.

Больше ничего о структуре БД этот концепт не диктует.

## 6. Кнопки, доступы, опросники

- **Approve/reject кнопками — минимальный диф:** обработчик `callback_query` и парсер
  `gw:approve:<jobId>` в коде УЖЕ есть, клавиатура просто нигде не отправляется. Доработка —
  `ApprovalGate.request` шлёт `InlineKeyboard` [✅ Approve | ❌ Reject] с готовыми callback-данными.
  Текстовые /approve /reject остаются как fallback.
- **Запрос недостающих прав** (§3c плана): агенту не хватает права → gateway (движок, не агент —
  жёсткие правила енфорсит движок) шлёт владельцу карточку: что, кому, зачем + кнопки
  [разово | на сессию | навсегда | отказ], callback `gw:grant:<reqId>:<scope>`. Решение пишется
  узлом-decision в граф (аудит выдачи прав). Ограничение: callback_data ≤ 64 байт → в кнопке только
  короткий id, payload в БД.
- **Опросники-conversation:** стейт-машина «вопрос → кнопки → следующий вопрос», состояние — узел
  survey в БД (не в памяти процесса — переживает рестарт); реализация — плагин
  `@grammyjs/conversations` либо своя FSM поверх callback. Нативный `sendPoll` — для простых
  множественных выборов; оговорка: в каналах опросы анонимны, в группах можно неанонимные.

## 7. Карта возможностей (честный ответ на «всё ли реально?»)

Статусы: ✅ есть в gateway · 🔧 возможно средствами Bot API (в gateway нет) · ⚠️ возможно с оговорками · ❌ невозможно.

| Возможность | Статус | Комментарий |
|---|---|---|
| Хедеры исходящих сообщений | ✅ | `reply-header.util.ts`; развить контекст-строкой (§3.2) |
| Топик → сессия (ingress) | ✅ | `chat:thread → conversationId → sessionKey` |
| Бот отвечает reply'ем на сообщение владельца | ✅ | `reply_parameters` из `job.origin` |
| Управление сессиями из Telegram | ✅ | /new /resume /compact /fork |
| Нарезка сообщений > 4096 | 🔧 | в gateway нет — большие ответы сейчас падают (подозрение владельца верно) |
| .md-вложения / документы | 🔧 | `sendDocument` до 50 МБ, caption ≤ 1024; в gateway нет |
| Создание форум-топиков ботом | 🔧 | `createForumTopic`; нужна супергруппа + право can_manage_topics |
| Pinned README-статус с правками | 🔧 | `editMessageText`+`pinChatMessage`; правки не пушат уведомления (фича) |
| Inline-кнопки approve/reject | ⚠️ | наполовину готово: callback-парсер есть, клавиатуры не шлются; малый диф |
| Reply-маршрутизация по message_id | ⚠️ | Bot API даёт `reply_to_message`, НО gateway не хранит message_id (пробел §4); сообщения до включения записи — неопознаваемы навсегда (истории нет) |
| Кнопка «выдать право» | 🔧 | расширение ApprovalGate (§6); енфорс движком |
| Опросники | 🔧 | кнопки-FSM или `sendPoll` (в каналах — только анонимные) |
| Прогресс через редактирование сообщения | ⚠️ | задел `TelegramMessageHandle.edit` есть; rate-limit ~1 сообщение/сек на чат, 20/мин в группе — редактировать по вехам, не по токенам |
| Markdown-форматирование | ⚠️ | parse_mode сейчас не задан (plain); MarkdownV2 требует эскейпинга (`md2tg.mjs` уже есть), HTML надёжнее (⚑3) |
| Дерево/фильтры «как в UI» | ⚠️ | Telegram не рендерит деревья; эмуляция тремя видами (§2.2): резюме+кнопки+вложение |
| История/поиск чата средствами бота | ❌ | Bot API принципиально не даёт боту историю и поиск — потому БД-запись каждого сообщения (§1, §5) обязательна, это не опция |
| Reply на сообщения третьих лиц в группе | ⚠️ | при privacy mode может не доставиться боту; reply на сообщения самого бота — доставляется всегда |

## 8. ⚑ Развилки владельцу

1. **Группировка потоков:** форум-топики (рекомендация §2.3) vs отдельные боты vs reply-нити.
   Решает форму всей коммуникации — первая развилка по порядку.
2. **Порог «резюме + вложение»:** предложено ~7000 симв. (≈2 куска текста); подтвердить/сдвинуть.
3. **parse_mode:** MarkdownV2 (красивее; `md2tg.mjs` уже есть; хрупкий эскейпинг) vs HTML (надёжнее,
   выглядит так же) vs plain (как сейчас). Рекомендация: HTML в egress-слое.
4. **Неоднозначный reply:** всегда переспрашивать кнопками vs эвристика по типу узла с переспросом
   только при неуверенности (рекомендация — второе).
