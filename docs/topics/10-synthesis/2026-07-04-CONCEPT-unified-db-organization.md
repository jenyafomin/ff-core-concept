# CONCEPT — Единая БД + ОРГАНИЗАЦИЯ

## 0. Суть одним абзацем

«Единая БД для (почти) всех проектов» — это **один логический граф узлов** (одно пространство `id`,
один паспорт, один движок-хранитель), а не «один физический файл, куда складывают всё». Единица
централизации — **контракт** (паспорт ADR-0002 + движок ADR-0004 + один writer), физика — деталь.
Граф живёт в **ОРГАНИЗАЦИИ** — папке-уровне «организация деятельности» рядом с `PROJETS/`: дерево
знаний, агенты, планирование. Проекты не получают копий и не держат свои экземпляры базовых вещей —
они **подключаются** к одному графу (ровно модель распространения из плана §1a). «Умные папки»
владельца — не новый механизм: это композиция уже ратифицированных примитивов (группа-узел +
home-каскад + категории-фасеты + паттерны + линзы). Честных новых дельт у концепта две:
**два класса хранения** узлов (authored: md=истина ⟂ stream: БД=истина), без которых «сохранять ВСЕ
telegram-сообщения» и «каждый агент логирует каждое действие» взорвут файловую модель, — и
**отчуждаемый pack-формат подграфа** (§4a.5), без которого marketplace-механика плагинов невозможна.

## 1. Что такое единая БД и что такое ОРГАНИЗАЦИЯ

### 1.1 Разделение, которое всё упрощает: план знаний ⟂ план исполнения

В экосистеме уже есть ДВЕ базы, и это правильно — они разные по природе:

| План | Что в нём | Истина | Пример сегодня |
|---|---|---|---|
| **План знаний** (единая БД) | всё, над чем ДУМАЮТ и что КООРДИНИРУЮТ: задачи, планы, инструкции, доки, сообщения-записи, трейсы, сессии-записи, люди, проекты-карточки, память агентов, политики | граф (движок + файлы) | FF-граф (проектируется) |
| **План исполнения** (рантайм модулей) | мгновенное состояние машин: очереди jobs, process leases, блокировки, живые websocket/поллинг | рантайм-хранилище модуля | `gateway.db` (jobs, leases) |

**Правило границы:** *если организация/агенты рассуждают об этом или это нужно завтра — это узел
графа; если это живёт секунды-минуты и нужно только процессу — это рантайм модуля, а его
ДОЛГОВЕЧНЫЕ события журналируются в граф.* Gateway остаётся со своим `gateway.db` для очередей,
но каждое сообщение, сессия, решение об approve — становится узлом единого графа. Это то же
CQRS-разделение, что уже принято в движке («файлы = истина содержимого, движок = истина структуры»),
поднятое на уровень экосистемы: **граф = истина ЗАПИСИ, рантайм = истина МОМЕНТА.**

Так «централизация без обходов» выполняется там, где она осмысленна — в плане знаний ровно ОДНА
база, без исключений и без копий. А очередь jobs в gateway — не «обход централизации», потому что
она вообще не знание: пересоздаваема, никем не читается задним числом.

**Контракт коннектора gateway→граф (принят по кросс-ревью с CONCEPT-telegram-communication):
OUTBOX-паттерн.** Gateway пишет ТОЛЬКО в свой `gateway.db`; его таблица `messages` = outbox;
движок забирает записи асинхронно с ack; идемпотентность — по `canonical_id`
(`channel, chat_id, message_id`): повторный забор не создаёт дублей. Терминология:
**gateway = единственный ПРОДЮСЕР узлов `message`; движок = единственный WRITER графа.**
Это снимает кажущееся противоречие «упал движок — рантайм жив» vs «один writer»: gateway
продолжает принимать и копить в outbox, граф догоняет после подъёма; истина записи всё равно
проходит через один enforcement-пункт.

### 1.2 «Может вырасти вплоть до целого проекта внутри»

Путь роста встроен: проект может жить в графе ЦЕЛИКОМ — его доки, задачи, планы, спеки, диалоги,
аналитика = узлы; код остаётся в git и представлен href-узлами («git = книга, узел = карточка» —
решено ещё в ADR-0001 и сохранено). То есть «проект внутри БД» = проект, чья вся организационно-
знаниевая часть — узлы, а бинарно-кодовая — по ссылке. Ничего нового изобретать не нужно.

### 1.3 ОРГАНИЗАЦИЯ — место на диске

```
~/Documents/IT/Apps/
├── ОРГАНИЗАЦИЯ/            ← организация деятельности: ДАННЫЕ + управление
│   ├── graph/              ← единая БД: SQLite-структура + md-тела authored-узлов
│   ├── docs/ …             ← канон/планы (до миграции в граф; потом — проекция графа)
│   └── (управляющие сессии, планирование)
├── CORE/                   ← КОД переиспользуемых модулей (agent-gateway, doc-system, @ff/core)
└── PROJETS/                ← прикладные проекты (dwizh · CRM-Rent · jenek · Cardex · music-video)
```

Три роли не смешиваются: **ОРГАНИЗАЦИЯ = состояние и управление** (данные графа, планирование,
центр управления), **CORE = исходники модулей** (код движка и gateway живёт тут, отдельными
git-репо), **PROJETS = прикладные проекты** (подключаются к графу коннекторами/агентами).
Сегодняшний `FF-Personal-Managment` — это фактически ОРГАНИЗАЦИЯ в зачатке (граф + управляющие
сессии + канон) плюс код `@ff/core`, которому место в CORE. ⚑ Развилка B: FF переименовывается
в ОРГАНИЗАЦИЮ или ОРГАНИЗАЦИЯ создаётся заново, а FF вливается.

## 2. Умные папки: альтернативы и выбор

Запрос владельца: «единое — как дерево, папки, но каждая папка по-своему умная»: (а) группа даёт
логику всему внутри; (б) есть известные системе файлы — README/топики, «важно знать все топики
глобально»; (в) подгруппы/домены с известными значениями для фильтрации и индексации; (г) у значений
своя специфика и логика.

### 2.1 Рассмотренные способы выразить «ум» папки

**Вариант A — папка = обычный узел-группа + композиция существующих примитивов** ✅ выбран.
Никакого рода «SMART-FOLDER» нет. «Ум» набирается из четырёх уже ратифицированных механизмов:

| Просьба владельца | Механизм (уже есть) | Где решено |
|---|---|---|
| (а) «группа даёт логику всему внутри» | **home-каскад**: группа — home-родитель; по home-спине наследуются sensitivity-дефолты, дефолтная линза, теги-категории | ADR-0002 §2а (BELONGING) |
| (б) «известные файлы: README/топики» | **типизированные узлы** `type: topic` / `type: index`; «знать все топики глобально» = производный индекс движка (`filter(type=topic)`), а не ручной список | паспорт `type` + движок V1/V5 |
| (в) «подгруппы/домены с известными значениями → фильтровать» | **категории-фасеты**: `facet-of` → узел-категория; иерархия — `subcategory-of`; фильтрация — предикат линзы | SYNTHESIS-smart-categories 1a |
| (в') значения, которые ДИКТУЮТ форму записи | **вариант-тип**: `variant-of` + delta-схема; дискриминатор в паспорте `schema` | SYNTHESIS-smart-categories 1b, INV-SC1/SC2 |
| (г) «у значений своя специфика и логика» | логика раскладывается по трём родам: ТИП (валидация формы) · ЛИНЗА (проекция/сортировка/доступ) · ПАТТЕРН с `when_scope` (авто-связи только внутри группы); енфорсит движок | ADR-0002 §4, INV-SC3 |

**Вариант B — новый род control-plane «умная папка»** ❌ отклонён. Тот же аргумент, которым
ADR-0002 §4 отклонил ПОЛИТИКУ как 4-й род: всё поведение «умной папки» — сумма контрактов уже
существующих родов; новый род дублирует оси и раздувает ядро (анти-N-040). Папка, которой нужна
своя форма записей, — это вариант-тип; папка, которая красит членов, — категория; папка, которая
что-то делает при попадании внутрь, — паттерн со scope.

**Вариант C — логика в файловой системе** (конфиг-файлы в папках, à la `.claude/` per-folder,
роутеры `&README.md` из dwizh) ❌ отклонён как НОСИТЕЛЬ, принят как ПРОЕКЦИЯ. ФС даёт файлу ровно
одного родителя — это ломает главное преимущество БД над ФС (D-C: «файл живёт в одном месте, узел —
в нескольких», подтверждено потребностью владельца «файл живёт 3-4 раза», план §1a). Дерево папок,
которое видит владелец, — это **проекция home-спины**, которую движок может материализовать в ФС
(и роутер-README dwizh становится проекцией узла `type: index`). Ум живёт в узлах, рендерится где угодно.

### 2.2 Ключевая инверсия (ментальная модель)

> **Не «папки, которые поумнели», а «граф, который умеет притворяться папками».**
> Папка = группа-узел. Её «ум» = четыре подключаемых слота: каскад-дефолты (home-спина) ·
> известные дети (типизированные узлы + глобальный индекс) · оси фильтрации (фасеты/варианты) ·
> поведение (паттерны со scope, линзы). Любая папка набирает свой «ум» из этих слотов данными,
> без кода и без новых механизмов.

Дисциплина соблюдена: 0 новых полей паспорта, 0 новых родов control-plane, 0 новых механизмов.
Рост — горизонтальный (новые типы в открытом реестре: `topic`, `index`, `project`, `session`…).

## 3. Модели данных ключевых сущностей

Все сущности — обычные узлы с тонким паспортом (9 обяз. + 2 опц. полей, без изменений). Ниже —
только типо-специфика: payload, рёбра, класс хранения (см. §4.0 про классы).

### 3.0 Два класса хранения — честная новая дельта ⚑

«Файлы = истина» писалось про авторский контент. Милллион telegram-сообщений и «каждый агент
логирует каждое действие» дают миллионы крошечных узлов — файл-на-узел здесь абсурден (это те самые
«структурно-плоские классы» из ADR-0002 Consequences). Предлагаемое уточнение (расширяет OQ-1 ADR-0004):

- **authored-класс** (доки, задачи, планы, инструкции, идеи, синтезы — всё, что пишет человек/агент
  как содержимое): md-файл = истина ТЕЛА, SQLite = истина структуры. Как в ADR-0004.
- **stream-класс** (сообщения, трейсы, лог-записи, метрики — импортируемые/порождаемые потоки):
  **SQLite = истина целиком** (паспорт+payload в БД), append-only; md-материализация — по требованию
  (экспорт/просмотр), не хранение. Формула становится: «**авторские файлы = истина; потоки = истина
  в БД; структура = истина в движке**».

Класс хранения задаёт ТИП узла (в реестре типов), не автор. Это ⚑ развилка A владельцу — уточнение
принципа «файлы=истина», того же ранга, что OQ-1.

### 3.1 Telegram-сообщения (владелец: «сохранять ВСЕ, с message_id»)

- `type: message` · stream-класс · `source: human|import` · `level` дефолт `data`.
- payload: `text`, `channel: telegram`, `chat_id`, `message_id`, `author`, `ts`, `attachments[href]`.
- Идентичность: `canonical_id` от движка по ключу `(channel, chat_id, message_id)` — дедуп при
  повторном импорте гарантирован, «коннект» с Telegram всегда восстановим.
- Рёбра: home → узел-сессия (или узел-чат, если вне сессии); `in-reply-to` → сообщение;
  `facet-of` → топики; `about` → узлы, которых касается (проставляет движок/агент как `derived`).
- Голосовые: узел-сообщение + href на аудио + дочерний authored-узел транскрипта.

### 3.2 Логи действий (пользователь и агенты)

- `type: trace` · stream-класс · `source: system|agent`. ADR-0002 уже требует трейс-узлы для
  промоушенов — это расширение того же механизма на все действия.
- payload: `action`, краткие `args`, `result`, `cost/tokens?`.
- Рёбра: `actor` → узел-агент/человек · home → сессия · `touched` → задействованные узлы.
- Источник трейсов — два уровня: gateway видит только ХОДЫ (сообщение → job → ответ);
  действия ВНУТРИ сессии Claude (tool-calls, правки файлов) поставляет runner/hooks.
  Оба потока идут в граф через тот же outbox-контракт §1.1.
- Инвариант: трейсы пишет только движок/gateway (не сам агент о себе задним числом) — иначе
  наблюдаемость становится самоотчётом.

### 3.3 Сессии и их связи

- `type: session` · authored-класс (тело — резюме сессии; поток событий — трейсы рядом).
- payload: `gateway_session_key`, `project_path`, `model`, `status`, резюме-итог.
- Рёбра: `actor` → агент · `about` → проект/направление · home → группа сессий направления ·
  **`forked-from` / `resumed-from`** (ровно /fork /resume gateway) · `spawned-by` → сессия-оркестратор ·
  `produced` → узлы-результаты · `instructed-by` → инструкция/луп (§3.4).
- Так «навигация коммуникации агентов» (самая слабая часть по D-B) становится запросом по графу:
  кто над чем работает = `filter(type=session, status=active)` + линза с бюджетом (`getContext`).

### 3.4 Задачи · планы · инструкции-лупы (IDEA-loop-instructions)

- Три рода управляющих данных = три типа: `task` (что) · `plan` (в каком порядке) · `instruction`
  (КАК работать). Луп = `instruction` с дочерними `stage`-узлами (`seq` назначает движок),
  каждая stage несёт exit-условия; **луп без выхода отклоняется валидатором типа**.
- Задача может нести инструкцию: ребро `instructed-by` либо встроенный промпт в payload.
- Ступенчатая видимость («агент видит свой этап детально / весь луп по переключению») = две ЛИНЗЫ
  над лупом — механизм уже есть, ничего нового.
- Текущая итерация = состояние сессии: ребро `at-stage` от session-узла к активному stage.

### 3.5 Проекты · модули · аналитика портфеля (D-E)

- `type: project` (карточка: путь, статус, приоритет) · `type: module` (home → проект).
- Задача принадлежит нескольким местам сразу: один home + N `facet-of`/`involves` — уже валидировано.
- Аналитика («сколько модулей где; по каким модулям задачи») = **линзы + rollup-поля движка**,
  не хранимые агрегаты; rollup пишет только движок (инвариант №6 engine-синтеза). «Разная
  группировка = разные грани визуализации» = буквально линзы.

## 4. Эксплуатация

### 4.1 Ротация (объёмы: «каждый агент логирует каждое действие»)

Оценка масштаба: ~10 сессий/день × сотни действий = порядка 10⁵–10⁶ трейсов/год. Для SQLite это
немного, но контекст агентов и индексы засоряются. Схема трёх температур, управляется
**узлами-политиками ретенции** (control-plane = данные, по аналогии с promotion-policy; енфорсит движок):

1. **Горячее** — сырые stream-узлы, полный период N дней (⚑ развилка D: N=30?).
2. **Консолидация** — движок сворачивает окно сырых трейсов в authored-узел-резюме
   (`derived`, `rule_ref`) — та же sleeptime-консолидация из ресёрча конкурентов, уже названная
   в плане §3c принципом самоулучшения. Сырьё получает `epistemic: archived`.
3. **Холодное** — archived-партиции (attached archive-БД помесячно); никогда не удаляется
   (конвенция never-delete), но выходит из рабочих индексов.
- Authored-узлы НЕ ротируются никогда — только `archived` + 90-historical-проекция.
- Сообщения владельца («сохранять ВСЕ») — ротация не применяется к телу, только выход из горячих
  индексов; восстановимы всегда.

### 4.2 Кэширование (Redis)

**Redis в v1 — нет.** Сам владелец сказал: сначала оптимизировать без кэша — и архитектура это
подтверждает: движок УЖЕ и есть кэш. CQRS-модель чтения (V1-V9: паспорт-индекс, backlinks, FTS,
heat/recency, кэш производных рёбер) — это материализованный, пересобираемый кэш над истиной;
плюс page-cache SQLite; плюс бюджетный `getContext`. Один пользователь, локальная машина, WAL —
узкого места, которое лечится Redis, здесь нет. Redis добавил бы ВТОРУЮ истину (инвалидация двух
слоёв) и постоянный сервис-демон. Честный триггер пересмотра: измеренная p95 задержка запросов
под реальной мульти-агентной нагрузкой, с профилем, указывающим на повторные вычисления движка, —
не раньше. До этого «кэш» = добавить недостающий производный вид Vn движку.

### 4.3 Путь миграции (от «файлы+md сегодня» к единой БД)

Пять шагов, каждый обратим, ни один не требует big-bang:

- **M0 (сейчас):** docs живут по DOC-CONVENTION; в frontmatter появляются `id` (ULID) — узлы
  рождаются ещё в файлах. Ничего не ломается.
- **M1 (walking skeleton движка):** индексатор читает `tree-test/` → SQLite-индекс (read-only
  производная; файлы = истина). Первый запрос: «все топики глобально» (§2.1б) — тест умных папок.
- **M2 (структура → движок):** записи структуры (рёбра, home, статусы) идут через движок;
  SQLite = истина структуры, md = тело. Это ратификация OQ-1 ADR-0004.
- **M3 (подключение gateway):** сообщения/сессии/трейсы журналируются как stream-узлы (§3.1-3.3).
  С этого момента база растёт сама — bootstrap-петля P3 плана.
- **M4 (проекты-потребители):** карточки проектов/модулей D-E; doc-system-скил читает/пишет граф;
  дерево папок — материализуемая проекция.
- Блокеры-развилки перед M2: OQ-1 (SQLite-для-структуры) и OQ-2 (библиотека-vs-сервис) — см. §6/⚑ C.

## 4a. Плагины / модульность (marketplace-механика; голос 04.07 00:33)

Требование владельца: модульность = скачивание → установка → подключение → расширение; плагин может
быть целой системой агентов со своей памятью и ресурсами, подключаемой к ЛИМИТИРОВАННОЙ области;
плагины саморасширяются вариациями поверх базовых (пример: «спорт» + народные улучшения); БД должна
позволять плагинам «создавать гибкие структуры данных НА ЛЕТУ, контролируемо».

Ключевой вывод: **модель уже спроектирована под это** — `principal` в паспорте обязателен именно
«потому что multi-tenant/маркетплейс заблокированы без него» (ADR-0002), R4 ограничивает сторонние
политики, открытый реестр типов даёт структуры-на-лету. Ничего не изобретаем — раскладываем.

### 4a.1 Жизненный цикл плагина = 4 шага на существующих механизмах

| Шаг владельца | Что это в модели |
|---|---|
| **Скачивание** | импорт **pack'а** — пакета узлов: control-plane (ТИПЫ-`model-def`, линзы, паттерны, инструкции-лупы) + seed-данные. Каждый узел несёт паспорт: `principal` = автор плагина, `source: import`, `epistemic: proposal` (НЕ fact — чужое утверждение не истина по прибытии) |
| **Установка** | регистрация типов в открытом реестре + валидация движком. Жёсткий гейт R4 (ADR-0002): сторонние узлы класса hard-ABAC с `enforce_point: promotion\|valve` **отклоняются** — плагин не может привезти себе политику доступа |
| **Подключение** | выдача **SCOPE**: грант-узел (hard-ABAC-линза от владельца, first-party) на ограниченную область — home-поддерево «дом плагина» + явно перечисленные точки чужого графа. Дефолт — **default-deny** (решение из стресс-теста-2, слой D: «всё видно ИИ» = только first-party; модули/юзеры default-deny) — плагины делают эту ратификацию блокером, ⚑ F |
| **Расширение** | вариации/опции поверх базового — §4a.3 |

### 4a.2 Плагин = целая система агентов со своей памятью и ресурсами

- **Память плагина** = подграф под его `principal` (память агентов = узлы — уже спроектировано в
  SYNTHESIS-agent-memory; здесь просто третий владелец памяти: user ⟂ agent ⟂ plugin).
- **Ресурсы/рантайм** = план исполнения (§1.1): свои процессы, очереди, даже своя рантайм-БД —
  внутреннее дело плагина; всё долговечное журналируется в ЕГО подграф. Граница §1.1 работает
  и для чужого кода без изменений.
- **Лимитированная область** = композиция трёх рычагов, все из ADR-0002/0003: home-поддерево (где
  живёт) + hard-ABAC-линза (что видит) + capability-гранты (что может). Агенты плагина действуют под
  его `principal` → автоматически: `→fact` сторонним запрещён, внешние необратимые действия — только
  через клапан, каждое действие — трейс-узел. Sandbox не строится отдельно — он следует из модели.

### 4a.3 Расширения и вариации («спорт» + чужие улучшения)

- Базовый плагин `sport` привозит типы (`training-plan`, `exercise`, `progression`) — `model-def`-узлы.
- Чужая вариация = **`variant-of` + delta-схема** поверх базового типа (smart-categories 1b: форма =
  base ∪ delta, дискриминатор в паспорте `schema`) — вариация НЕ форкает весь плагин, а наращивает тип.
- Форк/гибрид = новый control-plane-узел с lineage-рёбрами (`forked-from`, два родителя у гибрида) —
  version/lineage-модуль из SWEEP; реестр версионируем по построению (`type@version` в паспорте).
  Механизм «версий и гибридов», который владелец назвал ценной фичей D-F, = рёбра между
  control-plane-узлами, т.е. данные, а не отдельная подсистема.
- Конфликт имён (два `training-plan` от разных авторов) → неймспейс по `principal`
  (smart-categories A5); «какой активен у меня» — выбор владельца, хранится грант-узлом.

### 4a.4 «Гибкие структуры данных на лету, контролируемо» — критерий к самой БД

- **На лету:** новый тип = ЗАПИСЬ control-plane-узла, не миграция и не код. Тонкий паспорт
  гарантирует: движок умеет обращаться с узлом ЛЮБОГО незнакомого типа, не вскрывая payload
  (инвариант несущести) — поэтому чужие типы не могут сломать ядро по построению.
- **Контролируемо** = четыре независимых рычага, все уже в модели: форма (валидатор по `schema`) ·
  доверие (`epistemic`, сторонний `→fact` запрещён) · доступ (scope/ABAC, default-deny) ·
  наблюдаемость (трейсы всех действий плагина).
- Критерий добавлен строкой в матрицу §5.

### 4a.5 Что это требование меняет (честно)

1. **V3 не ломается — усиливается.** Плагин = ещё один вид коннектора со своим principal. V1
   ломается окончательно: чужой исполняемый контент в одной физической БД со всем личным — прямое
   нарушение границы principal. V2 не реабилитируется (вариации через копии = расхождение версий
   базового плагина по проектам — ровно то, чего владелец боится).
2. **Отчуждаемость повышается из «опции» в ОБЯЗАТЕЛЬНОЕ свойство.** Граница §6.4 (экспорт подграфа)
   при marketplace перестаёт быть будущей спекой: скачивание/распространение плагина — это и есть
   **pack-формат подграфа** (узлы + рёбра + control-plane, срез по principal/scope, версионируемый).
   Это вторая честная новая дельта концепта (после stream-класса) — её нужно закладывать в
   engine-спеку сейчас, реализовывать позже.
3. **ADR-0003 (ABAC/scope/default-deny) становится блокером всей marketplace-механики** — без него
   «подключение к лимитированной области» нечем енфорсить. Приоритет ADR-0003 повышается.

## 5. Три архитектурных варианта — сравнение и выбор

| Критерий | V1: одна физическая БД-сервис для ВСЕГО | V2: федерация per-project БД с общим ядром | V3: один граф знаний + рантаймы модулей + коннекторы ✅ |
|---|---|---|---|
| Централизация знания | максимальная, но неразборчивая | слабая: знание размазано | **полная в плане знаний** (одна база, один id-space) |
| Синхронность | автоматическая | ГЛАВНАЯ проблема: sync/копии — то, что владелец явно отверг | автоматическая (источник один) |
| Чужие данные (клиенты CRM, юзеры jenek) | попадают в личный граф — нарушение principal/приватности | остаются по проектам ✓ | остаются в БД приложений; в графе — href-карточки |
| Рантайм (очереди, локи) | смешан со знанием: шум, contention, ротация усложняется | по проектам ✓ | в рантаймах модулей; долговечное — журналируется |
| Отказоустойчивость | сервис упал — встало ВСЁ (даже очередь бота) | независимая ✓ | упал движок — знание недоступно, но рантайм модулей жив |
| Гибкие структуры «на лету» от плагинов (§4a.4) | типы создаются, но чужой код живёт в одном пространстве со всем личным — изоляции нет | плагин ставится N раз по проектам → версии базового типа расходятся | **открытый реестр: тип = control-plane-узел под `principal`; scope/ABAC изолирует; pack-формат отчуждает** |
| Соответствие уже принятому | противоречит границе «план знаний ⟂ исполнение» | противоречит §1a «НЕ копировать» | совпадает с §1a, ADR-0002, ADR-0004, D-C/D-E |

**Выбор: V3** — «один логический граф, движок-как-сервис, рантаймы модулей отдельно, приложения
подключаются коннекторами». Это НЕ компромисс против централизации, а её точная формулировка:
централизуется то, что и было болью — знание и координация (задачи в 4 местах, доки в 2 конвенциях,
агенты не знают друг о друге). V1 отвергнут не из осторожности, а потому что смешивает три
несовместимых лайфцикла (знание/рантайм/чужие-данные) в одном хранилище — это «прямолинейность»
не в ту сторону. V2 отвергнут словами самого владельца: копии ломают синхронность.

Физика при этом проста: на старте один SQLite-файл графа в `ОРГАНИЗАЦИЯ/graph/` + md-тела рядом.
Один пользователь, одна машина — этого хватит надолго; партиционирование (archive-БД, отдельный
FTS-файл) — по мере роста, без смены контракта.

**Следствие для OQ-2 (библиотека vs сервис):** единая БД на несколько проектов практически
решает этот вопрос в пользу **СЕРВИСА** (или библиотеки со strict single-writer-демоном): писатели
из разных проектов должны проходить через один enforcement-пункт, иначе клапан обходится прямой
записью (ровно named-риск engine-синтеза). Централизация и честный клапан — один и тот же аргумент. ⚑ C.

## 6. Границы применимости (где централизация НЕ сработает — честно)

1. **Данные чужих principal** (клиенты CRM-Rent, конечные пользователи jenek): им нельзя жить в
   личном графе владельца — другой владелец данных, другой масштаб, другие требования. В графе —
   карточки/агрегаты/href.
2. **Суб-секундные горячие циклы** (очередь сообщений бота, поллинг, локи): движок графа не
   предназначен быть message-broker'ом. Рантайм модуля + журналирование.
3. **Крупные бинари** (рендеры music-video, аудио): href-узлы, тело — в ФС/сторадже.
4. **Проект, который должен жить автономно/отчуждаемо** (маркетплейс-модуль D-F, передача другому
   человеку): ему нужен ЭКСПОРТ подграфа (subset по principal/scope), а не доступ к целому графу.
   С требованием плагинов (§4a.5) экспорт-подграф — уже не будущая опция, а обязательный pack-формат;
   зависит от ADR-0003 (ABAC).
5. **Пока нет движка-enforcement** (до M2): единая БД без единого writer'а — это просто общая папка;
   централизация реальна ровно с того момента, когда запись идёт через один пункт. До того — не
   объявлять базу «единой», чтобы не создавать ложное доверие.
6. Если однажды появится **вторая машина/облако** — «один SQLite-файл» перестанет быть ответом
   (репликация md+SQLite нетривиальна); контракт V3 переживёт это (сервис получает сетевой API),
   физика — нет. Заложено границей, не решается сейчас.
