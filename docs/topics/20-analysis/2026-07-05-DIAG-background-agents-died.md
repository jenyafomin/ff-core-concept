# DIAG — Почему гибли фоновые агенты и «перезапускался шлюз» (2026-07-05)

> Статус: draft · Для пересылки мейнтейнеру шлюза (agents-manager / dwizh gateway) · Автор: Opus (наблюдения из сессии топика 56)

## Симптом
В ходе сессии 4 фоновых ресёрч-агента и адвайзер Fable **несколько раз погибали, не дописав работу**. Уведомления показывали два вида смерти: `killed by user` и `stopped — process exited, no completion record`.

## Наблюдаемые факты (из этой сессии)
1. **Одно и то же голосовое сообщение владельца пришло ~6 раз подряд** (идентичный транскрипт, разные ходы). Каждый повтор шлюз обработал как НОВЫЙ ход.
2. По конвенции шлюза (`CLAUDE.md`): «каждый ход группы = свежий `claude -p --resume`». Значит **каждое входящее сообщение = новый процесс `claude`**.
3. Фоновые субагенты (`Agent` с `run_in_background`) — дочерние процессы ТЕКУЩЕГО `claude`. Когда приходит следующий ход, новый `claude`-процесс стартует, а предыдущий (с живыми детьми) убивается → дети получают SIGKILL. Отсюда `killed`/`stopped`.
4. **`WebSearch`/`WebFetch` запрещены в песочнице** — ресёрч-агенты, пытавшиеся верифицировать источники в вебе, дополнительно стопорились.

## Корневая причина (гипотеза, 2 слоя)
- **A. Модель «сообщение = новый процесс» несовместима с фоновыми субагентами.** Фоновая работа не переживает границу хода: старый процесс убивается при старте нового. Это архитектурное, не случайное.
- **B. Дубли входящего сообщения (×6).** Даже без фоновых агентов повторная доставка одного голосового = повторный старт процесса = убийство ещё бегущей работы. Похоже на retry без дедупликации/ack (сообщение не «подтверждено обработанным», шлюз шлёт снова) ИЛИ повторную отправку из Telegram.

## Что проверить мейнтейнеру
1. **Почему одно голосовое доставилось 6 раз?** Логи ack/повторов шлюза. Есть ли дедуп по `message_id`/`update_id`? (Скорее всего — ключевая проблема.)
2. **Как шлюз завершает предыдущий ход?** Убивает ли всё дерево процессов при новом сообщении? Можно ли вместо kill — ставить входящие в очередь, пока идёт текущий ход?
3. Долгие задачи в этой модели в принципе должны быть **синхронными в пределах хода** (не background), либо шлюзу нужен персистентный воркер вне жизненного цикла `claude -p`.

## Обходные пути, применённые сейчас (работают)
- **Писать результаты в файлы НЕМЕДЛЕННО** — прогресс не теряется при kill (агентам явно велено писать отчёт файлом; тяжёлый ресёрч в итоге написан inline и лёг сразу).
- Тяжёлую фоновую работу заменять **прямой записью артефактов в текущем ходе**.
- Ресёрч — на знаниях, без веба (пока `WebSearch` закрыт).

## Рекомендация (приоритет)
1. **Дедуп входящих по id** (чинит ×6-повтор) — вероятно, самый быстрый и важный фикс.
2. **Очередь ходов вместо kill** — чтобы фоновая работа доживала; либо явно отказаться от background-субагентов в этой модели.
3. Решить судьбу `WebSearch` для ресёрч-агентов (allow-network или знание-only по договорённости).
