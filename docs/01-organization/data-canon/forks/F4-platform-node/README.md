# F4 — Узел «платформа»/«модуль» (D1-Q8)

## Вопрос
Завести ли `node_type` **«платформа»/«модуль»** + дом `02-infrastructure/03-platforms/`?

## Варианты
- **(А)** Да — новый `node_type` + дом `02-infrastructure/03-platforms/`.
- **(Б)** Нет — платформа выражается существующими примитивами/узлами.

## Ход мысли — что учесть (открыто, не исчерпывающе)
- Может добавить звенья в ось `02-project` (см. F3).
- Связано с F1: «платформа» как узел vs как домен-грань — не спутать.

## От чего зависит / downstream
- F3 (добавляет звенья в ось), F1 (домен vs узел).

## РЕШЕНИЕ: **Б — никакого нового `node_type`; модуль = КОМПОЗИЦИЯ существующих примитивов (манифест-узел + граница)** (статус review)

- **Расщепить слово (тот же ход, что в F1):** «платформа» и «модуль» — два разных понятия, слитых
  в одном форке. **Платформа** = сам субстрат + рантайм агентов (граф целиком, Машина A+B) — она
  НЕ живёт узлом внутри самой себя, это уровень системы, не уровень данных. **Модуль** = plug-in
  единица видения — вот про него и есть настоящий вопрос.
- **Модуль — не ВИД единицы, а ГРАНИЦА над единицами.** Субстанция модуля — множество узлов/рёбер/
  актов/линз; тег `node_type: module` на одном узле этого не выражает и врёт про природу вещи.
  Модуль выражается уже имеющимся: **один манифест-узел** (обычный `node`, реифицированная граница)
  + **рёбра принадлежности** + **линза-концепт**. Хребет это УЖЕ зафиксировал: §4.2
  VOCABULARY-SPINE — «Один навигационный концепт на модуль (всегда один)». Представимость есть —
  значит (А) добавляет онтологию без нужды.
- **Plug-in «с 1-й итерации» — это обязательство на КОНТРАКТ, а не на тип.** Подключаемость даёт
  граница+манифест (что внутри, что торчит наружу), а не слово в реестре типов. Новый `node_type` —
  реальное онтологическое обязательство в базовой анатомии; по правилу promotion-by-evidence его
  заводят после 2+ живых модулей, а не до первого. Сегодня живых модулей-манифестов — ноль.
- **Checkable-предикат «X — модуль»:** (1) у X ровно один манифест-узел (концепт-линза: цель +
  интерфейс + состав); (2) все внутренние единицы достижимы от манифеста по рёбрам принадлежности —
  множество замкнуто; (3) все рёбра НАРУЖУ границы проходят только через задекларированные в
  манифесте контрактные точки — т.е. X можно отключить, не порвав инварианты чужих единиц.
  Не проходит все три — это не модуль, а просто папка/кластер.
- **Дом `02-infrastructure/03-platforms/` НЕ заводим.** Пустой слот под несуществующие манифесты —
  ossification ровно того сорта, от которого предостерегает F4. Первый реальный манифест живёт в
  доме своего модуля; выделенный дом — по evidence (2+ манифеста), обратимым ходом.
- **Downstream для F3:** F4 **не добавляет звеньев** в ось `02-project` — нумеровать `core→01-core`
  можно, не резервируя слот под «платформы». Связь с F1 чистая: домен = ГДЕ анатомия
  специализируется под правила; модуль = ЧТО упаковано границей и отключаемо. Зрелый модуль может
  СО ВРЕМЕНЕМ дорасти до домена (своя специализация правил) — это переход по предикату F1, не
  третий тип сущности. Связь с F7 (reification): манифест — канонический пример реифицированной
  границы, решать согласованно.

**Риск выбора (один, честно):** без типа граница модуля держится конвенцией (манифест + рёбра),
а не системой типов — агенты могут плодить «дырявые» модули с рёбрами в обход контракта. Ответ —
integrity-check/линт предиката (в духе `concept-lint`), а не тип; но пока линта нет, дисциплина
границы держится только на ревью.
