# Root-cause: жизненный цикл фоновой работы vs жизненный цикл хода

> Разбор read-only по коду `agents-manager` (`/Users/mac16/Documents/IT/Apps/TOOLS/agents-manager`),
> commit-состояние на 2026-07-30. Правки продуктового кода НЕ вносились. Ссылки — `файл:строка`.

## TL;DR

Единица durable-работы шлюза — **Job = ОДИН ход** (`src/core/domain/job.interface.ts`: «Ход агента = Job»).
Ход исполняет `TurnExecutor.execute`, который вызывает `runner.run(task)` и ждёт **ровно один**
`IAgentResult` (финальное сообщение ГЛАВНОГО агента). В тот момент, когда `runner.run` зарезолвился, ход
считается завершённым — шлюз персистит ответ и рвёт рантайм хода.

Но фоновый суб-агент (`run_in_background` у Task/Bash) живёт **внутри** этого рантайма — его хостит
эфемерный носитель хода:
- **SdkRunner** (дефолт): носитель = in-process `query()` Agent SDK. `query()` резолвится по финалу
  главного агента; фоновый Task, запущенный внутри, шлюз НЕ дожидается (его нет в `IAgentResult`) —
  контекст query утилизируется, фон брошен.
- **PrintRunner** (fallback): носитель = дочерний процесс `claude -p --resume`. One-shot `claude -p`
  выходит после финального JSON → его дети-Task умирают вместе с ним. Следующий ход спавнит НОВЫЙ
  `claude --resume`, и Claude Code на резюме печатает `No completion record found … may have been
  running when the previous process exited` — **это и есть симптом из INDEX.md**.

**Структурный разрыв:** машинерия durability шлюза (`process-lease` + `orphan-reaper` + `queue.recover`)
защищает **ход как процесс** через рестарты, но НЕ имеет ни представления, ни владельца, ни канала
доставки для работы, порождённой ВНУТРИ хода. Домен даже *документирует* правильную модель
(«Фоновый агент = долгий Job, а не живой процесс») — но НЕ даёт механизма, которым агент внутри хода мог
бы такой Job создать. Поэтому фон утекает в Claude-нативный `run_in_background` — вне конверта durability —
и умирает молча (out-Message для него не рождается никогда → «тишина»).

## Два жизненных цикла, которые шлюз путает

| Слой | Что это | Кто владелец жизни | Durability |
|------|---------|--------------------|------------|
| L1 — **ход (turn)** | Один Job: prompt → финальный ответ | Queue + TurnExecutor + Runner | ЕСТЬ: `job-status`, `process-lease`, `orphan-reaper`, `queue.recover` |
| L2 — **фоновая работа внутри хода** | `run_in_background` Task/Bash, суб-агенты | НИКТО (хостит эфемерный рантайм L1) | НЕТ: не отмоделировано, не персистится, не доставляется |

ADR-0001 усиливает путаницу: в «Последствиях» SdkRunner записан плюс «выживающие фоновые ходы». Но это
про L1 — ход переживает ПРИХОД НОВОГО входящего (устранение one-shot-смерти хода), а НЕ про L2 — фоновый
суб-агент, переживающий ЗАВЕРШЕНИЕ хода. Это разные вещи; ADR-0001 их слил в одну формулировку.

## Точная трассировка (файл:строка)

### Граница хода — где ход объявляется «готов»
`src/server/orchestration/turn-executor.ts`
- `execute` (:132–160): `this.runner.bindJob(...)` (:151) → `const result = await this.runner.run(task)`
  (:152) → `await this.applyResult(job, result)` (:159). Ход = ожидание ОДНОГО `IAgentResult`.
- `applyResult` (:402–412) → `persistOutcome` (:422–478): единственный путь доставки ответа в канал
  (`this.channel.send`, :514/:530). Он привязан к ВОЗВРАЩАЕМОМУ результату главного агента. У L2-фона
  нет ни `IAgentResult`, ни вызова `channel.send` — отсюда «тишина» даже когда фон доделал работу на диске.

### Носитель хода в SdkRunner (дефолт) — где фон брошен
`src/claude-runner/sdk-runner.ts`
- `runOnce` (:128–219): `const outcome = await this.runQuery({...})` (:151) — единственная точка ожидания.
  `query()` резолвится по финалу главного агента.
- `finally { this.active.delete(task.sessionKey) }` (:216–218): AbortController хода снят, рантайм query
  утилизируется. Любой in-flight фоновый Task, порождённый query, здесь брошен — шлюз его не ждёт и не знает.
- `active`/`cancelled`/`jobIndex` (:53–55) — учёт только на уровне sessionKey хода; L2-задач нет.

### Носитель хода в PrintRunner (fallback) — где фон убит процессом
`src/claude-runner/print-runner.ts`
- `invokeOnce` (:168–202): `this.cli.invoke({...})` (:181) спавнит `claude -p`. One-shot: процесс выходит
  после финального JSON → дети-Task умирают вместе с ним.
- Следующий ход: `runOnce` → `buildClaudeArgs` (:125) → новый `claude --resume` (:143 генерит/резолвит id).
  Резюме на осиротевший фон и печатает «No completion record found …».

### Durability активно ВРАЖДЕБНА выжившему фону
`src/server/lifecycle/orphan-reaper.ts`
- `reap` (:39–54): на старте инстанса SIGKILL'ит ЛЮБОЙ живой `claude`-процесс этого хоста по
  `process-lease` (:47–50), чтобы `--resume` не форкнул транскрипт дважды. Вызывается в
  `build-app.start()` ДО `queue.recover()`.
- Следствие: даже если бы фоновый `claude`-процесс пережил крэш, reaper убил бы его на следующем старте.
  Текущий дизайн durability спроектирован ПРОТИВ выживания фоновой работы, не за неё.

### Восстановление после рестарта видит только L1
`src/server/queue/queue.ts`
- `recover` (:70–81): `requeueRunning()` + подъём `queued` — это ходы (Job), не L2-фон. Комментарий F7(б)
  прямо про «ре-диспатч turn 2+», не про фоновые суб-агенты.
- `drain` (:95–111): дренаж перед `/rebuild` ждёт только `activeJobs` (ходы). L2-фон в `activeJobs` не
  входит → дренаж его не видит и не ждёт → `/rebuild` рвёт фон, не подозревая о нём.
- Shutdown-путь: `main.ts` SIGTERM → `app.stop()` → `queue.stop()` + `onRunnerCleanup()` (build-app
  :415–419). PrintRunner.shutdown() (:109–117) абортит активные ХОДЫ; фоновых детей внутри `claude -p`
  оно не адресует (они дети чужого процесса).

### Модель уже описывает правильный ответ, но он не проведён
`src/core/domain/job.interface.ts` (шапка): «"Фоновый агент" = долгий Job, а не живой процесс.» —
намерение верное. Но НЕТ инструмента/порта, которым агент внутри хода создаёт такой Job. Существующие
in-process инструменты, публикуемые адаптером SdkRunner (`buildLiveEgressTurn`, `buildSendToTopicTurn`,
sdk-runner.ts :135–146), показывают ГОТОВЫЙ ШОВ, куда такой инструмент лёг бы. Он просто не заведён.

## Почему `--resume` «убивает» in-flight фон (явно)

`--resume` сам по себе ничего не убивает — к моменту резюме носитель предыдущего хода УЖЕ мёртв:
1. PrintRunner: предыдущий `claude -p` — one-shot, вышел после финала → дети уже мертвы; `--resume` лишь
   *печатает* про осиротевший фон.
2. SdkRunner: предыдущий query утилизирован в `finally` (:216) по возврату из `runOnce`; фон брошен там же.
3. На рестарте шлюза `orphan-reaper` добивает любой выживший `claude` до `recover`.

То есть «resume убивает фон» = сокращение для «фон хостит эфемерный носитель хода; носитель рвётся на
границе хода / на рестарте, а resume/reaper — момент, когда это становится видно».

## Смежные баги — один мета-корень

Все четыре бага — утечка ДОЛГОЖИВУЩЕГО состояния через ЭФЕМЕРНЫЙ per-turn носитель:
- **background-die** (этот): фоновый результат переживает ход — носителя нет.
- **dup-kill** (`../../gateway-dup/`): конкурентный/дубль-ход рвёт стрим активного; L2-фон дренаж не видит.
- **AskUserQuestion-not-delivered** (`../../gateway-askquestion-not-delivered/`): интерактив, который должен
  пережить один stdout-стрим хода, не имеет durable-канала (не транслируется в кнопки Telegram).
- **tool-permission-stream** (`../../gateway-tool-permission-stream/`): канал подтверждений рвётся вместе
  со стримом хода → «Stream closed».

**Мета-корень (для ADR):** шлюз отождествляет «ход» с «временем жизни процесса» и не имеет durable,
turn-независимого канала для асинхронного/интерактивного состояния (фоновые результаты, вопросы посреди
хода, round-trip подтверждений). Каждый смежный баг — тот же протекающий шов.
