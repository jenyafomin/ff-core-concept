# ADR-draft · Фоновая работа как durable Job шлюза (turn-independent)

> **Status: draft.** Это ЧЕРНОВИК для проекта `agents-manager` — предлагается завести там как следующий
> ADR (напр. ADR-0005). Пишется на бумаге; продуктовый код НЕ трогался. Владелец решает «строй».
> Дом реализации — `agents-manager`; этот файл живёт в FF как дом ПРОБЛЕМЫ (директива на починку).

## Контекст

Единица durable-работы шлюза — Job = один ход; фоновая работа (`run_in_background`) хостится эфемерным
носителем хода (SdkRunner `query()` / PrintRunner `claude -p`) и умирает на границе хода/рестарте, молча
(нет out-Message). Домен уже документирует правильную модель — «Фоновый агент = долгий Job, а не живой
процесс» — но механизма создать такой Job из хода НЕТ. Полный разбор с `файл:строка` — в
`01-root-cause.analysis.md`. Инцидент-подтверждение: 2026-07-27 (builder в фоне помечен `stopped`; работа
уцелела на диске только потому, что проверили вручную).

Это один из класса «шлюз ломает асинхронность/интерактив» (dup-kill, AskUserQuestion, permission-stream).
Мета-корень: нет durable, turn-независимого канала для долгоживущего асинхронного/интерактивного состояния.

## Решение (рекомендация)

Принять **слоёный фикс `(a′) + (b) + (c)`**, где ведущий структурный ход — **(a′): реифицировать фоновую
работу как durable Job шлюза**, а не как Claude-нативный turn-hosted `run_in_background`.

**Паттерн:** Ports & Adapters + durable Job/Outbox. Атомарная единица смещается с «ход» на «задача
разговора с durable-outbox». Outbox = таблица Job'ов (уже durable) + маркер «доставлено».

Конкретно, три слоя, вводимые по возрастанию инвазивности (можно катить поэтапно):

1. **Слой C (сначала, дёшево, честно) — never-silent.** Наблюдать запуск фоновой работы через
   существующий `guard`/PreToolUse-хук; durable-маркер «bg launched», снимаемый при завершении; скан не
   снятых маркеров на старте (рядом с `orphan-reaper`) → явный нотис в разговор. Немедленно убирает «тишину».

2. **Слой A′ (ядро) — фон = durable Job.** In-process инструмент `spawn_background_job` (публикуется
   адаптером SdkRunner тем же швом, что `send_to_topic`/live-egress). Вызов → новый `IJob` (child-session
   `<sessionKey>#bg:<uuid>`, `origin`=разговор родителя) в существующую `Queue`. Родительский ход
   возвращается сразу с квитанцией. Доставка результата child→parent — штатным `persistOutcome`/`channel.send`
   по `origin`. Guard от спавн-штормов (глубина/квота). Политика: стоп-список ADR-0002 деклайнит
   Claude-нативный `Task run_in_background` + директива каскада «фон запускай инструментом шлюза».

3. **Слой B (доставочная семантика, идея владельца) — recover/re-dispatch.** `queue.recover()` кроме ходов
   поднимает недоставленные bg-Job'ы и ре-диспатчит: агент читает частичный результат на диске и
   продолжает/переотдаёт — до доставки. Идемпотентность через «сначала прочитай что уже сделано».

**Почему именно так:** реюз существующей durability (Job/Queue/recover/ApprovalGate/origin-routing) вместо
второй параллельной машинерии; аддитивно и за фиче-флагом (обратимо); реализует уже задокументированное
намерение ADR-0001 и домена. Слой C даёт немедленную честность, пока A′/B строятся.

## Альтернативы (отклонены — см. `02-fix-options.design.md`)

- **(a1) SDK-detach (держать query живым после финала):** высокий риск, ломает mutex/capacity, конфликтует
  с orphan-reaper, в PrintRunner невозможно, зависит от неподтверждённой способности SDK. Противоречит ADR-0001.
- **Только (c):** честно, но не спасает работу и не доставляет результат — мост, не цель.
- **Только (b) без (a′):** нечего восстанавливать — Claude-нативный осиротевший Task шлюзу невидим.

## Последствия

**Плюсы:**
- Фоновая работа переживает границу хода и рестарт; результат доставляется гарантированно.
- «Тишины» больше нет (слой C — инвариант честности с первого этапа).
- Реализует документированную модель «фон = Job»; снимает концептуальный долг ADR-0001.
- Реюз Queue/recover/Gate — минимум нового кода, максимум проверенной durability.

**Минусы (принятые):**
- Новый инструмент + шов доставки child→parent + guard — средняя инвазивность. Принято: за флагом,
  поэтапно, обратимо.
- Нужно СТИР агентов с Claude-нативного `run_in_background` (стоп-список + директива) — иначе фон снова
  утечёт мимо инструмента. Принято как политика ADR-0002.
- Ре-диспатч не-идемпотентной работы рискует дублем side-effect'ов. Принято: семантика «прочитай diff на
  диске, продолжи», не «запусти заново с нуля».
- Смежные баги AskUserQuestion / permission-stream этим НЕ закрываются (другой шов egress/permission),
  только снижается экспозиция. Принято: тот же мета-корень, отдельные адресные фиксы.

## Закрывает ли класс багов заодно

| Смежный баг | Закрывается? | Чем |
|---|---|---|
| background-die (этот) | **да** | A′ (durable Job) + B (recover) + C (сигнал) |
| dup-kill | частично | A′ уводит работу с хрупкого стрима; + ingress-дедуп (DedupStore F11 уже есть) |
| AskUserQuestion не доставлен | нет (адресно) | отдельно: рендер интерактива в кнопки Telegram через `approval-callback` |
| tool-permission «Stream closed» | нет (адресно) | отдельно: keep-alive/ретрай permission-стрима ИЛИ `/trust` bypass (ADR-0002) |

Рекомендация: этим ADR закрыть background-die + вклад в dup-kill; для AskUserQuestion и permission-stream
завести отдельные ADR того же класса, сослаться на общий мета-корень.

## План валидации

1. **C-инвариант:** фоновая работа запущена → `/rebuild` шлюза → в разговор приходит явный нотис об обрыве
   (не тишина); маркер снят.
2. **A′ happy-path:** агент зовёт `spawn_background_job` → родительский ход отвечает квитанцией сразу →
   child-Job доезжает → результат доставлен в ТОТ ЖЕ разговор с атрибуцией.
3. **A′ durability:** child-Job в полёте → рестарт шлюза (SIGTERM) → `queue.recover()` поднимает →
   доставка после старта; `orphan-reaper` его не убивает (Job, не процесс).
4. **B re-dispatch:** child-Job прерван на середине (частичный результат на диске) → ре-диспатч →
   агент продолжает с диска, без дубля side-effect'ов → доставка.
5. **Политика:** попытка Claude-нативного `Task run_in_background` → деклайн стоп-списком + подсказка
   использовать инструмент шлюза.
6. **Регресс:** флаг off → поведение как сейчас (обратная совместимость, паритет с PrintRunner-веткой).
7. **Спавн-шторм:** рекурсивный/массовый спавн → guard глубины/квоты режет, владелец уведомлён.

## План отката

- Всё за фиче-флагом (зеркалит `liveEgress`/`sendToTopic` флаги в `sdk-runner.config`). Флаг off →
  инструмент не публикуется, наблюдение C — no-op, поведение = текущее.
- Слои независимы: можно откатить B (перестать ре-диспатчить bg-Job) и/или A′ (снять инструмент),
  оставив C (сигнал). C сам по себе best-effort (глотает ошибки, как decision-journal) — снимается флагом.
- Схема БД: новые поля/таблицы (bg-marker, «доставлено» на Job) — аддитивные, nullable; откат = не читать их.
- Точка возврата перед миграцией БД — по правилу git-working-tree-safety (коммит/ветка до изменений).

## Открытые вопросы (перенос из root-cause — решить в agents-manager до «строй»)

1. Режим раннера в проде FF (`sdk` vs `print`) — определяет приоритет путей фикса.
2. Умеет ли Agent SDK `query()` переживать `run_in_background`-Task (решает судьбу a1; на a′ не влияет).
3. Виден ли `run_in_background` в `input` тула для `guard` (дешёвая детекция слоя C) — сверить по sdk.d.ts.
4. Где SDK пишет транскрипт фонового Task — можно ли реально «подхватить» частичный результат (глубина B).
5. Деривация child-session `<sessionKey>#bg:<uuid>`: как ложится на `build-session-key`/`archive-key` и
   per-session mutex (не должна конкурировать с родительской сессией за один mutex-ключ).
