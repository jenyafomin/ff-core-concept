## Р-1 — DL-15 ↔ DL-21 (БД): PostgreSQL ратифицирован, кода нет

- **[факт кода]** В `packages/engine/src` **нет ни одного Postgres/pg-адаптера** (grep находит только
  упоминание PG в комментарии `store-port.ts`: «swap to PG at M4 = ADDITIVE new adapter»). Реально
  работающий M0-контракт = `MemoryStore` (RAM), md-мост — async-провизорный. read-model свёрнут в
  app-коде (`projection.ts`/`edge-index.ts`/`view-compiler.ts`), НЕ в БД → ядро **уже DB-agnostic по
  построению**.
- **[что говорит канон]** DL-21 (2026-07-18): «БД = PostgreSQL, закрывает DL-15». DL-15 (2026-07-12):
  «открыто, склон к графовой». По source-of-truth Rule-2 (позднее ратифицированное бьёт раннее) DL-15
  уже закрыт = Postgres. R3-фрейминг 07-31 его переоткрыл во фрейме; R4 классифицирует БД как **floor
  (подменяема), не корень**.
- **[предложение владельцу]** Снять расхождение «имя БД ратифицировано / кода нет / фрейм переоткрыт»
  одной формулировкой. Черновик уточнения DL-21 (или новый DL):
  > *«БД: **file-first за `StorePort`**; ядро **DB-agnostic** (fold/проекция — в app-коде, не в БД).
  > PostgreSQL = **аддитивный адаптер** целевого floor (не переписывание ядра); граф-натив — будущий
  > адаптер ПО ЗАМЕРУ горячих traverse-путей, не по эстетике. Выбор БД = floor-решение, НЕ блокер корня.»*
  Это согласует DL-15/DL-21 + R3 §2b + R4 (floor). ⏳ да/нет владельца.
  - **Сцепка:** истинность «аддитивности» PG зависит от sync/async развилки порта — см.
    `durable-storeport.design.md §3` (если порт остаётся sync, переход на PG = breaking, НЕ аддитивный).
    Эти два решения принимать вместе.

## Р-2 — DL-16 (build-репо в TOOLS/) молча не исполнена

- **[факт кода]** DL-16 ратифицировал «build-репо = **НОВЫЙ репозиторий в `TOOLS/`**» под движок/БД.
  Фактически движок построен **в `packages/engine` ЭТОГО репозитория** (FF-Personal-Managment), не в
  отдельном репо в `TOOLS/`. Расхождение канон↔реальность не зафиксировано ни в одном решении.
- **[что говорит канон]** DL-16: ✅ ратифицировано (владелец, 2026-07-13). Никакой отмены/superseded в
  DL-логе нет — решение висит «исполненным» на бумаге, но исполнено ИНАЧЕ.
- **[предложение владельцу]** Явно закрыть развилку — **это вопрос, не факт**. Два кандидата статуса:
  - **(a) superseded:** monorepo `packages/*` в этом репо оказался практичнее (движок + жильцы +
    доки рядом; границы держит import-lint, R3 §4). Тогда DL-16 → `superseded`, причина зафиксирована.
  - **(b) всё ещё в планах:** `packages/engine` = временный полигон, вынос в отдельный `TOOLS/`-репо —
    отложенный долг. Тогда DL-16 остаётся open с явной пометкой «не исполнено, отложено».
  ⏳ Решает владелец: (a) или (b)? Молчаливое расхождение убрать в любом случае.

## Р-3 — STATE.md «код не тронут» vs 4 build-коммита 07-26..28

- **[факт кода]** `packages/engine` содержит построенный CQRS-движок: `write→fold→node`, admission,
  resolve-PEP, rebuild, идемпотентность (коммиты `2c8d177`, `23a569a`, `ee70446`, `ecd0811` — M0/M1
  движок + ingest + rental-balance, 07-26..28). Движок реально построен и независимо проверен зелёным.
- **[что говорит канон]** STATE.md несёт формулировку **«код/git/packages не тронуты»** (строки 20 и 45,
  из контекста проходов дизайна 07-30/07-31). Взятая буквально и вне контекста, она противоречит наличию
  4 build-коммитов.
- **[предложение владельцу]** Уточнить формулировку в STATE (это правка навигатора — вносить отдельным
  ходом, здесь только текст-предложение; INDEX/STATE в этой сессии не трогаю):
  > *«Движок ПОСТРОЕН (M0/M1: CQRS-ядро + ingest + rental-balance, 4 коммита `refactor-tree`, не запушены).
  > Оговорка "код не тронут" относится к КОНКРЕТНОЙ сессии (дизайн-проходы 07-30/07-31: bumdага, без правок
  > packages) — НЕ к проекту в целом.»*
  Смысл: «код не тронут ЗА ЭТУ узкую сессию» — правда; «код проекта не тронут» — нет. Развести область
  действия оговорки, чтобы будущий читатель STATE не заключил, что движка нет.
