# 11 · Фасет-шаблон + нумерация/underscore

> Записано с голоса владельца 2026-07-21 поверх примера-структуры (другой проект). Наш класс — агент-
> субстрат, поэтому берём ЛОГИКУ. Слоты со `⚠️` — предложены мной, требуют подтверждения владельца.

## A. Фасет-шаблон единицы (домена / «единицы»)
Каждая единица (домен-модель, а внутри — под-единица) описывается ФИКСИРОВАННЫМ набором слотов.
**Правило нумерации:**
- `01-explain` — **ВСЕГДА с номером**. Это вход-объяснение единицы; всегда относится к конкретному
  родителю, поэтому живёт в нумерованном хребте.
- Все **фасет-слоты — ВСЕГДА с номером и разделены** (не свалка). Из примера + наш субстрат:

| Слот | Номер | Что несёт |
|---|---|---|
| `01-explain` | да | что это за единица (вход) |
| `02-entities` | да | единицы/сущности единицы |
| `03-relations` | да | связи между единицами |
| `04-mechanics` | да | механики этой единицы (domain-local) |
| `05-policy` ⚠️ | да | политики/доступ (наш субстрат-слот; в примере нет) |
| `06-nuances` | да | уникальные нюансы единицы |
| `0N-pages` ⚠️ | да | ТОЛЬКО если есть UI (для субстрата обычно нет) |
| `decisions/` | **можно ОБЩИМ** (без номера) | со-локейт решений единицы; глобально линкуется в `decisions.INDEX.md` |

- **`decisions` — исключение:** может быть общим бакетом (без номера), т.к. решения тянутся отовсюду.

## B. Per-домен: вопрос + общее представление
На уровне «4 единицы (домены-модели)» (и если станет 5 — так же):
- В папке каждой единицы **отдельно заводится узел-вопрос** (`questions` этой единицы) — крутить
  развилки прямо у дома единицы.
- **Общее представление** единицы = как она собой представляет: все грани + связи между ними + как
  единица «выглядит» целиком. Каждая единица описывает свои **уникальные моменты**.

## C. Underscore-бакеты (всегда `_`, вне нумерованного хребта)
Расширяет аспект 09. Владелец 2026-07-21:
- **Сквозные механики — ВСЕГДА с `_`** («более конкретно», чтобы сквозное было видно): `_shared/` /
  `_mechanics/`. Механика может содержать под-механики; общая механика, делимая между единицами, живёт
  сквозным `_`-бакетом и приписывается им по отдельности ссылкой.
- **`_unverified/`** (рабочее имя; ⚠️ подтвердить: `_on-verify/`) — механики, которые уже ВЫЯВЛЕНЫ, но
  ещё НЕ решены. Внутри может быть много аналитики; вокруг «крутим вопросы». Может нести свой внутренний
  номер / быть чёткой папкой-домом.
- **`_shared/`** в слое-реализации (backend) — под номером внутри: utility · middlewares · guards
  (⚠️ кандидаты — «надо подумать, будут ли нужны»).

## D. Два дома механик (подтверждает INS-2)
- **domain-local** механика → слот `04-mechanics/` ВНУТРИ своей единицы.
- **сквозная** механика → `_`-бакет уровня (`_shared/` / `_mechanics/`), помечена underscore.
- **integrations** = внешние адаптеры механики (сервисы, реализующие механику).

## E. Рекурсия + «зеркало» (документ отражает систему)
- На КАЖДОМ уровне рекурсивно отвечаем: «из чего состоит эта инфраструктура?» → frontend · backend ·
  база данных · плотные взаимодействия/связи = **модули · сервисы**.
- **То, что строим, раскладываем в документе ТЕМИ ЖЕ паттернами** (зеркало concept → shared → platform).
- Пример backend-слоя (`platforms/backend/`): `domains/` = зеркало концепт-доменов (те же NN); каждый
  домен → его логика · единицы (entities) · endpoints · data · сервисы; `_shared/` (utils/middlewares/guards).

## F. Параллельный трек — безопасность/доступ
Отдельно от brain/инфры развивать **модуль безопасности/доступа к данным**: что может получать АГЕНТ и
что — ПОЛЬЗОВАТЕЛЬ. Не часть хребта деривации, а сквозной трек (кандидат в `_`-модуль или свой домен).

## G. Что это меняет в карте переезда (перепроверка)
Единицы, которые едут в дом, **пере-раскладываются в фасет-слоты**, а не переносятся как есть:
- `values/0N-*/` направления → слоты своей ценности (explain/mechanics/…).
- `domains/01-knowledge-graph/` (node-types, edge-types, policy, growth, --decomp) → `02-entities`,
  `03-relations`, `05-policy`, `01-explain`, `04-mechanics/` соответственно + `decisions/`.
- Сквозные механики из `infrastructure/` → `_shared/`/`_mechanics/` с underscore.
- Выявленные-но-нерешённые (напр. часть `_wide`, gap-механики) → `_unverified/`.
→ Полный ре-мэппинг слотов допишем в `AUDIT-MAP` как колонку «слот» перед git mv.
