# 🗺️ Реестры типов — карта путаницы + единый источник (РЕКОМЕНДАЦИЯ)

> **MAP-ONLY.** Ничего не переносить/переписывать по этому файлу без «строй». Это разбор + дизайн, не миграция.
> Задача: владелец флагнул путаницу «где вообще объявлены типы». Ниже — все места, наложения/противоречия,
> и рекомендованный ОДИН источник по собственной двухслойной модели скилла.

## 2. Наложения и противоречия

**C1 — ДВА конкурирующих «базовых» реестра, разной формы (S1 ⟂ S3).**
S1 (богатый, `homeRule`) и S3 (плоский `{name,scope,note}`) оба претендуют быть базовым словарём. Наборы
типов НЕ совпадают: S3 имеет `theme-card·synthesis·registry·INDEX`, которых нет в S1; S1 имеет
`overview·idea·gaps·handoff·journal·session-log·values·mechanisms·…`, которых нет в S3. SKILL (S5) ссылается
на S1 как базу — S3 остаётся «висящим» вторым базовым словарём другой формы. → неоднозначно, что «источник».

**C2 — ДВА разных ТИП-СИСТЕМЫ с одинаковыми именами (S4 ⟂ S1/S2).**
S4 говорит про «типы-разделы» = ШАБЛОНЫ ПАПОК с внутренней жёсткой схемой (`values`-карточка 5 полей,
`scenarios`-карта, `open-questions`-трекер). S1/S2 говорят про «типы-доки» = суффикс файла + `homeRule`.
Имена ПЕРЕСЕКАЮТСЯ, но значат РАЗНОЕ: `plan` в S4 = папка-шаблон с «мягкой последовательностью»; `plan` в
S1 = fileType `.plan.md`. `decisions` в S4 = папка-лог; в S2 = плюрал-контейнер внутри темы. Один термин —
две несовместимые семантики → главный источник путаницы.

**C3 — Устаревший совет уже частично снят, но жил в S4.**
S4 предписывал единую кучу `decisions/DECISIONS-LOG.md` — противоречит O-14 (распределённые decisions).
Помечено SUPERSEDED в S4 сегодня (U-4), но это симптом: S4 как «реестр» дрейфует и расходится с решениями.

**C4 — Три JSON-хранилища типов после U-3 (S1+S2+S3).**
Двухслойная модель скилла предполагает РОВНО два (глобал+оверлей). S3 — лишний третий, к тому же другой
формы. Пока он «сид», но по факту это третий список, который надо синхронизировать вручную.

**C5 — `node_type` (S6) ничем не связан с реестрами.**
Значения `node_type` во frontmatter (design-note, patch…) — де-факто типы, но не сверяются с id из S1/S2.
Хук U-2 их не валидирует (пока). Дрейф словаря неизбежен, пока источник не один.

## 3. Рекомендованный ЕДИНЫЙ источник (по двухслойной модели самого скилла)

**Принцип:** РОВНО два авторитетных хранилища данных + всё остальное = ВИД или проза-комментарий.

1. **S1 = единственный ГЛОБАЛЬНЫЙ базовый реестр** (`~/.claude/registry/doc-types.json`, богатая форма).
2. **S2 = единственный ПРОЕКТНЫЙ оверлей** (`docs/.doc-types.json`, та же форма, бьёт S1 по id).
   → Это и есть двухслойная модель из S5. Больше JSON-реестров типов НЕ заводить.
3. **S3 (`registry.seed.json`) → ДЕМОТИРОВАТЬ до заглушки.** Уникальные типы (`theme-card·synthesis·
   registry·INDEX`) — влить в S1/S2 (богатая форма, с `homeRule`), затем пометить S3 `superseded` со
   ссылкой на S1+S2 (историю не удалять). Плоская форма `{name,scope,note}` упраздняется.
4. **S4 (`section-types-registry.md`) → перевести из «реестра» в ПРОЗУ-КОММЕНТАРИЙ.** Его жёсткие
   внутр. схемы (5-полей `values`, карта `scenarios`, трекер `open-questions`) переносятся в поле
   `contentTemplate` соответствующих `folderTypes` в S1/S2 — там им место по схеме реестра. Сам .md
   остаётся как человекочитаемое обоснование, но с явной шапкой «НЕ источник типов; источник = S1+S2».
   Свести словарь «тип-раздел» ↔ «folderType» в ОДНУ ось (folderTypes уже несут `contentTemplate`).
5. **S6 (`node_type`) → сделать производным от id реестра.** Допустимые значения `node_type` = id из
   S1∪S2. Валидацию добавить в хук U-2 следующей волной (после того как единый источник закреплён).

**Итог-инвариант:** один глобал (S1) + один оверлей (S2) = ИСТИНА типов. `registry.seed.json` и
`section-types-registry.md` = superseded-стабы / проза. `node_type` и авто-виды/линты = ВИДЫ поверх S1+S2,
не вторые источники. Это ровно закон «указатель = вид, не хранилище» (U-5), применённый к самим реестрам.

## 4. Порядок исполнения (для будущей сессии, по «строй»)
1. Влить уникальные типы S3 → S1/S2 (богатая форма) · пометить S3 `superseded`-стабом.
2. Перенести жёсткие схемы S4 → `contentTemplate` в S1/S2 · шапка S4 «не источник».
3. Обновить §«Реестр типов» в SKILL.md: явно «источник = S1+S2; seed и section-registry — история».
4. (следующая волна) хук U-2 валидирует `node_type` ∈ id(S1∪S2).
> Каждый шаг обратим: supersede-маркер + заглушка + git-точка. НЕ рип-реплейс.
