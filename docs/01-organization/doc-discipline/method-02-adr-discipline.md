# 📜 ADR-дисциплина (по-своему)  ← P5

## Что это (модель владельца)
- ADR **не пишем как «ADR»** — внутри ADR лежат принятые **DL-пункты** (номер, поэтапно, что входит).
- ADR **опровергаем** — никогда не принимать за финальный/явный вывод.
- Внутри ADR — **анализы**, показывающие когда/почему решение возникло (не только вердикт).
- ADR **связаны друг с другом**; решения тянут за собой БД (ADR → влияние на схему/стек).
- ADR **на разных уровнях**: крупная глобальная идея важнее маленького ADR.

## Предлагаемая форма
ADR = **папка**: `analysis/` (когда/почему) · принятые `DL-*` · `status` (опровержим) · `level` (глобальный/локальный) · `links` (ADR↔ADR↔БД).

## Зачем (для кого)
Чтобы решения были прослеживаемы и обратимы (эволюция/rollback — конституция POS), а не «камень».

## Где ляжет в канон
`decisions/` — доработать конвенцию «ADR-как-папка»; связать с `DECISIONS-LOG.md` (DL) и форками D*.

## Открыто
- Сколько уровней ADR; как «уровень» отражается в навигации/визоре.
- Связь ADR → конкретное влияние на схему БД (как помечать).
