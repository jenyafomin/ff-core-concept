# Движение и самоперепроверка (тонкий слой поверх CGC)

> Зачем: планы систематически теряют целые ГРАНИ сущности (спроектировали ЗАПИСЬ памяти — забыли
> ЧТЕНИЕ/recall). Метод проверял глубину и качество, но не ШИРИНУ. Этот файл вшивает самоперепроверяющий
> цикл. НЕ дублирует законы ниже — только НОВЫЕ несокращаемые правила движения+самопроверки.
> Это третий компаньон семьи CGC (жизненный цикл) / MIGRATION-to-canon (переход) — тот же дом.

## Правила движения (R)
- **R-a Одна ветка, неглубоко, хендоф спланирован ЗАРАНЕЕ.** Сессия = ОДНА ветка плана; ведём до
  «правильной точки» захода, не тонем; чем закроем и что передадим — знаем в НАЧАЛЕ ветки. (рабочая модель §2/§7-D)
- **R-b Нет входа в «строй» без ПЕРЕПИСИ ШИРИНЫ.** Для сущности ТЕКУЩЕЙ ветки перечислены ВСЕ её грани;
  каждая либо закрыта веткой, либо явно отложена с домом (задача+дом). **Пустая незаявленная грань = блок.**
  Гейт ПОВЕТОЧНЫЙ (по сущности ветки), не глобальный. Пока нет generator-check (это долг D0, параллель
  гейту D0), держится РУЧНОЙ переписью в ревью — но цель машинная (иначе гейт-прозой, что мы и чиним).
- **R-c Первичный якорь ВЕРБАТИМ.** Каждая задача несёт `file:line` + дословную строку кода/дока — не
  пересказ (иначе пере-судим решённое кодом; урок FORK-3, HANDOFF §6).
- **R-d Волнами, не за всеми сразу.** Синхронно 3–6 агентов, ХАРВЕСТ между волнами (обрыв стоит одной
  волны). См. глобальное правило `orchestration-sync-under-gateway` (фон под шлюзом мёртв).
- **R-e LOSE-NOTHING · один дом · статус-не-удаление.** Как в `doc-tree.md` (law 2, 9, 10) — не повторяем.

## Принципы владельца (P)
- **P1 Ошибка в ПЛАНЕ — самая дорогая.** Ошиблись в постановке → результат обречён. Самая глубокая
  перепроверка (ширина + адверсариал) применяется к ПЛАНАМ, ПОСТАНОВКАМ, ЗАБЛУЖДЕНИЯМ — не только к коду.
- **P2 Автор ошибётся by default.** Любой продукт агента проходит независимую адверсариальную перепроверку
  ДО фиксации. Оркестратор раздаёт и проверяет — сам не авторствует.
- **P3 План, который сам учит реализацию.** Хорошая карточка-план несёт ключевые СВЯЗИ (какие точки должны
  быть реализованы) и КРЮЧКИ САМОПРОВЕРКИ, чтобы реализатор знал, как себя проверить — особенно где
  глубокая механика связей.

## Цикл движения (один оборот)
1. **FRAME** — назвать сущность ветки + чем закроем + хендоф (R-a). *механизм:* рабочая модель §2, CGC шаг 1–3.
2. **ШИРИНА / перепись** — перечислить ВСЕ грани сущности ветки; каждая: закрыта / отложена-с-домом; пустая = блок (R-b, P1).
3. **ГЛУБИНА / копнуть грань** — веткой добираем до «правильной точки», не тонем (R-a). *механизм:* CGC шаг 4 (процессор-скилл).
4. **ЯКОРЬ-в-реальность** — каждый вывод/задача на `file:line`+вербатим (R-c). Адверсариал ДО фиксации (P2).
5. **ХАРВЕСТ → передача** — волнами (R-d); результат в baton/handoff, не в бегуне; план несёт связи+крючки (P3). *механизм:* HANDOFF §7-D, CGC шаг 5–7.
6. **ОБРАТНАЯ-СВЯЗЬ** — повторяющаяся боль → `../../process/PROBLEM-LEDGER.md` (частота→приоритет S-сферы). *механизм:* CGC «петля улучшения».
