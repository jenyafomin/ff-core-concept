# Session-logging — как вести журнал сессии

> Статус: **experimental**, схема R3 (создан 2026-07-06, переписан 2026-07-17 по ратификации —
> `docs/02-project/core/01-brain/decomposition/01-model/01-node/analyses/RATIFIED-and-new-concepts-2026-07-17.md`).
> Путь POS: project → domain. Бэкап схемы «сессия=дата» — `SKILL.md.bak-2026-07-17` рядом.
>
> ⚠️ **Установлен ТОЛЬКО как проектный скилл** — `.claude/skills/session-logging/` внутри
> FF-Personal-Management (и это зеркало-канон в `docs/01-organization/rules-and-skills/session-logging/`).
> **НЕ установлен глобально** (`~/.claude/skills/session-logging/` не существует). В сессии 2026-07-17
> синхронизировать правку в `.claude/skills/session-logging/SKILL.md` не удалось — запись в `.claude/`
> (проектную и глобальную) блокируют разрешения текущей сессии. Канон правила фиксируется здесь; перенос
> в `.claude/skills/` — ручная задача владельца или следующей сессии с нужными правами. Устанавливать

## ⚠️ ЭТА СХЕМА ЗАМЕНЯЕТ старую («сессия = дата»)

Старый механизм — `docs/01-organization/session-handoff/<ДАТА>-<контекст>/` (committed в git, темы `NN-*.md`
внутри) — **больше не используется для НОВЫХ сессий**. Существующие папки этой схемы — исторический архив,
их **не переносим и не удаляем**. С 2026-07-17 логирование идёт по схеме ниже (R3): разговор вместо
сессии-даты, `logs/` целиком вне git.

## Ядро (одно правило, всё остальное — следствия)

**ТЕМА = ПРОЕКЦИЯ ДОКУМЕНТА, а не второй экземпляр контента.**
Суть работы всегда ложится в реальный канон-документ (brain, contract, реестр…). Лог разговора — это
ТОНКИЙ СЛЕД: что обсудили · через каких агентов · какие решения · **→ указатель на канон-док, куда легло.**
Логи не дублируют содержание — они проецируют и ссылаются. Это и удерживает систему от нагромождения.

## Структура (R3)

```
logs/                                ← ВЕСЬ каталог в .gitignore — ничего отсюда не коммитится
└── conversations/
    └── NN/                          ← новый разговор = команда /new (порядковый номер, не дата)
        ├── concept.json             ← id · started · topic · status · summary · canon_links[] · speeches[]
        ├── analyses/                ← разборы разговора (контейнер без номера; файлы внутри — NN-<slug>.md)
        ├── questions/                ← открытые вопросы разговора (тот же принцип нумерации файлов)
        ├── ideas/                    ← идеи разговора
        └── speeches/                 ← ПОЯВЛЯЕТСЯ, когда разговор разрастается: под-раунды NN/ внутри

docs/01-organization/session-handoff/
└── STATE.md                          ← ЕДИНСТВЕННЫЙ committed-указатель «где мы» (синк вручную из concept.json)
```

- **Разговор** (не «сессия-дата») = единица логирования; новый — по команде `/new`, нумеруется порядково.
- **`concept.json`** — единственный слой, который знает, куда легла суть (`canon_links[]`), и статус
  разговора; он же перелинковывает `analyses/questions/ideas` без физического копирования контента.
- **Сырой промпт владельца НЕ хранить** — ни в `logs/`, ни где-либо ещё, даже локально. Хранится только
  `summary` (сжатый смысл) и `canon_links` (куда это привело).
- **`STATE.md` остаётся единственной committed точкой входа** — краткое «где мы», синхронизируется вручную
  в конце разговора/сессии из `concept.json`. Сам `logs/` в git не попадает и историей репозитория не является.

## Схема `concept.json`

```json
{
  "id": "NN",
  "started": "YYYY-MM-DDThh:mm",
  "topic": "короткое название темы разговора",
  "status": "open | closed",
  "summary": "2-4 предложения — что решили/поняли, без пересказа контента",
  "canon_links": ["docs/.../реальный-документ.md"],
  "speeches": []
}
```

- `canon_links[]` — пути к реальным канон-документам, куда легла суть (единственная связь наружу).
- `speeches[]` — заполняется, когда разговор разрастается и дробится на `speeches/NN/` (список под-разговоров).
- Статус `closed` выставляется в конце разговора, вместе с финальным `summary`.

## Процедура

1. **Старт разговора (`/new`):** создать `logs/conversations/NN/` (следующий порядковый номер) +
   `concept.json` с `id`, `started`, `topic`, `status: open`.
2. **По ходу:** класть разборы/вопросы/идеи в `analyses/ · questions/ · ideas/` разговора; **дописывать**
   `concept.json` (не пересказ, только `canon_links` и обновлённый `summary`) сразу, не в конце.
3. **Правило роста:** разговор разросся (много под-раундов) → выносить в `speeches/NN/` внутри того же
   `logs/conversations/NN/`, регистрируя каждый спич в `concept.json.speeches[]`.
4. **Конец разговора/сессии:** дозаполнить `summary`, `status: closed`, финальные `canon_links`; **вручную**
   синхронизировать `docs/01-organization/session-handoff/STATE.md` (единственный committed артефакт).
5. **Память:** в конце — указатель в auto-memory, что `STATE.md` = точка входа (как и раньше).

## Кто запускает и как настраивать

- **Кто:** оркестратор сессии (Fable/главная модель) — вызывает в начале и в конце. Позже можно выделить
  отдельного агента-логгера (sonnet) со спец-скиллом, чтобы разгрузить оркестратора.
- **Как вызвать:** «залогируй сессию» / «оформи хендофф» / «/new» на старте нового разговора.
- **Настройка (единственный параметр):** номер разговора `NN` — присваивается по порядку, не задаётся вручную.
- **Инвариант:** не дублировать контент в логи; всегда заполнять `canon_links`; `logs/` никогда не коммитится;
  промпт владельца никогда не сохраняется дословно.

## Границы

- Нумерация контейнеров (`analyses/ questions/ ideas/ speeches/`) и файлов внутри них — по конвенции R1,
  которую ведёт `doc-discipline` (контейнеры без номера, файлы внутри — с номером). Этот скилл не
  переопределяет R1, только применяет его к `logs/`.
- Тип «состояние» (state) — отдельная сущность `docs/00-states/` (см. `doc-discipline`, R2); session-logging
  её не подменяет и не пишет туда.
