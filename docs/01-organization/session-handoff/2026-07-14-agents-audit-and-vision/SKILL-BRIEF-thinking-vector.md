# Бриф: набор скиллов «concept-first» (v2)

## Решения владельца (зафиксировано)
- **Имя главного скилла: `concept-first`.**
- **Делаем ДВА разных скилла:** (1) `concept-first`; (2) `doc-discipline` (дерево + конвенции + размещение) — ОТДЕЛЬНО (в v1 я ошибочно смешал их).
- **`value-decomposition`** остаётся ОТДЕЛЬНЫМ скиллом, которым `concept-first` **владеет/вызывает** (не сливаем). Ценности глобально уже заводит скилл-инициализация — заново не выводим.
- **`state-management`** — вероятно ещё один отдельный скилл (состояний НЕСКОЛЬКО, см. ниже) — позже.
- **Поиск альтернативных скиллов** (find/download, собрать кооперирующую команду с точки зрения loop-engineering) — задача в очередь, сразу после `concept-first`.

## Секция, которую владелец одобрил (оставляем как есть)
**Какую повторяющуюся боль лечит** (подходит для Fable):
1. Агент слишком рано уходит в реализацию — «чуть-чуть не та задача».
2. Не хватает ПОЛНОЙ КАРТИНЫ; сказанное ≠ реализованное.
3. Найденные решения/настройки забываются.
4. Вторая итерация не ложится автоматически в правильное место (нет механизма, есть только промпт).

## СКИЛЛ 1 — `concept-first` (главный результат для Fable)

### Роль (уточнено — «держать высоту» было плоско)
`concept-first` — **высотный диспетчер идей** в ДВУХ режимах:
- **режим высоты:** наблюдает сверху, оперирует МИНИМАЛЬНЫМИ данными, постоянно спрашивает «всё ли есть? всё ли готово? точно ли? как это проверить?»;
- **режим контроля процесса:** следит за ЦЕЛЬЮ и ХОДАМИ МЫСЛИ, может запускать несколько `fable-orchestrator` отдельно, чтобы разные разборы шли параллельно, а он сводил.
Он **не собирает контекст сам** и не сваливается в детали — он двигает к цели через правильные вопросы.

### Ядро — РЕКУРСИВНЫЕ вопросы (самое важное)
- Правильный вопрос уже содержит ключ к ответу. Это **рекурсия, а не разовый этап**: на вопросах строим
  абстракции → что-то понимаем → переформулируем/переструктурируем → вопросы начинаются заново, везде, всегда.
- Вопросы искать **итерациями с критикой** (иная призма). Это дёшево по токенам, но задаёт ПРАВИЛЬНЫЙ путь.
- **Не ставить лимит на вопросы** — наоборот, разворачивать рекурсию. Задача — определить ПУТЬ (а путей может
  быть много, зависит от задачи) и что из вопросов приоритетно. Вопросов может быть миллион, по разным
  направлениям (где-то анализ, где-то открытые вопросы, где-то ещё) — это нормальный фон его работы.

### Дисциплина высоты
Оставаться на уровне картины/ценностей/проекций. В реализацию — только по явному «строй».

### Форма вывода (важно для шлюза)
- Ответ в чат — **короткий**, но содержит **`concept.json`, который открываешь одной командой** и он уже несёт
  разные направления/вопросы, структурированные по себе. Рост картины = растущее дерево + `concept.json`-навигатор
  (механику дерева держит `doc-discipline`; форму навигатора ещё до-продумать отдельно).

### Само-улучшение
Может звать `fable-orchestrator`, добавлять критику, по ходу улучшать себя. Владеет/вызывает `value-decomposition`.

## СКИЛЛ 2 — `doc-discipline` (отдельный скилл: дерево, размещение, конвенции)

### Канон структуры
**Много информации → папка лучше, чем много мелких файлов; много мелких файлов лучше, чем один залепленный.**
Каждая абстракция — файл ИЛИ целая папка (overview-файл или overview-папка в зависимости от глубины); наслаиваются.

### Разрешение противоречия (владелец поймал)
«Right-placement: выход сразу в нужную папку» ↔ «структурируется со временем». Разрешаем так:
- клади **разумно сразу** в подходящее место; **переструктурируй позже** (это норма);
- сверху есть **единый консенсус деления**: `project` / `library` / `infrastructure` / `organization` — папка тоже
  должна попадать в правильный «дом». `doc-discipline` **советует** размещение и когда переструктурировать.

### Конвенция имён/типов (отдельная настройка, глобальная, расширяемая)
- Типы смежных тем, доступные глобально: `question` · `problems` · `gaps` · `analysis` · `decisions` · `overview`.
- Каждый тип — **файл ИЛИ папка** (напр. папка `gaps/` + `gap-<N>`; правило = нумерация/последовательность).
- Структуру папки описывает её **README** (базовые правила).
- Типы **версионируются** (напр. `analysis-v2`); разделитель точка-или-дефис пока не принципиально.
- Тип может нести **встроенные паттерны/промпты**, по которым действует (как «вшитый промпт, который реализуется»).
- Конвенция имён проектов (напр. `domains`): что домен обычно содержит — как правило, не жёсткий лимит.

## Смежное (НЕ в этот заход, зафиксировать чтобы не забыть)
- **`state-management` (отдельный скилл, позже):** состояний НЕСКОЛЬКО — проект / тема / план (глобальное — менее
  вероятно); состояния могут быть вшиты в промпты топиков/чатов; свои для frontend/backend и т.п. Короткое, но
  чётко показывает «где что и как лежит». Отделить от `CLAUDE.md`: CLAUDE.md **объясняет**, STATE — **текущее
  состояние**; разные темы = состояния разных процессов. Связано с loop-engineering.
- **Alt-skill search:** найти/скачать скиллы (`find-skills`/маркетплейс), собрать кооперирующую команду с точки
  зрения loop-engineering. Один такой процесс уже есть — его надо контролировать качественнее.
