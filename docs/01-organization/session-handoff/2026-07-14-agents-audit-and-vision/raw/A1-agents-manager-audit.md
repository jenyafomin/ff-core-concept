## Что за проект

`@dwizh/gateway` — Telegram→Claude Code шлюз (grammY + Claude Code SDK-раннер). Каждое входящее
сообщение резюмирует durable-сессию Claude, агент делает один ход, процесс завершается. Статус в
README: **M4 — один бот end-to-end (MVP)**, плюс M4.5 (каскад конфигов диалога, voice, /model,
usage-хедер). Слои: `core` (контракты) ← `server` (routing/queue/approval/persistence/orchestration)
← `claude-runner` (SDK) / `channel-telegram` (grammY) ← `app` (композиционный корень).

Доки организованы в новую древовидную схему `docs/00-organization/` + `docs/01-project/` (ценности →
идеи → архитектура → проблемы), но рядом ещё живёт **старая** плоская схема `docs/architecture/`,
`docs/spec/`, `docs/plan/`, `docs/log(s)/`, `docs/handoff/` — реорганизация (см.
`docs/journal/2026-07-07-docs-restructure-and-next.md`) сделана НЕ до конца, обе схемы активны
одновременно.

## Механизм 1 — Авто-подтверждения / autopilot (approval)

**Готовность: ~35% (архитектура решена на бумаге, код = только предыдущий слой ADR-0001).**

**ЕСТЬ в коде (активно):**
- `src/claude-runner/sdk-tool-gate.ts` — `SdkToolGate`: read-only тулы (`Read/Glob/Grep/LS/
  NotebookRead/TodoWrite`) → авто-allow всегда; всё прочее (Write/Edit/Bash/…) → кнопки владельцу
  (3 кнопки: Да/Нет/Всегда через SDK `updatedPermissions`, `destination: 'localSettings'`).
- `src/server/approval/keyword-approval-policy.ts` — грубая эвристика по ключевым словам в промпте
  (`rm -rf`, `drop table`, `force push`, `удали`, `снеси`...) — это ВЕСЬ текущий "классификатор
  опасности". Никакого green/yellow/red-инварианта из ADR-0002(access-roles) в коде нет.
- `src/server/approval/approval-gate.ts`, `tool-approval-gate.ts` — гейт ждёт `/approve`/`/reject`.
  Fail-open, если approval-контекст отсутствует (`console.warn` + allow) — осознанный компромисс
  MVP "один владелец", explicitly помечен как несовместимый с моделью ролей (см. ADR ниже).
- `docs/01-project/problems/P3-approval-buttons.md` — 2 живых бага починены в коде (ZodError на
  compound-командах, "кнопка без реакции"), но **"ждёт рестарта/деплоя для подхвата"** — статус
  верификации не закрыт.

**ЕСТЬ только в доках (спроектировано, код НЕ начат):**
- `docs/architecture/ADR/ADR-0002-access-roles-and-approval-policy.md` (Status: **draft**) — полная

  durable-очередь отложенных RED, fail-closed при неизвестном юзере, флаги `GATEWAY_ROLES` /
  `GATEWAY_AUTOPILOT` / `GATEWAY_DELEGATED_APPROVAL`. **Ничего из этого не реализовано** — нет
  `IUser`, нет `PermissionPolicy`, нет durable-очереди, нет классификатора green/yellow/red.
- **Addendum 2026-07-11** (тот же файл, низ) — именно то, что просил владелец в задании: 3 режима
  (`ask-each` / `light-confirm` / `full-auto`), меню длительности `1ч·2ч·3ч·день·навсегда`,
  sonnet-ревьюер (закрывает V-4). Это **чистый текст решения**, ни одна строка кода не написана.
  `light-confirm` — вообще новый средний ярус, которого не было в §Decision(б) до аддендума.
- **Открытый вопрос V-6 "навсегда vs fail-closed"** — НЕ решён, только сформулирован с рекомендацией
  (а: "навсегда" только для YELLOW, RED/deny-list/сеть — всегда под гейтом). Владелец не подтвердил.

**ЧЕГО НЕТ вообще (ни в коде, ни в доках):**

## Механизм 2 — Управление агентами через топики + уровни ответа

**Готовность: ~40% (persona-по-топику и mute РЕАЛИЗОВАНЫ; уровни "молчит пока не позовут" и вся
адресация/handoff — только дизайн).**

**ЕСТЬ в коде (активно):**
- **Persona-по-топику** — `src/server/routing/router.ts`: `agents.findBinding(botId, threadRef)`,
  откат на bot-wide default, если нет топик-специфичной привязки. Реализовано и покрыто тестами
  (`router.spec.ts`, `scope-routing.spec.ts`).
- **`reportsToChat` (TM-9, режим "всегда молчит")** — `src/core/domain/agent.interface.ts:27`,
  `src/app/registry.config.ts:142`, `src/server/orchestration/turn-executor.ts:416-419`: если
  `agent.reportsToChat === false`, ход исполняется, персистится, но НЕ отправляется в чат
  (`🔇 агент тихий`). Это закрывает ровно уровень **(в) всегда молчит** из задания.
- Один бот = одна Telegram-идентичность, несколько агентов/ролей в реестре (`Bot`/`Agent`/
  `AgentBinding` TypeORM), один бот отвечает в разных топиках разными персонами через binding —
  но это ОДИН физический бот-токен с разными agentId, не "несколько независимых ботов в одном чате".

**ЕСТЬ только в доках:**
- Уровень **(б) "молчит, пока не вызовут по нику/команде"** — НЕ реализован. Ближайшее — дизайн-
  документ `docs/01-project/ideas/2026-07-08-multibot-addressing-and-lifecycles/addressing.md`
  (Status: **draft, код не начат**): 7 механизмов (reply-policy как scope-binding, брокер-ставки,
  мульти-mention-конклав, talking-stick handoff+TTL, floor-control mute/barge-in, роль-адресация,
  owner-facing "пульт"). Это богатая архитектура, но НИ ОДНА идея из неё не имеет кода — только
  README-уровня концепт с 7 открытыми вопросами внизу (в т.ч. "с какой политики стартует новый топик").
- `docs/01-project/ideas/2026-07-08-multibot-addressing-and-lifecycles/lifecycles.md` — "спящий
  агент, не тратит токены пока молчит" + адресация `@агент` — тоже draft/README, не код.
- `docs/01-project/01-architecture/00-system/egress-and-multiagent.md` (T3 топик=агент, T4 ленты) —
  статус "в очереди" по `docs/logs/topics.md`.

**ЧЕГО НЕТ:**
- Нет @mention-парсинга уровня "позвать по нику" в `parse-control.util.ts` / ingress.
- Нет "уровня ответа" как явного поля/enum на биндинге (`always` / `on-mention` / `silent`) —

  — это грубый keyword-фильтр деструктива в промпте ПЕРЕД ходом, не модель-ревьюер команд/tool-calls.
  Не то же самое, что "sonnet проверяет команду на подвох/эксплойт".

**ЕСТЬ только в доках (фрагментарно, не собрано в одну идею):**

  родственник "AI Guard", но **узко** заточен под YELLOW-авто-одобрение в режиме сна, не под общую
  проверку "любой команды на эксплойт". Только текст решения, нет кода.
- "Агенты отчитываются кто/куда" — частично покрыто `reportsToChat` + "живая строка пульта" (идея #7

  механизм (ближайшее — брокер-ставки на шине, идея #2, но это про выбор говорящего, не про триггер
  реакции на чужой ответ).
- `grep -rli "ai.guard|aiguard|guard-review|guardian"` по всему репо — **0 совпадений** кроме одной
  ссылки на абстрактную ценность "05.1 гуарды-vs-инструкции" в `lifecycles.md` (концептуальная линия
  "детерминированный гуард vs инструкция", не конкретный AI Guard механизм).

**ЧЕГО НЕТ вообще:**
- Нет отдельного ADR/Spec на "AI Guard" как сущность.
- Нет модели межагентного триггера ("агент Б реагирует на ответ агента А").
- Нет общей проверки команд на эксплойт вне approval-flow (т.е. защита есть только в момент
  tool-call к Claude Code SDK, не как независимый слой над любым исходящим действием).

"всегда молчит" уже есть**; добавить **уровень (б) "молчит, пока не позовут"** — это, по сути,
дописать один enum-режим на существующий `AgentBinding`/`reportsToChat` + парсер @mention в
`parse-control.util.ts` (тот же слой, что уже трогали для командных префиксов) — минимальный шаг
поверх готовой инфраструктуры, а не новая архитектура.

Второе по готовности — approval-gate ADR-0001 (SdkToolGate, 3 кнопки, "Всегда") — стабильный,
рабочий, протестированный слой, на который наслаивается всё из ADR-0002-access-roles. Но сам
