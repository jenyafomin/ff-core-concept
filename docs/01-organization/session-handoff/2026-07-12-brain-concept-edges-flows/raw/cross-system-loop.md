# Дайджест: система агентов + Loop Engineering — точки стыка с Brain

- **Дата:** 2026-07-12
- **Источники:** FF + agents-manager (кросс-проект)
- **Цель:** собрать ЦЕННОСТИ системы агентов и ключевые идеи Loop Engineering, чтобы понять, как Brain (память) и система агентов работают как ОДА целое.

---

## 1. ЧТО УЖЕ ЗАФИКСИРОВАНО — цели и ценности системы агентов (FF)

### Цели памяти (Brain)
Из `docs/topics/10-synthesis/2026-07-04-GOALS-why-memory-and-agents.md`:

- **Главная цель:** спроектировать **единицу памяти** (волна/частица) — может быть группой, файлом, пунктом, грани; решает **главную проблему многомерности информации**.
- **Ценности единицы:** субстрат для агентов · дешёвое понимание · накопление между сессиями · эволюция без ломки.
- **Грани:** scope одновременно общая/проект/агент/пользователь; актуальность; версии/наследование.

### Цели агентов
- **Функция:** руки, которые читают граф, делают работу, пишут обратно (с **глубиной**: N-агентное обсуждение, лупы, не 1:1).
- **Стратегии агентов эволюционируют:** разные удобные стратегии/выборы появляются со временем, не фиксировано.
- **Агенты — причина, по которой память должна быть agent-first** (не notes-first, не файлы-в-центре).

### Сквозная цель: самоулучшение (два уровня)
- Уровень системы/каркаса: механизмы, промпты, скиллы, стратегии.
- Уровень знаний на ходу: хрупкие, требуют чистки, переструктурирования, версионирования, повышения качества.

### Зачем вместе (единая система)
Два механизма одной самоподдерживающейся системы:
- **Память = субстрат**, агенты = рабочая сила.
- Оба plug-in-готовы.
- Наверху — **одна голова, распределяющая ресурсы** между продуктами (FF, 7days, др.).
- Общее дерево-граф — дешёвый слой ориентации.

### Стандартные проблемы, которым система обязана отвечать
Деградация/устаревание знаний · дубли и конфликты · где записывать (scope/топик) · как дёшево понять «что есть» · эволюция схемы без ломки старых версий · готовность быть частью большей системы.

## 2. Loop Engineering — 5 ключевых идей (ВНЕ проекта)

Источник: `/Users/mac16/Documents/IT/Apps/TOOLS/agents-manager/docs/plan/PLAN-0002-loop-engineering-adoption.md`

### A. Машинная единица паттерна — гибкость через данные
**Идея:** петля описывается **декларативной схемой**, не зашивается в код.

```
Паттерн (реестр):
  id · goal · cadence · risk · tools · skills · state · phases
  human_gates · cost{noop/report/action, daily_cap, early_exit}
```

**Ценность:** менять поведение петли = менять поле данных, не писать код → гибкие настройки, plug-in-модульность, проектируемость.

**Как ляжет на Brain:** паттерны хранятся как узлы типа `loop-pattern` или `system-instruction` в графе; агенты читают их как описание-в-данных, применяют, улучшают поля.

### B. Три примитива безопасности автономии
1. **Worktree-изоляция:** каждая правка кода агентом → отдельный git-worktree; REJECT/эскалация → worktree удалён.
2. **Verifier-гейт:** контракт — исполнитель не помечает done сам; отдельный агент/модель проверяет.
3. **Circuit breaker:** авто-стоп петли по счётчику попыток/токенов.

**Ценность:** контролируемая автономия, дебагируемость, откат возможностей. Brain записывает состояние гейтов как узлы `verification-report`, `circuit-status`.

### C. Наблюдаемость на полях паттерна
Повесить мониторинг на поля единицы паттерна; срезы по вектору: тема / риск / стоимость / фаза.

**Что видно:** текущий контекст агента (A1) · стоимость-на-сессию (A2) · граф делегирования (A3).

**Ценность:** управляемость без ручного сбора; сигналы для диспетчера (когда пауза, когда эскалировать).

### D. Гибкое форматирование (Telegram rich-HTML)
Агент выдаёт **структуру/таблицу** прямо в чат (Rich HTML — таблицы, списки, сворачиваемые блоки), не текстовый отчёт.

**Ценность:** меньше шума, собственник контролирует как данные показываются.

### E. Loop-prompting + чек-лист готовности
- `loop-audit` — внутренний чек-лист (skills, state, constraints, cost, budget) ДО запуска петли.
- `loop-pause-all` флаг в STATE — kill-switch.

**Ценность:** система сама себя ограничивает, предотвращает деградацию. Brain хранит audit-лог как узел типа `loop-readiness-check`.

## 3. Точки стыка Brain ↔ Агенты: где они обязаны договориться

### 3.1 Единица памяти = единица для агентов
**Что это значит:** волна/частица памяти (узел графа) = то, с чем агент работает, улучшает, передаёт дальше.

**Требование:** узел должен:
- Нести достаточно контекста, чтобы агент понял, что делать.
- Быть достаточно мелким, чтобы агент мог**локально** его улучшить (не трогая весь граф).
- Быть версионированным (история: кто писал, когда, почему изменилось).

### 3.2 Граф знаний = субстрат диспетчера и агентов
**Что это значит:** диспетчер гидрирует своё состояние из графа; агенты читают контекст оттуда же.

**Требование:** граф должен хранить:
- Сессии, темы, задачи, планы, шаги (Task/Plan/PlanStep из agents-manager).
- Паттерны лупов (Блок A из loop-engineering).
- Статусы гейтов, верификаций, circuit-breaker (Блок B).
- Audit-логи (кто что менял, когда, почему).

### 3.3 Лупы/петли = инструкции в памяти для агентов
**Что это значит:** петля не живёт в коде; она описана в памяти (паттерн + гварды + фазы).

**Требование:** агент должен уметь:
- Читать паттерн петли как узел типа `loop-pattern`.
- Понимать фазы (phases), гварды (dependsOn), риск-класс (riskClass).
- Адаптировать поля паттерна на основе реальности (если cadence 1d не работает, менять на 2d).

### 3.4 Модульность = плагины расширяют память и добавляют агентов
**Что это значит:** плагин = система с собственной БД и агентами, подключаемая к центральной памяти.

**Требование:** память должна:
- Иметь гибкие точки расширения (новые типы узлов, категории, фасеты).
- Ограничивать scope плагина (ABAC/клапан) — плагин видит только свои данные + general узлы.
- Позволять плагину переиспользовать узлы (многомерность, фасеты).

### 3.5 Самоулучшение = цикл: работа → анализ → улучшение
**Что это значит:** агенты работают → улучшают граф (узлы, связи, метрики) → граф подсказывает лучше → агенты работают лучше.

**Требование:** память должна:
- Допускать изменения узлов за счёт агентов (edit-права).
- Отслеживать качество узлов (score, freshness, deprecated).
- Позволять диспетчеру видеть узлы-проблемы (старые, конфликтующие, неиспользуемые).

### 3.6 Разделение сущностей (Task vs Plan vs Job, Session vs Topic)
**Что это значит:** разные слои абстракции; каждый слой понимается агентами и диспетчером отдельно.

**Слои (из agents-manager):**
- **Task** = намерение («что надо»), статус, провенанс.
- **Plan** = чёткая цепочка шагов, гварды, фазы.
- **PlanStep** = шаг с риск-классом, зависимостями.
- **Job** = durable-исполнение одного шага или подпроцесса.
- **Session** = контекст агента, один на топик.
- **Topic** = проекция сессии в Telegram.

**Требование:** Brain должен это различать (не путать план-данные с исполнением-данными).

## 4. Вопросы про объединение Brain + Система агентов (нельзя решать отдельно)

### Q1: Как граф представляет паттерны лупов, чтобы агенты их понимали?

**Почему не решается отдельно:** паттерн (loop-engineering Блок A) = данные, а не код. Если Brain не может хранить и выдавать паттерны структурированно, агенты не смогут их читать и адаптировать. Разделение = система ломается.

**Что спроектировать:**
- Тип узла `loop-pattern` с полями (goal, cadence, risk, tools, skills, phases, cost-budget).
- Как агент читает паттерн и применяет его (API, прямое обращение к графу, кэш).
- Как паттерн версионируется (история изменений, откат).
- Какие роли могут менять паттерн (только администратор? агент? система?).

### Q2: Где и как сохраняется состояние петель; как диспетчер гидрируется после рестарта?

**Почему не решается отдельно:** диспетчер (agents-manager) восстанавливает состояние из таблиц БД (Session, Plan, PlanStep, LoopRun). Если Brain — это тот же граф, то гидрация диспетчера = гидрация из графа. Но как? Структура ячеек графа vs структура сущностей SQL — нужно согласовать.

**Что спроектировать:**
- Какие узлы графа соответствуют Session/Topic/Plan/PlanStep (маппинг).
- Как диспетчер выводит состояние из графа (запросы, индексы).
- Какова интерфейс гидрации (API, прямое обращение).
- Как быстро это работает (оптимизация для рестарта <1с).

### Q3: Как агенты пишут обратно в граф, не ломая целостность; какие гварды?

**Почему не решается отдельно:** агенты улучшают узлы (Task → plan, поле cadence, кэш результата). Это изменения в памяти. Если нет гарда → риск деградации (конфликты, версионирование, ломка связей). Памяти и агентам нужны общие правила целостности.

**Что спроектировать:**
- Транзакции (ACID) для изменений узлов.
- Версионирование и откат (в памяти, не в git).
- Конфликты и их разрешение (две стратегии одновременно, что выигрывает).
- Audit-лог (кто писал, что писал, когда, почему).
- Верификация (перед коммитом, агент vs система; Блок B loop-engineering).

### Q4: Как плагины подключаются к памяти; какие точки расширения обязательны?

**Почему не решается отдельно:** модульность (цель ff) = плагин должен жить в своём пространстве, но видеть общие узлы. Если нет единого интерфейса расширения памяти, плагины либо копируют данные (рассинхрон), либо не могут подключиться.

**Что спроектировать:**
- Scope плагина (ABAC: какие узлы видит; default-deny или default-allow).
- Новые типы узлов (плагин добавляет свой тип, граф это понимает).
- Фасеты/проекции (узел видится по-разному из разных плагинов).
- API расширения (как плагин регистрируется, как читает/пишет).
- Изоляция ошибок (плагин упал, соседи живут).

### Q5: Как разделяются права между агентами и пользователями при работе с одним графом?

**Почему не решается отдельно:** агент работает под скопом (principal × project × role); пользователь видит свой срез. RBAC/ABAC/ReBAC (владелец 04.07) = критичны. Если нет согласованной модели прав, плагины либо обходят ограничения, либо не могут работать.

**Что спроектировать:**
- RBAC (роли: editor, viewer, admin).
- ABAC (атрибуты: scope, risk-class, principal).
- ReBAC (права по рёбрам: узел → фасет → плагин → видит/не видит).
- Линз/фокус (узел в памяти существует, но показывается или скрывается в зависимости от линзы).
- Гранты (владелец даёт право агенту на действие, узел `grant` в памяти).

### Q6: Какова архитектура памяти, чтобы она росла/эволюционировала вместе с системой агентов?

**Почему не решается отдельно:** со временем типы узлов меняются, структуры растут, категории расширяются. Если нет плана миграции и версионирования, старые данные ломаются или требуют ручного рефакторинга. Самоулучшение (цель ff) = память должна апгрейдиться сама.

**Что спроектировать:**
- Версионирование схемы (v1 → v2 → v3 без потери данных).
- Адаптеры между версиями (узел v1 читается как v2 через адаптер).
- Миграционные скрипты (как населяют новые поля).
- Откат версии (если новая версия не работает, вернуться).
- Автоматическое улучшение (система сама пересчитывает индексы, очищает дубли, обновляет кэши).

## Краткие резюме стыков

| Стык | Требование | От Brain | От Агентов |
|---|---|---|---|
| Единица памяти | Волна/частица: достаточно контекста, локально улучшается, версионируется. | Узел графа с историей | Читают, понимают, пишут обратно |
| Граф как субстрат | Хранит Task/Plan/PlanStep, паттерны, гейты, audit. | Индексы, быстрые запросы | Гидрация диспетчера |
| Лупы как инструкции | Паттерны описаны в данных, не в коде. | Узлы типа `loop-pattern` | Читают поля, адаптируют |
| Модульность | Плагины видят свой scope, общие узлы. | Гибкие точки расширения | Плагин-агенты видят свой universe |
| Самоулучшение | Агенты пишут, граф анализирует, диспетчер улучшает. | Транзакции, версии, audit | Анализирует качество узлов, пишет улучшения |
| Сущности | Task ≠ Plan ≠ Job ≠ Session. | Разные типы узлов | Понимают разницу, не путают |
