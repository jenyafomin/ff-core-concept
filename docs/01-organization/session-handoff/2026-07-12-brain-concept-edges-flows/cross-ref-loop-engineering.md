## Что важно: это НЕ дубль — это стыковка двух половин
Их линза = **схема данных агентной системы**; наша линза = **природа единицы памяти (узел/связь)**.
Обе целятся в ОДНУ модель данных (их keystone: «единая схема БД»). Совпадений много, но каждая
сторона закрывает то, чего нет у другой.

## Что это меняет для нашего вопроса Fable
1. **«Память-как-инструмент» (наш §3.4) уже частично решена там** (F6 = слой процесса + ChangeTrace/CommitLink
   для диффов за сессию). → в вопрос Fable добавить: наш ответ должен быть СОВМЕСТИМ с F6, а не изобретать заново.
2. **Наш центр (узел vs связь) — это ровно их пробел.** Ребро как первоклассная сущность в их схеме не
   выражено. Значит решение по ребру у нас = вклад в общую ER-схему (их задача Fable №1 «ER-схема»).
3. **3 scope vs 5 storageLevel** — надо свести в одну ось (иначе два разных языка про «где живёт»).
4. **Единый `canonicalId`/UUID** (их F10) — наша ось Тождества (Ц-2). Общий ключ для слияния БД.

## Развилка владельцу (стратегическая)
Два трека Fable складываются в один вопрос о **единой модели данных**:
- **(A) СЛИТЬ:** один заход Fable по объединённой схеме (память-узел/связь + сущности агентов + локальность).
  Плюс — цельность; минус — большой объём за раз.
- **(B) МОСТ:** наш вопрос Fable остаётся про узел/связь, но с явной привязкой «совместимо с их 15 задач БД»;
  их DB-трек идёт своим ходом; синхронизируем через `canonicalId` и этот мост. Плюс — параллельно и дёшево.

> Рекомендация (предварительно): **(B) сейчас** — наш острый вопрос про узел/связь закрывает их пробел и
> даёт им недостающий кусок; полное СЛИЯНИЕ (A) — когда обе стороны отдадут свои куски. Решает владелец.
