## 1. Суть в 5 строк
N-008…N-016 не ломают 5 правил — дают им ФИЗИКУ: типы-папки (N-008)=дом для «тип⇒место», wildcard-правила (N-011)=движок размещения, домены (N-010)=параметризованный тип, БД (N-014)=вид над файлами.
Три «способа раскладки» (тип·дата·символ-префикс) — не конкуренты, а три ОРТОГОНАЛЬНЫЕ оси: идентичность/время/порядок. Путём и id владеет только тип; дата и символ — украшения. Если символ/дата попадут в id — вернётся болезнь реоргов (конфликт с R3).
Wildcard-scope решается каскадом как CLAUDE.md/.gitignore: правило со `scope: self|subtree`, агент идёт ВВЕРХ по предкам (O(глубины)), не сканирует дерево.
Домены vs freeze: замораживается КОНТРАКТ типов/доменов и скелет, НЕ экземпляры; экземпляры растут свободно (N-016); новый тип/домен = версионированный gated-акт.
Стресс-тест: brain и дерево доков делят ОДИН структурный закон (граф типизированных self-describing ячеек со стабильным id и рёбрами), но РАЗНЫЙ жизненный цикл (доки не забывают; brain метаболизирует/забывает/стирает-по-согласию). Один скелет — два обмена веществ.

## 2. Переформулировка (раунд 2)
Риск сместился: не «нет закона роста», а «законов размещения теперь ТРИ, и они могут снова закодировать смысл в путь». Задача — свести N-008…016 к ОДНОЙ грамматике, где ровно одна ось владеет идентичностью, остальное — виды и украшения. Плюс: не изобретаем ли для доков вторую дисциплину, когда brain уже проектирует первую.

## 3. Задача 1 — Грамматика v1 (обновлённая)

**R1 · Тип ⇒ место** — материализован:
- N-008: в проекте папка `types/` со структурой каждого типа; тип самоопределяется во frontmatter. Физический наследник section-types-registry.
- N-010 домены = мета-тип: экземпляр параметризует структуру (backend→endpoints, frontend→hooks). Единая точка = один реестр.
- N-011: размещение как ПАТТЕРН, не хардкод-путь.
- N-016: НЕТ бестиповых папок — каждая описана структурой (или новым вариантом описания).

**R2 · Рост локально-монотонный** — уточнён N-013:
- Дата-поток = БУФЕР ПРИЁМА, не дом. Из потока документ переезжает в типовой дом.
- «Предугадывать» (ideas ⇒ папка-под-идею) разрешено, не обязательно. Перенос между родителями — только с tombstone-редиректом.

**R3 · Идентичность = id, не путь** — усилен против N-012/N-013:
- Префиксы (`_ % +`) и даты живут в ИМЕНИ файла, но НЕ в id (поле frontmatter).
- ⚠️ Конфликт: N-012 в лоб (префикс = часть адреса) ПРОТИВОРЕЧИТ R3. Разрешение: префикс — только сортировочный ярлык, ссылки всегда по id.

**R4 · Ничего не умирает (supersede)** — расширен на структуры:
- Версии типов (N-008) и «переписываемая структура домена» (N-010) подчиняются supersede: смена контракта = новая версия+draft, не тихая правка.

**R5 · Скелет заморожен** — точнее:
- Freeze покрывает: корни + набор ТИПОВ/ДОМЕНОВ + их контракты. НЕ покрывает экземпляры (растут вглубь безгранично, N-016).
- Новый тип/домен, смена контракта, новый корень, перенос узла ур.1-2 — gate/ADR.

**Три несущих механизма (новые):**
- **Ось-модель (напряжение a):** тип (владеет путём+id) · дата (журнал приёма) · символ-префикс (ранг сиблингов). Ровно ОДНА ось владеет идентичностью.
- **Каскад правил (напряжение b):** wildcard-правило `scope: self|subtree`, лежит рядом с узлом; агент резолвит вверх по предкам (как CLAUDE.md-каскад/.gitignore/CSS) — O(глубины). `baked`=`subtree` у предка; `local`=`self`.
- **Вид vs истина (напряжение d):** файл = истина (контент + рёбра: id, type, related-ids, status). БД = ПРОИЗВОДНЫЙ вид (агрегации, обратные ссылки, роллапы N-009, эмбеддинги). Инвариант: всё в БД ВОСПРОИЗВОДИМО пересканом; невоспроизводимое = в файле, не в БД.

**4 напряжения — сводка:**
- (a) символы vs даты vs тип — три ортогональные оси, не конкуренты. Опасность только если N-012/N-013 просочатся в id/путь; R3 запрещает.
- (b) wildcard-scope — ко-локальные каскадные правила, не скан дерева.
- (c) домены vs freeze — механизм разрешает, создание/смена = gated-акт + реестр; freeze защищает контракты, не экземпляры.
- (d) БД vs файлы — граница = воспроизводимость пересканом. Совпадает с хребтом brain: DATA=«что я есть» (файл) · DB=«что мы вместе» (индекс).

**P3 (гейт версий) — мягкая доработка:**
Гейт = не «разрешение человека», а КЛАССИФИКАТОР внутри скилла «работа с деревом»:
- добавить в существующий дом / экземпляр известного типа = R0-R1, агент сам, молча.
- новый тип/домен/вариант структуры, перенос, новый корень = R2+, агент кладёт `draft`, активирует владелец.
Граница «self-service для экземпляров / стейджинг для грамматики». Владелец активирует только малый класс грамма-меняющих актов.

## 4. Задача 2 — Стресс-тест против brain (7 ценностей)

| Ценность | Вердикт | Почему |
|---|---|---|
| Ц-1 Читаемость | Поддерживает | Агрегатор-индекс (N-009) = дешёвая линза над группой = progressive disclosure. |
| Ц-2 Тождество | Поддерживает, но требует | Ячейка в двух группах = одна ячейка ⇒ id независим от группы/пути (валидирует R3). |
| Ц-3 Доверие | Нейтральна(+) | Нужен лишь status/provenance-ярлык во frontmatter. |
| Ц-4 Витальность | **Конфликтует** | Brain хочет забывание/распад; доки по R4/N-002 не умирают. Разные политики удержания. |
| Ц-5 Суверенность | Поддерживает (сильно) | N-008/N-016: папка self-defines тип = policy-as-data на уровне доков. |
| Ц-6 Реляционность | Поддерживает (ядро) | «Самосвязывающийся граф» = буквально Реляционность; апгрейд: ребро может стать узлом. |
| Ц-7 Согласие | Нейтральна / частичный конфликт | «Право на забвение» конфликтует с never-delete. |

**Вывод: один структурный закон, две дисциплины жизненного цикла.**
- Общее ЯДРО: граф типизированных self-describing ячеек со стабильным id и рёбрами-первого-класса ⇒ дерево доков МОЖЕТ быть первым живым экземпляром субстрата brain (догфуд).
- Разный МЕТАБОЛИЗМ: доки = append+supersede, не забывают; brain = метаболизируют, забывают, стираются по согласию.
- Мирит их **policy-as-data**: каждая ячейка несёт политику (`retention: keep` vs `retention: metabolize`). Один движок графа — параметр на ячейке.

Ответ владельцу: **да, модель «ячейка→группы→граф» оправдана как СТРУКТУРА** (5/7 поддерживают/нейтральны). НЕ оправдана как единый жизненный цикл: там где brain забывает (Ц-4, Ц-7), доки обязаны НЕ копировать brain.

## 5. Ранжированные идеи
1. **Три ортогональные оси, путём владеет только тип.** Убивает «третий способ раскладки». Риск: префикс/дата не должны течь в id — чекер.
2. **Каскад wildcard-правил вверх по предкам (CLAUDE.md/.gitignore).** Scope за O(глубины). Риск: конфликты правил — ближайший предок побеждает.
3. **Freeze покрывает КОНТРАКТЫ, не экземпляры.** Закрывает «домен vs заморозка». Риск: частое «пишу новый вариант структуры» — считать в freeze-счётчик.
4. **Один закон + policy-as-data для удержания.** Доки = первый экземпляр brain. Риск: связь с недопроектированным brain — брать только ядро (id, тип, ребро, self-describe).
5. **БД = воспроизводимый вид, файл = истина+рёбра.** Не раздваивает правду. Риск: авторствовать связи в БД — инвариант «воспроизводимо пересканом».
6. **Гейт = классификатор в скилле, не бюрократия.** Self-service экземпляры / стейджинг грамматики. Риск: неверная классификация — дефолт «сомнение ⇒ draft».
7. **Домен = мета-тип + единый реестр + 8-10 пунктов + анти-разрастание.** Риск: реестр доменов разрастётся — применить к нему же группировку.
8. **Дата-поток = буфер приёма, не дом.** Не даёт дате стать вторым topics/. Риск: застревание в потоке — «уборка потока» при ревью.
9. **Ребро как узел (edge-with-passport) — заложить возможность сейчас.** Реляционность требует; ретрофит дорог. Риск: преждевременная сложность — пока related-by-id, но id-схема допускает «id ребра».
10. **Агрегатор-индексы = линзы; глобально ИЛИ локально через scope-поле.** Риск: дубль идеи — один экземпляр по id, индексы ссылаются.
11. **Забывание/стирание — явно вне доков-дисциплины.** Иначе архив начнёт «забывать» историю решений. Риск: если владелец захочет забывание в доках — policy-as-data на ветке, не дефолт.

## 6. Самокритика раунда 2
1. «Один закон, две политики» связывает темп доков с темпом brain — замораживать только стабильное ядро brain (id, тип, ребро), не ждать движка.
2. N-012 символы-приоритеты — соблазн якоря в путь; на практике владелец начнёт ссылаться на префикс. Нужен линт «ссылка по id, не по имени».
3. Каскад правил вводит невидимую сложность (правило далёкого предка влияет неявно). Нужен способ «показать эффективные правила узла» (как computed styles).
4. N-014 (нужна БД) рискует стать отговоркой «спроектируем потом»; пока БД нет — держится на ручных индексах = дрейф. Минимальный линт нужен РАНЬШЕ БД.
5. N-010 примеры (backend/frontend/endpoints) — из мира КОДА; проверить доменную модель на не-кодовом проекте («жизнь человека»).
