## Контекст
Продолжаем 3-й переход структуры документации. Тема раунда: **глобализация** дерева
(перенос дисциплины на ВСЕ проекты, а не только FF) + подготовка одной глубокой сессии Fable
для критического разбора. Фаза = ДИЗАЙН, ещё НЕ строим.

## Решения этого раунда (узлы)

- **N-001 · decision · Порядок = глобально сразу.** Не ждём полной обкатки на FF —
  переписываем `~/.claude/CLAUDE.md` на новую древовидную структуру сразу. Причина владельца:
  хотим управлять всем полноценно с самого начала. *(tension-with: 3 реорга за месяц, схема ещё не стабильна — см. слабые места.)*
- **N-002 · decision · Старое не удаляем.** `base/` и `topics/` (и старый глобальный CLAUDE.md)
  сохраняем как **read-only архив** + явные отсылки «где это лежит». Позже вытаскиваем оттуда
  хорошие куски. Ценное переносим в дерево явно.
- **N-003 · principle · Agent-first + саморост.** Правила/стандарты должны быть (а) читаемы агентом,
  (б) уметь **расти сами**: при новом вопросе агент создаёт **новую версию**, а не ломает старую.
  Версионность видима агенту.
- **N-004 · principle · Нумерация = топики по дате.** Каждый новый номер = топик (по дате создания).
  Файл или папка — но **предпочтительно папка** (топик = группировка с внутренней структурой).
- **N-005 · principle · Типовые группы по имени.** Имя раздела несёт ожидаемую структуру:
  «brain» ⇒ подразумевает, напр., `values` и т.д. Если где-то в проекте встречается ссылка на
  «brain» / «values», агент по правилам находит явную структуру этого типа
  *(развитие реестра типов-разделов `section-types-registry.md`).*
- **N-006 · principle · Анти-разрастание.** Если пунктов внутри становится слишком много
  (напр. domains 1..30) — НЕ плодить плоско, а **группировать логически** + добавлять
  дополнительный слой абстракции.
- **N-007 · decision · Процесс = сперва бриф, потом одна сессия Fable.** Сейчас не строим.
  Вместе готовим **критический бриф**, затем одна сессия Fable: найти слабые места, провести
  самокритику, выдать максимум идей → потом реализуем.

## Слабые места (сид для самокритики Fable)

1. **Глобалим нестабильное.** Это 3-я схема за 3 недели, «стоп-критерия реорга» нет.
   Переписать `~/.claude/CLAUDE.md` = правка класса R4 (universal core, трогает ВСЕ проекты).
   Риск: разнести неустоявшуюся схему по всем проектам и потом откатывать везде.
2. **Что переносимо vs специфично не разделено.** Реестр типов-разделов + правило роста —
   переносимы (кандидат в universal/domain). Оси `core/{brain,agents,contract}` — специфичны под FF.
   Единый глобальный скелет рискует навязать FF-специфику другим проектам.
3. **Версионность правил (N-003) не спроектирована.** «Новая версия» = новый файл? supersede-ссылка?
   Как агент выбирает актуальную? Пока только намерение.
4. **Дрейф уже есть.** `docs/NAVIGATION.md` и `docs/02-project/core/INDEX.md` всё ещё
   указывают на старый адрес brain. Структура «точка входа = истина» уже нарушена.
5. **Промоция не оформлена.** Правила `project → domain → universal` (нужны доказательства на 2+ проектах)
   лежат в глобальных rules, но дерево FF на них не ссылается и путь не заявлен.

## Бриф для Fable (одна сессия) — НА СОГЛАСОВАНИИ

**Настоящая боль:** 3 реорга за 3 недели. Прошлые попытки лечили симптом (раскладку папок),
а не причину — **у структуры нет закона роста**, она растёт руками.

**Цель (одна фраза):** спроектировать **ЗАКОН РОСТА документации** — правило, по которому
структура сама расширяется (не ручным реоргом), одинаково читается агентами во всех проектах и
допускает проектную специфику. Чтобы **4-го ручного переустройства не было.**

**Анти-цель:** НЕ выдавать «4-ю раскладку» как решение. Решение = *правило, из которого
раскладка выводится*, а не сама раскладка.

**Мандат:** критический разбор. Не строить — найти слабые места, самокритика, максимум идей за сессию.

**Вход:** этот файл (N-001..N-007 + слабые места) · `docs/INDEX.md` ·
`CANON-SKELETON-PROPOSAL.md` · `section-types-registry.md` · `~/.claude/rules/{evolution,constitution}.md`.

**Приоритеты (что важнее):**
- **P1 — Закон роста + стоп-критерий** (когда структура «достаточна» и не трогается). Самое важное.
- **P2 — Граница universal / domain / project** (что глобально vs специфично FF).
- **P3 — Саморост правил**: механика версий (агент создаёт → находит → выбирает актуальную).
- **P4 — Безопасная R4-правка** `~/.claude/CLAUDE.md` со стейджингом и откатом.
- **P5 — ≥10 ранжированных идей/рисков** + что вытащить из архивов (`base/`, `topics/`, старые ADR).

**Формат ответа (как Fable обязан писать):**
- Максимально **детально, но без раздувания** — каждая мысль в 1-3 строки, без повторов и «воды».
- **Без «личности»/лирики** — сухо, по делу, инженерным языком.
- Идеи **разделены и ранжированы** (по важности), чтобы мы уловили каждую отдельно.
- Структура ответа: (1) суть в 5 строк · (2) переформулировка настоящей проблемы ·
  (3) по P1–P5: вывод + краткое обоснование + конкретное предложение ·
  (4) ранжированный список идей (идея · зачем · риск) · (5) самокритика замысла ·
  (6) ≤5 вопросов владельцу (чтобы он подчеркнул один финальный).
- Effort: средний (по решению владельца; при нужде добавим).

## Разбор Fable раунд 2 получен (2026-07-07)

→ **`./03-fable-review-round2.md`**

**Ядро:** N-008..N-016 не ломают 5 правил — дают им физику. Три «способа раскладки» (тип·дата·символ)
= **три ортогональные оси** (идентичность/время/порядок); путём и id владеет **только тип**.
4 напряжения сняты: оси-модель · каскад wildcard-правил (как CLAUDE.md) · freeze покрывает
контракты, не экземпляры · БД = воспроизводимый вид над файлами-истиной.
**Стресс-тест brain:** один структурный закон (граф ячеек), но **две политики удержания** —
доки не забывают, brain забывает; мирит **policy-as-data** (`retention: keep|metabolize`).

**5 вопросов раунда 2 — ждут владельца (Q2 = кандидат в финальный):**
- Q1 структура vs метаболизм (доки не забывают, brain забывает?)
