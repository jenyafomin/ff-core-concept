# 🔬 АНАЛИЗ — федерация плагинов: типы (P1) и тождество экземпляров (P2)

> Грунт аналитика. Очерчивает проблему и всё пространство решений, опираясь на уже
> спроектированную ось M-G5/M-G3. **Финального вердикта здесь нет** — это следующий шаг (Fable).

---

## 0. Постановка

Плагины = мультитенант-маркетплейс. Плагин подключается («скачать свой фронт»), декларирует нужные
узлы/рёбра к общей БД. Разные плагины вводят **разные, НЕ одинаковые** типы, но семантически
пересекающиеся. Канонический пример владельца: плагин A завёл `user`, плагин B тоже завёл `user` —
технически это РАЗНЫЕ узлы, но потенциально ОДИН реальный субъект.

**Разложение на две НЕ смешиваемые подпроблемы:**

| | Уровень | Вопрос | Ось |
|---|---|---|---|
| **P1** | Схема (тип) | Как реестр держит два `user`-**типа** без коллизии? | M-G3 (реестр типов) |
| **P2** | Экземпляр | `user`-**узел** A и `user`-узел B — один субъект или два? Кто и когда это решает? | M-G5 (`canonicalId`, `same-as`) |

Смешение этих уровней — главная ловушка: «типы одинаковые» и «субъект один» — разные утверждения.
Можно иметь один общий тип и два разных субъекта; и два разных типа при одном субъекте.

**Жёсткие вводные из решений владельца (03-DECISIONS):**
- Владелец **не редактирует md руками** → декларация тождества НЕ может опираться на ручную кураторскую
  правку как основной путь. Основной путь = правило матчинга или агент-предложение + согласие (Ц-7).
- **Плагины сначала свои, потом мультитенант** → физический enforcement (READ-стены C4) НЕ P0, но
  `namespacing` типов, `canonicalId`, класс `assertion`-ребра, паспорт/payload — **заложить СЕЙЧАС**.

## P1 — Федерация ТИПОВ (schema-level)

### Что УЖЕ решено (переиспользуем)
- `node-type` = строка реестра с собственным `canonicalId` (I-1/I-2, M-G3).
- **Гейт типов:** новый `type-def` обязан `governed-by` → policy «когда вводить тип» (тест
  дубликата/синонима) — иначе не активируется. Это уже анти-свалка-синонимов.
- **`opaque-node` (FABLE C5):** плагинный тип без `view-def`-адаптера = паспорт виден, payload
  непрозрачен. Регистрация дёшева; полноправное участие в общих проекциях требует `view-def`.
  **«Налог по желанию, а не барьер входа».**
- `schema-version` + адаптеры (миграция = декларация, не разрушающий скрипт).
- `refines`-DAG (каскад) — готовый механизм для «тип уточняет тип».

### Опции

**P1-A. Namespacing / изоляция** — `pluginA:user` и `pluginB:user` = просто разные типы под префиксом-владельцем.
- *Как:* `canonicalId` типа несёт происхождение (плагин); гейт проверяет только уникальность
  namespaced-имени. Схемного слияния нет вообще. (Аналог: RDF-URI, XML namespaces, модули языка.)
- *Плюс:* нулевая коллизия; плагины полностью независимы; идеально ложится на I-1 (свой id у типа) и
  на `opaque-node`; retrofit-безопасно.
- *Минус:* система НЕ знает, что оба — «юзеры»; любая кросс-плагинная проекция требует явного мэппинга;
  прямой путь к **свалке синонимов** (тот самый риск M-G3).
- *Ложится на brain:* отлично — canonicalId-на-тип, opaque-node, гейт. Паспорт/payload: базовый паспорт
  одинаков, payload у каждого свой.
- *Retrofit:* 🟢 дёшево, namespacing и так P0.
- *Death by design:* болото почти-дублей, `user` = 5 разных смыслов, проекции множатся, никто не сводит.

**P1-B. Общий базовый тип + расширения-фасеты** — глобальный `person`/`subject` (или `user`) базовый тип;
плагины объявляют свой `user` как расширение, `refines` базу, добавляя поля.
- *Как:* `type-def` с ребром `refines` → базовый `type-def`; база = минимальный общий паспорт; плагин
  добавляет payload-поля фасетом. (Аналог: GraphQL interface, RDFS subClassOf, schema.org base+extension.)
- *Плюс:* система ЗНАЕТ, что оба — юзеры (общая база); проекции по базе работают кросс-плагинно; гасит
  свалку синонимов; **переиспользует `refines`-DAG и каскад M-G3 «как есть»**.
- *Минус:* требует, чтобы управляемая база уже существовала (кто владелец базы? цена governance);
  плагины скованы формой базы; эволюция базы = давление миграции; спор «какая база правильная».
- *Ложится на brain:* сильно — `refines`, каскад, гейт; база = policy уровня Конституции/global.
- *Retrofit:* 🟡 механизм расширения (`refines` на типах) заложить сейчас **дёшево**; но натянуть общую
  базу ПОЗЖЕ на уже разъехавшиеся типы — дорого. → закладываем механизм, базы заводим по мере нужды.
- *Death by design:* база-God-schema, за которую все воюют, ИЛИ настолько тонкая, что бесполезна;
  преждевременная онтология.

**P1-C. Адаптер / view-def-мэппинг между сосуществующими типами** — типы остаются namespaced (как A),
но `view-def`-узел переводит `pluginB:user` → форму `pluginA:user` (или оба → канонический вид) на read-time.
- *Как:* адаптер = `view-def`-узел M-G3, декларирует соответствие полей; Проектор (C2) применяет; данные
  не мутируются. (Аналог: schema-mapping/ETL, anti-corruption layer DDD, GraphQL `@shareable`+resolver.)
- *Плюс:* полная независимость плагинов И кросс-читаемость без принудительной базы; ровно ложится на
  CQRS/Проектор; **это и есть путь `opaque-node` → прозрачный** (FABLE C5) — «налог по желанию».
- *Минус:* N×N-взрыв адаптеров при многих плагинах; адаптер = семантический клей, тихо дрейфует; кто
  автор адаптера (агент? владелец?); неоднозначность мэппинга (поля не совпадают 1:1).
- *Ложится на brain:* отлично — это уже спроектированный `view-def` + Проектор C2; путь opaque→transparent
  уже есть.
- *Retrofit:* 🟢 позже дёшево, ЕСЛИ паспорт/payload split и `view-def` заложены сейчас.
- *Death by design:* разрастание адаптеров без владельца, дрейф; мэппинг становится вторым источником истины.

**P1-D. Гейт-как-примирение (policy поверх A/B/C, не 4-й механизм).** При регистрации `pluginB:user` гейт
M-G3 детектит near-duplicate и **форсит решение**: alias к существующему / расширить (→ P1-B) / обосновать
отдельный тип.
- *Плюс:* давит свалку в источнике, единая точка сведения.
- *Минус:* трение на install (маркетплейс хочет frictionless); чью-то стороннюю схему нельзя заставить
  переделать; кто решает — нагрузка на владельца/агента.
- *Статус:* это **политический слой** над A/B/C, а не альтернатива им. Fable решает, насколько жёсткий гейт.

## P2 — Тождество ЭКЗЕМПЛЯРОВ (instance-level)

### Что УЖЕ решено (переиспользуем — здесь основа заложена сильно)
- **`edge-type same-as`** = assertion-ребро `canonicalId ↔ canonicalId`: адресуемо, оспоримо, свой
  провенанс. «Два адреса — одна реальная сущность». Резолюция, **НЕ мутация ID**.
- **Слияние БД = идемпотентный union**: одинаковый `canonicalId` = буквально одна сущность; разные ID,
  оказавшиеся одним, → связываются `same-as`.
- **`effective-identity` (read-time view)** обходит `same-as` (mode `xor` = union-find: канонический
  представитель кластера). Проекция, ничего не зашивается.
- **`merge-policy`** — как резолвится `same-as` при конфликте (чей провенанс/committed выигрывает, read-time).
- **`node-type profile`** — обычная ячейка + `profile-ref` (thin-ref); каскад политик.
- Согласие (Ц-7) = consent-gate именно на assertion-рёбрах (M-G3) → естественно накрывает `same-as`.

→ **Вывод грунта:** структурная основа P2 (mesh `same-as` + union-find + merge-policy) **уже спроектирована
в M-G5**. Не хватает: (1) КТО/КОГДА объявляет тождество; (2) поведение при КОНФЛИКТЕ assertion-ов;
(3) нужен ли отдельный «канонический субъект»-узел или хватает mesh-представителя.

### Опции — СТРУКТУРА тождества

**P2-A. Mesh: `same-as` между узлами плагинов + union-find (as designed).**
- *Как:* узлы остаются раздельными; `same-as`-ребро связывает их canonicalId; `effective-identity`
  резолвит кластер, выбирает представителя. Без мутации. (Аналог: owl:sameAs, record-linkage clusters.)
- *Плюс:* обратимо (оспоримо) → **преждевременное слияние не смертельно** (можно расцепить); провенанс
  на каждой ассерции; недеструктивно; идемпотентный union БД; consent-gate Ц-7 садится на ребро.
- *Минус:* стоимость read-time резолюции растёт с кластером; кто асёртит? конфликтующие ассерции требуют
  merge-policy; выбор представителя оспорим.
- *Ложится на brain:* нативно — это спроектированный путь.
- *Retrofit:* 🔴 класс `assertion` + `canonicalId` должны быть сейчас (уже помечено 🔴).
- *Death by design:* спагетти-ассерции без провенанса/tie-break → неоднозначность тождества, никто не
  владеет слияниями.

**P2-B. Star: общий канонический профиль / golden-record, на который оба ссылаются.**
- *Как:* один канонический `person`/`profile`-узел = «реальный субъект»; узлы-`user` плагинов несут
  thin-ref/`same-as` НА него (звезда, не сетка). Плагинные узлы = представления. (Аналог: MDM golden
  record, EMPI master patient index.)
- *Плюс:* единый стабильный адрес «реального человека»; чистый каскад (профиль несёт политику); нет
  N×N-связей (звезда vs сетка); проверенный MDM-паттерн; переиспользует `profile` + `profile-ref`.
- *Минус:* нужно решить/создать канонический узел (кто, когда); риск **преждевременной канонизации**
  (связали два, оказались разными → дорого расцеплять, если thin-ref не оспорим); чьи поля авторитетны
  (survivorship rules).
- *Ложится на brain:* сильно — переиспользует `profile` + thin-ref; НО сейчас `profile` = ячейка политики,
  не мастер-идентичности; это расширение его роли. Взаимодействует с mesh (`same-as`).
- *Retrofit:* 🟡 узел `profile` есть; роль identity-master — 🟢 позже, ЕСЛИ canonicalId+refs заложены.
- *Death by design:* golden-record становится оспариваемым god-узлом; survivorship-правила костенеют;
  преждевременное слияние (если связь thin-ref, а не оспоримая assertion — теряется обратимость P2-A).

**P2-C. Отложенная корреляция / адаптер (не утверждать тождество на уровне данных).**
- *Как:* тождество НЕ асёртится; когда агенту нужна корреляция, matching-view предлагает соответствие
  read-time (правило/вероятностно), не персистится как истина; подтверждение → превращает в P2-A.
  (Аналог: EMPI probabilistic matching, record linkage без merge.)
- *Плюс:* никакого преждевременного обязательства; безопасный дефолт (два юзера = два, пока не доказано);
  логика матчинга = данные (view-def); ложится на Проектор + consent-gate.
- *Минус:* корреляция пересчитывается, не durable; агенты могут действовать на неподтверждённом матче;
  по сути НЕ решает тождество, а откладывает.
- *Ложится на brain:* хорошо — это стадия «предложения», питающая P2-A.
- *Retrofit:* 🟢 позже.
- *Death by design:* вечная отсрочка — тождество не резолвится, агенты гадают, дубли субъектов множатся.

### Кросс-ось (ортогональна A/B/C, но Fable ОБЯЗАН назвать) — КТО объявляет и что при КОНФЛИКТЕ
- **Кто/когда declarер:** (i) детерминированное правило-матчинга (общий верифицированный ключ — email/phone
  → авто-`same-as`); (ii) агент-предложение + подтверждение человеком (consent-gate Ц-7); (iii) только
  человек вручную. **Ограничение владельца (не редактирует md) → (iii) не основной; основа = (i)/(ii).**
- **Конфликт (A: «одно», B: «разное»):** обе ассерции = узлы с провенансом → либо merge-policy tie-break
  read-time (committed/доверие выигрывает), либо всплытие противоречия в Human Inbox (C7). Недеструктивность
  mesh (P2-A) позволяет держать оба утверждения одновременно, не «побеждая» силой записи.

## 🎯 2-3 острых вопроса, которые должен решить Fable (НЕ решаю сам)

1. **P1 — онтология-first или мэппинг-first?** Заводим ли управляемый ОБЩИЙ БАЗОВЫЙ тип
   (`person`/`subject`) на уровне Конституции, который плагинные `user` обязаны `refines` (P1-B) — или
   типы остаются полностью namespaced (P1-A) + связываются адаптерами `view-def` по требованию (P1-C),
   без принудительной базы? **Ретрофит-натяжка:** механизм расширения (`refines` на типах) дёшев сейчас,
   но НАТЯНУТЬ базу позже на разъехавшиеся типы — дорого. Что закладываем в P0-схему?

2. **P2 — mesh или star?** `same-as` между узлами плагинов (P2-A, уже спроектировано) — или у «реального
   субъекта» появляется first-class канонический узел-`profile`/golden-record, на который оба ссылаются
   (P2-B)? И **композируются ли** они (`same-as` между профилями)? Ключ: сохранить недеструктивную
   обратимость P2-A (расцепить ошибочный матч) — thin-ref в P2-B её теряет, если ссылка не оспорима.

3. **P2 — кто объявляет тождество и что при конфликте?** Учитывая, что владелец НЕ правит md руками:
   детерминированное правило-матчинга по общему ключу (авто) vs агент-предложение + consent-gate (Ц-7)
   vs ручное? И когда A асёртит «одно», B — «разное»: read-time merge-policy tie-break ИЛИ эскалация
   противоречия в Human Inbox? (Дефолт при отсутствии доказательства = «два разных субъекта».)

## 🔴 Риски / death-by-design (честно, слабые места)

- **Инъекция тождества через недоверенный плагин (пересечение со слепой зоной №1 FABLE).** Плагин с
  провенансом `external/untrusted` может **асёртить `same-as` к чужому/корневому субъекту** — заявить, что
  его `user` ЕСТЬ владелец → захват идентичности/эскалация грантов. Требование: `same-as` от untrusted-
  principal обязан быть consent-gated + provenance-маркирован; ассерции, касающиеся **`root-self`, —
  всегда human-gate** (плагин не может «через тождество» пролезть в корневой профиль = governance capture).
  Это НЕ покрыто ни M-G5, ни M-G3 явно — надо назвать.
- **Преждевременное слияние vs вечная фрагментация — двойной обрыв.** Слить два разных субъекта (ложный
  `same-as`) → загрязнение; никогда не сводить → дубли, агенты действуют по неполному/задвоенному субъекту.
  Mesh (P2-A) смягчает первый (обратимо); дефолт-deny смягчает — но не решает — второй.
- **Свалка синонимов (P1-A в чистом виде).** Без базы/адаптеров/гейта `user` расползается в N несводимых
  типов; проекции множатся; система «гибкая, но не знает своего поведения» (эхо policy-rot из FABLE C5).
- **N×N-адаптеры (P1-C) и god-base (P1-B) — противоположные крайности.** Мэппинг-first масштабируется в
  клубок адаптеров без владельца; онтология-first — в узкое горло базовой схемы. Оба лечатся владельцем+
  review-by на узле (адаптера/базы), которого пока в дизайне НЕТ для этих сущностей.
- **Стоимость read-time резолюции.** `effective-identity` + `effective-policy` + адаптеры — три read-time
  обхода на большом графе; C4/C7 предупреждали, что сборка контекста сама жрёт бюджет. Федерация усиливает
  этот риск — резолюция тождества не бесплатна.
- **Survivorship-правила (P2-B) не спроектированы.** Если появляется golden-record, «чьи поля
  авторитетны» = отдельная policy-группа, которой сейчас нет; без неё мастер-узел молча выбирает произвольно.

## Что переиспользуем / чего не хватает (сводка для Fable)

**Переиспускаем как есть:** `canonicalId` (I-1), `same-as` assertion + `effective-identity` union-find,
`merge-policy`, `type-def` + гейт типов, `opaque-node`, `refines`-DAG, `view-def` + Проектор C2, consent-gate Ц-7.

**Не хватает (кандидаты в решение Fable / спеку):** (a) механизм связи двух типов — namespacing-only vs
`refines`-база vs адаптер (P1); (b) first-class «канонический субъект» — нужен ли (P2-B); (c) declarер
тождества + консент/конфликт-протокол (кросс-ось P2); (d) защита `root-self`/untrusted от identity-инъекции;
(e) survivorship-политика, если выбран golden-record.
