# Fable-бриф — «Combination»: единица модульности + шов объединения

- **Status:** active · Owner: jenya.stasik@gmail.com · Date: 2026-07-13
- **Тип:** Fable-advisor артефакт (развилка · контекст · отвергнутое · формат · готовность)

## 1. Развилка (в одном-двух предложениях)
У нас два разнородных куска: **Brain** (граф-субстрат памяти, стадия ДИЗАЙНА) и **agents-manager**
(рабочий шлюз-оркестратор, стадия РАБОЧЕГО КОДА). Нужно объединить их в ОДНУ платформу так, чтобы в
будущем функциональность подключалась **модулями как marketplace** (кто-то делает модуль «План», другой
берёт/форкает/улучшает), с **версионированием и апгрейдами модулей поверх живой БД со старыми данными**.
**Несущая абстракция, которую просим вскрыть: ЧТО ТАКОЕ «модуль» как единица**, такая, что и Brain, и
шлюз, и «План» — её частные случаи; и как на ней держатся апгрейд/форк/совместимость.

## 2. Контекст-выжимка (суть, не пересказ файлов)

### Brain (граф-субстрат, НЕ построен, фаза DESIGN)
- Философия: **substrate-first** — «всё есть узел/ребро на одном субстрате» (DL-01).
- **Паспорт = policy-as-data**: узел несёт свой блок политики (видимость, доступ, confidence, retention…).
- **Конституция** = инварианты над ячейкой (потолок над локальной политикой; напр. согласие референта
  нельзя переопределить политикой владельца; единый порог доступа; безусловное право hard-erase).
- **integrity-as-engine-duty**: категории/связи/дедуп/конфликты/циклы гарантирует ДВИЖОК (не политика).
- **Bitemporal** + **canonical_id** (идентичность-хребет). **INSERT-not-migrate (DL-14):** новые типы
  узлов добавляются INSERT-ом в реестр типов, БЕЗ миграций схемы после M1.
- **Engine Contract / Portability (#15)** уже помечен как **фундамент плагинов/marketplace + key-custody**.
- **16 инфраструктурных модулей** (canonical_id, bitemporal, referent-anchor, PEP-доступ, паспорт,
  confidence, forgetting, edge-engine, provenance, lens, gardener, ingress-adapter…). 7 закрытых ценностей.
- План: M0→M8 walking skeleton. Важное: **R6 — agents-manager обязан звать ТОЛЬКО API графа (M-G1),
  никогда прямой SQL**; M2 — «переиспользовать agents-manager как runner»; агенты живут на субстрате
  (Personality→Slot→Session как подграф).

### agents-manager (рабочий шлюз, ПОСТРОЕН, чистая гексагональная арх.)
- Порты-и-адаптеры: **13 портов** (IChannel, IAgentRunner, IApprovalGate, IQueue, репозитории…). Строгая
  дисциплина импортов; композиция только в `app/build-app.ts`.
- **Своё состояние в SQLite**: `bots, agents, agent_bindings, sessions, jobs, messages, topics,
  process_leases, seen_updates, summaries`. Репозитории — интерфейсы, SQLite один из адаптеров (→ Postgres
  меняется без связности схемы).
- **Реестр**: bot + agent грузятся из env (M5 → мульти-бот в SQLite, namespace-изоляция).
- **Каскад PROMPT.md** (chat→topic) + config.json (cwd/model) — правится файлами, применяется след. ход.
- **Approval-гейты** (job-level keyword + per-tool SDK canUseTool → 3 кнопки в TG). Runner: print|sdk.
- Роадмап (PLAN-0001): Task/Plan-сущности → Dispatcher (мульти-топик) → safety-reviewer → автономный
  ночной цикл. **Открытый вопрос 2a (заблокирован на ADR): планы/задачи живут per-project или в
  универсальном `~/.claude`?** — это прямо про кросс-проектную/модульную архитектуру.

### Что уже видно как ядро противоречия
- **Два хранилища состояния.** Brain: «всё — узлы на одном субстрате» (пуризм DL-01). Шлюз: своя
  реляционная SQLite (sessions/jobs/messages). Объединяем → шлюзовое операционное состояние **сливается
  в граф** (один субстрат) ИЛИ **остаётся федеративным** (две БД + контракт между)?
- **Два понимания «плагина» на разных слоях.** Brain: policy-as-data + Engine Contract (#15) — плагин на
  уровне ДАННЫХ/движка. Шлюз: ports/adapters + registry — плагин на уровне ИСПОЛНЕНИЯ/кода. «Модуль
  marketplace» должен свести оба в одну единицу.

## 3. Что уже пробовали / отвергли (не повторять)
- Мысль «просто сделать Brain агентом внутри шлюза» — отвергаем: теряется substrate-first и общий граф
  как единая память; шлюз тогда просто дергает инструменты, а не живёт на субстрате (противоречит M2/R6).
- Мысль «шлюз — истина, граф — сбоку как хранилище заметок» — отвергаем: рефрейм msg141 «граф = рабочий
  СУБСТРАТ для агентов, а не хранилище файлов».
- «Начать с кода комбинации сейчас» — НЕТ: фаза DESIGN, сначала концепт и ценности.

## 4. Запрошенный формат ответа (лимит ~1500 слов, резко и конкретно)
1. **ВЕРДИКТ**: что такое «модуль» как единица — дай его **анатомию/манифест** (перечни полей/частей),
   так чтобы Brain, шлюз и «План» были её экземплярами. Одно предложение-определение + структура.
2. **ХРАНИЛИЩЕ**: один субстрат или два (федерация)? Один резкий выбор + почему + чем рискуем.
3. **АПГРЕЙД/ФОРК/СОВМЕСТИМОСТЬ**: механизм версионирования модуля и апгрейда поверх живой БД со старыми
   данными; как форк («сделал свой лучше») связан с оригиналом (lineage/наследование/совместимость версий).
   Как это ложится на bitemporal + INSERT-not-migrate + policy-as-data + Конституцию.
4. **ЧТО ФИЗИЧЕСКИ ЕСТЬ 3-Й ПРОЕКТ «Combination»**: контракт/спека (docs)? движок реестра+апгрейдов (код)?
   зонтик, где Brain=«storage-модуль», шлюз=«runtime-модуль»? Резко: чем он владеет, чего НЕ делает.
5. **ЧТО МЫ УПУСКАЕМ**: 2-3 слепых пятна/риска, которые обычные линзы (analyst/critic) не увидят.
6. Заверши **3-5 инфраструктурными модулями-кандидатами** для «Combination» (по образцу 16 модулей Brain:
   имя · что сводит · паттерн · ADR-кандидат) — это станет скелетом.

## 5. Готовность к ответу (что делаем при любом варианте)
- Любой вердикт → строю скелет проекта «Combination»: `values/` (лестница) + `infrastructure/` (модули по
  образцу Brain) + `decisions/` (ADR-кандидаты) + `plan/`. Вопрос Fable определяет ГЛАВНЫЙ ADR (единица
  модульности + один/два стора + апгрейд-движок), а не «строить ли».
- «Один субстрат» → ADR-0001 Combination: операционное состояние шлюза = узлы графа; шлюз зовёт только API.
- «Федерация» → ADR-0001 Combination: контракт-мост между двумя БД + правила согласованности.
- В любом случае: manifest модуля → станет спекой; upgrade/fork-механизм → отдельный инфра-модуль + ADR.
- Затем адверсариальная проверка (critic против разреза Fable); выживает то, что переживает обоих.
