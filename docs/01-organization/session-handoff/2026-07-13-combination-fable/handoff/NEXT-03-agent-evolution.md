# NEXT-03 · Эволюционируемый механизм самообучения агентов

> Ключ: реально в session-handoff агенты не ходят. Ценны только АНАЛИТИЧЕСКИЕ моменты — «механизм сделан
> неверно», «шли не туда». Их надо ловить и хранить как первоклассные, искомые записи.

## Идея (стоячий вопрос)
Есть механизм, который мы **всегда держим включённым**: «а не пошли ли мы не туда? не сделан ли механизм
неправильно?». Каждый раз, когда стыкаемся с этим — **активируем и самообучаемся**: понимаем, где была
зарыта проблема.

## Протокол фиксации
1. Владелец: «тут по-моему фигня, согласен?».
2. Агент: если согласен → **фиксирует запись** `Type: problem` (см. `PROBLEMS.md`): `id`, `status`
   (open/in-progress/solved), место (где в файлах), ссылки.
3. Проблема живёт в конкретном месте; **привязывается к плану** — описываем, что план вообще не учёл
   (→ `../combination-scaffold/docs/plan/GAPS.md`).
4. Статус меняется: решена / не решена / в работе — с указанием, ГДЕ решена.

## Свойства записи (чтобы искалось)
- Свой **тип файла / «расширение»** (`Type: problem`) — как у всех артефактов, чтобы делать удобный поиск.
- Поиск по `Type: problem` + `status:` даёт «все нерешённые проблемы», «решённые», «в этом модуле».
- Это ручной прототип будущего: провенанс (**M4**) + петля обучения над графом.

## Задача следующей сессии
1. Утвердить словарь `Type` и `status` (мини-стандарт) — часть `PROTOCOL-concept-first.md`.
2. Решить, где физически живут проблемы: в session-handoff, в логах завершения плана, у самого плана — или
   везде, но с единым `Type` для сквозного поиска.
3. Прикинуть «активацию»: когда и как агент сам поднимает стоячий вопрос (не только по реплике владельца).
