## Чего именно (объекты)
Что такое «новая версия»; апгрейд-как-добавление (не переписывание); линзы чтения; откат; видимость апгрейда.

## Направления

### D2.1 — Что такое «новая версия»
- **Развилка (решена):** версия по **двум осям** — версия КОДА (адаптер) и версия СЛОВАРЯ (типы). Ломает
  совместимость только словарь. `Task@1`, `Task@2` — версии словаря.

### D2.2 — Апгрейд поверх живой БД (линзы)
- **Развилка (решена Fable, доработана critic):** новая версия НИКОГДА не переписывает старые узлы; она
  INSERT-ит новые версии типов + поставляет **линзы** — чистые функции чтения `@1→@2` (schema-on-read /
  upcasting, ср. Project Cambria). Материализация = новое утверждение с новым valid-time.
- **Правка critic (обязательна):**
  - **Тотальность линзы:** нетотальная линза не фабрикует тихо — помечает поле `derived/low-confidence`
    (эпистемический статус) или явный null-контракт.
  - **Стоимость цепочки:** N линз на чтение дорого → разрешён **материализованный кэш**, НО кэш = scratch
    (перестраиваем + erase-reachable) → M5. Плюс **компакция** цепочки в новую канон-версию (governed).

### D2.3 — Откат и видимость апгрейда
- **Развилка:** откат = «читать через старую линзу» (bitemporal хранит всё) vs явный откат-эвент. Видимость:
  как владелец видит «этот узел показан через линзу @1→@3»?
- **Идеи:** бейдж провенанса `module@version` на чтении (связано CV5/M4); diff-превью апгрейда до применения.

## Приоритет
**must-now** — прямой запрос владельца (тест БД на эволюции). Механизм = ядро тестируемости всей идеи.
