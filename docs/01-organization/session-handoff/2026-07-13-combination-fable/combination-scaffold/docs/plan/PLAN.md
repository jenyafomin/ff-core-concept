## Принцип
Combination — контрактный трек, НЕ стройка движка. Проверяем контракт на бумаге, где трещит — там ADR.
Рабочий шлюз не морозим (ADR-C6).

## Шаг 0 (первый боевой ход — совет Fable, подтверждён critic)
**Написать манифест модуля «План» на бумаге и прогнать через него шлюз.**
1. Заполнить манифест 8 частей (ADR-C1) для модуля «План»: словарь `Task/Plan`, порты, политики, зависимости.
2. Описать существующий **шлюз тем же манифестом** (runtime-модуль: порты IChannel/IAgentRunner, типы
   session/topic/binding, что truth / что scratch).
3. Зафиксировать, где манифест **«трещит»** → каждый треск = вход в ADR (ожидаемо: CQ6 core-словарь,
   поведенческий контракт портов, граница truth/scratch таблиц шлюза).

## Шаг 1 — минимальный фундамент ADR
ADR-C0 (kernel/seed) → ADR-C1 (манифест/граница) → ADR-C2 (версии+линзы). Достаточно, чтобы описать
«эволюцию БД» — прямой запрос владельца.

## Шаг 2 — тест «эволюционирующей БД» (запрос владельца)
На игрушечном модуле прогнать `Task@1→@2→@3` через линзы поверх живых данных + hard-erase + аудит
(валидация ADR-C2). Это и есть «протестировать БД на эволюционирующей модели модулей».

## Шаг 3 — классификация таблиц шлюза truth/scratch (ADR-C5) + набросок моста (ADR-C6)
Первый боевой тест контракта scratch. Готовит будущий инкрементальный cutover (когда Brain M1 зелёный).

## Зависимости от Brain
Combination-рантайм реестра живёт в ядре Brain. Реальная сборка ждёт Brain M0–M1. До этого Combination =
контракт+ADR+эталонный манифест (можно делать сейчас, не блокируя шлюз).
