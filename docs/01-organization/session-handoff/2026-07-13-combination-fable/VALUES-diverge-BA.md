## 0. Цель (1 абзац, человеческим языком)

Сейчас у владельца два разных куска труда: **Brain** — продуманная, но ещё не построенная база-субстрат
для памяти агентов, и **agents-manager** — рабочий, но самодостаточный шлюз Telegram↔Claude со своим
отдельным состоянием. Проблема не «как их склеить технически» — проблема глубже: каждый раз, когда
владельцу приходит идея новой возможности (план, задачи, привычки, финансы — что угодно), сейчас нет
готового способа **добавить это как отдельный, изолированный кусок**, который не требует переписывать
ядро и не боится, что завтра сам владелец (или кто-то другой) сделает версию лучше. «Combination» решает
именно эту боль: превратить два разрозненных куска в ОДНУ платформу, где функциональность — это
**модули**, которые можно подключать/менять/улучшать/форкать, как в marketplace, и где апгрейд модуля
**не роняет накопленные данные**. Это инвестиция в то, чтобы труд владельца **компаундился**: не
переписывать основание под каждую новую идею, а достраивать поверх устойчивого контракта — и в
перспективе дать возможность растить это не в одиночку (кто-то другой делает/улучшает модуль).

## CV1. Модульность / Подключаемость

**Чего именно касается (объекты):** единица модуля (что физически внутри — манифест), контракт границы
подключения (что модуль обязан заявить платформе), обнаружение/реестр (что установлено и доступно),
изоляция сбоя (падение одного модуля не роняет остальные), опыт автора модуля (насколько легко создать
новый — включая владельца как первого автора «Плана»).

**Приоритет:** must-now — почему: это буквально вопрос, вскрытие которого попросили у Fable («что такое
модуль как единица, такая что Brain, шлюз и «План» — её частные случаи»). Все остальные ценности
опираются на ответ здесь.

### Направление CV1-D1 · Манифест модуля

- **Суть:** что модуль обязан заявить о себе, чтобы платформа его узнала.
- **Развилки:**
  - (a) минимальный манифест: имя + версия + зависимости — просто, но мало что решает
  - (b) полный бандл-манифест (рабочая гипотеза из FABLE-BRIEF): схема узлов/рёбер · политики
    (policy-as-data) · роль-агент (prompt+tools) · команды/UI · миграции/версия · манифест
    зависимостей+совместимости — тяжелее, но закрывает CV2/CV3 сразу
  - (c) манифест по слоям: данные отдельно от рантайма отдельно от UI — гибче, но сложнее в реализации
- **Пул идей:**
  - шаблон `manifest.json`/`.yaml` для нового модуля `[CV1]`
  - генератор скелета модуля (`combination new-module`) по образцу scaffold Brain `[CV1]`
  - локальный реестр установленных модулей `[CV1, CV6]`
  - поле `author` в манифесте уже сейчас — дёшево, пригодится для CV3/CV6 `[CV1, CV3, CV6]`

### Направление CV1-D2 · Граница подключения (архетипы модуля)

- **Суть:** как модуль встраивается в целое — что он «видит» и чем управляет.
- **Развилки:**
  - (a) модуль = только данные (типы узлов/рёбер + политика), рантайм общий для всех
  - (b) модуль = данные + код роли-агента (аналог agent+agent_bindings в agents-manager)
  - (c) модуль = полный вертикальный срез: данные + код + UI/команды
  - (d) два архетипа модуля вместо одного: «storage-модуль» (как Brain) и «runtime-модуль» (как шлюз) —
    рабочая гипотеза FABLE-BRIEF `[сомнительно, пока не подтверждено Fable]`
- **Пул идей:**
  - единый интерфейс «модуль регистрирует себя», по аналогии с портами agents-manager `[CV1]`
  - namespace-изоляция типов узлов на модуль (без коллизий id между модулями) `[CV1, CV2]`
  - архетип storage- vs runtime-модуль как явная типизация в манифесте `[CV1, CV4]`

### Направление CV1-D3 · Обнаружение / реестр

- **Суть:** как владелец (и платформа) узнаёт, что установлено и что доступно.
- **Развилки:**
  - (a) локальный реестр (отдельный файл/таблица вне графа)
  - (b) реестр внутри самого графа — «модуль как узел» (зеркалит substrate-first философию Brain)
  - (c) внешний каталог — это уже CV6, здесь только заметка «не сейчас»
- **Пул идей:**
  - «модуль как узел графа» — реестр не отдельная сущность, а часть субстрата `[CV1, CV4]`
  - статус-дашборд установленных модулей владельцу в Telegram `[CV1]`

### Направление CV1-D4 · Изоляция сбоя

- **Суть:** ломает ли один плохой модуль остальную платформу.
- **Развилки:**
  - (a) sandbox по правам — модуль видит только свои типы узлов/рёбер (PEP-scope на модуль)
  - (b) process-level изоляция — отдельный процесс/раннер на модуль (дороже)
  - (c) без изоляции сейчас, доверяем — пока модули пишет только сам владелец `[сомнительно, риск при первом чужом модуле]`
- **Пул идей:**
  - расширение Unified PEP (#5 из Brain) до «PEP на уровне модуля» `[CV1, CV5]`
  - approval-гейт при установке нового модуля, по аналогии с approval-гейтами шлюза `[CV1, CV5]`

## CV2. Эволюционируемость без поломок (апгрейды)

**Чего именно касается:** что значит «новая версия» модуля, миграция как добавление (не перезапись —
согласуется с bitemporal Brain), путь отката, сосуществование версий, видимость апгрейда для владельца.

**Приоритет:** must-now — почему: дословная просьба владельца — «протестировать базу данных именно на
такой эволюционирующей модели» (модуль обновляется — граф это переживает). Это не побочный эффект, а
заявленная ЦЕЛЬ эксперимента.

### Направление CV2-D1 · Что считается «новой версией»

- **Суть:** единица версионирования модуля.
- **Развилки:**
  - (a) semver на манифест целиком (просто, но грубо — маленькая правка роли-агента бампает всю версию)
  - (b) версия по частям: схема отдельно от роли-агента отдельно от UI (точнее, сложнее отслеживать)
  - (c) версия = метка последнего INSERT в реестр типов (Brain-style, «версия = история INSERT'ов»)
- **Пул идей:**
  - привязка версии модуля к INSERT-not-migrate Brain: апгрейд = новый тип узла, старый не трогаем `[CV2, CV3]`
  - поле «минимальная версия платформы», которую модуль требует `[CV2, CV3]`

### Направление CV2-D2 · Миграция поверх живых данных

- **Суть:** что физически происходит с накопленными данными при апгрейде.
- **Развилки:**
  - (a) миграция-как-новый-узел: старые записи остаются, апгрейд добавляет новую интерпретацию сверху
    (bitemporal-подход Brain) — согласуется с их DL-14
  - (b) классическая миграция схемы (ALTER + бэкфилл) — риск для живых данных, но привычнее `[сомнительно, противоречит DL-14 Brain]`
  - (c) двойная запись (dual-write) на переходный период — дороже, безопаснее для длинных миграций
- **Пул идей:**
  - «апгрейд = добавление, не перезапись» как жёсткий инвариант Конституции Combination `[CV2, CV3]`
  - тестовый прогон миграции на копии/подмножестве графа перед боевым апгрейдом `[CV2, CV5]`

### Направление CV2-D3 · Путь отката

- **Суть:** что делать, если апгрейд оказался плохим решением.
- **Развилки:**
  - (a) откат = просто читать более раннюю bitemporal-версию (встроен в модель, отдельного механизма не нужно)
  - (b) отдельный snapshot/backup перед каждым апгрейдом (дублирующая инфраструктура)
  - (c) без отката, только forward-fix `[сомнительно, риск для владельца при плохом апгрейде]`
- **Пул идей:**
  - «время-истины» Brain как встроенный откат без доп. инфраструктуры `[CV2, CV4]`

### Направление CV2-D4 · Видимость апгрейда владельцу

- **Суть:** узнаёт ли владелец, что и когда обновилось / сломалось.
- **Развилки:**
  - (a) уведомление в Telegram при апгрейде («модуль X обновился до vY, что изменилось»)
  - (b) дашборд версий всех установленных модулей
  - (c) тихие апгрейды без уведомлений `[сомнительно, владелец теряет контроль]`
- **Пул идей:**
  - карточка апгрейда в Telegram по аналогии с approval-гейтами шлюза `[CV2, CV1]`

## CV3. Совместимость и происхождение версий (форки)

**Чего именно касается:** связь форка с оригиналом (lineage), заявленная совместимость версий (что можно
взаимозаменить), что происходит, если два форка одного модуля установлены одновременно, атрибуция автора.

**Приоритет:** must-now — почему: дословная просьба владельца — «кто-то создаёт модуль, другой берёт/
форкает/делает лучше» + «связка апгрейдов со старыми версиями». Без этого «marketplace» — просто лозунг.

### Направление CV3-D1 · Lineage форка

- **Суть:** как форк объявляет, от чего он произошёл.
- **Развилки:**
  - (a) явное ребро «форк-от» в графе (Brain-style edge, естественно для substrate-first)
  - (b) просто поле `forked_from` в манифесте, без графового ребра — легче реализовать сейчас
  - (c) происхождение не отслеживаем вовсе `[сомнительно, убивает саму идею «взял и улучшил»]`
- **Пул идей:**
  - «форк = lineage-ребро к оригиналу» — рабочая гипотеза из FABLE-BRIEF `[CV3, CV1]`
  - атрибуция автора в манифесте: кто сделал, кто улучшил `[CV3, CV6]`

### Направление CV3-D2 · Заявленная совместимость

- **Суть:** как модуль сообщает, с чем он может (не) взаимодействовать.
- **Развилки:**
  - (a) модуль сам объявляет «совместим с версией оригинала X.Y+» — доверие на слово автора
  - (b) движок платформы сам проверяет совместимость схем (structural check) — надёжнее, дороже в разработке
  - (c) совместимость никак не проверяется, риск на владельце `[сомнительно]`
- **Пул идей:**
  - матрица совместимости версий как часть манифеста `[CV3]`
  - «движок апгрейдов» Combination как отдельный сервис, проверяющий совместимость перед установкой `[CV3, CV1]`

### Направление CV3-D3 · Конкуренция версий/форков

- **Суть:** можно ли держать несколько версий/форков одного модуля одновременно.
- **Развилки:**
  - (a) несколько форков параллельно, по namespace — гибко, но сложнее для владельца выбрать
  - (b) только одна активная версия, форки — только для сравнения в песочнице
  - (c) явный выбор владельца при установке: «заменить» существующий или «добавить рядом»
- **Пул идей:**
  - песочница для пробы чужого форка без замены рабочего модуля `[CV3, CV5]`

## CV4. Суверенность и переносимость

**Чего именно касается:** экспорт/импорт данных модуля, key-custody (кто держит ключи доступа/шифрования
— перекликается с Engine Contract/Portability #15 из Brain), независимость от конкретного автора модуля,
независимость от конкретного хранилища.

**Приоритет:** soon — почему: критично для доверия к marketplace в будущем и для решения «один субстрат
или федерация» (это и есть узел напряжения №1, отправленный Fable), но не блокирует первый внутренний
модуль «План», который делает сам владелец.

### Направление CV4-D1 · Экспорт/импорт данных модуля

- **Суть:** может ли владелец забрать данные модуля и унести их (сменить автора модуля, уйти от платформы).
- **Развилки:**
  - (a) данные модуля = подграф с canonical_id, экспортируется как есть (Brain-native, естественно)
  - (b) отдельный экспорт-формат на каждый модуль — гибче для внешних систем, больше работы на автора модуля
  - (c) экспорт не продумываем сейчас — внутренний проект, не срочно `[допустимо для must-now объёма, отложить деталь]`
- **Пул идей:**
  - «экспорт = выгрузка подграфа по тегу модуля» `[CV4, CV1]`

### Направление CV4-D2 · Key-custody / контроль доступа

- **Суть:** кто физически держит ключи и решает, кто что видит.
- **Развилки:**
  - (a) ключи всегда у владельца платформы (Engine Contract #15 Brain), модуль их не видит напрямую
  - (b) модуль может запросить собственный scope ключей — гибче, больше поверхность риска
  - (c) без разделения пока — один владелец, один ключ (упрощение на старте)
- **Пул идей:**
  - прямая связка с Unified PEP Brain (#5) `[CV4, CV5]`

### Направление CV4-D3 · Независимость от хранилища (узел напряжения №1)

- **Суть:** операционное состояние шлюза (sessions/jobs/messages) сливается в граф или живёт отдельно.
  **Это главный открытый вопрос, отправленный Fable — здесь только фиксирую варианты, не решаю.**
- **Развилки:**
  - (a) один субстрат: состояние шлюза сливается в граф, шлюз зовёт только API графа (согласуется с R6
    Brain: «agents-manager обязан звать ТОЛЬКО API графа»)
  - (b) федерация: две БД остаются, между ними контракт-мост
  - (c) гибрид: горячие операционные данные (текущий job/сессия) — в SQLite шлюза для скорости, всё
    остальное (история, память, решения) — в графе
- **Пул идей:**
  - контракт-мост Brain↔agents-manager как отдельный инфра-модуль Combination, вне зависимости от
    исхода развилки `[CV4, CV1, CV2]`

## CV5. Доверие и безопасность подключаемого кода

**Чего именно касается:** скоуп прав модуля при установке, апрув перед установкой/апгрейдом, аудит
действий модуля (кто что изменил), песочница для пробы модуля перед боевым использованием.

**Приоритет:** soon — почему: реально нужна ДО того, как в систему попадёт первый чужой (не-владельца)
модуль; для первого модуля «План», который делает сам владелец, можно временно понизить строгость.

### Направление CV5-D1 · Скоуп прав на установку

- **Суть:** что именно модуль просит и что из этого владелец разрешает.
- **Развилки:**
  - (a) модуль декларирует нужные типы/scope в манифесте, владелец подтверждает при установке (аналог
    approval-гейтов шлюза, кнопки в Telegram)
  - (b) модуль получает полный доступ по умолчанию — просто реализовать, опасно `[сомнительно]`
  - (c) градация по доверию источника: свой модуль / известный автор / незнакомый — разный уровень
    проверки/предупреждений
- **Пул идей:**
  - расширение approval-гейтов шлюза на «установка/апгрейд модуля» `[CV5, CV1]`
  - тир доверия по автору (свой > проверенный > любой) `[CV5, CV6]`

### Направление CV5-D2 · Аудит действий модуля

- **Суть:** видно ли владельцу, какой модуль что записал/поменял в общем субстрате.
- **Развилки:**
  - (a) единый provenance-лог Brain фиксирует авторство изменения с тегом модуля
  - (b) отдельный лог на каждый модуль — проще для модуля, сложнее свести воедино
  - (c) без аудита пока `[сомнительно, теряется доверие как только модулей больше одного]`
- **Пул идей:**
  - расширить Provenance-модуль Brain тегом «какой модуль сделал изменение» `[CV5, CV2]`

### Направление CV5-D3 · Песочница перед боевым использованием

- **Суть:** можно ли попробовать модуль, не рискуя реальными данными.
- **Развилки:**
  - (a) тестовый прогон модуля на копии/подмножестве графа
  - (b) staging-режим модуля: видит данные, но не пишет
  - (c) сразу боевая установка, риск принят владельцем `[сомнительно для чужих модулей, ок для своих]`
- **Пул идей:**
  - staging-флаг в манифесте модуля `[CV5, CV2]`

## CV6. Экономика обмена / маркетплейс-механика

**Чего именно касается:** каталог/витрина модулей, атрибуция и (в перспективе) вознаграждение автора,
рейтинг/доверие сообщества, условия использования чужого модуля (лицензия).

**Приоритет:** later — почему: владелец прямо сказал «маркетплейс позже». Фиксирую здесь только чтобы не
потерять грань и не забыть дешёвые заделы (например, поле `author` в манифесте уже сейчас), которые
ничего не стоят внедрить рано, но дорого добавлять задним числом.

### Направление CV6-D1 · Каталог/витрина модулей

- **Суть:** где владелец (и, позже, другие) видят список доступных модулей.
- **Развилки:**
  - (a) публичный реестр модулей — явно «позже», вне этой сессии
  - (b) приватный список «модули, которые я видел у других» — минимальная форма уже сейчас
  - (c) не нужен пока, только владелец делает модули для себя
- **Пул идей:**
  - витрина модулей как просто внешняя ссылка/файл-список позже `[CV6]`

### Направление CV6-D2 · Атрибуция и условия использования

- **Суть:** кто автор, на каких условиях модуль можно взять/форкнуть.
- **Развилки:**
  - (a) поле `author` + `license` в манифесте — минимум, дёшево сделать сейчас
  - (b) полноценная монетизация/вознаграждение — явно «позже»
  - (c) не продумываем вообще, разберёмся когда появится первый внешний автор `[сомнительно, но допустимо для later]`
- **Пул идей:**
  - поле `author`/`license` в манифесте уже в первой версии — не блокирует CV1, дёшево, готовит CV3/CV6 `[CV6, CV3, CV1]`

## 2. Идеи с ≥2 тегами (кандидаты в сквозной инфра-модуль Combination)

Собрано механически из пулов выше — сигнал «этот механизм не живёт внутри одной ценности»:

- Расширение Unified PEP (#5 Brain) до PEP-на-модуль `[CV1, CV5]`
- Approval-гейт на установку/апгрейд модуля (аналог approval-гейтов шлюза) `[CV1, CV5]`
- «Модуль как узел графа» (реестр = часть субстрата) `[CV1, CV4]`
- Контракт-мост Brain↔agents-manager (независимо от исхода развилки «один стор/федерация») `[CV4, CV1, CV2]`
- INSERT-not-migrate как версионный механизм модуля `[CV2, CV3]`
- «Апгрейд = добавление, не перезапись» как инвариант Конституции Combination `[CV2, CV3]`
- «Форк = lineage-ребро к оригиналу» `[CV3, CV1]`
- «Движок апгрейдов» как отдельный сервис проверки совместимости `[CV3, CV1]`
- Provenance-модуль Brain, расширенный тегом модуля-автора изменения `[CV5, CV2]`
- Поле `author`/`license` в манифесте с первой версии `[CV6, CV3, CV1]`

Это ещё НЕ решённые инфра-модули — просто места, где несколько ценностей тянут к одному механизму.
Схождение (следующий цикл: critic + analyst) должно проверить каждую на прочность, прежде чем поднимать
в `infrastructure/`.
