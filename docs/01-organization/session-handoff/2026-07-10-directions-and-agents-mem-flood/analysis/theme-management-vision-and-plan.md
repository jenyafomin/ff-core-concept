# Управление темами/агентами в шлюзе — модель + быстрый план

> Фаза проекта = дизайн, но ЭТА часть — плумбинг: не зависит от памяти-brain, её можно строить
> прямо сейчас поверх зрелого кода. Ниже: единая модель жизненного цикла темы, персоны, центр/лог,
> rich-фиксы, быстрый план и развилки владельцу/Fable. Опора — карта реальности кода (Related).

---

## 0. Главный структурный инсайт

Сегодня «сессия» на один ключ (`channel:conversationId[:participantId][:agentId]`) — это ОДИН
изменяемый слот: `/new` **перезаписывает** его, теряя путь к старой claude-сессии; `/resume`
мёртв, потому что архивации нет (код это честно признаёт в комментариях). Владелец же хочет
**много сохранённых тем на топик**, между которыми можно переключаться. Значит нужен ровно один
недостающий сдвиг: **тема = архивируемая запись сессии с именем; «текущая» — это указатель на
Active-запись**. Всё остальное в коде под это уже готово (БД durable, claudeSessionId per-cwd,
каскад PROMPT, канало-агностичные кнопки).

## 1. Единый механизм жизненного цикла темы (TM-1..TM-5)

### Модель состояний (краткая, 6 строк)

- **Тема** = запись `ISession` с именем (`title`, новое поле) и удержанным `claudeSessionId`;
  инвариант: **≤1 `Active` на ключ**, прочие — `Archived` (resumable, claudeSessionId НЕ стёрт).
- **Два примитива:** `SAVE` (Active→Archived: claudeSessionId сохраняем, вешаем имя) и
  `ACTIVATE` (Archived→Active: восстанавливаем claudeSessionId как текущий для resume).
- `close` = SAVE. `new` = SAVE + создать пустую Active. `resume(t)` = SAVE текущей + ACTIVATE
  выбранной. `handoff+new` = SAVE + новая Active c `parentSessionId` и переносом контекста.
  `link-context` = проставить `parentSessionId` / сид-промпт из родителя.
- `naming` — на закрытии inline-кнопки: **оставить · ввести новое · агент придумает** (+«назад»);
  имя пишется в `ISession.title`; «агент придумает» = один дешёвый LLM-вызов по хвосту диалога.
- Закрытие ВСЕГДА = SAVE (TM-1): нет операции «выбросить». Из любой темы `new`/`resume` доступны.

### Как ложится на existing (что чинить, не строить)

| Операция владельца | Existing точка | Что доделать |
|---|---|---|
| `close`/`new` (архивация) | `command-handler.resetSession` (`566-589`) | Сейчас создаёт новую запись с тем же ключом, **опуская** claudeSessionId, старую **не сохраняет**. Изменить: старую запись перед этим перевести в `Archived`, **сохранив** claudeSessionId + проставив `title`. Инвариант ≤1 Active держит репо (фильтр по статусу). |
| `resume`/переключение | `ECommand.Resume` (`67-70`, `ensureActive`) | Команда уже умеет `Archived→Idle`, но списка/выбора нет и архивных записей нет. Дать: `/resume` без арга → список Archived тем топика (кнопки), выбор → ACTIVATE (Idle/Active + восстановить claudeSessionId). |
| `handoff+new` | `resetSession` + `ISession.parentSessionId` (поле есть, сейчас опускается) | На `new --handoff`: SAVE старой, у новой проставить `parentSessionId`, опц. засеять топик-PROMPT кратким контекстом-мостом старой темы. |
| `link-context` | `ISession.parentSessionId` + топик-PROMPT каскад | Явная связь = запись `parentSessionId` + (опц.) перенос выжимки в `topicPromptPath`. |
| `naming` на кнопках | `buildKeyboard()` (`494-518`, готов, multi-row) + callback-тракт (`fb:`/`wz:` как образец) | Новый callback-неймспейс `th:` (theme): keep/new/gen/back. «gen» дергает LLM за именем. |

Реюз максимальный: примитивы SAVE/ACTIVATE = ~+30 строк к `resetSession`+репо, кнопки и callback —
по образцу уже живущих `wizard`/`browse`.

## 2. Персоны/роли агента (TM-6/TM-7)

### Модель

- **Персона = строка `IAgent`** (`systemPrompt/model/tools/skills/limits`) — уже есть в БД.
- **Слой контекста** уже собирается в `turn-executor` (`242-267`): `Agent.systemPrompt` (персона)
  → PROMPT чата → PROMPT топика (рекомендации) → топик-строка. То есть «личный промт + доп. промт
  топика + слои» из TM-6 — это уже существующий конвейер, просто база (персона) сегодня одна.
- **Резолв роутером** — вот дыра: `router.ts:27` зовёт `findBinding(message.botId)` **без**
  `topicId`, хотя `IAgentRepo.findBinding(botId, topicId?)` и `IBotBinding.topicId?` это держат.
- **Смена персоны = смена темы** (тот же принцип new/resume): т.к. персона входит в контекст и
  claude-сессия живёт per-agent-per-cwd, переключение персоны = SAVE текущей темы + ACTIVATE/создать
  тему под новую персону. Один и тот же примитив.
- **Репликация** = клон строки `IAgent` (новый id, копия systemPrompt) → инстанс личности.

### Что достроить над готовой схемой

1. **Починить резолв (S):** передать `topicId` в `findBinding` — и мультиперсоны-по-топикам
   заработают на уже существующей many-to-many схеме `agent_bindings`.
2. **Runtime-команды (L):** `/agent list | new | switch <id> | clone <id>` — сейчас единственный
   путь завести агента = `seedRegistry()` из `.env` на старте (`seed-registry.ts`). Нужен runtime-
   путь через `command-handler` + запись биндинга `Agent↔Bot↔Topic`.
3. **TM-7 (агент ставит агента):** агент из General создаёт топик и биндит туда персону — это
   `/topic new` + `/agent switch --topic` под капотом; протестировать явным сценарием.

### Чего не хватает (дёшево дозаписать)

- **`title` темы** (из §1) — даёт живое «о чём», а не только id топика.
- **`planRef` / `links[]`** на сессии или топике — ссылка на глобальный план и связанные доки
  (владелец прямо просит «ссылки на план(ы), к чему относится»). Сейчас поля нет вообще.
- **Durable-статус «ждёт владельца»** на теме (`awaiting_owner`), а не только in-memory
  approval-gate — чтобы «какие темы ждут» переживало рестарт. NB: **полноценное** «тема ждёт
  вопросов/ответов» владелец сам отнёс к ПАМЯТИ (позже) — сейчас только грубый флаг.
- **Настройка «отчитывается в чат или нет»** (TM-9) = поле `reportsToChat` на `IAgent` или на
  биндинге (`silent`). Чистый конфиг, S.
- **Read-поверхность:** БД-лог богат, но UI/HTTP нет. Сейчас — расширить текстовые `/status`/`/topics`
  (добавить title/planRef/awaiting); дашборд/API — отдельный L, ничего не блокирует.

**RM-5 точная правка.** `toTelegramHtml()` сегодня — HTML-**экранировщик** (`& < >`) + перевод
ТОЛЬКО код-разметки (` ``` `→`<pre>`, `` ` ``→`<code>`); транслятора `**` нет. Нужен порядок:
1) выделить код-сегменты (уже делается) и НЕ трогать их; 2) на текст-сегментах сначала `escapeHtml`,

`~~x~~`→`<s>`, `[t](u)`→`<a href>`, строки `# ...`→жирная строка. Критично — эскейп раньше вставки
тегов, иначе `<b>` съест `escapeHtml`. Файл `docs/01-project/ideas/2026-07-10-telegram-rich-messages/`

## 6. Развилки (владельцу / Fable)

1. **Один ли универсальный `close=SAVE` для тем И персон?** Моя позиция — ДА: SAVE/ACTIVATE —
   один примитив, персона входит в тот же контекст/ключ, переключение персоны = переключение темы.
   Развилка: считать ли смену персоны **ортогональной** теме (персона живёт поверх нескольких тем)
   или **вложенной** (каждая персона — свой набор тем). От этого зависит, входит ли `agentId` в ключ.

2. **Персона = узел памяти (brain) или конфиг (строка `IAgent` + файл-слой)?** Для плумбинга-сейчас
   — конфиг (БД-строка + PROMPT-слой топика), строим без памяти. Позже brain может владеть
   идентичностью персоны (её опыт, «вела сессии»). Где ставим границу — решить с Fable.

3. **`title`/`planRef`/`awaiting` — в БД (config) или узлы графа знаний?** Сейчас предлагаю БД-поля
   (дёшево, durable, независимо от brain). Риск дубля с будущей памятью: когда brain появится,
   «о чём тема» и «чего ждёт» могут стать узлами, а БД-поля — их проекцией. Развилка: закладывать ли
   уже сейчас `title` как ссылку-на-будущий-узел или как простое строковое поле (я за простое поле,
   миграция в узел позже дешевле, чем преждевременная связь).
