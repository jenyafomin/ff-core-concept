# Prior art: память для агентов + агент-оркестраторы

> ⚠️ **Ограничение метода:** веб-инструменты (WebSearch/WebFetch) в этой суб-агентской сессии
> вернули ошибку `Stream closed` на каждой попытке (permission/stream проблема окружения, не
> запрет по контенту) — фактического живого поиска не произошло. Бриф написан **по обученным
> знаниям модели** (срез — январь 2026), тем же методом, что и предыдущий заход
> `docs/topics/60-raw/2026-07-05-memory-research/*.md` («inline, веб недоступен»). Риск: детали

дублировать — править на месте, менять Date).

## Зачем этот бриф

Найти, что уже решено индустрией для двух модулей нашей системы, чтобы (а) не изобретать заново
инженерию, которая уже решена (bitemporal рёбра, кэш-политики забывания, паттерны делегирования),
и (b) чётко назвать, где наш дифференциатор реален, а где — самообман.

## Модуль 1 — Память для агентов (единица · связи · забывание · доверие)

### Mem0
Open-source «memory layer» для LLM-приложений (персонализация чат-ботов/ассистентов).
- **Единица:** «факт» — короткое утверждение, извлечённое LLM из диалога (не сырой текст).
- **Запись:** новый факт сравнивается с существующими той же LLM-функцией → решение
  `ADD / UPDATE / DELETE / NOOP`. Это **операционная модель ре-записи через LLM-суждение**, а не
  ручной merge.
- **Хранение:** вектор-стор (семантический поиск) + опциональный граф-стор («Mem0g») для
  сущностей/связей.
- **Скоуп:** память привязана к `user_id` / `agent_id` / `session_id` — обязательная
  многоуровневая область видимости.
- **Забывание:** слабое место — по сути нет декея/salience, `DELETE` = мягкое удаление факта по
  решению LLM, не политика времени.
- **Итог:** проще всех, хорошо для персонализации ассистента, но **тонко** там, где у нас
  Ц-4 Витальность (декей/всплытие) и Ц-3 Доверие (история пересмотров) — этого просто нет.

### Zep (движок Graphiti, open-sourced)
Наиболее близкий прецедент к нашим Гр.4-вопросам (время/происхождение).
- **Единица:** граф сущностей и связей, извлекаемый из диалогов/документов инкрементально
  (без полного пересчёта — в отличие от классического GraphRAG).
- **Ключевое:** каждое **ребро-факт бивременное** — два независимых интервала:
  `valid_at/invalid_at` (когда факт истинен в мире) и `created_at/expired_at` (когда система
  о нём узнала/перестала считать актуальным). Это **прямое, боевое решение нашего FQ12**
  (снапшот-в-момент vs bitemporal) и вопроса о В2.
  - Пример нашей эквивалентности: `source=origin+effective` (заложить сейчас) ≈ `created_at` vs
    `valid_at` Graphiti — они это уже разделили и назвали.
- **Конфликты:** новый факт, противоречащий старому, **инвалидирует старое ребро** (проставляет
  `invalid_at`), не удаляет — прямой аналог нашего «hard-erase — отдельная операция от обычного
  забывания» (FQ7): у Zep обычное протухание/противоречие НИКОГДА не физическое удаление.
- **Извлечение:** гибридный ретрив — семантика + ключевые слова + BFS-обход графа от
  «якорных» узлов.
- **Итог:** самый сильный референс для «рёбра проводят поток» (Ц-6) и для конституции времени
  (referent/hard-erase/снапшот). Но **нет** понятия «политика на самой ячейке» (наш
  policy-as-data) и нет модели согласия/суверенности по узлу.

### Letta (ранее MemGPT)
ОС-подобная модель памяти агента, самый близкий прецедент к «ячейка носит своё поведение».
- **Три уровня:** *core memory* (в окне контекста, редактируемые блоки — persona/human/system),
  *archival memory* (вне окна, векторный архив, агент сам решает, что подгрузить/выгрузить —
  функция-вызов), *recall memory* (история диалога, по запросу).
- **Memory blocks:** переиспользуемый, адресуемый, редактируемый объект памяти, который можно
  **прикрепить к нескольким агентам одновременно** — очень близко к нашему FQ22 (узел-ПРОФИЛЬ,
  каскад политик как CSS, «профиль = обычная ячейка»).
- **Self-editing:** агент сам вызывает функции для правки своей памяти («что подгрузить/
  выгрузить/переписать») — прямая параллель нашему «ячейка несёт своё поведение»
  (policy-as-data), но у Letta это поведение **агента над памятью**, не самой memory-единицы.
- **Sleep-time compute:** фоновая консолидация в паузах — уже отражено в нашем
  `REPORT-living-memory.md` (фаза C = reflection).
- **Итог:** сильный референс для FQ22 (профиль/каскад) и для «кто редактирует, агент или
  единица» — но у них политика живёт на агенте, у нас должна жить на единице (наш тезис
  сильнее и рискованнее).

### Cognee
Open-source «AI memory engine», пайплайн-ориентированный (ECL: Extract → Cognify → Load).
- **Единица:** граф знаний + вектор + реляционные таблицы одновременно, строится из
  неструктурированных данных батчем/пайплайном, с онтологией.
- **Фокус:** улучшение RAG через структурную память, **не** реал-тайм разговорная
  salience/decay — скорее аналог нашего «холодного» (COLD/REFERENCE) слоя из
  `REPORT-data-temperature.md`, батч-ingestion.
- **Итог:** полезный референс для инфраструктурных идей I-2 (трейс) и I-5 (планы-как-данные) —
  паттерн «сырой вход → извлечение → загрузка в граф» как отдельная труба, не смешанная с
  живой salience-моделью.

### LangMem (LangChain/LangGraph)
Явная таксономия памяти для LangGraph-агентов.
- **Три типа:** *semantic* (факты), *episodic* (примеры прошлого опыта — few-shot), *procedural*
  (инструкции/системный промпт, который со временем переписывается).
- **Namespaces:** память скоупится по `(user, thread, agent)` — снова обязательная
  многоуровневая область видимости (как у Mem0).
- **Consolidation:** фоновый «memory manager» извлекает/сжимает память из диалога в бэкграунде,
  подключается как pluggable store к персистентности LangGraph (checkpointer).
- **Итог:** таксономия (semantic/episodic/procedural) — прямая пища для нашего FQ16 («брейн =
  4 плана» — у них 3, у нас обсуждается 4-5 с Аффектом/FQ17). Ни один продукт из пятёрки не
  вводит явный «аффективный» план — это может быть реальным нашим отличием, а может быть
  оверинжинирингом (см. FQ17 «оспорено»).

### Векторно-графовые гибриды (общий паттерн, GraphRAG/LlamaIndex property graph/Neo4j+vector)
- Общий рецепт индустрии: LLM извлекает сущности+связи в граф, вектор-индекс поверх текстовых
  чанков/сущностей для семантического якоря, ретрив = вектор находит «точку входа» → обход графа
  добирает контекст. GraphRAG сверху добавляет **community detection + иерархическая
  суммаризация** (map-reduce по кластерам графа) для глобальных вопросов — это ровно наш
  «rollup-узел» / консолидация (уже отмечено в `REPORT-living-memory.md`).

### Сквозные наблюдения (важно для конституции)

1. **Двухплановость universal:** сырой лог событий (append-only) отделён от материализованной
   памяти (факт/summary) — во всех пяти. Прямое подтверждение нашего FQ13 (append-only) и FQ20
   (биография как отдельный род).
2. **Мягкое, не жёсткое, обычное забывание.** Никто физически не удаляет историю при обычном
   protuxании/конфликте — только инвалидация/понижение видимости (Zep: `invalid_at`; Mem0:
   soft-delete факта). Жёсткое стирание — если оно вообще есть — отдельная, редкая операция
   (GDPR-эндпоинт), не часть обычного механизма. Это **подтверждает** нашу интуицию FQ7
   (referent+hard-erase как ОТДЕЛЬНАЯ операция от забывания), но **никто не поднял это на
   уровень конституционного права референта** — они решают это как compliance-фичу, не как
   этический инвариант с согласием.
3. **Скоуп/namespace как узел доверия — universal**, но нет ни одного продукта с полем
   «согласие референта» или «многосторонняя суверенность» (память о ДРУГОМ человеке требует его
   согласия) — это реальный **незанятый угол**, кандидат в наш дифференциатор (Ц-5+Ц-7).
4. **Policy-as-data на уровне ЕДИНИЦЫ памяти нигде не встречена.** Везде политика (decay,
   consolidation, access) — глобальная настройка системы или максимум настройка агента (Letta).
   Наш тезис «ячейка сама несёт свою политику» (нацелен на разнородность жизни человека одним
   контрактом) — не имеет прямого прецедента. Это либо наш реальный дифференциатор, либо
   недоказанная гипотеза, которую стоит стресс-тестировать раньше, чем строить (см. под-вопрос
   ниже).
5. **Никто не строит субстрат «под много модулей экосистемы» (I-9).** Все пять — библиотека
   памяти ДЛЯ одного агента/приложения, а не база, на которой стоят разнородные модули (задачи,
   финансы, календарь), которые сам агент — лишь один из потребителей. Это ближе к нашему видению
   уровня VISION, не memory-SDK уровня.

## Модуль 2 — Агент-оркестраторы/менеджеры (сравнение с agents-manager)

### LangGraph (LangChain)
- **Thread + checkpointer:** каждый разговор адресуется `thread_id`, состояние (checkpoint)
  персистентно между ходами ЭТОГО треда; новый `thread_id` = чистый лист, тот же — продолжение.
  Это готовый словарь, снимающий нашу путаницу I-1 («resume ≠ new session, если это тот же
  thread_id»): **ход = один шаг графа, сессия = один thread_id + цепочка чекпоинтов**, «новая
  сессия» — явное решение завести новый thread_id, а не побочный эффект случайного клика.
- **Supervisor pattern:** отдельный узел-«супервизор» решает, какой под-агент обрабатывает
  следующий ход, может зациклить обратно к себе — прямой референс для I-7 («один чат управляет
  многими»).
- **`interrupt()` как узел графа:** явная точка «спросить человека», а не произвольный ad-hoc
  вопрос где угодно — референс для I-11 (human-in-the-loop только на ключевых развилках,
  формализовано как data, не как решение агента на лету).

### AutoGen / AG2 (Microsoft)
- **GroupChatManager:** менеджер-агент в групповом чате выбирает следующего говорящего среди
  участников по стратегии (round-robin / LLM-выбор / кастом) — ещё один референс для «один чат,
  много агентов, видно у кого висит вопрос» (I-7).
- Агенты — «conversable», обмен сообщениями явный, история группового чата — общий журнал,
  видимый всем участникам (в отличие от изолированных тредов LangGraph).

### CrewAI
- Роль-ориентированные «команды» (crew) с заранее заданными ролями/целями/инструментами,
  процесс sequential или hierarchical. Более статичная конфигурация (YAML/код), меньше похоже на
  наш «топик = живой долгоживущий агент с редактируемым промптом на лету».

### OpenAI Swarm / Agents SDK
- **Handoff как данные:** передача управления другому агенту — просто функция, возвращающая
  следующего агента + контекст, без магии оркестратора. Явная лёгкая модель — созвучна нашему
  «policy-as-data»: делегирование — тоже данные, не скрытая логика.
- Сам SDK **не берёт на себя память** — разработчик обязан хранить контекст сам (совпадает с
  нашей позицией «agents-manager — генератор требований к памяти», не сама память).

### LangSmith (трассировка, не оркестратор, но релевантно I-2)
- **Run tree:** каждый вызов — узел с `parent_run_id`, рекурсивное дерево вызовов, на каждом узле
  — токены/стоимость/время. Это **буквально та же модель данных**, что нужна для I-2
  (экономический трейс: сам съел / дети съели, дерево делегирования). Не нужно изобретать формат
  — взять «run tree с parent_run_id + token usage per node» как есть.

### Сквозные наблюдения

1. **Ни один из фреймворков не имеет «промпт/конфиг как редактируемый агентом markdown-файл,
   применяемый со следующего хода»** — это специфика agents-manager (каскад
   `PROMPT.md` chat→topic, `config.json` bind), нигде в прior art не встречена в таком виде.
   Это реальная сильная сторона нашей системы (policy-as-data доведено до уровня оркестрации,
   не только памяти) — **беречь, не менять на фреймворк**.
2. Все фреймворки разводят «сессию» (постоянный контейнер состояния) от «хода» (один шаг) —
   подтверждает наш словарь I-1, но переносит развилку на: **что у нас формально образует новый
   `thread_id`** — смена топика Telegram? команда `/new`? смена cwd (`config.json`)? Сейчас это
   неявно (ADR agents-manager), стоит формализовать так же явно, как LangGraph.
3. Токен-трейс (I-2) — решённая задача с готовой формой данных (run tree), не нужно
   изобретать — нужно решить, **где она живёт** (в базе памяти как узел-тип, или отдельная
   телеметрия сбоку) — это открытый вопрос, не инженерный риск.

## Варианты решения (см. `options` в структурированном выводе) + предварительная рекомендация

Коротко: **не пересаживаться целиком** ни на один продукт (у каждого не хватает нашей
конституционной части — referent/hard-erase-как-право, согласие, policy-as-data на уровне
единицы, agents-manager-специфика промпт-каскада), но **точечно занять** проверенные форматы
данных там, где прецедент уже решил инженерную часть (bitemporal рёбра Zep/Graphiti, run tree
LangSmith, thread/checkpoint словарь LangGraph, memory-blocks Letta для профиля/каскада).

## Под-вопросы, требующие решения владельца/Fable

1. Принять ли **бивременной формат ребра-факта** (`valid_at/invalid_at` + `created_at/expired_at`,
   по образцу Zep/Graphiti) как конкретную реализацию нашего FQ12/В2 — вместо более дешёвого
   «снапшот-в-момент»? Цена: 4 поля на ребро вместо снапшота; выгода: решает FQ7 (инвалидация ≠
   удаление) бесплатно, как побочный эффект формата.
2. Вводить ли **узел-тип «профиль/политика»** (аналог Letta memory-blocks, наш FQ22) прямо сейчас
   как часть «заложить сейчас, ретрофит невозможен» — или это можно отложить без риска?
3. Формализовать ли **явную границу «сессия/тред»** в agents-manager по словарю LangGraph
   (thread_id + checkpoint), чтобы закрыть путаницу I-1 — не мигрируя сам гейтвей на LangGraph
   (просто заимствуя словарь и правило «когда рождается новый thread_id»)?
4. Куда кладём **run tree токен-трейса (I-2)** — как узел-тип внутри той же базы памяти (единый
   субстрат, Ц-1 Читаемость) или как отдельная телеметрическая труба сбоку (Cognee-подобный
   батч-пайплайн), которая лишь ссылается на ячейки?
5. **Тезис policy-as-data на уровне единицы** (не агента, не системы) — нигде в prior art не
   встречен как реализованный. Стоит ли заложить дешёвый прототип-стресс-тест ДО того, как
   строить на нём весь хребет (риск: строим уникальное здание на непроверенном фундаменте)?
6. ⚠️ Этот бриф написан без живого веб-поиска (инструмент не сработал в сессии). Прогнать ли его
   повторно с рабочим WebSearch перед тем, как на него опираться при финальных решениях FQ7/FQ12/
   FQ22 (проверить: не изменились ли форматы Zep/Letta/Mem0 к июлю 2026)?
