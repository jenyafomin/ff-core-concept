# Сходимость единицы памяти под требования agents-manager — исследовательский бриф

> Готовится как материал для дорогого совета Fable. Веб-поиск в этой сессии оказался недоступен
> (инструмент упал с ошибкой доступа) — prior art ниже дан по обученным знаниям агента, без
> живой сверки; пометить как advisory до отдельной проверки, если Fable сочтёт важным.

## 1. Рамка вопроса

Владелец забросил ~12 идей 2026-07-10 (`CAPTURE.md`), почти все — требования к agents-manager,
которые хотят жить «в базе»: сессии, планы-деревья, экономический трейс токенов (рекурсивное
дерево делегирования), связи-как-первоклассная-сущность (роутер), области/группы с фильтруемой
видимостью. Синтез CAPTURE.md уже дал рамку: agents-manager — не конкурирующий трек, а
**генератор требований** к единице памяти. Вопрос этого брифа: **удовлетворяет ли** текущая модель
памяти (7 ценностей · паспорт/policy-as-data · canonical_id · bitemporal · единый PEP · Edge Engine)
эти требования, или нужно закладывать что-то ещё СЕЙЧАС (ретрофит невозможен — правило проекта).

## 2. Что уже готово в agents-manager (не гипотеза — код/дизайн есть)

- **Durable Job-дерево** (`durable-orchestration-step.md`, дизайн Fable от 2026-07-05, статус
  proposed): `parentJobId`, `kind` (turn/spawn/continuation), `status`+`WaitingChildren`,
  `dedupeKey` UNIQUE, `resumeSessionId`, `resultMessageId`, `depth`. Это Saga/Process-Manager
  поверх атомарных `claude -p`-ходов, с барьерной транзакцией (3 чекпоинта) и barrier-scan на
  рестарте. Это уже РАБОТАЕТ как модель на уровне SQLite (Queue/lease/reaper переиспользуются).
- **Session/Topic**: `session.entity` (`newAt`), `ITopic`/`topicId`, `findByThreadId` — уже
  ADR-принято (ADR-0002, approved 2026-07-08). Топик=агент=тема — существующий субстрат.
- **Token/cost наблюдаемость** (A2/A3, observability-refactor): счётчик стоимости за сессию (нужен
  id сессии), граф расходов по агентам — рекурсивно (сам съел / дети съели), в разбивке по
  периодам и модели. Модель данных для этого **не спроектирована** («узел=агент/сессия, ребро=
  делегирование+токены+модель+временной срез» — открытый вопрос, «пересекается с
  durable-step-design»).
- **Scope-резолвер** (IDEAS-INDEX, цикл 4): независимо от brain, agents-manager вывел **тот же
  каскадный приём** — дерево `глобально → группа → область → топик → агент`, любая привязка
  (контекст/навыки/лимиты/права) = `binding` на узле дерева, каскад «как CSS» (узкое
  переопределяет широкое). Открытый вопрос там же: каскад **разный по типу** — для прав «строгий
  побеждает», для контекста «специфичный побеждает».
- **Task/Plan** (PLAN-0001 Фаза 2): `Task` = намерение+атрибуция, `Plan` = цепочка шагов, каждый
  шаг несёт риск-класс; спроектировано как SQLite-персистенция, **не как узел brain**.
  Плюс открытое требование **межпроектности** (2026-07-08): план/диспетчер не привязаны к одному
  репозиторию — нужен универсальный слой поверх проектов (Universal/Domain по конституции, не
  Project — выше планка ADR).

## 3. Сведение с 7 ценностями/хребтом brain — по пунктам

### 3.1 Сессии/ходы/темы (I-1)
Хребет тождества (`canonical_id`+bitemporal) и паспорт технически МОГУТ описать «Сессию» как
ячейку. Но нигде в FQ1-24 не проговорено, что Session/Turn/Job — это тоже роды узлов. Ключевая
неопределённость — не техническая, а **разграничение слоёв**: сессия — это ДЛЯЩАЯСЯ ячейка (одна
версия во времени, bitemporal-история статусов), или ПРОИЗВОДНОЕ представление, выводимое из
append-only потока ходов (turn-событий) без отдельного «канонического» узла-сессии? От ответа
зависит, нужен ли Session отдельный `canonical_id`-неймспейс уже сейчас.

### 3.2 Планы-деревья (I-5) и Job-дерево agents-manager
`durable-orchestration-step.md` уже решил дерево через `parentJobId`+статус+барьерную транзакцию —
это ОПЕРАЦИОННЫЙ примитив (нужны: unique-constraint на `dedupeKey`, атомарный barrier-check при
последнем ребёнке, lease/reaper на рестарте). Brain’s Edge Engine (#11, инфраструктура) сегодня
решён УЗКО (В4, ратифицировано): паспорт получают только **рёбра-инсайты**, не любое ребро. Значит
формально «дешёвое» структурное ребро (parent-child Job, plan-step-of) уже подразумевается как
рёбро БЕЗ паспорта — совместимо. Но ЖИВЁТ ли Job-дерево *в* brain или *рядом с* ним — не решено
нигде, и это разное по цене: Job — высокочастотная, шумная, чисто операционная сущность (десятки
статус-флипов на ход); bitemporal-версионирование КАЖДОГО флипа статуса Job'а — дорогая
(по духу) операция для движка, спроектированного вокруг «жизни человека», не «очереди задач».

### 3.3 Токен-трейс / граф расходов (I-2, A3)
Рекурсивный граф делегирования (агент→агент, токены/деньги/модель, срез во времени) — это по сути
**новый род ребра** («spend-edge»), плюс rollup-агрегация. Он логически близок к «снапшоту-в-
момент» (FQ12, уже 🔴 заложить сейчас) — снимки во времени уже предусмотрены как примитив. Но
сам факт «трата токенов» — это высокочастотное МЕХАНИЧЕСКОЕ событие (не инсайт, не встреча) —
подпадает ли оно вообще под 7 ценностей (согласие/доверие/confidence), или это исключённый из
эпистемической машины класс «системной телеметрии»? Это нигде не разведено.

### 3.4 Связи-как-роутер (I-3) ↔ Scope-резолвер agents-manager ↔ FQ22 (узел-профиль)
**Сильная конвергенция, уже найденная независимо в обеих ветках.** Brain (FQ22, review) предложил
почти ТОЧНО тот же механизм, что Scope-резолвер agents-manager: каскад override→profile→
конституция, «как CSS». НО FQ22 сейчас на голосовании держит **конституционный лимит глубины
каскада = 1** (обоснование через FQ23 стоп-правило: «профиль профиля» не даёт различающей силы).
**Прямая нестыковка**: Scope-резолвер agents-manager требует каскад из **пяти** уровней
(глобально→группа→область→топик→агент), не одного. Если это ОДИН и тот же механизм — предложенный
FQ22-инвариант «глубина=1» нужно убить/переформулировать ДО ратификации, иначе он закрывает дверь,
которую agents-manager явно собирается открывать. Если это ДВА разных механизма (внутриячейковый
policy-каскад vs операционное дерево адресации) — тогда конфликта нет, но это надо явно
зафиксировать сейчас, а не обнаружить после ратификации FQ22.

### 3.5 Области/группы + видимость (I-4) ↔ Единый PEP
PEP (#5, инфраструктура, 🔴 заложить сейчас) уже проектируется с `tenant-изоляция` в списке —
хорошее пересечение. Но PEP — это **read-time гейт** (кто что видит при обращении), а Area из
голосового владельца — это ещё и **адресуемый узел** для роутинга/биндинга (тот же узел, на
который вешаются context/skills/limits в Scope-резолвере). Т.е. Area должна одновременно быть:
(а) партиция видимости, которую спрашивает PEP, и (б) узел дерева, на который навешиваются
привязки. Agents-manager уже нашёл манеру развести это правильно: **каскад разный по типу
привязки** (права → «строгий побеждает», контекст → «специфичный побеждает») — один и тот же
дерево-субстрат, разные правила композиции по виду binding'а. Это хороший паттерн для переноса в
brain, но его нужно явно принять как ЕДИНОЕ решение (не проектировать PEP-партиции и Scope-дерево
как два независимых дерева).

## 4. Главный сквозной вывод

Все четыре пересечения (3.2–3.5) упираются в один и тот же нерешённый вопрос более высокого
порядка: **у brain должна быть ОДНА консистентность-модель, или ДВЕ параллельных?**

- **Эпистемическая плоскость** (факты о жизни человека): мягкая, policy-driven, живёт по 7
  ценностям (confidence, забывание, согласие, температура). Спроектирована подробно (L0-L2, FQ1-24).
- **Операционная плоскость** (Job/Session/Queue/cost-edge): нужна ACID-семантика — unique
  constraint, атомарный барьер, lease/reaper, высокая частота записи, НЕ требует confidence/decay/
  hard-erase в том же смысле, что личный факт.

Если brain становится единственным субстратом для ОБЕИХ — паспорт/policy-as-data и forgetting-
engine должны либо научиться игнорировать операционные ячейки (нужен явный флаг класса ячейки
с 1-й итерации — «эпистемическая» vs «системная/операционная»), либо операционные сущности вообще
не должны жить в brain как источник истины, а только как ПРОЕКЦИЯ (снимок на контрольных точках).
Это решение — по духу ровно то, что список «заложить сейчас» уже требует для другого (referent,
source=origin+effective, снапшот-в-момент) — тот же класс необратимости: если сейчас решить
неверно, поздно разводить постфактум.

## 5. Варианты (для решения владельца/Fable)

### Вариант A — Единый субстрат (brain = источник истины и для Job/Plan/cost-графа)
- **Плюсы:** одна истина, самообучение (CBR-ретривер) видит вообще всё без синхронизации;
  «видно ИИ, видно что делает» выполняется по построению; нет дублирования Task/Plan-модели.
- **Минусы:** тащит ACID-нужды (unique dedupeKey, атомарный барьер, lease) в движок, спроектированный
  вокруг мягкой policy; риск раздуть паспорт «системными» полями и сломать Ц-1 Читаемость («не
  CRM», принцип из reframe msg 141, но CRM-подобный шум — ровно то, чего боялись в FQ12 recheck);
  требует переписать уже рабочий SQLite Job-движок agents-manager (durable-orchestration-step.md
  уже спроектирован и почти готов к MVP) — конфликт с фазой «дизайн, не стройка».

### Вариант B — Два слоя: движок операций (agents-manager, source of truth) + проекция в brain (рекомендация-сид)
- Agents-manager держит СВОЙ быстрый SQLite-движок (Job/Queue/Session/Lease) как источник истины
  для исполнения — он уже спроектирован и не требует ретрофита brain. Brain получает **тонкие
  проекции с паспортом** в контрольных точках (по FQ12 «снапшот-в-момент»): итог сессии, срез
  дерева плана, rollup стоимости за период — не каждый статус-флип.
- **Плюсы:** не трогает уже рабочую машинерию agents-manager (Фаза 0-3 идут независимо, как и
  спланировано в PLAN-0001); brain остаётся token-экономным (не читает сырой шум каждый ход,
  принцип из `token-cost-of-file-ops.md`); совпадает с уже ратифицированной философией FQ12.
- **Минусы:** два источника (хоть и асимметричных — один авторитетный, один производный) требуют
  явного контракта «когда именно проецируем и что именно» — новая поверхность дизайна, не бесплатно.

### Вариант C — Разделение по критерию «читаемости» (уточнение B)
- Не всё операционное одинаково ценно для будущего агента/человека. Явный тест: «человек или
  будущий агент захочет ВСПОМНИТЬ/порассуждать об этом, или это чистый плампинг?» — Plan/Task и
  граф расходов (A3) проходят тест (владелец прямо просил самообучение и видимость трат);
  низкоуровневый Queue/lease/dedupe — не проходит, остаётся только у agents-manager.
- **Плюсы:** минимальная, осмысленная поверхность brain; прямое применение Ц-1.
- **Минусы:** требует решить порог «что достойно памяти» ПРЯМО сейчас по каждому будущему типу
  сущности — риск ошибиться и не заметить важное (например, не затрассировать cost вовремя).

### Вариант D — Разрешить только Area/Scope сейчас, Job/Plan отложить
- Закрыть СЕЙЧАС только конфликт FQ22-глубина vs 5-уровневый Scope-резолвер (он единственный уже
  проверенно неретрофитируемый — FQ22 идёт к голосованию с несовместимым лимитом). Job/Plan/
  cost-graph — отложить до реальных данных использования (Фаза 2/3 agents-manager даст факты, не
  мнения — по правилу «evidence not opinion» из evolution.md).
- **Плюсы:** соответствует дисциплине «не строить впереди доказательств»; закрывает единственный
  уже-обнаруженный неретрофитируемый конфликт.
- **Минусы:** риск, что решение «brain=проекция, не источник истины» для Job/Plan само окажется
  неретрофитируемым, если его не зафиксировать сейчас (сменить курс с «источник истины» на
  «проекция» позже — дорогая миграция).

## 6. Предварительная рекомендация

Гибрид **B+C**: agents-manager остаётся источником истины по операционному исполнению (Job/Queue/
Session/Lease — уже спроектировано, почти готово к MVP, не нужно ждать brain). Brain получает
паспортные ПРОЕКЦИИ по контрольным точкам (FQ12) для того, что проходит тест читаемости (Ц-1):
Plan/Task-срез, граф расходов, итог сессии — это войдёт в самообучение (CBR-ретривер agents-manager
сам называет тот же паттерн). Area/Scope-резолвер — **решить сейчас как ЕДИНЫЙ механизм** (не
плодить второе дерево), что требует пересмотреть FQ22 depth=1 ДО ратификации, с явным правилом
«каскад разный по типу binding'а» (права/контекст — как уже нашёл agents-manager). Это не решение
владельца — представлено как материал для Fable/владельца, а не финальный выбор.

## 7. Под-вопросы для Fable (острые развилки)

1. **Модель консистентности:** brain должен допускать ДВА режима (эпистемический мягкий + системный
   ACID) в одном движке, или операционные сущности (Job/Session/Queue) конституционно НИКОГДА не
   являются источником истины в brain, а только проекцией из отдельного движка исполнения?
2. **FQ22 depth=1 vs 5-уровневый Scope-резолвер:** это один и тот же каскадный механизм (тогда
   лимит глубины=1 нужно убить/переписать ДО голосования) или два разных дерева, которые только
   выглядят похоже (тогда развести явно в engine-spec, чтобы не путать при реализации)?
3. **Граница «дешёвого» ребра:** нужен ли явный класс структурных/операционных рёбер без паспорта
   (parent-child Job, plan-step-of, spend-edge) отдельно от узкого класса рёбер-инсайтов (В4),
   зафиксированный СЕЙЧАС в контракте Edge Engine — или это можно оставить неявным и добавить позже?
4. **Статус токен-трейса:** трата токенов/делегирование — это факт, подчинённый confidence/
   consent/forgetting как любой другой узел графа, или системная телеметрия, освобождённая от
   эпистемической машины (и если освобождена — какой флаг паспорта это помечает с 1-й итерации)?
5. **Словарь Сессия/Ход/Тема (I-1):** Session — это длящаяся ячейка с собственным canonical_id и
   bitemporal-историей статусов, или чисто ПРОИЗВОДНОЕ представление, вычисляемое из append-only
   потока ходов без отдельного канонического узла? От ответа зависит, резервировать ли
   `canonical_id`-неймспейс под Session уже сейчас.

## 8. Prior art (advisory — не сверено вживую, веб-поиск в сессии недоступен)

- **LangGraph (checkpointer/threads)** — durable execution state графа per `thread_id`, явно
  ОТДЕЛЕНО от их отдельного API долгосрочной памяти (memory store). Прецедент ровно для
  «два слоя» (Вариант B): исполнение и память — разные хранилища с разной дисциплиной консистентности.
- **Temporal.io** — workflow/activity durable execution через event-history+replay; workflow —
  источник истины исполнения, никогда не «база знаний». Child-workflow + барьер по паттерну очень
  близки к `durable-orchestration-step.md` (Saga/Process Manager) — подтверждает, что Job-дерево
  agents-manager уже реализует известную, отдельную от «памяти» дисциплину.
- **Letta / MemGPT** — тройное деление памяти: core (маленькое, всегда в контексте), archival
  (векторное, по запросу), recall (история диалога). Прецедент тиринга «снапшот-в-момент» (core,
  решающие точки) vs полная append-only история (archival/recall) — поддерживает FQ12 как
  уже верный примитив.
- **OpenTelemetry GenAI semantic conventions** — стандартизация span/trace атрибутов LLM-вызовов
  (conversation.id, token usage, model) как ОБСЕРВАБИЛИТИ-телеметрия, отдельно от «знания».
  Поддерживает трактовку токен-трейса как системной телеметрии (см. под-вопрос 4), а не
  эпистемического факта.
- **CSS cascade/specificity** — та же аналогия, к которой независимо пришли FQ22 (brain) и
  Scope-резолвер (agents-manager). Известная боль CSS — неограниченная глубина специфичности;
  прямое обоснование для под-вопроса 2 (глубина каскада должна быть решена явно, не оставлена
  неявной).

## 9. Что НЕ решается этим брифом

Не выбирается финальный вариант (A/B/C/D) — это решение владельца после совета с Fable. Не
предлагается конкретная схема таблиц/паспорта — только развилки уровня архитектуры/конституции.
