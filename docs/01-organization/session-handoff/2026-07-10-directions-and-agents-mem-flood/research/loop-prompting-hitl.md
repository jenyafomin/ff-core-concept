# Ресёрч-бриф: loop-prompting / «бесконечный» цикл + human-in-the-loop

> ⚠️ **Оговорка метода.** В этой сессии инструмент веб-поиска был недоступен (permission/stream error
> при каждой попытке) — ресёрч опирается на (а) уже проделанный в `agents-manager` разбор внешнего
> референса (см. ниже, это САМ факт первоклассного prior art — не пересказ, а живой артефакт в
> соседнем проекте) и (б) обученное знание автора (срез до начала 2026) по общим паттернам
> human-in-the-loop, которое **не ратифицировано** внешней проверкой в этой сессии — трактовать как
> advisory (Source-of-truth уровень E), не как подтверждённый факт. Рекомендация: при следующей
> возможности прогнать веб-поиск повторно и дозаписать сюда актуализацию.

## 1. Главная находка: prior art уже лежит рядом, разобран и один в один

В `agents-manager` (сосед-проект, тот же владелец, тот же шлюз) **уже есть** законченный разбор
GitHub-проекта «loop» — это `cobusgreyling/loop-engineering` (MIT, ~6.8k★, TypeScript), плюс
собственный независимо выведенный план автономной оркестрации, который сверился с этим референсом
и совпал почти 1:1. Файлы:

- `docs/01-project/references/loop-engineering/VERDICT.md` — разбор + карта соответствий
- `docs/01-project/references/loop-engineering/raw/source-extract.md` — сырые факты из репо
- `docs/plan/PLAN-0001-autonomous-orchestration.md` — свой план (фазы 0-5), написан ДО сверки
- `docs/plan/PLAN-0002-loop-engineering-adoption.md` — план переноса переносимых концептов

**Ядро идеи источника** (цитата Boris Cherny, глава Claude Code, приведена в VERDICT.md): «Я больше
не промпчу Claude. У меня крутятся петли, которые сами промптят Claude и решают, что делать» —
точка приложения силы смещается с «промпта» на «петлю» как инженерный, повторяемый объект.

### Строительные блоки loop-engineering
Scheduling · Worktrees (git-изоляция попытки) · Skills (устойчивое знание) · Connectors/MCP ·
Sub-agents (maker/checker) · State/Memory (`STATE.md` — хребет памяти вне разговора).

**Анатомия петли:** расписание → skill-триаж → чтение/запись STATE → изолированный worktree →
sub-agent-исполнитель → sub-agent-верификатор → MCP/Git → человеческий гейт (safe/allowlist vs
risky/escalate) → commit/PR или эскалация → снова петля. Ключевой инвариант: **исполнитель никогда
сам не помечает работу «done»** — только отдельный верификатор.

### Машинная единица «паттерн» (данные, не код)
Обязательные поля: `id · name · file · goal · cadence · risk(low|medium|high) · tools[] · skills[] ·
state · phases[] · human_gates[]`. Опционально: `cost{tokens_noop, tokens_report, tokens_action,
suggested_daily_cap, early_exit_required}`. **`human_gates[]` обязателен и непустой** — это прямой
ответ на «запросы к человеку только на ключевых развилках»: развилка объявляется ДАННЫМИ в паттерне,
не решается на лету агентом.

### Фазность и безопасность
L1 (только отчёт) → L2 (ассистированные патчи по allowlist + гейт) → L3 (автономно, circuit
breaker). Loop Ready Score (балльная проверка готовности петли перед автономным запуском).
Kill-switch (флаг `loop-pause-all` в STATE или label). Denylist необратимого/чувствительного —
только через человека, никогда автоматом.

### Карта совпадений с agents-manager (уже сверено в VERDICT.md)
| loop-engineering | agents-manager | Вердикт |
|---|---|---|
| L1→L2→L3 | Фаза 1 зоны 🟢🔴🟡, PLAN-0001 фазы 4-5 | ✅ совпало 1:1 |
| allow/deny + human gate + kill-switch | `ToolApprovalGate`, ADR-0001, deny-list | ✅ есть |
| STATE.md | Job-дерево + диспетчер (Фаза 3) | ✅ есть, богаче |
| `registry.schema.json` | `Task`/`Plan` с риск-классом на шаге (Фаза 2) | 🔶 взять схему |
| maker/checker | делегирование есть, явного verifier-гейта в коде нет | 🔶 добрать |

### Три примитива, которых у agents-manager (и тем более у brain) НЕТ
1. **Worktree-изоляция** — попытка живёт в одноразовой ветке, выбрасывается при REJECT.
2. **Явный verifier-гейт** — «исполнитель не помечает done сам».
3. **Circuit breaker** — авто-стоп по счётчику попыток/токенов.

## 2. Дополнительные практики HITL (общее знание, НЕ веб-верифицировано в этой сессии)

Для полноты картины — паттерны из более широкого поля агентных систем, которые концептуально решают
ту же задачу «петля крутится сама, человек нужен только в развилках». Помечены как advisory.

- **LangGraph `interrupt()` + checkpointer** — граф явно объявляет узел, на котором исполнение
  ставится на паузу и персистится; человек отвечает — граф резюмируется с того же места. Механика
  почти дословно совпадает с уже принятой в FF моделью «ход = resume, не reset» (I-1 добор в
  CAPTURE.md) — сильный концептуальный мост, стоит проверить при следующем доступе к вебу.
- **AutoGen `human_input_mode=TERMINATE`** — агент сам решает, когда позвать человека (вызывает
  явное действие «спросить»), в остальное время крутится автономно. Самая дешёвая механика для
  «спрашивать только на развилках», но и самая рискованная: агент сам судит о своей неуверенности —
  тот же класс ошибки, что убивал AutoGPT/BabyAGI (2023): без внешнего бюджета/circuit-breaker петля
  расходится или зацикливается, а «развилка» может быть не распознана вовремя.
- **HumanLayer-стиль approval-required-for-tool** (Slack/email approval перед необратимым действием)
  — концептуально то же, что уже есть в проекте: `ToolApprovalGate` / permission-prompt самого
  Claude Code / клапан доверия на необратимые внешние действия (уже канон в CLAUDE.md проекта).

**Вывод раздела 2:** ничего принципиально нового сверх того, что уже осмыслено в
`agents-manager` + каноне brain (клапан доверия, PEP). Совпадение с `interrupt()`-паттерном полезно
как независимое подтверждение модели «ход=resume».

## 3. С пониманием / вслепую — что брать, что опасно тащить

**Брать (переносимо, safe):**
- Машинную единицу «паттерн» как данные (`human_gates[]` обязателен, риск-класс на шаге) —
  ложится на уже спроектированные `Task`/`Plan` (PLAN-0001 Фаза 2), не требует нового стора.
- Контракт **verifier ≠ executor** — дёшево добавить как правило, не примитив.
- **Circuit breaker + kill-switch** — минимальная защита от рантайм-катастрофы петли.
- **Cost-профиль (no-op/report/action + daily cap)** — прямое пересечение с I-2 (экономический
  трейс токенов) из CAPTURE.md — вероятно, один и тот же инфра-модуль, не два разных.
- `STATE.md`-хребет — FF уже независимо изобрёл тот же паттерн (`session-handoff/STATE.md`,
  «канонический статус проекта: docs/STATE.md»).

**Опасно тащить вслепую:**
- **npm-CLI и сами 7 паттернов** (`loop-audit`, `loop-cost`, PR Babysitter, CI Sweeper…) — заточены
  под GitHub PR/CI-воркфлоу автора. FF/brain — не CI-агрегатор кода, а агрегатор ЖИЗНИ; копировать
  паттерны дословно значит унаследовать чужую предметную область.
- **Worktree-изоляция как есть** — примитив предполагает git-правку кода. Для petель над ПАМЯТЬЮ
  (курирование узлов, синтез диалога) нужен свой аналог «одноразовой песочницы» — скорее всего
  draft/staging-узел или снапшот-в-момент (уже есть кандидат FQ12), а не буквальный git-worktree.
  Нужен явный перевод примитива, не копипаста.
- **Полная автономия (L3) до гейтов** — сам источник и agents-manager сходятся: L3 требует ADR +
  circuit breaker + verifier ДО включения. Для brain это ещё жёстче: память — единственный слой, где
  «ретрофит невозможен» (INDEX.md, «Заложить СЕЙЧАС»), поэтому автономный цикл, пишущий в граф без
  верификатора, — прямой риск death-by-design.
- **Агент сам решает, что считать «развилкой»** (AutoGen-стиль) — рискованно как единственный
  механизм без явного реестра `human_gates[]`; лучше комбинировать: реестр решает, ГДЕ гейт есть по
  умолчанию, агент может лишь ЭСКАЛИРОВАТЬ сверх реестра, не занижать его.

## 4. Базовый функционал топиков — что уже строится СЕЙЧАС, без brain (ответ на I-12)

Это НЕ гипотеза — уже заспецифицировано и реализовано (implemented, не задеплоено) в
`agents-manager`:

- **`SPEC-telegram-topics.md`** (status: implemented, 2026-07-08): `/send [<path>...]` — файлы в
  топик; `/send --topic <threadId>` — адресация в выбранный топик; `/bind --topic`, `/prompt --topic`
  — настройка НЕ текущего, а указанного топика; `/topic new|rename` — бот сам заводит/переименовывает
  темы (нужно право `manage_topics`).
- **`ADR-0002-gateway-topic-and-reply-awareness.md`** (status: approved, 2026-07-08): каждый ход
  получает строку контекста темы в `systemPrompt`; `session.topicId` проставляется при создании
  сессии (если тема уже зарегистрирована); reply-осведомлённость — сниппет цитируемого сообщения
  протаскивается как фолбэк, когда истории сессии недостаточно.
- Из PLAN-0001 (§1, «что уже есть»): топики + очередь + durable Job + live-egress + persistent
  сессии на тему — уже готовые кирпичи, НЕ зависят от модели памяти brain.
- **Явно НЕ сделано / отложено** (не блокирует, но и не путать с «готово»): полная агрегация истории
  сообщений по теме поперёк сессий (S9, PLAN уровня «полный», отложен как дорогой); диспетчер —
  реестр «какие темы запущены, в каком статусе» (PLAN-0001 Фаза 3, ждёт своей очереди); файловый
  навигатор кнопками (design-doc без реализации).

**Практический вывод:** «один топик = один поток/окно» уже частично работает по плюмбингу (сессия
на тему, конфиг на тему, файлы в тему, ре-адресация). Не хватает только диспетчерского слоя
(«кто сейчас говорит», статус нескольких параллельных тем разом) — это explicitly Фаза 3, гейтится
только объёмом работы, не решениями-развилками.
