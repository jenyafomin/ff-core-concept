# Планы-как-данные — дерево задач в графе памяти (research brief)

> Задача сессии: не строить код, а исследовать развилку. Ниже — материал для решения, не решение.

## Вопрос

Сейчас план = один документ (`PLAN.md`/`TODO.md`, плоский текст). Владелец хочет: план — это
**дерево задач-узлов с состоянием**, живущее в графе памяти; планов много (глобальные и
проектные), состояний много; агент, заходя в новый ход (`claude -p --resume`), должен **понять
текущий план и состояние** без ручной раскопки файлов. Как это представить и как этим управлять
в рамках чата/сессии — не сваливаясь в оверинжиниринг на фазе дизайна.

Прямая связь с проектным контекстом: каждый ход шлюза — это свежий процесс без тёплой памяти
(см. `CLAUDE.md` проекта, «Если ты работаешь через Telegram-шлюз»). Значит план обязан быть
**перечитываемым состоянием**, а не тем, что держится «в голове» агента между ходами.

## Prior art

Отранжировано по релевантности к конкретно этой задаче (агент-первый субстрат, ход = restart).

1. **Родные инструменты Task* этой же среды (TaskCreate/TaskList/TaskGet/TaskUpdate/TaskStop).**
   Самое близкое и уже боевое: плоский реестр задач с полями `id · subject · description · status
   (pending/in_progress/completed/deleted) · owner · blockedBy/blocks · metadata (произвольный
   бэг)`. Иерархии как таковой нет — есть **DAG через `blocks`/`blockedBy`**, а не строгое дерево.
   `TaskList` — это ровно операция «пойми план+состояние с нуля» (agent-first: без владельца,
   без owner, без блокировки). Ключевой вывод: minimal viable schema для «задачи как узла» уже
   существует и проверена на практике прямо в этой оболочке.
2. **HTN (Hierarchical Task Network planning).** Классика AI-планирования: составная задача
   раскладывается «методом» на подзадачи до примитивных (исполнимых). Даёт **явное дерево** +
   аудит «каким методом задача была раскрыта». Этот репозиторий уже намекал на этот паттерн:
   `docs/base/architecture/AGENTS-CATALOG.md` строка «Планировщик» описывает роль как «one-shot
   декомпозиция в parent_id-дерево» — то есть HTN-подобная декомпозиция уже была на радаре.
3. **Behavior Trees (робототехника/игровой AI, ROS2 BT.CPP, Nav2).** Дерево управляющих узлов
   (Sequence/Selector/Parallel) + листья-действия; на каждом **тике** дерево обходится заново,
   статус (`RUNNING/SUCCESS/FAILURE`) пересчитывается, а не хранится вручную. Существенно похоже
   на модель «ход = тик»: BT спроектированы именно для акторов без непрерывной памяти между
   вызовами — это ближе всего к реальности шлюза (`claude -p --resume` = свежий процесс каждый раз).
4. **GTD (Getting Things Done).** Проекты → next actions, контекст-теги, someday/maybe. Полезен
   не как структура данных, а как **словарь состояний** богаче, чем pending/done (в частности —
   разделение «что можно делать прямо сейчас» от «зависит от другого»).
5. **Project-as-data системы (Jira epic→story→subtask + workflow states + sprints; Linear
   issues/sub-issues/cycles/projects).** Проверенный на масштабе UX-паттерн «много планов, много
   состояний, агент/человек видит срез». Полезны как референс для будущего UI пульта (I-7 из
   CAPTURE.md), не как модель хранения.
6. **Оркестраторы workflow-как-данные (Temporal.io durable workflow + event log/replay; Airflow/
   Prefect/Dagster декларативные DAG'и задач).** Дают паттерн **восстановления состояния из
   журнала событий**, а не из отдельного «текущего» поля — прямая параллель с FQ13 (append-only)
   и FQ12 (снапшот-в-момент) в этом же проекте: план не обязан хранить один мутируемый статус,
   можно выводить его из лога событий.
7. **Агентные фреймворки 2024-2026.** LangGraph (граф состояний с persisted checkpointer между
   вызовами — тот же вызов «понять состояние с нуля»); ранние AutoGPT/BabyAGI (плоская очередь
   задач по приоритету — предостерегающий пример: без графа связей быстро теряется «почему это
   вообще задача»); CrewAI/MetaGPT (иерархия crew→task, SOP-как-граф).
8. **Аутлайнеры (Org-mode, Roam/Logseq).** Бесконечно вложенные TODO-узлы с циклом состояний +
   бэклинки; «всё — узел» — философски ближе всего к текущей архитектуре brain (задача — просто
   ещё один РОД узла, не отдельная подсистема). Смотри и FQ20 «Биография как род узлов» — тот же
   ход мысли уже применён к другому типу.
9. **Внутренний прецедент этого экопроекта:** `agents-manager` уже начал этот путь —
   `idea-cards/03-task-plan-layer.md` (Task = намерение + атрибуция источника: владелец/агент/
   пункт плана; статус) и `PLAN-0001` Фаза 2 («Задача»/«План» как сущности, один-к-одному план на
   задачу, шаг несёт риск-класс 🟢/🟡/🔴). Это уже почти consensus-view требований к памяти
   (см. CAPTURE.md синтез: «agents-manager — генератор требований к памяти»).
10. **git commit DAG / merge-деревья.** Аналогия для «план может форкнуться и слиться обратно» —
    полезна, если разные агенты параллельно ведут альтернативные подпланы одной задачи.

## Варианты (2-4, с pros/cons)

### Вариант A — Task как первоклассный род узла графа + DAG-рёбра (blocks/blockedBy)

Буквально переиспользовать схему родных Task-инструментов этой среды как формат: узел-задача
(`id · subject · description · status · owner · metadata`), связи-рёбра `blocks`/`blockedBy` —
это уже первоклассные рёбра по Ц-6 («рёбра проводят поток»). «План» — не отдельный тип документа,
а **запрос/срез** графа (все узлы с данным `plan_id` + их рёбра), который агент выполняет в начале
хода вместо парсинга файла.

- **Плюсы:** проверенный паттерн, работающий прямо в этой оболочке сейчас; минимум новых
  концепций (задача = ещё один род узла, не новая подсистема); естественно поддерживает много
  планов/scope (глобал/проект) через теги/рёбра, а не через отдельные файлы; статус+owner+metadata
  расширяем под нужды FF (риск-класс из PLAN-0001, provenance из idea-card 03) без миграции схемы.
- **Минусы:** DAG через blocks/blockedBy — это НЕ то же самое, что «дерево», которое просил
  владелец буквально; без явного «основного родителя» рендер в простое дерево неочевиден;
  плоский DAG рискует захламиться и требует отдельного решения по «видимости» (Ц-4 Витальность/
  salience), чтобы агент на каждом ходу не читал всю историю целиком.

### Вариант B — HTN-декомпозиция с явным parent_id (дерево)

Составная задача раскрывается «методом» на подзадачи до примитивных; хранится как узлы с явным
`parent_id`. Прямое совпадение с уже упомянутой в этом репо ролью «Планировщик» (one-shot
декомпозиция в parent_id-дерево, `AGENTS-CATALOG.md`).

- **Плюсы:** настоящее дерево — совпадает с мысленной моделью владельца буквально; декомпозиция
  явная и аудируемая («каким методом/почему эта подзадача появилась» — ложится на Ц-2 Тождество/
  происхождение); естественно разводит глобальный и проектный план как отдельные корневые узлы.
  строгая иерархия проще визуализировать (для будущего пульта/Telegram-карточек, I-7/I-10).
- **Минусы:** классический HTN подразумевает декомпозицию заранее целиком — реальная работа
  агента эмерджентна (подзадачи открываются по ходу сессии), нужна надстройка «вставить узел под
  уже выполняющийся»; межплановые зависимости (задача плана А ждёт задачу плана Б — ровно запрос
  владельца про «межпроектность», см. `PLAN-0001 §2a`) не ложатся на строгое дерево без
  добавления неструктурного ребра «waits-on» поверх — то есть всё равно съезжает к варианту A;
  тяжеловесно для мелких quick-win-задач, не заслуживающих полной декомпозиции.

### Вариант C — Behavior-Tree / реактивный тик поверх дерева

План — дерево управляющих узлов (Sequence/Selector/Parallel) + листья-действия; каждый ход шлюза
= один «тик»: обход дерева от корня, статусы (`RUNNING/SUCCESS/FAILURE`) пересчитываются заново, а
не читаются как застывшее поле.

- **Плюсы:** спроектировано ровно под текущую модель исполнения («ход» = свежий процесс без
  тёплой памяти) — BT существуют именно для акторов без continuity между вызовами; встроенная
  реактивность (реплан — это просто повторный тик, без ручного «где я остановился»); статус —
  вычисляемое свойство, а не ручное поле, что снижает риск рассинхрона (тот самый паттерн,
  которого боится вариант D).
- **Минусы:** непривычный словарь вне робототехники/геймдева — цена перевода для владельца и
  будущих читателей выше, чем у «задача/статус»; кто-то должен реально «тикать» дерево каждый ход
  — либо сам вызывающий агент рассуждает по промпту, либо нужен отдельный лёгкий «движок»
  (это уже покушение на 3-й уровень хребта `integrity-as-engine-duty`, которого пока нет);
  избыточная церемония для простых линейных планов (todo→done), которые сегодня составляют
  большинство (см. нынешние тривиальные `PLAN.md`/`TODO.md` самого brain).

### Вариант D — Документы остаются, добавляется «оверлей состояния» (узел-индекс поверх файла)

Не переносить содержимое плана в граф; вместо этого на каждый файл-план (`PLAN.md`, `PLAN-0001…`)
завести один узел-оверлей: текущий шаг, статус по шагам, дата обновления. Граф даёт быстрый
запрос «что активно», содержимое остаётся в привычных md-файлах.

- **Плюсы:** самый дешёвый шаг, без миграции формата; переиспользует то, что уже реально работает
  в brain и agents-manager (PLAN.md/TODO.md/PLAN-0001/PLAN-0002); совместим с текущей фазой
  («дизайним, не строим») как временный мост перед выбором A/B/C.
- **Минусы:** два источника истины (текст файла vs узел-оверлей) — тот же класс риска
  рассинхрона, который FQ12 сознательно терпит для другого случая (DECISIONS-LOG), но здесь это
  ровно та боль, которую владелец назвал явно («план в файлах — тяжело»); не решает исходный
  запрос («агент понимает план+состояние» всё ещё требует чтения+доверия отдельному документу, а
  не запроса к графу); при реальном росте числа планов («много планов, много состояний» — прямая
  цитата владельца) это латание дыр, не назначение.

## Предварительная рекомендация

Гибрид **A + B**: задача — род узла графа с минимальной схемой родных Task-инструментов
(`id · subject/description · status · owner · metadata`) на уровне листа/атома (вариант A), плюс
явное ребро «родитель-план» HTN-стиля (вариант B, уже намеченное в `AGENTS-CATALOG.md` как роль
«Планировщик») на уровне иерархии. «План» не отдельный тип документа — это запрос по графу (корень
+ потомки + рёбра blocks/blockedBy), который агент выполняет в начале хода вместо чтения файла.
Это прямо ложится на Ц-6 Реляционность («рёбра проводят поток») и сходится с уже начатым в
`agents-manager` (`idea-cards/03-task-plan-layer.md`, `PLAN-0001` Фаза 2). Вариант C (BT-тик)
стоит вернуть к рассмотрению отдельно и позже — конкретно для автономного ночного цикла
(`PLAN-0001` Фаза 5), где нужна настоящая реактивность, но это избыточная церемония для текущей
фазы дизайна. Вариант D можно использовать как временный мост, но не как назначение — иначе
получаем именно ту боль (два источника истины), которую владелец и просил снять.

## Под-вопросы (нужны, прежде чем фиксировать решение)

1. **Дерево vs DAG:** хватает ли строгого parent-дерева (HTN), или планам реально нужны
   межплановые зависимости (задача плана А блокируется задачей плана Б — см. заявленную
   владельцем «межпроектность», `PLAN-0001 §2a`)? Если да — дерево B неизбежно обрастает
   неструктурными рёбрами A, и стоит сразу проектировать как DAG с «основным родителем», а не
   как чистое дерево.
2. **Scope/видимость:** план — узел, подчиняющийся тому же единому порогу доступа (Ц-5
   Суверенность/PEP), что и любой другой узел, или планам нужна отдельная модель видимости
   (глобал видит все проектные, проект видит только своё — I-4 из CAPTURE.md)?
3. **Словарь статусов:** достаточно ли общего pending/in_progress/completed/deleted (схема
   родных Task-инструментов), или нужен богаче словарь сразу — риск-класс 🟢/🟡/🔴 из
   `PLAN-0001`, provenance (владелец/агент-инициатива/пункт-плана) из idea-card 03 — с учётом,
   что FQ7/FQ13 (append-only + hard-erase) означают «удаление задачи» = мягкий статус, не факт.
4. **Кто «тикает» план на каждом ходу:** это соглашение (агент сам перечитывает граф и решает по
   промпту) или нужен детерминированный лёгкий «движок плана» (3-й уровень хребта
   integrity-as-engine-duty), пересчитывающий агрегированный статус узла-родителя из статусов
   детей — как в BT? От ответа зависит, нужен ли вариант C уже сейчас или можно отложить.
5. **Глубина истории:** план хранит снапшот-в-момент (FQ12, дёшево) с append-only логом событий
   для аудита (FQ13), или только «текущее состояние» без истории? Это прямо определяет, попадаем
   ли мы в ловушку варианта D (два места правды) при попытке сэкономить.

## Как это соотносится с уже открытыми вопросами brain

- Пересекается с **FQ4** (линза первоклассная — план/задача такой же кандидат в «первоклассная
  единица», как и линза) и **FQ16** (4 плана брейна — задача, скорее всего, «Процесс»-план).
- Прямо требует ответа по **FQ7/FQ13** (append-only + hard-erase) для словаря статусов.
- **FQ20** («Биография как род узлов») — тот же архитектурный ход, что предлагается здесь для
  задач: не грань ячейки, а отдельный род узлов со своими рёбрами.
- Ничего из этого не в списке «заложить сейчас, ретрофит невозможен» (INDEX.md, строка 84-86) —
  можно решать не в спешке, но стоит сверить со списком перед фиксацией схемы задачи-узла.
