# Экономический трейс токенов — исследовательский бриф

> Задача (I-2 из CAPTURE 2026-07-10): как учитывать токены **рекурсивно по дереву делегирования**
> (сам съел / дети съели), делать **снапшоты во времени** для самообучения системы, и что это значит
> для критериев качества дизайна БД. Это НЕ спека — материал для решения (owner/Fable/архитектор).

## 0. Формулировка задачи (переформулировано из заброса)

Три оси, которые владелец слил в одну фразу — их надо держать раздельно (дальше это станет
источником опций):

1. **Ось «дерево» (структура делегирования).** Агент A вызывает агента B, B вызывает C. Нужно уметь
   ответить: «сколько потратил A **сам**» vs «сколько потратил A **через тех, кому передал**»
   (self vs propagated/cumulative), рекурсивно на любую глубину.
2. **Ось «время» (снапшоты).** Не просто «сколько всего», а «когда начался перерасход», «в каком
   периоде» — тайм-серия, а не одно число.
3. **Ось «обучение».** Итоговая цель — не дашборд ради дашборда, а вход для **самообучения системы**:
   роутинг модели (какой шаг какой модели стоит), бюджет-губернатор (когда остановить), критерий
   дизайна БД (см. §5).

## 1. Prior art

### 1.1 Уже найденное ВНУТРИ репозитория (важнее внешнего — уже адаптировано к нашему языку)

- **Собственный гэп, зафиксированный ещё 2026-06-15** (`docs/base/council/raw/2026-06-15-cluster4-schema-stress/architect.md`,
  Scenario 7 «Model config, cost, tokens»): *«Token accounting (tokens ↔ tariff) — измерение-во-времени
  на каждый вызов; это та же дыра, что time-series в кластере 1: value/unit/occurredAt не первоклассные.
  Каждый вызов = measurement-узел без контракта агрегации.»* Вердикт был **⚠️ Strains** — схема тянется,
  но у неё нет класса «измерение» и нет контракта, как такие измерения агрегируются. Это тот же вопрос,
  который владелец поднял сейчас, просто с другой стороны (тогда — как класс узла, сейчас — как дерево).
- **agents-manager уже прошёл цикл `value-decomposition` по этой же теме** (2026-07-09, ценность
  «Прозрачность», направление 03 «Стоимость и ресурсы» — `02-transparency/03-cost-and-resources/README.md`)
  и параллельно брейн-дамп 2026-07-07 (`ideas/2026-07-07-observability-multiagent-refactor.md`, пункты A1-A4).
  Оттуда уже вытащены:
  - **A2 / 02.3** — счётчик стоимости **в рамках сессии** (с момента New), не за всю жизнь чата.
  - **A3 / 02.2** — «граф расходов по агентам»: **узел = агент/сессия, ребро = делегация**, на ребре
    висят токены/стоимость/модель/период; **рекурсивно** (у каждого агента свой такой же граф).
  - **02.5** — снэпшоты во времени + дашборд (та же «ось времени», что в заброшенной идее I-2).
  - Явно названный **открытый вопрос "момент фиксации"**: на каждый turn (точно, но объём) vs агрегат
    на завершении хода vs снэпшот по расписанию — уже сформулированная развилка, не решённая.
  - Явно названа **опора #5 «Событийная шина (event sourcing)»** в инфраструктуре agents-manager —
    *«одни события считаются раз: стоимость, снэпшоты, крон-триггеры»* — то есть учёт токенов уже
    спроектирован НЕ как отдельная фича, а как один из потребителей общего событийного лога.
  - **#9 «Бюджет-губернатор + circuit-breaker»** — потребитель тех же данных с другой стороны
    (не «видеть», а «остановить»); явно разведено от #5/03 как отдельный модуль («видеть расход» ≠
    «решение стоп»).
- **CLI/SDK уже отдаёт число**: `claude -p --output-format json` → `total_cost_usd`, `--verbose
  stream-json` — построчные события; официальный **Usage & Cost API** на уровне организации
  (`docs/base/architecture/CLAUDE-CODE-RUNTIME-OPTIONS.md`, §5/§9). Это готовый источник сырых данных
  «сколько стоил этот вызов» — не нужно вычислять токены самим, только собирать и раскладывать по дереву.
- **Хребет brain уже принял три инварианта**, которые прямо ограничивают решение здесь:
  FQ13 append-only (факты не мутируются, только новые события + tombstone), FQ12 снапшот-в-момент
  (вместо тотального bitemporal-всего — снапшот в точке решения, дёшево, «из CRM»), Edge Engine (#11,
  ребро = полноценная ячейка с паспортом). Экономический трейс — это, по сути, ПЕРВЫЙ реальный
  потребитель всех трёх сразу: событие=факт (append-only), агрегат=снапшот (FQ12), делегация=ребро (#11).

### 1.2 Внешний prior art (из обучающих данных; веб-поиск в этой сессии был недоступен — see caveat ниже)

- **OpenTelemetry GenAI semantic conventions** — индустриальный стандарт трейсинга LLM-вызовов:
  каждый вызов = **span** (`trace_id`, `span_id`, `parent_span_id`) с атрибутами `gen_ai.usage.input_tokens`
  / `output_tokens` и т.п.; вложенный вызов (агент → суб-агент → tool call) — просто дочерний span.
  Идея self vs cumulative — это ровно классика профилировщиков (**self time vs cumulative/inclusive
  time** в gprof/pprof/flame graphs): узел дерева вызовов хранит «съел сам», агрегат по поддереву
  вычисляется суммированием потомков. Токены — то же самое число, только вместо CPU-тиков — токены/$.
- **LLM-observability платформы (Langfuse, LangSmith, Helicone, OpenLLMetry/Traceloop)** — все строят
  «trace tree» из generations/spans; стоимость на каждый span считается из (модель, токены, прайс-лист),
  затем **роллапится вверх по дереву** до trace-уровня. Общий паттерн: **ledger (сырые события) +
  read-model (агрегат по дереву)** — сырые события не трогают, агрегат пересчитывается или кэшируется.
- **FinOps / хирархический cost allocation** (AWS Cost Categories, k8s cost allocation по
  namespace/label, классический управленческий учёт P&L «прямые vs распределённые затраты
  подразделения») — тот же паттерн self/propagated, но в мире денег, не токенов; давно решённая
  задача с типовыми решениями (closure table / materialized path для быстрых subtree-сумм).
- **Distributed tracing (Jaeger/Zipkin)** — тот же span-tree, что и в OTel GenAI (GenAI-конвенции
  выросли из этого же корня); подтверждает, что «дерево делегирования» и «дерево вызовов» — одна и
  та же структура данных на разных доменах.

> ⚠️ **Честная оговорка:** веб-поиск (`WebSearch`) в этой сессии не смог выполниться (ошибка
> инструмента), поэтому внешний prior art в §1.2 — из обучающих данных (cutoff начало 2026), а не
> свежепроверенных источников. Названия/API могли обновиться. Перепроверить перед тем, как на них
> закладываться (особенно OTel GenAI semconv — область активно развивается).

## 2. Варианты решения

### Вариант A — Событийный ledger (append-only) + материализованный роллап поверх дерева делегирования
Каждый LLM-вызов пишет неизменяемое **событие использования**: `{span_id, parent_span_id, session_id,
agent, model, input_tokens, output_tokens, cost, ts}`. Отдельный read-model рекурсивно считает
`self(X) = Σ events(span=X)`, `subtree(X) = self(X) + Σ subtree(children(X))`.

- **+** Ложится прямо на уже принятые инварианты: append-only (FQ13), событийная шина agents-manager
  (#5) — не отдельная труба, а ещё один потребитель одного канонического потока.
  Полный аудит-трейл «кто когда сколько потратил» без потерь.
- **−** Subtree-роллап рекурсивный → на файловой/лёгкой БД (не полноценный граф-движок) недёшево
  на глубоких деревьях без индекса; агрегат может «протухнуть» при редком re-parenting (переносе
  делегации после факта — редкий, но грязный случай).

### Вариант B — Мутируемые счётчики на узле (self_tokens/cumulative_tokens прямо в ноде агента/сессии)
Каждая нода агента/сессии хранит поля-счётчики, обновляемые upsert'ом на каждый ход; при завершении
дочернего — синхронно прибавляем к счётчику родителя вверх по цепочке.

- **+** Дёшево читать (число уже лежит, не нужен агрегирующий запрос); простая ментальная модель,
  созвучная «ячейка носит своё состояние» (policy-as-data).
- **−** **Прямо конфликтует с уже принятым append-only (FQ13)** — мутация вместо лога событий;
  теряется история («сколько было потрачено НА МОМЕНТ T» без отдельного механизма снапшотов);
  гонки записи при параллельных дочерних агентах, пишущих в общий счётчик родителя (нужен
  atomic-increment/лок — доп. сложность там, где append-only её просто не имеет).

### Вариант C — Closure-table / materialized-path над деревом делегирования, отдельно от ledger'а событий
Структура делегирования (кто кого породил) хранится отдельно как closure-table (все пары
предок-потомок материализованы) или materialized-path (`/root/agentA/agentB/`). Суммы токенов —
join этой структуры с ledger'ом событий (Вариант A), а не рекурсивный обход на лету.

- **+** Дешёвые subtree-запросы без рекурсивных CTE (важно, если хранилище — плоские файлы/SQLite,
  не графовая БД); отделяет «форму дерева» (меняется редко, после коммита почти неизменна) от
  «метрики» (события копятся постоянно) — чистое разделение забот; re-parenting — просто новая
  строка closure, история событий не трогается (append-only сохранён).
- **−** Доп. запись при каждом новом узле (O(глубины) новых строк closure); ещё один индекс, который
  надо держать синхронным с деревом; концептуальная нагрузка — команда должна понимать ДВЕ связанные,
  но разные структуры (ledger + closure), а не одну.

### Вариант D — Периодические тайм-снапшоты (материализация по расписанию) поверх уже решённого FQ12
Не агрегировать «на лету», а фоновой задачей (кандидат-модуль «Gardener», #14 в infra) периодически
(каждые N ходов / на закрытии сессии) обходить текущее дерево делегирования и писать неизменяемый
снапшот-узел: `{as_of, node_id, self_tokens_period, subtree_tokens_period, model_mix}`. История
расхода = ряд снапшотов, а не пересчёт на лету.

- **+** Переиспользует уже принятый паттерн **FQ12 «снапшот-в-момент»** (дёшево, прецедент из CRM) —
  не нужен новый тип инварианта; напрямую даёт ответ на заявленную цель владельца («когда начался
  перерасход», самообучение по времени) без дорогих live-join'ов на каждый вопрос; частоту снапшота
  можно крутить как ручку цена/точность.
- **−** «Сколько прямо сейчас» между снапшотами всегда чуть устаревшее — нужен дешёвый
  live-счётчик-компаньон (кусок Варианта A/B) на «строку статуса сессии»; сама частота снапшота
  (каждый ход / на закрытии сессии / раз в N минут) — открытая ручка без очевидного дефолта
  (это ровно развилка «момент фиксации», уже названная в agents-manager 03-cost-and-resources).

## 3. Предварительная рекомендация

Варианты не взаимоисключающие — они закрывают разные оси задачи (§0). Рекомендация — **комбинация
A + C + D, без B**:

- **Ledger (A)** как единственный источник истины — append-only событие на каждый вызов, **пишется
  в ТОТ ЖЕ канонический событийный поток**, который agents-manager уже согласовал как опору #5
  («стоимость, снэпшоты, крон-триггеры считаются раз») — не городить отдельную трубу под токены.
- **Closure/materialized-path (C)** поверх дерева делегирования — чтобы self-vs-subtree считался
  дёшево без рекурсивных запросов на лёгком хранилище; форма дерева (структура) и метрика (события)
  осознанно разведены.
- **Периодические снапшоты (D)** — для оси «время»/«самообучение», напрямую наследуя уже принятый
  FQ12 паттерн, а не изобретая новый.
- **Без Варианта B** — мутируемые счётчики прямо конфликтуют с уже ратифицированным append-only
  (FQ13); держать как анти-паттерн явно, чтобы не всплыл случайно при кодировании.

Это не «принятое решение», а заземлённая отправная точка — сама комбинация и её швы (особенно
момент фиксации, §4 подвопрос 4) требуют owner/Fable-развилки, а не тихого решения агентом.

## 4. Под-вопросы (нерешённое, требует ответа/развилки)

1. **Откуда берётся span/delegation id?** Синтезируем свой span-id в обёртке-оркестраторе, или
   переиспользуем нативные id из Claude Agent SDK / session_id шлюза (`--resume`, `session_id` из
   `--output-format json`)? Влияет, строим ли своё дерево трейса с нуля или маппимся на чужие id.
2. **Гранулярность «self».** Атом — один LLM API-вызов, или целый ход (turn), который может включать
   несколько tool-calls/суб-агентских вызовов? От этого зависит кардинальность строк ledger'а и то,
   отделяем ли стоимость tool-call от стоимости хода.
3. **Бывает ли re-parenting** (делегацию агента переназначают на лету)? Если да — closure-table
   переписывается ретроактивно, или это redko-случай, который просто добавляет новое ребро (старое —
   tombstone), по аналогии с FQ7 referent/hard-erase? Нужен явный прецедент.
4. **Момент фиксации снапшота** (уже названная развилка в agents-manager 03-cost-and-resources,
   пункт 6): на каждый turn (точно, дороже) vs агрегат на завершении хода vs фиксированный интервал —
   владельцу нужно выбрать дефолт, не откладывать бесконечно.
5. **Экономический трейс — это заявка на новый первоклассный тип узла в brain** («измерение-во-
   времени», ровно та дыра, что нашёл `architect.md` в июне: «tokens = unaggregated time-series, no
   aggregation contract»)? Или это остаётся бесповоротно локальной структурой agents-manager, вне
   схемы brain? Это стержневой вопрос для §5 — куда именно ложится модуль.
6. **Кто потребляет «обучение».** Только человеческий дашборд (03-cost-and-resources явно
   ограничивает себя «видеть», не «решать») — тогда запись может быть batch/async; или это питает
   бюджет-губернатор (#9, circuit-breaker) и model-routing (06.1) напрямую — тогда путь записи должен
   быть low-latency и предсказуемым. Разное требование к архитектуре в зависимости от ответа.

## 5. Как это становится критерием качества дизайна БД

Экономический трейс — удобный **лакмус для хребта brain** (canonical_id · Bitemporal · Edge Engine ·
единый PEP · Конституция), потому что это первая реальная сущность, которая одновременно требует:

- **(a)** append-only измерение, привязанное к **ребру** (делегация = связь агент→агент), а не только
  к узлу — прямой тест для Edge Engine (#11, ещё не заспекан, только ратифицирован В4 «ребро с
  паспортом, узко»);
- **(b)** дешёвый **self vs subtree** роллап по рекурсивной структуре — тест, умеет ли движок вообще
  агрегировать по дереву без спецхаков (это тот самый гэп из архитектора-2026-06-15: «tokens =
  unaggregated time-series, no aggregation contract»);
- **(c)** **снапшот-в-момент** (FQ12) как механизм временнóй оси, не полный bitemporal-на-всё.

Если 5 опор хребта могут выразить (a)+(b)+(c) **без изобретения новых примитивов** — это сильное
свидетельство, что хребет достаточен не только для «памяти-контента», но и для служебной телеметрии
в целом (что подтверждает тезис владельца I-9: «brain — лишь один tool среди многих», значит его
хребет должен нести и не-контентные нагрузки). Если НЕ может — это конкретный, проверяемый провал,
который нужно вернуть в FQ12/FQ13/Edge Engine (#11) ДО того, как решать инфраструктуру навсегда
(«заложить сейчас, ретрофит невозможен» — INDEX.md brain, строка 84-86).
