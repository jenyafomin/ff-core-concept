# Сессия / Тема / Ход — исследовательский бриф

> Задача (I-1 из CAPTURE 2026-07-10): как смоделировать «сессию», «тему» и «ход» узлами графа памяти
> для агентной системы поверх шлюза (каждый топик Telegram = один агент = `claude -p --resume`).
> Развилка владельца: тема 1:1 с сессией, или 1:N (тема переживает много сессий)? Нужен ли отдельный
> node-тип «сессия» поверх «темы»? Это НЕ спека — материал для решения.

## 0. Важная находка прежде всего: словарь уже расколот на 2 места в проекте

Прежде чем решать I-1, нужно увидеть, что термины «сессия» и «тема» уже используются
**с противоположным вложением** в двух местах этого же проекта:

1. **`session-logging` skill** (доки, `docs/01-organization/rules-and-skills/session-logging/SKILL.md`):
   **Сессия** = внешний временной контейнер («как идём во времени, через разных агентов»),
   **Тема** = внутренняя единица, много тем на одну сессию, нумеруются `01-`, `02-`… → **Тема ⊂ Сессия**.
2. **CAPTURE.md I-1 / agents-manager** (реальные агентские ходы): **Тема** = топик Telegram, долгоживущая
   (недели/месяцы), а под вопросом — переживает ли она много **сессий** (эпизодов работы) → если да,
   то **Сессия ⊂ Тема** — ОБРАТНОЕ вложение.

Это не опечатка, а два разных явления, случайно названных одинаковыми словами. Рекомендация ниже
(§4) предлагает разрешить это явно, а не тихо смешать.

## 1. Что уже есть в коде agents-manager (не изобретаем заново)

`agents-manager` уже реализует три слоя, почти точь-в-точь совпадающих с Ход/Сессия/Тема
владельца — но под другими именами и с одним важным нюансом:

| Код | Что это | Соответствует |
|---|---|---|
| `IJob` | «единица работы для очереди… **Ход агента = Job**» | **Ход (turn)** |
| `ISession` | «durable-нить диалога. Наш ключ ↔ claude session_id (resume)» | ближе к **Теме**, не к «сессии» в бытовом смысле — см. ниже |
| `ITopic` | «ось группировки диалогов + вложенность (тема→под-тема)… проецируется в форум-топики» | **Тема**, включая под-темы |

**Ключевой нюанс (источник путаницы владельца в I-1 добор, msg «то ли новая сессия, то ли resume»):**
`ISession` — это долгоживущая строка, keyed по `conversationId` (`chat:thread`). Команда `/new`
**не создаёт новую строку `ISession`** — она обнуляет ПОЛЕ `claudeSessionId` внутри той же строки
(«`/new` полноценно сбрасывает маппинг: следующий ход — свежая claude-сессия», `command-handler.ts:565`).
Обычный ход = **resume** того же `claudeSessionId`. `/new` = **новый** `claudeSessionId`, но тот же
`ISession.key`. Итого в коде уже трёхслойно, но безымянно:

```
Topic (топик Telegram, долгоживущий, именованный, может иметь под-темы)
  └─ ISession-row (по conversationId; живёт ПОКА жив топик; не пересоздаётся)
       └─ claudeSessionId-эпоха (меняется на /new, /fork, смену cwd; ЭТО и есть
          "непрерывный разговорный контекст" в бытовом смысле "сессия")
            └─ Job = один ход (resume)
```

То, что владелец интуитивно называет «сессией» (непрерывный контекст, который рвётся на `/new`) —
в коде НЕ отдельная сущность, а **мутируемое поле** внутри `ISession`. Это и есть источник путаницы
I-1 добор: «каждый раз при [?] — новая сессия» ощущается верно (новый `claudeSessionId`), но код
называет неизменную обёртку тем же словом `Session`.

**Ещё одна находка — Topic уже предполагает 1:N.** Комментарий к `ITopic.lastSummaryId`:
«при `scope=user` указывает на топик-агрегат (свод над **N per-session саммари**), а не на саммари
одной сессии» — то есть код уже закладывает, что один топик может агрегировать несколько
сессий-эпизодов. Это прямое попадание в развилку владельца, только на уровне саммари, не узла.

**`parentSessionId`** («родословная для `/fork`, паттерн Hermes») — уже есть поле для ветвления
сессий-эпизодов от одной темы (дерево эпизодов, не линия).

**Риск потери истории (важно для brain, «заложить сейчас»):** т.к. `/new` **перезаписывает**
`claudeSessionId` в той же строке (не версионирует), после нескольких `/new` прошлые
`claudeSessionId` нигде не хранятся построчно (только транскрипт на диске у Claude Code, не в БД
шлюза). Если Session станет узлом графа памяти, backfill прошлых эпизодов из текущей схемы
agents-manager **невозможен** — ретрофит не работает, ровно та же логика, что уже применена в
brain к `referent+hard-erase` (`docs/02-project/core/01-brain/INDEX.md:86` «заложить сейчас»).

## 2. Prior art вне проекта (известные паттерны — не верифицировано живым поиском, для ориентира)

- **OpenAI Assistants API (Threads/Runs).** `Thread` — персистентный контейнер сообщений;
  `Run` — одно исполнение ассистента над тредом (≈ Ход). Явного среднего слоя «сессия» между Thread
  и Run нет — Thread один раз играет обе роли (и «тема», и «непрерывный контекст»). Ближе к Опции A
  ниже (слияние).
- **LangGraph checkpointer (`thread_id`).** Каждый `thread_id` — независимая линия состояния;
  ветвление обычно делается НОВЫМ `thread_id` с явной связью «форк от», а не полем внутри старого —
  ближе к явному узлу-эпизоду, а не мутируемому полю.
- **Slack / форумы (channel → thread → message).** Channel долгоживущий (≈ Тема), thread — более
  короткая ветка внутри канала (≈ ближе к Сессии-эпизоду), message = Ход. Здесь три слоя явно
  разделены и это привычная ментальная модель для владельца (Telegram-топики уже это дают).
  Идёт вразрез с session-logging skill, где вложенность обратная (см. §0) — сигнал, что бытовой смысл
  ближе ко второму варианту (Тема ⊃ Сессия ⊃ Ход), и doc-skill стоит либо переименовать, либо явно
  пометить как другой домен (доки, не агентские диалоги).
- **CRM / support-тикеты (Case → Interaction → Message).** Case (топик проблемы) живёт неделями,
  переоткрывается, внутри — несколько Interaction-сессий (звонок, чат, письмо), каждая — свои
  сообщения. Прямой аналог «тема переживает много сессий» (1:N), с чёткой причиной: Case = про ЧТО,
  Interaction = КОГДА и КАКИМ КАНАЛОМ говорили в этот раз.

## 3. Варианты (для брейна)

### Вариант A — Слить: Тема = Сессия (нет отдельного node-типа «сессия»)
Тема — единственный долгоживущий узел; Ход крепится прямо к Теме.
- **Pros:** минимум типов узлов (Ц-1 Читаемость); прямое отражение текущей бытовой практики
  владельца (`/new` жмут редко, топик почти всегда = один длинный контекст); нулевая миграция кода
  (просто переименовать `ISession`-row → узел «Тема»).
- **Cons:** теряет то, что уже ЕСТЬ в коде (`claudeSessionId`-эпохи, `parentSessionId`/fork);
  нельзя адресовать «эпизод от 3 марта» отдельно от темы целиком; вся полугодовая тема стареет/забывается
  (Ц-4 Витальность) одним куском, а не по эпизодам — грубая зернистость для будущего salience/decay.

### Вариант B — Три слоя: Тема → Сессия(эпизод) → Ход
Session-узел = **не** копия текущего `ISession`-row, а именно эпоха одного `claudeSessionId`
(границы: `/new`, `/fork`, смена cwd — и, возможно, тайм-аут тишины, см. под-вопрос §5.1).
- **Pros:** 1:1 отражает уже спроектированную (хоть и безымянную) трёхслойность кода — ничего не
  придумываем, только называем и переносим в граф; включает `/fork` естественно (Session — сиблинг
  с `parent_session_id`, дерево эпизодов); даёт адресуемую единицу для салиенс/забывания per-эпизод
  (Ц-4) и для «саммари поверх N сессий» (Ц-1, уже предусмотрено в `ITopic.lastSummaryId`); Ход = Job
  остаётся тонким и одноразовым, как в коде.
- **Cons:** 3 типа узлов + рёбра между ними — больше поверхности синхронизации (риск дрейфа);
  нужно явно решить границу эпизода (только `/new`? + тишина? — открытый под-вопрос); дороже на
  запись (каждый ход должен знать, к какому Session он относится, а не только к Теме).

### Вариант C — Тема + Ход как узлы; «Сессия» — не узел, а тег/атрибут Хода
`episode_id` (= `claudeSessionId` на момент хода) хранится ПРЯМО на узле Хода; группировка в
«сессию» выводится (derive) запросом по этому полю, не хранится отдельной сущностью.
- **Pros:** дешевле всего — 0 новых node-типов; ничего не решаем «сейчас» (это ретрофит-способно:
  можно позже материализовать Session-узлы из уже накопленных `episode_id` на Ходах — в отличие от
  находки §1, при условии что мы НАЧНЁМ писать `episode_id` на каждый Ход СЕЙЧАС, не позже);
  соответствует правилу brain «заложить только то, что нельзя ретрофитнуть».
- **Cons:** у эпизода нет своего адресуемого узла — некуда повесить эпизодную salience/summary/decision
  напрямую (придётся либо тащить на Тему целиком, либо выдумывать «виртуальный» узел на лету);
  не участвует в рёбрах графа (нельзя сказать «эта сессия tension-with той сессией», «эта сессия
  escalated-to владелец»).

### Вариант D — Отложить: Session = проекция (лінза), связать с уже открытым FQ4
Не заводить новый открытый вопрос параллельно — вместо этого явно смерджить I-1 (Session-узел) с уже
существующим `FQ04-linza-pervoklassnaya` («линза как первоклассная единица» — статус ⚠️ спорно, риск
дубля уже отмечен в самом FQ4 с FQ16/FQ22). Session = материализованная лінза (срез Ходов по
времени+`episode_id`), первоклассный узел только если FQ4 решится «да».
- **Pros:** не плодит четвёртый параллельный открытый вопрос почти про то же самое (линза vs
  первоклассный узел); дисциплина «не дублировать открытые вопросы» уже явно требуется в проекте.
- **Cons:** привязывает решение по Session к чужому нерешённому и оспоренному вопросу (FQ4 сам
  помечен ⚠️ уточнить) — блокировка без явной необходимости; если FQ4 закроется «линза НЕ
  первоклассна» по причинам, не относящимся к Session (например, из-за конфликта с FQ16/FQ22), Session
  утянется вниз за компанию, хотя у него есть отдельные веские причины быть узлом (учёт стоимости,
  per-эпизод забывание) — плохая связка.

## 4. Предварительная рекомендация

Склоняюсь к **Варианту B с элементами C как переходного шага**, и обязательно — к явному
разведению словаря из §0:

1. **Разрешить коллизию терминов сейчас, до решения по узлам.** Зафиксировать (например, в
   `open-questions/`, отдельным пунктом «терминологический контракт»): бытовое/агентское
   `Тема ⊃ Сессия(эпизод) ⊃ Ход` — это ПРО АГЕНТСКИЕ ДИАЛОГИ (данный бриф). `Сессия ⊃ Тема` в
   `session-logging` skill — это ПРО ЛОГИРОВАНИЕ ДОК-РАБОТЫ человека+Claude Code в этом репо, другой
   домен. Разные слова, разные домены → либо явно переименовать один из двух (напр. skill
   `session-logging` → `worklog-logging`, сессия-папка → «рабочий блок»), либо держать документированное
   явное предупреждение о коллизии в обоих местах. Не смешивать молча.
2. **Начать с Варианта C сейчас (дёшево, ретрофит-способно), готовиться к B.** Прямо сейчас — просто
   писать `episode_id` (=`claudeSessionId` на момент хода) на каждый узел-Ход в графе памяти. Не решать
   прямо сегодня, материализуется ли Session как отдельный узел — но НЕ откладывать сам факт записи
   поля, иначе backfill невозможен (см. находку §1 про потерю истории). Это соответствует правилу
   brain «заложить сейчас то, что нельзя ретрофитнуть» — здесь ретрофитнуть нельзя ИМЕННО сырое поле
   `episode_id`, а не решение о материализации узла.
3. **Материализовать Session-узел (полный Вариант B), когда появится первая реальная причина** —
   вероятный триггер: (а) нужен per-эпизод salience/decay (Ц-4), или (б) нужен `/fork` как ветвление
   в графе, или (в) нужна агрегированная сводка «за этот эпизод» отдельно от сводки всей Темы. До этого
   момента Session остаётся выводимой (derived view), не отдельной таблицей/узлом — избегаем
   преждевременного усложнения (Ц-1 Читаемость, тот же дух, что и FQ23 «стоп-правило слоёв»).
4. **Границу эпизода** брать по уже существующим в коде триггерам (`/new`, `/fork`, смена `cwd`) —
   не изобретать новую политику; тайм-аут тишины — отдельный под-вопрос (§5.1), не блокирует старт.

Итого: **Тема 1:N Сессия** (когда Session материализуется) — потому что код УЖЕ спроектирован в эту
сторону (`parentSessionId`, `lastSummaryId` над N-сессиями) и потому что бытовая модель владельца
(«каждый раз новая сессия, но топик тот же») требует именно этого направления вложенности, а не
слияния 1:1.

## 5. Под-вопросы владельцу / для дальнейшего копания

1. **Граница эпизода — только `/new`+`/fork`+смена cwd, или ещё тайм-аут тишины?** В коде уже есть
   пороги 2ч/6ч для «стареет»/«пора `/new`» (`reply-header.util.ts`) — это подсказка UX, не авто-разрыв
   эпизода. Считать ли долгую паузу владельца САМА ПО СЕБЕ границей новой Session, или граница только
   явная (владелец/команда)?
2. **Кто пишет границу — движок или агент?** По хребту brain (`integrity-as-engine-duty`) — детект
   границы эпизода должен быть обязанностью движка (детерминированно из `/new`/`/fork`/cwd-события),
   а не решением агента на лету. Подтвердить, что это не спорно.
3. **`EScopeMode` (topic vs user)** — при `scope=user` один Topic может обслуживать разные
   session-цепочки для разных `participantId`. Учитывать ли участника как часть идентичности
   Session-узла, или это отдельная грань, не относящаяся к I-1?
4. **Слить или разнести с FQ4 (линза первоклассная)?** Если Session станет узлом — это довод «за» для
   FQ4, или это отдельная сущность, не относящаяся к спору о линзах? Нужно явное решение владельца,
   чтобы не плодить дубль (см. Вариант D).
5. **Нужно ли агенту-агенту-манагеру (коду) переименование?** Если брейн примет словарь «Тема/Сессия
   (эпизод)/Ход», стоит ли завести follow-up ADR в `agents-manager`, чтобы `ISession`-row переименовать
   в нечто вроде `TopicBinding`/`Thread`, а слово `Session` в коде освободить под настоящий
   эпизод (`claudeSessionId`-эпоху) — чтобы код и brain говорили одним языком? Или жить с разными
   словами в коде и в brain (с явным маппингом), не трогая работающий код ради терминологии?
6. **Хранить историю `claudeSessionId` уже сейчас?** Согласиться, что `agents-manager` начинает
   аппенд-логировать смену `claudeSessionId` (а не перезаписывать), даже до решения по Session-узлу —
   иначе прошлые эпизоды текущих активных тем навсегда недоступны для будущего brain.
