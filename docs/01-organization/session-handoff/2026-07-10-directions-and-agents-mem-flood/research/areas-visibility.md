# Ресёрч-бриф: Области/группы с фильтруемой видимостью (I-4)

> ⚠️ **Оговорка о методе.** Инструмент живого веб-поиска в этой сессии был недоступен (permission
> stream закрылся на каждой попытке). Prior art ниже — из тренировочных знаний модели (не
> проверено свежими источниками за сегодня) + из уже существующего внутреннего ресёрча в этом
> репозитории (он оказался НЕОЖИДАННО глубоким — см. ниже). Если решение станет необратимым —
> стоит перепроверить внешние источники отдельно (например через `deep-research`).

## 1. Формулировка вопроса

Владелец (I-4, CAPTURE.md): «области/группы с фильтруемой видимостью: проект не видит планы
других, глобал (ff personal) видит всё; БД выделяет область-контекст; граф». Вопрос — **где и как
в модели памяти живёт эта граница видимости**, и как она согласуется с Ц-5 Суверенность
(«единый порог доступа») и уже принятыми на трек модулями.

## 2. Находка №1 — вопрос уже наполовину решён внутри репозитория

Прежде чем идти вовне: этот вопрос **не новый** для проекта. Он трижды всплыл независимо в цикле
декомпозиции ценностей 2026-07-09, под именем «tenant», а не «область» — но это тот же объект:

- **`infrastructure/INDEX.md`** уже называет «Единый PEP / Порог доступа» (модуль **#5**) опорой
  №4 из 5 несущих, и explicitly пишет: «Линза, capability, use≠read, **tenant**, taint — всё
  принуждается здесь» — т.е. область-видимость уже спроектирована как ОСЬ внутри PEP, не как
  отдельный модуль.
- **`scenarios/02-adversarial.md` (S10, 🟠 CONCERN)** — «Межарендная утечка через общий
  canonical_id/merge»: два проекта ссылаются на одну сущность → merge/дедуп в модулях #1
  (canonical_id) и #13 (Ingress Adapter) **не изолирован по арендатору** → идентичность может
  «утечь» раньше, чем сработает PEP. Уже сформулировано INFRA DEMANDED: **«Tenant-scoped
  identity/merge»** — canonical_id и слияние первично изолированы по области; общий референт
  (одна и та же сущность в двух проектах) = **явный мост с provenance, а не тихий merge**.
- **`scenarios/01-multi-actor.md`** идёт дальше и поднимает вопросы, которые «область/фильтр
  видимости» тянет за собой на масштабе людей, не только проектов: S6 (тот же референт — участник
  в двух независимых базах/вендорах), S7 (новый участник получает ли ретроактивный доступ ко всей
  прошлой памяти области), с предложенным примитивом **[G] Membership epoch** — грант доступа несёт
  «с какого момента», а не открывает всю историю области при вступлении.
- **Г31** (L0-memory-unit.md) уже называет как цель «показывать себя по-разному разным ролям
  (field/row-level, **„свой мир“ проекта**, capability-шеринг)» — то есть «свой мир проекта» уже
  был в списке из 39 целей до сегодняшнего заброса.

Вывод: I-4 — не новая идея, а **фокусировка** уже разбросанного материала. Задача этой сессии —
не изобрести область с нуля, а решить, **какой архитектурный паттерн** реализует уже найденную
опору (PEP #5 + tenant-scoped identity #1/#13 + membership epoch), и записать это как решаемую
развилку, а не оставлять размазанным по 3 файлам.

## 3. Prior art (внешнее, из общих знаний — не проверено вебом сегодня)

| Паттерн | Суть | Релевантность к I-4 |
|---|---|---|
| **Multi-tenancy: pool vs silo vs bridge** (классика SaaS-архитектуры) | Pool = общая БД + `tenant_id` колонка + фильтр на каждом запросе (часто Postgres Row-Level Security). Silo = отдельная БД/схема на арендатора. Bridge = общая БД, отдельные схемы. | Прямая аналогия «проект = tenant». Pool — дёшево, но ИМЕННО pool-паттерн (общий `tenant_id`, фильтр вместо структуры) — источник класса багов, который проект уже сам нашёл как S10 (утечка через общий id/merge, если фильтр где-то забыт). |
| **Google Zanzibar / ReBAC (relation-based access control)** — модель, стоящая за Google Docs/Drive-правами; открытые реализации: SpiceDB, OpenFGA, Ory Keto | Права = тройки `(объект, отношение, субъект)` + **hierarchical "arrows"**: право на папку прорастает на вложенные документы через явное отношение `parent`. «Кто видит весь родительский узел — видит и потомков» — не спецкейс, а следствие обхода графа отношений. | Это ровно паттерн «глобал видит всё, проект — только своё»: глобал = узел-предок в дереве членства, а не «исключение из правила». Совпадает по духу с «Единый PEP» проекта (централизованная точка проверки, не разбросанные if'ы) и с Edge Engine (#11) — отношения-рёбра как первоклассные объекты. |
| **ABAC + PEP/PDP/PIP/PAP (XACML-архитектура)** | Policy Enforcement Point — единая точка, где ЛЮБОЙ запрос на доступ проверяется против политики (Policy Decision Point), решение читает атрибуты (Policy Information Point). | Проект уже сам пришёл к этому имени — «Единый PEP» (#5) буквально из этого словаря. Область/tenant — просто ещё один атрибут в ABAC-политике, не новый механизм. |
| **Capability-based security (object-capability model)** | Нет «ambient» прав по идентичности; есть неподделываемый токен-capability на конкретный ресурс/область. Владение токеном = единственное основание доступа. | Уже семя в Ц-5 `05-ownership-keys` («capability-токены»). Более радикальный вариант, чем ABAC — обсуждается ниже как Вариант D. |
| **Kubernetes namespaces + RBAC (ClusterRole vs Role)** | Namespace — граница по умолчанию; `Role` действует внутри namespace, `ClusterRole` — видит все. Admission control — единая точка проверки. | Простая интуиция для «проект = namespace, ff-personal = cluster-admin». Известная боль: cross-namespace ссылки (аналог S10) требуют явных `NetworkPolicy`/RBAC-биндингов, не бывают «сами собой». |
| **Продуктовые аналоги: Notion (workspace→page-дерево, права наследуются вниз, owner видит всё), Linear (workspace→team→project, admin видит все team), git monorepo + CODEOWNERS** | Иерархия контейнеров + наследование видимости вниз по дереву + один админ-корень. | Ближе всего к формулировке владельца буквально («проект/глобал»); подтверждает, что 2-уровневая модель — частный случай N-уровневой (не стоит проектировать только 2 уровня). |
| **Property-graph multi-tenancy (Neo4j-style)**: tenant как label/property на каждом узле + query-time filter, vs Neo4j Fabric/multi-database (физическая изоляция БД) | Тот же выбор pool/silo, но применительно к графовой БД конкретно (проект уже думает в терминах графа). | Пары с Суверенность `04-foreign-residence` (право ячейки жить не здесь / прокси на внешнюю БД) — «silo» вариант там уже частично предусмотрен архитектурно. |

## 4. Варианты решения

### Вариант A — Тег-и-фильтр (`area_id` как поле + PEP фильтрует на чтении)
- **Суть:** каждая ячейка/ребро несёт поле `area` (или список областей) в паспорте (#7); «Единый
  PEP» (#5) на каждом канале чтения добавляет `WHERE area IN (доступные владельцу)`; «глобал»
  получает доступ ко всем `area` спецкейсом (роль/флаг без ограничения).
- **Pros:** дешёвый, ложится сразу на существующий паспорт (#7) как ещё одно policy-поле; не
  требует нового типа узла; можно строить инкрементально поверх текущего дизайна PEP.
- **Cons:** это ровно pool-паттерн, который уже породил найденную самим проектом уязвимость
  **S10** (canonical_id/merge между проектами не изолирован — «утечка раньше PEP»); «глобал видит
  всё» реализуется как ИСКЛЮЧЕНИЕ из правила, а не как следствие — противоречит собственному
  принципу «единый порог доступа, без обходов» (anti-zombie, Ц-5/Ц-3/Ц-7); при добавлении новой
  точки чтения легко забыть фильтр (класс багов «one query without the WHERE»).

### Вариант B — Область как первоклассная ячейка + иерархическое членство (в духе Zanzibar) ⭐ (см. рекомендацию)
- **Суть:** область (`area`) — это ТАКАЯ ЖЕ ячейка, как всё остальное (self-describing, Ц-5),
  несущая свою policy. Узлы/рёбра не «помечены полем», а связаны типизированным ребром
  `member-of → area` (Edge Engine, #11). Области образуют дерево/DAG через ребро `sub-area-of`.
  «Глобал» (`ff-personal`) — корневая область, к которой транзитивно принадлежат все остальные;
  видит всё не по спецправу, а потому что PEP при проверке видимости обходит цепочку предков
  членства (тот же механизм, каким уже спроектирован consent-taint #10 и forgetting-cascade).
- **Pros:** не вводит новый класс примитивов — переиспользует уже согласованные опоры (PEP #5,
  canonical_id #1, Edge Engine #11); закрывает S10 «в лоб»: пересечение сущности между областями
  становится явным типизированным ребром-мостом с provenance (ровно то, что INFRA DEMANDED в
  S10 уже требует — «мост с явным provenance, не тихий merge»); N-уровневая иерархия (не только
  2 уровня проект/глобал) — бесплатно; согласуется с Г31 («свой мир» проекта) и с Membership
  epoch [G] (грант несёт «с какого момента», не открывает всю историю при вступлении).
- **Cons:** тяжелее в реализации — зависит от Edge Engine (#11), который сам помечен «🔴
  перестройка, заложить сейчас» (ещё не спроектирован до конца); риск, что «область» станет
  перегруженным понятием (и организационная группировка, и граница доступа одновременно) — прямо
  предупреждение направления `06-constitutional-ceiling` в Ц-5; каждое чтение требует обхода
  предков области (нужен кэш/материализация — уже предусмотрено Read-scale Index #12 hot/cold).

### Вариант C — Физическое разделение (БД/схема на проект) + федеративный глобальный вид
- **Суть:** классический silo. Каждый проект физически — отдельное хранилище (или явная
  под-область через foreign-data-wrapper, Ц-5 `04-foreign-residence`); «глобал» — федеративный
  слой (агрегатор/прокси), который стягивает данные из всех проектных хранилищ по запросу.
- **Pros:** сильнейшая изоляция — «проект не видит планы других» гарантируется отсутствием
  доступа, а не корректностью фильтра; напрямую реализует vision-тезис I-9 («FF Personal — не
  единая БД, а координатор многих инструментов/MCP», brain = один tool среди многих); совпадает с
  уже заложенной Ц-5 гранью foreign-residence (прокси/материализация live-кэш-копия).
- **Cons:** identity-резолюция между силосами становится тяжёлой инженерной задачей (тот же класс
  проблемы, что и S6 «референт как чужой tenant» — нужен федеративный протокол [D], которого пока
  нет); «глобал видит всё» = дорогой fan-out/join по N хранилищам, а не простой фильтр; это скорее
  ДОЛГОСРОЧНАЯ архитектура marketplace (соответствует тому, что foreign-residence сейчас 🟡
  критично, а не 🔴 заложить сейчас) — преждевременно строить это ПЕРВЫМ слоем, пока нет даже
  единой ячейки.

### Вариант D — Capability-токены вместо ambient-области
- **Суть:** отказ от идеи «область даёт видимость по факту принадлежности»; вместо этого —
  неподделываемый capability-токен на конкретную область/поддерево, без токена доступа НЕТ ни у
  кого, включая «глобал» (глобал просто ДЕРЖИТ токен на корень).
- **Pros:** убирает целый класс ошибок конфигурации ambient-ролей; естественно ложится на
  marketplace/plug-in-видение (сторонний плагин получает узкий capability, а не «роль»); уже есть
  семя в Ц-5 `05-ownership-keys`.
- **Cons:** сильный сдвиг парадигмы относительно того, как владелец сформулировал вопрос («проект
  не видит» звучит как роль/членство, не как обладание токеном); для соло/малой команды — скорее
  оверинжиниринг сейчас (перекликается со стоп-правилом FQ23 против лишних слоёв); можно ввести
  ПОЗЖЕ как способ ВЫДАЧИ грантов на area-cell из Варианта B, не как замену ей — не обязательно
  выбирать D вместо B.

## 5. Предварительная рекомендация

**Вариант B** (область = первоклассная ячейка + иерархическое членство через типизированное
ребро, единый PEP обходит предков) — лучше всего ложится на то, что проект уже решил:

1. Не изобретает новый примитив — компонует три уже согласованных несущих модуля (PEP #5,
   canonical_id #1, Edge Engine #11) вместо добавления четвёртого.
2. Устраняет уже найденную самим проектом дыру (S10 cross-tenant leak) СТРУКТУРНО — пересечение
   областей = видимое ребро-мост с provenance, а не тихий merge за спиной фильтра.
3. «Глобал видит всё» перестаёт быть спецкейсом/дырой в стене (что противоречило бы «единому
   порогу доступа» как принципу без исключений) и становится обычным следствием того, что
   ff-personal — корень дерева членства.

**Вариант C** (физическое разделение) — правильный ответ для ДОЛГОСРОЧНОГО horizon'а
(marketplace/plug-in, I-9), но преждевременен как ПЕРВЫЙ слой: можно спроектировать так, чтобы
area-cell из Варианта B при необходимости получала `foreign-residence` (прокси на внешнюю БД,
уже заложено в Ц-5 #04) для «тяжёлых» проектов — то есть C не отменяется, а откладывается ВНУТРЬ
B как опция policy на конкретной area-cell, не отдельная архитектура.

**Вариант A** — соблазнительная ловушка: дёшево сейчас, но воспроизводит именно ту уязвимость
(S10), которую проект уже сам нашёл и назвал критичной. Не рекомендуется как базовый механизм;
годится разве что как временный костыль ДО того, как Edge Engine (#11) спроектирован.

**Вариант D** — вероятно преждевременен сейчас, но не противоречит B: может быть встроен позже
как механизм ВЫДАЧИ доступа к area-cell (capability = билет на конкретную area), без пересмотра
структуры.

## 6. Под-вопросы (владельцу / для FQ)

1. **Глубина иерархии.** Проектируем сразу N-уровневую вложенность (проект → под-проект →
   команда → ff-personal) или фиксируем сейчас только 2 уровня (проект/глобал), допуская
   расширение позже? От ответа зависит, стоит ли Edge Engine (#11) сразу тянуть «sub-area-of».
2. **Дерево или DAG?** Может ли узел/ячейка принадлежать НЕСКОЛЬКИМ областям одновременно
   (пример: задача видна и в `seven days`, и в `ff personal`), или строго одно дерево с одним
   родителем на область? Это решает, membership — tree (проще PEP) или DAG (нужен explicit
   join-policy при пересечении, как в S10).
3. **Кто меняет членство.** Может ли агент, работающий в теме/топике, сам перемещать/расширять
   область узла, или это конституционный шлюз только владельца (пересекается с
   `06-constitutional-ceiling` Ц-5 — кто держит ключ)?
4. **Видимость рёбер vs узлов.** Если ребро соединяет узлы из РАЗНЫХ областей — само ребро
   принадлежит какой области (обеим? отдельной «мостовой»)? Прямое продолжение INFRA DEMANDED из
   S10 («мост с явным provenance») — нужно решить ДО того, как Edge Engine получит финальный
   паспорт (#11 сейчас 🔴 «заложить сейчас»).
5. **Ретроактивность при входе в область.** Когда agents-manager привязывает новый топик к
   проекту (область создаётся или подключается) — открывается ли вся прошлая история области
   сразу, или действует Membership epoch [G] (видно только с момента подключения)? Совпадает с
   S7 из `01-multi-actor.md`.
