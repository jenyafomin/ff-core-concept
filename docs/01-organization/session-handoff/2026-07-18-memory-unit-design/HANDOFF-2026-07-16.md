## 🔷 Fable #1 — hard-erase: вердикт и что выжило
**Вердикт Fable (сильный):**
- **R-ERASE:** конфликт ролей решается НЕ выбором победителя, а **расщеплением узла**: `referent` абсолютен
  над содержанием-о-себе · `owner` — над существованием/оболочкой · `author` = ноль erase-прав.
- **Слой бьёт тип** по вашему же «авторитет > охват» → C-1 закрывается без новых сущностей.
- **Физика:** журнал никогда не хранит единственную копию; ref + **солёный** hash; erase = purge
  payload-store + анонимное терминальное событие; WAL/бэкапы — crypto-shredding.
- **ADR шире:** не «журнал без inline-payload», а **«erasable payload separation»** (журнал+WAL+бэкапы+реплики).
- **INV-LINEAGE (новый инвариант-на-сейчас):** движок отклоняет запись без `about`+`derived_from` — охват
  erase должен быть вычислим с рождения (ретрофит провенанса невозможен).
- **Слепая зона:** стёртое уже **метастазировало в производные** (summary, память агентов, эмбеддинги,
  отправленные сообщения) — «re-check at emit» ловит будущее, не уже-выведенное.

**Что сказал критик (трещины — важно):**
- 🔴 **Главный остаток:** вся конструкция молча предполагает, что **контент уже сегментирован по референту
  на уровне записи**. Для свободного текста (дневник, диалог двух людей) этой гранулярности НЕТ — расщеплять
  физически нечем. Без этого шва R-ERASE и per-referent-ключи **неисполнимы**.
- 🔴 **Гарантия забвения неполна для вне-графового** (отправленные сообщения) — это не край, а стандартный
  агентный путь «суммировать→отправить». Механизма нет.
- 🟠 Опекун = конфликт интересов (owner судит чужой erase без внешнего аудита) — «кто сторожит сторожей».
- 🟠 INV-LINEAGE «без исключений» — блокирует корневые/системные узлы без `derived_from`; цена «дешёвого
  INSERT» растёт до валидируемой транзакции. Нужны явные исключения.
- 🟠 taint-замыкание по `derived_from` без потолка глубины = новая DoS-поверхность через сам erase-запрос.

**Итог по hard-erase:** направление Fable верное (референт-примат · слой>тип · провенанс-с-рождения ·
нужен taint-каскад), но **несущий незакрытый шов = сегментация контента по референту** (связан с
гранулярностью D-4 anchor/span). Это новое самое слабое звено.

## 🔶 Fable #2 — направление: главный рефрейм ночи
**Мы спроектировали СУЩЕСТВИТЕЛЬНОЕ (единицу), но не ГЛАГОЛ (АКТ).** Половина открытых дыр (гонка,
конкурентность D8-Q3, self-escalation, дубль-баг шлюза) — дыры **акта**, не единицы.

**Три упущенные несущие абстракции:**
1. **АКТ** — `journal-entry` как вторая полноправная единица со своим паспортом
   (`actor · authority · idempotency-key · ref+hash`). Запись policy и чтение — тоже акты.
2. **`namespace@version` типа** + правило совместимости + маппинг-рёбра — условие маркетплейса и ответ на
   «эволюцию живого типа» (D8-Q4). Ретрофит имён после первой записи невозможен.
3. **Контракт пропагации** — erase-каскад · отзыв согласия · stale-вариант · derived-кэш = **пять имён
   одной механики** (lineage + инвалидация + freshness-policy). ← сюда схлопываются мои D-U5/6/7.

**Death-by-design кандидат:** «read-time проекция везде» без бюджета и контракта инвалидации умрёт на
~100k узлов. Межпроектность не держится при одном молчаливом реестре типов (столкновение смыслов).

**Ответ на твой исходный вопрос** (что выдаём: события/сохранение/фильтр/поиск + как делится):
> Всё **схлопывается в ОДИН механизм** — «всякое взаимодействие = **акт** через один порог, в один журнал,
> через одну линзу». События = view-def над потоком актов. `user / система / агенты / проекты` = **значения
> оси `actor`**, не отдельные подсистемы. Плагин = **актор с паспортом + поставка словаря**.

**Один ход по Fable:** ADR **«Акт и журнал»** — закрывает разом DEC-6, гонку, self-escalation,
идемпотентность (и текущий дубль-баг шлюза) и попутно определяет **plug-in API**. `namespace` типов — ход №2 до первой записи.
