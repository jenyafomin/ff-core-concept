# Критика Fable-ответа — hard-erase

Форма: по каждому тезису — конкретный сценарий (вход → неверный результат) → вердикт
ВЫЖИЛ / ТРЕЩИНА / СЛОМАН. Цель — не согласиться, а найти вход, на котором правило рвётся.

---

## 1. R-ERASE (расщепление узла: referent/owner/author)

**Вход:** дневниковая запись-медиация — owner=UserA пишет узел о конфликте с referent=UserB:
«Б сказал мне, что стыдится события E» — одно предложение неразделимо описывает и внутреннее
состояние Б (content-about-referent, абсолютное право Б), и личную рефлексию/собственность А
(владелец записи, его архив). Assertion-рёбра (DEC-8), на которые ссылается Fable, дают
гранулярность ТОЛЬКО если текст УЖЕ был предварительно сегментирован по референту в момент
записи — а паспорт явно отсеял `anchor/span` как поле УЗЛА (только поле РЕБРА, D-U1). Для
свободного текста (диалог, дневник, голосовая заметка) такой сегментации при записи никто не
требует и не гарантирует.

**Что ломается:** нет шва, по которому резать. Либо (а) движок вынужден резать по границе
предложения/абзаца грубо — теряя контекст остальных частей, либо (б) требование
пред-сегментации по референту на КАЖДУЮ запись с >1 референтом — новое обязательство, нигде не
объявленное, огромная нагрузка на авторство (голос/агент должен на лету размечать, «что тут о
ком»). Дополнительно — регрессия: если содержимое о референте В вложено ВНУТРИ content-about-A
(«А сказал, что Б сделал В»), у нас уже 2-3 конкурирующих «абсолютных» референт-права над одним
блобом — правило не говорит, кто режет первым и как сходится.

**Вердикт: ТРЕЩИНА** (близко к СЛОМАН для реального свободного текста/диалоговых узлов). Правило
работает только если структурные assertion-рёбра уже существуют на нужной гранулярности — а это
не гарантировано ничем в модели.

## 2. Опекун согласия как «дежурное поведение Конституции»

**Вход:** запись содержит referent «Иван Петров», который на момент записи — упомянутое третье
лицо (guardian-режим применяется). Позже тот же человек регистрируется в системе как активный
пользователь под тем же или другим alias. Модель не имеет объявленного механизма
identity-reconciliation (canonicalId — per-node, не per-реальный-человек).

**Что ломается:** триггер «референт не действующий субъект» не вычислим — нет процедуры
сверки узла-упоминания с узлом-пользователем. Guardian либо продолжает защищать (и блокирует
человеку доступ/erase к его же данным — теперь ложный default-deny), либо тихо перестаёт
действовать без уведомления. Второе: erase-по-запросу «через owner-канал» означает, что именно
OWNER — тот, у кого может быть встречный интерес хранить данные о третьем лице (агрессивный
партнёр, работодатель) — становится единоличным судьёй чужого erase-запроса, и Fable сам
отказывается вводить guardian как роль («не плодите роли») — то есть НЕТ внешней стороны,
которая аудирует, честно ли owner-канал исполняет запрос отсутствующего референта. Это
воспроизводит дыру A2.3 из `_critique.md` («кто сторожит policy-запись») один в один, просто
переименовано в «конституционное поведение».

**Вердикт: ТРЕЩИНА.** Два независимых нерешённых шва: (1) вычислимый триггер активации,
(2) конфликт интересов owner-канала без аудита.

## 3. «Слой бьёт тип по авторитету>охвату» закрывает C-1

**Вход:** узел `system-config` лежит на КОНСТИТУЦИОННОМ слое (максимальный авторитет), содержит
PII-поле (например захардкоженный email админа как payload, а не структурные метаданные). Слой
объявляет `no-mutate`. По правилу «авторитет > охват» — слой ВСЕГДА побеждает тип, без клапана
исключения. Юридический erase-запрос (например legal/GDPR-обязательство) не имеет пути победить
структурную неприкосновенность слоя — правило абсолютно, без override-ветки.

**Что ломается:** правило неявно постулирует, что целостность цепочки (`no-mutate`) —
аксиоматически выше согласия/юридического обязательства, не проверяя это против собственного же
Ц7 (Согласие), стоящего на том же ранге ценностей. Отдельно — внутреннее противоречие самого
ответа: п.2 утверждает «C-1 закрывается БЕЗ новых сущностей» этим правилом, но тут же (следующий
абзац) вводит НОВУЮ архитектуру — разделение journal/payload-store + per-referent×segment
crypto-shredding. Это и есть новая сущность (новый физический механизм), просто не названная
«ролью» или «типом».

**Вердикт: ТРЕЩИНА.** Правило разруливает заявленный кейс, но (а) не имеет клапана для случая,
где охват/закон ДОЛЖЕН победить слой, (б) заявление «без новых сущностей» опровергается тем же
абзацем.

## 4. Физика: солёный hash + crypto-shredding + per-referent×segment ключ

**Вход A (гранулярность ключа):** аудит-запись с тремя референтами в одном сегменте payload
(actor + target + witness одного события). «Per-referent×segment» ключ требует либо (а)
сегмент уже пред-разделён по референту (тот же нерешённый шов, что в п.1 — если содержимое
неразделимо, ключ неотделим тоже), либо (б) один ключ шифрует весь сегмент для «комбинации
референтов» — тогда erase ОДНОГО референта (уничтожение его ключа) уничтожает доступ и к валидным
данным ДРУГИХ референтов, которые erase не просили. Побочный урон согласия, которого никто не
просил.

**Вход B (auditability vs anti-linkability):** терминальное событие анонимизируется тем же
per-record солёным hash. Но тогда система не может позже доказать «мы стёрли данные референта X
по его запросу N месяцев назад» (subject-access-request / регуляторный аудит) — соль по записи
разрушает как раз ту корреляцию, которая нужна для ответа на «докажи, что забыл меня». Fable
называет это «закрытым», но по факту заменяет одну утечку (PII в терминальном событии) на другую
дыру доверия (невозможность доказать факт исполнения erase).

**Что ломается на масштабе:** ключей = O(референты × сегменты) без указанной схемы деривации
(HKDF и т.п.) — при 10⁶+ узлах это комбинаторный взрыв операционного KMS-долга (ротация,
бэкап, восстановление), не вычислительная, а административная NP-боль.

**Вердикт: ТРЕЩИНА, местами СЛОМАН.** Крипто-механика решает названную утечку ценой (а)
коллатерального erase чужих данных при неотделимых сегментах, (б) потери auditability
(Доверие Ц3 разменяно на Согласие Ц7 без явного признания компромисса), (в) неописанной схемы
деривации ключей на масштабе.

## 5. INV-LINEAGE (отклонять запись без `about`+`derived_from`, без исключений)

**Вход:** owner создаёт первый узел с нуля — голосовая заметка «чувствую усталость сегодня» —
или системный `policy`-узел, декларирующий governance-правило. Ни то, ни другое не ПРОИЗВЕДЕНО
из чего-то другого в графе: это источник, не производная. INV-LINEAGE требует `derived_from`
«без исключений, включая записи самих агентов» — буквально исполненное правило блокирует запись
самого первого, корневого, наблюдательного факта, потому что derived_from ссылаться не на что.

**Что ломается:** либо нужен спец-кейс (`derived_from: self` / null-допустимо для
primary-source узлов) — то есть исключение, которое правило прямо запрещает («без
исключений»), либо на Day 1 нельзя записать вообще ничего первичного. Отдельно: возведение
`about`+`derived_from` в ОБЯЗАТЕЛЬНОЕ, движком-проверяемое условие каждой записи превращает
«рост = дешёвый INSERT» (заявленная ценность модели, Ц5) в «INSERT + обязательная валидация
двух графовых ссылок на существование» — то есть цена записи растёт для КАЖДОГО узла, включая
случайные обрывки мысли, где провенанс ещё не осознан автором в момент записи.

**Вердикт: ТРЕЩИНА.** Направление верное (ретрофит происхождения задним числом невозможен —
Fable прав именно в этом), но формулировка «без исключений» ломается о собственные корневые/
конфигурационные узлы модели и молча поднимает пол стоимости записи, обещанной дешёвой.

## 6. Слепая зона — метастазы в производные (taint-замыкание) + вне-графовые артефакты

**Вход:** узел N → агент суммирует в недельный дайджест D1 → D1 сжимается в месячный дайджест
D2 → D2 цитируется в сообщении, отправленном во внешний Telegram-чат человеку. Referent узла N
вызывает hard-erase. Taint-замыкание по `derived_from` находит D1, D2 внутри графа (в принципе
редактируемы) — но отправленное сообщение УЖЕ покинуло границу записи графа: ни erase, ни любой
другой механизм модели не имеет пути дотянуться до чужого телефона.

**Что ломается:** Fable сам называет это («вне-графовые артефакты — индексы, кэши») но НЕ даёт
ни одного механизма — просто фиксирует как открытое. Это значит: гарантия hard-erase логически
неполна для ЛЮБОГО узла, чья цепочка деривации когда-либо пересекла «emit»-границу — а в
агент-центричной архитектуре (агенты постоянно суммируют и ОТПРАВЛЯЮТ) это не редкий край,
а стандартный путь. «Мы решили erase» и «отправленное нельзя достать» — два одновременно верных
и несовместимых утверждения; вторая не отменяет первую, она её опровергает как ПОЛНУЮ гарантию.

**Дополнительно (вычислимость in-graph части):** taint-замыкание по `derived_from` требует
обратной достижимости по всему графу деривации — без объявленного потолка глубины/веера (та же
дыра A3.3 уже поднятая для резолвера, здесь для erase удвоенная). Не указано, ациклична ли
`derived_from` гарантированно (агент А суммирует Б, суммирующего А — цикл), и не указано,
вычисляется ли замыкание online по запросу (стоимость на КАЖДЫЙ erase, потенциальный DoS —
референт с «тяжёлым» узлом может триггернуть полный обход графа одним запросом) или
инкрементально по мере роста (материализованное множество предков на каждом производном узле).

**Вердикт: СЛОМАН** для внешней/вне-графовой части (сам Fable фиксирует дыру и не предлагает
механизма — заявленная гарантия erase логически неполна для узлов с emit-историей).
**ТРЕЩИНА** для in-graph части (замыкание вычислимо в принципе, но без потолка стоимости,
без гарантии ацикличности — новая поверхность DoS через сам erase-запрос).

## Ранжир по несущести (от самого опасного)

1. **#6 Вне-графовые артефакты** — SLOMAN. Опровергает саму полноту гарантии erase для
   стандартного (не краевого) агентного паттерна «суммировать → отправить».
2. **#1 R-ERASE расщепление** — ТРЕЩИНА/на грани SLOMAN. Правило работает только если
   гранулярность assertion-рёбер уже существует; для свободного текста — не существует.
3. **#4 Физика (ключи/hash)** — ТРЕЩИНА/местами SLOMAN. Коллатеральный erase чужих референтов
   + потеря auditability, разменянная без признания.
4. **#5 INV-LINEAGE «без исключений»** — ТРЕЩИНА. Верное направление, но блокирует
   корневые/системные узлы и молча поднимает цену INSERT.
5. **#2 Опекун-как-поведение** — ТРЕЩИНА. Нет вычислимого триггера + owner-канал без аудита
   (конфликт интересов).
6. **#3 Авторитет>охват** — ТРЕЩИНА. Нет клапана для legal/scope-override; «без новых сущностей»
   опровергается тем же абзацем, вводящим payload-store separation.

## Что выжило без трещин
- Сама диагностика Fable, что ретрофит провенанса невозможен (направление INV-LINEAGE) —
  верно по существу, трещина только в абсолютизме формулировки.
- Разделение journal(ref+hash) / payload-store как ФОРМА (не как «закрыто без вопросов») —
  корректный примитив, если снять недосказанные допущения из #1 и #4.
