# 📇 Реестр типов + навигация (дерево = БД)

## 1. Минимальный сид реестра (6-10 базовых типов, засеять примерами)
1. **theme-card** — карточка одной темы/грани модели (что это, зачем, открыто).
2. **analysis** — глубокий разбор вопроса одним агентом (этот файл — пример).
3. **synthesis** — свод нескольких analysis/critique в один вердикт слоя.
4. **decision-card / decision** — зафиксированный выбор с датой и причиной (не переоткрывать без повода).
5. **plan / work-plan** — что делаем дальше, по шагам, со статусом.
6. **state** — живой указатель «где мы сейчас» (STATE.md-паттерн, один на скоуп).
7. **registry** — сид списка сущностей одного рода (сам этот реестр — тоже registry).
8. **open-question** — незакрытый вопрос, ждёт ответа/раунда.
9. **concept** (`*.concept.json`) — не текст, а машинный узел-навигатор (см. §4).
10. **README/INDEX** — вход в папку, не контент, а указатель на её типы.

## 2. Глобальный vs проектный реестр
- **Глобальный** (`~/.claude/...` уровень пользователя) — типы, общие для ЛЮБОГО проекта/клуба: theme-card,
  analysis, synthesis, decision, plan, state, registry, open-question, concept, README. Это ядро out-of-box.
- **Проектный локальный** (внутри `docs/.../<проект>` или настройка «клуба»/шлюза) — типы-надстройки под
  специфику: например `pages` во фронте (роуты/компоненты) ≠ `pages` в мобайле (экраны/навигация) — разные
  правила рендера и связей, хотя имя совпадает. Правило: **имя может совпадать, семантика — нет**; проектный
  реестр переопределяет/уточняет, не ломает глобальный костяк.
- Конфликт разрешать явной пометкой уровня в самом реестре (`scope: global | project`), не угадывать.

## 3. Как реестр «подсказывает структуру»
Тип узла = мини-шаблон папки: если завели `plan`, система/агент ожидает рядом `state` (что сейчас) и
`decisions` (что зафиксировано) — так же как `session-logging` уже подсказывает «тема=проекция, не копия».
Реестр = каталог таких шаблонов; заводя тип, ты неявно обязуешься завести его типовых соседей (аналог
policy-as-data из §05-categories-tags-facets: тип несёт с собой ожидаемую форму, а не просто ярлык).

## 4. Системные типы навигации (ссылка/связь) + роль `concept.json`
1. **link** (`refines/answers/raises/tension-with/grounds`) — типизированное ребро между двумя узлами
   любого рода (уже канон в диалоговом графе THREAD-*).
2. **projection** (тема-как-проекция) — узел, который НЕ хранит контент, а указывает на реальный документ +
   ракурс (session-logging паттерн); не второй экземпляр истины.
3. **index/registry-of** — служебный узел «что есть в этой папке и какого рода», авто- или полу-авто-
   генерируемый (README/INDEX, module-registry).
4. **concept** (`*.concept.json`) — машиночитаемый визор: даёт агенту/владельцу «полную картину» по ссылкам
   без обхода файловой системы; отвечает на «в brain найди активные plans по теме Y → покажи связанные
   state↔plan↔analysis» через граф `links`, а не через путь. Роль — единственный слой, который знает, ГДЕ
   что лежит логически; остальные типы просто ссылаются в него/из него.

## 5. Риск
**Тривиальный поиск как индульгенция** — раз "всё найдётся по типу+ссылкам", легко засеять реестр
спекулятивными типами "на будущее" (мёртвый вес, как и просил владелец не делать). Ограничение: тип
попадает в реестр ТОЛЬКО когда есть ≥1 реальный узел этого типа в дереве; иначе — open-question, не
registry-entry.
