# 🔶 Fable-ответ #2 — направление верное, но модель однобокая: вы спроектировали существительное и не спроектировали глагол

## 1. Вердикт по направлению

**Путь сформирован верно.** Форма→стек, 4 примитива, рост=INSERT, «policy = ПРАВИЛО · паспорт =
ЗНАЧЕНИЕ · view-def = ЛОГИКА», резолвер как пересечение, ломать от слабейшего звена — это правильная
последовательность, и она честно себя дефектует (критик нашёл настоящие дыры, а не декоративные).
Это редкость. Направление не менять.

**Где кривизна — три места, по нарастающей тяжести:**

1. **Кривизна лёгкая: продуктовый срез сформулирован как три фичи, а это одна грамматика.**
   «События · сохранение · поиск» — не три подсистемы, а три глагола одного механизма (ниже, §3).
   Если проектировать их порознь — получите три PEP, три формата событий и три аудита. Кривизна
   формулировки, не пути.

2. **Кривизна средняя: концепт полностью асимметричен — богатая анатомия ЕДИНИЦЫ (~22 поля,
   policy-оси, резолвер) и почти нулевая анатомия АКТА.** Журнал назван «позвоночником» в одной
   строке OVERVIEW и дальше живёт как сантехника. Между тем **половина открытых дыр — это дыры
   акта, не единицы**: гонка резолвер↔журнал (Ф5), конкурентная запись (D8-Q3), self-escalation
   policy-записи, идемпотентность (живой баг дубля шлюза!), snapshot-контракт. Вы разобрали «что
   лежит» и не разобрали «что происходит». Единица без акта — музей, не субстрат.

3. **Кандидат в death-by-design: «производное = read-time проекция» без бюджета и без контракта
   инвалидации.** Резолвер = пересечение трёх множеств + consent-чек на КАЖДЫЙ hop + рекурсивные
   CTE — это O(граф) на каждый чих агента. Спасение названо («derived-кэш»), но derived-кэш,
   сплетённый с отзывом согласия, erase-каскадом и variant-каскадом — это самая трудная задача
   проекта, спрятанная под невинной фразой. Пока нет ответа «что именно и к какому сроку
   пересчитывается при изменении базы» — принцип проекции-первой умрёт при первых 100k узлов
   либо будет тихо предан материализацией без правил. Это чинится (см. §2.3), но чинится СЕЙЧАС.

**Держится ли под продуктовым срезом (много проектов, разные правила, взаимодействие)?**
Наполовину. Оси паспорта + engine-contract выдерживают «много проектов с разными правилами» —
scope-полоса + owner/tenant + policy-по-ссылке действительно дают это ноль-колонками. **НЕ
выдерживает взаимодействие МЕЖДУ проектами:** вся модель молча предполагает один граф и один
реестр типов. Два проекта = два реестра = столкновение смыслов (`node_type: task` от двух плагинов
— критик это уже поймал как type-squatting, но не поднял в несущее). Без пространства имён типов
федерация проектов невозможна в принципе — а ретрофит имён после первой записи почти невозможен.

**Мета-замечание о методе:** конвейер производит provisional-agent-решения быстрее, чем владелец
их подписывает (DEC-4…DEC-10 + Ф1–Ф5 висят). Система проектирует поле `committed` для узлов — а её
собственные решения живут без `committed`. Ирония диагностическая: долг ратификации = та же дыра
акта, что и в модели.

## 2. Несущие абстракции, которые упускаете

**2.1. АКТ (speech-act, спроектированный journal-entry) — вторая единица системы.**
Единица отвечает «что есть», акт — «что случилось и по чьей власти». У акта свой паспорт: actor
(identity) · authority (по какому праву) · scope · idempotency-key · payload-ref+hash · результат.
Запись policy — тоже акт и тоже гейтится (закрывает self-escalation). Чтение — тоже акт (закрывает
«видно, что он делает» из msg 141 — аудит чтений бесплатно). Без акта не решаются: конкурентность,
идемпотентность, snapshot-контракт, provenance единообразно. **На этом повиснет всё рантаймовое.**

**2.2. Пространство имён и версия ТИПА (контракт словаря).**
Сейчас тип = строка реестра без владельца имени. Нужно: `namespace:type@version` + владелец
пространства + правило совместимости (например, widen-only: поля добавлять можно, менять/удалять
— новая версия) + ребро-маппинг между типами разных пространств («их task ≈ наш task»). Это
одновременно ответ на D8-Q4 (эволюция живого типа = новая версия + маппинг, а не мутация),
на type-squatting и ЕДИНСТВЕННОЕ условие существования маркетплейса. **На этом повиснет всё
межпроектное и весь plug-in.**

**2.3. Контракт пропагации (lineage + инвалидация как одна механика).**
Erase-каскад (Ф4), отзыв согласия (Ф5, дыра №3), stale variant (дыра №4), derived-кэш, пересборка
умных категорий — это ПЯТЬ имён одного вопроса: «база изменилась — что из выведенного обязано
измениться и к какому сроку». Механика одна: каждый derived носит lineage-ребро `derived-from`;
движок должен bounded-staleness-гарантию; срок = policy-as-data (freshness как правило, не код).
Consent-revocation = просто самое строгое правило пропагации (срок 0, каскад по taint).
**На этом повиснет вся Суверенность/Согласие и вся производительность.**

## 3. Продолжение концепта

**Следующий несущий узел после единицы — АКТ.** И тогда продуктовый срез схлопывается в один
механизм, а не в три:

> **Всякое взаимодействие = акт через один порог (PEP), записанный в один журнал, видимый через
> одну линзу.**

- **Сохранение** = write-акт: propose → гейт (то же 2-шаговое разрешение авторитет×охват, что у
  policy!) → commit → журнал. Поля `status`/`committed` паспорта — это тень акта на единице.
- **События** = не отдельная подсистема, а **view-def над потоком актов**. Подписка = линза на
  журнал; «уведомить агента X о задачах проекта Y» = resolve(journal-anchor, lens, identity) —
  та же формула Достижимое∩Релевантное∩Разрешённое, применённая к актам вместо узлов.
- **Поиск/фильтр** = read-акт: тот же резолвер, тот же порог, и он журналируется (аудит чтений).

**Разделение user/system/агенты/проекты собирается тем же механизмом:** это не четыре режима, а
разные значения actor-оси акта × scope-оси единицы. Человек в кокпите = `resolve(human-anchor,
cockpit-lens, ownerIdentity)` — уже сказано в B3; акт достраивает симметрию: человек и агент
ходят через один порог, различаясь паспортом, а не подсистемой.

**Что plug-in/маркетплейс требует уже сейчас — рефрейм: плагин не особая сущность.**
**Плагин = актор с паспортом + поставка словаря.** То есть: (identity-узел + capability-policy
«какие акты и в каких scope ему можно» — тем же policy-as-data + строки реестра в СВОЁМ namespace).
Никакого нового механизма маркетплейс не требует, ЕСЛИ уже сейчас: (а) типы именованы через
namespace@version (§2.2); (б) engine-contract = единственная поверхность, и эта поверхность —
**API актов** (плагин никогда не трогает таблицы, только совершает акты через порог). Следствие:
спроектировать акт = спроектировать API плагина. Двух зайцев одним узлом.

## 4. Один следующий ход

**ADR «Акт и журнал» — спроектировать journal-entry как вторую единицу** (паспорт акта, гейт на
запись/чтение, идемпотентность, snapshot-семантика чтения, payload по ref+hash).

Почему именно это, а не подпись Ф1–Ф5 и не namespace: hard-erase уже ушёл в Fable-бриф #1 —
не дублировать; namespace важен, но виснет на поверхности контракта, которую задаёт акт. А ADR
акта **одним документом закрывает пять открытых хвостов**: DEC-6 (журнал без инлайн-payload),
D8-Q3 (конкурентность), Ф5 (snapshot-контракт), self-escalation policy, идемпотентность (и живой
баг дубля шлюза как валидационный кейс) — и попутно определяет plug-in API и «события» как линзу
на журнал. Ни один другой одиночный ход не схлопывает столько открытого. Это дизайн-ход, не
стройка — фазе не противоречит. Namespace типов (§2.2) — ход №2, сразу следом, до первой записи.
