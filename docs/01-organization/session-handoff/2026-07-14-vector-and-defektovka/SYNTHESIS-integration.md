# 🌅 СВЕДЁНКА — интеграция 11 тем (ночной проход, 7 агентов)

> Свёл вердикты 6 разборов по швам (D-1..D-6) + сквозного критика. Форма — вердикт, не сырьё.
> Каждое решение ниже **предварительное (агентское), ждёт твоей ратификации** — не вписано в DECISIONS-LOG.

## 👑 Главный инсайт — всё сошлось в ОДНОМ принципе
Шесть независимых разборов пришли к одной мысли-арбитру:

**«Храни минимум фактов в одном доме — остальное выводи (read-time), адресуй по `id`, не дублируй.»**

- D-1: паспорт = **3 оси**, видимость — read-time policy, не колонка.
- D-2: policy-as-data — **узкие governance-флаги**, retention/consent/ACL живут на паспорте (не дублировать).
- D-3: категории — **view-def по умолчанию**, материализация только под контрактом (DL-04+DL-11).
- D-4: anchor к тексту — **quote-поле на ребре**, дробить на ноты только по нужде.
- D-5: **Postgres** (один дом) бьёт графовую БД (labels = второй дом типа).
- D-6: гражданство по стабильному **`id`, не пути**; один реестр связей, прочие = проекции.

Вывод: модель **интегрируется связно, ЕСЛИ этот принцип — арбитр**. Именно его отсутствие как явного
правила и есть скрытый шов (ниже D-7).

## Вердикты по швам (одной строкой + ключевое решение)
| Шов | Интегрируется? | Ключевое решение (предварительно) |
|---|---|---|
| **D-1 оси паспорта** | условно да | Паспорт = `owner`(+origin-kind) · `scope` · `storageLevel`. Слой/аудитория/локальность → policy+рёбра+view, не колонки. Мульти-user = диапазон `owner`. |
| **D-2 policy-as-data** | условно | policy хранит только governance-декларации; значения (retention/consent/ACL) — на паспорте. **Гейт: D5 integrity решить ДО роста policy.** |
| **D-3 инварианты** | условно / нет | **(а)** journal-entry НЕ инлайнит payload (ref+hash), иначе rebuild воскрешает стёртое → нужен ADR. **(б)** «умные» категории = view-def; прямая машинная запись `categorized-as` без derivation-rule запрещена. |
| **D-4 гранулярность** | условно | anchor = **quote-based** поле паспорта assertion-ребра (не offset — рвётся; не 5-й примитив). Ноты — по порогу «адресуемо отдельно». |
| **D-5 форма→стек** | да | **Postgres** (nodes/edges+JSONB+recursive CTE+app-level view-def). GraphQL = тонкий read-API визора, не хранилище. Граф-натив — только по замерам. *Вход для Fable, не финал.* |
| **D-6 метод** | условно | Гражданство по `id` (не путь); traceability `ADR.affects ↔ SCHEMA.governed_by ↔ migration`. Риск: 4 параллельных реестра связей разъедутся. |

## ⚠️ 3 глобальных противоречия (вынесены как узлы)
- **C-1 · erase двудомный:** тип (D-2/DL-13) vs слой (D-1: «системное не стираем»). Кто главный при `erase=true` в системном слое?
- **C-2 · инварианты под RDBMS vs склон к графу:** DL-17/18/04 естественны для Postgres; DEC-1 декларативно закрыл риск, но D-5 подтвердил: граф ломает эти инварианты. (D-5 снимает C-2 в пользу Postgres — но это тебе решать.)
- **C-3 · давление материализации:** «аудитория как ось?» (D-1) и «умные категории» (D-3) — один и тот же вопрос «вычислять vs материализовать», разнесён без ссылки. Общий арбитр = главный принцип выше.

## 🕳️ Скрытый шов D-7 (нашёл сквозной критик) — несущее
**«Разводящее правило»**: нет процедуры, кто и по какому критерию решает — новое измерение (слой,
аудитория, уровень детализации, класс policy) становится **полем паспорта / policy-узлом / типом /
атрибутом ребра / view-def**. Без него каждая волна агентов будет плодить новую ось. Это и есть явная
форма «главного принципа». **Завести отдельным узлом-владельцем.**

## 🔲 Слепые зоны (не спрошено нигде) → D-8
1. Конфликт policy при **мульти-владельце** одного узла (два consent/ACL — кто побеждает).
2. **Enforcement:** кто физически проверяет ACL/consent в рантайме — движок / GraphQL-резолвер / БД?
3. **Конкурентная запись** в append-only журнал (гонки за пределами canonicalId-merge).
4. **Эволюция схемы живого типа** (не новый тип INSERT'ом, а смена полей у существующего) — «рост=INSERT» не покрывает.
5. **Cost/ROI:** оправдана ли сложность для single-user личного приложения (бизнес-разрез отсутствует).

## 🔴 Самое слабое звено — с него ломать дальше
**Право на забвение (hard-erase).** Сходятся сразу три незакрытых спора: тип-vs-слой (C-1),
rebuild-vs-erase + WAL/бэкапы (D-3a), зависимость от выбора БД (D-5). Плюс это одна из 7 ценностей
(Суверенность/Согласие). До его закрытия **нельзя писать сырой личный payload** (риск R1).

## ❓ 4 фокусных вопроса тебе (утром)
1. **hard-erase — свойство типа, слоя, или оба через «разводящее правило»?** И принимаешь ли, что erase
   требует «журнала без инлайн-payload» (ADR) + решения по WAL/бэкапам (это блокер: писать ли личные данные)?
2. **«Продолжительные» категории** — ты имел в виду **версионно-хранимые** (история версий) или
   **пересчитываемые на лету**? Это слово разводит целый спор с «проекцией-первой».
3. **Стек:** принять **Postgres** рабочей основой (форма это диктует), а графовую/GraphQL держать
   отложенной опцией под замеры — или хочешь, чтобы **Fable** отдельно оспорил это?
4. **«Разводящее правило» (D-7)** — завести отдельным узлом-владельцем (кто решает, куда садится новое
   измерение)? Без него агенты будут плодить оси.
