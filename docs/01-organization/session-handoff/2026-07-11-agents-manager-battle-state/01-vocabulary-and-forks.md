## 2. resume-vs-clear — РАЗРЕШЕНО (по коду, снимаем путаницу C-13)

Твой вопрос: «каждый раз, когда жму [?] — новая сессия, или мы делаем resume, а не clear?»

**Ground truth:**
- **Каждый ход = RESUME той же сессии.** Первый ход — SDK генерит `claudeSessionId`, сохраняем; ходы
  2..N передают `resume: id`. Ход N — это resume сессии, созданной на ходе 1. Не обнуление.
- **`/new` = очистить указатель resume, НЕ удалить.** Сегодня `resetSession` перезаписывает запись с
  тем же ключом, **опуская** `claudeSessionId` → следующий ход стартует с чистого листа. Старый
  `claudeSessionId` **терялся** (архива не было, `/resume` был мёртв — код честно это признавал).
- **Смена `cwd` (`/bind`) = неявный `/new`** (транскрипты Claude привязаны к папке).

**Что чинит Пакет 2 (уже собран, ждёт активации):** `/new` теперь **АРХИВИРУЕТ** (SAVE:
Active→Archived, `claudeSessionId` сохраняется + имя), `/resume` **ожил** (ACTIVATE: Archived→Active).
Инвариант: **≤1 Active на ключ**. → «много сохранённых тем на топик, между которыми переключаешься».

**Короткий словарь для UI (предлагаю закрепить):**
- **Ход** — одно сообщение-ответ. **Сессия** — живая нить (одна Active). **Тема** — сохранённая
  именованная сессия (Archived, resumable). `/new` = сохранить тему + начать пустую. `/resume` =
  сохранить текущую + активировать выбранную.

**Развилка словаря (мелкая):** тема = «длящаяся сессия» (1:1) или «переживает много сессий» (1:N)?
По коду Пакета 2 сейчас **тема ≈ сессия (1:1)**: тема — это именно архивированная запись сессии.
Моя позиция: оставить 1:1 (проще, durable); отдельный node-тип «сессия поверх темы» — только если
появится реальный кейс «одна тема, много перезапусков с разным контекстом» (тогда решать в ПАМЯТИ).

## 3. Развилка F-a — 3-слойная модель Личность → Агент(слот) → Сессия (C-9)

**Что просил:** у **личности** несколько **агентов** (зарезервированные слоты, отдельно от сессии);
каждый агент берёт свои сессии; агент, прикреплённый к топику, отчитывается прямо в топик.

**Сегодня в коде — 2 слоя:** `IAgent` (персона) и `ISession`. `agentId` может входить в ключ сессии;
`IBotBinding(agent↔bot↔topic)` есть, но резолвится без `topicId` (`router.ts:27`) → мультиперсона
дремлет. Прошлый план (`theme-management-vision-and-plan §2`) трактовал персону = `IAgent` (один слой).

**Твоё уточнение вводит СРЕДНИЙ слой** «агент/слот» между личностью и сессией. Варианты:

- **F-a.1 — Агент = слот-инстанс личности (3 слоя).** `Личность(шаблон IAgent)` → `Агент(runtime-слот,
  копия/ссылка на личность, привязан к топику)` → `Сессии(темы) под агентом`. Репликация = несколько
  агентов от одной личности (естественно ложится на C-10 «считать репликации»). Цена: новая сущность
  + запись в ключ сессии (`...:personaId:agentSlotId`).
- **F-a.2 — Оставить 2 слоя, «агент» = биндинг личности к топику.** Средний слой = `IBotBinding` с
  `topicId` (уже есть в схеме, надо оживить резолв). Дёшево (1 строка + runtime-команды), но
  «зарезервированный слот, отдельный от сессии» выражен слабее.

**Моя позиция:** начать с **F-a.2** (оживить `findBinding(botId, topicId)` — 1 строка, разблокирует
мультиперсону-по-топику уже на готовой many-to-many схеме), а «Агент-как-слот» (F-a.1) вводить, только
когда реально понадобится репликация с подсчётом (C-10). Преждевременный 3-й слой = лишний вес в ключе.
**Вопрос тебе:** «агент» — это отдельная сущность-слот (F-a.1) или роль биндинга (F-a.2)?

### ✅ РЕШЕНИЕ ВЛАДЕЛЬЦА (2026-07-11) — F-a закрыт в сторону многослойной (моя прошлая формулировка была ошибкой)
Правильная модель (слова владельца):
- **Личность** — верх, идентичность. Одна. Под ней **создаём Агентов**.
- **Агент** — под личностью. У агента **зарезервированные слоты**; слот **привязан или НЕ привязан** к
  топику/чату. Привязан → **отвечает в топик**; не привязан → может **работать в фоне**; часть — с задачей
  и **отчитывается**; «всегда отчитываться» может быть **прописано в самой личности** (дефолт поведения).
- **Сессия** — содержит **память агента**, поэтому **привязана к агенту** (формально любой агент мог бы взять
  сессию, но раз в ней его память — закрепляем за ним).
- Настройки **топика/чата** создают свою **область** (scope) взаимодействия.
- **ГЛАВНАЯ ЦЕННОСТЬ** всего этого = грамотная **репликация слотов и сессий**.
- **Полное управление** — через **одного оркестратор-агента**, который раздаёт грамотные задачи; под-агенты
  могут сразу **ставить вопросы**.

**Следствие для фаз:** структурную слоистость (личность→агенты→слоты, привязка к топику, области) можно
плумбить; но **«сессия = контейнер памяти агента» — это brain-концепт** → тяжёлую часть проектируем в
сессии по ПАМЯТИ. То есть эта модель — сама по себе **требование к единице памяти** (см. HANDOFF).

## 4. Развилка F-b — глобальная политика «отчёт = концепт по умолчанию» (C-5)

**Что просил:** все проекты, что общаются через шлюз, **по умолчанию** отчитываются концептом
(«синтез контекста из правил»); спец-настройка default-on; переопределение по чату/топику.

**Сегодня:** `reportsToChat` — per-agent (тихо/не тихо). Финальный ход = prose-текст. Механизм
«ход → md + rich + concept» = **Пакет 3** (не начат). Формат отчёта = `*.concept.json` уже узаконен
правилом `investigation-reporting/RULE.md`.

**Развилка — где живёт «политика вывода» и что такое default:**
- **F-b.1 — Глобальный флаг форматирования финала** (env/конфиг шлюза `GATEWAY_OUTPUT_MODE=concept|prose`,
  default `concept`), переопределяемый в `config.json` топика (каскад — как `cwd/model` сейчас).
  Чисто, ложится на существующий каскад конфига. **Моя позиция — это.**
- **F-b.2 — Свойство личности** (у каждой персоны свой output-mode). Гибче, но «глобальный default»
  выражается хуже (надо ставить на каждой).

**Что значит «синтез контекста из правил»:** финал = концепт, чьи `paths[]` = дерево
`личность → темы(сессии) → доки-этой-темы`. Это стыкуется с F-a (модель личностей) и с concept v1
(C-1..C-4). **Нюанс-риск:** «всё всегда концептом» уберёт быстрые prose-ответы — нужен лёгкий
переключатель на топик (Блок 1 concept-сессии 5 это уже как открытый вопрос держит).
**Вопрос тебе:** глобальный флаг вывода в каскаде конфига (F-b.1)? и prose остаётся параллельно доступен?

## 5. Развилка F-c — оркестрация ↔ worktree ↔ концепт (C-12)

**Что просил:** один чат управляет многими; параллельная работа в **отдельных ветках**, потом
**мерж/сдружить**; где планируются наложения — выносить в **отдельные модули**; концепт помогает это решать.

**Сегодня:** TM-9 «центральный пульт» — захвачен, не начат (размер L). Worktrees использовались вручную
в прошлой сессии (`am-pkg1/am-pkg2/am-merge`). Связка «оркестратор порождает изолированные ветки-агенты
и мержит» в шлюзе не автоматизирована.

**Развилка — уровень амбиции сейчас:**
- **F-c.1 — Ручной паттерн + концепт-как-карта-мержа.** Пока: оркестратор запускает под-агентов в
  worktree вручную; каждый пишет отчёт-концепт; финальный концепт = карта «кто что тронул», пересечения
  видны по совпадающим `paths[]` → эти файлы выносим в общий модуль. Дёшево, без новой инфраструктуры.
- **F-c.2 — Встроенный оркестратор в шлюз** (пульт TM-9: реестр агентов, статусы, кому дать задачу,
  авто-worktree, авто-мерж). Мощно, но L и **пересекается с ПАМЯТЬЮ** (агенты/сессии/трейсы = узлы БД).

**Моя позиция:** сейчас — **F-c.1** (паттерн + концепт-карта пересечений; это и есть «концепт помогает
мержить»); F-c.2 строить после того, как память определит, что такое агент/сессия/трейс как узлы.
**Вопрос тебе:** достаточно ли ручного паттерна F-c.1 на сейчас, или пульт TM-9 нужен в этот заход?
