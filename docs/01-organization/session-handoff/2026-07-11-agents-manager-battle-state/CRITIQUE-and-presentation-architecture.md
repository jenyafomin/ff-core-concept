# Критика владельца + презентационная архитектура (2026-07-11)

> Заброс-критика после C-15. Принято без защиты. Суть: **мы пишем идеи сухо и линейно**, а они должны
> цепляться к **механизмам** и прорабатываться **по ценностям**; Telegram нельзя прибивать гвоздями;
> в доке есть ошибки + возможно потерян контекст; **следующий хендофф** должен быть концепт-навигируемым
> и сгруппированным по механикам — с учётом уже написанного (не затирая хорошее). Этот файл — сам пример
> группировки по механикам, а не списком.

## Мета-принципы процесса (как вести работу дальше)
- **MP-1 · Идеи — по МЕХАНИЗМАМ и ЦЕННОСТЯМ, не линейно.** Линейный список `C-1..C-15` в `CAPTURE.md` —
  ровно та ошибка. Мигрировать в **индекс по механикам** (ниже) + прогонять через `value-decomposition`
  (7 ценностей brain). Релейшность — **в самих файлах** (frontmatter `Related`, ссылки по id).
- **MP-2 · Хендофф = КОНЦЕПТ, не сообщение.** Шлюз в конце шлёт не prose, а концепт с кнопками: у блоков
  комментарии; статусы **сделано / открытые вопросы / непонятно** с указанием **строк/диапазонов**; лежит
  рядом с сессией; владелец и агент ходят по нему **не гадая, не ища**. (Этот хендофф — сделать таким в след. сессии.)
- **MP-3 · Долг: ревизия ошибок.** В написанном есть ошибки и, возможно, потерян контекст. Нужен проход
  **по ценностям**, исправить, **не затирая** хорошее. → задача след. сессии, не сейчас.
- **MP-4 · Провенанс промптов/инструкций.** Агент должен **самоанализировать, из какой инструкции/промпта**
  пришла директива (каскад `.gateway/PROMPT.md` чат→топик + system-prompt + правила). Путаница здесь —
  одна из самых дорогих; заложить в промпт возможность «откуда это указание».
- **MP-5 · Мышление апгрейдом.** Для любого существующего функционала + новой задачи — сразу думать **как
  это апгрейдить дальше**, а не только «сделать сейчас».

## Архитектурные принципы
- **AR-1 · Развязать каналы. Telegram = отдельный модуль.** Появятся новые каналы — ядро должно быть
  **channel-agnostic**. Частично уже так (порт `IChannel`, кнопки канало-агностичны → grammY на границе),
  но Telegram-специфика местами протекает. → **кандидат в ADR** «Channel abstraction / Telegram как плагин»:
  явно вынести весь Telegram в `channel-telegram/*`, ядро знает только порты. Долг, не срочный код.

## МЕХАНИКИ (сгруппированные требования презентации)

### MECH-VIEWER · files + concept = ОДИН механизм просмотра
Опора: `channel-telegram/browser/{file-browser,tree,wizard,concept-*}`. Сейчас это близко, но не един.
- **Три режима просмотра** (один механизм, слегка меняется структурно, те же правила):
  1. **сообщение как есть** (текущее);
  2. **только текущая последовательность** — короткий **хедер всегда**, а описание — только в этом режиме;
  3. **окружение папок** — видно текущую позицию (отдельная **стрелка**) + остальные, помеченные в концепте.
- **Рекурсивная вложенность — презентационно как drill-down:** «пойдёшь сюда → там это·это·это» (блок A→дети).
- **Линейный ↔ дерево** — переключатель (Блок 3 уже есть).
- **Пульт управления — ближе к ВЕРХУ** (сейчас низко/коряво).
- **files: объединить файлы+папки в одну «папку»-кнопку** → нажал → видно и файлы, и папки текущей директории.
  Для **концепта** папки **фильтруются** теми, где есть (концепт-)файлы; **галочка** снять фильтр → все файлы
  директории (но «пройти по всему» — с оговоркой, не всё возвращать).
- **Две кнопки:** одна — папки+файлы; другая — **концепты** (смотреть концепт как файл vs **запустить концепт
  в работу** → это и есть «режим концепта»).

### MECH-BUTTONS · подсистема управления кнопками (продумать очень чётко)
- **Пагинация по кнопкам** (кнопок много → страницы).
- **Пагинация/скролл по тексту** (текст вверх/вниз в зависимости от показанного сообщения).
- **Группировка папок в одну кнопку** → нажатие **расширяет** интерфейс основных кнопок.
- **Базовые кнопки дерева** — в одну или две линии для навигации по уровням; **интуитивнее**: стрелки
  коряво → подобрать понятные режимы; напр. **лупа** для «больше/меньше»/новых уровней; «две в ряд vs в колонну».
- **Связанные многоуровневые кнопки → ПЕРЕИСПОЛЬЗОВАТЬ готовый механизм из Cardex:**
  `PROJETS/Cardex/scaner/src/infrastructure/tamplate/register-button-template.service.ts`
  (`createButtonWithSharedContext` + `TemplateService.generateCallbackData(props,data)`; тип `IButton[][]`),
  и интеграция `PROJETS/Cardex/scaner/@grammy-nestjs/` (декораторы `callback-query`). Динамически строит
  callback_data с общим контекстом — ровно «управление кнопками, связанными между собой». *(владелец
  предлагал скинуть — найдено, путь зафиксирован; изучить как образец, не копировать слепо.)*

### MECH-RICH · «красиво» по умолчанию + адаптив
- **ВСЕ сообщения = rich («красиво») сразу + кнопки** (RM-1). Владелец **до сих пор этого не видит** →
  проверить после активации (RM-5 жирность влита) + это часть Пакета 3 (D-1) и «кнопки от хода агента» (B-6).
- **Адаптив desktop vs mobile** — размеры **и кнопок, и текста**: мобилка — компактный вариант; десктоп —
  полный. Для длинного/«красиво» с большими данными — **показывать навигацию** (пагинацию/скролл, см. MECH-BUTTONS).

### MECH-HANDOFF-CONCEPT · хендофф-как-концепт (реализация MP-2)
- Шлюз понимает: в конце слать **концепт с кнопками и правильным форматом**, а не сообщение.
- В концепте — **комментарии по блокам**: «здесь сделано», «здесь просил ознакомиться», «здесь открытые
  вопросы», «здесь непонятно вот это·это» + **ссылки на строки/диапазоны**, статусы готовности.
- Лежит рядом с папкой хендоффа; и владелец, и агент проходят его быстро, углублённо, **не гадая**.
