## TL;DR

**Вывод:** «извлечение» и «маршрут» — это не два модуля, а ОДИН узел, идущий вверх по лестнице доверия;
граница между ними = эпистемический статус. **Вопрос:** где живёт ещё-не-проверенный узел, созданный ИИ —
ВНУТРИ графа (агенты видят/могут действовать) или СНАРУЖИ (стейджинг, невидим до апрува)?

## 🎯 Сильная конвергенция (совпало у всех 4 линз)

### 1. РАСЩЕПИТЬ `status` на две ортогональные оси — самый главный вывод
Сейчас одно поле `status` тянет два несвязанных вопроса. Это «первородный грех» модели.
- **`epistemic` (доверие):** `proposal | fact | hypothesis | archived` — «насколько этому верить / кто поручился».
- **`state` (рабочий процесс):** `open | doing | done` — «сделано ли». Зависит от типа (у факта его нет).
Узел может быть `epistemic:fact + state:done` ИЛИ `epistemic:proposal + state:open`. Слияние их в одно поле —
та самая категориальная ошибка, что «протекает» в каждый запрос, промпт и каскад (абстракция назвала это
ЕДИНСТВЕННОЙ путаницей, которая гниёт всё; критик и архитектор — независимо то же).

### 2. Извлечение и маршрут = один акт, разделённый доверием
C2 создаёт узел с `epistemic:proposal`. C3 = поднять тот же узел до `fact` + (побочно) назначить дом и связи.
`raw → proposed → routed → enriched` — это не 4 модуля, а ОДНО поле, меняющее значение во времени.
→ Не строить «экстрактор» и «роутер» как отдельные скилы с форматом передачи. Строить `propose(node)` +
`commit(node, home)` (commit = поднять статус + назначить дом).

### 3. Эпистемический статус — это СПИНА, не опция (решение #4 = ДА)
Извлечение ВСЕГДА рождает `epistemic:proposal`. Повышение до `fact` = явный, логируемый переход = шлюз доверия
= тот самый «клапан» из стратегии A/B (ширина клапана = порог авто-повышения; механизм фиксирован). Без этого
поля невозможно отличить «я сказал» от «ИИ догадался» → агент цитирует свои гипотезы как факты.

### 4. Один дом + связи (решение #1 = ДА), но красивый рефрейм
**Дом = не отдельный вид связи, а ПРИВИЛЕГИРОВАННОЕ ребро** — единственное, по которому наследуется
контекст и важность. Модель: «у узла много рёбер; ровно одно помечено `inherit:true` — это и есть дом».
Так Axis B (полиморфизм vs каскад) РАСТВОРЯЕТСЯ: можно принадлежать Спорту И Карьере двумя рёбрами, одно
наследующее. «Принадлежит двум» = `links[] rel:also_serves` (видно в графе/бэклинках, но НЕ второй каскад).
*Сюрфейс-решение:* оставить `home` отдельным полем (читаемость + Obsidian-граф), но понимать как «ребро с флагом».

### 5. Открытый реестр типов (решение #3 = ДА), типы-модули НАСЛЕДУЮТ ядро
`type` = открытая строка vs runtime-реестр; `schema: type@version` фиксирует валидатор. Модуль регистрирует тип
с валидатором, НАслоённым на базовую схему (`registerType({name,version,validate,resolveHome})`). Валидация =
база (всегда) → тип (если известен); неизвестный тип → деградирует до `note` + warning, не reject. Ядро закрыто
для модификации, открыто для расширения.

### 6. Поток = inbox-стейджинг гибрид (НЕ чистый single-pass, НЕ чистый two-pass)
- Single-pass (ИИ пишет сразу): мусор копится как факты, необратимо.
- Two-pass (предложить→апрув): при 10-50 заметках/день очередь апрува убивает смысл, протухает.
- **Гибрид (рекоменд. анализом):** (1) синхронно: сырьё → минимальный узел `epistemic:proposal, stage:inbox`,
  <2с, ничего не теряем; (2) асинхронно батчем: ИИ обогащает группой (лучше ловит связи между соседними),
  выдаёт differential view (что классифицировал, confidence, неуверенность); высокоуверенные авто-повышаются
  с окном тихого апрува, на ревью всплывают ТОЛЬКО неуверенные; (3) ревью владельца — 5-10 мин/день, не на каждый ввод.

## 🏛 Конкретная форма узла (схема архитектора, Obsidian-совместимая)
Принцип: **frontmatter = типизированный контракт; тело markdown = поверхность для человека.** Obsidian
игнорирует незнакомые ключи (но они переживают round-trip, видны в properties, запрашиваются Dataview).

```yaml
id: <ULID>                 # стабильный, ≠ имя файла
type: <string>             # открытый, по реестру
schema: <type@version>     # пин валидатора
title: <string>
description: <string>      # всегда (ИИ читает первым)   [⚠ спор: абстракция предлагает выкинуть]
created/updated: <iso>
occurred: <iso?>           # время-истины/события        (ось ВРЕМЯ)
valid_from/valid_until: <date?>   # битемпоральность
supersedes: <id?>          # заменяет старый узел
home: "[[<один узел>]]"     # РОВНО один каскад-родитель   (ось ПРИНАДЛЕЖНОСТЬ)
epistemic: fact|hypothesis|proposal|archived   #            (ось ДОВЕРИЕ)
state: <по типу?>          # open|doing|done — отдельно от epistemic
stage: inbox|routed|enriched                   # маркер обогащения C3
links: [{to, rel, href?}]  # N типизированных рёбер; мульти-принадлежность ЗДЕСЬ
importance: 1..5           # контекстна дому
actor: user|agent:<id>
source: <провенанс>        # откуда сырьё (telegram:msg/130)
tags: [..]                 # #теги Obsidian; направления, НЕ принадлежность
<typeBlock>: {...}         # measurement:/person:/task: — валидируется type@version
```

## 🧩 Границы: СКИЛ vs АГЕНТ vs ДВИЖОК (важно для модульности)
- **ДВИЖОК (`@ff/core`, без ИИ, юнит-тесты):** parse/serialize frontmatter↔FFNode; реестр типов + валидация;
  МЕХАНИКА `route()` (запись файла в дом, set stage, цикл/глубина-гарды); целостность ссылок. ИИ НИКОГДА не на
  пути «валиден ли / куда физически кладём».
- **СКИЛ (процедура, стабильный I/O, суждение модели):** `extract` (сырьё → ProposedNode[]); ПОЛИТИКА `route`
  (предложить дом).
- **АГЕНТ (роль, авторитет):** *Библиотекарь* зовёт extract+route; *Inbox* — захват/триаж; *Хранитель* —
  обогащение/переходы доверия. Агенты владеют «КОГДА» и «что разрешено коммитить», не процедурой.
→ `extract` = СКИЛ (переиспользуем Библиотекарём/cron/владельцем). `route` = РАСЩЕПЛ�ён: механика=ДВИЖОК,
политика=СКИЛ. «Писать сразу или подтверждать» — управляется `epistemic+stage`, не хардкодом.

## 🩹 Дыры/риски, которые критик требует закрыть (НЕ блокеры концепта, но в план)
1. **Дедуп — first-class:** перед созданием искать существующий узел (иначе 12 «Антонов» за 3 мес). Нужен
   `supersedes` + поиск кандидатов.
2. **Бэклинки/обратный обход — канонические:** один-дом создаёт слепые зоны выборки, если связи не
   запрашиваются обратно (встреча в Карьере невидима из Антона). `getContext` обязан ходить по рёбрам, не только по дому.
3. **`getContext` = ограниченный конверт с явным «обрезано на глубине N»:** тихое усечение хуже отсутствия.
   Реализовать maxDepth-гард (в коде его нет) + цикл-гард по `links` (не только parentId).
4. **«надо разобраться с этим»** (нулевой сигнал) — допустимо как `type:thought, stage:inbox`; НЕ заставлять ИИ
   выдумывать тип/дом.
5. **Type sprawl** (meeting/call/interview/sync) — нужен поиск типа / «did you mean» / merge, иначе владелец не
   знает, какой тип брать.
6. **Напряжение «второй мозг, который действует сам» vs «ежедневный ритуал ревью»** — гибрид смягчает, но ось
   автономии должен задать владелец.

## ⏳ Решения, которые синтез ПРЕДлагает закрыть (ратификация владельца)
- **#1 Принадлежность → ДА:** один дом (привилегированное ребро) + мульти-принадлежность как `links`.
- **#3 Открытые типы → ДА:** реестр; модульные типы наследуют ядро + слой валидации; `type@version`.
- **#4 Эпистемический статус → ДА, обязателен:** расщепить `status` на `epistemic` (доверие) ⟂ `state` (процесс).
- **#2 Метрики/время:** да, как `typeBlock` (measurement{metric,value,unit}) + `occurred` — тип, не универсальное поле.
- **#5 Коммиты:** git = книга, узел = карточка со ссылкой `href`; не зеркалить (вывод абстракции, «карточка тонкая»).

## ❗ ДВА вопроса к владельцу, которые реально меняют дизайн (всё остальное следует из них)
**Q-A (ось автономии — keystone, сошлись 3 линзы):** ещё-не-проверенный узел от ИИ — ВНУТРИ графа (агенты
видят и могут действовать, фильтр по `epistemic`) или СНАРУЖИ (стейджинг, невидим агентам до апрува)?
**Q-B (физическая форма — архитектор):** `home` — это ПАПКА (файл лежит в каталоге дома; re-home = перемещение
файла) или ЛОГИЧЕСКИЙ указатель (плоский vault; re-home = правка одной строки)? Определяет, route() — это
перемещение файла или запись frontmatter, и сколько навигации Obsidian наследуем.
