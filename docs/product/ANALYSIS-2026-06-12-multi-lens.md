# Мульти-линзовый анализ видения — синтез

- **Status:** review
- **Owner:** jenya.stasik@gmail.com
- **Date:** 2026-06-12
- **Related links:** [VISION.md](VISION.md)
- **Источник:** параллельный анализ тремя агентами (abstract-thinker, system-architect, critic)

## 1. Где все три линзы сошлись (самые надёжные выводы)

1. **Домены — не контейнеры, а проекции на графе.** «Сквозные» домены (Финансы,
   Обучение, Планирование) перестают быть аномалией, когда домен — это тег/проекция,
   а не папка. Граф связей выносится в ядро, а не размазывается по доменам.
2. **Микро-фронтенды + БД на домен — преждевременно.** Для одного человека:
   модульный монолит с границами «module-per-domain», готовыми к выделению.
   Гипотеза не отвергнута, а отложена с сохранением опциона.
3. **Smart Messages — не фича чата, а протокол памяти всей системы** (формат записи
   в общую базу знаний с уровнями сжатия L1–L3+). И это **единственная по-настоящему
   уникальная идея**, которой нет в готовых продуктах — здесь кастомная разработка
   оправдана сильнее всего.

## 2. Концептуальное ядро (abstract-thinker)

Строятся **две машины**, спутанные в одну:
- **Машина A:** граф знаний/контекста о жизни владельца.
- **Машина B:** среда исполнения, где агенты действуют над графом через каналы
  (Telegram, фронтенды).

Минимальное ядро — **3 примитива**:
| Примитив | Что покрывает |
|---|---|
| **Node** (узел, с уровнями L1–L3) | сообщение, задача, тема, человек, заметка — типы узла |
| **Edge** (типизированная связь) | ссылается / принадлежит теме / блокирует / относится к домену |
| **Actor** (актор) | человек или агент — порождает и изменяет узлы |

Производные: домен = тег-проекция; проект = подграф + свой runtime;
тема = узел-агрегатор; задача = узел со статусом.

Обнаруженные концептуальные дубли: Тема ≈ Домен ≈ Проект (группировки разного
масштаба); Сообщение ≈ единица базы знаний; Планирование ≈ Задачи ≈ Хаб
(разный горизонт, одна природа); Агентская система ≈ Telegram-модуль
(Telegram — транспорт, не отдельная система).

**Незаданный вопрос №1:** *что является единицей, которую никогда не хочется
дублировать?* Когда одна мысль всплывает в Telegram, в задаче и в теме — это один
узел в трёх проекциях или три записи? Ответ определяет всю модель данных;
без него ADR-0002 принимать нельзя.

## 3. Архитектурный каркас (system-architect)

Три слоя, зависимости только вниз:

```
Domain Subsystems (11 доменов; общаются ТОЛЬКО через ядро)
        ↓                    ↓
Connectors (порты/адаптеры: AI-система, Telegram, позже Notion/Calendar)
        ↓
Shared Kernel (ID и ссылки, модель Message/Topic, Link Registry,
               Event Bus, примитивы Time/Task)
```

- Ядро — словарь, не оркестратор: не содержит доменной логики.
- Хаб — не слой, а доменная подсистема «надзора»: read-model поверх событий
  и статусов всех доменов. Тесно связан с Планированием/Задачами.
- Связи между доменами: (а) рёбра в Link Registry — данные, а не импорты кода;
  (б) события через шину вместо прямых вызовов; (в) сквозные домены как
  capability-порты («прикрепи финансовый аспект к любой сущности»).

**Первые ADR:**
- **ADR-0001** — стратегия границ/деплоя: модульный монолит vs микро-фронтенды vs гибрид.
- **ADR-0002** — модель данных и владение связями: единый граф + Link Registry vs БД-на-домен vs гибрид.
- **ADR-0003** — контракт интеграции: Event Bus + Ports & Adapters vs прямые вызовы; read-model для Хаба.
- (следом) ADR по Smart Messages/Topics как сущности ядра.

## 4. Главные риски (critic)

1. **Смерть в фазе проектирования** — самый правдоподобный сценарий заброса:
   через 6 месяцев есть красивая документация и ADR, но нет ни одного экрана,
   который открываешь каждый день. Ранний сигнал: 3 месяца проектирования модели
   данных без работающего среза.
2. **Неизвестно, где данные сейчас** (вопрос так и не отвечен). Если есть годы
   заметок в Notion/файлах — миграция не случится, будет две параллельные системы
   и откат в старую.
3. **Противоречие «тщательно продумать» vs «поэтапно получать ценность»** — выбор
   не сделан; грозит «и недопродумано, и медленно».
4. **«Изюминка» каждого домена vs общие коннекторы** — без общего ядра это
   N×M интеграций (ловушка решена архитектурой из п.3, если её соблюдать).
5. **Готовые продукты:** Notion/Obsidian закрывают базу знаний, связи, задачи,
   планирование. Честная рекомендация: вести «обычные» домены в готовом
   инструменте, пока кастомная система не докажет превосходство хотя бы
   в одном домене. Уникальны и стоят разработки: Smart Messages и агентская
   оркестрация под личные нужды.

## 5. Решения, которые нужны от владельца (блокируют следующий шаг)

1. **Идентичность узла:** одна мысль в трёх местах — один узел или три записи?
2. **Где данные живут сейчас** (Notion / таблицы / файлы / голова)?
3. **Первый срез ценности:** какой ОДИН домен/экран будет использоваться ежедневно
   через 2–4 недели? (Кандидат от всех линз: Задачи+Планирование через Telegram.)
4. Принять/отклонить рекомендацию «модульный монолит, микро-фронтенды отложены» (→ ADR-0001).
