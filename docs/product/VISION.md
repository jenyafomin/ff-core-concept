## 1. Суть

Этот проект — **центр управления (hub)** личной мульти-системой. Он самый общий уровень.
Каждое направление жизни со временем может получить **свою подсистему** (управление, аналитика,
подключение других направлений), потенциально со своим бекендом/БД/микро-фронтендом.

**Роль хаба (уточнено 2026-06-12):**
- Верхнеуровневые обсуждения: что делаем и как автоматизируем всё остальное.
- Аналитика и статусы по направлениям и проектам.
- Планирование/автоматизация других проектов — как системных, так и конкретных,
  которые будут появляться по ходу карьеры.
- Хаб тесно связан с модулем Задачи+Планирование.

**Подход к развитию:**
- Поэтапное внедрение; тщательное обдумывание перед реализацией.
- Каждое направление требует внимания и понимания его уникальности.
- Абстрактное продумывание с подключением разных агентов/линз/скилов параллельно —
  чтобы сформировать общее видение и понять, что развивать и куда направлять
  внимание в каждый период времени.

**Общие модули-коннекторы:**
Есть общие модули, которые как коннекторы дополняют каждый проект:
ИИ-система (агенты), Telegram-модуль и другие.

## 3. Связанные проекты (отдельные, но в экосистеме)

### 3.1 Система управления агентами/чатами
- Создание и управление чатами/сессиями агентов.
- В одном чате несколько агентов, каждый со своей ролью/контекстом (контекст может быть общим).
- Дебаты между агентами и другие режимы взаимодействия.
- Возможен свой локальный фронтенд для управления агентами, чатами, контекстами.

### 3.2 Telegram-модуль
- Гибкое управление через личные чаты.
- Управление агентами в разных чатах.
- В чате: управление контекстом + выполнение команд.
- Может быть связан с 3.1, но может жить и отдельно.

### 3.3 Умные сообщения (Smart Messages)
- Продуманный (или гибко-динамический) набор категорий → фильтры и поиск для ИИ и пользователя.
- Многоуровневое описание сути сообщения прямо в сообщении:
  - **L1** — самая общая суть, одно короткое предложение (обязательный).
  - **L2** — опциональный, до ~50 слов.
  - **L3+** — каждый следующий уровень ×10 по объёму (500 слов, 5000 слов…).
- Кейс: огромные ответы (например, проектная работа по коду) — 5k слов должно хватать почти всегда.

### 3.4 Проектная аналитика
- Для проектов внутри системы: бизнес-аналитика, разборы, управление.
- Возможность запускать Claude с контекстом конкретного приложения/проекта.

### 3.5 Общая база знаний
- Единая база знаний для всех направлений.
- Возможная основа — хранение переписки/сообщений (связь со Smart Messages, п. 3.3).
- В сообщениях важно определять **ссылки и привязки** к другим сообщениям и темам.
- Следствие: помимо линейных сообщений, в диалоге существуют **темы обсуждения**
  (topics/threads) как отдельные сущности.

## 4. Принципы (предварительно)

- У каждого проекта/направления — своя «изюминка», свой подход и взгляд.
- Hub — самый общий уровень; подсистемы доменов создаются по мере необходимости.
- Архитектурная гипотеза: микро-фронтенды, у каждого домена свой бекенд и БД (**требует ADR — не решено**).

## 6. Сессия 2 — ответы владельца и решения (2026-06-13)

### Ответы на стартовые вопросы
- **Первый шаг:** Hub-обзор и ревью — но с акцентом «увидеть, как всё связано между собой».
- **Где данные сейчас:** всё разбросано (голова + чаты + разные приложения). → строим с нуля,
  сборка воедино — часть задачи.
- **Интерфейс:** сразу локальный фронтенд (не Telegram-first).
- **Что удержит от заброса:** ИИ реально делает работу за меня; видимый прогресс;
  привычки/ритуалы; экономия времени и систематизация.

### Сильный сдвиг видения (явное предпочтение владельца)
1. **Каждое направление = отдельное приложение** со своей инфраструктурой и, возможно, своей БД.
   Мотив: так проще разрабатывать И качество каждого модуля становится «очень явным»,
   проработанным по всем деталям. Каждый модуль делается с максимальной глубиной.
2. **Глубокие модули, а не плоские.** Пример: не просто TODO, а многоуровневые задачи, где
   каждая подзадача **расширяет контекст родителя**, с привязкой задач между модулями.
   Принцип «максимальная полезность и глубина» для всего функционала.
3. **Связность обязательна.** Отдельные приложения должны плотно связываться между собой
   (кросс-модульные задачи, общий контекст). Hub — место, где это видно.

### Новая ключевая сущность: Центр брейншторминга
Главный центр для планирования проектов, по структуре как Telegram:
- **Супер-группа** = ключевой контекст проекта.
- **Топик** внутри супер-группы = агент + его контекст.
- **Чаты** внутри топика = отдельные темы; в них следишь и управляешь контекстом,
  вызываешь команды и агентов.
- **Агенты общаются между собой, и пользователь это видит** (наблюдаемый мульти-агентный диалог).
- Реализационно ложится в модуль управления ИИ-агентами (п. 3.1) — это его UX-воплощение.

### Зафиксированные противоречия (передать совету)
- **T1.** Владелец выбрал «Hub-обзор» первым шагом, НО hub нечего обозревать, пока нет модулей,
  которые дают данные. Риск «смерти в проектировании» (см. ANALYSIS §4).
- **T2.** «Отдельные приложения со своей БД» (проще разрабатывать, явное качество) ПРОТИВ
  «плотная связность + кросс-модульные многоуровневые задачи + общий контекст» — связать N
  отдельных БД по живому графу это самая дорогая интеграционная задача. Прямо противоречит
  рекомендации ANALYSIS «модульный монолит, микро-фронтенды отложить».
- **T3.** «Сразу локальный фронтенд» против «ценность за 2-3 недели» — фронтенд для N модулей
  откладывает первую ценность.

### Куда копать дальше (вход для ask-council)
Центральный вопрос: при таком предпочтении (глубокие отдельные приложения) — какова правильная
**связующая архитектура** и **первый срез**, чтобы (a) модули строились глубоко и независимо,
(b) реально соединялись (общая идентичность/ссылки/контекст), (c) владелец получил пользу за
~3 недели, не утонув в проектировании.

## 7. ЦЕНТР ТЯЖЕСТИ ПРОЕКТА — уточнено (2026-06-13, после совета #2)

> Это уточнение **меняет приоритеты**. Советы проектировали органайзер (задачи+заметки), но
> владелец на прямой вопрос «где ИИ делает работу» дал ответ, смещающий суть проекта.

**Суть проекта — не органайзер, а гибкая система агентов, которые работают и расширяют владельца
внутри его же системы.** (Дословно: «хочу создать гибкую систему агентов, которые смогут работать
и расширять меня в моей же системе».)

Это подтверждает разделение из ANALYSIS §2 (abstract-thinker):
- **Машина A** — субстрат знаний/контекста (граф `nodes`).
- **Машина B** — рантайм агентов, действующих над субстратом через каналы. **Машина B — сердце.**

**Форма направлений:** «общий ствол + плоды» — общее ядро (узлы/задачи/заметки/связи) + у
направлений свои спец-плоды поверх. (Владелец: «но над этим нужно хорошо подумать».)

**Вход данных — ИИ-driven, а не ручной:**
- агент сам тянет данные;
- извлекает из БД других систем;
- диалог с ИИ, который создаёт документы/заметки в базе знаний по направлениям.

**Следствие (косяк, который надо признать):** первый срез из COUNCIL-2026-06-13-first-slice
(Electron + CRUD задач + уведомление) — это Машина A без Машины B. Он не выражает сердце проекта.
Нужно пересмотреть, что является настоящим первым срезом.

**Наблюдение Председателя:** примитивная версия целевой системы УЖЕ работает прямо сейчас —
Claude Code (рантайм агентов) + файлы `docs/` (граф узлов) + Telegram (канал) + советы
(мульти-агентные дебаты) + память. Возможно, первый шаг — не строить Electron-приложение с нуля,
а формализовать то, что уже происходит.

### Уточнение рефрейма (владелец, 2026-06-13)
- **Агенты — не модуль, а горизонтальный слой:** «агентов я буду использовать ВО ВСЕЙ системе».
  Это сквозная способность, пронизывающая каждое направление (ср. «модули-коннекторы» §1).
- **На уровне хаба важны организация И АГРЕГАЦИЯ.** Новое ключевое слово — **агрегация**:
  хаб сводит/агрегирует across направлений (статусы, знания, сигналы, контекст).
- Итог: три слоя суть — **организация (структура) + агенты (действие) + агрегация (синтез)**.
  Не «агенты вместо органайзера», а все три вместе. Это вход для совета #3.
