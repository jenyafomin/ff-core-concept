## 0. Главный вердикт (одной картиной)
**ЯДРО ВЫСТОЯЛО.** На GitHub-масштабе (монорепо ~4k файлов, 40k функций, 120k коммитов, PR/issue/CI/зависимости) паспорт
**не растолстел ни на одно обязательное поле**. Главный ПРУФ — разделение **принадлежность⟂ссылка**: циклы вызовов
(A→B→A), круговые импорты, утилита с 500 входящими связями **не угрожают** ни хранению, ни каскаду — потому что home-спина
**всегда лес** (один home → дерево), а `calls/imports` — обычные рёбра, могут циклиться сколько угодно. **Твой худший
сценарий (рекурсия/сложные паттерны) — ровно там, где модель сильнее всего.**

**Честно (важно):** изящество **условно** — держится на «движке», который мы откладываем (индекс/rollup/кэш производных).
Стресс показал: **главный риск — не паспорт, а неописанный ДВИЖОК.** Ни один CRITICAL **не вскрывает** ADR-0002; почти всё
чинится на РЕБРЕ / в ЕНДЖИН-СПЕКЕ / записью ИНВАРИАНТА. Модель по-настоящему **растёт ровно в 2 местах** (версии и потоки)
— и оба §5 ADR-0002 уже предвидел.

## 1. ПРУФЫ — где модель держится по-настоящему (твой запрос «искать пруфы»)
Каждый пруф — с механизмом, не «работает»:
1. **Принадлежность⟂ссылка.** Циклы/рекурсия/500-фан-ин не ломают каскад — home-спина ацикличная по построению. *Самый
   несущий результат.*
2. **Тонкий паспорт type-agnostic** на 12+ сущностях GitHub (commit/PR/issue/review/branch/release/CI/package/person/file/
   function/code) — **0 новых обязательных полей**. (`epistemic` несёт жизненный цикл PR/issue; `source` — human/agent/system;
   `href/external_ref` — git/npm.)
3. **`level`-линза = реальный анализ репо БЕЗ открытия файлов** (L1 из заголовка, L2 из сигнатур, L3 из тела) — для
   нормально структурированного кода.
4. **Re-home самозалечивается** при `git mv` (ежедневная реальность рефакторинга — автоматически).
5. **Ромб/круговое наследование разрешается детерминированно и тотально** (ближайший→cascade_order→id всегда есть финал);
   «ближайший контейнер выигрывает» — семантически верно для scope/sensitivity кода.
6. **Control-plane самохостит семантику кода + безопасные сторонние инструменты:** добавить язык = добавить данные (узлы
   ТИП/ЛИНЗА); линтеры = read-only «линзы восприятия» (безопасны для плагинов); авто-мёрж/деплой — за клапаном.

## 2. ИЗЪЯНЫ — по 4 корзинам (большинство НЕ трогает паспорт)

### A. Маленькие правки на РЕБРЕ / в ДВИЖКЕ (паспорт не трогаем)
- **Общие/реплицируемые значения** (твоя тема): «канонический узел + проекции» покрывает только простой случай. Нужно
  различать **`binds` (живая привязка, тянется при изменении)** vs **`references` (упоминание, не тянется)** + флаг ребра
  **`binding: live|frozen`** (заморозил значение на момент привязки vs читает текущее). *+1 флаг ребра.*
- **Порядок/последовательность** (коммиты, сообщения, шаги плана): сейчас `priority` (важность) перегружен под порядок.
  Нужен отдельный **`seq`** на ребре (шаг-3 не «важнее» шага-2). *+1 поле ребра.*
- **`level` ≠ центральность** (важный нюанс): ядровая утилита *глубокая* (низкий level по глубине) но *центральная*
  (высокая важность по фан-ину). Это **не противоречие** — две РАЗНЫЕ линзы: level считается по спине принадлежности,
  центральность — по фан-ину ссылок. **Нельзя их сливать.** (§1 ADR — одна уточняющая строка, не пересмотр.)
- **Рекурсия в данных** (граф вызовов): `first-visit-wins` верно для каскада, но *прячет* цикл, который инструмент должен
  *показать*. Терминатор ПАТТЕРНА = enum `prune | mark-cycle`. *Заполняем неуказанное, 0 нового.*
- **`maxDepth` неверно режет глубокий каскад:** одна ручка делает 2 работы. Разделить на `cycle_guard` (revisit) и
  `cascade_depth` (легальная глубина 6-8 уровней кода). *+1 параметр движка.*
- **Индекс/rollup/кэш производных — НАЗВАНЫ, но НЕ ОПИСАНЫ** (вклад аналитика, и это #1 стоячий риск): на масштабе
  обязательны — бэклинки фан-ина (500), широкие папки (2000 файлов), rollup коммитов/сообщений (N-043), инвалидация
  кэша производных функций. *Это ЕНДЖИН-СПЕКА, 0 полей модели — но её надо НАПИСАТЬ.*

### B. Два настоящих новых МОДУЛЯ — модель тут РАСТЁТ (честно; §5 ADR это предвидел)
- **Версии/lineage** (твоя тема «варианты/версии»): модель сейчас **НЕ держит** — `supersedes` = «старое мертво»,
  `canonical_id` = «схлопнуть в одно». Ни одно не выражает **«сосуществующая упорядоченная история, всё реально»** (цепочка
  коммитов — постоянная история, не замена). → нужен **модуль версий**: узел-`lineage` + ребро `version-of`+`seq` + home на
  якорь; `supersedes` сузить до «настоящей замены». **«Каждый вариант = тип» — НЕТ** (взорвёт реестр 500k узлов); «один
  логический объект через версии» собирается ЛИНЗОЙ. *+1 модуль, без новых полей паспорта.*
- **Лёгкий / поток-класс:** 9 обязательных полей × миллионы строк лога/коммитов/сообщений = налог, делающий «всё = узел»
  невыполнимым на масштабе. → **узел-`stream`** держит паспорт, а записи **почти голые** (наследуют поля от потока по home).
  **Строки кода, call-sites, транзитивные зависимости — вообще НЕ узлы.** *+1 класс-конвенция (это вычитание полей, в духе
  «меньше родов»).*

### C. ИНВАРИАНТЫ записать (0 нового, но молчание = баг)
- **Клапан (твой D1!):** одобрение «вовне» — да, гранулярное (per-stage/per-cell), НО **енфорсит ВСЕГДА движок;
  модуль агентов несёт только ДАННЫЕ-политику** (какие шаги/ячейки требуют одобрения). **Агент НИКОГДА не одобряет сам
  себя** (иначе вернулась дыра «автор=одобряющий»). Это одна записанная строка, предотвращающая обвал безопасности.
- **Производные узлы кода — read-only:** файл = истина; функция-узел = производная проекция; писать в файл, не в узел.
- **Multi-schema реестр** (см. §3 ниже).
- **Контейнер: home ≠ категория** для одних и тех же членов (см. §3).

### D. Вне рамок этого раунда (флаг, не начинаем): **РЕАКТИВНОСТЬ** — по-прежнему #1 отсутствующий КЛАСС (CI-триггеры,
CVE-алерты, «застрявший PR») = ~½ ценности; ждёт твоего ответа про «агента вовне» (D1) и ADR-0003.

## 3. Твои НОВЫЕ концепты — вердикты (стресс показал тонкости)
- **Гибкие типы / мульти-схема (N-075) — ОСТОРОЖНО.** Именно твой любимый вариант («один тип с под-вариантами внутри»)
  **ломает главный инвариант:** чтобы выбрать схему, движку придётся ОТКРЫТЬ payload (прочитать `deal.kind`) — а весь смысл
  паспорта в том, что движок решает, НЕ вскрывая. **Безопасное решение:** вариант **ЕСТЬ тип** (`deal-sale`, `deal-rent` —
  отдельные типы открытого реестра), а **«один логический deal» собирается ЛИНЗОЙ** (`kind-of: deal`). *Тебе видно один
  тип; движку — безопасные разные.* Запись инварианта реестра: «`schema` обязан однозначно определять валидатор из паспорта;
  ветвление по значению payload запрещено».
- **Версии (N-072)** — модель растёт (модуль, §2B). «Каждый вариант=тип» — нет.
- **Группа-ячейка (N-074)** — частично ты прав: у группы могут быть свои свойства (= свой ТИП), «группа только группирует» =
  контракт типа (валидатор запрещает payload). **НО «группа = ещё и категория» — опасно:** нельзя одному узлу быть и `home`
  (принадлежность), и категорией для тех же членов — переместишь файл из `auth/`, и он молча потеряет ярлык «auth». Запрет в
  контракте контейнера. «связь группа↔группа ≠ объект↔объект» — уже покрыто (паттерн по типу концов), не дефект.
- **Реплицируемые значения (N-072)** — `binds` vs `references` + `live|frozen` (§2A). Шаблон-с-переопределением = контракт
  типа (E2), каскад его НЕ покрывает.
- **external_ref (N-073)** — оба размещения ок (узел-коннектор И/ИЛИ inline-схема ячейки). Не дефект.

## 4. Оптимизация (твой прямой запрос «как оптимизировать»)
**Правило «что достойно стать узлом»:** вещь = узел ⟺ (a) стабильный id при правках · (b) своя принадлежность (свой home
осмыслен) · (c) ценность как ЕДИНИЦА запроса.
- **НЕ узлы:** строки кода (нет стабильного id), call-sites (нет своей принадлежности), транзитивные зависимости (нет (b)+(c)),
  каждый коммит/сообщение по отдельности (поток + rollup, материализуются лениво).
- **Узлы, но лениво:** функции (ценны как L2, но 40k жадно — тяжело → производные по запросу + кэш).
- **Обязательны и отсутствуют:** бэклинк-rollup фан-ина · секция-индекс широких папок · abstract-by-name для потоков (N-043)
  · инвалидация кэша производных.

## 5. D5 — «композиты из скрытых данных» (ты сказал, что не понял — объясняю просто)
**Что это:** когда система берёт НЕСКОЛЬКО приватных значений (напр. доходы по 5 источникам) и сводит в ОДНО (общий доход),
чтобы показать это одно там, где сами 5 скрыты. **Проблема:** даже спрятав входы и отдав только сумму — по сумме часто можно
ВЫЧИСЛИТЬ вход (знаешь 4 из 5 → пятый = сумма минус 4; или следишь, как сумма меняется во времени). Поэтому «спрятать входы,
отдать композит» в общем случае **НЕ безопасно**. **Вопрос к тебе (D5):** разрешать ли такую фичу вообще ДО того, как
опишем модель раскрытия (бюджеты/правила), или заблокировать пока. **Рекомендация:** заблокировать до ADR-0003 — для
здоровья/финансов риск утечки высок.

## 6. Статус ядра + следующие шаги
**ADR-0002 остаётся APPROVED и здоров.** Стресс его КОНСОЛИДИРОВАЛ (ровно как ты просил — «через сомнение»). Минимальная
дизайн-работа (порядок), вся в ДИЗАЙНЕ, без «строй»:
1. **Записать инвариант клапана** (§2C, D1) — одна строка, предотвращает обвал безопасности.
2. **Записать 3 инварианта** (multi-schema реестр · derived read-only · контейнер home≠категория) — 0 нового.
3. **Описать движок** (индекс/rollup/кэш + split maxDepth + терминатор паттерна + level≠центральность) — **главная задача и
   главный стоячий риск.**
4. **Рёбра вместе:** `seq` + `binding: live|frozen`.
5. **Модуль версий/lineage** (использует `seq`, сужает `supersedes`).
6. **Stream-класс** (поток держит паспорт, записи голые; строки/call-sites — не узлы).
7. *(Вне рамок, флаг)* реактивность/реактор — ждёт D1/topic-4 + ADR-0003.
