# Память агента / пользователя (направление 2)

> 2 агента: модель данных + жизненный цикл/забывание. Фаза = DESIGN.

## Сквозной вывод
**Память — это обычные узлы графа с СУЩЕСТВУЮЩИМИ полями паспорта + СУЩЕСТВУЮЩИМИ рёбрами. 0 новых обязательных полей
паспорта.** Мы уже сидим в C∩D (темпоральный граф ∩ файлы-истина) — ровно там, где живёт правильная память агента.
Память лишь УСИЛИВАЕТ тонкий паспорт, не расширяет его.

## Модель: 3 класса памяти → наши TYPE
- **Semantic (стабильный факт)** → тип `memory-fact`, epistemic hypothesis→fact, ребро `about → subject`.
- **Episodic (событие)** → `trace` (атомарный шаг) + `episode` (контейнер), epistemic `fact` (оно случилось),
  рёбра `about`, `produced-by → agent`.
- **Procedural (как делать)** → УЖЕ ЕСТЬ как control-plane: `prompt`/`skill`/`pattern`/`lens`. Бесплатно (ADR-0002).
- Новые ТИПЫ: `trace`, `episode`, `memory-fact` (реестр, R0/R1). Новые рёбра: `derived-from`, `consolidates` (словарь
  рёбер, R1 — НЕ паспорт).

## User-память vs agent-память — через `principal` + LENS (нового механизма нет)
- `principal:owner` = жизненные факты пользователя (шарятся hard-ABAC-линзой, фильтр по sensitivity).
- `principal:agent:N` = рабочие заметки/трейсы агента N (по умолчанию агенты НЕ видят чужую рабочую память).
- `principal:shared` = консолидированное/промоутнутое знание.
- Выборка = ЛИНЗА с предикатом `principal==…`, не «движок памяти». `sensitivity`(приватность) ⟂ `principal`(чьё) — остаются ортогональны.

## Консолидация (уважает автор≠авторизатор)
`trace[] → reflection → memory-fact(epistemic:hypothesis)`. Консолидирующий агент дотягивает ТОЛЬКО до hypothesis.
`hypothesis→fact` — ДРУГОЙ актор (владелец/верификатор) по promotion-policy, с трейсом. `derived-from → trace[]`
хранит провенанс; сырые трейсы архивируются, не удаляются. Sleeptime = PATTERN-узел + триггер движка.

## Конфликт без потери данных
Новый факт получает ребро `contradicts`/`supersedes`/`builds_on`; старый → `epistemic:archived` (не удаление) +
инвалидация ребра. Неразрешённый конфликт показывается агенту с флагом — НИКОГДА не молчаливая перезапись.

## Tiers (горячее/тёплое/холодное) = ВИД, а не хранилище
Hot/warm/cold = выходы линзы над одним графом, ранг по recency+epistemic+(опц.)heat. Один факт горячий для планировщика,
холодный для бухгалтера. = `getContext(node, budget)` + сортировка по heat.

## Жизненный цикл (агент 2)
### Bi-temporal — концепт РЕБРА (0 новых полей паспорта)
Новые ОПЦ. поля ребра: `valid_from?/valid_to?` (когда факт был истинен в реальности) и `known_from?/known_to?` (когда
система записала/инвалидировала). Отлично от `created/updated` узла (когда тронули файл). Забывание по Zep =
`known_to=now` на старом ребре + новое ребро `valid_from=now`; старое НЕ удаляется. «Текущий граф» = `valid_to IS NULL
AND known_to IS NULL`. Рекоменд.: начать с `known_to`-only, полный bi-temporal — Этап 2.

### 4 состояния забывания (движок выводит, нового поля нет)
`active` (epistemic≠archived и known_to=null) · `superseded` (есть входящее `supersedes`) · `invalid` (ребро
known_to≠null) · `archived` (epistemic=archived). Cold = линза движка, не отдельное хранилище. Физическое удаление
запрещено; забывание = архив + инвалидация ребра. `active→archived` = авторизация как у промоушна в fact (не сам автор);
`archived→active` = только владелец-человек + трейс.

### Heat — только derived, НИКОГДА не в .md
`heat = 0.5·recency + 0.3·frequency + 0.2·priority`. Живёт в SQLite-индексе движка, не в frontmatter. heat ≠ epistemic ≠
priority. Только сигнал ранга для `getContext`; «heat>0.5 = факт» ЗАПРЕЩЕНО. Клапан от heat не зависит.

### Протокол сессии = PATTERN-узел (закрывает компакт-тревогу N-079)
`pattern/session-protocol-v1`: **INITIALIZER** (старт: читает session-state по `home→agent`, последний progress-log,
DECISIONS-LOG → восстанавливает контекст) → **PROGRESS-LOG** (на каждый шаг: узел `progress-log-entry`, принцип
«ожидай прерывания — пиши, будто следующий шаг делает ДРУГОЙ агент») → **END-UPDATE** (session-outcome + апдейт задачи +
сводка в DECISIONS-LOG). Графо-нативная замена ручной конвенции STATE.md. Рекоменд.: MD-конвенция работает сейчас,
промоут в граф — после скелета.

### Identity-guard (закрывает CRITICAL коллапса версий)
`canonical_id` (движок нашёл near-dup → алиас) ⟂ `version-of` (со-существующая история, всё живо) ⟂ `supersedes`
(реальная замена, старое в архив) ⟂ bi-temporal инвалидация (истёк ФАКТ ребра, узлы не тронуты). `supersedes` требует
трейс-узел (актор+ts+обоснование), иначе движок отклоняет. «Не знаю какой механизм» → inbox, не молчаливый supersedes.

## Кандидат-инварианты (16, 0 новых обязательных полей паспорта)
BT-1/2/3 (bi-temporal) · FG-1/2/3 (забывание) · HT-1/2/3 (heat) · SS-1/2/3 (сессия) · IG-1/2/3/4 (identity). Не
конфликтуют с 7 инвариантами из SWEEP. Раскладка: часть → ADR-0003 (ABAC/клапан), часть → ADR-0004 (движок).
3 кандидат-PATTERN: `session-protocol-v1`, `bi-temporal-invalidation-v1`, `forgetting-v1`.

## 🟡 Вопросы к владельцу
1. **Гранулярность трейсов** — логировать каждый шаг (миллионы)? Рекоменд.: агрегировать в episode + TTL-архив сырых. Порог?
2. **Верификатор бытовых фактов** — владелец подтверждает рискованное (здоровье/деньги/люди), а низкориск авто-промоут после N подтверждений? (узел-политика; пороги — решение владельца).
3. **Heat** строить вообще, или стартовать на `updated+priority` и добавить по доказанной боли (как векторы)?
4. **Ратифицировать bi-temporal** (ADR-0004)? Память — его первый реальный потребитель → аргумент ЗА.
5. **Видимость рабочей памяти между агентами** — исключение «оркестратор видит всё»? (ADR-0003).
6. **Sleeptime-триггер** — расписание / простой / порог несconsolidated-трейсов?
7. **Эмбеддинг приватной памяти** — `sensitivity:private` НЕ эмбеддить в облако (паспорт уже поддерживает исключение).
