## 1. Валидация (10 ячеек) — модель ДЕРЖИТ 9/10
Прогнали паспорт ADR-0002 против 10 намеренно разных миров: task · metric · person · plan · file-chunk · lens · agent-memory
· **session · dialogue-thread · telegram-message** (последние 3 — новая тема владельца).

- **6 ✅ / 3 ⚠️ / 1 ❌.** Открытый реестр типов + тонкий паспорт+ребро покрыли 9 миров **без единого нового
  обязательного поля** — сильное подтверждение «несущее ядро не растёт» (N-046).
- **Единственная ❌ — `telegram-message`: нужен `external_ref?`** — опциональное поле паспорта, близнец `canonical_id?`,
  но направленный НАРУЖУ (message_id / chat_id / uri файла). По нему агент действует (редактировать сообщение, привязать
  кнопку, проверить «отправлено ли») БЕЗ вскрытия payload → претендует на несущее. Это **несущая ось целого слоя
  интеграций** (Telegram, почта, календарь, файлы, импорт), а не край. → добавить `external_ref?` (опц., пусто у ~90% нод,
  тонкость ядра не страдает; R1-дополнение к ADR-0002).
- **Кнопки и редактирование — НЕ дыры:** кнопка = ребро `offers-action` → action-узел (необратимое действие проходит
  клапан §3 ✅); редактирование = мутация+трейс или supersedes-ребро (мелкий спор, не блокер).
- **2 замечания на будущее:** (1) доменное время (`occurred`) ушло в модуль верно, но для metric/event/session это
  ОСНОВНОЙ режим — контракт линзы обязан сортировать по нему так же легко, как по `created`; (2) не размывать тонкий
  паспорт под давлением контейнеров (state сессии/темы → модуль, не ядро).

## 3. ГЛАВНОЕ — механизмы агента = УЗКИЙ контракт глаголов
Прямой ответ на твой вопрос «какие механизмы должны быть доступны агенту, чтобы строить интуитивно».
**~8 глаголов ядра:** `createNode` · `link` (ребро/home/priority) · **`query`** (ЕДИНЫЙ глагол наблюдения — свернул
getContext/линзу/проекцию/поиск/группировку) · `editNode` · `setLifecycle` · `trace` + заглушены до ADR-0003:
`requestPromotion` (запрос повышения доверия — автор≠авторизатор) · `requestExternalAction` (декларация намерения; клапан
срабатывает в движке, не как глагол).
**В модули, не ядро:** `saveMessage/saveSession`, `bindAction` (кнопка к message_id) → модуль Telegram; `decompose`
(дефектовка) → типо-модуль; батч-метрики → модуль-метрика.
**Мысль-ключ:** интуитивность — НЕ богатый API, а **узкий контракт глаголов поверх control-plane-как-данных**: агент
учит ~8 глаголов ОДИН раз, а всё типо-специфичное (как заполнять, как проецировать, как собирать) **спрашивает у узлов
графа** (ТИП/ЛИНЗА/ПАТТЕРН). → **граф объясняет себя сам.**

## 4. Диалог=данные + DOGFOOD (msg 231 N-055 + msg 233 N-058/059/060)
**Тема владельца раскрылась в общий принцип: система ест свой собственный процесс.** Два первых наполнителя:
- **(a) Диалог:** session · dialogue-thread · message@human/agent · agent-thought · action. MVP работает СЕЙЧАС на
  md+frontmatter без кода: на каждый значимый обмен — message-узел + ребро к сессии + опц. ребро к узлу-решению.
- **(b) Сам проект FF (msg 233):** коммиты, задачи, планы, КОД — связанные ячейки. **«Одна ячейка в двух местах: меняешь
  одно — меняется другое»** = мультиродитель + единый источник истины (валидировано N-041/N-052). Самый честный dogfood.
- **Результаты агентов** (msg 233) сами документируются и СВЯЗЫВАЮТСЯ в тему (этот файл — пример) → выводы агента = узлы.

**Декомпозиция кода по уровням (msg 233) даёт КОНКРЕТНУЮ семантику оси `level` из ADR-0002:**
- **L1** = за что файл отвечает в целом (≈ why/what)
- **L2** = список функций / что умеет (≈ how)
- **L3** = кейсы использования ИЛИ сам код (≈ data)
→ усиливает решение «уровень = ось ЛИНЗЫ, не поле»: файл проецируется на L1 из заголовка/докстринга, L2 из сигнатур, L3
из тела — **уровень из СТРУКТУРЫ, без вскрытия**. Принцип «истина в одном месте, интерпретация в других» = канонический
узел + проекции (валидирует `canonical_id`/shared-node).

**Риски наполнителей:** приватность (sensitivity:private по умолчанию до ABAC) · дубли/объём (message-узлы vs THREAD-файлы
и code-узлы vs реальные файлы — выбрать, кто ПЕРВИЧЕН; гибрид без движка = дубли) · структурно-плоские классы (поток
сообщений/строк кода — топология бедна, опираемся на `level`+абстракцию-по-имени из ADR-0002).

## 6. Что НЕЛЬЗЯ упустить
- `external_ref?` — несущая ось слоя интеграций, решить до того, как диалог=данные станет кодом.
- Контракт линзы обязан фильтровать по доменному времени (`occurred`), не только по `created`.
- Выбрать первичность (узлы vs файлы) до dogfood, иначе дубли без движка-дедупа.
- Глаголы агента зафиксировать (шаг G) ДО скелета — иначе непонятно, что именно строить.
