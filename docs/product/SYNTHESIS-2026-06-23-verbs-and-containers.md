## 1. external_ref — ОБОБЩЁН (точно как ты просил)

**Решение совета (= твоя мысль «резолв по ключу типа, не хардкод»):**
- В паспорте — только тонкий указатель: `external_ref?: { connector: <id-узла>, key: "<строка>" }`. Два скаляра, пусто у ~90% узлов.
- Вся «конструкция, из чего состоит» — в отдельном узле **КОННЕКТОР** (control-plane): `key_schema` (что внутри key для
  этого сервиса), `capabilities` (read/edit/send/exists?), `binds_to_types`, `resolver`. → «telegram/gmail/signal/файлы» —
  это РАЗНЫЕ узлы-коннекторы; паспорт у всех одинаковый. Это и есть плагинуемость: имена не зашиты, резолвятся через узел.
- Сходится с N-062: некоторые ТИПЫ не хранят данные inline, а **объявляют, откуда читать** (тип = контракт, узел = координата).

**Каверза от критика (важно):** коннектор — это **ПЕРВЫЙ control-plane-узел, который тянется НАРУЖУ** (умеет `send`/`edit`
живого сервиса). Это категорически иное, чем ТИП/ЛИНЗА/ПАТТЕРН (все они — внутренние операции графа). Архитектор предложил
считать коннектор «подвидом ТИПА, чтобы не плодить роды» — критик возражает: его природа (побочные эффекты, рядом с
клапаном, плагин из маркетплейса) → **род коннектора решать по его БЕЗОПАСНОСТИ в ADR-0003, а не ранним «меньше родов».**
→ это связано с topic-4 (§5): коннекторы, которые ПИШУТ наружу, заблокированы тем же вопросом.

## 2. Шаг G (глаголы) — главный сдвиг: ТРИ СЛОЯ, не «8 операций»

**Твоя каверза N-066 («8 глаголов ⟷ много возможностей per skill») — ложный выбор.** Это разные СЛОИ:

```
СЛОЙ 3 — СКИЛЛ-МАНИФЕСТ (узел): какие линзы/типы/scope доступны ЭТОМУ скиллу + его процедура.
         ← здесь живёт «по-разному для каждого агента». Богатство — ТУТ.
СЛОЙ 2 — CONTROL-PLANE: ТИП·ЛИНЗА·ПАТТЕРН (+коннекторы, +триггеры). Знают КАК: валидировать, проецировать
         с глубиной, сворачивать (rollup), обходить контейнеры. Выразительность — ТУТ, растёт с доменами.
СЛОЙ 1 — ГЛАГОЛЫ: узкая стабильная поверхность движка (~8). НЕ растут с числом доменов/скиллов.
```
**Аналогия:** глаголы = система команд процессора; линзы/паттерны/типы = библиотеки (бесконечны, это данные); скилл-манифест
= программа, выбирающая, что ей доступно. Никто не добавляет команду в процессор ради новой программы — добавляют библиотеку.
**Вывод:** «узкий контракт глаголов» ОСТАЁТСЯ ВЕРНЫМ — но только если рядом есть явный слой способностей, иначе выразительность
утечёт в код скиллов и тезис «граф объясняет сам себя» рухнет. **Метод инвертировать:** идти от СЦЕНАРИЕВ (capability-first),
глаголы выводить как минимальный остаток; по умолчанию способность — НЕ глагол, пока не доказано.

**Что 8 глаголов СЕЙЧАС пропускают (вскрыл широкий проход):**
1. **Реактивность** (стоячие запросы) — см. §3. Самое крупное.
2. **Вычисление над проекцией** (тренд/свёртка/rollup/diff/cross-project) — почти все скиллы хотят ПРОИЗВОДНУЮ над узлами, а
   `query` отдаёт узлы. Решение: глубина/rollup/режим живут в ЛИНЗЕ/ПАТТЕРНЕ как ВЫБИРАЕМЫЕ узлы, не как параметры (иначе
   `query` = God-глагол). **Критик:** это правильно, но создаёт риск «God-реестра» — когда линз 200, выбрать нужную = снова
   задача поиска; реестру нужна своя навигация (это и есть твоя «карта», §4).
3. **Scope/права per skill** — прямой ответ на «по-разному для каждого». Некуда положить без **скилл-манифеста**. Критик:
   манифест сейчас — одна строка; в нём прячется «процедура-макрос» (= программа/DSL) и ABAC. → **открытая задача, не решено.**

**Критерии качества для G (ты просил ДО запуска) — 8 ворот:** покрытие 7 архетипов скиллов × 10 доменов БЕЗ роста глаголов ·
тест-не-CRUD (намерение+инвариант на каждый глагол) · O(1) глаголов от доменов · 4 слепые зоны CRUD размещены явно
(реактивность/макрос/dry-run/scope) · `query` не God-глагол · «граф объясняет сам себя» проверен на незнакомом скилле ·
клапан обязателен на любом пути во-вне · контейнер сохраняет один home.

## 3. РЕАКТИВНОСТЬ — класс, которого модель НЕ держит (самое важное из широкого прохода)

Сценарии: «каждое утро собери, что застряло, и пришли», напоминания, «уведоми, когда метрика упадёт», авто-ревью. Это **не
операция над графом — это ПОДПИСКА на граф**: «когда выполнится условие C — сделай Y». CRUD-рамка (и текущие 8 глаголов)
**структурно слепы** к этому классу.

**Спор внутри совета:** abstract сказал «это просто узел-триггер + движок-реактор, новый глагол НЕ нужен». **Критик разнёс:**
узел-триггер инертен без (1) **движка-реактора**, который вычисляет предикат по расписанию/событию; (2) правила **«кто
принципал автономного действия»** (реактор действует от чьего имени?); (3) **границы клапана для действия без синхронного
вызывающего** (клапан ADR-0002 §3 собирает «прямо задействованные узлы» у ВЫЗЫВАЮЩЕГО — а у утреннего триггера вызывающего
нет). **Все три — не спроектированы, и все три упираются в topic-4.** → нельзя записывать реактивность как «решено».

**Связанное (критик добавил):** **dry-run / симуляция** («покажи, что будет, если переставлю встречи / разложу так» — БЕЗ
записи) недооценён. Для платформы, где главная тревога — необратимость, симуляция-до-действия = естественный напарник
клапана. Поднять в первоклассный открытый вопрос (глагол-флаг? режим линзы? — открыто).

## 4. КАРТА ПЕРЕМЕННЫХ (черновик — твой прямой запрос N-065)

Ты просил «карту всех переменных, доступных в системе» — артефакт, который можно ПОСМОТРЕТЬ. Совет сначала свёл это к «это
просто линза над control-plane» — критик справедливо назвал это уходом от запроса. Вот **первый черновик карты** (классы
«переменных» × видимость). Технически карта генерится как линза над узлами control-plane, но СОДЕРЖАНИЕ — вот:

**Классы «переменных» (всё — узлы графа, видны ИИ):**
| Класс | Что это | Примеры |
|---|---|---|
| **ТИПЫ** | роды узлов (открытый реестр) | task · metric · person · plan · file · message · session · dialogue-thread · agent-memory · trace · action · container/project/folder · model-def · connector |
| **ЛИНЗЫ** | как НАБЛЮДАТЬ/проецировать | zoom-по-уровню(L1/L2/L3) · окно-времени · rollup/тренд · «что застряло» · cross-project · ABAC-disclosure |
| **ПАТТЕРНЫ** | как СОБРАТЬ подграф | плоская-агрегация(maxDepth1) · уровневая-группировка · декомпозиция · рекурсия-с-терминатором |
| **КОННЕКТОРЫ** | указатели НАРУЖУ (плагины) | telegram · gmail · gcal · файлы · … (каждый: key_schema + capabilities) |
| **ОБЛАСТИ (scope)** | где «переменная» доступна | `global` · `project:<id>` · `container:<id>` |
| **ПОЛИТИКИ** | правила доверия/доступа (= класс линзы) | promotion-policy · valve-policy · ABAC-disclosure |
| **ПРОИЗВОДНЫЕ/композиты** | скрытые входы → одно значение, переиспользуется | «итог по приватным метрикам» (derived + sensitivity:private) |
| **СКИЛЛ-МАНИФЕСТЫ** | что доступно скиллу + его процедура | daily-review · research · decompose · find-stuck |

**Видимость (твои три уровня):**
- **ПУБЛИЧНЫЕ** (на весь проект) = `scope: project|global`, видны всем принципалам проекта.
- **ЗАШИТЫЕ ВНУТРИ** = `scope: container:<id>` + `disclosure: internal` (используются внутри, не экспортируются).
- **СКРЫТЫЕ-КОМБИНИРУЕМЫЕ** = производный композит: движок сводит приватные входы в одно значение (`sensitivity: private`),
  наружу отдаётся только композит через disclosure-линзу.

**⚠️ Каверза критика (высокая важность):** «отдать композит, спрятав входы» **в общем случае НЕ безопасно** — атаки вывода
(композит + один известный вход → раскрывается другой; разности во времени; малый домен значений). Для платформы со здоровьем/
финансами это высший класс риска. → **переиспользование скрытых данных через композит — пометить КАК НЕ РЕШЁННОЕ, отложить в
ADR-0003** (нужны бюджеты раскрытия / шум / ограничения), не подавать как готовую фичу.

## 5. topic-4 — ГЛАВНЫЕ ворота (то, что ты не ответил; объясняю по-простому)

**Что значит «агент действует ВОВНЕ» простыми словами:** граф внутри — это «думать/записывать у себя». «Вовне» = агент сам
делает НЕОБРАТИМОЕ действие в реальном мире от твоего имени: **отправил сообщение в Telegram, написал письмо, создал событие
в календаре, заплатил, изменил внешний файл.** Вопрос topic-4: **может ли агент делать это САМ (автономно), или он только
ПРЕДЛАГАЕТ, а нажимаешь ты (человек подтверждает)?**

**Почему это ворота (критик показал — блокирует НЕ только реактивность):**
1. Реактивность («утром пришли») = автономное действие во-вне. ⛔
2. Коннекторы с `send/edit` (писать в Telegram/почту/календарь). ⛔ (читающие — ОК)
3. Модель клапана: кто принципал, что «задействовано», когда действие никто синхронно не звал. ⛔
4. `requestExternalAction` — весь смысл в эффекте наружу. ⛔
5. Скилл-макрос, заканчивающийся отправкой. ⛔ на шаге send
6. Маркетплейс/сторонние агенты (зачем вообще был first-party-гейт). ⛔

**Вывод:** **ВСЯ «пишущая-наружу» половина платформы ждёт твоего ответа на topic-4. ЧИТАЮЩАЯ половина (query/линзы/паттерны,
читающие коннекторы, сама карта) — НЕ заблокирована, её можно проектировать сейчас.** Проектировать пишущую половину до
ответа = риск переделки.

## 6. Честный итог (где модель сильна / где слаба)

**Сильно (подтверждено):** контейнер = узел + home-рёбра (мультиродитель = обычные рёбра) — почти всё из N-068 УЖЕ выразимо,
новый механизм НЕ нужен; «контейнер шарит вниз» = каскад дефолт-линзы/scope по home-спине (НЕ наследование типа payload —
документ внутри проекта остаётся документом); «два режима» = два ПАТТЕРН-узла (плоский / уровневый). external_ref обобщён чисто.

**Слабо / не решено (честно):**
- **Реактивность не держится** без неспроектированного реактора + правила принципала + клапана-для-автономных. (CRITICAL)
- **Тень имён типов при мультиродителе** (узел в двух контейнерах, оба определяют `budget` по-разному — кто победит?):
  «nearest-first» архитектора НЕ отвечает на DAG (только на дерево). Это вопрос КОРРЕКТНОСТИ (детерминированная типизация), не
  стиля. (CRITICAL)
- **Приватность композитов** — атаки вывода (выше). (CRITICAL)
- **Скилл-манифест** — несущая деталь ответа на N-066, но пока одна строка (прячет DSL-макрос + ABAC). (CONCERN)
- **«Тонкий паспорт» ≠ «тонкая система»:** изящество держится на том, что 3 CRITICAL отложены в «движок» + ADR-0003; ADR-0003
  перегружен (доверие/scope/ABAC/раскрытие/приватность/гейты). Тонкость УСЛОВНА на успехе ADR-0003. (CONCERN)
