## Зачем этапы (не просто P0/P1/P2/P3)

Приоритет-стек ранжирует по одному числу; этапы группируют по **что зависит от чего и что открывает
следующее**, чтобы волны направления N-G (Волна B → C → …) знали, что брать пачкой. Три оси, по которым
собраны этапы: (1) активный блокер vs дремлющий вопрос, (2) кластер-примитив kernel (определяет «зелёное»
для всех граней сразу) vs частная механика одной грани (durable-store/acts-as-git), (3) явная пауза
владельца (OQ-1) не снимается этапом, просто ждёт своего места без блокировки соседей.

## Схема связей (лёгкая, id-based)

Существующие типы рёбер уже используются текстом в INDEX/файлах (`tension-with`, «блокирует», «закрывает»,
«зависит от») — здесь они формализованы как словарь, не новый механизм:

- **`answers`** — decision → question (когда вопрос закрывается, decision-файл ссылается `answers: [id]`,
  question переходит в `status: closed`, файл НЕ удаляется — закон 9 doc-tree.md).
- **`blocks`** — question → invariant/цель («KQ-4 blocks I-7»). Уже пишется прозой в таблицах STATE/приоритет-стека;
  формализуется как поле, когда вопрос переезжает в постоянный дом (не здесь, не сейчас).
- **`tension-with`** — question ↔ question, симметрично, НЕ значит «сливать» (закон в самих question-файлах
  уже соблюдён: KQ-8↔OQ-7, Q-branch↔OQ-1 явно помечены и НЕ объединены).
- **`refines`** — analysis/synthesis → предыдущий analysis/synthesis той же темы (напр. Волна B «модель
  зелёного» будет `refines` → `analyses/00-COVERAGE-MAP.synthesis.md`, не переписывать поверх).
- **`raises`** — synthesis/decision → question (новый вопрос родился из синтеза; так уже родились OQ-4≡HANDOFF-R4≡SYNTHESIS-R4).

Схема одной фразой: **STAGED-CONCEPT группирует id по этапам → question-файлы несут содержание и уже
проставленные tension-with → закрытие пишет decision с `answers:` на question → синтезы Волны B `refine`
карту покрытия → всё это триггерит ОДНУ строку-обновление в STATE (см. homing-plan §4), не копию контента.**
