# План домов + перелинковки — направление N-G

> **ОПИСАТЕЛЬНО.** По doc-tree.md: «на диск — только по явному "строй"». Ниже — план размещения/переездов
> с планом отката, НЕ выполнение (никакого `git mv`). Фаза направления N-G = Волна B (корень), переезды
> актуальны с Волны C (поэтапный разбор граней).

## 1. Вход/вопрос

Запрос владельца: «концепты и синтезы перелинковываются; всё должно жить где-то в проекте, минимум —
состояние должно о них знать». Три под-вопроса: (а) что остаётся в `_inbox`-боксе постоянно/временно,
(б) что переезжает в канон (`core/00-kernel/`, `core/01-brain/`) и когда, (в) как именно STATE фиксирует
знание об этом без дублирования контента.

## 2. Варианты/призмы

**Вариант А — весь бокс переезжает целиком после Волны B.** Просто, но нарушает закон 2 (один дом на
тему) — вопросы KQ-* УЖЕ имеют исходный дом (`core/00-kernel/open-questions.md`), а OQ-* — исходный дом
(`docs/_inbox/2026-08-04-durable-store-substrate/questions/OQ-open-decisions.question.md`). Бокс
picture-coverage — это ХАРВЕСТ-копия для кросс-темного приоритет-скоринга, не новый дом. Переезд «всем
кустом» задвоил бы контент.

**Вариант Б — бокс остаётся местом ранжирования/этапной раскладки НАВСЕГДА, вопросы никуда не едут.**
Плохо: бокс `_inbox` по doc-tree — стейджинг, не постоянный дом; DIRECTION.md сам обещает «созревшее →
переезжает». Оставить навсегда = нарушить обещание чартера направления.

**Вариант В (выбран) — расщепление по типу артефакта, каждый едет в СВОЙ постоянный дом, когда СОЗРЕВАЕТ,
бокс остаётся тонким индексом-скорером.** Соответствует закону «тип решает дом» (закон 5) — вопрос,
идея, анализ, решение едут в разные места, а не одним комом.

## 3. Разбор по критериям (что куда, по типу + этапу)

### 3.1 Вопросы (`questions/*.question.md`, 14 шт., см. STAGED-CONCEPT)

- **KQ-1, KQ-2, KQ-4, KQ-8, KQ-9, KQ-11 (Э1-Э2, kernel-кластер).** Исходный/итоговый дом уже существует:
  `docs/02-project/core/00-kernel/open-questions.md` (откуда они харвестились) + при закрытии —
  `docs/02-project/core/00-kernel/decisions/`. **Бокс-копии в `questions/kq-*.question.md` — временный
  срез для приоритет-скоринга.** План: при закрытии каждого KQ — decision пишется В `core/00-kernel/decisions/`
  (не в боксе), исходный `open-questions.md` получает статус-пометку у этого пункта (не удаляется —
  закон 9), а бокс-копия помечается `status: closed` + `superseded-by: <путь decision>` (редирект-заглушка,
  закон 9), не удаляется физически до конца направления N-G (для трассировки этапной работы).
- **Q-branch, OQ-1..OQ-7 (Э3, durable-store/acts-as-git).** Исходный дом — комбинированный файл
  `docs/_inbox/2026-08-04-durable-store-substrate/questions/OQ-open-decisions.question.md` (тот же бокс
  ещё не закрыт/не промотирован сам). План: при закрытии каждого OQ — decision едет туда же, куда
  промотируется сама durable-store-substrate тема (кандидат: `core/00-kernel/durable-storeport.design.md`
  получает секцию «решения», т.к. design-note уже `status: active`); бокс-копия в picture-coverage —
  та же редирект-логика, что для KQ.
- **⚠️ Пока НЕ переезжать ни один вопрос физически.** Причина: Волна B (модель «условий зелёного») может
  переоткрыть формулировку части вопросов (DIRECTION.md сторона 2 — «пересмотр путей»); переезжать до
  того, как корень обдуман, — риск переезда дважды.

### 3.2 Идеи (`ideas/*.idea.md`, 4 шт.)

Живут в `ideas/` до кристаллизации (закон типа `idea`: «созревает → меняет тип»). `policy-scope-project-vs-universal`
ближе всего к готовности (P1, C=2, прецедент есть) — при кристаллизации станет `.decision.md` и переедет
в дом ADR-0004 (`core/00-kernel/decisions/` или где сидит ADR-0004 — сверить при исполнении).
`folder-in-folder-restructuring` — при ответе владельца («дерево или граф») превращается в `.decision.md`
там же. Остальные две (`client-n8n-toolkit`, `self-upgrade-under-valve`) остаются сырыми (P2/P3) — не
трогать.

### 3.3 Анализы/синтезы Волны B (модель «условий зелёного» + пересмотр путей + этот STAGED-CONCEPT)

- **Пока живут в боксе** (`analyses/`, `questions/STAGED-CONCEPT.md`) — это рабочая копия текущей волны.
- **При ратификации Волны B** (гейт критика/co-orchestrator пройден, владелец подтвердил модель) —
  модель «условий зелёного» переезжает в `docs/02-project/core/01-brain/analyses/2026-08-0X-green-conditions-model/`
  (следует конвенции уже существующих дат-снапшотов: `2026-07-12-architecture-synthesis/`,
  `2026-07-31-wider-multilevel-and-self-augmenting/`). Список «подозрительных путей» (сторона 2) с

  путь, если решение материально, иначе строка в существующем `decisions.INDEX.md`).
- **`analyses/00-COVERAGE-MAP.synthesis.md`** остаётся ЖИТЬ в боксе как snapshot-carrier до конца

  дата-версия карты со-размещается рядом, потом синтез.

## 4. Как STATE узнаёт (без дублирования)

Уже сделано корректно (проверено чтением): `state-03/state.md` пункт N-A7 содержит ОДНУ строку-указатель
на `docs/_inbox/2026-08-04-picture-coverage/DIRECTION.md` + карту покрытия — это правильный паттерн
(закон 8, навигатор=вид). **Что добавить дальше, тоже ОДНОЙ строкой каждое, не контентом:**

1. Когда `STAGED-CONCEPT.md` появляется (этот ход) — `state-03/state.md` под N-G дописывает:
   «`+ этапный концепт вопросов: questions/STAGED-CONCEPT.md (Э1 KQ-4+OQ-4 · Э2 kernel-кластер · Э3 durable-грани)`».
2. Когда Волна B закрывается (модель зелёного ратифицирована) — **`STATE.md` (корневой)** получает новый
   `RESUME`-блок (как уже принято конвенцией файла) с указателем на новый дом в `core/01-brain/analyses/2026-08-0X-...`
   + одну строку «Волна B закрыта, next = Волна C по приоритету Э1→Э2→Э3».
3. Когда любой вопрос Э1/Э2/Э3 закрывается decision-ом — **НЕ трогать STATE построчно на каждый вопрос**
   (14 вопросов = 14 правок = шум). Батчить: обновление STATE делается РАЗ на этап (закрыли весь Э1 →
   одна строка; закрыли весь Э2 → одна строка), либо на гейте Э4.
4. `questions/INDEX.md` бокса (уже существует) — обновляется по мере закрытия (статус-колонка), это его
   прямая роль (навигатор контейнера), не конфликтует с STATE-строкой.

## 6. Нарушения doc-discipline, уже видимые в боксе (флаг, не исправление)

1. **Дублирующийся дом для OQ-1..OQ-7 (закон 2 «один дом на тему»).** Полный текст этих 7 вопросов
   существует ДВАЖДЫ: как единый файл `docs/_inbox/2026-08-04-durable-store-substrate/questions/OQ-open-decisions.question.md`
   И как 7 отдельных id-файлов в этом боксе (`questions/oq-*.question.md`). Ни один явно не помечен
   `superseded-by`/`derived-from` в сторону другого — риск, что оба начнут независимо мутировать
   (уже есть прецедент: этот бокс сам знает о дедупе OQ-4 из 3 источников, но не связал его с оригиналом
   durable-store-box явной ссылкой `derived-from`). Рекомендация: пометить box-копии picture-coverage
   `derived-from: docs/_inbox/2026-08-04-durable-store-substrate/questions/OQ-open-decisions.question.md`
   (не переезд, просто явная стрелка правды).
2. **`decisions/priority-stack.decision.md` — суффикс не по содержанию (закон 5).** Файл несёт
   `.decision.md`, но собственный текст говорит: «это ТОЛЬКО ранжирование, ни одна развилка не решена» +
   `status: draft`. Ранжирующая таблица с методом (V×G×R×Rdy/C) по форме — анализ (сравнение по критериям),
   не решение (выбор одной альтернативы). Сигнал на перенос в `analyses/` под суффиксом `.analysis.md`
   ИЛИ переименование по факту — когда стек РЕАЛЬНО фиксирует решение «эту волну берём» (топ-4 P0/P1 уже
   похожи на решение), тогда `.decision.md` оправдан для ЭТОЙ части, а полная таблица 18 пунктов — анализ.
   Не исправляю сейчас (вне границ хода), просто флагую для следующего прохода `doc-discipline`.
