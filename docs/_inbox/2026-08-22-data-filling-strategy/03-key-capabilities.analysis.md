# 03 · Ключевые приколы (измеримые)

Пять формулировок «вот ЭТО система умеет благодаря памяти», привязанных к типам (не к промпту/LLM-догадке).

## 1. Единая точка сборки человека (досье без пересчёта) — для АГЕНТА
Once `mentions`-рёбра существуют (см. `02-ignition-and-connections.analysis.md`), ЛЮБОЙ агент, спрашивающий
«что я знаю про Женю», получает мульти-хоп трейверс (`mentions`→Женя, inverse) по ВСЕМ дням БЕЗ повторного
чтения сырого текста. Это буквально паттерн `observation/customer-lens.ts` (rentacar), перенесённый на
личных референтов. **Измеримо:** после N засеянных дней один вызов линзы возвращает полную кросс-дневную
историю Женя за <1 чтение, вместо того чтобы агент сегодня grep'ал/передумывал это каждый раз заново.

## 2. «Сегодня без пересчёта» (day-mirror-преемник) — для СИСТЕМЫ
Фиксированный вид линзы (day-mirror-подобный) рендерит «что живо прямо сейчас по всем проектам»
непосредственно из лога, без рассуждения агента — система понимает БЕЗ вызова LLM, чисто по ТИПУ (акт
помечен `domain_event` + известный набор предикатов — этого достаточно view-compiler'у, чтобы спроецировать
его). Это прямой ответ на «система быстро понимает агента/владельца через определённые ТИПЫ».

## 3. Просрочки/напоминания по типу, не по промпту (rentacar Tier-1, обобщаемый)
`deadline`/`reminder` node-type + поле даты + одна линза показывают «что горит» чисто структурно, без
LLM-суждения — уже доказуемо СЕГОДНЯ на реальных полях rentacar (`License Exp`/`Insurance Exp`/`Follow-up`,
`docs/03-projects/ga-rentacar/analyses/03-capability-potential.analysis.md:19-24`) даже на фикстурном
масштабе, и идентично переносимо на личные дедлайны владельца при той же форме. Это конкретное воплощение
«определённой структуры — задачи, напоминания», которую владелец просил показать первой.

## 4. «Он это уже знал» (тождество во времени, Ц2/Ц6) — для АГЕНТА
Постоянство `id`/`source_ref` узла означает, что агент, действующий в день 10 про «rentacar», автоматически
наследует всё, что было утверждено про этот узел в дни 1-9 (рёбра копятся на ОДНОМ узле) — не нужно
объяснять контекст заново каждую сессию. Это прямое лекарство от уже диагностированной боли проекта
(docs:code 14.5:1, ре-вывод контекста каждый раз) — не абстрактная польза, а измеримое сокращение
«объясни мне ситуацию заново».

## 5. Один долг, три источника (агрегация через типы узлов) — мост к §04
Rentacar Tier-1 «`Orders.Remaining` + `Unpaid.Remaining` + `Fines.Unpaid` → кто и сколько должен» — это
шаблон дешёвой READ-линзы (Ц1: получить сводную грань, не вскрывая каждое тело), сворачивающей несколько
разных типов актов/рёбер в одно число. Тот же шаблон прямо переиспользуем для запроса владельца из п.4
(«ресурсы одной агент-системы, per-project vs shared») — «сколько внимания/бюджета должно проекту X» имеет
ТУ ЖЕ форму, что «сколько должен клиент X». См. `04-agent-system-resources.analysis.md`.

## Что демонстрируем ПЕРВЫМ (порядок, не список)
№2 и №3 достижимы почти немедленно (день-лог уже есть; rentacar Tier-1 уже на фикстурах) и не требуют
решения ни одной открытой развилки (D1-D5). №1 и №4 требуют апгрейда day-log на `domain_event`+рёбра
(§02) — это следующий шаг после переписи загорания. №5 сознательно ПОСЛЕДНИЙ: он опирается на open forks
D1/D2/D5 (см. `04-agent-system-resources.analysis.md`), фронтранить его сейчас — забегание перед решением
владельца.
