# 2. Тех-требования к нашей памяти — вытекающие из модели Движа

Каждая позиция: требование → почему (со ссылкой на раздел 1) → как выглядело бы на FF-примитивах
(Act/Edge/EnvelopeNode, `packages/engine/src/core/types.ts`).

## R1 — Типы узлов для единиц работы агента (задача/тик/находка/решение)
Движ различает: `loop-run` (сам ход), находка-ждёт-владельца, решение (approved/rejected/errored),
паттерн, хэндофф (§1.3–1.5). Наша память должна уметь заводить `EnvelopeNode.type` для этих же
сущностей: `agent-task`, `agent-finding`, `approval-decision`, `pattern`, `handoff` — не как разные
таблицы (как у Движа сегодня, §1.5 «четыре тетради»), а как РАЗНЫЕ ТИПЫ ОДНОГО узла + `domain_event`.
Пример: `{ actKind: 'domain_event', provenance: { source_ref: 'agent-task:2026-08-22-fix-bug' },
payload: { type: 'agent-task', status: 'pending-owner' } }`.

## R2 — Рёбра «агент → работает-над / породил / выполняет»
Движ моделирует родительство и исполнение как рёбра-заготовки (`parent-ref`, `definition-ref`,
§1.5 08-graph-structure) и уже РАБОТАЕТ через inverse-edge запрос «кто выполнил это действие»
(`actionsByAgent`, см. файл 3). Требование: типизированные предикаты `performs`, `parent-of`,
`hands-off-to`, `pattern-applies-to` в predicate-registry с явной cardinality (`one`/`many`) —
FF уже умеет это как ДАННЫЕ (`predicates.ts`), нужно только НАПОЛНИТЬ реестр этими предикатами, когда
появится реальный агент-write-путь.

## R3 — Хранение памяти агента / трасс как side-journal, не как граф
Движ (в замысле ADR-0005/ADR-0009 и мех.02) явно разводит «то, что проецируется в граф-знание»
(domain_event) от «то, что просто журналируется рядом» (расход токенов, находки, решения-аудит).
Требование: наша память ДОЛЖНА уметь писать `agent_trace`/`system_telemetry`/`observation` акты,
которые НИКОГДА не проецируются в узел, но лежат в том же append-only логе рядом с `domain_event`.
Пример: агент делает 5 внутренних шагов рассуждения → 5 `agent_trace` актов с одним `provenance`
(ссылка на родительский `agent-task`), граф не видит эти 5 записей как узлы/рёбра.

## R4 — Запрос «что делать дальше / что ждёт меня» (approval-queue как проекция)
Мех.04 (§1.5): каждая находка помечена «решено само» / «ждёт владельца»; это должно уметь собираться в
ОДИН экран очереди БЕЗ отдельного хранилища — данные уже помечены. Требование: read-лекса
(`view` типа `visible-to`/новый `pending-approval`) над узлами `agent-finding`/`agent-task`, фильтрующая
по полю статуса в `body`, а не отдельная таблица очереди.

## R5 — Идемпотентность / дедуп повторного тика
Мех.02 (§1.5): каждый тик лупа — свежий независимый запуск; повтор реального действия (файл, команда)
после падения процесса — открытая дыра у Движа («барьер от повтора» — TODO). Требование к FF: любой
`domain_event` от агента ДОЛЖЕН нести `provenance.source_ref` + `snapshotHash` — так повторный тик с
теми же входными данными схлопывается в no-op вместо дублирования узла/ребра.

## R6 — Гвард глубины/итераций (loop-guard) как данные, не хардкод
Мех.08 требует гвард глубины на дерево-лупов (§1.5, «предохранители ПЕРЕД автономностью»). Требование:
лимит (`max_iterations`, `on_exceed`) должен жить в узле-политике (`policy_ref`), а не в коде движка —
т.е. ТА ЖЕ форма, что уже используется у нас для `visible-to`/access policy.

## R7 — Провенанс исполнителя (кто реально стоит за актом)
Мех.05/ADR-0010-параллель у Движа: нужен способ отличить «агент решил сам» от «владелец нажал кнопку»
от «пришло от чужого канала». Требование: акт агента должен уметь нести уровень доверия по двум
независимым осям — кто реально действовал (`whoActed`) и от чьего имени (`underWhoseAuthority`).

## R8 — Осознанность контекста (topic/conversation ↔ состояние/лог памяти)
ADR-0004 Движа (§1.6): дешёвая связь тема↔стейт↔лог как ОДНО nullable JSON-поле, растущее без миграций.
Требование: у FF нет аналога «топика диалога» вообще (граф — про жизнь владельца, не про сессии
агентов) — если агенты начнут работать МНОГО сессий над ОДНОЙ темой, потребуется узел/поле
`awareness-ref`, связывающее «эта работа агента» ↔ «эта область графа памяти».

## R9 — Паттерн (поведение) как декларативные данные, читаемые агентом
ADR-0009 (§1.4): паттерн = `TypeUnit` с `fieldSchema={name, trigger, steps[], guards[], exit}`.
Требование к FF (по аналогии, не факт): если FF когда-то захочет, чтобы агент сам читал «как вести себя
в этой ситуации» из графа (а не из хардкода промпта), нужен узел-тип `pattern` с такой же формой —
FF уже имеет прецедент «поведение как данные» в `predicates.ts` (cardinality-as-data), это тот же принцип
на уровень выше.

## R10 — Handoff между сессиями агента как узел, а не только markdown
ADR-0009 переводит `handoff.concept.json` в read-side проекцию Unit (§1.4). FF сегодня делает хэндоффы
ТОЛЬКО файлами (`docs/_log/.../HANDOFF.md`, `recursive-orchestration-method.md`). Требование (кандидат,
не срочный): если агент-система FF вырастет, хэндофф между волнами/сессиями стоит проецировать как
`domain_event` с `source_ref = handoff:<session-id>` — тогда «что происходило между сессиями» становится
частью графа, а не только текстом в git.
