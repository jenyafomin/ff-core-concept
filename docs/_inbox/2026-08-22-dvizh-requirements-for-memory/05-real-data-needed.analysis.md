# 5. Где нужны РЕАЛЬНЫЕ данные, чтобы прогнать эти паттерны

Честная рамка (согласуется с проектной памятью, `MEMORY.md` §START HERE 2026-08-16): у FF **0 реальных
эпизодов** данных за 2 месяца дизайна, docs:code ≈14.5:1. Всё, что написано в файлах 1-4 — гипотеза ПО
АНАЛОГИИ с системой Движа, которая сама во многом ещё замысел (мех.05-08 «замысел, не код»), плюс один
частичный прецедент внутри FF (файл 3, находка R1/R2/R6). Ниже — что именно нельзя решить на бумаге.

## Что уже есть как частичный прецедент (не с нуля)
`docs/02-project/core/02-agents/examples/01-agent-manager/_generated-examples/README-depth2.md:28-33` —
токены `builder-A` (`116 157`), `thinker-B` (`65 378`), `explorer-A/B/C` — РЕАЛЬНЫЕ замеры одной прошлой
сессии (2026-07-24). Но: (а) это `measured` числа СВЕРХУ вручную собранной иерархии (`reconstructed`
структура) — не живой лог агента, пишущего акты по ходу работы; (б) один агент-персонаж (`loop-worker`)
целиком выдуман, чтобы у стопкрана было что ловить; (в) корпус — 64-65 узлов, честно помечен «не
нагрузка» (README-depth2.md:106, дыра Q-7). Это доказывает МЕХАНИЗМ (loop-guard, subtree≠direct), не
доказывает, что ЭТА ФОРМА узла/ребра переживёт реальный, не сконструированный агентный процесс.

## Что нужно реально прогнать, чего нет вообще
1. **Хотя бы один живой агент-write-путь.** Ни один файл в `packages/engine/src` не СОЗДАЁТ узел
   `type: 'loop-run'`/`agent-task` — есть только чтение (`loopGuard`, `actionsByAgent`) над данными,
   положенными руками (тест или narrative-фикстура). Нужно: реальный агентский процесс (например, эта
   же recursive-orchestration-сессия — волна из 3-6 агентов), пишущий `domain_event`-акты по ходу
   работы через `packages/engine`, а не только markdown в `docs/_log/`. Только тогда видно, держится ли
   форма `parent-ref/depth/definition-ref` (§1.5, П2) при РЕАЛЬНОЙ, не сконструированной вложенности.
2. **Реальные эпизоды approval-очереди («решено само» / «ждёт владельца», R4).** У Движа это уже
   боевой паттерн (`decision_journal`, кнопки в Telegram). У FF нет ни одного зафиксированного случая
   «агент написал акт, который должен был подождать подтверждения владельца» — без него нельзя решить,
   должен ли approval-статус жить как поле в `body`, как отдельное ребро на `pending-approval`-узел, или
   как отдельный `ActKind`. Формы из файла 2 (R4) — гипотезы, не выбор.
3. **Реальный `agent_trace`.** `ACT_KINDS` включает `agent_trace` (VERIFIED, файл 3), но единственное
   его употребление — синтетическая строка в `projection.test.ts:130`. Нет ни одного реального
   агентского рассуждения, записанного как `agent_trace`, — неизвестно, нужна ли ему структура вообще,
   или это просто текстовый blob по `payloadRef`.
4. **Реальная многосессийная работа над ОДНОЙ темой (R8, topic-awareness).** Сегодня FF-агенты работают
   через markdown-хендоффы (`docs/_log/.../HANDOFF.md`) — ни разу не пробовали связать «эта сессия
   агента» с «этой областью графа памяти» через данные, а не через текст. Без такой попытки форма
   `awareness?{stateRef, logRef}` из ADR-0004 Движа — недоказанное заимствование.
5. **Реальный конфликт двух агентов на одном узле** — чтобы понять, нужен ли FF свой аналог CAS
   (`expectedHeadEventId`, ADR-0005 Движа) поверх уже существующего `foldEdges`/predicate-cardinality, или
   текущей модели (append-only акты, freshest-wins в проекции) достаточно без явного optimistic-lock.

## Рекомендация (не решение — граница вопроса ясна, ответ владельца не запрашивается)
Прежде чем ратифицировать любое из R1-R10 (файл 2) как ADR/инвариант, нужен ХОТЯ БЫ ОДИН реальный
агент-прогон через `packages/engine` (не через narrative-фикстуру, не через markdown-хендофф) —
симметрично тому, что владелец уже решил для day-graph/памяти-жизни («перепись загорания на 3-5
реальных эпизодах» вместо гадания, `MEMORY.md` START HERE). Естественный кандидат на такой прогон —
сама recursive-orchestration-волна (текущий метод сессии, `.claude/rules/recursive-orchestration-method.md`)
— она УЖЕ производит ровно те объекты (задачи волны, приёмка помощника, критик), которые R1/R2/R4
описывают гипотетически.
