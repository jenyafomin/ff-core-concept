# 1. Что Движ строит — модель агента/узла/паттерна/лупа

Источник — `/Users/mac16/Documents/IT/Apps/TOOLS/agents-manager` (проект «Движ», gateway Telegram→Claude
Code). Ниже — только то, что релевантно вопросу «как система моделирует агента и его работу», с опорой
на конкретные файлы.

## 1.1 Слой сущностей шлюза (operational, TypeORM/SQLite)
`README.md:41-44` — уже сегодня в бою: `sessions, messages, jobs, bots, agents, agent_bindings, topics`
(+ `decision_journal`, `process_lease` из ADR-0005 контекста). Это НЕ модель памяти-знания, это
операционные агрегаты раннера (кто с кем говорит, какой бот/роль, какая сессия). Явно разведено с
memory-слоем (ADR-0005: «узкие контракты 10 репо — операционные агрегаты, не owner-facing знание»).

## 1.2 Runner = агент как исполнитель (ADR-0001-sdk-runner.md)
Агент моделируется как исполнитель за портом `IAgentRunner`, с in-process `query()` (Claude Agent SDK),
approval-мостом `canUseTool` НА КАЖДЫЙ тул-колл (`ADR-0001-sdk-runner.md:42-53`):
- read-only тулы → allow молча;
- мутации → `IToolApprovalGate.requestTool()` → владельцу 3 кнопки (Раз/Всегда/Отклонить);
- «Всегда» пишется как SDK-нативное правило (`updatedPermissions`, `addRules`), без своего хранилища.

Это модель «агент = процесс с политикой доступа к действиям», не «агент = узел в графе знания».

## 1.3 Единый стор Unit/Event (ADR-0005, draft) — алфавит для памяти
`ADR-0005-one-store-unit-type-event-schema.md:37-114`. Три примитива:
- **Unit** — типизированная адресуемая версионируемая запись (`namespace:slug`, `typeRef@typeVersion`,
  `headEventId`); текущая форма = fold её Events.
- **Event/Commit** — append-only история: `{eventId, unitId, typeRef@version, op, author, approvalRef?,
  parentEventId, payload, ts}`. Перезапись = новый Event, не мутация.
- **Ref/Lens** (порт, не спроектирован в этом ADR) — именованный скоуп-предикат над Units.

Concurrency — optimistic CAS на `expectedHeadEventId` (мотив: реальная потеря данных от careless
concurrent writes, `ADR-0005:105-115`). Хранилище — Postgres с первого дня (решение владельца Движа,
`ADR-0005:118-140`), доступ ТОЛЬКО через порт (`IUnitStore/IEventLog/ITypeRegistry`).

## 1.4 Паттерн-как-данные (ADR-0009, draft) — как растёт поведение
`ADR-0009-pattern-as-data-handoff-foundation.md:15-42`. Ключевой инсайт: «разговор»/«задача» — не жёсткие
типы, а ПАТТЕРНЫ (поведение) над одним алфавитом Unit·Event·Ref. Паттерн должен быть ДАННЫМИ:
- `TypeUnit system:pattern@1` — `fieldSchema = {name, trigger, steps[], guards[], exit}`;
- `TypeUnit system:handoff@1` — экземпляр = Unit; Events = переходы `packing→written→spawning→received→
  questioning→resumed`; `fold(Events)` = текущее состояние;
- ребро `hands-off` (преемственность сессий), ОТДЕЛЬНО от `parentSessionId` (не смешивать `/fork` с
  хэндоффом).

Осознанно НЕ строят generic-движок паттернов сейчас («правило двух» — не обобщать по одному прецеденту);
хэндофф исполняется частным интерпретатором поверх декларативной формы (`ADR-0009:36-51`).

## 1.5 Граф-луп: агент как узел надзираемого дерева (state-07 + mechanics/)
Несущая абстракция (`mechanics/README.md:48-52`): **надзираемое дерево журналируемых ходов с бюджетом**.
Восемь механик, из них релевантные модели агента:
- **01 шаговый луп** — каждый тик = свежий независимый запуск (не живущий процесс); непрерывность несёт
  ТОЛЬКО строка состояния в БД (`02-memory-durability/README.md:20-25, 101-107`).
- **02 память** — сегодня ЧЕТЫРЕ разные тетради (состояние лупа / расход токенов / находки-ждут-владельца
  / журнал решений); целевое — ОДИН Event-журнал с меткой рода записи (`02-memory-durability/README.md:
  46-66`).
- **04 две дорожки** — сортировка не «насколько страшно», а «можно ли отменить»: обратимое → автопилот
  (авто-запись решения для аудита), необратимое/неясное → очередь владельцу, fail-closed на
  неопределённости (`04-two-lanes-queue/README.md:26-29, 87-92`). Каждая находка агента — отдельная
  запись с меткой «решено само» / «ждёт владельца» (`04-two-lanes-queue/README.md:57-59, 113-116`).
- **08 граф-структура** — луп как ДЕРЕВО, не линия: узел несёт `parent-ref` (кто породил), `depth`
  (гвард рекурсии), `definition-ref` (портируемое «что делать», отдельно от «что произошло» — один
  агент, много инстансов). Вниз идёт СЖАТЫЙ засев (цель + нужные факты), вверх — СЖАТАЯ выжимка
  (handoff-итог), не сырая история (`08-graph-structure/README.md:100-137`). Сегодня это ТОЛЬКО
  забронированные поля в БД — логика их не читает, граф пока линия (`08-graph-structure/README.md:34-67`).
- **06 надзиратель / 05 страж** — read-only наблюдатель флота (частично), отдельный «дотошный» read-only
  агент-страж для необратимых действий (замысел, не код).

## 1.6 Topic-awareness (ADR-0004-topic-awareness-model.md) — связь тема↔состояние↔лог
Одно nullable JSON-поле `awareness?: {stateRef?, logRef?, planRef?, handoffAt?}` на `ITopic`, без новой
таблицы, растёт БЕЗ миграций (`ADR-0004-topic-awareness-model.md:39-51`). Слой-1 (push в system prompt,
дёшево) vs Слой-2 (on-demand pull для координатора агентов, DEFERRED). Явное требование владельца:
«дешёвый срез — честное подмножество большой картины, не выкидыш» (`:34-36`).

## Итог раздела
Движ моделирует агента в ТРЁХ разных слоях одновременно, каждый на своей стадии зрелости: (а) операционный
runner+approval-gate — в бою; (б) Unit/Event/TypeUnit как единый стор памяти — черновик ADR, 0% в коде;
(в) граф-луп как дерево ходов с провенансом/бюджетом — частично в коде (шаговый луп, память по тику,
токен-счётчик), в основном замысел (граф, страж, надзиратель, периметр ценностей). Наш вопрос («что
наша память должна уметь») смотрит в основном на (б)+(в) — это то, что ближе к «субстрату для агентов»,
а не к транспорту Telegram.
