# 4. Якорные паттерны — что берём как форму, «затачиваем под себя»

Отобраны по критерию: конкретный, воспроизводимый, у Движа либо УЖЕ в бою, либо доказан на данных (не
чистая декларация в ADR).

## П1 — Единый Event-журнал вместо N разных тетрадей (мех.02, §1.5)
Движ сегодня платит цену за то, что «состояние лупа / расход токенов / находки-ждут-владельца / журнал
решений» — четыре разные таблицы; целевое состояние — один журнал событий с меткой рода записи
(`02-memory-durability/README.md:46-66`). **У FF это УЖЕ архитектурный принцип** (`ActKind` enum +
`isProjectable` фильтр, VERIFIED в файле 3, R3) — но пока используется только для проекции графа
владельца. Якорь: когда появится первый реальный агент-write-путь (см. файл 5), НЕ заводить отдельную
таблицу «находки агента» / «токен-счётчик» — класть их актами `agent_trace`/`system_telemetry` в ТОТ ЖЕ
append-only лог, с `provenance.source_ref`, указывающим на родительскую задачу.

## П2 — Loop-guard как политика-узел, не хардкод (мех.08 + собственный прецедент)
Форма У ДВИЖА пока замысел; у FF — уже РАБОТАЮЩИЙ код (`view-compiler.ts:176-192`) И реальный прогон
на частично-измеренных данных (`docs/02-project/core/02-agents/examples/01-agent-manager/
_generated-examples/README-depth2.md:67-87`, «loop-guard tripped at iteration 6»). Якорь: НЕ изобретать
заново форму гварда — она уже спроектирована и один раз доказана. Следующий шаг — не дизайн, а
ПОДКЛЮЧЕНИЕ: дать реальному циклу агента (когда он появится) писать `body.iterations`/`body.loop_backs`
на лету, а не как фикстуру.

## П3 — Две дорожки (обратимо/автопилот vs необратимо/спроси), fail-closed на неопределённости (мех.04)
Движ развёл ось РЕСУРС (ползунок) от оси ОПАСНОСТЬ (стена) — «дёшево-катастрофичное не должно проходить
под бюджетом» (`04-two-lanes-queue/README.md:26-33, 86-92`). У FF ЕСТЬ структурный аналог стены —
`Admission`/admission-gate (`types.ts:351`, fail-closed на inline PII) — но это про PII, не про
обратимость действий агента вообще. Якорь: если FF заведёт агента, который пишет в граф автономно,
взять ГОТОВУЮ формулу Движа «неясно = необратимо = спроси» как ДЕФОЛТНУЮ политику, а не изобретать
свою классификацию с нуля — она уже прошла адверсариал у Движа (критик, аудит A1, `04-two-lanes-queue/
README.md:36-41`).

## П4 — Provenance + идемпотентность (source_ref + snapshotHash) — здесь FF ДАЁТ, а не берёт
`Provenance{source_ref, snapshotHash}` (`types.ts:256-260`) уже решает ровно ту задачу, которую Движ
только формулирует как открытую («барьер от повтора», мех.02, §1.5, TODO). Якорь наоборот: если/когда
FF-агент начнёт писать в собственный граф памяти, он уже наследует эту защиту БЕСПЛАТНО — не нужно
переизобретать CAS/дедуп, которые у Движа всё ещё в разработке (ADR-0005 optimistic CAS, draft).

## П5 — Topic-awareness как одно аддитивное nullable-поле, не новая таблица (ADR-0004, §1.6)
Явное требование владельца Движа: «дешёвый срез — честное подмножество, не выкидыш», решение — ОДНО
JSON-поле `awareness?{stateRef, logRef, planRef, handoffAt}` на существующей сущности, растущее без
миграций (`ADR-0004-topic-awareness-model.md:39-51`). У FF уже есть тот же СТИЛЬ решения (аддитивное
расширение `Provenance` до `string | Provenance`, `PrincipalAssurance` как опциональный `principal?`
слот на `Act` — оба 0-миграционные). Якорь: когда понадобится связать «эта работа агента» с «этой
областью графа», делать это ТАК ЖЕ — один optional-слот на существующем узле, а не новый тип сущности.

## Что сознательно НЕ берём сейчас
- Unit/TypeUnit/generic auto-UI-из-типа (ADR-0005 §«Тип самоописывает свой UI») — у Движа это тоже 0% в
  коде, черновик; копировать черновик черновиком нет смысла, ждём, пока у НЕГО дозреет до кода, а у нас
  появится реальная потребность.
- Generic pattern-engine (ADR-0009 «движка паттернов НЕТ, это B через C») — Движ сам применяет «правило
  двух» и не строит обобщённый движок по одному прецеденту; FF тем более не должен опережать это на
  чужом черновике.
