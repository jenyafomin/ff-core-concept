# Требования к памяти FF со стороны агент-систем (разбор на примере «Движ»)

**Вопрос сессии:** Движ строит СВОЮ независимую систему агентов (узлы/связи/паттерны/граф-луп). Мы не
копируем Движ и не связываемся с ним технически — но его дизайн-документы (много глубже проработаны,
т.к. там реальная нагрузка живого шлюза) дают КОНКРЕТНЫЕ технические требования и паттерны: «что наша
память ДОЛЖНА уметь, чтобы питать агент-систему такого рода», если/когда FF обрастёт своими агентами.

## Файлы
1. [Что Движ строит](01-dvizh-agent-model.analysis.md) — модель агента/узла/паттерна/лупа, с опорой file:line.
2. [Тех-требования к нашей памяти](02-tech-requirements.analysis.md) — список возможностей + пример на каждую.
3. [Verified vs gaps](03-verified-vs-gaps.analysis.md) — что у FF-engine уже есть (file:line) vs чего нет.
4. [Якорные паттерны](04-anchor-patterns.analysis.md) — 3-5 паттернов Движа, которые берём как форму.
5. [Где нужны реальные данные](05-real-data-needed.analysis.md) — что нельзя решить на бумаге.

## Вердикт одной строкой
FF-engine (Act/Edge/EnvelopeNode, CQRS-проекция, provenance+idempotency, predicate-cardinality-as-data)
УЖЕ структурно совместим с тем, к чему Движ только идёт (ADR-0005 «один стор Unit/Event» — у Движа
черновик, у FF — работающий аналог); но FF **не имеет** ни одного write-пути, который реально пишет
данные агент-лупа (`loop-run` тип читается guard'ом, но никто его не пишет), ни модели
topic/conversation-осознанности, ни approval-очереди как узла. Все требования ниже — гипотезы по
АНАЛОГИИ с чужой (более нагруженной) системой, не проверенные на своих данных (см. файл 5).
