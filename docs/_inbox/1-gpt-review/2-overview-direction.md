## Моя оценка

**Концептуальное ядро действительно может быть небольшим. Но создать надёжную систему вокруг него — сложно.**

Здесь важно разделить три разных продукта:

| Уровень                                       | Что это                                                           | Сложность по моей оценке |
| --------------------------------------------- | ----------------------------------------------------------------- | -----------------------: |
| Архитектурный прототип                        | Вещи, связи, акты, проекции, один storage adapter                 |                     4/10 |
| Полезная система для одного пользователя      | Агенты, история, права, плагины, интерфейс, поиск                 |                     7/10 |
| Многопользовательская платформа и marketplace | Изоляция, безопасность, версии плагинов, биллинг, масштабирование |                     9/10 |

Один сильный разработчик может создать убедительный прототип. Но production-платформа с чужими плагинами — уже задача уровня полноценной инфраструктурной компании.

Главная мысль:

> **Ядро может быть маленьким по количеству кода, но оно должно быть очень строгим по семантике.**

Это скорее microkernel или операционная система для знаний, чем обычный CRUD-конструктор.

# Где находится настоящая сложность

Не в том, чтобы сохранить универсальный JSON:

```ts
{
  id: "...",
  type: "task",
  data: { ... }
}
```

Это относительно просто.

Сложность начинается, когда нужно гарантировать:

* что один объект сохраняет идентичность после изменений;
* что два агента не испортят его одновременными операциями;
* что старые события можно корректно воспроизвести;
* что новая версия плагина понимает старые данные;
* что проекция не показывает запрещённые сведения;
* что удалённый плагин не разрушает данные;
* что пользователь понимает, почему агент что-то изменил;
* что семантический индекс не стал источником истины;
* что система отличает факт от предположения агента;
* что результат можно восстановить после сбоя.

То есть сложность не в количестве сущностей. Она в **инвариантах между ними**.

# Каким я вижу легковесное ядро

Я бы разделил систему на три слоя:

```text
Kernel
↓
Runtime
↓
Plugins
```

## 1. Kernel

Ядро должно знать только фундаментальные понятия.

```text
Identity
Envelope
Entity
Relation
Act
Projection
Policy decision
Plugin capability
Transaction
Provenance
```

Пример минимального конверта:

```ts
interface RecordEnvelope<T = unknown> {
  id: string;
  kind: string;
  type: string;

  scopeId: string;
  actorId: string;

  version: number;
  payload: T;

  provenance: {
    sourceIds: string[];
    createdBy: string;
    correlationId?: string;
  };

  temporal: {
    recordedAt: Date;
    validFrom?: Date;
    validTo?: Date;
  };
}
```

Ядро должно гарантировать:

1. Глобальную адресуемость.
2. Контроль версий.
3. Проверяемое происхождение.
4. Атомарность операций.
5. Единый протокол чтения и записи.
6. Возможность восстановить состояние.
7. Невозможность обойти policy layer.

При этом ядро **не должно знать**, что такое:

* задача;
* CRM;
* календарь;
* медицинская запись;
* embedding;
* OpenAI;
* Telegram;
* workflow;
* конкретный интерфейс.

Это всё находится выше.

## 2. Runtime

Runtime реализует механику:

```text
Persistence adapters
Projection engine
Policy engine
Plugin registry
Plugin executor
Job processing
Event delivery
Caching
Indexing
Observability
```

Это уже не чистое ядро, но без этого система не будет практически полезной.

Например, kernel определяет контракт проекции:

```ts
interface Projection<TInput, TOutput> {
  id: string;
  version: string;

  execute(
    input: TInput,
    context: ProjectionContext
  ): Promise<TOutput>;
}
```

А runtime решает:

* где её запустить;
* как проверить доступ;
* как закэшировать;
* что делать при ошибке;
* как вести аудит;
* как ограничить ресурсы;
* какой storage использовать.

## 3. Plugins

Плагинами могут быть:

* RAG и semantic retrieval;
* планировщик;
* задачи;
* CRM;
* agent memory;
* workflow engine;
* импорт Telegram;
* календарь;
* UI-проекции;
* аналитика;
* cost accounting;
* различные типы политик.

Плагин должен поставлять не только код, но и декларативный пакет:

```ts
interface PluginManifest {
  id: string;
  version: string;

  provides: {
    types?: TypeDefinition[];
    relations?: RelationDefinition[];
    projections?: ProjectionDefinition[];
    policies?: PolicyDefinition[];
    actions?: ActionDefinition[];
    agents?: AgentDefinition[];
  };

  requires: {
    capabilities: string[];
    pluginVersions?: Record<string, string>;
  };

  permissions: {
    read: string[];
    write: string[];
    execute: string[];
    network?: string[];
  };
}
```

Вот здесь твоя идея «плагин как актор с паспортом и словарём» становится практически реализуемой.

# Что не стоит помещать в ядро

Это критически важно. Если положить туда слишком много, проект станет неподъёмным.

Я бы не помещал в kernel:

* vector database;
* конкретную embedding-модель;
* LLM orchestration;
* UI-компоненты;
* workflow DSL;
* конкретные domain schemas;
* prompt management;
* billing;
* конкретный policy language;
* конкретную БД;
* marketplace.

Kernel должен определять **точки расширения**, но не владеть всеми реализациями.

Например:

```ts
interface RetrievalProvider {
  index(records: IndexableRecord[]): Promise<void>;

  search(
    query: RetrievalQuery,
    context: AuthorizedContext
  ): Promise<RetrievalResult[]>;
}
```

Один плагин использует PostgreSQL `pgvector`, другой — отдельную vector DB, третий — только full-text search. Ядро этого не знает.

# Но пользователю всё равно нужны базовые возможности

Здесь есть важная ловушка.

Можно создать идеальное ядро и получить продукт, которым невозможно пользоваться. Поэтому рядом с microkernel нужен **официальный базовый набор плагинов**.

Я бы включил в первоначальную поставку:

### Базовые данные

* создание типов;
* создание единиц;
* создание связей;
* изменение единиц;
* журнал актов;
* версии;
* источники и provenance.

### Базовое чтение

* фильтрация;
* сортировка;
* traversal по связям;
* временной срез;
* сохранённая проекция;
* простой полнотекстовый поиск.

### Базовая агентная работа

* прочитать разрешённый контекст;
* предложить операцию;
* провалидировать операцию;
* применить или отправить на подтверждение;
* сохранить причину и источники решения.

### Базовый интерфейс

* просмотр единицы;
* граф связей;
* timeline;
* inspector исходных актов;
* просмотр проекции;
* управление типами и плагинами.

### Базовая безопасность

* actor;
* scope;
* capabilities;
* read/write/execute;
* audit;
* запрет прямого обхода policy layer.

Без этого получится библиотека. С этим уже может появиться продукт.

# Самый большой архитектурный риск

Он не технический.

Ты можешь попасть в ловушку:

> «Мы строим систему, способную представить всё, но пока она не решает ни одну задачу лучше специализированного приложения».

Универсальность сама по себе почти не ощущается пользователем.

Чтобы доказать идею, нужен один **вертикальный сценарий**, который одновременно показывает все преимущества.

Например:

## Сценарий «задача человека и агентов»

1. Пользователь создаёт цель.
2. Агент создаёт связанные задачи.
3. Другой агент добавляет исследование.
4. Планировщик меняет приоритет.
5. Пользователь видит задачу в кокпите.
6. Memory-агент воспринимает её как воспоминание.
7. RAG находит похожее прошлое решение.
8. Часть данных скрыта от определённого агента.
9. Пользователь смотрит состояние недельной давности.
10. Видна стоимость всей цепочки делегирования.

Если ты реализуешь этот сценарий без специальных таблиц под каждый шаг, ты действительно докажешь основную гипотезу.

# Что я бы сознательно отложил

В первой серьёзной версии я бы не строил:

* публичный marketplace;
* выполнение непроверенных сторонних плагинов;
* сложную распределённую архитектуру;
* полноценную bitemporal-модель для всего;
* несколько физических хранилищ;
* автоматическое разрешение конфликтов между агентами;
* универсальный визуальный workflow builder;
* собственную vector database;
* собственный язык запросов общего назначения;
* полностью автономное изменение критических данных агентами.

Начать лучше с:

```text
PostgreSQL
+
append-only acts
+
materialized current state
+
JSONB payload
+
relation projection
+
versioned type registry
+
policy boundary
+
plugin SDK
```

Это не ограничит будущую модель, но даст возможность проверить фундамент.

Я бы также не пытался сразу хранить **каждое чтение** в основном domain log. Лучше разделить:

```text
Domain log       — то, что изменяет или объясняет состояние
Access audit     — кто что прочитал
Agent trace      — рассуждения, вызовы инструментов, делегирование
Telemetry        — latency, tokens, errors, infrastructure
```

У них может быть общий envelope, но разные политики хранения и replay.

# Критические инварианты

До активной разработки стоит письменно зафиксировать около десяти правил.

Например:

```text
1. Любой канонический объект имеет стабильный ID.
2. Канонические изменения происходят только через Acts.
3. Act после принятия не изменяется.
4. Текущее состояние является проекцией, а не вторым источником истины.
5. Projection имеет ID и версию.
6. Любое агентное изменение имеет actor и provenance.
7. Retrieval не предоставляет данные до policy evaluation.
8. Embeddings можно полностью перестроить без потери знания.
9. Удаление плагина не удаляет канонические данные автоматически.
10. Старые данные остаются читаемыми после обновления определения типа.
```

Если эти правила расплывчаты, код начнёт принимать архитектурные решения случайно.

# Как понять, что ядро получилось правильным

Не по количеству классов и не по красоте abstraction layer.

Проверка должна быть практической:

### Тест 1

Добавить новый тип данных без изменения физических таблиц ядра.

### Тест 2

Добавить semantic search как плагин без изменения механизма записи.

### Тест 3

Полностью удалить semantic index и восстановить его из канонических данных.

### Тест 4

Показать состояние объекта на определённый момент времени.

### Тест 5

Запретить агенту доступ к полю и доказать, что оно не попадает:

* в обычный query;
* в graph traversal;
* в vector search;
* в prompt;
* в trace.

### Тест 6

Обновить плагин, сохранив возможность прочитать старые записи.

### Тест 7

Объяснить каждое изменение цепочкой:

```text
source
→ actor
→ command
→ policy decision
→ act
→ resulting projection
```

Если система проходит эти проверки, фундамент уже серьёзный.

## Итог

Я бы не сказал, что ты пытаешься создать невозможную систему. **Ты пытаешься создать сложный инфраструктурный продукт, ядро которого действительно может быть маленьким.**

Реалистичная формула:

> Маленький kernel, строгие инварианты, достаточно мощный runtime и большая часть возможностей в versioned plugins.

Основная опасность — не объём кода, а преждевременная универсальность. Поэтому сначала нужно доказать три вещи:

1. Новая модель подключается без перестройки ядра.
2. Разные агенты и человек действительно работают с одним объектом.
3. История, права и retrieval остаются согласованными.

После подключения репозитория правильным первым заданием для меня будет не «улучшить код», а:

> **Восстановить фактическую архитектуру системы, сравнить её с заявленной моделью, проверить границы kernel/runtime/plugins и составить список нарушенных или незафиксированных инвариантов.**
