Я вижу у проекта **очень сильное направление**, но его лучшая версия — не буквально «n8n + GitHub».

Более точная формула:

> **Git-подобная эволюция данных и поведения + n8n-подобная композиция процессов + единое поле знаний + безопасная среда исполнения агентов.**

* От Git стоит взять историю, ветвление, изменения, review, merge и происхождение.
* От n8n — визуальную композицию действий, триггеры, исполнения и подключаемые узлы.
* От базы данных — источник истины и запросы.
* От систем durable execution — восстановление долгих процессов после сбоев.
* От тебя — единое адресное пространство, где данные, агенты, политики, процессы и проекции используют совместимый контракт.

Git сам опирается на неизменяемые объекты, commits, references и reflogs; это хорошая модель для версий и ветвей, но не готовая модель предметных знаний. n8n, в свою очередь, рассматривает workflow и его executions как центральные операционные сущности. Твоя система может объединить эти идеи, не делая ни файлы, ни workflow главным источником истины. ([Git][1])

# 1. Нужно проектировать не одну плоскость, а пять

Сейчас фраза «всё является единицами» полезна как общий фундамент. Но одной универсальной плоскости недостаточно.

Я бы разделил систему на пять логических пространств.

## Knowledge plane — что существует

Здесь живут:

* сущности;
* утверждения;
* связи;
* документы;
* цели;
* задачи;
* решения;
* пользователи;
* агенты;
* результаты;
* источники.

Это мир, с которым работает система.

## Execution plane — что происходит

Здесь находятся:

* команды;
* workflows;
* agent runs;
* tool calls;
* ожидания;
* retries;
* approvals;
* compensation;
* расписания;
* реакции на события.

Это не сами знания, а процессы изменения мира.

## Governance plane — что разрешено

Здесь живут:

* участники;
* роли;
* возможности;
* делегирование;
* ограничения;
* политики;
* подтверждения;
* пределы стоимости;
* ограничения по проектам и данным.

## Evolution plane — как система меняется

Здесь находятся:

* версии типов;
* версии агентов;
* версии prompts;
* версии workflow;
* ветки;
* эксперименты;
* diff;
* merge;
* migrations;
* rollout;
* rollback.

## Experience plane — как всё показывается

Здесь находятся:

* проекции;
* dashboards;
* таблицы;
* графы;
* timelines;
* редакторы;
* agent context packages;
* API;
* semantic search.

Главный принцип:

> Эти пространства используют общую идентичность и общий envelope, но не должны смешиваться семантически.

Например, задача, запуск агента, политика доступа и лог ошибки могут быть адресуемыми единицами, но у них разные правила жизни.

# 2. «Всё является единицей» — только на уровне конверта

Слишком универсальная модель легко превращается в это:

```ts
{
  id: string;
  type: string;
  data: unknown;
}
```

Технически она может хранить всё, но почти ничего не гарантирует.

Лучше иметь универсальный envelope и несколько фундаментальных семантических видов:

```ts
type UnitKind =
  | "entity"
  | "claim"
  | "artifact"
  | "relation"
  | "command"
  | "event"
  | "policy"
  | "workflow"
  | "execution"
  | "projection";
```

У всех может быть:

```ts
interface UnitEnvelope<T> {
  id: string;
  kind: UnitKind;
  type: string;
  version: number;

  scopeId: string;
  actorId: string;

  payload: T;

  provenance: Provenance;
  temporal: TemporalMetadata;
}
```

Но каждый `kind` должен иметь собственные инварианты.

Например:

* `event` нельзя изменить после фиксации;
* `command` может быть отклонена;
* `claim` может противоречить другой claim;
* `projection` можно перестроить;
* `execution` может ожидать внешнего сигнала;
* `policy` требует особого процесса публикации.

Это критически важно. Даже официальные рекомендации OpenFGA предупреждают, что чрезмерно универсальная метамодель авторизации ухудшает ясность и производительность; они рекомендуют отражать реальный домен, а пользовательскую гибкость переносить в данные. ([OpenFGA][2])

Тебе нужен тот же баланс:

> Универсальный фундамент, но конкретные семантические контракты поверх него.

# 3. Главным объектом проекта должно стать изменение

Система не выиграет только потому, что умеет хранить любые данные. Это уже умеют JSON-хранилища, knowledge graphs и конструкторы баз.

Настоящее преимущество появится, если она одинаково хорошо управляет изменением:

* данных;
* схем;
* связей;
* процессов;
* агентов;
* политик;
* prompts;
* проекций.

Я бы поставил в центр не просто `Unit`, а конструкцию:

```text
Состояние
+
Предлагаемое изменение
+
Основание
+
Проверка
+
Фиксация
+
Новая версия
```

То есть агент не должен просто делать:

```ts
updateEntity(...)
```

Он должен формировать change set:

```ts
interface ChangeSet {
  id: string;

  baseRevision: string;
  actorId: string;
  scopeId: string;

  operations: Operation[];
  evidence: SourceReference[];
  rationale?: string;

  requiredApprovals: ApprovalRequirement[];
  expectedEffects: ExpectedEffect[];
}
```

Затем:

```text
propose
→ validate
→ authorize
→ simulate
→ approve
→ commit
→ project
→ observe
```

Это и будет точка пересечения Git, агентов и базы знаний.

# 4. Агенты должны работать через shared world, а не через скрытые разговоры

Сильная часть твоей идеи — агенты могут взаимодействовать через саму систему.

Например:

```text
Research Agent создаёт evidence
↓
Появляется relation supports
↓
Decision Agent подписан на такое изменение
↓
Он создаёт proposal
↓
Policy требует подтверждение человека
↓
После подтверждения создаётся decision
↓
Planner Agent перестраивает задачи
```

Агенты не обязаны вызывать друг друга напрямую. Они реагируют на изменение общего мира.

Это очень близко к модели ActiveGraph: append-only log выступает источником истины, граф строится как его проекция, а behaviors реагируют на изменения графа и создают новые события. Авторы связывают такую конструкцию с replay, fork, diff и end-to-end lineage, хотя отдельно не утверждают, что уже доказали её преимущество для самосовершенствующихся агентов. ([arXiv][3])

Но shared world требует ещё нескольких примитивов:

* subscriptions;
* leases;
* ownership;
* inbox/outbox;
* deduplication;
* idempotency;
* correlation ID;
* causation ID;
* ожидание сигнала;
* deadlines;
* отмена;
* компенсационные действия.

Без них реактивные агенты начнут:

* запускать друг друга циклически;
* повторно выполнять операции;
* бороться за одни данные;
* создавать бесконечные цепочки;
* расходовать деньги без контроля.

Поэтому любое агентное действие должно иметь бюджет:

```ts
interface ExecutionBudget {
  maxCost?: number;
  maxDuration?: number;
  maxSteps?: number;
  maxDelegationDepth?: number;
  allowedCapabilities: string[];
}
```

# 5. Развитие агентской системы должно выглядеть как контролируемая эволюция

Саморазвивающаяся система не должна напрямую переписывать собственные правила.

Правильный цикл:

```text
Наблюдение
→ Гипотеза улучшения
→ Ветка
→ Изменение
→ Симуляция
→ Тесты
→ Сравнение
→ Approval
→ Merge
→ Ограниченный rollout
→ Наблюдение
→ Rollback или закрепление
```

Причём ветвиться может не только база данных.

Можно создать ветку:

* проекта;
* workflow;
* политики;
* prompt;
* конфигурации агента;
* модели retrieval;
* набора типов;
* целой агентской системы.

Например:

```text
main
└── experiment/research-agent-v3
    ├── другой prompt
    ├── другой набор инструментов
    ├── новая политика выбора источников
    └── изменённый workflow проверки фактов
```

После выполнения система сравнивает:

* качество результата;
* стоимость;
* время;
* количество ошибок;
* число неподтверждённых утверждений;
* вмешательство человека;
* нарушения политик.

Здесь главное понимание:

> **Самоулучшение — это не функция памяти. Это version control + evaluation + governance.**

Свежая работа по execution lineage также рассматривает AI-работу как граф вычислений и артефактов со стабильными границами, зависимостями и replay; её ключевая мысль — качество конечного ответа и качество поддерживаемого состояния являются разными характеристиками. ([arXiv][4])

# 6. Что именно стоит взять у Git

## Взять

### Стабильную историю

Каждая зафиксированная версия должна быть восстанавливаемой.

### Commit

Не просто отдельный event, а логическая группа согласованных изменений:

```text
Изменили задачу
+
Добавили основание
+
Создали связь с решением
+
Пересчитали приоритет
```

### Branch и fork

Агент может исследовать альтернативу, не портя основной мир.

### Diff

Пользователь должен видеть:

* что изменилось;
* почему;
* кем;
* на основании чего;
* какие зависимые объекты затронуты.

### Review и approval

Критические изменения сначала существуют как proposal.

### Blame и provenance

Нужно иметь возможность пройти от результата до источника и инициатора.

Git хранит неизменяемые content-addressed objects и использует references как именованные указатели на историю. Это хороший источник вдохновения для immutable revisions и branches. ([Git][1])

## Не переносить буквально

В предметной системе нельзя полностью отождествлять идентичность с хешем содержимого.

У задачи должны быть:

```text
Logical ID: task-123
Revision ID: task-123@revision-8
Content hash: 7a8f...
```

Задача остаётся той же задачей, даже когда меняются её поля.

Также обычный текстовый merge недостаточен. Нужен semantic diff:

```text
deadline changed
assignee removed
policy weakened
relation invalidated
claim contradicted
workflow step reordered
```

# 7. Что взять у n8n

## Взять

* workflow как данные;
* trigger/action модель;
* визуальный редактор;
* node contracts;
* шаблоны;
* executions;
* retry;
* inspection конкретного запуска;
* credentials и integrations;
* ручные и автоматические запуски.

n8n предоставляет отдельную историю executions, возможность фильтрации, повторного запуска и загрузки данных предыдущего исполнения. Это хороший UX-ориентир для операционной части. ([n8n Documentation][5])

## Но не делать workflow центром вселенной

В твоей системе workflow должен быть поведением над общим полем:

```text
Workflow читает units
→ создаёт commands
→ получает результаты
→ создаёт acts
→ обновляются projections
```

Если workflow удалён или обновлён:

* созданные им канонические данные не должны исчезать;
* старые executions должны оставаться объяснимыми;
* использованная версия workflow должна быть доступна;
* replay не должен неожиданно использовать новый workflow.

# 8. Multi-user и scopes нужно сделать отдельной архитектурной осью

Одного `projectId` будет недостаточно.

Я бы представлял scopes как граф:

```text
Organization
├── Team
│   ├── Project
│   │   ├── Workspace
│   │   └── Private agent branch
│   └── Shared knowledge
└── Personal space
```

Объект может принадлежать одному scope и быть опубликован или связан с другим.

Нужно различать:

```text
Principal   — кто прошёл аутентификацию
Actor       — кто совершает действие
Delegator   — кто дал полномочие
Scope       — в каком контексте действие происходит
Resource    — над чем выполняется действие
Capability  — что разрешено сделать
Policy      — при каких условиях
```

Например:

```text
Пользователь Александр
→ делегировал Research Agent
→ право читать public project sources
→ только в project-alpha
→ без доступа к private-finance
→ на 30 минут
→ бюджет до $3
```

Relationship-based authorization хорошо подходит для организаций, проектов, папок, документов и унаследованных прав: OpenFGA, например, вычисляет доступ на основании authorization model и relationship tuples, включая отношения между объектами и условия запроса. ([OpenFGA][6])

Но есть важное правило:

> Авторизация должна повторно проверяться в момент фиксации изменения.

Агент мог получить разрешение в начале работы, но к моменту записи:

* роль пользователя изменилась;
* документ переместили;
* approval отозвали;
* ветку закрыли;
* политика обновилась.

Поэтому полезно разделять:

```text
read-time authorization
execution-time authorization
commit-time authorization
```

Недавняя работа о commit-time authorization отдельно показывает риск, когда агент фиксирует постоянный результат на основании уже устаревшего разрешения. ([arXiv][7])

# 9. Необходимо ввести эпистемическую модель знаний

Система должна понимать не только **что записано**, но и **какого качества это знание**.

Следует различать:

```text
Observation — что было замечено
Claim       — утверждение
Evidence    — основание
Inference   — вычисленный вывод
Hypothesis  — предположение
Decision    — принятое решение
Policy      — действующее правило
Artifact    — созданный результат
```

Например:

```text
«Рынок вырос на 20%»
```

Это не просто поле `text`. Нужно знать:

* кто это утверждает;
* откуда взялась цифра;
* на какой период она действует;
* подтверждена ли она;
* какие источники её поддерживают;
* какие ей противоречат;
* использовалась ли она для принятия решения.

Я бы не перезаписывал противоречивые знания. Лучше хранить несколько claims:

```text
Claim A supports Decision X
Claim B contradicts Claim A
Claim C supersedes Claim A after July
```

W3C PROV уже предлагает стабильную базовую модель для entities, activities, agents, derivation, responsibility, versioning и reproducibility. Не обязательно реализовывать PROV-O буквально, но стоит сопоставить твою модель с этим стандартом, чтобы не изобретать provenance-вопросы заново. ([W3C][8])

# 10. Domain log, agent trace и telemetry нельзя смешивать

У них может быть общий envelope, но это разные данные.

```text
Domain event
Что изменилось в предметном мире?

Execution event
На каком шаге находится процесс?

Agent trace
Как агент пришёл к действию?

Access audit
Кто что прочитал?

Telemetry
Сколько это заняло, стоило и где упало?
```

Например, model call — не обязательно каноническое событие предметного мира.

OpenTelemetry отдельно различает traces, metrics, logs и baggage, поскольку каждый сигнал отвечает на свой вопрос. Такой же принцип лучше использовать в твоей архитектуре. ([OpenTelemetry][9])

При этом их нужно связывать идентификаторами:

```text
correlationId
causationId
executionId
traceId
commitId
actorId
```

Тогда можно пройти цепочку:

```text
Цель пользователя
→ запуск workflow
→ вызов агента
→ tool call
→ evidence
→ proposal
→ approval
→ commit
→ новая проекция
```

# 11. Долгоживущим агентам потребуется durable execution

Когда агент работает несколько секунд, можно обойтись очередью и retry.

Но если он:

* ждёт человека;
* спит до определённой даты;
* вызывает несколько сервисов;
* делегирует подагентам;
* переживает deployment;
* работает часами или днями,

нужны:

* checkpoints;
* resumability;
* deterministic orchestration;
* idempotent activities;
* signals;
* timers;
* cancellation;
* compensation;
* workflow versioning.

Temporal строится именно вокруг восстановления выполнения после сбоев и разделения durable workflows от failure-prone activities. ([Temporal Docs][10])

Но я бы **не строил собственный Temporal в первой версии**.

На старте:

```text
PostgreSQL
+
outbox
+
worker queue
+
idempotency keys
+
execution checkpoints
```

Позже execution provider можно заменить или расширить Temporal-подобным runtime.

# 12. Плагин должен поставлять целый смысловой модуль

Не только код или node.

Хороший плагин может включать:

```ts
interface PluginPackage {
  manifest: PluginManifest;

  types: TypeDefinition[];
  relations: RelationDefinition[];

  commands: CommandDefinition[];
  projections: ProjectionDefinition[];

  workflows: WorkflowDefinition[];
  agents: AgentDefinition[];

  policies: PolicyDefinition[];

  migrations: PluginMigration[];
  tests: PluginTest[];
  fixtures?: PluginFixture[];
}
```

Например, плагин `Project Management` поставляет:

* `Goal`;
* `Task`;
* `Milestone`;
* `blocks`;
* `dependsOn`;
* task board;
* planning workflow;
* planner agent;
* permission defaults;
* migration rules;
* демонстрационные данные.

## Что обязательно должно быть в manifest

* версия plugin API;
* зависимости;
* capabilities;
* permissions;
* network access;
* используемые secrets;
* события, на которые он реагирует;
* типы, которые он изменяет;
* стоимость или ресурсные ограничения;
* стратегия удаления;
* backward compatibility.

VS Code использует manifest, contribution points, activation events и отдельный extension host; расширения загружаются по необходимости, а прямой доступ к внутреннему UI ограничивается API. Это хороший образец для декларативных вкладов, ленивой активации и изоляции плагинов. ([Visual Studio Code][11])

GitHub Apps дают ещё один хороший принцип: приложение по умолчанию не получает полномочий и должно запрашивать минимально необходимые permissions; расширение разрешений требует отдельного согласия. ([GitHub Docs][12])

## Критические правила плагинов

1. Плагин не должен владеть пользовательскими данными монопольно.
2. После удаления плагина данные остаются читаемыми.
3. Плагин не получает доступ ко всему workspace автоматически.
4. Обновление permissions требует подтверждения.
5. Код плагина изолируется от kernel.
6. Плагин не может напрямую писать в storage.
7. Все изменения проходят через command/commit boundary.
8. Плагин обязан поставлять compatibility tests.

# 13. MCP лучше использовать как внешний порт

MCP уже разделяет:

* resources;
* prompts;
* tools;
* capabilities;
* lifecycle;
* authorization.

Он хорошо подходит для подключения внешних агентов и инструментов. Спецификация также подчёркивает необходимость пользовательского согласия, контроля данных и осторожности с executable tools. ([Model Context Protocol][13])

Но я бы не делал внутреннюю модель системы копией MCP.

Правильное положение:

```text
Внешний агент
↕ MCP
System Gateway
↕
Policy + Projection + Command APIs
↕
Твой субстрат
```

То есть MCP — это порт совместимости, а не внутренний источник истины.

Через него система сможет предоставлять:

* resources — разрешённые проекции;
* tools — команды;
* prompts — шаблоны взаимодействия;
* subscriptions — через дополнительный event API.

# 14. Пользователю нельзя показывать универсальность напрямую

Это, возможно, главный продуктовый риск.

Человек не хочет:

> Создать универсальную сущность, добавить relation и выбрать projection.

Он хочет:

> Создать проект, распределить задачи и подключить исследовательского агента.

Поэтому системе нужны три режима.

## Рабочий режим

Пользователь видит готовый продукт:

* проект;
* задачи;
* решения;
* документы;
* агентов;
* timeline.

## Режим конструктора

Пользователь меняет:

* поля;
* представления;
* правила;
* automation;
* агентов;
* связи.

## Режим разработчика

Доступны:

* manifests;
* schemas;
* events;
* policies;
* execution traces;
* SDK;
* migrations.

Правильный продукт скрывает универсальность до момента, когда она нужна.

> Универсальность должна ощущаться как отсутствие ограничений, а не как необходимость самому проектировать онтологию.

# 17. Критерии, по которым нужно судить архитектуру

Не количество поддерживаемых типов и не число плагинов.

Я бы измерял следующее:

### Расширяемость

Сколько нового модуля удалось реализовать без изменения kernel?

### Восстанавливаемость

Можно ли удалить все производные индексы и перестроить их?

### Объяснимость

Можно ли для любого результата получить:

```text
кто
→ на каком основании
→ каким процессом
→ какой версией агента
→ через какие действия
→ создал этот результат
```

### Изоляция

Можно ли доказать, что запрещённые данные не попали в:

* projection;
* retrieval;
* prompt;
* agent trace;
* export;
* plugin.

### Эволюция

Можно ли обновить workflow, policy или plugin, не разрушив старую историю?

### Конфликты

Понимает ли система разницу между:

* параллельными совместимыми изменениями;
* логическим конфликтом;
* противоречащими утверждениями;
* устаревшей базовой версией?

### Удобство

Может ли человек решить конкретную задачу, не понимая внутренней универсальной модели?

### Экономика

Можно ли определить стоимость:

* результата;
* агента;
* проекта;
* ветки;
* workflow;
* всей цепочки делегирования?

# 18. Самая важная архитектурная формула

Я бы сейчас зафиксировал проект так:

```text
Canonical Knowledge/Event Substrate
+
Versioned Semantic Contracts
+
Proposal/Commit Protocol
+
Permission and Delegation Kernel
+
Projection Runtime
+
Durable Execution Runtime
+
Plugin Packages
+
External Protocol Adapters
```

И главные правила:

1. Всё адресуемо, но не всё семантически одинаково.
2. Изменения важнее хранения.
3. Агент предлагает, kernel фиксирует.
4. Канонический мир отделён от производных индексов.
5. Права проверяются до чтения и перед commit.
6. Агент, workflow, policy и schema имеют версии.
7. Эксперименты выполняются в ветках.
8. Self-improvement проходит через evaluation и approval.
9. Domain events отделены от traces и telemetry.
10. Универсальность скрыта за готовыми модулями.

## Главный вывод

На мой взгляд, твой проект может стать действительно ценным не как «база, которая умеет хранить всё», а как:

> **Среда эволюции общего мира человека и агентов, в которой любое знание, действие, правило и изменение имеет идентичность, историю, владельца, область действия, основание и контролируемый жизненный цикл.**

Самая сильная идея здесь — не `Unit`.

Самая сильная идея:

> **Любая часть системы — данные, агенты, процессы, политики и даже сама структура — может изменяться тем же управляемым способом: через ветку, проверку, diff, approval, commit и наблюдение результата.**

Именно это может превратить конструктор в постоянно развивающуюся агентную среду, а не в очередную универсальную базу.

Следующим разумным этапом будет deep research не просто конкурентов, а шести архитектурных линий: event-sourced agent systems, temporal knowledge graphs, Git/CRDT collaboration, durable execution, authorization/delegation и plugin ecosystems — с итогом в виде карты паттернов, рисков, архитектурных решений и точной спецификации первого вертикального сценария.
