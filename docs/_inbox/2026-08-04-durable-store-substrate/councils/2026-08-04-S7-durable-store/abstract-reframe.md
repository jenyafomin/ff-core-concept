# S7 durable StorePort — взгляд сверху

> Линза: abstract-thinker (иду ВВЕРХ, снижаю сложность). НЕ проектирую интерфейс StorePort —
> даю РАМКУ, из которой другие его выведут. Три-фазный протокол сжат: ADR-0008 и ADR-0006 уже
> ратифицировали половину ответа, поэтому фаза вопросов короткая — большинство допущений
> подтверждены документами, а не догадками.

---

## Фаза 1 — что я проверял вопросами к докам (не к владельцу)

- **Что уже решено?** ADR-0008: лог актов = система-записи, граф = проекция (CQRS). ADR-0006:
  размещение = политика-на-тип; DB-first → лог в PG; file-first → `md+journal` = write-model,
  журнал строится ДИФФОМ ФС. I-5/I-11: состояние = проекция, истина = логическая (граф/журнал).
- **Значит «три истины» — это НЕ три открытых вопроса.** Это ОДИН решённый (лог⟂граф) плюс
  ОДИН решённый (логическое⟂физическое) плюс ОДИН scope-развод (doc-tree = дерево ДОКОВ, не
  рабочие данные движка, ADR-0006 §(c) явно). Осталась не «истина», а **durability**: журнал
  сейчас RAM-only, испаряется в конце хода. Вот настоящая дыра S7.

## Фаза 2 — подтверждённые допущения

- A1. Граф RAM-only — и это **нормально по дизайну**: граф пересобираем (I-5, rebuild-index).
  Терять граф в конце хода не больно. **Больно терять журнал** — его сейчас негде «помнить».
- A2. Файлы md уже durable (ФС переживает ход). То есть из «трёх истин» durable-проблема
  касается РОВНО ОДНОЙ — журнала актов.
- A3. Владелец хочет 5 свойств: помнит навсегда · проецирует под вопрос · ветки-гипотезы ·
  синк по правилам · сам растит слои. Проверка: **все пять — это роли ОДНОЙ операции**
  `fold(journal) → projection`, а не пять механизмов.

## Фаза 3 — синтез

### Несущая абстракция (одна фраза, языком владельца)
**Субстрат помнит навсегда РОВНО ОДНУ вещь — ленту того, что случилось (журнал актов);
всё остальное — граф, файлы-выгрузки, ветки-гипотезы, кэш, новые слои — он каждый раз ЗАНОВО
сворачивает из этой ленты под текущий вопрос.** «Durable StorePort» = «сделай ленту
несгораемой; всё, что из неё сворачивается, держи дешёвым и пересобираемым».

Принцип-инвариант (кандидат, S7):
> **Durable = только журнал актов.** Всё, что можно свернуть из журнала (граф, current-state,
> индексы, md-выгрузка DB-типов, ветка-гипотеза, кэш), НЕ хранится как истина — это проекция:
> сносимо, пересобираемо, с меткой свежести. **Ветка · синк · кэш · новый слой — это РОЛИ
> одной операции `fold(journal)`, а не отдельные подсистемы.** (Иммутабельность/append-only =
> I-3/I-4; проекция ≠ второй источник = I-5.)

### Разрешение «трёх истин» — одной моделью (две оси, не три истины)
Мнимый конфликт исчезает, когда видишь, что «три истины» живут на РАЗНЫХ ОСЯХ:

- **Ось 1 (ADR-0008, CQRS): что истина vs что производное.** Журнал = write-model (истина
  произошедшего). Граф = read-model (истина смысла СЕЙЧАС, производна). Не иерархия «главный/
  слуга» — две истины РАЗНОГО РОДА.
- **Ось 2 (ADR-0006, persistence-as-policy): где байты лежат.** Файл vs PG — это РАЗМЕЩЕНИЕ,
  свойство типа, данные-настройка. Не истина.
- **doc-tree «файлы = истина» — это про ТРЕТЬЕ вещество:** дерево ДОКОВ-артефактов проекта
  (этот файл — док), а не рабочие данные движка (клиенты/трейсы/журнал). ADR-0006 §(c) уже
  провёл эту границу явно. Конфликта нет — просто разные вещества (trace ⟂ knowledge ⟂
  engine-data).

**Проверка гипотезы задания** («журнал = единственная истина, И граф И md = две проекции»):
**почти верно, но слишком чисто — ломается на file-first.** Для типов, что владелец правит
руками (`doc/config/prompt/agent-манифест/adr`), **ФАЙЛ авторски-первичен**, а акт ВЫВОДИТСЯ
диффом ФС (движок — «первый читатель», ADR-0006 §(f)). Значит файл там не проекция журнала —
он ВХОД, из которого журнал рождается. Точная формулировка:

> Единственная durable истина = **лента событий авторства**. Авторство приходит двумя путями:
> через движок (акт-первый, DB-first) ИЛИ через правку файла (файл-первый, акт-выведенный).
> Как только событие ЗАПИСАНО — журнал единственный источник, а граф/current-state/PG/
> md-выгрузка/индексы пересобираемы. **Файл играет ДВЕ роли: для человеческих типов — ПЕРО
> (вход-авторство), для машинных — ОТПЕЧАТОК (выход-выгрузка).** Файл никогда не «истина»,
> конкурирующая с журналом: он либо перо, либо отпечаток.

Это и снимает кажущуюся третью истину: md-файл — не третий претендент, а вход ИЛИ выход
одной и той же ленты.

### Аналогии — какая ближе и где врёт
- **Event-sourcing / CQRS — это НЕ аналогия, это принятая модель** (ADR-0008). Точка отсчёта.
- **Datomic — самый верный технический родич ЦЕЛИ.** «База — это ЗНАЧЕНИЕ, свёрнутое из ленты
  иммутабельных фактов»; as-of/time-travel даром. Ровно I-5 + битемпоральный конверт ADR-0006
  §(h). *Врёт где:* Datomic знает ОДИН путь авторства (транзактор), у него нет file-first
  ручной правки md как первоклассной поверхности человека.
- **Git — лучшая КАРТИНКА для владельца.** Лента коммитов (append-only, иммутабельны) +
  рабочее дерево (checkout = проекция) + ветки. Журнал≈DAG коммитов, граф≈checked-out дерево,
  гипотезы≈ветки. *Врёт где:* git хранит СНИМКИ состояния, а не СОБЫТИЯ (snapshot-sourced, не
  event-sourced); и git не умеет спросить «кто клиент X сейчас» — нет семантического
  read-model. Git = отличная картинка спины и веток, недо-показывает query-граф.
- **Basic Memory (md + SQLite + MCP two-way) — «почти наша модель» ТОЛЬКО в половине.** Совпадает
  file-first-поверхность (md=человеческая правда, SQLite=производный индекс). *Врёт где:* (1)
  это ДВУСТОРОННИЙ sync file↔DB — ровно то, что ADR-0006 Alt-3 ОТКЛОНИЛ (два живых писателя =
  два источника истины = нарушение I-5); (2) у неё НЕТ иммутабельного журнала актов — нет
  истории «во что верили тогда», нет rebuild-from-journal, нет битемпоральности. Basic Memory =
  «наша поверхность чтения/письма» БЕЗ «нашей системы-записи». Брать её как эталон = потерять
  durable-спину.
- **CRDT — целится в проблему, которую мы УБРАЛИ дизайном.** CRDT нужен при НЕСКОЛЬКИХ
  конкурентных писателях с авто-merge. FF выбрал одного писателя (движок через resolve()),
  sync = export-on-demand, ветки = what-if реплей (не конкурентный merge). CRDT = over-engineering,
  пока не появится реальное офлайн-мульти-девайс редактирование. Соблазн («ветки-гипотезы») —
  ложный: ветка тут не слияние параллельных правок.

Итог: **вести владельца git-картинкой, строить по Datomic-субстанции (= event-sourcing,
уже принято); Basic Memory = только поверхность, CRDT = не наш.**

### Что НЕ строить (снижение сложности)
Минимальный субстрат S7 = **durable append-only журнал (StorePort, который персистит `acts[]`)
+ функция `fold`**. Из этого ОДНОГО примитива всё остальное вырастает КАК РОЛЬ, не как механизм:

- **НЕ строить «acts-as-git» отдельной подсистемой версий.** Ветка-гипотеза = форк-указатель
  над той же лентой + вариант-reducer (overlay). Роль fold, не новый стор.
- **НЕ строить двусторонний sync file↔DB.** Синк = export-on-demand (материализовать свёртку в
  файл) + file-first ingest (дифф→акт). Один писатель на поток. ADR-0006 §(d) уже решил.
- **НЕ строить слой кэша.** Граф/current-state И ЕСТЬ кэш — материализованная свёртка со
  staleness-меткой. Инвалидация = rebuild-from-journal. Кэш = роль проекции, не компонент.
- **НЕ строить машинерию «роста слоёв».** Новый слой = зарегистрировать новую проекцию над той
  же лентой. Аддитивно, без миграции (I-13). ADR-0008: «новый потребитель = новая проекция».
- **НЕ строить durability отдельно на каждый артефакт.** Durable-объект РОВНО ОДИН — журнал.
  Остальное disposable-и-пересобираемо → может жить в RAM или лениво материализоваться.

Так S7 схлопывается: «durable StorePort» = «журнал переживает ход; всё прочее — foldable».

### Открытые напряжения / вопрос владельцу (несёт S7, НЕ покрыт ADR-0008/0006)
- **Ветка-гипотеза: форк ЛЕНТЫ или вариант ПРОЕКЦИИ?** Владелец хочет «версионировать гипотезы
  как git-ветки». Это две РАЗНЫЕ вещи по цене и смыслу, и ни один ADR их не закрыл:
  - (A) **форк журнала** — расходящаяся история событий, которую позже мержат/выкидывают
    (истинный git — новые акты в отдельной ленте);
  - (B) **вариант проекции** — та же лента, другой reducer/overlay поверх (гипотеза = линза,
    ничего не форкается в системе-записи).
  (A) даёт настоящее «что-если с записью», но плодит мульти-ленты (concurrency/merge → тянет к
  CRDT, который мы убрали). (B) дёшев и держит одну истину, но «ветка» иллюзорна — это фильтр.
  **Это развилка уровня FQ25 для S7 → решать РЕШЕНИЕМ, не кодом** (иначе P-06 рецидив).
- **Вторичное напряжение (file-first gap):** между save-файла и emit-акта есть окно, где
  файл ≠ журнал. Покрывает ли durable-гарантия это окно (файл — истина до наблюдения), или
  правка «реальна» только став актом? Связано с write-time-гейтом ADR-0006 §(g)/KQ-9.

### Что модель НЕ покрывает (честно)
- Форму снапшотов/компакции (replay длинных лент дорог — ADR-0006 минус; это оптимизация
  ПОВЕРХ ленты, не замена; форма отложена).
- Concurrency/порядок записи в журнал одного `state` (долг tri-linzy §Механики).
- Границу детерминизма rebuild после crypto-shred (ADR-0007 carve-out) — не воскрешает
  стёртый payload; координаты/факт целы.

### Рекомендованный следующий шаг
1. **Владельцу — один вопрос-развилка (ветка = форк-ленты A vs вариант-проекции B).** Пока
   открыт — S7-«durable StorePort» проектировать нельзя без молчаливого пред-решения (риск P-06).
2. После ответа — **system-architect** проектирует StorePort-контракт над ОДНИМ примитивом
   (persist `acts[]` + `fold`), где git/sync/кэш/слои — роли, не порты.
3. Возможный **ADR-0009 «durable journal / branch-as-projection»** если владелец выберет модель
   веток (R4-развилка о семантике истории → по конституции ADR до кода).
