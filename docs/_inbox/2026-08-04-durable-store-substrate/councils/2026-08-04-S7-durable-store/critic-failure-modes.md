# Критик: разнос дизайна durable-store ДО стройки

Читал: ADR-0006 (persistence-as-policy, §a-h + Alternatives + Consequences), ADR-0008 (CQRS лог/граф),
`invariants.md` (I-1..I-14 + pending carve-out к I-4), `durable-storeport.design.md` (S7 контракт C1-C5,
AC-1..AC-5, §3 sync/async развилка, §5 разграничитель от шлюза).

Не всё ниже одинаково опасно. Ранжировано по опасности, с классификацией CRITICAL/CONCERN/PROVOCATION/NOTED.

---

## CRITICAL — реально рушит контракт до того, как код написан

### C-1. File-first durability не спроектирована вообще — второй писатель без лока, без атомарности, без теста

`durable-storeport.design.md` целиком говорит про `Engine.write(act)` — то есть про DB-first/engine-driven
путь. Но ADR-0006 §(f) явно определяет ВТОРОЙ путь записи: **file-first-типы (doc/config/prompt/agent-манифест/
adr/spec/lens) — журнал строится ДИФФОМ ФС (git-hook/fs-watcher), движок = "первый читатель", не "первый
писатель"**. Это значит: когда владелец руками правит `.md`-файл (ADR, spec, prompt) — пишет НЕ движок, пишет
редактор ОС, вне `resolve()`, вне `Engine.write()`, вне C1-C5.

Durable-storeport.design.md вообще не упоминает этот путь. Ни один AC (AC-1..AC-5) не тестирует его. Это значит:
- **Нет single-writer гарантии** для file-first: если владелец правит файл ПОКА watcher вычисляет diff (или
  редактор делает неатомарную запись — многие делают `write→flush` без `temp+rename`), watcher может прочитать
  частично записанный файл и поднять акт с ОБРЕЗАННЫМ/битым содержимым. Акт **иммутабелен (I-4)** — испорченный
  diff навсегда зацементирован в append-only лог. Это прямое нарушение духа I-4 ("что мы считали правдой тогда"
  должно быть правдой, а не артефактом гонки записи).
- **Watcher физически не существует** (по факту кода: `store-md.ts` признаёт md-мост "async, провизорный,
  незавершённый", `TODO(M3)`). Значит СЕГОДНЯ каждая ручная правка ADR/spec/prompt файла **уже расходится**
  с журналом — граф(=истина по ADR-0008) не знает о правке, пока кто-то не построит watcher. Doc-tree правило
  "файлы=истина" (project CLAUDE.md) физически верно для содержимого файла, но ЛОЖНО для "граф знает об этом" —
  тихий, недокументированный дрейф, ИМЕННО тот класс, который прошлый раунд (STATE.md 2026-08-01) уже назвал
  "враг = enforcement/дрейф".

**Триггер:** владелец редактирует любой ADR/spec/prompt файл (что происходит КАЖДУЮ сессию по факту рабочего
процесса проекта) → журнал не видит правку (watcher не построен) → любая будущая проекция/rebuild будет НЕ
соответствовать текущему файлу, без staleness-маркера, потому что staleness-маркер (ADR-0006 §e) описан для
PG-read-model-от-file-first-write-model, а не для "watcher вообще не запущен".

**Что рушит:** ADR-0008 validation #2 ("граф детерминированно пересобирается из лога, бит-в-бит эквивалентен")
— неверно для file-first-типов уже сегодня, потому что часть write-model (правки файлов) не попадает в лог.

**Must-fix перед стройкой:** durable-storeport.design.md обязан ЛИБО (а) спроектировать file-first durability
symmetric к C1-C5 (атомарная запись через temp+rename ожидается от владельца/редактора — недоказуемо; значит
нужен detect-and-refuse на torn read, не molчаливый accept), ЛИБО (б) явно СКОУПИРОВАТЬ file-first path ВНЕ S7
и зафиксировать письменно: "до появления watcher'а file-first-типы НЕ durable в журнале — граф может расходиться
с файлами без предупреждения". Сейчас — ни то, ни другое; это тихая дыра.

### C-2. Acceptance-тесты проверяют graceful exit, а не crash — ложно-зелёное durability против уже задокументированного режима отказа

AC-2 (несущий тест) описан как "процесс P1 пишет акт → P1 **завершается** → новый процесс P2 поднимается".
"Завершается" читается как штатный exit. Нигде в C1-C5 или AC-1..AC-5 нет теста `kill -9` / SIGKILL посреди
`writeAct`. Это принципиально другой режим отказа: обрыв **посреди** записи (torn write), а не после неё.

Это не гипотетический риск — это УЖЕ задокументированный операционный факт этого же проекта: память
(`gateway-agents-die-on-restart`, `gateway-dup-message-bug`) прямо фиксирует, что шлюз **убивает процессы
посреди хода**, и это уже один раз стоило потери работы (10-агентная оркестрация оборвалась в фоне). Durable
store спроектирован ИМЕННО чтобы пережить эту границу процесса (§ "survive-turn"), но тестируется на самом
безобидном сценарии (чистый exit), а не на том, который реально происходит в проде этого проекта.

**Конкретные дыры, не закрытые контрактом:**
- Нет упоминания `fsync`/`fdatasync`. `appendFileSync` без fsync возвращает управление ДО того, как ОС гарантированно
  сбросила данные на диск — kill -9 / OOM-kill / power-loss между `write()` и физическим flush = потеря "уже
  подтверждённого" акта, при этом AC-1 ("акт физически на диске") не проверяем без явного fsync-контракта.
- Нет политики на **truncated tail** журнала при rebuild на боте (последняя строка оборвана). Молча пропустить
  (тихая потеря знания, нарушение "0 потери знания" из ADR-0008 validation #2) vs fail-closed (I-9 требует
  refuse-before-compute) — контракт не выбирает ни то, ни другое.

**Триггер:** шлюз убивает процесс во время `Engine.write()` (задокументированный, не гипотетический сценарий
этого проекта) → журнал получает обрезанный хвост → следующий boot либо тихо теряет акт, либо падает
недетерминированно в зависимости от реализации парсера, которая ещё не написана.

**Must-fix:** явный fsync-контракт в C1; явная torn-tail-политика (рекомендация: fail-closed по I-9, не
best-effort skip); AC-2 переформулировать на реальный `kill -9` spawn/kill-тест, не graceful exit — иначе тест
доказывает не то, что нужно доказывать.

## CONCERN — должно быть решено или осознанно принято как риск

### C-3. Sync vs async (§3, OQ-1) framing недооценивает durability-последствия, не только рефактор-цену

Документ честно называет развилку "не косметика", но сравнивает варианты ТОЛЬКО по цене рефактора (сейчас vs
на M4/PG). Не разобраны durability-последствия самого выбора:
- **(A) sync + durable-fs (`appendFileSync`)** блокирует event loop Node.js на время записи. Если store-dir
  когда-нибудь окажется не на локальном SSD (сетевой диск, контейнер с медленным volume — вполне вероятно при
  multi-tenant per-topic store-dir под шлюзом), блокируется ВЕСЬ процесс, не только текущий acts-write — это
  availability-риск, не упомянутый вообще.
- **(B) async** снимает блокировку event loop, но advisory file-lock (C5) — типично МЕЖпроцессная защита; она
  НЕ обязательно защищает от гонки ДВУХ ASYNC-записей внутри ОДНОГО процесса (два `await writeAct()` могут
  интерливиться на уровне промисов раньше, чем дойдут до файлового лока), а именно async открывает эту дверь,
  которой у sync не было. Документ не проговаривает эту новую категорию гонки, которую сам же вносит.

**Риск, если проигнорировать:** выбор решается только "что дешевле сейчас переписать", а не "что безопаснее
для durability" — при этом durability и есть ЗАЯВЛЕННАЯ цель S7.

### C-4. "Rebuild детерминирован бит-в-бит" против PENDING carve-out I-4 (retention-prunability) — заложенное противоречие

`invariants.md` I-4 несёт незакрытый carve-out (B3-b/f, KQ-8): `observation`/trace-акты **policy-prunable**,
`domain_event` — нет. Если/когда retention когда-нибудь включится (а он уже спроектирован, просто не
ратифицирован), rebuild ПОСЛЕ prune **не может** быть бит-в-бит равен rebuild ДО prune — pruned-акты физически
исчезли. `durable-storeport.design.md` AC-4 формулирует "append-only-forward replay" без единого слова про
retention/prune как легитимное исключение из "та же проекция". Слово "durable" и слово "детерминированный
rebuild" будут означать РАЗНОЕ, в зависимости от того, читает ли кто-то ADR-0008 (жёсткий бит-в-бит) или
kernel invariants (мягкий carve-out для не-domain-актов). Никто пока не свёл эти два текста.

**Риск:** первый же PR, реализующий retention для trace/observation-актов, "сломает" ADR-0008 validation #2
буквально по тексту — и придётся либо переписывать ADR postfactum, либо тихо не соблюдать rebuild-гарантию.
Лучше зафиксировать явное исключение ДО кода.

### C-5. Нет adversarial-теста "bypass and assert refused", симметричного ADR-0006 §(e) `persistence-lock.test.ts`

ADR-0006 сам устанавливает паттерн: замок доказывается ИСПОЛНЯЕМЫМ тестом, который АКТИВНО пытается обойти
защиту (сырой SQL в обход `resolve()`) и утверждает REFUSED. Durable-storeport.design.md, живущий в том же
ядре и решающий тот же класс проблемы ("что мешает кому-то тихо обойти путь записи"), содержит только
happy-path AC (durable write работает, rebuild работает). Нет теста "кто-то написал акт напрямую в файл журнала
в обход `Engine.write()` — система это обнаруживает/отказывает/флагует". Given the project's own named pattern
P-06 ("объявить строй, пока развилка тихо решена кодом") — отсутствие adversarial-теста здесь воспроизводит
ровно тот способ провала, который проект уже трижды ловил на себе.

## PROVOCATION — над чем стоит подумать, не обязательно действовать

### P-1. CQRS/журнал — оправдана ли сложность на текущем масштабе?

Проект — single-owner, ~4100 Order-строк, один активный писатель (движок), формализующий multi-writer file-lock
"до того как появится второй писатель" (C5 явно говорит об этом). Вопрос: не преждевременная ли это
инвестиция? Альтернатива низкой сложности — периодический atomic-snapshot (`write-temp+rename`) всего
in-memory графа на диск + журнал только НАБЛЮДАЕМЫХ мутаций как debug-trail, без полной CQRS-инфраструктуры
(projectionId/version, rebuild-эквивалентность бит-в-бит) — была бы значительно проще, и решила бы 90% боли
("акт исчезает в конце хода") при 20% сложности. ADR-0008 уже привёл контраргументы (аудит/undo/битемпоральность)
— это НЕ игнорируется, но стоит явно спросить: при текущем масштабе (один владелец, не multi-tenant прод) —
эти преимущества уже нужны, или это архитектура "на вырост", которую собирают раньше, чем доказана боль?
Ранее сам проект называл это анти-паттерном ("анти-ossification": стораджи по факту боли, не заранее — ADR-0006
Consequences). Multi-writer file-lock — ровно такой случай.

### P-2. Bit-for-bit rebuild как ЖЁСТКИЙ acceptance-гейт может быть over-specified

I-6 УЖЕ вводит `projectionId/version` именно чтобы обслуживать смену reducer-логики без разрыва. Если
версионирование проекций и так покрывает "reducer изменился — старая проекция другая" — зачем ADR-0008
validation #2 требует именно "бит-в-бит эквивалентен", а не "семантически эквивалентен под той же версией
reducer'а"? Возможно это нормально (замораживает M0/M1 shape специально), но стоит явно проверить: не станет
ли этот гейт тормозом на первом же баг-фиксе reducer'а (любой фикс "рёбра затирались целиком", как уже было в
истории проекта — RESUME 2026-07-28 — формально ломает "бит-в-бит", если тест буквален).

### P-3. Advisory file-lock (C5) — stale-lock/livelock не разобран

Advisory-локи (flock) обычно освобождаются ОС при завершении процесса, включая abnormal — но контракт этого
не проговаривает явно. Если реализация выберет lock-файл-как-маркер (не настоящий OS flock), а процесс убит
шлюзом посреди хода (задокументированный сценарий, см. C-2) — lock-файл может остаться, и следующий процесс
либо навсегда ждёт (livelock), либо fail-closed навсегда без ручного вмешательства. Не критично сейчас
(single-writer factически), но стоит явно закрыть до появления второго писателя (OQ-4 уже это признаёт как
открытый).

## NOTED — вижу, ничего делать сейчас не нужно, но следить

- **Три "истины" (doc-tree files=truth / ADR-0008 лог=SoR / I-11 граф=логическая истина) НЕ противоречат друг
  другу на уровне ТЕКСТА** — ADR-0006 §(c) явно развёл "два вещества" (doc-tree = дерево документов проекта;
  persistence-as-policy = рабочие данные движка), и ADR-0008 даёт глоссу к I-11 (граф=query-истина/проекция,
  лог=durable-запись). Формально это не тройное противоречие. НО практически именно на СТЫКЕ этих двух веществ
  — file-first-типы (doc/adr/spec), где ОБА закона одновременно применяются к ОДНОМУ файлу — дыра реальна
  (см. CRITICAL C-1). Смотреть за этим стыком, не за абстрактным "три истины".
- **DB-first path (PG) capability-safe заявлен корректно** — замок §(e) + risk R-2 + запланированный
  `persistence-lock.test.ts` выглядят методологически здоровыми (тест АКТИВНО пытается обойти, не просто
  описывает). Если S7-durable-store для DB-first унаследует этот паттерн теста (не только happy-path AC) —
  этой части дизайна доверяю больше, чем file-first-стороне.
- **Sync-vs-async развилка (OQ-1) уже явно помечена P0 самим документом** — не открытие критика, но подтверждаю:
  это действительно блокер, не theoretical bikeshedding, потому что она определяет форму C1-C5 контракта.

## Сводка: что реально должно случиться ДО кода

1. Спроектировать (или явно вывести из скоупа с письменным предупреждением) durability file-first-пути —
   сейчас её нет вообще, а разрыв там уже активен КАЖДУЮ сессию.
2. Заменить graceful-exit AC-2 на реальный `kill -9`-тест; добавить явный fsync-контракт + явную torn-tail-
   политику (рекомендация: fail-closed, не best-effort skip).
3. Решить OQ-1 (sync/async) с учётом durability-последствий (блокировка event loop / внутрипроцессные гонки
   async), не только рефактор-цены.
4. Свести "бит-в-бит rebuild" (ADR-0008) с pending retention-carve-out I-4 ДО того, как retention реализован —
   иначе первый PR по retention формально ломает ADR-0008.
5. Добавить adversarial "bypass-and-assert-refused" тест для durable-store, симметричный ADR-0006
   `persistence-lock.test.ts` — иначе S7 повторяет паттерн P-06 (happy-path зелёный, обход не проверен).
