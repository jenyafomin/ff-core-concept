## Диагноз линейности

1. **`docs/00-states/STATE.md` — сам себе противоречит собственному замыслу.** Задуман как «живой указатель» (1 экран), по факту — append-only стек из ≥9 блоков «⭐⭐⭐ RESUME» от 08-04 назад до 07-27 (517 строк), каждый новый блок дублирует часть старого текста через `⛔ УСТАРЕЛО, см. выше` вместо замены. Пример: RESUME 08-04 «S7-ЯДРО запечатано» явно отменяет три более старых блока (07-31, 08-01), которые остаются в файле нетронутыми с зачёркивающими пометками — хронология вместо структуры.
2. **Трек-пульты (`00-states/0N-*/state.md`) не используются как приёмник новых веток работы.** Правило R2 требует «новая параллельная работа → заводи НОВЫЙ state» — но ga-rentacar (с 07-26), durable-store-substrate и picture-coverage (обе 08-04) вообще НЕ зарегистрированы как `05-*`/`06-*` в `00-states/`; они живут как `docs/03-projects/ga-rentacar/` и `docs/_inbox/2026-08-04-*/`. Пульт (`STATE.md`) знает о них только текстовой ссылкой внутри линейного стека — государство состояний физически устарело относительно реальной работы.
3. **`log.md` (append-only журнал по R2) заброшен ровно в момент, когда работа ускорилась.** Все 4 `log.md` замерли 07-19…07-22; вместо них факты «что произошло» теперь пишутся ТОЛЬКО в датированные `_log/<дата>-<тема>/HANDOFF.md` — параллельный, несвязанный механизм трассировки, который сам по себе тоже линеен (42 папки подряд по дате, без сводного индекса «что из этого ещё живо»).

## К правильной организации (тезис)

Пульт должен быть **графом активных веток работы с состоянием каждой** (state = карточка «где мы / что дальше»,
живущая ровно там, где идёт работа — `03-projects/<X>/state.md` или `00-states/0N-<slug>/`), а не одним
раздувающимся файлом-хроникой. `STATE.md` — максимум таблица-индекс «ветка → статус → куда идти», без
воспроизведения содержимого; трейс (`_log/`) — одноразовый след сессии со сроком жизни (сжатие/архивация по
факту, не бесконечный рост), связанный с state ссылкой `handoff:`, а не наоборот.
