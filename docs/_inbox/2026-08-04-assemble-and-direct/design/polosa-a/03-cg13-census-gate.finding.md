# CG-13 — census-gate (R-b) сегодня проза; план нарушает свой же запрет prose-only-gate

## A. Дословно: правило §43-45 + место прозы-гейта

**Плановое правило (запрет prose-only), `docs/_inbox/2026-08-04-assemble-and-direct/design/01-execution-plan.synthesis.md:43-45`:**
> «**Anti-rot corollary (red-team KILL-SHOT 2 — no gate ships as prose-only):** every gate in this plan is
> paired with a **generator-level check**, never a prose convention. Prose gates are exactly what rotted 4/5
> `00-states` tracks as `active`. See the enforcement column in §4.»

**Место, где census-gate (R-b) сам нарушает это правило** — правило заведено в
`docs/01-organization/doc-discipline/growth-and-sequencing/CONVENTION-movement-and-selfcheck.md:26-29`:
> «**R-b Нет входа в «строй» без ПЕРЕПИСИ ШИРИНЫ.** Для сущности ТЕКУЩЕЙ ветки перечислены ВСЕ её грани;
> каждая либо закрыта веткой, либо явно отложена с домом (задача+дом). **Пустая незаявленная грань = блок.**
> Гейт ПОВЕТОЧНЫЙ (по сущности ветки), не глобальный. Пока нет generator-check (это долг D0, параллель
> гейту D0), держится РУЧНОЙ переписью в ревью — но цель машинная (иначе гейт-прозой, что мы и чиним).»

И тот же гейт прозой описан в органе переписи, `.../design/02-coverage-gate.synthesis.md:95-106`:
> «**R-b — census-gates-build, ПОВЕТОЧНО.** Ветка не переходит в «строй», пока для СУЩНОСТИ ЭТОЙ ВЕТКИ
> матрица держит P0/P1-строку в `⬜`/`UNCLAIMED` без одного из трёх: (a) задачи, **принятой карточкой
> ветки-дома**... (b) промоции в owner-fork...; (c) явной датированной пометки «отложено, риск принят
> владельцем».» ...
> «Статус на 2026-08-05: все CG-* **посеяны как задачи**..., но ещё **НЕ поглощены карточками веток** →
> критерий (a) формально не закрыт. Сам этот гейт пока проза — его машинизация = задача **CG-13**...»

Итого: план запрещает себе prose-only gates (§43-45), но сам R-b/census-gate — ровно такой gate: правило
и критерий приёмки существуют только как текст, который держится «ручной переписью в ревью» (сам файл это
признаёт открытым текстом).

## B. Что ассёртить — минимальный первый срез

Не проектирую под схему root-пульта CG-12 (со-оркестратор §3: мягкая цепь И2→И3, харвест сводит). Первый
срез читает НАПРЯМУЮ два существующих файла:
- `docs/00-states/05-assemble-and-direct/_shared/task-pool.md` (таблица «Индекс»: id · ветка/план · приор · статус)
- `docs/_inbox/2026-08-04-assemble-and-direct/design/02-coverage-gate.synthesis.md` (таблица «Задачи,
  посеянные пустыми/ложными клетками»: id · приоритет · клетка · дом-ветка-куда)

**Ассёрт (fail-closed):** для каждой строки `CG-*` в coverage-gate.synthesis.md с приоритетом P0 или P1 —
проверить, что id либо (a) есть отдельной строкой в task-pool.md `Индекс`, либо (b) явно перечислен ВНУТРИ
текста существующей task-pool-задачи (пример: `T-plan-honesty` дословно перечисляет «CG-11 DV-коллизия ·
CG-12 генератор D0 · CG-13 гейт-прозой» — `task-pool.md:41`), либо (c) промотирован в owner-fork (§6
execution-plan) с явной датированной пометкой. Если ни (a), ни (b), ни (c) — **FAIL**, печатает id +
приоритет + «клетка» (пустая незаявленная грань = блок, R-b дословно).

**Проверка на реальных данных прямо сейчас (не синтетика):** P1-строки `CG-02, CG-03, CG-05, CG-06, CG-07`
(`02-coverage-gate.synthesis.md:80-93`) НЕ встречаются ни отдельной строкой, ни внутри текста ни одной
задачи в `task-pool.md`. Значит, если бы generator-check уже существовал, он бы **упал СЕЙЧАС** на этих
пяти — что и подтверждает открытым текстом сам coverage-gate-файл («критерий (a) формально не закрыт»,
`02-coverage-gate.synthesis.md:105`). Это одновременно доказательство, что ассёрт не вакуумный (есть на чём
падать), и живой acceptance-тест для реализации.

## D. Заметка общего дома с И2

И2 (CG-12) и И3 (CG-13) оба указывают на `tools/lint/doc-tree.mjs` как естественную точку расширения:
И2 чинит «root `STATE.md` не генерируется» (`01-execution-plan.synthesis.md:119` врёт про существующий
генератор), И3 чинит «R-b не машинизирован». **Это ОДНА точка расширения, не два независимых генератора**
(закон 2 doc-tree.md — «один дом на тему»; `00-coorch-framing.md:79-82` называет тот же риск явно). Харвест
должен решить: (i) один скрипт с двумя режимами (`--pult` для CG-12, `--census` для CG-13), (ii) один модуль
с двумя entry-точками, или (iii) осознанно два файла в `tools/lint/`, если логика слишком разная (root-пульт
= генерация карточки; census-check = линт существующих таблиц) — но решение должно быть явным, не default.
Не проектирую сам выбор — это харвест-решение, не diagnostic И3.

## E. Риски для критика

1. **Парсинг markdown-таблиц регэкспом хрупок.** Обе таблицы (`task-pool.md`, `02-coverage-gate.synthesis.md`)
   меняют форму от сессии к сессии (видно по различию колонок между ними). Первый срез скрипта должен
   зафиксировать ожидаемый формат заголовка таблицы и явно падать (не молча пропускать строки) при
   несовпадении — иначе тихий false-green хуже, чем отсутствие гейта (rider R2 плана, §37-39, применим не
   только к durable-store meter, но и к любому derived-статусу).
2. **Критерий (b) («упомянут внутри текста существующей задачи») — субстринг-мэтч, размыт.** CG-11/12/13 в
   `T-plan-honesty` совпадают по буквальному id в тексте — повезло. Не гарантировано для будущих CG-*.
   Нужна либо явная конвенция (каждая task-pool-задача, поглощающая CG-id, перечисляет id списком в
   отдельном поле фронтматтера/строке), либо v1 принимает риск и требует ручной ревью при добавлении новых
   CG-строк (не полностью машинный).
3. **Первый срез — диагностика, НЕ жёсткий блокер.** Скрипт печатает FAIL, но никуда не подключён
   (pre-commit/CI) в этом патче — значит R-b формально всё ещё держится ручной переписью в ревью, только
   с machine-assisted подсказкой. Это САМО по себе пустая незаявленная грань под R-b (диагностика без
   крючка — тот же паттерн прозы-с-виду-механизма, который CG-13 и чинит), поэтому не оставлена сноской —
   заведена как явная follow-up задача с домом+owner в §C (`T-census-check-ci`), не молчаливый риск.
4. **Циркулярность — проверено, НЕ падает на себе сейчас.** CG-13 уже поглощена критерием (b): текст
   `T-plan-honesty` (`task-pool.md:41`) буквально содержит подстроку «CG-13» («CG-11 DV-коллизия · CG-12
   генератор D0 · CG-13 гейт-прозой»). Скрипт при первом запуске на СЕГОДНЯШНИХ данных найдёт CG-13
   поглощённой и НЕ упадёт на себе (см. §B, §F — прогон должен дать ровно 5 фейлов: CG-02/03/05/06/07).
   Остаточный риск — только будущий: если T-plan-honesty когда-нибудь переформулируют без буквальной
   подстроки «CG-13», скрипт перестанет видеть поглощение задним числом — это покрыто риском §E2
   (subsrting-match хрупок), отдельно заводить не нужно.
5. **Зависимость от И2 не строгая, но реальная.** Если И2 решит, что root-пульт-генератор ДОЛЖЕН стать
   единственным источником статусов карточек (заменив task-pool.md как canonical), скрипт CG-13 придётся
   переписать на чтение пульта вместо task-pool.md напрямую — это ре-ворк, не catastrophic, но нужно назвать
   на харвесте явно (co-orch framing уже предупредил, `00-coorch-framing.md:75-78`).
