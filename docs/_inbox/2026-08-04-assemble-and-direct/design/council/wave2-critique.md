# Final red team — wave-2 reconciled plan

> Verdict: **SURVIVES-WITH-FIXES.** The reconciliation is unusually disciplined — it correctly resolves
> the two cruxes, keeps the risk lens's non-compaction argument, and the engineering lens's file-coupling
> argument, without hand-waving them away. It fails one specific place: it under-sizes its own keystone
> deliverable (D1.c) and, ironically, ships that keystone as a one-time DECLARED event rather than a
> standing DERIVED gate — the exact pathology it names as the root cause of everything else.

## Attack 1 — Is the "thin vertical slice" actually thin?

No. D1.c's gate ("Vitality has >0 code; status card auto-derived from run; one 'agent acted on memory'
trace exists," line 128) quietly bundles at least three pieces of **net-new** infrastructure that the
fact-base states are currently **0 lines of code**: (a) a Vitality/usage observer — no spec for what a
"liveness reading" is, what triggers it, how it distinguishes a real run from a test run; (b) a
status-card schema + write path — nothing in the codebase today lets a code run mutate a
`docs/00-states/*/state.md` card, so this is a new docs↔code bridge, with no concurrency story for
multiple teams writing cards; (c) wiring `balance-observer`'s output through that bridge. Compare this to
D1.a/D1.b, which both cite exact files and exact existing mechanisms to reuse (`resolve()` already exists,
`store-durable-fs` already exists) — D1.c cites nothing to reuse because nothing exists to reuse. The
blind-spot lens itself flagged this honestly in its own caveats section ("auto-derived status needs a
minimal observer to exist... that is small but non-zero work and must be named as the slice's true first
brick") — the reconciler kept the content item but dropped the warning tone, turning a flagged risk into
a routine numbered step. **This is the plan's single largest concealed cost**, sitting exactly at the
milestone the whole reframe's rhetorical payoff depends on ("first time green means something").

## Attack 2 — The A-before-B law (PEP-door before durable)

The engineering argument holds (testing durability of a bypassed path proves nothing about the
access-control invariant it's meant to certify) and the risk argument compounds it correctly (durable
never compacts, so don't journal an unfixed bug permanently). No case found where doing them together is
cheaper *in substance* — they touch different files (`lens/*` vs `cli.ts`), so "together" would only save
review ceremony, not engineering risk.

However, there is an internal **contradiction** in the plan's own sequencing: §4.1's table says D1.b's
only dependency is D1.a ("after D1.a"), but §4.3 says "Wave 2 (strict seq, after **D1.a green + D0
landed** + fact-base re-verified): D1.b → D1.c" — bundling D0 into D1.b's gate when the table explicitly
scopes D0 as a dependency of D1.c only ("after D1.b **and** D0"). If D0 slips, this ambiguity could stall
D1.b for no technical reason. Minor but real — a plan whose whole thesis is "derive, don't hand-wave" should
not itself contain a hand-wavy edge.

## Attack 3 — What did the reconciler drop from wave-1?

1. **Value lens: "no named human beneficiary for ga-rentacar... well-documented fiction" risk.** Completely
   absent from the reconciled plan. The cross-exam table captures "zero acceptance evidence memory changes
   agent behavior" but not this sharper, harder claim — that nobody who runs a rental-car business has ever
   looked at the output. D1.c's "trace exists" gate does not touch this; a trace can exist and still be
   fiction if no real user ever consumes it.
2. **Process lens: the concrete anti-rot mechanism for the generated-view law.** Process lens specified
   *how* to keep `STATE.md` from re-rotting: teams edit only their own card frontmatter, root `STATE.md` is
   generated by reusing the existing `tools/lint/doc-tree.mjs` generator. The reconciled plan keeps the
   label ("generated index," §4.0/§4.1) but drops the concrete mechanism and the tool-reuse pointer — so a
   future team could still hand-edit the root file and nobody would notice the law was dropped.
3. **Process lens Q4: sweep isolation ("own commit/branch, status-edits + new index files only").** D5's
   description keeps the `cwd`-audit gate but drops the "own commit/branch" isolation instruction, which
   was the concrete answer to "how do we sweep a dirty tree without git-working-tree-safety violations."
4. **Value lens Q4: sweep `_inbox/values-v2/` specifically into S-D's cleanup.** Folded generically into "doc-discipline debt sweep" (D5) but not named — low-severity, content-value pile could still get missed.

None of these are fatal alone, but #1 and #2 are exactly the kind of finding whose absence lets the plan's
own success criteria be gamed later (a trace with no real user; a generated view that quietly reverts to
hand-maintained).

## Attack 4 — Parallelism: file-safe or team-safe?

File-level: checked. D1.a (`packages/ingest-rentacar/src/lens/*`), D0 (`docs/00-states/` root +
`05-assemble-and-direct/`), D4 (external repo, zero overlap), D2-canon-cleanup (docs-only), D5-prep
(read-only audits + snapshot). No literal file collisions found — the engineering lens's file-coupling
table was carried forward correctly and the reconciler didn't introduce a new overlap.

Team/logical-level: one real gap. D0's deliverable is "4 branches registered as cards" with a fixed schema
(id·theme·status·gate·home·handoff·value-checkpoint·fork?) — but nothing in the plan assigns who creates
the actual `state.md` skeleton files at D1's `00-states/06-substrate-slice/`, D2's `07-substrate-core/`,
D3's `08-agent-layer/`. If D0's team pre-creates them while D1/D2 teams are independently starting code
work in the *same* wave, there's no file collision, but there is an **ownership ambiguity** that could
produce two divergent ideas of the schema before D0 "lands." Not a kill-shot — self-correcting, cheap to
fix — but the plan should name an owner for the skeleton-creation step.

Secondary nitpick: D4's gate reads "no new agents until D1.a (E2)" — ambiguous whether this blocks D4
*starting* (fixing dup/restart bugs, which adds no new agents) or only blocks *adding new agents*. As
written it risks a team reading it as "don't touch D4 yet," stalling a track the engineering lens proved
has zero coupling and should start immediately.

## Attack 5 — Is the plan itself DECLARED, not DERIVED?

Partially, and this is the sharpest finding. The plan's "done means" block (lines 77–81) is a genuine
attempt at a derived gate — a real run, through the door, on durable storage, producing a status. Good.
But it is a **one-time verification event**, not a **standing structural gate**. Nothing in D1 makes it
*impossible* to reintroduce a `graph.byId` bypass in a future lens — there's no lint rule, no architecture
test, no type-level seal forbidding direct `graph.byId` access outside `resolve()`. The plan proves the
invariant once and then relies on the same "declare it and hope" discipline that produced the original M2
overclaim. Likewise, D0's "harvest/close gate documented as a RULE" is, on its own admission, words on a
page — process lens itself warned "it must be a rule, not a column nobody fills," but the reconciled plan
doesn't pair the rule with a generator check (e.g., "card `status:active` + unchanged >N days → flagged in
the generated view") that would make staleness *derived* rather than *self-reported*. The fix for the
disease (four rotted `00-states/0N` tracks that already had a written convention and rotted anyway) is
prescribed using the same mechanism (a written convention) that already failed once. This is not fatal —
it's a phase-1 gap that a phase-2 lint rule can close cheaply — but it is a real recurrence of the
diagnosed pathology inside the cure.

## Attack 6 — Single biggest reason this plan fails in execution

**Convergence risk at D1.c.** The plan carefully de-risks every step up to D1.b (existing mechanisms,
named files, clear owners) and then asks D1.c — the one milestone the entire "first true green" narrative
depends on — to simultaneously land five different pieces of net-new or fragile work with no single owner
and no size estimate: a new Vitality observer, a stable D0 card schema, a working D1.b durable path, a
dist/src parity checker, and a same-as guard proof-by-real-replay. Every other step in this plan has a
reuse pointer; D1.c has none. If it slips, the plan's rhetorical payoff ("green finally means something")
slips with it, and the team is left exactly where it started — with declared, not derived, status — just
one layer deeper.

## What survives clean

- The A-before-B ordering law itself (PEP before durable) — correctly derived from two independent lenses,
  no real counter-case found.
- The file-coupling analysis (D1.a co-owned with S-B, Fix-β sequenced after) — verified against the
  engineering lens's own greps, nothing contradicts it.
- FORK-2/FORK-3 (PII/erasure gating durable-adoption of PII payloads) — correctly kept as an owner
  decision, not silently resolved either direction.
- The non-compaction argument (risk lens) as the reason ordering is a hard edge — carried forward intact
  and correctly used to justify the strict D1.a→D1.b→D1.c sequence.
