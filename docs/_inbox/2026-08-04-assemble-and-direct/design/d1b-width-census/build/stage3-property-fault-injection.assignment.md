# Этап 3 — §9-4: durable-плоскость выживает частичную порчу журнала, проверено НЕЗАВИСИМЫМ byte-oracle

> Кейстоун D1.b доказывает: ставка «граф растёт без миграций» держится на durable append-only журнале.
> §9-1..§9-3b (Этапы 1-2) закрыли: граница writeAct→hydrate, erasure-on-disk, edges⟂payload, same-as, F6.
> §9-4 — СЛЕДУЮЩАЯ грань: журнал на диске должен ВЫЖИВАТЬ частичную порчу/усечение (crash mid-write,
> обрезанная последняя строка, битый байт), и это надо проверять **независимым byte-oracle**, а НЕ через
> `project()`/`hydrateFromDisk` (иначе тавтология — той же природы, что §9-3 «edges целы по типу»).

---

## 0. ⚠️ Разведка — реальное состояние кода СЕЙЧАС (читал, не census)

Census (`00-width-census.synthesis.md:56`) описывает §9-4 так: *«`crash-mid-turn.test.ts:119` hand-picked
offset; oracle переиспользует ту же parse-цепочку что и `hydrateFromDisk`»*. **Подтверждено чтением, и
уточнено — дыра шире, чем одна строка.** Три реальных факта:

### 0.1 Реально устойчиво (не трогать, это работает)
- **Торн последней строки** (crash mid-append, без завершающего `\n`): `hydrateFromDisk`
  (`store-durable-fs.ts:171-188`) читает файл, `raw.split('\n')`, на строке, которая не парсится —
  `catch { break }` (`:182-184`). Последняя торн-строка отбрасывается, ранние целы. Один hand-picked
  случай ЗЕЛЁН и покрыт: `crash-mid-turn.test.ts:106-140` (`appendFileSync(... 'act:torn-C', ...)`
  усечённый JSON без `\n`, ассерт `actIds == ['act:clean-A','act:clean-B']`). fsync-путь тоже доказан
  (`crash-mid-turn.test.ts:80-104`, real SIGKILL, `foundA`, `totalA==111`).
- Torn/непарсящаяся строка НЕ роняет boot целиком: `catch` ловит, процесс поднимается.

### 0.2 Реальная ДЫРА §9-4 (то, что доказать)
1. **Порча в СЕРЕДИНЕ файла → тихое усечение всего хвоста.** `hydrateFromDisk:184` делает `break`, а не
   `continue`. Значит: битый байт в строке 2 из 5 → строки 2,3,4,5 ВСЕ теряются молча. Контракт C3
   (`store-durable-fs.ts:19`) обещает падучесть только для *«torn LAST line»*; порча интерьера —
   не определена и НЕ протестирована. Это ГЛАВНАЯ грань §9-4: свойство должно перебрать порчу по ВСЕМУ
   диапазону смещений, не по одному ручному offset.
2. **Нет НЕЗАВИСИМОГО oracle нигде.** Единственная проверка порчи (`crash-mid-turn.test.ts`) верифицирует,
   поднимая `DurableFsStore` и читая `acts()`/`readNode` — т.е. через тот же `hydrateFromDisk`+`project`
   (`crash-harness.ts:82-102`, ветка `--verify`). «Правда» = руками захардкоженные `actIds` для ОДНОГО
   фикстура. Если бы `hydrateFromDisk` тихо ел хорошую строку или оставлял битую — тот же баговый путь
   использовался бы для «проверки» и не поймал бы дефект. Это и есть тавтология, которую §9-4 снимает.
3. **Latent (вторичный) — граница durability = «JSON распарсился», а НЕ «строка завершена `\n`».**
   `hydrateFromDisk` парсит сегмент `raw.split('\n')`; если торн-хвост случайно оказался валидным JSON,
   он будет ПРИНЯТ как настоящий акт (нет проверки, что за строкой стоит `\n`). Для JSON-объектов префикс
   почти всегда невалиден → на практике редко, но это реальная слабость контракта, которую независимый
   byte-oracle (правило «строка durable только с завершающим `\n`») ОБНАЖАЕТ. Зафиксировать как находку.

### 0.3 Инструментарий, который УЖЕ есть (переиспользовать, не плодить)
- Cross-process дисциплина: `crash-mid-turn.test.ts:31-34` (`runProcess` = `spawnSync tsx harness`),
  harness `crash-harness.ts` с режимами `--write-clean` (2 fsync'd акта, `:72-81`), `--verify` (эмитит
  `{booted, actIds, actsLen, foundA, totalA, ...}`, `:82-112`). **`--verify` уже отдаёт `actIds` —
  готовый «что движок восстановил».**
- `deadPid()` / orphan-lock хелперы (`crash-mid-turn.test.ts:42-46,122`).
- Прецедент независимого before-snapshot и обязательного мутанта — Этап 2:
  `erasure-plane-harness.ts:98-103` (мутант монки-патчем `actToLine` в ЭТОМ процессе, не правит боевой файл)
  и `erasure-plane-falsify.test.ts` (мутант как обязательный `it(...)`, красный вывод в acceptance).
- `fast-check`/property-либы в проекте НЕТ (grep по всем `package.json` — 0). Property-перебор писать
  вручную: сид-RNG + N сэмплов смещений (или полный перебор для короткого журнала). Не тянуть новую зависимость.

## 1. Что построить

Цель: доказать, что для journal.jsonl из N настоящих fsync'd актов durable-плоскость под ЛЮБОЙ порчей
хвоста восстанавливает РОВНО тот набор актов, который НЕЗАВИСИМЫЙ byte-oracle объявил уцелевшим — без
краша, без выдуманного акта, без частичного акта. Три компонента.

### 1.1 Property-based генератор порчи (в ТЕСТ-процессе, над сырым файлом)
Детерминированный (сид-RNG, чтобы падение воспроизводилось — печатать сид в assert-сообщении). Каждый
кейс порчи — одна из мутаций сырых байт journal.jsonl ПОСЛЕ того, как P1 честно записал N актов и вышел:

- **M1 truncate-at-offset (ГЛАВНАЯ — физически реальный crash mid-write):** обрезать файл на случайном
  байтовом смещении `k ∈ [0, len]`. Перебрать много `k` (сэмпл ≥ ~50, или полный перебор для короткого
  журнала). Это даёт богатое пространство: `k` попадает и на границу `\n` (чистая потеря хвоста), и в
  середину строки (торн-хвост).
- **M2 drop-last-complete-line:** удалить последнюю завершённую строку целиком (файл валиден, N−1 строк).
- **M3 flip-byte-in-last-line:** испортить один байт в ПОСЛЕДНЕЙ строке (торн-хвост, но не усечение).
- **M4 flip-byte-in-INTERIOR-line (адверсариал — бьёт `break`, §0.2 п.1):** испортить байт во внутренней
  строке (не последней). Это зонд на тихое усечение хвоста.

Мутации — чистые операции над `Buffer`/строкой сырого файла (`readFileSync`/`writeFileSync`), НЕ через
адаптер. НЕ править `store-durable-fs.ts` под §9-4 (см. §3 крючок).

### 1.2 НЕЗАВИСИМЫЙ byte-oracle (сердце этапа)
Отдельная функция (напр. `test/oracle/journal-survivors.ts`), которая по СЫРЫМ байтам испорченного файла
вычисляет множество `id` актов, которые ОБЯЗАНЫ уцелеть — **не вызывая ни `lineToAct`, ни `project`, ни
`hydrateFromDisk`, ни `splitAct`/`foldInto`** (импорт из `store-durable-fs.ts`/`projection.ts` в oracle =
провал независимости).

Правило oracle (кодирует ЧЕСТНЫЙ append-only контракт, независимо от движка):
1. Durable-префикс = байты до последнего `\n` включительно. Всё после последнего `\n` — недописанный
   хвост, НЕ durable (строка durable только когда её завершающий `\n` на диске — правило §0.2 п.3).
2. Разбить префикс по `\n`; для каждого непустого сегмента — СОБСТВЕННЫЙ `JSON.parse` (примитив языка;
   тавтология census про `lineToAct`/`project`/`break`-логику, а не про `JSON.parse`). Взять `.id`.
3. При первом сегменте, который НЕ парсится (порча интерьера) — oracle объявляет контракт явно и
   ЕДИНОЖДЫ: append-only-движок доверяет журналу только ДО первой порчи → уцелевшие = валидные `id` строго
   ДО первого битого сегмента. (Это фиксирует текущий контракт `break`; см. §2 — движок ОБЯЗАН совпасть,
   а расхождение = находка, не молчаливый провал.)
4. Вернуть упорядоченное множество `id` + флаг «была ли обнаружена порча интерьера».

Oracle читает только `id` (top-level meta и в split-, и в legacy-строке — не нужно понимать
`erasable`/payload). Держать oracle ~40-60 строк, чистый, без импорта движка.

### 1.3 Cross-process прогон + сравнение
По дисциплине `crash-mid-turn.test.ts` (spawn дочернего процесса, ничего общего кроме store-dir):
1. **P1** (новый процесс через harness): пишет N настоящих fsync'd актов РАЗНОЙ длины (варьируй payload,
   чтобы `\n`-границы стояли на разных смещениях → богаче M1). Выходит 0 (лок отпущен).
2. **Тест-процесс:** для каждого кейса порчи — копирует чистый journal.jsonl → применяет мутацию (§1.1) →
   вычисляет `expected = oracle(коррумпированные_байты)` (§1.2).
3. **P2** (свежий процесс, `--verify`): поднимает `DurableFsStore` над испорченным store-dir, эмитит
   `{booted, actIds}` (ветка уже есть — `crash-harness.ts:82-112`).
4. **Ассерт:** `P2.booted === true` (не крашнулся) И `sort(P2.actIds) === sort(expected)` (движок
   восстановил РОВНО oracle-множество — не меньше, не больше, без частичного/битого акта). Сид/offset —
   в сообщении ассерта, чтобы падение воспроизводилось.

**Harness:** РАСШИРИТЬ существующий `crash-harness.ts` режимом `--write-series` (уложить N≥4 fsync'd
актов варьируемой длины, эмитнуть их `id` по порядку), НЕ плодить новый harness-файл (правило cap, §3).
`--verify` переиспользовать как есть.

### 1.4 Мутант движка (обязателен как часть acceptance)
Свойство «падуче» только если под сломанным движком оно КРАСНЕЕТ. Мутант = сломанный вариант разбора,
внедрённый в ЭТОМ процессе монки-патчем (по прецеденту `erasure-plane-harness.ts:98-103`), НЕ правкой
боевого `store-durable-fs.ts`. Выбрать мутант, однозначно НЕВЕРНЫЙ против oracle:

- **Мутант-A (рекоменд.): «оставляет торн-хвост».** Патч `hydrateFromDisk`/`lineToAct` так, чтобы
  недописанный хвостовой сегмент (после последнего `\n`) принимался как акт (напр. без `break`, лениво
  коерсит). Под M1/M3 движок выдаст акт, которого oracle (правило «только завершённые `\n`») НЕ ждёт →
  `actIds` ⊋ expected → ассерт КРАСНЫЙ.
- (Альтернатива для M4: мутант, который `continue` вместо `break` — восстановит хвост ПОСЛЕ порчи, больше
  oracle-контракта → тоже красный. Использовать, если хочешь зонд именно на интерьер.)

Прогнать мутант как обязательный `it(...)`, ПОКАЗАТЬ красный вывод в handoff (не «должен упасть по логике»).

## 2. Acceptance (фальсифицируемый чек-лист)

- [ ] Есть НЕЗАВИСИМЫЙ byte-oracle (§1.2): читает сырые байты, СВОЙ `JSON.parse`, НЕ импортирует
      `lineToAct`/`project`/`hydrateFromDisk`/`splitAct`/`foldInto` (проверяемо грепом импортов в oracle-файле).
- [ ] Property-генератор перебирает M1 truncate-at-offset по ≥50 сэмплам (или полный перебор короткого
      журнала), плюс M2/M3/M4 — детерминированно (сид печатается при падении).
- [ ] Для каждого кейса: `P2.booted===true` И `sort(actIds) === sort(oracle_expected)` — движок
      восстановил РОВНО oracle-множество (не меньше/не больше/без частичного акта).
- [ ] M4 (порча интерьера) прогнан явно: зафиксировано поведение (движок = oracle-контракт «до первой
      порчи»); ЛЮБОЕ расхождение (краш, лишний/битый акт, потеря валидной строки до порчи) — репортится
      как находка, НЕ замазывается.
- [ ] Мутант движка (§1.4) прогнан как обязательный `it(...)` и ПАДАЕТ против того же oracle-ассерта;
      красный вывод вложен в handoff. Зелёный тест под мутантом = переписывать ассерт, а не мутант.
- [ ] Cross-process: порча применяется к файлу на диске в тест-процессе, восстановление — в ОТДЕЛЬНОМ
      P2 (`spawnSync`), ничего общего кроме store-dir. НЕ same-process симуляция.
- [ ] Boot ни на одном кейсе порчи не бросает необработанно (torn/битьё → `booted:true` с усечённым
      набором, а не исключение наружу).
- [ ] Численный cap соблюдён (§3). Продакшн-код (`store-durable-fs.ts`) НЕ изменён (§9-4 — это тест+oracle
      поверх существующего hydrate; если правишь hydrate — стоп, эскалируй, см. §3).

## 3. Крючки самопроверки (I7) + численный cap

- **Независимость oracle — грепни сам.** Прежде чем звать oracle «независимым»: `grep -n "import"` по
  oracle-файлу — ноль импортов из `store-durable-fs`/`projection`/`erasure`/движка. Если тянешь оттуда
  хоть парс-функцию — это НЕ oracle, это та же цепочка (тавтология census). `JSON.parse` — единственный
  разрешённый общий примитив.
- **Мутант ПЕРЕД «падуче».** Обязательно прогнать ассерт под мутантом (§1.4) и вложить КРАСНЫЙ вывод в
  handoff. Не полагаться на «должен упасть по логике».
- **Не чинить движок под тест.** Если ловишь себя на правке `hydrateFromDisk` (`break`→`continue`,
  проверка `\n`-границы и т.п.), чтобы свойство позеленело — **СТОП.** §9-4 ПИНИТ текущее поведение
  независимым oracle и репортит расхождения; смена recovery-политики hydrate (skip-and-continue,
  newline-boundary durability) — ОТДЕЛЬНАЯ грань/контракт (владелец решает), не тащить сюда молча.
- **Не тянуть новую зависимость.** Property-перебор — руками (сид-RNG + цикл смещений). `fast-check` в
  проекте нет; не добавлять ради этого.
- **Один harness, не россыпь.** Расширить `crash-harness.ts` (`--write-series`), НЕ создавать новый
  harness-файл, если не доказана необходимость.
- **Численный cap (эта грань ДЕШЕВЛЕ Этапа 2 — продакшн-код не трогаем):**
  ориентир ~2 файла + 1 расширение harness · ~120-180 строк теста · ~40-60 строк oracle · ~25-40 строк
  расширения harness. **0 строк продакшн-адаптера** (иначе см. крючок выше). Вышел за пределы —
  эскалируй лиду, не раздувай молча.

## 4. Риски + что НЕ тянуть

1. **Соблазн «починить» тихое усечение хвоста (M4).** `break` на первой битой строке — возможно, это
   слабость, но её ИСПРАВЛЕНИЕ — смена контракта recovery, отдельная грань. §9-4 её только ОБНАЖАЕТ
   независимым oracle и репортит; не чинить в этом этапе.
2. **F3 (WAL / атомарность / порядок durability) — СОСЕДНЯЯ грань, НЕ сюда.** §9-4 = устойчивость ЧТЕНИЯ
   к уже-испорченному файлу. F3 = атомарность ЗАПИСИ/шреда (`store-durable-fs.ts:221-224` явно DEFER'ит
   WAL-order). Не проектировать fsync-порядок/WAL под видом fault-injection. (`T-D1b-durability-order-contract`.)
3. **Blob/by-ref PII (грань №3 Этапа 2, `T-D1b-shred-by-ref-pii`) — НЕ сюда.** §9-4 — про журнал-строки,
   не про payload-blob-стор.
4. **Cascade/supersede (F5/FORK-2) — НЕ сюда.**
5. **Тавтология-рецидив: oracle, который «умный».** Риск, что oracle начнёт воспроизводить логику
   `hydrateFromDisk` (тот же `break`, тот же split-skip-empty) «чтобы совпало». Тогда совпадение движка и
   oracle пусто. Держать oracle на НЕЗАВИСИМОМ правиле (durable = завершённая `\n`-строка, валидный JSON),
   а не «делать как движок». Если приходится копировать движок, чтобы позеленело — это находка о движке,
   не повод копировать.
6. **Property-флейки.** Недетерминированный RNG → мигающий тест. Сид фиксировать и печатать; падение
   должно воспроизводиться одним сидом/offset.
7. **Форма акта.** §9-4 form-agnostic (oracle читает только `id`) → синтетических актов harness'а
   достаточно; тащить реальный ga-rentacar путь (как Этап 2) НЕ обязательно (нет payload-семантики в
   игре). Если берёшь реальные акты — только ради разной длины строк, не ради семантики.
