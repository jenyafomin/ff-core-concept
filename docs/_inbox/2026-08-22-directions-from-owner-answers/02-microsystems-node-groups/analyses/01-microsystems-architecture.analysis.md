# D2 · Микросистемы — архитектурный разбор

## 1. ЧТО такое «микросистема» в терминах движка

**Определение.** Микросистема = **именованная переиспользуемая композиция трёх вещей**: (а) набор
**типов** (`node-type`/`edge-type` — строки реестра M-G3), (б) одна+ **линза** (`ViewDef`, `types.ts:190`),
через которую «системы понимают, как взаимодействовать», (в) один+ **policy-узел**, который группа несёт
при себе (`governed-by`, M-G3). Это НЕ новый примитив движка — это **паттерн композиции поверх уже
существующего субстрата** (`EnvelopeNode` `types.ts:122` + типизированные `Edge` `types.ts:32`).

**Ключевой раскол (ответ на «крепить к ТИПУ или к ДАННЫМ»)** — это **class ↔ instance**, не два соперника:
- **Type-bound (КИТ / пакет-определение):** живёт в реестре типов как манифест-строка, ссылающаяся на
  свои `type-def`+`view-def`+`policy`. Переиспользуется = инстанцируешь его типы где угодно. Как класс.
- **Data-bound (СБОРКА / инстанс):** конкретный подграф реальных узлов, связанных ребром членства.
  Переиспользуется = клонируешь/шаблонируешь сборку. Как объект.
Связь между ними — ребро `instance-of`. **Обе «разновидности владельца» — два конца одного отношения
инстанцирования**, а не альтернативы.

**Границы. ВНУТРИ:** манифест-узел, набор type-def, view-def(ы), policy-узлы, контракт членства (по типу
ИЛИ по ребру). **СНАРУЖИ:** доменный payload узлов (`body`), ядро движка, tenant-словарь предикатов
(`predicates.ts:44`, ядро знает 0 доменных нунов — G1).

## 2. Механизмы реализации (2–4, за/против)

**M1 · Именованный набор типов (кит) в M-G3.** Микросистема = манифест `type-def`, ребром `bundles`
собирающий свои node-type/edge-type/view-def/policy. Attach-to-TYPE.
- *За:* рост INSERT-ом, не миграцией (канон M-G3); self-hosting; портируемо (Ц5); гейт типов гасит
  свалку синонимов. *Против:* задаёт только ФОРМУ, не живой инстанс; нужен шаг инстанцирования; риск —
  кит дублирует policy → второй источник истины.

**M2 · View-шаблон (линза над подграфом).** Микросистема = `ViewDef` (`from`/`traverse` выбирает группу);
«система понимает как взаимодействовать» = скомпилированная линза (`view-compiler.ts:205`). Прецедент в
коде реален. Attach-to-TYPE или -DATA (через `from:{type}` vs `from:id`).
- *За:* read-переиспользование уже доказано (`day-mirror.ts:50`); нулевой новый примитив; линза
  портируется строкой-данными. *Против:* `ViewDef.kind` ЗАМОРОЖЕН на 3 граф-линзы (`types.ts:192`) —
  групп-линза либо едет side-journal-ом как day-mirror (не граф-узел), либо требует открыть enum; линза
  read-only, правил не несёт.

**M3 · Сборка через ребро членства (data-instance).** Инстанс = узел `microsystem-instance` + рёбра
`member-of` от участников. «Системы понимают» = обходят `member-of`. Attach-to-DATA.
- *За:* рёбра-как-память первого класса (Ц6); живая группа, может затухать/консолидироваться (D3);
  reuse клонированием. *Против:* ссылочная целостность — сироты-рёбра при стирании участника; кардинальность
  `member-of` обязана быть ДАННЫМИ (`predicates.ts`); тождество инстанса при merge/split (Ц2).

**M4 · Группа, несущая правила (policy_ref / governed-by).** Owner: «узлы КЛЮЧЕВЫ для наполнения правил».
Член крепит правило `policy_ref[]` (узел→policy, доказано в `view-compiler.ts:180` loopGuard) ИЛИ ребром
`governed-by` (M-G3). Два режима = policy на ТИП (все узлы типа X) vs на ДАННЫЕ (этот инстанс).
- *За:* переиспользование policy-as-data (D1); каскад через `refines`. *Против:* цена разрешения; конфликт
  type-level vs instance-level policy требует объявленного порядка каскада (M-G3: Конституция>policy>integrity).

**Рекомендация:** M1⊕M3 связкой `instance-of` (кит определяет → инстансы живут), M2 как линза-контракт,
M4 как способ крепления правил. Один концепт, две грани.

## 3. Зависимости

- **Реальный код:** `EnvelopeNode` `types.ts:122`; `Edge`(+provenance) `types.ts:32`; `PredicateRegistry`
  `types.ts:105` + tenant-инъекция `predicates.ts:44`; `ViewDef` `types.ts:190` + `compile` `view-compiler.ts:205`;
  крепление правила к данным `view-compiler.ts:180`; групп-линза-прецедент `day-mirror.ts:50`; идентичность
  инстанса через `source_ref` проекции `projection.ts` (`isProjectable`).
- **D1 (policy-as-data / M-G3):** кит регистрируется здесь; `type-def` подвиды node/edge/view-def; гейт типов.
  D2 БЕЗ D1 не строится.
- **D3 (витальность):** data-инстанс = живая единица → group-level decay/консолидация. Жизненный цикл
  инстансов берём из D3.

## 4. Открытые развилки для владельца

- **F1:** Микросистема — ОДИН концепт (кит ↔ инстансы через `instance-of`) или два раздельных механизма?
  (рекомендую: один, class/instance.)
- **F2:** Дом членства — по типу (неявно «все узлы типа X») vs явным ребром `member-of` vs маркером в body?
  (ребро = Ц6-честно, но цена целостности.)
- **F3:** Заводим ли первоклассный `node-type: microsystem` (манифест-узел) в M-G3, или это соглашение
  об именовании поверх существующих `type-def`?
- **F4:** Открываем ли замороженный `ViewDef.kind` под групп-линзу, или держим групп-линзы рукописными
  на surface (прецедент day-mirror), пока не доказано?
- **F5:** Приоритет крепления правил — когда type-level и instance-level policy применимы к одному члену,
  что побеждает? (нужен явный порядок каскада.)

## 5. Напряжения по 7 ценностям

- **Ц5 Суверенность (главное):** type-bound кит = кандидат-plug-in ТОЛЬКО если несёт свою схему+policy
  С СОБОЙ (манифест `bundles` type-def+view-def+policy). Риск: если policy кита ссылается на глобальную
  конституцию движка — не портируется в другой движок. Кит обязан быть самодостаточным.
- **Ц6 Реляционность:** data-членство держится на рёбрах → ребро обязано быть памятью первого ранга
  (свой id/паспорт/confidence/stale, `types.ts:32`), не служебной нитью. Каскад на сироты-рёбра при
  стирании участника; `member-of` кардинальность = данные.
- **Ц2 Тождество:** инстанс сам есть узел с идентичностью → merge/split правила действуют и на ГРУППУ;
  `canonical_id`/`source_ref` инстанса переживает re-type/слияние/раскол.
- **Кратко:** Ц3 — провенанс кита (кто автор пакета); Ц4 — group-level затухание (D3); Ц7 — микросистема,
  пересекающая референтов (`day-mirror.ts:29`), тянет consent-форму на членство.
